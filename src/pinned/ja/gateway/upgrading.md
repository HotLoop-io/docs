{{hotloop}} への道は6つあり、どれもまったく似ていません。4.22.1 からは、テーブルと列を3つ追加し、機器の状態確認のためにホストを読み取り専用でマウントするだけの `helm upgrade` なので、Pod Security プロファイルを確認してください。4.18.11 からも通常の `helm upgrade` ですが、稼働中のプラントの動作を変えるものが2つあるため、先にお読みください。4.18.10 からはデータベースエンジンが内部で入れ替わるので、その前に知っておく必要があります。4.17.0 からは通常の `helm upgrade` で、いくつかの既定値が変わっています。4.16.0 からは先に 4.17.0 を経由し、その後は新しい Secret がデータベースと同じくらいプラントのデータの一部になります。4.3.1 からは名前の変わったチャートであり、通常の `helm upgrade` では扱えず、途中で 4.16.0 と 4.17.0 を経由します。リリースノートは1段階ずつしか扱っておらず、リリースを飛ばす手順はどこにも載っていないため、このページもそれが動くとは約束しません。自分に当てはまる経路を見つけ、稼働中のプラントに手を付ける前に最後まで読んでください。

:::caution[4.20.2 以前から更新する場合: Basic256 を使う OPC UA クライアントが接続できなくなります]
4.21.0 では、アップグレードでも新規インストールでも `Basic128Rsa15` と `Basic256` が既定で無効になりました。サーバーはこの2つを一覧に出さず、名前で要求するクライアントを拒否します。お使いの OPC UA クライアント(Ignition の接続で確認できます)の中に `Basic256` より新しいものに対応していないものがないか確認し、そのクライアントを `Basic256Sha256` に移してください。移せない場合は `HOTLOOP_OPCUA_SERVER_ALLOW_DEPRECATED_POLICIES=true`(チャートでは `opcuaServer.allowDeprecatedPolicies: true`)で2つのポリシーを戻せ、サーバーは起動時にそのことを知らせます。4.21.0 では新しいテーブルを作るマイグレーション 0027 も加わりますが、それ以外は通常の `helm upgrade` です。リリース検証では 4.20.2 をマイグレーション後のスキーマで起動して動作を確認しているため、このテーブルがロールバックを危険にする理由にはなりません。
:::

:::note[古いチャートは URL で取得します]
チャートリポジトリのインデックスには Gateway のチャートが 4.16.0 まで残っているので `hotloop/hotloop --version 4.17.0` は解決され、パッケージは URL でも配信されます。以下の 4.16.0 と 4.17.0 のコマンドは `https://hotloop.io/hotloop/hotloop-4.17.0.tgz` のようにチャートを URL で指定しており、どちらの方法でも動作します。IoT と Edge は 4.18.10 から始まります。
:::

## 4.22.1 からのアップグレード

通常の `helm upgrade` で、機器にすでにあるものは何も変わりません。初回起動時にマイグレーションが3件実行され、どれも追加のみです。`0028_unifi_port_cycles`、`0029_energy`、`0030_energy_demand` です。4.22.1 で取ったバックアップはここで復元できますが、ここで取ったバックアップは古いリリースには復元できないため、戻る可能性があるなら先にバックアップを取ってください。

- **チャートが機器の状態確認のためにホストを読み取り専用でマウントするようになりました。** Gateway と Edge のチャートは、EmberNet ダッシュボードが機器のディスク、CPU、メモリを読めるように、ホストのルートと `/proc` をマウントします。権限は追加されません。restricted の Pod Security プロファイルのクラスターは hostPath を拒否するため、そこではアップグレード前に `opcuaServer.dashboard.boxHealth.enabled: false` を設定してください。値は [Gateway のインストール](/ja/gateway/install/#ボックスの状態とホストのマウント)にあります。
- **完成した機能は有効な状態で出荷されます。** チャートに該当の機能がある場合、`broker.enabled`、`opcuaServer.enabled`、`reports.enabled`、`backup.enabled`(毎日、`backup.interval: 24h`)、すべてのアラームチャネルを含む `notify.enabled`、`edgePublish.enabled`、`monitoring.serviceMonitor.enabled`(Prometheus オペレーターの CRD が入っている場所でのみ生成されます)、`ingress.enabled` はすべて true です。Ingress にはホスト名がないため、ingress クラスが扱うどのホストにも応答します。1つの名前に固定するには `ingress.hosts[0].host` を設定してください。送信先のないアラームチャネルや edge パブリッシャーは待機し、その旨を表示します。管理者が設定の「アラームと測定値の送信先」で送信先を指定します。ご自身のファイルで設定した値は引き続き優先され、`false` にした項目はリスナー、Service、ボリューム、Ingress を生成しません。
- **読み取りだけができる新しいログインが1つ増えます。** チャートはこのバージョンの初回インストール時に `embernet-dashboard-read` とその Secret `<release>-opcua-dashboard` を作成し、ローテーションはしません。
- **UniFi のコマンドは存在しますが無効です。** 5種類のポイントがコンソールにコマンドを送れますが、人がそのタグを有効にするまでは読み取り専用のままです。動作させるには、コンソールのアカウントがローカル管理者である必要があります。
- **Quadlet のアップグレードユニットは自動的にスキップされます。** `hotloop-db-upgrade` はボリュームにまだ PostgreSQL 16 のデータがあるときだけ実行されるため、すでに 17 の機器では失敗ではなく非アクティブと表示されます。新しいユニットファイルは `deploy/quadlet/` から取得してください。
- **チャートはアンインストール時に認証情報の Secret を残します。** データベースのボリュームと同じです。最初からやり直すには、ボリュームと一緒に Secret を手で削除してください。

## 4.18.11 からのアップグレード

アップグレードする理由: MCP 経由のエージェントが書き込めるようになり、スケールのあるタグに書いた値が意図どおりにレジスタへ入り、CODESYS ランタイムをプログラマーが変数に付けた名前で読めるようになり、HotLoop が測定値とシステムログを Kafka ブローカーに送れるようになり、UADP 上の OPC UA PubSub が双方向で動作し、ストアからのインストールではご自身のアカウントでサインインされます。[4.19.4 のリリースノート](/ja/releases/hotloop-4-19-4/)に全リストがあり、[4.19.5](/ja/releases/hotloop-4-19-5/)はそのマルチアーキテクチャビルド、[4.19.8](/ja/releases/hotloop-4-19-8/)はログブックの修正とプラント全体を検索するタグピッカーを加えます。4.19.0 から 4.19.3、4.19.6、4.19.7 はタグ付けされただけで公開されなかったため、アップグレード元としては存在しません。

```bash
helm repo update
helm upgrade hotloop hotloop/hotloop --version {{hotloop}} \
  --namespace hotloop --reset-then-reuse-values
```

`hotloop-edge`、`hotloop-iot`、`hotloop-edge-relay` も同じです。データベースは 4.18.11 からすでに PostgreSQL 17 で、ここでは何も変わらないため、4.18.11 への `helm rollback` は問題ありません。

- **エージェントが書き込めます。** `allowMcpWrites` はコードと3つのチャートのすべてで既定で有効です。`allowWrites` を有効にしていて `allowMcpWrites` を一度も設定していないデプロイでは、このアップグレードで画面と同じゲートを通してエージェントの書き込みが可能になります。`allowMcpWrites: false` を保存したデプロイは無効のままです。エージェントを読み取り専用にしたい場合は、アップグレード前に `false` に設定してください。
- **MCP エンドポイントには必ずトークンがあります。** トークンを設定したことのない単体バイナリや Quadlet ユニットは、初回起動時に自分で作成してデータベースに保存します。`hotloop mcp-token` で表示でき、トークンなしで `/mcp` を指していたエージェントは、このトークンを渡すまで動作しなくなります。
- **スケールのあるタグ。** スケール 0.1 のタグに 55.5 を書くとレジスタには 555 が入ります。以前は 55 でした。これを避けるために生のカウント値を入力していた場合、今度は10倍の値を送ることになります。オートメーションやレシピなどから人が手で書き込む、スケールやオフセットのあるすべてのタグを確認し、それらの数値をアップグレードと同じ手順で工学値に変更してください。
- **時刻は `Z` です。** API が書き出す時刻はすべて UTC です。ローカルのオフセットを解析していたスクリプトは、今後 `Z` を受け取ります。
- **マイグレーション1件、** `0026` が、ヒストリアンのターゲットに `options` 列を追加します。既存のすべてのターゲットでは空です。

## 4.18.10 からのアップグレード

アップグレードする理由: データベースが PostgreSQL 17 になり、機器が自分で移行します。さらに SNMP と BACnet/IP の[連携](/ja/iot/integrations/)、キオスクのサインイン、アラームのエスカレーション、スマートフォンにインストールできる UI が加わります。一覧は [4.18.11 のリリースノート](/ja/releases/hotloop-4-18-11/)にあります。以下は注意が必要な部分です。

PostgreSQL は別のメジャーバージョンのデータディレクトリを開けないため、イメージを差し替えるだけでは、既存のすべての機器に起動できないデータベースが残っていたでしょう。HotLoop はダンプと再読み込みを求めません。アップグレード後の初回起動で、データベースの前にスクリプトが実行され、そのスクリプトが移行を行います。

```bash
helm repo update hotloop
helm upgrade <release> hotloop/hotloop --version {{hotloop}} --reset-then-reuse-values
```

`hotloop-edge` と `hotloop-iot` も同じです。先に 4.18.10 でバックアップを取り、機器の外にコピーしてください。HotLoop 自身のバックアップは稼働中のアプリが稼働中のデータベースを通して作成するため、データベースの起動前に実行される手順では作成できません。

### 4.18.10 からの初回起動で起こること

- **データベースの Pod は `Init` のままになり、アプリはそれを待ちます。** チャートではデータベース Pod の init コンテナ2つです。古いイメージが PostgreSQL 16 のインストールを引き渡し、新しいイメージが古いディレクトリの隣の新しいディレクトリに対して、コピーモードで `pg_upgrade` を実行します。新しいサーバーを1回起動して開けることを確認し、その後で初めて名前を入れ替えます。所要時間はデータ量に比例するため、大きなデータでは初回にログを見てください: `kubectl logs <release>-postgresql-0 -c pg-upgrade`。Quadlet では `hotloop-db-upgrade.container` で、データベースユニットが必要とする oneshot ユニットです: `journalctl -u hotloop-db-upgrade`。
- **データと同程度の空き容量が必要で、開始前に確認します。** 容量が足りなければ、16 のデータをそのままにし、データベースを起動せずに停止します。ディスクを空けてから再度開始してください。
- **`pgdata.pg16` はボリュームに残り、削除はお客様の判断です。** 古いディレクトリは名前を変更されて残されます。アップグレード時点の PostgreSQL 16 データベースそのものであり、バックアップであり戻る道でもあって、データベースと同じ大きさです。機器を 17 で十分な期間運用したら:

  ```bash
  # chart
  kubectl -n hotloop exec hotloop-postgresql-0 -c postgresql -- rm -rf /var/lib/postgresql/data/pgdata.pg16
  # Quadlet
  sudo rm -rf "$(sudo podman volume inspect hotloop-db --format '{{.Mountpoint}}')/pgdata.pg16"
  ```

- **失敗しても元の状態に戻ります。** 入れ替え前に何かが失敗しても、16 のデータには手が付けられておらず、データベースが中途半端なディレクトリで起動することもありません。チャートでは Pod が `Init:Error` のままになります。Quadlet ではアップグレードユニットが失敗し、その後ろのデータベースユニットは起動しません。ログの指示どおりに直して、再度開始してください。
- **4.18.10 への `helm rollback` ではデータベースが起動しません。** これが注意点です。ロールバックするとデータベースのイメージが PostgreSQL 16 に戻り、16 は 17 のディレクトリを開けません。失われるものも中途半端に変わるものもなく、データベースが起動しないだけです。戻すには、k3s と Helm のページの[元に戻す](/ja/install/helm/#元に戻す)にある入れ替えが必要です。データベースを停止し、`pgdata` を `pgdata.pg17` に、`pgdata.pg16` を `pgdata` に移します。**これでアップグレード後に 17 で書き込まれたすべてが失われます。** `pgdata.pg16` はその時点のデータベースだからです。可能なら前に進んでください。元に戻す入れ替えは1回だけ有効で、次のアップグレードは `pgdata.pg16` が残っている間は実行を拒否します。手順は文書化されていますが、テストでは実行されていません。
- **Quadlet の機器はこの影響を受けません。** Podman の自動更新が戻すのはアプリだけでデータベースは戻さず、マイグレーションは追加のみなので、4.18.10 のアプリは PostgreSQL 17 のデータベースを問題なく読めます。更新をロールバックした Quadlet の機器は動き続けます。
- **新しいマイグレーション1件、`0025_kiosk_pin`。** 追加するのは列だけで、すべて既定値があるため、4.18.10 はこれが残すスキーマで動作します。
- **すべてのインストールでロックアウトが有効になりました。** パスワードまたは PIN を10回連続で間違えると、そのアカウントが5分間ロックされ、管理者が解除できます。間違ったパスワードを10回を超えて再試行するスクリプトは `429` を受け取り始めます。`HOTLOOP_AUTH_LOCKOUT_ATTEMPTS=0` で無効にできます。
- **アップグレードを無効にする場合。** `database.postgresql.upgrade.enabled: false` は init コンテナを外し、ボリュームがまだ 16 のままだとデータベースが起動しなくなります。有効のままにしてください。有効にしていても、init コンテナのイメージは実行前に取得されるため、新規インストールではノードごとに1回 PostgreSQL 16 のイメージを取得します。

### Quadlet と Edge Relay

製品の `deploy/quadlet/` ディレクトリから新しい `hotloop-db.container`、`hotloop-db-upgrade.container`、`hotloop-db-upgrade.sh` をユニットのディレクトリにコピーし、`systemctl daemon-reload` を実行して `hotloop-db.service` を再起動します。データベースユニットがアップグレードユニットを必要とするため、新しいデータベースユニットだけを取り込んだ機器は 16 のデータでは起動せず、その理由を表示します。Edge Relay にはデータベースがなく、やることはありません。すべての製品が同期して出荷されるため、{{hotloop}} で出荷されます。

### 4.18.10 からの API の変更

- **新しいルート:** `GET` と `PUT /api/notify/escalation`、`GET /manifest.webmanifest` と `GET /sw.js`(誰もサインインする前にスマートフォンが要求するためセッションなし)、`GET /api/integrations` と `POST /api/integrations/{id}/probe`、`/setup`、`POST /api/auth/kiosk`、`POST /api/auth/activity`、`PUT` と `DELETE /api/users/{username}/pin`、`DELETE /api/users/{username}/lockout`。
- **新しい権限 `notify.escalation`** は管理者専用です。閲覧者とオペレーターのロールには付与されていません。
- **新しいプロトコル2つ、** `snmp` と `bacnet` が `GET /api/protocols` に加わります。アラームの履歴には新しいイベント種別 `escalated` と `escalation-ended` が追加され、古い一覧を前提にしたスクリプトはこれに遭遇します。
- **時刻は UTC で返ります。** 履歴が返すすべての時刻が対象です。文字列を比較していたスクリプトでは、オフセットが `Z` になるのが見えます。時刻として比較しているスクリプトには何も見えません。

## 4.17.0 からのアップグレード

アップグレードする理由: Gateway が唯一のイメージではなくなります。IoT と Edge が新たに加わり、データベースは設定になり、MQTT で自ら名乗るデバイスが自動的に現れ、履歴をプラント自身のデータベースに書き出せ、`:stable` に従う機器は不具合のある更新を自分でロールバックします。最後のものは、マイグレーションが追加のみだからこそ成り立ちます。一覧は [4.18.10 のリリースノート](/ja/releases/hotloop-4-18-10/)にあります。

通常の `helm upgrade` です。4.17.0 と {{hotloop}} の Gateway チャートを同じ値で並べてレンダリングしたところ、同じ8つのオブジェクト、同じセレクター、同じボリューム要求でした。

```bash
helm repo update hotloop
helm upgrade <release> hotloop/hotloop --version {{hotloop}} --reset-then-reuse-values
```

`--reset-then-reuse-values` を使うか、`-f` で値ファイルを指定してください。単なる `--reuse-values` は今回たまたまレンダリングされますが、4.17.0 の値を再適用してこのリリースが追加したすべての既定値を失い、意図せず後述の古いキュー上限のままになります。

### 4.17.0 からの初回起動で起こること

- **マイグレーション 0016 から 0025 が実行されます:** `0016_mqtt_discovery`、`0017_broker_logins`、`0018_mqtt_sources`、`0019_historian_targets`、`0020_net_finds`、`0021_mqtt_source_dialects`、`0022_mqtt_source_shelly`、`0023_dashboards`(作成したダッシュボードが保存されるテーブル)、`0024_tag_no_data`(タグの `no_data` 列で、既存のすべてのタグでは空であり、それらのタグがすでに行っていた動作と同じです)、`0025_kiosk_pin`(PIN のハッシュ、セッションのアイドル上限、ロックアウトのカウンター用の列)。すべて追加のみです。いつものように、先に `pg_dump` を取ってください。
- **`edgePublish.queueMaxBytes` の既定値は無制限ではなく 64 MiB です。** Sparkplug で上位へ発行する場合にのみ関係します。上限を超えると最も古い測定値が破棄され、件数が数えられます。無制限のキューは十分に長い停止でボリュームを埋めてしまうため、そのほうが悪いのですが、既定値が変わったことには違いありません。64 MiB は約 248,000 件の測定値で、毎秒 2,000 件なら約2分です。ご自身の速度(1件あたり約 240 バイト)から大きさを決めるか、従来の動作にするには `0` に設定してください。そうすると HotLoop は起動時に警告します。`--reuse-values` でアップグレードしたリリースは、それまでの値を保持します。
- **ブローカーのログイン。** `HOTLOOP_BROKER_USERS` のログインは従来どおり何でもできます。自分で書いていないルールに Sparkplug のトラフィックが弾かれるプラントへアップグレードさせてはならないからです。設定、MQTT で作成したログインは、プロファイルのトピックルールを持ちます。`HOTLOOP_BROKER_USERS` のないブローカーも起動するようになり、HotLoop とその中で作成したログインだけが接続できます。
- **データベースはこの初回起動で PostgreSQL 16 から 17 へ移ります。** 自動で行われ、空きディスクが必要です。進み方は [4.18.10 の節](#41810-からのアップグレード)にあり、最初に読むべき部分です。
- **4.17.0 に戻すことは、`helm rollback` ではなくデータベースの入れ替えになりました。** スキーマは増えただけで 4.17.0 はその上で動作しますが、4.17.0 のデータベースは PostgreSQL 16 であり、アップグレードが残した 17 のディレクトリを開けません。戻すための入れ替えは 4.18.10 の節にあります。それでもアップグレード前にバックアップを取ってください。これ以降、アプリは自分よりデータベースがどれだけ先にあるかも数え、データベースが2リリース先に進むと両方のバージョンを示して起動を拒否します。
- **別の製品にしたいですか?** IoT から Edge、Gateway へ移っても、すべてのデバイス、タグ、エンティティ、オートメーション、アラーム、ユーザー、履歴の1時間分までが保たれます。バックアップを取り、同じリリースで `helm upgrade hotloop hotloop/hotloop-edge` を実行します。方法は[製品ラインナップ](/ja/products/)にあります。製品を下位に戻すのは、大切な機器でやることではありません。

### Edge Relay と Quadlet

リレーのチャートも `--reset-then-reuse-values` でアップグレードしてください。Quadlet のユーザーは新しい `edge-relay.container` を取得します。4.17.0 に固定せず `:stable` に従い、不具合のある更新をロールバックさせる healthcheck と `--sdnotify=healthy` を備えています。この2つがないと、失敗した更新が成功として報告されます。Gateway から送った機器ファイルは再起動なしで即座に適用されるようになりました。4.17.0 では再起動まで待っていました。ユニットの全体は [Edge Relay のインストールページ](/ja/edge-relay/install/)にあります。

Gateway には Quadlet ユニットが加わりました。4.17.0 にはありませんでした。[Podman Quadlet](/ja/install/quadlet/) の `gateway/` ディレクトリにあり、手順は [Gateway のインストールページ](/ja/gateway/install/#podman-quadlet)にあります。

### 4.17.0 からの API の変更

- **新しいルート:** `/api/discovery` とそのアクション `accept`、`ignore`、`unignore`、`review`、`/api/network-discovery` とその `probe`、`accept`、`ignore`、`unignore`、`/api/mqtt/brokers`、`/api/broker/logins`、`/api/historian/targets`、`GET /api/entities/{entity_id}/image`、そしてリレーが保留しているイメージ更新を承認する `POST /api/fleet/{id}/update`。削除されたものはありません。
- **`GET /api/status` は `product` と `features`、** そしてイメージのダイジェストを返します。スクリプトは手探りで試す代わりに問い合わせられます。その製品にない機能のルートは、`404` と `{"error":...,"product":...,"feature":...}` で応答します。
- **新しい権限:** `fleet.update`、管理者専用です。オペレーターのロールは変わっていません。

## 4.16.0 からのアップグレード

これは 4.17.0 への段階であり、4.17.0 からは[上の節](#4170-からのアップグレード)で {{hotloop}} へ進みます。以下はすべて 4.17.0 に対して検証されたものです。

アップグレードする理由: 4.16.0 には稼働中のプラントが引っかかりうる不具合があり、4.17.0 がそれを修正します。コマンドプロンプトが Set を飲み込むことがあり、オペレーターはプロンプトが閉じるのを見て設定値が出たと思いますが、何も書き込まれていません。エディターでルールを保存すると、名前を変えるだけでも、実行の予算が静かに5分に戻ります。Edge Relay に送った機器ファイルは、Gateway が `config pushed` と言っても届きません。EmberNet App Store のデプロイはテナントを失います。修正に加えて、[レシピ](/ja/iot/recipes/)、[スクリプト](/ja/iot/scripts/)、[ブループリント](/ja/iot/blueprints/)、[ヘルパー](/ja/iot/helpers/)、[ログブック](/ja/iot/logbook/)、新しい[オートメーション](/ja/iot/automations/)のステップ、読み取り専用の [UniFi](/ja/iot/unifi/)、そしてツールが16個から25個になった [MCP](/ja/iot/mcp/) が加わります。

通常の `helm upgrade` です。両方のバージョンで両方のチャートをレンダリングしたところ、すべてのセレクターとボリューム要求が同一で、新しいオブジェクトはキーの Secret だけでした。

```bash
helm upgrade <release> https://hotloop.io/hotloop/hotloop-4.17.0.tgz --reset-then-reuse-values
```

`--reset-then-reuse-values` を使うか、`-f` で値ファイルを指定してください。**`--reuse-values` は使わないでください。** 4.16.0 の値を再適用してこのチャートが追加したすべての既定値を失い、レンダリングは必要とする最初の値で失敗します(`secretKey` による `nil pointer evaluating interface {}.enabled`)。その場合クラスターには何も変更されないので、正しい方法でもう一度実行してください。

### 初回起動で起こること

リリース済みの 4.16.0 イメージをデータベースで動かし、続いて同じデータベースで 4.17.0 を動かして確認しました。

- **マイグレーション 0009 から 0015 が実行されます:** `0009_helpers`、`0010_logbook`、`0011_scripts`、`0012_tag_device_class`、`0013_recipes`、`0014_blueprints`、`0015_unifi`。すべて追加のみです。空のプラントでは 0.2 秒でした。お客様の環境ではデータベースの大きさ相応にかかります。いつものように、先に `pg_dump` を取ってください。
- **機器のパスワードが暗号化されます。** チャートはこのアップグレードで `<release>-secret-key` を作成し(4.16.0 にはありませんでした)、Gateway はその起動で保存されているすべての認証情報を封印してログに `encrypted stored device credentials devices=N` と記録します。機器は接続を続け、誰も入力し直す必要はありません。
- **それ以降、このキーはデータの一部です。** キーなしで Gateway を起動すると、封印されたパスワードを持つすべての機器は、必要なキーの名前を示すエラーとともに再試行を続け、停止したままになります。アップグレード後に取ったバックアップは、このキーがマウントされている場所でのみ復元でき、それ以外の場所では `--restore-from` が名前を挙げて拒否します。キーが完全に失われた場合は、`--restore-keep-unreadable-credentials` でそれ以外のすべてを復元できますが、それらの機器は誰かがパスワードを入力し直すまで停止したままです。4.16.0 のバックアップはどこにでも復元でき、その認証情報は復元が終わるとすぐに封印されます。
- **4.16.0 に戻す**ことは、同じデータベースで起動はします(試しました)が、4.16.0 は封印について何も知りません。各機器に封印されたテキストをパスワードとして渡すため、パスワードを確認するものはすべて拒否します。戻す必要がある場合は、アップグレード前に取った `pg_dump` を復元してください。そのために取っておくのです。
- **チャートをインストールせずにレンダリングしていますか?** キーは、実際の `helm install` または `helm upgrade` でしか実行できない `lookup` で生成されます。`helm template` を実行して結果を適用するものは、レンダリングのたびに新しいキーを得て、次の同期で封印されたすべてのパスワードが締め出されます。`hotloop gen-secret-key` で自分のキーを作り、ご自身で管理する Secret に入れて `secretKey.existingSecret` を設定してください。Helm、Fleet、EmberNet App Store は実際にインストールするので、これは不要です。

したがって、このアップグレード後の新しい作業は、`<release>-secret-key` をクラスターの他の Secret と同じ方法でバックアップし、バックアップの隣ではない別の場所に保管することです。守る対象のバックアップの隣に置かれたキーは、何も守りません。キーが対象とするその他のことは[インストール](/ja/gateway/install/#必要になる前にキーをバックアップする)にあります。

### Edge Relay

リレーも同じタグからリリースされた 4.17.0 です。チャートを同じ種類の URL、`https://hotloop.io/hotloop/hotloop-edge-relay-4.17.0.tgz` で 4.17.0 にアップグレードし、フラグの規則も同じです。`--reset-then-reuse-values` か値ファイルです。リレーでの `--reuse-values` は失敗さえしません。チャートの新しい `pushedDevicesFile` の既定値を失い、変数が空でレンダリングされ、プッシュはまた読み取り専用マウントで失敗します。そこで、次の4点を知っておいてください。

- **プッシュされた機器ファイルは `/data/pushed-devices.json` にあります**(`HOTLOOP_EDGE_RELAY_PUSHED_FILE`、チャートの `pushedDevicesFile`)。リレーのボリューム上にあります。存在する間は、再起動、Pod の再配置、`devices` を変える `helm upgrade` を経ても、チャートの `devices` より優先されます。リレーはどのファイルで起動したかをログに記録します。ローカルのファイルに戻すには、リレーが接続されている間に Gateway で `DELETE /api/fleet/{id}/config`(`fleet.config`)を実行してから、再起動します。この再起動は 4.17.0 の動作です。4.18.10 からは、接続中のリレーはその場で切り替わります。
- **古いプッシュが戻ってくることがあります。** 4.16.0 のリレーに行ったプッシュは届きませんでしたが、ブローカーが retained のまま保持しており、4.17.0 のリレーは初回起動でそれを受け取って実行します。古いものであれば、アップグレード直後に同じ `DELETE` で消去してリレーを再起動してください。4.18.10 からは消去がその場で適用され、再起動は不要です。
- **Quadlet: 新しい `edge-relay.container` を取得してください。** 4.17.0 のユニットは 4.17.0 に固定して `HOTLOOP_EDGE_RELAY_PUSHED_FILE` を設定しており、現在のユニットもこれを設定しますが `:stable` に従います。この行がないと、読み取り専用のルートでプッシュが失敗します。ユニットの全体は [Edge Relay のインストールページ](/ja/edge-relay/install/#quadlet)にあります。
- **`persistence.enabled=false` で起動するようになりました。** `persistence.size` で上限が決まる emptyDir 上で動きます。選ぶ前にその代償を知っておいてください。Pod が置き換わるたびに、転送キュー、プッシュされた機器ファイル、OPC UA クライアント証明書が失われます。大切なものは PVC を使ってください。これが既定です。

### API を使うスクリプトが気付く変更

- **起きていない時刻は省略されます。** `null` ではなく省略です。4.16.0 は、一度も実行されていないルールやスクリプトの `lastRun`、一度もポーリングされていない機器の `lastPoll` と `lastGood`、継続中のアラームの `clearedAt`、`ackedAt`、`shelvedUntil`、一度も発生していないアラームの `raisedAt`、ライブフィードの `alarm` イベントの同じフィールドなどに `0001-01-01T00:00:00Z` を送っていました。そのため、一度も実行されていないルールが「最終実行 739887日前」と表示されていました。コードで1年を判定しているなら、代わりにフィールドが存在するかを判定してください。
- **オペレーターはアップグレードした時点で新しい権限を得ます。** `helpers.write`、`scripts.run`、`recipes.apply`、`blueprints.apply` です。そのため、オペレーターはすぐにヘルパーを設定し、スクリプトを実行し、レシピを適用し、ブループリントからルールを作れます。スクリプト、レシピ、ブループリントの作成(`scripts.write`、`recipes.write`、`blueprints.write`)は管理者の権限です。読み取りは全員が可能です。レシピは独自の `recipes.apply.<name>` を指定することもできます。
- **新しいルート:** `/api/helpers`、`/api/logbook`、`/api/scripts`、`/api/recipes`、`/api/blueprints`、`POST /api/automations/{id}/blueprint-upgrade`、UniFi のルート(`/api/devices/{id}/network` と `/api/unifi/{id}/...`)、`DELETE /api/fleet/{id}/config`。
- **タグは `deviceClass` を持ち、** それはエンティティにも引き継がれます。
- **ルールは `blueprintId`、`blueprintVersion`、`blueprintInputs` を持ちます。** 手で書いたルールにはありません。ルールを保存すると今までどおり丸ごと置き換えられ、リクエスト本文でルールを別のブループリントやバージョンに移すことはできません。

## 4.3.1 からのアップグレード

4.3.1 は8月に公開され、4.16.0 までその後は何も公開されませんでした。4.4.0 から 4.15.3 まではマージされただけで公開されなかったため、4.3.1 を離れると、新しい名前、新しいイメージ、新しいチャート、新しいライセンスのもとで、そのすべてを一度に受け取ることになります。この節は、この手順を検証したリリースである 4.16.0 まで案内します。そこから先は、上の [4.16.0 からのアップグレード](#4160-からのアップグレード)が 4.17.0 への通常のアップグレードで、[4.17.0 からのアップグレード](#4170-からのアップグレード)がその次です。稼働中のプラントに手を付ける前に3つとも読んでください。短く、ヒストリアンが空な理由をプラントマネージャーに説明するよりずっと短く済みます。

### すべてが新しい名前に

| 項目 | 4.3.1 | 4.16.0 以降 |
|---|---|---|
| イメージ | `ghcr.io/embernet-ai/industrial-iot` | `ghcr.io/hotloop-io/hotloop` |
| チャートリポジトリ | 旧アドレス、現在は 404 | `https://hotloop.io/hotloop` |
| チャート | `industrial-iot` | `hotloop` |
| 環境変数 | `IIOT_*` | `HOTLOOP_*`(4.9.0 から) |

### 通常の helm upgrade ではありません

チャートの名前は Deployment と StatefulSet のセレクターに組み込まれており、Kubernetes はセレクターをその場で変更することをきっぱり拒否します。古いリリースを新しいチャートに向けると、ただ失敗します。リリース名とネームスペースはそのままにして、次の手順を行います。

1. データベースを `pg_dump` します。念には念を入れてください。やっておいてよかったと思うはずです。
2. 古い Deployment(`<release>`)と StatefulSet(`<release>-postgresql`)を削除します。データベースのボリュームは別の要求で、そのまま残ります。
3. リポジトリを追加し、4.3.1 を動かしていた値ファイルでアップグレードします:

   ```bash
   helm upgrade <release> https://hotloop.io/hotloop/hotloop-4.16.0.tgz \
     -n <namespace> -f your-4.3.1-values.yaml
   ```

   これは URL で指定した 4.16.0 のチャートで、リポジトリを追加する前でも動作します。4.16.0 に上がったら、その後の段階のためにリポジトリを追加してください(`helm repo add hotloop https://hotloop.io/hotloop`)。

   そのファイルの値はチャートから何も削除されていません。`extraEnv` の `IIOT_` はすべて `HOTLOOP_` に変更し、`image.repository` の上書きがあれば削除してください。`--reuse-values` は使わないでください。4.3.1 以降にこのチャートが追加したすべての既定値、つまりキーの半分以上を飛ばしてしまい、ほとんど穴だらけのチャートを動かすことになります。

名前、Secret のデータベースパスワード、ボリューム要求は 4.3.1 と同一にレンダリングされるため、新しいデータベース Pod は古いデータをマウントします。Gateway は起動時にスキーマを先へ移行し、そのついでに TimescaleDB を 2.29.1 から 2.30.1 に更新します。

これは両方のチャートを並べてレンダリングして確認しました。手順1が戻る道です。アップグレードで想定外のことが起きても、5分前のダンプがあります。その場合は [helpdesk@fireballz.ai](mailto:helpdesk@fireballz.ai) までお知らせください。

### 動作が変わる点

- **ログインがあります。** 4.4.0 より前には全くありませんでした。チャートは初回インストールで `admin` アカウントを作成します。パスワードを読み出すコマンドは[インストール](/ja/gateway/install/#サインイン)にあります。
- **書き込みは既定で無効です。** 4.4.0 からエージェントも含みます。4.3.1 の値ファイルで `safety.allowWrites` を設定していなければ、オペレーターやルールがこれまで行っていたすべての書き込みは、設定するまでアップグレード後に拒否されます。意図した動作であり、再び有効にする前に何が有効化されているかを見直す合図です。
- **読み込めないタイムゾーンは起動を止めます。** でたらめな値を設定した `HOTLOOP_TIMEZONE` や `TZ` は、以前は何も言わずに UTC で動き、すべてのレポート、スケジュール、シフト交代を静かに数時間ずらしていました。
- **機器の認証情報は、管理者を含むすべてのロールに `[redacted]` として読み出されます**(4.15.1)。プレースホルダーのまま機器を保存すると、保存済みのパスワードが維持されます。
- **ポーリングの設定は `HOTLOOP_POLL_INTERVAL`、`HOTLOOP_MIN_POLL_INTERVAL`、`HOTLOOP_POLL_TIMEOUT` です。** 古い設定画面は `HOTLOOP_POLL_INTERVAL_MS`、`HOTLOOP_MIN_POLL_INTERVAL_MS`、`HOTLOOP_TIMEOUT_MS` を設定するよう案内していましたが、これらを読むものはありませんでした。設定していても何の効果もありませんでした。名前を変更してください。
- **インポートした OPC UA タグは、インポート時の型を保ちます。** タグの検出は以前、すべてのノードを float と扱っていました。現在は各ノードの実際の型を読みますが、以前にインポートしたタグは `float` のままで、HotLoop 自身の OPC UA サーバーはタグを宣言された型で公開するため、テキストタグは Ignition に `Bad_TypeMismatch` として届きます。テキストのタグは `string` として宣言してください。
- **Edge の発行に値のブロックができました。** `extraEnv` で設定している場合は `edgePublish:` に移して変数を削除してください。そうしないと二重に設定されます。
- **OPC UA サーバーは製造元を `HotLoop` と名乗ります。** 以前のバージョンは別の製造元名を使っていました。クライアントや棚卸しスクリプトがその文字列で一致を判定している場合は、一致しなくなる前に変更してください。
- **ライセンス。** 4.3.1 の後に条件が変わりました。現在の条件は[ライセンスのページ]({{LICENSE_URL}})にあります。

### 4.3.1 からの API の変更

API を使うスクリプトや連携がある場合は、これが一覧です。それ以外はすべて追加です。[上の](#api-を使うスクリプトが気付く変更) 4.16.0 から 4.17.0 への変更がその上に加わり、[その上の](#4170-からの-api-の変更) 4.17.0 から {{hotloop}} への変更も同様です。

- **空のリストは `[]` で、`null` ではありません。** すべてのレスポンスとすべてのストリームイベントで、どの深さでも同じです。`GET /api/runs`、オートメーション、機器のタグ、書き込み監査、ユーザー、アラームイベント、スパークライン、空の履歴ウィンドウは、以前はすべて `null` を返していました。今も見える `null` はリストではなく、エンティティの `equipment_id` のような、文書化された null 可のフィールドです。
- **正常な測定値のない `/api/history` のバケットは `null` で、** 欠損として描画され、不良な測定値はトレンドの平均から除外されます。同じ時間のトレンドとレポートが、同じことを示すようになりました。
- **API が原因を特定できないエラーは 400 ではなく 500 で、** サーバーログへの参照が付きます。書き込みや参照でエラーを返す機器は 502 です。[書き込みゲート](/ja/gateway/write-gate/#拒否ごとの応答)に、書き込みが受け取りうるすべてのステータスがあります。
- **`alarm.turn_on`、およびアラームエンティティが受け付けないその他のサービスは 400 です**("unknown service")。以前は成功を返して何もせず、これは考えうる最悪の応答でした。
- **保留されていないアラームの保留解除は 409 です。** 以前はアラームがどの状態であってもノーマルにしてしまい、復帰済みで未確認のアラームを一覧から消すことがありました。それは ISA-18.2 が一覧に残すために存在する、まさにそのアラームです。
- **タグの JSON には常に `minValue`、`maxValue`、`hasRange` が含まれ、** 範囲があるかどうかは `hasRange` だけが示します。0 から始まる範囲は、以前は最小値がないように見えました。
- **新機能: `POST /api/services/{domain}/{service}` の `?dry_run=true`。** ゲートのチェックを実行し、何も書き込まず、監査にも記録せず、実際の呼び出しが返す拒否の応答を返します。`dry_run` は `true` か `false` だけを受け付けます。`yes` は 400 です。間違った方向に推測すると、問い合わせがコマンドになってしまうからです。
- **`GET /api/settings`** は、値が実際にどの変数から来たかを `envVar` に示し、フォールバックも含みます。空文字列に設定された変数は未設定として扱われます。

[リリースノート](https://hotloop.io/releases/core/)には、4.4.0 まで遡って、バージョンごとの変更点の残りがあります。4.16.0 に上がってもヒストリアンがまだ満杯なら、[4.16.0 からのアップグレード](#4160-からのアップグレード)を行い、続いて [4.17.0 からのアップグレード](#4170-からのアップグレード)を行ってください。
