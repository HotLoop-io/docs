चार्ट दो वर्कलोड तैनात करता है: गेटवे (एक Deployment, जो अपनी कोई स्थायी स्थिति नहीं रखता) और TimescaleDB (वॉल्यूम वाला एक StatefulSet)। यही डिफ़ॉल्ट है। `database.type` दूसरा डेटाबेस चुनता है: सादा PostgreSQL, या SQLite, जो कोई दूसरा वर्कलोड है ही नहीं ([SQLite](#sqlite), नीचे)।

## इंस्टॉल

EmberNet डैशबोर्ड के App Store से, या सीधे:

```bash
helm install hotloop ./charts/hotloop \
  --namespace hotloop --create-namespace
```

या चार्ट रिपॉज़िटरी से, जो वही URL भी है जिस पर App Store इंगित करता है:

```bash
helm repo add hotloop https://hotloop.io/hotloop
helm install hotloop hotloop/hotloop \
  --namespace hotloop --create-namespace
```

यह दूसरा रूप 4.16.0 से चलता है, जो `hotloop` नाम से प्रकाशित पहला रिलीज़ है। उससे पहले का आख़िरी रिलीज़ पुराने नाम से `industrial-iot` 4.3.1 था, और उससे अपग्रेड करना एक अलग प्रक्रिया है: README के 4.16.0 नोट्स में "Upgrading from 4.3.1" देखें। पुराना रिपॉज़िटरी पता, `https://embernet-ai.github.io/industrial-iot/`, 404 देता है।

सादी इंस्टॉल चलती है। चार्ट रिलीज़ के Secret में डेटाबेस पासवर्ड और MCP टोकन बनाता है और अपग्रेड में उन्हें दोबारा इस्तेमाल करता है, इसलिए कुछ देना नहीं पड़ता और अपग्रेड चल रहे डेटाबेस के नीचे से पासवर्ड नहीं बदलता।

इस तक पहुंचने के लिए न ingress चाहिए न सबडोमेन। डैशबोर्ड ऐप को उसके स्टोर लेबल से खोजता है और क्लस्टर के अंदर के पते पर प्रॉक्सी करता है:

```
<release>.<namespace>.svc.cluster.local:8080
```

इसे सीधे देखने के लिए:

```bash
kubectl -n hotloop port-forward svc/hotloop 8080:8080
```

## तय करने लायक मान

### प्रमाणीकरण

4.4.0 से। पूरे मॉडल के लिए [प्रमाणीकरण और यूज़र](/hi/iot/authentication/) देखें; यह उसका चार्ट वाला हिस्सा है।

```yaml
auth:
  enabled: true    # the default; requires a login
  insecure: false  # set true only for a deployment truly isolated behind the
                    # dashboard's own NetworkPolicy -- see AUTH.md
```

`enabled: true` (डिफ़ॉल्ट) होने पर चार्ट पहली इंस्टॉल पर रिलीज़ के Secret में एक एडमिन खाता बनाता है, उसी तरह जैसे वह डेटाबेस पासवर्ड और MCP टोकन बनाता है, और अपग्रेड में उसे दोबारा इस्तेमाल करता है:

```bash
kubectl get secret hotloop -n hotloop \
  -o jsonpath='{.data.admin-password}' | base64 -d
```

`auth.admin.password` को साफ़ तौर पर सेट करने से बनाया गया पासवर्ड बदल जाता है।

### सुरक्षा

वे मान जो तय करते हैं कि यह पॉड मशीनरी चला सकता है या नहीं।

```yaml
safety:
  allowWrites: false      # the master switch -- off by default since 4.4.0
  allowMcpWrites: true    # agents (MCP) write wherever an operator could, once writes are on
  confirmWrites: true     # the UI asks before writing
```

लिखना डिफ़ॉल्ट रूप से बंद है। टैग तब तक केवल पढ़ने वाला रहता है जब तक उसका अपना `writable` फ़्लैग सेट न हो, टैग की कॉन्फ़िगर की गई सीमा से बाहर का मान अस्वीकार हो जाता है (कभी काटा नहीं जाता: किसी के 500 टाइप करने पर 250 भेजना चुपचाप कुछ और करना है), और हर कोशिश, **हर अस्वीकृति समेत**, करने वाले और स्रोत के साथ दर्ज होती है। लेकिन नई इंस्टॉल को सुरक्षित होने के लिए तीनों के एक साथ मेल खाने की ज़रूरत नहीं होनी चाहिए, इसलिए मास्टर स्विच ख़ुद बंद से शुरू होता है।

तैनाती की समीक्षा हो जाने के बाद लिखना चालू करने के लिए:

```yaml
safety:
  allowWrites: true
```

बस इतना ही चाहिए: MCP क्लाइंट ऑपरेटर की तरह पढ़ते और लिखते हैं, उन्हीं अनुमतियों, लिखने योग्य टैग और सीमाओं के तहत। `allowMcpWrites` हर चार्ट में चालू भेजा जाता है; यह उस तैनाती के लिए है जो कुछ और तय करे, और कहीं भी डिफ़ॉल्ट नहीं है।

### हिस्टोरियन

```yaml
historian:
  retentionDays: 90     # 0 keeps everything until the volume fills
  useTimescale: true

logbook:
  retentionDays: 90     # entity state changes; 0 keeps everything (see LOGBOOK.md)

database:
  postgresql:
    persistence:
      size: 20Gi
      storageClass: longhorn
```

आकार टैग की संख्या, स्कैन दर और डेडबैंड से तय होता है। एक हज़ार टैग हर सेकंड, बिना डेडबैंड के, लगभग 8.6 करोड़ पंक्तियां प्रतिदिन होते हैं; वही प्लांट समझदार डेडबैंड के साथ आमतौर पर एक दर्जा कम होता है। स्टोरेज ख़रीदने से पहले डेडबैंड सेट करें।

`useTimescale: false` नेटिव पार्टिशनिंग का रास्ता लागू करता है, जो सादे PostgreSQL पर चलने जैसा दिखता है। एज तैनाती को दोहराने के लिए उपयोगी।

**जब TimescaleDB इमेज बदलती है।** इमेज में हर पुराने संस्करण की लाइब्रेरी होती है, इसलिए पुरानी इमेज से बना डेटाबेस नई पर चलता रहता है, लेकिन एक्सटेंशन के पुराने संस्करण पर, और वहीं रहता है जब तक कोई `ALTER EXTENSION timescaledb UPDATE` न चलाए। गेटवे शुरू होते समय यह करता है: वह इंस्टॉल किए संस्करण की तुलना सर्वर के साथ आने वाले संस्करण से करता है और अलग होने पर अपडेट को नए कनेक्शन के पहले स्टेटमेंट के रूप में चलाता है (TimescaleDB इसे उस सेशन में अस्वीकार करता है जिसने पुराना संस्करण पहले ही लोड कर लिया हो)। लॉग में `timescaledb extension updated from=... to=...` दिखता है। इसके लिए सुपरयूज़र चाहिए, जो साथ आने वाले डेटाबेस का यूज़र है। बाहरी या मैनेज्ड डेटाबेस पर जहां ऐसा नहीं है, आपको चलाने वाले कमांड के साथ एक चेतावनी मिलती है, और इस बीच इतिहास पुराने संस्करण पर चलता रहता है। यह केवल तब होता है जब `useTimescale` चालू हो और माइग्रेशन शुरू होते समय चलते हों (`HOTLOOP_DB_MIGRATE`, डिफ़ॉल्ट रूप से चालू)।

### पोलिंग

```yaml
runtime:
  defaultPollIntervalMs: 1000
  minPollIntervalMs: 100      # a floor applied to every device
  timeoutMs: 10000
  maxConcurrentPolls: 32
```

`minPollIntervalMs` पर भरोसा नहीं किया जाता, उसे लागू किया जाता है। सीरियल गेटवे पर 10 ms की पोलिंग कुछ अतिरिक्त क़दमों वाला सेवा-अवरोध (denial of service) है।

### OPC UA क्लाइंट

```yaml
opcuaClient:
  persistence:
    enabled: true      # off by default
    size: 64Mi
```

जो डिवाइस सुरक्षित OPC UA सर्वर से जुड़ता है, या ऐसे यूज़र नाम और पासवर्ड से लॉग इन करता है जिन्हें सर्वर एन्क्रिप्टेड मांगता है, वह एक प्रमाणपत्र और स्वीकृत सर्वर प्रमाणपत्रों का ट्रस्ट स्टोर रखता है (`HOTLOOP_OPCUA_CLIENT_PKI_DIR`, `/data/opcua-client-pki`)। ऐसा डिवाइस जोड़ने से पहले इसे चालू करें: रूट फ़ाइल सिस्टम केवल पढ़ने वाला है, इसलिए वॉल्यूम के बिना डिवाइस अगले रीस्टार्ट पर खो जाने वाले प्रमाणपत्रों से जुड़ने के बजाय ऐसी त्रुटि बताता है जो यही कहती है। यह डिफ़ॉल्ट रूप से बंद है क्योंकि यह मौजूदा इंस्टॉल में PersistentVolumeClaim जोड़ता है, जो बिना डिफ़ॉल्ट StorageClass वाले क्लस्टर पर Pending में रहता है। असुरक्षित चैनल के अनाम डिवाइस इसका उपयोग नहीं करते। सर्वर का प्रमाणपत्र स्वीकृत करना, और इन डिवाइसों के बारे में बाक़ी सब, [प्रोटोकॉल और ड्राइवर](/hi/iot/protocols/#opc-ua-सुरक्षा-और-क्रेडेंशियल) में है।

### नेटवर्किंग

```yaml
networkPolicy:
  enabled: true
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: dashboard-system
      ports:
        - protocol: TCP
          port: 8080
```

डैशबोर्ड का नेमस्पेस पता चलते ही ingress को उसी तक सीमित करें। Egress जान-बूझकर असीमित है: यह ऐप ऐसे पतों पर उपकरणों तक पहुंचने के लिए है जिन्हें पहले से कोई गिन नहीं सकता, और जो egress नीति किसी पोल को चुपचाप रोक दे वह फ़ायरवॉल नियम से ज़्यादा टूटे हुए ड्राइवर जैसी लगती है।

### हार्डवेयर: USB रेडियो, सीरियल अडैप्टर और Bluetooth

4.19.7 से हर HotLoop चार्ट (Gateway, IoT, Edge और Edge Relay) हार्डवेयर के लिए ज़रूरी पहुंच चालू करके भेजा जाता है, इसलिए App Store या helm से सादी इंस्टॉल बिना हाथ से संपादन के पॉड नेटवर्क पर नोड में लगी चीज़ें देख लेती है। यह `values.yaml` का `hardware:` ब्लॉक है: तीन स्विच जो डिफ़ॉल्ट रूप से चालू हैं, और एक वैकल्पिक जो डिफ़ॉल्ट रूप से बंद है:

| मान | डिफ़ॉल्ट | क्या करता है |
|---|---|---|
| `hardware.privileged` | `true` | ऐप कंटेनर privileged (`privileged: true`, `allowPrivilegeEscalation: true`) और root (`runAsUser: 0`, `runAsNonRoot: false`, कोई capability नहीं हटाई जाती) के रूप में चलता है। root इसलिए कि USB सीरियल नोड `root:dialout 0660` है और BlueZ की D-Bus नीति root और `bluetooth` समूह को अंदर आने देती है; दोनों में से किसी में भी न आने वाला कंटेनर यूज़र कुछ नहीं खोल पाता। रूट फ़ाइल सिस्टम केवल पढ़ने वाला रहता है, और init कंटेनर और साथ आने वाला डेटाबेस अपना non-root, सभी capability हटाया हुआ संदर्भ रखते हैं। |
| `hardware.usbDevices.enabled` | `true` | नोड का `/dev` (`hardware.usbDevices.hostPath`) `/dev` पर माउंट होता है: USB सीरियल अडैप्टर (`/dev/ttyUSB*`, `/dev/ttyACM*`, `/dev/serial/by-id/*`), पॉड शुरू होने के बाद लगाया गया भी। privileged कंटेनर को केवल वे डिवाइस मिलते हैं जो उसके शुरू होते समय मौजूद थे; माउंट ही दोबारा लगाए गए स्टिक को दिखाता है। |
| `hardware.bluetooth.enabled` | `true` | नोड की D-Bus डायरेक्टरी (`hardware.bluetooth.dbusPath`, `/run/dbus`, जिसमें `system_bus_socket` है) उसी पथ पर माउंट होती है, ताकि क्लाइंट नोड के BlueZ तक पहुंच सके। D-Bus के बिना नोड पर यह ख़ाली बनती है, इसलिए पॉड वहां भी शुरू होता है। |
| `hardware.bluetooth.hostNetwork` | `false` | वैकल्पिक चयन, डिफ़ॉल्ट रूप से बंद, उसके लिए जिसे नोड का नेटवर्क चाहिए: कर्नेल के Bluetooth सॉकेट (HCI, L2CAP) केवल नोड के नेटवर्क नेमस्पेस में होते हैं, इसलिए जो क्लाइंट सीधे एक खोलता है, और जो खोज नोड के अपने नेटवर्क पर सुनती है (mDNS, SSDP, रेडियो का multicast), उन्हें इसकी ज़रूरत है। जो क्लाइंट BlueZ के D-Bus API से जाता है उसे केवल माउंट किया सॉकेट चाहिए और वह पॉड नेटवर्क से चलता है। चालू होने पर पॉड नोड के नेटवर्क पर चलता है, उन परिणामों के साथ जो [नेटवर्किंग](#नेटवर्किंग) में हैं। |

आज HotLoop इसके साथ क्या करता है: अभी कुछ नहीं। HotLoop में Bluetooth, Z-Wave या USB सीरियल का अपना कोड नहीं है (Zigbee, MQTT पर Zigbee2MQTT ब्रिज से आता है, देखें [एम्बेडेड MQTT ब्रोकर](/hi/iot/broker/)); यह वह पहुंच है जो कोई फ़ीचर, या रेडियो पढ़ने वाला sidecar, मांगे जाने से पहले ही तैयार रखता है।

इसकी क़ीमत, जान-बूझकर और तय की हुई: पॉड नोड पर root है (privileged, नोड के `/dev` के साथ), और चार्ट की NetworkPolicy डिफ़ॉल्ट उन चीज़ों के लिए चालू रहती है जिन्हें वह कवर करती है। पॉड पॉड नेटवर्क पर ही रहता है। किसी भी हिस्से को `--set hardware.privileged=false --set hardware.usbDevices.enabled=false --set hardware.bluetooth.enabled=false` से बंद करें; तीनों बंद होने पर रेंडर, पंक्ति दर पंक्ति, वही पॉड है जो 4.19.6 ने रेंडर किया था (non-root, हर capability हटाई गई, केवल पढ़ने वाला रूट, पॉड नेटवर्क)। जिसे नोड का नेटवर्क चाहिए उसके लिए `hardware.bluetooth.hostNetwork=true` (या `hostNetwork=true`) सेट करें: तब पेज नोड के हर पते पर `service.targetPort` पर जवाब देता है, प्रति नोड प्रति पोर्ट एक HotLoop, NetworkPolicy पॉड पर लागू नहीं होती, और `nodeSelector` उसे उस नोड से बांध देता है जिसका रेडियो उसे देखना है।

### एज तैनाती

ऐप इमेज amd64 और arm64 के लिए बनती है, और TimescaleDB 2.30.1-pg17 multi-arch है, इसलिए एज इंस्टॉल को हिस्टोरियन नहीं रोकता।

```yaml
resources:
  requests: {cpu: 100m, memory: 128Mi}
  limits:   {cpu: 500m, memory: 256Mi}

database:
  postgresql:
    persistence: {size: 5Gi}
    resources:
      requests: {cpu: 100m, memory: 256Mi}
      limits:   {cpu: 500m, memory: 512Mi}

historian:
  retentionDays: 30

nodeSelector:
  kubernetes.io/arch: arm64
```

### Sparkplug पर ऊपर की ओर प्रकाशित करना

एज गेटवे जो कुछ पढ़ता है उसे Sparkplug B एज नोड के रूप में केंद्रीय गेटवे को भी प्रकाशित कर सकता है। वह क्या प्रकाशित करता है और फ़ॉरवर्ड कतार कैसे व्यवहार करती है, इसके लिए [एज प्रकाशन और स्टोर-एंड-फ़ॉरवर्ड](/hi/edge/edge-publish/) देखें; यह चार्ट वाला हिस्सा है।

```yaml
edgePublish:
  enabled: true
  broker: tcp://central.example.local:1883
  group: Plant1
  node: press-line-3          # empty uses the release name
  username: press-line-3
  existingSecret: central-mqtt # key "password", or set secretKey
  tls: false
  queueMaxBytes: 536870912     # 512 MiB; the default is 64 MiB, and 0 is unbounded
  persistence:
    size: 1Gi
```

इसे चालू करने से क्या बदलता है, और क्यों:

- **फ़ॉरवर्ड कतार के लिए 1Gi का PVC**, `/data/edge-publish` पर माउंट। अपलिंक बंद रहने पर रीडिंग यहीं जमा होती हैं, इसलिए यह पॉड से ज़्यादा टिकना चाहिए। `persistence.enabled: false` इसे emptyDir पर रखता है, जो कंटेनर रीस्टार्ट से बच जाता है और किसी और चीज़ से नहीं।
- **Deployment `Recreate` से रोल होता है।** कतार एक फ़ाइल है जिस पर लॉक है। रोलिंग अपडेट पहले नया पॉड शुरू करता है, नया पॉड कतार नहीं खोल सकता, कभी तैयार नहीं होता, और रोलआउट हमेशा के लिए अटका रहता है। Recreate पहले पुराने को रोकता है; हर अपग्रेड में पोलिंग के कुछ सेकंड जाते हैं।
- **`replicaCount` 1 होना ज़रूरी है**, और अन्यथा चार्ट रेंडर करने से मना कर देता है। दो रेप्लिका एक ही Sparkplug नोड पर दावा करने वाले दो प्रकाशक होंगे।
- **नोड id डिफ़ॉल्ट रूप से रिलीज़ का नाम है**, पॉड का होस्टनाम नहीं। होस्टनाम हर रोलआउट पर बदलता है, और Sparkplug होस्ट हर बार बिल्कुल नया एज नोड देखेगा।

पासवर्ड कभी सादे टेक्स्ट वाले डिफ़ॉल्ट में नहीं जाता। अनाम ब्रोकर के लिए `password` और `existingSecret` ख़ाली छोड़ें तो कोई Secret नहीं बनता; `password` सेट करें तो चार्ट उसे `<release>-edge-publish` में रखता है; `existingSecret` सेट करें तो आप अपना संभाला हुआ Secret इस्तेमाल करते हैं।

### बाहरी डेटाबेस

```yaml
database:
  postgresql:
    enabled: false
    auth:
      existingSecret: my-db-credentials
      secretKey: password
  external:
    host: timescale.plant.local
    port: 5432
    database: industrial
    username: industrial
  sslMode: require
```

ऐप TimescaleDB पहचानता है और एक्सटेंशन होने पर `tag_history` को hypertable में बदल देता है। सादे PostgreSQL पर वह विफल होने के बजाय नेटिव रेंज पार्टिशनिंग पर लौट आता है।

यह निर्णय दर्ज होता है और **स्थायी** है। hypertable के रूप में बना डेटाबेस बिना एक्सटेंशन वाले सर्वर पर चुपचाप कहीं और लिखने के बजाय शुरू होने से मना कर देता है; यह त्रुटि दिखे तो आपने ऐप को उस डेटाबेस से अलग डेटाबेस पर इंगित किया है जिस पर वह बना था।

### SQLite

डेटाबेस एक सेटिंग है, इमेज नहीं। हर उत्पाद एक ही बाइनरी से SQLite, Postgres या TimescaleDB पर चलता है (IoT TimescaleDB छोड़ देता है, नीचे देखें):

| वेरिएबल | डिफ़ॉल्ट | क्या करता है |
|---|---|---|
| `HOTLOOP_DB_TYPE` | `postgres` | `postgres` या `sqlite`। TimescaleDB सर्वर पर एक्सटेंशन के साथ `postgres` है |
| `HOTLOOP_DB_PATH` | `/data/hotloop.db` | SQLite फ़ाइल। इसे केवल SQLite पढ़ता है |

SQLite शुद्ध Go वाला है (`modernc.org/sqlite`), हर इमेज में कंपाइल किया हुआ, इसलिए कोई दूसरा कंटेनर नहीं, SD कार्ड पर 300 MB की Postgres इमेज नहीं, और arm बिल्ड स्थिर रहते हैं। फ़ाइल को ऐसे वॉल्यूम पर रखें जो कंटेनर से ज़्यादा टिके, और Pi पर वह वॉल्यूम USB SSD पर रखें। दिन भर SD कार्ड पर लिखने वाला हिस्टोरियन बहुत सारे SD कार्ड ख़रीदने का तरीक़ा है।

जो एक जैसा है: हर टेबल, हर कॉलम, हर फ़ीचर। जो अलग है:

- इतिहास पार्टिशन या hypertable नहीं, इंडेक्स वाली एक टेबल है, और रिटेंशन महीने गिराने के बजाय पुरानी पंक्तियां मिटाता है। हर सेकंड के इतिहास के सालों वाली साइट को Postgres या TimescaleDB चाहिए, और वहां जाना बैकअप और रीस्टोर है (BACKUP.md)।
- एक समय में एक लिखने वाला। SQLite लिखने में बारी लेता है और उनके साथ-साथ पढ़ता है (WAL), जो एक HotLoop और उसी फ़ाइल पर उसके बगल के `--mcp-stdio` हेल्पर के लिए काफ़ी से ज़्यादा है। यह नेटवर्क स्टोरेज पर दो रेप्लिका के लिए नहीं है: NFS पर SQLite ख़राब हो जाता है, इसलिए SQLite तैनाती लोकल वॉल्यूम वाला एक पॉड है।
- कमिट `synchronous=FULL` हैं: जब API कहे कि सहेजा गया, तो वह डिस्क पर है, बिजली गई हो या नहीं।

**HotLoop IoT** डिफ़ॉल्ट रूप से 30 दिन का इतिहास रखता है (`HOTLOOP_HISTORIAN_RETENTION_DAYS` सेट होने पर अब भी वही चलता है) और कभी hypertable नहीं बनाता: TimescaleDB, Edge और Gateway का हिस्सा है। IoT पर `HOTLOOP_HISTORIAN_TIMESCALE=true` सेट करें तो वह शुरू होते समय यह बताता है और सादे पार्टिशन पर चलता है। Edge या Gateway से नीचे लाया गया डेटाबेस जिसमें पहले से hypertable है, उसे रखता है और चलता रहता है।

#### चार्ट में डेटाबेस चुनना

एक मान, `database.type`, और हर उत्पाद वही लेता है जिन पर वह चलता है:

| `database.type` | क्या तैनात होता है | IoT | Edge | Gateway |
|---|---|---|---|---|
| `timescaledb` | ऐप और TimescaleDB (एक StatefulSet और उसका वॉल्यूम)। इतिहास hypertable में | अस्वीकृत | डिफ़ॉल्ट | डिफ़ॉल्ट |
| `postgresql` | ऐप और सादा PostgreSQL 17 (एक StatefulSet और उसका वॉल्यूम)। इतिहास नेटिव पार्टिशन में | डिफ़ॉल्ट | हां | हां |
| `sqlite` | अकेला ऐप, डेटाबेस फ़ाइल अपने वॉल्यूम पर | हां | हां | हां |

```bash
helm install hotloop hotloop/hotloop-iot --namespace hotloop --create-namespace   --set database.type=sqlite
```

IoT से `timescaledb` मांगने पर इंस्टॉल विफल होती है और बताती है कि IoT किन पर चलता है (`database.type is "timescaledb", and HotLoop IoT runs on sqlite, postgresql`), और App Store का फ़ॉर्म इसे पेश नहीं करता। `helm lint` इसे नहीं पकड़ता (helm 3.22 इसे साफ़ मानता है), इसलिए रेंडर ही इसे अस्वीकार करता है। `database.type` छोड़ने पर उत्पाद का अपना डिफ़ॉल्ट मिलता है, इसलिए कुंजी के होने से पहले के संस्करण से `--reuse-values` वाला अपग्रेड वही डेटाबेस रखता है जो उसके पास था।

`sqlite` रेंडर करता है:

- `HOTLOOP_DB_TYPE=sqlite` और `HOTLOOP_DB_PATH=/data/db/hotloop.db`, और Postgres कनेक्शन की कोई सेटिंग नहीं। कोई डेटाबेस पॉड नहीं, Secret में डेटाबेस पासवर्ड नहीं, उसका इंतज़ार करता कोई init कंटेनर नहीं।
- `<release>-db` नाम का एक PersistentVolumeClaim (`database.sqlite.persistence`: `size`, `storageClass`, `accessMode`, शुरू में 10Gi और क्लस्टर का डिफ़ॉल्ट), `/data/db` पर माउंट। फ़ाइल नहीं, डायरेक्टरी: SQLite डेटाबेस के बगल में `-wal` और `-shm` रखता है। इसे लोकल स्टोरेज पर रखें; NFS पर SQLite ख़राब हो जाता है।
- Deployment `Recreate` पर, रोलिंग अपडेट नहीं, क्योंकि वॉल्यूम `ReadWriteOnce` है और फ़ाइल का एक ही लिखने वाला है। 1 से ऊपर का `replicaCount` इंस्टॉल को विफल कर देता है।

NetworkPolicy बदलती नहीं और चालू रहती है: ऐप की अपनी नीति अब भी लागू है, और डेटाबेस की नीति तभी रेंडर होती है जब बचाने के लिए डेटाबेस पॉड हो।

जिस रिलीज़ में पहले से डेटा है उस पर `database.type` बदलने से डेटा नहीं हिलता। नया डेटाबेस ख़ाली शुरू होता है, इसलिए प्लांट को एक डेटाबेस से दूसरे में ले जाना बैकअप और रीस्टोर है (BACKUP.md), जैसा वेरिएबल के साथ होता है। ख़ास तौर पर TimescaleDB hypertable के रूप में बना डेटाबेस सादे PostgreSQL पर शुरू होने से मना कर देता है, इसलिए किसी मौजूदा Edge या Gateway को `timescaledb` से `postgresql` पर पलटकर उसके चल पड़ने की उम्मीद न करें।

#### Quadlet में डेटाबेस चुनना

`deploy/quadlet/` के नीचे हर उत्पाद की डायरेक्टरी में PostgreSQL या TimescaleDB की फ़ाइलें जैसी थीं वैसी हैं, और उनके बगल में एक `sqlite/` डायरेक्टरी: `hotloop.container` और `hotloop-data.volume`, अकेला ऐप जिसकी फ़ाइल `hotloop-data` वॉल्यूम पर `/data/hotloop.db` में है। यह `:stable` का पालन करता है और ख़राब अपडेट को उसी तरह वापस करता है। दूसरी फ़ाइलों की जगह ये दो फ़ाइलें इंस्टॉल करें (वे वही यूनिट नाम इस्तेमाल करती हैं), और तीन की जगह दो सीक्रेट बनाएं: डेटाबेस पासवर्ड नहीं है। चरण [`deploy/quadlet/README.md`](/hi/install/quadlet/) में हैं।

Quadlet के तहत Edge या Gateway पर सादे Postgres पार्टिशन के लिए TimescaleDB यूनिट रखें और `hotloop.container` में `Environment=HOTLOOP_HISTORIAN_TIMESCALE=false` जोड़ें। IoT की यूनिट पहले से सादा PostgreSQL चलाती है।

### डिवाइस क्रेडेंशियल कुंजी

```yaml
secretKey:
  enabled: true
  existingSecret: ""     # or a Secret you manage, with the key under secret.key
```

डिवाइस पासवर्ड (UniFi कंसोल लॉगिन, OPC UA या MQTT पासवर्ड, HTTP API कुंजियां) डेटाबेस में इस कुंजी से एन्क्रिप्ट होते हैं, इसलिए डंप या बैकअप में केवल सिफ़रटेक्स्ट होता है। बॉक्स से चार्ट पहली इंस्टॉल पर `<release>-secret-key` में एक बनाता है, उसे अपग्रेड में रखता है, और `helm uninstall` पर भी रखता है (`helm.sh/resource-policy: keep`), क्योंकि अपने वॉल्यूम पर रखा डेटाबेस उसके बिना अपने क्रेडेंशियल के लिए बेकार है। यह फ़ाइल के रूप में माउंट होती है और `HOTLOOP_SECRET_KEY_FILE` के रूप में दी जाती है, कभी एनवायरनमेंट वेरिएबल के रूप में नहीं।

Secret का बैकअप डेटाबेस बैकअप से अलग लें: जिन बैकअप की यह रक्षा करती है उनके बगल में रखी कुंजी किसी चीज़ की रक्षा नहीं करती। अपनी कुंजी लाने के लिए `hotloop gen-secret-key` एक छापता है। Kubernetes के बाहर इसे ऐसी फ़ाइल में लिखें जिसे केवल HotLoop पढ़ सके और `HOTLOOP_SECRET_KEY_FILE` को उस पर इंगित करें। कुंजी के बिना HotLoop चलता है, शुरू के लॉग में कहता है कि डिवाइस पासवर्ड वैसे ही सहेजे जाते हैं जैसे टाइप किए गए, और UniFi कंसोल सहेजने से मना कर देता है। पहले से सहेजे क्रेडेंशियल कुंजी के साथ पहली बार शुरू होने पर एन्क्रिप्ट हो जाते हैं। रीस्टोर के लिए इसका क्या अर्थ है, यह [बैकअप और रीस्टोर](/hi/iot/backup/#डिवाइस-क्रेडेंशियल-और-गुप्त-कुंजी) में देखें।

## कॉन्फ़िगरेशन, और सेटिंग्स स्क्रीन क्या बदल सकती है

लगभग हर सेटिंग एनवायरनमेंट वेरिएबल से आती है जिसे चार्ट Helm मान से सेट करता है। यही सही जगह है: यह तय करने वाला कॉन्फ़िगरेशन कि यह प्रक्रिया मशीनरी को कमांड दे सकती है या नहीं, तैनाती का है, समीक्षित, किसी वेब पेज के फ़ॉर्म का नहीं।

**सेटिंग्स** स्क्रीन सब कुछ दिखाती है, हर सेटिंग, उसका प्रभावी मान, वह डेटाबेस, एनवायरनमेंट वेरिएबल या बिल्ट-इन डिफ़ॉल्ट में से कहां से आया, और उसे बदलने वाला वेरिएबल। ज़्यादातर केवल पढ़ने के लिए है, और यही मुद्दा है: जिस सवाल का वह जवाब देती है वह है "यह ऐसा क्यों कर रहा है, और मैं क्या बदलूं?"

चार सेटिंग व्यवहार नहीं, प्लांट की पहचान हैं, और वहां संपादित हो सकती हैं। वे डेटाबेस में सहेजी जाती हैं और तुरंत लागू होती हैं, क्योंकि प्लांट का नाम दोबारा तैनात करने से कहीं ज़्यादा बार बदला जाता है:

| सेटिंग | जिस वेरिएबल को वह बदलती है |
|---|---|
| प्लांट का नाम | `HOTLOOP_PLANT_NAME` |
| साइट ID | `HOTLOOP_SITE_ID` |
| टाइमज़ोन | `HOTLOOP_TIMEZONE` |
| लिखने से पहले पुष्टि | `HOTLOOP_CONFIRM_WRITES` |

सेटिंग्स के नीचे वे कार्ड हैं जो कॉन्फ़िगरेशन नहीं, डेटा हैं, और उसी कारण संपादित हो सकते हैं: **यूज़र** ([प्रमाणीकरण और यूज़र](/hi/iot/authentication/)), **अलार्म एस्केलेशन**, जो बताता है कि जब कोई अलार्म स्वीकार न करे तो आगे किसे और कब सूचित किया जाए ([अलार्म सूचनाएं](/hi/iot/notifications/#एस्केलेशन)), और हिस्टोरियन गंतव्य व MQTT लॉगिन। जिन चैनलों का एस्केलेशन उपयोग कर सकता है वे अब भी तैनाती के हैं, `HOTLOOP_NOTIFY_*` से सेट।

सहेजा हुआ मान एनवायरनमेंट वेरिएबल पर भारी पड़ता है, इसलिए चार्ट का मान आख़िरी बात नहीं, शुरुआती बिंदु बन जाता है। जिस टाइमज़ोन को मशीन हल नहीं कर सकती वह स्वीकार करके चुपचाप अनदेखा करने के बजाय अस्वीकार कर दिया जाता है, जिससे हर टाइमस्टैंप बिना कारण बताए UTC पर लौट जाता।

तैनाती के अपने मान पर भी यही लागू होता है। अगर `HOTLOOP_TIMEZONE` (या `TZ`, जब वह सेट न हो) ऐसा ज़ोन बताए जो लोड नहीं होता, तो HotLoop शुरू होने से मना कर देता है और त्रुटि में वेरिएबल और मान का नाम होता है। पहले वह कंधे उचकाकर UTC पर चलता था। रिपोर्ट, शेड्यूल और शिफ़्ट के समय सब प्लांट की घड़ी पर चलते हैं, और घंटों ग़लत अंदाज़ा उस पॉड से बुरा है जो बताता है कि वह क्यों नहीं उठ रहा।

साइट का स्थान `HOTLOOP_SITE_LATITUDE` और `HOTLOOP_SITE_LONGITUDE` है (चार्ट: `plant.latitude`, `plant.longitude`), दशमलव डिग्री, उत्तर और पूर्व धनात्मक। सूर्योदय, सूर्यास्त और सूर्य की एंटिटी व ट्रिगर इनसे बॉक्स पर ही निकाले जाते हैं ([सूर्य](/hi/iot/sun/))। दोनों या कोई नहीं, और ग़लत मान वेरिएबल का नाम बताकर शुरू होना रोक देता है। सेटिंग्स स्क्रीन इन्हें केवल पढ़ने के लिए दिखाती है: नियम सूर्योदय पर चलते हैं, इसलिए उसे हिलाना एक तैनाती है।

**सुरक्षा स्विच संपादन योग्य नहीं हैं और नहीं होंगे।** `HOTLOOP_ALLOW_WRITES` इस पर मास्टर नियंत्रण है कि यह प्रक्रिया उपकरण को कमांड दे सकती है या नहीं; जो नियंत्रण उसी ब्राउज़र सेशन से वापस चालू हो सके जो लिखने जारी करता है, वह नियंत्रण नहीं है। `HOTLOOP_HISTORIAN_RETENTION_DAYS` भी इसी तरह केवल तैनाती का है: रिटेंशन नीति शुरू होते समय डेटाबेस पर लागू होती है, इसलिए स्क्रीन का एक फ़ील्ड काम करता दिखता और कोई डेटा नहीं हिलाता। एंडपॉइंट संपादन योग्य समूह के बाहर की किसी भी कुंजी को अनदेखा करने के बजाय **नाम लेकर** अस्वीकार करता है।

एक सीमा, जो इसलिए बताई गई क्योंकि स्क्रीन भी बताती है: MCP सर्वर अपने निर्देश शुरू होते समय बनाता है, इसलिए पॉड रीस्टार्ट होने तक वह उस प्लांट नाम का प्रचार करता है जिसके साथ वह शुरू हुआ था। बाक़ी सब कुछ नाम बदलने को अगले अनुरोध पर उठा लेता है।

## PostgreSQL 17

HotLoop का डेटाबेस PostgreSQL 17 है (Edge और Gateway के लिए उस पर TimescaleDB 2.30.1, IoT और `database.type: postgresql` के लिए सादा PostgreSQL 17.11)। इससे पहले के रिलीज़ PostgreSQL 16 चलाते थे, और PostgreSQL दूसरे मेजर संस्करण की डेटा डायरेक्टरी नहीं खोलता। इसलिए यह बदलाव आपके लिए अपग्रेड में हो जाता है, और चलाने को कुछ नहीं है।

**चार्ट पर,** डेटाबेस पॉड को दो init कंटेनर मिलते हैं। पहला PostgreSQL 16 इमेज चलाता है और, केवल जब वॉल्यूम में 16 का डेटा हो, उस इंस्टॉल को एक अस्थायी वॉल्यूम में कॉपी करता है। दूसरा नई इमेज चलाता है और पुरानी के बगल की नई डायरेक्टरी में `pg_upgrade` करता है। दोनों नए वॉल्यूम को, या जो पहले से 17 पर है उसे, अकेला छोड़ देते हैं। अपग्रेड `helm upgrade` है, और कुछ नहीं। मानकर चलें कि डेटाबेस पॉड उतनी देर `Init` में रहेगा जितनी देर डेटा की कॉपी में लगे, और ऐप उसका इंतज़ार करेगा; `kubectl logs <release>-postgresql-0 -c pg-upgrade` उसका लॉग है।

**Quadlet पर,** `hotloop-db-upgrade.container`, `hotloop-db.service` से पहले चलता है और oneshot यूनिट में वही करता है। अपने उत्पाद की डायरेक्टरी से नए `hotloop-db.container`, `hotloop-db-upgrade.container` और `hotloop-db-upgrade.sh` को यूनिट डायरेक्टरी में कॉपी करें और डेटाबेस यूनिट रीस्टार्ट करें; कमांड [Quadlet README](/hi/install/quadlet/) में हैं। डेटाबेस यूनिट को अपग्रेड यूनिट चाहिए, इसलिए जिस बॉक्स को केवल नई डेटाबेस यूनिट मिली वह 16 के डेटा पर शुरू नहीं होता और बताता है कि क्यों: वह विफल होता है, अंदाज़ा नहीं लगाता। `journalctl -u hotloop-db-upgrade` उसका लॉग है। यूनिट केवल तब चलती है जब वॉल्यूम में 16 का डेटा हो: नए बॉक्स पर, और अपग्रेड के बाद हर शुरुआत पर, systemd उसे छोड़ देता है (वह निष्क्रिय दिखती है, विफल नहीं) और PostgreSQL 16 इमेज कभी खींची नहीं जाती। जब वॉल्यूम में 16 का डेटा हो, यूनिट पहले वह इमेज खींचती है।

वह क्या करता है, क्रम से, सब `hotloop-pg-upgrade.sh` में (एक फ़ाइल, वही जो चार्ट और यूनिटें चलाती हैं):

1. कोई डेटा डायरेक्टरी नहीं, या पहले से 17 पर: कुछ नहीं, और वह यह बताता है। कोई भी दूसरा मेजर संस्करण बिना कुछ बदले अस्वीकार कर दिया जाता है।
2. पुराने सर्वर को एक बार निजी सॉकेट पर शुरू करता है और साफ़ तरीक़े से रोकता है, जो बिजली जाने के बाद का लॉग दोहराता है और वह एन्कोडिंग व लोकेल पढ़ता है जिससे नए क्लस्टर को मेल खाना है।
3. उन सेटिंग के साथ पुरानी डायरेक्टरी के बगल में नई डायरेक्टरी `initdb` करता है, कॉपी मोड में `pg_upgrade` चलाता है (पुरानी डायरेक्टरी केवल पढ़ी जाती है), और `postgresql.conf`, `postgresql.auto.conf`, `pg_hba.conf` और `pg_ident.conf` को साथ ले जाता है।
4. नए सर्वर को एक बार शुरू करता है यह साबित करने के लिए कि वह अंतिम सेटिंग पर खुलता है, और वे प्लानर आंकड़े जुटाता है जो `pg_upgrade` साथ नहीं ले जाता।
5. तभी नाम बदलता है: पुरानी डायरेक्टरी `pgdata.pg16` बन जाती है, नई `pgdata`।

इसे डेटा के बगल में उतनी ही ख़ाली जगह चाहिए जितनी डेटा लेता है, और शुरू करने से पहले जांच लेता है। अगर चरण 5 से पहले कुछ भी विफल हो, तो अपग्रेड शून्य से अलग कोड के साथ निकलता है, 16 का डेटा बिल्कुल वैसा रहता है जैसा था, और डेटाबेस आधी बनी डायरेक्टरी पर शुरू नहीं होता: चार्ट पर पॉड `Init:Error` में रहता है, Quadlet पर अपग्रेड यूनिट विफल होती है और उसके पीछे की डेटाबेस यूनिट कभी शुरू नहीं होती। जो लॉग कहे उसे ठीक करें और फिर शुरू करें; अधूरी कोशिश हटाकर दोबारा की जाती है। TimescaleDB एक्सटेंशन उसी संस्करण पर आता है जिस पर वह था, और ऐप उसे अगली शुरुआत पर भेजे गए संस्करण पर अपडेट करता है, जैसा हमेशा करता है। जगह पर PostgreSQL अपग्रेड के लिए TimescaleDB का अपना मार्गदर्शन पुराने और नए बाइनरी के साथ `pg_upgrade` है ([Tiger Data, "Upgrade PostgreSQL"](https://www.tigerdata.com/docs/deploy/self-hosted/upgrades/upgrade-pg))।

बैकअप पुरानी डायरेक्टरी ही है। कॉपी मोड का `pg_upgrade` उसमें कभी नहीं लिखता, इसलिए `pgdata.pg16` वैसा ही पूरा PostgreSQL 16 डेटाबेस है जैसा वह था, जो डंप से बेहतर बैकअप है और वह इकलौती चीज़ है जो नीचे के वापसी के रास्ते को संभव बनाती है। HotLoop का अपना बैकअप ([बैकअप और रीस्टोर](/hi/iot/backup/)) चल रहा ऐप चल रहे डेटाबेस के ज़रिए लेता है, इसलिए वह उस चरण में नहीं लिया जा सकता जो डेटाबेस शुरू होने से पहले चलता है। फिर भी अपग्रेड से पहले पुराने रिलीज़ पर एक लें और उसे बॉक्स के बाहर कॉपी करें।

### वापस जाना

`helm rollback`, या पिछला `hotloop-db.container` वापस रखना, डेटाबेस को PostgreSQL 16 इमेज पर लौटाता है (Podman का ऑटो-अपडेट ऐसा नहीं करता: वह केवल ऐप को हिलाता है), और PostgreSQL 16 17 की डायरेक्टरी नहीं खोलता (`database files are incompatible with server`, लॉग कहता है कि डायरेक्टरी संस्करण 16 से इनिशियलाइज़ हुई थी)। कुछ खोता नहीं और कुछ आधा बदला नहीं होता; डेटाबेस बस शुरू नहीं होता। पिछले रिलीज़ को अपनी 16 की डायरेक्टरी चाहिए, जो `pgdata.pg16` है। डेटाबेस रोकें, फिर नाम वापस रखें:

```sh
# chart: after the rollback, stop the database, swap in a one-off pod, start it
kubectl -n hotloop scale statefulset/hotloop-postgresql --replicas=0
kubectl -n hotloop run pgswap --rm -it --restart=Never --image=busybox \
  --overrides='{"spec":{"securityContext":{"runAsUser":999,"fsGroup":999},"containers":[{"name":"pgswap","image":"busybox","command":["sh","-c","cd /d && mv pgdata pgdata.pg17 && mv pgdata.pg16 pgdata"],"volumeMounts":[{"name":"d","mountPath":"/d"}]}],"volumes":[{"name":"d","persistentVolumeClaim":{"claimName":"data-hotloop-postgresql-0"}}]}}'
kubectl -n hotloop scale statefulset/hotloop-postgresql --replicas=1

# Quadlet: the volume is named hotloop-db
sudo systemctl stop hotloop.service hotloop-db.service
d=$(sudo podman volume inspect hotloop-db --format '{{.Mountpoint}}')
sudo mv "$d/pgdata" "$d/pgdata.pg17" && sudo mv "$d/pgdata.pg16" "$d/pgdata"
```

यह डेटाबेस वैसा है जैसा अपग्रेड के समय था, और तब से कुछ लिखा नहीं गया। वापस अदला-बदली केवल एक बार काम करती है: अपग्रेड तब तक चलने से मना करता है जब तक रास्ते में `pgdata.pg16` है, इसलिए अगली अपग्रेड कोशिश के लिए पहले `pgdata.pg17` और पुरानी डायरेक्टरी को निपटाना होगा। आगे बढ़ना रास्ता है, और रोलबैक उस बॉक्स के लिए है जो 17 चला ही नहीं सकता। ऐप का अपना रोलबैक नियम नहीं बदला: 16 की डायरेक्टरी का स्कीमा वह है जो अपग्रेड से पहले के रिलीज़ ने छोड़ा था, और जो रिलीज़ ऐसे माइग्रेशन पाता है जिन्हें वह नहीं जानता वह यह बताता है, देखें [माइग्रेशन केवल जोड़ते हैं](/hi/iot/migrations/)।

### जब आप संतुष्ट हों

`pgdata.pg16` तब तक रहता है जब तक आप उसे मिटा न दें, क्योंकि उसे मिटाना वापसी का इकलौता रास्ता मिटाना है। वह डेटाबेस जितना ही बड़ा है। जब बॉक्स 17 पर उतनी देर चल चुका हो जितनी आप चाहें:

```sh
# chart
kubectl -n hotloop exec hotloop-postgresql-0 -c postgresql -- rm -rf /var/lib/postgresql/data/pgdata.pg16
# Quadlet
sudo rm -rf "$(sudo podman volume inspect hotloop-db --format '{{.Mountpoint}}')/pgdata.pg16"
```

### इसे बंद करना

`database.postgresql.upgrade.enabled: false` init कंटेनर हटा देता है। तब 16 पर रहा वॉल्यूम डेटाबेस को शुरू होने से रोकता है, और बदलाव आपका काम बन जाता है। इसे चालू रहने दें: चालू होने पर भी नई इंस्टॉल हर नोड पर एक बार PostgreSQL 16 इमेज खींचती है क्योंकि init कंटेनर की इमेज चलने से पहले खींची जाती है, और फिर उसे कभी चलाती नहीं।

## 3.x से अपग्रेड

**यह प्रतिस्थापन है, अपग्रेड नहीं।** 3.x एक अलग उत्पाद था। उसके डेटा के लिए कोई माइग्रेशन रास्ता नहीं है, क्योंकि वह टैग हिस्टोरियन के साथ कोई डेटा मॉडल साझा नहीं करता।

```bash
helm uninstall hotloop -n hotloop
# keep or delete the old PVCs deliberately, they hold the HA recorder database
helm install hotloop ./charts/hotloop -n hotloop
```

वे चीज़ें जो अब मौजूद नहीं हैं और सेट करने पर अस्वीकार होंगी: `sidecarProxy`, `homeassistant`, `mqtt`/`nodered`/`esphome`/`zigbee2mqtt` ऐड-ऑन, `devices`, `cameras`, `customConfig`, `network.hostNetwork`।

## अपडेट रोलबैक करना

`helm rollback hotloop -n hotloop` पिछले रिलीज़ की इमेज वापस रखता है। वह डेटाबेस वापस नहीं रखता: रिलीज़ शुरू होने पर माइग्रेट करता है, और वह हो चुका रहता है। नियम और जांच [माइग्रेशन केवल जोड़ते हैं](/hi/iot/migrations/) में हैं।

PostgreSQL 17 रिलीज़ के आर-पार रोलबैक जो एक चीज़ वापस रखता है वह डेटाबेस इंजन है: चार्ट की डेटाबेस इमेज 16 पर लौट जाती है, जो अपग्रेड की गई डायरेक्टरी नहीं खोलेगी। [वापस जाना](#वापस-जाना) निकलने का रास्ता है।

यह एक रिलीज़ पीछे तक सुरक्षित है। डेटाबेस दर्ज करता है कि हर माइग्रेशन किस रिलीज़ ने लागू किया, और जो रिलीज़ अपने से दो या अधिक रिलीज़ नए माइग्रेशन पाता है वह शुरू होने से मना कर देता है:

```
refusing to start: this database's schema is more than one release ahead of
HotLoop 4.18.10. ...
```

यह ऐसी ख़राबी नहीं जिसके इर्द-गिर्द काम किया जाए। इसका मतलब है कि डेटाबेस उससे आगे जा चुका है जितना यह रिलीज़ कभी चला है। ऐसे रिलीज़ पर आगे बढ़ें जो स्कीमा जानता हो, यानी सबसे नए पर, या उस रिलीज़ का लिया बैकअप रीस्टोर करें जिस पर आप हैं ([बैकअप और रीस्टोर](/hi/iot/backup/))। ठीक एक रिलीज़ पीछे शुरू होता है, लॉग में दोनों संस्करणों के नाम वाली चेतावनी के साथ। अपग्रेड से पहले बैकअप लें; रोलबैक वह डेटा पूर्ववत नहीं कर सकता जो नए रिलीज़ ने लिखा।

## इंस्टॉल की जांच

```bash
kubectl -n hotloop get pods
kubectl -n hotloop logs deploy/hotloop | head -20
```

स्वस्थ शुरुआत बताती है कि वह कौन से प्रोटोकॉल बोलता है, माइग्रेशन लागू करती है, इतिहास मोड बताती है, और जानने लायक हर बात पर चेतावनी देती है:

```
msg=starting version=4.0.0 protocols="[ethernet-ip http modbus mqtt mtconnect opcua s7comm]"
msg="writes are ENABLED: the UI, API, automations and MCP can all command devices"
msg="tag_history promoted to a hypertable" timescale=2.30.1
msg="history schema ready" mode=timescale
msg=listening addr=:8080 mcp=/mcp writes=true
```

फिर वे लेबल जांचें जो डैशबोर्ड को चाहिए। यही वह जांच है जो भटकाव पकड़ती है, **समूह** जांचें, गिनती नहीं, क्योंकि गिनती की जांच तब भी पास हो जाती है जब समूह ग़लत हो:

```bash
kubectl -n hotloop get svc <release> -o json \
  | jq -r '.metadata.labels | keys[] | select(startswith("embernet.ai/"))'
```

ठीक चार, Service पर और पॉड पर:

```
embernet.ai/app-name
embernet.ai/gui-port
embernet.ai/gui-type
embernet.ai/store-app
```

अगर ऐप चल रहा है लेकिन चल रहे ऐप में नहीं दिखता, तो Service के लेबल देखने की पहली जगह हैं: डैशबोर्ड Service को `embernet.ai/store-app` से क्वेरी करता है।

App Store से तैनाती पांच और जोड़ती है, उन `tenantLabels` से जो डैशबोर्ड देता है: `embernet.ai/tenant`, `app-id`, `source`, `deployed-by` और `deployment-id`। वे चार्ट के रेंडर किए हर संसाधन पर और गेटवे पॉड पर लगते हैं। डैशबोर्ड टेनेंट को Service से पढ़ता है और कहीं और से नहीं, इसलिए Service पर `embernet.ai/tenant` के बिना स्टोर से तैनात Gateway किसी का नहीं है। सादा `helm install` इन पांच में से कोई रेंडर नहीं करता।

## प्रोब

- `/healthz`, liveness। प्रक्रिया चलने तक जवाब देता है।
- `/readyz`, readiness। इसके अलावा डेटाबेस भी चाहिए, इसलिए जिस पॉड ने अपना हिस्टोरियन खो दिया वह ऐसा इंटरफ़ेस परोसने के बजाय ट्रैफ़िक लेना बंद कर देता है जो कुछ जवाब नहीं दे सकता।

स्टार्टअप प्रोब दो मिनट देता है, क्योंकि पहली इंस्टॉल माइग्रेशन चलाती है और liveness प्रोब को उसे माइग्रेशन के बीच में नहीं मारना चाहिए।

## शटडाउन

`terminationGracePeriodSeconds: 45`। SIGTERM पर ऐप अनुरोध लेना बंद कर देता है, फिर हिस्टोरियन कतार ख़ाली करता है ताकि पहले ली जा चुकी रीडिंग फेंकी न जाएं, लिख दी जाएं। ग्रेस अवधि बहुत छोटी कर देने से जो कुछ रास्ते में था वह खो जाता है।

## समस्या निवारण

**डिवाइस `connecting` में अटका है।** डिवाइस कार्ड पर `lastError` देखें। अक्सर पॉड और उपकरण के बीच फ़ायरवॉल, या ग़लत पोर्ट। चार्ट egress नहीं रोकता, इसलिए उसे रोकने वाली NetworkPolicy क्लस्टर पर कोई और चीज़ है।

**टैग ख़राब गुणवत्ता पढ़ते हैं।** डिवाइस ने जवाब दिया लेकिन उस बिंदु ने नहीं। Modbus के लिए पता आधार जांचें, `oneBased` अगर आपके ड्रॉइंग 40001 क्रमांकन इस्तेमाल करते हैं। OPC UA के लिए जांचें कि नोड id हल हुआ; `nsu=` रूप को प्राथमिकता दें।

**मान विश्वसनीय लगते हैं पर ग़लत हैं।** Modbus पर यह शब्द क्रम है, `CDAB` आज़माएं। यह वह विफलता है जो ख़ुद नहीं बताती, क्योंकि संख्या साफ़ तौर पर ग़लत नहीं दिखती।

**कुछ भी हिस्टोराइज़ नहीं हो रहा।** प्रोटोकॉल स्क्रीन का डायग्नोस्टिक जांचें। `filtered` डेडबैंड से दबाई गई रीडिंग गिनता है, जो इरादे के अनुसार काम करना है; `dropped` उन रीडिंग को गिनता है जो इसलिए खोईं कि डेटाबेस साथ नहीं दे सका, जो ऐसा नहीं है।

**MCP 401 लौटाता है।** बियरर टोकन। इसे रिलीज़ के Secret से पढ़ें।

**हर `/api/` अनुरोध 401 लौटाता है।** अपेक्षित है जब `auth.enabled` true हो और अभी किसी ने लॉग इन न किया हो, यही 4.4.0 का मक़सद है। रिलीज़ के Secret से बनाया गया एडमिन पासवर्ड पढ़ें (देखें [प्रमाणीकरण](#प्रमाणीकरण)) और UI से लॉग इन करें, या सीधे `POST /api/auth/login`। देखें [प्रमाणीकरण और यूज़र](/hi/iot/authentication/)।

**एडमिन पासवर्ड खो गया और कोई दूसरा एडमिन खाता नहीं है।** नया हैश बनाएं और Secret को पैच करें, फिर पॉड रीस्टार्ट करें ताकि वह एनवायरनमेंट दोबारा पढ़े; `EnsureAdminUser` पहले से मौजूद खाते को नहीं छूएगा, इसलिए यह चार्ट से गुज़रने के बजाय पंक्ति को सीधे बदलता है:

```bash
hotloop hash-password -password 'a-new-one'
kubectl exec -n hotloop deploy/hotloop -- \
  psql "$DATABASE_URL" -c \
  "UPDATE users SET password_hash = '<the hash>' WHERE username = 'admin'"
```

**कोई ऑटोमेशन चालू है लेकिन चल नहीं रहा।** वह कंपाइल नहीं हुआ। ऑटोमेशन स्क्रीन उसे कारण के साथ NOT ARMED दिखाती है, और सिस्टम लॉग में त्रुटि है।
