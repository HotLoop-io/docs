공장에는 이미 스스로를 정리하는 방식이 있고, 공장이 가진 모든 SCADA, MES, 히스토리안이 그 방식을 씁니다. 바로 ISA-95입니다. 기업, 사이트, 구역, 라인, 셀, 유닛, 설비. HotLoop도 그대로 씁니다. 층별 목록, 구역별 목록, 장치별 목록을 따로 두지 않고 하나의 트리로 관리합니다. 여기에 무엇이 달리는지는 [엔티티](/ko/iot/entities/)를 참고하십시오.

## 레벨

| 레벨 | 보통 가리키는 것 |
|---|---|
| `enterprise` | 회사 |
| `site` | 공장 한 곳 |
| `area` | 부서 또는 건물: 포장, 유틸리티, 탱크 구역 |
| `line` | 생산 라인 |
| `cell` | 라인의 작업 셀, 또는 배치 공장의 공정 셀 |
| `unit` | 생산 유닛: 반응기, 칠러, 가열로 |
| `equipment` | 기계 또는 기계의 일부: 펌프, 스키드, 모터 |

자식은 항상 부모보다 낮은 레벨이며, 따라서 사이트가 라인 아래에 들어가는 일은 없습니다. 레벨을 건너뛸 수는 있습니다. 구역 바로 아래의 유닛도 괜찮고, 구역이 없는 공장에서는 사이트 바로 아래의 라인도 괜찮습니다. 유일한 예외는 `equipment` 안의 `equipment`입니다. 스키드에는 펌프가 있고 펌프에는 모터가 있으며, ISA-95가 레벨 이름 짓기를 멈추는 것은 공장이 설비를 겹쳐 두기를 멈추는 것보다 훨씬 이르기 때문입니다. 노드는 어떤 레벨이든 루트에 둘 수 있으며, 대부분의 공장은 `site`에서 시작합니다.

레벨과 이름이 같은 형제 두 개는 같은 장소이므로, 트리는 두 번째를 거부합니다.

노드는 자기 자신의 조상이 될 수 없습니다. 노드를 자기 자신 아래나 그 아래의 어떤 노드 밑으로 옮기는 것은 거부됩니다. 루프가 생기는 유일한 경로는 `equipment` 테이블을 직접 손으로 편집하는 것입니다. 누군가 그렇게 해도 트리를 순회하는 어떤 동작도 멈추지 않으며, 루프 안의 노드를 바꾸려 하면 해당 노드의 이름과 함께 그중 하나의 `parent_id`를 NULL로 설정하라는 메시지가 표시되고 거부됩니다.

## 사이트, 구역, 라인 텍스트도 계속 동작합니다

모든 장치는 트리가 생기기 전부터 자유 텍스트 필드 `site`, `area`, `line`을 갖고 있었습니다. 이 필드는 없어지지 않습니다. 4.15의 장치 편집기가 이 필드를 쓰고, `list_devices`와 `describe_device`가 읽으며, 이를 바탕으로 누군가 작성한 모든 에이전트와 스크립트도 마찬가지입니다. 그래서 텍스트와 트리는 변경과 같은 트랜잭션 안에서 양방향으로 맞춰집니다.

**텍스트만 있고 `equipmentId`가 없는 장치를 저장하면** 텍스트가 가리키는 사이트, 구역, 라인을 찾거나 각각 앞의 것 아래에 만들고, 장치를 가장 깊은 노드에 둡니다. 텍스트가 같은 두 장치는 같은 노드에 놓이며, 중복이 생기는 일은 없습니다. 보낸 텍스트는 그대로 저장됩니다. 트리를 전혀 모르는 클라이언트는 항상 받던 응답에 무시해도 되는 `equipmentId`가 더해진 응답을 받습니다.

**장치를 옮기는 `equipmentId`와 함께 저장하면** 함께 온 텍스트와 상관없이 노드의 경로에서 텍스트를 가져옵니다. 장치를 `Plant A / Packing / Line 2` 아래의 셀에 두면 텍스트는 `Plant A`, `Packing`, `Line 2`가 됩니다.

트리를 모르는 클라이언트에도 안전하도록 두 가지 세부 규칙이 있습니다.

- 장치의 현재 노드가 말하는 내용과 같은 텍스트는 장치를 제자리에 둡니다. 텍스트에는 세 개의 열밖에 없으므로, 라인 아래의 셀이나 기계에 있는 장치는 라인까지만 말할 수 있습니다. 같은 텍스트로 저장해도 장치가 라인으로 올라가지 않습니다.
- 장치를 읽은 뒤 `equipmentId`를 포함한 전체를 텍스트만 고쳐 되돌려 보내는 클라이언트는 텍스트 편집이 적용됩니다. 되돌려 보낸 `equipmentId`는 장치가 이미 갖고 있던 것이므로 이동이 아니며, 텍스트가 결정합니다.

사이트는 루트가 아니어도 어디에 있든 찾아지므로, 기업 아래에 `Plant A`를 두어도 다음에 `Plant A`라고 말하는 장치가 두 번째 사이트를 만들지 않습니다.

**노드의 이름을 바꾸거나 옮기면** 그 노드와 그 아래에 있는 모든 장치의 텍스트가 같은 트랜잭션 안에서 다시 쓰입니다. 하나라도 실패하면 아무 일도 일어나지 않은 것이 됩니다. 트리와 장치 텍스트가 서로 다르게 말하는 상태야말로 둘을 맞춰 두려는 목적이 막으려던 일이기 때문입니다. 응답과 시스템 로그에는 텍스트가 바뀐 모든 장치가 나열됩니다.

### 업그레이드

마이그레이션 `0006_hierarchy.sql`은 기존 장치가 이미 가진 텍스트로 트리를 만듭니다. 서로 다른 사이트 이름마다 사이트 하나, 사이트 아래의 서로 다른 구역 이름마다 구역 하나, 구역 아래의 서로 다른 라인마다 라인 하나를 만들고, 각 장치는 텍스트가 가리키는 가장 깊은 노드에 놓습니다. 구역은 있고 사이트는 없는 장치는 루트 구역을 받고, 라인은 있고 구역은 없는 장치는 사이트 바로 아래의 라인을 받습니다. 공백뿐인 텍스트는 아무것도 가리키지 않습니다. 텍스트는 공백과 대소문자까지 저장된 그대로 사용합니다. 트리의 이름이 나중에 텍스트를 다시 쓰는 근거가 되므로, 업그레이드 중에 공백을 잘라 내면 군더더기 공백이 있던 모든 장치의 이름이 몰래 바뀌는 셈이 되기 때문입니다. 업그레이드로 바뀌는 장치 텍스트는 없습니다.

Go 쪽도 같은 규칙으로 장치를 배치하며, 테스트가 둘을 일치시킵니다. 업그레이드가 배치한 모든 장치는 건드리지 않고 다시 저장해도 제자리에 남고 트리를 하나도 늘리지 않습니다.

## 노드 삭제

**아래에 무엇이든 있는 노드는 거부됩니다.** 자식 노드나 그 위에 놓인 장치가 해당됩니다. 먼저 옮기십시오. 거부 메시지가 걸림돌이 무엇인지 알려 줍니다.

대안은 자식을 삭제된 노드의 부모로 옮겨 붙이는 것이었습니다. 그러면 아래의 모든 장치가 움직이고 텍스트가 다시 쓰이는데, 아무도 건드리지 않은 노드 밑에서 일어나는 일이며, 구역 없이 사이트 바로 아래에 라인이 놓이는, 누구도 그리지 않은 트리가 만들어질 수 있습니다. 반대로 장치의 배치만 해제하면 텍스트는 더 이상 없는 장소를 가리키게 되고, 그중 하나를 다음에 저장할 때 노드가 조용히 다시 만들어집니다. 둘 다 예상 밖의 일입니다. 무엇을 옮겨야 하는지 알려 주는 거부는 그렇지 않습니다.

삭제된 노드에 놓여 있던 엔티티는 배치를 잃고 다시 자기 장치를 따릅니다.

## 트리 위의 엔티티

이제 모든 엔티티 응답에 필드가 세 개 더 들어 있습니다.

| 필드 | 내용 |
|---|---|
| `equipment_id` | 엔티티 자체가 놓인 위치. 장치가 가는 곳을 그대로 따르면 null |
| `area_id` | 엔티티 자신의 노드 또는 그 위에서 가장 가까운 `area`. 자신의 노드가 없으면 장치의 노드. 구역별로 묶는 모든 기능이 이 필드를 읽습니다. 위에 구역이 없으면 null |
| `labels` | 엔티티의 label_id 목록 |

엔티티 자신의 위치가 장치의 위치보다 우선합니다. PLC 전체가 하나의 장치인 경우에 중요합니다. 온도 태그는 가열로에, 칠러 태그는 유틸리티에 속합니다. 엔티티는 `PUT /api/entities/{entity_id}`로 배치합니다.

```json
{ "equipment_id": 42, "labels": ["critical"] }
```

`"equipment_id": null`은 다시 장치를 따르게 합니다. `labels`는 전체 집합을 바꿉니다. 둘 다 다른 모든 레지스트리 필드처럼 `entities.write`가 필요합니다.

## 레이블

레이블은 흔히 말하는 태그입니다. `critical`, `line 1 utilities`, `calibrate quarterly` 같은 것입니다. 장치와 엔티티는 레이블을 몇 개든 가질 수 있습니다.

레이블에는 `label_id`와 `name`이 있습니다. `label_id`는 처음에 이름에서 만들어지고(소문자, 숫자, 밑줄이며 충돌하면 `_2`, `_3`을 붙입니다) 절대 바뀌지 않습니다. 자동화와 화면이 이것을 참조하기 때문입니다. 이름은 언제든 바꿀 수 있습니다. 레이블을 만들 때 `label_id`를 직접 정할 수도 있습니다.

레이블을 삭제하면 그것을 가진 모든 항목에서 제거됩니다.

장치 레이블은 `POST /api/devices`가 아니라 `PUT /api/devices/{id}/labels`로 설정합니다. 지금 장치를 저장하는 모든 클라이언트는 레이블 없이 장치 전체를 보내므로, 저장할 때마다 레이블이 지워질 것입니다.

## API

설비와 레이블 엔드포인트는 엔티티 엔드포인트처럼 snake_case 필드 이름을 씁니다. 트리가 엔티티 모델의 구역 레지스트리이고 같은 소비자에 맞춰 만들어졌기 때문입니다. 장치에 새로 생긴 필드는 나머지 장치 API처럼 camelCase인 `equipmentId`입니다.

| 엔드포인트 | 권한 | 내용 |
|---|---|---|
| `GET /api/equipment` | `equipment.read` | 모든 노드와 루트부터의 이름 `path`. 필터: `?level=` |
| `GET /api/equipment/{id}` | `equipment.read` | `{"equipment", "children", "devices", "entities"}`: 노드, 바로 아래 노드, 그리고 바로 위에 놓인 항목 |
| `POST /api/equipment` | `equipment.write` | `{"parent_id", "level", "name", "description"}` |
| `PUT /api/equipment/{id}` | `equipment.write` | `name`, `description`, `level`, `parent_id` 중 아무거나(루트는 null). `{"equipment", "devices_rewritten"}`로 응답 |
| `DELETE /api/equipment/{id}` | `equipment.write` | 아래에 무엇이든 있으면 409로 거부 |
| `GET /api/labels` | `equipment.read` | 모든 레이블 |
| `GET /api/labels/{label_id}` | `equipment.read` | 레이블을 가진 `{"label", "devices", "entities"}` |
| `POST /api/labels` | `equipment.write` | `{"label_id"?, "name", "color", "icon", "description"}` |
| `PUT /api/labels/{label_id}` | `equipment.write` | 이름, 색상, 아이콘, 설명. label_id는 절대 바꾸지 않음 |
| `DELETE /api/labels/{label_id}` | `equipment.write` | 모든 항목에서 제거 |
| `PUT /api/devices/{id}/labels` | `equipment.write` | `{"labels": [...]}`, 전체 집합 |
| `POST /api/devices` | `devices.write` | 위에서 설명한 선택 항목 `equipmentId`가 추가됨 |
| `GET /api/devices/{id}` | `devices.read` | `device`, `tags` 옆에 `labels`가 추가됨 |

모든 역할이 `equipment.read`를 가집니다. 사물이 어디에 있는지는 장치의 사이트와 구역이 이미 조회자에게 알려 주던 내용이기 때문입니다. `equipment.write`는 관리자만 가집니다. 노드 하나의 이름을 바꾸거나 옮기면 그 아래 모든 장치의 사이트, 구역, 라인이 다시 쓰이고, 이는 구성에 해당하기 때문입니다.

모든 변경은 시스템 로그에 기록됩니다. 카테고리는 `config`, 대상은 `equipment:<id>` 또는 `label:<label_id>`입니다.

## MCP

`list_devices`와 `describe_device`는 예전처럼 텍스트에서 응답하며 출력은 바뀌지 않습니다. 테스트가 출력을 트리 이전 버전의 응답과 바이트 단위로 고정한 뒤, 장치 주변의 트리를 재배열(사이트 위에 기업, 라인 아래에 셀, 레이블)하고 에이전트가 보는 것이 하나도 움직이지 않았는지 확인합니다. 이름 변경처럼 트리가 텍스트를 실제로 바꾸면 에이전트는 누군가 장치에 직접 입력한 것과 똑같이 새 텍스트를 봅니다. 에이전트가 트리를 보는 곳은 `list_entities`입니다. 노드와 그 아래 전체로 필터링하고 각 엔티티의 위치를 알려 줍니다. [MCP](/ko/iot/mcp/#엔티티)를 참고하십시오.

## 백업과 복원

`equipment`, `labels`, `entity_labels`, `device_labels`는 백업에 포함되며, 새 `equipment_id` 열도 마찬가지입니다. `equipment`는 자기 자신을 참조(`parent_id`)하는데, 복원은 이를 순서대로 정렬할 수 없습니다. 노드를 옮기고 나면 부모가 자식보다 뒤에 저장되는 일이 얼마든지 생기기 때문입니다. 이 제약은 `DEFERRABLE INITIALLY DEFERRED`이므로 복원이 커밋될 때, 모든 행이 들어간 뒤에 검사되며, 트리를 둘 이상의 문장으로 다시 쓰는 다른 모든 작업도 마찬가지입니다. 백업 가드 테스트는 제약이 지연된 경우에만 테이블이 자기 자신을 참조하도록 허용하고, 왕복 테스트는 일부러 자식을 부모보다 먼저 저장합니다.

이 버전 이전에 만든 백업도 그대로 복원됩니다. 그 백업의 `devices`와 `entities` 파일에는 열이 하나 적습니다. 복원은 이를 테이블의 앞쪽 열에 불러오고(새 열은 항상 끝에 추가됩니다) 새 열에는 기본값이 들어갑니다. 그런 다음 같은 트랜잭션 안에서 업그레이드가 했을 방식대로 복원된 모든 장치를 텍스트에 따라 트리에 배치합니다.

## 공장 화면

옆쪽에 트리가 있고, 선택한 노드의 카드가 표시됩니다. 경로, 그 위의 장치, 그 위에 놓인 엔티티, 그리고 그 아래에 있는 것이 나옵니다. 관리자는 루트 또는 선택한 노드 아래에 노드를 추가하고, 이름 변경, 레벨 변경, 이동, 삭제를 하고, 장치를 놓거나 빼고, 장치의 레이블을 설정할 수 있습니다. 레벨 목록에는 부모와 이미 아래에 있는 자식 모두에 대해 규칙이 허용하는 레벨만 나오고, 이동에는 해당 레벨의 노드가 들어갈 수 있는 부모만 나오며, 노드 자신이나 그 아래의 어떤 노드도 나오지 않습니다. 서버가 모든 것을 다시 검사하며, 거부(아래에 아직 무언가 있는 삭제 등)는 서버가 쓴 그대로 표시됩니다. 장치 이동은 장치 편집기가 하는 것과 같은 저장이며 `equipmentId`를 함께 보내므로, 앞에서 설명한 대로 텍스트가 트리를 따라갑니다.

레이블은 화면 맨 아래에서 관리합니다. 이름, 색상, 설명이 있고 `label_id`는 한 번 정해지면 고정됩니다. 엔티티는 엔티티 화면의 서랍에서 위치와 레이블을 지정합니다.

그 외 사용자는 누를 것이 없는 같은 화면을 봅니다.
