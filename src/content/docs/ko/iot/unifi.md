공장의 네트워크도 설비입니다. PLC가 조용해지면 가장 먼저 나오는 질문은 "PLC 문제인가, 아니면 PLC가 꽂힌 스위치 포트 문제인가"이고, 지금까지 그 답은 누군가의 휴대폰에 있는 UniFi 앱 안에 있었습니다. 그래서 HotLoop는 UniFi 콘솔 자체를 읽습니다. 모든 스위치, 모든 포트, PoE 사용량, WAN 링크, 사이트 상태를 일반 태그로 읽습니다. 따라서 알람, 트렌드, 엔터티, 자동화, OPC UA, MCP가 UniFi의 존재를 몰라도 이 태그 위에서 모두 동작합니다.

여기서는 드라이버, 그 위에서 동작하는 OT 감시, 화면, 이벤트 스트림, 그리고 첫 명령(U1부터 U5까지, [로드맵](/ko/roadmap/) 참고)을 설명합니다. **네트워크를 읽기만 하며, 사람이 해당 태그를 활성화한 경우에만 네트워크를 변경합니다.** 모든 태그는 읽기 전용으로 만들어집니다. 명령인 몇 가지 포인트(아래 "명령")는 다른 태그와 마찬가지로 쓰기 게이트를 거칩니다. 누군가 그 태그를 쓰기 가능으로 표시하기 전에는 아무것도 명령을 보내지 않으며, View Only 콘솔 계정은 콘솔 자체가 거부합니다. 명령을 제외한 모든 기능에는 View Only 계정을 사용할 수 있습니다.

## 콘솔 추가

HotLoop 장치 하나는 **콘솔 하나의 사이트 하나**입니다. Cloud Gateway와 그 뒤의 Express는 두 개의 콘솔이므로 장치 두 개, 로그인 두 개가 필요합니다. 각 콘솔에는 자체 로컬 계정이 있기 때문입니다.

1. **콘솔에서 로컬 계정을 만듭니다.** Settings, Admins & Users, Add Admin에서 **Restrict to Local Access Only**를 선택하고 역할은 **View Only**로 합니다. Ubiquiti 클라우드 계정은 앱 외에는 로그인할 수 없습니다. MFA가 필요하며, 스크립트에는 콘솔이 403으로 응답합니다. 저희는 `hotloop-ro`라는 이름을 씁니다.
2. **장치를 추가합니다.** 프로토콜은 `unifi`, 주소는 콘솔의 URL입니다. UniFi OS가 실행되는 콘솔(Cloud Gateway, Dream Machine, UniFi OS Server)은 `https://host`, 자체 호스팅 Network Application은 `https://host:8443`을 씁니다. 폴링 간격은 15초 정도가 적당합니다. 드라이버는 설정값과 관계없이 콘솔을 10초에 한 번보다 자주 읽지 않습니다.
3. **지문 없이 저장합니다.** 첫 연결은 의도적으로 실패하며, 콘솔이 제시한 인증서의 지문을 보여 줍니다. 본인의 콘솔이 맞는지 확인한 뒤(콘솔이 인증서를 보여 주며, `openssl s_client -connect host:443`의 출력을 `openssl x509 -pubkey -noout | openssl pkey -pubin -outform der
   | sha256sum`에 넘겨도 같은 값이 나옵니다) `certFingerprint`에 붙여 넣고 저장합니다.
4. 태그는 다음 폴링에서 저절로 만들어집니다. 아래를 참고하십시오.

UniFi 장치는 HotLoop에 비밀번호를 암호화할 키(`HOTLOOP_SECRET_KEY_FILE`, 차트가 자동으로 설정합니다)가 있어야만 저장할 수 있습니다. [백업 및 복원](/ko/iot/backup/#device-credentials-and-the-secret-key)을 참고하십시오.

| 옵션 | 기본값 | 동작 |
|---|---|---|
| `site` | `default` | 콘솔 URL에 나오는 사이트의 짧은 이름입니다. `default`는 모든 콘솔의 첫 번째 사이트입니다 |
| `username`, `password` | 필수 | 로컬 계정입니다. 비밀번호는 API를 통해 쓰기 전용이며 데이터베이스에 암호화되어 저장됩니다 |
| `certFingerprint` | 없음 | 콘솔 인증서 공개 키의 SHA-256을 16진수로 입력합니다. 콜론, 공백, 대문자는 상관없습니다 |
| `caFile` | 없음 | 정식 인증서가 있는 콘솔에서 핀 대신 CA를 신뢰합니다 |
| `insecureSkipVerify` | `false` | 모든 인증서를 신뢰합니다. 시험대에서만 쓰고 공장에서는 절대 쓰지 마십시오 |
| `clientTimeoutSec` | `90` | 콘솔이 클라이언트를 마지막으로 본 뒤 얼마 동안 네트워크에 있는 것으로 칠지 정합니다. 최소값은 30입니다. [클라이언트](#클라이언트-ot-네트워크-plc가-꽂힌-위치)를 참고하십시오 |

### 인증서를 고정하는 이유

콘솔은 자체 서명 인증서와 함께 출하되며, 쉬운 방법은 검증을 건너뛰는 것입니다. 계량기 하나를 읽는 데는 괜찮습니다. 하지만 공장 네트워크 전체를 볼 수 있고, 쓰기 PR 이후에는 포트의 전원을 껐다 켤 수도 있는 로그인에는 안 됩니다. 핀이 설정된 콘솔이 다른 인증서를 제시하면 **사용자 이름이나 비밀번호를 보내기 전에** TLS 핸드셰이크 단계에서 거부되며, 오류에는 두 지문이 모두 표시됩니다. 핀은 공개 키에 걸려 있으므로, 같은 키로 인증서를 다시 발급하는 콘솔은 계속 동작합니다.

조용히 넘어가는 "첫 사용 시 신뢰(trust on first use)"는 없습니다. 인증서를 신뢰하는 일이 의미를 갖는 순간은 사람이 그것을 보고 있을 때뿐이므로, 그때 신뢰가 이루어집니다.

## 로그인: 한 번만, 꼭 필요할 때만 다시

점검할 때마다 로그인하자 저희 Cloud Gateway가 429로 응답하며 계정을 잠갔습니다. 두 번이나 그랬습니다. 그래서 다음과 같이 합니다.

- **콘솔당, 프로세스당 세션 하나.** 모든 폴링과 콘솔의 모든 사이트가 같은 로그인을 씁니다. 같은 콘솔의 두 사이트를 위한 장치 두 개가 같은 계정을 쓰면 세션은 하나입니다.
- **콘솔이 세션이 없어졌다고 알릴 때(401)만 다시 로그인하며**, 한 번에 한 호출자씩, **무슨 일이 있어도 1분에 한 번을 넘지 않습니다.** 1분 안에 세션이 두 번 끊기면 1분이 지날 때까지 장치는 불량으로 읽히며, 이것이 저희가 원하는 절충입니다.
- **거부된 로그인은 재시도하지 않습니다.** 잘못된 비밀번호, 클라우드 계정, 429 잠금은 최소 5분을 기다리며, 콘솔의 `Retry-After`가 더 길면 그만큼 기다립니다. 장치 오류에 어느 경우인지 표시됩니다. 장치를 껐다 켜도 다시 시도할 수 없습니다. 프로세스가 기억합니다.
- **콘솔을 쓰는 마지막 장치가 멈추면 로그아웃합니다.** 그래서 재시작해도 콘솔에 세션이 쌓이지 않습니다.
- **`--mcp-stdio` 도우미는 절대 로그인하지 않습니다.** 이미 세션을 가진 Gateway 옆에서 실행되며, 같은 장비에서 두 번째로 로그인하면 바로 429를 부르기 때문입니다. 이 도우미에서는 UniFi 장치가 중지된 상태로 보이고, 실제로는 Gateway에서 동작합니다.

## 태그

모든 태그는 드라이버가 만들며, 사람이 활성화하기 전까지 읽기 전용이고, 표시 이름이 아니라 MAC 주소와 포트 번호로 이름이 붙으므로 UniFi 앱에서 스위치 이름을 바꿔도 아무것도 깨지지 않습니다. `<mac>`은 구분자 없는 소문자 장치 MAC이고, `<nn>`은 두 자리 포트 번호입니다.

| 태그 | 형식 | 설명 |
|---|---|---|
| `d.<mac>.state` | 텍스트 | `connected`, `disconnected`, `pending`, `upgrading`, `provisioning`, `heartbeat_missed`, `adopting`, ... |
| `d.<mac>.online` | bool, connectivity | 콘솔에 연결됨 |
| `d.<mac>.uptime_s` | int, s | 가동 시간 |
| `d.<mac>.cpu_pct`, `.mem_pct` | float, % | CPU와 메모리 |
| `d.<mac>.temp_c` | float, °C | 온도, 센서가 있는 장치에 한함 |
| `d.<mac>.clients` | int | 이 장치를 통해 연결된 클라이언트 |
| `d.<mac>.fw` | 텍스트 | 펌웨어 버전 |
| `d.<mac>.wan<N>.up` | bool, connectivity | 게이트웨이 자체 상태 점검(`last_wan_interfaces`, 그다음 `last_wan_status`)에서 WAN N이 **살아 있음**. WAN 블록의 `up`(구성됨을 뜻함)이 아닙니다. 둘 다 제공하지 않는 콘솔은 불량으로 읽히며 절대 up이 되지 않습니다 |
| `d.<mac>.wan<N>.latency_ms` | float, ms | 지연 시간, WAN이 살아 있는 동안에만 유효 |
| `d.<mac>.wan<N>.availability_pct` | float, % | 게이트웨이가 보고하는 경우 그 자체 모니터가 측정한 가용성(기간은 하루) |
| `d.<mac>.wan.active` | 텍스트 | 트래픽을 나르는 WAN: 업링크의 WAN이 살아 있으면 그것, 아니면 처음 살아 있는 WAN, 없으면 `none` |
| `d.<mac>.wan.failover` | bool, problem | 트래픽이 첫 번째 WAN이 아닌 다른 WAN으로 흐름: 공장이 백업 회선을 쓰는 중 |
| `p.<mac>.<nn>.up` | bool, connectivity | 포트 링크 |
| `p.<mac>.<nn>.speed_mbps` | int, Mbit/s | 링크 속도, 링크가 없는 포트는 0이며 정상 값 |
| `p.<mac>.<nn>.rx_bps`, `.tx_bps` | float, bit/s | 트래픽 |
| `p.<mac>.<nn>.errors` | int | 수신 오류와 송신 오류의 합 |
| `p.<mac>.<nn>.poe_w` | float, W, power | PoE 사용량, PoE를 공급할 수 있는 포트에 한함 |
| `p.<mac>.<nn>.poe_mode` | 텍스트 | `auto`, `off`, `pasv24`, `passthrough` |
| `site.<subsystem>.status` | 텍스트 | 사이트 상태: `wan`, `www`, `lan`, `wlan`, `vpn` |
| `site.www.latency_ms` | float, ms | 인터넷 지연 시간, 보고되는 경우 |
| `site.network_version` | 텍스트 | 콘솔에서 실행 중인 Network 버전 |
| `site.events_live` | bool, connectivity | 콘솔의 이벤트 웹소켓이 연결됨. 0이면 HotLoop가 폴링만 한다는 뜻이며, 속도만 느려질 뿐 다른 손해는 없습니다 |
| `site.last_event` | 텍스트 | 콘솔이 사이트에 대해 보고한 가장 최근 이벤트, 콘솔 자체의 표현 그대로 |
| `d.<mac>.last_event` | 텍스트 | 해당 장치에 대한 가장 최근 이벤트. 이벤트가 생기기 전까지는 비어 있음 |

장치 클래스는 엔터티로 이어지므로, 포트의 링크는 연결 상태 이진 센서로, PoE 사용량은 전력 센서로 아무도 설정하지 않아도 나타납니다.

**태그는 저절로 추가되며, 저절로 사라지지 않습니다.** 다음 주에 어댑트하는 스위치는 다음 폴링에서, 같은 세션에서, 아무것도 재시작하지 않고 태그로 나타납니다. 연결이 끊긴 스위치는 `online`이 0으로 읽히고 포트는 품질 불량이 되므로, 그 스위치에 건 알람은 함께 사라지지 않고 상황을 알려 줍니다. 태그를 삭제하는 것은 사람의 결정입니다. 누군가 꺼 둔 태그는 꺼진 채로 남습니다. 드라이버에게는 발언권이 없습니다.

어댑트된 장치만 태그를 받습니다. 누군가 꽂았지만 아무도 어댑트하지 않은 스위치는 아직 공장 네트워크의 일부가 아닙니다. 콘솔이 보고하지 않는 포인트는 불량으로 읽히며, 지어낸 0이 되는 일은 없습니다. PoE 사용량을 보고하지 않는 스위치는 `poe_w` 태그가 불량으로 읽힙니다.

Edge Relay도 콘솔을 폴링할 수 있습니다. 장치 파일에 선언된 태그를 읽을 뿐 태그를 추가하지는 않습니다. 태그를 보관할 곳이 없기 때문입니다.

## 명령

다섯 종류의 포인트가 명령입니다. 각각 다른 태그처럼 읽기 전용으로 만들어지며, 누군가 쓰기 가능으로 표시하기 전까지는 아무 일도 하지 않습니다. 이 명령을 쓰려면 HotLoop가 로그인하는 계정이 로컬 Administrator여야 합니다. View Only이면 콘솔이 HTTP 403으로 응답하고, HotLoop가 그렇게 알려 주며, 아무것도 바뀌지 않습니다.

| 태그 | 쓰기 | 콘솔의 동작 |
|---|---|---|
| `d.<mac>.locate` | `true` 또는 `false` | 끌 때까지 장치의 LED를 깜박입니다. 콘솔이 말하는 값을 다시 읽습니다. |
| `d.<mac>.restart` | `true` | 장치가 다음에 정보를 보낼 때 재시작합니다. `false`는 아무 일도 하지 않습니다. 읽으면 0입니다. |
| `p.<mac>.<nn>.power_cycle` | `true` | 포트의 PoE를 껐다 켭니다. `false`는 아무 일도 하지 않습니다. 읽으면 0입니다. |
| `w.<id>.enabled` | `true` 또는 `false` | 무선 네트워크를 켜거나 끕니다. 해당 필드만 전송되므로 암호와 다른 모든 설정은 그대로 남습니다. `<id>`는 콘솔이 그 네트워크에 부여한 ID이며 이름을 바꿔도 변하지 않습니다. |
| `c.<mac>.blocked` | `true` 또는 `false` | 감시 대상 클라이언트를 네트워크에서 차단하거나 다시 허용합니다. 콘솔이 본 적 있는 클라이언트에 대해서만 이 포인트가 존재합니다. |

전원 사이클은 공장에 해를 끼칠 수 있으므로(자동화가 2분마다 PLC를 사이클하면 전원 공급 장치가 타 버립니다) 누가 요청하든 두 가지 규칙이 적용됩니다. 포트는 15분에 최대 한 번만 사이클됩니다(마지막 사이클 시각은 데이터베이스에 보관되므로 재시작해도 잊히지 않으며, 시각을 확인할 수 없는 사이클은 거부됩니다). 그리고 네트워크를 나르는 포트는 절대 사이클되지 않습니다. 업링크, 그리고 콘솔 자체의 토폴로지에 따라 다른 장비가 매달린 모든 포트가 해당하며, 5G 백업에 전원을 공급하는 포트도 그중 하나입니다. 거부될 때는 어느 규칙 때문인지 알려 줍니다. 콘솔이 스스로 거부한 명령은 대기 시간을 소모하지 않습니다.

## 클라이언트, OT 네트워크, PLC가 꽂힌 위치

두 가지 작업이며, 둘 다 읽기 전용입니다.

**어디에 꽂혀 있는가.** PLC가 조용해지면 첫 질문은 PLC 문제인지 스위치 포트 문제인지입니다. HotLoop 장치를 네트워크의 해당 클라이언트와 한 번 연결해 두면, 누군가 UniFi 앱을 열기도 전에 장치 서랍에 "USW Lite 8 PoE 포트 5, 링크 다운"이라고 표시됩니다. 이 연결은 콘솔의 장치에 클라이언트 태그도 만들어 주므로, 멈춘 Modbus 값 옆에서 포트 상태가 트렌드와 알람으로 이어집니다.

**SCADA 네트워크에 무엇이 있는가.** 네트워크를 OT로 표시하고 거기 속한 것을 승인하면, 그 외의 것이 나타날 때 그것을 지목하는 알람이 울립니다. 누군가 새벽 2시에 SCADA 스위치에 노트북을 꽂으면 새벽 2시에 알게 됩니다.

### IP로 식별하지 않습니다

콘솔의 클라이언트 목록은 늦게 갱신됩니다. 그래서 다음과 같이 합니다.

- **클라이언트는 곧 MAC입니다.** 연결 시 PLC에 대해 아는 정보가 IP이므로 IP로 클라이언트를 제안하지만, 사람이 한 번 확인하고 나면 그 뒤로는 MAC이 키입니다. IP 태그는 그것이 콘솔의 의견임을 표시합니다.
- **온라인은 "목록에 있음"이 아닙니다.** 클라이언트는 콘솔이 `clientTimeoutSec`(90초) 안에 보았고, **유선이라면** 해당 스위치 포트에 링크가 있을 때 온라인입니다. 포트가 빠른 쪽입니다. 케이블을 뽑으면 목록이 따라잡는 동안에도 포트는 다음 읽기에서 다운으로 읽힙니다.

### 장치 연결

장치의 서랍을 엽니다. HotLoop가 읽는 UniFi 콘솔이 그 장치의 IP로 클라이언트를 나열하고 있으면 Network 섹션이 그것을 제안하며, 관리자가 **Link**를 누릅니다. 기준이 될 IP가 없으면(이름으로 지정된 장치) MAC으로 연결합니다. 또는 API `PUT /api/devices/{id}/network`를 통해서도 할 수 있으며, [HTTP API](/ko/iot/api/#put-apidevicesidnetwork)를 참고하십시오.

연결된 장치의 클라이언트는 태그와 알람 **"PLC-07 off the network"**를 받습니다. 우선순위는 1이고, 재부팅 중인 PLC가 아무도 호출하지 않도록 켜짐 지연이 120초입니다.

### OT 네트워크와 알려진 목록

네트워크를 OT로 표시(`PUT /api/unifi/{id}/networks/{network}`에 `{"ot": true}`)한 다음, 그 안에 있는 것을 승인합니다. 지금 상태 그대로 한 번에 승인(`POST .../accept-all`)하거나 장치를 하나씩 승인합니다. 표시하면 `n.<network>.unknown`에 알람 **"Unknown device on SCADA"**(우선순위 1)가 만들어집니다. 가장 최근의 낯선 장치는 MAC, 스스로 밝힌 이름, IP, 들어온 스위치 포트 또는 SSID와 함께 `n.<network>.unknown_last`에 표시됩니다.

알려진 장치는 **감시**(`"watch": true`)할 수 있습니다. 연결된 장치와 같은 태그와 같은 네트워크 이탈 알람이 생깁니다. PLC는 감시합니다. 허용되었지만 오가는 정비용 노트북은 알려진 장치이되 감시하지 않습니다. 그러지 않으면 떠날 때마다 누군가를 호출하게 됩니다.

알람은 일반 알람 정의입니다. 보류하고, 확인하고, Discord로 보내고, 지연을 편집할 수 있습니다. 감시, 연결, OT 표시를 없애면 HotLoop는 그것 때문에 만든 알람도 없애므로, 더 이상 아무도 읽지 않는 태그가 알람을 열어 두는 일은 없습니다. 관리자가 직접 작성한 알람은 절대 건드리지 않습니다.

이 기록은 HotLoop의 것이며, HotLoop 자체 데이터베이스(`unifi_networks`, `unifi_known`, `unifi_links`, 모두 백업에 포함)에 있고 콘솔에 있지 않습니다. 변경은 실행 중인 드라이버의 다음 읽기에서 이미 가진 세션으로 반영됩니다. 장치를 재시작하지 않는데, 재시작하면 로그아웃되어 분당 한 번이라는 로그인 한도 때문에 1분간 들어갈 수 없게 되기 때문입니다.

### 태그

| 태그 | 형식 | 설명 |
|---|---|---|
| `n.<network>.clients` | int | 위 기준으로 온라인인, 지금 네트워크에 있는 클라이언트. 모든 LAN 네트워크에 하나씩 생깁니다 |
| `n.<network>.unknown` | int | OT 네트워크에서 알려진 목록에 없는 온라인 클라이언트 |
| `n.<network>.unknown_last` | 텍스트 | 그중 가장 최근의 것을 문장으로 표시. 없으면 비어 있음 |
| `c.<mac>.online` | bool, connectivity | 네트워크에 있는 감시 대상 또는 연결된 클라이언트 |
| `c.<mac>.ip` | 텍스트 | 콘솔이 마지막으로 본 IP |
| `c.<mac>.sw_mac`, `.sw_port` | 텍스트, int | 유선 클라이언트가 연결된 스위치와 포트. 케이블을 뽑은 뒤에도 유지됩니다. 어디에 *있었는지*가 핵심입니다 |
| `c.<mac>.port_up` | bool, connectivity | 해당 포트의 링크. 스위치 자체가 콘솔에서 사라졌을 때는 아무도 알 수 없으므로 불량으로 읽힙니다 |
| `c.<mac>.last_seen_s` | int, s | 콘솔이 마지막으로 본 뒤 경과한 초 |

`<network>`는 콘솔의 네트워크 ID이므로 앱에서 SCADA 이름을 바꿔도 아무것도 깨지지 않습니다. OT로 표시했는데 콘솔이 이후 삭제한 네트워크는 그 사유와 함께 불량으로 읽히며, 조용한 0이 되지 않습니다. 콘솔이 한 번도 본 적 없는 클라이언트는 `online`이 0이고 나머지는 불량으로 읽히며, 그렇게 표시합니다.

감시 대상과 연결된 클라이언트만 `c.*` 태그를 받습니다. 휴대폰 300대가 오가는 게스트 네트워크가 태그 세트 300개를 만들지는 않습니다.

### 콘솔에 묻지 않고 읽기

`GET /api/unifi/{id}/networks`, `/clients`, `/known`, 서랍, MCP 도구 `find_network_client`는 모두 드라이버의 마지막 읽기 결과를 읽습니다. 어느 것도 자체 요청을 보내지 않으므로, 화면을 열어 두거나 에이전트가 반복해서 질문해도 콘솔에는 아무 부담이 없고 429의 원인이 될 수 없습니다. 반대로 로그인하지 않는 `--mcp-stdio` 도우미는 자신의 프로세스에 콘솔 읽기가 없다고 알려 줍니다.

## 화면

UniFi 탭에는 보기 여섯 개와 콘솔 선택기가 있습니다. 탭의 모든 내용은 드라이버가 마지막으로 읽은 콘솔 정보이므로 열어 두어도 콘솔에 부담이 없고 429의 원인이 될 수 없습니다. 몇 초마다 HotLoop에 다시 묻고 무언가 바뀌었을 때만 다시 그리므로, 누군가 구석으로 스크롤해 둔 지도는 그 자리에 그대로 있습니다.

- **개요.** 콘솔마다 카드 하나입니다. 게이트웨이 카드 맨 위에는 WAN 띠가 있습니다. WAN마다 구간 하나가 있으며, 게이트웨이 자체 상태 점검이 살아 있다고 하면 녹색, 아니면 빨간색이고, 트래픽을 나르는 구간은 테두리가 있습니다. 사이트가 백업으로 운영 중이면 띠 전체가 호박색이 되고 어느 회선인지와 언제부터인지를 알려 줍니다. 그 "언제부터"는 HotLoop가 처음 그렇게 읽은 시각이며 게이트웨이가 전환한 시각이 아니고, 사이트가 이미 5G로 운영 중일 때 시작한 HotLoop는 자신의 시작 시점부터라고 표시합니다. 저희는 모르는 시각을 표시하지 않습니다. 그 아래에는 온라인 장치, 유선 및 무선 클라이언트, 네트워크별 클라이언트, 콘솔이 놓친 장치, 최근 이벤트가 있습니다. 콘솔이 아무것도 알려 주지 않는 WAN은 회색이며 "no liveness reported"라고 표시되고 절대 녹색이 되지 않습니다. 지연 시간을 보고하는 모든 WAN에는 숫자 옆에 추이선이 있으며, 엔터티 타일이 그리는 선과 같은 것으로 해당 태그에 대한 HotLoop 자체 버퍼에서 가져옵니다. 관리자는 카드 맨 아래에서 **Create the usual alarms**를 사용할 수 있습니다. [기본 알람](#기본-알람)을 참고하십시오.
- **지도.** 게이트웨이에서 왼쪽에서 오른쪽으로 배치됩니다. 매번 같은 방식으로 배치되므로(깔끔한 트리, 물리 시뮬레이션 없음, 같은 입력에 같은 픽셀) 벽걸이 보드에서 흔들리지 않습니다. 케이블은 콘솔 자체의 `downlink_table`입니다. 스위치가 다른 스위치에 연결된 것은 콘솔이 그렇다고 말하기 때문일 뿐입니다. 어디에 연결되었는지 어떤 것도 나열하지 않는 장치는 혼자 놓이며 "no uplink listed"라고 표시됩니다. 추측으로 게이트웨이에 매달았다가 PLC 네트워크가 어디로 가는지 틀리는 일은 하지 않습니다. 유선 클라이언트는 콘솔이 알아낸 스위치와 포트에, 무선 클라이언트는 AP와 SSID에 놓이며 카드의 칩에 개수가 표시됩니다. 장치를 클릭하면 그 장치의 하위에 있지 않은 모든 것이 흐려지고, 측면 패널에 하위에 있는 것, 클라이언트, 그리고 그 장치가 전원을 공급하는 Plant 트리의 라인이 나열됩니다. 그 아래 클라이언트에 연결된 HotLoop 장치와 각 장치가 위치한 설비 경로입니다. 지도는 확대하고 이동할 수 있습니다. 두 손가락으로 핀치하고, 한 손가락으로 끌고, ctrl과 스크롤 또는 트랙패드 핀치로 포인터 주변을 확대하거나, 플러스, 마이너스, Fit 버튼을 쓰며, 전체 지도에서 최대 8배까지 가능합니다. 순수 SVG이므로 어떤 배율에서도 선명하고, 화면이 새로 고쳐져도 놓아 둔 위치가 유지됩니다. 장치 위에서 끝나는 드래그는 그 장치를 선택하지 않습니다. **Plant overlay**는 클라이언트에 연결된 HotLoop 장치를 Plant 트리의 라인마다 점선 상자에 담아 네트워크 오른쪽에 라인 경로를 라벨로 붙여 표시하며, 각 장치에는 꽂힌 스위치 포트로 가는 케이블, 네트워크가 말하는 상태(up, down 또는 확인 안 됨), HotLoop가 말하는 상태가 표시됩니다. 연결은 되었지만 어느 라인에도 없는 장치는 "Not on the Plant tree"라는 상자에 들어갑니다. 한 번 켜면 계속 켜져 있습니다. 콘솔 두 개가 한 그림이 됩니다. HotLoop가 읽는 다른 콘솔의 장비를 이 콘솔이 유선 클라이언트로 나열하면, 여기에 자체 하위 트리와 함께 점선으로 그려지고 "separate console"이라고 표시됩니다. 지도는 사이트 바인더용 SVG로 내보낼 수 있습니다.
- **장치.** 표이며, 하나를 클릭하면 전면 패널이 나옵니다. 포트가 전면 패널처럼 그려지며, 작은 스위치는 한 줄, 24포트와 48포트는 두 줄이고 홀수 포트가 짝수 포트 위에 있습니다. 링크가 있으면 녹색, 없으면 회색, **올라와 있다가 내려간 포트는 빨간색**(HotLoop가 감시를 시작한 뒤 올라와 있었음을 기억합니다), 비활성 포트는 점선, PoE 번개 표시(와트는 포트의 툴팁과 상세에 있습니다), 업링크에는 화살표가 있습니다. 포트를 클릭하면 거기 있는 대상, 꽂힌 장비, PoE 모드, 와트, 트래픽과 함께 수신 및 송신 추이선을 볼 수 있습니다. 콘솔이 놓친 장치는 마지막으로 말한 내용이 현재가 아니므로 숫자와 포트 링크를 표시하지 않습니다.
- **클라이언트.** 이름, MAC, IP로 검색할 수 있으며, 위치, 콘솔이 마지막으로 본 시각, OT 네트워크에서 알려졌는지 여부, 연결된 HotLoop 장치를 보여 줍니다. 관리자는 행에서 알 수 없는 클라이언트를 승인할 수 있습니다.
- **네트워크.** 네트워크별 OT 스위치와 "현재 상태 그대로 모두 승인"이 있습니다. 이는 HotLoop의 기록을 바꾸며 콘솔은 바꾸지 않습니다.
- **WiFi.** SSID, 각각이 송출 중인지, 어느 네트워크에 있는지, 클라이언트가 몇 대인지를 보여 줍니다. 콘솔이 계정에 무선 네트워크를 보여 주지 않으면, 화면은 없다고 주장하지 않고 그 사실을 알려 줍니다.

이 화면 뒤의 라우트는 `GET /api/unifi/consoles`, `.../overview`, `.../topology`, `.../devices`, `.../wifi`, `.../events`이며 [HTTP API](/ko/iot/api/)에 문서화되어 있습니다.

### 기본 알람

공장이 네트워크에서 누가 따로 고민하기 전에 갖추고 싶어 하는 알람으로, 콘솔이 지금 가진 정보로 만들어집니다. 개요에서 **Create the usual alarms**(또는 `POST /api/unifi/{id}/starter-alarms`, [HTTP API](/ko/iot/api/) 참고)를 누르면 다음이 만들어집니다.

| 알람 | 대상 | 우선순위 | 켜짐 지연 |
|---|---|---|---|
| 장치 오프라인 | `d.<mac>.online`, 어댑트된 모든 스위치, AP, 게이트웨이 | 2 | 60초, 펌웨어 재부팅이 아무도 호출하지 않도록 |
| 업링크 다운 | `p.<mac>.<nn>.up`, 각 장치가 상위와 연결된 포트 | 1 | 10초 |
| 백업 WAN을 쓰는 게이트웨이 | `d.<mac>.wan.failover`, WAN이 두 개 이상인 게이트웨이 | 2 | 30초 |
| 한도를 넘은 PoE 포트 | `p.<mac>.<nn>.poe_w`, 와트 단위 한도를 지정한 경우에만 | 3 | 30초 |

이들은 일반 알람 정의입니다. 보류하고, 확인하고, Discord로 보내고, 지연이나 한도를 편집하고, 삭제할 수 있습니다. 장비를 더 어댑트한 뒤 다시 누르면 새 장비만 추가되며, 수동으로 또는 이전에 눌러서 이미 알람이 있는 태그는 그대로 둡니다. PoE 알람은 HotLoop가 고르는 값이 아니라 사용자가 지정한 한도를 받습니다. 저희가 읽는 어떤 콘솔도 포트의 예산을 알려 주지 않으며, 저희가 짐작한 숫자는 누군가 믿게 될 숫자이기 때문입니다. "Unknown device on an OT network"와 "a watched client off the network"는 이 버튼에 포함되지 않습니다. 이 알람은 네트워크를 OT로 표시할 때와 장치를 감시하거나 연결할 때, 그 의미를 부여하는 기록과 함께 만들어집니다.

## 이벤트

콘솔의 이벤트 웹소켓(UniFi OS에서는 `/proxy/network/wss/s/<site>/events`, 자체 호스팅 애플리케이션에서는 `/wss/s/<site>/events`)은 다른 모든 것과 같은 세션을 씁니다. 스스로 로그인하지 않습니다. 401로 거부된 핸드셰이크는 읽기와 같은 로그인 한도를 거치며, 거부된 로그인은 재시도하지 않고 기다립니다.

**폴링이 여전히 정답입니다.** 이벤트는 태그를 쓰지 않습니다. 이벤트가 하는 일은 다음과 같습니다.

1. 도착하는 순간 **로그북**에 기록되며, 컨트롤러 자체의 문장("Switch[...] was disconnected")과 키가 함께 들어갑니다. 스위치가 끊어지면 다음 폴링이 알아채는 시점이 아니라 발생한 시점에 타임라인에 올라갑니다. 이벤트는 콘솔 자체의 장치 아래가 아니라 이벤트가 다루는 스위치, 액세스 포인트, 게이트웨이 아래에 정리됩니다. 콘솔은 컨트롤러가 실행되는 장비일 뿐 끊어진 대상이 아니기 때문입니다. 클라이언트만 지목하는 이벤트(콘솔이 누가 접속했는지는 알려 주지만 어디인지는 알려 주지 않음)는 마지막 읽기에서 그 클라이언트가 있는 스위치나 AP 아래에 정리되며, 클라이언트가 새 것이면 이벤트가 방금 요청한 읽기를 최대 30초 기다린 뒤, 그 읽기에도 없으면 콘솔 아래로 들어갑니다. 로그북의 **Where** 필터는 공장 쪽에서 이벤트를 찾습니다. 클라이언트에 연결된 HotLoop 장치, 콘솔이 그 클라이언트가 있다고 하는 스위치, 그리고 콘솔 자체의 downlink 테이블에 따라 그 스위치부터 게이트웨이까지의 모든 스위치입니다. 끊어진 스위치는 그것이 전원을 공급하는 모든 라인의 타임라인에 나타나고, 그렇지 않은 라인에는 나타나지 않습니다. 콘솔 자체를 요청하는 것은 예전처럼 동작합니다. `subject`가 콘솔의 id와 같은 시스템 로그와, 범위 장치에 콘솔이 포함된 로그북은 스위치별 이벤트를 포함해 그 콘솔의 모든 이벤트를 반환합니다.
2. 개요에 표시되는 로그에 들어가며 `site.last_event`와 `d.<mac>.last_event`에도 들어가므로 자동화가 그것을 트리거로 삼을 수 있습니다.
3. 즉시 다음 읽기를 요청합니다. 읽기 최소 간격은 10초이며, 이벤트가 오면 5초로 줄어들므로 태그와 엔터티는 최대 10초 뒤가 아니라 다음 폴링에서 따라잡습니다. 바쁜 WiFi 네트워크는 지나가는 휴대폰마다 이벤트를 보내며, 콘솔을 그때마다 읽지는 않습니다.

컨트롤러는 문제가 생겼음을 뜻하는 이벤트(`is_negative`: 스위치가 연결을 잃는 것은 해당하고, 클라이언트가 연결을 끊는 것은 해당하지 않음)를 표시하며, 이들은 로그북에서 경고가 됩니다. 나머지는 모두 정보이며, HotLoop가 본 적 없는 키도 포함됩니다.

**웹소켓이 끊기면 속도만 손해를 보고, 정확성은 손해를 보지 않습니다.** 2초에서 최대 1분까지 백오프하며 다시 연결합니다. ping을 보내고, 90초 동안 아무 응답이 없는 스트림은 네트워크가 뭐라고 하든 끊어진 것이므로 닫고 다시 엽니다. 끊어져 있는 동안 `site.events_live`는 0으로 읽히고, 개요에 이유와 함께 "polling only"라고 표시되며, 폴링은 이전과 똑같이 계속됩니다.
## 검증된 내용

UniFi 드라이버와 화면은 실제 UniFi Network Application과 UniFi OS 콘솔을 대상으로 View Only 계정으로 읽기 전용 실행했고, 2026-11-17에 실제 장비에서도 확인했습니다. 로그인과 단일 세션, 장치, 포트, PoE, WAN, 클라이언트 태그, 실시간 이벤트 스트림, 그리고 이를 기반으로 한 화면입니다.
