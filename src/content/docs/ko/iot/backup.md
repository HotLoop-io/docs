HotLoop은 4.12.0부터 히스토리안의 논리 스냅숏(테이블 데이터만)을 만들고 복원합니다. 기본으로 켜져 있고 매일 실행되며(`HOTLOOP_BACKUP_ENABLED`, `HOTLOOP_BACKUP_INTERVAL` 24h) 바이너리와 Helm 차트 모두 그렇습니다. 백업은 `HOTLOOP_BACKUP_DIR` 아래에 저장되며, 기본값은 HotLoop 데이터 디렉터리 안의 `backups`입니다(`HOTLOOP_DATA_DIR`, 없으면 쓸 수 있는 `/data`, 그것도 없으면 `~/.local/share/hotloop`). 백업 볼륨을 설정하지 않은 배포에서 이 프로세스가 컨테이너의 임시 파일 시스템에 조용히 쓰는 일이 없어야 하기 때문입니다.

## 이 기능이란

백업은 디렉터리입니다. 테이블마다 파일 하나와 작은 `manifest.json`으로 이루어집니다(HotLoop 버전, 데이터베이스에 적용된 스키마 마이그레이션, 타임스탬프, 각 테이블의 행 수와 열 및 열 타입).

## 이 기능이 아닌 것

- **`pg_dump`/`pg_restore`가 아닙니다.** Gateway의 런타임 이미지(`gcr.io/distroless/static-debian12:nonroot`)는 의도적으로 정적 바이너리 하나뿐입니다. 셸도, 패키지 관리자도, 어떤 종류의 외부 바이너리도 없습니다. 여기서는 모든 것이 앱이 이미 열어 둔 같은 데이터베이스 연결을 통해 이루어집니다.
- **스키마 백업이 아닙니다.** 스키마는 시작할 때마다 자동으로 다시 만들어집니다(`HOTLOOP_DB_MIGRATE`, 기본값은 켜짐). 백업은 테이블의 *데이터*만 담고, 복원은 항상 그 마이그레이션이 먼저 스키마를 다시 만들었다고 가정합니다.
- **특정 시점 복구가 아닙니다.** 여기에는 WAL 아카이빙도 연속 복제도 없습니다. 백업은 실행된 순간의 스냅샷이며, 그 순간 이후부터 다음 백업 전까지 기록된 내용은 포함되지 않습니다.
- **기기 밖 저장소가 아닙니다.** 백업 디렉터리(`HOTLOOP_BACKUP_DIR`, 이 차트가 프로비저닝하는 `backup.persistence` PVC가 받치도록 설계됨)는 여전히 같은 클러스터 안의 볼륨 하나입니다. 백업을 정말로 내구성이 있고 복제되었거나 오프라인인 저장소로 옮기는 일(볼륨을 오브젝트 스토리지에 복사하거나 PVC를 스냅샷하는 등 운영자의 실제 인프라가 제공하는 방식)은 운영자의 몫입니다. 이 프로젝트가 이미 내구성 있는 저장소를 인프라의 책임으로 보고, 앱이 멀티 클라우드 백업 어댑터를 새로 만들지 않는 것과 같은 방식입니다.

## 백업 파일 보호

백업 파일은 민감합니다. `users.copy` 파일에는 비밀번호와 키오스크 PIN의 bcrypt 해시가 들어 있고, `sessions.copy`와 `write_audit.copy`에는 세션 기록과 쓰기 감사 기록이 들어 있습니다. 파일은 `0640` 모드로(백업 디렉터리는 `0750`) 생성되며, 이미 있는 파일은 덮어쓰지 않고 오류가 됩니다. 하지만 이는 최소한의 보호일 뿐 볼륨 보호를 대신하지 못합니다. 백업 볼륨은 저장 시 암호화되는 저장소에 두고, 누가 무엇으로 읽을 수 있는지 제한하며, 운영자가 만드는 기기 밖 복사본에도 같은 주의를 기울이세요.

`devices.copy` 파일에는 각 장치의 주소와 프로토콜 구성이 저장된 그대로 들어 있으며, 드라이버가 로그인에 쓰는 자격 증명도 포함됩니다. 얼마나 읽을 수 있는지는 아래의 키에 달려 있습니다. 4.15.1부터 API는 관리자를 포함한 모든 역할에게서 모든 장치 자격 증명을 숨기지만, 백업 파일은 API 뒤에 있지 않습니다. [인증 및 사용자](/ko/iot/authentication/#자격-증명이-여전히-평문인-곳)를 참고하세요.

## 장치 자격 증명과 비밀 키

백업은 노트북, 공유 폴더, 티켓으로 복사되어 돌아다니는 파일입니다. 그래서 그 안의 자격 증명은 데이터베이스에도 백업에도 없는 키로 암호화됩니다.

- **`HOTLOOP_SECRET_KEY_FILE`이 설정된 경우**(차트가 설정하며, 설치 시 키를 생성해 업그레이드와 제거 후에도 유지합니다) 키로 보호되는 모든 자격 증명(OPC UA, CODESYS, MQTT, HTTP, MTConnect, UniFi 장치의 `password`, SNMP 장치의 `community`와 패스프레이즈, API 키 같은 HTTP 및 MTConnect 헤더 값, 검색이 수신하는 다른 MQTT 브로커 각각의 비밀번호, 각 히스토리안 대상의 비밀번호)이 데이터베이스에서 암호화되며, `devices.copy`, `mqtt_sources.copy`, `historian_targets.copy`에는 암호문이 들어 있습니다. 매니페스트에는 암호화에 쓰인 키가 `secretKeyIds`로 나열됩니다. 키 자체가 아니라 id입니다.
- **설정하지 않으면** 이 자격 증명은 데이터베이스와 `devices.copy`에 평문으로 들어 있으며, HotLoop은 시작 로그에서 이 사실을 알립니다. UniFi 콘솔, 비밀번호가 있는 MQTT 브로커, 비밀번호가 있는 히스토리안 대상은 키가 없으면 저장 자체가 안 됩니다. 키를 설정하고 다시 시작하세요. 이미 저장된 모든 것이 그 시작 때 암호화됩니다.
- **URL이나 텍스트에 적힌 자격 증명도 봉인됩니다**(`mqtt://user:pass@host`, `?token=` 또는 `?api_key=` 쿼리 값, 비밀번호를 언급하는 HTTP `body`). 이런 값이 들어 있는 장치의 주소나 옵션은 통째로 봉인되며, 드라이버는 입력된 그대로 돌려받습니다. 비밀이 없는 URL은 그대로 읽을 수 있게 둡니다. 키가 없으면 이것들도 나머지처럼 평문이며 시작 로그가 이를 알립니다. 키가 있으면 이미 저장된 모든 것이 그 시작 때 봉인됩니다. 비밀번호는 여전히 비밀번호 옵션에 두는 편이 낫습니다.

**복원에는 같은 키가 필요합니다.** `--restore-from`은 행을 하나라도 불러오기 전에 매니페스트를 확인합니다. 복원하는 HotLoop이 가지고 있지 않은 키로 암호화된 백업은 거부되며, 오류에 필요한 키가 표시됩니다. 그 키 파일을 마운트하고 복원하세요. 키를 영영 잃어버렸다면 `--restore-keep-unreadable-credentials`를 추가하세요. 나머지는 모두 복원되고, 자격 증명을 열 수 없는 장치는 필요한 키를 알려 주며 중단된 상태로 남아 있다가 누군가 자격 증명을 다시 입력하면 돌아옵니다. 키가 생기기 전에 만든 백업은 어디서든 복원되며, 복원이 끝나는 즉시 자격 증명이 암호화됩니다.

**키는 백업이 없는 곳에 보관하세요.** 백업 옆에 둔 키는 아무것도 보호하지 못합니다. 차트에서는 `<release>-secret-key` Secret이 그 키이며, 클러스터의 다른 시크릿을 백업하듯 따로 백업하세요.

## 무엇을 어떤 순서로 백업하는가

모든 사용자 데이터 테이블을 외래 키 의존 순서로 백업합니다(테이블은 자신의 외래 키가 가리키는 모든 테이블 뒤에 옵니다).

```
devices → tags → tag_latest → alarm_definitions → alarm_state →
alarm_events → automations → automation_runs → blueprints → scripts → script_runs →
recipes → recipe_versions → recipe_applications → events → write_audit →
settings → users → sessions → user_certificates → energy_meters → energy_meter_state →
energy_buckets → fleet_members → report_definitions →
report_runs → entity_state_log → tag_history
```

(요약본입니다. `backup.Tables`가 전체 목록이며 엔터티와 장비 테이블, `entity_last_state`도 포함합니다.) 로그북의 `entity_state_log`는 두 히스토리 모드 모두에서 월별로 파티션되어 있고, 이보다 큰 유일한 테이블인 `tag_history` 바로 앞에 옵니다. 복원은 월별 파티션이 하나도 없을 때 그 행을 불러오므로 행은 기본 파티션에 들어갑니다. 기록하는 Gateway가 시작될 때 로그북 유지 관리가 지난달과 이번 달의 파티션을 그에 속하는 행 둘레에 만들고, 보관 기간을 넘긴 오래된 행을 기본 파티션에서 지우므로 보관 기간은 복원된 모든 행에 적용됩니다. [로그북](/ko/iot/logbook/)을 참고하세요.

스크립트는 이력과 함께 돌아옵니다. 백업이 실행 도중에 잡아낸 실행은 `running`으로 돌아오고, Gateway가 처음 시작할 때 이를 충돌로 끊긴 실행과 같이 `interrupted by restart`라며 취소로 표시합니다. 실행을 이어서 하는 것은 없습니다. [스크립트](/ko/iot/scripts/)를 참고하세요.

레시피는 모든 버전과 모든 적용 기록과 함께 돌아옵니다. 백업이 적용 도중에 잡아낸 적용은 `applying`으로 돌아오고, Gateway가 처음 시작할 때 이를 쓰기 감사의 호출 id를 가리키며 `failed`로 표시합니다. 적용을 이어서 하거나 되돌리는 것은 없습니다. [레시피](/ko/iot/recipes/)를 참고하세요.

`schema_migrations`는 의도적으로 제외됩니다. `store.Migrate`가 내장된 마이그레이션에서 이 테이블과 모든 테이블의 DDL을 다시 만듭니다. 이것이 제외된 각 테이블이 왜 제외되는지 기록하는 `backup.ExcludedTables`의 유일한 항목입니다.

이 목록은 손으로 관리하며, 그래서 마이그레이션이 테이블을 추가하고도 이후 모든 백업에서 조용히 빠질 수 있습니다. 이를 막는 테스트가 두 개 있고, 둘 다 두 가지 저장 모드에서 실제 데이터베이스를 상대로 실행됩니다. 예약 보고서 테이블(`report_definitions`, `report_runs`)이 이 안전장치 아래 처음 추가된 테이블입니다. 보고서의 출력 파일은 보고서 볼륨에 있으며 데이터베이스 백업에 포함되지 않습니다. `tag_history`는 복원 시 마지막으로 불러옵니다. 자체 외래 키가 없고 압도적으로 큰 테이블이므로, 작은 구성 테이블은 실패할 일이 있다면 그 긴 단계가 시작되기 전에 일찍 실패합니다.

**`settings`에는 의도적인 예외가 하나 있습니다.** `history_mode` 행은 `Migrate`가 아무것도 없는 상태에서 스키마를 만드는 순간 `store.ensureHistorySchema`가 한 번만 기록합니다. *이 서버*가 `tag_history`를 TimescaleDB hypertable로 만들었는지 기본 파티션 테이블로 만들었는지를 기록하며, 이는 공장이 아니라 `Migrate`가 방금 실행된 데이터베이스에 대한 사실입니다. 이 행은 `settings`의 백업과 복원 모두에서 제외됩니다. 원본 설치의 과거 결정을 기능이 다른 대상에(또는 같은 종류의 서버에 대한 새 `Migrate` 실행에도) 복원하면 대상에 실제로 없는 구조를 설명하도록 이 행이 바뀔 수 있습니다. 대상 자신의 `Migrate`가 `Restore`가 `settings`를 보기 전에 이미 올바른 결정을 내렸으며, 그 결정은 그대로 둡니다.

## 요청 시 백업

- `POST /api/backup`(`backup.run`, 관리자 전용)은 지금 바로 백업을 만들고 매니페스트를 반환합니다.
- `GET /api/backup`(`backup.read`, 관리자 전용)은 백업 볼륨에 있는 것을 나열합니다. 이름, 디스크 크기, 각 백업의 매니페스트(테이블 목록, 행 수, HotLoop 버전, 타임스탬프)입니다.

둘 다 운영자 역할에서 빠져 있어 관리자 전용이며, `fleet.restart`/`fleet.config`/`notify.test`가 다른 운영 작업, 즉 "지금 실행"이나 관리 범위의 작업에 이미 적용하는 것과 같은 제한입니다. `users`와 `sessions`를 포함한 백업 목록의 행 수는 운영자 역할이 보도록 되어 있는 현장 읽기(장치, 태그, 알람)보다 관리 진단에 가까워서, 일부 읽기처럼 `backup.read`를 더 낮은 권한으로 나누지 않았습니다. 이것은 기술적 제약이 아니라 판단이며, 실제 운영자 작업 흐름에 필요하다면 다시 검토할 수 있습니다.

## 예약과 보관

`HOTLOOP_BACKUP_INTERVAL`(예: `24h`)은 고정된 주기로 백업을 실행합니다. 의도적으로 cron 표현식 파서가 아닌 단순한 간격입니다. 현실적인 필요는 "가끔 백업하라"이며, 아직 아무도 필요로 하지 않는 것을 만들지 않는다는 것이 이 프로젝트의 관례입니다. 설정하지 않으면(또는 `0`이면) 스케줄러가 꺼집니다. 요청 시 엔드포인트는 직접 트리거하려는 운영자나 외부 cron을 위해 계속 동작합니다.

`HOTLOOP_BACKUP_RETAIN`(기본값 `7`)은 최신 N개의 백업 디렉터리를 유지하고 백업이 성공할 때마다 오래된 것을 삭제합니다. `0` 이하는 모두 보관하며, 작은 볼륨에서는 운영자가 의도적으로 해야 하는 선택입니다.

## 백업 복원

**복원은 의도적으로 API 엔드포인트가 아닙니다.** 운영 트래픽을 처리 중일 수 있는 데이터베이스에 대해 "지금 복원"을 네트워크로 트리거할 수 있는 실시간 작업으로 자동화하는 것은 실제 위험입니다. 클릭 한 번의 실수나 탈취된 관리자 세션 하나로 운영 데이터를 덮어쓸 수 있으며, 이 프로젝트는 명시적으로 요청받지 않는 한 이를 만들지 않습니다. 복원은 바이너리 자체의 플래그이며, 대상 데이터베이스가 이를 받아야 한다고 이미 결정한 운영자가 직접 한 번 실행합니다.

```sh
hotloop --restore-from=/data/backups/20260918T220000Z
```

이 플래그가 수행하는 순서는 다음과 같습니다.

1. 구성을 불러오고 일반 시작과 똑같이 데이터베이스에 연결합니다. `store.Open`이 같은 마이그레이션을 실행해 복원이 데이터를 불러올 스키마를 만듭니다.
2. **무언가를 잃지 않고는 불러올 수 없는 백업을 거부합니다.** 이 데이터베이스보다 새로운 스키마에서 만든 백업이거나, 이 버전에 더 이상 없는 테이블이나 열이 있는 백업입니다. 둘 다 행을 하나도 불러오기 전에 확인합니다. 아래 "다른 버전으로 복원"을 참고하세요.
3. **대상 테이블에 이미 데이터가 있으면 거부합니다.** `Migrate`가 방금 심은 것(`settings`의 `history_mode` 행 하나)을 넘는 데이터가 있는 경우입니다. 복원은 아직 아무것도 없는 데이터베이스에서만 실행됩니다. 이것이 안전 점검입니다. 기존 행이 하나만 있는 테이블이 있어도 `COPY FROM STDIN`이 실행되기 전에 복원 전체가 중단됩니다.
4. 모든 테이블을 의존 순서대로 단일 트랜잭션 안에서 매니페스트가 지정한 열로 불러옵니다.
5. `bigserial` 기본 키가 있는 모든 테이블(`tags`, `alarm_events`, `automation_runs`, `events`, `write_audit`, `sessions`)의 시퀀스를 복원된 가장 큰 id보다 하나 큰 값으로 재설정합니다. `COPY FROM STDIN`은 시퀀스를 건드리지 않고 명시적인 id 값을 불러오므로, 이 단계를 건너뛰면 바로 다음 일반 삽입이 복원된 행과 충돌합니다.
6. 아직 열려 있는 같은 트랜잭션 안에서 모든 테이블의 행 수를 다시 세어 매니페스트의 행 수와 비교합니다.
7. 모든 수가 일치할 때만 커밋합니다. 불일치나 앞선 단계의 오류가 있으면 전체 트랜잭션을 롤백하여 대상 데이터베이스를 발견했을 때와 똑같이 비워 둔 채로, 일부만 불러온 상태로 두는 일은 없습니다.
8. 종료합니다. 프로세스에서 다른 것은 시작되지 않습니다. 폴링 스케줄러도, 알람 엔진도, API 서버도 없습니다. 복원에는 이들이 필요 없으며, 복원 도중의 데이터베이스에 런타임을 시작하는 것은 그 자체로 위험합니다.

### PostgreSQL 17로 옮기기

이 백업은 실행 중인 앱이 실행 중인 데이터베이스 연결로 만들기 때문에, PostgreSQL 16에서 17로 옮길 때의 백업이 될 수 없습니다. 그 이동은 데이터베이스가 시작되기 전에 이루어집니다. 업그레이드 자체의 안전장치는 PostgreSQL 16 디렉터리에 절대 쓰지 않고 `pgdata.pg16`으로 그대로 보존하는 것입니다(k3s와 Helm 페이지, "PostgreSQL 17"). 그래도 업그레이드 전에 이전 릴리스에서 이 백업을 만드세요. 기기 밖에 보관되는 사본이기 때문입니다. 이를 새 데이터베이스에 복원하는 것은 아래의 일반 복원이며, 엔진이 아니라 행을 옮기므로 어느 메이저 버전이 썼는지는 상관없습니다.

### 다른 버전으로 복원

복원에 쓰는 릴리스가 백업을 만든 릴리스인 경우는 드뭅니다. 백업은 몇 달 전 당시 실행 중이던 버전으로 만들었고, 다시 구축하는 기기는 오늘의 버전을 실행합니다. 어떤 백업이 어떤 버전에 복원되는지 정리합니다.

**오래된 백업을 더 새로운 HotLoop에: 됩니다.** 이것이 중요한 경우이며, `0001_core`부터 오늘까지 있었던 모든 스키마 수준에서 TimescaleDB와 일반 PostgreSQL로, 이후 앱을 시작해 시험합니다.

- 모든 매니페스트는 각 테이블의 열과 이름, 타입을 기록합니다. 복원은 각 파일을 정확히 그 열에 이름으로 불러옵니다. 백업 이후에 추가된 열은 기본값을 가집니다. `write_audit`의 `entity_id`, `service`, `call_id`는 엔터티 서비스 이전의 모든 감사 행에서 비어서 돌아오며, 그 행들은 단순한 태그 쓰기였기 때문입니다.
- 백업 이후에 추가된 테이블은 비어 있고, 앱이 시작할 때 채울 수 있는 것을 채웁니다. 엔터티 레지스트리의 첫 동기화가 복원된 모든 태그에 읽기 엔터티를, 활성화된 모든 태그에 제어 엔터티를, 모든 알람 정의에 알람 엔터티를 레지스트리가 붙였을 이름으로 부여합니다. 장비 트리 이전 백업의 장치는 복원 중에 사이트, 구역, 라인 텍스트에 따라 트리에 배치되며, 업그레이드가 배치했던 방식 그대로입니다. 백업에 한 번도 없던 것은 돌아올 수 없습니다. 레이블, 복합 엔터티, 백업 이후 운영자가 바꾼 엔터티 이름입니다.

**더 새로운 백업을 더 오래된 HotLoop에: 안 됩니다. 거부됩니다.** 매니페스트는 백업 데이터베이스에 적용된 모든 마이그레이션을 기록합니다. 이 데이터베이스가 한 번도 실행하지 않은 마이그레이션이 있으면, 복원은 행을 불러오기 전에 멈추고 이를 알립니다.

```
refusing to restore: this backup was taken by HotLoop <its version> with the
database schema at <its newest migration>, which is newer than this database's
schema at <this database's newest migration> (HotLoop <this version>). ...
Restore it with HotLoop <its version> or a later release
```

"더 새롭다"는 버전 문자열이 아니라 마이그레이션을 뜻합니다. 버전 문자열은 어느 바이너리가 백업을 만들었는지를 알려 줄 뿐이고, 개발 빌드와 릴리스 후보, 핫픽스 브랜치 때문에 이를 비교하는 것은 추측이 됩니다. 마이그레이션은 스키마가 실제로 무엇이었는지를 알려 주며 집합으로 비교하므로, 순서 어디에 빠져 있어도 누락된 마이그레이션이 잡힙니다. 메시지에 버전이 들어 있는 이유는 버전이 조치할 수 있는 정보이기 때문입니다. 어느 릴리스로 복원해야 하는지입니다.

**이 버전에 더 이상 없는 열이 있는 백업: 이름을 지목하며 거부됩니다.** 마이그레이션이 열을 삭제하거나 이름을 바꾸거나 타입을 바꾸는 날, 그 이전 백업에는 새 테이블에 들어갈 자리가 없는 데이터가 있습니다. 복원은 추측하지 않습니다. 아무것도 불러오기 전에 모든 테이블에 걸쳐 그런 열을 모두 이름으로 알려 줍니다.

- 실행 중인 테이블에 없는 열은 `backup.columnRenames`가 새 이름으로 매핑하지 않는 한 거부됩니다. 열 이름을 바꾸는 마이그레이션은 그 항목을 추가하고, 같은 변경에서 그 이전 백업을 복원하는 테스트도 추가합니다. 지금은 이름 변경이 없으므로 맵은 비어 있습니다.
- 타입이 바뀐 열은 거부됩니다. 바이너리 COPY는 타입을 담지 않으므로 바이트가 새 타입으로 읽히거나 도중에 거부될 수 있습니다.
- 실행 중인 테이블이 기본값 없이 `NOT NULL`로 추가한 열은 거부됩니다. 채울 수 있는 것이 없기 때문입니다.

세 경우 모두 해결 방법은 같습니다. 백업을 만든 릴리스로 복원한 다음 그 데이터베이스를 제자리에서 업그레이드하세요. 마이그레이션이 그 데이터를 만나도록 설계된 방식입니다.

이름으로 불러오면 아무도 알아채지 못하는 변경도 처리됩니다. 열이 삭제되었다가 다시 추가되었거나 테이블이 재구축되어 열 순서가 달라지는 경우입니다. 위치로 불러오면 타입이 맞을 때마다 오류 없이 한 열의 값이 다른 열로 들어갑니다. 이름으로 불러오면 각각 제자리에 들어갑니다.

**매니페스트가 이런 정보를 기록하기 전에 만든 백업**(이 릴리스 이전에 만든 모든 백업)에는 열 목록도 스키마도 없습니다. 그래도 복원됩니다.

- 열 목록이 없으면 복원은 위치로 대체합니다. 테이블보다 열이 적은 파일은 테이블의 앞쪽 열에 들어가고 나머지는 기본값을 갖습니다. 지금까지의 모든 스키마에서 이것이 맞는 이유는 오늘까지의 모든 마이그레이션이 열만 추가했고 `ALTER TABLE ADD COLUMN`은 항상 끝에 추가하기 때문입니다. 테이블보다 열이 많은 파일은 PostgreSQL이 직접 거부합니다.
- 스키마가 없으면 복원은 백업이 가능한 한 가장 최신이라고 가정합니다. 매니페스트가 기록하기 시작했을 때 가장 최신 마이그레이션이던 `0007_service_audit.sql`입니다. 이 가정은 성공했을 복원을 거부하는 경우만 있을 수 있고, 성공하지 않았을 복원을 통과시키는 경우는 절대 없습니다. 실제로는 아무것도 거부하지 않습니다. 이 점검이 있는 모든 HotLoop은 이미 그 마이그레이션까지 모두 실행했기 때문입니다.

이 릴리스가 만드는 첫 백업부터는 모든 것을 기록하므로, 대체 동작은 이미 백업 볼륨에 있는 백업에만 해당합니다.

### 복원 절차, 단계별

1. 대상 배포의 `hotloop` 바이너리가 읽을 수 있는 머신이나 볼륨에 백업 디렉터리를 가져옵니다. 운영자가 만든 백업 볼륨의 기기 밖 사본이 다시 쓰이는 지점입니다.
2. `HOTLOOP_DB_*`를 **대상** 데이터베이스로 지정합니다. 접근 가능해야 하고 백업된 테이블에 아직 데이터가 없어야 합니다(새로 만든 빈 데이터베이스가 일반적이며, 스키마는 3단계에서 만들어집니다).
3. `hotloop --restore-from=<path to the backup directory>`를 실행합니다.
4. 마지막 로그 줄을 읽습니다. 테이블 및 행 수와 함께 `restore complete`가 있거나, 무엇이 왜 거부되었는지 정확히 설명하는 오류가 있습니다.
5. 같은 데이터베이스를 대상으로 `hotloop`을 정상적으로 시작합니다.

## 데이터베이스 간 이동

백업은 어떤 데이터베이스가 만들었든 같은 것입니다. PostgreSQL의 바이너리 COPY 파일과 각 열의 Postgres 타입을 명시한 매니페스트이기 때문입니다. 그래서 공장을 한 데이터베이스에서 다른 데이터베이스로 옮기는 일은 이전 데이터베이스에서 백업하고 새 데이터베이스에 복원하는 것이 전부입니다.

- **SQLite에서 Postgres 또는 TimescaleDB로.** 파일 한계를 넘어선 Pi입니다. 백업하고, `HOTLOOP_DB_*`를 새 서버로 지정하고(`HOTLOOP_DB_TYPE=postgres`), 복원하세요. TimescaleDB 서버에서는 이력이 hypertable에 들어갑니다.
- **Postgres 또는 TimescaleDB에서 SQLite로.** 작은 기기로 규모를 줄이는 공장입니다. 반대 방향도 같으며 `HOTLOOP_DB_TYPE=sqlite`를 씁니다.
- **일반 Postgres에서 TimescaleDB로, 그리고 반대로.** 히스토리 모드는 한 번 정해지면 유지되므로, Gateway를 IoT 기기의 일반 Postgres에 연결하면 파티션이 유지됩니다. hypertable을 얻으려면 새 TimescaleDB에 복원하세요. 반대 방향에서는 파티션을 얻습니다.

들어올 때 확인하는 것은 모든 복원에서 확인하는 것과 같습니다. SQLite의 열을 Postgres 타입으로 읽어 모든 열을 이름과 타입으로 대상과 비교하므로, 한쪽의 백업은 다른 쪽에 복원되거나 어디서든 거부될 이유와 같은 이유로 거부됩니다. `history_mode`는 복사되지 않습니다. 대상은 자신의 마이그레이션이 결정한 것을 유지합니다. 시퀀스는 양쪽 모두에서 올바르게 맞춰집니다. Postgres에서는 `fixSequences`가 이동시키고, SQLite의 AUTOINCREMENT는 복원된 id를 넘어 스스로 이동합니다.

## 구성

| 변수 | 기본값 | <span class="sr-only">세부 정보</span> |
|---|---|---|
| `HOTLOOP_BACKUP_ENABLED` | `false` | 이 값을 설정하기 전까지는 API 경로를 포함해 기능이 꺼져 있습니다 |
| `HOTLOOP_BACKUP_DIR` | `/data/backups` | 백업이 기록되는 위치이며 PVC(차트의 `backup.persistence`)여야 합니다 |
| `HOTLOOP_BACKUP_RETAIN` | `7` | 최신 N개의 백업을 유지하며 `0` 이하는 모두 유지합니다 |
| `HOTLOOP_BACKUP_INTERVAL` | 설정 안 됨 | 예: `24h`. 설정하지 않으면 요청 시에만 실행됩니다 |

`--restore-from=<dir>`은 환경 변수가 아니라 `hotloop` 바이너리의 명령줄 플래그입니다. 위의 "백업 복원"을 참고하세요.

HotLoop은 실제 장비와 실제 서버를 상대로, 그리고 2026-11-17에는 베어메탈에서 실행되었습니다.
