장치를 HotLoop 브로커에 연결하면 바로 나타납니다. 센서는 값을 읽고, 스위치는 상태를 보여 주며, 엔티티는 장치가 알린 이름, 단위, 클래스를 갖습니다. 태그 목록을 직접 입력하는 사람은 없습니다.

그리고 장치는 아무것도 명령할 수 없습니다. 디스커버리가 만드는 모든 포인트는 읽기 전용이며, admin이 장치를 수락한 뒤 명령이 갈 정확한 토픽을 확인하면서 각 포인트를 직접 활성화하기 전까지 그대로 유지됩니다. 스스로를 알리는 장치는 자신이 무엇인지 알려 주는 장치일 뿐입니다. 그것은 유용합니다. 하지만 공장의 릴레이를 켜고 끌 권리를 얻는 것은 아니며, HotLoop도 그런 척하지 않습니다.

## 무엇이 이를 사용하나

형식은 `homeassistant/sensor/kitchen/power/config` 같은 토픽을 쓰는 것입니다. 이 형식을 정의한 프로젝트의 이름을 갖고 있습니다. HotLoop이 이를 사용하는 이유는 퍼블리셔들이 그렇게 하기 때문이며, 관계는 그것이 전부입니다.

| 퍼블리셔 | 여기에 도달하는 방식 | 무엇으로 테스트하는가 |
|---|---|---|
| **ESPHome** (`mqtt:` 컴포넌트) | 컴포넌트별, 기본으로 켜짐, retained | 실제 노드의 녹화된 출력 (아래 참고) |
| **Zigbee2MQTT** | 컴포넌트별, 거의 모든 곳에 템플릿 사용 | 실제 설치 환경의 녹화된 출력 |
| **Tasmota** | 자체 형식, 아래 참고 | 실제 장치 9대의 녹화된 출력 |
| **Shelly** (Gen2, Gen3, Gen4) | 알림 없음. 장치가 게시하는 상태에서 학습, 아래 참고 | 실제 메시지 15세트의 녹화된 출력과 제조사 문서 |
| 이 형식을 게시하는 그 밖의 모든 것 | 동일 | 형식 자체의 규칙 |

ESPHome은 Zigbee2MQTT와 마찬가지로 실제 노드의 녹화본으로 검증합니다.

녹화본은 실제 설치 환경이 게시한 메시지를 운영자가 캡처한 것으로, 퍼블리셔, 버전, 장치가 기록되어 있고 JSON 공백 외에는 아무것도 바뀌지 않았습니다.

## Tasmota

현재의 Tasmota는 `homeassistant/` 형식을 게시하지 않습니다. 문서에는 모든 빌드에서 제거되었다고 적혀 있습니다. 대신 Tasmota가 retained로 게시하는 것은 자체 형식입니다.

- `tasmota/discovery/<MAC>/config`: 장치(토픽, 풀 토픽 패턴, 릴레이와 조명, 켜짐과 꺼짐 문구, 라스트 윌 문구)
- `tasmota/discovery/<MAC>/sensors`: 그 시점에 센서가 읽는 값

둘 다 Tasmota의 `xdrv_12_discovery.ino`에 있는 `TasDiscovery`가 작성합니다(arendst/Tasmota `development` 5c295fb, 2026-10-12에서 확인). HotLoop은 이 둘을 다른 모든 퍼블리셔가 만드는 것과 같은 컴포넌트로 바꾸므로, 이후의 모든 단계(발견됨 화면, 수락, 활성화, 쓰기 게이트, 읽기)는 하나의 코드 경로입니다. MAC은 장치의 신원입니다. `homeassistant/` 형식으로도 스스로를 알리는 장치(SetOption19가 있는 구형 펌웨어)는 같은 장치입니다.

| Tasmota가 알리는 것 | HotLoop이 만드는 것 |
|---|---|
| 릴레이(`rl` 1) | 스위치: `stat/<topic>/POWER`를 읽고(여러 개면 `POWER1`, `POWER2` 등), 장치 고유의 켜짐과 꺼짐 문구를 사용합니다. `cmnd/<topic>/POWER[n]`으로 ON 또는 OFF를 명령합니다 |
| 조명(`rl` 2) | 조명: 켜짐과 꺼짐은 같은 방식입니다. 디머가 하나이면 밝기는 `tele/<topic>/STATE`의 `Dimmer` 키이며 0에서 100까지이고, `cmnd/<topic>/Dimmer`로 설정합니다 |
| 센서 메시지의 모든 숫자 | 각각 센서 하나. 경로(`ENERGY` `Power`, `SCD40` `CarbonDioxide`)로 `tele/<topic>/SENSOR`에서 읽으며, Tasmota가 그 이름에 부여하는 단위와 클래스를 사용합니다. 3상 계량기의 배열은 상마다 센서 하나입니다 |
| 라스트 윌 | 가용성: `tele/<topic>/LWT`, 장치 고유의 Online과 Offline 문구 |

토픽은 Tasmota가 만드는 방식대로 만들어집니다. 풀 토픽에 `%prefix%`와 `%topic%`을 채우므로, 소유자가 풀 토픽을 바꾼 장치(`tasmota/35D7A0/%prefix%/` 또는 `bi/test/%topic%/%prefix%`)도 실제로 사용하는 토픽에서 읽고 명령합니다.

읽지 못하는 것은 침묵하지 않고 소스의 문제 목록에서 알려 줍니다. 셔터, 스위치 입력, 버튼, iFan, 카메라, 컬러 조명의 색상, 조명이 둘 이상인 장치의 밝기입니다. 녹화본 어디에도 이들이 동작한다는 증거가 없으므로, 여기서는 이를 읽는다고 주장하지 않습니다.

**질의.** Tasmota는 릴레이가 바뀔 때 이를 보고하고, 전체는 5분마다 보고합니다. 그래서 장치 읽기를 시작할 때 HotLoop은 `cmnd/<topic>/POWER`로 빈 메시지를 하나 보내고, Tasmota는 아무것도 움직이지 않은 채 모든 릴레이의 상태로 응답합니다. 이것이 없으면 변하지 않은 장치는 HotLoop이 시작한 뒤 최대 5분 동안 알 수 없음으로 읽힙니다. 메시지는 비어 있고, `POWER`로 끝나는 토픽 외에는 어디로도 가지 않으며, 수신 전용 소스는 아무것도 보내지 않습니다.

**조명의 밝기**는 Tasmota의 텔레메트리(장치의 `TelePeriod`가 더 짧지 않다면 5분마다)와 함께 도착하며, 바뀌는 즉시 도착하지는 않습니다. 켜짐과 꺼짐은 즉시 도착합니다.

**각 브로커에서** 이 형식은 스위치입니다(브로커의 `tasmota`, 설정, MQTT). 지금 추가한 브로커는 켜져 있고, 내장 브로커는 항상 켜져 있으며, 이미 있던 브로커는 이전과 똑같이 수신하므로 누군가 켤 때까지 꺼져 있습니다. 꺼짐은 HotLoop이 그곳에서 `tasmota/discovery/#`를 구독조차 하지 않는다는 뜻입니다.

구성은 다른 모든 것과 마찬가지로 신뢰할 수 없습니다. 자신이 말하는 MAC이 아닌 MAC으로 게시된 것, `%topic%`이 없거나 와일드카드가 있는 풀 토픽, 슬래시가 들어 있는 토픽, 따옴표가 들어 있는 켜짐 문구, 알지 못하는 버전은 각각 이유와 함께 거부되며 아무것도 만들어지지 않습니다. 따옴표가 들어 있는 센서 이름은 템플릿에 도달하지 않습니다.

**무엇으로 테스트했나.** Tasmota 자체 콘솔에서 캡처한 실제 장치 9대의 메시지입니다.

|---|---|---|

이것은 녹화본이지 벤치 위의 장치가 아닙니다. 녹화본에 없는 것은 밝기(디머의 `tele/STATE` 줄이 원본 로그에서 깨져 있었고, `Dimmer` 키는 같은 녹화본의 `STATUS11`에 있으며 Tasmota는 이를 같은 함수로 만듭니다)와 전력 질의에 대한 응답(녹화본에는 HotLoop이 묻는 것이 아니라 Tasmota 콘솔에서 본 질문과 답이 있습니다)입니다.

## Shelly

Shelly Gen2, Gen3, Gen4는 아무것도 알리지 않습니다. 기다릴 구성 토픽이 없습니다. MQTT가 켜지고 상태 알림이 켜지면, 장치는 각 컴포넌트의 전체 상태를 변경될 때마다 `<prefix>/status/<component>`(`switch:0`, `cover:0`, `light:0`, `input:0`, 가상 `boolean:200`)에 게시하고, 라스트 윌을 `<prefix>/online`에 게시합니다. 그래서 HotLoop은 장치가 말하는 것으로 장치를 파악합니다. 게시한 컴포넌트, 각 컴포넌트가 실어 온 필드, 그리고 `sys` 상태의 MAC입니다. 프리픽스는 기본적으로 장치의 id(`shellyplus2pm-485519968144`)이며, 이는 모델과 MAC이므로 기본 프리픽스를 쓰는 장치는 `sys`를 기다릴 필요조차 없습니다. 누군가 입력한 프리픽스(`ShellyLichtGarten`)를 쓰는 장치는 다른 장치와 구별되기 전에 `sys`를 게시해야 하며, 그 전까지는 소스의 문제 목록에 이름이 오르고 만들어지지 않습니다.

학습한 내용은 프리픽스별로 보관되며 늘어나기만 합니다. 조용해진 컴포넌트는 제거된 것이 아니며, 이전보다 내용이 적은 상태도 아무것도 지우지 않으므로, 재시작해도 장치가 일부를 잃지 않습니다. 그 뒤는 다른 모든 퍼블리셔와 같은 경로입니다. 발견됨 화면, 수락, 각 포인트 활성화, 쓰기 게이트, 읽기입니다.

| Shelly가 알리는 것 | HotLoop이 만드는 것 |
|---|---|
| `output`이 있는 `switch:n` | 스위치: `<prefix>/status/switch:n`에서 `output`을 읽고, `<prefix>/command/switch:n`으로 `on` 또는 `off`를 명령합니다 |
| `light:n` | 같은 방식의 조명이며 `set,true`와 `set,false`를 사용합니다. 상태에 `brightness`가 있으면 0에서 100까지의 밝기를 `set,true,<level>`로 보냅니다 |
| `cover:n` | 커버: `state`(open, closed, opening, closing, stopped)를 읽고 `open`, `close`, `stop`을 보냅니다. `pos_control`을 알리는 커버는 보정된 것이므로 `current_pos`도 읽고 `pos,<n>`을 받습니다. 그렇지 않은 커버는 열고 닫기만 합니다 |
| switch, light, cover의 `apower`, `voltage`, `current`, `freq`, `pf`, `aenergy.total`, `temperature.tC` | 각각 센서 하나이며 W, V, A, Hz, Wh, 섭씨 단위를 쓰고, Shelly 문서가 정한 클래스를 따릅니다 |
| `input:n` | `state`의 바이너리 센서 |
| `devicepower:n`, `voltmeter:n`, `illuminance:n`, `presencezone:n` | 배터리, 외부 전원, 전압, 조도, 재실, 객체 수의 센서와 바이너리 센서 |
| `boolean:n`, `number:n`, `enum:n` (가상 컴포넌트) | 읽기 전용 센서. 가상 컴포넌트 설정은 RPC 호출이며 이 기능은 이를 하지 않고, 각각이 소스의 문제 목록에 표시됩니다 |
| `online` 라스트 윌 | 가용성, Shelly 고유의 `true`와 `false` |

명령은 제조사의 MQTT 페이지가 MQTT Control 아래에 나열하는 것이며, 테스트는 HotLoop이 그 목록을 따르도록 강제합니다. 스위치는 `on`, `off`, `toggle`, 조명은 `set,<bool>,<brightness>`, 커버는 `open`, `close`, `stop`, `pos,<n>`입니다. 모든 명령은 사람이 활성화한 게이트를 거치는 쓰기입니다.

**질의.** Shelly는 컴포넌트가 바뀔 때 이를 게시하므로, 변하지 않은 장치는 바뀔 때까지 알 수 없음으로 읽힐 것입니다. 장치 읽기를 시작할 때 HotLoop은 `<prefix>/command`로 `status_update`를 보내며, 같은 페이지에 따르면 이것은 장치가 컴포넌트의 상태를 게시하게 하고 아무것도 움직이지 않습니다. 그 한 단어만 `/command`로 끝나는 토픽으로 가며 그 외에는 어디에도 가지 않고, 수신 전용 소스는 아무것도 보내지 않습니다. 장치 읽기가 시작될 때마다 일어나므로, 여러 포인트를 연달아 활성화하면 여러 번 질의합니다.

**장치에서 켜 두어야 하는 것.** 브로커 주소와 함께 MQTT 활성화, 상태 알림 켜짐(`status_ntf`), 그리고 명령을 위해서는 제어 켜짐(`enable_control`)이 필요합니다. HotLoop의 자체 브로커에는 장치의 프리픽스 이름을 딴 `shelly` 로그인 프로필이 있어서, 장치의 상태를 게시하고 `<prefix>/command`를 수신하는 것만 허용하고 다른 것은 허용하지 않습니다.

**읽지 못하는 것.** 침묵하지 않고 소스의 문제 목록에서 알려 줍니다. 본 적 없는 종류의 컴포넌트(LoRa 애드온이 있는 Gen4의 `lora:100`, `pm1`, `em`), 읽는 대상 필드가 빠진 switch나 cover, 가상 컴포넌트의 설정입니다. 입력 이벤트(두 번 누름, 길게 누름)는 RPC 알림 토픽 `<prefix>/events/rpc`로 도착하며 읽지 않습니다. 입력의 `state`만 읽습니다. 레벨이 둘을 넘는 프리픽스(`home/garage/boiler`)는 수신되지 않으며, 한두 레벨은 수신됩니다. RPC로는 아무것도 보내지 않습니다.

**각 브로커에서** 이것은 스위치입니다(브로커의 `shelly`, 설정, MQTT). 지금 추가한 브로커는 켜져 있고, 내장 브로커는 항상 켜져 있으며, 이미 있던 브로커는 이전과 똑같이 수신하므로 누군가 켤 때까지 꺼져 있습니다. 스위치인 이유는 수신하는 토픽 `+/status/+`의 범위가 넓고, `*/status/*` 아래에 다른 것을 싣는 브로커는 이를 꺼 두려 하기 때문입니다. 꺼짐은 HotLoop이 그곳에서 이 토픽을 구독하지 않는다는 뜻입니다.

다른 토픽과 마찬가지로 신뢰할 수 없습니다. 문자, 숫자, `_.-`가 아닌 프리픽스, `kind:number`가 아닌 컴포넌트, 객체가 아니거나 64 KiB를 넘는 페이로드, 64개를 넘는 컴포넌트를 알리는 장치, 동시에 학습 중인 512대를 넘는 장치는 각각 무시되며, 한 프리픽스 아래 보관된 구조가 다른 프리픽스라고 주장하면 거부됩니다.

**무엇으로 테스트했나.** 실제 메시지 15세트와 제조사 자체 문서입니다.

## 무언가 스스로를 알리면 일어나는 일

1. **나타납니다.** 내장 브로커에서 스스로를 알리는 장치는 곧바로 HotLoop 장치가 됩니다. 프로토콜은 `mqtt`이고, 트리에는 배치되지 않으며, 스스로 붙인 이름(`kitchen-plug`, 충돌하면 `-2`)을 갖고 읽습니다. 태그는 알린 이름(`power`, `relay`)을 따릅니다. 엔티티는 구성이 준 이름, 장치 클래스, 상태 클래스, 단위, 카테고리, 아이콘을 받으며, 구성이 기본적으로 꺼져 있다고 지정한 엔티티는 비활성화된 상태로 시작합니다.
2. **아무것도 활성화되지 않습니다.** 모든 태그는 읽기 전용으로 만들어집니다. 스위치, 숫자, 텍스트는 제어 엔티티를 곧바로 받지만 활성화되지 않은 상태(`armed: false`)이므로, 화면이나 자동화가 첫날부터 `switch.kitchen_plug_relay`라는 이름을 쓸 수 있습니다. 사람이 포인트를 활성화하는 순간부터 동작하며, 그 전에는 동작하지 않습니다.
3. **admin이 결정합니다.** 장치, 발견됨. 누가 알렸는지(내장 브로커에서는 구성을 게시한 로그인과 클라이언트 id), 만들게 될 모든 컴포넌트, 읽는 모든 토픽, 모든 명령 토픽 전체, 그리고 살펴볼 것은 다음과 같습니다.

   - 컴포넌트가 읽는 토픽 밖의 명령 토픽("램프"의 명령이 `cmnd/boiler/POWER`로 가는 경우)
   - 디스커버리 프리픽스 안의 명령 토픽, 또는 다른 장치도 사용을 주장하는 명령 토픽
   - retained 명령을 요구하는 구성. retained 명령은 장치가 다시 연결될 때마다 재생되기 때문입니다
   - HotLoop이 평가할 수 없는 템플릿, 형식이 정의하지 않는 구성 키

   **수락**하면 계속 읽으며 포인트를 태그 편집기에서 하나씩 활성화할 수 있게 됩니다. 아무것도 활성화하지 않습니다. 장치가 영역을 제안했고 트리 노드가 정확히 그 이름이면 수락 대화상자가 이를 미리 채웁니다. 퍼블리셔가 스스로를 보일러실 아래에 분류할 수는 없으며, 사람이 수락을 클릭합니다. **무시**하면 장치, 태그, 엔티티를 버리고(이력은 다른 장치와 마찬가지로 남습니다) 다시 알려도 계속 버려진 상태로 둡니다. 발견된 장치를 삭제하는 것은 무시하는 것과 같습니다. 계속 알리는 장치는 그냥 다시 나타날 것이기 때문입니다.

## 장치가 마음을 바꿀 때

**다른 로그인은 무엇이라 말하든 검토를 위해 보류됩니다.** 내장 브로커에서 장치는 수락된 로그인을 기억합니다. 같은 장치를 다른 로그인이 알리면 구성이 한 글자도 다르지 않더라도 두 로그인을 나란히 보여 주며 검토를 위해 보류되고, 로그에 경고가 남습니다. 누군가 장치를 새 로그인으로 옮겼거나, 로그인이 자기 것이 아닌 장치를 알리고 있는 것입니다. 적용하면 새 로그인이 수락 기준 로그인이 됩니다. 거부하면 같은 것을 알리는 그 로그인은 계속 거부된 상태로 남습니다.

**수락된 장치의 구성이 바뀌면 검토를 위해 보류됩니다.** 수락된 구성은 계속 실행됩니다. 발견됨 화면은 변경 사항을 필드별로, 실행 중인 값과 알린 값을 비교해 보여 주며, admin이 적용하거나 거부합니다. 단위가 °C에서 °F로 바뀌거나 상태 토픽이 다른 곳을 가리키는 것이야말로 잘못된 숫자가 신뢰받는 얼굴을 얻는 방식입니다. 변경을 적용해도 포인트의 활성화 여부는 절대 바뀌지 않습니다. 그것은 사람의 결정이었고 앞으로도 그렇습니다.

펌웨어 업데이트, 새 장치 이름, 새 모델, 다른 아이콘은 저절로 적용됩니다. 버전이 올라갔다고 누군가 클릭해야 해서는 안 됩니다.

아무도 장치를 수락하기 전에는 항상 가장 최근의 알림이 적용됩니다. 아직 아무도 그 위에 무엇을 쌓지 않았기 때문입니다.

**빈 구성은 컴포넌트를 철회합니다.** 해당 포인트는 "14:02에 퍼블리셔가 철회함"이라는 사유와 함께 불량으로 읽히고, 아무것도 삭제되지 않습니다. 그 포인트의 알람은 대상을 유지하고 불량인 이유를 알려 줍니다. 같은 컴포넌트가 돌아오면 복원되며, 새 값을 보내기 전까지는 떠나기 전의 값을 그대로 내보내는 대신 "철회 후 다시 알림, 다음 값을 기다리는 중"으로 읽힙니다. 아무도 수락하지 않은 장치가 모든 컴포넌트를 철회하면 사라집니다. 아무도 그 위에 무엇을 쌓지 않았기 때문입니다.

**Zigbee2MQTT가 장치 이름을 바꾸면** 이전 구성 토픽을 지우고 같은 고유 ID로 새 토픽을 알립니다. HotLoop은 컴포넌트를 고유 ID로 식별하므로, 이는 1초 간격의 철회와 복원이며 잃는 것은 없습니다.

## 읽기

상태는 컴포넌트의 값 템플릿이 있으면 그것을 거친 뒤 컴포넌트 자체의 매칭을 거칩니다. 바이너리 센서는 `payload_on`/`payload_off`(기본 `ON`/`OFF`), 스위치는 `state_on`/`state_off`, 숫자는 숫자, select는 옵션 중 하나입니다. **맞지 않는 모든 것은 이유와 함께 불량 읽기가 되며** 타일에 표시됩니다.

- `"CLOSE" is neither payload_on "CLOSED" nor payload_off "OPEN"`
- `value_json has no key 'temperature'`
- `"unavailable" is not a number`
- `the publisher sent no value` (`None`, `null`, 빈 값, `unknown`을 보낸 경우)
- `no update for 300 s (expire_after)`

첫 번째는 실제 사례입니다. Zigbee2MQTT 1.41.0은 Avatto TRV07의 창문 센서를 이렇게 알리며, 이를 캡처한 사람은 창문이 전혀 표시되지 않아서 이슈를 열었습니다. HotLoop은 추측하지 않고 불량으로 표시하고 그 이유를 알려 줍니다.

**가용성**은 읽기가 아니라 장치의 연결 상태입니다. 장치가 가용성 토픽에서 오프라인이라고 하는 동안에는 자체 문구("the device says it is offline (plug/status = offline)")와 함께 연결 끊김으로 표시되고 엔티티는 사용할 수 없습니다. 첫 가용성 메시지가 도착하기 전까지는 가용성이 구성된 장치도 사용할 수 없는 상태입니다. 이것이 형식의 규칙이며 올바른 규칙입니다. 이 때문에 브로커 세션을 끊지는 않습니다. 그 브로커의 다른 모든 장치와 공유하는 세션이기 때문입니다.

`expire_after`는 그 초 동안 업데이트가 없으면 값을 불량으로 만듭니다. `off_delay`는 구성에서 장치가 꺼짐을 절대 보내지 않는다고 하므로, 그 초가 지나면 바이너리 센서를 끕니다. JSON 속성은 최대 64개 키, 8 KiB까지 엔티티에 들어가며 HotLoop 자체 속성(`friendly_name`, `source`, `armed` 등)보다 우선순위가 낮습니다(HotLoop 쪽이 항상 이깁니다).

상태 토픽이 없는 컴포넌트는 영원히 불량으로 읽힙니다. HotLoop은 명령으로부터 상태를 가정하는 일이 절대 없습니다.

## 명령

다음 세 가지가 이 순서로 충족되기 전에는 아무것도 명령되지 않습니다.

1. **사람이 장치를 수락했습니다.** 그 전에는 태그 편집기가 해당 장치의 포인트를 활성화하지 못하고("accept the device first"), 쓰기 게이트도 스스로 그 명령을 거부하므로, 손으로 수정한 행이나 포인트가 활성화되어 있는 오래된 백업도 아무 곳에도 이르지 못합니다.
2. **사람이 포인트를 활성화했습니다.** 태그 편집기에서 하나씩 합니다. 체크박스 앞에서 편집기는 명령이 어디로 가고 무엇을 보내는지 알려 줍니다. "Commands go to `plug/relay/set`, sending ON or OFF."
3. **쓰기 게이트가 명령을 통과시킵니다.** 다른 모든 쓰기와 같습니다. 쓰기 켜짐, 에이전트를 위한 MCP 스위치, 태그의 범위, 엔티티 자체의 검사, 유효한 세션입니다. 거부되든 아니든 호출 id와 함께 감사됩니다. 드라이런도 정확히 같은 질문을 합니다.

나가는 것은 구성이 말하는 그대로입니다. 스위치는 `payload_on`과 `payload_off`, 버튼은 `payload_press`, select는 옵션, 숫자나 텍스트는 값(정수는 정수로, `5.0`이 아니라 `5`)이며, 구성에 명령 템플릿이 있으면 그것을 거칩니다. 버튼은 한 번 누릅니다. "떼기"는 장치가 요청한 적 없는 두 번째 명령이 되므로, 발견된 버튼은 단발입니다.

조명은 `payload_on`/`payload_off`(JSON 스키마 조명은 `{"state":"ON"}`)를 받고, 밝기 명령 토픽으로는 자체 `brightness_scale`에 맞게 환산하고 반올림한 퍼센트 밝기를 받습니다(JSON 스키마 조명은 `{"state":"ON", "brightness":128}`). 커버는 `payload_open`, `payload_close`, `payload_stop`을 받고, 위치는 `set_position_template`을 거쳐 퍼센트에서 자체 `position_closed`..`position_open` 범위로 환산해 받습니다. 밸브는 열기와 닫기 페이로드(위치를 보고하는 밸브는 `position_open`과 `position_closed`)를 받고, 명령 토픽으로 위치를 받으며, `payload_stop`을 한 번 받습니다. 버튼처럼 발견된 밸브의 정지는 단발입니다. 구성이 `null`로 꺼 둔 페이로드(정지가 없는 커버)는 게이트가 이유와 함께 거부하는 명령입니다.

게이트는 다음 경우에 이유와 함께 명령을 거부합니다.

- 아무도 장치를 수락하지 않았습니다.
- 장치가 속한 브로커가 수신 전용입니다.
- 퍼블리셔가 컴포넌트를 철회했습니다.
- 명령 템플릿이 지원 범위 밖입니다("command template not supported: filter `regex_replace` is not supported at column 12"). "원시 값을 대신 보내기"는 절대 없습니다.
- 구성에 명령 토픽이 없습니다.
- 구성에 요청된 동작의 페이로드가 없습니다. 구성이 `payload_stop: null`인 커버의 정지, select에 없는 옵션, 100%를 넘는 밝기입니다. 페이로드는 검사 과정에서 만들어지므로 드라이런도 거부합니다.

**retained 명령은 구성을 따릅니다.** 구성이 `retain: true`를 요구하면 HotLoop은 그 컴포넌트의 명령을 retained로 게시하며, 사람이 이에 대해 결정하는 모든 곳에서 이를 알립니다. 발견됨 화면이 표시하고 태그 편집기가 쉬운 말로 설명합니다. 활성화하기 전에 그 의미를 이해하십시오. 브로커는 마지막 명령을 보관하다가 장치가 다시 연결될 때마다, 새벽 세 시에, 아무도 아무것도 만지지 않았는데도 장치에 전달합니다. 명령은 여전히 게이트를 통과했고 감사 기록에 이름과 함께 남아 있지만, 다시 일어나는 것입니다.

"이것을 저 토픽에 게시"하는 기능은 어디에도 없습니다. 자동화, 스크립트, MCP 어디에도 없습니다. 그것은 이름만 그럴듯한, 게이트를 우회하는 옆문이 될 것입니다. 코드에서 디스커버리 중 게시하는 것은 두 가지입니다. 게이트만 닿을 수 있는 드라이버의 쓰기, 그리고 birth입니다. 가드 테스트가 드라이버 패키지를 타입 검사하여 다른 무언가가 둘 중 하나를 호출하면 빌드를 실패시키며, 심어 둔 우회 코드로 이것이 실제로 작동함을 증명합니다.

## 템플릿

Python도 Jinja 엔진도 없습니다. 반복문이 없으므로 템플릿의 비용은 길이만큼입니다.

`{% set name = value %}`는 포함되며 그 형태만 지원합니다. Zigbee2MQTT는 모든 온도 조절기의 모드를 `{% set values = {'manual':'heat', ...} %}`로 쓴 다음 조회하며, 모드를 읽을 수 없는 온도 조절기는 신뢰할 수 없는 온도 조절기이기 때문입니다. 네임스페이스, 언패킹, 블록 형식은 없습니다. `.keys()`도 포함되지만 `in`의 오른쪽 항으로만 쓸 수 있으며, 그 템플릿들이 그것을 쓰는 곳이 그곳뿐이기 때문입니다.

| <span class="sr-only">세부 정보</span> | <span class="sr-only">세부 정보</span> |
|---|---|
| 구조 | 텍스트, `{{ expr }}`, `{% if %}` / `{% elif %}` / `{% else %}`, `{% set name = value %}`, `{# comments #}`, `-` 공백 제어 |
| 변수 | 값 템플릿: `value`, `value_json` (페이로드가 JSON일 때만), `entity_id`, `name`. 명령 템플릿: `value`, `entity_id`, `name` |
| 표현식 | 리터럴, `.attr`, `['key']`, `[0]`, 슬라이스, `+ - * / // % **`, `~`, 비교, `and or not`, `in`, `x if c else y`, 매핑의 `.get(key, default)`, `in mapping.keys()` |
| 테스트 | `defined`, `undefined`, `none`, `number`, `integer`, `float`, `boolean`, `string`, `mapping`, `sequence`, `true`, `false`, `eq`, `ne`, `lt`, `le`, `gt`, `ge`, `in`, `odd`, `even`, `divisibleby` |
| 필터 | `float`, `int`, `round`, `bool`, `default`/`d`, `string`, `lower`, `upper`, `capitalize`, `title`, `trim`, `replace`, `truncate`, `abs`, `length`/`count`, `min`, `max`, `tojson`, `to_json`, `from_json`, `is_defined`, `iif` |
| 함수 | `float()`, `int()`, `bool()`, `iif()`, `min()`, `max()` |

형식이 어떤 필터를 표준 Jinja와 다르게 문서화한 경우 HotLoop은 형식을 따릅니다. 중요한 것은 이것입니다. **기본값이 없는 `float`와 `int`는 실패합니다**, 숫자가 아닌 값에서. 표준 Jinja는 조용히 `0`을 돌려주는데, 센서가 응답을 멈췄을 때 그 0은 탱크가 비었다고 말하는 0이 됩니다.

값은 Python의 `str()`이 표현하는 방식으로 표현됩니다. 모든 퍼블리셔의 구성이 그것을 기준으로 작성되었기 때문입니다. `True`, `None`, `21.0`은 `21.0` 그대로입니다. 이는 겉모양의 문제가 아닙니다. Zigbee2MQTT의 접점 센서는 `payload_on: false`를 알리며 표현된 `False`와 일치합니다.

**누락된 키는 처리하지 않았다면 오류입니다.** 키가 없는 페이로드에서 `{{ value_json.temperature }}`는 빈 문자열이 아니라 그렇다고 말하는 불량 읽기입니다. `default`, `is defined`, 그리고 단독 `{% if value_json.x %}`는 의도적으로 이를 처리하므로 문제없습니다.

**지원 범위 밖은 구성이 도착할 때 거부되며** 위치도 알려 줍니다. "value template not supported: filter `regex_findall_index` is not supported at column 12". 컴포넌트는 존재를 볼 수 있도록 그래도 만들어지며 그 이유와 함께 불량으로 읽힙니다. 최선을 다한 부분 렌더링도, "원시 페이로드를 대신 사용"도 없습니다. 실제 템플릿 두 가지는 의도적으로 거부됩니다. `now()`(HotLoop이 언제 평가했느냐에 따라 달라지는 값은 장치의 읽기가 아닙니다), 그리고 네임스페이스와 `regex_findall`로 정규식 패턴을 만드는 Zigbee2MQTT 이벤트 템플릿입니다.

한도: 템플릿 4 KiB, 중첩 깊이 32, 출력 64 KiB, 64비트 정수(오버플로는 감김이 아니라 오류).

형식 고유의 필터는 표준 Jinja가 아니므로, 각각이 우리에게 요구하는 문서화된 동작을 인용한 손으로 쓴 테스트 케이스가 있습니다. 녹화본의 모든 템플릿은 파싱되어야 합니다.

조명, 커버, 밸브, 이벤트, 트리거, 그리고 그 뒤 행의 모든 컴포넌트에서는 태그 자체의 읽기 엔티티가 숨김으로 만들어지며, 화면에서는 하나의 엔티티로 보입니다. 각 태그는 여전히 따로 활성화되므로, 위치는 신뢰하지만 열기와 닫기는 신뢰하지 않는 커버도 그대로 구성할 수 있습니다. 수락 후에 값을 얻는 것(밝기를 보고하기 시작한 펌웨어)은 검토 대상 변경이며, 사람이 적용하면 엔티티도 태그와 함께 그 역할을 받습니다.

JSON 스키마 조명의 상태 메시지는 스키마가 변경된 것만 보내므로 하나로 합쳐집니다. 밝기만 있는 메시지나 Zigbee2MQTT의 `last_seen`만 있는 메시지는 조명을 켜진 채로 둡니다. 색상, 색온도, 효과는 속성으로 표시되며 명령되지 않습니다. 켜짐, 꺼짐, 밝기는 명령되며, 발견됨 화면은 색상이 있는 조명에 대해 이를 알려 줍니다. 기본 스키마 조명의 색상 토픽도 마찬가지로 읽지 않고 명령하지 않으며 목록에 표시됩니다. 템플릿 스키마는 지원되지 않으며 그렇다고 알려 줍니다. 커버의 틸트는 읽거나 명령하지 않으며 그렇다고 알려 줍니다.

장치 트리거는 자체 `payload`에서만 동작합니다. Zigbee2MQTT는 버튼의 모든 동작을 하나의 토픽에 두며 각 트리거는 그중 하나입니다. `payload`가 없는 트리거는 해당 토픽의 모든 것에서 동작합니다.

팬의 속도는 형식이 하는 대로 구성 자체의 `speed_range_min`..`speed_range_max` 기준으로 읽습니다. 꺼짐 위의 첫 단계가 첫 번째 퍼센트입니다. 구성이 일어날 수 없다고 한 수준(4단계를 알리면서 25를 보고하는 ESPHome 팬)은 625퍼센트가 아니라 그렇다고 말하는 불량 읽기입니다.

발견됨 화면은 컴포넌트의 명령이 갈 수 있는 모든 토픽을 나열합니다. 주 토픽 외에 조명의 밝기 토픽, 팬의 속도 토픽도 나열하며, 컴포넌트가 읽는 범위 밖에 있거나, 프리픽스 안에 있거나, 다른 장치가 사용을 주장하는 토픽에 표시를 합니다.

온도 조절기나 온수기의 설정값 범위는 구성 자체의 범위이며, 구성이 주지 않으면 형식의 기본값입니다(온도 조절기는 7에서 35 °C, 온수기는 43.3에서 60 °C이고, 구성이 `temperature_unit: F`이면 °F). 이것이 태그의 범위이므로, 게이트는 최대 30까지인 라디에이터 밸브에 31 °C를 무엇이든 전송하기 전에 거부합니다. 모드는 구성의 목록이며, 나열되지 않은 모드도 같은 방식으로 거부됩니다. 화면은 정확히 그 모드들을 제공하고, 적용된 변경으로 새 모드가 생기면 화면도 그것을 받습니다.

알람 패널의 `code`는 소비자 화면이 무언가를 보내기 전에 요구하는 것입니다. HotLoop에서는 사람이 활성화한 태그와 감사되는 모든 명령으로, 누가 경계 설정이나 해제를 할 수 있는지는 게이트가 결정하므로 동작은 구성이 말하는 대로 나갑니다. 명령 템플릿이 코드 자체(`{{ code }}`)를 요구하는 패널은 명령할 수 없습니다. HotLoop에는 그곳에 넣을 코드가 없으며 발견됨 화면이 그렇다고 알려 줍니다. 청소기의 `send_command_topic`은 사용하지 않습니다. 임의의 명령은 HotLoop이 구성과 대조해 검사할 수 없는 바로 그것이기 때문입니다.

카메라나 이미지의 사진은 컴포넌트마다 최신 것 하나를 메모리에 최대 4 MiB까지 보관하며 `GET /api/entities/{entity_id}/image`로 제공됩니다. HotLoop은 바이트가 JPEG, PNG, GIF, WebP일 때만, 구성의 `content_type`이 무엇이라고 주장하든 보관합니다. SVG는 스크립트를 실행하는 문서이고, 대시보드를 여는 사람에게 스크립트를 실행하는 "사진"은 보안 구멍이기 때문입니다. 태그는 짧은 해시를 보관하므로 JPEG로 가득 찬 데이터베이스 없이도 이력에 사진이 언제 바뀌었는지 남습니다. URL로 알린 이미지는 링크입니다. HotLoop은 http 또는 https일 때만 이를 보여 주며 절대 가져오지 않습니다. 장치가 지정한 주소를 아무거나 가져오는 서버는 네트워크의 무엇이든 가리키도록 조작될 수 있기 때문입니다. 둘 다 로그북에 기록되지 않습니다. 카메라는 매초 바뀌며 tag_history에 이미 모든 변경이 있습니다.

형식이 정의하는 모든 컴포넌트는 무언가가 됩니다. 정의하지 않는 컴포넌트(`kettle` 등)는 알린 내용과 함께 저장되고 아무것도 만들지 않는 것으로 목록에 나옵니다. 형식에는 날짜, 시간, datetime 컴포넌트가 없으므로 이 목록에도 없습니다.

엔티티 ID는 HotLoop의 것이며 장치와 태그로 만들어집니다. 구성의 `object_id`와 `default_entity_id`는 무시됩니다. 구성은 HotLoop의 네임스페이스에서 이름을 고를 수 없으며, 악의적인 구성이라면 `switch.boiler_main`을 고를 것입니다.

## 모두 신뢰할 수 없습니다

구성이 말하는 모든 것은 프리픽스에 게시할 수 있는 누구에게서든 왔습니다. 그래서:

- 이름과 텍스트는 길이가 제한되고 제어 문자가 제거되며, 화면은 이를 HTML이 아니라 텍스트로 페이지에 둡니다.
- 와일드카드가 있는 토픽, `$` 토픽, 넣을 기준이 없는 `~`는 이유와 함께 거부됩니다.
- 64 KiB를 넘는 구성은 거부됩니다. 장치는 컴포넌트를 512개 넘게 가질 수 없고, 한 브로커에서 결정을 기다리는 장치는 256대를 넘을 수 없으며, 초당 200개를 넘는 구성 메시지는 버려지고 집계됩니다. 모든 거부는 집계되어 발견됨 화면에 표시되며 말없이 버려지는 일은 없습니다.
- HotLoop은 `<prefix>/+/+/config`와 `<prefix>/+/+/+/config`를 구독하며 프리픽스 아래의 `#`는 구독하지 않으므로, 잘못된 깊은 토픽이 무언가를 파싱하게 만들 수 없습니다.
- 256 KiB를 넘거나 UTF-8이 아닌 상태 페이로드는 불량 읽기입니다.

내장 브로커에서 익명 연결을 허용하면 네트워크의 누구나 장치를 알리고 어떤 명령 토픽에든 게시할 수 있으며, 발견됨 화면은 이를 빨간색으로 알립니다. 각 장치에 HotLoop에서 프로필로 만든, 토픽 이름을 딴 자체 로그인을 주십시오([내장 MQTT 브로커](/ko/iot/broker/)). 그러면 장치는 스스로를 알릴 수만 있고 다른 장치의 명령 토픽은 건드릴 수 없습니다.

## 브로커 쪽

디스커버리는 내장 브로커에서 실행되며([내장 MQTT 브로커](/ko/iot/broker/) 참고), 브로커가 켜져 있으면 기본으로 켜집니다. HotLoop 자체 클라이언트는 시작할 때마다 만들어져 메모리에만 보관되는 로그인으로 접속하므로, 설정할 것도, 백업에 유출될 것도 없습니다. 자체적으로 게시하는 것은 birth(`<prefix>/status` = `online`) 하나뿐이며, 이를 수신하는 퍼블리셔가 다시 알리게 합니다.

| 변수 | 기본값 | <span class="sr-only">상세</span> |
|---|---|---|
| `HOTLOOP_BROKER_DISCOVERY` | `true` | 내장 브로커에서 알림 수신 |
| `HOTLOOP_BROKER_DISCOVERY_PREFIX` | `homeassistant` | 알림이 도착하는 토픽 프리픽스 |

브로커당 클라이언트 하나인 `hotloop-disc-embedded`를 리스너와 발견된 모든 장치의 드라이버가 공유합니다. `--mcp-stdio` 헬퍼는 하나도 열지 않습니다. 같은 id의 두 번째 클라이언트는 몇 초마다 Gateway의 클라이언트를 브로커에서 쫓아낼 것이기 때문입니다. 하나의 데이터베이스에 복제본이 여럿이면 디스커버리 잠금을 쥔 복제본만 수신합니다.

## 다른 브로커

많은 공장이 이미 브로커를 운영합니다. UNS 역할을 하는 Mosquitto, 또는 Zigbee2MQTT 장치가 가져온 브로커입니다. HotLoop은 이들도 수신합니다. 설정, MQTT, 브로커 추가에서 id(그 브로커에서 온 모든 장치에서 브로커를 가리키는 이름), 위치, 로그인, 퍼블리셔가 알리는 프리픽스를 입력합니다. 브로커가 켜져 있을 필요는 없으며, HotLoop은 이를 위해 내장 브로커가 필요하지 않습니다.

HotLoop 자체 브로커와 다른 점이 세 가지 있으며 의도된 것입니다.

- **장치는 받은편지함에서 기다립니다.** 바쁜 공장 브로커에서 "저절로 나타남"은 점심 전에 화면에 장치 300대가 뜨는 것을 뜻합니다. 그래서 알려진 장치는 누군가 수락하기 전까지 아무것도 만들지 않고 읽지도 않은 채 발견됨 화면에 목록으로만 올라갑니다. 수락하면 만들어지고, 읽고, 다른 장치처럼 포인트를 활성화할 수 있습니다. 모든 것을 쏟아 내도 신뢰하는 브로커라면 "장치가 저절로 나타남"으로 전환할 수 있습니다.
- **라스트 윌 없음.** HotLoop은 라스트 윌 없이 접속합니다. 공유 브로커의 `offline` 윌은 HotLoop뿐이었을 때에도 그곳의 다른 모든 퍼블리셔에게 무언가가 사라졌다고 알리게 됩니다. 테스트는 CONNECT 패킷 자체를 검사하고, 연결을 끊어 아무 말도 하지 않음을 증명합니다.
- **ACL은 그 브로커의 것입니다.** HotLoop은 다른 사람의 브로커에서 누가 무엇을 게시했는지 볼 수 없으므로 그곳에는 "로그인이 알림"이 없고, 각 로그인이 무엇을 만질 수 있는지는 그 브로커의 몫입니다. HotLoop에 프리픽스와 수락한 장치의 토픽을 읽고, birth와 명령 토픽을 쓰는 로그인을 주고 그 외에는 주지 마십시오. Mosquitto의 경우:

  ```
  user hotloop
  topic read homeassistant/+/+/config
  topic read homeassistant/+/+/+/config
  topic write homeassistant/status
  # the devices you accept, for example a Zigbee2MQTT bridge:
  topic read zigbee2mqtt/#
  topic write zigbee2mqtt/+/set
  ```

**수신 전용**은 HotLoop이 말해서는 안 되는 브로커를 위한 것입니다. 운영 UNS나 다른 사람의 공장입니다. HotLoop은 그곳에 아무것도 게시하지 않습니다. birth도 명령도 없습니다. 이것은 화면이 아니라 세션의 규칙입니다. 게시가 거부되고, 쓰기 게이트는 누군가 수락한 장치와 누군가 활성화한 포인트라 하더라도 드라이런을 포함해 그 장치에 대한 모든 명령을 "the broker plant-uns is listen-only"로 거부합니다. 로그인에는 `topic read` 줄만 있으면 됩니다.

비밀번호는 UniFi 콘솔의 것처럼 장치 자격 증명 키(`HOTLOOP_SECRET_KEY_FILE`)로 봉인되며 API에서 다시 나오지 않습니다. 키가 없으면 비밀번호가 있는 브로커는 평문으로 저장되지 않고 거부됩니다. 백업에는 봉인된 채로 담기며 장치 자격 증명과 같은 규칙으로 복원됩니다([백업과 복원](/ko/iot/backup/)). 비밀번호를 열 수 없는 브로커는 연결되지 않고 목록에만 나타나며 이유를 알려 줍니다.

브로커를 변경하면 리스너와 그 브로커에서 온 모든 장치가 새 설정으로 다시 연결됩니다. 하나를 끄면 해당 장치는 남아 있으며, 불량으로 읽히고 이곳에서 브로커가 실행되고 있지 않다고 알려 줍니다. 브로커를 제거하면 받은편지함도 함께 사라지며, 그 브로커에서 누군가 수락한 장치가 아직 있으면 해당 장치를 지목하며 거부됩니다.

## Edge Relay에서

Edge Relay도 같은 코드로 디스커버리를 하지만, 결정을 보관할 데이터베이스도 결정을 내릴 화면도 없습니다. 그래서 들리는 것을 받아 읽고 Sparkplug로 전달하며, 찾은 어떤 것도 활성화할 수 없습니다. 태그는 모든 발견된 태그처럼 읽기 전용이고, 장치는 수락되지 않으며, 릴레이에는 쓰기 경로가 전혀 없습니다. 장치 파일에 브로커를 지정하십시오. [Edge Relay 레퍼런스](/ko/edge-relay/reference/#디스커버리-41810)를 참고하세요. 명령할 수 있는 장치는 반대편에서 도달합니다. Gateway에서 수락하고 활성화한 뒤, Gateway가 푸시하는 파일로 전달됩니다. 릴레이는 멈추면 들은 것을 잊고, 브로커에서 다시 듣습니다.

## 재시작과 재생

수락된 장치는 장치 행에서 실행됩니다. HotLoop은 공장과 함께 다시 올라오는 데 retained 메시지가 하나도 필요하지 않습니다.

내장 브로커는 재시작 후 아무것도 보관하지 않으므로, 이후에는 모든 구성이 "없음"이 됩니다. **구성이 없는 것은 철회가 아닙니다.** 명시적인 빈 구성만 철회입니다. 그렇지 않으면 장비가 재부팅될 때마다 공장 전체가 철회될 것입니다. 장치가 다음 상태를 보내기 전까지 엔티티는 재시작 전의 값을 현재 값처럼 꾸미지 않고 알 수 없음으로 읽힙니다.

브로커가 retained 구성 수백 개를 한꺼번에 재생하면 하나의 배치입니다. 2초의 정적, 한 번의 처리, 한 번의 다시 불러오기입니다. 이미 기록된 것의 재생은 아무것도 바꾸거나 다시 불러오지 않습니다.

## 백업

`mqtt_devices`(누가 무엇을 수락하고 무시했는지), `mqtt_configs`(도착한 그대로의 모든 구성, 바이트 단위), `mqtt_discovered`(정규화된 각 컴포넌트)는 모든 백업에 들어 있습니다. 결정은 어떤 장치도 다시 알릴 수 없는 부분입니다.
