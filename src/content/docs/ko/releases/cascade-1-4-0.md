## 개요

1.4.0은 Cascade 설치를 오래 운영하기 쉽게 만듭니다. 서버는 충돌하는 대신 데이터베이스를 기다리고, 완료된 실행은 지정한 일수 동안 보관했다가 파일과 함께 정리할 수 있으며, 소유자는 API 키 하나가 호출하는 빈도를 제한할 수 있고, 인스턴스 전체를 백업하고 복원할 수 있습니다. 로드맵에 남아 있던 확장성 테스트 하나도 마무리합니다. 엔진, 워크플로 파일 형식, REST API, MCP 서버(도구 83개), 14개 언어는 1.3.0과 같습니다.

## 데이터베이스를 기다림

분리 설치(PostgreSQL 위의 서버, 워커, 웹훅 파드)에서는 파드가 데이터베이스 이름이 확인되기 전에 시작되어 준비되기까지 두세 번 재시작했습니다. 1.2.1과 1.3.0도 그랬습니다. 이제 데이터베이스에 연결하지 못하는 서버, 워커, 웹훅은 로그에 그렇다고("waiting for the database", 기다린 시간과 함께) 남기고 최대 5분 동안 다시 시도한 뒤 데이터베이스가 응답하면 연결합니다. 잘못된 비밀번호, 형식이 틀린 주소, 존재하지 않는 데이터베이스는 기다려도 해결되지 않으므로 여전히 즉시 중단됩니다. 차트의 시작 프로브는 프로그램만큼 기다립니다. 실제 k3s에서 새로 분리 설치를 한 결과, 차트 테스트를 세 번 실행하는 동안 재시작이 없었습니다.

## 완료된 실행 보관

설정에 완료된 실행 보관 기간(일)이라는 새 필드가 생겼고, `PATCH /api/v1/settings`는 `retentionDays`를 받습니다. 기본값은 꺼짐(0)이며 모든 실행은 이전처럼 보관됩니다. 숫자를 지정하면 한 시간에 한 번 메인 노드가 그보다 오래전에 끝난 성공, 실패, 취소된 실행을 단계 데이터와 함께 삭제합니다. 아직 진행 중인 실행이나 부모가 진행 중인 실행은 건드리지 않습니다. 각 배치는 감사 로그에 `execution.pruned`를 쓰고, 설정을 바꾸면 `instance.retention`을 씁니다.

같은 시간별 정리 작업이 이제 보관 설정과 관계없이 Blob 저장소도 정리합니다. 데이터베이스에 넣기엔 너무 큰 출력과, 더 이상 어떤 실행도 가리키지 않는 첨부 파일이 대상입니다. 두 실행이 공유하는 파일은 마지막 실행이 사라질 때까지 남고, 24시간이 지난 파일만 확인하므로 단계가 방금 저장한 파일은 절대 지워지지 않습니다. 직접 삭제한 실행에도 새로 적용됩니다. 이전에는 삭제된 실행의 큰 출력이 디스크에 영원히 남았습니다. 필요한 것을 읽지 못한 작업은 아무것도 지우지 않으며, 각 작업은 감사 로그에 `blobs.collected`를 씁니다.

## API 키별 제한

설정에 키당 분당 API 요청 수라는 새 필드가 생겼고, `PATCH /api/v1/settings`는 `apiRateLimit`를 받습니다. 기본값은 꺼짐입니다. 숫자를 지정하면 각 API 키와, 키로 MCP에 로그인한 각 에이전트가 분당 그 수만큼 요청할 수 있습니다. 제한을 넘은 호출은 `Retry-After`와 함께 429로 응답합니다. 키마다 자체 카운트가 있고, 에디터에 로그인한 사람은 제한을 받지 않습니다. 카운트는 프로세스별이므로 메인 노드가 세 개이면 키 하나가 최대 세 배까지 요청할 수 있습니다. 변경하면 감사 로그에 `instance.api_rate_limit`를 씁니다.

## 백업과 복원

`hotloop-cascade backup DIR`은 서버가 실행 중일 때 만든 SQLite 데이터베이스의 일관된 사본, 저장된 모든 자격 증명을 봉인하는 키 파일, Blob 파일, 그리고 이들의 해시가 담긴 `manifest.json`을 새 디렉터리에 씁니다. `hotloop-cascade restore DIR`은 매니페스트와 대조해 모든 파일을 확인한 뒤 되돌려 놓으며, `--replace`를 지정하지 않으면 데이터베이스나 다른 키를 덮어쓰기를 거부합니다. PostgreSQL에서는 백업에 키, Blob, 매니페스트가 들어 있고 데이터베이스 부분을 위한 `pg_dump` 명령을 출력하며, 복원은 `pg_restore` 명령을 출력합니다. S3나 Azure에 보관된 Blob은 복사되지 않습니다. 자세한 내용은 `docs/GOVERNANCE.md`에 있습니다.

## 뒷받침한 테스트

- 로드맵이 정한 확장성 테스트가 끝났습니다. 하나의 PostgreSQL 위의 메인 노드 두 개가 매분 실행되는 워크플로를 한 시간 동안 돌리는 동안, 한 노드를 시각 경계에서 SIGKILL로 종료하고 매번 약 25초 동안 내려 둔 채 이를 연속으로 일곱 번 했습니다. 61개의 1분 시각에 61번 실행되었고 누락도 중복도 없었습니다.
- 테스트 스택의 OAuth 서버(Hydra)가 이제 Postgres에서 실행됩니다. 이전에는 병렬 실행에서 실패했고, 변경 후에는 통과했으며, 변경을 되돌리자 다시 실패했습니다. Cascade 코드는 토큰을 조회하지 않습니다.
- 차트 테스트는 이제 설치 중 파드가 재시작하면 실패합니다.
- 실패한 로그 대상은 이제 전송이 실패한 시점이 아니라 실패가 기록된 시점부터 백오프를 기다립니다. 실패 메모를 쓰는 속도가 느려 첫 1초가 소진되었고, 직후의 재시도가 보류되지 않고 전송되었으며, 부하 속에서 테스트 모음이 이 지점에서 멈췄습니다.
- 언어 점검이 이제 실행 하나를 보여 주는 화면을 두 가지 너비로 모든 언어에서 훑습니다. 실행의 단계와 상태 용어는 공장 현장에서 가장 많이 읽는 말이기 때문입니다.
- 새 설정 거부 메시지 두 개는 모든 언어로 번역되었고, 설정 도움말에는 큰 출력이 실행과 함께 사라진다고 안내되어 있습니다.

## amd64 전용인 이유

이 릴리스는 amd64만 빌드합니다. 멀티 아키텍처는 별도의 실행으로 나가므로, 다음 릴리스는 둘 다 빌드하는 작은 버전 올림입니다. `stable`, `latest`, `1.4`, `1`은 이미 가리키던 arm64 이미지 옆에 새 amd64 이미지를 함께 나열합니다.

## 업그레이드와 되돌리기

마이그레이션은 없습니다. 스키마는 1.3.0과 같습니다. 1.4.0으로 `helm upgrade`하거나 `:stable`이 Quadlet 유닛을 옮기게 두세요. 데이터베이스에서 바뀐 것이 없으므로 1.3.1로 되돌려도 안전합니다. 롤백으로 되돌릴 수 없는 것은 정리입니다. 보관 기간이 삭제한 실행은 사라지고, 시간별 정리가 제거한 Blob도 사라집니다. 보관 기간은 켜기 전까지 꺼져 있으므로 먼저 백업하세요. Blob 정리는 보관 기간 없이도 실행됩니다.
