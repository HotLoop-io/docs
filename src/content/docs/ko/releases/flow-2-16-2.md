HotLoop Flow 2.16.2는 큰 플로를 싸게 돌리게 합니다. 노드 12,000개를 초당 약 3,000개 메시지로 돌리는 플랜트는 아무도 대시보드를 보지 않는데도 CPU 한계에 걸려 있었습니다. 같은 플로가 이제 CPU는 약 3분의 1, 메모리는 절반도 안 씁니다. 플로, 설정, chart에는 바뀌는 것이 없습니다.

## 바뀐 내용

- **function 노드가 JavaScript 런타임을 다시 만들지 않습니다.** function 노드마다 작은 런타임 풀을 따로 갖고 있었고, Go의 가비지 컬렉터가 매 주기마다 그 풀을 모두 비웠습니다. function 노드가 수천 개인 플로는 거의 모든 메시지마다 새 런타임을 만들었고, 그때 생긴 쓰레기가 다음 수집을 일으켰습니다. 노드 12,000개짜리 플로의 프로파일은 CPU의 41%를 여기에 쓰고 있었습니다. 이제 런타임은 컬렉터가 비울 수 없는 공유 목록에서 가져옵니다. 함수가 전역 객체를 바꾼 런타임은 버려지고 다른 노드에 절대 넘겨지지 않습니다.
- **큐에 있는 메시지가 64바이트 대신 24바이트를 차지합니다.** 모든 노드의 받은 편지함은 노드가 시작될 때 1,024칸 전체로 할당되므로, 노드 12,000개짜리 플로에서는 받은 편지함만 약 800MB였고 컬렉터가 매 주기마다 이를 훑어야 했습니다. 이제 약 300MB입니다.
- **대시보드가 아무도 볼 수 없는 업데이트를 준비하지 않습니다.** 열린 페이지가 없는데도 대시보드는 바뀐 모든 위젯의 JSON 업데이트를 초당 열 번 만들고 버렸습니다. 이제는 변경 사항을 비우고 아무것도 만들지 않습니다. 나중에 열리는 페이지는 포인트를 포함해 여전히 전체 상태에서 시작합니다.
- 예산은 고정된 스핀 루프로 조정되므로 느린 머신이 불이익을 받지 않습니다. 2.16.1에서 실패합니다.
- **Helm 인덱스가 게시된 모든 버전을 유지합니다.** chart를 게시하면 예전에는 새 버전만으로 `index.yaml`을 다시 만들었기 때문에, 이전 chart에 고정된 고객은 더 새로운 chart가 나오면 다시 렌더링할 수 없었습니다. 이제 Pages가 가진 모든 버전을 유지합니다.
- **브라우저 테스트가 확인마다 최대 20초를 기다립니다.** 부하가 걸린 러너에서는 런타임이 보낸 값을 페이지가 보여 주는 데 기본 5초보다 오래 걸렸습니다. 이것은 테스트만 바꿉니다.

## 무엇을 고치는지, 숫자로

한 대의 머신에서 같은 합성 플로로, 초당 약 2,930개 메시지, 연결된 클라이언트 없이 측정했습니다.

| <span class="sr-only">세부 정보</span> | 2.16.1 | 2.16.2 |
|---|---|---|
| 사용한 CPU | 0.79코어 | 0.29코어 |
| 메시지 1,000개당 CPU | 268 ms | 99 ms |
| 유휴 플로가 차지한 메모리 | 799 MB | 333 MB |

## 새 설정

없습니다.

## 업그레이드

2.16.2 이미지와 chart로 평소처럼 `helm upgrade`를 하거나, Quadlet 유닛에 새 태그를 넣으면 됩니다. 처음 시작할 때 일어나는 일은 없고 마이그레이션할 것도 없습니다. 플로 파일은 이전과 바이트 단위로 똑같이 불러오고 저장됩니다. 이번 릴리스는 amd64 이미지를 빌드합니다. `2.16`과 `2` 태그는 2.16.1에서 이미 가진 arm64 이미지를 유지하고, arm64는 2.16.3에서 돌아옵니다. arm64를 쓰신다면 그때까지 2.16.1에 머무르세요.

이미지: `ghcr.io/hotloop-io/hotloop-flow:2.16.2`, linux/amd64. Chart: `https://hotloop.io/hotloop-flow/`. 이 태그의 README에 나머지가 그림과 함께 있습니다: https://github.com/HotLoop-io/hotloop-flow/blob/v2.16.2/README.md
