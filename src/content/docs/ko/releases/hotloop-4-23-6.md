로드맵의 Protect, Access, 전원 박스 항목에 코드가 생기고, Shelly 장치가 Shelly와 직접 통신하며, OPC UA PubSub에 메시지 보안과 메타데이터가 생깁니다. amd64 전용으로 빌드되었고 멀티 아키텍처 빌드는 다음 버전으로 이어집니다.

## 바뀐 내용

- **UniFi Protect, 장치로.** 프로토콜 `unifi-protect`이며, 콘솔의 Integrations 페이지에서 받은 API 키를 콘솔 비밀번호처럼 봉인하고 인증서를 고정합니다. 카메라, 센서, 조명, 사이렌은 스스로 추가되는 tag입니다. 카메라의 움직임과 스마트 감지(사람, 차량, 택배, 번호판, 얼굴, 동물)는 이벤트 websocket에서 오며, 끊겨 있는 동안은 「움직임 없음」이 아니라 불량으로 읽힙니다. 사이렌은 울리도록 활성화할 수 있고, `alarm.<trigger>.fire`는 알람 관리자의 webhook을 보내 HotLoop 알람이 카메라를 녹화하게 합니다. 카메라의 스냅숏은 라우트 하나입니다. 모든 이벤트가 logbook에 있습니다. [UniFi Network](/ko/iot/unifi/#unifi-protect)를 보세요.
- **UniFi Access, 장치로.** 프로토콜 `unifi-access`이며 API 토큰을 씁니다. 각 문의 위치와 잠금은 tag이며 알림 websocket이 최신 상태로 유지하고, 모든 변경이 logbook에 있습니다. 잠금 해제는 사람이 활성화하는 쓰기이며 쓰기 게이트를 거쳐 감사됩니다. [UniFi Network](/ko/iot/unifi/#unifi-access)를 보세요.
- **SmartPower PDU 아웃렛.** 아웃렛의 릴레이, 전력, 전류, 전압, 역률은 UniFi Network 장치의 tag이고, PDU의 총 소비량도 하나입니다. 아웃렛의 `on`에 쓰면 그것을 켜고 다른 모든 아웃렛의 이름을 유지합니다. `cycle`은 끄고, 기다리고, 다시 켜며, 15분에 최대 한 번이고 항상 켜진 상태로 끝납니다. [UniFi Network](/ko/iot/unifi/#smartpower-pdu-콘센트)를 보세요.
- **Shelly 장치.** 프로토콜 `shelly`: 장치 자체의 digest 로그인을 쓰는 Gen2 이상의 RPC, 보고하는 모든 구성 요소의 tag, 스위치, 조명, 커버, 온도조절기에 대한 쓰기입니다. Gen1은 MQTT로 안내하는 메시지와 함께 거부됩니다.
- DataSetMetaData와 디스커버리 응답은 클 때 청크로 나뉘며, Siemens 발행자가 캡처한 메시지에서 읽었습니다. 발행자는 기본적으로 열 번의 간격마다 메타데이터를 알립니다(`HOTLOOP_UADP_PUBLISH_METADATA_EVERY`, 0이면 끔). [프로토콜과 드라이버](/ko/iot/protocols/)를 보세요.
- **포워드 큐의 배출기가 다시 확인하고, 실패하면 알립니다.** 읽기값이 기다리는데 아무것도 보내지 않은 패스는 조용한 폴링이 절대 보내지 않는 신호를 기다렸고, 실패한 패스는 로그에 한 줄도 없이 30초간 물러났습니다.
- **테스트가 기다리는 것을 기다립니다.** 에너지 테스트 여섯 개가 고정된 sleep 대신 장비의 읽기값을 기다립니다.

- **응답 없는 Modbus 장치는 모든 포인트가 불량으로 읽힙니다.** 시리얼 회선에서 타임아웃된 요청이 폴링 마감 시간 전체를 썼기 때문에 첫 번째 블록만 불량이 되고, 이후의 모든 포인트는 케이블이 뽑혀 있는 동안 마지막 정상 값을 유지했습니다. 이제 아무 응답도 하지 않는 장치는 같은 폴링에서 모든 포인트를 불량으로 표시합니다. [프로토콜과 드라이버](/ko/iot/protocols/)를 보세요.
- **완성된 기능은 켜진 채 출시됩니다.** Helm 차트와 바이너리에서: 내장 MQTT 브로커(로그인은 HotLoop에서 만듭니다), OPC UA 서버(인증 켜짐, 관리자에게 Settings가 보여 주는 생성된 `opcua-reader` 로그인 포함), 예약 리포트, 매일의 로컬 백업(24시간마다, 5 Gi 볼륨), ServiceMonitor(Prometheus 오퍼레이터 CRD가 있는 곳에서만 렌더링되므로 없는 클러스터는 이전처럼 설치됩니다), 호스트 이름이 없는 Ingress(`ingress.hosts[0].host`를 설정하기 전까지 클래스가 제공하는 모든 호스트에 응답합니다)입니다. 리포트, 백업, OPC UA 인증서, edge 큐는 기본적으로 HotLoop 데이터 디렉터리 아래의 쓰기 가능한 디렉터리를 쓰며, 다른 서비스가 이미 잡고 있는 포트는 유휴 상태로 두고 그렇다고 알립니다. 차트 `hotloop`과 생성된 IoT, Edge 차트에 모두 들어 있습니다.
- **알람 채널과 edge 발행자는 켜져 있으며 대상을 기다립니다.** webhook, 이메일, ntfy, Gotify, Discord webhook, Discord 봇 채널과 `edgePublish`는 첫 시작부터 켜져 있습니다. 보낼 곳이 없는 채널은 더 이상 설치나 시작을 막지 않고 기다리며 그렇다고 알립니다. 관리자는 Settings의 「Where alarms and readings go」에서 각 대상을 입력하며, 거기에 저장한 것이 차트 값보다 우선합니다. 알람 채널은 저장할 때 적용되고, edge 발행자의 대상은 다음 재시작에 적용됩니다. Settings에는 엔드포인트와 생성된 로그인이 있는 OPC UA 서버 카드도 있습니다.
- **Kafka 대상은 브로커가 새 topic을 배치하기를 기다립니다.** 바쁜 호스트가 잠시 펜스한 단일 브로커는 첫 확인을 `INVALID_REPLICATION_FACTOR`로 실패시켰는데, 이제 대상은 자신의 시간이 다할 때까지 기다리고 브로커가 답한 내용을 알립니다.
- **포워드 큐의 배출기가 다시 확인하고, 실패하면 알립니다.** 읽기값이 기다리는데 아무것도 보내지 않은 패스는 조용한 폴링이 절대 보내지 않는 신호를 기다렸고, 실패한 패스는 로그에 한 줄도 없이 30초간 물러났습니다.

- **4.23.4와 4.23.5에서 이어짐.** TwinCAT `.TcVIS`와 cds-text-sync, codescribe 화면이 버튼, 프레임, 램프, 식 규칙과 함께 가져와지고, UniFi 화면의 새로 고침은 불러오는 중인 뷰를 기다립니다. 두 버전 모두 공개되지 않았으므로 둘 다 여기에 있습니다. [4.23.4](/ko/releases/hotloop-4-23-4/)와 [4.23.5](/ko/releases/hotloop-4-23-5/)를 보세요.

## 마이그레이션

없습니다.

## API 변경 사항

`GET /api/unifi-protect/{id}/cameras/{camera}/snapshot`은 카메라의 현재 JPEG를 돌려줍니다. 프로토콜 목록에 `unifi-protect`와 `unifi-access`가 있습니다. [HTTP API](/ko/iot/api/)를 보세요.

## 4.23.5에서 업그레이드

평범한 `helm upgrade`입니다. 마이그레이션도 새 secret도 없습니다. 4.23.4와 4.23.5는 태그가 만들어졌으나 릴리스 실행이 아무것도 공개하기 전에 테스트 작업에서 실패했으므로, 이전 릴리스는 4.23.3이며 이번 릴리스에 둘의 변경이 모두 들어 있습니다. 위 기능 중 어떤 것이든 설정하는 values 파일이 여전히 우선하며, 하나를 `false`로 설정하면 listener, Service, 볼륨, Ingress를 렌더링하지 않습니다.

## 검증되지 않은 것

- Protect, Access, PDU의 아웃렛은 공개된 API를 바탕으로 만들었고 상태를 유지하는 대역 콘솔로 검증했습니다. 어느 것도 실제 콘솔이나 PDU에서 사용된 적이 없으므로 로드맵의 해당 항목은 체크하지 않았습니다.
- 알람 알림에 첨부하는 스냅숏은 구현되지 않았습니다.
- PubSub: Security Key Service는 구현되지 않았고(키는 정적입니다), Siemens, CODESYS, Beckhoff 발행자가 벤치에 올라온 적은 없습니다.
- UniFi 포트 비활성화는 여전히 실제 10.6 콘솔 웹 UI의 요청을 기다리고 있습니다.
