HotLoop Flow 2.16.5는 요청보다 느리게 응답하는 장치 뒤에 Modbus 읽기가 쌓이는 것을 막습니다. 플로, 설정, chart는 아무것도 바뀌지 않습니다.

## 바뀐 내용

- **이전 요청에 응답하는 중에 다시 들어온 폴링은 가장 최신 것으로 합쳐집니다.** 다른 노드와 공유하는 연결을 통해 한 번에 하나의 요청에만 응답하는 PLC를 폴링하는 Modbus getter, flex getter, read 노드는 장치가 응답할 수 있는 것보다 많은 요청을 보냈습니다. 노드의 수신함은 가득 찰 때까지 커졌고, 앞단의 노드는 막혔다가 30초 한도에서 메시지를 버렸습니다. 공장의 파드에서는 대기 중인 메시지 320,000개 중 190,000개가 getter에 있었고, getter 179개의 수신함이 가득 찼으며, 밀린 양과 함께 메모리가 올라갔습니다. 이제 노드는 대기 중인 메시지 중 같은 것을 요청하는 것이 무엇인지 알려 줄 수 있고, 다음 메시지를 가져올 때 각 그룹에서 가장 최신 것만 처리합니다. getter, flex getter, read 노드는 함수 코드, 유닛 id, 주소, 수량을 기준으로 하므로, 서로 다른 주소를 보내는 flex getter는 서로 다른 주소마다 계속 응답합니다. 나오는 것은 항상 그래왔던 같은 메시지이며, 가장 최신 폴링의 결과입니다.
- **쓰기는 절대 합치지 않습니다.** 모든 쓰기는 순서대로 장치에 도달해야 하므로, 쓰기 노드는 여기에 참여하지 않습니다.
- **새 메트릭이 이를 셉니다.** `hotloop_flow_node_messages_coalesced_total`은 노드별로 더 새로운 메시지에 합쳐진 대기 중 메시지의 수입니다.

## 무엇을 고치는지, 숫자로

응답에 40 ms가 걸리는 장치를 getter 하나가 초당 100번 요청하는 상황을 한 대의 머신에서 6초 동안 측정했습니다.

| <span class="sr-only">세부 정보</span> | 2.16.4 | 2.16.5 |
|---|---|---|
| 수신함에 쌓인 폴링 | 377개, 계속 증가 | 1개 |
| 응답한 폴링 | 123 | 123 |
| 합쳐진 폴링 | 0 | 376 |

## 새 설정

없습니다.

## 업그레이드

2.16.5 이미지와 chart로 평소처럼 `helm upgrade`를 하거나, Quadlet 유닛에 새 태그를 넣으면 됩니다. 처음 시작할 때 일어나는 일은 없고 마이그레이션할 것도 없습니다. 플로 파일은 이전과 바이트 단위로 똑같이 불러오고 저장됩니다. 이번 릴리스는 amd64 이미지를 빌드합니다. `2.16`과 `2` 태그는 2.16.1에서 이미 가진 arm64 이미지를 유지하고, arm64는 2.16.6에서 돌아옵니다. arm64를 쓰신다면 그때까지 2.16.1에 머무르세요.

이미지: `ghcr.io/hotloop-io/hotloop-flow:2.16.5`, linux/amd64. Chart: `https://hotloop.io/hotloop-flow/`. 이 태그의 README에 나머지가 그림과 함께 있습니다: https://github.com/HotLoop-io/hotloop-flow/blob/v2.16.5/README.md
