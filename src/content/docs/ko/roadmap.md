HotLoop이 무엇인지, 무엇을 더 만들어야 하는지, 무엇이 고장 났는지를 정리한 문서입니다. 이 목록에 없으면 하지 않는 일이므로, 필요한 것은 목록에 올려 주세요.

## HotLoop이란

**HotLoop은 현장을 위한 자동화 플랫폼으로, Go로 처음부터 새로 작성했습니다.** 정적 바이너리 하나로 이루어져 있습니다. Python도, 따로 관리할 런타임도, 권한이 높은 컨테이너도, 필요 이상의 capability도 없습니다. 엔티티, 자동화, 헬퍼, 스크립트, 로그북, 대시보드, 알림, MCP, 디스커버리를 지원하는 MQTT가 산업용 계층 위에 올라갑니다. 실제 PLC 프로토콜, 실제 히스토리안, ISA-18.2 알람, OPC UA, Sparkplug B가 그 계층입니다.

모든 줄이 우리 코드입니다. 포함시키거나 브리지하거나 포크한 것이 없으므로, 새벽 3시에 무언가 고장 나도 읽을 코드베이스는 하나이고 남의 버그를 기다릴 일이 없습니다.

HotLoop은 현장을 위한 여덟 가지 제품입니다. 사이트와 함께 성장하는 네 가지(IoT, Edge, Gateway, Edge Relay)에, 로직 연결을 맡는 Flow, 워크플로를 맡는 Cascade, PLC 자체 화면을 위한 HotLoop for CODESYS, PLC 값을 네트워크로 내보내는 Transmitter가 더해집니다. 이 로드맵은 하나의 코드베이스에서 나오는 네 제품인 HotLoop core의 로드맵입니다. [제품](#제품)을 참조하세요. Flow, Cascade, HotLoop for CODESYS, Transmitter는 각자 <a href="/ko/flow/roadmap/">Flow 로드맵</a>, <a href="/ko/cascade/roadmap/">Cascade 로드맵</a>, <a href="/ko/codesys/roadmap/">HotLoop for CODESYS 로드맵</a>, <a href="/ko/transmitter/roadmap/">Transmitter 로드맵</a>을 따로 갖고 있습니다.

## 제품

HotLoop core는 하나의 코드베이스와 하나의 태그를 쓰는 네 제품입니다. 코어 릴리스는 네 제품을 같은 버전으로 동시에 내며, 제품마다 이미지와 Helm 차트가 따로 있습니다. 필요한 드라이버가 우연히 들어 있는 제품이 아니라, 장비에 맞는 제품을 고르시면 됩니다.

| 제품 | 설명 | 데이터베이스 | 현재 상태 |
|---|---|---|---|
| **HotLoop IoT** | 엔티티, 자동화, 헬퍼, 스크립트, 로그북, 대시보드, 알림, MCP, 디스커버리를 지원하는 MQTT, ISA-18.2 알람 엔진, 백업, 모든 드라이버. Edge와 Gateway의 바탕이 되는 제품 | SQLite 또는 Postgres | 분리 완료: 자체 이미지(`hotloop-iot`, amd64, arm64, arm/v7), 차트, Quadlet 유닛을 모든 태그마다 빌드하고 게시합니다. 4.18.10에서 출시 |
| **HotLoop Edge** | IoT에 더해 OPC UA 서버, 상위로의 저장 후 전달, 기계 옆의 로컬 화면 | SQLite, Postgres 또는 TimescaleDB | 분리 완료: 자체 이미지(`hotloop-edge`, amd64, arm64, arm/v7), 차트, Quadlet 유닛을 모든 태그마다 빌드하고 게시합니다. 4.18.10에서 출시(Gateway는 4.5.0부터 엣지에서 실행되며 Sparkplug를 상위로 게시합니다) |
| **HotLoop Gateway** | Edge에 더해 플릿, 멀티 사이트, 예약 보고서. 사이트의 두뇌 | SQLite, Postgres 또는 TimescaleDB | 제공 중 |
| **HotLoop Edge Relay** | 단순하고 튼튼합니다. 폴링하고, 전달하고, 살아남습니다. 데이터베이스도 UI도 없습니다. 화면을 뗀 Edge가 아니라 독립된 제품입니다 | 없음 | 제공 중. 4.16.0부터 모든 릴리스에서 이미지와 차트를 게시합니다 |

**제품을 가르는 것은 기능이지 프로토콜이 아닙니다.** 모든 제품이 우리가 가진 모든 드라이버 위에서 MQTT를 지원합니다. 책상에 중고 S7-1200을 둔 취미 사용자도 IoT 사용자이며, IoT는 업그레이드 없이 그 PLC와 통신합니다.

- [x] 분리 자체를 코드에 반영했습니다. `-tags hotloop_edge`는 Edge, `-tags hotloop_iot`는 IoT이고, 둘을 동시에 지정하면 컴파일되지 않습니다. 해당 제품에 없는 기능의 API 경로는 404로 응답하며 그 기능을 가진 제품을 알려 줍니다. `hotloop --product`와 `GET /api/status`는 지금 어떤 제품과 통신 중인지 알려 줍니다
- [x] 하나의 태그에서 이미지 네 개와 차트 네 개를 병렬로 빌드해 같은 Helm 저장소에 게시합니다. 네 차트 중 하나라도 태그와 맞지 않으면 릴리스가 거부됩니다. Gateway는 `ghcr.io/hotloop-io/hotloop` 이미지와 `hotloop` 차트를 그대로 유지하므로 4.16 사용자가 고장 난 상태로 깨어나는 일은 없습니다
- [x] 데이터베이스는 이미지가 아니라 설정입니다. SQLite, Postgres, TimescaleDB를 실행 시점에 고르며 모두 같은 바이너리에 들어 있습니다. SQLite는 cgo가 없는 순수 Go 버전이라 arm 빌드도 정적으로 유지되고, Pi에 컴파일러 도구 체인이 없어도 됩니다. 전체 테스트 스위트는 세 데이터베이스 모두에 대해 실행됩니다. 테스트하지 않는 데이터베이스는 지원하지 않는 데이터베이스이기 때문입니다
- [x] 사이트를 IoT에서 Edge, Gateway로 옮겨도 모든 장치, 태그, 알람, 사용자, 이력이 그대로 남습니다. 이미지만 바꾸면 끝입니다. 다시 내려가도 지워지는 것은 없고, 없어진 기능이 다시 올라올 때까지 비활성 상태로 남을 뿐입니다
- [x] IoT나 Edge에 있는 Gateway 전용 설정은 경고를 내고 계속 실행되며, 설정 화면에는 그대로 표시되고 저장됩니다. 무엇을 설정했고 왜 아무 일도 하지 않는지 추측하지 않고 정확히 볼 수 있습니다
- [x] IoT는 기본으로 30일치 이력을 보관합니다. Pi의 디스크는 작고, 긴 이력은 Gateway의 몫입니다
- [x] 라이선스 키도, 실행 중 잠금 해제도 없습니다. 유료 등급도 없습니다. 등급은 이미지이고, 업그레이드는 같은 데이터 위에서 이미지를 바꾸는 일입니다
- [x] **모든 장비가 `:stable`을 따르고 스스로 업데이트합니다.** Gateway, Edge, IoT의 Quadlet 유닛은 릴레이의 유닛처럼 `:stable`을 따르며, Podman 자동 업데이트, 셸이 필요 없는 헬스체크, 새 이미지가 올라오지 못할 때의 롤백을 갖추고 있습니다. `release_guard.sh`는 유닛이 고정되어 있거나, 비정상으로 보고될 수 없거나, 데이터베이스를 자동 업데이트하는 릴리스를 거부합니다. 데이터베이스는 차트가 실행하는 태그에 고정되어 있습니다. PostgreSQL 메이저 버전은 덤프와 재적재가 필요하고, 앱의 TimescaleDB 확장 업데이트는 되돌릴 수 없는 일방향 변경이라 앱과 달리 취소할 수 없기 때문입니다. Gateway에서 실제로 실행해 확인했습니다. 마이그레이션이 포함된 업데이트를 데이터가 그대로인 상태로 적용했고, 마이그레이션 후 시작하지 못하는 업데이트는 롤백했습니다. 이 실행 때문에 파드가 없어졌습니다. 앱이 파드 안에 있으면 Podman이 파드의 유닛을 재시작했고, 그 유닛은 멀쩡히 올라왔기 때문에 고장 난 릴리스가 성공으로 보고되고 롤백되지 않았습니다. [Quadlet README](/ko/install/auto-update/)를 참조하세요
- [x] 라이선스의 적용 범위 문구가 정본 라이선스와 모든 사본에서 네 제품을 모두 명시합니다. 예전에는 Gateway만 적혀 있어서 나머지 세 제품은 사실상 사용 허가가 없다고 볼 여지가 있었습니다
- [x] **분리는 MQTT 디스커버리와 함께 4.18.10에 출시되었습니다**(4단계). IoT의 첫 릴리스는 Shelly와 ESPHome 장치를 별도 설정 없이 찾아냅니다

## 자동화 기반

순서대로 진행합니다. 각 단계는 별도로 테스트한 PR로 출시되며, 앞 단계 위에 쌓입니다. 모두 HotLoop IoT에 들어가므로 Edge와 Gateway에도 포함됩니다.

### 1단계: 엔티티

기초입니다. HotLoop의 모든 자동화, 헬퍼, 스크립트, 화면은 엔티티를 기준으로 하므로 가장 먼저 만들었습니다. 4.15.3 이후 PR 1~6으로 병합되었고 4.16.0에서 처음 출시되었습니다. 자세한 내용은 [엔티티](/ko/iot/entities/)와 [장비 트리와 라벨](/ko/iot/equipment/)에 있습니다.

- [x] 엔티티 모델: 타입이 있는 도메인(센서, 바이너리 센서, 스위치, 숫자, 선택, 버튼, 텍스트와 OT용 도메인인 밸브, 모터, PID 루프, 카운터, 알람), 상태, 속성, 변하지 않는 엔티티 ID. 펌프, 팬, 컨베이어, 압축기는 별도 도메인이 아니라 모터의 한 종류입니다
- [x] 복합 장비: 시작, 정지, 리셋, 가동 중, 고장, 속도 태그로 하나의 모터 엔티티를 구성합니다. 모터가 실제로 그런 것이기 때문입니다
- [x] 기존 태그를 엔티티에 매핑하되, 태그, API 호출, MCP 도구, OPC UA 노드, 자동화, 엣지 릴레이 장치 파일 어느 것도 깨뜨리지 않습니다
- [x] `switch.turn_on`, `number.set_value` 같은 서비스는 기존 쓰기 관문을 통해서만 실행되며 다른 경로는 없습니다
- [x] ISA-95 장비 트리 하나(전사, 사이트, 영역, 라인, 셀, 유닛, 장비)와 라벨. 이미 쓰고 있는 사이트 / 영역 / 라인 필드는 계속 동작합니다
- [x] 단위와 장치 클래스
- [x] MCP, 자동화, 실시간 피드의 엔티티와 엔티티 화면 및 공장 화면
- [x] 엔티티 상태 트리거의 `for:` 지속 시간("펌프가 5분 동안 꺼져 있음"). 2단계에서 `state` 트리거의 `forSec`으로 출시되었으며, 진행 중인 대기는 재시작 후 유지되지 않습니다([자동화](/ko/iot/automations/#상태-유지-forsec))

### 2단계: 헬퍼, 스크립트, 씬, 로그북

- [x] 헬퍼: 입력 불리언, 숫자, 선택, 텍스트와 타이머, 카운터, 스케줄. 공장에서는 설정값과 교대 일정에 해당합니다. 재시작 후에도 백업에도 보존되며 타이머는 벽시계 기준입니다. [헬퍼](/ko/iot/helpers/)를 참조하세요
- [x] 스크립트: 자동화, UI, MCP에서 호출할 수 있는 이름 붙은 동작 시퀀스. 타입이 있는 필드, 실행 모드, 실제 관문을 거치는 드라이런, `script:<id>`로 기록되는 모든 쓰기, 로그북과 백업에 포함됩니다. [스크립트](/ko/iot/scripts/)를 참조하세요
- [x] 씬은 **레시피**로 제공됩니다. 설정값 묶음을 캡처해 함께 적용하며 감사 기록이 남습니다. 전체를 검사하고 전체를 거부하며 값을 자르지 않습니다. 하나의 호출 ID로 순서대로 쓰고 롤백하지 않으며, 장치에서 다시 읽어 확인합니다. 버전은 불변이고 UI, 규칙, 스크립트, MCP에서 적용합니다. [레시피](/ko/iot/recipes/)를 참조하세요
- [x] 로그북: 모든 상태 변화, 쓰기, 알람, 자동화 실행을 엔티티별, 영역별로 보여 주는 하나의 타임라인입니다([로그북](/ko/iot/logbook/))
- [x] 블루프린트: 재사용할 수 있는 자동화 템플릿. 범위를 벗어난 입력은 거부하며 값을 자르지 않습니다. 규칙은 누군가 업그레이드를 검토해 수락할 때까지 만들어진 당시의 버전을 유지합니다. 기본 제공 네 가지. [블루프린트](/ko/iot/blueprints/)를 참조하세요
- [x] 자동화 언어: 시퀀스 안의 조건, 대기, 중지 단계와 상태 트리거의 `forSec`("5분 동안 켜져 있음")

### 3단계: 대시보드

"더 낫고 더 멋지다"는 점이 방 건너편에서도 보여야 하는 단계입니다.

- [x] 대시보드 빌더: 카드, 드래그 앤 드롭, 원하는 만큼의 대시보드. 저장할 때 시작한 버전을 기록하므로 두 사람이 같은 페이지를 만들어도 모르는 사이에 덮어쓰는 일이 없습니다. [대시보드](/ko/iot/dashboards/)를 참조하세요
- [x] 화면 파일: 대시보드를 버전이 있는 파일로 저장해 다른 설치로 가져옵니다. 고객의 화면은 고객의 것이며 제품의 일부가 되지 않습니다. 없는 태그나 장치는 저장하기 전에 모두 나열하고 매핑합니다. [화면 파일](/ko/iot/screen-file/)을 참조하세요
- [x] 카드 세트: 게이지, 숫자, 트렌드, 엔티티 목록, 확인이 있는 쓰기 버튼, 스크립트 버튼, 알람 목록, 마크다운, 카메라, 실시간 태그가 있는 평면도, 레시피 선택기, 공장 상태 막대. 카드는 스스로 아무것도 명령하지 않으며, 버튼은 쓰기 관문을 통해 씁니다
- [x] 역할별, 화면별 대시보드. 벽걸이 보드도 그중 하나이며 같은 전환기와 같은 할당을 씁니다
- [x] 패널 PC, 노트북, 휴대폰에서 같게 보입니다. 12열에서 1열로 접히는 하나의 레이아웃을 다섯 가지 너비로 테스트했습니다
- [x] 웹 UI는 영어와 13개 언어를 지원합니다. 스페인어, 프랑스어, 이탈리아어, 독일어, 노르웨이어, 불가리아어, 그리스어, 한국어, 일본어, 베트남어, 힌디어, 중국어 간체, 아랍어(오른쪽에서 왼쪽)이며, 상단 바에서 선택하고 브라우저가 기억합니다. [언어](/ko/iot/languages/)를 참조하세요

### 4단계: 통합과 디스커버리

- [x] 통합 프레임워크: 통합은 장치와 엔티티를 추가하고, 설정 흐름이 있으며, 실제 장치를 대상으로 테스트합니다
- [x] **MQTT 디스커버리**: Zigbee2MQTT와 ESPHome은 게시하는 형식으로, Tasmota는 자체 형식으로, Shelly Gen2 이후는 게시하는 상태 정보로 찾습니다. 장치는 내장 브로커든 다른 브로커든 읽기 상태로 나타나며, 사람이 장치를 수락하고 각 포인트를 활성화하기 전에는 아무것도 활성화되지 않습니다. Edge Relay도 디스커버리를 지원하며 읽기와 전달만 합니다. Frigate는 포함되지 않습니다. MQTT 페이지에 디스커버리 메시지가 문서화되어 있지 않기 때문입니다. 모든 것은 실제 장치의 녹화본으로 검증했고, Tasmota와 Shelly는 제조사 문서로도 검증했으며 작업대의 실제 장치로 검증한 것은 아닙니다. [MQTT 디스커버리](/ko/iot/mqtt-discovery/)와 [Edge Relay 레퍼런스](/ko/edge-relay/reference/#디스커버리-41810)를 참조하세요. 네 제품으로의 분리는 이 기능을 기다렸습니다
- [x] 네트워크 디스커버리(mDNS, SSDP, DHCP): 공장 네트워크에서 들린 장치가 발견 화면에 무엇인지, HotLoop이 어떻게 통신할 수 있는지와 함께 나타나며, 사람이 하나씩 수락하거나 무시합니다. OPC UA 서버는 OPC UA 장치가 되고, Shelly는 HTTP 장치가 되며, ESPHome 노드는 MQTT로 안내합니다. 저절로 추가되거나 활성화되는 것은 없습니다. 기본은 수신 전용이며 탐색은 배포에서 네트워크별로 켭니다. DHCP는 호스트 네트워킹과 67번 포트가 필요하므로 배포가 둘 다 제공하기 전에는 꺼져 있습니다. 실제 avahi, MiniDLNA, udhcpc로 테스트했고 작업대의 실제 장치로는 아직 테스트하지 않았습니다. [네트워크 디스커버리](/ko/iot/network-discovery/)를 참조하세요
- [x] CODESYS: 프로그래머가 붙인 이름 그대로 PLC 변수를 런타임 자체의 OPC UA 서버를 통해 다룹니다. 애플리케이션이 내보내는 항목 디스커버리, 읽기와 쓰기, 설정에서 만드는 첫 대시보드, 재시작이나 다운로드 후의 무인 재연결을 지원합니다. HotLoop의 랩 프로그램과 훨씬 큰 두 번째 프로그램을 실행하는 컨테이너의 4.22.0.0 런타임, 그리고 베어메탈(2026-11-17)에서 검증했습니다. [CODESYS](/ko/iot/protocols/#codesys)를 참조하세요
- [x] BACnet/IP와 SNMP, 읽기 전용. [프로토콜과 드라이버](/ko/iot/protocols/)를 참조하세요
- [x] ONVIF 카메라: 탐색(WS-Discovery), 장치 정보, 모든 미디어 프로필의 스트림과 스냅샷 주소(Media와 Media2), PTZ 위치와 명령, 카메라 자체의 이벤트를 태그와 로그북 줄로 제공합니다. ONVIF 자체 WSDL 파일에서 생성한 ONVIF 스택인 onvif_srvd를 상대로 실행했고, 모든 요청을 ONVIF 스키마에 맞춰 검증했습니다. 실물 카메라를 시험대에 올린 적은 없습니다. ONVIF.md와 [프로토콜과 드라이버](/ko/iot/protocols/#onvif)를 참조하십시오
- [x] Shelly 네이티브: Gen2 이상은 RPC와 실시간 웹소켓(변경과 버튼 입력이 발생하는 즉시 도착), Gen1은 자체 HTTP 인터페이스로 지원합니다. 실제 장치의 녹화 기록에 맞춰 검증했습니다. 실물 Shelly를 시험대에 올린 적은 없습니다. SHELLY.md와 [프로토콜과 드라이버](/ko/iot/protocols/#shelly)를 참조하십시오
- [x] **Firmata**, USB 시리얼 또는 TCP로 연결하는 Arduino용: 디지털과 아날로그 I/O, PWM, 서보, I2C. 시뮬레이션한 Uno에서 Arduino 프로젝트 자체의 StandardFirmata를 상대로 실행했습니다(응답하는 것은 우리 프로그램이 아니라 펌웨어입니다). 실물 보드를 시험대에 올린 적은 없습니다. FIRMATA.md와 [프로토콜과 드라이버](/ko/iot/protocols/#firmata)를 참조하십시오
- [ ] UniFi, [UniFi](#unifi)를 참조하세요
- [x] 야외 장비를 위한 태양: `binary_sensor.sun_up`, 태양 고도와 방위각, 새벽, 일출, 정오, 일몰, 황혼에 오프셋을 줄 수 있는 `sun` 트리거. 사이트의 위도와 경도에서 NOAA 방정식으로 장비 안에서 계산하며 외부 서비스가 필요 없고, NOAA가 2026년에 공개한 유타키아그빅부터 키토까지 여섯 곳의 모든 일출, 일몰, 정오 값과 대조했습니다. [태양](/ko/iot/sun/)을 참조하세요
- [x] 날씨. 클라우드 날씨 API가 아닙니다. HotLoop은 비가 오는지 알아보려고 누구에게도 전화하지 않습니다. `weather` 엔티티는 공장 자체 지붕 위의 관측소이며 태그를 역할(온도, 습도, 기압, 바람, 비, 일사)에 연결하고, 이슬점, 열지수, 체감온도는 장비 안에서 계산해 NWS 표와 대조합니다. 읽을 수 없는 센서는 0이 아니라 사용 불가입니다. 카드 하나, 14개 언어, 에이전트가 MCP로 만들고 읽습니다. [날씨](/ko/iot/weather/)를 참조하세요

## 알림

웹훅, 이메일, ntfy, Gotify, Discord 웹훅, Discord 봇이 있으며 모두 같은 기반 위에서 동작합니다. [알람 알림](/ko/iot/notifications/)을 참조하세요.

- [x] **기반 먼저:** 채널별 속도 제한, 병합("지난 1분간 알람 7건 추가"를 메시지 하나로), `Retry-After`를 지키는 제한된 재시도
- [x] **서명된 확인 링크:** 휴대폰에서 한 확인은 실제 ISA-18.2 확인으로 기록되며, 오래된 버튼으로 같은 알람이 다시 울릴 때 확인할 수 없습니다. ntfy는 누가 눌렀는지 알려 주지 않으므로 기록되는 이름은 채널의 이름(`notify:ntfy`)이고, Discord 봇은 누른 사람의 이름을 기록합니다

채널은 네 가지입니다. 이것이 전부입니다.

- [x] **ntfy를 먼저.** 무료이고 직접 호스팅하며 인터넷이 없는 공장 네트워크에서도 동작합니다(Android 기준이며 iPhone은 서버가 ntfy.sh를 통해 중계해야 합니다). 동작 버튼은 공장 네트워크를 통해 알람 확인을 HotLoop으로 곧바로 돌려보냅니다.
- [x] **Gotify.** 무료이고 직접 호스팅하며 인터넷 없이 동작합니다. 확인 버튼도 iPhone 앱도 없으므로 양방향이 아니라 호출기입니다.
- [x] **Discord 웹훅.** URL을 붙여 넣으면 끝입니다. `allowed_mentions`를 잠가 두어 알람 이름이 @everyone을 멘션할 수 없고, 심각한 알람은 역할을 호출할 수 있습니다. Discord가 거부하는 웹훅은 IP 차단을 당할 때까지 재시도하지 않고 꺼집니다.
- [x] **Discord 봇.** 채널 안에서 바로 확인과 보류 버튼을 쓰며, Discord 역할로 제한하고(지정하기 전에는 아무도 못 씁니다) 누른 사람의 이름으로 기록합니다. 아웃바운드 연결(Gateway)로 Discord와 통신하므로 공장에 공인 주소가 필요 없습니다.
- [x] 에스컬레이션: N분 안에 아무도 확인하지 않으면 다음 사람이나 다음 채널을 호출합니다
- 하지 않는 것: SMS와 Google Messages(RCS는 회사별, 국가별 통신사 승인이 필요하고 직접 호스팅하는 장비는 받을 수 없습니다), Slack, Teams, Google Chat, Pushover, PagerDuty, Telegram, Opsgenie, Signal, Matrix

## UniFi

공장의 네트워크도 장비입니다. PLC가 조용해지면 첫 질문은 "PLC 문제인가, 스위치 문제인가"이고, 지금은 UniFi 앱까지 걸어가서 답을 찾습니다. 그래서 UniFi는 별도 시스템이 아니라 **프로토콜 드라이버**로 들어옵니다. 모든 스위치, 포트, PoE 예산, WAN이 태그입니다. 덕분에 한 벤더를 위해 각 기능의 절반을 다시 만들 필요 없이 쓰기 관문, 감사, 드라이런, 알람, 트렌드, 엔티티, 자동화, OPC UA, MCP를 그대로 쓸 수 있습니다.

IoT 기반에 들어가므로 네 제품 모두가 쓸 수 있고, Edge Relay도 다른 장치처럼 콘솔을 폴링할 수 있습니다.

### 네트워크

순서대로 진행합니다. U5 이전에는 컨트롤러에 쓰는 것이 아무것도 없습니다.

- [x] **U1: 읽기 전용 드라이버.** 콘솔당 하나의 세션을 모든 작업에 재사용하며 로그인 횟수 예산이 있습니다. 점검할 때마다 로그인했더니 우리 Cloud Gateway가 429로 응답하며 두 번 잠겼기 때문에, HotLoop은 한 번만 로그인하고 잠금을 연장하지 않고 풀릴 때까지 기다립니다. 콘솔의 인증서는 처음 사용할 때 고정되며 무조건 통과시키지 않습니다. 장치, 스위치 포트, PoE 소비, WAN, 페일오버가 저절로 동기화되는 태그로 들어옵니다. 내일 추가된 스위치는 알아서 나타나고, 사라진 스위치는 알람 밑에서 증발하지 않고 품질 불량으로 바뀝니다. 첫 실제 읽기에서는 이틀 동안 죽어 있던 5G 백업을 살아 있다고 보고했는데, 콘솔 요약과 마찬가지로 WAN 블록의 오래된 `up`을 믿었기 때문입니다. 헬스체크는 알고 있었으므로 드라이버는 이제 그것을 읽고, 테스트가 이를 고정합니다. 완료. [UniFi Network](/ko/iot/unifi/)를 참조하세요
- [ ] **U2: 클라이언트와 OT 감시.** 컨트롤러의 클라이언트 표에는 기계가 몇 시간 전에 떠난 주소가 남아 있으므로 IP가 아니라 MAC으로 클라이언트를 구분합니다. 네트워크를 OT로 표시하고 거기 있는 것을 수락하면, 새로 나타나는 것은 모두 알람을 냅니다. HotLoop 장치를 스위치 포트에 한 번 연결해 두면, 조용해진 PLC가 어느 포트에 있고 그 링크가 살아 있는지 알려 줍니다. 랙 앞에 사람이 필요한 두 단계, 즉 실제 케이블 뽑기와 휴대폰이 SCADA에 연결되는 것을 확인한 뒤에 체크합니다. [UniFi Network](/ko/iot/unifi/)를 참조하세요
- [x] **U3: 화면과 토폴로지 맵.** WAN 띠(사이트가 5G 백업으로 동작하면 주황색이 됩니다)가 있는 개요, 벽걸이 보드에서 흔들리지 않도록 매번 같은 방식으로 배치하는 토폴로지 맵, 스위치 전면, 클라이언트, 네트워크, WiFi. 두 콘솔을 하나의 그림으로 이어 붙였습니다. 스위치를 클릭하면 공장 트리의 어느 라인에 전원을 공급하는지 보입니다. 케이블은 콘솔 자체의 다운링크 표에서 가져오므로, 어디에도 연결되어 있다고 나오지 않는 스위치는 추측으로 게이트웨이에 매달지 않고 독립적으로 놓입니다. 실제 장비에서는 아직 확인하지 않았습니다. 맵은 핀치, 드래그, 최대 8배 확대를 지원하고, 연결된 HotLoop 장치를 라인 아래로 묶는 공장 오버레이가 있으며, 각 WAN 옆에 지연 시간이 표시되고 포트의 입출력이 추적되며, 관리자는 자주 쓰는 알람(장치 오프라인, 업링크 다운, 게이트웨이가 백업 상태, 지정한 한도를 넘는 PoE)을 한 번에 만들 수 있습니다. 이것들은 2026-10-19에 화면이 아니라 에뮬레이션한 터치로 검증했으며, WAN 처리량 추적은 아직 없습니다. 실제 게이트웨이에서 이를 위한 콘솔 필드를 읽은 적이 없기 때문입니다. [UniFi Network](/ko/iot/unifi/#화면)를 참조하세요
- [x] **U4: 이벤트.** 컨트롤러의 이벤트 웹소켓으로 스위치가 떨어지면 다음 폴링이 아니라 몇 초 안에 나타나고 로그북에 기록됩니다. 폴링이 기준이며, 죽은 웹소켓은 속도를 잃을 뿐 정확성을 잃지 않습니다. 끊어진 웹소켓과 조용한 웹소켓은 로그인 없이 다시 연결됩니다. 이벤트는 해당하는 스위치나 AP 아래의 로그북에 기록되고, 장비 필터가 연결된 장치에서 그 장치에 전원을 공급하는 스위치를 거쳐 찾아 줍니다. 에이전트 도구 `get_network_topology`와 `get_network_events`가 맵과 이벤트를 읽습니다. [UniFi Network](/ko/iot/unifi/#이벤트)를 참조하세요
- [ ] **U5: 관문을 통한 쓰기.** 먼저 위치 표시 LED: 위험이 전혀 없고 방 반대편에서도 보이며, 실제 장비에서 쓰기 경로 전체를 증명합니다. 그다음 PoE 모드, 포트 전원 사이클, WLAN 켜기와 끄기, 클라이언트 차단, 그리고 그 형태가 실제 컨트롤러와 빈 포트 하나에서 증명된 뒤 알 수 없는 장치의 포트 비활성화를 합니다. 전원 사이클은 포트당 15분 쿨다운이 있습니다. PLC를 2분마다 사이클하는 자동화가 전원 공급 장치를 태우는 방법이기 때문입니다. 보호 포트는 토폴로지에서 나옵니다. HotLoop은 누가 요청하든 업링크나 5G 백업에 전원을 공급하는 포트를 사이클하지 않습니다. 장치 재시작은 단순한 버튼입니다. 누르면 장치가 재시작되고, 확인 절차는 없으며, 감사는 그대로 남습니다. 구축하고 테스트에서 증명한 것: 위치 표시, 재시작, 전원 사이클, PoE 모드, WLAN 켜기와 끄기, 클라이언트 차단. 포트 비활성화는 대기 중입니다. Network 10.6은 포트를 끄는 포트 설정을 저장하지 않습니다. [UniFi Network](/ko/iot/unifi/#명령)를 참조하십시오
- [ ] **U6: 자가 복구.** 기본 제공 블루프린트: 장치가 N분 동안 조용하면 포트의 전원을 한 번 껐다 켠 다음 알람을 냅니다. 영원히가 아니라 한 번만 합니다. 구축 완료: `device_silent_cycle_its_port` 블루프린트이며, 15분 쿨다운과 보호 포트가 있는 포트 전원 사이클 위에 만들어졌습니다. [블루프린트](/ko/iot/blueprints/)를 참조하십시오. 실제 스위치의 실제 PoE 장치 포트를 사이클해 보기 전까지는 체크하지 않은 채로 둡니다

[프로토콜과 드라이버](/ko/iot/protocols/#unifi-protect)를 참조하십시오
- [x] **Access.** 문 위치, 로그북의 문 이벤트, 게이트를 통한 쓰기로서의 잠금 해제. MCP의 잠금 해제는 다른 쓰기와 마찬가지로 쓰기 게이트를 통해 허용되며 다른 쓰기와 마찬가지로 감사됩니다. 유지 관리되는 오픈 클라이언트가 기록한 내용에 맞춰 구축했습니다. `unifi-access` 장치, 각 문의 위치와 잠금을 태그로, 로그북의 문 이벤트, 쓰기로서의 잠금 해제입니다. [프로토콜과 드라이버](/ko/iot/protocols/#unifi-access)를 참조하십시오
- [x] **SmartPower PDU.** 콘센트 전력, 켜기, 끄기, 사이클을 태그로 제공하며 5단계 에너지 작업에 쓰입니다. 콘솔 자체의 콘센트 API에 맞춰 구축했습니다. 콘센트의 켜기, 전력, 전류, 전압, 사이클이 UniFi Network 장치의 태그가 됩니다. [UniFi Network](/ko/iot/unifi/#smartpower-pdu-콘센트)를 참조하십시오

## HotLoop Edge Relay

- [x] **이미지를 실제로 릴리스합니다.** 릴리스는 Gateway만 빌드했습니다. 이제 릴리스는 `ghcr.io/hotloop-io/hotloop-edge-relay`(amd64와 arm64)도 푸시하고 같은 Helm 저장소에 `hotloop-edge-relay`를 게시하며, 릴레이 차트가 태그와 맞지 않으면 그 태그를 거부합니다. 첫 실제 푸시는 다음 태그에서 이루어집니다
- [x] **플릿 관리를 통한 원격 업데이트.** "원격"이 솔직히 무엇을 뜻할 수 있는지는 설치마다 달라서, 설치마다 다르게 제공합니다. Quadlet 릴레이는 `:stable`을 따르며 Podman 자동 업데이트가 각 릴리스로 재시작하고, 새 이미지가 올라오지 못하면 Podman이 이전 이미지를 되돌려 놓는 헬스체크가 있습니다. 사이트는 관리자가 Gateway에서 승인할 때까지 업데이트를 보류하도록 선택할 수 있습니다. Helm 릴레이는 `helm upgrade`로 업데이트하며 문서에도 그렇게 분명히 적혀 있습니다. 모든 릴레이가 버전과 이미지 다이제스트를 보고하고, 플릿 목록에 표시되며, 모든 변경이 시스템 로그에 기록됩니다. 실제 레지스트리를 상대로 한 실제 Podman 자동 업데이트 실행으로 검증했습니다. 업데이트, 시작하지 못해 롤백된 릴리스, 보류했다가 승인한 업데이트입니다. 일부러 만들지 않은 것: 서명되거나 다이제스트로 고정한 이미지(Gateway는 닿지 않는 장비에서 이를 강제할 수 없으며, 서명은 Podman의 pull 정책에 두는 것이 맞습니다)와 단계적 롤아웃(롤백이 나쁜 릴리스의 피해를 제한하고, 사이트를 보류하면 순서를 정할 수 있습니다). [Edge Relay 레퍼런스](/ko/edge-relay/reference/#relay-업데이트)를 참조하세요
- [x] **실시간 구성 다시 불러오기.** 푸시된 장치 파일은 누군가 릴레이를 재시작하기 전까지 디스크에 놓여 있었고, 태그 하나를 바꾸려면 브로커 세션과 모든 장치 세션을 끊어야 했습니다. 이제 파일이 도착하는 순간 적용됩니다. 새 장치는 연결하고, 제거된 장치는 놓아 주고, 바뀐 장치는 다시 연결하며, 나머지는 세션을 유지합니다. Sparkplug 세션과 전달 큐는 유지되고, 노드는 새 메트릭 집합으로 다시 birth를 보내며, 제거된 메트릭은 먼저 null로 내보내 어떤 호스트도 마지막 정상 값에 머물지 않게 합니다. 잘못된 파일은 거부되고 이전 파일이 계속 실행되며, `/status`가 실행 중인 파일과 거부된 파일을 알려 줍니다.

## 리뷰에서 수정한 항목

코드 리뷰에서 발견해 `main`에서 수정했습니다. 각 버전의 릴리스 노트에 운영 중인 사이트에 무엇이 달라졌는지 적혀 있습니다.

- [x] **복원이 이전 스키마의 백업을 불러오지 못했고, 백업의 `hotloopVersion`을 아예 확인하지 않았습니다.** 이제 매니페스트에 모든 테이블의 열과 적용된 스키마 마이그레이션이 기록됩니다. 복원은 각 파일을 이름으로 그 열에 불러오고, 더 새로운 열은 기본값을 쓰게 하며, 더 새로운 테이블은 앱이 채우도록 두고, 더 새로운 스키마의 백업이나 이 버전이 삭제, 이름 변경, 타입 변경한 열이 있는 백업은 한 행도 불러오기 전에 거부합니다. 그 이전 백업은 여전히 위치 기준으로 복원됩니다. 지금까지 존재한 모든 스키마 단계에서 테스트했습니다. 수정 완료. - [x] **레코더의 "데이터 없음" 코드가 정상 측정값으로 읽혔습니다.** 스케일 0.1인 `input:1:int16`에서 0x8005(미정의)를 돌려주는 Yokogawa DX 채널이 정상, -3276.3으로 들어와 온도로 기록되었습니다. 이제 태그가 "측정 없음"을 뜻하는 원시 값을 이유와 함께 나열합니다. 하나는 스케일과 오프셋보다 먼저 검사되어 이유와 함께 불량으로 읽히며 값 알람을 울리지 않습니다. Modbus는 레지스터의 비트 패턴(모든 정수 너비, 바이트와 워드 순서, 16진수 부동소수점 패턴)을 검사하고, 숫자를 디코딩하는 다른 모든 드라이버도 같은 목록을 검사합니다. 우리 것이 아닌 Modbus 서버로 DX 코드 여덟 개 모두를 검증했습니다. 수정 완료. [프로토콜과 드라이버](/ko/iot/protocols/#데이터-없음-값)를 참조하세요
- [x] 소켓은 열린 채 조용해진 Modbus 장치(케이블이 뽑히거나 PLC가 멈춘 경우)가 다운이 아니라 저하로 표시되었고, TCP가 포기할 때까지 엔티티가 마지막 값에 머물렀습니다. 이제 폴링 한 번에 타임아웃의 두 배를 더한 시간 안에 다운으로 표시됩니다. 수정 완료
- [x] S7comm과 EtherNet/IP도 폴링이 시간 초과될 때 같은 조기 반환이 있어서, 소켓이 열린 채 조용해진 PLC가 다운이 아니라 저하 상태로 남았습니다. 이제 둘 다 Modbus처럼 읽기를 멈추고 세션을 판단합니다. 마감까지 막히는 읽기를 넣어 폴링 루프를 통해 검증했습니다(이전 반환에서는 실패하고 수정 후에는 통과하며, 일부 블록에 응답하는 PLC는 계속 살아 있습니다). 네트워크 선로 위에서가 아닙니다. 수정 완료
- [x] 위의 S7comm과 EtherNet/IP 무응답 장치 테스트는 소켓이 아니라 폴링 루프를 구동했습니다. 이제 소켓에서 실행됩니다. 테스트가 프로세스 안에 S7 서버(ISO-on-TCP 연결, 통신 설정, 변수 읽기)와 CIP 서버(RegisterSession, forward open, 연결된 읽기, 다중 서비스 읽기)를 띄우고, 각각 표에서 응답하다가 명령에 따라 조용해지며, 드라이버가 TCP로 폴링합니다. 조용한 PLC는 폴링 한 번에 타임아웃의 두 배를 더한 시간 안에 다운이 되고, 일부 블록에 응답하는 PLC는 계속 살아 있으며, 앞선 수정을 되돌리면 테스트가 실패합니다. 수정 완료
- [x] **배치에 태그가 둘 이상인 EtherNet/IP 장치가 폴링에서 패닉을 일으켰습니다.** 드라이버가 라이브러리의 `ReadMulti`로 배치를 읽었는데, 이것은 태그가 달린 필드의 구조체나 맵을 받으며 태그 이름을 주면 아무것도 보내기 전에 reflect에서 패닉합니다. 서버를 상대로 배치를 실행하는 테스트가 없어서 드러나지 않았습니다. 이제 배치는 `ReadList`를 거치며, 응답하지 않는 컨트롤러에는 태그마다 다시 묻지 않으므로 태그당 타임아웃만큼 폴링이 붙잡히던 일이 없어졌습니다. 수정 완료
- [x] **태그 화면에서 연 페이지의 Pin이 실제 보드를 태그 하나짜리 보드로 덮어썼습니다.** 페이지가 보드 화면을 열 때만 보드를 읽었기 때문에 `#tags`에서 새로 고치면 목록이 비어 있었고, 첫 Pin이 공장의 보드를 그 태그 하나로 바꿔 버렸습니다. 이제 페이지가 시작할 때 보드를 읽고, 읽기 전에는 Pin과 Unpin이 거부되며, 저장에는 보드의 `rev`가 들어갑니다. 서버는 읽은 뒤에 바뀐 보드 위의 저장을 거부하므로(`409`) 오래된 탭도 그렇게 할 수 없습니다. 수정 완료. [HTTP API](/ko/iot/api/#get-apiboard)를 참조하세요
- [x] **MCP가 쓰기가 꺼진 채 출시되었습니다.** 서버는 켜져 있었지만 `allowMcpWrites`가 코드와 세 차트 모두에서 기본 false여서 에이전트는 공장을 읽을 수만 있었고, 켜려면 주 스위치가 이미 포괄하는 두 번째 스위치까지 설정해야 했습니다. 이제 MCP는 모든 HotLoop 제품에서 읽고 씁니다. 코어와 Flow는 쓰기가 켜진 채 출시되며, Cascade도 만들어지면 그렇게 됩니다. `allowMcpWrites`는 기본 true이며 UI, API, 에이전트 모두의 주 스위치로 남는(기본은 꺼짐) `allowWrites`를 따릅니다. 사용자의 권한, 태그의 쓰기 가능 표시와 범위는 화면에 적용되듯 에이전트에도 적용됩니다. 문서는 더 이상 읽기 전용 에이전트를 실행하라고 안내하지 않습니다. 수정 완료. [MCP](/ko/iot/mcp/#쓰기)를 참조하세요
- [x] **MCP는 바꿀 수 없는 것을 대부분 읽을 수 있었습니다.** 27개 도구가 장비를 명령하고 스크립트를 실행하고 레시피를 적용했지만, 블루프린트는 미리 볼 수만 있고 규칙으로 만들 수 없었고, 알람은 확인할 수 있어도 보류할 수 없었으며, 장치, 태그, 헬퍼, 규칙, 스크립트, 레시피, 대시보드, UniFi 네트워크는 만들거나 바꿀 수 없었습니다. 이제 64개 도구가 그렇게 하고, 42개 도구가 더해져 관리자 자체 기능(사용자, 설정, 백업, 에스컬레이션, 히스토리안 대상, 브로커 로그인, 플릿, 보고서)에 닿습니다. 각각은 해당 경로가 요구하는 권한과 사유를 갖고 자체 핸들러를 거쳐 실행되는 API 경로 하나이며, 에이전트가 로그에 남습니다. 쓰기 스위치는 배포의 것이며 경로가 없으므로, 설정 경로는 화면에 대해서처럼 에이전트에 대해서도 이를 거부합니다. 수정 완료. [MCP](/ko/iot/mcp/#구성-변경)를 참조하세요
- [x] **MCP는 CODESYS 알람 내보내기를 가져올 수 없었고, 바꾼 것의 대부분을 다시 읽을 수 없었으며, 저장 전에 본문을 확인할 수 없었습니다.** 알람 화면은 CODESYS Export Alarms 파일을 가져오는데, 에이전트에서 하는 유일한 방법은 curl이었습니다. `import_codesys_alarms`는 같은 경로로 미리 보고 적용하며 적용할 때 사유를 남깁니다. 이제 24개의 읽기 도구가 해당하는 쓰기 옆에 있고(알람 정의, 대시보드, 보드, 장비 트리, 라벨, 발견된 장치, 네트워크 발견, 브로커, 통합, 블루프린트, 스크립트, 실행, UniFi 콘솔과 네트워크), `validate_automation`, `validate_script`, `browse_device`는 편집기의 드라이런입니다. 쓰기 역할이 없는 호출자는 일반 읽기만 할 수 있습니다. 총 163개 도구입니다. `screen_export`와 `screen_import`는 화면을 설치 사이에 옮기며, 가져오기는 달리 지시하지 않으면 드라이런입니다. 수정 완료. [MCP](/ko/iot/mcp/#읽기와-드라이런)를 참조하세요
- [x] `HOTLOOP_MCP_TOKEN`이 설정되지 않았을 때(모든 차트는 설정하지만 순수 바이너리나 Quadlet 유닛은 그렇지 않았습니다) MCP 엔드포인트가 포트에 닿는 누구에게나 열려 있었고, 프로세스는 로그에만 그렇게 말했습니다. 이제 처음 시작할 때 토큰을 만들어 데이터베이스에 보관하고, `hotloop mcp-token`이 이를 출력하며, 토큰 없는 호출은 `401`입니다. 빌드한 바이너리로 검증했습니다. 토큰 없음 401, 틀린 토큰 401, 올바른 토큰 200, 재시작 후에도 같은 결과. 수정 완료. [MCP](/ko/iot/mcp/)를 참조하세요
- [x] **8포트 스위치의 전면 그림이 휴대폰에서 페이지 전체를 약 115px 넓혔습니다.** 각 열이 54px을 요구해서 여덟 개가 화면보다 넓어졌고, 상단 바와 모든 카드가 함께 옆으로 밀렸습니다. 이제 포트는 34px의 촘촘한 타일이며, PoE 와트는 타일에서 포트 상세와 툴팁으로 옮겼고(번개 표시가 타일의 PoE를 나타냅니다), 전면이 카드보다 커지면 카드 안에서 스크롤됩니다. 브라우저 테스트가 페이지 자체의 전면 코드에 390px에서 포트 여덟 개를 주었습니다. 수정 전에는 113px 넓었고, 수정 후에는 페이지가 창 너비와 정확히 같습니다. 수정 완료

- [x] **디스크 부족으로 브로커가 쓰기를 거부하는 Kafka나 Redpanda 대상이 "records have timed out"이라고만 했습니다.** 타임아웃 후에 대상은 레코드가 없는 produce로 브로커에게 이유를 한 번 묻고 그 답을 알려 줍니다(Redpanda가 여유 공간 임계값 미만: `KAFKA_STORAGE_ERROR`, 브로커 밑의 디스크). 측정값은 결코 사라지지 않았고, 브로커가 다시 쓰기를 받으면 전송됩니다. 임계값을 디스크보다 높게 설정한 Redpanda, 그리고 정상적인 Redpanda와 Apache Kafka(아무 말도 하지 않아야 함)로 검증했습니다. 수정 완료

## 마지막: 현대적인 UI

이 항목은 일부러 이 페이지의 맨 뒤에 둡니다. 새 프런트엔드는 만들기에 가장 재미있고, 공장이 아직 필요한 일을 못 하는 동안 분기 하나를 쓰기에 가장 쉬운 방법입니다. 그래서 기다리며, 위의 어떤 항목도 이 때문에 늦춰지지 않습니다.

- [x] **HotLoop IoT, Edge, Gateway의 웹 UI를 Astro로 다시 작성합니다.** HotLoop 웹사이트를 만든 것과 같은 프레임워크입니다. 지금의 UI와 똑같이 하나의 Go 바이너리에 포함되는 정적 에셋으로 빌드되므로, 모든 제품은 옆에 설치할 것이 없는 하나의 이미지로 계속 출시됩니다. 장비에 Node도, 두 번째 프로세스도, CDN도 없습니다. 목표는 모든 HotLoop 프로젝트에서 시대별 화면이 아니라 하나의 모습과 하나의 부품 세트로 이루어진 현대적인 UI입니다
- [x] **디자인 작업이 먼저입니다.** 컴포넌트를 하나라도 쓰기 전에 화면, 내비게이션, 새벽 3시에 휴대폰에서 보이는 알람의 모습, 사이트와 모든 제품이 공유하는 하나의 디자인 시스템을 정합니다. 이것 없이 화면을 다시 쓰면 혼란을 더 새로운 프레임워크로 옮길 뿐입니다
- [x] **아무것도 퇴보하지 않습니다.** 오늘 브라우저 테스트가 구동하는 모든 화면은 계속 동작하고 계속 구동되며, API는 UI를 위해 바뀌지 않습니다. 현장에서 누군가 쓰는 화면을 잃는 재작성은 끝난 것이 아닙니다
