늘어나는 워크플로를 공장이 어떻게 관리하는지 다룹니다. 공용 설정, 폴더, 주석을 단 실행, 마스킹, 시간에 따른 수치, 외부 시크릿, 로그 스트리밍, 대용량 데이터의 위치를 설명합니다. 여기 있는 모든 기능은 무료이며 모든 빌드에 들어 있습니다.

아래에 나오는 모든 엔드포인트는 `/api/v1/openapi.json`의 OpenAPI 문서에 있으며, 각각을 호출하는 테스트가 SQLite와 Postgres 모두에서 있습니다.

## 변수

편집기 상단 막대의 변수에서 다룹니다. 인스턴스 전체 변수는 맨 위에, 각 프로젝트의 변수는 프로젝트 이름 아래에 있습니다. 역할이 허용하는 것만 표시됩니다.

변수는 워크플로가 `vars.NAME`으로 읽는 이름 있는 값입니다. 설정값 상한, 공장 이름, 시험 라인과 실제 라인에서 다른 기본 URL 같은 것입니다.

```yaml
- name: Check limit
  type: core.if
  version: 1
  params:
    condition: "{{ item.json.temp > toNumber(vars.TEMP_LIMIT) }}"
```

- 변수는 **인스턴스 전체**에 적용되거나 **한 프로젝트**에 속합니다. 둘 다 같은 이름이 있으면 프로젝트의 것이 이기며, 그 프로젝트의 워크플로에만 적용됩니다.
- 값은 최대 8 KiB의 텍스트입니다. 숫자가 필요하면 `toNumber(vars.X)`를 쓰세요.
- 이름은 문자, 숫자, 밑줄로 이루어지고, 문자나 밑줄로 시작하며, 최대 64자입니다. `vars.NAME`으로 읽혀야 하기 때문입니다.
- **변수는 시크릿이 아닙니다.** 프로젝트를 읽을 수 있는 사람은 누구나 그 변수를 읽으며, 값은 실행 데이터에서 지워지지 않습니다. 비밀번호, 토큰, 키는 자격 증명 보관소나 외부 시크릿 저장소(아래)에 넣으세요.
- 실행은 시작할 때 변수를 읽고, 대기나 재시작 뒤에 재개될 때 다시 읽습니다. 변경은 다음 실행에 반영되며, 이미 한 단계 중간에 있는 실행에는 반영되지 않습니다. 없는 이름은 오류가 아니라 빈 값으로 읽힙니다.

| 호출 | 하는 일 |
|---|---|
| `GET /api/v1/variables` | 인스턴스 변수와 읽을 수 있는 프로젝트의 변수. `?project=`로 한 프로젝트로 좁힙니다. |
| `POST /api/v1/variables` | 변수를 만듭니다. `projectId`가 있으면 프로젝트 변수, 없으면 인스턴스 전체 변수입니다. |
| `PUT /api/v1/variables/{variable}` | 이름과 값을 바꿉니다. |
| `DELETE /api/v1/variables/{variable}` | 삭제합니다. |

권한: 프로젝트에서는 `variable.read` 권한으로 목록을 보고, `variable.create`, `variable.update`, `variable.delete`로 바꿉니다. viewer와 operator는 읽고, editor와 admin은 바꿉니다. 인스턴스 전체 변수는 어떤 프로젝트의 워크플로도 읽을 수 있으므로 로그인한 누구나 읽을 수 있고, 인스턴스 소유자나 관리자만 바꿉니다. 사용자 지정 역할은 이 네 권한 중 무엇이든 가질 수 있습니다. 변경은 감사 로그에 `variable.created`, `variable.updated`, `variable.deleted`로 남으며, 이름만 남고 값은 남지 않습니다.

## 폴더

편집기에서 워크플로 목록이 곧 폴더입니다. 새 폴더로 만들고, 하위 폴더 추가로 중첩하고, 목록의 해당 행에서 워크플로를 옮깁니다. 워크플로를 만들 때 폴더를 고르면 그곳에 놓입니다.

폴더는 프로젝트의 워크플로를 묶고, 공장이 구성된 방식대로 중첩됩니다. 구역, 라인, 셀 같은 식입니다.

- 폴더는 한 프로젝트에 속합니다. 이름은 같은 위치의 폴더끼리 중복될 수 없고, 최대 100자입니다.
- 폴더는 최대 10단계까지 중첩됩니다.
- 워크플로는 한 폴더에 있거나 프로젝트의 최상위에 있습니다. 새 버전을 저장해도 옮겨지지 않습니다.
- 워크플로나 폴더가 들어 있는 폴더는 삭제할 수 없으므로(409), 폴더를 삭제해서 워크플로가 사라지는 일은 없습니다. 폴더는 자기 자신이나 자기 하위 폴더 안으로 옮길 수 없고, 다른 프로젝트로도 옮길 수 없습니다.

| 호출 | 하는 일 |
|---|---|
| `GET /api/v1/folders` | 읽을 수 있는 프로젝트의 폴더를 평면 목록으로, 각각 `parentId`와 함께 반환합니다. `?project=`로 좁힙니다. |
| `POST /api/v1/folders` | `projectId`에 `parentId` 안 또는 최상위로 폴더를 만듭니다. |
| `PATCH /api/v1/folders/{folder}` | 이름을 바꾸거나 `parentId`로 옮깁니다(최상위는 빈 문자열). |
| `DELETE /api/v1/folders/{folder}` | 빈 폴더를 삭제합니다. |
| `PUT /api/v1/workflows/{workflow}/folder` | 워크플로를 폴더에 넣거나, 빈 `folderId`로 최상위에 놓습니다. |
| `GET /api/v1/workflows?folder=` | 한 폴더의 워크플로, 또는 `folder=none`으로 각 프로젝트의 최상위. |

API가 반환하는 모든 워크플로에는 `folderId`가 들어 있습니다. `folder.read`, `folder.create`, `folder.update`, `folder.delete` 권한은 변수 권한과 같은 방식으로 작동하고, 워크플로를 옮기려면 `workflow.update`가 필요합니다. 폴더 변경은 감사 로그에 남으며, 이동은 `workflow.moved`로 남습니다.

## 실행 주석

편집기에서 각 실행의 페이지에는 엄지 위 또는 아래, 메모, 태그를 넣는 주석 상자가 있고, 실행 목록은 태그와 평가로 필터링합니다.

실행이 끝난 뒤에 그 실행에 대해 한마디 남길 수 있습니다. 엄지 위 또는 아래, 메모, 그리고 찾을 때 쓸 태그입니다. "금형 교체 후 첫 양품 배치"나 `scrap` 같은 내용이 여기에 들어갑니다.

```sh
curl -X PUT $CASCADE/api/v1/executions/$RUN/annotation -H "Authorization: Bearer $KEY" \
  -d '{"vote":"up","note":"first good batch after the die change","tags":["die-change","first-shift"]}'
```

- 평가는 `up`, `down` 또는 비어 있음입니다. 메모는 최대 2000자입니다. 한 실행에는 태그를 최대 20개 둘 수 있고, 각 태그는 제어 문자 없이 1자에서 40자이며 한 번씩만 나열됩니다.
- `PUT`은 주석 전체를 교체하므로 남기려는 내용을 모두 보내야 합니다. 아무 내용도 없는 주석은 주석이 없는 것과 같습니다. `DELETE /api/v1/executions/{execution}/annotation`은 주석을 지웁니다.
- API가 반환하는 모든 실행에는 주석이 들어 있고, 목록도 각 행에 주석을 담습니다. `GET /api/v1/executions?tag=scrap`과 `?vote=down`으로 필터링하며, 다른 필터와 함께 쓸 수 있습니다.
- 주석에는 누가 언제 남겼는지가 감사 로그와 같은 ID로 기록됩니다.
- 주석을 달려면 operator, editor, admin이 가진 `execution.annotate` 권한이 필요하며 viewer에게는 없습니다. viewer는 주석을 읽을 수 있습니다.
- 주석은 해당 실행이 삭제되면 함께 사라집니다. 감사 로그에는 평가와 태그와 함께 `execution.annotated`와 `execution.annotation_cleared`가 남고, 메모가 남겨졌다는 사실만 기록되며 내용은 기록되지 않습니다.

## 완료된 실행 보관

편집기의 설정, 완료된 실행 보관 기간(일)에서 정합니다. API로는 `{"retentionDays": 90}`과 함께 `PATCH /api/v1/settings`를 호출하며, 다른 설정과 마찬가지로 `instance.settings` 권한이 필요합니다.

기본적으로 완료된 모든 실행은 지금까지처럼 영원히 보관됩니다. 일수를 정하면 main이 한 시간에 한 번, 그보다 오래전에 끝난 완료된 실행(성공, 실패, 취소)을 단계 데이터와 함께 삭제합니다. 0이면 다시 끕니다.

- 대기열에 있거나 실행 중이거나 대기 중인 실행은 건드리지 않으며, 부모가 아직 진행 중인 실행도 건드리지 않습니다. 부모가 그 실행이 무엇을 했는지 물을 것이기 때문입니다.
- 최대 500건의 실행 묶음마다 별도의 트랜잭션으로 처리되고, 삭제된 건수와 기준 시점이 담긴 `execution.pruned` 행 하나를 감사 로그에 씁니다. 설정을 바꾸면 `instance.retention`이 기록됩니다.
- 모든 main이 이 작업을 실행하며, 두 개가 동시에 실행되어도 할 일이 줄어들 뿐입니다.
- 블롭 정리는 같은 작업을 따르며, 보관 설정이 켜져 있든 아니든 한 시간에 한 번 실행되므로 직접 삭제한 실행도 정리됩니다. 아래 "블롭 정리"를 참고하세요.

## API 키 제한

편집기의 설정, 키당 분당 API 요청 수에서 정합니다. API로는 `{"apiRateLimit": 120}`과 함께 `PATCH /api/v1/settings`를 호출하며, `instance.settings` 권한이 필요합니다.

기본적으로 키는 원하는 만큼 자주 호출할 수 있습니다. 숫자를 정하면 각 API 키와, 그 키로 MCP에 로그인한 각 에이전트가 분당 그만큼의 요청을 할 수 있습니다. 한도를 넘는 호출에는 몇 초를 기다려야 하는지 알려 주는 `Retry-After` 헤더와 함께 `429`가 반환됩니다. 키마다 자체 카운트를 가지므로 폭주한 스크립트 하나가 다른 키의 몫을 쓸 수 없습니다. 편집기에 로그인한 사람은 이 제한을 받지 않습니다.

카운트는 각 프로세스의 것입니다. 그것이 프로세스를 보호하기 때문입니다. main이 세 개면 키 하나가 그 수의 최대 세 배까지 요청할 수 있고, 이는 세 main에 나뉩니다. 설정 변경은 5초 안에 모든 main에 반영됩니다. 변경하면 이전 값과 새 값이 담긴 `instance.api_rate_limit`이 감사 로그에 기록됩니다.

웹훅에는 트리거에서 정하는 자체 한도가 있고, 계정은 비밀번호를 반복해서 틀리면 잠깁니다. 둘 다 바뀌지 않습니다.

## 백업과 복원

```
hotloop-cascade backup /backups/2026-11-20
hotloop-cascade restore /backups/2026-11-20
```

`backup`은 새 디렉터리를 만들어 SQLite 데이터베이스의 일관된 사본(서버가 실행 중일 때 `VACUUM INTO`로 만든 것), 저장된 모든 자격 증명을 봉인하는 키 파일, 블롭 파일, 각 파일의 SHA-256이 담긴 `manifest.json`을 넣습니다. 서버와 같은 `--database`, `--key-file`, `--blob-dir` 설정을 같은 환경 변수에서 받습니다. 디렉터리는 아직 없거나 비어 있어야 하며, 백업은 이전 백업과 섞이지 않습니다. 키 파일이 없으면 백업도 없습니다. 키가 없는 데이터베이스에는 아무도 읽을 수 없는 자격 증명이 들어 있기 때문입니다.

`restore`는 이를 되돌려 놓으며, 먼저 서버를 중지해야 합니다. 무엇이든 쓰기 전에 매니페스트와 모든 파일을 대조하므로, 손상되었거나 불완전한 백업은 아무것도 바꾸지 않습니다. 이미 있는 데이터베이스나 다른 키 파일을 덮어쓰기를 거부하며, `--replace`로 의도했음을 알립니다. 이후 서버를 시작하면 스키마를 최신으로 올리고, 자신보다 새로운 릴리스로 만든 백업은 거부합니다.

PostgreSQL에서는 `backup`이 키, 블롭, 매니페스트를 쓰고 데이터베이스 부분을 만드는 `pg_dump --format=custom` 명령을 출력합니다. 그 프로그램은 PostgreSQL 자체의 것이라 Cascade 이미지에 들어 있지 않기 때문입니다. `restore`는 키와 블롭을 되돌리고 `pg_restore` 명령을 출력합니다. S3나 Azure에 보관한 블롭은 복사되지 않으므로 그 버킷은 그곳에서 백업하세요.

마이그레이션이 있는 릴리스로 업그레이드하기 전에 백업을 하나 만드세요. 마이그레이션은 앞으로만 진행되며, 이전 이미지로 돌아가려면 백업이 필요합니다.

## 실행 마스킹 정책

편집기의 설정, 마스킹에서 정책을 만듭니다. 워크플로는 아무것도 선택하지 않은 편집기 측면 패널의 워크플로 설정에서 정책을 고릅니다.

자격 증명 보관소는 이미 실행이 저장하는 모든 것에서 시크릿을 제외합니다. 마스킹 정책은 자격 증명은 아니지만 실행 기록에도 남기지 않아야 하는 데이터를 위한 것입니다. 출입증 번호, 작업자 이름, 웹훅으로 들어온 카드 번호 같은 것입니다.

정책은 이름과 규칙으로 이루어집니다.

- **fields**: 아이템 키 이름입니다. 정책이 이름을 든 키는 값 전체가 `[redacted]`로 바뀌며, 깊이와 값의 형식에 상관없이 적용됩니다. 대소문자를 구분하지 않고 `*`와 `?`는 와일드카드로 작동하므로, `*secret*`은 `plant_secret`과 `SecretKey`를 잡습니다.
- **patterns**: Go의 RE2 문법의 정규 표현식입니다. 어떤 텍스트 안이든 일치하는 부분은 `[redacted]`로 바뀝니다. 빈 텍스트와 일치하는 패턴은 거부됩니다.
- **steps**: 선택 사항입니다. 정책은 나열된 단계에만 적용됩니다. 비어 있으면 모든 단계입니다.
- **appliesToAll**: 선택 사항입니다. 워크플로가 정책을 지정했는지와 관계없이 모든 워크플로에 적용됩니다.

워크플로는 설정에서 이름으로 정책을 고릅니다.

```yaml
settings:
  redaction: Badges
```

동작과 시점은 다음과 같습니다.

- **실행이 끝날 때** 실행되며, 실행을 성공, 실패, 중지로 표시하는 같은 트랜잭션 안에서 처리됩니다. 그때까지 실행은 실제 데이터를 가지고 있습니다. 다음 단계가 그것을 필요로 하고 재시작도 그 데이터에서 이어지기 때문입니다. 대기 중인 실행은 여전히 실제 데이터를 가지고 있습니다.
- 각 단계의 저장된 출력, 각 단계의 저장된 오류 메시지, 실행 자체의 오류, 저장된 웹훅 응답을 정리합니다. 파일 내용은 건드리지 않습니다. 정책은 아이템 데이터를 읽고, 파일은 바이트에 대한 참조이기 때문입니다.
- 저장된 내용이 그 실행의 중간부터 다시 실행하거나 재시도할 때의 출발점이므로, 다시 실행하면 정리된 값이 보입니다. 워크플로의 트리거 아이템은 첫 단계의 출력에 있으며 마찬가지로 정리됩니다.
- 그 실행이 가졌던 시점의 워크플로를 읽으므로, 워크플로나 정책을 편집해도 이미 끝난 실행은 바뀌지 않습니다.
- 존재하지 않는 정책을 지정한 워크플로는 **닫힌 쪽으로 실패합니다**. 그 실행들은 `metadata` 저장 설정처럼 아이템 데이터를 전혀 보관하지 않으며, 워크플로의 `problems`에 그렇게 표시됩니다. 정책이 없다는 것이 누군가 정리하려던 데이터가 보관된다는 뜻이어서는 안 됩니다.
- 워크플로가 지정한 정책은 삭제할 수 없고(409) 이름도 바꿀 수 없습니다. 규칙은 바꿀 수 있습니다.

| 호출 | 하는 일 |
|---|---|
| `GET /api/v1/redaction-policies` | 모든 정책. 워크플로를 작성하는 사람에게 이름이 필요하므로 로그인한 누구나 읽을 수 있습니다. |
| `POST /api/v1/redaction-policies` | 정책을 만듭니다. |
| `PUT /api/v1/redaction-policies/{policy}` | 설명과 규칙을 교체합니다. |
| `DELETE /api/v1/redaction-policies/{policy}` | 어떤 워크플로도 지정하지 않은 정책을 삭제합니다. |

정책을 만들고, 바꾸고, 삭제하려면 소유자와 관리자가 가진 인스턴스 권한 `redaction.manage`가 필요합니다. 각각 감사 로그에 `redaction.created`, `redaction.updated`, `redaction.deleted`로 남습니다.

## Insights

편집기 상단 막대의 Insights에서 봅니다. 기간, 프로젝트, 워크플로를 고르면 합계, 일별 차트와 표, 워크플로별 표를 보여 줍니다.

`GET /api/v1/insights`는 한 기간의 실행을 집계합니다. 어떻게 끝났는지, 얼마나 걸렸는지를 일별과 워크플로별로 보여 줍니다.

```sh
curl "$CASCADE/api/v1/insights?from=2026-10-10&to=2026-10-14&project=$PROJECT" -H "Authorization: Bearer $KEY"
```

- `from`과 `to`는 RFC 3339 시각이나 날짜(UTC 자정)입니다. 둘 다 없으면 지금까지의 최근 7일입니다. 응답하는 최대 기간은 366일입니다.
- `project`와 `workflow`로 좁힙니다. 지정하지 않으면 호출한 사람이 실행을 읽을 수 있는 모든 프로젝트를 집계하므로, 각 사람의 수치는 자신의 것입니다.
- 실행은 생성된 UTC 날짜에 집계됩니다.
- `totals`와 `days`, `workflows`의 각 행에는 `total`, `succeeded`, `failed`, `canceled`, `unfinished`(대기열, 실행 중, 대기 중), 시작과 종료가 모두 있는 실행의 평균 및 최장 실행 시간(밀리초), `failureRate`가 들어 있습니다.
- `failureRate`는 실패 건수를 성공과 실패를 합한 건수로 나눈 값입니다. 취소된 실행은 실패가 아니고 끝나지 않은 실행은 아직 결과가 정해지지 않았으므로, 둘 다 포함되지 않습니다. 어느 쪽으로도 끝난 것이 없으면 0입니다.
- `days`는 기간 안의 모든 UTC 날짜를 나열하며, 아무것도 실행되지 않은 날은 0으로 채우므로 차트에 짐작해야 할 빈 구간이 없습니다. `workflows`는 가장 바쁜 50개이며 가장 바쁜 것이 먼저입니다.

실행 목록과 같은 실행 행을 읽으므로 `execution.read` 권한과 그에 맞는 범위의 키가 필요합니다.

## 외부 시크릿

편집기의 설정, 외부 시크릿에서 다룹니다. 공급자를 추가하고, 같은 카드에서 경로로 시험해 보고, 그 공급자를 가리키는 참조가 어떤 모양인지 확인합니다.

자격 증명의 시크릿 필드는 시크릿을 직접 담는 대신 HashiCorp Vault나 OpenBao에 보관된 시크릿을 가리킬 수 있습니다. 저장소에서 비밀번호를 교체하면 모든 워크플로가 다음 실행부터 새 비밀번호를 쓰며, 누구도 자격 증명을 편집할 필요가 없고, 데이터베이스 사본에는 비밀번호가 담기지 않습니다.

참조는 자격 증명의 어떤 시크릿 필드에서든 다음과 같은 모양입니다.

```
secret://bao/plant/line-3/db#password
```

이것은 `bao`라는 이름의 공급자, `plant/line-3/db`의 시크릿, 그리고 그 `password` 키입니다. 자격 증명은 이 텍스트를 다른 시크릿처럼 봉인해서 저장합니다. 가리키는 대상은 여기에 저장되지 않습니다. 값은 실행이 자격 증명을 열 때 읽히고, 공급자의 캐시 시간 동안 메모리에 보관되며, 보관소의 비밀번호처럼 실행이 저장하는 모든 것에서 정리됩니다. 참조는 시크릿 필드에서만 받습니다. 시크릿이 아닌 필드에 입력한 참조는 그냥 텍스트입니다.

### 공급자 설정

공급자는 서버, Cascade가 그 서버에 로그인하는 방법, 읽을 수 있는 위치로 이루어집니다. 공급자를 만들고, 바꾸고, 제거하는 일은 인스턴스 소유자나 관리자의 몫이며 `secrets.manage` 권한이 필요하고, API 키가 아니라 로그인한 사람이 해야 합니다.

```sh
curl -X POST $CASCADE/api/v1/secret-providers -H "X-CSRF-Token: ..." -d '{
  "name": "bao",
  "address": "https://bao.plant.example:8200",
  "authMethod": "approle", "roleId": "...", "secretId": "...",
  "allowedPaths": ["plant"]
}'
```

| 필드 | 하는 일 |
|---|---|
| `name` | 소문자, 숫자, 대시로 1자에서 40자. 모든 참조에 들어가므로 나중에 바꿀 수 없습니다. |
| `address` | 서버의 URL. |
| `mount`, `kvVersion` | KV 엔진이 마운트된 위치(기본값 `secret`)와 버전 1 또는 2 여부(기본값 2). |
| `namespace` | 서버의 네임스페이스를 위한 `X-Vault-Namespace`로 전송됩니다. |
| `authMethod` | `token`과 `token`, 또는 `approle`과 `roleId` 및 `secretId`. `authMount`는 AppRole이 마운트된 위치(기본값 `approle`)입니다. AppRole은 스스로 로그인하고, 토큰이 만료되면 다시 로그인합니다. |
| `caCert` | 서버의 인증서가 시스템이 신뢰하는 기관의 것이 아닐 때 서버에 대해 신뢰할 PEM 인증 기관. |
| `allowedPaths` | **필수.** 참조가 읽을 수 있는 유일한 위치입니다. `plant`는 `plant`와 그 아래의 모든 것을 허용하며 `plantation`은 허용하지 않습니다. |
| `projects` | 선택 사항. 공급자를 쓸 수 있는 유일한 프로젝트입니다. 비워 두면 모든 프로젝트가 쓸 수 있습니다. |
| `cacheSeconds` | 읽은 시크릿을 메모리에 보관하는 시간, 0에서 3600. 기본값 30. 0이면 매번 읽습니다. |

Cascade가 로그인하는 방법(토큰, 또는 AppRole의 ID와 시크릿)은 인스턴스 키로 봉인되고, 키 교체 때 다른 모든 것과 함께 다시 감싸지며, 어떤 호출도 이를 보여 주지 않습니다. 변경할 때 생략하면 저장된 값이 그대로 유지됩니다.

`POST /api/v1/secret-providers/{provider}/test`는 로그인하고, `path`가 있으면 그 경로를 읽어서 성공했는지 알려 줍니다. 값을 반환하지는 않습니다. `GET /api/v1/secret-providers`는 자격 증명을 만드는 사람에게 이름이 필요하므로 로그인한 누구에게나 공급자 목록을 보여 줍니다. 호출은 감사 로그에 `secrets.provider_created`, `_updated`, `_deleted`로 남습니다.

### 하지 않는 것

- **공급자에는 허용된 경로가 필요합니다.** Vault 토큰은 보통 자격 증명을 편집하는 사람이 지정할 수 있어야 하는 범위보다 훨씬 많이 읽을 수 있고, 목록이 없다면 자격 증명을 만들 수 있는 누구든 토큰이 닿는 아무 시크릿이나 가리키게 해서 워크플로가 그것을 어딘가로 보내게 할 수 있습니다. 공급자에는 자격 증명에 필요한 경로를 주고, 그 정책에도 같은 경로를 주세요.
- **참조는 자격 증명을 저장할 때 검사됩니다.** 실행이 사용할 때만이 아닙니다. 공급자가 존재하고, 자격 증명의 프로젝트에 열려 있고, 경로를 허용해야 합니다. 빈 부분, 점, `..`이 들어 있는 경로는 거부됩니다.
- **시크릿을 읽지 못한 실행은 실패하며 이유를 알립니다.** 공급자, 경로, 키를 밝히되 값은 절대 밝히지 않습니다. 그런 공급자가 없음, 공급자가 허용하지 않는 경로, 그 위치에 시크릿이 없음, 그런 키가 없음, 또는 서버 자체의 거부(읽기를 허용하지 않는 정책은 "permission denied")입니다.
- **공급자를 삭제해도 자격 증명은 편집되지 않습니다.** 그 공급자를 가리키는 자격 증명은 실행이 열 때 공급자가 없어졌다는 메시지와 함께 실패합니다.
- 실제로 `secret://`로 시작하는 시크릿 값은 참조로 읽히므로 시크릿으로 저장할 수 없습니다.
- 숫자나 true, false인 값은 텍스트로 읽힙니다. 객체 전체이거나 목록인 값은 거부됩니다.
## 로그 스트리밍

편집기의 설정, 로그 스트리밍에서 다룹니다(소유자와 관리자). 각 대상은 얼마나 보냈는지, 마지막으로 언제 전달했는지, 마지막 오류가 무엇인지를 보여 주며, 테스트 이벤트 하나를 보내는 버튼이 있습니다.

감사 로그와, 끝나는 모든 실행의 한 줄을 공장이 이미 로그를 두는 곳으로 보냅니다. syslog 서버, 또는 HTTP로 OTLP 로그를 받는 모든 것(OpenTelemetry 수집기, Loki, 로그 플랫폼)이 해당합니다. 이벤트는 발생하는 즉시 나가므로 SIEM이 몇 초 안에 로그인 실패를 보고, 감사 기록은 이 인스턴스의 관리자가 고쳐 쓸 수 없는 곳에 남습니다.

대상은 하나의 장소입니다. 필요한 만큼 만드세요.

```sh
curl -X POST $CASCADE/api/v1/log-destinations -H "X-CSRF-Token: ..." -d '{
  "name": "plant syslog", "kind": "syslog",
  "address": "syslog.plant.example:6514", "network": "tls",
  "caCert": "-----BEGIN CERTIFICATE-----..."
}'
curl -X POST $CASCADE/api/v1/log-destinations -H "X-CSRF-Token: ..." -d '{
  "name": "collector", "kind": "otlp", "endpoint": "https://otel.plant.example/v1/logs",
  "headers": {"Authorization": "Bearer ..."}
}'
```

대상을 만들고, 바꾸고, 제거하는 일은 인스턴스 소유자와 관리자(`logstream.manage`)의 몫이며, 대상은 감사 로그가 가는 곳이므로 API 키가 아니라 로그인한 사람이 해야 합니다. 호출은 감사 로그에 `logstream.destination_created`, `_updated`, `_deleted`로 남습니다.

### 전송되는 것

- **감사 이벤트**: 감사 로그의 모든 행이 순번과 해시와 함께 전송됩니다. 순번과 해시로 수신자가 중복을 알아보며, 해시는 그 행 자체의 것이므로 도착한 것만으로 체인을 검증할 수 있습니다. 실패하거나 거부된 로그인은 경고이고, 나머지는 알림입니다.
- **실행 이벤트**: 어떻게 끝났든 끝나는 실행마다 하나씩 전송됩니다. 실행 ID, 워크플로 ID와 이름, 프로젝트, 상태, 모드, 생성, 시작, 종료 시각, 실행 시간, 오류와 실패한 단계가 들어 있습니다. 실패한 실행은 오류, 중지된 실행은 알림, 성공한 실행은 정보입니다. 실행이 끝나고 몇 초 뒤에 전송됩니다.
- **아이템 데이터는 절대 보내지 않습니다.** 실행의 단계가 보고 만든 것은 마스킹 정책이 보호하는 실행 안에 남습니다. 감사 로그에는 시크릿이 들어가지 않습니다.

`events`는 하나 또는 둘 다를 고릅니다(`["audit"]`, `["execution"]`, 기본값은 둘 다). `start`는 새 대상이 어디서 시작하는지 정합니다. 기본값 `now`는 대상을 만든 뒤에 일어나는 것을 보내고, `beginning`은 감사 로그 전체와 끝난 모든 실행을 먼저 보냅니다.

### Syslog

메시지는 RFC 5424 형식입니다. `<priority>1 time host hotloop-cascade pid msgid - {json}`이며, 이벤트는 JSON 한 줄입니다. 우선순위는 facility에 8을 곱하고 심각도를 더한 값입니다. msgid는 감사 동작(`workflow.saved`) 또는 실행 상태입니다.

| 필드 | 하는 일 |
|---|---|
| `address` | `host:port`. |
| `network` | `tcp`(기본값), `udp`, `tls`. |
| `framing` | `tcp`와 `tls`용: `octet`(RFC 6587 옥텟 카운팅, 기본값) 또는 `newline`. UDP는 이벤트마다 데이터그램 하나입니다. |
| `facility` | 기본값 `local0`. 모든 syslog facility 이름. |
| `appName` | 헤더의 APP-NAME, 기본값 `hotloop-cascade`. |
| `caCert`, `serverName` | `tls`용: 신뢰할 기관과, 인증서가 호스트가 아닌 이름으로 발급되어야 할 때 그 이름. 검사를 건너뛰는 설정은 없습니다. |

### OTLP

로그는 JSON 본문의 HTTP OTLP로 `endpoint`에 전송됩니다. 이벤트마다 로그 레코드 하나이고, 본문은 JSON 이벤트이며, 각 부분은 속성(`cascade.event`, `cascade.action`, `cascade.status`, `cascade.project`, `cascade.actor.name` 등)으로 담겨 수신자가 파싱 없이 필터링할 수 있습니다. 리소스에는 `service.name=hotloop-cascade`, 버전, 호스트가 들어 있습니다. `headers`는 토큰이나 테넌트를 위해 모든 요청과 함께 전송됩니다. 인스턴스 키로 봉인되고, 키 교체 때 다시 감싸지며, 표시되지 않습니다. 목록에는 이름만 나옵니다. `caCert`와 `serverName`은 syslog와 같게 작동합니다.

### 전달 방식

- **최소 한 번, 순서대로.** 대상은 마지막으로 보낸 감사 행과 마지막으로 보낸 끝난 실행을 기억합니다. 중단된 대상은 돌아오면 놓친 모든 것을 순서대로 받고, 재시작해도 멈춘 곳에서 이어갑니다. 전송과 기록 사이에 발신자가 끊기면 그 이벤트가 다시 전송되며, 순번이 그래서 있습니다.
- **실패하는 대상은 점점 더 기다립니다.** 1초에서 시작해 두 배씩 늘어 5분까지이며, 상태에 무엇이 잘못되었고 언제인지가 `lastError`, `lastErrorAt`으로 표시됩니다. 성공하면 지워집니다. 중단된 동안에는 아무것도 버려지지 않으므로 한계는 대기열이 아니라 감사 로그입니다.
- **한 번에 하나의 발신자.** main이 여럿이면 대상의 리스를 가진 쪽이 보내고, 나머지는 기다리다가 그쪽이 멈추면 넘겨받습니다.
- **대상을 바꿔도 자리는 유지됩니다.** 다른 주소로 옮겨도 아무것도 다시 보내거나 건너뛰지 않습니다. 변경에서 생략한 헤더는 유지되고, 빈 객체는 헤더를 지웁니다. 이름과 종류는 바꿀 수 없습니다.
- `POST /api/v1/log-destinations/{destination}/test`는 같은 경로로 가짜 이벤트 하나를 보내고 도착했는지 알려 주며, 도착하지 않았다면 이유를 알려 줍니다. 아무것도 옮기지 않습니다.
- `GET /api/v1/log-destinations`는 각 대상의 상태를 보여 줍니다. 보낸 이벤트 수, 마지막으로 전달된 감사 순번, 마지막으로 성공한 시각, 마지막 오류입니다.

## 대용량 데이터의 위치

실행이 가지고 다니는 파일과 큰 페이로드(내려받은 PDF, 카메라 프레임, 스프레드시트)는 데이터베이스와 별도로 블롭으로 저장됩니다. 기본적으로 인스턴스의 디스크에 있습니다. `HOTLOOP_CASCADE_BLOB_STORE`를 설정하면 S3 버킷이나 Azure 블롭 컨테이너에 두게 되어, main을 다시 만들 때 블롭을 옮기지 않아도 되고 여러 main이 사본 하나를 공유합니다.

| 설정 | 의미 |
| --- | --- |
| `HOTLOOP_CASCADE_BLOB_STORE` | `fs`(기본값), `s3`, `azure`. |
| `HOTLOOP_CASCADE_BLOB_SPOOL_DIR` | 업로드 전에 해시를 계산하는 동안 블롭이 대기하는 위치. 기본값은 데이터 디렉터리의 `blob-spool`입니다. |
| `HOTLOOP_CASCADE_BLOB_S3_BUCKET`, `_ACCESS_KEY`, `_SECRET_KEY` | `s3`에 필수. 시크릿은 `_SECRET_KEY_FILE`도 읽습니다. |
| `HOTLOOP_CASCADE_BLOB_S3_ENDPOINT`, `_REGION` | AWS에서는 엔드포인트를 생략합니다. Garage, MinIO, Ceph에서는 설정합니다. |
| `HOTLOOP_CASCADE_BLOB_S3_PATH_STYLE` | `true` 또는 `false`. 엔드포인트가 설정되면 경로 방식이 기본값입니다. |
| `HOTLOOP_CASCADE_BLOB_S3_CA_FILE` | 사설 인증서를 쓰는 엔드포인트를 위한 CA 번들. |
| `HOTLOOP_CASCADE_BLOB_S3_PREFIX` | 버킷 안의 폴더. 한 버킷에 인스턴스를 둘 이상 둘 수 있습니다. |
| `HOTLOOP_CASCADE_BLOB_AZURE_CONTAINER` | `azure`에 필수. |
| `HOTLOOP_CASCADE_BLOB_AZURE_CONNECTION_STRING`, 또는 `_KEY`가 있는 `_ACCOUNT`, 또는 `_SAS` | 로그인하는 방법 중 하나. 시크릿은 `_FILE` 형식도 읽습니다. |
| `HOTLOOP_CASCADE_BLOB_AZURE_ENDPOINT`, `_PREFIX` | Azurite나 사설 클라우드의 엔드포인트와 컨테이너 안의 폴더. |

차트에서는 이 값들을 `env`와 `extraEnv`로 설정하고, 시크릿은 Kubernetes Secret에서 가져옵니다.

- **내용으로 주소를 지정합니다.** 블롭은 SHA-256(`sha256/ab/cdef...`) 아래에 저장되므로, 같은 파일은 몇 개의 실행이 가지고 있든 한 번만 저장됩니다. 다시 넣어도 아무 일도 일어나지 않으며, 두 실행이 동시에 넣어도 같습니다.
- **업로드 전에 해시합니다.** 데이터는 스풀 파일로 한 번 읽히고, 해시된 다음 전송되므로 크기와 관계없이 메모리 사용량은 일정합니다. 크기 제한을 넘는 블롭은 거부되며, 취소된 업로드는 버킷에 아무것도 남기지 않습니다.
- **읽을 때 검사합니다.** 읽기는 스트리밍되는 동안 해시와 대조되므로, 손상된 객체는 실행에 잘못된 데이터를 넘기는 대신 분명하게 실패합니다.
- **크기.** 단일 업로드는 S3에서는 멀티파트 전송으로, Azure에서는 블록으로 올라가므로 요청당 5 GiB라는 일반적인 제한은 적용되지 않습니다.
- **블롭 정리.** 한 시간에 한 번 어떤 행도 가리키지 않는 블롭을 제거하는 작업이 돕니다. 데이터베이스에 넣기에는 너무 커서 파일로 저장된 단계 출력, 그리고 아이템이 가진 첨부 파일이 해당합니다. 단계 실행, 부분 출력, 저장된 응답, 워크플로 중 어느 하나라도 직접 또는 첨부를 담은 저장된 출력을 통해 여전히 그 블롭을 가리키는 동안은 블롭이 유지되므로, 출력이 같은 두 실행이 공유하는 파일은 마지막 실행이 없어질 때까지 남습니다. 마지막으로 기록된 지 24시간이 넘은 블롭만 검토하며, 이미 저장된 바이트를 다시 넣는 것은 첫 한 시간이 지난 뒤에 다시 쓴 것으로 치므로, 단계가 방금 저장했지만 아직 기록하지 않은 파일은 절대 제거되지 않습니다. 저장된 출력을 읽지 못한 작업은 아무것도 제거하지 않습니다. 제거된 파일 수와 바이트 수가 담긴 `blobs.collected` 행 하나를 감사 로그에 씁니다. 이 작업은 블롭 저장소가 한 인스턴스의 것이라고 가정합니다(한 설치의 worker와 main이 공유함). 같은 버킷이나 폴더를 가리키는 두 설치는 서로의 파일을 제거하므로, 각각 자기 것을 쓰게 하세요(`HOTLOOP_CASCADE_BLOB_S3_PREFIX`가 이를 위해 있습니다).
- **나중에 저장소를 바꾸기.** 기존 블롭은 기록된 곳에 그대로 남습니다. 전환하기 전에 새 저장소로 옮기세요. 새 저장소에 없는 블롭에 대한 참조는 사라진 파일이 되기 때문입니다.

이 두 백엔드는 디스크 저장소와 같은 적합성 테스트 모음으로 테스트 스택에서 Garage와 Azurite를 상대로 시험합니다. 쓰기와 읽기, 빈 블롭, 동시성 상황의 중복 제거, 손상, 한도, 잘못된 ID, 삭제, 목록, 취소된 쓰기, 힙 검사를 곁들인 192 MiB 스트리밍 업로드가 포함됩니다.

사용자에게 의미하는 바: 다시 만들거나 교체한 main도 실행이 가지고 있던 모든 파일을 복사 없이 찾습니다.
