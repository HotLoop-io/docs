title: "모든 배포는 기록이 됩니다"

---

"무엇이 바뀌었고, 누가 바꿨고, 되돌려 주세요."는 라인이 멈춘 뒤 누구나 가장 먼저 묻는 말입니다. `.bak` 파일 세 개로는 아무것도 답할 수 없습니다. 누가 했는지 모르고, 세 번 저장하면 덮어써지며, 필요한 것은 언제나 네 번째 파일입니다.

그래서 모든 배포는 `data/deployments/` 아래에 변경할 수 없는 기록을 남깁니다. 누가 배포했는지(클라이언트가 주장하는 값이 아니라 토큰으로), 어디서, 언제, 남긴 메모, 교체된 리비전, 바이트 단위의 플로 파일, 그리고 배포 직후의 자격 증명이며, 자격 증명은 자격 증명 파일과 똑같이 암호화됩니다. 기록은 추가만 가능합니다. 로그는 기본적으로 최근 100개를 보관하고(`history.retain`, 0이면 전부 보관), 가장 최근 것은 절대 지우지 않습니다. 가장 최근 것이 지금 실행 중인 것이기 때문입니다.

```bash
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:1880/deployments
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:1880/deployments/42/flows > flows-42.json
```

메모는 배포와 함께 들어갑니다. 감싼 문서의 `"note"`(`{"rev": ..., "flows": [...], "note": "..."}`)로 넣거나 `HotLoop-Flow-Deployment-Note` 헤더로 넣습니다. 문서 형식이 있는 이유는 브라우저가 헤더에 Latin-1 바깥의 문자를 넣지 못하는데, 사람들은 메모를 자기 언어로 쓰기 때문입니다.

문제가 생기고 나서야 아쉬울 두 가지가 있습니다.

- **수동 편집을 잡아냅니다.** 프로세스가 멈춘 동안 누군가 디스크의 플로 파일을 편집해서 로그가 마지막으로 기록한 것과 다르면, 시작할 때 이를 알려 주는 `baseline` 항목으로 기록합니다. 플로 파일이 이미 있는 상태의 첫 시작도 같습니다. 그렇지 않으면 수동 편집은 아무도 기록하지 않은 과거가 되어 조용히 묻힙니다.
- **쓸 수 없는 로그가 라인을 멈추지 않습니다.** 그 시점에 플로 파일은 이미 저장되어 있으므로, 배포를 거부하면 다음 재시작 때까지 디스크와 실행 중인 플로가 서로 어긋나게 됩니다. 배포는 그대로 진행되고, 응답과 로그 모두 이 배포에는 기록이 없다고 말로 알려 줍니다.

API는 기록 안의 자격 증명을 암호화된 상태로든 아니든 절대 내주지 않습니다. 자격 증명은 되돌리는 한 가지 일을 위해서만 보관되며, 히스토리 엔드포인트는 그것을 가져가는 통로가 아닙니다.

## 차이는 리뷰처럼 읽힙니다

플로 파일의 줄 단위 diff는 정직하지만 쓸모가 없습니다. 노드를 20픽셀 끌어도 변경이고, 임계값을 바꿔도 변경입니다. 리뷰어는 둘 중 어느 쪽이 프레스를 멈추게 할지 알 수 없습니다. 그래서 Flow는 노드 단위로 비교합니다.

```
1 changed, 2 moved

Tab "Line 3" (t1)
  ~ switch "Pressure check" (sw1)
      rules[1].v: "7.5" -> "8.0"
      wire added: port 1 -> change "set alarm" (alarm1)

Moved on the canvas only
  mqtt in "press 01" (in1)
  debug "ok" (ok1)
```

추가, 삭제, 변경을 속성별로 이전 값과 새 값과 함께 보여 주고, 어떤 연결이 출력 포트별로 옮겨졌는지 보여 주며, **레이아웃은 로직과 분리됩니다**. 레이블을 옮기거나 크기를 바꾸거나 숨기는 것은 "캔버스에서 이동"일 뿐 변경이 아니므로, 정리는 정리로 읽힙니다. 자격 증명은 "설정됨" 또는 "변경됨"으로만 표시되고 값은 절대 나오지 않습니다. 서브플로 안의 편집은 서브플로에 표시되며, 서브플로의 포트를 끄는 것도 레이아웃입니다.

어디서나 같은 답이 나오며, 엔진의 패키지 하나에서 나옵니다.

- `GET /deployments/{from}/diff/{to}`는 두 배포를 비교합니다.
- `POST /flows/diff`는 실행 중인 것과 아직 아무도 배포하지 않은 문서를 비교하며, 배포를 누르기 전에 보는 것이 바로 이것입니다.
- 명령줄의 `hotloop-flow diff old.json new.json`입니다. 프로그램용은 `-json`입니다. 다른 것이 있으면 `diff`처럼 1로 종료합니다.
- **git 안에서.** 이것을 플로 파일의 git diff 드라이버로 만들면 `git diff`, `git log -p`, `git show`가 JSON 덩어리 대신 의미 단위의 diff를 출력합니다.

  ```bash
  git config diff.hotloop-flow.command 'hotloop-flow diff'
  echo 'flows.json diff=hotloop-flow' >> .gitattributes
  ```

  difftool로도 쓸 수 있습니다. `git config difftool.hotloop-flow.cmd 'hotloop-flow diff "$LOCAL" "$REMOTE"'`를 설정하고 `git difftool -t hotloop-flow`를 실행합니다.

자기 자신과 비교한 플로는 파서가 받아들이는 어떤 문서든 변경이 전혀 없는 것으로 나옵니다.

## 되돌리기

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  -H "HotLoop-Flow-Deployment-Rev: $CURRENT_REV" \
  -d '{"note":"42 broke the label printer"}' \
  http://localhost:1880/deployments/41/rollback
```

롤백은 이전 기록을 **새 기록으로** 다시 배포합니다. 히스토리는 계속 추가만 가능합니다. 배포 41은 건드리지 않고, 롤백은 "배포 41로 롤백", 누가 했는지, 왜 했는지를 적은 별도의 항목이 됩니다. 플로 파일은 바이트 단위로 그대로 돌아오므로, 그때와 같은 리비전입니다.

**자격 증명도 함께 돌아옵니다.** 모든 기록이 당시 상태의 자격 증명을 담고 있어서, 삭제했던 노드가 돌아올 때 브로커 비밀번호도 함께 돌아오며, 돌아왔는데 로그인하지 못하는 일이 없습니다. 익명 클라이언트를 거부하는 실제 Mosquitto를 상대로 테스트합니다. 구독자를 삭제하고, 배포하고, 롤백하면 다시 로그인하고 메시지가 흐릅니다.

무엇이든 쓰기 전에 세 가지 경우에 거부합니다. 오래된 `HotLoop-Flow-Deployment-Rev`는 배포와 같은 409를 받습니다. 다른 사람의 배포와 경쟁하는 롤백도 여전히 경쟁이기 때문입니다. 보존 기간으로 이미 삭제된 배포는 404입니다. 그리고 현재 자격 증명 비밀로 자격 증명을 복호화할 수 없는 기록은 422입니다. 어디에도 로그인할 수 없는 플로는 성공한 것처럼 보이기만 하는 롤백이기 때문입니다.

## 편집기에서

**Deploy는 배포하지 않습니다.** 리뷰를 엽니다. 실행 중인 것과 엔진의 diff를 캔버스에 그리고 말로 나열하며, 메모를 쓰는 칸이 있습니다. 초록은 추가, 호박색은 변경, 파랑은 이동만이며, 삭제된 노드와 연결이 있던 자리에는 빨간 유령이 놓입니다. 변경이 있는 탭에는 점이 붙습니다. 두 번째 Deploy 버튼이 실제로 배포하는 버튼이고, 메모는 로그에 들어갑니다. 리뷰가 열려 있는 동안 무엇이든 편집하면 리뷰가 닫힙니다. 그사이 바뀐 것에 대한 리뷰는 곧 밀어 넣으려는 것에 대한 거짓말이기 때문입니다.

**히스토리 패널**은 모든 배포를 누가, 언제, 메모와 함께 보여 줍니다. *Changes*는 그 배포를 읽기 전용 캔버스에 열고 바뀐 것을 그 위에 그리며, 작업 중인 사본은 두고 간 그대로 유지됩니다. *Roll back*은 이유를 묻고, 저장하지 않은 편집을 버리려 하면 경고한 다음 배포합니다.

**배포 충돌은 상대가 한 일을 보여 줍니다.** 예전에는 브라우저 `confirm()`이 상대의 것이 무엇인지 말하지 않고 상대의 것을 덮어쓸지 내 것을 잃을지만 물었습니다. 이제는 누가, 언제 배포했는지, 그 사람의 메모와 노드별 변경을 보여 주고, 그 사람의 것을 불러오거나, 내 것으로 덮어쓰거나, 계속 편집하게 합니다.

**복사, 잘라내기, 붙여넣기는 예상대로 동작하며 플로 파일 형식을 씁니다.** 노드를 선택하고 Ctrl+C를 누르면 클립보드에는 다른 모든 플로 도구가 읽는 것과 같은 JSON이 담기므로, 채팅, 티켓, 다른 박스에 붙여 넣을 수 있습니다. 붙여넣기는 포인터가 있는 곳에 매번 새 id로 놓이므로, 두 번 붙여넣으면 사본 두 개가 생길 뿐 충돌은 없습니다. 복사하지 않은 대상으로 가는 연결은 허공을 가리키는 대신 끊기고, 노드가 쓰는 설정 노드는 함께 옵니다. 붙여넣는 플로에 그 설정 노드가 이미 있으면, 연결 수를 세는 대상에 두 번째 연결을 열지 않고 사본이 그것을 공유합니다. 자격 증명은 클립보드에 절대 들어가지 않습니다. 붙여넣기 버퍼에 있는 비밀번호가 버그 리포트에 들어가는 방식이기 때문입니다.

**Import와 Export**는 선택 영역, 플로 하나, 전체에 대해 같은 일을 하며, 복사할 상자, Download 버튼, 가져올 때 쓰는 파일 선택기가 있습니다. 잘못된 입력은 이유를 알려 주고("id a가 두 번 나옵니다", "항목 1에 id가 없습니다") 대화 상자는 열린 채로 남습니다. 이 런타임에 없는 노드 유형은 회색 점선으로 들어오고, 가져오기가 어느 것인지 알려 줍니다. 조용히 버려지는 노드가 시끄러운 노드보다 나쁘기 때문입니다.

화면도 그 파일의 일부입니다. 플로가 그리는 대시보드(`ui_tab`, `ui_group`, 위젯)는 플로 안의 노드이므로, 고객의 화면은 Export와 Import를 통해 플로와 함께 이동하며, 어느 것도 HotLoop Flow 자체에 있지 않습니다.

**서브플로는 자기 캔버스에서 편집합니다.** *+ subflow*를 누르면 입력과 출력 포트가 있는 상태로 열립니다. 다른 것과 똑같이 안쪽 노드에 연결하십시오. *Subflow properties*는 이름, 색, 출력 개수, 인스턴스가 설정할 수 있는 속성을 정합니다. 플로에 있는 인스턴스는 모양이 바뀌면 따라가고, 팔레트에는 모든 서브플로가 나열되어 있어 하나를 놓을 수 있습니다. 인스턴스를 더블클릭하면 자기만의 이름과 속성별 값을 줄 수 있습니다. 서브플로는 자기 자신이나 자신을 담은 서브플로 안에 둘 수 없고, 아직 쓰이는 서브플로는 삭제할 수 없습니다. 편집기는 다음 배포가 알아내게 두지 않고 그 자리에서 알려 줍니다.

**선택 영역을 서브플로로.** 노드를 선택하고 *Selection to subflow*를 누릅니다. 노드들이 자기만의 서브플로로 옮겨지고 그 자리에 인스턴스가 들어옵니다. 선택 영역의 경계를 넘던 모든 연결은 포트가 됩니다. 안으로 들어오는 단 하나의 길이 서브플로의 입력이고, 다른 곳으로 가던 선택된 노드의 각 출력은 서브플로의 출력이 되므로 플로는 하던 대로 동작합니다. 서브플로의 입력은 하나이므로, 선택 영역이 서로 다른 두 노드에 연결되어 있으면 그렇게 말하고 아무것도 바꾸지 않습니다. 둘을 둘 다에서 공급하면 다른 플로가 되기 때문입니다. 그룹을 선택하면 그 안의 모든 것과 함께 옵니다. 플로에 속하고 선택 영역만 쓰는 설정 노드는 가리키는 대상과 함께 서브플로로 들어갑니다. 남은 쪽에서도 쓰는 설정 노드는 대신 전역이 되어 양쪽이 같은 연결을 계속 공유합니다. 연결 수를 세는 박스에서 두 번째 브로커 연결이 생기는 것은 우리가 내놓지 않는 종류의 놀라움이기 때문입니다. 옮겨진 노드가 읽고(env 유형, 문자열 안의 `${NAME}` 또는 `$(NAME)`, `env.get`) 플로가 선언한 환경 변수는 플로로 전달하는 서브플로 속성이 되므로, 값은 여전히 원래 있던 곳에서 오고 인스턴스가 덮어쓸 수 있습니다. Ctrl+Z로 전부 되돌립니다.

**플로.** 탭을 더블클릭하거나 *Flow properties*를 눌러 이름을 바꾸거나 삭제합니다. 삭제는 확인을 묻고, 플로의 모든 노드를 함께 지우며, 파일이 허공을 가리키지 않도록 다른 플로에서 그 플로로 오던 연결과 링크를 끊습니다. 삭제된 노드를 이름으로 지정하던 Catch, Status, Complete 범위에서도 그 노드를 뺍니다. 목록 전체가 삭제된 Catch나 Status는 마지막 id를 유지합니다. 빈 목록은 플로 전체를 뜻하므로, 모르는 사이에 노드가 한 가지를 보던 상태에서 전부를 보는 상태로 바뀌게 하지 않습니다. Ctrl+Z는 배포하기 전까지 되살립니다. 마지막 플로는 삭제할 수 없습니다. 플로가 없는 런타임에는 노드를 둘 곳이 없기 때문입니다.

**설정 노드**는 팔레트의 *configuration* 아래에 있습니다. 어느 캔버스에도 놓이지 않으므로 유형을 더블클릭하고 대화 상자를 채우면 *configuration in use* 아래 목록에 추가되며, 더블클릭하면 편집하고 X를 누르면 삭제합니다. 노드가 아직 쓰는 것은 삭제되지 않고 몇 개가 쓰는지 알려 줍니다. 노드 대화 상자의 "Add one from the palette first"가 보내는 곳이 여기입니다.

**연결 삭제.** Alt를 누른 채 클릭합니다. 그냥 클릭하면 아무 일도 일어나지 않으므로, 선택하다가 연결을 스쳐도 플로가 망가지지 않습니다. Ctrl+Z로 되돌립니다.

**지속형 연결.** 연결을 더블클릭하십시오. *Durable*에 체크하면 더 굵은 파란색으로 그려지고, 연결이 출발하는 노드의 파일에 `ew_durable`이 들어갑니다. 표시는 노드 쌍에 있으므로 둘 사이의 모든 연결에 적용됩니다. 런타임에 대한 배선이므로 하나를 표시해도 노드가 재시작되지 않습니다.

**그룹.** Ctrl+G는 선택 영역을 감싸고 Ctrl+Shift+G는 해체합니다. 제목 표시줄을 더블클릭해 이름과 색을 정합니다. 그룹을 끌면 안의 모든 것이 따라갑니다. 노드를 그룹 안으로 끌면 합류하고 밖으로 끌면 떠납니다. 그룹은 중첩할 수 있습니다. 그룹을 삭제하면 안의 것도 삭제되고, Ctrl+Z가 전부 되돌립니다.

**검색**(Ctrl+F 또는 버튼)은 모든 플로와 서브플로를 한꺼번에 봅니다. 이름, 유형, id, 모든 설정, 그리고 함수 본문 중간의 한 줄까지 찾습니다. 결과를 누르면 올바른 탭으로 이동해 노드가 선택되고 화면 중앙에 놓입니다. 설정 노드도 나타나며, 캔버스에 자리가 없으므로 결과를 누르면 대화 상자가 열립니다.

**디버그 필터링.** 사이드바를 플로 하나, 선택한 노드, 단어 하나, 또는 오류만으로 좁힐 수 있습니다. 앞으로 오는 것만이 아니라 이미 로그에 있는 것에도 적용되므로, 좁혀도 보고 있던 줄이 사라지는 일이 없습니다.

이 모든 것은 모든 pull request마다 실제 브라우저에서, 편집기가 내장된 실제 바이너리를 상대로 클릭하며 검증합니다. 런타임이 제공하는 모든 노드 대화 상자가 포함됩니다. 목록이 `GET /nodes`에서 오므로 다음 달에 추가된 노드는 누가 추가하는 것을 기억하지 않아도 다음 달 테스트에 들어갑니다. 이 테스트를 쓰다가 Chromium에서 한 번도 동작한 적이 없던 두 가지를 찾았습니다. 노드를 더블클릭해 대화 상자를 여는 것과, 연결을 노드 위로 끌어 놓는 것입니다. 캔버스가 끌기 내내 포인터를 쥐고 있어서 이벤트의 대상은 늘 캔버스였고, 노드 위에서 놓은 연결은 노드를 찾지 못했습니다. 둘 다 시각 편집기의 버그로는 더없이 민망한 것이었습니다. 둘 다 고쳤습니다.

## 코드로서의 플로

플로를 리뷰하는 곳은 저장소이므로, 저장소가 그것을 배포할 수 있어야 합니다. 플로 파일을 git에 두고, 위의 diff 드라이버를 설정해 pull request가 리뷰처럼 읽히게 하고, 머지가 배포하게 하십시오.

```bash
hotloop-flow export -o flows.json          # the live file, byte for byte, to commit
hotloop-flow deploy -file flows.json -note "PR #12: line 3 pressure check"
```

`deploy`는 실행 중인 것과의 diff를 다른 곳과 같은 텍스트로 출력한 다음, 그 diff를 만든 리비전을 기준으로 배포합니다. 그사이 다른 사람이 배포하면 조용한 덮어쓰기가 아니라 409와 빨간 파이프라인이 됩니다. `-expect-rev`는 리뷰된 계획이 만들어진 리비전에 고정하고, `-dry-run`은 diff를 출력하고 아무것도 배포하지 않습니다. 바꿀 것이 없는 파일은 아무것도 배포하지 않고 히스토리에도 아무것도 추가하지 않으므로, 플로를 건드리지 않은 머지가 로그를 어지럽히지 않습니다. 시작에 실패하는 노드는 배포되고 작업도 실패로 끝납니다. 나머지 플로는 실행 중이고 누군가 살펴봐야 하기 때문입니다. `export -deployment 41`은 히스토리에서 어떤 배포든 꺼냅니다.

**파이프라인은 관리자 비밀번호를 절대 갖지 않습니다.** API 토큰을 받습니다.

```bash
hotloop-flow token -name ci
```

토큰을 한 번 출력해 pipeline 시크릿 저장소에 넣게 하고, 런타임에 줄 해시를 출력합니다. 배포 토큰이면 `HOTLOOP_FLOW_DEPLOY_TOKEN_HASH`, 그 밖의 것은 설정 파일의 `auth.tokens`입니다. 런타임은 비밀번호와 마찬가지로 해시만 보관합니다. 배포 토큰은 플로를 읽고 배포할 수 있으며 롤백도 포함하고, 그 밖에는 아무것도 못 합니다. 설정, inject, 편집기는 안 됩니다. 두 명령 모두 토큰을 `HOTLOOP_FLOW_TOKEN`(또는 `-token-file`)에서, 인스턴스를 `HOTLOOP_FLOW_URL`(또는 `-url`)에서 읽으며, 명령줄에 토큰을 쓰는 일은 없습니다. 명령줄에 쓰면 프로세스 목록과 명령을 그대로 출력하는 모든 pipeline 로그에 남기 때문입니다. 히스토리는 토큰을 배포자 `token:ci`로 표시하고, 파이프라인이 넘긴 메모를 함께 보여 줍니다.

자격 증명은 이 방식으로는 절대 이동하지 않습니다. 플로 파일에 들어 있지 않으므로 git에서의 배포는 모든 브로커 비밀번호를 있던 자리에 그대로 둡니다.

## 원하신다면 git 미러

배포 로그는 박스에 있습니다. 저장소는 다른 모든 사람이 이미 보는 곳이며, 웹 보기, blame, 백업, 읽을 줄 아는 사람들이 있습니다. Flow를 저장소에 연결하면 모든 배포가 Flow만 쓰는 브랜치에 플로 파일의 커밋이 되며, **배포한 사람이 작성자**로, 배포한 시각에, 메모가 메시지로 들어갑니다.

```yaml
history:
  git:
    url: https://git.plant.example/line3/flows.git
    branch: main              # one nobody else pushes to
    path: flows.json
    emailDomain: plant.example  # dana deploys, the commit is from dana@plant.example
```

비밀번호는 git 서버의 액세스 토큰이며, 파일이 아니라 Secret에서 `HOTLOOP_FLOW_GIT_PASSWORD`로 들어갑니다(`HOTLOOP_FLOW_GIT_URL`과 `HOTLOOP_FLOW_GIT_USERNAME`도 사용할 수 있습니다). 비밀번호가 들어 있는 URL은 시작할 때 거부되므로 URL은 언제나 로그에 남길 수 있습니다. `http://`와 `https://`만 지원합니다. 이미지에는 `file://`용 git 바이너리도 `ssh://`용 키도 없으며, 푸시마다 실패하는 미러는 시작을 거부하는 미러보다 나쁩니다. 롤백과 시작 기준선은 커밋에서 자신이 무엇인지 밝히고, 모든 커밋은 `Flow-Deployment: N` 트레일러를 가지며, 이것으로 재시작한 프로세스나 클론이 지워진 프로세스가 저장소가 말하는 지점에서 중복 없이 정확히 이어갑니다.

**배포를 절대 붙잡지 않습니다.** 푸시는 자기 고루틴에서 일어납니다. git 서버가 내려가 있거나 느리거나 푸시를 거부해도 배포에는 아무 비용이 없습니다. 커밋은 `data/git-mirror` 아래의 로컬 클론에서 기다리다가 다음에 성공하는 푸시에 나가며, 1분마다 재시도합니다. `GET /deployments`는 미러가 어디까지 갔는지와 마지막 오류를 알려 주고, `hotloop_flow_git_mirror_behind_deployments`가 경보를 걸 숫자입니다. 기본 인증 뒤의 git 자체 smart-HTTP 서버로 테스트했습니다. 배포 세 번이 세 명의 작성자로 커밋 세 개가 되고, 서버가 거부한 푸시는 기다렸다가 거부를 멈추면 따라잡으며, 거절하는 데 10초 걸리는 git 서버에서도 배포는 몇 밀리초 만에 돌아옵니다.

순수 Go(go-git)이므로 바이너리는 정적으로 유지됩니다. 바이너리가 약 3.8 MB 늘어나며, 그래서 추정하지 않고 측정했습니다. 카탈로그 이전 바이너리는 48,083,106바이트였습니다.
