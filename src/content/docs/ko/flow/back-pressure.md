---
title: "백프레셔를 눈에 보이게"
description: "모든 큐에 상한을 두고, 상한에서 일어나는 일의 정책을 정하고, 들어가지 못한 모든 메시지를 OOM 종료로 번지기 전에 그래프로 보여 줍니다."
---

이것이 프로젝트의 전부입니다. 엣지 박스에서 플로 엔진이 보이는 전형적인 장애는, kubelet이 죽일 때까지 조용히 부풀어 오르는 파드이며, 그것이 남기는 로그는 호출기를 들고 있는 사람에게 아무것도 설명해 주지 않습니다. 그래서 메시지나 바이트가 쌓일 수 있는 모든 곳에 상한이 있고, 모든 상한은 우리가 정해 놓고 말하지 않은 제한이 아니라 [Node-RED 호환성](/ko/flow/compatibility/)에 기록된 문서화된 결정입니다.

| 쌓일 수 있는 것 | 막는 것 |
|---|---|
| 노드의 받은 편지함 | 상한(기본 1024)과 네 가지 오버플로 정책 중 하나 |
| 지연 및 속도 제한 큐 | 상한. 넘으면 Catch 노드로 거부됩니다 |
| Trigger 타이머 | 상한 |
| `exec` 출력 | 스트림별 상한. 잘리면 오류가 발생합니다 |
| `exec` 프로세스 | 동시 실행 제한. 넘으면 거부됩니다 |
| 파일 읽기 | 상한이 있으며 줄 단위와 청크 모드가 있습니다 |
| HTTP 요청 본문 | 상한 있음 |
| HTTP 응답 대기 | 제한 시간 후 504 |
| TCP 연결과 프레임 | 한도 있음 |
| WebSocket 전송 큐 | 한도 있음. 느린 클라이언트는 연결이 끊깁니다 |

전역으로 설정하고 노드별로 재정의할 수 있는 오버플로 정책:

| 정책 | 동작 |
|---|---|
| `block` | 보내는 쪽이 `blockTimeout`까지 공간이 생기기를 기다립니다. 백프레셔가 상류로 올라가며, 거의 항상 이것이 맞는 답입니다. |
| `drop-newest` | 도착한 메시지를 버립니다. 집계되고 알림이 갑니다. |
| `drop-oldest` | 큐의 맨 앞이 빠져 자리를 만듭니다. 집계되고 알림이 갑니다. "최신 값만 중요한 경우"에 씁니다. |
| `error` | 전송이 거부되어 Catch 노드로 전달되며, 플로가 결정합니다. |

조용히 버려지는 것은 없습니다. 버려지는 모든 경우가 집계되고, 이벤트로 편집기에 전달되며, 경보를 걸 수 있는 지표로 내보내집니다. 한도에 걸리면 운영자가 아니라 그래프로 알게 됩니다.

## 노드마다 고루틴 하나

모든 노드 인스턴스는 자기만의 고루틴과 받은 편지함을 가집니다. 노드 안에서는 순서대로, 노드 사이에서는 병렬로 동작합니다. 실제 작업을 하는 Function 노드는 코어 하나를 차지하고, 그동안 편집기, API, 웹소켓, 다른 모든 플로는 계속 움직입니다.

## 모든 수신자가 자기 사본을 받습니다

와이어가 갈라지면 반대편의 모든 노드가 메시지의 자기 사본을 받으므로, 각자 메시지가 자기 것이라고 생각하는 두 분기가 서로를 망가뜨릴 수 없고, 같아 보이는 형제 분기와 다르게 동작하는 일도 연결한 순서 때문에 생기지 않습니다. 화요일마다 재현되는 버그인데, 여기에는 없습니다.

공짜는 아닙니다. 작은 메시지(측정값 하나와 토픽)를 복사하는 데 411~453 ns와 680바이트가 들고, 노드 다섯 개의 체인은 복사를 포함해 1.14~1.40 µs마다 메시지 하나를 옮깁니다. 복사가 아픈 곳은 큰 바이너리 페이로드입니다. 1 MiB 버퍼는 수신자마다 128~156 µs와 힙의 1메가바이트가 더 듭니다. 그래서 큰 바이너리 페이로드는 버퍼를 복사하지 않고 공유하는 `ImmutableBytes`로 전달됩니다. **같은 1 MiB 메시지에 250~279 ns와 360바이트입니다.** 파일 노드와 HTTP 노드는 이미 바이너리 페이로드를 이 방식으로 넘기므로 요청하지 않아도 적용됩니다.

## 셀 수 있는 컨텍스트

플로 컨텍스트와 전역 컨텍스트에는 `get`과 `set`이 있고, `CompareAndSwap`, `Increment`, `Update`도 있습니다. 한 카운터에서 get-modify-set을 하는 두 분기는 서로 경쟁하다가 갱신을 잃으며, get과 set만으로는 방법이 없습니다. `Increment`를 쓰면 경쟁할 것이 없습니다.

그리고 재시작을 견딥니다. 플로, 전역, 노드 컨텍스트는 볼륨의 SQLite 파일에 있으며, 범위를 처음 사용할 때 불러오고 나중에 기록하므로, 파드가 돌아오면 플로의 카운터나 래치는 두고 간 그 자리에 있습니다. 원자적 연산은 이전과 같은 코드입니다. 변경은 30초마다 한 번의 쓰기로 묶이고, 이미 그 값이던 것으로 설정하면 아무것도 쓰지 않습니다. 영리해 보이는 것보다 이것이 SD 카드에 미치는 영향이 더 중요하기 때문입니다. 정상 종료는 모든 것을 기록하고, `kill -9`는 최대 그 30초를 잃으며, `store.context.flushInterval`이 그 조절값입니다. 자세한 내용과 카드에 드는 비용은 [docs/durable](/ko/flow/durable-state/)에 있습니다.
