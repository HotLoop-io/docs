HotLoop Flow가 앞으로 무엇이 될지, 만들어지는 순서대로 적었습니다. 이 목록에 없으면 하지 않는 일이니, 필요한 것은 목록에 올려 주세요.

Flow는 HotLoop과 나란히 만들어지며 독립된 제품으로 남습니다. FlowLab과 그 다이어그램인 9단계는 메시지 런타임 옆에 놓이는 별도 팩입니다.

## Flow는 무엇을 위한 것인가

공장 현장을 위한 시각적 플로 엔진입니다. 모든 배포는 비교되고, 테스트되고, 클릭 한 번이면 되돌릴 수 있습니다. 새벽 3시에 무언가 틀어졌을 때 메시지가 어떤 경로로 갔고 홉마다 어떤 모습이었는지 정확히 볼 수 있습니다. 정적 바이너리 하나로 실행되며 Pi에 올릴 만큼 작고, 센서가 수다스러워져도 무너지지 않습니다.

기존 `flows.json`도 바꾸지 않고 그대로 읽습니다. 그것은 기능일 뿐, 핵심은 아닙니다.

아래 모든 항목이 지키는 규칙은 다음과 같습니다.

- 스텁은 없습니다. 만들어지지 않았거나, 실제 대상으로 테스트되지 않았거나, 동작하지 않으면 체크하지 않습니다.
- 장비에 명령을 내릴 수 있는 것은 모두 거부할 수 있는 게이트를 거치며, 거부하면 이유를 알려 줍니다.
- 아무것도 조용히 버려지지 않습니다. 모든 폐기, 거부, 넘침은 집계되어 메트릭에 나타납니다.
- 플로 파일은 바이트 단위로 그대로 불러오고 저장됩니다. 새 데이터는 다른 도구가 무시하는 키에 담기고, 왕복 테스트는 그런 데이터를 담은 파일까지 다룹니다.

### 0단계: 사실대로 말하기

README에는 코드가 뒷받침하지 못하는 주장이 있습니다. 새로운 약속을 하기 전에 먼저 바로잡습니다. 한 번 거짓말한 README는 그 뒤로 늘 거짓말처럼 읽히기 때문입니다.

- [x] WASM 샌드박스는 실제로 있고 테스트도 되었지만, 이를 쓰는 노드가 없고 바이너리에도 들어 있지 않습니다. 6단계에서 사실이 될 때까지 그렇게 밝힙니다
- [x] 존재하지 않는 내장 컨텍스트 저장소를 가리키는 코드 주석이 두 곳 있었습니다. 삭제했습니다
- [x] 유휴 상태와 부하 상태의 메모리를 같은 장비에서 같은 방식으로 다시 측정하고, 수치와 함께 그 명령을 공개하며, 아무도 재현할 수 없는 수치는 뺍니다
- [x] CVE-2025-41656은 다른 플로 엔진을 인증을 끈 채로 출하한 벤더의 문제이며, 그 엔진 자체의 CVE가 아닙니다. README와 `docs/compatibility.md`의 `exec` 행에서 출처를 바로잡습니다
- [x] README 첫머리를 Flow가 하는 일 중심으로 다시 씁니다. 기존 플로 가져오기는 아래쪽 별도 절로 옮기고, 바이트 단위 왕복과 `hotloop-flow import`를 증거로 둡니다
- [x] 배포 문서는 한 회사의 App Store가 아니라 Kubernetes, Podman, Quadlet을 다룹니다
- [x] 테스트가 없던 패키지의 테스트: `api`(로그인, 권한, 오래된 배포에 대한 409), `config`(README에 적힌 모든 시작 거부), `cmd`(배포는 이전 런타임을 멈추기 전에 플로 파일을 씁니다), 그리고 역시 테스트가 없던 Function 노드의 샌드박스인 `js`

### 1단계: 기록, 비교, 롤백

모든 배포는 하나의 기록입니다. 누가, 언제, 메모, 정확한 바이트, 무엇이 바뀌었는지가 남습니다. 라인이 멈춘 뒤 누구나 가장 먼저 묻는 것이 "무엇이 바뀌었고, 누가 바꿨고, 되돌려 줘"인데, 지금은 그 답이 `.bak` 파일 세 개입니다.

- [x] 배포 로그: 모든 배포는 사용자, 시간, 선택 메모, 플로 바이트, 당시의 암호화된 자격 증명을 담은 불변 기록입니다. 보존 기간은 설정으로 정합니다. `GET /deployments`
- [x] 의미 단위 비교: 노드별, 속성별로 비교합니다. 추가, 제거, 변경, 재배선을 구분합니다. 노드를 끌어 옮기면 로직 변경이 아니라 레이아웃으로 표시됩니다. API와 `hotloop-flow diff a.json b.json`으로 사용합니다
- [x] 이 비교는 git difftool로도 동작하므로, 플로에 대한 풀 리퀘스트가 JSON 덩어리 대신 "규칙 2 임계값 7.5에서 8.0으로"처럼 읽힙니다
- [x] 롤백: 이전 기록을 새 기록으로 다시 배포하며 자격 증명도 함께 복원하므로, 삭제했던 노드가 브로커 비밀번호와 함께 돌아옵니다. 기록은 추가만 가능한 상태로 남습니다
- [x] 편집기: 기록 패널, 캔버스에 그려지는 비교, 메모를 남기는 "검토 후 배포", 롤백 버튼. 배포 충돌이 나면 예/아니오 상자 대신 다른 사람이 무엇을 바꿨는지 보여 줍니다
- [x] 코드로서의 플로: CI/CD용 `hotloop-flow deploy`와 `hotloop-flow export`, 그리고 배포 전용 토큰이 있어 파이프라인이 관리자 비밀번호를 쥘 일이 없습니다
- [x] 선택형 git 미러: 모든 배포를 배포한 사람을 작성자로 하는 커밋으로 푸시합니다. 순수 Go이며 바이너리 크기 검사도 계속 통과합니다
- [x] 감사 로그: 로그인, 로그인 실패, 배포, 롤백, 주입을 각각 누가 어디서 했는지와 함께 남깁니다. 배포 로그가 그 첫 번째 테이블입니다
- [x] MFA(TOTP), 무료이며 원하는 사람은 누구나 켤 수 있습니다. 안전하게 로그인하는 일은 어떤 것도 유료로 막지 않습니다. 앞으로도 마찬가지입니다
- [x] 로그인 속도 제한과 잠금, 재시작 후에도 유지되는 세션, 그리고 URL 대신 서브프로토콜로 보내는 웹소켓 토큰. URL의 토큰은 기존 스크립트를 위해 계속 동작하며 경고를 남깁니다. 업그레이드에서 스크립트가 깨지는 것이 유출보다 나빴기 때문이며, 제거는 메이저 릴리스까지 기다립니다

### 2단계: 플로 테스트

"내 변경이 라인을 망가뜨렸나?"에는 배포 후가 아니라 배포 전에 답합니다. 테스트는 플로 옆에 놓인 YAML이라서, 같은 방식으로 비교하고 검토할 수 있습니다.

- [x] `hotloop-flow test`: 실제 런타임과 실제 노드를 프로세스 안에서 실행합니다. 메시지를 주입하고, 포트에서 기한 안에 나오는 것을 기대하거나, 아무것도 나오지 않기를 기대하거나, 오류가 Catch에 도달하기를 기대합니다. CI/CD용 JUnit 출력이 있습니다
- [x] 가상화된 I/O: 테스트 안의 MQTT out, 데이터베이스 쓰기, HTTP 요청은 보냈을 내용을 기록만 하고 네트워크에는 닿지 않습니다
- [x] 가상 시계: 5분짜리 Delay가 몇 밀리초 만에 실행되며, 모든 타이밍 노드가 이를 기준으로 검증됩니다
- [x] 컨텍스트와 자격 증명 픽스처, 그리고 이후 컨텍스트에 대한 검증. 한 테스트가 다른 테스트가 남긴 것에 기대지 못합니다
- [x] 배포 게이트: 켜 두면 테스트에 실패한 배포는 실패한 검증과 함께 거부되고, 이미 실행 중인 플로는 영향을 받지 않습니다
- [x] 편집기: 캡처한 디버그 메시지를 클릭 두 번으로 테스트로 바꾸고, 편집기에서 스위트를 실행하며, 노드에 통과와 실패를 표시합니다

### 3단계: 추적과 재생

- [x] 디버그 메시지를 클릭하면 캔버스에 그 메시지가 지나간 경로가 켜지고, 분할, 합류, 서브플로를 거치며 홉마다 소요 시간과 페이로드가 표시됩니다
- [x] 한정된 추적 버퍼. 백만 건의 메시지 소크 테스트에서도 메모리가 일정하게 유지되며, 그 수치를 공개합니다
- [x] 캡처한 메시지를 플로 초안에 재생하고 출력을 비교합니다
- [x] 캡처한 추적이 2단계의 테스트가 됩니다
- [x] OpenTelemetry 내보내기, 실제 콜렉터로 검증했습니다

### 4단계: 지속형 상태

히스토리언이 한 시간 멎는다고 한 시간치 측정값을 잃어서는 안 됩니다.

- [x] SQLite 기반 영속 컨텍스트: 순수 Go에 cgo가 없고, 원자적 연산(비교 후 교환, 증가, 갱신)을 갖췄습니다. 지금은 컨텍스트용, 다음은 지속형 큐용으로 저장소를 둘이 아니라 하나로 씁니다. 현재는 재시작할 때마다 플로와 글로벌 컨텍스트가 사라지는데, 누군가 가장 먼저 겪을 가능성이 큰 공백입니다. 30초마다 한 번의 트랜잭션으로 지연 기록하며, 이미 같은 값으로 설정된 값은 쓰지 않습니다
- [x] 지속형 와이어: 와이어를 지속형으로 표시하면 그 큐가 막히거나 버리는 대신 같은 저장소로 넘쳐 흐릅니다. 재시작 후에도 남고, 순서를 지키며, 디스크 할당량을 따르고, 깊이는 메트릭으로 나옵니다. 플로 파일에는 `ew_durable`로 표시되므로 왕복은 바이트 단위로 그대로입니다. 편집기에서 와이어를 더블클릭하면 표시됩니다
- [x] 저장 후 전달을 가장 험한 방식으로 검증했습니다. 일정한 입력 아래에서 실제 InfluxDB를 10분간 죽였다가 되살리고 행을 셉니다. 빠진 것도 겹친 것도 없었습니다. 그다음 큐가 찬 도중에 런타임을 kill -9로 죽이고 다시 셉니다. 스크립트, 개수, 시간당 디스크 쓰기는 [durable/](/ko/flow/durable-state/)에 있습니다
- [x] 실제 Pi 5에서 검증: 메모리, 시작 시간, 지속 처리량은 [docs/bench](/ko/flow/benchmarks/#raspberry-pi-5-결과)에 있으며, 나타난 스로틀링도 함께 적혀 있습니다
- [ ] Pi 4와 Zero 2 W에서의 검증, 그리고 카드에서의 시간당 SD 카드 쓰기량. SD 카드를 갉아먹는 컨텍스트 저장소는 버그이기 때문입니다. 보드가 필요해서 열려 있습니다. Pi 5는 측정했고, 다른 장비의 수치는 지어낸 수치가 됩니다

### 5단계: 공장 현장

`scan`은 지금 PLC를 찾아내지만 팔레트의 어떤 것도 그와 통신하지 못합니다. 공장을 위해 만든 제품에서 가장 큰 구멍입니다.

- [x] Modbus TCP 읽기와 쓰기
- [x] OPC UA 읽기, 구독, 쓰기
- [x] S7 읽기와 쓰기
- [x] Sparkplug B, 에지 노드와 호스트 양쪽 모두
- [x] EtherNet/IP 읽기와 쓰기
- 모두 시뮬레이터입니다. 이 중 어느 것도 실제 Siemens CPU나 Logix 컨트롤러 앞에 놓인 적이 없습니다
- [x] HotLoop 노드: 엔티티 변경 수신, 엔티티 상태, 스크립트 호출, 레시피 적용. 모든 명령은 HotLoop의 쓰기 게이트를 거쳐 `flow:<node id>`로 로그북에 남으며, 게이트가 거부한 쓰기는 게이트가 밝힌 이유와 함께 Catch 노드에 도착합니다
- [x] HotLoop이 있으면 Flow의 장비 쓰기는 PLC로 곧바로 가지 않고 HotLoop의 게이트를 거칩니다. 둘 다 2.3.0에 포함되어 출하되었습니다. 실제 게이트를 통한 쓰기는 공개된 HotLoop 이미지를 상대로 Modbus에서 검증했습니다. OPC UA, S7, EtherNet/IP 쓰기 노드는 같은 코드로 보내며, 각각이 게이트를 제공하는지 테스트가 확인합니다.

### 6단계: npm 없는 플러그인

- [x] 이미 있는 호스트 위의 `wasm` 노드: 메모리 상한과 타임아웃이 엄격하며, 둘 중 하나를 넘는 게스트는 다른 것에 영향을 주지 않고 트랩에 걸립니다
- [x] 플러그인 형식: 모듈, 편집기가 대화 상자를 그리게 하는 기술자, 그리고 서명. 서명되지 않았거나 변조된 플러그인은 로드를 거부하고 이유를 알려 줍니다
- [x] 기능 권한: 플러그인은 매니페스트가 요청하고 운영자가 허용하지 않으면 호스트에 접근하지 못합니다. 허용되지 않은 것을 요청하면 배포가 실패합니다

### 7단계: 타입이 있는 와이어와 MCP

- [x] `json` 노드의 스키마 검증, 첫 번째 단계
- [x] 포트의 선택형 스키마. 편집기가 볼 수 있는 불일치는 배포에서 거부되고, 볼 수 없는 불일치는 잘못된 필드의 경로와 함께 Catch 노드와 메트릭으로 갑니다
- [x] 편집기에서 와이어 위에 타입을 표시합니다
- [x] 도구로서의 플로: tool 노드가 이름, 설명, 입력 스키마를 선언하면 Flow가 `/mcp`를 제공합니다. 플로를 호출하는 에이전트는 사람과 같은 권한과 같은 감사 로그를 갖습니다
- [x] MCP 클라이언트 노드: 플로가 HotLoop을 포함한 다른 서버의 도구를 호출할 수 있습니다
- [x] Flow 자체의 MCP 도구: 플로를 나열, 읽기, 배포, 롤백하고, 배포 목록을 보고, inject 노드를 누릅니다. 관리자 API의 핸들러를 그대로 거치므로 같은 권한, 같은 배포 검사, 같은 감사 기록이 적용됩니다. 플로 작성자가 연결해 둔 것만 호출할 수 있는 MCP로는 Flow 자체를 읽거나 쓸 수 없기 때문입니다
- [x] 다이어그램과 계측기를 위한 Flow 자체의 MCP 도구: 다이어그램 나열과 읽기, 실행과 정지, 디버거 조작, 패널의 컨트롤 설정, 중단점과 프로브 설정, 하위 다이어그램 만들기, 계측기의 쓰기 읽기와 전환. 각각은 관리자 경로를 그 경로가 요구하는 권한(`status.read`, `diagram.run`, `instrument.write`)으로 자체 핸들러를 거쳐 실행합니다. 지금까지는 다이어그램 경로에 도구가 없어서 에이전트가 다이어그램을 배포할 수는 있어도 실행할 수는 없었습니다. 이제 모든 관리자 경로는 도구이거나, 사람이 해야 한다고 테스트에 명시되어 있으며, 새 경로가 도구 없이 추가되면 테스트가 실패합니다. 스테이션, 페일오버, 추적 도구를 포함해 이제 도구는 44개입니다

### 8단계: Astro로 다시 쓴 편집기

끝났고, 앞당겼습니다. 원래는 마지막이었지만 Flow의 첫 스크린샷보다 앞으로 옮겼습니다. 다른 회사에서 나온 것처럼 보이는 편집기로 첫 화면을 보게 해서는 안 되기 때문입니다.

HotLoop의 모든 프로젝트가 하나의 현대적인 UI를 갖게 되고, 이 편집기가 맞지 않던 하나였습니다. 네이티브 SVG 위에 손으로 만든 바닐라 TypeScript였고, 감사할 것이 없는 작은 정적 바이너리가 목표였을 때는 옳은 선택이었습니다. 지금은 Svelte 아일랜드를 쓰는 Astro이며, Cascade 편집기와 같은 스택에 같은 HotLoop 토큰을 쓰고 라이트와 다크를 모두 지원합니다.

- [x] Astro 코드를 한 줄 쓰기 전에 먼저 디자인 작업. 편집기가 HotLoop의 나머지와 나란히 놓였을 때 어떤 모습과 느낌이어야 하는지를 종이와 공유 토큰으로 확정해, 재작성이 하면서 정하는 일이 아니라 이미 정해진 것을 만드는 일이 되게 합니다
- [x] 캔버스, 대화 상자, 기록, 검토, 테스트, 추적, 검색, 그룹을 모두 가져와 Astro로 다시 만든 편집기. 어느 하나도 나빠지면 안 됩니다. `web/e2e`의 브라우저 테스트가 기준이며, 새 편집기에서 수정 없이 통과합니다
- [x] 여전히 정적 바이너리 하나에 내장되고, 에지 장비에서도 네트워크가 필요 없으며, 바이너리 크기 예산 안에 있고, 라이선스 게이트는 번들에 담긴 모든 것을 계속 다룹니다

캔버스와 그 아래의 그래프는 다시 쓰지 않았습니다. 원래의 TypeScript 그대로 `web/src/lib`로 옮겨 새 겉모습을 입혔으므로, 배선, 끌기, 실행 취소, 바이트 단위의 플로 파일 왕복은 이미 테스트된 코드입니다. 그 주변은 모두 Svelte입니다.

이 모든 과정에서도 Flow는 독립된 제품으로 남습니다. HotLoop과 모양은 공유하지만 코드는 공유하지 않으며, HotLoop에 내장되는 일은 없습니다.

### 9단계: FlowLab, 다이어그램

탭을 실행하는 두 번째 방식으로, 메시지 방식 옆에 놓이며 그것을 대신하지 않습니다. 다이어그램에서는 연결된 입력이 모두 값을 가졌을 때 모든 노드가 한 번 실행되고, 서로 와이어로 이어지지 않은 분기는 동시에 실행됩니다. 시험대나 데이터 로거에 필요한 것이 바로 그것입니다. 한 패스에서 다음 패스로 값을 넘기는 루프, 자기만의 와이어로 이동하는 오류, 운영자가 휴대폰으로 열 수 있는 패널, 실행을 멈추고 모든 와이어 위의 값을 보여 주는 디버거가 있습니다. 기존 플로는 바뀌지 않으며 플로 파일은 여전히 바이트 단위로 그대로 불러오고 저장됩니다. 다이어그램은 `ew_diagram` 키를 가진 탭이고, 와이어가 어느 입력에 닿는지는 와이어가 떠나는 노드의 `ew_in`에 보관됩니다. 나머지는 [FlowLab](/ko/flow/flowlab/)에 있습니다.

- [x] 스케줄러: 연결된 모든 입력이 준비되면 실행, 독립된 분기는 병렬 실행, 데이터가 흐르지 않는 곳의 순서를 위한 `after` 와이어
- [x] 값을 이어받는 while과 for 루프, 그리고 오류 이후의 노드를 건너뛰고 루프를 멈추며 그 출처와 코드를 싣는 오류 와이어
- [x] 시리얼 포트: 종결 문자나 바이트 수까지 읽기, 오류 와이어로 가는 타임아웃, 케이블이 뽑힌 뒤 다시 열리고 그 횟수가 집계되는 포트
- [x] 측정값 파서, 안정값 감지, 시간 열이 있는 텍스트 로그
- [x] Flow가 제공하는 패널: 컨트롤, 표시기, 차트나 그래프가 실행 중에 휴대폰에서 열리고, 데스크톱의 두 번째 관찰자도 1초 안에 실행을 따라갑니다
- [x] 실행, 정지, 실행 강조, 모든 와이어의 프로브, 노드와 와이어와 패스의 중단점, 스텝 인, 오버, 아웃
- [x] 편집기는 이름 붙은 포트를 그리고, 놓은 곳의 포트로 와이어를 잇습니다. 같은 페이지에서 실행하고 디버그합니다
- [x] 케이스 구조, 레코드와 공유 타입, 파형
- [x] TDMS와 바이너리 로깅, 그리고 데이터베이스와 MQTT out
- [x] 계측기 세션: 원시 소켓과 시리얼을 통해, 시뮬레이터와 pty를 상대로 검증했습니다
- [ ] NI의 자체 서버를 상대로 검증한 데이터 수집 클라이언트. 만들어서 출하했고 대역 서버로만 테스트했으므로, NI의 서버와 장치를 상대로 실행해 볼 때까지 열어 둡니다
- [x] 분석: 통계와 필터
- [x] 하위 다이어그램, CI/CD의 오류 목록, 편집기의 확대와 레이아웃 작업
- [x] 끝난 실행의 재생: 모든 노드의 시작과 종료, 모든 와이어의 값이 기록되며, 다이어그램 바가 마지막 실행을 캔버스에서 다시 재생합니다. `GET /diagrams/{id}/trace`, `get_diagram_trace` 도구
- [x] 데이터베이스가 놓친 것을 보관하는 데이터베이스 싱크: `postgres out`, 지속형이며 데이터베이스가 돌아오면 순서대로 배치로 기록됩니다. 실제 TimescaleDB로 검증했습니다
- [x] 하나의 플로 파일, 곧 다이어그램 한 벌을 테넌트가 EmberNet에서 운영하는 모든 Flow 설치에 밀어 넣고, 각각 확인하며, 실패한 곳은 되돌립니다([테넌트 스테이션으로 푸시하기](/ko/flow/stations/)). 실제 Flow 프로세스 세 개로 검증했습니다
- [ ] Pi에서 하루 동안 검증. 보드와 긴 실행이 필요합니다

## 일상의 빈틈

이것들은 여러 단계와 나란히 진행됩니다. 이것이 있어서 플로 엔진을 고르는 사람은 없지만, 없어서 버리는 사람은 많습니다.

- [x] 부분 배포: 바뀐 노드와 그 와이어만 다시 시작합니다. 지금은 저장할 때마다 모든 MQTT 세션과 처리 중인 메시지가 모두 끊겨서, 운영자가 근무 시간에는 배포하지 않게 됩니다
- [x] JSONata, 공개된 예제로 검증했습니다. 가져온 플로가 가장 흔히 걸리는 부분이기 때문입니다
- [x] 크론 방식의 inject
- [x] Link Call과 Link Out의 반환 모드
- [x] 시간 제한으로 합치기와 reduce, 시간 단위 배치, 분할 스트리밍
- [x] MQTT v5와 유언
- [x] TCP의 TLS, HTTP의 쿠키와 multipart
- [x] 편집기: 복사와 붙여넣기, 선택 영역 가져오기와 내보내기, 서브플로와 그룹 편집, 플로 전체 검색, 디버그 필터링
- [x] 첫 작업이 남긴 편집기의 빈틈: 팔레트에서 설정 노드 추가(대화 상자가 그렇게 하라고 안내하는데 할 수 없었습니다), 선택 영역을 서브플로로 만들기, 플로 이름 바꾸기와 삭제, 와이어를 더블클릭해 지속형으로 표시하기
- [x] 지속형 와이어의 대상이 영영 거부하는 메시지의 탈출구: 와이어별로 선택하는 시도 횟수 제한. 그 횟수만큼 거부되면 메시지는 첨부된 채로 플로의 Catch에 오류로 전달되고 와이어는 다음으로 넘어갑니다. 기본은 꺼져 있어서, 와이어는 이전과 똑같이 붙들고 재시도합니다
- `store.*`는 지속형 작업에서 이미 있었고 이제 같은 검사를 받습니다
- [x] 파일에 없는 설정 노드를 가리키는 노드(서브플로, 손 편집, 가져오기가 여전히 그 이름을 가리키는 상태에서 자체 브로커와 함께 삭제된 플로)는 `hotloop-flow import`, 로드와 배포 시의 편집기, 배포 응답에서 보고되며, 그 노드는 조용히 동작하지 않는 노드가 아니라 시작 실패가 됩니다
- [x] 그것이 남긴 빈틈: 탭, 서브플로, 그룹, 일반 노드, 또는 잘못된 종류의 설정 노드를 가리키는 설정 참조도 아무것도 가리키지 않는 것과 똑같이 보고되고 시작에 실패하며, 롤백은 파일의 경고를 편집기 로그에 두 번이 아니라 한 번만 남기고, `hotloop-flow import`는 `deploy`처럼 보고서를 라이터에 쓰므로 테스트가 표준 출력을 바꿔치기할 필요가 없습니다
- 업스트림에는 아직 그 줄이 남아 있습니다. 그쪽에 변경을 받아 달라고 요청하지는 않았습니다
- [x] 지속형 와이어 퍼지 테스트가 큐에 있다고 샘플링한 것보다 하나 더 많이 버려진 것으로 셀 수 있었습니다. 틀린 것은 큐가 아니라 테스트였습니다. 디스크에 30건 중 28건이 오기를 기다린 다음 스풀이 마지막 몇 건을 세는 중인데도 퍼지가 본 것과 정확히 같아야 한다고 요구했습니다. 와이어가 사라질 때 30건 중 몇 건이 디스크에 있는지는 타이밍에 달려 있으므로, 이제는 본 것을 하한으로, 보낸 30건을 상한으로 삼습니다
- [x] 지속형 와이어 kill 테스트는 로컬에서는 통과하고 느린 러너에서는 실패했습니다. 큐가 메시지를 디스크에 쓰기 전에 대기 중으로 세었으므로, 카운트가 100에 닿는 순간 가져간 복사본에서 하나가 모자랄 수 있었습니다. 이제는 커밋 후에 셉니다
- [x] 편집기, 노드 설명, 대시보드 페이지가 영어 외 13개 언어로 제공되며 하나의 공통 용어집을 씁니다
- [x] Kafka out, 그리고 ntfy, gotify, discord out. 코어가 이미 가진 알림 설정을 그대로 씁니다
- [x] InfluxDB로 가는 지속형 와이어는 최대 256건씩 배치로 따라잡으므로, 한 시간치 밀린 데이터가 몇 분이 아니라 몇 초 만에 빠집니다
- [x] 플랜트 이전에 필요한 Node-RED 커넥터 노드(네트워크 인터페이스의 Modbus 서버, 이메일, postgres, 대시보드 노드)를 네이티브로 실행합니다
- [x] 스테이션으로 푸시하기 위한 차트 값과 렌더 검사
- [x] 참조로 관리하는 시크릿: 노드가 마운트된 Kubernetes Secret이나 파일에서 비밀번호를 읽으므로, 플로 파일에는 아예 들어가지 않습니다
- [x] 내 플로 가져오기: `hotloop-flow import`는 무엇이 실행되고 무엇이 실행되지 않을지를 배포 전에 정확히 보고합니다. 실행되는 노드 유형, 차이가 있게 실행되는 노드와 그 차이, 시작되지 않을 노드, 그리고 파일에 없는 설정 노드를 가리키는 노드를 나열합니다

## 이후

- [x] 액티브/스탠바이: 펜싱 번호가 있는 PostgreSQL의 리스, 장비에 쓰는 모든 쓰기에 걸리는 펜스, 리스를 넘겨받기 전까지 쓰기를 붙들고 있는 스탠바이([리스를 쓰는 웜 스탠바이](/ko/flow/failover/)). 실제 Flow 프로세스 두 개를 실제 PostgreSQL과 모든 쓰기를 기록하는 Modbus 서버에 붙여 검증했습니다. 스트림 도중 종료, 정지 후 해제, 정상 종료 모두에서 양쪽이 쓴 경우는 없었습니다. 컨텍스트는 Postgres가 아니라 각 설치의 디스크에 남으며, 이는 첫 구상이었지만 두 쓰기 주체를 떼어 놓는 데는 필요하지 않았습니다
