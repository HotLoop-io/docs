EmberNet의 테넌트는 공장이나 라인마다 하나씩, HotLoop Flow 설치본을 여러 개 운영할 수 있습니다. 이 각각을 스테이션이라고 부릅니다. 이 페이지는 플로 파일 하나, 곧 FlowLab 다이어그램 한 벌을 모든 스테이션에 올리고, 각각을 확인하고, 실패한 스테이션을 되돌리는 방법을 설명합니다.

요약하면 `hotloop-flow stations push -tenant acme -file flows.json`은 EmberNet이 `acme`에 대해 실행 중으로 표시하는 스테이션에 한 곳씩 푸시합니다. 이후 스테이션이 정상이 아니면 그 스테이션은 이전 상태로 돌아가고 푸시는 멈춥니다. 파일이 실행 중인 로거를 재시작시킨다면, 허용한다고 말하기 전에는 아무 일도 일어나지 않습니다.

## 스테이션은 어디서 오는가

스테이션은 아무도 직접 입력하지 않습니다. 목록은 EmberNet 대시보드가 테넌트에 대해 실행 중으로 표시하는 것, 즉 Running Apps 페이지와 같은 목록입니다. `hotloop-flow` 레이블이 붙어 있고 실행 중이며 테넌트에 속한 모든 앱입니다. 스테이션은 대시보드가 Flux 주소를 알려 주면 그 주소로, 아니면 클러스터 주소로 접속하므로, 그 주소가 해석되는 곳에서 푸시를 실행하십시오.

테넌트는 항상 지정하며, 푸시는 언제나 그 테넌트 하나만 대상으로 합니다. 대시보드에는 대시보드 토큰으로 질의하고 볼 수 있는 테넌트로 제한되며, 우리는 응답을 다시 확인합니다. 다른 테넌트로 도착한 행은 버려지고 집계될 뿐 사용되지 않습니다. 실행 중인 Flow가 없는 테넌트는 오류로 응답합니다.

## 명령

```bash
hotloop-flow stations list -tenant acme
hotloop-flow stations push -tenant acme -file flows.json -note "new line 3 logger"
```

대시보드 주소는 `-dashboard` 또는 `HOTLOOP_FLOW_DASHBOARD_URL`에서, 그 토큰은 `-dashboard-token-file` 또는 `HOTLOOP_FLOW_DASHBOARD_TOKEN`에서 가져옵니다. 스테이션이 받아들이는 토큰은 `hotloop-flow deploy`와 같이 `-token-file` 또는 `HOTLOOP_FLOW_TOKEN`에서 가져옵니다. `hotloop-flow token`으로 만들고, 각 스테이션에 `flows.read`, `flows.write`, `status.read`를 가진 API 토큰으로 그 토큰을 주십시오(일반 배포 토큰에는 앞의 둘만 있습니다). 확인 단계에서 각 스테이션의 다이어그램을 읽어야 하는데 일반 배포 토큰으로는 읽을 수 없기 때문입니다. 한 테넌트의 스테이션은 같은 토큰을 사용합니다.

| 플래그 | 기능 |
|---|---|
| `-dry-run` | 모든 스테이션을 계획만 하고 아무것도 바꾸지 않습니다. 현재 운영 중인 내용, 각 스테이션이 재시작할 것, 계획할 수 없었던 스테이션을 보여 줍니다. |
| `-confirm-restart` | 실행 중인 로거가 이 푸시로 재시작될 수 있음에 동의합니다. |
| `-window 02:00-04:00` | 재시작에 미리 동의한 시간대로, `-window-zone`(IANA 이름, 생략하면 UTC)에서 해석됩니다. 이 시간대 안의 푸시는 진행됩니다. `22:00-02:00`처럼 자정을 넘길 수 있습니다. |
| `-settle 5s` | 확인 단계에서 스테이션의 다이어그램을 실행 중이 아닌 것으로 판정하기 전까지 시작에 주어지는 시간. |
| `-json` | JSON 형식의 보고서. |

종료 코드 0은 모든 스테이션 완료입니다. 3은 스테이션이 실패해 푸시가 멈췄음을 뜻합니다. 4는 푸시가 재시작에 대한 동의를 기다리고 있다는 뜻입니다. 5는 응답하지 않았거나 계획할 수 없어서 건너뛴 스테이션이 있다는 뜻입니다.

## 푸시가 하는 일

먼저 아무것도 바꾸지 않고 모든 스테이션을 계획합니다. 각 스테이션에서 현재 플로 파일과 리비전을 읽고, 되돌아갈 수 있는 배포 기록을 찾고, 다이어그램을 나열하고, 파일이 재시작시킬 실행 중인 로거를 가려냅니다. 그다음 동의가 필요한 것이 없으면 이름 순서대로 스테이션을 하나씩 진행합니다.

1. **배포**는 계획이 본 리비전으로 파일을 배포하므로, 그 사이에 다른 사람이 한 배포는 덮어쓰이지 않고 거부됩니다. 바뀐 것만 재시작합니다. 자격 증명은 전송되지 않습니다. 각 스테이션은 자기 비밀번호를 유지하며, 계측기의 쓰기는 그 스테이션의 누군가가 켤 때까지 꺼진 상태로 남습니다.
2. **확인.** 스테이션은 모든 스테이션이 가져야 할 리비전으로 응답해야 합니다. 리비전은 파일의 내용에서 나오므로 같은 파일은 어디서나 같은 리비전이며, 푸시는 시작하기 전에 그것이 무엇인지 알려 줍니다. 파일에서 스스로 시작하는 모든 다이어그램은 스테이션에 문제없이 있어야 하고, 안정화 시간 안에 실행 중이거나 끝나 있어야 합니다. 시작되지 않은 노드도 확인에 실패합니다.
3. **확인에 실패한 스테이션은 되돌립니다.** 원래 있던 배포로 별개의 배포로서 롤백되고, 이전 리비전에 있는지 확인합니다. 푸시는 거기서 멈춥니다.

보고서는 각 스테이션에 무슨 일이 있었는지 알려 줍니다.

| 상태 | 의미 |
|---|---|
| `done` | 배포되었고 확인을 통과했습니다. |
| `unchanged` | 이미 이 리비전이며 다이어그램도 정상입니다. |
| `failed` | 배포되지 않았거나(스테이션이 거부했거나 그 사이에 누군가 배포함), 이미 이 리비전인데 정상이 아닙니다. 아무것도 바뀌지 않았습니다. |
| `reverted` | 확인에 실패해 이전 리비전으로 돌아갔습니다. |
| `revert-failed` | 확인에 실패했고 되돌릴 수 없었습니다. 이 스테이션은 사람이 봐야 합니다. |
| `skipped` | 건드리지 않았습니다. 응답하지 않았거나 현재 리비전의 배포 기록이 없어, 실패한 푸시를 거기서 되돌릴 수 없습니다. 한 번 직접 배포하거나 연결을 고친 다음 다시 푸시하십시오. |
| `not-started` | 이 스테이션 앞에서 푸시가 멈췄습니다. 원래 상태 그대로입니다. |
| `planned` | 드라이 런의 응답. |

건너뛴 스테이션은 푸시를 멈추지 않습니다. 푸시는 반복할 수 있습니다. 이미 그 리비전에 있는 스테이션은 `unchanged`이므로, 두 번째 푸시는 첫 번째가 끝내지 못한 것만 마무리합니다.

## 재시작

스스로 시작하는 다이어그램은 로거입니다. 바뀐 로거를 배포하면 재시작되고, 제거된 로거는 멈춥니다. 실행 중인 로거에 그렇게 하게 될 푸시는 아무것도 건드리기 전에 멈추며, 보고서는 각 스테이션과 각 로거를 알려 줍니다. 그다음 다음 셋 중 하나가 있으면 진행합니다.

- 명령을 터미널에서 실행했을 때 프롬프트에 예라고 답합니다.
- `-confirm-restart`를 지정합니다.
- 시간이 `-window`로 지정한 시간대 안에 있습니다.

이 중 하나가 없으면 아무것도 재시작하지 않습니다. 바뀌지 않은 다이어그램은 실행이 유지되고, 새 다이어그램은 그냥 시작됩니다.

## 인스턴스에서, 그리고 에이전트를 위해

인스턴스는 관리자 API를 통해 자기 테넌트의 스테이션으로 푸시할 수 있으며, MCP 도구 `list_stations`와 `push_to_stations`가 이를 사용합니다. 다음 네 가지를 모두 설정하면(설정 파일의 `stations:` 아래 또는 환경 변수로) `GET /stations`와 `POST /stations/push` 경로가 나타납니다. 설정하지 않으면 이 경로는 존재하지 않습니다.

| 설정 | 환경 변수 | 설명 |
|---|---|---|
| `stations.dashboardUrl` | `HOTLOOP_FLOW_STATIONS_DASHBOARD_URL` | 테넌트의 설치본을 아는 EmberNet 대시보드. |
| `stations.tenant` | `HOTLOOP_FLOW_STATIONS_TENANT` | 이 인스턴스가 푸시하는 단 하나의 테넌트. 요청으로 다른 테넌트를 지정할 수 없습니다. |
| `stations.dashboardTokenFile` | `HOTLOOP_FLOW_STATIONS_DASHBOARD_TOKEN_FILE` | 대시보드 토큰이 든 파일. |
| `stations.deployTokenFile` | `HOTLOOP_FLOW_STATIONS_DEPLOY_TOKEN_FILE` | 스테이션이 받아들이는 배포 토큰이 든 파일. |

차트에서는 `stations.dashboardUrl`, `stations.tenant`, `stations.dashboardTokenSecret`, `stations.deployTokenSecret`이며, 각 Secret에는 토큰 하나가 들어 있고 파일로 마운트됩니다. Podman과 Quadlet에서는 [Flow 배포](/ko/flow/deploying/)의 환경 변수 네 개와 마운트된 시크릿 두 개입니다. 네 개를 모두 설정하거나 하나도 설정하지 마십시오. 일부만 설정한 차트 렌더링은 거부되며, 일부만 설정한 시작도 거부됩니다.

`POST /stations/push`는 `flows.write`가 필요하며 `{flows, note, confirmRestart, window, windowZone, dryRun}`을 받습니다. `flows`를 생략하면 이 인스턴스가 실행 중인 것을 푸시합니다. 같은 보고서에 `ok`를 더해 응답하며, 푸시는 감사 로그에 `stations.push`로 남습니다. `GET /stations`는 `flows.read`가 필요합니다. 동의를 기다리는 푸시는 `needsConfirm`을 true로 응답하고 아무것도 바꾸지 않았으므로, `confirmRestart` 또는 시간대와 함께 다시 보내십시오.

## 검증되지 않은 것

대시보드 목록의 형태는 실제 테넌트의 운영 중인 대시보드에서 읽은 것입니다. 테넌트의 스테이션에 Flux를 통해 푸시해 본 적은 없으므로, 대시보드가 알려 주는 주소가 푸시를 실행하는 위치에서 닿는지는 `stations list`와 `-dry-run`으로 직접 확인하셔야 합니다.
