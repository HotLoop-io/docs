형태가 잘못된 메시지는 가동 중인 라인에서 우리가 가장 원하지 않는 장애입니다. 문자열 `"hot"`으로 도착한 온도, 빠진 `id`, 목록이어야 할 자리에 온 숫자. 아무것도 멈추지 않고 플로는 계속 돌아가며, 하류의 무언가가 조용히 엉뚱한 일을 합니다. Flow는 이 문제에 JSON Schema를 세 단계로 적용합니다.

## `json` 노드의 스키마

`json` 노드의 설정에 스키마를 주면 그 노드가 다루는 모든 값이 스키마에 맞춰 검사됩니다. 맞는 값은 계속 진행합니다. 맞지 않는 값은 Catch 노드로 가고, 와이어를 따라 계속 가지 않으며, 오류는 잘못된 모든 필드를 알려 줍니다.

```
does not match the schema: payload.temp: got string, want number; payload.id: missing property "id"
```

`msg.schemaError`에는 같은 내용이 `{path, keyword, message}` 객체의 목록으로 담겨 있어, 이를 기준으로 라우팅하려는 Catch 노드가 쓸 수 있습니다. 경로는 Change 노드가 쓰는 방식으로 읽습니다. `payload.sensors[2].temp`

노드의 설정에 스키마가 없고 메시지에 `msg.schema`가 있으면, Node-RED의 `json` 노드처럼 그 스키마로 검증합니다. 통과한 메시지는 `msg.schema`가 제거됩니다. 실패한 메시지는 그대로 유지합니다. 둘 다 있으면 설정의 스키마가 우선합니다.

- 스키마는 `$schema`로 다른 드래프트를 지정하지 않는 한 JSON Schema draft 2020-12입니다. 드래프트 4, 6, 7, 2019-09도 받아들입니다.
- 설정의 스키마가 잘못되면 검증기가 알려 주는 이유와 함께 배포가 실패합니다. 잘못된 `msg.schema`는 그 메시지의 오류입니다.
- 스키마는 자기 완결적입니다. 다른 URL이나 파일을 가리키는 `$ref`는 가져오지 않고 거부하므로, 외부로 나갈 경로가 없는 엣지 박스도 다른 박스와 똑같이 동작합니다.
- `format`은 검증기가 아는 형식만 검사하고 나머지는 무시합니다. 대부분의 검증기와 같습니다.
- 스키마가 어디에도 없는 플로는 이전과 완전히 똑같이 동작합니다.

값을 스키마에 맞춰 검사해야 하는 Flow의 다른 모든 부분도 같은 패키지를 씁니다.

## 포트의 스키마

어떤 노드든 자신이 받는 것과 각 출력 포트가 약속하는 것을 선언할 수 있습니다. 노드에 선택 키 두 개를 두며, 둘 다 플로 파일에 있고, 그 파일을 읽는 다른 도구는 둘 다 무시하므로, 이 키를 가진 플로도 바이트 단위로 그대로 왕복합니다.

```json
{"id":"sensor","type":"function","outputs":2,"wires":[["limit"],[]],
 "ew_outSchemas":[{"type":"object","properties":{"payload":{"type":"object",
   "required":["temp"],"properties":{"temp":{"type":"number"}}}}}, null]},
{"id":"limit","type":"switch","wires":[[],[]],
 "ew_inSchema":{"type":"object","required":["topic"]}}
```

`ew_inSchema`는 노드가 받는 것입니다. `ew_outSchemas`는 출력 포트마다 스키마 하나 또는 `null`을 둔 목록입니다. 스키마는 메시지 전체를 설명하므로 페이로드는 `properties.payload`입니다. 밑줄로 시작하는 키, 즉 `_msgid`와 런타임의 다른 내부 관리용 키는 스키마가 보는 대상에서 빠지므로, 닫힌 스키마가 그것들을 적을 필요가 없습니다. `json` 노드의 것과 같은 JSON Schema이며, 같은 패키지가 검사합니다.

**편집기가 볼 수 있는 불일치는 배포에서 거부됩니다.** 와이어 양쪽 끝이 스키마를 선언했고 두 스키마를 모두 만족할 수 있는 메시지가 없으면, 테스트 게이트와 같게 한 바이트도 쓰기 전에 배포가 거부됩니다. 422가 반환되고, 아무것도 재시작되거나 저장되지 않으며, 감사 기록에 이유 `typed wires`와 함께 `deploy.refused`가 남습니다.

```
the deploy was refused because of 1 typed wire problem, and the flows already running are untouched; junction "sensor" (sensor) output 1 -> "limit" (limit): payload.temp: the sender sends string and the receiver takes number
```

증명할 수 있는 것만 거부합니다. 같은 필드의 서로 다른 타입, 반대쪽 끝의 `enum`이나 범위를 벗어난 값, 수신 측이 요구하는데 송신 측의 닫힌 스키마가 배제하는 필드, 송신 측이 항상 보내는데 수신 측의 닫힌 스키마가 거부하는 필드가 그것입니다. 수신 측이 요구하는 필드를 송신 측이 그저 언급하지 않았다면 거부하지 않습니다. 메시지가 그 필드를 담고 있을 수 있기 때문입니다. `$ref`, `allOf`, `anyOf`, `oneOf`, `not`, `if`를 쓰는 스키마는 그 부분에서 다시 따지지 않습니다. 잘못된 거부는 배포를 이유 없이 막고, 증명할 수 없는 것은 어차피 실행 시점에 잡힙니다. 컴파일되지 않는 스키마나 노드의 출력 수보다 긴 `ew_outSchemas`도 같은 방식으로 거부됩니다. 롤백은 검사하지 않으며, 테스트의 관문을 거치지 않는 것과 같은 이유입니다.

**Inject 노드의 리터럴은 타입으로 칩니다.** Inject에는 자체 스키마가 없지만, 확실히 설정하는 값은 스키마만큼 쓸모가 있습니다. Inject가 `ew_inSchema`가 있는 노드에 바로 연결되면, 리터럴 페이로드와 그것이 설정하는 다른 리터럴 속성이 배포 시 그 스키마에 맞춰 검사되고, 수신 측이 절대 받을 수 없는 리터럴은 같은 방식으로 거부됩니다. 같은 422와 감사 기록의 같은 `deploy.refused`가 따릅니다.

```
inject "reading" (i1) output 1 -> "limit" (l1): payload: the inject sets "hot", which the receiver does not take: got string, want number
```

검사하는 것은 리터럴뿐입니다. 문자열, 숫자, 불리언, JSON이 그렇습니다. 타임스탬프, 환경 변수, 플로나 글로벌 컨텍스트, 다른 메시지 속성, JSONata, 버퍼, 정규식은 노드가 실행될 때까지 알 수 없으므로 건너뛰며 추측하지 않습니다. Inject가 설정하지 않는 필수 속성도 충돌이 아닙니다. 정적이지 않은 값이 그것을 설정할 수 있기 때문입니다. Inject에서 노드로 이어지는 와이어만 판단합니다. 다른 노드를 먼저 거치는 리터럴은 실행 시점 검사에 맡깁니다. 편집기도 그 와이어에 같은 충돌을 표시합니다.

**볼 수 없는 불일치는 Catch 노드와 메트릭으로 갑니다.** 노드에 도착해 그 `ew_inSchema`를 어기는 메시지는 노드에 닿지 않습니다. 포트를 떠나며 그 스키마를 어기는 메시지는 송신 측에서 멈추고 전달되지 않습니다. 어느 쪽이든 스키마를 가진 노드의 오류로 발생하고, Catch 노드는 잘못된 모든 필드의 경로를 `msg.error.message`에, 목록으로는 `msg.error.violations`에 받습니다. 각 항목은 `{path, keyword, message}`입니다.

```
the message does not match the schema of output 1: payload.temp: got string, want number
```

`hotloop_flow_node_schema_mismatches_total`은 이를 노드별로 세고, `json` 노드의 불일치도 셉니다. 스키마가 없는 노드는 nil 검사 한 번의 비용이 들고, 스키마가 하나도 없는 플로는 이전과 완전히 똑같이 동작합니다.

## 편집기의 와이어 타입

어느 한쪽 끝에라도 타입이 있는 와이어는 그 타입을 지닙니다. 편집기는 와이어 곡선의 중간에 타입을 적습니다. 송신 측의 타입을 몇 글자(`payload {temp: number}`)로 보여 주고, 와이어에 마우스를 올리면 전체 내용을 보여 줍니다.

- **양쪽 끝이 타입을 선언하고 일치:** 초록 윤곽선과 송신 측의 타입.
- **한쪽 끝만 선언:** 점선에 흐린 색으로, 와이어가 아직 타입이 없는 곳을 알아볼 수 있습니다.
- **양쪽 모두 선언했고 결코 일치할 수 없음:** 와이어와 라벨이 빨갛게 바뀌고 어느 필드인지(`≠ payload.temp`) 알려 주며, 툴팁에는 런타임이 말하는 이유가 있습니다. 배포가 이를 거부하게 되는데, 이제 Deploy를 누르기 전에 미리 볼 수 있습니다.

빨간색은 편집기가 추측한 것이 아닙니다. 편집기는 런타임에 `POST /flows/types`로 물어보며, 이는 배포가 거부할 때 쓰는 것과 같은 검사를 실행하므로 캔버스와 배포가 서로 다른 결론을 낼 수 없습니다. 편집기는 캔버스의 무언가에 스키마가 있을 때, 마지막 편집 직후에만 묻습니다. 스키마가 없는 플로는 호출도 하지 않고 새로 그리는 것도 없습니다.

노드의 대화상자에서 **Types** 아래에 타입을 설정합니다. 입력 스키마 하나와 출력 포트마다 하나입니다. 비어 있으면 타입이 없다는 뜻이고, 타입을 지정한 적 없는 노드에는 키가 생기지 않습니다. JSON이 아니거나 객체가 아닌 것을 쓰면 대화상자에서 거부됩니다.
