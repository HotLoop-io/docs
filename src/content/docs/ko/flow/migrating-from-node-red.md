---
title: "Node-RED 플로를 그대로 가져오기"
description: "Node-RED의 flows.json을 변경 없이 가져오고, 노드별로 무엇에 대응하는지와 Flow가 실행을 거부하는 항목과 그 이유를 확인하세요."
---

Flow는 Node-RED의 `flows.json` v1 형식을 읽습니다. 모든 Node-RED 내보내기와 플로 라이브러리 항목이 쓰이는 평평한 JSON 배열입니다. 파일을 지정하면 그대로 실행됩니다.

**바이트 단위로 그대로 불러오고 저장합니다.** 파일을 불러와 아무것도 수정하지 않고 저장하면 똑같은 바이트가 돌아옵니다. 키 순서, 공백이 같고 이스케이프를 임의로 고쳐 쓰지도 않습니다. 속성 하나를 고치면 노드 전체가 아니라 한 줄만 달라집니다.

Go에서는 보기보다 어렵습니다. JavaScript 객체는 키의 삽입 순서를 유지하므로 JavaScript 런타임은 `JSON.parse`와 `JSON.stringify`에서 누구도 신경 쓰지 않아도 이를 공짜로 얻습니다. Go의 맵에는 순서가 전혀 없고 `encoding/json`은 일부러 키를 정렬합니다. 코드의 모든 읽기 경로에 순서를 보존하는 맵을 강제로 끼워 넣는 대신, 각 항목의 원본 바이트를 보관해 두었다가 분석된 형태가 바뀌지 않았으면 그대로 다시 내보내고, 바뀌었으면 원래 키 순서에 맞춰 다시 인코딩합니다. `json.Compact`와 `json.Indent`는 바이트 수준의 변환이므로 아무것도 재정렬하지 않고 들여쓰기만 바꿉니다.

이것은 두 가지 이유로 중요하며, 둘 다 평범하지만 실제적입니다. 플로 파일은 볼륨과 git에 있으므로 파드가 재시작했다는 이유만으로 달라져서는 안 됩니다. 그리고 운영자가 라인에 배포하기 전에 배포 diff를 검토할 때는 무엇이 바뀌었는지만 보여야 하고 그 밖의 것은 절대 보이면 안 됩니다. 테스트와 타입이 파일에 들어와도 이 규칙은 유지됩니다. 새 데이터는 다른 도구가 무시하는 키에 들어가고, 왕복 테스트가 그런 키를 가진 파일도 검사합니다.

이 빌드가 한 번도 본 적 없는 노드 유형도 불러오기와 저장을 거쳐 모든 속성이 그대로 남으므로, 여기서 플로를 실행하고 나중에 되돌려 주어도 안전합니다. AES-256-CTR로 암호화된 Node-RED의 `flows_cred.json`은 읽기 전용으로 가져오며, 이렇게 읽은 내용은 다음 저장 때 GCM으로 다시 암호화됩니다.

**무엇이든 배포하기 전에 어떤 일이 일어날지 먼저 물어보세요.**

```bash
hotloop-flow import flows.json
```

파일 안의 모든 노드 유형을 보고합니다. 서브플로 안의 것도 포함하며, 지원, 부분 지원(빠진 부분을 명시), 미지원으로 나눕니다. 서브플로의 내부는 파일이 아니라 펼쳐진 그래프를 기준으로 세므로, 인스턴스가 안에 든 것을 말하지 않은 채 "지원"으로 보고되는 일이 없습니다. 책상에서 알게 되느냐, 라인이 멈췄을 때 알게 되느냐의 차이입니다.

노드가 파일에 없는 설정 노드를 가리킬 수도 있습니다. 플로를 삭제하면 그 플로 자신의 MQTT 브로커도 함께 사라지는데, 그 브로커를 쓰던 서브플로는 아무것도 가리키지 않는 id를 계속 가리킵니다. 직접 수정했거나 내보내기를 반쯤만 복사해도 같은 일이 생깁니다. 예전에는 첫 메시지가 노드에 도달했을 때 알게 되었고, 서버를 조회하기만 하는 노드는 그때도 아무 말이 없었습니다. 이제 가져오기 보고서에 이를 위한 섹션이 있어 모든 노드와 찾지 못한 id를 알려 주고, 편집기는 불러올 때 같은 줄을 로그에 남기며, 배포는 그 내용으로 응답하면서 해당 노드를 시작 실패로 표시하고 잘못된 id를 담은 속성을 알려 줍니다. 나머지 플로는 계속 실행됩니다. 사용자가 비활성화한 노드와, 비어 있거나 `true` 또는 `false`로 된 TLS 설정은 실수가 아니므로 보고하지 않습니다.

id가 존재한다고 해서 동작하는 id는 아닙니다. 처음에는 이 점을 놓쳤습니다. 설정이 탭, 서브플로, 그룹, 일반 노드를 가리키거나 MQTT 브로커를 향한 TLS 설정처럼 종류가 다른 설정 노드를 가리키면 같은 보고서와 같은 시작 실패가 나오며, 그 줄에는 id가 실제로 무엇인지와 설정이 어떤 종류를 원하는지가 적힙니다. 편집기는 올바른 종류만 보여 주므로 이는 직접 수정하거나 id를 붙여 넣을 때만 생기며, 바로 그때 문제가 됩니다.

호환성 수준별로 108개 메시지 노드 유형은 완전 호환 12개, 부분 호환 50개, 의도적으로 다른 것 14개, Flow 고유 32개입니다. 모든 노드는 이름이 같은 Node-RED 노드와의 관계를 선언하며, **노드가 부분 호환이라고 하면서 무엇이 빠졌는지 글로 밝히지 않으면 테스트가 빌드를 실패시킵니다.** 90% 호환인데 나머지 10%를 말하지 않는 노드는 눈에 띄게 없는 노드보다 위험합니다. 앞의 것은 플로가 동작하는 것처럼 보이게 하기 때문입니다. 전체 매트릭스는 [Node-RED 호환성](/ko/flow/compatibility/)이며, 손으로 관리하지 않고 레지스트리에서 생성합니다. 손으로 관리하는 호환성 문서는 날짜가 찍힌 거짓말이기 때문입니다.

다른 점은 모두 의도된 것이며 하나하나 그곳에 적혀 있습니다. 분기에서 각 수신자는 자기만의 사본을 받고, `exec` 노드는 허용 목록이 있고 셸이 없으며, 파일 노드는 범위가 제한되고, [백프레셔를 눈에 보이게](/ko/flow/back-pressure/)에 나열된 모든 것에는 상한이 있습니다.

**대부분의 Node-RED 커뮤니티 노드는 여기서 실행되지 않습니다.** 이들은 Node.js가 필요한 npm 패키지이며, Node가 필요한 패키지가 갑자기 동작하는 미래 버전은 없습니다. 작은 크기와 샌드박스를 위해 치르는 대가이며, 반대로 결정하실 수 있도록 분명히 밝힙니다. 서명된 WASM 플러그인은 직접 작성하는 기능에 대한 Flow의 답입니다. [npm 없는 플러그인](/ko/flow/plugins/)을 보세요.

공장이 의지하는 커뮤니티 노드는 다른 문제입니다. Flow는 Node-RED의 Modbus, 대시보드, PostgreSQL, 이메일 유형을 자체 유형 이름으로 Go에서 네이티브로 실행하므로, 이를 쓰는 플로는 변경 없이 불러와 실행되며, 주변 함수 노드가 호출하는 `Buffer`와 `setInterval`도 마찬가지입니다. 무엇이 실행되고, 무엇이 다르고, 무엇이 검증되었는지는 docs/node-red-types.md에 있습니다. 플로 안의 그 밖의 커뮤니티 노드는 유형 이름이 표시된 채 단독으로 실패하고, 나머지 플로는 시작됩니다.

JSONata는 가져온 플로가 걸려 넘어지는 항목의 맨 위였습니다. 동작하지 않는 13가지는 각각의 이유와 함께 테스트에 고정되어 있으며, 그중 열 가지는 여전히 오류를 일으키되 코드만 다릅니다. `$moment`는 아쉬워하게 될 유일한 Node-RED 함수이며, 조용히 실패하는 대신 무엇을 쓰면 되는지 알려 줍니다.

cron으로 예약된 Inject 노드가 그다음이었습니다. 이제 실행되며, Node-RED와 같은 분에 실행됩니다. crontab은 Node-RED의 Inject 노드 안에 있는 스케줄러인 cronosjs 1.7.1의 포트가 읽으며, cronosjs 자체가 만든 22,620번의 실행을 여섯 개 시간대에서 실제 시간 변경 전후로 대조해 검증했습니다. 새벽 2시에 이것이 중요합니다. 봄에 사라지는 시간에 걸리는 교대 시작은 시계가 건너뛰는 순간 실행되고, 가을에 반복되는 시간은 두 번이 아니라 한 번 실행됩니다. 스케줄은 매분 벽시계를 다시 읽으므로, 잘못된 시간으로 부팅했다가 나중에 NTP로 바로잡힌 박스도 몇 시간 늦게가 아니라 올바른 시각에 실행되기 시작합니다.

Link Call은 세 가지 중 마지막이었습니다. 이제 Link Out의 반환 모드와 함께 동작합니다. "이 배치 조회", "이 인터록 확인" 같은 로직을 자기 탭에 한 번만 작성해 모든 라인에서 호출하며, 돌아올 길은 메시지에 스택으로 보관되므로 호출된 플로도 자기 호출을 할 수 있습니다. 돌아오지 않는 호출은 멈춰 있는 대신 제한 시간 후 오류를 일으킵니다. 늦게 도착한 반환도 Node-RED처럼 그대로 나갑니다. 그리고 돌아갈 곳이 없는 반환은 Node-RED가 로그에 남기지만 아무도 읽지 않는 경고 대신 Catch 노드가 보는 오류가 됩니다.
