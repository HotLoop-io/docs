Model Context Protocol을 사용하는 에이전트는 플로를 도구로 호출할 수 있고, 플로는 HotLoop 자체를 포함해 어떤 MCP 서버의 도구든 호출할 수 있습니다. 노드 세 개와 설정 노드 하나로 이를 구현합니다. `mcp tool`과 `mcp result`는 플로를 서비스하고, `hotloop-flow-mcp-server` 연결 위의 `mcp client`는 밖으로 호출합니다. 센서를 대시보드에 연결하기만 한다면 이 내용은 건너뛰어도 됩니다. 이 노드를 하나도 쓰지 않는 플로는 MCP 호출을 전혀 하지 않으며, Flow가 자체적으로 제공하는 도구는 플로를 읽고 바꾸는 도구뿐입니다([아래](#flow-자체-도구)).

프로토콜은 Go SDK(`github.com/modelcontextprotocol/go-sdk` v1.8.0, 허용적 라이선스이며 프로젝트가 라이선스 변경을 마무리하는 동안 일부 파일은 아직 MIT이고 MCP 프로젝트가 유지 관리)의 것입니다. 핸드셰이크가 없고 모든 요청에 버전을 싣는 현재 사양 개정판 2026-07-28과, 같은 엔드포인트에서 2025-11-25까지의 핸드셰이크 개정판을 모두 지원합니다. 클라이언트는 연결을 열 때 사용한 개정판을 그대로 받으므로 따로 설정할 것이 없습니다.

## 도구로서의 플로

`mcp tool` 노드는 도구를 선언합니다. 이름, 이를 읽는 모델을 위한 설명, 입력 스키마가 필요합니다. 플로가 배포되어 있는 동안 Flow는 이 도구를 `/mcp`에서 제공합니다(관리자 루트를 옮겼다면 그 아래에서). 호출은 노드에서 나오는 메시지가 되며, `msg.payload`는 호출의 인수, `msg.topic`은 도구 이름, `msg.mcp`는 `tool`, `caller`, `callId`를 담습니다. 아래쪽 어딘가의 `mcp result` 노드가 `http response`가 `http in`에 응답하듯 답을 돌려줍니다. 둘 사이의 모든 것은 다른 플로와 같은 플로입니다.

```json
[
  {"id": "t1", "type": "tab", "label": "Line"},
  {"id": "tool", "type": "mcp tool", "z": "t1", "toolName": "line_status",
   "description": "Status of a production line: its state and speed.",
   "schema": "{\"type\":\"object\",\"properties\":{\"line\":{\"type\":\"string\",\"enum\":[\"L1\",\"L2\",\"L3\"]}},\"required\":[\"line\"],\"additionalProperties\":false}",
   "x": 100, "y": 100, "wires": [["status"]]},
  {"id": "status", "type": "function", "z": "t1", "name": "status", "outputs": 1,
   "func": "msg.payload = {line: msg.payload.line, state: 'running', askedBy: msg.mcp.caller};\nreturn msg;",
   "x": 300, "y": 100, "wires": [["answer"]]},
  {"id": "answer", "type": "mcp result", "z": "t1", "x": 500, "y": 100, "wires": []}
]
```

**스키마는 플로가 실행되기 전에 검사됩니다.** JSON Schema이며 `json` 노드가 읽는 방식으로 읽습니다(스키마가 다른 초안을 지정하지 않으면 초안 2020-12이고, 다른 URL로의 `$ref`는 오류입니다). 유효하지 않은 스키마, 객체가 아닌 루트, MCP가 허용하지 않는 도구 이름, 같은 이름을 서비스하는 두 노드는 이유와 함께 해당 노드의 배포를 실패시킵니다. 인수가 맞지 않는 호출에는 잘못된 필드를 알려 주는 도구 오류, `arguments.line: value must be one of "L1", "L2", "L3"`로 응답하므로 모델이 이를 고쳐 다시 시도할 수 있고, 플로는 그 호출을 보지 못합니다. 객체 페이로드는 객체로, 그리고 JSON 텍스트로 돌아가고, 텍스트는 텍스트로 돌아갑니다. Catch 노드가 공급하는 `mcp result`, 또는 "The work failed"를 선택한 것은 오류 자체의 문장을 담은 도구 오류로 응답합니다. 아무도 답하지 않은 호출은 응답 제한 시간(따로 정하지 않으면 30초)이 지나면 그 사실을 통보받고, 오류는 Catch 노드로 갑니다. 재배포는 진행 중인 호출이 끝나기를 기다립니다.

**에이전트도 다른 호출자와 같은 호출자입니다.** `/mcp`는 관리자 API와 같은 토큰, 즉 세션 토큰이나 API 토큰만 받습니다. 익명 호출은 없습니다. 토큰이 없으면 401, Flow가 모르는 토큰도 401, `mcp.call` 권한이 없는 토큰은 403이며, 프로토콜이 요청을 보기 전에 판정됩니다. `HOTLOOP_FLOW_INSECURE`로 실행 중인 인스턴스는 도구 호출을 감사 로그에 남길 호출자가 있어야 하므로 모든 `/mcp` 요청에 403으로 응답합니다. 에이전트용 토큰도 다른 토큰과 같은 토큰입니다:

```yaml
auth:
  tokens:
    - name: agent
      hash: sha256:...          # from: hotloop-flow token -name agent
      permissions: ["mcp.call"]
      rateLimit: {calls: 60, per: 1m}   # optional; no rateLimit, no limit
```

호출은 그 신원의 권한으로 실행됩니다. 모든 호출자에게는 `mcp.call`(또는 `mcp.*`, 또는 `*`)이 필요합니다. 도구의 "Extra permission" 칸에 `mcp.line3` 같은 다른 권한을 넣으면 호출자에게는 그 권한도 필요하며, 없으면 목록에서 그 도구가 보이지 않습니다. 에이전트 두 개가 Flow 하나를 공유하면서 서로 다른 도구를 볼 수 있습니다.

**토큰마다 호출 횟수를 제한할 수 있습니다.** `auth.tokens`의 API 토큰에 있는 `rateLimit`은 한 구간 `per` 동안의 `calls`이며, 생략하면 1분입니다. 구간은 토큰의 첫 호출과 함께 시작되고, 횟수를 넘은 호출은 구간이 끝날 때까지 거부되며, 그 뒤 횟수를 다시 셉니다. 거부된 호출은 플로에 도달하지 않고 몇 초를 기다려야 하는지 알려 주는 도구 오류로 응답하므로, 반복에 갇힌 에이전트는 자기가 읽을 수 있는 말로 속도를 늦추라는 안내를 받습니다. 사양에는 이를 위한 오류가 없으므로, 수행할 수 없는 호출에 대해 이미 정의된 도구 오류를 사용합니다. `rateLimit`이 없는 토큰은 제한되지 않으며, 세션 토큰은 사람의 것이므로 역시 제한되지 않습니다. 각 토큰은 따로 집계하고, 집계는 메모리에 있으므로 재시작하면 처음부터 다시 셉니다. 거부는 이유가 `rate limit exceeded`인 `mcp.refused` 행이므로 호출 폭주도 감사 로그에 남습니다.

**모든 호출은 호출자의 이름으로 감사 로그에 남습니다.** `mcp.call`은 플로가 실행되기 전에 도구, 노드, 호출 ID와 함께 기록되고, `mcp.result`는 실행 후에 결과와 걸린 밀리초와 함께 기록됩니다. `mcp.refused`는 잘못된 토큰, 권한이 없는 토큰, 호출할 수 없는 도구, 맞지 않는 인수를 뜻합니다. 인수 자체는 기록하지 않습니다. 토큰이 아예 없는 요청도 기록하지 않습니다. 이름을 붙일 상대가 없기 때문입니다. `GET /audit?event=mcp.`로 전부 읽을 수 있고, `?user=token:agent`로 에이전트 하나로 좁힐 수 있습니다.

Flow가 없어도 되는 MCP 프로젝트 자체의 인스펙터로 시험해 보십시오:

```bash
npx @modelcontextprotocol/inspector@2.12.0 --cli http://localhost:1880/mcp \
  --transport http --header "Authorization: Bearer $TOKEN" \
  --method tools/call --tool-name line_status --tool-arg line=L3
```

플로 테스트는 호출이 만들었을 메시지를 `mcp tool` 노드가 있는 자리에 넣고, `mcp result`는 자신이 응답했을 내용을 `{isError, text, structuredContent}` 형태로 테스트에 넘기므로 서버 없이 플로를 테스트할 수 있습니다.

## Flow 자체 도구

플로 작성자가 연결해 둔 것만 호출할 수 있는 에이전트는 플로를 볼 수도 바꿀 수도 없으므로, Flow는 같은 `/mcp`에서 플로의 도구와 나란히 자체 도구 45개를 제공합니다. 읽기와 쓰기가 모두 됩니다. 7개는 플로에 관한 것으로 아래 표에 있고, 나머지는 관리자 API의 다른 경로입니다. 설정, 팔레트, 감사 로그, 배포 상세와 차이, 내보내기, 플로 테스트, 메시지 추적, 런타임 수치, 2단계 인증 재설정, 그리고 다이어그램과 계측기입니다. 다이어그램 목록과 읽기, 실행과 중지, 디버거 조작, 패널의 컨트롤 설정, 계측기 쓰기 전환이 여기에 속합니다. MCP 페이지에는 모든 도구와 그 경로 및 권한, 그리고 도구가 아닌 몇 개의 경로와 그 이유가 있습니다.

| 도구 | 기능 | 권한 |
|---|---|---|
| `list_flows` | 모든 탭과 서브플로: ID, 레이블, 비활성화 여부, 노드 수, 리비전 | `flows.read` |
| `get_flows` | 에디터가 읽는 그대로의 배포된 전체 집합과 리비전 | `flows.read` |
| `get_flow` | 탭 또는 서브플로 하나와 그 노드를 ID로 조회 | `flows.read` |
| `deploy_flows` | **deploy**: 읽은 리비전과 메모를 보내 전체 집합 교체 | `flows.write` |
| `list_deployments` | 배포 이력, 최신순 | `flows.read` |
| `rollback_deployment` | 이전 배포로 **롤백**, 새 배포로 기록 | `flows.write` |
| `inject_node` | inject 노드를 직접 만든 메시지로 **press** | `inject.write` |

이 중 어느 것도 별도의 구현이 아닙니다. 각 도구는 엔드포인트가 인증한 호출자로서 같은 작업을 하는 관리자 API의 핸들러를 그대로 실행하므로, 배포는 에디터에서 배포할 때 만나는 모든 검사를 거칩니다. 문서가 파싱되어야 하고, 리비전은 현재 것이어야 하며(빈 리비전은 의도적으로 덮어씁니다), 전달되는 내용이 서로 맞지 않는 와이어는 거부되고, 허용되지 않은 플러그인은 거부되며, 실패한 플로 테스트는 배포를 막고, 각각 그 경로 자체의 문장으로 알려 줍니다. 배포 이력에는 호출자와 메모가 기록되고, 감사 로그에는 모든 도구 호출이 남기는 `mcp.call`과 `mcp.result` 행뿐 아니라 호출자 이름의 `deploy` 또는 `inject` 행도 남습니다. 호출자에게는 `mcp.call`과 도구 자체의 권한이 필요하며, 호출할 수 없는 도구는 목록에 나타나지 않습니다. 이 도구들은 배포 후에도 유지되며 배포는 플로의 도구만 내리고, 플로는 이 도구들의 이름을 서비스할 수 없습니다.

`deploy_flows`는 전체 집합을 교체하므로, 에이전트는 먼저 `get_flows`를 읽고 받은 `rev`와 함께 수정한 내용을 돌려보냅니다.

## 다른 서버의 도구 호출

`mcp client` 노드는 메시지가 도착하면 `hotloop-flow-mcp-server` 연결을 통해 도구를 호출합니다. 연결에는 서버의 MCP 주소, 필요한 경우 베어러 토큰, 제한 시간이 들어갑니다. 도구와 인수는 형식이 있는 입력이므로 둘 다 메시지에서 가져올 수 있습니다. `msg.payload`는 도구에 구조화된 응답이 있으면 그 응답이고, 응답이 모두 텍스트였으면 텍스트이며, 그 밖의 것이었으면 온 그대로의 콘텐츠입니다. `msg.mcp`에는 서버, 도구, 전체 응답이 있습니다. 다른 동작인 "List the tools"는 서버가 가진 모든 도구를 설명과 입력 스키마와 함께 `msg.payload`에 넣습니다.

오류를 보고하는 도구는 서버의 문장 그대로 오류를 발생시키므로, Catch 노드는 모델이 보았을 내용을 그대로 봅니다. **호출은 두 번 보내지 않습니다.** 도구는 장비를 움직일 수 있고, 끊어진 연결은 서버가 실행했는지 알려 주지 않으므로, 오류는 연결이 실패했다고만 알리고 다음 메시지가 다시 연결합니다. 토큰은 지정한 주소로만 가고 다른 곳에는 가지 않으며, 리다이렉트는 따르지 않고, 오류에도 토큰이 반복되지 않습니다. 연결은 시스템의 인증서 루트만 신뢰합니다.

HotLoop의 경우 `/mcp` 주소와 릴리스 Secret의 `mcp-token`을 사용하며, HotLoop MCP 문서의 모든 도구를 쓸 수 있습니다:

```json
{"id": "plant", "type": "mcp client", "z": "t1", "server": "hotloop",
 "tool": "get_plant_status", "toolType": "str", "arguments": "{}", "argumentsType": "json",
 "x": 300, "y": 100, "wires": [["use"]]}
```

HotLoop은 이 호출을 MCP 클라이언트의 호출로 보고 자체 규칙에 따라 처리합니다. MCP는 읽고 쓰며 다른 모든 호출과 같은 관문을 지나므로, 활성화되어 범위 안에 있는 태그에 대한 `write_tag`는 통과하고(HotLoop 자체의 쓰기를 켠 후), 거부되는 호출, 예컨대 아무도 쓰기 가능으로 표시하지 않은 태그는 HotLoop의 문장으로 된 노드 오류로 돌아옵니다. MCP 없이 플로에서 HotLoop의 관문을 통해 쓰려면 위의 HotLoop 노드를 사용하십시오.

## 시험한 대상

**서버**는 Go SDK의 자체 클라이언트로 실제 HTTP 위에서 두 세대 모두 시험합니다. 목록 조회, 호출, 거부된 인수, 거부된 권한, 거부된 토큰, 감사 행, 노드가 멈추면 사라지는 도구, 그리고 실제 API 토큰과 세션 토큰, 디스크의 감사 로그를 갖춘 전체 관리자 서버까지 포함합니다. MCP 프로젝트의 Inspector CLI 2.12.0은 실행 중인 Flow의 도구를 나열하고 호출했으며, 토큰이 없을 때와 지어낸 토큰일 때 거부되었습니다. `mcp client` 노드는 실제 HotLoop 4.18.10(공개된 IoT 이미지)을 상대로 실행했습니다. 도구 27개를 모두 나열했고, `get_plant_status`, `list_devices`, `get_states`를 호출해 그 응답을 사용했으며, 잘못된 토큰과 토큰 없음으로 거부되었고, 존재하지 않는 도구와 MCP가 할 수 없는 쓰기에 대해 HotLoop 자체의 오류를 받았습니다. 또한 Inspector가 호출한 Flow 도구가 HotLoop의 MCP를 호출하는 플로를 실행해 그 응답을 돌려주었습니다.

**하지 않은 것:** OAuth(베어러 토큰이 양방향의 유일한 진입 수단), stdio 서버, 리소스, 프롬프트, 샘플링, 유도 요청과 진행 알림, 도구의 출력 스키마입니다. HotLoop 4.18.10은 핸드셰이크 개정판을 지원하므로 노드는 그 방식으로 연결하며, 현재 개정판 서버에 대해서는 Flow 자체 서버로만 시험했습니다. 세션을 잊어버리는 핸드셰이크 서버(재시작)는 그 직후 첫 호출을 한 번 실패시키고, 다음 호출은 다시 연결합니다. 호출 제한은 API 토큰 단위이며 설정하기 전에는 꺼져 있으므로, `rateLimit`이 없는 토큰은 이미 상한이 있는 큐와 요청 크기 4 MiB로만 제한됩니다.
