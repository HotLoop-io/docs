절대 수치만 싣습니다. 나란히 놓은 비교표는 장비가 바뀔 때마다 달라지고, 결국 이 제품보다 다른 제품을 더 설명하게 됩니다.

Flow는 데스크톱에서 초당 약 15,000건, Raspberry Pi 5에서 초당 약 13,000건의 요청에 응답하며, 메모리는 데스크톱에서 30 MiB 미만, Pi에서 42 MiB입니다. 공장 현장의 박스에 들어갈 만큼 작은 플로 엔진이 필요한 이유가 바로 이것입니다.

## 플로

노드 다섯 개입니다. HTTP 엔드포인트, 속성 편집 세 개, 응답 하나입니다. 일부러 빠르게 만든 것은 없습니다. 작은 실제 플로의 모양이며, 플로 엔진의 벤치마크가 다뤄야 할 대상이 바로 이것입니다. 부하 생성기는 폐루프 방식입니다. 각 클라이언트는 이전 요청이 돌아오면 다음 요청을 보내므로, 상대편이 받아낼 수 있는 양을 측정하며, 대상이 뒤처질 때 개루프 생성기가 보고하는 오해를 부르는 지연 시간을 만들어 낼 수 없습니다.

## 직접 실행해 보기

`hotloop-flow bench`는 바이너리에 포함되어 있습니다. `-launch`는 바이너리를 시작하고, 플로가 응답할 때까지의 시간(콜드 스타트)을 재고, 2초 뒤 프로세스의 상주 메모리(유휴)를 읽은 다음, 부하 동안 이를 샘플링해 최고값을 유지합니다. `-launch` 없는 `-target`은 이미 실행 중인 인스턴스, 즉 컨테이너나 파드를 HTTP로 구동하여 처리량과 지연 시간을 측정합니다.

```bash
hotloop-flow bench -mode http -launch ./hotloop-flow -target http://127.0.0.1:18897 -path /bench -duration 30s -warmup 5s -connections 8
hotloop-flow bench -mode engine -chain 5 -messages 200000
```

## 결과

x86 데스크톱(CPU 24개)에서 네이티브 정적 바이너리로 각각 세 번씩 측정했습니다.

| <span class="sr-only">세부 정보</span> | 실행 1 | 실행 2 | 실행 3 |
|---|---|---|---|
| 콜드 스타트 | 0.05 s | 0.05 s | 0.05 s |
| RSS, 유휴 | 16.7 MiB | 16.7 MiB | 16.4 MiB |
| RSS, 부하 시 최고값 | 26.4 MiB | 26.4 MiB | 28.5 MiB |
| HTTP 처리량 | 15.0k req/s | 15.3k req/s | 13.0k req/s |
| HTTP 지연 시간 p50 / p95 / p99 | 0.39 / 1.22 / 1.82 ms | 0.39 / 1.20 / 1.78 ms | 0.41 / 1.49 / 4.03 ms |
| 엔진, 메시지당 | 2.61 µs | 3.11 µs | 2.20 µs |
| 엔진, 메시지당 할당량 | 3,868 bytes | 3,869 bytes | 3,868 bytes |

## Raspberry Pi 5 결과

8 GB Raspberry Pi 5 한 대에서 클럭을 2.0 GHz로 제한하고, k3s의 파드로 실행했으며 노드에는 다른 것이 없었습니다. 같은 플로를 세 번, 매번 새 파드에서 실행했습니다.

| <span class="sr-only">세부 정보</span> | 실행 1 | 실행 2 | 실행 3 |
|---|---|---|---|
| 콜드 스타트 | 0.46 s | 0.15 s | 0.10 s |
| RSS, 부하 시 최고값 | 40.3 MiB | 40.5 MiB | 40.3 MiB |
| HTTP 처리량 | 13.2k req/s | 13.4k req/s | 13.3k req/s |
| HTTP 지연 시간 p50 / p95 / p99 | 0.48 / 1.45 / 2.78 ms | 0.48 / 1.42 / 2.72 ms | 0.48 / 1.44 / 2.74 ms |
| 엔진, 메시지당 | 8.15 µs | 7.74 µs | 7.89 µs |

같은 보드에서 같은 명령을 600초 동안 유지하면 11.4k req/s, p50 0.58 ms, p99 3.00 ms로 안정됩니다. 이 보드는 능동 쿨러 없이 방열판만으로 동작하며 이 정도 부하에서는 스로틀링되므로, 계속 부하가 걸리는 박스에 대해서는 이것이 정직한 수치입니다.

### 이 수치가 의미하지 않는 것

**HTTP 처리량에는 HTTP 스택이 포함됩니다.** 의도한 것입니다. 플로를 호출하는 클라이언트가 실제로 겪는 값이기 때문입니다. 스케줄러의 측정값은 아닙니다. 엔진 행은 경로에 I/O가 전혀 없는 스케줄러 측정값입니다.

**플로 모양 하나, 페이로드 크기 하나, 동시성 하나입니다.** MQTT 발행이나 데이터베이스 쓰기처럼 실제 I/O를 하는 플로는 I/O가 지배합니다. 이 수치는 런타임 자체의 오버헤드이며 모든 워크로드에 대한 약속이 아닙니다.

**꼬리는 중앙값보다 더 많이 움직입니다.** 포화 상태에서는 모든 것이 대기하고 p99는 대기열이 좌우합니다. 요청 하나를 처리하는 비용은 중앙값에서 드러납니다.

**이것은 벤치마크용 플로이며 내구성 와이어가 아닙니다.** 내구성 와이어 뒤의 저장소나 SD 카드 쓰기는 여기서 측정하지 않습니다.

## 메모리

RSS는 `/proc`에서 읽은 프로세스 자체의 상주 메모리입니다. 커널이 컨테이너에 청구하는 양을 보여 주는 `podman stats`가 보고하는 값과는 다르며, 이 값은 프로세스가 실제로 보유한 양보다 훨씬 낮게 나올 수 있습니다.
