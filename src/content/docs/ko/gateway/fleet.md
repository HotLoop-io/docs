플릿 관리는 4.7.0부터 Gateway가 등록된 엣지 릴레이를 추적하고, 살아 있는지 확인하며, 권한 있는 운영자가 릴레이에 rebirth, 재시작, 방금 푸시한 설정 적용을 요청할 수 있게 해 줍니다. 기본은 꺼져 있습니다(`HOTLOOP_FLEET_ENABLED`). 엣지 릴레이가 없는 배포에는 이 기능을 연결할 브로커가 없기 때문입니다.

## 아닌 것

플릿 관리는 별도의 자체 MQTT 연결을 갖고 다른 질문에 답합니다. *등록된* 엣지 릴레이가 살아 있는지를 보며, 그 태그 중 하나가 어떤 값인지는 보지 않습니다. 태그를 폴링하는 드라이버에 이를 붙이면, 플릿만 보려고 호환되는 장치를 설정하게 하거나, 공유하도록 만들어진 적 없는 그 패키지의 노드별 내부 기록을 건드려야 했을 것입니다.

**자동이 아닙니다.** 엣지 릴레이가 브로커에 나타난다고 해서 플릿 구성원이 되지는 않습니다. 구성원은 선언해야 하며, `POST /api/fleet`으로 만드는 `fleet_members`의 한 행입니다. 이 앱이 이미 드라이버가 찾아낸 태그와 사람이 설정한 태그를 구분하는 방식과 같습니다. 아무도 등록하지 않은 그룹이나 노드의 NBIRTH는 debug 수준으로 기록하고 그 외에는 무시합니다.

## 구조

- **접속 상태**는 NBIRTH와 NDEATH에서 얻습니다. 릴레이 쪽에서는 아웃바운드만 사용합니다. 측정값을 게시할 때처럼 브로커로 걸어 연결하므로, 릴레이로 들어오는 연결 없이 NAT를 통해 동작합니다.

명령은 Sparkplug NCMD로 반대 방향으로 전달되며, 릴레이가 이미 처리하던 것을 확장합니다.

- 해가 없는 멱등 신호입니다.
- **재시작**(`Node Control/Reboot`, 이 앱이 만든 이름이 아니라 Sparkplug 사양 자체의 이름)은 릴레이가 자신의 정상 NDEATH를 게시하고 종료합니다. 감독자(Quadlet 유닛의 `Restart=always` 또는 Deployment의 기본 `restartPolicy: Always`)가 그 순간 디스크에 있는 내용으로 다시 올립니다. 새로운 종료 경로는 없고, 릴레이가 `SIGTERM`에서 이미 따르는 정상 종료 경로와 같습니다.

명령이 릴레이가 이미 바깥으로 걸어 둔 같은 MQTT 연결로 오가므로, 명령을 보내는 데도 릴레이로 들어오는 연결이 필요 없습니다.

온라인으로 보이는 릴레이는 반드시 명령할 수 있습니다. 모든 릴레이는 연결할 때마다 생성을 게시하기 전에 자신의 NCMD 토픽을 구독하고 브로커가 확인할 때까지 기다리므로, "온라인"이 "도달 가능"보다 앞서는 일이 없습니다. 관리자도 자기 쪽에서 같은 규칙을 지킵니다. NBIRTH와 NDEATH 구독이 확인되기 전에는 시작했다고 보고하지 않으므로, Gateway가 올라오는 순간 생성되는 릴레이도 놓치지 않습니다. 브로커의 ACL이 어느 쪽 구독이든 거부하면, 그쪽은 반쯤 귀가 먼 채 실행하지 않고 시작을 거부하며 그 사실을 알립니다.

## 설정 푸시

릴레이가 폴링하는 내용을 푸시하는 일은 NCMD로 하지 않습니다. Sparkplug 메트릭은 장치 파일 전체를 담도록 설계되지 않았기 때문입니다. 릴레이마다 **retained 일반 MQTT 토픽**인 `hotloop/edge-relay-config/<group>/<node>`로 갑니다. retained 전달 덕분에 "따라잡게 해 달라"는 별도 요청 없이 동작합니다. 그곳에 마지막으로 게시된 내용은 구독하는 모든 클라이언트에 즉시 전달되며, 오프라인이었다가 다시 연결되는 릴레이나 처음 시작하는 릴레이도 마찬가지입니다.

릴레이는 수신 시 다시 검증합니다. 이 앱은 그 토픽에 Gateway만 게시한다고 가정할 수 없고, 스스로 망가진 것을 게시하지 않아야 한다는 것만 보장합니다.

**장치 파일에는 자격 증명이 들어 있을 수 있고, 푸시하면 그것이 게시됩니다.** 장치의 `config` 블록에는 드라이버가 로그인에 쓰는 값, 예를 들어 OPC UA `username`과 `password`(4.15.0)가 들어 있고, 파일은 그대로 retained로 게시됩니다. `hotloop/edge-relay-config/#`를 구독할 수 있는 사람은 누구나 읽을 수 있으므로, 자격 증명이 든 파일을 푸시하기 전에 브로커에 TLS와 그 토픽에 대한 ACL이 필요합니다. Gateway의 API는 4.15.1부터 모든 역할에게 장치 자격 증명을 숨기지만, 푸시한 파일은 API 뒤에 있지 않아 이 변경의 영향을 받지 않습니다. [Edge Relay 레퍼런스](/ko/edge-relay/reference/#credentials-in-the-device-file-4150)와 [인증과 사용자](/ko/iot/authentication/#where-credentials-are-still-in-the-clear)를 참고하세요.

**푸시는 즉시 적용되며 아무것도 재시작하지 않습니다.** 4.17까지는 푸시가 파일을 준비만 했고, 적용하려면 `POST /api/fleet/{id}/restart`라는 두 번째 동작이 필요했으며, 태그 하나를 바꾸려고 릴레이의 브로커 세션과 장치 세션 전부를 끊었습니다. 이제는 다음과 같습니다.

- **실행 중인 릴레이**는 파일을 검증하고 저장한 뒤 그 자리에서 적용합니다. 새 장치는 연결되고, 제거된 장치는 연결이 끊기고, 바뀐 장치는 다시 연결되며, 바뀌지 않은 장치는 세션을 그대로 유지합니다. Sparkplug 세션과 전달 큐는 내내 유지됩니다. 노드는 새 메트릭 세트로 rebirth를 하며 빠진 메트릭은 먼저 null로 만들어, 호스트가 제거된 장치의 마지막 정상 값을 계속 보여 주지 않게 합니다. [Edge Relay 레퍼런스](/ko/edge-relay/reference/#what-a-live-apply-keeps-and-what-it-changes)에 선로로 나가는 내용과 그 이유가 정확히 나와 있습니다.
- **릴레이가 거부한 파일**(파싱되지 않거나, 검증되지 않거나, 저장할 수 없는 경우)은 릴레이를 전혀 바꾸지 않으며, 릴레이의 `/status`가 `config.rejected`에서 그렇게 알립니다. `GET /api/fleet`은 `statusUrl`이 있는 모든 구성원에 대해 이를 실행 중인 파일의 다이제스트 옆에 보여 주므로, "푸시했다"와 "실행 중이다"가 가정이 아니라 확인할 수 있는 두 가지가 됩니다. Gateway도 게시 전에 검증하므로, 실제로는 더 새롭거나 오래된 릴리스의 릴레이가 규칙에 의견이 다르거나, Gateway가 아닌 무언가가 그 토픽에 게시한 경우입니다.
- **오프라인 릴레이**는 연결되는 순간 retained 푸시를 받습니다. 부팅 시 로컬 파일을 불러오기 전에 몇 초 기다리므로, 옛 목록으로 시작했다가 바꾸는 대신 푸시된 목록으로 올라옵니다.

푸시된 파일은 릴레이의 로컬 장치 파일 위가 아니라 데이터 볼륨에 놓이며, 푸시를 지울 때까지 로컬 파일보다 우선합니다. 릴레이의 [Edge Relay 레퍼런스](/ko/edge-relay/reference/#where-a-pushed-file-lives-and-which-file-wins)에 우선순위 규칙과 그 규칙이 필요해진 4.16.0 버그가 나와 있습니다.

**푸시 철회**는 `DELETE /api/fleet/{id}/config`(`fleet.config`, 푸시와 같음)입니다. 구성원의 설정 토픽에 빈 retained 메시지를 게시하는데, MQTT가 retained 값을 지우는 방식이므로 이후 어떤 부팅도 푸시를 적용하지 않습니다. 그때 연결된 릴레이는 푸시된 파일을 버리고 푸시가 적용될 때처럼 즉시 로컬 파일로 돌아가지만, 로컬 파일이 로드되지 않으면 푸시된 파일을 유지하고 그렇게 알립니다. 오프라인이던 릴레이는 삭제를 듣지 못하므로(빈 메시지는 보존되지 않습니다), 릴레이가 돌아오면 다시 보내세요.

## 각 릴레이가 실행하는 것과 업데이트

모든 릴레이는 생성 때마다 자신의 버전과 이미지 다이제스트를 담으며, 엣지 게시가 켜진 Edge나 Gateway도 마찬가지이므로, 여기에 구성원으로 등록된 박스도 같은 정보를 보여 줍니다(`Node Info/Version`과 `Node Info/ImageDigest`라는 문자열 메트릭, 별칭 없음, 이를 모르는 Sparkplug 호스트는 무시합니다). `GET /api/fleet`은 이를 각 구성원의 `release`로 보여 줍니다. `version`, `imageDigest`, `since`(Gateway가 그 빌드를 처음 들은 시점)입니다. 그 이전의 릴레이는 아무것도 보고하지 않으며, Gateway는 "알 수 없는 빌드"를 지어내지 않고 아무 말도 하지 않습니다.

구성원의 빌드가 바뀌면 Gateway는 그 구성원에 대한 `config` 이벤트로 시스템 로그에 기록하며, 이전과 새 버전과 다이제스트가 상세에 들어갑니다(`{"kind":"fleet.release",...}`). 처음 듣는 빌드도 다음 빌드와 비교할 기준으로 기록합니다. 마지막 기록을 로그에서 다시 읽으므로 Gateway를 재시작해도 유지되며, 재시작이 업데이트를 지어내는 일은 없습니다. 이것은 릴레이가 받는 모든 업데이트의 감사 기록이며 경로는 상관없습니다(Podman의 타이머, 승인, `helm upgrade`, 박스 앞의 사람). Gateway는 업데이트를 일으키지 않고 보고만 할 수 있기 때문입니다. 움직이는 태그가 `:stable`이 업데이트되는 방식이므로, 같은 버전 아래에서 바뀐 다이제스트도 "같은 버전의 다른 이미지"로 기록됩니다.

`POST /api/fleet/{id}/update`(`fleet.update`, 관리자 전용)는 릴레이가 보류 중인 업데이트를 승인합니다. 업데이트를 보류하도록 설정된 릴레이에만 효과가 있으며, 다른 릴레이는 무시했다고 기록합니다. 요청에는 이미지가 지정되지 않습니다. 설치 유형별로 이것이 하는 일과 하지 않는 일은 [Edge Relay 레퍼런스](/ko/edge-relay/reference/#updating-a-relay)에 있습니다.

## 명령 권한

일부러 한 겹이 아니라 두 겹입니다.

- **API에서** 운영자가 rebirth를 요청하려면 `fleet.rebirth`가 필요합니다. 재시작, 업데이트 승인, 설정 푸시에는 각각 `fleet.restart`, `fleet.update`, `fleet.config`가 필요하며 관리자에게만 부여됩니다. 재시작은 rebirth 신호보다 진행 중인 폴링 주기를 더 크게 방해하고, 릴레이가 폴링하는 내용을 푸시하는 것도 같은 방식으로 다룹니다. `alarms.ack`와 `automations.trigger`가 다른 "지금 실행" 동작에 대해 이미 보여 주는 것과 같은 제한입니다.
- **브로커에서** 이 앱은 아무것도 강제할 수 없습니다. NCMD 게시와 설정 토픽은 둘 다 브로커 자체의 ACL로 Gateway 자신의 MQTT 자격 증명에만 제한되어야 합니다. 그렇지 않으면 브로커에 닿을 수 있고 릴레이의 그룹과 노드를 아는 누구든 이 기능과 같은 명령이나 설정을 게시할 수 있습니다. 배포할 때 설정하세요. 이 앱의 코드 바깥에 있다고 해서 선택 사항은 아닙니다.

## API

| 경로 | 권한 | <span class="sr-only">세부 정보</span> |
|---|---|---|
| `GET /api/fleet` | `fleet.read` | 등록된 모든 구성원과 실시간 접속 상태, 설정된 경우 폴링한 `/status` |
| `POST /api/fleet` | `fleet.write` | 구성원을 만들거나 갱신합니다(기존 `id`가 있는 본문은 갱신) |
| `DELETE /api/fleet/{id}` | `fleet.write` | 등록된 구성원을 제거합니다 |
| `POST /api/fleet/{id}/rebirth` | `fleet.rebirth` | `Node Control/Rebirth`를 게시합니다 |
| `POST /api/fleet/{id}/restart` | `fleet.restart` | `Node Control/Reboot`를 게시합니다 |
| `POST /api/fleet/{id}/update` | `fleet.update` | 릴레이가 보류 중인 이미지 업데이트를 승인합니다(보류하지 않는 릴레이에는 아무 일도 하지 않음) |
| `POST /api/fleet/{id}/config` | `fleet.config` | 새 장치 파일을 푸시합니다(원시 JSON 본문, 게시 전에 검증). 실행 중인 릴레이는 즉시 적용합니다 |
| `DELETE /api/fleet/{id}/config` | `fleet.config` | 푸시를 지워 릴레이가 로컬 장치 파일로 돌아가게 합니다. 연결되어 있으면 즉시 적용됩니다 |

|---|---|---|
| `HOTLOOP_FLEET_ENABLED` | `false` | 이 값을 설정하기 전까지 기능이 꺼져 있습니다 |
| `HOTLOOP_FLEET_BROKER` | n/a | 활성화 시 필수입니다. 호스트만, `host:port`, 또는 전체 URL |
| `HOTLOOP_FLEET_USER` / `_PASSWORD` | n/a | 브로커 자격 증명 |
| `HOTLOOP_FLEET_TLS` | `false` | |
| `HOTLOOP_FLEET_TLS_SKIP_VERIFY` | `false` | 배포별로 직접 선택하는 옵션입니다. 기본으로 설정하지 마세요 |

## 검증된 것과 검증되지 않은 것

HotLoop은 실제 장비와 실제 서버를 상대로, 그리고 2026-11-17에 실제 하드웨어에서 실행되었습니다.
