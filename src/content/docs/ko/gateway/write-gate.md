이 시스템은 기계를 움직일 수 있습니다. 그래서 요청과 장치 사이에 정확히 무엇이 있는지, 코드가 실행하는 순서대로 보여 드립니다.

장치로 향하는 모든 값은 **우회할 수 없는 하나의 함수**를 거칩니다. 화면 클릭, `POST /api/write`, 엔티티 서비스 호출, 자동화, 스크립트, 레시피, MCP를 통한 에이전트 모두 마찬가지입니다. 정책은 그곳에만 있습니다. 여섯 곳에 복사된 점검은 일곱 번째에서 누군가 빠뜨리기 마련이고, 그 일곱 번째가 항상 가동 중인 프레스에 쓰는 곳이기 때문입니다. 런타임의 무엇이든 게이트를 거치지 않고 장치 쓰기에 닿을 수 있으면 테스트가 빌드를 실패시키며, 패키지 사본에 네 가지 우회를 심어 모두 잡아냄으로써 이 테스트가 실패할 수 있다는 것을 증명합니다.

읽는 것보다 직접 느껴 보고 싶으신가요? [hotloop.io에 대화형 버전이 있습니다](https://hotloop.io/gateway/#the-gate). 스위치를 바꾸고 설정값을 보내서 정확히 어디서 막히는지 확인하세요.

## 점검 순서

1. **호출자에게 쓰기 권한이 있다.** 이 점검은 게이트 앞, API의 입구에서 이루어집니다. 로그인한 사용자가 `POST /api/write`를 호출하려면 `values.write`가 필요합니다. 운영자와 관리자는 갖고 있고 뷰어는 없으며, 없으면 API가 403으로 응답합니다. 에이전트의 입구는 MCP bearer 토큰이고, 없으면 401을 받으며 도구 목록조차 보지 못합니다. 어느 쪽이든 게이트는 아무것도 듣지 못하므로 쓰기 감사에는 남지 않습니다. (엔티티 서비스 호출은 다르게 동작합니다. [아래](#모든-입구-같은-게이트)를 보세요.)
2. **쓰기가 켜져 있다.** `safety.allowWrites`, 마스터 스위치입니다. 4.4.0부터 기본값은 꺼짐입니다.
3. **에이전트 쓰기가 켜져 있다.** `safety.allowMcpWrites`는 요청이 MCP로 들어왔을 때만 점검합니다. 마스터 스위치의 범위를 좁힐 뿐 결코 우회할 수 없습니다. 쓰기가 켜져 있고 이것이 꺼져 있으면 운영자는 태그를 명령할 수 있지만 에이전트는 할 수 없습니다. `safety.allowWrites`가 꺼진 상태에서 이것을 켜면 어느 쪽이 우선인지 추측하게 두지 않고 Gateway가 시작을 거부합니다.
4. **태그가 활성화되어 있다.** 모든 태그는 누군가 `writable`로 표시하기 전까지 읽기 전용이며, 하나씩 의도적으로 표시해야 합니다. 태그 4,000개를 탐색해 가져와도 하나도 활성화되지 않습니다. 존재하지 않는 태그도 여기서 거부됩니다.
5. **값이 범위 안에 있다.** 태그에 범위가 있고 값이 숫자일 때, 범위를 벗어난 값은 **잘라내지 않고 거부**합니다. 최대 400인 태그에 500을 입력한 사람은 실수를 했고, 그 사실을 알아야 합니다. 조용히 400을 보내면 아무도 요청하지 않은 일을 하는 것이고, 본인은 끝내 알지 못합니다.
6. **호출자 자체의 점검을 통과한다.** 엔티티는 자신만 아는 것을 더합니다. 숫자의 단계와 더 좁은 범위, 텍스트의 패턴과 길이, 선택 항목의 옵션, 루프가 지금 수동이 아니면 거부되는 루프 출력, 호출 도중 비활성화되거나 삭제된 엔티티 등입니다. 이 점검은 게이트 안에서 태그의 정책과 범위 뒤에 실행되어 운영자가 항상 태그 문제를 먼저 듣게 하고, 감사 행보다 앞에 실행되어 엔티티 거부도 태그 거부와 똑같이 기록됩니다. 거부만 할 수 있습니다. 값을 바꾸거나 게이트가 막았을 것을 통과시킬 수는 없습니다.
7. **장치가 동작 중이다.** HotLoop에 해당 장치를 위한 실행 중인 worker가 있어야 합니다. 비활성화된 장치나 한 번도 시작되지 않은 장치는 허공에 값을 던지는 대신 `the device is not connected`로 거부됩니다.

**그제야 감사 행이 열리고, 그제야 값이 나갑니다.** 행을 쓸 수 없으면 쓰기는 아예 전송되지 않습니다. 감사할 수 없는 쓰기는 나중에 누구도 책임질 수 없는 쓰기이며, 움직이는 장비에서는 감수할 만한 거래가 아닙니다. 행은 요청에서 분리된 컨텍스트에서 결과와 지연 시간으로 마무리되므로, 시간 초과되거나 취소된 쓰기도 무슨 일이 있었는지 기록합니다.

점검 2부터의 모든 거부는 거부로 감사됩니다. 행위자, 출처, 요청된 값, 대체했을 값, 이유가 담긴 `refused:`가 한 행에 들어가고, 시스템 로그에는 경고가 남습니다. 허용되지 않은 태그를 반복해서 명령하려는 시도는 적어 두지 않으면 보이지 않고, 엔지니어는 나중에 그것을 찾아낼 수 있어야 합니다. 점검 1은 게이트가 본 적이 없으므로 쓰기 감사에 없습니다.

### 이 순서인 이유

정책은 감사 행이 열리기 전에 실행되므로, 거부는 우연히 실패한 시도가 아니라 거부로 기록됩니다. 감사 행은 값이 선로에 닿기 전에 열리므로, 멈춰 버리거나 프로세스째 죽어 버린 쓰기도 시도되었다는 증거를 남깁니다. 공장 현장에서 "그 명령이 나갔는지 모르겠다"는 가장 나쁜 답입니다.

### 점검 7이 잡지 못하는 한 가지

점검 7은 장치에 worker가 있는지를 묻지, 세션이 지금 이 순간 살아 있는지를 묻지 않습니다. 네트워크에서 떨어져 재연결 중인 장치는 통과합니다. 감사 행이 열리고, 드라이버에 세션이 없어 쓰기는 `the device is not connected`로 실패하며, 거부가 아니라 실패한 시도로 기록됩니다. 어느 쪽이든 장치에는 아무것도 닿지 않습니다. [사전 점검](#보내기-전에-물어보기-사전-점검)은 세션까지 확인하고, 그 사실을 처음부터 알려 줍니다.

## 거부별 응답

상태 코드는 누구의 문제인지를 알려 줍니다. 운영자가 그렇게 읽기 때문입니다.

| 일어난 일 | 오류 메시지 | HTTP |
|---|---|---|
| 입구에서 권한 없음 | `<user> does not have the "values.write" permission` | 403 |
| 쓰기가 꺼져 있음 | `writes are disabled on this deployment` | 403 |
| 에이전트 쓰기가 꺼져 있음 | `writes from MCP clients are disabled on this deployment` | 403 |
| 태그가 활성화되지 않음 | `this tag is not marked writable` | 403 |
| 엔티티가 비활성화됨 | `the entity is disabled` | 403 |
| 태그가 존재하지 않음 | 해당 태그와 `not found` | 404 |
| 호출 도중 엔티티가 사라졌거나 허용하는 상태가 아님(수동이 아닌 루프) | 달라진 내용 | 409 |
| 값이 태그의 범위를 벗어남 | `value is outside the tag's configured range` | 422 |
| 엔티티가 값을 받지 않음(단계, 패턴, 옵션, 자체 범위) | `the value is not one this entity accepts`와 이유 | 422 |
| 장치가 연결되지 않음 | `the device is not connected` | 503 |
| 장치가 응답했으나 거부함 | 장치가 직접 보낸 메시지 | 502 |
| 쓰기를 감사할 수 없음, 또는 API가 분류할 수 없는 그 밖의 경우 | `internal error (ref …)`, 상세 내용은 해당 참조 번호로 서버 로그에 있음 | 500 |

API가 분류할 수 없는 것은 모두 500입니다. 예전에는 400이었는데, 그러면 데이터베이스 장애가 운영자에게 뭔가 잘못 입력했다고 알려 주었고, 존재하지 않는 오타를 찾아 헤매게 되었습니다.

MCP에는 상태 코드가 없습니다. 거부는 `isError`로 표시된 도구 결과로 돌아오며, 게이트 자신의 말이 담깁니다.

```
> write_tag tag=press-01/Zone1_Temp value=99 reason="testing"
write refused: press-01/Zone1_Temp: this tag is not marked writable
```

이것은 전송 실패가 아니라 답입니다. 호출은 이해되었고 의도적으로 거부되었으며, 다시 시도해도 같은 답이 나옵니다.

## 보내기 전에 물어보기: 사전 점검

게이트에는 실행하지 않고 묻기만 하는 두 번째 진입점이 있습니다. 같은 점검을 같은 순서로 실행하고, 거부 시 같은 오류 문구를 줍니다. 감사 행을 열지 않고, 이벤트를 발생시키지 않고, 아무것도 집계하지 않으며, 장치에는 결코 닿지 않습니다. 실제 쓰기보다 한 걸음 더 나아가, worker는 켜져 있지만 세션이 끊긴 장치를 "이대로 나갈 것"이 아니라 연결되지 않음으로 보고합니다.

사용할 수 있는 곳:

- **엔티티 서비스 호출**: `POST /api/services/{domain}/{service}?dry_run=true`. 판정과 함께 200으로 응답합니다. 쓰게 될 각 쓰기는 `would_write`로, 거부될 첫 쓰기는 `not_sent`로, 이유는 한 글자도 바꾸지 않고 보여 줍니다. 계획조차 세울 수 없는 요청(없는 엔티티, 도메인이 받지 않는 서비스, 잘못된 데이터)은 실제 호출과 같은 상태로 응답합니다. `dry_run`은 `true` 또는 `false`만 받으며 `yes`는 400입니다. 잘못 짐작하면 질문이 명령이 되기 때문입니다.
- **명령 프롬프트**는 입력하는 동안 묻고, 누군가 확인하기 전에 "Would be refused: ..."를 보여 줍니다.
- **스크립트**, 4.17.0 신규: `POST /api/scripts/{id}/run?dry_run=true`, 실행 서랍의 **Check first**, 또는 `dryRun`이 있는 MCP의 `run_script`. 모든 단계를 지금 이 순간의 공장 상태에 대해 따라가 보며, 거부될 첫 쓰기가 게이트의 말로 이 과정을 끝냅니다. [스크립트](/ko/iot/scripts/)를 보세요.
- **레시피**, 4.17.0 신규: 첫 값이 나가기 전에 모든 대상이 이 점검을 거치며, 잘못된 값이 하나라도 있으면 아무것도 쓰지 않고 레시피 전체가 거부됩니다. `POST /api/recipes/{id}/validate`와 MCP의 `validate_recipe`는 적용하지 않고 묻습니다. [레시피](/ko/iot/recipes/)를 보세요.
- **Blueprints**, 4.17.0 신규: **Check first**는 규칙이 지금 실행된다면 무엇을 할지를 보여 주며, 규칙이 만들어지기 전에 모든 쓰기가 이 점검을 거칩니다. [Blueprints](/ko/iot/blueprints/)를 보세요.

깨끗한 사전 점검은 조언일 뿐 약속이 아닙니다. 질문과 명령 사이에 장치가 끊기거나 누군가 태그를 비활성화할 수 있으므로, 게이트는 실제 쓰기 시점에 다시 판단합니다.

:::caution[아직 4.16.0인가요? 프롬프트가 Set을 삼킬 수 있습니다]
4.16.0에서는 입력을 멈추고 약 0.25초 뒤에 사전 점검 판정이 나타나는데, 마침 마우스가 Set으로 향할 때이고 그 아래에서 프롬프트가 커지거나 줄어듭니다. Set이 약 30px 움직이므로 클릭이 빈 곳이나 배경에 떨어져 프롬프트가 닫힙니다. 운영자는 프롬프트가 닫히는 것을 보고 설정값이 나갔다고 생각하지만 아무것도 쓰이지 않았습니다. 4.17.0에서 수정되었습니다. 판정이 버튼 옆에 놓이고 아무것도 움직이지 않습니다. [업그레이드](/ko/gateway/upgrading/)하기 전까지는 Set을 누른 뒤 값이 실제로 바뀌었는지 확인하세요.
:::

## 모든 입구, 같은 게이트

- **화면과 `POST /api/write`.** 행위자는 로그인한 사용자 이름이며, 누구나 설정할 수 있는 헤더가 아닙니다.
- **엔티티 서비스**, `POST /api/services/{domain}/{service}`. `switch.press_01_pump`에 대한 `switch.turn_on`은 이 게이트를 거치는 태그 쓰기이며, entity_id, 서비스, 호출 ID와 함께 해당 엔티티에 대해 감사됩니다. 버튼 한 번은 하나의 호출 ID 아래 두 번의 쓰기입니다. 여기서는 `values.write`가 없는 사용자도 입구에서 막히지 않습니다. 없는 권한이 호출자 자체의 점검으로 게이트에 전달되므로, 거부된 엔티티 호출은 다른 거부와 똑같이 요청된 값과 함께 엔티티에 대해 감사되고, 응답은 여전히 403입니다.
- **자동화**는 `automation:<rule-id>`로 씁니다. 규칙은 사람보다 더 많은 권한을 얻지 못합니다. [자동화](/ko/iot/automations/)를 보세요.
- **스크립트**는 4.17.0 신규이며 `script:<id>`로 쓰고 시작한 쪽의 출처를 유지하므로, 에이전트가 시작한 스크립트는 에이전트 자신의 `write_tag`와 똑같이 에이전트 스위치에 걸립니다.
- **레시피**는 4.17.0 신규이며 모든 대상을 하나의 호출 ID로 쓰므로, `GET /api/writes?call=<id>`가 감사 기록에 남은 적용 전체입니다.
- **에이전트**는 `mcp:<client name>`으로 씁니다. `write_tag`와 `call_service`는 운영자와 같은 점검을 거치며, 둘 다 이유를 명시하지 않으면 실행을 거부합니다. 그 이유는 쓰기 옆의 시스템 로그에 남습니다. 6개월 뒤 아무도 설명하지 못하는 감사 행은 켕기는 양심이 달린 타임스탬프일 뿐입니다. `trigger_automation`은 에이전트 쓰기가 꺼져 있는 동안 완전히 거부되고, `run_script`와 `apply_recipe`도 마찬가지입니다. 규칙, 스크립트, 레시피는 장비를 명령할 수 있어 그렇지 않으면 스위치를 우회하는 길이 되기 때문입니다. [Model Context Protocol](/ko/iot/mcp/)을 보세요.

## 쓰기가 기본적으로 꺼져 있는 이유

4.4.0 이전에는 `safety.allowWrites`와 `safety.allowMcpWrites`의 기본값이 `true`였습니다. 지금은 `false`입니다. 태그는 활성화되기 전까지 항상 읽기 전용이었지만, 새로 설치한 시스템이 아무도 살펴보기 전에 `writable` 플래그 하나만으로 장비를 명령할 수 있어서는 안 됩니다.

게이트 위에 `safety.confirmWrites`(기본값 켜짐)가 있어 화면이 무엇을 보내기 전에 확인을 요청합니다. 이것은 게이트의 점검이 아니라 브라우저의 프롬프트이며, 설정 화면에서 바꿀 수 있는 유일한 안전 설정입니다. `safety.allowWrites`와 `safety.allowMcpWrites`는 일부러 그곳에서 읽기 전용입니다. 이 프로세스가 장비를 명령할 수 있는지를 정하는 마스터 제어는 쓰기를 발행하는 바로 그 브라우저 세션 뒤에 있어서는 안 됩니다.

## 쓰기를 의도적으로 켜기

1. 장치를 추가하고, 프로토콜이 나열할 수 있는 경우 태그를 검색합니다. Modbus와 S7comm은 자체 포인트를 열거할 수 없으므로 장치 문서를 보고 직접 선언하세요.
2. 태그는 하나씩, 의도한 것만 쓰기 가능으로 표시합니다.
3. 값 파일에 `safety.allowWrites: true`를 설정하고 `helm upgrade`를 실행합니다. 그때까지는 1, 2단계의 어떤 것도 밸브를 움직일 수 없습니다.
4. 에이전트도 장비를 명령해야 하는 경우에만 `safety.allowMcpWrites: true`를 설정합니다.

## 하지 않는 일

애플리케이션이 모든 것을 강제할 수는 없으며, 짐작하시게 두느니 말씀드리는 편이 낫습니다.

- **인터록이 아닙니다.** 사람이나 설비를 보호하는 트립은 네트워크에서 돌아가는 무언가가 아니라, 필요한 곳에 하드와이어링된 PLC에 있어야 합니다.
- **브로커를 감시하지 않습니다.** MQTT로 엣지 릴레이에 노드 명령을 보낸다면, 누가 그것을 발행할 수 있는지는 브로커 자체의 접근 제어가 Gateway의 자격 증명으로 제한해야 합니다.
- **OPC UA 서버는 아예 쓸 수 없습니다.** 쓰기 핸들러도, 그것을 추가하는 설정도 없는 읽기 전용이므로, 이를 읽는 SCADA는 이를 통해 아무것도 명령할 수 없습니다.
