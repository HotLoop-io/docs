Το HotLoop έχει τη δική του σύνδεση από την 4.4.0, και κάθε προϊόν την απαιτεί από προεπιλογή. Η λειτουργία χωρίς αυτήν παραμένει δυνατή, σκόπιμα, για μια εγκατάσταση που είναι πράγματι απομονωμένη πίσω από τον πίνακα ελέγχου και θέλει να το δηλώσει, δείτε [Λειτουργία χωρίς σύνδεση](#λειτουργία-χωρίς-σύνδεση), αλλά ένα απλό `helm install` ή μια μονάδα Podman Quadlet ξεκινά πλέον απαιτώντας σύνδεση.

## Εν συντομία

- **Τοπικοί χρήστες, κωδικοί bcrypt, συνεδρίες στον διακομιστή.** Δεν υπάρχει ακόμη εξωτερικός πάροχος ταυτότητας· δείτε το [MCP](/el/iot/mcp/) για το ξεχωριστό όριο με bearer tokens που προστατεύει τη διεπαφή των πρακτόρων και που αυτό δεν αντικαθιστά.
- **Τρεις ρόλοι: admin, operator, viewer.** Ο ρόλος admin μπορεί να κάνει τα πάντα, μαζί με τη διαχείριση χρηστών. Ο ρόλος operator μπορεί να διαβάζει τα πάντα και να γράφει tags, να επιβεβαιώνει συναγερμούς και να ενεργοποιεί αυτοματισμούς. Ο ρόλος viewer μπορεί να διαβάζει τα πάντα και τίποτε άλλο. Σε έναν χρήστη μπορεί επίσης να δοθεί ρητή λίστα δικαιωμάτων αντί για ρόλο, για κάτι στενότερο.
- **Μια συνεδρία είναι ένα cookie ή ένα bearer token**, ό,τι είναι ευκολότερο για τον πελάτη. Η διεπαφή του προγράμματος περιήγησης χρησιμοποιεί το cookie· ένα σενάριο ή άλλη υπηρεσία χρησιμοποιεί `Authorization: Bearer <token>`.
- **Ένας κοινός πίνακας συνδέει τους ανθρώπους με PIN ή κάρτα** και τους αποσυνδέει όταν δεν τον αγγίζει κανείς, ώστε κάθε εγγραφή εκεί να έχει το όνομα ενός ανθρώπου. Δείτε [Πίνακες kiosk](#πίνακες-kiosk-pin-ή-κάρτα-και-αποσύνδεση-λόγω-αδράνειας).
- **Οι συνεδρίες λήγουν.** `HOTLOOP_AUTH_SESSION_TTL`, 12 ώρες από προεπιλογή. Δεν υπάρχει «να με θυμάσαι»: μια συνεδρία που ξεπερνά μια βάρδια είναι μια συνεδρία που κανείς δεν παρακολουθεί.

## Ο πρώτος λογαριασμός

Το chart δημιουργεί έναν κατά την πρώτη εγκατάσταση και τον δείχνει μία φορά, στην έξοδο NOTES του `helm install`:

```
helm install hotloop ./charts/hotloop \
  --namespace hotloop --create-namespace
```

Αν τρέχετε απευθείας το εκτελέσιμο, δημιουργήστε ένα hash και ορίστε δύο μεταβλητές:

```sh
hotloop hash-password
# Password: ********
# Confirm password: ********
# $2a$10$....................................................

export HOTLOOP_AUTH_ENABLED=true
export HOTLOOP_ADMIN_USER=admin
export HOTLOOP_ADMIN_PASSWORD_HASH='$2a$10$....................................................'
```

Το `hash-password` δέχεται και απευθείας `-password`, για ένα σενάριο που ήδη έχει κωδικό:

```sh
hotloop hash-password -password 'something-long'
```

Ο λογαριασμός admin που δημιουργείται έτσι είναι **αρχικός**, όχι διακόπτης επαναφοράς. Μόλις υπάρξει, η αλλαγή του `HOTLOOP_ADMIN_PASSWORD_HASH` και η επανεκκίνηση δεν κάνουν τίποτα: το `EnsureAdminUser` δημιουργεί τον λογαριασμό μόνο αν δεν υπάρχει ήδη αυτό το όνομα χρήστη, ώστε μια τιμή εδώ να μην μπορεί ποτέ να αντικαταστήσει έναν κωδικό που ένας χειριστής έχει αλλάξει έκτοτε από τη διεπαφή. Αυτό μετράει περισσότερο σε μια αναβάθμιση Helm: η εκ νέου εφαρμογή του ίδιου `values.yaml` δεν πρέπει να επαναφέρει σιωπηλά τον κωδικό κανενός.

## Ρόλοι

| Ρόλος | Τι μπορεί να κάνει |
|---|---|
| **admin** | Τα πάντα: `*`. Μαζί με τη δημιουργία, την απενεργοποίηση και τη διαγραφή χρηστών. |
| **operator** | Να διαβάζει κάθε οθόνη. Να γράφει tags (`POST /api/write`) και να εντέλλεται οντότητες (`POST /api/services/...`), να ορίζει βοηθούς (`helpers.write`, δείτε [Βοηθοί](/el/iot/helpers/)), να εκτελεί και να σταματά σενάρια (`scripts.run`, δείτε [Σενάρια](/el/iot/scripts/)), να εφαρμόζει συνταγές (`recipes.apply`, δείτε [Συνταγές](/el/iot/recipes/)), να φτιάχνει κανόνα από ένα blueprint και να τον αναβαθμίζει (`blueprints.apply`, δείτε [Blueprints](/el/iot/blueprints/)), να βλέπει τους πίνακες ελέγχου που προσφέρονται στον ρόλο (`dashboards.read`, δείτε [Πίνακες ελέγχου](/el/iot/dashboards/)), να διαβάζει την ενέργεια που καταναλώθηκε και πόσο κόστισε (`energy.read`, δείτε [Ενέργεια](/el/iot/energy/)· η δημιουργία μετρητή ή τιμολογίου είναι `energy.write`, δουλειά του admin), να αναδιατάσσει τον πίνακα, να επιβεβαιώνει, να αναβάλλει και να επαναφέρει συναγερμούς, να ενεργοποιεί αυτοματισμούς. Δεν μπορεί να επεξεργαστεί τους *ορισμούς* συσκευών, tags, συναγερμών, αυτοματισμών, σεναρίων, συνταγών, blueprints ή πινάκων ελέγχου, και δεν μπορεί να διαχειριστεί χρήστες. |
| **viewer** | Να διαβάζει κάθε οθόνη. Τίποτε άλλο. |

Σε έναν χρήστη μπορεί να δοθεί ρητή λίστα `permissions` αντί για ρόλο, η οποία **αντικαθιστά** εξ ολοκλήρου τον ρόλο αντί να προστίθεται σε αυτόν: ένας χρήστης είναι είτε «ο ρόλος operator» είτε «ακριβώς αυτά τα δικαιώματα», ποτέ και τα δύο, ώστε να υπάρχει ένα μέρος όπου κοιτάς για να ξέρεις τι μπορεί να κάνει κάποιος.

Οι συμβολοσειρές δικαιωμάτων έχουν τη μορφή `resource.action`, `tags.write`, `alarms.ack`, ή μπαλαντέρ πόρου, `tags.*`, ή το καθολικό μπαλαντέρ `*`.

## Πίνακες kiosk: PIN ή κάρτα, και αποσύνδεση λόγω αδράνειας

Στον δικό σας υπολογιστή είστε ήδη συνδεδεμένοι: πληκτρολογήσατε τον κωδικό μία φορά, και μια εγγραφή περνά κατευθείαν από την πύλη εγγραφής και καταγράφεται στο όνομά σας, όπως πάντα. Αυτό δεν άλλαξε. Ένας πίνακας στον τοίχο δεν είναι υπολογιστής κανενός. Αν είναι συνδεδεμένος ως `panel-3`, το ίχνος ελέγχου λέει «το panel-3 άνοιξε τη βαλβίδα», και αυτό δεν είναι ίχνος ελέγχου. Έτσι ένας πίνακας συνδέει έναν άνθρωπο με PIN ή κάρτα, κάθε εγγραφή είναι αυτού του ανθρώπου, και ο πίνακας τον αποσυνδέει όταν δεν τον αγγίζει κανείς.

### Τι βλέπει ο χειριστής

Ένας πίνακας είναι μια φυσική οθόνη: το HotLoop ανοιγμένο στο `/?screen=<name>` (δείτε [Πίνακες ελέγχου](/el/iot/dashboards/#ρόλοι-και-οθόνες)). Όσο δεν είναι κανείς συνδεδεμένος, δείχνει ένα πεδίο, «PIN ή κάρτα», και τίποτα από το εργοστάσιο. Πληκτρολογήστε το PIN και πατήστε Enter, ή περάστε την κάρτα. Ο πίνακας ανοίγει τον πίνακα ελέγχου του, με το ποιος είναι συνδεδεμένος και ένα κουμπί **Έξοδος** στη γωνία, επειδή η κεφαλίδα που κανονικά θα το έλεγε λείπει σε έναν πίνακα. Το πάτημα ενός κουμπιού εγγραφής ζητά επιβεβαίωση και αιτιολογία όπως παντού, και η εγγραφή καταγράφεται στο όνομα αυτού του ανθρώπου.

Μετά το όριο αδράνειας, χωρίς να αγγίξει κανείς την οθόνη, ο πίνακας αποσυνδέει τον άνθρωπο και επιστρέφει στο πεδίο του PIN. Το επιβάλλει και ο διακομιστής, όχι μόνο η σελίδα: μια συνεδρία kiosk που έχει μείνει αδρανής τόσο διαγράφεται, και μια εγγραφή που στέλνεται μετά με το cookie της απορρίπτεται με `401`, ώστε το κλείσιμο της σελίδας, ή μια σελίδα που κόλλησε, να μην αφήνει κανέναν συνδεδεμένο. Αν ο πίνακας πρέπει να χρησιμοποιηθεί με κωδικό, το «Χρήση κωδικού» κάτω από το πεδίο είναι η συνηθισμένη σύνδεση, με τις συνηθισμένες 12 ώρες και χωρίς όριο αδράνειας, επειδή είναι η προσωπική σύνδεση κάποιου.

Ως άγγιγμα μετράει: ένα πάτημα, ένα κλικ, ένα πλήκτρο ή μια εγγραφή. Δεν μετράει: ο πίνακας ελέγχου που ανανεώνει τους αριθμούς του, ή η ζωντανή ροή, που συνεχίζουν είτε είναι εκεί κάποιος είτε όχι.

### Ρύθμιση

Ένας admin δίνει σε κάθε άνθρωπο έναν κωδικό στις **Ρυθμίσεις, Χρήστες**: **PIN ή κάρτα** στη γραμμή του, ο κωδικός δύο φορές, **Ορισμός**. Ή μέσω του API, που είναι ό,τι θα χρησιμοποιούσε ένα σενάριο που εκδίδει κάρτες:

```sh
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"code":"482913"}' https://gateway/api/users/olga/pin

# Take it away (also signs them out of every panel)
curl -X DELETE -H "Authorization: Bearer $TOKEN" https://gateway/api/users/olga/pin
```

- **Ένα PIN είναι διαπιστευτήριο.** Αποθηκεύεται ως hash bcrypt με το ίδιο κόστος με έναν κωδικό, ποτέ σε καθαρό κείμενο, ποτέ στο αρχείο καταγραφής του συστήματος και ποτέ σε απάντηση. Η λίστα χρηστών λέει μόνο `hasPin`. Ένα αντίγραφο ασφαλείας κρατά τα hashes ακριβώς όπως κρατά αυτά των κωδικών ([Αντίγραφα ασφαλείας και επαναφορά](/el/iot/backup/)).
- **Μια κάρτα είναι μια τιμή που πληκτρολογεί ένας αναγνώστης τύπου πληκτρολογίου.** Δεν υπάρχει πρόγραμμα οδήγησης υλικού. Ένας αναγνώστης που λειτουργεί ως πληκτρολόγιο πληκτρολογεί τον αριθμό της κάρτας στο μοναδικό πεδίο του πίνακα και πατά Enter, που είναι η υποβολή της φόρμας. Άρα μια κάρτα είναι ένας κωδικός σαν PIN: ό,τι πληκτρολογεί ο αναγνώστης, 6 έως 72 χαρακτήρες χωρίς κενά, ορισμένος στον λογαριασμό στο ίδιο σημείο. Η ανάγνωση από αναγνώστη που δεν λειτουργεί ως πληκτρολόγιο δεν έχει υλοποιηθεί.
- **Ένας κωδικός, ένας λογαριασμός.** Ο πίνακας βρίσκει τον άνθρωπο μόνο από τον κωδικό, αφού ο αναγνώστης καρτών δεν πληκτρολογεί όνομα χρήστη, οπότε ο ορισμός κωδικού που έχει ήδη άλλος λογαριασμός απορρίπτεται.
- **Ο κωδικός ελέγχεται απέναντι σε κάθε λογαριασμό που έχει έναν,** με το ίδιο bcrypt που κοστίζει ένας κωδικός, επειδή ένα hash με salt δεν αναζητείται κατά τιμή. Αυτό διαρκεί όσο είναι οι λογαριασμοί με κωδικούς, μερικά δευτερόλεπτα στη χειρότερη περίπτωση με δεκάδες, και διαρκεί το ίδιο είτε ο κωδικός είναι σωστός είτε λάθος.
- **Ένας κωδικός συνδέει με τον ρόλο του λογαριασμού.** Δώστε τον σε κάποιον του οποίου ο ρόλος είναι αυτός που πρέπει να έχει σε έναν πίνακα. Μια συνεδρία kiosk έχει τα δικαιώματα του ίδιου του λογαριασμού και τίποτα στενότερο, και ο κωδικός ενός viewer συνδέει έναν viewer, του οποίου τις εγγραφές η πύλη απορρίπτει όπως πάντα.
- **Η απενεργοποίηση ενός λογαριασμού** τερματίζει τις συνεδρίες του στους πίνακες μαζί με τις υπόλοιπες, και ο κωδικός ενός απενεργοποιημένου λογαριασμού δεν συνδέει. **Η αφαίρεση του κωδικού** αποσυνδέει τον λογαριασμό από τους πίνακες και αφήνει ήσυχους τον κωδικό του και τη συνεδρία του δικού του υπολογιστή.

### Ο χρόνος αποσύνδεσης λόγω αδράνειας

Δεκαπέντε λεπτά από προεπιλογή. Είναι αρκετός για να δουλέψει κανείς μια αλλαγή παρτίδας στον πίνακα με έναν φάκελο στο χέρι, ή για να πάει στη βαλβίδα και να τη δει να κινείται, και αρκετά σύντομος ώστε ένας πίνακας που έμεινε στο τέλος μιας δουλειάς να μην είναι ακόμη το όνομα κάποιου όταν φτάσει ο επόμενος. Είναι δική μου κρίση, όχι αριθμός που ορίζει ο κώδικας ή ένα πρότυπο. Αλλάξτε τον στις **Ρυθμίσεις, Εργοστάσιο, Αποσύνδεση kiosk λόγω αδράνειας (δευτερόλεπτα)**, από 10 δευτερόλεπτα έως 12 ώρες, χωρίς νέα εγκατάσταση, ή ορίστε προεπιλογή με `HOTLOOP_AUTH_KIOSK_IDLE` (διάρκεια, `15m`). Ό,τι ορίζεται στις Ρυθμίσεις υπερισχύει της μεταβλητής. Η συνεδρία τελειώνει επίσης στο `HOTLOOP_AUTH_SESSION_TTL`, όπως κάθε συνεδρία.

### Το κλείδωμα μετά από λάθος κωδικούς και PIN

Ένας λάθος κωδικός ή PIN μετριέται απέναντι στον **λογαριασμό** στον οποίο δοκιμάστηκε. Δέκα λάθη στη σειρά κλειδώνουν αυτόν τον λογαριασμό για πέντε λεπτά, και κανέναν άλλο. Ένας σωστός κωδικός ή PIN πριν από το δέκατο ξεκινά πάλι το μέτρημα, και ένα κλείδωμα που έληξε δίνει δέκα νέες προσπάθειες. Ένας κλειδωμένος λογαριασμός αρνείται μια σύνδεση ό,τι κι αν πληκτρολογηθεί, σωστό ή λάθος, με ένα `429` που λέει πόσο να περιμένει κανείς. Ένα κλείδωμα σταματά τις νέες συνδέσεις και τίποτε άλλο: μια συνεδρία που ήδη έχει ο λογαριασμός συνεχίζει, με τα αιτήματά της και τη ζωντανή ροή της, ώστε δέκα λάθος εικασίες από κάποιον άλλον να μην μπορούν να σβήσουν την οθόνη ενός χειριστή στη γραμμή. Ισχύει εξίσου για τη σύνδεση με κωδικό και με PIN, και κάθε κλείδωμα καταγράφεται στο αρχείο καταγραφής του συστήματος (κατηγορία `auth`).

- **Από πού προέρχονται οι αριθμοί.** Το NIST SP 800-63B λέει ότι ένας επαληθευτής περιορίζει τις διαδοχικές αποτυχημένες προσπάθειες σε έναν λογαριασμό: η αναθεώρηση 3, ενότητα 5.2.2, και η αναθεώρηση 4, ενότητα 3.2.2, θέτουν και οι δύο ως μέγιστο το 100 και λένε ότι ένας φορέας λειτουργίας μπορεί να το ορίσει χαμηλότερα. Η αναθεώρηση 4 επιτρέπει επίσης να περιμένει όποιος προσπαθεί μετά από αποτυχίες. Αυτή είναι αυτή η αναμονή, όχι μόνιμη απενεργοποίηση. Το δέκα είναι το ένα δέκατο του ανώτατου ορίου του NIST, και περισσότερο από όσο κάνει κανείς λάθος κατά λάθος. Πέντε λεπτά είναι αρκετά ώστε δέκα προσπάθειες ανά πέντε λεπτά να κρατούν εκτός εμβέλειας το εκατομμύριο δυνατότητες ενός PIN έξι χαρακτήρων (περίπου 350 ημέρες για να δοκιμαστούν όλες), και αρκετά σύντομα ώστε ένας χειριστής που πληκτρολόγησε λάθος κωδικό να επιστρέψει μετά από έναν καφέ. Έξι χαρακτήρες ως ελάχιστο για ένα PIN είναι το κατώτατο όριο της ενότητας 5.1.1.2 της αναθεώρησης 3 για ένα μυστικό που ανατίθεται, όπως είναι ένα PIN που μοιράζει ένας admin. Δέκα και πέντε είναι δική μου επιλογή μέσα στο όριο του NIST, όχι αριθμοί του NIST.
- **Και τα δύο είναι ρυθμίσεις.** **Ρυθμίσεις, Εργοστάσιο**: «Κλείδωμα λογαριασμού μετά από τόσους λάθος κωδικούς ή PIN» (προεπιλογή 10, από 1 έως 100, και το 0 το απενεργοποιεί) και «Για πόσο μένει κλειδωμένος ένας λογαριασμός» (προεπιλογή 5 λεπτά, από 10 δευτερόλεπτα έως μία ημέρα). Οι μεταβλητές είναι `HOTLOOP_AUTH_LOCKOUT_ATTEMPTS` και `HOTLOOP_AUTH_LOCKOUT_DURATION` (διάρκεια, `5m`). Η ρύθμιση υπερισχύει της μεταβλητής.
- **Ένας admin μπορεί να ξεκλειδώσει έναν λογαριασμό.** Οι **Ρυθμίσεις, Χρήστες** δείχνουν έναν κλειδωμένο λογαριασμό ως `locked` με ένα κουμπί **Ξεκλείδωμα**, ή `DELETE /api/users/{username}/lockout`. Το μέτρημα ξεκινά από το μηδέν.
- **Ποτέ ο πίνακας.** Ένας λάθος κωδικός που πληκτρολογείται σε έναν πίνακα δεν μετριέται ποτέ απέναντι στον πίνακα, ώστε τα λάθη ενός ανθρώπου να μη σταματούν τον επόμενο.
- **Ένας κωδικός μόνος του δεν μπορεί να μετρηθεί, γι' αυτό ο πίνακας επιβραδύνεται.** Ένας αναγνώστης καρτών πληκτρολογεί μόνο την κάρτα, και ένα PIN που πληκτρολογείται μόνο του δεν ταιριάζει με κανέναν λογαριασμό όταν είναι λάθος, οπότε δεν υπάρχει λογαριασμός απέναντι στον οποίο να μετρηθεί. Το να μετρηθεί απέναντι στον πίνακα θα έκλεινε έξω τον επόμενο εργαζόμενο για τα λάθη του προηγούμενου, και ο πίνακας δεν κλειδώνει ποτέ. Αντί γι' αυτό, κάθε διαδοχικό λάθος κάνει αυτόν τον πίνακα να περιμένει μισό δευτερόλεπτο περισσότερο πριν ελεγχθεί το επόμενο: 0,5 δευτερόλεπτα μετά το πρώτο λάθος, 1 μετά το δεύτερο, και ούτω καθεξής μέχρι το ανώτατο όριο, 3 δευτερόλεπτα από προεπιλογή. Ένα σωστό ξεκινά πάλι από την αρχή. Έτσι ο επόμενος εργαζόμενος μπαίνει το πολύ μετά το ανώτατο όριο, και όποιος μαντεύει περιορίζεται σε μία προσπάθεια ανά ανώτατο όριο ανά πίνακα: ένα εκατομμύριο εξαψήφια PIN θα έπαιρναν πάνω από έναν μήνα. Οι προσπάθειες που στέλνονται μαζί μπαίνουν σε ουρά και καθεμία περιμένει τη σειρά της. Ένα PIN που πληκτρολογείται με το όνομα χρήστη του δεν επιβραδύνεται· ανήκει στον λογαριασμό και τον κλειδώνει όπως ένας λάθος κωδικός. Η μεγαλύτερη αναμονή είναι στις **Ρυθμίσεις, Εργοστάσιο, Μεγαλύτερη αναμονή ενός πίνακα μετά από λάθος PIN (δευτερόλεπτα)**, 0 έως 30, με το `HOTLOOP_AUTH_PANEL_DELAY_CAP` ως προεπιλογή (διάρκεια, `3s`) και το 0 να την απενεργοποιεί. Τρία δευτερόλεπτα είναι μια παύση που αντέχει ένας εργαζόμενος που έκανε λάθος, και αρκετά αργή ώστε να μετράει για κάποιον που δοκιμάζει κάθε κωδικό. Το βήμα του μισού δευτερολέπτου είναι σταθερό.
- **Ποιος πίνακας είναι ποιος.** Η διεύθυνση του πελάτη: το πρώτο άλμα του `X-Forwarded-For` όταν το όρισε ένα proxy, αλλιώς η ίδια η σύνδεση, που είναι και αυτό που καταγράφει η λίστα συνεδριών. Τίποτα καλύτερο δεν είναι γνωστό πριν από τη σύνδεση: δεν υπάρχει ακόμη συνεδρία, και ένα cookie που μοιράζει ο διακομιστής είναι κάτι που ο πελάτης μπορεί να πετάξει για να ξεκινήσει πάλι την αναμονή. Έτσι πίσω από ένα proxy που ορίζει `X-Forwarded-For` κάθε πίνακας περιμένει μόνος του. Πίσω από ένα που δεν το κάνει, όλοι οι πίνακες μοιράζονται τη διεύθυνση του proxy και επιβραδύνουν ο ένας τον άλλον, το πολύ μέχρι το ανώτατο όριο. Και ένας πελάτης που φτάνει απευθείας στη θύρα μπορεί να στείλει δικό του `X-Forwarded-For` και να αποφύγει την αναμονή. Γι' αυτό αυτό είναι επιβράδυνση και το κλείδωμα του λογαριασμού είναι ο έλεγχος: για μαντεψιά που μετράει, χρησιμοποιήστε τη μορφή με όνομα χρήστη, ή μακριές τυχαίες τιμές καρτών.
- **Λέει ότι ο λογαριασμός υπάρχει.** Το `429` αφορά λογαριασμό που υπάρχει, άρα λέει σε όποιον δοκιμάζει ονόματα ποια υπάρχουν. Αυτό είναι ένα κλείδωμα.

### Τι δεν κάνει

- **Ένας κωδικός μόνος του δεν μπορεί να κλειδωθεί.** Δείτε [Το κλείδωμα](#το-κλείδωμα-μετά-από-λάθος-κωδικούς-και-pin), που εξηγεί γιατί.
- **Καμία προειδοποίηση πριν από την αποσύνδεση.** Ο πίνακας επιστρέφει στο πεδίο του PIN όταν τελειώσει ο χρόνος.
- **Ένας πίνακας που έμεινε συνδεδεμένος με κωδικό** (όπως έπρεπε να λειτουργεί ένας πίνακας πριν από αυτό) λειτουργεί όπως πριν και γράφει ακόμη ως αυτός ο λογαριασμός. Μη δίνετε σε κοινό πίνακα μόνιμη σύνδεση χειριστή· δώστε PIN στους ανθρώπους που τον χρησιμοποιούν.
- **Κανένα πρόγραμμα οδήγησης αναγνώστη, κανένα SSO, κανένα δικαίωμα ανά πίνακα.**

## Διαχείριση χρηστών

Μόνο για admin. Στη διεπαφή είναι οι **Ρυθμίσεις, Χρήστες**: κάθε λογαριασμός με τον ρόλο του, αν είναι ενεργός, και πότε συνδέθηκε τελευταία φορά, με Προσθήκη χρήστη, Επεξεργασία (ρόλος και απενεργοποίηση), Νέος κωδικός και Διαγραφή. Τίποτα δεν σχεδιάζεται για όποιον δεν έχει `users.manage`, ή όταν η ταυτοποίηση είναι απενεργοποιημένη. Ένας λογαριασμός του οποίου τα δικαιώματα καταγράφηκαν ένα προς ένα εμφανίζεται ως `custom` με το πόσα είναι, και η Επεξεργασία κρατά τη λίστα εκτός αν επιλέξετε ρόλο, που την αντικαθιστά. Τα ίδια μέσω του REST API:

Ένας κωδικός είναι 8 έως 72 byte: το 72 είναι το δικό όριο του bcrypt, και ένας μεγαλύτερος απορρίπτεται με αναφορά σε αυτό. Λειτουργεί το ίδιο μέσω OPC UA (δείτε [Ο διακομιστής OPC UA](/el/edge/opc-ua-server/#ποιος-μπορεί-να-συνδεθεί)). σε προηγούμενες εκδόσεις ένας κωδικός πάνω από 64 byte μπορούσε να συνδεθεί εδώ και όχι εκεί.

```sh
# List
curl -H "Authorization: Bearer $TOKEN" https://gateway/api/users

# Create
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"username":"j.smith","password":"something-long","role":"operator"}' \
  https://gateway/api/users

# Disable (does not delete; also revokes every session that account holds)
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"role":"operator","disabled":true}' \
  https://gateway/api/users/j.smith

# Reset a password an operator forgot
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"password":"a-new-one"}' \
  https://gateway/api/users/j.smith/password
```

Αξίζει να γνωρίζετε δύο απορρίψεις πριν εκπλήξουν κάποιον:

- **Δεν μπορείτε να διαγράψετε τον δικό σας λογαριασμό ενώ είστε συνδεδεμένοι με αυτόν.** Μεταβείτε πρώτα σε άλλον λογαριασμό admin.
- **Δεν μπορείτε να απενεργοποιήσετε ή να διαγράψετε τον τελευταίο ενεργό λογαριασμό admin.** Προαγάγετε έναν δεύτερο λογαριασμό σε admin, ή αφήστε έναν ήσυχο, πριν αφαιρέσετε τον πρώτο. Χωρίς αυτόν τον έλεγχο, ένα μόνο λάθος σε έναν σεναριοποιημένο συγχρονισμό χρηστών είναι αποκλεισμός χωρίς καμία συνεδρία admin για να το αναιρέσει.

Κάθε συνδεδεμένος χρήστης μπορεί να αλλάξει τον δικό του κωδικό χωρίς κανέναν από τους δύο περιορισμούς:

```sh
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"currentPassword":"old","newPassword":"new"}' \
  https://gateway/api/auth/password
```

Μια αλλαγή κωδικού ανακαλεί κάθε συνεδρία που κατέχει ο λογαριασμός, μαζί με αυτήν που έκανε το αίτημα. Ο πελάτης αναμένεται να συνδεθεί ξανά.

## Τα διαπιστευτήρια συσκευών είναι μόνο για εγγραφή

Προστέθηκε στην 4.15.1. Πριν, τα `GET /api/devices` και `GET /api/devices/{id}` επέστρεφαν το `config` και το `address` μιας συσκευής ακριβώς όπως αποθηκεύτηκαν, ώστε κάθε συνδεδεμένος χρήστης, και οι viewers, να μπορεί να διαβάσει τον κωδικό του MQTT broker, τα διαπιστευτήρια HTTP και MTConnect, και οτιδήποτε άλλο αποθηκευόταν σε μια συσκευή. Η 4.15.0 έκρυβε μόνο τον κωδικό OPC UA. Από την 4.15.1 τα διαπιστευτήρια μιας συσκευής δεν μπορούν να διαβαστούν πίσω μέσω του API από κανέναν ρόλο, **ούτε από τον admin**. Για να αλλάξετε ένα, στέλνετε νέα τιμή.

### Τι μετράει ως διαπιστευτήριο

| Πρωτόκολλο | Κρυμμένο στη διαμόρφωση | Κρυμμένο επίσης |
|---|---|---|
| MQTT | `password` | οι πληροφορίες χρήστη και οι μυστικές τιμές ερωτήματος στη διεύθυνση (`mqtt://user:pass@broker`) |
| HTTP | `password`· κάθε τιμή στο `headers` εκτός από λίγες απλές (`Accept`, `Accept-Encoding`, `Accept-Language`, `Cache-Control`, `Content-Type`, `User-Agent`)· τα `body` και `writeBody` όταν αναφέρουν διαπιστευτήριο (`password`, `token`, `apiKey`, και παρόμοια)· μια τιμή ερωτήματος με όψη μυστικού στο `writeUrl` | οι πληροφορίες χρήστη και οι μυστικές τιμές ερωτήματος στη διεύθυνση και στο `writeUrl` |
| MTConnect | `password`· κάθε τιμή στο `headers`, με τις ίδιες εξαιρέσεις | οι πληροφορίες χρήστη και οι μυστικές τιμές ερωτήματος στη διεύθυνση |
| OPC UA | `password` | οι πληροφορίες χρήστη στη διεύθυνση κρύβονται κι αυτές, και το πρόγραμμα οδήγησης τις αγνοεί, αφού το URL ενός endpoint OPC UA δεν φέρει διαπιστευτήρια |
| Modbus, S7comm, EtherNet/IP | καμία από τις επιλογές τους δεν είναι διαπιστευτήριο | οι πληροφορίες χρήστη στη διεύθυνση κρύβονται και αγνοούνται από το πρόγραμμα οδήγησης, για τον ίδιο λόγο |

Μια διαδρομή προς ένα αρχείο κλειδιού (`keyFile`) δεν είναι υλικό κλειδιού και εμφανίζεται. Ούτε μια σημαία όπως η `allowInsecureCredentials`.

Οι παραπάνω λίστες ελέγχονται στον κώδικα. Ένα τεστ διαβάζει τη δομή επιλογών κάθε προγράμματος οδήγησης και αποτυγχάνει όταν μια επιλογή δεν είναι ούτε στη λίστα των διαπιστευτηρίων ούτε στη λίστα των επιλογών που είναι γνωστό ότι δεν είναι τέτοιες (`plainConfigKeys`), όταν ένας χάρτης ελεύθερων καταχωρίσεων ή ένα πεδίο ελεύθερου κειμένου δεν είναι στη λίστα των διαπιστευτηρίων, και όταν οποιαδήποτε λίστα αναφέρει κάτι που κανένα πρόγραμμα οδήγησης δεν διαβάζει. Έτσι μια νέα επιλογή δεν μπορεί να κυκλοφορήσει χωρίς να αποφασίσει κάποιος ποια από τις δύο είναι.

Ως δίχτυ ασφαλείας κάτω από τις λίστες, κάθε κλειδί σε οποιοδήποτε βάθος της διαμόρφωσης μιας συσκευής κρύβεται με βάση το όνομά του, σε οποιοδήποτε πρωτόκολλο, όταν περιέχει `password`, `passwd`, `passphrase`, `pwd`, `secret`, `token`, `apikey`, `authorization`, `credential`, `private`, `bearer`, `cookie`, `basicauth`, `signature`, `jwt`, `oauth`, `sessionid` ή `connectionstring`, ή τελειώνει σε `key`, ή έχει ως ολόκληρη λέξη μία από τις `pass`, `pw`, `pwd`, `passwd`, `auth`, `cred`, `creds`, `sig`, `signature`, `sas`, `jwt`, `otp`, `pin` ή `psk`. Οι λέξεις χωρίζονται στα σημεία στίξης και στα όρια από πεζό σε κεφαλαίο, ώστε τα `db_pass`, `smtp_pw`, `apiAuth` και `sasToken` να μετρούν και τα `bypass`, `compass`, `passive`, `authority` και `pinned` όχι. Τα κεφαλαία και τα σημεία στίξης αγνοούνται, όπως και οι γραφές που το `encoding/json` θα διάβαζε ακόμη ως το ίδιο κλειδί (ένα μακρύ s για s, το σύμβολο Kelvin για k). Ο κανόνας των σύντομων λέξεων είναι τραχύς επίτηδες: ένα κλειδί που κανείς δεν έχει εξετάσει, όπως το `authMode`, είναι κρυμμένο μέχρι να προστεθεί στο `plainConfigKeys`.

Μια τιμή που κρύβεται με βάση το όνομα, και ό,τι βρίσκεται κάτω από ένα τέτοιο κλειδί, αντικαθίσταται όποιου τύπου κι αν είναι (ένας αριθμός κρύβεται όπως μια συμβολοσειρά), εκτός από μια λογική τιμή, που δεν μπορεί να είναι διαπιστευτήριο. Μια συμβολοσειρά που φέρει διαπιστευτήριο στο κείμενό της κρύβεται ολόκληρη όπου κι αν βρίσκεται: μια γραμμή εντολών με `--password hunter2`, ένα ζεύγος `password=...` ή μια συμβολοσειρά σύνδεσης, `Authorization: Bearer ...`. Μια συσκευή χωρίς ορισμένο διαπιστευτήριο δεν δείχνει κανένα, ώστε το «χωρίς κωδικό» και το «κωδικός που δεν μπορώ να δω» να ξεχωρίζουν. Μια διαμόρφωση που δεν μπορεί να διαβαστεί ως JSON εμφανίζεται ως `{}` αντί για ό,τι είναι.

Μια κρυμμένη τιμή εμφανίζεται ως `[redacted]`. Σε μια διεύθυνση αντικαθιστά τον κωδικό και κρατά το όνομα χρήστη (`http://svc:[redacted]@meter/api`), ή ολόκληρες τις πληροφορίες χρήστη όταν δεν υπάρχει άνω τελεία, και την τιμή κάθε παραμέτρου με όψη μυστικού του ερωτήματος και του τμήματος (`?fmt=json&token=[redacted]`, `#access_token=[redacted]`). Οι παράμετροι χωρίζονται με `&` ή `;`, ή με τις κωδικοποιημένες μορφές τους `%26` και `%3B`, και η καθεμία κρίνεται μόνη της, ώστε το `?fmt=json` να μένει αναγνώσιμο. Μια παράμετρος με όνομα `code` μετράει ως μυστικό σε μια διεύθυνση, για το κλειδί Azure Functions στο `?code=`, και πουθενά αλλού. Ένα ερώτημα που δεν διαβάζεται καθαρά (μια άκυρη ακολουθία διαφυγής ποσοστού, ένας χαρακτήρας ελέγχου) κρύβεται ολόκληρο αντί να μαντευτεί.

### Αποθήκευση μιας συσκευής

Το `POST /api/devices` δημιουργεί μια συσκευή όταν το id είναι νέο και την αντικαθιστά όταν το id υπάρχει. Δεν υπάρχει ξεχωριστό `PUT`. Για κάθε διαπιστευτήριο στη διεύθυνση και στη διαμόρφωση:

| Τι στέλνει το αίτημα | Αποτέλεσμα |
|---|---|
| Μια νέα συσκευή με πραγματική τιμή | Η τιμή αποθηκεύεται όπως δόθηκε. |
| Μια νέα συσκευή με `[redacted]` | Απορρίπτεται με 400. Η υποκατάστατη τιμή δεν αποθηκεύεται ποτέ ως διαπιστευτήριο. |
| Μια υπάρχουσα συσκευή, `[redacted]` | Η αποθηκευμένη τιμή διατηρείται. |
| Μια υπάρχουσα συσκευή, το κλειδί παραλείπεται | Η αποθηκευμένη τιμή διατηρείται. Ένας πελάτης που δεν γνωρίζει τα μυστικά δεν μπορεί να σβήσει ένα κατά λάθος. |
| Μια υπάρχουσα συσκευή, μια νέα συμβολοσειρά ή ένας νέος αριθμός | Αντικαθιστά την αποθηκευμένη τιμή. |
| Μια υπάρχουσα συσκευή, μια κενή συμβολοσειρά ή `null` | Σβήνει την αποθηκευμένη τιμή. Αυτός είναι ο μοναδικός τρόπος να αφαιρεθεί ένα διαπιστευτήριο. |
| `[redacted]`, χωρίς τίποτα αποθηκευμένο να διατηρηθεί | Απορρίπτεται με 400. |

Η υποκατάστατη τιμή δεν αποθηκεύεται ποτέ, όπου κι αν εμφανίζεται σε μια διαμόρφωση ή διεύθυνση: αντικαθίσταται από την αποθηκευμένη τιμή στο ίδιο σημείο, ή απορρίπτεται όταν δεν υπάρχει.

Δύο λεπτομέρειες. Μέσα στο `headers` (έναν χάρτη του οποίου τις καταχωρίσεις επέλεξε ο άνθρωπος) ο χάρτης είναι η μονάδα: μια καταχώριση που παραλείπεται αφαιρείται, το `{}` τις σβήνει όλες, και η παράλειψη ολόκληρου του κλειδιού `headers` τις διατηρεί. Ένα κλειδί ταιριάζει χωρίς διάκριση πεζών και κεφαλαίων, όπως το ταιριάζουν τα προγράμματα οδήγησης. Και ό,τι δεν είναι διαπιστευτήριο αντικαθίσταται όπως πάντα: μια συσκευή που αποθηκεύεται χωρίς καθόλου `config` κρατά τα διαπιστευτήριά της και τίποτε άλλο.

Ο επεξεργαστής συσκευών της διεπαφής ιστού δείχνει τη διαμόρφωση μιας συσκευής όπως την επιστρέφει το API, με τις υποκατάστατες τιμές, και αποθηκεύει ό,τι δείχνει. Η επεξεργασία μιας συσκευής χωρίς να αγγιχτεί ένα διαπιστευτήριο το διατηρεί, λοιπόν. **Για να αλλάξετε ένα μυστικό στη διεπαφή, αντικαταστήστε το `[redacted]` στη διαμόρφωση (ή στη διεύθυνση) με τη νέα τιμή.** Τίποτα δεν συμπληρώνεται εκ των προτέρων με την παλιά, οπότε όποιος αλλάζει μια συσκευή πρέπει να γνωρίζει το διαπιστευτήριο για να το αλλάξει.

### Η μετακίνηση μιας συσκευής δεν παίρνει μαζί της τα μυστικά της

Τα διατηρημένα διαπιστευτήρια στέλνονται σε ό,τι δείχνει η συσκευή. Αν διατηρούνταν όταν μετακινείται μια συσκευή, όποιος επιτρέπεται να αποθηκεύσει μια συσκευή θα μπορούσε να διαβάσει ένα αποθηκευμένο διαπιστευτήριο δείχνοντάς την σε έναν δικό του ακροατή και αφήνοντας την πύλη να το παρουσιάσει. Έτσι, όταν μια αποθήκευση αλλάζει τον κεντρικό υπολογιστή ή τη θύρα στη διεύθυνση, ή στο `writeUrl`, και θα διατηρούσε ένα αποθηκευμένο διαπιστευτήριο (με υποκατάστατη τιμή ή με παράλειψη), απορρίπτεται με 400 που κατονομάζει τα διαπιστευτήρια. Εισαγάγετέ τα ξανά, ή στείλτε μια κενή συμβολοσειρά για να τα σβήσετε. Η αλλαγή της διαδρομής, του σχήματος ή οτιδήποτε άλλου στη συσκευή δεν μετράει ως μετακίνηση, και μια συσκευή χωρίς αποθηκευμένο διαπιστευτήριο μπορεί να μετακινηθεί ελεύθερα.

### Πού δεν εμφανίζεται ένα διαπιστευτήριο

Για μια συσκευή κάθε πρωτοκόλλου, με διαπιστευτήριο σε κάθε δυνατό σημείο, τα τεστ το αναζητούν σε: κάθε endpoint συσκευών (απαντήσεις λίστας, ανάγνωσης, δημιουργίας και ενημέρωσης) για έναν viewer, έναν operator και έναν admin· κάθε άλλο endpoint ανάγνωσης· τα `/api/diagnostics` και `/api/status`· το `/api/sites` και τους εξερχόμενους διακομιστές MCP που απαριθμεί· τη ζωντανή ροή συμβάντων· το αρχείο καταγραφής του συστήματος και τον έλεγχο εγγραφών· τις απαντήσεις σφάλματος· κάθε εργαλείο και πόρο MCP· και το αρχείο καταγραφής της διεργασίας σε επίπεδο debug, από το runtime και από τα προγράμματα οδήγησης. Το κείμενο σφάλματος ενός προγράμματος οδήγησης και τα συμβάντα και τα αρχεία καταγραφής του runtime καθαρίζονται από τα διαπιστευτήρια μιας συσκευής, κατά τιμή και κατά μορφή, επειδή ένα σφάλμα μπορεί να επαναλάβει μια διεύθυνση ή την απάντηση ενός διακομιστή. Ένα διαπιστευτήριο ενός ή δύο χαρακτήρων αντικαθίσταται μόνο όπου στέκεται ως λέξη από μόνο του, αφού η αντικατάσταση παντού θα κατέστρεφε το μήνυμα.

### Πού τα διαπιστευτήρια είναι ακόμη σε καθαρό κείμενο

Το μόνο για εγγραφή αφορά το API. Η πύλη χρειάζεται τις πραγματικές τιμές για να συνδεθεί, και αυτά τα σημεία τις κρατούν όπως αποθηκεύονται:

- **Η βάση δεδομένων.** Τα διαπιστευτήρια συσκευών βρίσκονται στις στήλες `config` και `address`. Με ορισμένο το `HOTLOOP_SECRET_KEY_FILE`, τα κλειδωμένα στο `config` (κάθε `password`, τιμές κεφαλίδων) κρυπτογραφούνται με κλειδί που φυλάσσεται έξω από τη βάση, και το ίδιο μια διεύθυνση ή επιλογή με διαπιστευτήριο γραμμένο στο κείμενό της (`mqtt://user:pass@host`, `?token=`), σφραγισμένα ολόκληρα. Δείτε [Αντίγραφα ασφαλείας και επαναφορά](/el/iot/backup/#διαπιστευτήρια-συσκευών-και-το-μυστικό-κλειδί).
- **Τα αντίγραφα ασφαλείας.** Το `devices.copy` σε ένα αντίγραφο τα περιέχει, κρυπτογραφημένα ή όχι ακριβώς όπως η βάση δεδομένων. Δείτε [Αντίγραφα ασφαλείας και επαναφορά](/el/iot/backup/#προστατέψτε-τα-αρχεία-αντιγράφων).
- **Τα αρχεία συσκευών του Edge Relay.** Το relay διαβάζει ένα αρχείο JSON που φέρει τα διαπιστευτήρια των συσκευών του. Δείτε [Αναφορά Edge Relay](/el/edge-relay/reference/#διαπιστευτήρια-στο-αρχείο-συσκευών-4150).
- **Η ώθηση διαμόρφωσης στον στόλο.** Ένα αρχείο συσκευών που ωθείται σε ένα relay δημοσιεύεται σε ένα θέμα MQTT, retained, ως έχει. Δείτε [Διαχείριση στόλου](/el/gateway/fleet/).

Προστατέψτε αναλόγως τη βάση δεδομένων, τον τόμο αντιγράφων, το αρχείο συσκευών του relay και τον broker. Η απόκρυψη στο API δεν αλλάζει κανένα από αυτά.

### Αν μη αξιόπιστοι χρήστες μπορούσαν να φτάσουν στο API

Πριν από την 4.15.1, κάθε συνδεδεμένος χρήστης μπορούσε να διαβάσει αποθηκευμένα διαπιστευτήρια συσκευών μέσω του API. Ένας φορέας λειτουργίας του οποίου η πύλη ήταν προσβάσιμη σε χρήστες που δεν έπρεπε να την έχουν (ένας λογαριασμός viewer που δόθηκε σε εργολάβο, για παράδειγμα) πρέπει να αλλάξει τα διαπιστευτήρια των συσκευών που κρατά: τον MQTT broker, τα endpoints HTTP και MTConnect, και τους λογαριασμούς OPC UA. Δεν έχει υπάρξει δημόσια έκδοση από την 4.3.1, οπότε η έκθεση περιορίζεται σε εγκαταστάσεις μη δημοσιευμένων builds.

## Τι καταγράφει το ίχνος ελέγχου

Κάθε εγγραφή περνούσε ήδη από το `write_audit` με μια στήλη `actor`, δείτε την πύλη εγγραφής στο κύριο README. Αυτή η στήλη προέρχεται τώρα από τη συνεδρία, όχι από κεφαλίδα, και σε έναν πίνακα kiosk η συνεδρία είναι ο άνθρωπος που συνδέθηκε με το PIN ή την κάρτα του:

```
> write_tag tag=press-01/Zone1_Temp value=99 reason="testing"
```

καταγράφει `j.smith`, το όνομα χρήστη της συνεδρίας που έκανε την κλήση, όχι ό,τι έτυχε να πει το `X-Forwarded-User`. Οι συνδέσεις, οι συνδέσεις kiosk, οι αποσυνδέσεις, οι αλλαγές κωδικών και κάθε ενέργεια διαχείρισης χρηστών, μαζί με τον ορισμό ή τη διαγραφή ενός PIN (ποτέ το ίδιο το PIN), καταγράφονται στο αρχείο καταγραφής του συστήματος (`GET /api/events`, κατηγορία `auth`) για τον ίδιο λόγο που υπάρχει ο έλεγχος εγγραφών: μια αλλαγή σε έξι μήνες πρέπει να μπορεί να εξηγηθεί, όχι απλώς να φαίνεται.

## Λειτουργία χωρίς σύνδεση

Ορίστε `HOTLOOP_AUTH_INSECURE=true` (ή `auth.insecure: true` στο chart) για να λειτουργεί ακριβώς όπως κάθε έκδοση πριν από την 4.4.0: χωρίς απαίτηση συνεδρίας, ο δράστης που καταγράφεται για μια εγγραφή προέρχεται από το `X-EmberNET-User` ή παρόμοιες κεφαλίδες proxy, και πέφτει στο `"operator"` αν δεν έχει οριστεί καμία.

Είναι μια πραγματική και υπερασπίσιμη επιλογή για μια εγκατάσταση όπου το ίδιο το NetworkPolicy του πίνακα ελέγχου EmberNet είναι το πραγματικό όριο και τίποτε άλλο δεν μπορεί να φτάσει στο pod. Δεν είναι πλέον η προεπιλογή επειδή είναι εύκολο να πιστέψει κανείς ότι αυτή η συνθήκη ισχύει και δύσκολο να την επαληθεύσει μέσα από το ίδιο το pod: όλο το νόημα της 4.4.0 είναι ότι ένα λάθος σε ένα NetworkPolicy, ή μια εγκατάσταση που αποδεικνύεται τελικά ότι δεν είναι πίσω από τον πίνακα ελέγχου, δεν πρέπει να σημαίνει επιπλέον ότι το `actor(r)` επιστρέφει κάτι που επέλεξε ένας επιτιθέμενος.

Το `config.Validate` αρνείται να ξεκινήσει με την ταυτοποίηση ούτε ενεργοποιημένη ούτε αναγνωρισμένη με αυτόν τον τρόπο, ακριβώς ώστε το «χωρίς ταυτοποίηση» να είναι πάντα μια απόφαση που πήρε κάποιος επίτηδες, γραμμένη στη δική της διαμόρφωση της εγκατάστασης, και όχι μια προεπιλογή που δεν επέλεξε κανείς.

## Σύνδεση από τον πίνακα ελέγχου EmberNet

Ένας tenant που εγκαθιστά το HotLoop από το App Store του EmberNet πηγαίνει από το LAUNCH στην εφαρμογή ήδη συνδεδεμένος ως ο ίδιος, χωρίς να μοιραστεί κανένας κωδικός. Ο οικοδεσπότης εφαρμογών του πίνακα ελέγχου βάζει το `X-Embernet-Assertion` σε κάθε αίτημα που φέρνει σε αυτό το pod: ένα token ES256, έγκυρο για περίπου ένα λεπτό, υπογεγραμμένο με ένα ιδιωτικό κλειδί που κατέχει μόνο ο πίνακας ελέγχου. Κατονομάζει τον άνθρωπο (`email`), τον tenant, τη μία εφαρμογή για την οποία φτιάχτηκε (`aud`, `<tenant>/<Service name>`) και τον ρόλο HotLoop στον οποίο ο tenant αντιστοιχίζει τον ρόλο του ανθρώπου στον πίνακα ελέγχου (`role`: `admin`, `operator` ή `viewer`).

Είναι απενεργοποιημένο εκτός αν έχει ρυθμιστεί δημόσιο κλειδί, και τότε όλα τα άλλα λειτουργούν όπως πριν: τοπικοί λογαριασμοί, το cookie, το bearer token, ο πίνακας kiosk.

| Μεταβλητή | Τιμή chart | Κάνει |
|---|---|---|
| `HOTLOOP_AUTH_ASSERTION_PUBLIC_KEY` | `embernetSignin.publicKey` | το ΔΗΜΟΣΙΟ κλειδί του πίνακα ελέγχου, PKIX PEM, ECDSA P-256. Το store το συμπληρώνει κατά την εγκατάσταση. |
| `HOTLOOP_AUTH_ASSERTION_AUDIENCE` | υπολογίζεται από το namespace και το όνομα του release | `<tenant>/<Service name>`. Απαιτείται μαζί με το κλειδί· ένα token που φτιάχτηκε για άλλη εφαρμογή ή άλλον tenant απορρίπτεται. |
| `HOTLOOP_AUTH_ASSERTION_ISSUER` | `embernetSignin.issuer` | `embernet-dashboard` |
| `HOTLOOP_AUTH_ASSERTION_HEADER` | `embernetSignin.header` | `X-Embernet-Assertion` |

Τι κάνει μια καλή δήλωση: ο άνθρωπος αποκτά έναν χρήστη εδώ την πρώτη φορά που ο πίνακας ελέγχου εγγυάται γι' αυτόν (με όνομα από τη διεύθυνσή του, χωρίς κωδικό, ώστε να μην υπάρχει τίποτα να μαντευτεί), ο ρόλος του χρήστη ακολουθεί ό,τι έστειλε ο πίνακας ελέγχου σε κάθε αίτημα, και το ίχνος ελέγχου τον κατονομάζει. Τι κάνει μια κακή: 401, και δεν παραμερίζεται σιωπηλά υπέρ ενός cookie συνεδρίας που τυχαίνει να υπάρχει. Απορρίπτονται μια κακή υπογραφή, κάθε αλγόριθμος εκτός από ES256, ένα ληγμένο ή όχι ακόμη έγκυρο token, ένα που ζει πάνω από δέκα λεπτά, λάθος εκδότης, το audience άλλης εφαρμογής ή tenant, μια δήλωση tenant που διαφωνεί με το audience, ένας ρόλος που δεν είναι δικός μας και ένα όνομα χωρίς διεύθυνση.

Ένας τοπικός admin έχει τον τελευταίο λόγο για κάποιον που άφησε να μπει ο πίνακας ελέγχου: απενεργοποιήστε τον χρήστη και μένει έξω, και δώστε του ρητή λίστα δικαιωμάτων και την κρατά. Οι εγγραφές εξακολουθούν να χρειάζονται τους δικούς του διακόπτες εγγραφής του pod· μια δήλωση δεν τους διευρύνει ποτέ. Η αποσύνδεση από μια συνεδρία που δημιούργησε ο πίνακας ελέγχου δεν τη τερματίζει: η πρόσβαση τελειώνει στο επόμενο αίτημα που ο πίνακας ελέγχου σταματά να υπογράφει.

## Τι δεν καλύπτει ακόμη αυτό

- **Όχι OpenID Connect.** Τοπικοί λογαριασμοί, συν την υπογεγραμμένη δήλωση του πίνακα ελέγχου EmberNet που περιγράφηκε παραπάνω. Μια ενσωμάτωση παρόχου ταυτότητας δεν έχει υλοποιηθεί.
- **Όχι ρόλοι ανά tenant ή ανά εγκατάσταση.** Τα δικαιώματα ενός χρήστη είναι τα ίδια παντού όπου τρέχει το Gateway, κάτι που είναι εντάξει για ένα εργοστάσιο και θα χρειαζόταν περισσότερη σκέψη για τη συγκεντρωτική εικόνα πολλών τοποθεσιών στο `Sites`.
- **Όχι κλείδωμα για PIN ή κάρτα που πληκτρολογείται μόνη της,** μόνο για κωδικό και για PIN με το όνομα χρήστη του· δείτε [Το κλείδωμα](#το-κλείδωμα-μετά-από-λάθος-κωδικούς-και-pin). Η σύγκριση σταθερού χρόνου στο `handleLogin` εμποδίζει την απαρίθμηση ονομάτων χρηστών από τον χρόνο απόκρισης. Ένα NetworkPolicy ή ένα proxy ανάντη αξίζει πάντα να υπάρχει μπροστά από το endpoint σύνδεσης.
