Αυτό το έγγραφο λέει ακριβώς τι μιλάει η πύλη, μέχρι πού έχει επαληθευτεί κάθε driver και τι να κάνετε για όλα τα υπόλοιπα. Είναι το πρώτο που πρέπει να διαβάσετε και αυτό στο οποίο πρέπει να βασιστείτε όταν κάτι διαφωνεί μαζί του.

Η λίστα των εγγενών πρωτοκόλλων προκύπτει από τους drivers που είναι μεταγλωττισμένοι μέσα στο εκτελέσιμο: το `/api/protocols`, η οθόνη Πρωτόκολλα και το εργαλείο MCP `describe_protocol` διαβάζουν όλα το ίδιο μητρώο. Ο κατάλογος δεν μπορεί να διαφημίσει πρωτόκολλο που δεν έχει το εκτελέσιμο.

## Κατάσταση επαλήθευσης

Κάθε πρωτόκολλο που μιλάει εγγενώς το HotLoop έχει μετακινήσει πραγματικές τιμές από πραγματικό διακομιστή ή συσκευή και έχει τρέξει σε πραγματικό υλικό (2026-11-17). Όπου υπάρχει ανεξάρτητη υλοποίηση, το HotLoop έχει τρέξει απέναντί της και προς τις δύο κατευθύνσεις.

| Πρωτόκολλο | Εγγενές | Κατάσταση |
|---|---|---|
| Modbus TCP/RTU | ναι | **επαληθευμένο ζωντανά** |
| OPC UA | ναι | **επαληθευμένο ζωντανά**, συμπεριλαμβανομένου του Ignition 8.3.9 προς τις δύο κατευθύνσεις με όνομα χρήστη και κωδικό πρόσβασης μέσω ασφαλούς καναλιού |
| MQTT / Sparkplug B | ναι | **επαληθευμένο ζωντανά** |
| MTConnect | ναι | **επαληθευμένο ζωντανά** |
| HTTP / REST | ναι | **επαληθευμένο ζωντανά** |
| S7comm | ναι | **επαληθευμένο ζωντανά** (πραγματικό υλικό, 2026-11-17) |
| EtherNet/IP | ναι | **επαληθευμένο ζωντανά** (πραγματικό υλικό, 2026-11-17) |
| UniFi Network | ναι | **επαληθευμένο ζωντανά**, μόνο για ανάγνωση, σε πραγματικές κονσόλες και switches, με τις συνδέσεις WAN και το failover |
| SNMP | ναι | **επαληθευμένο ζωντανά**, μόνο για ανάγνωση, μέσω v1, v2c και v3 σε κάθε επίπεδο ασφάλειας |
| CODESYS | ναι | **επαληθευμένο ζωντανά**, αναγνώσεις και εγγραφές, συμπεριλαμβανομένου ενός προγράμματος με πάνω από 100.000 μεταβλητές που διαβάστηκε σε 2,4 δευτερόλεπτα |
| BACnet/IP | ναι | **επαληθευμένο ζωντανά**, μόνο για ανάγνωση |
| OPC UA PubSub (UADP) | ναι | **επαληθευμένο ζωντανά**, προς τις δύο κατευθύνσεις |
| Kafka API (έξοδος) | ναι | **επαληθευμένο ζωντανά** απέναντι σε Apache Kafka και Redpanda, με TLS και σύνδεση SASL |

Οι κατασκευαστές διαφέρουν ως προς τις προεπιλογές τους: ποια πιστοποιητικά και πολιτικές token προσφέρει ένας διακομιστής OPC UA, τι βάζει ένας ελεγκτής BACnet στη λίστα αντικειμένων του, ποια MIB εξυπηρετεί μια συσκευή SNMP, πώς αριθμεί τα δεδομένα του ένα PLC. Μια νέα συσκευή σε ένα νέο εργοστάσιο παραμένει εργασία θέσης σε λειτουργία, οπότε συγκρίνετε μια γνωστή τιμή στον ανιχνευτή της ενσωμάτωσης με την ένδειξη της ίδιας της συσκευής πριν εμπιστευτείτε μια οθόνη.

## Εγγενή πρωτόκολλα

### OPC UA

Προτιμήστε αυτό όταν μια συσκευή δίνει επιλογή. Περιηγείται, είναι σωστά ασφαλισμένο και εγγράφεται.

Ο driver **εγγράφεται αντί να κάνει polling**. Ο διακομιστής στέλνει μια τιμή όταν αλλάζει, με ρυθμό που μπορεί να αντέξει, αντί να του τίθεται η ίδια ερώτηση σε κάθε κύκλο από έναν client που δεν ξέρει αν κάτι κινήθηκε. Αν ένας διακομιστής αρνηθεί μια εγγραφή, ο driver επιστρέφει σε ομαδικές αναγνώσεις αντί να αποτύχει η συσκευή.

Επιστρέφει επίσης όταν μια εγγραφή δεν παραδίδει τίποτα απολύτως. Ένας διακομιστής στέλνει την τρέχουσα τιμή κάθε κόμβου στην πρώτη του δημοσίευση και δεν την ξαναστέλνει μέχρι να αλλάξει, οπότε μια χαμένη πρώτη δημοσίευση σημαίνει μια τιμή στόχου που διαβάζεται ως κακή για όσο διαρκεί η συνεδρία. Αν περάσουν δέκα διαστήματα δημοσίευσης (τουλάχιστον πέντε δευτερόλεπτα) χωρίς καμία τιμή από την εγγραφή, ο driver καταγράφει μια προειδοποίηση, διαγράφει την εγγραφή και διαβάζει τα tags σε κάθε polling μέχρι να επανασυνδεθεί η συσκευή. Η βιβλιοθήκη client OPC UA πάνω στην οποία είναι χτισμένος αυτός ο driver μπορεί να ξεκινήσει τον βρόχο δημοσίευσής της σε παύση σε φορτωμένο host και να μην στείλει ποτέ αίτημα δημοσίευσης· γι' αυτήν την περίπτωση υπάρχει αυτό.

Επιστρέφει επίσης όταν μια εγγραφή σταματά αφού έχουν φτάσει τιμές. Η βιβλιοθήκη κρατά τα keep-alive για τον εαυτό της, οπότε ένας σταματημένος βρόχος δημοσίευσης μοιάζει ακριβώς με ένα εργοστάσιο όπου τίποτα δεν αλλάζει. Αφού μια εγγραφή μείνει σιωπηλή για δέκα διαστήματα δημοσίευσης (τουλάχιστον τριάντα δευτερόλεπτα), ο driver διαβάζει κάθε κόμβο μία φορά και τον συγκρίνει με ό,τι παρέδωσε τελευταία η εγγραφή. Αν κάποιος κόμβος διαφέρει σε τιμή ή ποιότητα, ο διακομιστής κρατά κάτι που θα είχε στείλει, οπότε ο driver καταγράφει μια προειδοποίηση, διαγράφει την εγγραφή και διαβάζει σε κάθε polling μέχρι να επανασυνδεθεί η συσκευή. Αν ταιριάζουν, συνεχίζει και ελέγχει ξανά μετά την ίδια σιωπή. Μια υγιής σιωπηλή εγγραφή κοστίζει μία ομαδική ανάγνωση κάθε τριάντα δευτερόλεπτα.

**Διευθυνσιοδοτήστε τους κόμβους με URI χώρου ονομάτων.** Αυτό μετράει περισσότερο απ' όσο φαίνεται:

```
nsu=http://opcua.edge.server;s=Zone1_Temperature    good
ns=3;s=Zone1_Temperature                            works until it doesn't
```

Ένας *δείκτης* χώρου ονομάτων ανατίθεται με όποια σειρά τυχαίνει να φορτώσει ο διακομιστής τους χώρους ονομάτων του. Προσθέστε έναν χώρο ονομάτων, αναβαθμίστε το firmware, και ο δείκτης 3 γίνεται αθόρυβα κάτι άλλο: κάθε ένδειξη είναι τότε λάθος χωρίς κανένα σφάλμα πουθενά. Το URI είναι μέρος του μοντέλου και δεν μετακινείται. Το `Browse` επιστρέφει τη μορφή URI ακριβώς γι' αυτόν τον λόγο.

Μια γυμνή συμβολοσειρά απορρίπτεται ως διεύθυνση. Διαβασμένο ως `ns=0;s=Temperature`, ένα τυπογραφικό λάθος θα αναλυόταν χωρίς πρόβλημα ως κόμβος που δεν υπάρχει και το tag θα διαβαζόταν κακό για πάντα. Απαιτείται ρητή μορφή ώστε το λάθος να βγει στην επιφάνεια όταν το αποθηκεύετε.

**Ο εντοπισμός tags δηλώνει κάθε tag με τον τύπο που λέει ο διακομιστής ότι έχει ο κόμβος**: το Boolean είναι `bool`, οι ακέραιοι τύποι κρατούν το πλάτος τους (`int16`, `uint16`, `int32`, `uint32`, `int64`, `uint64`· τα SByte και Byte παίρνουν το επόμενο μέγεθος), τα Float και Double είναι `float`, και τα String, DateTime, LocalizedText και οι άλλοι τύποι που ο driver διαβάζει ως κείμενο είναι `string`. Ένας τύπος που ο διακομιστής δεν δηλώνει, ή ένας χωρίς καλύτερο όνομα (μια απαρίθμηση, μια δομή), μένει `float`. Μέχρι την εργασία με το Ignition παρακάτω, κάθε tag που εντοπιζόταν ήταν `float`. Ο driver διάβαζε ακόμη το κείμενο ενός κόμβου String, αλλά το tag έλεγε float, και ο ίδιος ο διακομιστής OPC UA του Gateway δημοσιεύει ένα tag με τον τύπο με τον οποίο είναι δηλωμένο, οπότε ένας client αυτού του διακομιστή έπαιρνε `Bad_TypeMismatch`. Το Ignition έδειξε το `System_Status` του Emberburn ακριβώς έτσι. Τα tags που εισήχθησαν πριν από τη διόρθωση κρατούν τον τύπο τους: αλλάξτε με το χέρι ένα tag κειμένου σε `string`.

Ρύθμιση: οι επιλογές ασφάλειας, ταυτότητας και πιστοποιητικών περιγράφονται στο [OPC UA: ασφάλεια και διαπιστευτήρια](#opc-ua-ασφάλεια-και-διαπιστευτήρια). Οι υπόλοιπες είναι `subscribe`, `publishIntervalMs`, `samplingIntervalMs`, `queueSize`, `sessionTimeoutMs`, `browseMaxNodes`, `browseRoot` και `browseServerNodes`. Ένα όνομα επιλογής που ο driver δεν γνωρίζει είναι σφάλμα που απαριθμεί αυτά που γνωρίζει, όχι ρύθμιση που αγνοείται σιωπηλά: ένα τυπογραφικό λάθος στο `securityMode` θα συνδεόταν χωρίς καμία ασφάλεια και θα έμοιαζε ακριβώς με συσκευή που λειτουργεί.

**Ο εντοπισμός tags παραλείπει το ίδιο το αντικείμενο `Server` του διακομιστή** (`i=2253`: την κατάστασή του, τις δυνατότητες, τα διαγνωστικά, τον πίνακα χώρων ονομάτων και τη ρύθμιση). Κάθε διακομιστής OPC UA έχει ένα και μπορεί να είναι εκατοντάδες μεταβλητές ανάμεσα σε αυτές του εργοστασίου. Ορίστε `browseServerNodes` σε `true` στη συσκευή για να τις πάρετε πίσω, ή ορίστε `browseRoot` σε `i=2253` για να κοιτάξετε μέσα επίτηδες· μια περιήγηση που ξεκινά εκεί το διατρέχει παρ' όλα αυτά.

### OPC UA: ασφάλεια και διαπιστευτήρια

Μέχρι την 4.15.0 ο driver μπορούσε να κάνει μόνο ανώνυμη, μη ασφαλή σύνδεση, και όχι σε κάθε διακομιστή που ακολουθεί την προδιαγραφή: δεν ρωτούσε ποτέ τον διακομιστή ποιες πολιτικές token ταυτότητας προσφέρει, οπότε έστελνε κενό id πολιτικής token, που ένας συμβατός διακομιστής απορρίπτει. Αυτό περιλάμβανε τον ίδιο τον διακομιστή OPC UA του HotLoop. Ο driver τώρα ανακαλύπτει τα endpoints του διακομιστή, διαλέγει ένα που ταιριάζει με τη συσκευή και επαναλαμβάνει το id πολιτικής που απαρίθμησε εκείνο το endpoint.

#### Επιλογές συσκευής

| Επιλογή | Προεπιλογή | Τι κάνει |
|---|---|---|
| `securityMode` | `None` | `None`, `Sign` ή `SignAndEncrypt`. Αν παραλειφθεί με `securityPolicy` διαφορετικό από `None`, είναι `SignAndEncrypt`. |
| `securityPolicy` | η καλύτερη που προσφέρει ο διακομιστής για τη λειτουργία | `None`, `Basic256Sha256`, `Aes128_Sha256_RsaOaep` ή `Aes256_Sha256_RsaPss`. Τα `Basic128Rsa15` και `Basic256` απορρίπτονται. |
| `username`, `password` | ανώνυμο | Πιστοποίηση με όνομα χρήστη. |
| `userCertificate`, `userPrivateKey` | κανένα | Πιστοποίηση χρήστη X.509: η συνεδρία συνδέεται ως ο χρήστης στον οποίο ο διακομιστής αντιστοιχίζει αυτό το πιστοποιητικό, χωρίς κωδικό πρόσβασης. Και τα δύο σε PEM, ορίζονται μαζί. Το κλειδί είναι RSA (η βιβλιοθήκη OPC UA υπογράφει μόνο με RSA· ένα κλειδί EC απορρίπτεται με σχετικό μήνυμα) και είναι μυστικό όπως ο κωδικός πρόσβασης: σφραγισμένο σε αδράνεια, κρυμμένο σε κάθε απάντηση του API, δεν καταγράφεται ποτέ. Το πιστοποιητικό είναι του χρήστη, όχι το πιστοποιητικό της εφαρμογής client στο `certFile`. Αν έχει οριστεί και `username`, χρησιμοποιείται το πιστοποιητικό. Με τον ίδιο τον διακομιστή του HotLoop το πιστοποιητικό πρέπει πρώτα να συνδεθεί με έναν χρήστη ([Ο διακομιστής OPC UA](/el/edge/opc-ua-server/#πιστοποιητικά-χρήστη-x509)). |
| `allowInsecureCredentials` | `false` | Επιτρέπει την αποστολή κωδικού πρόσβασης μέσω μη ασφαλούς καναλιού (`securityMode` `None`), ή όταν δεν τον κρυπτογραφεί τίποτα. |
| `certFile`, `keyFile` | παράγονται | Το πιστοποιητικό εφαρμογής αυτού του client και το κλειδί RSA του, για ασφαλή λειτουργία. Ορίστε και τα δύο ή κανένα. |
| `pkiDir` | `HOTLOOP_OPCUA_CLIENT_PKI_DIR` (`/data/opcua-client-pki`) | Όπου βρίσκονται το παραγόμενο πιστοποιητικό και οι αποθήκες `trusted/` και `rejected/`. |
| `serverCertThumbprints` | κανένα | Αποτυπώματα SHA-1 (40 δεκαεξαδικά ψηφία) ή SHA-256 (64) πιστοποιητικών διακομιστή που θα εμπιστεύεται χωρίς αρχείο στο `trusted/`. Οι άνω και κάτω τελείες και τα κενά αγνοούνται. |
| `insecureSkipVerify` | `false` | Δέχεται οποιοδήποτε πιστοποιητικό διακομιστή. |

Μια συσκευή χωρίς καμία από αυτές είναι ό,τι ήταν πάντα: ανώνυμη, μέσω μη ασφαλούς καναλιού.

#### Πώς ο driver διαλέγει endpoint

Ο driver ζητά από τον διακομιστή τα endpoints του μέσω μη ασφαλούς καναλιού, κάτι που η προδιαγραφή υποχρεώνει τους διακομιστές να επιτρέπουν για την ανακάλυψη και που δεν μεταφέρει τίποτα μυστικό, αφού η λίστα των endpoints είναι δημόσια εκ σχεδιασμού. Κρατά τα endpoints των οποίων η λειτουργία και πολιτική ασφάλειας ταιριάζουν με τη συσκευή και, μεταξύ αυτών, την πολιτική token για την ταυτότητα της συσκευής (ανώνυμη, ή όνομα χρήστη όταν έχει οριστεί `username`). Το token ταυτότητας που στέλνει στη συνέχεια φέρει το id πολιτικής που απαρίθμησε εκείνο το endpoint· δεν στέλνει ποτέ κενό.

- **Δεν επιλέγει ποτέ `Basic128Rsa15` ή `Basic256`.** Και τα δύο έχουν καταργηθεί από το OPC Foundation. Αυτό ισχύει όταν το ένα έχει το υψηλότερο επίπεδο ασφάλειας της λίστας, που είναι ο τρόπος με τον οποίο οι διακομιστές τα κατατάσσουν, και όταν το ένα είναι το μόνο που προσφέρει ο διακομιστής, οπότε η σύνδεση αποτυγχάνει με σφάλμα που το λέει. Μια συσκευή δεν μπορεί να ρυθμιστεί να χρησιμοποιεί κάποιο, και μια πολιτική token που θα κρυπτογραφούσε κωδικό με κάποιο απορρίπτεται επίσης. Ο ίδιος ο διακομιστής του HotLoop προσφέρει και τα δύο δίπλα στις σύγχρονες πολιτικές και δεν μπορεί να τα απενεργοποιήσει, οπότε αυτό δοκιμάζεται απέναντι σε πραγματικό διακομιστή, και οι δοκιμές ελέγχουν ότι το URI καμίας από τις δύο πολιτικές δεν εμφανίζεται σε όσα στέλνει ο driver.
- **Όταν η συσκευή δεν ονομάζει πολιτική, προτιμά `Basic256Sha256`, μετά `Aes128_Sha256_RsaOaep`, μετά `Aes256_Sha256_RsaPss`**, όποιο επίπεδο ασφάλειας κι αν τους δίνει ο διακομιστής. Η σειρά είναι ανάλογα με το πόσο ευρέως λειτουργεί κάθε μία, όχι με την ισχύ. Μερικοί διακομιστές δεν μπορούν να ανοίξουν κανάλι με `Aes256_Sha256_RsaPss` και κλείνουν τη σύνδεση χωρίς να πουν γιατί, οπότε χρησιμοποιείται μόνο όταν μια συσκευή την ονομάσει.
- **Αν τίποτα δεν ταιριάζει, το σφάλμα απαριθμεί ό,τι προσφέρει πραγματικά ο διακομιστής**, με την πολιτική και το id πολιτικής token κάθε endpoint, ώστε η ρύθμιση να διορθώνεται από το μήνυμα και μόνο.

#### Το πιστοποιητικό του ίδιου του client

Κάθε ασφαλής λειτουργία χρειάζεται πιστοποιητικό εφαρμογής. Αν η συσκευή ονομάζει `certFile` και `keyFile`, χρησιμοποιούνται ως έχουν, μετά από ελέγχους (RSA, τουλάχιστον 2048 bit, όχι ληγμένο). Διαφορετικά δημιουργείται ένα αυτο-υπογεγραμμένο κατά την πρώτη χρήση και φυλάσσεται στον κατάλογο PKI: RSA-2048, πέντε χρόνια, το URI εφαρμογής `urn:hotloop:client:<host name>` στα subject alternative names, το κλειδί με λειτουργία `0600`, το πιστοποιητικό με `0644` και οι κατάλογοι με `0750`. Η διάταξη αντικατοπτρίζει αυτή του διακομιστή OPC UA:

```
own/cert.pem, own/key.pem   this client's certificate
trusted/                    server certificates an operator has approved
rejected/                   server certificates the driver turned away
```

Δεν δημιουργείται ξανά σε μια συνηθισμένη εκκίνηση, ώστε ένας διακομιστής στον οποίο έχει ειπωθεί να το εμπιστεύεται να μην ενημερώνεται ξανά. Αντικαθίσταται, με προειδοποίηση ότι κάθε διακομιστής πρέπει να εγκρίνει το νέο, μόνο αν δεν μπορεί να διαβαστεί, δεν είναι RSA τουλάχιστον 2048 bit ή του απομένουν λιγότερες από 30 ημέρες. Συσκευές που ξεκινούν την ίδια στιγμή μοιράζονται ένα πιστοποιητικό αντί να γράφει η καθεμία το δικό της.

Ο κατάλογος πρέπει να είναι εγγράψιμος και μόνιμος. Στο chart του Helm αυτό είναι το `opcuaClient.persistence.enabled` (απενεργοποιημένο από προεπιλογή, επειδή προσθέτει ένα volume σε υπάρχουσα εγκατάσταση)· στο edge relay είναι το υπάρχον volume `/data`. Χωρίς εγγράψιμο κατάλογο, μια ασφαλής συσκευή αναφέρει σφάλμα που ονομάζει τη μεταβλητή που πρέπει να οριστεί, αντί να συνδεθεί με πιστοποιητικά που θα χάνονταν στην επόμενη επανεκκίνηση.

Ο **διακομιστής** πρέπει επίσης να εμπιστεύεται αυτό το πιστοποιητικό, κάτι που είναι ρύθμιση του ίδιου του διακομιστή. Για τον ίδιο τον διακομιστή του HotLoop είναι η ίδια κίνηση: το πιστοποιητικό του driver εμφανίζεται στον κατάλογο `rejected/` του διακομιστή μετά την πρώτη απορριφθείσα απόπειρα, και η μετακίνησή του στο `trusted/` το εγκρίνει. Όταν ένας διακομιστής κλείνει τη σύνδεση ενώ ανοίγει το ασφαλές κανάλι, που είναι ο τρόπος με τον οποίο πολλοί διακομιστές απορρίπτουν ένα πιστοποιητικό που δεν εμπιστεύονται, το σφάλμα ονομάζει το αρχείο πιστοποιητικού αυτού του client και το αποτύπωμά του, ώστε ο χειριστής να ξέρει τι να ψάξει στον διακομιστή.

#### Έγκριση του πιστοποιητικού ενός διακομιστή

Για ασφαλή λειτουργία, ή για κωδικό πρόσβασης που θα κρυπτογραφηθεί με το κλειδί του διακομιστή, **ο driver δεν δέχεται οποιοδήποτε πιστοποιητικό παρουσιάσει ο διακομιστής.** Εμπιστεύεται το πιστοποιητικό μόνο αν είναι καρφιτσωμένο στο `serverCertThumbprints` της συσκευής ή είναι ακριβώς το πιστοποιητικό στο `trusted/`. Οτιδήποτε άλλο γράφεται στο `rejected/<thumbprint>.der` και η σύνδεση αποτυγχάνει, πριν σταλεί οποιοδήποτε διαπιστευτήριο, με μήνυμα σαν αυτό:

```
opcua: the server at opc.tcp://plc-01:4840 presented a certificate that is not
trusted (subject "CN=PLC01", SHA-1 thumbprint 5A6DB35A..., expires 2031-09-18).
It has been saved to /data/opcua-client-pki/rejected/5A6DB35A....der. To approve
it, first check that the thumbprint matches the one the server shows, then move
that file into /data/opcua-client-pki/trusted (the next connection attempt picks
it up; no restart is needed). Alternatively pin it by adding the thumbprint to
this device's serverCertThumbprints. Until then this device will not connect
```

Ελέγξτε το αποτύπωμα με την ένδειξη του ίδιου του διακομιστή πριν εγκρίνετε: αυτή η σύγκριση είναι ολόκληρη η απόφαση εμπιστοσύνης. Μετά κάντε `mv` το αρχείο στο `trusted/` (διαβάζονται και αρχεία PEM και DER) και η συσκευή συνδέεται στην επόμενη απόπειρά της, που είναι μέσα στο διάστημα επανασύνδεσης του runtime. Μερικές λεπτομέρειες:

- Η εμπιστοσύνη αφορά το ακριβές πιστοποιητικό, όχι μια αλυσίδα. Ένας διακομιστής του οποίου το πιστοποιητικό εκδίδεται από CA εγκρίνεται τοποθετώντας το ίδιο το πιστοποιητικό του διακομιστή στο `trusted/`, όπως ένα αυτο-υπογεγραμμένο. Η εμπιστοσύνη σε CA δεν υποστηρίζεται.
- Ένα πιστοποιητικό που έχει λήξει αλλά έχει εγκριθεί από χειριστή εξακολουθεί να εμπιστεύεται, με προειδοποίηση στο log σε κάθε σύνδεση. Το να απορριφθεί ένα που ένας χειριστής ενέκρινε επίτηδες θα τον έσπρωχνε μόνο προς το `insecureSkipVerify`.
- Ένα αρχείο στο `trusted/` που δεν είναι πιστοποιητικό παραλείπεται και αναφέρεται, και δεν καθιστά απρόσιτους τους άλλους εγκεκριμένους διακομιστές.
- Το `rejected/` κρατά το πολύ 256 αρχεία, ώστε ένας διακομιστής που παρουσιάζει διαφορετικό πιστοποιητικό σε κάθε σύνδεση να μην μπορεί να γεμίσει τον δίσκο. Πέρα από αυτό η σύνδεση εξακολουθεί να απορρίπτεται, και το μήνυμα λέει ότι το αρχείο δεν διατηρήθηκε και πώς να εγκρίνετε το πιστοποιητικό παρ' όλα αυτά.
- Το `insecureSkipVerify` απενεργοποιεί τον έλεγχο. Ένα μέρος στη διαδρομή μπορεί τότε να υποδυθεί τον διακομιστή και να διαβάσει ό,τι του στέλνεται, κωδικό πρόσβασης συμπεριλαμβανομένου. Είναι απενεργοποιημένο από προεπιλογή και προειδοποιεί, με το αποτύπωμα του πιστοποιητικού, σε κάθε σύνδεση.

Μια ανώνυμη συσκευή σε μη ασφαλές κανάλι δεν χρειάζεται τίποτα από αυτά, γιατί δεν υπογράφεται ούτε κρυπτογραφείται τίποτα με το κλειδί του διακομιστή.

#### Διαπιστευτήρια

Ένας κωδικός πρόσβασης απορρίπτεται, πριν σταλεί, εκτός αν το κανάλι είναι ασφαλές και κάτι κρυπτογραφεί τον κωδικό. Τι αποφασίζει ο driver, από ό,τι προσφέρει ο διακομιστής για το endpoint που ταίριαξε:

| Κανάλι | Πολιτική token ονόματος χρήστη του διακομιστή | Αποτέλεσμα |
|---|---|---|
| `SignAndEncrypt` | κρυπτογραφεί τον κωδικό (η συνήθης περίπτωση) | συνδέεται |
| `SignAndEncrypt` | δεν τον κρυπτογραφεί | συνδέεται: το κρυπτογραφημένο κανάλι τον μεταφέρει, και το log το λέει |
| `Sign` | κρυπτογραφεί τον κωδικό | συνδέεται |
| `Sign` | δεν τον κρυπτογραφεί | **απορρίπτεται** εκτός αν υπάρχει `allowInsecureCredentials`. Το `Sign` πιστοποιεί τα μηνύματα αλλά δεν τα κρύβει. |
| `None` | κρυπτογραφεί τον κωδικό | **απορρίπτεται** εκτός αν υπάρχει `allowInsecureCredentials`. Σε μη ασφαλές κανάλι, το κλειδί με το οποίο κρυπτογραφείται ο κωδικός προέρχεται από απάντηση που δεν πιστοποιεί τίποτα, οπότε όποιος μπορεί να αλλοιώσει την κίνηση μπορεί να τον ανακτήσει. Με ρητή αποδοχή συνδέεται, με προειδοποίηση. |
| `None` | δεν τον κρυπτογραφεί | **απορρίπτεται** εκτός αν υπάρχει `allowInsecureCredentials` |

**Ένα όνομα χρήστη με `securityMode` `None` απορρίπτεται ακόμη και όταν η πολιτική token του διακομιστή κρυπτογραφεί τον κωδικό.** Μια κρυπτογράφηση της οποίας το κλειδί μπορεί να διαλέξει ένας επιτιθέμενος δεν προστατεύει από αυτόν τον επιτιθέμενο, και σε μη ασφαλές κανάλι το πιστοποιητικό με το οποίο κρυπτογραφείται ο κωδικός λαμβάνεται από την απάντηση του διακομιστή στο `CreateSession`, που δεν πιστοποιεί τίποτα (η δοκιμή παρακάτω αντικαθιστά ένα πιστοποιητικό και ανακτά τον κωδικό). Το σφάλμα το λέει και ονομάζει τη λύση, `securityMode` `SignAndEncrypt`. Οι ανώνυμες συνεδρίες δεν επηρεάζονται.

Το `allowInsecureCredentials` είναι ο μοναδικός διακόπτης που αφήνει έναν κωδικό να φύγει με αυτούς τους όρους. Είναι απενεργοποιημένο από προεπιλογή και προειδοποιεί σε κάθε σύνδεση όταν είναι αυτό που επέτρεψε τη σύνδεση. Όπου η πολιτική token κρυπτογραφεί τον κωδικό, αλλάζει ό,τι μπορεί να διαβάσει ένας ακροατής, όχι ό,τι μπορεί ένα μέρος που αλλοιώνει την κίνηση: δείτε [τι διασχίζει το δίκτυο](#τι-διασχίζει-το-δίκτυο). Ακόμη και με αυτό, το πιστοποιητικό του διακομιστή πρέπει πρώτα να εγκριθεί όταν ο κωδικός κρυπτογραφείται με αυτό.

Ο κωδικός πρόσβασης είναι μυστικό παντού όπου τον χειρίζονται ο driver και το API:

- **Απαντήσεις του API.** Αντικαθίσταται με `[redacted]` σε κάθε απάντηση που επιστρέφει μια συσκευή (`GET /api/devices`, `GET /api/devices/{id}` και η απάντηση σε μια αποθήκευση), ώστε ένας θεατής, που έχει `devices.read`, να μην μπορεί να τον διαβάσει. Από την 4.15.1 αυτό ισχύει για κάθε ρόλο, συμπεριλαμβανομένου του διαχειριστή, και για τα διαπιστευτήρια κάθε πρωτοκόλλου, όχι μόνο αυτού. Η αποθήκευση μιας συσκευής με το σύμβολο υποκατάστασης κρατά τον αποθηκευμένο κωδικό· μια νέα τιμή τον αντικαθιστά· μια κενή συμβολοσειρά τον διαγράφει· το σύμβολο υποκατάστασης για συσκευή χωρίς κωδικό απορρίπτεται αντί να αποθηκευτεί. Η παράλειψη του πεδίου τον κρατά πλέον (στην 4.15.0 τον διέγραφε). Οι πλήρεις κανόνες βρίσκονται στο [Πιστοποίηση και χρήστες](/el/iot/authentication/#τα-διαπιστευτήρια-συσκευών-είναι-μόνο-για-εγγραφή). Ο επεξεργαστής συσκευών της διεπαφής ιστού δείχνει τη ρύθμιση όπως την επιστρέφει το API και αποθηκεύει ό,τι δείχνει, κάτι που αυτό χειρίζεται, οπότε η επεξεργασία μιας συσκευής δεν χάνει τον κωδικό της. (Οι δοκιμές το ελέγχουν μέσω του API, όχι μέσω προγράμματος περιήγησης.)
- **Logs και σφάλματα.** Ούτε οι γραμμές log του driver ούτε κανένα σφάλμα που επιστρέφει φέρουν τον κωδικό: τα μηνύματα χτίζονται από κωδικούς κατάστασης και από τις μη μυστικές ρυθμίσεις της συσκευής. Οι δοκιμές συλλαμβάνουν το log της διεργασίας, το log του διακομιστή και τα σφάλματα, και ψάχνουν σε όλα για τον κωδικό.
- **Εργαλεία και πόροι MCP, η ζωντανή ροή συμβάντων, το log συστήματος.** Κανένα δεν επιστρέφει τη ρύθμιση μιας συσκευής (το καθένα περιγράφει μια συσκευή μέσω ενός σταθερού συνόλου πεδίων), και οι δοκιμές καλούν κάθε εργαλείο και πόρο, ανοίγουν τη ροή και διαβάζουν το log συστήματος με ρυθμισμένο κωδικό, και δεν τον βρίσκουν πουθενά.
- **Η βάση δεδομένων και τα αντίγραφα ασφαλείας.** Ο κωδικός αποθηκεύεται στη στήλη `config` της συσκευής, όπως των άλλων drivers. Μέχρι την 4.16.0 είναι σε απλό κείμενο, και ένα αντίγραφο ασφαλείας τον περιέχει. Από την 4.17.0 είναι κρυπτογραφημένος με κλειδί που φυλάσσεται έξω από τη βάση δεδομένων (δείτε "Encrypted at rest" παρακάτω), οπότε ένα dump ή αντίγραφο ασφαλείας περιέχει κρυπτογραφημένο κείμενο. Είτε έτσι είτε αλλιώς, δείτε [Αντίγραφα ασφαλείας και επαναφορά](/el/iot/backup/#προστατέψτε-τα-αρχεία-αντιγράφων) και προστατεύστε αναλόγως τη βάση δεδομένων και το volume των αντιγράφων.
- **Το edge relay.** Ένα αρχείο συσκευής φέρει επίσης τον κωδικό. Στο chart του Helm, βάλτε ένα αρχείο συσκευής με διαπιστευτήρια σε ένα Secret και ονομάστε το στο `devicesSecret`· οι συσκευές που ορίζονται απευθείας στις τιμές του chart καταλήγουν σε ConfigMap. Ένα αρχείο συσκευής που στέλνεται με fleet config push δημοσιεύεται, retained, σε ένα MQTT topic, οπότε ο broker πρέπει να έχει TLS και να περιορίζει ποιος μπορεί να διαβάζει αυτό το topic.

Ένας λάθος κωδικός πρόσβασης είναι ένα σαφές σφάλμα, με μία απόπειρα, χωρίς κόλλημα και χωρίς επαναλήψεις μέσα στον driver:

```
opcua: authentication rejected: the server at opc.tcp://plc-01:4840 rejected the
user name and password for "svc-hotloop" (StatusBadUserAccessDenied). ...
```

Το runtime περιμένει τότε **δέκα λεπτά** (με τυχαία απόκλιση μεταξύ πέντε και δέκα) πριν από την επόμενη απόπειρα, αντί να ανεβαίνει στο συνηθισμένο backoff επανασύνδεσής του (`HOTLOOP_RECONNECT_MAX`, 60 δευτερόλεπτα από προεπιλογή). Δύο πράγματα κάνουν μια απορριφθείσα σύνδεση ακριβότερη να επαναληφθεί από μια βλάβη δικτύου. Ένας διακομιστής που κλειδώνει έναν λογαριασμό μετά από λίγες αποτυχίες μετατρέπει κάθε γρήγορη επανάληψη σε διακοπή για όποιον άλλον χρησιμοποιεί αυτόν τον λογαριασμό. Και κάθε απορριφθείσα σύνδεση μπορεί να αφήσει μια **συνεδρία που δημιουργήθηκε και δεν ενεργοποιήθηκε ποτέ** στον διακομιστή, που μετράει προς το όριο συνεδριών του μέχρι να λήξει (η βιβλιοθήκη ζητά είκοσι λεπτά· το `sessionTimeoutMs` το αλλάζει): απέναντι στον ίδιο τον διακομιστή του HotLoop, μια συσκευή με λάθος κωδικό που επαναλάμβανε κάθε λίγα δευτερόλεπτα γέμισε το προεπιλεγμένο όριό του των είκοσι συνεδριών, μετά το οποίο ο διακομιστής αρνήθηκε κάθε άλλον client με `BadTooManySessions`. Ένας ελεγκτής με μικρό πίνακα συνεδριών είναι ακόμη πιο εκτεθειμένος. Η συσκευή δεν σταματά να προσπαθεί, οπότε ένας διακομιστής του οποίου ο κωδικός διορθώνεται από τη μεριά του αποκαθίσταται μέσα σε δέκα λεπτά χωρίς να αγγίξει κανείς το HotLoop· η διόρθωση του κωδικού στη συσκευή, ή το σβήσιμο και άναμμά της, ξεκινά νέο worker, που προσπαθεί αμέσως.

#### Τι διασχίζει το δίκτυο

Μετρημένο, όχι συλλογισμένο: οι δοκιμές βάζουν έναν proxy καταγραφής ανάμεσα στον driver και σε έναν διακομιστή και ψάχνουν κάθε byte και προς τις δύο κατευθύνσεις. Η αναζήτηση βρίσκει byte που είναι γνωστό ότι υπάρχουν (η λίστα endpoints του διακομιστή, σταλμένη σε απλό κείμενο), κάτι που δείχνει ότι ο proxy κατέγραψε τη συνομιλία.

| Ρύθμιση | Κωδικός πρόσβασης | Όνομα χρήστη | Αναγνωριστικά κόμβων και τιμές tags |
|---|---|---|---|
| `SignAndEncrypt` | δεν φαίνεται | δεν φαίνεται | δεν φαίνεται |
| `Sign` | δεν φαίνεται (η πολιτική token τον κρυπτογραφεί) | **αναγνώσιμο** | **αναγνώσιμο** |
| `None`, όνομα χρήστη, η πολιτική token του διακομιστή κρυπτογραφεί (απαιτεί `allowInsecureCredentials`) | δεν φαίνεται | **αναγνώσιμο** | **αναγνώσιμο** |
| `None`, ανώνυμο | μη εφαρμόσιμο | μη εφαρμόσιμο | **αναγνώσιμο** |
| ένας διακομιστής που προσφέρει μη κρυπτογραφημένο κωδικό, με `allowInsecureCredentials` | **αναγνώσιμο** | **αναγνώσιμο** | εξαρτάται από τη λειτουργία |

Η τελευταία γραμμή δοκιμάζεται απέναντι σε διακομιστή που στην πραγματικότητα δεν το προσφέρει αυτό: ένα μέρος μπροστά από έναν πραγματικό διακομιστή ξαναγράφει τη λίστα endpoints του ώστε να λέει ότι ο κωδικός δεν είναι κρυπτογραφημένος, στο κανάλι που χρησιμοποιεί η ανακάλυψη, το οποίο δεν πιστοποιεί τίποτα. Έτσι οι δοκιμές δείχνουν και την άρνηση: χωρίς ρητή αποδοχή ο driver αρνείται, ανοίγει μόνο τη σύνδεση ανακάλυψης, και κανένα διαπιστευτήριο δεν βρίσκεται στο καλώδιο. Η λίστα endpoints είναι ακριβώς αυτό που μπορεί να ξαναγράψει ένα μέρος στη διαδρομή, γι' αυτό ο κανόνας του driver εφαρμόζεται σε αυτό που του λένε και δεν αφήνεται στον διακομιστή να τον επιβάλει.

Ένα μη ασφαλές κανάλι με κωδικό έχει ένα όριο που ο πίνακας δεν δείχνει και μια δοκιμή δείχνει· γι' αυτό ο driver απορρίπτει αυτόν τον συνδυασμό χωρίς ρητή αποδοχή. Ο κωδικός κρυπτογραφείται με το πιστοποιητικό του διακομιστή, που τον κρατά μακριά από έναν ακροατή, και ο driver δεν θα τον στείλει μέχρι να εγκριθεί αυτό το πιστοποιητικό. Αλλά το πιστοποιητικό με το οποίο κρυπτογραφεί η βιβλιοθήκη OPC UA είναι αυτό στην απάντηση του διακομιστή όταν δημιουργείται η συνεδρία, και σε μη ασφαλές κανάλι αυτή η απάντηση δεν είναι πιστοποιημένη. Ένα μέρος που μπορεί να αλλοιώσει την κίνηση βάζει το δικό του πιστοποιητικό, και ο κωδικός κρυπτογραφείται τότε με το κλειδί αυτού του μέρους: η δοκιμή το κάνει, αποκρυπτογραφεί τον κωδικό με το αντικατεστημένο κλειδί και τον παίρνει πίσω. **Μέσω `Sign` ή `SignAndEncrypt` το ίδιο μέρος δεν μπορεί**, επειδή η απάντηση προστατεύεται από κλειδιά που δεν έχει. Χωρίς `allowInsecureCredentials` ο driver αρνείται να στείλει καθόλου τον κωδικό, και η δοκιμή δείχνει ότι το ίδιο μέρος δεν παίρνει τότε τίποτα· με αυτό, ο driver προειδοποιεί σε κάθε σύνδεση. Χρησιμοποιήστε `SignAndEncrypt` όπου ο διακομιστής το προσφέρει· ένα μη ασφαλές κανάλι με κωδικό, με ρητή αποδοχή, είναι προστασία από έναν ακροατή και τίποτα παραπάνω.

#### Επανασύνδεση

Η δική της επανασύνδεση της βιβλιοθήκης OPC UA είναι απενεργοποιημένη, και το runtime επανασυνδέεται. Η βιβλιοθήκη, μόλις χαθεί μια συνεδρία, ανοίγει νέα με τα διαπιστευτήρια που της δόθηκαν και, όταν ο διακομιστής τα απορρίπτει, ξαναδοκιμάζει αμέσως χωρίς καθυστέρηση: μετρήθηκαν περίπου είκοσι απορριφθείσες συνδέσεις σε δώδεκα δευτερόλεπτα, απέναντι σε διακομιστή του οποίου ο κωδικός είχε αλλάξει. Έτσι ένας λογαριασμός κλειδώνεται για όλους όσους τον μοιράζονται. Τώρα μια χαμένη συνεδρία κάνει το `Poll` να αναφέρει σφάλμα, το worker του runtime κλείνει τον driver και ανοίγει νέο, και το νέο ανακαλύπτει τα endpoints, ελέγχει το πιστοποιητικό του διακομιστή και συνδέεται ξανά, με το backoff με τυχαία απόκλιση του runtime και την αναμονή δέκα λεπτών μετά από αποτυχία πιστοποίησης. Μια επανεκκίνηση του διακομιστή ξεπερνιέται με τον ίδιο τρόπο: η συσκευή διαβάζει τη νέα τιμή μετά την επανεκκίνηση, αφού έχει συνδεθεί ξανά, κάτι που οι δοκιμές ελέγχουν μετρώντας τις συνδέσεις του διακομιστή και αλλάζοντας την τιμή μετά την επανεκκίνηση.

Μια συσκευή χωρίς tags δεν έχει τίποτα να διαβάσει, και μέχρι την 4.15.2 αυτό σήμαινε ότι το polling της δεν έστελνε απολύτως τίποτα. Ο διακομιστής έκλεινε την αδρανή συνεδρία στη λήξη του χρονικού ορίου συνεδρίας, η συσκευή συνέχιζε να λέει ότι είναι συνδεδεμένη επειδή κανείς δεν είχε ρωτήσει τίποτα τον διακομιστή, και κάθε περιήγηση αποτύγχανε με `BadSessionIDInvalid` μέχρι να επανεκκινηθεί η διεργασία. Αυτό είναι κάθε συσκευή τη στιγμή ακριβώς που κάποιος την προσθέτει και πατά Εντοπισμός tags. Το έπιασε το Ignition. Τώρα μια συσκευή χωρίς tags διαβάζει την κατάσταση του διακομιστή σε κάθε polling, κάτι που κρατά ζωντανή τη συνεδρία και αντιλαμβάνεται πότε πεθαίνει, και μια περιήγηση που βρίσκει τη συνεδρία χαμένη το αναφέρει ώστε το runtime να επανασυνδεθεί.

Ένα tag που δεν έχει αλλάξει από πριν ξεκινήσει η συνεδρία διαβάζει πλέον την τρέχουσα τιμή του με καλή ποιότητα. Πριν, η προσωρινή ένδειξη που αναφερόταν όσο περίμενε την πρώτη τιμή ήταν νεότερη από τη χρονοσφραγίδα πηγής της ίδιας της τιμής, και το runtime κρατά τη νεότερη ένδειξη και απέρριπτε την τιμή, οπότε ένα σταθερό tag διαβαζόταν κακό μέχρι να αλλάξει την επόμενη φορά.

#### Τι δοκιμάστηκε και τι όχι

Το OPC UA έχει τρέξει απέναντι στο Ignition 8.3.9 και σε ανεξάρτητους διακομιστές OPC UA, με ανώνυμη σύνδεση και με όνομα χρήστη και κωδικό πρόσβασης μέσω `None`, `Sign` και `SignAndEncrypt`, και σε πραγματικό υλικό στις 2026-11-17. Κάθε διακομιστής παραγωγής έχει τις δικές του συνήθειες για το ποιες πολιτικές προσφέρει και πώς απορρίπτει ένα πιστοποιητικό, οπότε αντιμετωπίστε μια πρώτη σύνδεση με τον διακομιστή ενός νέου κατασκευαστή ως θέση σε λειτουργία.

Τι να ξέρετε:

- Κάθε σύνδεση ρωτά πλέον πρώτα τον διακομιστή για τα endpoints του, και μια συσκευή χωρίς επιλογές ασφάλειας χρειάζεται ένα μη ασφαλές endpoint που απαριθμεί πολιτική ανώνυμου token με id. Ένας διακομιστής που δεχόταν ανώνυμες συνεδρίες χωρίς να απαριθμεί μία απορρίπτεται με σφάλμα που απαριθμεί ό,τι προσφέρει.
- Η πιστοποίηση χρήστη με πιστοποιητικό X.509 και με εκδοθέν token δεν έχει υλοποιηθεί για τον driver. Το `certFile` μιας συσκευής είναι το πιστοποιητικό εφαρμογής της.
- Η εμπιστοσύνη αφορά το ακριβές πιστοποιητικό. Η εμπιστοσύνη σε αρχή πιστοποίησης και η ανάκληση πιστοποιητικών δεν υποστηρίζονται.
- Οι πολιτικές ασφάλειας ελλειπτικών καμπυλών δεν υποστηρίζονται, ούτε και οι διακομιστές που αρνούνται την ανακάλυψη σε μη ασφαλές κανάλι.
- Μια διαδρομή δικτύου που πέφτει χωρίς κανένα άκρο να δει το κλείσιμο αφήνει τη συσκευή στις τελευταίες της τιμές μέχρι το λειτουργικό σύστημα να εγκαταλείψει τη σύνδεση.
- Μερικοί διακομιστές δεν μπορούν να ανοίξουν κανάλι με `Aes256_Sha256_RsaPss`.
- Ο ίδιος ο διακομιστής του HotLoop δέχεται κωδικούς έως 72 byte. Ένας άλλος διακομιστής μπορεί να έχει δικό του όριο.

#### Ignition 8.3

Επαληθευμένο απέναντι στο **Ignition 8.3.9**, την τρέχουσα σταθερή έκδοση, στο δικό της container image της Inductive Automation: ο driver του HotLoop ως client, ο διακομιστής OPC UA του Ignition από την άλλη πλευρά, `Basic256Sha256` με `SignAndEncrypt`, με σύνδεση με όνομα χρήστη και κωδικό πρόσβασης. Το Browse βρήκε τα tags του Ignition κάτω από `nsu=urn:inductiveautomation:ignition:opcua:tags`, και τα tags `[System]/Gateway` ρολογιού, CPU, μνήμης και χρόνου λειτουργίας εισήχθησαν και διαβάστηκαν με καλή ποιότητα, σπρωγμένα μέσω εγγραφής.

Μια τυπική πύλη Ignition 8.3 θα σας σταματήσει τέσσερις φορές πριν προλάβει το HotLoop να πει κουβέντα:

1. **Ο διακομιστής OPC UA της ακούει μόνο στο localhost.** Από το κουτί, η 8.3 δένει τη θύρα 62541 στο `localhost`, οπότε ένα HotLoop οπουδήποτε αλλού παίρνει άρνηση σύνδεσης και τίποτε άλλο. Στο Gateway, στις ρυθμίσεις του διακομιστή OPC UA, ορίστε το Bind Addresses σε `0.0.0.0`. Προσθέσαμε επίσης το όνομα host που καλεί το HotLoop στα Endpoint Addresses· το αν το χρειάζεται ο driver δεν δοκιμάστηκε.
2. **Τα tags δεν είναι στο OPC UA από προεπιλογή.** Ενεργοποιήστε το Expose Tag Providers, αλλιώς μια περιήγηση βρίσκει μόνο τα διαγνωστικά του ίδιου του διακομιστή και τους φακέλους των συσκευών.
3. **Πιστοποιητικά, προς τις δύο κατευθύνσεις.** Το HotLoop απορρίπτει το πιστοποιητικό του Ignition μέχρι να το εγκρίνετε, όπως παραπάνω. Το Ignition απορρίπτει αυτό του HotLoop μέχρι να το εμπιστευτείτε στα πιστοποιητικά του διακομιστή OPC UA του Gateway. Στον δίσκο αυτό σημαίνει μετακίνησή του από το `data/config/local/com.inductiveautomation.opcua/server/security/pki/rejected/certs` στο `.../trusted/certs`, χωρίς επανεκκίνηση. **Το Ignition δεν ονομάζει αυτό το αρχείο με το αποτύπωμα SHA-1 που καταγράφει το HotLoop.** Ανοίξτε το πιστοποιητικό και συγκρίνετε το δακτυλικό του αποτύπωμα· το όνομα του αρχείου δεν θα ταιριάζει και αυτό δεν είναι ένδειξη απατεώνα.
4. **Η σύνδεση OPC UA είναι `opcuauser` / `password`** στην πηγή χρηστών `opcua-module`, σε κάθε φρέσκια εγκατάσταση. Αλλάξτε την πριν συνδεθεί οτιδήποτε πραγματικό.

Μόνο ό,τι προσφέρει ο διακομιστής της 8.3 από το κουτί δοκιμάστηκε προς αυτή την κατεύθυνση: `Basic256Sha256` και `SignAndEncrypt`.

**Η άλλη κατεύθυνση είναι επίσης επαληθευμένη: ο client OPC UA του Ignition 8.3.9 διαβάζει τον διακομιστή OPC UA του HotLoop**, συνδεδεμένος ως θεατής του HotLoop, μέσω κάθε πολιτικής και λειτουργίας ασφάλειας που προσφέρει το Ignition. Η ρύθμιση, η εμπιστοσύνη πιστοποιητικών προς τις δύο κατευθύνσεις, οι παγίδες και ο πίνακας πολιτικών βρίσκονται στο [Ο διακομιστής OPC UA](/el/edge/opc-ua-server/#το-ignition-83-ως-πελάτης). Βρήκε δύο σφάλματα του HotLoop, και τα δύο διορθωμένα: ο διακομιστής δημιουργούσε νέο πιστοποιητικό κάθε φορά που ξαναδημιουργούνταν το container του, κάτι που έσπαγε την εμπιστοσύνη του Ignition μετά από κάθε αναβάθμιση, και ο Εντοπισμός tags δήλωνε κάθε tag ως float, οπότε ένα tag κειμένου έφτανε στο Ignition ως `Bad_TypeMismatch` (παραπάνω).

Ο κόμβος edge Sparkplug του HotLoop και το Edge Relay απέναντι στο MQTT Engine του Ignition είναι το επόμενο, και δεν έχουν γίνει.

### OPC UA PubSub (UADP)

Το άλλο OPC UA: όχι ένας client που ρωτά έναν διακομιστή, αλλά ένας publisher που στέλνει DataSets ως datagrams UDP σε όποιον ακούει, unicast ή multicast (OPC 10000-14, η κωδικοποίηση UADP). Το HotLoop εγγράφεται, ως συσκευή, και δημοσιεύει, ως ρύθμιση.

**Εγγραφή.** Προσθέστε μια συσκευή με το πρωτόκολλο `opcua-pubsub`. Η διεύθυνση είναι αυτό στο οποίο ακούει: το `udp://239.0.0.1:4840` εντάσσεται σε μια ομάδα multicast, το `udp://:4840` ακούει unicast. Η διεύθυνση ενός tag είναι `<DataSetWriterId>/<field index>`, η θέση του πεδίου στο DataSet του publisher μετρώντας από το 0: το `1000/3` είναι το τέταρτο πεδίο που δημοσιεύει ο writer 1000. Το UADP δεν μεταφέρει ονόματα πεδίων (ζουν σε ένα DataSetMetaData που ο publisher εξυπηρετεί αλλιώς, ή καθόλου), οπότε η θέση είναι ό,τι μπορεί να πει ένα datagram. Ένα πεδίο που είναι πίνακας διαβάζεται ένα στοιχείο τη φορά: το `1000/3[17]` είναι η δέκατη όγδοη τιμή του πίνακα που είναι το τέταρτο πεδίο. Το Browse απαριθμεί τα πεδία που έχουν ακουστεί, με τους τύπους τους, και έναν πίνακα ως τα στοιχεία του (τα πρώτα 1000).

```json
{"publisherId":"2234","writerGroupId":100,"interface":"eth0","timeoutMs":30000,
 "dataSets":[{"writerId":62541,"types":["Float","UInt16","Boolean","Int32","Double"]}]}
```

- Τα `publisherId` και `writerGroupId` κρατούν μια συσκευή σε έναν publisher και μια ομάδα. Το κενό και το μηδέν δέχονται τα πάντα. Έτσι μοιράζονται διεύθυνση αρκετές συσκευές: ένας publisher που στέλνει δύο WriterGroups στο `udp://:4840` είναι δύο συσκευές εκεί, μία με `"writerGroupId":1` και μία με `"writerGroupId":2`.
- Οι συσκευές μπορούν να μοιράζονται διεύθυνση και θύρα. Το HotLoop ανοίγει ένα socket γι' αυτήν (μία ένταξη, για μια ομάδα multicast σε μία κάρτα) και δίνει κάθε datagram σε κάθε συσκευή πάνω σε αυτό. Κάθε συσκευή εφαρμόζει μετά τα δικά της `publisherId`, `writerGroupId` και `dataSets`, ώστε η καθεμία να βλέπει ολόκληρη τη ροή του publisher της και καμία να μην χωρίζεται ανάμεσα σε συσκευές. Το socket κλείνει όταν η τελευταία συσκευή πάνω του αφαιρεθεί ή σταματήσει, και η επόμενη που ξεκινά το ανοίγει ξανά. Οι συσκευές ταιριάζονται με τη διεύθυνση όπως είναι γραμμένη: τα `udp://:4840`, `udp://0.0.0.0:4840` και `udp://[::]:4840` είναι τρεις διευθύνσεις για το HotLoop, και το αν μπορούν να συνυπάρξουν εξαρτάται από το λειτουργικό σύστημα, όπως πάντα. Μια ομάδα multicast που εντάσσεται σε δύο διαφορετικές κάρτες είναι δύο sockets. Τίποτα δεν αλλάζει για μια συσκευή που είναι μόνη στη διεύθυνσή της.
- Η ομάδα, η θύρα και η κάρτα ανήκουν στη συσκευή: τίποτα δεν είναι σταθερό στο HotLoop. Το `udp://239.192.0.1:4850` με `"interface":"eth0"` εντάσσεται σε εκείνη την ομάδα σε εκείνη την κάρτα, και το `udp://127.0.0.1:4842` ακούει έναν publisher στο ίδιο μηχάνημα. Πολλές συσκευές μπορούν να ακούν ταυτόχρονα σε διαφορετικές ομάδες και θύρες, ή στην ίδια.
- Το `interface` είναι η κάρτα δικτύου στην οποία εντάσσεται μια ομάδα multicast, με όνομα (`eth0`, `lo`) ή με μία από τις διευθύνσεις IPv4 της (`127.0.0.1`). Ένα μηχάνημα με περισσότερες από μία κάρτες το χρειάζεται. Ένας publisher στο ίδιο μηχάνημα που στέλνει σε ομάδα μέσω loopback (`IP_MULTICAST_IF` 127.0.0.1, TTL 0, loopback ενεργό, χωρίς διαδρομή) ακούγεται από συσκευή με `"interface":"lo"` ή `"127.0.0.1"`· χωρίς ονομασμένο interface και χωρίς διαδρομή, η ένταξη αποτυγχάνει με `no such device` και το λέει.
- Το `dataSets` είναι μόνο για RawData, που δεν μεταφέρει τύπους στο καλώδιο: οι τύποι πεδίων του publisher, με τη σειρά, ώστε να διαβάζονται τα byte. Τα μηνύματα Variant και DataValue μεταφέρουν τα δικά τους. Κάθε καταχώριση είναι ένα όνομα τύπου (`"Float"`), και μπορεί επίσης να λέει πώς είναι διατεταγμένο ένα μπλοκ τιμών: το `"Float*250"` είναι 250 πεδία το ένα μετά το άλλο χωρίς μήκος μπροστά, όπως γράφει ένα PLC που στέλνει ένα μπλοκ REAL ως χωριστά πεδία· το `"Float[250]"` είναι ένα πεδίο-πίνακας το πολύ 250 τιμών, γραμμένο όπως γράφει η στοίβα του OPC Foundation έναν πίνακα RawData (μετρητής Int32, οι τιμές και συμπλήρωση μηδενικών μέχρι 250 από αυτές)· και το `"String(40)"` είναι ένα String συμπληρωμένο στα 40 byte, μόνο του ή ως `"String(40)[4]"`.
- Τα key frames αντικαθιστούν τα πεδία ενός DataSet· τα delta frames αλλάζουν αυτά που κατονομάζουν· τα keep alives αποδεικνύουν ότι ο publisher είναι ζωντανός. Ένα χαμένο μήνυμα (ένα κενό στους αριθμούς ακολουθίας) σημαδεύει τα tags εκείνου του DataSetWriter ως **αβέβαια** μέχρι το επόμενο key frame, αφού ένα delta μπορεί να χάθηκε μαζί του. Μια αλλαγή στην έκδοση ρύθμισης του DataSet κάνει να ξεχαστούν όλα τα πεδία μέχρι ένα key frame να πει τι σημαίνουν τώρα.
- Ένας writer σιωπηλός για `timeoutMs` (30 δευτερόλεπτα αν δεν οριστεί) διαβάζεται **κακός** με αυτό αναφερόμενο, και μια συσκευή από την οποία δεν ακούστηκε τίποτα από τον publisher της μέσα στο χρονικό όριο είναι εκτός λειτουργίας. Ένα πεδίο που ο publisher σημαδεύει ως Bad είναι κακό, και ένα που σημαδεύει ως Uncertain είναι αβέβαιο· ο λόγος είναι ο κωδικός κατάστασης.
- Ο χρόνος της ένδειξης είναι ο χρόνος του publisher, από το πεδίο, το DataSetMessage ή το NetworkMessage, όταν είναι ορισμένος και όχι περισσότερο από ένα λεπτό μπροστά από αυτό το ρολόι, και ο χρόνος άφιξης διαφορετικά.
- Οι πίνακες διαβάζονται σε μηνύματα Variant και DataValue (ένας μετρητής Int32 και οι τιμές, OPC 10000-6 5.2.2.16· ένας πολυδιάστατος έρχεται επίπεδος, γραμμή προς γραμμή) και, με μια διάταξη, σε RawData. Ένας μετρητής που το datagram δεν μπορεί να χωρέσει απορρίπτεται πριν δημιουργηθεί οτιδήποτε γι' αυτόν.
- Μόνο για ανάγνωση. Η ασφάλεια μηνυμάτων (υπογεγραμμένα ή κρυπτογραφημένα NetworkMessages), τα κατακερματισμένα μηνύματα, τα μηνύματα ανακάλυψης, τα συμβάντα και τα πεδία δομής δεν υποστηρίζονται· ένα datagram με οποιοδήποτε από αυτά απορρίπτεται, μετριέται ανά λόγο και δεν μαντεύεται ποτέ.

**Δημοσίευση.** Απενεργοποιημένη μέχρι να οριστεί το `HOTLOOP_UADP_PUBLISH_ENABLED`, στα Edge και Gateway (τα προϊόντα που έχουν τον διακομιστή OPC UA). Στέλνει τα tags που κατονομάζει μια διάταξη:

```json
{"dataSets":[{"writerId":1,"name":"press","configMajor":1,"fields":[
  {"device":"press-01","tag":"Zone1_Temp","type":"Float"},
  {"device":"press-01","tag":"Cycle","type":"UInt32"}]}]}
```

| Μεταβλητή | Προεπιλογή | <span class="sr-only">Λεπτομέρειες</span> |
|---|---|---|
| `HOTLOOP_UADP_PUBLISH_ADDRESS` | | `udp://239.0.0.1:4840` για ομάδα multicast, `udp://host:4840` για έναν συνδρομητή |
| `HOTLOOP_UADP_PUBLISH_LAYOUT_FILE` ή `_LAYOUT` | | η διάταξη παραπάνω, ως αρχείο ή ενσωματωμένη (το αρχείο υπερισχύει) |
| `HOTLOOP_UADP_PUBLISH_PUBLISHER_ID` | `1` | ένας αριθμός ή ένα κείμενο |
| `HOTLOOP_UADP_PUBLISH_WRITER_GROUP_ID` | `1` | |
| `HOTLOOP_UADP_PUBLISH_INTERVAL` | `1s` | |
| `HOTLOOP_UADP_PUBLISH_KEY_FRAME_EVERY` | `10` | το πολύ τόσα διαστήματα ανάμεσα σε key frames |
| `HOTLOOP_UADP_PUBLISH_DATAVALUE` | `false` | πεδία DataValue (τιμή, κατάσταση, χρόνος) αντί για Variants |
| `HOTLOOP_UADP_PUBLISH_DELTA_FRAMES` | `false` | ένα DataSet που άλλαξε βγαίνει ως delta frame (μόνο τα πεδία που άλλαξαν) ανάμεσα σε key frames |
| `HOTLOOP_UADP_PUBLISH_METADATA_EVERY` | `10` | τα ονόματα και οι τύποι των πεδίων κάθε DataSet ανακοινώνονται κάθε τόσα διαστήματα· το `0` δεν στέλνει κανένα |
| `HOTLOOP_UADP_PUBLISH_INTERFACE`, `_TTL` | του συστήματος, `1` | η κάρτα από την οποία βγαίνει το multicast, και το όριο hop του |

Κάθε DataSet φεύγει από τον δικό του DataSetWriter, ένα NetworkMessage το καθένα. Ένα DataSet του οποίου οι τιμές άλλαξαν φεύγει ως key frame (κάθε πεδίο), ένα που δεν άλλαξε ως keep alive, και ένα key frame τουλάχιστον κάθε `KEY_FRAME_EVERY` διαστήματα ώστε ένας συνδρομητής που ήρθε αργά να συγκλίνει. Ένα key frame είναι πλήρες, οπότε ένα χαμένο datagram κοστίζει ένα διάστημα και όχι μια λάθος τιμή. Με `HOTLOOP_UADP_PUBLISH_DELTA_FRAMES=true` ένα DataSet που άλλαξε φεύγει αντί αυτού ως delta frame, που φέρει μόνο τα πεδία που άλλαξαν από το τελευταίο μήνυμα και τις θέσεις τους, και το key frame έρχεται και πάλι τουλάχιστον κάθε `KEY_FRAME_EVERY` διαστήματα· ένα χαμένο delta κοστίζει τότε έως τόσα διαστήματα με ένα ξεπερασμένο πεδίο, που είναι το τίμημα ενός μικρότερου μηνύματος σε αργή σύνδεση. Ο δικός του συνδρομητής του HotLoop διαβάζει delta frames. value. Ένα tag που είναι κακό δημοσιεύεται ως η κατάστασή του και ποτέ ως η τελευταία τιμή του· ένα από το οποίο δεν έχει διαβαστεί ακόμη τίποτα δημοσιεύεται ως `BadWaitingForInitialData`. Οι τιμές περιορίζονται στον δημοσιευμένο τύπο τους, δεν αναδιπλώνονται. Η ασφάλεια μηνυμάτων δεν υποστηρίζεται, οπότε αυτό ανήκει σε δίκτυο που εμπιστεύεται το εργοστάσιο. Τα tags της ίδιας διάταξης μπορούν να διαβαστούν από τον δικό του συνδρομητή του HotLoop σε άλλο μηχάνημα.

**Τι αποδείχθηκε.** Μια ανεξάρτητη στοίβα OPC UA PubSub δημοσιεύει στον συνδρομητή του HotLoop και εγγράφεται στον publisher του HotLoop μέσω multicast, και ο publisher του HotLoop διαβάζεται σωστά από τον δικό του συνδρομητή του HotLoop. **Ασφάλεια μηνυμάτων.** Μια συσκευή συνδρομητή μπορεί να απαιτεί τα NetworkMessages του publisher της να είναι υπογεγραμμένα, ή υπογεγραμμένα και κρυπτογραφημένα (OPC 10000-14 7.2.4.4.3), με τις δύο πολιτικές που ορίζει η προδιαγραφή, `PubSub-Aes128-CTR` και `PubSub-Aes256-CTR`:

```json
{"publisherId":"2234","security":{"mode":"signAndEncrypt","policy":"PubSub-Aes128-CTR",
 "keys":[{"keyId":1,"signingKey":"<64 hex digits>","encryptingKey":"<32 hex digits>","keyNonce":"<8 hex digits>"}]}}
```

Τα κλειδιά είναι στατικά: ορίζονται και στις δύο πλευρές κάτω από ένα SecurityTokenId (`keyId`), σε hex ή base64. Είναι μυστικά, εμφανίζονται ως `[redacted]` και διατηρούνται κατά την αποθήκευση. Μια συσκευή που κρατά δύο κλειδιά δέχεται έναν publisher που περνά από το ένα στο άλλο. Με το `security` ορισμένο, ένα μήνυμα που δεν είναι υπογεγραμμένο (ή δεν είναι κρυπτογραφημένο, υπό `signAndEncrypt`), που είναι υπογεγραμμένο με άλλο κλειδί ή που άλλαξε στη διαδρομή απορρίπτεται και μετριέται (`unsecured`, `signature`, `security_key`) προτού διαβαστεί οτιδήποτε μέσα του. Ένα Security Key Service (GetSecurityKeys, εναλλασσόμενα κλειδιά) δεν έχει υλοποιηθεί. Ο publisher υπογράφει με `HOTLOOP_UADP_PUBLISH_SECURITY_MODE` (`sign` ή `signAndEncrypt`), `_POLICY`, `_KEY_ID`, `_SIGNING_KEY`, `_ENCRYPTING_KEY` και `_KEY_NONCE`.

**Μεταδεδομένα και ανακάλυψη.** Ένας publisher ανακοινώνει πώς λέγονται και από τι αποτελούνται τα DataSets του ως απάντηση ανακάλυψης που φέρει ένα DataSetMetaData, σε κομμάτια όταν είναι μεγάλο (7.2.4.4.4, 7.2.4.6). Μια συσκευή συνδρομητή τα διαβάζει: τα πεδία ονομάζονται στο Browse (`writer1001_<field name>`), ένα DataSet RawData δεν χρειάζεται τύπους `dataSets` στη ρύθμιση επειδή τα μεταδεδομένα το διατάσσουν, και ένα DataSet που αλλάζει την έκδοση ρύθμισής του ξεκινά από την αρχή από το επόμενο key frame του. Τα `dataSets` της ρύθμισης εξακολουθούν να υπερισχύουν όταν υπάρχουν και τα δύο. Το αίτημα ανακάλυψης ενός συνδρομητή δεν στέλνεται, και ένας publisher δεν απαντά σε κανένα.

**Πεδία δομής, συμβάντα.** Ένα πεδίο που τα μεταδεδομένα λένε ότι είναι δομή διαβάζεται ως τα μέλη του, που ένα tag διευθυνσιοδοτεί ως `1001/0.Value` (και `1001/7[2].Angle` για ένα στοιχείο ενός πίνακα δομών)· μια δομή που στέλνεται σε Variant διαβάζεται όταν τα μεταδεδομένα την περιγράφουν. Οι δομές με προαιρετικά πεδία και οι ενώσεις αναφέρονται με το όνομά τους, δεν μαντεύονται. Ένα DataSetMessage Event εφαρμόζεται όπως τα πεδία που φέρει και αφήνει τα υπόλοιπα ήσυχα (`Events` στα στατιστικά της συσκευής)· η διάταξή του είναι αυτή ενός key frame (7.2.4.5.7), διαβασμένη από την προδιαγραφή και όχι ελεγμένη απέναντι σε άλλη στοίβα. Ορισμένοι publishers γράφουν ένα FieldCount πριν από ένα key frame RawData, κάτι που η προδιαγραφή δεν κάνει· η συσκευή ενημερώνεται με `"rawFieldCount":true`.

### CODESYS

Ένα PLC που τρέχει runtime CODESYS Control (Linux SL, ARM64, Raspberry Pi, Windows, το εικονικό PLC), που διαβάζεται και γράφεται με τα ονόματα που έδωσε ο προγραμματιστής του στις μεταβλητές: `Application.GVL_Line.rTemp`, όχι με id κόμβου. Είναι ο driver OPC UA με όσα χρειάζεται επιπλέον ένα PLC CODESYS, οπότε ό,τι βρίσκεται στο [OPC UA: ασφάλεια και διαπιστευτήρια](#opc-ua-ασφάλεια-και-διαπιστευτήρια) ισχύει για αυτόν και οι επιλογές του είναι εκείνες οι επιλογές.

**Οι δικοί του συναγερμοί του PLC.** Ένα έργο με Alarm Configuration κρατά τους συναγερμούς του στον διαχειριστή συναγερμών του PLC. Με το μπλοκ της βιβλιοθήκης HotLoop Alarms στο έργο (δείτε CODESYS alarms), το HotLoop δείχνει αυτούς τους συναγερμούς στη λίστα συναγερμών του, από τη στιγμή που η συσκευή συνδέεται, και μια αναγνώριση που γίνεται στο HotLoop πηγαίνει πίσω στον διαχειριστή συναγερμών. Επαληθεύτηκε ζωντανά απέναντι σε πραγματικό runtime CODESYS Control for Linux SL 4.22.0.0: ενεργοποίηση, αναγνώριση, επαναφορά και επιβεβαίωση. Οι δικές του λίστες κειμένων του διαχειριστή συναγερμών και μια κλάση εκτός από τις δύο που δοκιμάστηκαν δεν έχουν επαληθευτεί.

**Γιατί ο διακομιστής OPC UA, και τι σημαίνει αυτό για το PLC.** Το CODESYS τεκμηριώνει έναν μόνο τρόπο για να διαβάσει τρίτος τις μεταβλητές ενός ελεγκτή, και είναι ο ίδιος ο διακομιστής OPC UA του runtime: το Symbol Configuration της εφαρμογής (ή, από το CODESYS 3.5 SP18, ένα IEC Symbol Set κάτω από το Communication Manager) λέει ποιες μεταβλητές δημοσιεύονται και με ποια πρόσβαση, και ο διακομιστής τις εξυπηρετεί. Το πρωτόκολλο καναλιού του CODESYS Gateway δεν τεκμηριώνεται για τρίτους και αυτός ο driver δεν το μιλάει. Άρα το PLC πρέπει να δημοσιεύει αυτό που θέλετε να δείτε:

1. Στο IDE προσθέστε ένα **Symbol Configuration** στην εφαρμογή, με ενεργό το *Support OPC UA features*, και τσεκάρετε τις μεταβλητές, ή σημειώστε τις στη δήλωση με `{attribute 'symbol' := 'readwrite'}` (`'read'` για μόνο ανάγνωση).
2. Κατεβάστε. Ένα PLC χωρίς Symbol Configuration απαντά στη ρύθμιση με ένα μήνυμα που λέει να προσθέσετε ένα.
3. Μια μεταβλητή είναι εγγράψιμη από το HotLoop μόνο όταν το σύμβολό της είναι `readwrite` και ο χρήστης με τον οποίο συνδέεται επιτρέπεται να τη γράψει (τα *Symbol Rights* της συσκευής). Το HotLoop διαβάζει το επίπεδο πρόσβασης και λέει ποιο από τα δύο αρνήθηκε μια εγγραφή.

Πηγές: [CODESYS help, Symbol Configuration](https://content.helpme-codesys.com/en/CODESYS%20Communication/_cds_symbolconfiguration.html) και [IEC Symbol Set](https://content.helpme-codesys.com/en/CODESYS%20Communication/_comm_symbol_configuration.html) (το όνομα του συμβόλου είναι `<application>.<POU>.<variable>`, η πρόσβαση είναι ανάγνωση, εγγραφή ή εκτέλεση ανά σύμβολο, τα δικαιώματα των ομάδων είναι στην καρτέλα Symbol Rights της συσκευής, και το OPC UA χρειάζεται πιστοποιητικό στον ελεγκτή)· το [PLCopen OPC UA information model for IEC 61131-3](https://plcopen.org/system/files/downloads/plcopen_opc_ua_information_model_for_iec61131-3_version1.02.pdf) (έκδοση 1.02, η διάταξη παρακάτω)· OPC UA Part 5 (OperationLimits). Τα id κόμβων είναι αυτά που απάντησε ένα runtime 4.22.0.0, απέναντι στο οποίο γράφτηκε αυτός ο driver· η ακριβής ορθογραφία του `|var|` είναι του runtime, όχι δημοσιευμένο συμβόλαιο, γι' αυτό ένα tag διευθυνσιοδοτείται με σύμβολο και ο driver χτίζει το id κόμβου.

**Διάταξη.** Το runtime δημοσιεύει, στο `DeviceSet` του OPC UA Device Integration, μία συσκευή για το PLC, από κάτω της τα `Resources`, και από κάτω την εφαρμογή, με τα `GlobalVars` (τις λίστες μεταβλητών) και τα `Programs` από κάτω. Ο κόμβος μιας μεταβλητής είναι `ns=<n>;s=|var|<device>.<application>.<list or program>.<variable>` στον χώρο ονομάτων `CODESYSSPV3/3S/IecVarAccess`. Ο driver βρίσκει τη συσκευή και την εφαρμογή περιηγούμενος, οπότε ένα tag επιβιώνει όταν το έργο μετονομάζεται.

**Διευθύνσεις.** Ένα σύμβολο IEC, με ή χωρίς την εφαρμογή:

```
Application.GVL_Line.rTemp        a variable of a variable list
GVL_Line.rTemp                    the same; the application is assumed
Application.PLC_PRG.nCount        a program's variable
GVL.motors[2].speed               a field of an element of an array of structures
nsu=CODESYSSPV3/3S/IecVarAccess;s=|var|CODESYS Control for Linux SL.Application.GVL.x
                                  a node id, if you have one
```

**Ο εντοπισμός tags** απαριθμεί ό,τι εξάγει η εφαρμογή, με τους τύπους που έχει: ένα STRING είναι `string`, ένα BYTE `uint16`, ένα TIME `int64` (χιλιοστά του δευτερολέπτου), μια απαρίθμηση `int32`, τα ακέραια πλάτη κρατούν το δικό τους, τα REAL και LREAL είναι `float`. Το runtime λέει ότι ένα STRING, BYTE ή TIME είναι τύπος του μοντέλου PLCopen (για παράδειγμα `ns=3;i=3013`)· ο driver ακολουθεί τις αναφορές του `HasSubtype` μέχρι τον τυπικό τύπο του οποίου είναι είδος, που είναι και ο τρόπος με τον οποίο μια εγγραφή σε BYTE στέλνεται ως Byte. Κάθε μεταβλητή φέρει την πρόσβαση που δόθηκε στο σύμβολό της. Μια δομή και ένας πίνακας διατρέχονται: ένα σημείο ανά πεδίο και ανά στοιχείο. Παραλείπει τις ιδιότητες του ίδιου του runtime (`|vprop|`), τη λίστα εργασιών και το αντικείμενο Server.

Ένας πίνακας απαριθμεί τα πρώτα 32 στοιχεία του (`arrayElements`), επειδή ένα buffer χιλίων στοιχείων δεν είναι χίλια πράγματα για έναν πίνακα ελέγχου, και ένα tag μπορεί να διευθυνσιοδοτήσει οποιοδήποτε στοιχείο με το σύμβολό του έτσι κι αλλιώς. Η λίστα σταματά στο `browseMaxNodes` και το λέει· το `browseRoot` ορισμένο σε σύμβολο (`Application.GVL_Demo`) απαριθμεί ένα μέρος της εφαρμογής. Η περιήγηση γίνεται κατά πλάτος, οπότε οι μεταβλητές μιας λίστας έρχονται πριν από τα στοιχεία των πινάκων της, και οι απαντήσεις κρατούνται σε μέγεθος που δέχεται το runtime (κλείνει τη σύνδεση σε απάντηση εκατό πινάκων χιλίων στοιχείων).

Ρύθμιση: οι επιλογές OPC UA, και `device` (το όνομα του PLC, μόνο αν το runtime απαριθμεί περισσότερα από ένα), `application` (μόνο αν κανένα δεν λέγεται Application), `arrayElements`, `alarmSymbol` (το μπλοκ HotLoop Alarms, μόνο για να παραλειφθεί η αναζήτησή του). Μια επιλογή με λάθος ορθογραφία είναι σφάλμα που απαριθμεί τις έγκυρες. Ο κωδικός είναι μυστικό, αποθηκεύεται και αποκρύπτεται όπως κάθε μυστικό συσκευής.

**Τι ζητά το runtime από έναν client.** Δημοσιεύει `OperationLimits` 100 για αναγνώσεις, περιηγήσεις και παρακολουθούμενα στοιχεία ανά αίτημα, και απορρίπτει μεγαλύτερο με `BadTooManyOperations`. Ο driver διαβάζει αυτά τα όρια κατά τη σύνδεση και κόβει κάθε αίτημα σε αυτά, για κάθε συσκευή OPC UA (ένα runtime CODESYS ήταν το πρώτο για το οποίο μέτρησε: πριν από αυτό ο driver ανέφερε κάθε tag που εντόπιζε ως float και δεν διάβαζε κανένα από τα tags μιας συσκευής με πάνω από 100). Η δειγματοληψία είναι ένα δευτερόλεπτο από προεπιλογή και η ουρά ένα στοιχείο, επειδή ένα PLC έχει έναν κύκλο να προστατεύσει και μια πύλη Ignition που ήδη το διαβάζει δεν πρέπει να του τον στερηθεί· ορίστε `samplingIntervalMs` για να ζητήσετε περισσότερα.

**Λήψεις, επανεκκινήσεις και χαμένη σύνδεση.** Μια επανεκκίνηση του runtime, ή ένα νέο πρόγραμμα που φορτώνεται, διακόπτει τη συνεδρία. Η συσκευή γίνεται αποσυνδεδεμένη, κάθε tag διαβάζεται κακό με τον λόγο «το runtime του PLC δεν απαντά», και το HotLoop επανασυνδέεται μόνο του με backoff και διαβάζει τα σύμβολα όπως είναι τώρα. Ένα σύμβολο που διαβαζόταν και απορρίπτεται ως εξαφανισμένο δύο φορές στη σειρά λογίζεται ως λήψη στην οποία το runtime κράτησε τη συνεδρία, και η συνεδρία εγκαταλείπεται για την ίδια επανασύνδεση. Ένα tag για μεταβλητή που το πρόγραμμα δεν έχει διαβάζεται κακό με τον λόγο του διακομιστή και δεν προκαλεί επανασύνδεση.

**Ασφάλιση του διακομιστή OPC UA του runtime.** Ένα runtime CODESYS Control προσφέρει μόνο μη ασφαλή endpoints μέχρι ο διακομιστής OPC UA του να αποκτήσει πιστοποιητικό, και τότε προσφέρει επίσης τις πολιτικές του `CommunicationPolicy` του (AES128-SHA256-RSAOAEP από προεπιλογή, Basic256Sha256, AES256-SHA256-RSAPSS) με Sign και SignAndEncrypt. Το CODESYS τεκμηριώνει τη δημιουργία αυτού του πιστοποιητικού στο Security Screen (CODESYS Security Agent, Devices, ο ελεγκτής, OPC UA Server) και την εμπιστοσύνη σε έναν client μετακινώντας το πιστοποιητικό του από το «Certificates in Quarantine» στο «Trusted Certificates». Το PLC shell του runtime Linux κάνει το ίδιο χωρίς το IDE, με εντολές που το CODESYS απαριθμεί για το PLC shell του επεξεργαστή συσκευών (`cert-getapplist`, `cert-genselfsigned <n>`, `cert-getcertlist quarantine`, `cert-export`, `cert-import trusted`), μέσω του Unix socket που τεκμηριώνει γι' αυτό το runtime Linux (`/var/opt/codesyscontrolapi/plcshell.sock`, «Accessing the PLC Shell»). Ορίστε τη συσκευή σε `securityMode` `SignAndEncrypt` με ένα `securityPolicy`, συνδεθείτε μία φορά (το δικό του πιστοποιητικό του HotLoop καταλήγει στην καραντίνα του runtime και η σύνδεση απορρίπτεται, με μήνυμα που το λέει), εμπιστευτείτε εκείνο το πιστοποιητικό, και η συσκευή διαβάζει. Δεν δείχνονται: το Security Screen του IDE, ένα πιστοποιητικό υπογεγραμμένο από CA, η διαχείριση χρηστών με ασφαλισμένο runtime.

**Ένα runtime χωρίς άδεια σταματά μόνο του.** Ένα runtime CODESYS Control που δεν έχει άδεια τρέχει σε λειτουργία demo και τερματίζεται μετά από περίπου δύο ώρες (το log του runtime λέει `no runtime license - running in demo mode(~2 hours)` σε κάθε εκκίνηση). Από τη μεριά του HotLoop αυτό είναι μια επανεκκίνηση του runtime όπως κάθε άλλη: η συσκευή γίνεται αποσυνδεδεμένη με «το runtime του PLC δεν απαντά» και επανέρχεται μόνη της μόλις κάτι ξεκινήσει ξανά το runtime (η πολιτική επανεκκίνησης ενός container, μια μονάδα systemd). Τίποτα στο HotLoop δεν μετρά τις δύο ώρες ούτε αντιμετωπίζει τη διακοπή διαφορετικά, και τίποτα δεν επανεκκινεί το runtime για λογαριασμό σας· ένα runtime που δεν ξεκινά ξανά μένει αποσυνδεδεμένο. Δοκιμάστηκε σε runtime 4.22.0.0 σε container χωρίς άδεια: σταμάτησε μόνο του 2 ώρες και 5 λεπτά μετά την εκκίνησή του, με κωδικό εξόδου 0· η πολιτική επανεκκίνησης του container το ξεκίνησε ξανά 31 δευτερόλεπτα αργότερα, η εφαρμογή του έτρεχε 82 δευτερόλεπτα μετά, και η συσκευή διάβασε ξανά καλά 35 δευτερόλεπτα μετά την εκκίνηση της εφαρμογής (2 λεπτά και 28 δευτερόλεπτα από τη διακοπή), χωρίς κανένα χειροκίνητο βήμα.

**Εγγραφές.** Ένα tag είναι μόνο για ανάγνωση μέχρι κάποιος να το σημειώσει ως εγγράψιμο, όπως για κάθε συσκευή, και τίποτα από όσα δημιουργεί μια ρύθμιση δεν είναι. Μετά η πύλη εγγραφής είναι όπως για το OPC UA, με το μέρος του PLC μπροστά της: μια εγγραφή σε σύμβολο που έχει εξαχθεί ως μόνο για ανάγνωση, ή που ο χρήστης δεν επιτρέπεται να γράψει, απορρίπτεται με τα λόγια του PLC και δεν στέλνεται ποτέ.

**Ρύθμιση από τη ροή ενσωματώσεων** (`codesys`): η διεύθυνση του runtime, οι ερωτήσεις ασφάλειας OPC UA, και προαιρετικά ένας πρώτος πίνακας ελέγχου με τα σημεία που κρατούνται (η οθόνη που θα ήταν το WebVisu· δείτε [Ενσωματώσεις](/el/iot/integrations/#codesys)). Επαληθευμένο απέναντι σε runtime 4.22.0.0 σε container· δείτε τον πίνακα κατάστασης για όσα αυτό δεν καλύπτει.

### Modbus TCP/RTU

Το υποζύγιο του 1979. PLC, μετατροπείς συχνότητας, μετρητές ενέργειας, RTU, και η εφεδρεία κάθε πύλης που δεν έχει κάτι καλύτερο.

```
holding:100:float32:CDAB    a float across registers 100-101, word-swapped
holding:40:bit3             bit 3 of register 40
holding:200:string16        16 characters from register 200
input:12:int16              a signed input register
coil:5                      a single coil
```

**Η σειρά λέξεων** είναι η ρύθμιση που οι άνθρωποι κάνουν λάθος, και ένα float που διαβάζεται με λάθος σειρά δεν είναι προφανώς λάθος σε μια οθόνη, είναι ένας εύλογος αριθμός που δεν είναι η αλήθεια. Και οι τέσσερις μεταθέσεις υποστηρίζονται με τα ονόματα που τυπώνουν τα εγχειρίδια των κατασκευαστών: `ABCD`, `CDAB`, `BADC`, `DCBA`. Ορίστε μια προεπιλογή συσκευής με `byteOrder` και παρακάμψτε ανά tag με το τέταρτο πεδίο της διεύθυνσης.

**Η διευθυνσιοδότηση** είναι ωμή και με βάση το μηδέν. Αν τα σχέδιά σας χρησιμοποιούν την παραδοσιακή αρίθμηση τύπου 40001, ορίστε `oneBased: true` και γράψτε τους αριθμούς από τα σχέδια. Το να κάνετε λάθος κατά ένα είναι το αρχαιότερο σφάλμα του Modbus.

Οι αναγνώσεις συγχωνεύονται σε μπλοκ: διπλανοί και σχεδόν διπλανοί καταχωρητές γίνονται ένα αίτημα. Το `maxGap` ελέγχει πόσοι αχρησιμοποίητοι καταχωρητές αξίζει να διαβαστούν για να αποφευχθεί ένα δεύτερο ταξίδι (προεπιλογή 8), το `maxBlock` βάζει όριο σε ένα αίτημα (προεπιλογή 120, ανώτατο όριο πρωτοκόλλου 125).

Η εγγραφή ενός μεμονωμένου bit ενός holding register είναι ανάγνωση-τροποποίηση-εγγραφή, επειδή το Modbus δεν έχει ατομικό καθορισμό bit εκεί. Τα άλλα δεκαπέντε bit διατηρούνται.

### MQTT και Sparkplug B

Απλό MQTT, ή Sparkplug B ως **πλήρης πρωτεύουσα εφαρμογή host**.

Απλά topics:
```
mqtt:plant/line1/temperature              a scalar payload
mqtt:plant/line1/state|data.temperature   JSON, extracted by path
mqtt:plant/+/flow                         wildcards work
```

Μετρικές Sparkplug:
```
spb:GroupId|EdgeNodeId|DeviceId|Metric/Name
spb:Plant|Edge1||Node/Uptime               empty device = a node-level metric
```

Ως πρωτεύων host ο driver κάνει όσα ζητά η προδιαγραφή και οι περισσότερες ενσωματώσεις παραλείπουν:

- Δημοσιεύει μια retained γέννηση `STATE` με αντίστοιχο will, ώστε οι κόμβοι edge να βλέπουν τον host να πέφτει αντί να το συμπεραίνουν από χρονικό όριο. Μορφή Sparkplug 3.0 (`spBv1.0/STATE/<host>` που φέρει JSON) από προεπιλογή· ορίστε `legacyState` για τη συμβολοσειρά `ONLINE`/`OFFLINE` πριν από την 3.0.
- Παρακολουθεί τον κυλιόμενο αριθμό ακολουθίας κάθε κόμβου και ζητά από έναν κόμβο να ξαναγεννηθεί όταν παραλείπει έναν, επειδή ένα κενό σημαίνει ότι χάθηκαν μηνύματα και ο πίνακας ψευδωνύμων δεν είναι πια αξιόπιστος.
- Ζητά rebirth μετά τη δική του επανασύνδεση. Ένας host που έλειπε δεν έχει ιδέα τι άλλαξε όσο έλειπε.
- Ταιριάζει το `NDEATH` με το `NBIRTH` μέσω `bdSeq`, ώστε ένα πιστοποιητικό θανάτου που έμεινε από προηγούμενη συνεδρία να μην μπορεί να σκοτώσει την τρέχουσα.

Η σειρά των μηνυμάτων επιβάλλεται. Η ταυτόχρονη παράδοση μηνυμάτων Sparkplug τα αναδιατάσσει, κάτι που κάνει έναν υγιή κόμβο να μοιάζει ότι χάνει μηνύματα και προκαλεί καταιγίδα rebirth.

### EtherNet/IP (CIP)

Allen-Bradley ControlLogix, CompactLogix και Micro820. Τα tags έχουν ονόματα, οπότε ο ελεγκτής μπορεί να ερωτηθεί τι κρατά.

```
Temperature                    type from the tag's declared dataType
Speed:dint                     an explicit type wins
Program:MainProgram.Speed      a program-scoped tag, the colon is part of the path
Zones[0].Heater.On:bool        array elements and UDT members
```

Το CIP είναι ισχυρά τυποποιημένο και ο ελεγκτής απορρίπτει μια ανάγνωση της οποίας ο δηλωμένος τύπος δεν ταιριάζει, οπότε ο τύπος πρέπει να προέλθει από κάπου. Λαμβάνεται από το `dataType` του tag, ή από ένα επίθημα `:type` που υπερισχύει. Το άγνωστο πέφτει στο `REAL`, που είναι οι περισσότερες τιμές διεργασίας.

Οι αναγνώσεις ομαδοποιούνται σε αιτήματα πολλαπλών υπηρεσιών, με επιστροφή σε μεμονωμένες αναγνώσεις όταν αποτύχει μια ομάδα, ώστε μία κακή διαδρομή tag να μην τυφλώνει τα άλλα δεκαεννιά.

### S7comm

Siemens S7-300, 400, 1200 και 1500, πάνω από ISO-on-TCP με rack και slot.

```
db1:0:real        a REAL at DB1.DBD0
db1:4:dint        a DINT at DB1.DBD4
db1:8.3:bool      bit 3 of DB1.DBB8
db2:20:string32   a 32-character STRING
m:10:word         merker word MW10
i:0.1:bool        input I0.1
q:2:byte          output byte QB2
```

Ο τύπος απαιτείται για οτιδήποτε πλατύτερο από ένα byte. Το πρωτόκολλο δεν μπορεί να σας πει αν τέσσερα byte είναι REAL ή DINT, αυτό είναι γεγονός για το πρόγραμμα του PLC, όχι για το καλώδιο.

Από προεπιλογή rack 0, slot 1 (S7-1200/1500). Τα S7-300/400 είναι συνήθως slot 2. Το `connectType` είναι 3 από προεπιλογή (S7 Basic) ώστε η πύλη να μην καταλαμβάνει τη θέση σύνδεσης PG που θέλει ένας μηχανικός για το TIA Portal.

Δεν υπάρχει περιήγηση. Μια CPU S7 δεν δημοσιεύει τη διάταξη των data blocks της, που ζει στο έργο του TIA Portal.

### MTConnect

Τηλεμετρία εργαλειομηχανών μόνο για ανάγνωση. Δεν υπάρχει κανάλι εντολών στο MTConnect, και αυτός ο driver δεν προσποιείται το αντίθετο.

Διευθυνσιοδοτήστε με `dataItemId` ή με όνομα· οι agents είναι ασυνεπείς ως προς το ποιο είναι σταθερό, και η τεκμηρίωση των μηχανημάτων δείχνει το ένα ή το άλλο.

Δύο λεπτομέρειες που ξεχωρίζουν μια ενσωμάτωση που λειτουργεί από μια απλώς εύλογη: το `UNAVAILABLE` είναι ο agent που λέει ρητά ότι δεν έχει ένδειξη, γίνεται κακή ποιότητα, όχι το κείμενο «UNAVAILABLE» και όχι μηδέν. Και το νόημα ενός Condition είναι το όνομα του στοιχείου του (`Normal`, `Warning`, `Fault`, `Unavailable`), όχι τα δεδομένα χαρακτήρων του, που συνήθως είναι κενά.

Το `Browse` διαβάζει το `/probe` και διατρέχει το δέντρο εξαρτημάτων σε οποιοδήποτε βάθος.

### HTTP / REST

Η λύση για όλα τα υπόλοιπα, για μετρητές ενέργειας, αισθητήρες περιβάλλοντος, ελεγκτές OEM και την πλευρά REST μιας πύλης που μιλά κάτι ιδιοκτησιακό από κάτω.

```
power.kw                      nested fields
readings[0].value             array indexing
zones[name=Zone1].temp        select an array element by a field value
$.data.temperature            a leading $. is accepted
```

Αυτή η τρίτη μορφή είναι εκείνη που μετράει: αυτά τα API λατρεύουν να επιστρέφουν έναν μη ταξινομημένο πίνακα αντικειμένων `{name, value}`, και η ευρετηρίαση κατά θέση είναι ένα σφάλμα που περιμένει μια ενημέρωση firmware.

Ένα αίτημα εξυπηρετεί κάθε tag της συσκευής. Το `Browse` διατρέχει το έγγραφο και αναφέρει κάθε βαθμωτό με τη διαδρομή που οδηγεί σε αυτό.

### Υγεία του κουτιού

Το μηχάνημα στο οποίο τρέχει το HotLoop, ως συσκευή μόνο για ανάγνωση: `cpu_util_pct` (χρόνος CPU που δεν ήταν αδρανής από την τελευταία ανάγνωση), `mem_util_pct` (MemTotal έναντι MemAvailable), `disk_util_pct` (ο δίσκος του μηχανήματος, ένα statfs της ρίζας του host προσαρτημένης μόνο για ανάγνωση στο `diskPath`, `/host` από προεπιλογή), `data_util_pct` (ο τόμος στο `dataPath`, `/data`, ή ο πλησιέστερος υπάρχων φάκελος πάνω από αυτόν όταν δεν έχει προσαρτηθεί ακόμη κάτι εκεί), και `rtos_jitter_core1_us` έως `core3_us` όταν το `jitterFile` ονομάζει το αρχείο JSON `{"core1_us":3.2,"core2_us":2.9,"core3_us":4.1}` που ξαναγράφει ένας πράκτορας πραγματικού χρόνου (ένα αρχείο παλαιότερο από πέντε λεπτά διαβάζεται ως κακό). Η CPU και η μνήμη προέρχονται από το `procRoot` (`/proc`, ή `/host/proc` όταν είναι προσαρτημένο αυτό του host). Μια τιμή που δεν μπορεί να διαβαστεί είναι κακής ποιότητας με τον λόγο, ποτέ μηδέν. Η συσκευή δημιουργείται από το `HOTLOOP_BOX_HEALTH_NODE` ([Ο διακομιστής OPC UA](/el/edge/opc-ua-server/#υγεία-του-μηχανήματος-για-τον-πίνακα-ελέγχου-embernet)).

### Shelly

Ένα Shelly οποιασδήποτε γενιάς με το οποίο μιλάμε απευθείας, χωρίς broker στη μέση. Δείτε SHELLY.md. Προσθέστε μια συσκευή με το πρωτόκολλο `shelly` και τη διεύθυνση της συσκευής· αν έχει ορισμένη σύνδεση, `{"password":"..."}` (ο χρήστης είναι `admin`· μια συσκευή Gen2 ή νεότερη απαντάται με την πρόκληση digest SHA-256 και μια συσκευή Gen1 με Basic). Το `/shelly` λέει ποια γενιά είναι. Μια συσκευή Gen2, Gen3 ή Gen4 διαβάζεται με `Shelly.GetStatus` (`POST /rpc`) και κάθε στοιχείο που αναφέρει γίνεται tags που προστίθενται μόνα τους, μόνο για ανάγνωση μέχρι να τα οπλίσει ένας άνθρωπος: `switch:0.output`, `switch:0.apower`, `switch:0.aenergy.total`, `switch:0.temperature.tC`, `input:0.state`, `cover:0.current_pos`, `pm1:0.apower`, `em:0.total_act_power`, `temperature:100.tC`, `humidity:100.rh`, και τα `sys.uptime` και `wifi.rssi` της συσκευής. Ένα πεδίο που η συσκευή δεν έστειλε δεν γίνεται tag. Η έξοδος ενός διακόπτη (`Switch.Set`), η έξοδος και η φωτεινότητα ενός φωτός, η θέση ενός καλύμματος (`Cover.GoToPosition`) και ο στόχος ενός θερμοστάτη μπορούν να οπλιστούν για εγγραφή.

Μια συσκευή Gen2 ή νεότερη παίρνει επίσης ένα websocket (`ws://<device>/rpc`): ο driver στέλνει ένα πλαίσιο αιτήματος με `src`, όπως απαιτεί η σελίδα του καναλιού RPC του Shelly πριν ειδοποιήσει μια συσκευή, απαντά σε ένα πλαίσιο 401 με το τεκμηριωμένο αντικείμενο `auth` (SHA-256 πάνω στο `dummy_method:dummy_uri`), και διπλώνει τα `NotifyStatus` και `NotifyFullStatus` στο αντίγραφό του της κατάστασης, ώστε μια αλλαγή να φτάνει αμέσως στο tag και η ανίχνευση ενδιάμεσα να διαβάζει το αντίγραφο αντί για τη συσκευή. Το `NotifyEvent` (ένα πάτημα κουμπιού, μια αλλαγή ρύθμισης) καταχωρείται στο ημερολόγιο κάτω από τη συσκευή. Όταν το websocket είναι εκτός λειτουργίας, ή δεν έχει επιβεβαιώσει την κατάσταση πρόσφατα (45 δευτερόλεπτα χωρίς πλαίσιο ή pong, 2 λεπτά χωρίς πλήρη ανάγνωση), η ανίχνευση διαβάζει τη συσκευή μέσω HTTP.

Μια συσκευή Gen1 (`/status` και απλές διαδρομές ελέγχου GET, σύνδεση Basic) παίρνει το ίδιο σχήμα tags από τα δικά της λόγια: `relay:0.output`, `meter:0.power`, `meter:0.total` (watt-λεπτά μετατρεμμένα σε Wh), `light:0.output` και `.brightness`, `roller:0.current_pos`, `input:0.state`, `temperature:0.tC`, και για μετρητές ενέργειας και αισθητήρες `emeter:0.power`, `humidity:0.rh`, `flood:0.alarm`. Ένα ρελέ γράφεται με `/relay/<id>?turn=on|off`, ένα φως με `/light/<id>?turn=&brightness=`, ένα ρολό με `/roller/<id>?go=to_pos&roller_pos=`. Φτιαγμένο από τη δημοσιευμένη τεκμηρίωση του Shelly για Gen1 και Gen2 και δοκιμασμένο απέναντι σε καταγραφές πραγματικών συσκευών (ένα Plus 1, ένα Plug S και μια λάμπα Vintage)· όχι ακόμη απέναντι σε συσκευή στον πάγκο. Τα πεδία Gen1 για μετρητή ενέργειας, υγρασία, μπαταρία και πλημμύρα προέρχονται από την τεκμηρίωση και δεν έχουν καμία καταγραφή πίσω τους.

### Firmata

Ένα Arduino, ή οποιαδήποτε πλακέτα που τρέχει firmware Firmata, μέσω USB serial ή TCP, χωρίς πρόγραμμα host στη μέση. Δείτε FIRMATA.md. Προσθέστε μια συσκευή με το πρωτόκολλο `firmata` και τη σειριακή θύρα (`/dev/ttyACM0`, `serial:/dev/ttyUSB0`) ή `host:port`· επιλογές `{"baudRate":57600,"samplingMs":19,"bootWaitMs":5000}`. Ο driver περιμένει την έκδοση πρωτοκόλλου της πλακέτας (ρωτώντας κάθε 300 ms), ρωτά για το firmware, τις δυνατότητες και τον αναλογικό χάρτη της, και φτιάχνει ένα tag μόνο για ανάγνωση για κάθε ψηφιακό pin και αναλογική είσοδο που έχει η πλακέτα. Η διεύθυνση ενός tag λέει τι να γίνει με ένα pin: `D13`, `D2:in`, `D2:pullup`, `D13:out`, `D9:pwm`, `D10:servo`, `A0`, `I2C:0x48:0x00:2`. Η ψηφιακή είσοδος είναι η αναφορά θύρας που στέλνει η πλακέτα σε αλλαγή, η αναλογική είναι η αναφορά κάθε διαστήματος δειγματοληψίας, και κάθε ανίχνευση ζητά την έκδοση πρωτοκόλλου ώστε μια πλακέτα που χάθηκε να φαίνεται μέσα σε μία ανίχνευση· μια αναφορά firmware που φτάνει χωρίς να ζητηθεί είναι πλακέτα που επανεκκίνησε. Ένα pin που τα tags δεν αναφέρουν δεν αγγίζεται, και ένα απλό tag `D<n>` ορίζει το pin του ως είσοδο όταν συνδέεται ο driver, και ως έξοδο στην πρώτη εγγραφή του. Φτιαγμένο από το πρωτόκολλο 2.8.0 (protocol.md και i2c.md στο github.com/firmata/protocol) και εκτελεσμένο απέναντι σε StandardFirmata 2.5.9 σε προσομοιωμένο ATmega328P: τα ψηφιακά του pins, τα pull-ups, οι αναλογικές είσοδοι στα 0, 2,5 και 5 V, οι καταχωρητές σύγκρισης PWM, το pin ενός servo και οι καταχωρητές μιας συσκευής I2C διαβάστηκαν καθένα πίσω από το chip, όχι από τον driver. Δεν έχει εκτελεστεί σε φυσική πλακέτα.

### ONVIF

Μια κάμερα IP, ένας κωδικοποιητής ή ένα NVR. Δείτε ONVIF.md. Προσθέστε μια συσκευή με το πρωτόκολλο `onvif`, τη διεύθυνση της κάμερας και `{"username":"...","password":"..."}`. Ο driver διαβάζει πρώτα το GetSystemDateAndTime και σφραγίζει το WS-Security UsernameToken του με το ρολόι της ίδιας της κάμερας (Core Specification 5.12: το digest είναι `base64(SHA-1(nonce + created + password))`), διαβάζει τα GetDeviceInformation και GetServices (GetCapabilities για παλαιότερη κάμερα), χρησιμοποιεί Media2 όταν η κάμερα το απαριθμεί και Media όταν όχι, και διαβάζει τον κωδικοποιητή, την ανάλυση, τη διεύθυνση ροής και τη διεύθυνση στιγμιότυπου κάθε προφίλ. Μια κάμερα που θέλει HTTP Digest ή Basic στο SOAP post απαντάται με αυτό. Οι διευθύνσεις υπηρεσιών προσεγγίζονται στον host με τον οποίο προστέθηκε η συσκευή εκτός αν `"keepXAddrHosts":true`. Ένα προφίλ PTZ προσθέτει `ptz.<token>.pan`, `.tilt`, `.zoom` και `.moving` από το GetStatus, και τις οπλίσιμες εντολές `.move` (ContinuousMove, με προαιρετικό timeout), `.absolute` (AbsoluteMove), `.goto_preset` (GotoPreset, με token ή όνομα), `.stop` και `.home`. Τα συμβάντα έρχονται από ένα pull point (CreatePullPointSubscription, PullMessages, Renew, Unsubscribe) και γίνονται tags `event.<topic>|<source>|<item>` που προστίθενται μόνα τους, με κάθε αλλαγή στο ημερολόγιο. Ένα στιγμιότυπο είναι `GET /api/onvif/<device>/profiles/<token>/snapshot` και η ανακάλυψη είναι `POST /api/onvif/discover` (WS-Discovery, ένα multicast Probe για `NetworkVideoTransmitter`).

Φτιαγμένο από τις προδιαγραφές ONVIF Core, Media, Media2, PTZ και Event (onvif.org/specs). Κάθε αίτημα που στέλνει είναι έγκυρο απέναντι στα αρχεία WSDL και XSD του ONVIF (xmllint, με τους 33 τύπους και ένα στοιχείο που το libxml2 αρνείται για μοναδική απόδοση σωματιδίων χαλαρωμένα, κανένα από τα οποία δεν χρησιμοποιεί ένα αίτημα), και εκτελείται απέναντι στο onvif_srvd, μια ανεξάρτητη στοίβα ONVIF που αναλύει την κεφαλίδα WS-Security αλλά δεν την ελέγχει, οπότε το digest της σύνδεσης κρατιέται αντί αυτού στο zeep 4.3.3. Η υπηρεσία συμβάντων και το WS-Discovery έχουν μόνο σενάρια γραμμένα από την προδιαγραφή για να τρέξουν απέναντί τους. Δεν έχει εκτελεστεί σε φυσική κάμερα.

### UniFi Network

Το δίκτυο του εργοστασίου ως συσκευή: ένας χώρος σε μία κονσόλα UniFi, τα switches της, κάθε θύρα switch, η κατανάλωση PoE, οι συνδέσεις WAN και η υγεία του χώρου, ως tags που δημιουργούνται μόνα τους καθώς υιοθετείται ο εξοπλισμός, μόνο για ανάγνωση μέχρι να οπλιστεί. Μία σύνδεση ανά κονσόλα, το πιστοποιητικό καρφιτσωμένο και ο κωδικός της κονσόλας κρυπτογραφημένος στη βάση δεδομένων. Αλλάζει την κονσόλα μόνο μέσω των λίγων tags εντολών που οπλίζει ένας άνθρωπος (ένα LED εντοπισμού, μια επανεκκίνηση, ένας κύκλος τροφοδοσίας PoE μιας θύρας· δείτε UNIFI.md). Ακούει επίσης το websocket συμβάντων της κονσόλας, ώστε ένα switch που πέφτει να είναι στο ημερολόγιο όταν συμβαίνει, με το polling να παραμένει η αλήθεια από κάτω, και η καρτέλα UniFi σχεδιάζει την επισκόπηση, τον χάρτη, τις πρόσοψεις, τους clients, τα δίκτυα και το WiFi. Τα πάντα γι' αυτό βρίσκονται στο [UniFi Network](/el/iot/unifi/).

### UniFi Protect

Οι κάμερες, οι αισθητήρες, τα φώτα και οι σειρήνες ενός Protect NVR, μέσω του Protect Integration API με κλειδί API από τη σελίδα Integrations της κονσόλας (το κλειδί μπαίνει στο `{"apiKey":"..."}`, σφραγισμένο όπως ο κωδικός της κονσόλας, και το πιστοποιητικό καρφιτσώνεται με `certFingerprint` όπως για το UniFi Network). Προσθέστε μια συσκευή με το πρωτόκολλο `unifi-protect` και τη διεύθυνση της κονσόλας. Τα tags προστίθενται μόνα τους, μόνο για ανάγνωση μέχρι να οπλιστούν: `cam.<id>.online`, `.motion`, και `.smart_person`, `.smart_vehicle`, `.smart_package`, `.smart_licensePlate`, `.smart_face` και `.smart_animal` για τα είδη που υποστηρίζει μια κάμερα· `sen.<id>.online`, `.open`, `.motion`, `.leak`, `.tamper`, `.temp_c`, `.humidity_pct`, `.light_lux`· `light.<id>.online`, `.on`, `.motion`· `siren.<id>.online`. Η κίνηση και οι έξυπνες ανιχνεύσεις μιας κάμερας προέρχονται από το websocket συμβάντων της κονσόλας, αφού η εγγραφή REST δεν έχει καμία, οπότε διαβάζονται ως κακές, ποτέ ως "καμία κίνηση", όσο είναι εκτός λειτουργίας. Κάθε συμβάν είναι στο ημερολόγιο κάτω από τη συσκευή. Το `.play` μιας σειρήνας είναι οπλισμένο για εγγραφή (το `true` παίζει, το `false` σταματά), και το ίδιο το `alarm.<trigger>.fire`, που στέλνει το webhook του διαχειριστή συναγερμών για το αναγνωριστικό εναύσματος που έφτιαξε ο άνθρωπος στο Protect, ώστε ένας συναγερμός του HotLoop που το γράφει να κάνει τις κάμερες να καταγράφουν. Το στιγμιότυπο μιας κάμερας είναι `GET /api/unifi-protect/<device>/cameras/<camera>/snapshot`, ένα JPEG που λαμβάνεται όταν ζητηθεί. Φτιαγμένο από το έγγραφο OpenAPI της Ubiquiti για το Protect 7.4.102· δεν έχει εκτελεστεί ακόμη απέναντι σε κονσόλα. Δείτε [UniFi Network](/el/iot/unifi/#unifi-protect).

### UniFi Access

Οι πόρτες μιας κονσόλας Access, μέσω του Access developer API στη θύρα 12445 με token API από τις προηγμένες ρυθμίσεις της (`{"token":"..."}`, σφραγισμένο). Προσθέστε μια συσκευή με το πρωτόκολλο `unifi-access` και τη διεύθυνση της κονσόλας. Ανά πόρτα, `door.<id>.open` (ο αισθητήρας θέσης· μια πόρτα χωρίς τέτοιον διαβάζεται ως κακή, ποτέ κλειστή), `door.<id>.unlocked` (το ρελέ της κλειδαριάς), και `door.<id>.unlock`, που οπλίζει ένας άνθρωπος και ξεκλειδώνει την πόρτα όταν γραφτεί `true`, μέσα από την πύλη εγγραφής και ελεγμένο όπως κάθε εγγραφή· η κονσόλα την κλειδώνει ξανά με τον δικό της κανόνα. Το websocket ειδοποιήσεων κρατά τη θέση και την κλειδαριά ενημερωμένες ανάμεσα στις ανιχνεύσεις, και κάθε αλλαγή ("1F - Front: opened", "unlocked") είναι στο ημερολόγιο κάτω από τη συσκευή. Φτιαγμένο από το API όπως το μιλά ο συντηρούμενος ανοιχτός client (py-unifi-access, MIT)· δεν έχει εκτελεστεί ακόμη απέναντι σε κονσόλα. Δείτε [UniFi Network](/el/iot/unifi/#unifi-access).

### SNMP

Οτιδήποτε έχει agent SNMP: switches, UPS, PDU, μετρητές ενέργειας και κάθε μηχάνημα Linux που τρέχει agent SNMP. Μόνο για ανάγνωση. Το HotLoop δεν στέλνει ποτέ SNMP SET, επειδή ένα SET μπορεί να αλλάξει τη ρύθμιση ενός switch και ο σκοπός αυτού του driver είναι να βλέπει το δίκτυο του εργοστασίου, όχι να το τρέχει.

```
1.3.6.1.2.1.1.5.0             sysName
.1.3.6.1.2.1.1.3.0            sysUpTime, a leading dot is accepted
1.3.6.1.2.1.2.2.1.8.2         ifOperStatus of the interface with ifIndex 2
```

Η διεύθυνση ενός tag είναι το OID μίας εμφάνισης, αριθμοί χωρισμένοι με τελείες. Ένα βαθμωτό τελειώνει σε `.0`· ένα κελί πίνακα τελειώνει στον δείκτη της γραμμής του. Το `dataType` του tag αποφασίζει σε τι μετατρέπεται:

* Ένας αριθμός που έστειλε ο agent (Integer, Gauge32, Counter32, Counter64, TimeTicks) είναι αυτός ο αριθμός. Η κλίμακα και η μετατόπιση εφαρμόζονται όπως παντού.
* Ένα OCTET STRING είναι κείμενο, εκτός αν το tag είναι αριθμός, οπότε αναλύεται. Έτσι φτάνει ένας μέσος όρος φορτίου (το `laLoad` είναι το κείμενο `0.15`) ή μια θερμοκρασία πίσω από έναν agent. Κείμενο που δεν είναι αριθμός είναι κακή ένδειξη που το λέει, ποτέ μηδέν.
* Ένα OCTET STRING που δεν είναι εκτυπώσιμο (μια διεύθυνση MAC) είναι `0x` και δεκαεξαδικά ψηφία.

**Οι μετρητές είναι ωμοί.** Ένας Counter32 ή Counter64 μόνο ανεβαίνει και κάνει περιτύλιξη. Το tag κρατά ό,τι έστειλε ο agent, και ο ρυθμός είναι δουλειά αυτού που διαβάζει το tag. Ο Counter64 κρατιέται ως float, που είναι ακριβής μέχρι το 2^53· μια θύρα με ταχύτητα γραμμής χρειάζεται δεκαετίες για να φτάσει εκεί.

**Τα TimeTicks είναι εκατοστά του δευτερολέπτου**, οπότε το `sysUpTime` διαβασμένο ως απλό tag είναι σε 1/100 s. Η ενσωμάτωση το μετατρέπει σε δευτερόλεπτα για εσάς· ένα tag φτιαγμένο με το χέρι πρέπει να ορίσει `scale` σε `0.01`.

**Ένα αντικείμενο που ο agent δεν έχει είναι κακή ένδειξη με τον λόγο**, και τα άλλα στο ίδιο αίτημα διαβάζονται παρ' όλα αυτά: το v2c και το v3 λένε ποια έλειπαν, και για το v1, που απαντά σε ένα αντικείμενο που λείπει με σφάλμα για ολόκληρο το αίτημα, ο driver αφαιρεί εκείνο και ρωτά ξανά για τα υπόλοιπα. Μια απάντηση πολύ μεγάλη για τον agent ζητείται ξανά σε μισά.

Επιλογές συσκευής (`config`):

| Επιλογή | Σημασία |
|---|---|
| `version` | `1`, `2c` ή `3`. Προεπιλογή `2c` |
| `community` | Η κοινότητα v1 και v2c. Απαιτείται για αυτά, και **δεν υπάρχει προεπιλογή**: το `public` είναι ο τρόπος με τον οποίο διαβάζονται τα switches ενός εργοστασίου από όποιον ρωτήσει. Μυστικό |
| `username` | Ο χρήστης v3 |
| `securityLevel` | `noAuthNoPriv`, `authNoPriv` ή `authPriv`. Προεπιλογή: `authPriv` με φράση πρόσβασης απορρήτου, `authNoPriv` με μόνο μία πιστοποίησης, αλλιώς `noAuthNoPriv` |
| `authProtocol` | `MD5`, `SHA`, `SHA224`, `SHA256`, `SHA384` ή `SHA512`. Προεπιλογή `SHA` |
| `authPassword` | Η φράση πρόσβασης πιστοποίησης. Μυστικό |
| `privProtocol` | `DES`, `AES`, `AES192`, `AES256`, `AES192C` ή `AES256C`. Προεπιλογή `AES` |
| `privPassword` | Η φράση πρόσβασης απορρήτου. Μυστικό |
| `contextName` | Το πλαίσιο v3. Σχεδόν πάντα κενό |
| `transport` | `udp` (προεπιλογή) ή `tcp` |
| `retries` | Πόσες φορές ξαναστέλνεται ένα αίτημα που δεν πήρε απάντηση, 0 έως 10. Προεπιλογή 1 |
| `maxRepetitions` | Γραμμές ανά GETBULK σε μια διάσχιση. Προεπιλογή 10, στο οποίο απαντούν και οι μικρότεροι agents |
| `browseRoots` | OID που διατρέχονται κατά τον εντοπισμό σημείων. Προεπιλογή: system, οι πίνακες διεπαφών, host resources, ο πίνακας φορτίου και οι έξοδοι extend ενός agent SNMP |
| `browseMaxNodes` | Πού σταματά μια περιήγηση. Προεπιλογή 2000 |

Η διεύθυνση είναι `host` ή `host:port`, θύρα 161 από προεπιλογή.

**Μια λάθος κοινότητα απαντά με τίποτα.** Ένας agent SNMPv1 ή v2c πετά ένα αίτημα που φέρει κοινότητα που δεν γνωρίζει, οπότε μια λάθος κοινότητα, μια λάθος θύρα, ένα firewall και ένας agent εκτός λειτουργίας μοιάζουν όλα με timeout, και το μήνυμα του HotLoop αναφέρει και τα τέσσερα. Το SNMPv3 τα ξεχωρίζει: μια λάθος φράση πρόσβασης ή ένας άγνωστος χρήστης απορρίπτεται ως τέτοιος (`ErrAuthRejected`), και το HotLoop περιμένει πολλή ώρα πριν ξαναδοκιμάσει τα ίδια διαπιστευτήρια.

Το `Browse` διατρέχει τα υποδέντρα που μπορεί να κατονομάσει το HotLoop και δίνει σε κάθε αντικείμενο ένα όνομα: αυτό της MIB, όπως `sysName`, `ifOperStatus.2`, `ifHCInOctets.2`, `laLoad.1`, ή το OID ως `oid.1.3.6.1...` για ένα που δεν γνωρίζει. Τα ονόματα, και τα OID, οι τύποι και οι μονάδες πίσω από αυτά, προέρχονται από τις MIB που τα ορίζουν: SNMPv2-MIB (RFC 3418), IF-MIB (RFC 2863), HOST-RESOURCES-MIB (RFC 2790) και UCD-SNMP-MIB και NET-SNMP-EXTEND-MIB ενός agent SNMP. Όλα τα άλλα που έχει ο agent εξακολουθούν να διαβάζονται· προσθέστε τα ως tag με OID.

Η ενσωμάτωση (δείτε [Ενσωματώσεις](/el/iot/integrations/#snmp)) κάνει τις ερωτήσεις για εσάς.

### BACnet/IP

Ένας ελεγκτής αυτοματισμού κτιρίου, ένας μετρητής, ένας θερμοστάτης: οτιδήποτε στο δίκτυο IP μιλά BACnet. Μόνο για ανάγνωση. Το HotLoop δεν γράφει ποτέ μια ιδιότητα BACnet, επειδή μια εγγραφή προσγειώνεται σε έξοδο που μπορεί να διαταχθεί μέσω ενός πίνακα προτεραιοτήτων, και μια προτεραιότητα που μένει ορισμένη κρατά τον εξοπλισμό εκεί που τοποθετήθηκε πολύ αφότου έχει πάει σπίτι του όποιος την όρισε. Αυτό είναι χαρακτηριστικό που σχεδιάζεται σκόπιμα, όχι κάτι που αφήνεται να σέρνεται.

Κρατιέται σε πλαίσια καταγεγραμμένα από πραγματική συσκευή, αποκωδικοποιημένα από δοκιμές που τρέχουν πάντα, και σε εκείνη τη συσκευή στις δοκιμές.

```
analog-input:1                present value of analog input 1
ai:1                          the same, abbreviated
av:3.units                    a property other than the present value, by name
analog-input:1.117            or by number
multi-state-value:2           present value of a multi-state value
```

Η διεύθυνση ενός tag είναι το αντικείμενο, `<type>:<instance>`, και μια τελεία και μια ιδιότητα όταν δεν είναι η present value. Οι τύποι, με όνομα ή συντομογραφία: `analog-input` (`ai`), `analog-output` (`ao`), `analog-value` (`av`), `binary-input` (`bi`), `binary-output` (`bo`), `binary-value` (`bv`), `multi-state-input` (`msi`), `multi-state-output` (`mso`), `multi-state-value` (`msv`), `accumulator` (`acc`), `integer-value` (`iv`), `positive-integer-value` (`piv`), `large-analog-value` (`lav`) και `characterstring-value` (`csv`). Οι ιδιότητες με όνομα είναι `present-value`, `object-name`, `description`, `units`, `status-flags`, `out-of-service`, `reliability`, `number-of-states`, `state-text`, `object-type`, `object-identifier`, `object-list`, `vendor-name`, `vendor-identifier`, `model-name`, `firmware-revision` και `application-software-version`· οποιαδήποτε άλλη ιδιότητα είναι ο αριθμός της.

Το τι γίνεται ένα tag ακολουθεί το `dataType` του: ένας αριθμός που έστειλε η συσκευή (real, double, unsigned, signed, enumerated, boolean) είναι αυτός ο αριθμός, και το `active` ενός δυαδικού αντικειμένου είναι 1 και το `inactive` είναι 0· μια συμβολοσειρά χαρακτήρων είναι κείμενο, ή αριθμός αν το tag είναι και το κείμενο είναι αριθμός· μια present value `null` είναι κακή ένδειξη που λέει ότι η συσκευή δεν έχει τίποτα να αναφέρει. Μια ιδιότητα που κρατά περισσότερες από μία τιμές (μια λίστα αντικειμένων) δεν μπορεί να είναι tag.

**Οι σημαίες κατάστασης είναι μέρος της ένδειξης.** Κάθε polling ζητά τις σημαίες κατάστασης ενός αντικειμένου στο ίδιο αίτημα με την present value του, και ένα αντικείμενο του οποίου η σημαία **fault** είναι ενεργή διαβάζεται **κακό**, με τον λόγο. Ένα που είναι **εκτός λειτουργίας** ή **παρακαμφθέν** διαβάζεται **αβέβαιο**: η present value του είναι κάτι που έβαλε εκεί άνθρωπος ή πρόγραμμα, όχι μέτρηση, και τα διαγράμματα τάσης και οι αναφορές αφήνουν έξω τις αβέβαιες ενδείξεις όπως τις κακές (ο κανόνας ποιότητας). Το **σε συναγερμό** μόνο του είναι καλή ένδειξη ενός σημείου που βρίσκεται σε συναγερμό.

**Ό,τι δεν έχει η συσκευή είναι κακή ένδειξη με τον λόγο, και τα υπόλοιπα διαβάζονται παρ' όλα αυτά.** Το ReadPropertyMultiple απαντά για κάθε ιδιότητα χωριστά, οπότε ένα αντικείμενο που δεν υπάρχει (`unknown-object`) ή μια ιδιότητα που δεν έχει (`unknown-property`) αποτυγχάνει εκείνο το tag και κανένα άλλο. Μια συσκευή που αρνείται το ReadPropertyMultiple διαβάζεται από εκεί και πέρα μία ιδιότητα τη φορά.

**Τίποτα δεν τεμαχίζεται.** Ο client λέει στη συσκευή ότι δεν μπορεί να δεχτεί τεμαχισμένη απάντηση. Μια συσκευή της οποίας η απάντηση δεν θα χωρούσε σε ένα πλαίσιο διακόπτει (`segmentation-not-supported`), και το HotLoop ζητά τα μισά αντικείμενα τη φορά· μια συσκευή της οποίας η λίστα αντικειμένων είναι πολύ μεγάλη για να σταλεί ολόκληρη διαβάζεται ένα στοιχείο τη φορά.

Επιλογές συσκευής (`config`):

| Επιλογή | Σημασία |
|---|---|
| `deviceInstance` | Ο αριθμός εμφάνισης που αναμένεται να έχει η συσκευή σε αυτή τη διεύθυνση. Όταν είναι ορισμένος και η συσκευή δηλώνει άλλον, η σύνδεση απορρίπτεται: μια διαφορετική συσκευή που απαντά σε επαναχρησιμοποιημένη διεύθυνση, ή ένας ελεγκτής που αντικαταστάθηκε, είναι ο τρόπος με τον οποίο ένα εργοστάσιο παίρνει έναν καθαρής όψης λάθος αριθμό |
| `localAddress` | Η διεύθυνση της κάρτας δικτύου αυτού του μηχανήματος από την οποία γίνεται η αποστολή, για host με περισσότερες από μία. Συνήθως κενό |
| `retries` | Πόσες φορές ξαναστέλνεται ένα αίτημα που δεν πήρε απάντηση, 0 έως 10. Προεπιλογή 1 |
| `browseMaxObjects` | Πού σταματά μια περιήγηση. Προεπιλογή 1000 |

Η διεύθυνση είναι `host` ή `host:port`, θύρα 47808 από προεπιλογή. Τίποτα στο BACnet/IP δεν είναι διαπιστευτήριο, οπότε δεν υπάρχουν να κρυφτούν.

**Η σύνδεση ρωτά τη συσκευή ποια είναι.** Το HotLoop στέλνει στη συσκευή ένα unicast Who-Is και παίρνει την εμφάνιση συσκευής από το I-Am. Μια συσκευή που δεν απαντά σε ένα τέτοιο ερωτάται για το δικό της αντικείμενο συσκευής κάτω από την εμφάνιση-μπαλαντέρ (4194303), στην οποία το πρότυπο λέει ότι μια συσκευή απαντά ως ο εαυτός της. Μια συσκευή που δεν απαντά σε κανένα αναφέρεται με δοκιμασμένα και τα δύο, επειδή οι συνήθεις λόγοι μοιάζουν: λάθος διεύθυνση ή θύρα, ένα firewall, μια συσκευή εκτός λειτουργίας, ή μια συσκευή σε δίκτυο πίσω από router.

**Η δρομολόγηση δεν έχει χτιστεί.** Το HotLoop μιλά σε μια συσκευή στην οποία μπορεί να στείλει ένα datagram UDP. Ένας ελεγκτής σε κορμό MS/TP πίσω από router BACnet, ή σε άλλο δίκτυο BACnet, δεν είναι προσβάσιμος, ούτε μια συσκευή που τη φτάνει μόνο ένα BBMD (εγγραφή ξένης συσκευής). Διευθυνσιοδοτήστε την πλευρά BACnet/IP του ίδιου του router, ή βάλτε μια πύλη μπροστά: δείτε [λειτουργία πύλης](#όλα-τα-υπόλοιπα-λειτουργία-πύλης).

Το `Browse` διαβάζει το αντικείμενο της ίδιας της συσκευής (το όνομά της, τον κατασκευαστή, το μοντέλο και το firmware), τη λίστα αντικειμένων της, και κάθε αντικείμενο που διαβάζει το HotLoop: όνομα, περιγραφή, μονάδες, present value και σημαίες κατάστασης, και το κείμενο κατάστασης ενός αντικειμένου πολλαπλών καταστάσεων. Ένα tag παίρνει το όνομα του ίδιου του αντικειμένου, με τη διεύθυνση προστιθέμενη όταν δύο αντικείμενα το μοιράζονται. Οι μονάδες γίνονται ετικέτα και, όπου σημαίνουν μία, κλάση οντότητας: οι βαθμοί Κελσίου είναι `°C` και `temperature`, το ποσοστό σχετικής υγρασίας είναι `%` και `humidity`, η κιλοβατώρα είναι `kWh` και `energy`. Μια μονάδα για την οποία το HotLoop δεν έχει ετικέτα μένει χωρίς ετικέτα και κατονομάζεται στην περιγραφή με τον αριθμό της. Οι αριθμοί και τα ονόματα αυτών των μονάδων κρατιούνται σε πραγματική συσκευή, που στέλνει τον αριθμό που δίνει ο δικός της πίνακας σε κάθε όνομα. Η ενσωμάτωση (δείτε [Ενσωματώσεις](/el/iot/integrations/#bacnetip)) κάνει τις ερωτήσεις για εσάς.

## Προς τα έξω: το Kafka API

Όλα τα παραπάνω φέρνουν μέσα τις τιμές μιας συσκευής. Το HotLoop μπορεί επίσης να τις στείλει προς έναν broker Kafka ως ροή συμβάντων: κάθε ένδειξη που κρατά ο historian, και κάθε γραμμή του log συστήματος (συναγερμοί, συσκευές που πέφτουν και επανέρχονται, αλλαγές), ως JSON σε topics που ονομάζετε εσείς. Είναι προορισμός historian, που ρυθμίζεται στο Ρυθμίσεις, Προορισμοί historian, και δέχεται Apache Kafka, Redpanda και οτιδήποτε άλλο μιλά το Kafka API, μέσω TLS με σύνδεση SASL. Οι μορφές εγγραφών, τι σημαίνει εδώ το «τουλάχιστον μία φορά», και τι έχει και τι δεν έχει αποδειχθεί βρίσκονται στο [Προορισμοί historian](/el/iot/historian-targets/#kafka-api-ροή-συμβάντων). Ο client είναι το [franz-go](https://github.com/twmb/franz-go).

## Όλα τα υπόλοιπα: λειτουργία πύλης

**PROFINET · EtherCAT · HART · DNP3 · FINS · MELSEC/SLMP · CANopen · FANUC FOCAS**

Αυτά δεν μιλιούνται εγγενώς και δεν υπάρχει driver γι' αυτά. Είναι συνειδητή επιλογή, όχι κενό που περιμένει να γεμίσει με ένα stub.

Οι χώροι που τρέχουν αυτά τα πρωτόκολλα έχουν σχεδόν πάντα ήδη μια πύλη που αναδημοσιεύει σε OPC UA ή Modbus: έναν ελεγκτή PROFINET IO με διακομιστή OPC UA, έναν πολυπλέκτη HART με χάρτη Modbus. Στρέψτε μια συσκευή σε εκείνο το endpoint και ρυθμίστε την ως OPC UA ή Modbus.

Το να γραφτούν οκτώ ακόμη drivers που ο καθένας διπλασιάζει ό,τι κάνει ήδη η υπάρχουσα πύλη ενός χώρου θα πρόσθετε οκτώ ακόμη πράγματα να γίνουν λάθος με λεπτό τρόπο, για πρωτόκολλα όπου ο εξοπλισμός είναι ο πιο δύσκολος να δοκιμαστεί. Αν ένας χώρος πράγματι δεν έχει πύλη και χρειάζεται ένα από αυτά εγγενώς, αυτό είναι πραγματική δουλειά που πρέπει να προγραμματιστεί, όχι ένα αρχείο που προστίθεται και καταγράφει «not implemented».

**Δεν υπάρχουν driver-υποκατάστατα σε αυτό το δέντρο.** Ένα πρωτόκολλο είτε έχει λειτουργική υλοποίηση είτε βρίσκεται σε αυτή την ενότητα. Μια δοκιμή επιβάλλει ότι κάθε πρωτόκολλο που δηλώνει το μοντέλο έχει driver μεταγλωττισμένο, και αντίστροφα.

## Διαπιστευτήρια συσκευής

Το `config` και το `address` μιας συσκευής είναι εκεί όπου ένας driver βρίσκει αυτό με το οποίο συνδέεται. Αυτά είναι τα διαπιστευτήρια που διαβάζει κάθε πρωτόκολλο, και όλα είναι μόνο για εγγραφή μέσω του API (4.15.1): εμφανίζονται ως `[redacted]` σε κάθε ρόλο, μια αποθήκευση που στέλνει το σύμβολο υποκατάστασης ή παραλείπει το κλειδί κρατά την αποθηκευμένη τιμή, και μια νέα συμβολοσειρά την αντικαθιστά. Οι κανόνες, και ό,τι δεν περνά από το API, βρίσκονται στο [Πιστοποίηση και χρήστες](/el/iot/authentication/#τα-διαπιστευτήρια-συσκευών-είναι-μόνο-για-εγγραφή).

| Πρωτόκολλο | Διαπιστευτήρια στη ρύθμιση | Διαπιστευτήρια στη διεύθυνση |
|---|---|---|
| OPC UA | `password` (με `username`) | κανένα: οι πληροφορίες χρήστη στη διεύθυνση κρύβονται και ο driver τις αγνοεί |
| MQTT / Sparkplug B | `password` (με `username`) | `mqtt://user:pass@host`, που το χρησιμοποιεί ο client |
| HTTP / REST | `password` (με `username`, σταλμένο ως basic auth)· κάθε τιμή στο `headers` εκτός από τις απλές όπως `Accept` και `Content-Type`, που είναι εκεί όπου πηγαίνει ένα κλειδί API ή μια κεφαλίδα `Authorization`· τα `body` και `writeBody` αν αναφέρουν διαπιστευτήριο | `http://user:pass@host` και τιμές ερωτήματος τύπου `?api_key=`, στη διεύθυνση και στο `writeUrl` |
| MTConnect | `password` (με `username`)· κάθε τιμή στο `headers`, με τις ίδιες εξαιρέσεις | `http://user:pass@host` και τιμές ερωτήματος |
| UniFi Network | `password` (με `username`). Αποθηκεύεται μόνο κρυπτογραφημένο: χωρίς κλειδί (παρακάτω) η συσκευή δεν μπορεί να αποθηκευτεί | κανένα: η διεύθυνση είναι το URL `https://` της κονσόλας |
| BACnet/IP | κανένα | κανένα: η διεύθυνση είναι `host` ή `host:port` |
| CODESYS | `password` (με `username`), όπως για το OPC UA | κανένα: οι πληροφορίες χρήστη στη διεύθυνση κρύβονται και ο driver τις αγνοεί |
| SNMP | `community` (v1, v2c)· `authPassword` και `privPassword` (v3), με `username` | κανένα: η διεύθυνση είναι `host` ή `host:port` |
| Modbus, S7comm, EtherNet/IP | κανένα | κανένα: οι πληροφορίες χρήστη στη διεύθυνση κρύβονται και ο driver τις αγνοεί |

**Κρυπτογραφημένα σε αδράνεια.** Με ορισμένο το `HOTLOOP_SECRET_KEY_FILE` (το chart το ορίζει, με κλειδί που παράγει), κάθε διαπιστευτήριο στη στήλη ρύθμισης παραπάνω κρυπτογραφείται στη βάση δεδομένων με αυτό το κλειδί, που ζει έξω από τη βάση δεδομένων, οπότε ένα dump ή αντίγραφο ασφαλείας περιέχει κρυπτογραφημένο κείμενο. Το υπόλοιπο HotLoop, και οι drivers, δεν βλέπουν ποτέ τη διαφορά. Ένα διαπιστευτήριο γραμμένο σε URL (`mqtt://user:pass@host`, `?api_key=`) ή σε ελεύθερο κείμενο όπως ένα HTTP `body` κρυπτογραφείται επίσης: ολόκληρη η διεύθυνση ή επιλογή σφραγίζεται και επιστρέφει ακριβώς όπως πληκτρολογήθηκε, και ένα URL χωρίς τίποτα μυστικό μένει αναγνώσιμο. Η επιλογή `password` παραμένει το πιο τακτοποιημένο μέρος για ένα. Δείτε [Αντίγραφα ασφαλείας και επαναφορά](/el/iot/backup/#διαπιστευτήρια-συσκευών-και-το-μυστικό-κλειδί).

Οποιαδήποτε άλλη επιλογή με όνομα που μοιάζει με διαπιστευτήριο (περιέχει `password`, `token`, `secret`, `apikey`, `authorization`, `private`, `passphrase`, ή τελειώνει σε `key`, ή έχει ολόκληρη λέξη όπως `pass`, `pw`, `auth`, `cred` ή `sig`, μεταξύ άλλων) κρύβεται επίσης, σε όποιο πρωτόκολλο κι αν βρίσκεται, οπότε μια επιλογή που προστίθεται αργότερα σε έναν driver μένει κρυμμένη μέχρι κάποιος να αποφασίσει ότι δεν πρέπει να είναι. Μια δοκιμή διατρέχει τις επιλογές κάθε driver και αποτυγχάνει μέχρι κάθε μία να βρίσκεται είτε στη λίστα των διαπιστευτηρίων είτε στη λίστα των επιλογών που είναι γνωστό ότι δεν είναι. Δείτε [Πιστοποίηση και χρήστες](/el/iot/authentication/#τα-διαπιστευτήρια-συσκευών-είναι-μόνο-για-εγγραφή) για τους πλήρεις κανόνες.

## Προσθήκη συσκευής

1. **Συσκευές → Προσθήκη συσκευής.** Διαλέξτε το πρωτόκολλο, δώστε του μια διεύθυνση.
2. **Εντοπισμός tags** όπου το πρωτόκολλο το υποστηρίζει: OPC UA, EtherNet/IP, MTConnect, MQTT (μετά από γέννηση Sparkplug), HTTP, SNMP, BACnet/IP, CODESYS. Το Modbus και το S7comm δεν μπορούν να απαριθμήσουν τα δικά τους σημεία, οπότε δηλώστε τα από την τεκμηρίωση της συσκευής.
3. Τα tags που εισάγονται δημιουργούνται **μόνο για ανάγνωση**. Ένα σημείο που τυχαίνει να εκθέτει η συσκευή δεν είναι σημείο που κάποιος αποφάσισε ότι επιτρέπεται να διαταχθεί. Σημειώστε τα tags ως εγγράψιμα ένα-ένα, σκόπιμα.
4. Ορίστε `scale` και `offset` για ωμές μετρήσεις: `engineering = raw × scale + offset`. Αν το όργανο στέλνει έναν κωδικό όταν ένα κανάλι είναι νεκρό ή εκτός εύρους, καταχωρίστε τον στις [Τιμές χωρίς δεδομένα](#τιμές-χωρίς-δεδομένα) ώστε να διαβάζεται κακός αντί για αριθμός.
5. Ορίστε `deadband` σε οτιδήποτε έχει θόρυβο. Καταστέλλει τις εγγραφές στον historian για αλλαγές πολύ μικρές για να μετρούν, και χωρίς αυτό ένας αισθητήρας 12 bit που τρέμει στο τελευταίο του bit γράφει μια γραμμή σε κάθε κύκλο για πάντα.

## Τιμές χωρίς δεδομένα

Ένας καταγραφέας με καμένο θερμοζεύγος δεν σιωπά. Συνεχίζει να απαντά, και ό,τι βάζει στον καταχωρητή είναι ένας κωδικός: 0x8005 για «undefined», 0x7FFF για «over range». Διαβασμένο ως int16 με κλίμακα 0,1, το 0x8005 είναι -3276,3 βαθμοί, και μέχρι να το διορθώσουμε επέστρεφε με **καλή** ποιότητα, έμπαινε στον historian ως πραγματική θερμοκρασία και καθόταν εκεί για να το κρίνουν οι συναγερμοί. Ένας νεκρός αισθητήρας έμοιαζε με κρύο.

Έτσι ένα tag μπορεί να απαριθμήσει τις ωμές τιμές που σημαίνουν «καμία μέτρηση». Καθεμία έχει λόγο. Όταν η ωμή τιμή μιας ένδειξης βρίσκεται στη λίστα, η ένδειξη είναι **κακή**, ο λόγος είναι πάνω της, και η κλίμακα και η μετατόπιση δεν την αγγίζουν ποτέ.

```json
{
  "deviceId": "dx-1", "name": "ch01", "address": "input:1:int16",
  "dataType": "float", "unit": "C", "scale": 0.1, "enabled": true,
  "noData": [
    {"raw": "0x7FFF", "reason": "+over"},
    {"raw": "0x8001", "reason": "-over"},
    {"raw": "0x8002", "reason": "skip"},
    {"raw": "0x8004", "reason": "error"},
    {"raw": "0x8005", "reason": "undefined"},
    {"raw": "0x7F7F", "reason": "power fail"},
    {"raw": "0x7FFA", "reason": "burnout up"},
    {"raw": "0x8006", "reason": "burnout down"}
  ]
}
```

Αυτοί οι οκτώ είναι οι κωδικοί της οικογένειας Yokogawa DX, από το εγχειρίδιο επικοινωνίας του DX (IM 04L41B01-17E, ενότητα 4.3, σελίδα 4-35). Δεν είναι ειδικοί για το HotLoop: είναι το ίδιο πεδίο σε κάθε tag κάθε πρωτοκόλλου, και η λίστα του DX είναι απλώς αυτή που μας δάγκωσε πρώτη. Καθένας βρίσκεται στο tag, οπότε ένα κανάλι καταγραφέα που πράγματι μπορεί να διαβάσει 0x7F7F σε κάποια άλλη μονάδα το κρατά ως ένδειξη.

| Πεδίο | <span class="sr-only">Λεπτομέρειες</span> |
|---|---|
| `raw` | Ο κωδικός της συσκευής, γραμμένος όπως τον τυπώνει το εγχειρίδιό της: `"0x8005"` (δεκαεξαδικό), `"-32763"` ή `32773` (δεκαδικό). Μια συμβολοσειρά ή ένας απλός αριθμός. Απαιτείται |
| `reason` | Τι λέει η ποιότητα της ένδειξης. Έως 120 χαρακτήρες. Αν παραλειφθεί, λέει `raw value 0x8005 means no measurement`, ώστε μια ένδειξη να μην γίνεται ποτέ κακή χωρίς να λέει γιατί |

Στον επεξεργαστή tags είναι το πλαίσιο **Τιμές χωρίς δεδομένα**: ένας κωδικός ανά γραμμή, ο κωδικός, ένα κενό, ο λόγος.

### Ποιον αριθμό γράφετε

Για ένα σημείο Modbus που βασίζεται σε καταχωρητή, ο κωδικός είναι ο ακέραιος που κρατά η συσκευή, αφού εφαρμοστεί η σειρά byte και λέξεων του σημείου. Είναι ο ίδιος αριθμός στον οποίο αποκωδικοποιείται το σημείο, οπότε ένα εγχειρίδιο που λέει «το όργανο επιστρέφει 8005h» σημαίνει ακριβώς `"0x8005"` εδώ.

- **int16 και οι άλλοι προσημασμένοι τύποι.** Το `0x8005` και το `-32763` είναι ο ίδιος καταχωρητής, και το `32773` επίσης. Γράψτε ό,τι γράφει το εγχειρίδιο· και τα τρία ταιριάζουν. Ένας κωδικός που δεν χωρά στον τύπο (`0x10000` σε int16) απορρίπτεται όταν συνδεθεί η συσκευή, επειδή μια λίστα που δεν μπορεί ποτέ να ταιριάξει είναι χειρότερη από σφάλμα. Δύο γραφές της ίδιας τιμής στο ίδιο tag απορρίπτονται επίσης.
- **uint16 και οι άλλοι ανυπόσημοι τύποι.** Από `0` μέχρι το μέγιστο του τύπου. Ένας αρνητικός αριθμός απορρίπτεται.
- **int32, uint32, int64, uint64.** Οι ίδιοι κανόνες στα 32 και 64 bit. Το `0x7FFFFFFF` σε int32 με σειρά λέξεων `CDAB` είναι η τιμή αφού οι λέξεις μπουν στη σωστή σειρά, όχι η σειρά με την οποία βγήκαν από το καλώδιο.
- **float32 και float64.** Ο κωδικός είναι το μοτίβο bit του καταχωρητή, οπότε πρέπει να είναι δεκαεξαδικός: `0x7FC00000` για ένα σιωπηλό NaN. Ένας δεκαδικός απορρίπτεται, επειδή το 32773 ως float και το 32773 ως μοτίβο bit είναι διαφορετικά πράγματα και δεν θα μαντέψουμε.
- **Bits, coils, διακριτές είσοδοι και συμβολοσειρές.** Δεν υπάρχει ωμός αριθμός για σύγκριση, οπότε το `noData` σε ένα από αυτά απορρίπτεται όταν συνδεθεί η συσκευή.

Ο έλεγχος γίνεται στα ωμά bit, πριν από την αποκωδικοποίηση, πριν από την κλίμακα, πριν από τη μετατόπιση.

### Άλλα πρωτόκολλα

Κάθε driver που παραδίδει έναν ήδη αποκωδικοποιημένο αριθμό ελέγχει την ίδια λίστα: S7comm, EtherNet/IP, OPC UA, HTTP και MQTT (συμπεριλαμβανομένων των συσκευών που εντοπίζονται). Αυτό που συγκρίνουν είναι αυτός ο αποκωδικοποιημένος αριθμός, ως ακέραιος, οπότε γράψτε τον ως τον αριθμό που είναι. Ένα S7 INT που κρατά 0x8005 είναι -32763, οπότε γράψτε `-32763`. Το δεκαεξαδικό εδώ είναι απλώς ένας άλλος τρόπος να γραφτεί ο ίδιος αριθμός, επειδή ένας αποκωδικοποιημένος αριθμός έχει χάσει το πλάτος του και δεν μπορεί να διαβαστεί πίσω ως μοτίβο bit. Μια κλασματική τιμή δεν ταιριάζει ποτέ. Η λίστα αξίζει να οριστεί μόνο εκεί όπου η συσκευή στέλνει κωδικούς σαν αυτούς· τα περισσότερα από όσα αναφέρουν το MTConnect και το UniFi δεν το κάνουν ποτέ.

### Τι κάνει μια τιμή-φρουρός

- Η **ποιότητα** είναι `bad` και η ένδειξη φέρει τον λόγο. Εμφανίζεται στο `GET /api/values` και στη ζωντανή ροή (`reason`), δίπλα στην ποιότητα στην οθόνη Tags, και στις οντότητες του tag ως το χαρακτηριστικό `quality_reason`.
- Η **τιμή** είναι κενή, όχι μηδέν και όχι ο κωδικός σε κλίμακα. Η κλίμακα και η μετατόπιση δεν εφαρμόζονται.
- Ο **historian** καταγράφει την ποιότητα ως κακή, όπως κάθε άλλη κακή ένδειξη, και η στήλη τιμής του δεν περιέχει τίποτα με νόημα. Ένα διάστημα χωρίς καμία καλή ένδειξη εμφανίζεται ως κενό σε μια τάση, όπως για κάθε κακή ένδειξη.
- **Συναγερμοί.** Μια κακή ένδειξη δεν ενεργοποιεί ποτέ συναγερμό τιμής: υψηλό, χαμηλό, ίσο, ρυθμός μεταβολής κρατούν όλα την προηγούμενη κατάστασή τους, όπως για κάθε κακή ένδειξη. Ένας συναγερμός `bad-quality` στο tag ενεργοποιείται, και το προεπιλεγμένο μήνυμά του φέρει τον λόγο (`dx-1/ch01 bad-quality: undefined`). Χρησιμοποιήστε `{reason}` στο δικό σας μήνυμα για να τον βάλετε εκεί.
- Το **ημερολόγιο** καταγράφει ότι η οντότητα του tag γίνεται κακή, και ο λόγος είναι το χαρακτηριστικό `quality_reason` της οντότητας.

### Πού ζει

Στο tag, αποθηκευμένο μαζί του. Μέσω του API είναι η λίστα `noData` στο `POST /api/tags` (δείτε [το HTTP API](/el/iot/api/#post-apitags)), στον επεξεργαστή είναι το πλαίσιο παραπάνω, και σε ένα Edge Relay είναι το ίδιο JSON στο tag του αρχείου συσκευής (δείτε [Αναφορά Edge Relay](/el/edge-relay/reference/)). Η αποθήκευση του tag φορτώνει ξανά την εκτελούμενη συσκευή, οπότε μια αλλαγή ισχύει στο επόμενο polling και τίποτα δεν επανεκκινείται με το χέρι. Ένας νέος εντοπισμός αφήνει ανέγγιχτη τη λίστα ενός tag.

## Ποιότητα

Κάθε ένδειξη φέρει `good`, `uncertain` ή `bad`.

**Κακό σημαίνει ότι η τιμή δεν είναι γνωστή. Δεν σημαίνει μηδέν.** Ένας driver που δεν μπορεί να διαβάσει ένα σημείο εκπέμπει παρ' όλα αυτά μια ένδειξη, σημειωμένη ως κακή, επειδή η σιωπή δεν διακρίνεται από μια τιμή που δεν άλλαξε, και σε μια τάση η διαφορά ανάμεσα στο «ο αισθητήρας διαβάζει 0» και στο «ο αισθητήρας σταμάτησε να απαντά» είναι η διαφορά ανάμεσα σε πρόβλημα διεργασίας και πρόβλημα οργάνου.

Η αξιολόγηση συναγερμών κρατά την προηγούμενη κατάστασή της σε μια κακή ένδειξη αντί να την αξιολογεί. Ένας αισθητήρας που αποτυγχάνει προς το μηδέν θα ενεργοποιούσε αλλιώς κάθε συναγερμό χαμηλού της μονάδας και θα έμοιαζε με συμβάν διεργασίας.
