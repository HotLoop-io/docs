Το Edge Relay, από την 4.6.0, είναι ένα δεύτερο εκτελέσιμο και τρέχει μόνο του: ένας κόμβος Sparkplug B edge που διαβάζει και προωθεί, χωρίς βάση δεδομένων, χωρίς web διεπαφή, χωρίς έλεγχο ταυτότητας και χωρίς διαδρομή εγγραφής. Υπάρχει για να τρέχει σε ένα Pi ή σε έναν μικρό βιομηχανικό υπολογιστή στην άκρη και να προωθεί ό,τι διαβάζει σε ένα πλήρες Gateway που τρέχει κάπου αλλού με πραγματική βάση δεδομένων, μέσω του ίδιου εκδότη Sparkplug B που πρόσθεσε η 4.5.0.

Η σημείωση της 4.5.0 το έλεγε ευθέως: η δημοσίευση από το edge υπήρχε ως λειτουργία που μπορούσες να ενεργοποιήσεις μέσα στη διεργασία του πλήρους Gateway, «όχι ακόμη η αυτόνομη, ελαφρύτερη έκδοση Edge Relay». Αυτή είναι εκείνη η έκδοση.

## Τι δεν είναι

**Όχι ένα μικρότερο Gateway με λιγότερες επιλογές.** Είναι άλλο εκτελέσιμο με πολύ μικρότερο σύνολο εξαρτήσεων. Δεν έχει βάση δεδομένων, web διεπαφή, έλεγχο ταυτότητας, διακομιστή ή πελάτη MCP, μηχανή αυτοματισμού ούτε μητρώο οντοτήτων.

**Δεν μπορεί να σερβίρει διεπαφή, να δεχτεί εγγραφή ή να απαντήσει σε κλήση εργαλείου MCP.** Και τα τρία χρειάζονται κάτι που αυτό το εκτελέσιμο σκόπιμα δεν έχει: μια πιστοποιημένη ταυτότητα στην οποία να αποδοθεί η ενέργεια. Ένα edge relay δεν αποφασίζει τίποτα και δεν επιβεβαιώνει τίποτα σε άνθρωπο· διαβάζει και προωθεί.

**Δεν διαμορφώνεται μέσω βάσης δεδομένων και δεν έχει δικό του API διαμόρφωσης.** Οι συσκευές και τα tag προέρχονται από ένα τοπικό αρχείο JSON που διαβάζεται κατά την εκκίνηση, ή από ένα αρχείο που το Gateway στέλνει μέσω του broker και εφαρμόζεται άμεσα (δείτε [Αποστολή διαμόρφωσης](#αποστολή-διαμόρφωσης-480)). Τίποτα στο relay δεν ακούει για νέα διαμόρφωση: η μόνη είσοδος είναι η σύνδεση με τον broker που ήδη ανοίγει προς τα έξω.

## Πώς δένουν όλα

Εσωτερικά επαναχρησιμοποιεί την πραγματική μηχανή ανάγνωσης του Gateway, όχι μια επανυλοποίησή της: ο ίδιος worker, η ίδια επανασύνδεση με backoff και ο ίδιος βρόχος ανάγνωσης που τρέχουν στην παραγωγή ως μέρος του Gateway τρέχουν εδώ αμετάβλητοι. Αυτό που διαφέρει είναι *πού πηγαίνουν η διαμόρφωση και το ιστορικό*.

Ό,τι ακολουθεί μια ανάγνωση, ο driver, ο δίαυλος των tag, ο εκδότης Sparkplug και η ουρά προώθησης στον δίσκο, είναι ακριβώς ο ίδιος κώδικας που χρησιμοποιεί το Gateway όταν έχει οριστεί το `HOTLOOP_EDGE_PUBLISH_ENABLED`. Δείτε τη σελίδα Edge publish για το τι κάνει πράγματι ο εκδότης: births, αριθμοί ακολουθίας, buffering κατά τη διάρκεια διακοπής, επανάληψη κατά την επανασύνδεση. Τίποτα από αυτά δεν άλλαξε εδώ· αυτό το εκτελέσιμο είναι απλώς άλλος δρόμος προς την ίδια κλήση `Offer()`.

## Το αρχείο συσκευών

```json
{
  "devices": [
    {
      "id": "press-01",
      "name": "Press 1",
      "protocol": "opcua",
      "address": "opc.tcp://press-01.local:4840",
      "enabled": true,
      "pollIntervalMs": 1000
    }
  ],
  "tags": [
    {
      "deviceId": "press-01",
      "name": "Zone1_Temp",
      "address": "ns=2;s=Zone1.Temp",
      "dataType": "float",
      "enabled": true
    }
  ]
}
```

Ένα tag δέχεται ό,τι δέχονται τα tag του Gateway, συμπεριλαμβανομένου του `noData`: μια λίστα ακατέργαστων τιμών που σημαίνουν «καμία μέτρηση» (το 0x8005 ενός καταγραφέα), καθεμία με έναν λόγο, ώστε ένα νεκρό κανάλι να εμφανίζεται ως κακό στο relay και στη ροή Sparkplug αντί για αριθμός. Δείτε [Τιμές χωρίς δεδομένα](/el/iot/protocols/#no-data-values).

Και οι επτά driver πρωτοκόλλων του Gateway είναι ενσωματωμένοι: OPC UA, Modbus, MQTT/Sparkplug B, EtherNet/IP, S7comm, MTConnect και HTTP. Τίποτα στη μορφή του αρχείου συσκευών δεν είναι ειδικό για το edge relay.

### Discovery (4.18.10)

Ένα relay μπορεί να ακούει έναν MQTT broker για συσκευές που ανακοινώνονται μόνες τους, όπως κάνει το Gateway (δείτε [Ανακάλυψη MQTT](/el/iot/mqtt-discovery/)), και να διαβάζει και να προωθεί ό,τι ακούει. Ονομάστε τους brokers στο αρχείο συσκευών:

```json
{
  "devices": [],
  "tags": [],
  "discovery": [
    {
      "id": "yard",
      "broker": "10.0.0.5:1883",
      "username": "hotloop",
      "password": "...",
      "prefix": "homeassistant",
      "listenOnly": true,
      "tasmota": true,
      "shelly": true
    }
  ]
}
```

Το `id` είναι από 1 έως 63 πεζά γράμματα, ψηφία και `-`, και δεν είναι `embedded`. Τα `broker`, `username`, `password`, `useTls` και `insecureSkipVerify` είναι όσα δέχονται οι ρυθμίσεις MQTT του Gateway, ελεγμένα από τον ίδιο κώδικα. Το `prefix` είναι από προεπιλογή `homeassistant`, και τα `tasmota` και `shelly` είναι ενεργά. Ένα αρχείο που δεν ονομάζει κανέναν broker δεν αλλάζει τίποτα στον τρόπο λειτουργίας ενός relay.

Ό,τι ακούει γίνεται συσκευές και tag, φτιαγμένα από τον ίδιο κώδικα που τρέχει το Gateway (η μορφή `homeassistant/`, η δική του Tasmota, οι καταστάσεις του Shelly), και διαβάζονται και προωθούνται μέσω Sparkplug όπως όλα τα άλλα. Το id μιας συσκευής προκύπτει από το id του broker και από το ποια λέει η συσκευή ότι είναι, και είναι κάθε φορά το ίδιο (`disc-<identity>-<hash>`), ώστε ένα relay που επανεκκινεί να ονομάζει τις μετρικές του με τον ίδιο τρόπο. Μια συσκευή εμφανίζεται μερικά δευτερόλεπτα μετά την ανακοίνωσή της, μια αποσυρμένη φεύγει από το birth του κόμβου σε ένα rebirth, και κανένα από τα δύο δεν κοστίζει τη συνεδρία Sparkplug ούτε την ουρά προώθησης. Ένα αρχείο που στέλνεται και προσθέτει ή αφαιρεί έναν broker εφαρμόζεται επίσης άμεσα.

**Τίποτα από όσα ανακαλύπτει δεν μπορεί να οπλιστεί.** Όχι επειδή το λέει κάποιος έλεγχος. Κάθε tag που δημιουργεί η ανακάλυψη είναι μόνο για ανάγνωση, όπως στο Gateway· κάθε συσκευή που δημιουργεί δεν είναι αποδεκτή· δεν υπάρχει κανείς στο relay να αποδεχτεί μία· και ένα relay δεν έχει καμία διαδρομή εγγραφής, οπότε μια εντολή προς ένα ανακαλυφθέν σημείο, ή προς οποιοδήποτε σημείο, απορρίπτεται πριν πλησιάσει συσκευή. Η δοκιμή ζητά από ένα relay με επιτρεπόμενες εγγραφές να ενεργοποιήσει μια ανακαλυφθείσα αντλία και ελέγχει ότι το topic εντολών της αντλίας έμεινε σιωπηλό.

Μια συσκευή που μπορείτε να διατάξετε φτάνει σε ένα relay από την αντίστροφη πορεία: την αποδέχεστε σε ένα Gateway, οπλίζετε τα σημεία που θέλετε και στέλνετε το αρχείο. Όταν ένα αρχείο έχει μια συσκευή που ακούει και το relay (ίδιο id broker, ή ίδια διεύθυνση, και ίδια ταυτότητα), κερδίζει το αρχείο και το ανακαλυφθέν αντίγραφο δεν δημιουργείται, ώστε μια συσκευή να μην προωθείται ποτέ δύο φορές.

Το `listenOnly` είναι ενεργό εκτός αν το απενεργοποιήσετε, και τότε το relay δεν δημοσιεύει τίποτα σε εκείνον τον broker: ούτε το μήνυμα birth που κάνει έναν εκδότη να ανακοινωθεί ξανά, ούτε το `status_update` ενός Shelly, ούτε το ερώτημα ισχύος ενός Tasmota. Μια συσκευή που μιλά μόνο όταν αλλάζει εμφανίζεται ως άγνωστη μέχρι να το κάνει. Αν το απενεργοποιήσετε, αυτά είναι τα μόνα που στέλνει, στα topic που κατονομάζει το DISCOVERY.md.

Ένα relay δεν κρατά τίποτα από όσα άκουσε. Οι διαμορφώσεις `homeassistant/` και Tasmota είναι retained στον broker τους και επιστρέφουν κατά την εκκίνηση· ένα Shelly λέει τις καταστάσεις του όποτε αλλάζει κάτι, οπότε μια συσκευή που σιωπά από την εκκίνηση του relay δεν υπάρχει μέχρι να μιλήσει. Αυτό, και η έλλειψη βάσης δεδομένων για να θυμάται μια αποδεκτή συσκευή, είναι η διαφορά από το Gateway.

Το `/status` λέει, κάτω από το `discovery`, για κάθε broker: αν ακούει και είναι συνδεδεμένος, πόσα μηνύματα έλαβε, απέρριψε και αρνήθηκε, πόσα προβλήματα έχει, και τον αριθμό συσκευών και tag που δημιούργησε η ανακάλυψη. Δεν λέει πού βρίσκεται ένας broker ή σε ποιο topic εμφανίστηκε ένα πρόβλημα.

### Διαπιστευτήρια στο αρχείο συσκευών (4.15.0)

Ο driver OPC UA του relay είναι αυτός του Gateway, οπότε μια συσκευή μπορεί να φέρει `username` και `password` OPC UA (και τις επιλογές ασφάλειας από [Πρωτόκολλα και drivers](/el/iot/protocols/#opc-ua-security-and-credentials)) στο μπλοκ `config` της, και το ίδιο μπορεί μια συσκευή οποιουδήποτε άλλου πρωτοκόλλου (κωδικοί MQTT και HTTP, κεφαλίδες HTTP, διαπιστευτήρια σε μια διεύθυνση). Βρίσκονται σε απλό κείμενο στο αρχείο συσκευών, και το relay δεν έχει API πίσω από το οποίο να τα κρύψει (η απόκρυψη API που προστέθηκε στο Gateway στην 4.15.1 δεν ισχύει εδώ· δείτε [Έλεγχος ταυτότητας και χρήστες](/el/iot/authentication/#πού-τα-διαπιστευτήρια-είναι-ακόμη-σε-καθαρό-κείμενο)), άρα έχει σημασία πού βρίσκεται το αρχείο:

- **Στο Helm chart, χρησιμοποιήστε το `devicesSecret`.** Οι συσκευές που ορίζονται στις τιμές `devices` και `tags` του chart αποδίδονται σε ένα ConfigMap, που μπορεί να διαβάσει όποιος έχει δικαίωμα ανάγνωσης ConfigMap στο namespace, και διατηρούνται στην εγγραφή της έκδοσης Helm. Για συσκευές με διαπιστευτήρια, βάλτε ολόκληρο το αρχείο συσκευών σε ένα Secret με κλειδί `devices.json` και ονομάστε το στο `devicesSecret`· το Secret προσαρτάται στη θέση του ConfigMap, που τότε δεν δημιουργείται.
- **Και ένα αρχείο συσκευών που στέλνεται τα φέρει.** Ένα αρχείο που στέλνεται με `POST /api/fleet/{id}/config` δημοσιεύεται, retained, σε ένα MQTT topic, οπότε ο broker πρέπει να έχει TLS και να περιορίζει ποιος μπορεί να διαβάσει το `hotloop/edge-relay-config/#`, αλλιώς όποιος μπορεί να εγγραφεί σε αυτό διαβάζει κάθε διαπιστευτήριο που περιέχει. Το relay γράφει ένα αρχείο που στέλνεται με mode `0600` στον τόμο δεδομένων του (`/data/pushed-devices.json` στο chart και στη μονάδα Quadlet), άρα βρίσκεται και στο PVC, όχι σε Secret.
- **Μια ασφαλής συσκευή OPC UA κρατά ένα πιστοποιητικό και ένα trust store.** Βρίσκονται κάτω από το `/data/opcua-client-pki` (`HOTLOOP_OPCUA_CLIENT_PKI_DIR`), στον ίδιο τόμο διατήρησης με την ουρά προώθησης. Με απενεργοποιημένη τη διατήρηση του chart είναι ένα emptyDir, οπότε κάθε νέο pod φτιάχνει νέο πιστοποιητικό και κάθε ασφαλής διακομιστής πρέπει να το εμπιστευτεί ξανά (δείτε «Persistence off» παρακάτω)· μια ανώνυμη συσκευή σε μη ασφαλές κανάλι δεν επηρεάζεται. Η έγκριση του πιστοποιητικού ενός διακομιστή είναι η ίδια κίνηση όπως στο Gateway, από `rejected/` σε `trusted/`, που γίνεται στον τόμο του relay.

## Απομακρυσμένες εντολές (4.7.0)

Δύο εντολές Sparkplug NCMD, και οι δύο μέσω της ίδιας σύνδεσης που το relay ήδη ανοίγει προς τα έξω, χωρίς εισερχόμενη σύνδεση:

- **Restart** (`Node Control/Reboot`), από την 4.7.0: το relay δημοσιεύει το δικό του ομαλό NDEATH και βγαίνει, βασιζόμενο στον επόπτη του (το `Restart=always` μιας μονάδας Quadlet, ή το προεπιλεγμένο `restartPolicy: Always` ενός Deployment) για να το ξαναθέσει σε λειτουργία.

- **Update** (`Node Control/Update`): ένας χειριστής που εγκρίνει την ενημέρωση εικόνας που κρατά πίσω ένα relay. Κάνει κάτι μόνο σε relay ρυθμισμένο να κρατά πίσω τις ενημερώσεις· δείτε [Ενημέρωση ενός relay](#ενημέρωση-ενός-relay).

Τίποτα από την πλευρά του relay δεν αποφασίζει ποιος επιτρέπεται να τις στείλει· δείτε τη σελίδα διαχείρισης στόλου για τον διαχειριστή στόλου από την πλευρά του Gateway που τις στέλνει, και την απαίτηση ACL του broker, που είναι το πραγματικό όριο εξουσιοδότησης.

## Ενημέρωση ενός relay

Ένα relay δεν ενημερώνεται από το Gateway. Δεν μπορεί: το Gateway δεν έχει τρόπο να μπει στο μηχάνημα, και το relay δεν μπορεί να αντικαταστήσει το δικό του container, οπότε η «απομακρυσμένη ενημέρωση» σημαίνει διαφορετικά πράγματα για τους δύο τρόπους εγκατάστασης, και αυτή η σελίδα λέει ποιο, γιατί μια υπόσχεση που η πλατφόρμα δεν μπορεί να τηρήσει είναι χειρότερη από καμία.

**Ο κανόνας είναι αυτός που ακολουθεί κάθε κουτί HotLoop: ακολουθήστε το `:stable`, μην καρφώνετε ποτέ.** Ένα relay καρφωμένο στο `4.17.0` είναι τόσο παλιό όσο η μέρα που το εγκατέστησε κάποιος, και κανείς δεν θυμάται να γυρίσει στο εργοστάσιο να το ανεβάσει. Έτσι η εικόνα που ακολουθεί ένα relay είναι η `ghcr.io/hotloop-io/hotloop-edge-relay:stable`, και κάθε έκδοση μετακινεί αυτό το tag. Αυτό που διαφέρει είναι ποιος επανεκκινεί το relay σε αυτήν.

### Quadlet (ένα Pi ή ένας μικρός βιομηχανικός υπολογιστής): ενημερώνεται μόνο του

Η μονάδα στο [`deploy/quadlet`](/el/install/quadlet/) ακολουθεί το `:stable` και φέρει την ετικέτα που αναζητά η αυτόματη ενημέρωση του Podman. Ενεργοποιήστε το χρονόμετρο μία φορά ανά μηχάνημα:

```sh
sudo systemctl enable --now podman-auto-update.timer
```

Όταν ενεργοποιείται το χρονόμετρο, το Podman κατεβάζει το `:stable` και, αν το digest άλλαξε, επανεκκινεί τη μονάδα στη νέα εικόνα. Τρία πράγματα το κάνουν ασφαλές να το αφήσετε μόνο του, και τα τρία αποδείχθηκαν εκτελώντας τα, όχι διαβάζοντας:

- **Ένα relay που δεν μπορεί να επανέλθει επαναφέρεται.** Η μονάδα έχει healthcheck (`/edge-relay --healthcheck`, επειδή η εικόνα δεν έχει shell ή curl για να τρέξει ένα) και λέει στο systemd ότι δεν είναι ενεργή μέχρι να περάσει. Αν η νέα εικόνα δεν το περάσει ποτέ, το Podman μετακινεί την προηγούμενη εικόνα πίσω κάτω από το `:stable` και ξεκινά εκείνη. Μια έκδοση που δεν ξεκινά κοστίζει λίγα λεπτά σε ένα κουτί, όχι ένα relay που μένει εκτός λειτουργίας. Στο Podman 4.9 (Ubuntu 24.04) το `Notify=healthy` μόνο του δεν το κάνει: διαβάζεται ως απλό `true`, το relay θεωρείται ενεργό μόλις ξεκινήσει το container του, και το Podman αναφέρει την ενημέρωση ως επιτυχή ενώ το relay είναι νεκρό. Η μονάδα ορίζει ρητά `--sdnotify=healthy` γι' αυτόν τον λόγο.
- **Το Gateway βλέπει κάθε ενημέρωση.** Ένα relay βάζει την έκδοσή του και το digest της εικόνας του σε κάθε birth. Η λίστα στόλου του Gateway δείχνει και τα δύο ανά relay και γράφει μια γραμμή στο αρχείο καταγραφής συστήματος όταν αλλάξει το ένα: τι ήταν, τι είναι τώρα και τα δύο digest. Αυτό είναι το ίχνος ελέγχου, και καλύπτει ενημέρωση από οποιαδήποτε αιτία, συμπεριλαμβανομένου ενός χειριστή στο κουτί.
- **Μια ενημέρωση αφήνει τα δεδομένα ήσυχα.** Η ουρά προώθησης και ένα αρχείο συσκευών που στάλθηκε βρίσκονται στον τόμο δεδομένων, που μια νέα εικόνα δεν αγγίζει. Αυτό που χάνεται είναι η ανάγνωση όσο το relay επανεκκινεί, λίγα δευτερόλεπτα το πολύ.

Το digest που αναφέρει ένα relay είναι αυτό που εκτυπώνει το `podman image inspect --format '{{.Digest}}'` σε εκείνο το κουτί, δηλαδή αυτό που ακολουθεί η αυτόματη ενημέρωση. Το Podman μπορεί να γνωρίζει μια εικόνα με περισσότερα από ένα digest (τα απαριθμεί στο `RepoDigests`) όταν ένα registry αποθηκεύει διαφορετική μορφή manifest από αυτήν με την οποία δουλεύει, γι' αυτό συγκρίνετέ το με τον ίδιο τρόπο σε κάθε relay και όχι με την κεφαλίδα ενός registry.

### Quadlet, κράτημα ενημερώσεων μέχρι να εγκρίνει ένας χειριστής (προαιρετικό)

Ορισμένοι χώροι προτιμούν να αποφασίζουν πότε: ένα relay σε μια γραμμή που δεν μπορεί να τρεμοπαίξει κατά τη διάρκεια μιας βάρδιας. Αυτό είναι το `edge-relay-hold.conf`, ένα drop-in του systemd, και δεν είναι ποτέ η προεπιλογή. Με αυτό το relay αναφέρει `"updateMode": "approve"`, το χρονόμετρο είναι απενεργοποιημένο και τίποτα δεν ενημερώνεται μέχρι ένας διαχειριστής να στείλει `POST /api/fleet/{id}/update` από το Gateway. Το relay τότε βγαίνει με κατάσταση 75, το systemd το ξεκινά ξανά στην εικόνα που έχει, και μια ξεχωριστή εργασία περιμένει να είναι υγιές και τρέχει `podman auto-update`: τη νέα εικόνα αν υπάρχει, με την ίδια επαναφορά, και ένα relay που τρεμόπαιξε χωρίς λόγο αν δεν υπάρχει. Αποδείχθηκε με μια πραγματική ενημέρωση που κρατήθηκε 30 δευτερόλεπτα ενώ το relay έτρεχε ανέγγιχτο, και μετά ελήφθη με την έγκριση.

Να ξέρετε τι κοστίζει. Το χρονόμετρο πρέπει να είναι απενεργοποιημένο για όλο το μηχάνημα, επειδή η αυτόματη ενημέρωση του Podman δρα σε κάθε container με ετικέτα και δεν μπορεί να της ειπωθεί να παραλείψει ένα· ένα κουτί που πρέπει να την τρέχει για άλλα πράγματα δεν μπορεί να κρατήσει αυτό το relay. Και το Gateway δεν μπορεί να σας πει ότι μια ενημέρωση περιμένει, μόνο τι τρέχει τώρα κάθε relay, οπότε συγκρίνετε τη λίστα στόλου με ό,τι είναι το `:stable` πριν εγκρίνετε. Μια έγκριση δεν φέρει εικόνα: το relay μπορεί μόνο να του ειπωθεί να ενημερωθεί σε ό,τι ακολουθεί η δική του μονάδα.

### Helm: εσείς τρέχετε `helm upgrade`

Ένα pod δεν μπορεί να αντικαταστήσει τον εαυτό του, και ένα Deployment το αλλάζει το Helm, οπότε δεν υπάρχει απομακρυσμένη ενημέρωση για το chart. Το `image.tag` του chart έχει ως προεπιλογή το `appVersion` του, που είναι η έκδοση, άρα:

```sh
helm repo update
helm upgrade edge-relay hotloop/hotloop-edge-relay --reuse-values
```

μετακινεί το pod στη νέα έκδοση. Η στρατηγική του chart σταματά το παλιό pod πριν ξεκινήσει το νέο (`maxSurge: 0`, επειδή η ουρά προώθησης είναι αρχείο ενός μόνο γράφοντα σε έναν τόμο), οπότε υπάρχει ένα κενό όσο ανεβαίνει. Το Gateway βλέπει και πάλι τη νέα έκδοση στο επόμενο birth του relay και καταγράφει την αλλαγή. Κάτω από το Helm ένα relay δεν αναφέρει digest εικόνας (ένα container δεν βλέπει το δικό του και το Kubernetes δεν του το δίνει), μόνο την έκδοσή του. Το `Node Control/Update` δεν κάνει τίποτα εδώ και το relay το λέει στο αρχείο καταγραφής του· το Helm είναι η έγκριση.

### Τι δεν υπάρχει εδώ, και γιατί

- **Υπογεγραμμένες εικόνες και λίστα επιτρεπόμενων digest.** Το Gateway δεν μπορεί να επιβάλει κανένα από τα δύο σε ένα κουτί στο οποίο δεν έχει πρόσβαση, και ένας έλεγχος που τρέχει το relay στον εαυτό του είναι ένας που ένα παραβιασμένο relay παραλείπει. Το Podman μπορεί να επαληθεύει υπογραφές κατά το pull (`policy.json`), που είναι το σημείο όπου λειτουργεί· τίποτα εδώ δεν στήνει αυτήν την πολιτική για εσάς, και το `:stable` εμπιστεύεται όπως κάθε tag.
- **Σταδιακή διάθεση.** Κάθε relay σε ένα κουτί ακολουθεί το ίδιο tag με το δικό του χρονόμετρο, άρα ένας στόλος ενημερώνεται σύμφωνα με τη διασπορά του χρονομέτρου, όχι σε κύματα, και η επαναφορά παραπάνω είναι αυτή που περιορίζει μια κακή έκδοση. Για να κάνετε σκόπιμα σταδιακή διάθεση, κρατήστε πίσω τους χώρους που πρέπει να περιμένουν με το drop-in κρατήματος και εγκρίνετέ τους με τη σειρά που θέλετε.

## Αποστολή διαμόρφωσης (4.8.0)

Ένα νέο αρχείο συσκευών μπορεί να σταλεί σε ξεχωριστό, απλό (όχι Sparkplug), retained MQTT topic. Δείτε την ενότητα «Config push» της σελίδας διαχείρισης στόλου για την πλευρά του Gateway. Μέχρι την 4.17 μια αποστολή απλώς ετοίμαζε το αρχείο και το relay συνέχιζε να διαβάζει την παλιά λίστα μέχρι να το επανεκκινήσει κάτι. Αυτό έκανε κάθε αλλαγή σε όσα διαβάζει ένα relay επανεκκίνηση του relay, της συνεδρίας του με τον broker και κάθε συνεδρίας συσκευής που κρατούσε, σε ένα κουτί που υποτίθεται ότι κάθεται μήνες χωρίς να το αγγίζει κανείς. Τώρα μια αποστολή εφαρμόζεται τη στιγμή που φτάνει.

- Στάλθηκε ενώ το relay **τρέχει**: τα byte επικυρώνονται με τους ίδιους κανόνες που εφαρμόζει το `LoadDeviceFile` κατά την εκκίνηση, αποθηκεύονται στο `HOTLOOP_EDGE_RELAY_PUSHED_FILE` (ή πάνω στο `HOTLOOP_EDGE_RELAY_DEVICES_FILE` όταν αυτό δεν έχει οριστεί· δείτε παρακάτω) και εφαρμόζονται άμεσα. Αποθηκεύεται πρώτα, σκόπιμα: μια λίστα που έτρεξε αλλά δεν αποθηκεύτηκε ποτέ θα γύριζε σιωπηλά πίσω στην επόμενη εκκίνηση.
- **Μια κακή αποστολή απορρίπτεται και η παλιά λίστα συνεχίζει να τρέχει.** Μια που δεν αναλύεται, δεν επικυρώνεται (διπλή συσκευή, tag σε συσκευή που κανείς δεν δήλωσε, άγνωστο πρωτόκολλο) ή δεν μπορεί να αποθηκευτεί δεν αλλάζει τίποτα: ούτε τις συσκευές που τρέχουν ούτε το αρχείο στον δίσκο. Το αρχείο καταγραφής λέει γιατί, και το ίδιο το `/status` κάτω από το `config.rejected`, από όπου το παίρνει η οθόνη στόλου του Gateway.
- Στάλθηκε ενώ το relay ήταν **εκτός σύνδεσης**: δεν υπάρχει τίποτα να το λάβει μέχρι την επόμενη εκκίνηση, οπότε το relay δίνει σε μια retained αποστολή μερικά δευτερόλεπτα να φτάσει *πριν* φορτώσει το τοπικό αρχείο συσκευών του, και έτσι ξεκινά κατευθείαν με αυτήν. Μια αποστολή που φτάνει μετά από αυτά τα δύο δευτερόλεπτα εφαρμόζεται άμεσα όπως κάθε άλλη.
- Ο broker επιστρέφει την retained αποστολή σε κάθε επανασύνδεση. Το relay γνωρίζει το αρχείο που τρέχει από το sha256 του, άρα τα ίδια byte που φτάνουν ξανά δεν αλλάζουν τίποτα.

### Τι διατηρεί μια άμεση εφαρμογή, και τι αλλάζει

Το relay υπολογίζει τι άλλαξε ανάμεσα στο αρχείο που τρέχει και στο νέο, συσκευή προς συσκευή, και αγγίζει μόνο αυτό:

- **Μια συσκευή που δεν άλλαξε κρατά τη συνεδρία της.** Ίδια σύνδεση TCP με το PLC, ίδια συνδρομή OPC UA, κανένα κενό στις μετρήσεις της.
- **Μια συσκευή που άλλαξε** (η διεύθυνσή της, το πρωτόκολλο, το διάστημα ανάγνωσης, το timeout, το μπλοκ διαμόρφωσης ή τα tag) επανασυνδέεται με τον νέο ορισμό.
- **Μια νέα συσκευή** συνδέεται και αρχίζει να διαβάζεται.
- **Μια συσκευή που αφαιρέθηκε** (ή που τώρα έχει `"enabled": false`) αποσυνδέεται.
- **Η συνεδρία Sparkplug μένει ενεργή.** Κανένα NDEATH, καμία επανασύνδεση, ίδιο bdSeq, και η ουρά προώθησης δεν αγγίζεται. Μια επαναφόρτωση κατά τη διάρκεια διακοπής του broker αφήνει κάθε μέτρηση σε buffer στην ουρά· αδειάζουν όταν επιστρέψει ο broker, όπως και χωρίς επαναφόρτωση.

Στο καλώδιο, σύμφωνα με το Sparkplug B. Το relay είναι ένας κόμβος edge και κάθε tag είναι μια μετρική κόμβου με όνομα `device/tag`, οπότε αλλάζει το σύνολο μετρικών του κόμβου, και το Sparkplug δίνει σε έναν κόμβο μόνο έναν τρόπο να το αλλάξει: ένα νέο NBIRTH, που αντικαθιστά ολόκληρο το τελευταίο. Έτσι:

- **Οι μετρικές που έφυγαν** (μια συσκευή που αφαιρέθηκε, ένα tag που αφαιρέθηκε ή απενεργοποιήθηκε) στέλνονται άλλη μία φορά σε ένα NDATA ως null, και μετά ο κόμβος κάνει rebirth χωρίς αυτές: ίδια συνεδρία, ίδιο bdSeq, seq πίσω στο 0, το ίδιο rebirth που δίνει το `Node Control/Rebirth`. Το null υπάρχει επειδή ένας host επιτρέπεται να κρατά την τελευταία τιμή μιας μετρικής που ένα νέο birth παραλείπει, και ο host Sparkplug του ίδιου του Gateway κάνει ακριβώς αυτό. Χωρίς το null, μια βαλβίδα που αφαιρέσατε από το relay θα έμενε για πάντα στην τελευταία καλή μέτρησή της, φαινομενικά υγιής.
- **Οι νέες μετρικές** μπαίνουν σε ένα birth στην πρώτη ανάγνωση της συσκευής τους, με τον ίδιο τρόπο που μπαίνει κάθε μετρική κατά την εκκίνηση. Ένα birth δεν κατονομάζει ποτέ μια μετρική πριν υπάρξει μέτρηση πίσω της.
- **Οι μετρήσεις ενός tag που αφαιρέθηκε και βρίσκονται ακόμη στην ουρά προώθησης** απορρίπτονται όταν αδειάσει η ουρά, με μια γραμμή καταγραφής που τις μετρά. Το birth του κόμβου δεν φέρει πια αυτή τη μετρική, και το Sparkplug δεν έχει νόμιμο τρόπο να στείλει μια που δεν φέρει· η αποστολή τους θα σήμαινε ένα alias που κανένας host δεν ενημερώθηκε ποτέ.

Η επεξεργασία του τοπικού αρχείου συσκευών με το χέρι απαιτεί ακόμη επανεκκίνηση: το relay το διαβάζει κατά την εκκίνηση και όταν καθαρίζεται μια αποστολή, και δεν το παρακολουθεί. Κάτω από το chart αυτό κάνει έτσι κι αλλιώς ένα `helm upgrade` που αλλάζει τα `devices`.

### Πού βρίσκεται ένα αρχείο που στάλθηκε, και ποιο αρχείο κερδίζει

Και οι δύο υποστηριζόμενες εγκαταστάσεις προσαρτούν το τοπικό αρχείο συσκευών μόνο για ανάγνωση: το chart από ένα ConfigMap (ή Secret), η μονάδα Quadlet ως bind `:ro`, και οι δύο σε σύστημα αρχείων root μόνο για ανάγνωση. Μέχρι την 4.16.0 το relay έγραφε μια αποστολή ακριβώς δίπλα σε αυτό το αρχείο, οπότε και στις δύο εγκαταστάσεις κάθε αποστολή πέθαινε με

```
a pushed config was rejected; keeping the current one and continuing to run
error="write /etc/edge-relay/devices.json.tmp: open /etc/edge-relay/devices.json.tmp: read-only file system"
```

και το relay συνέχιζε να διαβάζει την παλιά λίστα. Το Gateway έλεγε `config pushed`, η επανεκκίνηση περνούσε και τίποτα δεν άλλαζε. Διορθώθηκε δίνοντας στην αποστολή το δικό της σπίτι:

- **`HOTLOOP_EDGE_RELAY_PUSHED_FILE`** είναι το σημείο όπου γράφεται μια αποστολή. Το chart το ορίζει στο `/data/pushed-devices.json` στο PVC (`pushedDevicesFile` στο values.yaml), και η μονάδα Quadlet ορίζει την ίδια διαδρομή στον ονομασμένο τόμο δεδομένων της. Και τα δύο επιβιώνουν από το container, και το PVC επιβιώνει από μια επαναπρογραμματισμένη τοποθέτηση. Το τελευταίο είναι σκόπιμο: ένα emptyDir θα ήταν επίσης εγγράψιμο, αλλά χάνεται μόλις μετακινηθεί το pod, και ένα relay που γυρίζει σιωπηλά στην παλιά λίστα συσκευών του μετά από drain κόμβου είναι το ίδιο σφάλμα με επιπλέον βήματα.
- **Το αρχείο που στάλθηκε κερδίζει.** Κατά την εκκίνηση το relay φορτώνει το αρχείο που στάλθηκε αν υπάρχει, και το τοπικό μόνο αν δεν υπάρχει. Αυτό ισχύει μετά από επανεκκίνηση, μετά από επαναπρογραμματισμό, αφού ο broker χάσει την retained αποστολή (επανεκκίνηση του Mosquitto χωρίς διατήρηση) και μετά από `helm upgrade` που αλλάζει τα `devices` ή `tags`. Η αποστολή είναι η νεότερη, σκόπιμη αλλαγή, και ο broker θα επέστρεφε το retained αντίγραφο στην επόμενη εκκίνηση έτσι κι αλλιώς, οπότε αν κέρδιζε το τοπικό αρχείο θα κρατούσε μόνο μία επανεκκίνηση. Οι πρώτες γραμμές του αρχείου καταγραφής λένε από ποιο αρχείο ξεκίνησε: `booting from the pushed device file; the local one is ignored until the push is cleared`.
- **Η επιστροφή στο τοπικό αρχείο** (τα `devices` του chart, ή το `/etc/edge-relay/devices.json` κάτω από το Quadlet) γίνεται με `DELETE /api/fleet/{id}/config` στο Gateway. Η διαγραφή καθαρίζει την retained αποστολή στον broker, ώστε καμία μεταγενέστερη εκκίνηση να μην την εφαρμόσει, και ένα relay που είναι συνδεδεμένο εκείνη τη στιγμή φορτώνει το τοπικό του αρχείο, διαγράφει το αρχείο που στάλθηκε, καταγράφει `the config push was cleared; the local device file takes over` και εφαρμόζει το τοπικό αρχείο άμεσα, με τον ίδιο τρόπο που εφαρμόζεται μια αποστολή. Αν το τοπικό αρχείο δεν φορτώσει, το relay κρατά το αρχείο που στάλθηκε σε λειτουργία και στον δίσκο και το λέει στο αρχείο καταγραφής και στο `/status`: αν το διαγράφατε πρώτα, θα μένατε με ένα relay που στην επόμενη επανεκκίνηση ξεκινά με χαλασμένο αρχείο. Διορθώστε το τοπικό αρχείο και στείλτε ξανά τη διαγραφή. Κάντε το ενώ το relay είναι **συνδεδεμένο**. Μια διαγραφή δεν είναι retained, οπότε ένα relay που ήταν εκτός σύνδεσης δεν το μαθαίνει ποτέ και κρατά το αρχείο που στάλθηκε· ξεκινήστε το και στείλτε ξανά τη διαγραφή. Είναι ασφαλές να επαναληφθεί.
- Ένα αρχείο που στάλθηκε, υπάρχει αλλά δεν φορτώνει (βλάβη δίσκου, ή μεταγενέστερη έκδοση με αυστηρότερους κανόνες), καταγράφεται ως σφάλμα και το relay ξεκινά από το τοπικό αρχείο αντί να μένει εκτός λειτουργίας γι' αυτόν τον λόγο.
- Με το `HOTLOOP_EDGE_RELAY_PUSHED_FILE` μη ορισμένο, μια αποστολή αντικαθιστά το ίδιο το `HOTLOOP_EDGE_RELAY_DEVICES_FILE`, η συμπεριφορά της 4.8.0. Αυτό είναι χρήσιμο μόνο για ένα γυμνό εκτελέσιμο με εγγράψιμο αρχείο συσκευών, και τότε δεν υπάρχει ξεχωριστό αντίγραφο που να μπορεί να απορρίψει ένας καθαρισμός.

Αν μια αποστολή «δεν πέρασε», κοιτάξτε το αρχείο καταγραφής του relay πριν από οτιδήποτε άλλο. Ή λέει από ποιο αρχείο ξεκίνησε, ή λέει γιατί απορρίφθηκε η αποστολή.

## Η επιφάνεια HTTP

Δύο endpoint, και τα δύο χωρίς έλεγχο ταυτότητας, και τα δύο μόνο για ανάγνωση:

- `GET /healthz`: η διεργασία είναι ενεργή. Τίποτα παραπάνω· μια συσκευή που είναι αποσυνδεδεμένη δεν σημαίνει ότι αυτή η διεργασία δεν είναι υγιής.
- `GET /status`, ένα στιγμιότυπο: πλήθος συσκευών ανά κατάσταση σύνδεσης, πλήθος tag, το τρέχον βάθος της ουράς προώθησης, η λίστα των ενσωματωμένων πρωτοκόλλων και το `uplink`: αν ο broker είναι συνδεδεμένος, αν τρέχει επανάληψη, και τι κρατά η ουρά προώθησης, πόσο ζυγίζει στον δίσκο και πόσα έχει απορρίψει στο όριό της (δείτε τη σελίδα Edge publish, «When the uplink is down»). Καμία τιμή tag, καμία διεύθυνση συσκευής, καμία διαμόρφωση: είναι μια επιφάνεια παρακολούθησης, όχι μικρότερο αντίγραφο του πίνακα ελέγχου του Gateway. Τα `version`, `imageDigest` και `updateMode` λένε ποιο build είναι και αν κρατά πίσω ενημερώσεις. Λέει επίσης, κάτω από το `config`, ποιο αρχείο συσκευών τρέχει: `source` (`local` ή `pushed`), `path`, το sha256 `digest` του, `appliedAt` και `rejected`, το τελευταίο αρχείο που απέρριψε το relay και γιατί, μέχρι να εφαρμοστεί μια μεταγενέστερη αποστολή. Το digest, όχι το αρχείο: το Gateway μπορεί να το ταιριάξει με ό,τι έστειλε χωρίς να βγουν οι διευθύνσεις και τα διαπιστευτήρια του αρχείου από μια πόρτα χωρίς έλεγχο ταυτότητας. Με έναν broker `discovery` στο αρχείο λέει επίσης, κάτω από το `discovery`, πώς τα πάει ο καθένας και πόσες συσκευές βρήκε (δείτε [Discovery](#discovery-41810)).

Σκόπιμα χωρίς έλεγχο ταυτότητας μπροστά σε κανένα από τα δύο: ένα edge relay δεν έχει βάση χρηστών, αποθήκη συνεδριών ή σύστημα ταυτότητας από το οποίο να χτιστεί ένα, και η προσθήκη ενός κοινόχρηστου token θα ήταν θέατρο και όχι ασφάλεια για δύο endpoint που δεν εκθέτουν τίποτα ευαίσθητο. Τρέξτε το πίσω από ό,τι περίμετρο δικτύου βρίσκεται και η ίδια η συσκευή, την ίδια προσδοκία που ήδη τεκμηριώνει η λειτουργία `auth.insecure` του Gateway για μια ανάπτυξη πίσω από έναν αξιόπιστο proxy.

|---|---|---|
| `HOTLOOP_EDGE_RELAY_DEVICES_FILE` | n/a | Υποχρεωτικό. Διαδρομή προς το αρχείο συσκευών που περιγράφεται παραπάνω |
| `HOTLOOP_EDGE_RELAY_PUSHED_FILE` | unset | Πού φυλάσσεται ένα αρχείο συσκευών που στάλθηκε· κερδίζει το παραπάνω όσο υπάρχει. Πρέπει να είναι εγγράψιμο και μόνιμο· το chart και η μονάδα Quadlet χρησιμοποιούν το `/data/pushed-devices.json`. Δείτε [Πού βρίσκεται ένα αρχείο που στάλθηκε](#πού-βρίσκεται-ένα-αρχείο-που-στάλθηκε-και-ποιο-αρχείο-κερδίζει) |
| `HOTLOOP_EDGE_RELAY_LISTEN_ADDR` | `:8081` | Ο διακομιστής για `/healthz` και `/status` |
| `HOTLOOP_EDGE_RELAY_UPDATE_MODE` | `auto` | Το `auto` αφήνει την ενημέρωση στον επόπτη και αγνοεί μια έγκριση από το Gateway· το `approve` κρατά πίσω τις ενημερώσεις μέχρι να έρθει μία. Δείτε [Ενημέρωση ενός relay](#ενημέρωση-ενός-relay) |
| `HOTLOOP_IMAGE_DIGEST` | unset | Το digest της εικόνας από την οποία τρέχει αυτό το relay, όπως το γνωρίζει ο επόπτης του. Η μονάδα Quadlet το ορίζει πριν από κάθε εκκίνηση. Αναφέρεται στο `/status` και σε κάθε birth· κενό είναι εντάξει |
| `HOTLOOP_LOG_LEVEL` | `info` | |
| `HOTLOOP_POLL_INTERVAL` | `5s` | Προεπιλεγμένο διάστημα ανάγνωσης· το δικό της `pollIntervalMs` μιας συσκευής το παρακάμπτει |
| `HOTLOOP_MIN_POLL_INTERVAL` | `100ms` | Κατώτατο όριο που επιβάλλεται σε κάθε συσκευή, ανεξάρτητα από τη δική της ρύθμιση |
| `HOTLOOP_POLL_TIMEOUT` | `10s` | Προεπιλεγμένο timeout ανά ανάγνωση· το δικό του `timeoutMs` μιας συσκευής το παρακάμπτει |
| `HOTLOOP_MAX_CONCURRENT_POLLS` | `32` | Συσκευές που μπορούν να βρίσκονται ταυτόχρονα στη μέση μιας ανάγνωσης |
| `HOTLOOP_RECONNECT_MIN` / `HOTLOOP_RECONNECT_MAX` | `1s` / `60s` | Όρια backoff ανάμεσα στις προσπάθειες επανασύνδεσης, με jitter |
| `HOTLOOP_RING_SIZE` | `120` | Δείγματα ανά tag που κρατιούνται για διαγνωστικά γύρω από το `/status` |
| `HOTLOOP_OPCUA_CLIENT_PKI_DIR` | `/data/opcua-client-pki` | Το πιστοποιητικό του driver OPC UA και οι αποθήκες του `trusted/` και `rejected/`· το δικό του `pkiDir` μιας συσκευής το παρακάμπτει. Το αγγίζει μόνο μια ασφαλής συσκευή OPC UA |

Ίδια ονόματα μεταβλητών και προεπιλογές με το `RuntimeConfig` του ίδιου του Gateway· δείτε την ενότητα «Polling» στη σελίδα k3s και Helm για τις ίδιες ρυθμίσεις ως τιμές Helm, επειδή και τα δύο εκτελέσιμα φορτώνουν αυτή τη διαμόρφωση μέσω της ίδιας συνάρτησης `config.LoadRuntimeConfig()`, όχι μέσω δύο αντιγράφων που θα μπορούσαν να αποκλίνουν.

Συν κάθε μεταβλητή `HOTLOOP_EDGE_PUBLISH_*` που τεκμηριώνει η σελίδα Edge publish, με μία διαφορά: το `HOTLOOP_EDGE_PUBLISH_ENABLED` αγνοείται και η προώθηση είναι πάντα ενεργή· η δημοσίευση όσων διαβάζει είναι ολόκληρος ο σκοπός αυτού του εκτελέσιμου, όχι προαιρετική λειτουργία όπως στο Gateway.

## Ανάπτυξη

Δύο υποστηριζόμενες διαδρομές, και οι δύο με containers, κανένα μεμονωμένο `podman run` από shell που πεθαίνει με τη συνεδρία, και χωρίς Docker:

- **`charts/hotloop-edge-relay`**, ένα Helm chart για k3s, ξεχωριστό από το δικό chart του Gateway (`charts/hotloop`), επειδή ένα edge relay είναι πραγματικά διαφορετικό αντικείμενο που συχνά τρέχει σε διαφορετικό, μικρότερο cluster από το Gateway στο οποίο προωθεί. Οι συσκευές και τα tag δηλώνονται στο `values.yaml` και αποδίδονται σε ένα ConfigMap· η ουρά προώθησης ζει σε ένα μικρό PVC (δείτε «Persistence off» παρακάτω πριν το απενεργοποιήσετε).
- **`deploy/quadlet`**, μια μονάδα Podman Quadlet για ένα Pi ή έναν μικρό βιομηχανικό υπολογιστή που δεν ανήκει καθόλου σε cluster k3s. Το Quadlet κάνει το container πραγματική υπηρεσία systemd: ξεκινά με την εκκίνηση, επανεκκινεί σε αποτυχία, γράφει στο journald· δείτε το README αυτού του καταλόγου για τα βήματα εγκατάστασης.

Και τα δύο χρησιμοποιούν την ίδια εικόνα και τις ίδιες μεταβλητές περιβάλλοντος που τεκμηριώνονται παραπάνω.

Κάθε έκδοση δημοσιεύει και τα δύο, από την 4.16.0. Η εικόνα είναι `ghcr.io/hotloop-io/hotloop-edge-relay`, με tag την έκδοση (συν `major.minor`, `major`, `latest` και `stable`· η μονάδα Quadlet ακολουθεί το `stable`, δείτε [Ενημέρωση ενός relay](#ενημέρωση-ενός-relay)). Είναι amd64 και arm64, και arm 32 bit (arm/v7) από την πρώτη έκδοση μετά την 4.17.0, επειδή ένα Pi 3 ή μια εγκατάσταση Pi OS 32 bit είναι ακριβώς το κουτί όπου καταλήγει ένα relay. Το chart βρίσκεται στο ίδιο αποθετήριο Helm με αυτό του Gateway:

```sh
helm repo add hotloop https://hotloop.io/hotloop/
helm install edge-relay hotloop/hotloop-edge-relay \
  --namespace hotloop --create-namespace \
  --set edgePublish.broker=tcp://gateway.example.local:1883 \
  --set edgePublish.group=Plant1
```

### Persistence off

Το `persistence.enabled=false` σας δίνει ένα relay που τρέχει χωρίς PVC, και ακριβώς αυτό. Στην 4.16.0 δεν έτρεχε καν: τίποτα δεν ήταν προσαρτημένο στο `/data`, το root είναι μόνο για ανάγνωση, και το relay πέθαινε κατά την εκκίνηση με `open forward queue at /data/forward.db: no such file or directory`. Τώρα το `/data` είναι ένα emptyDir, με όριο το `persistence.size`, και ό,τι γράφει το relay καταλήγει εκεί.

Ένα emptyDir ζει όσο το pod. Μια επανεκκίνηση container μέσα στο ίδιο pod το κρατά. Ένα νέο pod όχι, και παίρνετε νέο pod σε drain κόμβου, θάνατο κόμβου, eviction, `kubectl delete pod` και κάθε `helm upgrade` που ανανεώνει το Deployment. Κάθε φορά χάνετε:

- **Την ουρά προώθησης.** Κάθε μέτρηση σε buffer ενώ ο broker ήταν εκτός λειτουργίας χάνεται, και τίποτα στην πλευρά του Gateway δεν ξέρει ότι λείπει.
- **Ένα αρχείο συσκευών που στάλθηκε.** Το relay ξεκινά ξανά από τα `devices` του chart χωρίς παράπονο, μέχρι το Gateway να στείλει ξανά ή ο broker να επαναλάβει μια retained αποστολή. Αυτή είναι ακριβώς η αποτυχία που υπάρχει το PVC για να προλαβαίνει, και η απενεργοποίησή του σας ξαναεκθέτει σε αυτήν.
- **Το πιστοποιητικό πελάτη OPC UA και το trust store.** Κάθε ασφαλής διακομιστής πρέπει να εμπιστευτεί το νέο πιστοποιητικό, και ο χειριστής πρέπει να εγκρίνει ξανά το πιστοποιητικό κάθε διακομιστή.

Το γέμισμα του ορίου, που μια ουρά χωρίς όριο (`queueMaxBytes: 0`· η προεπιλογή είναι 64 MiB) θα κάνει σε αρκετά μεγάλη διακοπή, οδηγεί σε eviction του pod και χάνονται και τα τρία μαζί. Αυτό είναι ακόμη καλύτερο από το να γεμίσει ο δίσκος του κόμβου κάτω από όλα τα υπόλοιπα πάνω του. Οι σημειώσεις εγκατάστασης τυπώνουν προειδοποίηση όταν η διατήρηση είναι απενεργοποιημένη. Είναι εντάξει για δοκιμή. Για ένα relay του οποίου οι μετρήσεις έχουν σημασία, δώστε του το PVC.

### Από το EmberNet App Store

Το κατάστημα εμφανίζει το relay ως HotLoop Edge Relay, ένα ανά κόμβο. Μια ανάπτυξη από το κατάστημα δίνει στο chart τρία πράγματα: το εμφανιζόμενο όνομα (το όνομα της έκδοσης), έναν επιλογέα κόμβου και τις ετικέτες του tenant. Δεν έχει φόρμα για να ζητήσει οτιδήποτε άλλο, και το relay δεν μπορεί να τρέξει χωρίς broker και ομάδα Sparkplug. Έτσι μια ανάπτυξη του relay από το κατάστημα σταματά στην απόδοση, σκόπιμα, με ένα σφάλμα στο αρχείο καταγραφής της εργασίας helm-install που κατονομάζει τι λείπει και τυπώνει την ακριβή εντολή για τη διόρθωση.

Δεν του δώσαμε προεπιλεγμένο broker, επειδή δεν υπάρχει κανένας που να ισχύει για το εργοστάσιο κανενός, και ένα relay που δείχνει σε μια επινοημένη διεύθυνση θα έδειχνε αναπτυγμένο ενώ δεν προωθεί τίποτα. Ούτε μπορεί απλώς να περιμένει ένα αρχείο συσκευών που θα σταλεί: μια αποστολή φτάνει μέσω της σύνδεσης με τον broker που δεν έχει ακόμη.

Η λύση είναι να βάλετε τις δύο τιμές σε ό,τι έγραψε το κατάστημα, και η εγκατάσταση ξαναδοκιμάζει μόνη της:

```sh
# a node on the local cluster: add them under spec.valuesContent
kubectl -n default edit helmchart hotloop-edge-relay-<node>

# a tenant on its own cluster (Fleet): add them under spec.helm.values
kubectl -n fleet-default edit helmop hotloop-edge-relay-<node>
```

```yaml
edgePublish:
  broker: tcp://<gateway-or-broker>:1883
  group: <sparkplug group id>
```

Μόλις ανέβει, εμφανίζεται στις Εφαρμογές σε εκτέλεση με το όνομα που έδωσε το κατάστημα, με το εικονίδιο HotLoop, περιορισμένο στον tenant που το ανέπτυξε, και χωρίς κουμπί ΕΚΚΙΝΗΣΗ. Το τελευταίο είναι σκόπιμο: το chart το επισημαίνει με `embernet.ai/gui-type: none`, επειδή τα `/healthz` και `/status` είναι για μια διερεύνηση και το curl ενός χειριστή, όχι για σελίδα σε iframe.

Το relay και το Gateway μοιράζονται έναν αριθμό έκδοσης. Μια έκδοση δεν ξεκινά αν δεν φέρουν και τα δύο chart την έκδοση του tag και αν η μονάδα Quadlet του relay δεν ακολουθεί το `:stable`, οπότε το relay παίρνει νέα έκδοση σε κάθε έκδοση, είτε άλλαξε ο δικός του κώδικας είτε όχι. Αυτό είναι σκόπιμο: ένας αριθμός για να ρωτάς, και κανένα chart relay που δείχνει σε εικόνα relay που κανείς δεν έστειλε. Η μονάδα Quadlet παλιά καρφίτσωνε τον αριθμό έκδοσης, το αντίθετο από το πώς λειτουργεί ένα κουτί που ενημερώνεται μόνο του.
