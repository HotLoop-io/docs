Το chart αναπτύσσει δύο φόρτους εργασίας: το gateway (ένα Deployment, που δεν κρατά δικό του διαρκές state) και το TimescaleDB (ένα StatefulSet με έναν τόμο). Αυτή είναι η προεπιλογή. Το `database.type` επιλέγει άλλη βάση δεδομένων: απλή PostgreSQL, ή SQLite, που δεν είναι καθόλου δεύτερος φόρτος εργασίας ([SQLite](#sqlite), παρακάτω).

## Εγκατάσταση

Μέσω του App Store του πίνακα EmberNet, ή απευθείας:

```bash
helm install hotloop ./charts/hotloop \
  --namespace hotloop --create-namespace
```

Ή από το αποθετήριο των charts, που είναι και το URL στο οποίο δείχνει το App Store:

```bash
helm repo add hotloop https://hotloop.io/hotloop
helm install hotloop hotloop/hotloop \
  --namespace hotloop --create-namespace
```

Αυτή η δεύτερη μορφή λειτουργεί από την 4.16.0, την πρώτη έκδοση που δημοσιεύτηκε ως `hotloop`. Η τελευταία πριν από αυτήν ήταν η `industrial-iot` 4.3.1, με το παλιό όνομα, και η αναβάθμιση από αυτήν είναι ξεχωριστή διαδικασία: δείτε το "Upgrading from 4.3.1" στις σημειώσεις της 4.16.0 του README. Η παλιά διεύθυνση του αποθετηρίου, `https://embernet-ai.github.io/industrial-iot/`, επιστρέφει 404.

Μια απλή εγκατάσταση λειτουργεί. Το chart δημιουργεί έναν κωδικό βάσης δεδομένων και ένα MCP token στο Secret της έκδοσης και τα επαναχρησιμοποιεί σε κάθε αναβάθμιση, οπότε δεν χρειάζεται να δώσετε τίποτα και μια αναβάθμιση δεν αλλάζει τον κωδικό κάτω από μια βάση που τρέχει.

Η πρόσβαση δεν χρειάζεται ingress ούτε υποτομέα. Ο πίνακας ανακαλύπτει την εφαρμογή από τις ετικέτες του store και την προωθεί μέσω proxy στην εσωτερική διεύθυνση του cluster:

```
<release>.<namespace>.svc.cluster.local:8080
```

Για να την δείτε απευθείας:

```bash
kubectl -n hotloop port-forward svc/hotloop 8080:8080
```

## Τιμές που αξίζει να ορίσετε

### Έλεγχος ταυτότητας

Από την 4.4.0. Δείτε [Έλεγχος ταυτότητας και χρήστες](/el/iot/authentication/) για ολόκληρο το μοντέλο· αυτή είναι η πλευρά του chart.

```yaml
auth:
  enabled: true    # the default; requires a login
  insecure: false  # set true only for a deployment truly isolated behind the
                    # dashboard's own NetworkPolicy -- see AUTH.md
```

Με `enabled: true` (την προεπιλογή) το chart δημιουργεί έναν λογαριασμό διαχειριστή στο Secret της έκδοσης στην πρώτη εγκατάσταση, όπως δημιουργεί τον κωδικό της βάσης και το MCP token, και τον επαναχρησιμοποιεί στις αναβαθμίσεις:

```bash
kubectl get secret hotloop -n hotloop \
  -o jsonpath='{.data.admin-password}' | base64 -d
```

Ο ρητός ορισμός του `auth.admin.password` υπερισχύει του δημιουργημένου.

### Ασφάλεια

Οι τιμές που αποφασίζουν αν αυτό το pod μπορεί να κινήσει μηχανήματα.

```yaml
safety:
  allowWrites: false      # the master switch -- off by default since 4.4.0
  allowMcpWrites: true    # agents (MCP) write wherever an operator could, once writes are on
  confirmWrites: true     # the UI asks before writing
```

Οι εγγραφές είναι απενεργοποιημένες από προεπιλογή. Ένα tag είναι μόνο για ανάγνωση μέχρι να οριστεί η δική του σημαία `writable`, μια τιμή εκτός του ρυθμισμένου εύρους του tag απορρίπτεται (ποτέ δεν περικόπτεται: το να σταλεί 250 όταν κάποιος πληκτρολόγησε 500 σημαίνει να κάνεις κάτι άλλο σιωπηλά), και κάθε απόπειρα, **συμπεριλαμβανομένης κάθε απόρριψης**, καταγράφεται με τον δράστη και την πηγή. Αλλά μια καινούργια εγκατάσταση δεν πρέπει να χρειάζεται και τα τρία να ευθυγραμμιστούν για να είναι ασφαλής, γι' αυτό ο ίδιος ο γενικός διακόπτης ξεκινά κλειστός.

Για να ενεργοποιήσετε τις εγγραφές μόλις ελεγχθεί η ανάπτυξη:

```yaml
safety:
  allowWrites: true
```

Αυτό είναι όλο: οι πελάτες MCP διαβάζουν και γράφουν όπως ένας χειριστής, με τα ίδια δικαιώματα, εγγράψιμα tags και εύρη. Το `allowMcpWrites` έρχεται ενεργό σε κάθε chart· υπάρχει για μια ανάπτυξη που αποφασίζει διαφορετικά, και δεν είναι προεπιλογή πουθενά.

### Ιστορικό

```yaml
historian:
  retentionDays: 90     # 0 keeps everything until the volume fills
  useTimescale: true

logbook:
  retentionDays: 90     # entity state changes; 0 keeps everything (see LOGBOOK.md)

database:
  postgresql:
    persistence:
      size: 20Gi
      storageClass: longhorn
```

Το μέγεθος καθορίζεται από τον αριθμό των tags, τον ρυθμό σάρωσης και τις νεκρές ζώνες. Χίλια tags ανά δευτερόλεπτο χωρίς νεκρές ζώνες είναι περίπου 86 εκατομμύρια γραμμές την ημέρα· το ίδιο εργοστάσιο με λογικές νεκρές ζώνες έχει συνήθως μία τάξη μεγέθους λιγότερες. Ορίστε νεκρές ζώνες πριν αγοράσετε αποθηκευτικό χώρο.

Το `useTimescale: false` επιβάλλει τη διαδρομή του ενσωματωμένου partitioning, που είναι η μορφή της λειτουργίας πάνω σε απλή PostgreSQL. Χρήσιμο για αναπαραγωγή μιας ανάπτυξης στο edge.

**Όταν αλλάζει το image του TimescaleDB.** Το image περιέχει τη βιβλιοθήκη κάθε παλαιότερης έκδοσης, οπότε μια βάση που δημιουργήθηκε με παλαιότερο image συνεχίζει να τρέχει στο νέο, αλλά στην παλιά έκδοση της επέκτασης, και μένει εκεί μέχρι κάποιος να εκτελέσει `ALTER EXTENSION timescaledb UPDATE`. Το Gateway το κάνει κατά την εκκίνηση: συγκρίνει την εγκατεστημένη έκδοση με αυτήν που παραδίδει ο διακομιστής και, αν διαφέρουν, εκτελεί την ενημέρωση ως πρώτη εντολή μιας νέας σύνδεσης (το TimescaleDB την αρνείται σε συνεδρία που έχει ήδη φορτώσει την παλιά έκδοση). Το log λέει `timescaledb extension updated from=... to=...`. Χρειάζεται superuser, που είναι ο χρήστης της ενσωματωμένης βάσης. Απέναντι σε εξωτερική ή διαχειριζόμενη βάση όπου δεν είναι, παίρνετε μια προειδοποίηση με την εντολή που πρέπει να εκτελεστεί, και το ιστορικό συνεχίζει να λειτουργεί στην παλιά έκδοση στο μεταξύ. Συμβαίνει μόνο με ενεργό `useTimescale` και migrations που τρέχουν στην εκκίνηση (`HOTLOOP_DB_MIGRATE`, ενεργό από προεπιλογή).

### Polling

```yaml
runtime:
  defaultPollIntervalMs: 1000
  minPollIntervalMs: 100      # a floor applied to every device
  timeoutMs: 10000
  maxConcurrentPolls: 32
```

Το `minPollIntervalMs` επιβάλλεται αντί να θεωρείται δεδομένο. Ένα polling των 10 ms προς ένα σειριακό gateway είναι άρνηση υπηρεσίας με πρόσθετα βήματα.

### Πελάτης OPC UA

```yaml
opcuaClient:
  persistence:
    enabled: true      # off by default
    size: 64Mi
```

Μια συσκευή που συνδέεται σε ασφαλή διακομιστή OPC UA, ή που κάνει είσοδο με όνομα χρήστη και κωδικό που ο διακομιστής απαιτεί κρυπτογραφημένα, κρατά ένα πιστοποιητικό και ένα αποθετήριο εμπιστοσύνης εγκεκριμένων πιστοποιητικών διακομιστή (`HOTLOOP_OPCUA_CLIENT_PKI_DIR`, `/data/opcua-client-pki`). Ενεργοποιήστε το πριν προσθέσετε τέτοια συσκευή: το ριζικό σύστημα αρχείων είναι μόνο για ανάγνωση, οπότε χωρίς τον τόμο η συσκευή αναφέρει ένα σφάλμα που το λέει, αντί να συνδεθεί με πιστοποιητικά που θα χάνονταν στην επόμενη επανεκκίνηση. Είναι απενεργοποιημένο από προεπιλογή επειδή προσθέτει ένα PersistentVolumeClaim σε υπάρχουσα εγκατάσταση, που μένει Pending σε cluster χωρίς προεπιλεγμένο StorageClass. Οι ανώνυμες συσκευές σε μη ασφαλές κανάλι δεν το χρησιμοποιούν. Η έγκριση του πιστοποιητικού ενός διακομιστή, και όλα τα υπόλοιπα για αυτές τις συσκευές, βρίσκονται στα [Πρωτόκολλα και drivers](/el/iot/protocols/#opc-ua-security-and-credentials).

### Δίκτυο

```yaml
networkPolicy:
  enabled: true
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: dashboard-system
      ports:
        - protocol: TCP
          port: 8080
```

Περιορίστε το ingress στο namespace του πίνακα όταν γίνει γνωστό. Το egress είναι σκόπιμα απεριόριστο: αυτή η εφαρμογή υπάρχει για να φτάνει εξοπλισμό σε διευθύνσεις που κανείς δεν μπορεί να απαριθμήσει εκ των προτέρων, και μια πολιτική egress που μπλοκάρει σιωπηλά ένα polling μοιάζει με χαλασμένο driver και όχι με κανόνα firewall.

### Υλικό: ραδιοφωνικές συσκευές USB, σειριακοί προσαρμογείς και Bluetooth

Από την 4.19.7 κάθε chart του HotLoop (Gateway, IoT, Edge και Edge Relay) έρχεται με ενεργή την πρόσβαση που χρειάζεται το υλικό, ώστε μια απλή εγκατάσταση από το App Store ή από το helm να βλέπει ό,τι είναι συνδεδεμένο στον κόμβο χωρίς χειροκίνητη επεξεργασία, στο δίκτυο των pods. Είναι το μπλοκ `hardware:` του `values.yaml`: τρεις διακόπτες που είναι ενεργοί από προεπιλογή και μία προαιρετική ρύθμιση που είναι ανενεργή:

| Τιμή | Προεπιλογή | Τι κάνει |
|---|---|---|
| `hardware.privileged` | `true` | Το container της εφαρμογής τρέχει privileged (`privileged: true`, `allowPrivilegeEscalation: true`) και ως root (`runAsUser: 0`, `runAsNonRoot: false`, χωρίς αφαίρεση capabilities). Root επειδή ένας σειριακός κόμβος USB είναι `root:dialout 0660` και η πολιτική D-Bus του BlueZ αφήνει να μπουν το root και η ομάδα `bluetooth`· ένας χρήστης container σε καμία από τις δύο δεν ανοίγει τίποτα. Το ριζικό σύστημα αρχείων μένει μόνο για ανάγνωση, και το init container και η ενσωματωμένη βάση κρατούν το δικό τους non-root πλαίσιο με όλα τα capabilities αφαιρεμένα. |
| `hardware.usbDevices.enabled` | `true` | Το `/dev` του κόμβου (`hardware.usbDevices.hostPath`) προσαρτάται στο `/dev`: σειριακοί προσαρμογείς USB (`/dev/ttyUSB*`, `/dev/ttyACM*`, `/dev/serial/by-id/*`), ακόμη και ένας που συνδέθηκε μετά την εκκίνηση του pod. Σε ένα privileged container δίνονται μόνο οι συσκευές που υπήρχαν όταν ξεκίνησε· η προσάρτηση είναι αυτή που κάνει να εμφανιστεί ένα ξανασυνδεδεμένο stick. |
| `hardware.bluetooth.enabled` | `true` | Ο κατάλογος D-Bus του κόμβου (`hardware.bluetooth.dbusPath`, `/run/dbus`, που περιέχει το `system_bus_socket`) προσαρτάται στην ίδια διαδρομή, ώστε ένας πελάτης να φτάνει το BlueZ του κόμβου. Δημιουργείται άδειος σε κόμβο χωρίς D-Bus, οπότε το pod ξεκινά και εκεί. |
| `hardware.bluetooth.hostNetwork` | `false` | Η προαιρετική ρύθμιση, ανενεργή από προεπιλογή, για ό,τι χρειάζεται το δίκτυο του κόμβου: τα sockets Bluetooth του πυρήνα (HCI, L2CAP) υπάρχουν μόνο στο network namespace του κόμβου, οπότε ένας πελάτης που ανοίγει ένα απευθείας, και η ανακάλυψη που ακούει στο δίκτυο του ίδιου του κόμβου (mDNS, SSDP, το multicast ενός ραδιοφώνου), το χρειάζονται. Ένας πελάτης που περνά από το D-Bus API του BlueZ χρειάζεται μόνο το προσαρτημένο socket και λειτουργεί από το δίκτυο των pods. Ενεργό, το pod τρέχει στο δίκτυο του κόμβου με τις συνέπειες που περιγράφονται στο [Δίκτυο](#δίκτυο). |

Τι κάνει το HotLoop με αυτό σήμερα: τίποτα ακόμη. Το HotLoop δεν έχει δικό του κώδικα για Bluetooth, Z-Wave ή σειριακό USB (το Zigbee έρχεται μέσω μιας γέφυρας Zigbee2MQTT πάνω από MQTT, δείτε [τον ενσωματωμένο MQTT broker](/el/iot/broker/)). είναι η πρόσβαση που χρειάζεται μια λειτουργία, ή ένα sidecar που διαβάζει ένα ραδιόφωνο, έτοιμη πριν ζητηθεί.

Τι κοστίζει, σκόπιμα και αποφασισμένα: το pod είναι root στον κόμβο (privileged, με το `/dev` του κόμβου), και η προεπιλεγμένη NetworkPolicy του chart μένει ενεργή για ό,τι καλύπτει. Το pod μένει στο δίκτυο των pods. Απενεργοποιήστε οποιοδήποτε μέρος με `--set hardware.privileged=false --set hardware.usbDevices.enabled=false --set hardware.bluetooth.enabled=false`· με τα τρία ανενεργά το αποτέλεσμα είναι, γραμμή προς γραμμή, το pod που παρήγαγε η 4.19.6 (non-root, όλα τα capabilities αφαιρεμένα, ριζικό μόνο για ανάγνωση, δίκτυο pods). Για ό,τι χρειάζεται το δίκτυο του κόμβου, ορίστε `hardware.bluetooth.hostNetwork=true` (ή `hostNetwork=true`): η σελίδα τότε απαντά σε κάθε διεύθυνση του κόμβου στο `service.targetPort`, ένα HotLoop ανά κόμβο ανά θύρα, μια NetworkPolicy δεν εφαρμόζεται στο pod, και το `nodeSelector` το καρφώνει στον κόμβο του οποίου το ραδιόφωνο πρέπει να βλέπει.

### Αναπτύξεις στο edge

Το image της εφαρμογής χτίζεται για amd64 και arm64, και το TimescaleDB 2.30.1-pg17 είναι multi-arch, οπότε το ιστορικό δεν είναι αυτό που εμποδίζει μια εγκατάσταση στο edge.

```yaml
resources:
  requests: {cpu: 100m, memory: 128Mi}
  limits:   {cpu: 500m, memory: 256Mi}

database:
  postgresql:
    persistence: {size: 5Gi}
    resources:
      requests: {cpu: 100m, memory: 256Mi}
      limits:   {cpu: 500m, memory: 512Mi}

historian:
  retentionDays: 30

nodeSelector:
  kubernetes.io/arch: arm64
```

### Δημοσίευση προς τα πάνω μέσω Sparkplug

Ένα Gateway στο edge μπορεί επίσης να δημοσιεύει όλα όσα διαβάζει σε ένα κεντρικό, ως κόμβος edge Sparkplug B. Δείτε [Δημοσίευση στο edge και store-and-forward](/el/edge/edge-publish/) για το τι δημοσιεύει και πώς συμπεριφέρεται η ουρά προώθησης· αυτή είναι η πλευρά του chart.

```yaml
edgePublish:
  enabled: true
  broker: tcp://central.example.local:1883
  group: Plant1
  node: press-line-3          # empty uses the release name
  username: press-line-3
  existingSecret: central-mqtt # key "password", or set secretKey
  tls: false
  queueMaxBytes: 536870912     # 512 MiB; the default is 64 MiB, and 0 is unbounded
  persistence:
    size: 1Gi
```

Τι αλλάζει η ενεργοποίηση, και γιατί:

- **Ένα PVC 1Gi για την ουρά προώθησης**, προσαρτημένο στο `/data/edge-publish`. Εκεί συσσωρεύονται οι μετρήσεις όσο η ανοδική σύνδεση είναι κάτω, οπότε πρέπει να επιβιώνει του pod. Το `persistence.enabled: false` την βάζει σε emptyDir, που επιβιώνει από επανεκκίνηση του container και από τίποτα άλλο.
- **Το Deployment ενημερώνεται με `Recreate`.** Η ουρά είναι ένα αρχείο με κλείδωμα. Μια κυλιόμενη ενημέρωση ξεκινά πρώτα το νέο pod, το νέο pod δεν μπορεί να ανοίξει την ουρά, δεν γίνεται ποτέ έτοιμο, και το rollout μένει κολλημένο για πάντα. Το Recreate σταματά πρώτα το παλιό· χάνετε μερικά δευτερόλεπτα polling ανά αναβάθμιση.
- **Το `replicaCount` πρέπει να είναι 1**, και το chart αρνείται να αποδώσει αλλιώς. Δύο replicas θα ήταν δύο publishers που διεκδικούν έναν κόμβο Sparkplug.
- **Το id του κόμβου είναι από προεπιλογή το όνομα της έκδοσης**, όχι το hostname του pod. Το hostname αλλάζει σε κάθε rollout, και ένας host Sparkplug θα έβλεπε κάθε φορά έναν ολοκαίνουργιο κόμβο edge.

Ο κωδικός δεν μπαίνει ποτέ σε προεπιλογή σε απλό κείμενο. Αφήστε τα `password` και `existingSecret` κενά για έναν ανώνυμο broker και δεν δημιουργείται Secret· ορίστε `password` και το chart τον βάζει στο `<release>-edge-publish`· ορίστε `existingSecret` για να χρησιμοποιήσετε ένα που διαχειρίζεστε εσείς.

### Εξωτερική βάση δεδομένων

```yaml
database:
  postgresql:
    enabled: false
    auth:
      existingSecret: my-db-credentials
      secretKey: password
  external:
    host: timescale.plant.local
    port: 5432
    database: industrial
    username: industrial
  sslMode: require
```

Η εφαρμογή ανιχνεύει το TimescaleDB και προάγει το `tag_history` σε hypertable όταν υπάρχει η επέκταση. Απέναντι σε απλή PostgreSQL υποχωρεί σε ενσωματωμένο range partitioning αντί να αποτύχει.

Η απόφαση καταγράφεται και είναι **μόνιμη**. Μια βάση που δημιουργήθηκε ως hypertable αρνείται να ξεκινήσει απέναντι σε διακομιστή χωρίς την επέκταση αντί να γράψει σιωπηλά αλλού· αν δείτε αυτό το σφάλμα, έχετε στρέψει την εφαρμογή σε άλλη βάση από αυτήν πάνω στην οποία χτίστηκε.

### SQLite

Η βάση δεδομένων είναι ρύθμιση, όχι image. Κάθε προϊόν τρέχει σε SQLite, Postgres ή TimescaleDB από το ίδιο binary (το IoT παραλείπει το TimescaleDB, δείτε παρακάτω):

| Μεταβλητή | Προεπιλογή | Τι κάνει |
|---|---|---|
| `HOTLOOP_DB_TYPE` | `postgres` | `postgres` ή `sqlite`. Το TimescaleDB είναι `postgres` με την επέκταση στον διακομιστή |
| `HOTLOOP_DB_PATH` | `/data/hotloop.db` | Το αρχείο SQLite. Το διαβάζει μόνο η SQLite |

Η SQLite είναι η καθαρή Go έκδοση (`modernc.org/sqlite`), μεταγλωττισμένη σε κάθε image, οπότε δεν υπάρχει δεύτερο container, ούτε image Postgres 300 MB σε κάρτα SD, και τα arm builds μένουν στατικά. Βάλτε το αρχείο σε τόμο που επιβιώνει του container, και σε Pi βάλτε αυτόν τον τόμο σε USB SSD. Ένα ιστορικό που γράφει σε κάρτα SD όλη μέρα είναι ο τρόπος να αγοράσετε πολλές κάρτες SD.

Τι είναι ίδιο: κάθε πίνακας, κάθε στήλη, κάθε λειτουργία. Τι διαφέρει:

- Το ιστορικό είναι ένας πίνακας με ένα ευρετήριο, όχι partitions ή hypertable, και η διατήρηση διαγράφει παλιές γραμμές αντί να απορρίπτει μήνες. Ένας χώρος με χρόνια ιστορικού ανά δευτερόλεπτο θέλει Postgres ή TimescaleDB, και η μετακίνηση εκεί είναι αντίγραφο ασφαλείας και επαναφορά (BACKUP.md).
- Ένας εγγραφέας κάθε φορά. Η SQLite εναλλάσσεται στις εγγραφές και διαβάζει παράλληλα (WAL), που είναι υπεραρκετό για ένα HotLoop και έναν βοηθό `--mcp-stdio` δίπλα του στο ίδιο αρχείο. Δεν είναι για δύο replicas σε αποθήκευση δικτύου: η SQLite σε NFS αλλοιώνεται, οπότε μια ανάπτυξη SQLite είναι ένα pod με τοπικό τόμο.
- Τα commits είναι `synchronous=FULL`: όταν το API λέει ότι αποθήκευσε, είναι στον δίσκο, με ή χωρίς διακοπή ρεύματος.

Το **HotLoop IoT** έχει από προεπιλογή 30 ημέρες ιστορικού (το `HOTLOOP_HISTORIAN_RETENTION_DAYS` εξακολουθεί να υπερισχύει όταν οριστεί) και δεν χτίζει ποτέ hypertable: το TimescaleDB είναι μέρος των Edge και Gateway. Ορίστε `HOTLOOP_HISTORIAN_TIMESCALE=true` στο IoT και το λέει στην εκκίνηση και τρέχει σε απλά partitions. Μια βάση που μεταφέρθηκε προς τα κάτω από Edge ή Gateway και έχει ήδη hypertable την κρατά και συνεχίζει να λειτουργεί.

#### Επιλογή της βάσης δεδομένων στο chart

Μία τιμή, το `database.type`, και κάθε προϊόν δέχεται όσες τρέχει:

| `database.type` | Τι αναπτύσσεται | IoT | Edge | Gateway |
|---|---|---|---|---|
| `timescaledb` | Η εφαρμογή και το TimescaleDB (ένα StatefulSet και ο τόμος του). Ιστορικό σε hypertable | απορρίπτεται | προεπιλογή | προεπιλογή |
| `postgresql` | Η εφαρμογή και απλή PostgreSQL 17 (ένα StatefulSet και ο τόμος του). Ιστορικό σε ενσωματωμένα partitions | προεπιλογή | ναι | ναι |
| `sqlite` | Η εφαρμογή μόνη της, με το αρχείο της βάσης σε δικό της τόμο | ναι | ναι | ναι |

```bash
helm install hotloop hotloop/hotloop-iot --namespace hotloop --create-namespace   --set database.type=sqlite
```

Το να ζητήσετε `timescaledb` από το IoT αποτυγχάνει την εγκατάσταση και λέει σε τι τρέχει το IoT (`database.type is "timescaledb", and HotLoop IoT runs on sqlite, postgresql`), και η φόρμα του App Store δεν το προσφέρει. Το `helm lint` δεν το πιάνει (το helm 3.22 το περνά καθαρό), οπότε η απόρριψη γίνεται από την απόδοση. Η παράλειψη του `database.type` δίνει την προεπιλογή του ίδιου του προϊόντος, ώστε μια αναβάθμιση με `--reuse-values` από πριν υπάρξει το κλειδί να κρατά τη βάση που είχε.

Η `sqlite` αποδίδει:

- `HOTLOOP_DB_TYPE=sqlite` και `HOTLOOP_DB_PATH=/data/db/hotloop.db`, και καμία από τις ρυθμίσεις σύνδεσης Postgres. Κανένα pod βάσης, κανένας κωδικός βάσης στο Secret, κανένα init container που περιμένει έναν.
- Ένα PersistentVolumeClaim με όνομα `<release>-db` (`database.sqlite.persistence`: `size`, `storageClass`, `accessMode`, 10Gi και η προεπιλογή του cluster για αρχή), προσαρτημένο στο `/data/db`. Ο κατάλογος, όχι το αρχείο: η SQLite κρατά ένα `-wal` και ένα `-shm` δίπλα στη βάση. Βάλτε το σε τοπική αποθήκευση· η SQLite σε NFS αλλοιώνεται.
- Το Deployment σε `Recreate`, όχι κυλιόμενη ενημέρωση, επειδή ο τόμος είναι `ReadWriteOnce` και το αρχείο έχει έναν εγγραφέα. Ένα `replicaCount` πάνω από 1 αποτυγχάνει την εγκατάσταση.

Η NetworkPolicy δεν αλλάζει και είναι ενεργή: η δική της πολιτική της εφαρμογής ισχύει ακόμη, και η πολιτική της βάσης αποδίδεται μόνο όταν υπάρχει pod βάσης να προστατευτεί.

Η αλλαγή του `database.type` σε μια έκδοση που ήδη έχει δεδομένα δεν μετακινεί τα δεδομένα. Η νέα βάση ξεκινά άδεια, οπότε η μετακίνηση ενός εργοστασίου από βάση σε βάση είναι αντίγραφο ασφαλείας και επαναφορά (BACKUP.md), όπως και με τη μεταβλητή. Ειδικά μια βάση που δημιουργήθηκε ως hypertable του TimescaleDB αρνείται να ξεκινήσει απέναντι σε απλή PostgreSQL, οπότε μην αλλάζετε ένα υπάρχον Edge ή Gateway από `timescaledb` σε `postgresql` περιμένοντας να ξεκινήσει.

#### Επιλογή της βάσης δεδομένων στο Quadlet

Ο κατάλογος κάθε προϊόντος κάτω από `deploy/quadlet/` έχει τα αρχεία PostgreSQL ή TimescaleDB όπως ήταν, και έναν κατάλογο `sqlite/` δίπλα τους: `hotloop.container` και `hotloop-data.volume`, η εφαρμογή μόνη της με το αρχείο στο `/data/hotloop.db` στον τόμο `hotloop-data`. Ακολουθεί το `:stable` και επαναφέρει μια κακή ενημέρωση με τον ίδιο τρόπο. Εγκαταστήστε αυτά τα δύο αρχεία αντί των άλλων (χρησιμοποιούν τα ίδια ονόματα μονάδων) και φτιάξτε δύο secrets αντί για τρία: δεν υπάρχει κωδικός βάσης. Το [`deploy/quadlet/README.md`](/el/install/quadlet/) έχει τα βήματα.

Για απλά partitions Postgres σε Edge ή Gateway με Quadlet, κρατήστε τη μονάδα TimescaleDB και προσθέστε `Environment=HOTLOOP_HISTORIAN_TIMESCALE=false` στο `hotloop.container`. Η μονάδα του IoT τρέχει ήδη απλή PostgreSQL.

### Το κλειδί των διαπιστευτηρίων συσκευών

```yaml
secretKey:
  enabled: true
  existingSecret: ""     # or a Secret you manage, with the key under secret.key
```

Οι κωδικοί των συσκευών (σύνδεση σε κονσόλα UniFi, κωδικός OPC UA ή MQTT, κλειδιά HTTP API) κρυπτογραφούνται στη βάση με αυτό το κλειδί, οπότε ένα dump ή ένα αντίγραφο ασφαλείας περιέχει κρυπτογραφημένο κείμενο. Από το κουτί το chart δημιουργεί ένα στο `<release>-secret-key` στην πρώτη εγκατάσταση, το κρατά στις αναβαθμίσεις και το κρατά και στο `helm uninstall` (`helm.sh/resource-policy: keep`), επειδή μια βάση που μένει στον τόμο της δεν χρησιμεύει για τα διαπιστευτήριά της χωρίς αυτό. Προσαρτάται ως αρχείο και περνά ως `HOTLOOP_SECRET_KEY_FILE`, ποτέ ως μεταβλητή περιβάλλοντος.

Κάντε αντίγραφο ασφαλείας του Secret ξεχωριστά από τα αντίγραφα της βάσης: ένα κλειδί δίπλα στα αντίγραφα που προστατεύει δεν προστατεύει τίποτα. Για να φέρετε δικό σας, το `hotloop gen-secret-key` τυπώνει ένα. Εκτός Kubernetes, γράψτε το σε αρχείο που μπορεί να διαβάσει μόνο το HotLoop και στρέψτε το `HOTLOOP_SECRET_KEY_FILE` σε αυτό. Χωρίς κλειδί το HotLoop τρέχει, λέει στο log εκκίνησης ότι οι κωδικοί των συσκευών αποθηκεύονται όπως πληκτρολογήθηκαν, και αρνείται να αποθηκεύσει κονσόλα UniFi. Τα διαπιστευτήρια που είναι ήδη αποθηκευμένα κρυπτογραφούνται την πρώτη φορά που ξεκινά με κλειδί. Δείτε [Αντίγραφα ασφαλείας και επαναφορά](/el/iot/backup/#διαπιστευτήρια-συσκευών-και-το-μυστικό-κλειδί) για το τι σημαίνει αυτό για μια επαναφορά.

## Διαμόρφωση, και τι μπορεί να αλλάξει η οθόνη Ρυθμίσεις

Σχεδόν κάθε ρύθμιση προέρχεται από μια μεταβλητή περιβάλλοντος που το chart ορίζει από μια τιμή Helm. Αυτό είναι το σωστό μέρος: η διαμόρφωση που αποφασίζει αν αυτή η διεργασία μπορεί να διατάζει μηχανήματα ανήκει στην ανάπτυξη, ελεγμένη, όχι σε μια φόρμα σε ιστοσελίδα.

Η οθόνη **Ρυθμίσεις** τα δείχνει όλα, κάθε ρύθμιση, την ισχύουσα τιμή της, αν προήλθε από τη βάση, από μεταβλητή περιβάλλοντος ή από την ενσωματωμένη προεπιλογή, και τη μεταβλητή που την αλλάζει. Τα περισσότερα είναι μόνο για ανάγνωση, και αυτό είναι το νόημα: η ερώτηση στην οποία απαντά είναι "γιατί το κάνει αυτό, και τι αλλάζω;"

Τέσσερις ρυθμίσεις είναι ταυτότητα του εργοστασίου και όχι συμπεριφορά, και επεξεργάζονται εκεί. Αποθηκεύονται στη βάση και ισχύουν αμέσως, επειδή ένα εργοστάσιο μετονομάζεται πολύ πιο συχνά από όσο αναπτύσσεται ξανά:

| ρύθμιση | μεταβλητή που υπερισχύει |
|---|---|
| Όνομα εργοστασίου | `HOTLOOP_PLANT_NAME` |
| ID χώρου | `HOTLOOP_SITE_ID` |
| Ζώνη ώρας | `HOTLOOP_TIMEZONE` |
| Επιβεβαίωση πριν την εγγραφή | `HOTLOOP_CONFIRM_WRITES` |

Κάτω από τις ρυθμίσεις υπάρχουν κάρτες που είναι δεδομένα και όχι διαμόρφωση, και επεξεργάζονται για τον ίδιο λόγο: **Χρήστες** ([Έλεγχος ταυτότητας και χρήστες](/el/iot/authentication/)), **Κλιμάκωση συναγερμών**, που λέει ποιος ειδοποιείται μετά όταν κανείς δεν αναγνωρίζει έναν συναγερμό και πότε ([Ειδοποιήσεις συναγερμών](/el/iot/notifications/#escalation)), και οι προορισμοί του ιστορικού και οι συνδέσεις MQTT. Τα κανάλια που μπορεί να χρησιμοποιήσει μια κλιμάκωση παραμένουν της ανάπτυξης, ορισμένα από `HOTLOOP_NOTIFY_*`.

Μια αποθηκευμένη τιμή υπερισχύει της μεταβλητής περιβάλλοντος, οπότε η τιμή του chart γίνεται το σημείο εκκίνησης και όχι ο τελευταίος λόγος. Μια ζώνη ώρας που το μηχάνημα δεν μπορεί να επιλύσει απορρίπτεται αντί να γίνει δεκτή και να αγνοηθεί σιωπηλά, κάτι που θα άφηνε κάθε χρονοσφραγίδα να υποχωρεί σε UTC χωρίς τίποτα να λέει γιατί.

Το ίδιο ισχύει για την τιμή της ίδιας της ανάπτυξης. Αν το `HOTLOOP_TIMEZONE` (ή το `TZ`, όταν εκείνο δεν έχει οριστεί) ονομάζει ζώνη που δεν φορτώνεται, το HotLoop αρνείται να ξεκινήσει και το σφάλμα ονομάζει τη μεταβλητή και την τιμή. Παλιά σήκωνε τους ώμους και έτρεχε σε UTC. Οι αναφορές, οι χρονοπρογραμματισμοί και οι ώρες βάρδιας τρέχουν με το ρολόι του εργοστασίου, και μια εικασία με ώρες διαφορά είναι χειρότερη από ένα pod που λέει γιατί δεν ξεκινά.

Η τοποθεσία του χώρου είναι `HOTLOOP_SITE_LATITUDE` και `HOTLOOP_SITE_LONGITUDE` (chart: `plant.latitude`, `plant.longitude`), δεκαδικές μοίρες, βορράς και ανατολή θετικά. Η ανατολή, η δύση και οι οντότητες και οι σκανδάλες του ήλιου υπολογίζονται από αυτές στο ίδιο το μηχάνημα ([Ο ήλιος](/el/iot/sun/)). Και τα δύο ή κανένα, και μια λανθασμένη σταματά την εκκίνηση ονομάζοντας τη μεταβλητή. Η οθόνη Ρυθμίσεις τα δείχνει μόνο για ανάγνωση: οι κανόνες πυροδοτούνται σε μια ανατολή, οπότε η μετακίνησή της είναι ανάπτυξη.

**Οι διακόπτες ασφαλείας δεν επεξεργάζονται και δεν θα επεξεργάζονται.** Το `HOTLOOP_ALLOW_WRITES` είναι ο κύριος έλεγχος του αν αυτή η διεργασία μπορεί να διατάζει εξοπλισμό· ένας έλεγχος που μπορεί να ενεργοποιηθεί ξανά από την ίδια συνεδρία προγράμματος περιήγησης που εκδίδει τις εγγραφές δεν είναι έλεγχος. Το `HOTLOOP_HISTORIAN_RETENTION_DAYS` είναι επίσης μόνο της ανάπτυξης: η πολιτική διατήρησης εφαρμόζεται στη βάση στην εκκίνηση, οπότε ένα πεδίο σε οθόνη θα έδειχνε ότι δουλεύει και δεν θα μετακινούσε κανένα δεδομένο. Το endpoint απορρίπτει οποιοδήποτε κλειδί εκτός του επεξεργάσιμου συνόλου **με το όνομά του**, αντί να το αγνοεί.

Ένας περιορισμός, που δηλώνεται επειδή τον δηλώνει και η οθόνη: ο διακομιστής MCP χτίζει τις οδηγίες του στην εκκίνηση, οπότε διαφημίζει το όνομα του εργοστασίου με το οποίο ξεκίνησε μέχρι να επανεκκινηθεί το pod. Όλα τα υπόλοιπα παίρνουν μια μετονομασία στο επόμενο αίτημα.

## PostgreSQL 17

Η βάση του HotLoop είναι PostgreSQL 17 (με TimescaleDB 2.30.1 πάνω της για Edge και Gateway, απλή PostgreSQL 17.11 για IoT και για `database.type: postgresql`). Οι εκδόσεις πριν από αυτήν έτρεχαν PostgreSQL 16, και η PostgreSQL δεν ανοίγει τον κατάλογο δεδομένων άλλης major έκδοσης. Έτσι η μετάβαση γίνεται για εσάς, στην αναβάθμιση, και δεν υπάρχει τίποτα να εκτελέσετε.

**Στο chart,** το pod της βάσης παίρνει δύο init containers. Το πρώτο τρέχει το image PostgreSQL 16 και, μόνο όταν ο τόμος έχει δεδομένα 16, αντιγράφει αυτή την εγκατάσταση σε έναν προσωρινό τόμο. Το δεύτερο τρέχει το νέο image και κάνει `pg_upgrade` σε νέο κατάλογο δίπλα στον παλιό. Και τα δύο αφήνουν ήσυχο έναν καινούργιο τόμο ή έναν που είναι ήδη στο 17. Η αναβάθμιση είναι `helm upgrade`, τίποτα παραπάνω. Περιμένετε το pod της βάσης να μείνει σε `Init` όσο χρειάζεται ένα αντίγραφο των δεδομένων, και την εφαρμογή να το περιμένει· το `kubectl logs <release>-postgresql-0 -c pg-upgrade` είναι το log.

**Στο Quadlet,** το `hotloop-db-upgrade.container` τρέχει πριν από το `hotloop-db.service` και κάνει το ίδιο σε μια μονάδα oneshot. Αντιγράψτε τα νέα `hotloop-db.container`, `hotloop-db-upgrade.container` και `hotloop-db-upgrade.sh` από τον κατάλογο του προϊόντος σας στον κατάλογο των μονάδων και επανεκκινήστε τη μονάδα της βάσης· το [README του Quadlet](/el/install/quadlet/) έχει τις εντολές. Η μονάδα της βάσης απαιτεί τη μονάδα αναβάθμισης, οπότε ένα μηχάνημα που πήρε μόνο τη νέα μονάδα βάσης δεν ξεκινά σε δεδομένα 16 και λέει γιατί: αποτυγχάνει, δεν μαντεύει. Το `journalctl -u hotloop-db-upgrade` είναι το log. Η μονάδα τρέχει μόνο όταν ο τόμος έχει δεδομένα 16: σε νέο μηχάνημα, και σε κάθε εκκίνηση μετά την αναβάθμιση, το systemd την παραλείπει (εμφανίζεται ως ανενεργή, όχι αποτυχημένη) και το image PostgreSQL 16 δεν κατεβαίνει ποτέ. Όταν ο τόμος έχει δεδομένα 16, η μονάδα κατεβάζει πρώτα αυτό το image.

Τι κάνει, με τη σειρά, όλα στο `hotloop-pg-upgrade.sh` (ένα αρχείο, το ίδιο που τρέχουν το chart και οι μονάδες):

1. Κανένας κατάλογος δεδομένων, ή ένας ήδη στο 17: τίποτα, και το λέει. Κάθε άλλη major έκδοση απορρίπτεται, χωρίς καμία αλλαγή.
2. Ξεκινά τον παλιό διακομιστή μία φορά σε ιδιωτικό socket και τον σταματά καθαρά, κάτι που αναπαράγει το log μετά από διακοπή ρεύματος και διαβάζει την κωδικοποίηση και το locale που πρέπει να ταιριάζει το νέο cluster.
3. Κάνει `initdb` σε νέο κατάλογο δίπλα στον παλιό με αυτές τις ρυθμίσεις, τρέχει `pg_upgrade` σε λειτουργία αντιγραφής (ο παλιός κατάλογος μόνο διαβάζεται) και μεταφέρει τα `postgresql.conf`, `postgresql.auto.conf`, `pg_hba.conf` και `pg_ident.conf`.
4. Ξεκινά τον νέο διακομιστή μία φορά για να αποδείξει ότι ανοίγει με τις τελικές ρυθμίσεις και συλλέγει τα στατιστικά του planner που το `pg_upgrade` δεν μεταφέρει.
5. Μόνο τότε ανταλλάσσει τα ονόματα: ο παλιός κατάλογος γίνεται `pgdata.pg16`, ο νέος `pgdata`.

Χρειάζεται περίπου τόσο ελεύθερο χώρο δίπλα στα δεδομένα όσο καταλαμβάνουν τα δεδομένα, και το ελέγχει πριν ξεκινήσει. Αν οτιδήποτε αποτύχει πριν από το βήμα 5, η αναβάθμιση τερματίζει με μη μηδενικό κωδικό, τα δεδομένα 16 είναι ακριβώς όπως ήταν, και η βάση δεν ξεκινά σε μισοχτισμένο κατάλογο: στο chart το pod μένει σε `Init:Error`, στο Quadlet η μονάδα αναβάθμισης αποτυγχάνει και η μονάδα της βάσης πίσω της δεν ξεκινά ποτέ. Διορθώστε ό,τι λέει το log και ξεκινήστε ξανά· μια ημιτελής απόπειρα αφαιρείται και επαναλαμβάνεται. Η επέκταση TimescaleDB περνά στην έκδοση που ήταν, και η εφαρμογή την ενημερώνει σε αυτήν που παραδόθηκε στην επόμενη εκκίνηση, όπως πάντα. Η δική του οδηγία του TimescaleDB για επιτόπια αναβάθμιση PostgreSQL είναι το `pg_upgrade` με τα παλιά και τα νέα binaries ([Tiger Data, "Upgrade PostgreSQL"](https://www.tigerdata.com/docs/deploy/self-hosted/upgrades/upgrade-pg)).

Το αντίγραφο ασφαλείας είναι ο ίδιος ο παλιός κατάλογος. Το `pg_upgrade` σε λειτουργία αντιγραφής δεν γράφει ποτέ σε αυτόν, οπότε το `pgdata.pg16` είναι ολόκληρη η βάση PostgreSQL 16 όπως ήταν, που είναι καλύτερο αντίγραφο από ένα dump και το μόνο που κάνει δυνατό τον δρόμο της επιστροφής παρακάτω. Το δικό του αντίγραφο ασφαλείας του HotLoop ([Αντίγραφα ασφαλείας και επαναφορά](/el/iot/backup/)) γίνεται από την εφαρμογή που τρέχει μέσω της βάσης που τρέχει, οπότε δεν μπορεί να γίνει στο βήμα που τρέχει πριν ξεκινήσει η βάση. Κάντε ένα με την παλιά έκδοση πριν αναβαθμίσετε ούτως ή άλλως, και αντιγράψτε το έξω από το μηχάνημα.

### Επιστροφή

Το `helm rollback`, ή η επαναφορά του προηγούμενου `hotloop-db.container`, επιστρέφει τη βάση στο image PostgreSQL 16 (η αυτόματη ενημέρωση του Podman δεν το κάνει: μετακινεί μόνο την εφαρμογή), και η PostgreSQL 16 δεν ανοίγει κατάλογο 17 (`database files are incompatible with server`, το log λέει ότι ο κατάλογος αρχικοποιήθηκε από την έκδοση 16). Τίποτα δεν χάνεται και τίποτα δεν είναι μισοαλλαγμένο· η βάση απλώς δεν ξεκινά. Αυτό που χρειάζεται η προηγούμενη έκδοση είναι ο δικός της κατάλογος 16, που είναι το `pgdata.pg16`. Σταματήστε τη βάση και βάλτε τα ονόματα πίσω:

```sh
# chart: after the rollback, stop the database, swap in a one-off pod, start it
kubectl -n hotloop scale statefulset/hotloop-postgresql --replicas=0
kubectl -n hotloop run pgswap --rm -it --restart=Never --image=busybox \
  --overrides='{"spec":{"securityContext":{"runAsUser":999,"fsGroup":999},"containers":[{"name":"pgswap","image":"busybox","command":["sh","-c","cd /d && mv pgdata pgdata.pg17 && mv pgdata.pg16 pgdata"],"volumeMounts":[{"name":"d","mountPath":"/d"}]}],"volumes":[{"name":"d","persistentVolumeClaim":{"claimName":"data-hotloop-postgresql-0"}}]}}'
kubectl -n hotloop scale statefulset/hotloop-postgresql --replicas=1

# Quadlet: the volume is named hotloop-db
sudo systemctl stop hotloop.service hotloop-db.service
d=$(sudo podman volume inspect hotloop-db --format '{{.Mountpoint}}')
sudo mv "$d/pgdata" "$d/pgdata.pg17" && sudo mv "$d/pgdata.pg16" "$d/pgdata"
```

Αυτή είναι η βάση όπως ήταν στην αναβάθμιση, και τίποτα από ό,τι γράφτηκε μετά. Η αντιστροφή δουλεύει μόνο μία φορά: η αναβάθμιση αρνείται να τρέξει όσο υπάρχει `pgdata.pg16` στη μέση, οπότε η επόμενη απόπειρα αναβάθμισης χρειάζεται πρώτα το `pgdata.pg17` και να τακτοποιηθεί ο παλιός κατάλογος. Η μετάβαση προς τα εμπρός είναι ο δρόμος, και η επαναφορά είναι για ένα μηχάνημα που δεν μπορεί καθόλου να τρέξει 17. Ο κανόνας επαναφοράς της ίδιας της εφαρμογής δεν αλλάζει: το σχήμα του καταλόγου 16 είναι αυτό που άφησε η έκδοση πριν την αναβάθμιση, και μια έκδοση που βρίσκει migrations που δεν γνωρίζει το λέει, δείτε [Τα migrations μόνο προσθέτουν](/el/iot/migrations/).

### Όταν μείνετε ικανοποιημένοι

Το `pgdata.pg16` μένει μέχρι να το διαγράψετε, επειδή η διαγραφή του είναι διαγραφή του μόνου δρόμου επιστροφής. Είναι τόσο μεγάλο όσο η βάση. Όταν το μηχάνημα έχει τρέξει στο 17 όσο θέλετε:

```sh
# chart
kubectl -n hotloop exec hotloop-postgresql-0 -c postgresql -- rm -rf /var/lib/postgresql/data/pgdata.pg16
# Quadlet
sudo rm -rf "$(sudo podman volume inspect hotloop-db --format '{{.Mountpoint}}')/pgdata.pg16"
```

### Απενεργοποίηση

Το `database.postgresql.upgrade.enabled: false` αφαιρεί τα init containers. Ένας τόμος που είναι ακόμη στο 16 εμποδίζει τότε τη βάση να ξεκινήσει, και η μετάβαση είναι δική σας. Αφήστε το ενεργό: ενεργό, μια καινούργια εγκατάσταση κατεβάζει παρ' όλα αυτά το image PostgreSQL 16 μία φορά ανά κόμβο, επειδή το image ενός init container κατεβαίνει πριν τρέξει, και μετά δεν το τρέχει ποτέ.

## Αναβάθμιση από την 3.x

**Αυτό είναι αντικατάσταση, όχι αναβάθμιση.** Η 3.x ήταν διαφορετικό προϊόν. Δεν υπάρχει μονοπάτι migration για τα δεδομένα της, επειδή δεν μοιράζεται κανένα μοντέλο δεδομένων με ένα ιστορικό tags.

```bash
helm uninstall hotloop -n hotloop
# keep or delete the old PVCs deliberately, they hold the HA recorder database
helm install hotloop ./charts/hotloop -n hotloop
```

Πράγματα που δεν υπάρχουν πια και θα απορριφθούν αν οριστούν: `sidecarProxy`, `homeassistant`, τα πρόσθετα `mqtt`/`nodered`/`esphome`/`zigbee2mqtt`, `devices`, `cameras`, `customConfig`, `network.hostNetwork`.

## Επαναφορά μιας ενημέρωσης

Το `helm rollback hotloop -n hotloop` επαναφέρει το image της προηγούμενης έκδοσης. Δεν επαναφέρει τη βάση: μια έκδοση κάνει migration στην εκκίνηση, και αυτό μένει γεγονός. Ο κανόνας και ο έλεγχος βρίσκονται στα [Τα migrations μόνο προσθέτουν](/el/iot/migrations/).

Το μόνο που επαναφέρει μια επαναφορά πέρα από την έκδοση PostgreSQL 17 είναι η μηχανή της βάσης: το image βάσης του chart γυρίζει στο 16, που δεν θα ανοίξει τον αναβαθμισμένο κατάλογο. Η [Επιστροφή](#επιστροφή) είναι η διέξοδος.

Είναι ασφαλές για μία έκδοση πίσω. Η βάση καταγράφει ποια έκδοση εφάρμοσε κάθε migration, και μια έκδοση που βρίσκει migrations από δύο ή περισσότερες εκδόσεις νεότερες από την ίδια αρνείται να ξεκινήσει:

```
refusing to start: this database's schema is more than one release ahead of
HotLoop 4.18.10. ...
```

Αυτό δεν είναι σφάλμα που πρέπει να παρακαμφθεί. Σημαίνει ότι η βάση έχει προχωρήσει πιο πέρα από όσο έτρεξε ποτέ αυτή η έκδοση. Προχωρήστε σε μια έκδοση που γνωρίζει το σχήμα, την πιο πρόσφατη, ή επαναφέρετε ένα αντίγραφο ασφαλείας που έγινε από την έκδοση στην οποία βρίσκεστε ([Αντίγραφα ασφαλείας και επαναφορά](/el/iot/backup/)). Ακριβώς μία έκδοση πίσω ξεκινά, με μια προειδοποίηση στο log που ονομάζει και τις δύο εκδόσεις. Κάντε αντίγραφο ασφαλείας πριν αναβαθμίσετε· η επαναφορά δεν μπορεί να αναιρέσει δεδομένα που έγραψε η νεότερη έκδοση.

## Επαλήθευση μιας εγκατάστασης

```bash
kubectl -n hotloop get pods
kubectl -n hotloop logs deploy/hotloop | head -20
```

Μια υγιής εκκίνηση λέει τα πρωτόκολλα που μιλά, εφαρμόζει τα migrations, αναφέρει τη λειτουργία ιστορικού και προειδοποιεί για οτιδήποτε αξίζει να γνωρίζετε:

```
msg=starting version=4.0.0 protocols="[ethernet-ip http modbus mqtt mtconnect opcua s7comm]"
msg="writes are ENABLED: the UI, API, automations and MCP can all command devices"
msg="tag_history promoted to a hypertable" timescale=2.30.1
msg="history schema ready" mode=timescale
msg=listening addr=:8080 mcp=/mcp writes=true
```

Έπειτα ελέγξτε τις ετικέτες που χρειάζεται ο πίνακας. Αυτός είναι ο έλεγχος που πιάνει την απόκλιση, ελέγξτε το **σύνολο**, όχι τον αριθμό, επειδή ένας έλεγχος αριθμού περνά ενώ το σύνολο είναι λάθος:

```bash
kubectl -n hotloop get svc <release> -o json \
  | jq -r '.metadata.labels | keys[] | select(startswith("embernet.ai/"))'
```

Ακριβώς τέσσερις, στο Service και στο pod:

```
embernet.ai/app-name
embernet.ai/gui-port
embernet.ai/gui-type
embernet.ai/store-app
```

Αν η εφαρμογή τρέχει αλλά λείπει από τις Εφαρμογές που εκτελούνται, οι ετικέτες του Service είναι το πρώτο μέρος να κοιτάξετε: ο πίνακας ρωτά τα Services με `embernet.ai/store-app`.

Μια ανάπτυξη από το App Store προσθέτει άλλες πέντε, από τα `tenantLabels` που περνά ο πίνακας: `embernet.ai/tenant`, `app-id`, `source`, `deployed-by` και `deployment-id`. Μπαίνουν σε κάθε πόρο που αποδίδει το chart και στο pod του gateway. Ο πίνακας διαβάζει τον tenant από το Service και πουθενά αλλού, οπότε ένα Gateway που αναπτύχθηκε από το store χωρίς `embernet.ai/tenant` στο Service του δεν ανήκει σε κανέναν. Ένα απλό `helm install` δεν αποδίδει καμία από τις πέντε.

## Probes

- `/healthz`, liveness. Απαντά όσο η διεργασία τρέχει.
- `/readyz`, readiness. Απαιτεί επιπλέον τη βάση, ώστε ένα pod που έχασε το ιστορικό του να σταματά να δέχεται κίνηση αντί να σερβίρει μια διεπαφή που δεν μπορεί να απαντήσει τίποτα.

Το startup probe επιτρέπει δύο λεπτά, επειδή μια πρώτη εγκατάσταση τρέχει migrations και το liveness probe δεν πρέπει να την σκοτώσει στη μέση ενός migration.

## Τερματισμός

`terminationGracePeriodSeconds: 45`. Στο SIGTERM η εφαρμογή σταματά να δέχεται αιτήματα, και μετά αδειάζει την ουρά του ιστορικού ώστε οι μετρήσεις που ήδη ελήφθησαν να γραφτούν αντί να πεταχτούν. Αν η περίοδος χάριτος κοπεί υπερβολικά, χάνεται ό,τι ήταν σε εξέλιξη.

## Αντιμετώπιση προβλημάτων

**Μια συσκευή μένει σε `connecting`.** Δείτε το `lastError` στην κάρτα της συσκευής. Συνήθως firewall ανάμεσα στο pod και τον εξοπλισμό, ή λάθος θύρα. Το chart δεν περιορίζει το egress, οπότε μια NetworkPolicy που το μπλοκάρει είναι κάτι άλλο στο cluster.

**Τα tags διαβάζουν κακή ποιότητα.** Η συσκευή απάντησε αλλά το σημείο όχι. Για Modbus, ελέγξτε τη βάση διευθύνσεων, `oneBased` αν τα σχέδιά σας χρησιμοποιούν αρίθμηση 40001. Για OPC UA, ελέγξτε ότι επιλύθηκε το node id· προτιμήστε τη μορφή `nsu=`.

**Οι τιμές φαίνονται πιστευτές αλλά είναι λάθος.** Στο Modbus, αυτό είναι η σειρά των λέξεων, δοκιμάστε `CDAB`. Αυτή είναι η βλάβη που δεν ανακοινώνεται, επειδή ο αριθμός δεν είναι προφανώς λάθος.

**Τίποτα δεν καταγράφεται στο ιστορικό.** Ελέγξτε τα διαγνωστικά της οθόνης Πρωτόκολλα. Το `filtered` μετρά μετρήσεις που καταστέλλονται από τη νεκρή ζώνη, που λειτουργεί όπως προορίζεται· το `dropped` μετρά μετρήσεις που χάθηκαν επειδή η βάση δεν τα κατάφερε, που δεν είναι.

**Το MCP επιστρέφει 401.** Το bearer token. Διαβάστε το από το Secret της έκδοσης.

**Κάθε αίτημα `/api/` επιστρέφει 401.** Αναμενόμενο όταν το `auth.enabled` είναι true και κανείς δεν έχει συνδεθεί ακόμη, αυτό είναι το νόημα της 4.4.0. Διαβάστε τον δημιουργημένο κωδικό διαχειριστή από το Secret της έκδοσης (δείτε [Έλεγχος ταυτότητας](#έλεγχος-ταυτότητας)) και συνδεθείτε από τη διεπαφή, ή `POST /api/auth/login` απευθείας. Δείτε [Έλεγχος ταυτότητας και χρήστες](/el/iot/authentication/).

**Χάθηκε ο κωδικός διαχειριστή και δεν υπάρχει άλλος λογαριασμός διαχειριστή.** Δημιουργήστε νέο hash και κάντε patch το Secret, και μετά επανεκκινήστε το pod ώστε να ξαναδιαβάσει το περιβάλλον· το `EnsureAdminUser` δεν θα αγγίξει λογαριασμό που υπάρχει ήδη, οπότε αυτό αντικαθιστά τη γραμμή απευθείας αντί να περνά από το chart:

```bash
hotloop hash-password -password 'a-new-one'
kubectl exec -n hotloop deploy/hotloop -- \
  psql "$DATABASE_URL" -c \
  "UPDATE users SET password_hash = '<the hash>' WHERE username = 'admin'"
```

**Μια αυτοματοποίηση είναι ενεργοποιημένη αλλά δεν τρέχει.** Απέτυχε η μεταγλώττιση. Η οθόνη Αυτοματοποιήσεις την δείχνει ως NOT ARMED με τον λόγο, και το log του συστήματος έχει το σφάλμα.
