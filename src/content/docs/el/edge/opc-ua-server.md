Αυτή η σελίδα καλύπτει και μερικά πράγματα που είναι νεότερα από το HotLoop core 4.24.0, την τελευταία έκδοση. Ορισμένα από αυτά μπορεί να μην υπάρχουν σε αυτό που έχετε εγκαταστήσει. Οι [σημειώσεις έκδοσης](/el/releases/) λένε τι άλλαξε.
:::

Ο διακομιστής OPC UA του HotLoop, από την έκδοση 4.13.0, δημοσιεύει τις συσκευές και τα tags που έχουν ρυθμιστεί στο Gateway ως χώρο διευθύνσεων OPC UA. Έτσι ένας πελάτης OPC UA τρίτου, ένα πακέτο SCADA, ένα HMI, ένα historian ή ένα εργαλείο δοκιμών όπως το UaExpert μπορεί να διαβάσει τα ζωντανά tags του Gateway χωρίς να γράψει κανείς driver HotLoop για την άλλη πλευρά.

Είναι ενεργοποιημένος από προεπιλογή (`HOTLOOP_OPCUA_SERVER_ENABLED`), στο εκτελέσιμο και στο Helm chart. Ξεκινά με ενεργή την πιστοποίηση του HotLoop και με δική του σύνδεση, `opcua-reader`, την οποία το HotLoop δημιουργεί με έναν παραγόμενο κωδικό που οι Ρυθμίσεις δείχνουν σε έναν διαχειριστή (`GET /api/opcua/server`)· μπορεί να διαβάζει tags και τιμές και τίποτε άλλο. Με την πιστοποίηση του HotLoop ανενεργή δεν υπάρχουν χρήστες για σύνδεση, οπότε ο server περιμένει και το αναφέρει (δεν αρνείται να ξεκινήσει). Αν η 4840 είναι ήδη πιασμένη από άλλον OPC UA server στη συσκευή, περιμένει και το αναφέρει· μια θύρα που επιλέξατε και δεν μπορεί να ανοίξει είναι σφάλμα: το άνοιγμα ενός listener σε δίκτυο εργοστασίου είναι κάτι που η εγκατάσταση κάνει εσκεμμένα. Προεπιλεγμένη θύρα 4840.

**Είναι μόνο για ανάγνωση.** Δείτε [Γιατί είναι μόνο για ανάγνωση](#γιατί-είναι-μόνο-για-ανάγνωση). Εξυπηρετεί επίσης το ιστορικό κάθε tag: δείτε [Ιστορικό](#ιστορικό).

## Τι εκτίθεται

Ένας κόμβος **Object** για κάθε ενεργοποιημένη συσκευή, ακριβώς κάτω από τον τυπικό φάκελο *Objects*, και ένας κόμβος **Variable** για κάθε ενεργοποιημένο tag κάτω από τη συσκευή του. Οι απενεργοποιημένες συσκευές και τα tags δεν δημοσιεύονται: δεν έχουν worker ούτε ένδειξη, και η δημοσίευσή τους θα έβαζε μόνο έναν μόνιμα Bad κόμβο μπροστά στον πελάτη. Ο χώρος διευθύνσεων είναι ακριβώς ό,τι ερωτά το runtime.

Όλα βρίσκονται σε έναν χώρο ονομάτων, `urn:hotloop:ua:gateway`. Το URI του χώρου ονομάτων είναι σταθερά και δεν προκύπτει ούτε από το όνομα του host ούτε από το URI της εφαρμογής: ο πελάτης αποθηκεύει έναν κόμβο ως URI συν αναγνωριστικό και ξαναβρίσκει τον δείκτη του χώρου ονομάτων σε κάθε σύνδεση, και ένα URI που άλλαζε με το όνομα ενός pod θα άφηνε ορφανή κάθε συνδρομή που έχει ρυθμιστεί σε ένα έργο SCADA. Βρείτε τον δείκτη στον πίνακα χώρων ονομάτων του διακομιστή με βάση το URI, όπως κάνει ένας πραγματικός πελάτης· μην υποθέτετε `ns=2`.

### NodeIds

Τα αναγνωριστικά είναι συμβολοσειρές και σταθερά:

| Κόμβος | Αναγνωριστικό NodeId |
|---|---|
| Συσκευή | `<deviceId>` |
| Tag | `<deviceId>/<tagName>` |
| Η ιδιότητα `EngineeringUnits` / `EURange` ενός tag | `~EngineeringUnits/<deviceId>/<tagName>` και `~EURange/…` |

Η μορφή του tag είναι `model.TagKey.String()`, η γραφή `device/tag` που χρησιμοποιεί ήδη ο υπόλοιπος κώδικας, ώστε ένα NodeId και ένα κλειδί tag να μετατρέπονται το ένα στο άλλο με το `model.ParseTagKey`. Ένας διαχωριστής `.` δεν θα δούλευε: τα αναγνωριστικά συσκευών μπορεί να περιέχουν τελείες, οπότε το `a.b.c` θα μπορούσε να είναι η συσκευή `a` με tag `b.c` ή η συσκευή `a.b` με tag `c`. Ένα αναγνωριστικό συσκευής δεν μπορεί να περιέχει κάθετο, άρα η πρώτη κάθετος είναι πάντα το όριο, και ένα όνομα tag που περιέχει καθέτους (τις έχουν οι διαδρομές περιήγησης OPC UA και τα topics MQTT) αντιστοιχίζεται και πάλι στη σωστή συσκευή. Τα αναγνωριστικά ιδιοτήτων αρχίζουν με `~`, κάτι που ένα αναγνωριστικό συσκευής δεν μπορεί, ώστε μια ιδιότητα να μη συγκρούεται ποτέ με ένα tag, όπως κι αν λέγεται το tag.

### Χαρακτηριστικά

| Χαρακτηριστικό | Τιμή |
|---|---|
| `BrowseName` | το αναγνωριστικό της συσκευής / το όνομα του tag, στον χώρο ονομάτων HotLoop |
| `DisplayName` | το όνομα της συσκευής / το όνομα του tag |
| `Description` | η περιγραφή της συσκευής ή του tag |
| `DataType` | δείτε παρακάτω |
| `ValueRank` | βαθμωτό (-1) |
| `AccessLevel`, `UserAccessLevel` | μόνο `CurrentRead` (0x01) |
| `MinimumSamplingInterval` | το πραγματικό διάστημα ερώτησης της συσκευής σε ms· οι τιμές δεν μπορούν να αλλάξουν ταχύτερα απ' ό,τι τις ερωτά το runtime, άρα ένας πελάτης που ζητά ταχύτερο ρυθμό δειγματοληψίας τον βλέπει να αναβιβάζεται σε αυτό το διάστημα |
| `Historizing` | false |

Ένα tag με μονάδα παίρνει ιδιότητα `EngineeringUnits` (`EUInformation`, αναγνωριστικό μονάδας -1 = «όχι κωδικός UNECE», το κείμενο της μονάδας στο `DisplayName`), και ένα tag με εύρος παίρνει ιδιότητα `EURange`. Ένα tag χωρίς κανένα από τα δύο δεν έχει καμία.

### Τύποι δεδομένων

Το runtime ανάγει κάθε αριθμητική ένδειξη σε float64 σε μονάδες μηχανικής, άρα ο δηλωμένος τύπος είναι επιλογή παρουσίασης που γίνεται στο `kindForTag`, και πρέπει να είναι τύπος στον οποίο η τιμή μπορεί πάντα να εκφραστεί:

| `dataType` του tag | Τύπος OPC UA |
|---|---|
| `bool`, `boolean`, `bit`, `coil`, `discrete` | Boolean |
| `string`, `text`, `char` | String |
| `int16` | Int16 |
| `uint16`, `word` | UInt16 |
| `int32`, `dint` | Int32 |
| `uint32`, `dword` | UInt32 |
| `uint64` | UInt64 |
| `int`, `int64` | Int64 (ο ευρύτερος προσημασμένος τύπος, ώστε τίποτα να μην ξεχειλίζει) |
| οτιδήποτε άλλο, συμπεριλαμβανομένου του `float` | Double |
| **οποιοσδήποτε ακέραιος τύπος με κλίμακα ή μετατόπιση** | **Double** |

Η τελευταία γραμμή έχει σημασία: ένας καταχωρητής `int16` με κλίμακα 0,1 διαβάζει 23,4, και το κόψιμό του σε Int16 θα έδινε στον πελάτη 23 με κατάσταση Good. Μια τιμή που δεν χωρά στον δηλωμένο τύπο της, ένα tag `int16` που παραδίδει 70000, αναφέρεται ως `BadOutOfRange` χωρίς τιμή, ποτέ τυλιγμένη ή περικομμένη σε κάτι που φαίνεται εύλογο. Ένα αριθμητικό tag του οποίου η ένδειξη περιέχει κείμενο είναι `BadTypeMismatch`.

### Τιμή, ποιότητα και χρονοσφραγίδες

Κάθε ανάγνωση (και κάθε δείγμα συνδρομής) απαντιέται από τη ζωντανή κρυφή μνήμη του runtime, την ίδια πηγή που εξυπηρετεί το `/api/values`, ποτέ από τη βάση δεδομένων. Ο κωδικός κατάστασης προκύπτει από αυτή την ένδειξη **και από την κατάσταση της σύνδεσης της συσκευής πίσω της**, επειδή η κρυφή μνήμη από μόνη της δεν αρκεί: κρατά την τελευταία ένδειξη που επέστρεψε μια συσκευή, και μια συσκευή που έχει έκτοτε φύγει από το δίκτυο έχει ακόμη μια τελευταία ένδειξη που φαίνεται απολύτως καλή.

| Σύνδεση συσκευής | Ένδειξη | Κατάσταση | Τιμή |
|---|---|---|---|
| Συνδεδεμένη, τουλάχιστον μία ερώτηση παραδόθηκε σε αυτή τη συνεδρία | καλή | **Good** | στάλθηκε |
| | αβέβαιη | Uncertain | στάλθηκε |
| | κακή ή μη αναγνωρισμένη ποιότητα | Bad | καμία |
| Συνδεδεμένη, καμία ερώτηση δεν έχει παραδοθεί ακόμη σε αυτή τη συνεδρία | οποιαδήποτε | BadWaitingForInitialData | καμία |
| Συνδεδεμένη, τίποτα στην κρυφή μνήμη | n/a | BadWaitingForInitialData | καμία |
| Υποβαθμισμένη (η συνεδρία είναι ενεργή, οι ερωτήσεις αποτυγχάνουν ή είναι μερικές) | καλή | **UncertainLastUsableValue** | στάλθηκε |
| | αβέβαιη | Uncertain | στάλθηκε |
| | κακή | Bad | καμία |
| Αποσυνδεδεμένη, σε σύνδεση, απενεργοποιημένη | οποιαδήποτε | **BadNoCommunication** | καμία |
| Δεν υπάρχει worker για τη συσκευή | οποιαδήποτε | BadOutOfService | καμία |
| Tag ή συσκευή που αφαιρέθηκε | n/a | BadNodeIdUnknown | καμία |

Το Good αναφέρεται μόνο για συνδεδεμένη συσκευή, σε ερώτηση της τρέχουσας συνεδρίας, της οποίας η ένδειξη είναι καλή. Ένα tag σε αποσυνδεδεμένη συσκευή διαβάζει Bad, όχι την τελευταία τιμή του με κατάσταση Good.

Η ηλικία σκόπιμα δεν παίζει ρόλο. Οι πηγές που οδηγούνται από συμβάντα (ένα tag MQTT/Sparkplug, μια συνδρομή OPC UA) κρατούν δικαιολογημένα μια τιμή για ώρες επειδή δεν άλλαξε τίποτα, και να την ονομάσουμε παλιά με βάση το ρολόι θα ήταν λάθος· το αν μια συσκευή εξακολουθεί να παραδίδει είναι δουλειά της σύνδεσης.

Η **χρονοσφραγίδα πηγής** είναι η δική της χρονοσφραγίδα της ένδειξης, η στιγμή που ακούστηκε για τελευταία φορά η συσκευή, και αναφέρεται ακόμη και με κατάσταση Bad. Η **χρονοσφραγίδα διακομιστή** είναι η στιγμή που απαντήθηκε η ανάγνωση. Και οι δύο είναι σε UTC.

## Συνδρομές

Οι πελάτες μπορούν να δημιουργούν συνδρομές και παρακολουθούμενα στοιχεία σε μεταβλητές tag και να λαμβάνουν ειδοποιήσεις αλλαγής δεδομένων, που είναι ο τρόπος με τον οποίο οι πελάτες SCADA χρησιμοποιούν πράγματι τα tags. Σε αυτή τη βιβλιοθήκη η παρακολούθηση γίνεται με δειγματοληψία: ο διακομιστής διαβάζει κάθε παρακολουθούμενο στοιχείο στο διάστημα δειγματοληψίας του (τουλάχιστον 100 ms, και τουλάχιστον το διάστημα ερώτησης της συσκευής) μέσω του ίδιου χειριστή που χρησιμοποιεί μια ανάγνωση, και ειδοποιεί όταν αλλάζει η τιμή ή η κατάσταση. Έτσι μια αλλαγή *ποιότητας*, μια συσκευή που πέφτει, ανακοινώνεται με τον ίδιο τρόπο όπως μια αλλαγή τιμής.

Ένα παρακολουθούμενο στοιχείο σε tag που αφαιρείται δεν μένει μετέωρο: παίρνει `BadNodeIdUnknown`.

## Τι βλέπει ένας πελάτης όταν αλλάζει η ρύθμιση

Όταν αφαιρείται ένα tag, οι αναγνώσεις και τα παρακολουθούμενα στοιχεία πάνω του παίρνουν αμέσως `BadNodeIdUnknown`, και εξαφανίζεται αμέσως από την περιήγηση της συσκευής του. Ο ίδιος ο κόμβος μένει στον πίνακα κόμβων του διακομιστή για περίπου 5 δευτερόλεπτα ακόμη, απρόσιτος, και μετά διαγράφεται. Μια συσκευή που αφαιρείται λειτουργεί με τον ίδιο τρόπο κάτω από τον φάκελο Objects.

Μια επεξεργασία δεν αφήνει ποτέ κενό. Ένα επεξεργασμένο tag ή μια συσκευή αντικαθίσταται από τη νέα της έκδοση κάτω από το ίδιο NodeId σε ένα βήμα, ώστε μια ανάγνωση ή περιήγηση εκείνη τη στιγμή να βλέπει την παλιά ή τη νέα έκδοση, ποτέ «άγνωστο». Οι συνδρομές πάνω της συνεχίζουν.

Η καθυστέρηση πριν από τη διαγραφή δεν είναι διακοσμητική. Το Browse της βιβλιοθήκης διαβάζει τη λίστα αναφορών ενός κόμβου και μετά αναζητά κάθε στόχο χωρίς να κρατά κλείδωμα ανάμεσα στα δύο, και αν ένας στόχος έχει εξαφανιστεί στο μεταξύ, αποτυγχάνει η περιήγηση του *γονέα* με `BadNodeIdUnknown`, σαν να μην υπήρχε η συσκευή ή ο φάκελος Objects. Παλιότερα διαγράφαμε τους κόμβους αμέσως, και ένας πελάτης που περιηγούνταν σε μια συσκευή ενώ αφαιρούνταν ένα tag, ή διάβαζε ένα tag ενώ επεξεργαζόταν η συσκευή του, μπορούσε να ακούσει ότι ένας απολύτως υπαρκτός κόμβος δεν υπάρχει.

## Γιατί είναι μόνο για ανάγνωση

Αυτό το βήμα δεν υλοποιεί εγγραφές και το λέει σε τρία σημεία ταυτόχρονα, ώστε καμία μεμονωμένη αλλαγή να μην μπορεί να τις προσθέσει αθόρυβα:

- κάθε δημοσιευμένος κόμβος έχει `AccessLevel = CurrentRead | HistoryRead` και δεν είναι εγκατεστημένος κανένας χειριστής εγγραφής, άρα μια εγγραφή απορρίπτεται με `BadNotWritable` και ο πελάτης μπορεί να δει πριν δοκιμάσει ότι ο κόμβος δεν είναι εγγράψιμος·
- οι δοκιμές γράφουν σε ένα tag ως viewer, operator και admin, και ελέγχουν ότι η απάντηση είναι `BadNotWritable` **και ότι ο καταχωρητής στη συσκευή πίσω από το tag δεν άλλαξε**.

Μια διαδρομή εγγραφής OPC UA θα έπρεπε να περνά από αυτή την πύλη, να μεταφέρει τον principal της στο ίχνος ελέγχου και να σέβεται τον γενικό διακόπτη. Αυτό είναι αλλαγή με τη δική της αναθεώρηση, όχι κάτι που θα έρθει ως υποπροϊόν της δημοσίευσης tags, και σκόπιμα δεν υπάρχει σε αυτή την έκδοση ρύθμιση που να την ενεργοποιεί.

## Ιστορικό

Κάθε κόμβος tag ιστορικοποιείται και φέρει το επίπεδο πρόσβασης HistoryRead. Ο διακομιστής απαντά στην υπηρεσία HistoryRead του OPC UA από το ίδιο το ιστορικό του HotLoop, τις ίδιες αναγνώσεις που εξυπηρετεί το `/api/history`, ώστε ένας πελάτης στην άλλη άκρη μιας σύνδεσης OPC UA να διαβάζει ό,τι κράτησε το Gateway χωρίς δεύτερη βάση δεδομένων. Ένας χρήστης χρειάζεται ό,τι χρειάζεται μια ανάγνωση τιμής (`tags.read` και `values.read`), ελεγμένο όπως ελέγχεται μια ανάγνωση τιμής, για τον χρήστη της συνεδρίας, και όχι μόνο μία φορά κατά τη σύνδεση.

- **Raw** (`ReadRawModifiedDetails`): οι αναγνώσεις σε ένα παράθυρο, καθεμία με τη δική της ποιότητα ως κατάσταση και τη δική της χρονοσφραγίδα. Μια αρχή πριν από το τέλος διαβάζει προς τα εμπρός και μια αρχή μετά το τέλος διαβάζει προς τα πίσω, με τις πιο πρόσφατες πρώτες. Η αρχή περιλαμβάνεται και το τέλος αφήνεται έξω (OPC UA 10000-11, ενότητα 4.6), εκτός αν ο πελάτης ζητήσει όρια, οπότε προστίθενται η ανάγνωση στην αρχή ή πριν από αυτήν και η πρώτη ανάγνωση εκτός παραθύρου στο τέλος. Το `NumValuesPerNode` είναι πόσες επιστρέφει μία κλήση για έναν κόμβο· περισσότερες από αυτό, ή περισσότερες από 10.000, έρχονται σε σελίδες, καθεμία με σημείο συνέχισης που ισχύει πέντε λεπτά και για μία χρήση (το πολύ 1.000 κρατούνται ταυτόχρονα). Ένα παράθυρο χωρίς τίποτα είναι `Good_NoData`. Το τροποποιημένο ιστορικό απορρίπτεται (`BadHistoryOperationUnsupported`): εδώ τίποτα δεν τροποποιείται ούτε διαγράφεται ποτέ.
- **Processed** (`ReadProcessedDetails`): Average, Minimum, Maximum, Count, Start, End και Total, σε διαστήματα `ProcessingInterval` από την ώρα έναρξης, με τον κανόνα ποιότητας (README, «The quality rule»): μετρούν μόνο οι καλές αναγνώσεις με πεπερασμένο αριθμό. Ένα διάστημα χωρίς καμία είναι `Good_NoData` (το Count λέει 0), και ένα με παραλειμμένες αναγνώσεις διαβάζει `Uncertain_DataSubNormal`, ώστε ο αριθμός να μην είναι ποτέ καλύτερος από ό,τι περιείχε. Άλλο συγκεντρωτικό απορρίπτεται για αυτόν τον κόμβο (`BadAggregateNotSupported`), ένα tag κειμένου δεν έχει κανένα, και ένα παράθυρο με περισσότερα από 10.000 διαστήματα ή 500.000 αναγνώσεις απορρίπτεται (`BadTooManyOperations`) αντί να κοπεί. Απαντιέται μόνο ένα παράθυρο προς τα εμπρός με και τα δύο άκρα.
- **At time** (`ReadAtTimeDetails`): τι είχε το tag σε κάθε χρονική στιγμή, δηλαδή η τελευταία του ανάγνωση εκείνη τη στιγμή ή πριν, με χρονοσφραγίδα τη στιγμή που ζητήθηκε. Δεν παρεμβάλλει ποτέ, επειδή μια ανάγνωση είναι τιμή που πήρε κάποιος· μια στιγμή πριν από την πρώτη ανάγνωση του tag είναι `Bad_NoData`.
- Τα **συμβάντα** δεν εξυπηρετούνται: `BadHistoryOperationUnsupported`. Μια συσκευή ή οποιοδήποτε άλλο αντικείμενο δεν έχει επίσης ιστορικό, και ένας κόμβος ιδιότητας (`EngineeringUnits`, `EURange`) δεν φέρει HistoryRead.

Το historian κρατά μια ανάγνωση όταν ξεπερνά τη νεκρή ζώνη, όχι σε κάθε ερώτηση, άρα ένα ήρεμο tag έχει λίγες γραμμές: διαβάστε At time, ή ένα παράθυρο Processed γύρω από την τελευταία ανάγνωση ενός tag, όταν χρειάζεστε ό,τι είχε και όχι μόνο πότε άλλαξε. Το `HistoryServerCapabilities` λέει ότι το ιστορικό μπορεί να διαβαστεί και ότι μια κλήση επιστρέφει το πολύ 10.000 τιμές.

## Υγεία του μηχανήματος, για τον πίνακα ελέγχου EmberNet

Ο Διαχειριστής εργασιών του πίνακα ελέγχου διαβάζει CPU, μνήμη, δίσκο και jitter πραγματικού χρόνου ενός μηχανήματος από το ίδιο το μηχάνημα: το HotLoop τα δημοσιεύει ως συσκευή και ο διακομιστής εξυπηρετεί το ιστορικό τους ([Ιστορικό](#ιστορικό)), ώστε ο πίνακας ελέγχου να μη διαβάζει ποτέ τη δική του βάση δεδομένων γι' αυτά. Τι έχει χτιστεί και πώς ενεργοποιείται:

* **Η συσκευή.** Με ορισμένο το `HOTLOOP_BOX_HEALTH_NODE` (το chart το ορίζει στο όνομα του κόμβου Kubernetes) το HotLoop δημιουργεί μια συσκευή με αναγνωριστικό ακριβώς αυτό το όνομα, με το πρωτόκολλο `boxhealth` ([Πρωτόκολλα και drivers](/el/iot/protocols/#υγεία-του-κουτιού)). Τα tags της είναι `cpu_util_pct`, `mem_util_pct`, `disk_util_pct` (ο δικός του δίσκος του μηχανήματος), `data_util_pct` (ο τόμος όπου το HotLoop κρατά τα δεδομένα του) και, μόνο όταν το `HOTLOOP_BOX_HEALTH_JITTER_FILE` δείχνει το αρχείο JSON που γράφει ένας πράκτορας πραγματικού χρόνου, `rtos_jitter_core1_us`, `rtos_jitter_core2_us` και `rtos_jitter_core3_us`. Τα αναγνωριστικά κόμβων OPC UA τους βρίσκονται στον χώρο ονομάτων `urn:hotloop:ua:gateway` με αναγνωριστικό συμβολοσειράς `<device id>/<tag>`.
* **Οι αριθμοί του μηχανήματος.** Το chart προσαρτά τη ρίζα του host στο `/host` και το `/proc` του στο `/host/proc`, και τα δύο μόνο για ανάγνωση, και ορίζει το όνομα του κόμβου, **από προεπιλογή** (`opcuaServer.dashboard.boxHealth.enabled: true`), ώστε ο Διαχειριστής εργασιών του πίνακα ελέγχου να δουλεύει μόλις εγκατασταθεί το HotLoop. Διαβάζονται μόνο ένα statfs του `/host` και οι μετρητές CPU και μνήμης, και δεν προστίθεται κανένα προνόμιο. Ένα σύμπλεγμα που επιβάλλει το περιορισμένο προφίλ Pod Security αρνείται ένα hostPath: εκεί ορίστε `enabled: false` (καμία συσκευή, καμία προσάρτηση) ή `hostMount: false` (η συσκευή, αλλά ο δίσκος και η CPU του μηχανήματος διαβάζουν Bad και λένε τι να προσαρτηθεί). Η συσκευή δεν χρειάζεται τον διακομιστή OPC UA.
* **Μια σύνδεση που μπορεί να διαβάζει και τίποτα άλλο.** Το chart δημιουργεί τον χρήστη `embernet-dashboard-read` με ακριβώς `tags.read` και `values.read` (ρητή λίστα δικαιωμάτων, ποτέ ρόλος) στην πρώτη εγκατάσταση, και κρατά τον παραγόμενο κωδικό του στο Secret `<release>-opcua-dashboard` (κλειδιά `username`, `password` και `password-hash`). Μια αναβάθμιση δεν τον αλλάζει ποτέ. Ένας λογαριασμός που υπάρχει δεν αλλάζει ποτέ από επανεκκίνηση.
* **Το πιστοποιητικό του πίνακα ελέγχου.** Ο πίνακας ελέγχου δημιουργεί το Secret `<release>-opcua-trust`, ένα κλειδί ανά πιστοποιητικό με όνομα `<sha1 thumbprint>.crt`. Το chart το προσαρτά, προαιρετικά, στο `/etc/hotloop/opcua-trust`, και ο διακομιστής κρατά αυτά τα αρχεία στο `trusted/` (`HOTLOOP_OPCUA_SERVER_TRUST_DIR`): κατά την εκκίνηση και κάθε 30 δευτερόλεπτα, ένα νέο αρχείο προστίθεται, ένα αλλαγμένο ξαναγράφεται και ένα που φεύγει από το Secret αφαιρείται ξανά. Ένα αρχείο που έβαλε ένας χειριστής στο `trusted/` δεν αγγίζεται ποτέ και υπερισχύει ενός κλειδιού Secret με το ίδιο όνομα.
* **Η θύρα.** Το Service της ίδιας της έκδοσης (αυτό που ανακαλύπτει ο πίνακας ελέγχου) απαριθμεί τη θύρα OPC UA 4840 όταν ο διακομιστής είναι ενεργός, δίπλα στο δικό του Service του διακομιστή OPC UA.

Ο διακομιστής μένει όπως ήταν: Basic256Sha256 SignAndEncrypt, χωρίς ανώνυμες συνεδρίες, χωρίς εμπιστοσύνη σε όλα.

## Μοντέλο ασφάλειας

### Μεταφορά

Τα ασφαλή κανάλια χρησιμοποιούν τις πολιτικές της βιβλιοθήκης σε Sign και SignAndEncrypt. **Η `Basic256Sha256` προσφέρεται και στους δύο τρόπους λειτουργίας**, και αυτή πρέπει να επιλέγει ένας πελάτης.

**Η πολιτική ασφάλειας None είναι ρητή επιλογή** (`HOTLOOP_OPCUA_SERVER_ALLOW_INSECURE`, false από προεπιλογή), με προειδοποίηση κατά την εκκίνηση όταν είναι ενεργή. Όταν είναι απενεργοποιημένη, δεν διαφημίζεται κανένα endpoint None, και ένας πελάτης που ανοίγει παρ' όλα αυτά κανάλι None μπορεί να κάνει μόνο ανακάλυψη: κάθε άλλη υπηρεσία απορρίπτεται. Ακόμη και ενεργή, το όνομα χρήστη και ο κωδικός πρόσβασης ταξιδεύουν μέσα σε κρυπτογραφημένο token (η πολιτική του token είναι `Basic256Sha256`, ποτέ None), αν και κάθε τιμή που διαβάζει ο πελάτης στη συνέχεια είναι απροστάτευτη.

**Οι παρωχημένες πολιτικές είναι απενεργοποιημένες από προεπιλογή.** Το OPC Foundation έχει κρίνει παρωχημένες τις `Basic128Rsa15` (RSA με συμπλήρωση PKCS#1 v1.5) και `Basic256` (SHA-1). Σε προηγούμενες εκδόσεις και οι δύο προσφέρονταν σε κάθε λίστα endpoints χωρίς τρόπο αφαίρεσης. Το `HOTLOOP_OPCUA_SERVER_ALLOW_DEPRECATED_POLICIES` (chart: `opcuaServer.allowDeprecatedPolicies`, `false` από προεπιλογή) αποφασίζει:

- **Απενεργοποιημένο (η προεπιλογή, σε νέες εγκαταστάσεις και αναβαθμίσεις).** Καμία από τις δύο πολιτικές δεν υπάρχει σε κανένα endpoint που ανακοινώνεται σε πελάτη, και ένας πελάτης που ανοίγει παρ' όλα αυτά ασφαλές κανάλι με μία από αυτές απορρίπτεται κατά το άνοιγμα του καναλιού, πριν από οποιαδήποτε συνεδρία ή σύνδεση. Οι πελάτες με `Basic256Sha256`, `Aes128_Sha256_RsaOaep` ή `Aes256_Sha256_RsaPss` δεν επηρεάζονται.
- **Ενεργοποιημένο.** Και οι δύο προσφέρονται ξανά σε Sign και SignAndEncrypt, για έναν παλιό πελάτη που δεν μιλά τίποτα νεότερο, με προειδοποίηση κατά την εκκίνηση. Ενεργοποιήστε το μόνο μέχρι να ενημερωθεί ο πελάτης αυτός.

Ένας πελάτης που σταμάτησε να συνδέεται μετά την αναβάθμιση και χρησιμοποιεί μία από αυτές τις δύο πολιτικές δείχνει ότι το κανάλι απορρίπτεται· ορίστε τη ρύθμιση, ή μεταφέρετε τον πελάτη στην `Basic256Sha256`.

### Πιστοποιητικό διακομιστή

Αν έχουν οριστεί τα `HOTLOOP_OPCUA_SERVER_CERT_FILE` και `_KEY_FILE`, αυτό το ζεύγος RSA χρησιμοποιείται ως έχει. Διαφορετικά, **δημιουργείται και αποθηκεύεται κατά την πρώτη εκκίνηση ένα αυτο-υπογεγραμμένο πιστοποιητικό στιγμιότυπου εφαρμογής** στο `HOTLOOP_OPCUA_SERVER_PKI_DIR` (`own/cert.pem`, `own/key.pem`, κλειδί με λειτουργία 0600), ώστε η επόμενη εκκίνηση να παρουσιάσει το ίδιο πιστοποιητικό και ένας πελάτης στον οποίο είπαν μία φορά να το εμπιστευτεί να μην ερωτηθεί ξανά. Σε κάθε εκκίνηση καταγράφεται προειδοποίηση όσο το πιστοποιητικό είναι αυτο-υπογεγραμμένο, με το αποτύπωμα SHA-1, τη μορφή που δείχνουν τα εργαλεία OPC UA, ώστε ο χειριστής να το συγκρίνει με ό,τι εμφανίζει ο πελάτης.

Το πιστοποιητικό λέει ό,τι ελέγχουν οι πελάτες OPC UA, κάτι που ένα συνηθισμένο πιστοποιητικό TLS δεν κάνει: το **URI εφαρμογής** (`HOTLOOP_OPCUA_SERVER_APPLICATION_URI`, από προεπιλογή `urn:hotloop:gateway`, συν `:<siteId>` όταν έχει ρυθμιστεί) στα εναλλακτικά ονόματα υποκειμένου τύπου URI, τα ονόματα host και οι διευθύνσεις που χρησιμοποιούν οι πελάτες (ο host του endpoint, `HOTLOOP_OPCUA_SERVER_CERT_HOSTS`, `localhost`, loopback, το όνομα host αυτού του μηχανήματος) ως DNS και IP SAN, και οι χρήσεις κλειδιού που απαριθμεί το Μέρος 6 για ένα στιγμιότυπο εφαρμογής. RSA-2048, πέντε χρόνια.

Ένα αποθηκευμένο πιστοποιητικό αντικαθίσταται, με προειδοποίηση ότι οι πελάτες πρέπει να εμπιστευτούν το νέο, μόνο αν δεν μπορεί πια να κάνει τη δουλειά του: λιγότερες από 30 ημέρες ισχύος, URI εφαρμογής που δεν ταιριάζει πια με τη ρύθμιση, ρυθμισμένος host που δεν καλύπτει, ή κλειδί που δεν διαβάζεται.

**Το όνομα host του μηχανήματος δεν είναι ρυθμισμένος host.** Μπαίνει σε ένα νέο πιστοποιητικό, αλλά ένα αποθηκευμένο πιστοποιητικό διατηρείται όταν αλλάζει το όνομα host. Σε ένα container το όνομα host είναι το αναγνωριστικό του container, και στο Kubernetes είναι το όνομα του pod, άρα αλλάζει σε κάθε νέα ανάπτυξη. Μέχρι να διορθωθεί αυτό, μετρούσε, και κάθε αναβάθμιση ενός Gateway σε container έφτιαχνε νέο πιστοποιητικό: το Ignition, στο οποίο είχαν πει να εμπιστευτεί το παλιό, απέρριπτε τον διακομιστή με `Bad_SecurityChecksFailed` μέχρι να το εμπιστευτεί ξανά κάποιος, σε κάθε πελάτη, μετά από κάθε ανάπτυξη. Οι πελάτες φτάνουν στον διακομιστή μέσω `HOTLOOP_OPCUA_SERVER_ENDPOINT_HOST` και `_CERT_HOSTS`· ορίστε τα, και το πιστοποιητικό ζει μέχρι να πλησιάσει η λήξη του. (Ένα Gateway χωρίς ορισμένο host endpoint χρησιμοποιεί το όνομα host του μηχανήματος ως host endpoint, και αυτό μετρά, αφού είναι ό,τι λέγεται στους πελάτες. Άλλος ένας λόγος να το ορίσετε.)

**Ένα κλειδί μπορεί να είναι άχρηστο, και ο διακομιστής το απορρίπτει.** Περίπου ένα στα είκοσι κλειδιά RSA δεν μπορεί να μεταφέρει κρυπτογραφημένη σύνδεση OPC UA, και κάθε κρυπτογραφημένη σύνδεση με αυτό το κλειδί αποτυγχάνει τότε, κάθε φορά, με τον πελάτη να βλέπει μόνο «το ασφαλές κανάλι έκλεισε». Οι ανώνυμες και οι μη κρυπτογραφημένες συνεδρίες δεν επηρεάζονται, και αυτό κάνει εύκολη τη λανθασμένη διάγνωση. Ένα παραγόμενο κλειδί τραβιέται ξανά μέχρι να μην είναι ένα από αυτά· ένα κλειδί που δίνει ο χειριστής και είναι τέτοιο απορρίπτεται κατά την εκκίνηση με σφάλμα που λέει γιατί.

### Πιστοποιητικά εφαρμογής των πελατών

Το OPC UA ταυτοποιεί την εφαρμογή όσο και τον χρήστη. Ο διακομιστής κρατά λίστα εμπιστοσύνης στο `<PKI_DIR>/trusted/`: ένας πελάτης του οποίου το πιστοποιητικό δεν είναι εκεί απορρίπτεται στο ασφαλές κανάλι, και το πιστοποιητικό του γράφεται στο `<PKI_DIR>/rejected/`. **Για να εγκρίνετε έναν πελάτη, μετακινήστε το πιστοποιητικό του από το `rejected/` στο `trusted/`**, χωρίς επανεκκίνηση· ο κατάλογος διαβάζεται σε κάθε σύνδεση. Τα `<PKI_DIR>/issuers/` και `<PKI_DIR>/crl` περνούν ως έχουν για πιστοποιητικά πελατών που εκδίδονται από CA.

Το `HOTLOOP_OPCUA_SERVER_TRUST_ALL_CLIENT_CERTS` (false από προεπιλογή, με προειδοποίηση κατά την εκκίνηση) παραλείπει αυτό το βήμα. Αφαιρεί μόνο την ταυτοποίηση της εφαρμογής: ο χρήστης πρέπει και πάλι να ταυτοποιηθεί με όνομα χρήστη και κωδικό του HotLoop.

### Ποιος μπορεί να συνδεθεί

**Όνομα χρήστη και κωδικός πρόσβασης, έναντι των δικών χρηστών του HotLoop.** Υπάρχει μία βάση χρηστών, όχι δεύτερο αποθετήριο διαπιστευτηρίων: ο ταυτοποιητής αναζητά τον χρήστη με το ίδιο `store.User` που χρησιμοποιεί η σύνδεση HTTP, συγκρίνει με τα ίδια bcrypt hashes (`auth.CheckPassword`), κανονικοποιεί το όνομα χρήστη με τον ίδιο τρόπο (πεζά, χωρίς κενά στα άκρα), εκτελεί μία σύγκριση bcrypt είτε υπάρχει ο χρήστης είτε όχι ώστε ο χρόνος απόκρισης να μην αποκαλύπτει ποια ονόματα είναι αληθινά, και απορρίπτει απενεργοποιημένο λογαριασμό. Άγνωστος χρήστης, λάθος κωδικός, απενεργοποιημένος χρήστης και χρήστης χωρίς το δικαίωμα παίρνουν όλοι την ίδια απάντηση, `BadUserAccessDenied`.

**Ένας χρήστης μπορεί να διαβάζει tags μόνο αν ο ρόλος του δίνει `tags.read` και `values.read`**, το ίδιο ζεύγος με το οποίο το HTTP API προστατεύει τα `/api/tags` και `/api/values`, επιλυμένο μέσω των ίδιων `auth.Permissions` και `auth.Allows`, ώστε ένας ενσωματωμένος ρόλος και μια ρητή λίστα δικαιωμάτων να συμπεριφέρονται ακριβώς όπως εκεί. Απαιτούνται και τα δύο επειδή ένας πελάτης OPC UA περιηγείται στη λίστα tags και διαβάζει τιμές μέσω μίας σύνδεσης, και ένας χρήστης με μόνο το ένα θα έπαιρνε το άλλο δωρεάν. Κάθε ενσωματωμένος ρόλος που έχει `values.read` έχει και `tags.read`· αυτό αφορά μόνο χρήστη με ρητή λίστα δικαιωμάτων.

**Τα δικαιώματα ελέγχονται κατά τη χρήση, όχι μόνο κατά τη σύνδεση.** Η βιβλιοθήκη ζητά τους ρόλους μιας συνεδρίας σε κάθε περιήγηση, ανάγνωση και δείγμα συνδρομής· απαντιούνται από βραχύβια κρυφή μνήμη (10 s) της βάσης χρηστών. Ένας χρήστης που απενεργοποιείται, διαγράφεται ή χάνει δικαιώματα χάνει την πρόσβαση σε μια ζωντανή συνεδρία μέσα σε αυτό το διάστημα, με τα παρακολουθούμενα στοιχεία του να γίνονται Bad, αντί όταν ο πελάτης του επανασυνδεθεί. Μια αναζήτηση που αποτυγχάνει μετρά ως «όχι».

**Οι ανώνυμες συνεδρίες είναι απενεργοποιημένες** (`HOTLOOP_OPCUA_SERVER_ALLOW_ANONYMOUS`) και δεν προσφέρεται ανώνυμο token εκτός αν επιλεγεί, με προειδοποίηση κατά την εκκίνηση. Τα token ταυτότητας χρήστη X.509 είναι επίσης απενεργοποιημένα, και προσφέρονται όταν οριστεί το `HOTLOOP_OPCUA_SERVER_ALLOW_X509` (δείτε [Πιστοποιητικά χρήστη X.509](#πιστοποιητικά-χρήστη-x509)). Αν η δική του ταυτοποίηση του HotLoop είναι απενεργοποιημένη (`HOTLOOP_AUTH_INSECURE`), δεν υπάρχουν χρήστες για σύνδεση, και ο διακομιστής αρνείται να ξεκινήσει εκτός αν έχει επιλεγεί ανώνυμη πρόσβαση.

Μια επιτυχής σύνδεση καταγράφεται στο αρχείο καταγραφής του συστήματος όπως μια σύνδεση HTTP. Οι αποτυχημένες συνδέσεις καταγράφονται μόνο στο αρχείο καταγραφής της διεργασίας, με τον λόγο, ώστε ένας μη ταυτοποιημένος καλών να μη μπορεί να γεμίσει το ίχνος ελέγχου. Το πολύ τέσσερις έλεγχοι κωδικού τρέχουν ταυτόχρονα, αφού καθένας είναι σκόπιμα αργή σύγκριση bcrypt και το OPC UA δεν έχει ισοδύναμο του περιοριστή ρυθμού που υπάρχει μπροστά από το HTTP· πέρα από αυτό δεν υπάρχει κλείδωμα ή περιορισμός ρυθμού, όπως στη σύνδεση HTTP.

Η βιβλιοθήκη κρατά την αποκρυπτογραφημένη ταυτότητα χρήστη, κωδικό συμπεριλαμβανομένου, στο αντικείμενο της συνεδρίας όσο ζει η συνεδρία. Είναι μόνο στη μνήμη και δεν καταγράφεται ποτέ, αλλά ένα heap dump ενός Gateway που τρέχει θα περιείχε τους κωδικούς των χρηστών που είναι συνδεδεμένοι εκείνη τη στιγμή.

**Συνδέονται κωδικοί οποιουδήποτε μήκους δέχεται το HotLoop, έως 72 byte (το όριο του bcrypt).** Σε προηγούμενες εκδόσεις ένας κωδικός 65 έως 72 byte μπορούσε να συνδεθεί στη διεπαφή web και όχι εδώ (`BadIdentityTokenRejected`). Το μήκος μετρούσε τον κωδικό συν το nonce 32 byte του διακομιστή, άρα ο κωδικός έφτανε το πολύ τα 64 byte. Τίποτα στο RSA ή στην προδιαγραφή δεν το ζητά: το token κρυπτογραφείται σε όσα blocks χρειάζεται και ο αποκωδικοποιητής τα διαβάζει ήδη όλα. Ο έλεγχος τώρα είναι ότι το μήκος είναι τουλάχιστον 32 και όχι μεγαλύτερο από τα byte που αποκρυπτογραφήθηκαν πραγματικά, που είναι αυτό που ο έλεγχος όφειλε να εγγυάται, αφού καθορίζει το μέγεθος του buffer που δημιουργείται στη συνέχεια. Ένα μήκος που δηλώνει περισσότερα απ' όσα έφτασαν απορρίπτεται ακόμη, ώστε ένας πελάτης να μη μπορεί να κάνει τον διακομιστή να δεσμεύσει ό,τι δεν έστειλε. Ο upstream κλάδος `main` (έλεγχος 2026-11-16) έχει ακόμη το όριο· η αλλαγή προσφέρεται upstream ως pull request από το HotLoop-io/opcua.

### Πιστοποιητικά χρήστη X.509

Ένας πελάτης μπορεί να συνδεθεί με πιστοποιητικό αντί για κωδικό. Απενεργοποιημένο από προεπιλογή: ορίστε `HOTLOOP_OPCUA_SERVER_ALLOW_X509=true` (chart `opcuaServer.allowX509`), και ο διακομιστής προσφέρει το token χρήστη Certificate στα ασφαλή endpoints του και το δηλώνει κατά την εκκίνηση. Χωρίς αυτό κανένα endpoint δεν το προσφέρει και μια σύνδεση με πιστοποιητικό απορρίπτεται.

**Πώς αντιστοιχίζεται ένα πιστοποιητικό σε χρήστη.** Ένας admin επισυνάπτει το πιστοποιητικό σε έναν χρήστη HotLoop: Ρυθμίσεις, Πιστοποιητικά OPC UA, Επισύναψη πιστοποιητικού (ή μέσω του API, `POST /api/users/{username}/certificates`, ή του εργαλείου MCP `add_user_certificate`). Το μητρώο κρατά το δημόσιο πιστοποιητικό, το αποτύπωμα SHA-256, ποιος το επισύναψε και πότε, αν έχει ανακληθεί, και πότε συνδέθηκε τελευταία φορά. Ένας πελάτης που το παρουσιάζει και αποδεικνύει ότι κατέχει το ιδιωτικό κλειδί συνδέεται **ως αυτός ο χρήστης**. Τίποτε άλλο δεν ρυθμίζεται και τίποτα στο ίδιο το πιστοποιητικό δεν εμπιστεύεται: το κοινό όνομα δεν εξετάζεται, δεν υπάρχει CA προς λειτουργία, και ένα πιστοποιητικό που δεν επισύναψε κανείς δεν κάνει τίποτα.

**Τι μεταφέρει το token.** Ένας πελάτης μπορεί να στείλει το πιστοποιητικό του ακολουθούμενο από αυτά που το εξέδωσαν· το πρώτο είναι το πιστοποιητικό που επισυνάφθηκε, και τα υπόλοιπα αγνοούνται.

**Απόδειξη του κλειδιού.** Η βιβλιοθήκη ελέγχει την υπογραφή του token πάνω στο πιστοποιητικό του διακομιστή και το nonce της συνεδρίας, που μόνο ο κάτοχος του ιδιωτικού κλειδιού μπορεί να φτιάξει· ένα πιστοποιητικό που παρουσιάζεται με υπογραφή από άλλο κλειδί απορρίπτεται.

**Τι μπορεί να κάνει.** Ακριβώς ό,τι μπορεί να κάνει ο χρήστης. Η σύνδεση απαιτεί ο χρήστης να είναι ενεργοποιημένος και να έχει `tags.read` και `values.read`, το ίδιο ζεύγος με τη σύνδεση με κωδικό, και η συνεδρία ελέγχεται κάθε 10 δευτερόλεπτα όπως μια τέτοια: ένας χρήστης που απενεργοποιείται ή χάνει το δικαίωμα χάνει μια ζωντανή συνεδρία με πιστοποιητικό μέσα σε αυτό το διάστημα. Είναι μόνο για ανάγνωση όπως κάθε συνεδρία εδώ· μια συνεδρία με πιστοποιητικό δεν μπορεί να γράψει, όποιος κι αν είναι ο ρόλος του χρήστη.

**Απορρίπτεται, με τον λόγο στο αρχείο καταγραφής.** Ένα πιστοποιητικό που δεν είναι καταχωρισμένο, έχει ανακληθεί, έχει λήξει, δεν ισχύει ακόμη, ή του οποίου ο χρήστης έχει φύγει, είναι απενεργοποιημένος ή δεν έχει το δικαίωμα, παίρνει `BadUserAccessDenied`, την ίδια απάντηση για όλα, ώστε ο πελάτης να μη μαθαίνει τίποτα για το ποια περίπτωση ισχύει. Ο λόγος πηγαίνει στο αρχείο καταγραφής της διεργασίας και στο ίχνος ελέγχου.

**Ανάκληση.** Ανακαλέστε το στην ίδια οθόνη (ή με `POST .../{thumbprint}/revoke`). Σταματά να συνδέεται αμέσως και μια συνεδρία που άνοιξε με αυτό τελειώνει μέσα σε 10 δευτερόλεπτα. Ένα ανακληθέν πιστοποιητικό μένει στη λίστα, με το ποιος το ανακάλεσε και πότε, ώστε μια απορριφθείσα σύνδεση να λέει «ανακληθέν» και όχι «άγνωστο»· διαγράψτε το για να το ξεχάσετε. Τα αντίγραφα ασφαλείας μεταφέρουν το μητρώο, μαζί με τις ανακλήσεις.

**Έλεγχος.** Κάθε σύνδεση με πιστοποιητικό είναι εγγραφή στο ημερολόγιο (κατηγορία auth) που κατονομάζει τον χρήστη, το αποτύπωμα και το υποκείμενο του πιστοποιητικού, και την εφαρμογή πελάτη. Κάθε άρνηση είναι επίσης εγγραφή, με τον λόγο. Ένας πελάτης που επαναλαμβάνει την ίδια άρνηση γράφει μία εγγραφή το λεπτό για αυτό το πιστοποιητικό και τον λόγο, όχι μία ανά προσπάθεια· κάθε άρνηση παραμένει στο αρχείο καταγραφής της διεργασίας. Η επισύναψη, η ανάκληση και η διαγραφή ενός πιστοποιητικού είναι εγγραφές με το ποιος το έκανε. Το ιδιωτικό κλειδί δεν υπάρχει ποτέ σε καμία, και το HotLoop δεν έχει ποτέ κανένα: στέλνονται ή αποθηκεύονται μόνο δημόσια πιστοποιητικά.

**Όχι η λίστα εμπιστοσύνης εφαρμογών.** Ένα πιστοποιητικό εφαρμογής πελάτη στο `<PKI_DIR>/trusted/` επιτρέπει στον πελάτη να ανοίξει ασφαλές κανάλι· δεν είναι σύνδεση. Ένα πιστοποιητικό χρήστη είναι άλλο αντικείμενο: ενός ανθρώπου, επισυναπτόμενο σε χρήστη. Ένα πιστοποιητικό μπορεί να εξυπηρετεί και τα δύο από την πλευρά του πελάτη, αλλά ο διακομιστής τα αντιμετωπίζει ως δύο πράξεις.

**Ο δικός πελάτης του HotLoop** συνδέεται επίσης με αυτόν τον τρόπο: δείτε τα `userCertificate` και `userPrivateKey` στο [Πρωτόκολλα και drivers](/el/iot/protocols/#opc-ua).

Δεν έχει χτιστεί: μια αρχή πιστοποίησης που εμπιστευόμαστε να εγγυάται για πιστοποιητικά πελατών και ένας κανόνας ονομάτων που να τα αντιστοιχίζει σε χρήστες. Το μητρώο καλύπτει ένα εργοστάσιο που επισυνάπτει τα πιστοποιητικά πελατών του ένα προς ένα· μια CA θα ήταν προσθήκη σε αυτό, όχι αντικατάσταση.

### Τα διαγνωστικά του διακομιστή αφαιρούνται

Οι κόμβοι διαγνωστικών ανά συνεδρία της βιβλιοθήκης θα επέτρεπαν σε οποιονδήποτε συνδεδεμένο χρήστη να περιηγηθεί στο όνομα χρήστη και τη διεύθυνση πελάτη κάθε άλλης συνεδρίας, γι' αυτό είναι απενεργοποιημένοι, και το αντικείμενο `Server/ServerDiagnostics` αφαιρείται από τον χώρο διευθύνσεων (η βιβλιοθήκη γράφει επίσης τους μετρητές της χωρίς κλείδωμα).

## Αλλαγές του χώρου διευθύνσεων κατά την εκτέλεση

Οι συσκευές και τα tags προστίθενται, επεξεργάζονται και αφαιρούνται ενώ το Gateway τρέχει, και ο χώρος διευθύνσεων ακολουθεί χωρίς επανεκκίνηση. **Μηχανισμός: μια επανάκληση του runtime, συν ένας χρονιστής ως δίχτυ ασφαλείας.**

- Το `runtime.Manager.OnReload` καλεί πίσω μετά από κάθε επιτυχές `Reload`. Κάθε αλλαγή συσκευής και tag που κάνει το API τελειώνει σε `Reload`, άρα μια αλλαγή από τη διεπαφή ή το API δημοσιεύεται σε λίγες στιγμές. Η επανάκληση απλώς ειδοποιεί μια goroutine συμφωνίας· δεν κάνει ποτέ η ίδια τη δουλειά, ώστε μια αργή συμφωνία να μη μπορεί να μπλοκάρει το αίτημα API που την ενεργοποίησε.
- Μια περιοδική συμφωνία (`HOTLOOP_OPCUA_SERVER_RECONCILE_INTERVAL`, 30 s από προεπιλογή) πιάνει ό,τι αλλάζει τη ρύθμιση χωρίς `Reload`.

Και οι δύο τρέχουν την ίδια ιδεοδύναμη σύγκριση με τις ενεργοποιημένες συσκευές και tags στη βάση δεδομένων. Αγγίζει μόνο ό,τι διαφέρει: ένα επεξεργασμένο tag αντικαθίσταται, ένα αφαιρεμένο διαγράφεται, και όλα τα υπόλοιπα, συμπεριλαμβανομένων των παρακολουθούμενων στοιχείων που κρατούν οι πελάτες πάνω του, μένουν ακριβώς όπως ήταν. Οι κόμβοι μιας νέας συσκευής μπαίνουν στον χώρο με μία κλήση, άρα ένας πελάτης που περιηγείται στη μέση μιας συμφωνίας βλέπει μια συσκευή με όλα τα tags της ή καμία.

Προτιμήθηκε η επανάκληση από την ερώτηση μόνη της επειδή το runtime έχει ήδη το καθαρό σήμα (`Reload`) και κάνει μια αλλαγή ορατή σε χιλιοστά του δευτερολέπτου αντί για έως ένα ολόκληρο διάστημα· ο χρονιστής μένει επειδή ο χώρος διευθύνσεων δεν πρέπει να εξαρτάται από το αν κάθε μελλοντικός συντάκτης ρύθμισης θυμάται να κάνει επαναφόρτωση.

## Σύνδεση ενός πελάτη

Το endpoint είναι `opc.tcp://<HOTLOOP_OPCUA_SERVER_ENDPOINT_HOST>:<port>`. Σε σύμπλεγμα το chart ορίζει από προεπιλογή ως host το όνομα DNS του Service της έκδοσης· εκτός συμπλέγματος, ορίστε το στο όνομα ή τη διεύθυνση που θα χρησιμοποιούν πραγματικά οι πελάτες (διεύθυνση LoadBalancer, εγγραφή DNS): διαφημίζεται σε κάθε URL endpoint και γράφεται στο παραγόμενο πιστοποιητικό. **Δεν** είναι το σημείο όπου δεσμεύεται ο διακομιστής: η βιβλιοθήκη ακούει σε όλες τις διεπαφές και παίρνει μόνο θύρα.

Με το UaExpert ή οποιονδήποτε άλλο πελάτη:

1. Προσθέστε τον διακομιστή με αυτό το URL και επιλέξτε `Basic256Sha256` / `Sign & Encrypt`.
2. Επιλέξτε *Username* και συνδεθείτε με χρήστη HotLoop που έχει `tags.read` και `values.read`· ή, με ενεργό το `HOTLOOP_OPCUA_SERVER_ALLOW_X509`, επιλέξτε *Certificate* και δώστε το πιστοποιητικό χρήστη και το κλειδί που επισύναψε ένας admin σε έναν χρήστη.
3. Η πρώτη σύνδεση απορρίπτεται επειδή ο διακομιστής δεν εμπιστεύεται ακόμη το πιστοποιητικό του πελάτη. Βρείτε το στο `<PKI_DIR>/rejected/` (στον τόμο PKI σε σύμπλεγμα), μετακινήστε το στο `trusted/` και συνδεθείτε ξανά.
4. Την πρώτη φορά ο πελάτης ρωτά αν θα εμπιστευτεί το πιστοποιητικό του διακομιστή· συγκρίνετε το αποτύπωμα με αυτό στο αρχείο καταγραφής εκκίνησης.
5. Περιηγηθείτε στο *Objects* → τη συσκευή → τα tags της, και σύρετε tags στην προβολή πρόσβασης δεδομένων· κάνουν συνδρομή.

## Το Ignition 8.3 ως πελάτης

**Επαληθεύτηκε στις 2026-09-27 με το Ignition 8.3.9**, την τρέχουσα σταθερή έκδοση, στην επίσημη εικόνα container της Inductive Automation (`inductiveautomation/ignition:8.3.9`, τυπική έκδοση σε δοκιμαστική περίοδο), απέναντι σε ένα Gateway HotLoop του οποίου η συσκευή επίδειξης `extruder-1` τροφοδοτείται από προσομοιωτή. Τι αποδείχθηκε, από άκρη σε άκρη:

- μια σύνδεση OPC UA του Ignition στο `opc.tcp://<gateway>:4840` με `Basic256Sha256` και `SignAndEncrypt`, συνδεδεμένη ως **viewer** του HotLoop·
- η εμπιστοσύνη πιστοποιητικών και προς τις δύο κατευθύνσεις, όπως παρακάτω·
- tags OPC στον πάροχο `[default]` του Ignition που δείχνουν σε κόμβους HotLoop, με ανάγνωση ποιότητας Good και αλλαγές καθώς κινείται ο προσομοιωτής. Κάθε τιμή που έδειξε το Ignition ήταν μία που είχε κρατήσει το `/api/values` του HotLoop: το ίδιο double διασχίζει το καλώδιο αμετάβλητο, οπότε συγκρίνονται για ισότητα, όχι για εγγύτητα. Ένα tag κειμένου δηλωμένο `string` στο HotLoop διάβασε «RUNNING» σε tag String του Ignition·
- μια εγγραφή από το Ignition απορρίφθηκε: το Ignition έστειλε την εγγραφή, το HotLoop απάντησε `Bad_NotWritable` (διαβασμένο στο καλώδιο σε κανάλι μόνο Sign, όπου η απάντηση είναι υπογεγραμμένη αλλά όχι κρυπτογραφημένη), και η τιμή του HotLoop δεν κουνήθηκε·
- κάθε πολιτική και τρόπος ασφάλειας που προσφέρει το Ignition, παρακάτω.

### Πώς να το στήσετε

Από την πλευρά του HotLoop, πριν από το Ignition:

1. Ενεργοποιήστε τον διακομιστή και ορίστε το `HOTLOOP_OPCUA_SERVER_ENDPOINT_HOST` στο όνομα με το οποίο το Ignition φτάνει στο Gateway. Αυτό το όνομα υπάρχει σε κάθε URL endpoint που διαφημίζει ο διακομιστής και στο πιστοποιητικό του.
2. Δημιουργήστε έναν χρήστη HotLoop για το Ignition με τον ρόλο **viewer** (ένας admin το κάνει με `POST /api/users`· δείτε [Ταυτοποίηση και χρήστες](/el/iot/authentication/)). Οποιοσδήποτε ρόλος με `tags.read` και `values.read` συνδέεται· τίποτα περισσότερο δεν προσφέρεται, αφού ο διακομιστής είναι μόνο για ανάγνωση.

Στο Gateway του Ignition (η διεπαφή web στη θύρα 8088):

3. Στη σελίδα **OPC Connections** κάτω από το Connections (`/app/connections/opc-client-connections`), δημιουργήστε μια σύνδεση **OPC UA**. URL endpoint `opc.tcp://<gateway>:4840`· επιλέξτε το endpoint `Basic256Sha256` / `SignAndEncrypt`· ταυτοποίηση **Username**, με τον χρήστη και τον κωδικό του HotLoop. Η σύνδεση γίνεται αμέσως Faulted, κάτι αναμενόμενο: βήμα 4.
4. **Εγκρίνετε το Ignition στο HotLoop.** Το πιστοποιητικό πελάτη του Ignition βρίσκεται τώρα στο `<PKI_DIR>/rejected/` του Gateway (`/data/opcua-pki/rejected` στο container και στο chart), με όνομα το αποτύπωμα SHA-1, `<thumbprint>.crt`. Συγκρίνετε το αποτύπωμα με το δικό του πιστοποιητικό πελάτη OPC UA του Ignition, που εμφανίζεται στη σελίδα πιστοποιητικών OPC (`/app/connections/opc/security/certificates`). Μετά μετακινήστε το αρχείο στο `trusted/`. Καμία επανεκκίνηση σε καμία πλευρά. Το HotLoop δεν καταγράφει την άρνηση· το αρχείο είναι το μόνο σημάδι.
5. **Εγκρίνετε το HotLoop στο Ignition.** Η σύνδεση αποτυγχάνει τώρα προς την άλλη κατεύθυνση: η κατάσταση λέει `Bad_SecurityChecksFailed ... unable to find valid certification path`. Το πιστοποιητικό του HotLoop βρίσκεται στα απορριφθέντα πιστοποιητικά **πελάτη** του Ignition, στην ίδια σελίδα. Ελέγξτε το αποτύπωμά του με αυτό που καταγράφει το HotLoop κατά την εκκίνηση (`generated a self-signed OPC UA application certificate ... thumbprint=`) και εμπιστευτείτε το. Καμία επανεκκίνηση· η σύνδεση ανεβαίνει μέσα σε δευτερόλεπτα.
6. **Tags.** Δημιουργήστε tags OPC με τη σύνδεση ως διακομιστή OPC και διαδρομές στοιχείων στη μορφή URI χώρου ονομάτων, που το Ignition δέχεται ως έχουν:

   ```
   nsu=urn:hotloop:ua:gateway;s=extruder-1/Emberburn_Temperature
   ```

   Δηλώστε το καθένα ως αυτό που δημοσιεύει το HotLoop (δείτε [Τύποι δεδομένων](#τύποι-δεδομένων)): Float8 για float, Boolean, String, Int2 για `int16`, Int4 για `uint16` ή `int32`, Int8 για τους ευρύτερους ακεραίους. Κάνουν συνδρομή με τον ρυθμό της ομάδας tags, και το HotLoop αναβιβάζει έναν ταχύτερο ρυθμό δειγματοληψίας στο διάστημα ερώτησης της συσκευής.

Το ίδιο, ως αρχεία ή μέσω του REST API:

- Η σύνδεση είναι ο πόρος `data/config/resources/core/ignition/opc-connection/<name>/config.json`, τύπου προφίλ `com.inductiveautomation.OpcUaServerType`, ή `POST /data/api/v1/resources/ignition/opc-connection`. Δύο πράγματα σε αυτήν δεν είναι προφανή. Ο κωδικός είναι ενσωματωμένο μυστικό, ένα JWE που φτιάχνει το `POST /data/api/v1/encryption/encrypt` από το απλό κείμενο· μια απλή συμβολοσειρά δεν γίνεται δεκτή. Και το μπλοκ `security` χρειάζεται το ψευδώνυμο του χώρου κλειδιών πελάτη του gateway και τον κωδικό του: αν το παραλείψετε, η σύνδεση αποτυγχάνει με NullPointerException, και με κενό ψευδώνυμο αποτυγχάνει με `Unable to retrieve KeyPair for alias 'client'`. Αντιγράψτε το μπλοκ από την προεγκατεστημένη σύνδεση loopback `Ignition OPC UA Server`, που έχει και τα δύο.
- Τα πιστοποιητικά βρίσκονται στο `data/config/local/com.inductiveautomation.opcua/client/security/pki/` (`rejected/certs`, `trusted/certs`), ή μέσω `GET /data/opc-ua/api/v1/client/pki/certificates/rejected` και `POST .../trusted/<sha1>` από το API. **Το Ignition δεν ονομάζει τα αρχεία με το αποτύπωμα**· το πεδίο `signature` του API είναι το αποτύπωμα SHA-1, και ταιριάζει με ό,τι καταγράφει το HotLoop.
- Τα tags εισάγονται με `POST /data/api/v1/tags/import?provider=default&type=json`.
- Κάθε κλήση API χρειάζεται κλειδί API (η σελίδα API Keys, `/app/platform/security/api-keys`), και ένα κλειδί περνά μόνο αν ένα από τα επίπεδα ασφαλείας του βρίσκεται στα δικαιώματα ανάγνωσης ή εγγραφής του gateway (ο πόρος `security-properties`).

### Τι να περιμένετε

- **Το `Bad_SecurityChecksFailed` σημαίνει δύο διαφορετικά πράγματα.** Το Ignition δείχνει την ίδια κατάσταση όταν το HotLoop απορρίπτει το πιστοποιητικό του Ignition (βήμα 4· το μήνυμα δεν έχει λόγο) και όταν το Ignition απορρίπτει του HotLoop (βήμα 5· το μήνυμα λέει *unable to find valid certification path*). Κοιτάξτε πρώτα το `rejected/` του HotLoop.
- **Μια νέα ανάπτυξη του HotLoop κρατά το πιστοποιητικό της.** Μέχρι την 4.15.3 δεν το κρατούσε: το πιστοποιητικό έπρεπε να καλύπτει το όνομα host του container, που αλλάζει κάθε φορά που ξαναδημιουργείται το container, οπότε κάθε αναβάθμιση έφτιαχνε νέο πιστοποιητικό και το Ignition απέρριπτε τον διακομιστή μέχρι να το εμπιστευτεί ξανά κάποιος. Δείτε [Πιστοποιητικό διακομιστή](#πιστοποιητικό-διακομιστή). Το πιστοποιητικό εξακολουθεί να αλλάζει αν χαθεί ο τόμος PKI.
- **Ένα tag κειμένου δηλωμένο ως αριθμητικό διαβάζει `Bad_TypeMismatch`.** Το HotLoop δημοσιεύει ένα tag με τον τύπο με τον οποίο έχει δηλωθεί, και ένα tag `float` που περιέχει «RUNNING» δεν μπορεί να είναι Double. Τα tags που δημιουργούσε το Discover tags μέχρι την 4.15.3 ήταν όλα δηλωμένα `float`· δείτε [Πρωτόκολλα και drivers](/el/iot/protocols/#opc-ua). Δηλώστε τα `string`.
- **Οι εγγραφές απορρίπτονται, και το Ignition θολώνει τον λόγο.** Το HotLoop απαντά `Bad_NotWritable`. Ο δικός του διακομιστής OPC UA του Ignition, όταν του ζητείται να γράψει το ίδιο tag, προωθεί μόνο ένα γενικό `Bad` (0x80000000). Η τιμή του tag του Ignition δεν αλλάζει.
- **Οι παρωχημένες πολιτικές δουλεύουν μόνο όταν ενεργοποιηθούν.** Το Ignition προσφέρει `Basic128Rsa15` και `Basic256`. Επιλέξτε `Basic256Sha256` ή μία από τις πολιτικές `Aes` στη σύνδεση.
- **Η δοκιμαστική περίοδος.** Ένα gateway 8.3 χωρίς άδεια τρέχει για δύο ώρες και μετά σταματά να εκτελεί μέχρι να μηδενιστεί η δοκιμή στη διεπαφή web του Gateway. Τα tags παλιώνουν όταν λήξει· αυτό είναι το Ignition, όχι η σύνδεση.

### Πίνακας πολιτικών

Κάθε γραμμή είναι μια νέα συνεδρία με αυτή την πολιτική και τον τρόπο λειτουργίας, που διαβάζει ζωντανές τιμές. Οι δύο παρωχημένες γραμμές μετρήθηκαν με ενεργό το `HOTLOOP_OPCUA_SERVER_ALLOW_DEPRECATED_POLICIES`· όταν είναι απενεργοποιημένο, όπως από προεπιλογή, αυτές οι δύο πολιτικές δεν προσφέρονται και ένα κανάλι που ζητά μία απορρίπτεται:

| Πολιτική | SignAndEncrypt | Sign |
|---|---|---|
| `Basic256Sha256` | λειτουργεί | λειτουργεί |
| `Aes128_Sha256_RsaOaep` | λειτουργεί | λειτουργεί |
| `Aes256_Sha256_RsaPss` | λειτουργεί | λειτουργεί |
| `Basic256` (παρωχημένη) | λειτουργεί | λειτουργεί |
| `Basic128Rsa15` (παρωχημένη) | λειτουργεί | λειτουργεί |

Η `None` δεν προσφέρεται εκτός αν οριστεί το `HOTLOOP_OPCUA_SERVER_ALLOW_INSECURE`, και δεν δοκιμάστηκε.

| `HOTLOOP_OPCUA_SERVER_APPLICATION_URI` | `urn:hotloop:gateway[:<siteId>]` | Πρέπει να μένει σταθερό ανάμεσα σε επανεκκινήσεις· πρέπει να είναι URI |
| `HOTLOOP_OPCUA_SERVER_PKI_DIR` | `/data/opcua-pki` | Πιστοποιητικό, κλειδί, `trusted/`, `rejected/`. Στηρίξτε το με τόμο |
| `HOTLOOP_OPCUA_SERVER_CERT_FILE` / `_KEY_FILE` | n/a | Χρήση αυτού του ζεύγους RSA αντί για δημιουργία· ορίστε και τα δύο ή κανένα |
| `HOTLOOP_OPCUA_SERVER_CERT_HOSTS` | n/a | Επιπλέον ονόματα DNS / IP για παραγόμενο πιστοποιητικό |
| `HOTLOOP_OPCUA_SERVER_ALLOW_INSECURE` | `false` | Προσφέρει την πολιτική ασφάλειας None. Προειδοποίηση κατά την εκκίνηση |
| `HOTLOOP_OPCUA_SERVER_ALLOW_ANONYMOUS` | `false` | Δέχεται συνεδρίες χωρίς ταυτότητα. Προειδοποίηση κατά την εκκίνηση |
| `HOTLOOP_OPCUA_SERVER_TRUST_ALL_CLIENT_CERTS` | `false` | Παραλείπει την έγκριση πιστοποιητικών πελατών. Προειδοποίηση κατά την εκκίνηση |
| `HOTLOOP_OPCUA_SERVER_ALLOW_X509` | `false` | Προσφέρει το token χρήστη Certificate: ένας πελάτης συνδέεται με πιστοποιητικό επισυναπτόμενο σε χρήστη ([Πιστοποιητικά χρήστη X.509](#πιστοποιητικά-χρήστη-x509)). Σημείωση κατά την εκκίνηση |
| `HOTLOOP_OPCUA_SERVER_ALLOW_DEPRECATED_POLICIES` | `false` | Προσφέρει τις παρωχημένες πολιτικές `Basic128Rsa15` και `Basic256` για παλιό πελάτη ([Μεταφορά](#μεταφορά)). Προειδοποίηση κατά την εκκίνηση |
| `HOTLOOP_OPCUA_SERVER_MAX_SESSIONS` | `20` | 0 = απεριόριστες |
| `HOTLOOP_OPCUA_SERVER_MAX_SUBSCRIPTIONS` | `200` | 0 = απεριόριστες |
| `HOTLOOP_OPCUA_SERVER_RECONCILE_INTERVAL` | `30s` | Η περίοδος της συμφωνίας ασφαλείας |

Ο διακομιστής δεν ξεκινά στη λειτουργία `--mcp-stdio`: εκεί ένας πράκτορας εκκινεί αυτό το δυαδικό ως βοηθό, και να ανταγωνίζεται μια δεύτερη διεργασία το πραγματικό Gateway για τη θύρα 4840 δεν πρέπει να είναι δυνατό.

### Helm

`opcuaServer.*` στο `charts/hotloop/values.yaml`. Η ενεργοποίησή του προσθέτει ένα Service (`<release>-opcua`, ClusterIP από προεπιλογή· το LoadBalancer ή το NodePort είναι εσκεμμένη επιλογή για πελάτη εκτός συμπλέγματος), ένα PVC για τον κατάλογο PKI (`opcuaServer.persistence`· η απώλειά του σημαίνει ότι κάθε πελάτης πρέπει να εμπιστευτεί νέο πιστοποιητικό), τη θύρα του container και, ώστε το `networkPolicy.enabled` και το `opcuaServer.enabled` μαζί να μην αφήνουν σιωπηλά έναν διακομιστή να ακούει χωρίς να τον φτάνει τίποτα, τη θύρα στον κανόνα ingress του προεπιλεγμένου NetworkPolicy. Ένα προσαρμοσμένο `networkPolicy.ingress` αντικαθιστά αυτόν τον κανόνα, όπως και για τον broker, και πρέπει τότε να απαριθμεί μόνο του τη θύρα. Το `opcuaServer.tls.existingSecret` παρέχει ένα Secret `kubernetes.io/tls` αντί για παραγόμενο πιστοποιητικό.
