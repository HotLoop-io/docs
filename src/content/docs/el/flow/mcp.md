Ένας πράκτορας που μιλά το Model Context Protocol μπορεί να καλέσει μια ροή ως εργαλείο, και μια ροή μπορεί να καλέσει ένα εργαλείο σε οποιονδήποτε διακομιστή MCP, συμπεριλαμβανομένου του δικού του HotLoop. Το κάνουν τρεις κόμβοι και ένας κόμβος ρύθμισης: οι `mcp tool` και `mcp result` εξυπηρετούν μια ροή, ο `mcp client` πάνω σε μια σύνδεση `hotloop-flow-mcp-server` καλεί προς τα έξω. Αν απλώς συνδέετε αισθητήρες με πίνακες ελέγχου, μπορείτε να τα παραλείψετε όλα αυτά: μια ροή που δεν χρησιμοποιεί κανέναν από αυτούς τους κόμβους δεν κάνει ποτέ κλήση MCP, και τα μόνα εργαλεία που προσφέρει το ίδιο το Flow είναι εκείνα που διαβάζουν και αλλάζουν τις ροές του ([παρακάτω](#τα-δικά-του-εργαλεία-του-flow)).

Το πρωτόκολλο είναι αυτό του Go SDK (`github.com/modelcontextprotocol/go-sdk` v1.8.0, με ελεύθερη άδεια, με ορισμένα αρχεία ακόμη υπό MIT όσο το έργο ολοκληρώνει την αλλαγή άδειας, συντηρείται από το έργο MCP). Μιλά την τρέχουσα αναθεώρηση της προδιαγραφής, 2026-07-28, που δεν έχει χειραψία και μεταφέρει την έκδοση σε κάθε αίτημα, καθώς και τις αναθεωρήσεις με χειραψία έως την 2025-11-25, στο ίδιο τελικό σημείο. Ο πελάτης παίρνει όποια ανοίγει, οπότε δεν χρειάζεται καμία ρύθμιση.

## Ροές ως εργαλεία

Ένας κόμβος `mcp tool` δηλώνει ένα εργαλείο: ένα όνομα, μια περιγραφή για το μοντέλο που τη διαβάζει και ένα σχήμα εισόδου. Όσο η ροή είναι αναπτυγμένη, το Flow το προσφέρει στο `/mcp` (κάτω από τη ρίζα διαχείρισης, αν την έχετε μετακινήσει). Μια κλήση γίνεται μήνυμα που βγαίνει από τον κόμβο: το `msg.payload` είναι τα ορίσματα της κλήσης, το `msg.topic` είναι το όνομα του εργαλείου και το `msg.mcp` περιέχει τα `tool`, `caller` και `callId`. Ένας κόμβος `mcp result` κάπου πιο κάτω στέλνει πίσω την απάντηση, όπως το `http response` απαντά στο `http in`. Ό,τι υπάρχει ανάμεσά τους είναι μια ροή όπως κάθε άλλη.

```json
[
  {"id": "t1", "type": "tab", "label": "Line"},
  {"id": "tool", "type": "mcp tool", "z": "t1", "toolName": "line_status",
   "description": "Status of a production line: its state and speed.",
   "schema": "{\"type\":\"object\",\"properties\":{\"line\":{\"type\":\"string\",\"enum\":[\"L1\",\"L2\",\"L3\"]}},\"required\":[\"line\"],\"additionalProperties\":false}",
   "x": 100, "y": 100, "wires": [["status"]]},
  {"id": "status", "type": "function", "z": "t1", "name": "status", "outputs": 1,
   "func": "msg.payload = {line: msg.payload.line, state: 'running', askedBy: msg.mcp.caller};\nreturn msg;",
   "x": 300, "y": 100, "wires": [["answer"]]},
  {"id": "answer", "type": "mcp result", "z": "t1", "x": 500, "y": 100, "wires": []}
]
```

**Το σχήμα ελέγχεται πριν εκτελεστεί η ροή.** Είναι JSON Schema, διαβασμένο όπως το διαβάζει ο κόμβος `json` (πρόχειρο 2020-12 εκτός αν το σχήμα ονομάζει άλλο, και ένα `$ref` προς άλλο URL είναι σφάλμα). Ένα μη έγκυρο σχήμα, μια ρίζα που δεν είναι αντικείμενο, ένα όνομα εργαλείου που το MCP δεν επιτρέπει ή δύο κόμβοι που προσφέρουν το ίδιο όνομα αποτυγχάνουν στην ανάπτυξη αυτού του κόμβου, με τον λόγο. Μια κλήση της οποίας τα ορίσματα δεν ταιριάζουν παίρνει απάντηση ως σφάλμα εργαλείου που ονομάζει το λανθασμένο πεδίο, `arguments.line: value must be one of "L1", "L2", "L3"`, ώστε το μοντέλο να το διορθώσει και να ξαναδοκιμάσει, και η ροή δεν το βλέπει ποτέ. Ένα αντικείμενο payload επιστρέφει ως αντικείμενο και ως κείμενο JSON, το κείμενο επιστρέφει ως κείμενο, και ένας `mcp result` που τροφοδοτείται από κόμβο Catch, ή με επιλεγμένο το "The work failed", απαντά με σφάλμα εργαλείου με τα λόγια του ίδιου του σφάλματος. Μια κλήση στην οποία δεν απαντά κανείς ενημερώνεται μετά τη λήξη του χρονικού ορίου απάντησης, 30 δευτερόλεπτα αν δεν ορίσετε άλλο, και το σφάλμα πηγαίνει σε κόμβο Catch. Μια νέα ανάπτυξη περιμένει τις κλήσεις που βρίσκονται σε εξέλιξη.

**Ένας πράκτορας είναι καλών όπως κάθε άλλος.** Το `/mcp` δέχεται τα ίδια token με το API διαχείρισης, ένα token συνεδρίας ή ένα token API, και τίποτε άλλο. Δεν υπάρχει ανώνυμη κλήση: χωρίς token είναι 401, ένα token που το Flow δεν γνωρίζει είναι 401, και ένα token χωρίς το δικαίωμα `mcp.call` είναι 403, πριν το πρωτόκολλο δει το αίτημα. Μια εγκατάσταση που τρέχει με `HOTLOOP_FLOW_INSECURE` απαντά 403 σε κάθε αίτημα προς `/mcp`, επειδή μια κλήση εργαλείου πρέπει να έχει έναν καλούντα να καταγραφεί στο αρχείο ελέγχου. Το token ενός πράκτορα είναι token όπως κάθε άλλο:

```yaml
auth:
  tokens:
    - name: agent
      hash: sha256:...          # from: hotloop-flow token -name agent
      permissions: ["mcp.call"]
      rateLimit: {calls: 60, per: 1m}   # optional; no rateLimit, no limit
```

Η κλήση τρέχει με τα δικαιώματα αυτής της ταυτότητας. Κάθε καλών χρειάζεται `mcp.call` (ή `mcp.*`, ή `*`). Αν βάλετε άλλο δικαίωμα στο πλαίσιο "Extra permission" ενός εργαλείου, ας πούμε `mcp.line3`, ο καλών χρειάζεται και αυτό, και χωρίς αυτό δεν βλέπει καν το εργαλείο στη λίστα. Δύο πράκτορες μπορούν να μοιράζονται ένα Flow και να βλέπουν διαφορετικά εργαλεία.

**Ένα token μπορεί να περιοριστεί σε έναν αριθμό κλήσεων.** Το `rateLimit` σε ένα token API στο `auth.tokens` είναι `calls` μέσα σε ένα παράθυρο, `per`, ένα λεπτό αν το παραλείψετε. Το παράθυρο ξεκινά με την πρώτη κλήση του token, μια κλήση πάνω από τον αριθμό απορρίπτεται μέχρι να τελειώσει το παράθυρο, και μετά η μέτρηση ξεκινά ξανά. Μια κλήση που απορρίπτεται δεν φτάνει ποτέ στη ροή και παίρνει απάντηση ως σφάλμα εργαλείου που λέει πόσα δευτερόλεπτα να περιμένει, ώστε ένας πράκτορας σε βρόχο να ακούσει να επιβραδύνει με λόγια που διαβάζει. Η προδιαγραφή δεν ονομάζει σφάλμα γι' αυτό, οπότε είναι το σφάλμα εργαλείου που ήδη ορίζει για μια κλήση που δεν μπορεί να γίνει. Ένα token χωρίς `rateLimit` δεν περιορίζεται ποτέ, και ένα token συνεδρίας επίσης δεν περιορίζεται, επειδή ανήκει σε άνθρωπο. Κάθε token μετρά χωριστά, και η μέτρηση ζει στη μνήμη, οπότε μια επανεκκίνηση την ξαναρχίζει. Μια απόρριψη είναι μια γραμμή `mcp.refused` με τον λόγο `rate limit exceeded`, που σημαίνει ότι και μια πλημμύρα κλήσεων βρίσκεται στο αρχείο ελέγχου.

**Κάθε κλήση βρίσκεται στο αρχείο ελέγχου, με το όνομα του καλούντος.** Το `mcp.call` γράφεται πριν εκτελεστεί η ροή, με το εργαλείο, τον κόμβο και ένα αναγνωριστικό κλήσης, και το `mcp.result` μετά, με το αποτέλεσμα και τα χιλιοστά του δευτερολέπτου. Το `mcp.refused` είναι ένα λάθος token, ένα που στερείται το δικαίωμα, ένα εργαλείο που δεν επιτρέπεται να καλέσει ή ορίσματα που δεν ταίριαζαν. Τα ίδια τα ορίσματα δεν γράφονται ποτέ. Ένα αίτημα χωρίς κανένα token επίσης δεν γράφεται, επειδή στην άλλη άκρη δεν υπάρχει κανείς να ονομαστεί. Το `GET /audit?event=mcp.` τα διαβάζει όλα αυτά, και το `?user=token:agent` τα περιορίζει σε έναν πράκτορα.

Δοκιμάστε το με τον επιθεωρητή του ίδιου του έργου MCP, που δεν χρειάζεται τίποτα από το Flow:

```bash
npx @modelcontextprotocol/inspector@2.12.0 --cli http://localhost:1880/mcp \
  --transport http --header "Authorization: Bearer $TOKEN" \
  --method tools/call --tool-name line_status --tool-arg line=L3
```

Μια δοκιμή ροής βάζει το μήνυμα που θα είχε κάνει μια κλήση εκεί όπου βρίσκεται ο κόμβος `mcp tool`, και ο `mcp result` παραδίδει στη δοκιμή ό,τι θα είχε απαντήσει ως `{isError, text, structuredContent}`, ώστε η ροή να δοκιμάζεται χωρίς διακομιστή.

## Τα δικά του εργαλεία του Flow

Ένας πράκτορας που θα μπορούσε να καλεί μόνο ό,τι έχει συνδέσει ο δημιουργός μιας ροής δεν θα μπορούσε ούτε να δει τις ροές ούτε να τις αλλάξει, γι' αυτό το Flow προσφέρει 45 δικά του εργαλεία στο ίδιο `/mcp`, δίπλα σε αυτά των ροών. Διαβάζουν και γράφουν. Επτά αφορούν τις ροές, στον πίνακα παρακάτω, και τα υπόλοιπα είναι οι άλλες διαδρομές του API διαχείρισης: οι ρυθμίσεις, η παλέτα, το αρχείο ελέγχου, οι λεπτομέρειες και οι διαφορές των αναπτύξεων, η εξαγωγή, οι δοκιμές ροών, τα ίχνη μηνυμάτων, οι αριθμοί του χρόνου εκτέλεσης, η επαναφορά του δεύτερου παράγοντα, και τα διαγράμματα και τα όργανα: λίστα και ανάγνωση ενός διαγράμματος, εκτέλεση και διακοπή του, χειρισμός του αποσφαλματωτή του, ρύθμιση ενός ελέγχου στον πίνακά του και ενεργοποίηση ή απενεργοποίηση των εγγραφών ενός οργάνου. Η σελίδα MCP έχει κάθε εργαλείο, τη διαδρομή του και το δικαίωμά του, και τις λίγες διαδρομές που δεν είναι εργαλεία και γιατί.

| Εργαλείο | Λειτουργία | Δικαίωμα |
|---|---|---|
| `list_flows` | κάθε καρτέλα και υποροή: id, ετικέτα, απενεργοποιημένο, αριθμός κόμβων και η αναθεώρηση | `flows.read` |
| `get_flows` | όλο το αναπτυγμένο σύνολο όπως το διαβάζει ο επεξεργαστής, με την αναθεώρηση | `flows.read` |
| `get_flow` | μία καρτέλα ή υποροή με τους κόμβους της, ανά id | `flows.read` |
| `deploy_flows` | **deploy**: αντικαθιστά όλο το σύνολο, με την αναθεώρηση που διαβάσατε και μια σημείωση | `flows.write` |
| `list_deployments` | το ιστορικό αναπτύξεων, το πιο πρόσφατο πρώτο | `flows.read` |
| `rollback_deployment` | **roll back** σε προηγούμενη ανάπτυξη, ως νέα | `flows.write` |
| `inject_node` | **press** ενός κόμβου inject, με δικό σας μήνυμα | `inject.write` |

Κανένα δεν είναι δεύτερη υλοποίηση. Το καθένα τρέχει τον δικό του χειριστή του API διαχείρισης για την ίδια δουλειά ως ο καλών που επαληθεύτηκε από το τελικό σημείο, οπότε μια ανάπτυξη συναντά ό,τι συναντά και μια ανάπτυξη από τον επεξεργαστή: το έγγραφο πρέπει να αναλύεται, η αναθεώρηση πρέπει να είναι η τρέχουσα (μια κενή αντικαθιστά επίτηδες), οι συνδέσεις που διαφωνούν για το τι κυκλοφορεί πάνω τους απορρίπτονται, τα μη επιτρεπόμενα plugin απορρίπτονται, και οι δοκιμές ροών που αποτυγχάνουν απορρίπτουν την ανάπτυξη, η καθεμία με τα λόγια της διαδρομής. Το ιστορικό αναπτύξεων καταγράφει τον καλούντα και τη σημείωση, και το αρχείο ελέγχου έχει τη γραμμή `deploy` ή `inject` με το όνομα του καλούντος, εκτός από τις γραμμές `mcp.call` και `mcp.result` που αφήνει κάθε κλήση εργαλείου. Ένας καλών χρειάζεται `mcp.call` και το δικό του δικαίωμα του εργαλείου, και ένα εργαλείο που δεν επιτρέπεται να καλέσει δεν υπάρχει στη λίστα του. Τα εργαλεία μένουν κατά τις αναπτύξεις, που αφαιρούν μόνο τα εργαλεία των ροών, και μια ροή δεν μπορεί να προσφέρει κάποιο από τα ονόματά τους.

Το `deploy_flows` αντικαθιστά όλο το σύνολο, οπότε ένας πράκτορας διαβάζει πρώτα το `get_flows` και το στέλνει πίσω αλλαγμένο, με το `rev` που πήρε.

## Κλήση εργαλείων σε άλλους διακομιστές

Ένας κόμβος `mcp client` καλεί ένα εργαλείο όταν φτάνει ένα μήνυμα, πάνω σε μια σύνδεση `hotloop-flow-mcp-server`: τη διεύθυνση MCP του διακομιστή, ένα bearer token αν το δέχεται και ένα χρονικό όριο. Το εργαλείο και τα ορίσματά του είναι τυποποιημένες είσοδοι, οπότε και τα δύο μπορούν να έρχονται από το μήνυμα. Το `msg.payload` είναι η δομημένη απάντηση του εργαλείου όταν έχει, το κείμενο όταν ό,τι είπε ήταν κείμενο, και το περιεχόμενο όπως ήρθε όταν ήταν κάτι άλλο, και το `msg.mcp` έχει τον διακομιστή, το εργαλείο και ολόκληρη την απάντηση. Η άλλη λειτουργία, "List the tools", βάζει στο `msg.payload` κάθε εργαλείο που έχει ο διακομιστής με την περιγραφή και το σχήμα εισόδου του.

Ένα εργαλείο που αναφέρει σφάλμα προκαλεί ένα, με τα λόγια του διακομιστή, ώστε ένας κόμβος Catch να βλέπει ό,τι θα έβλεπε το μοντέλο. **Μια κλήση δεν στέλνεται ποτέ δύο φορές.** Ένα εργαλείο μπορεί να κινήσει εξοπλισμό, και μια διακοπείσα σύνδεση δεν λέει αν ο διακομιστής το εκτέλεσε, οπότε το σφάλμα λέει ότι η σύνδεση απέτυχε και το επόμενο μήνυμα συνδέεται ξανά. Το token πηγαίνει στη διεύθυνση που δώσατε και πουθενά αλλού, μια ανακατεύθυνση δεν ακολουθείται, και ένα σφάλμα δεν το επαναλαμβάνει ποτέ. Η σύνδεση εμπιστεύεται τις ρίζες πιστοποιητικών του συστήματος και τίποτε άλλο.

Για το HotLoop είναι η διεύθυνση του `/mcp` του και το `mcp-token` από το Secret της έκδοσής του, και κάθε εργαλείο της τεκμηρίωσης MCP του HotLoop βρίσκεται εκεί:

```json
{"id": "plant", "type": "mcp client", "z": "t1", "server": "hotloop",
 "tool": "get_plant_status", "toolType": "str", "arguments": "{}", "argumentsType": "json",
 "x": 300, "y": 100, "wires": [["use"]]}
```

Το HotLoop βλέπει την κλήση ως κλήση πελάτη MCP, με τους δικούς του κανόνες: το MCP διαβάζει και γράφει, από την ίδια πύλη με όλους τους άλλους, οπότε ένα `write_tag` σε armed tag εντός εύρους περνά (αφού ενεργοποιηθούν οι εγγραφές του ίδιου του HotLoop) και ένα που απορρίπτει, ένα tag που κανείς δεν σημείωσε ως εγγράψιμο για παράδειγμα, επιστρέφει ως σφάλμα του κόμβου, με τα λόγια του HotLoop. Για να γράψετε μέσω της πύλης του HotLoop από μια ροή χωρίς MCP, χρησιμοποιήστε τους κόμβους HotLoop παραπάνω.

## Με τι δοκιμάστηκε

**Ο διακομιστής** δοκιμάζεται με τον δικό του πελάτη του Go SDK πάνω σε πραγματικό HTTP, και στις δύο εποχές: λίστα, κλήση, ορίσματα που απορρίπτονται, δικαίωμα που απορρίπτεται, token που απορρίπτεται, οι γραμμές ελέγχου, ένα εργαλείο που εξαφανίζεται όταν σταματά ο κόμβος του, και ολόκληρος ο διακομιστής διαχείρισης μπροστά με πραγματικά token API και συνεδρίας και το αρχείο ελέγχου στον δίσκο. Το Inspector CLI 2.12.0 του έργου MCP έκανε λίστα των εργαλείων ενός Flow που έτρεχε, τα κάλεσε, και απορρίφθηκε χωρίς token και με επινοημένο. Ο κόμβος `mcp client` εκτελέστηκε απέναντι σε πραγματικό HotLoop 4.18.10 (η δημοσιευμένη εικόνα IoT): έκανε λίστα και των 27 εργαλείων του, κάλεσε τα `get_plant_status`, `list_devices` και `get_states` και χρησιμοποίησε τις απαντήσεις, απορρίφθηκε με λάθος token και χωρίς token, πήρε το δικό του σφάλμα του HotLoop για ένα εργαλείο που δεν υπάρχει και για μια εγγραφή που το MCP δεν επιτρέπεται να κάνει, και ένα εργαλείο του Flow που κλήθηκε από τον Inspector εκτέλεσε μια ροή που κάλεσε το MCP του HotLoop και απάντησε με ό,τι είπε αυτό.

**Δεν έγιναν:** OAuth (το bearer token είναι ο μόνος τρόπος εισόδου, προς τις δύο κατευθύνσεις), διακομιστές stdio, πόροι, prompts, δειγματοληψία, elicitation και ειδοποιήσεις προόδου, και το σχήμα εξόδου ενός εργαλείου. Το HotLoop 4.18.10 μιλά τις αναθεωρήσεις με χειραψία, οπότε ο κόμβος το συναντά έτσι· απέναντι σε διακομιστή της τρέχουσας αναθεώρησης δοκιμάζεται μόνο με αυτόν του Flow. Ένας διακομιστής με χειραψία που ξεχνά μια συνεδρία (μια επανεκκίνηση) αποτυγχάνει στην πρώτη κλήση μετά, μία φορά, και η επόμενη συνδέεται ξανά. Ο περιορισμός ρυθμού είναι ανά token API και είναι απενεργοποιημένος μέχρι να τον ορίσετε, οπότε ένα token χωρίς `rateLimit` περιορίζεται μόνο από τις ουρές, που έχουν ήδη ανώτατο όριο, και από το μέγεθος αιτήματος, 4 MiB.
