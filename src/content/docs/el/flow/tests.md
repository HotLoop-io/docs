«Χάλασε η αλλαγή μου τη γραμμή;» πρέπει να απαντιέται πριν από την ανάπτυξη, από αυτόν που κάνει την αλλαγή, και όχι στις 3 τα ξημερώματα από αυτόν που είναι σε εφημερία. Έτσι μια ροή μπορεί να έχει δοκιμές, που είναι YAML, ζουν δίπλα στο αρχείο της ροής και περνούν από την ίδια αναθεώρηση:

```yaml
# line3.test.yaml
flows: line3.json            # relative to this file; flows.json if you leave it out
tests:
  - name: a high reading raises the alarm and nothing else
    inject:
      - node: reading                  # by name or by id
        msg: {topic: line3/temp, payload: 92.5}
    expect:
      - node: over limit?              # the Switch
        port: 1
        msg: {payload: 92.5}
        within: 500ms
      - node: over limit?
        port: 2
        nothing: true
      - node: alarm out                # a Debug: checked on what it received
        msg: {payload: HIGH}

  - name: a negative reading is caught, not alarmed on
    inject:
      - node: reading
        msg: {payload: -4}
    expect:
      - node: errors                   # a Catch node
        error: "out of range"
```

```bash
hotloop-flow test -junit report.xml line3.test.yaml
```

```
--- PASS: a high reading raises the alarm and nothing else (0.00s)
--- PASS: a negative reading is caught, not alarmed on (0.00s)
ok	line3.test.yaml	2 passed, 0 failed, 0 errors (0.00s)
```

Αυτό είναι το πραγματικό runtime και οι πραγματικοί κόμβοι, μέσα στη διεργασία, χωρίς διακομιστή και χωρίς επεξεργαστή. Κάθε δοκιμή έχει δικό της runtime, οπότε τίποτα από όσα αφήνει μια δοκιμή σε ένα Delay ή σε ένα context δεν μπορεί να περάσει στην επόμενη.

- **`inject`** βάζει μηνύματα, με τη σειρά, και καθένα επεξεργάζεται πριν μπει το επόμενο. Ένας κόμβος με είσοδο το παίρνει εκεί. Μια πηγή όπως ένα Inject ή ένα MQTT In το στέλνει από την πρώτη της έξοδο σαν να το είχε παραγάγει η ίδια, και σε έναν κόμβο Inject χωρίς μήνυμα πατιέται το κουμπί.
- **`expect`** παρακολουθεί την έξοδο ενός κόμβου, με τις θύρες να μετρούν από το 1 όπως στον επεξεργαστή. Ένας κόμβος χωρίς εξόδους, όπως ένα Debug, ελέγχεται σε ό,τι έλαβε. Ένα στιγμιότυπο υποροής παρακολουθείται στις δικές του εξόδους, από όπου κι αν προέρχονται μέσα του.
- **`msg`** είναι ό,τι πρέπει να περιέχει το μήνυμα. Κάθε ιδιότητα που δίνετε πρέπει να υπάρχει με αυτήν την τιμή, μέχρι τα βάθη, και ό,τι άλλο έχει το μήνυμα αγνοείται, ώστε μια δοκιμή για το payload να μη σπάει όταν κάποιος αρχίσει να ορίζει `msg.topic`. Το **`assert`** είναι μια έκφραση JSONata που πρέπει να βγει αληθής, για ελέγχους που μια κυριολεκτική τιμή δεν μπορεί να κάνει. Το **`error`** είναι το κείμενο που πρέπει να περιέχει το σφάλμα που έπιασε ένας κόμβος Catch.
- **`within`** είναι προθεσμία. Ένα μήνυμα που έρχεται αργά αποτυγχάνει, και η αποτυχία λέει πόσο αργά. Τα **`nothing: true`** και **`count: N`** ελέγχονται όταν η ροή έχει ησυχάσει, που είναι η μόνη στιγμή που το «δεν βγήκε τίποτα» σημαίνει κάτι. Δύο προσδοκίες στην ίδια θύρα είναι δύο μηνύματα, με αυτή τη σειρά.

Μια δοκιμή τελειώνει μόλις συμβεί ό,τι περιμένει και η ροή δεν έχει τίποτα άλλο να κάνει. Το `timeout` είναι 5 δευτερόλεπτα εκτός αν πείτε άλλο, στο δικό της ρολόι, που είναι η επόμενη ενότητα.

Μια αποτυχία λέει τι βγήκε αντί για αυτό και πού διαφέρει:

```
--- FAIL: the alarm says LOW (0.00s)
    expect 1: debug "alarm out" (alarm-out): 1 message(s) received and none matched; the first one differs at msg.payload: wanted "LOW", got "HIGH"
      at 0s: {"payload":"HIGH","topic":"line3/temp"}
```

Μια δοκιμή που δεν μπορεί να τρέξει είναι σφάλμα, όχι επιτυχία: ένας κόμβος που ονομάζει και δεν υπάρχει στη ροή, ένα όνομα που μοιράζονται δύο κόμβοι, μια θύρα που ο κόμβος δεν έχει ή ένας κόμβος της ροής που δεν ξεκινά. Το ίδιο και ένα λάθος γραμμένο κλειδί. Το `expcet:` απορρίπτεται όταν διαβάζεται το αρχείο, γιατί ένα τυπογραφικό που θα προσπερνιόταν σιωπηλά θα άφηνε μια δοκιμή χωρίς τίποτα να ελέγξει, και μια δοκιμή χωρίς τίποτα να ελέγξει περνά. Η κατάσταση εξόδου είναι 1 για οτιδήποτε λιγότερο από πλήρη επιτυχία, και το `-junit` γράφει την αναφορά που διαβάζει κάθε σύστημα CI.

## Στο ρολόι της δοκιμής

Κανείς δεν τρέχει σουίτα δοκιμών που περιμένει ένα Delay πέντε λεπτών, οπότε μια δοκιμή δεν περιμένει. Κρατά δικό της ρολόι και το μετακινεί κατευθείαν στο επόμενο πράγμα που περιμένει κάτι στη ροή: ένα Delay που αφήνει, το δεύτερο μήνυμα ενός Trigger, ένα Inject σε διάστημα ή crontab, ένα Join ή Batch που λήγει, ένα Link Call που τα παρατά. Το χρονόμετρο ενεργοποιείται, η ροή χειρίζεται ό,τι έστειλε, και μόνο τότε το ρολόι ψάχνει το επόμενο που οφείλεται, με την ίδια σειρά που θα έφερναν τα πραγματικά λεπτά. Πέντε λεπτά Delay είναι ένα βήμα και περίπου ένα χιλιοστό του δευτερολέπτου.

```yaml
  - name: a reading at 4m pushes the watchdog's off out to 9m
    clock: 2026-10-05T06:00:00Z     # when the test starts; the real time if you leave it out
    timeout: 20m
    inject:
      - {node: watchdog, msg: {payload: reading}}
      - {node: watchdog, msg: {payload: reading}, at: 4m}   # at: on the test's clock
    expect:
      - {node: watchdog, msg: {payload: "on"}}
      - {node: watchdog, msg: {payload: "off"}, within: 9m}

  - name: and not a moment before
    timeout: 8m59s
    inject:
      - {node: watchdog, msg: {payload: reading}}
      - {node: watchdog, msg: {payload: reading}, at: 4m}
    expect:
      - {node: watchdog, count: 1}  # the "on", and nothing else yet
```

Το **`at`** βάζει μια έγχυση σε μια στιγμή του ρολογιού της δοκιμής, και ό,τι οφείλεται πριν από αυτήν γίνεται πρώτο. Τα **`within`** και **`timeout`** είναι επίσης σε αυτό το ρολόι, οπότε `timeout: 1h` σε ροή με ένα Inject ανά δέκα λεπτά είναι έξι τικ και λίγα χιλιοστά του δευτερολέπτου. Το **`clock`** ορίζει πότε ξεκινά η δοκιμή, για ροή που νοιάζεται για την ώρα: ένα crontab που ενεργοποιείται στις έξι και μισή ενεργοποιείται όταν το ρολόι της δοκιμής δείχνει έξι και μισή. Το `Date` ενός κόμβου Function, η χρονοσήμανση ενός Inject, ένας κόμβος Change που ορίζει ημερομηνία και το `Expires` ενός cookie διαβάζουν το ίδιο ρολόι, οπότε μια ροή που σημαδεύει και συγκρίνει ώρες συμφωνεί με τον εαυτό της κάτω από δοκιμή.

Η σουίτα αποδεικνύει με αυτό κάθε κόμβο χρονισμού της παλέτας, στο χιλιοστό του δευτερολέπτου: Delay σε σταθερή, τυχαία, ρυθμού και χρονισμένη λειτουργία, Trigger με extend, Inject σε διάστημα, μία φορά κατά την εκκίνηση και σε crontab, χρονικά όρια των Join και Batch και ένα Link Call που δεν παίρνει ποτέ απάντηση. Όλα, μια ώρα χρόνου εργοστασίου μαζί, τρέχουν σε πολύ λιγότερο από ένα δευτερόλεπτο. Αυτό που μια δοκιμή δεν μπορεί να μετακινήσει είναι η CPU: μια ροή που είναι ακόμα απασχολημένη μετά από ένα λεπτό πραγματικού χρόνου αποτυγχάνει τη δοκιμή αντί να κρεμάσει τη σουίτα. Τα `$now()` και `$millis()` του JSONata διαβάζουν ακόμα το ρολόι του τοίχου.

## Δοκιμές από τον επεξεργαστή

Κανείς δεν γράφει δοκιμή για μια ροή που δουλεύει. Τη γράφει τη μέρα που σταματά να δουλεύει, που είναι μια μέρα αργά. Γι' αυτό ο επεξεργαστής φτιάχνει μία από ό,τι μόλις έκανε η ροή, με δύο κλικ.

Κάθε μήνυμα στην πλαϊνή στήλη αποσφαλμάτωσης έχει ένα κουμπί **Test**. Πατήστε το και ο επεξεργαστής συντάσσει μια δοκιμή από εκείνο ακριβώς το μήνυμα: ό,τι μπήκε από την πηγή απ' όπου μπήκε, ξαναβαλμένο εκεί, και ό,τι έδειξε αυτός ο κόμβος Debug, αναμενόμενο εδώ. Αλλάξτε ό,τι θέλετε, γιατί μια μέτρηση με χρονοσήμανση ελέγχεται καλύτερα με `assert` παρά καρφωμένη στο χιλιοστό. Πατήστε **Add to tests** και μπαίνει στη σουίτα δίπλα στο αρχείο της ροής, στο τέλος, με ό,τι ήταν ήδη γραμμένο να μένει ακριβώς όπως ήταν, σχόλια μαζί. Ένα όνομα που η σουίτα έχει ήδη παίρνει έναν αριθμό στο τέλος αντί να αντικαταστήσει κάτι.

Πώς ξέρει ο επεξεργαστής τι μπήκε: το runtime κρατά τα τελευταία 64 μηνύματα που μπήκαν στη ροή από μια πηγή και τα τελευταία 64 που έφτασαν σε έναν κόμβο Debug, με το id που φέρει ένα μήνυμα από κόμβο σε κόμβο. Είναι ένας δακτύλιος με όριο μεγέθους, και ένα μήνυμα πάνω από 64 KB δεν κρατιέται καθόλου, οπότε δεν μπορεί ποτέ να είναι αυτό που θα μεγαλώσει ένα pod. Ένα μήνυμα που έχει εξοριστεί ή που ένας κόμβος αντικατέστησε με νέο στη διαδρομή δεν μπορεί να γίνει δοκιμή, και ο επεξεργαστής το λέει αντί να μαντεύει τι μπήκε.

Ο πίνακας **Tests** τρέχει τη σουίτα στο αντίγραφο εργασίας, αναπτυγμένο ή όχι, κι αυτό είναι το νόημα: το μαθαίνετε πριν από την ανάπτυξη. Κάθε κόμβος από τον οποίο πέρασε μια επιτυχημένη δοκιμή παίρνει ένα τικ, κάθε κόμβος που αφορά μια αποτυχία παίρνει ένα σταυρό με τον λόγο στο πέρασμα του δείκτη, και ένα κλικ σε μια αποτυχία σας πηγαίνει στον κόμβο της. Αλλάξτε οτιδήποτε και τα σημάδια φεύγουν, γιατί περιγράφουν μια ροή που δεν υπάρχει πια. Το **Edit** ανοίγει ολόκληρη τη σουίτα ως YAML. Μια ανάπτυξη που η [πύλη](#η-πύλη-ανάπτυξης) αρνείται καταλήγει στον ίδιο πίνακα, με τις αποτυχίες στους κόμβους.

Όλα αυτά τρέχουν σε πραγματικό πρόγραμμα περιήγησης απέναντι στο πραγματικό εκτελέσιμο σε κάθε pull request.

## Η πύλη ανάπτυξης

Οι δοκιμές στον φορητό κάποιου αποδεικνύουν τη ροή που είχε στον φορητό του. Η πύλη αποδεικνύει αυτή που αναπτύσσεται. Κρατήστε τη σουίτα στο instance, δίπλα στο αρχείο ροής που δοκιμάζει (το `data/flows.test.yaml` δίπλα στο `data/flows.json`, μέσω `PUT /tests` ή του επεξεργαστή), ενεργοποιήστε το `tests.gate`, και κάθε ανάπτυξη τη τρέχει απέναντι στις ροές που πρόκειται να στήσει. Αυτή που δεν περνά απορρίπτεται, με 422 και ολόκληρη την αναφορά:

```
$ hotloop-flow deploy -file flows.json -note "raise the alarm at 95"
1 changed

Tab "Line 3" (t1)
  ~ switch "over limit?" (chk)
      rules[0].v: "80" -> "95"
hotloop-flow: the deploy was refused: 1 of 2 flow tests didn't pass, and the flows already running are untouched; "a high reading raises the alarm and nothing else": expect 1: switch "over limit?" (chk): nothing sent from port 1

--- FAIL: a high reading raises the alarm and nothing else (0.00s)
    expect 1: switch "over limit?" (chk): nothing sent from port 1
    expect 2: switch "over limit?" (chk): expected nothing, and 1 message(s) sent from port 2
      at 0s: {"payload":92.5,"topic":"line3/temp"}
    expect 3: debug "alarm out" (alarm-out): nothing received
--- PASS: a negative reading is caught, not alarmed on (0.00s)
FAIL	flows.test.yaml	1 passed, 1 failed, 0 errors (0.00s)
```

Είναι πραγματική εκτέλεση: το εκτελέσιμο με την πύλη ενεργή, η σουίτα από την αρχή αυτής της ενότητας φυλαγμένη δίπλα στο αρχείο ροής της και ένα token ανάπτυξης.

**Οι ροές που ήδη τρέχουν δεν το καταλαβαίνουν.** Η πύλη τρέχει πριν γραφτεί ένα byte: όχι αρχείο ροών, όχι διαπιστευτήρια, όχι εγγραφή ανάπτυξης, όχι επανεκκίνηση. Η άρνηση καταγράφεται στο ίχνος ελέγχου ως `deploy.refused` που λέει ότι οι δοκιμές απέτυχαν. Και οι δοκιμές δεν τρέχουν καθόλου στη διεργασία του διακομιστή. Τρέχουν σε θυγατρική διεργασία, αυτό το ίδιο εκτελέσιμο ως `hotloop-flow test -stdin`, στο οποίο δίνονται οι υποψήφιες ροές και η σουίτα από το stdin, γιατί μια δοκιμή ξεκινά κάθε κόμβο της ροής και κάποιοι καταχωρούνται εκεί που τους μοιράζεται ολόκληρη η διεργασία: ένα Link In με το id του, μια διαδρομή HTTP με το μονοπάτι της. Αν έτρεχε εδώ μέσα, το Link In του υποψηφίου θα απαντούσε για αυτό της ροής που τρέχει μόλις ξεκινούσε. Σε θυγατρική δεν μπορεί να αγγίξει τίποτα από όσα χρησιμοποιεί η γραμμή, ένας κόμβος που πανικοβάλλεται σε δική του goroutine ρίχνει τη δοκιμή και όχι το εργοστάσιο, και η μνήμη επιστρέφεται όταν τερματίσει. Η δοκιμή το αποδεικνύει με τον δύσκολο τρόπο: ο απορριφθείς υποψήφιος έχει το ίδιο Link In, και μετά την άρνηση ένα μήνυμα μέσω του συνδέσμου της ροής που τρέχει φτάνει ακόμα.

Τρεις αποφάσεις που αξίζει να γνωρίζετε. **Είναι απενεργοποιημένη από προεπιλογή**, γιατί μια πύλη που δεν ζήτησε ο χειριστής είναι μια ανάπτυξη που αποτυγχάνει στις 3 τα ξημερώματα για λόγο που κανείς στη βάρδια δεν έχει ακούσει. **Οι δοκιμές που δεν μπορούν να τρέξουν δεν περνούν**: μια θυγατρική που δεν ξεκινά ή μια εκτέλεση μεγαλύτερη από το `tests.timeout` απορρίπτει την ανάπτυξη και λέει ποιο από τα δύο. Και **οι επαναφορές δεν περνούν από την πύλη.** Μια επαναφορά είναι ο τρόπος να βγει κανείς από κακή κατάσταση σε μία που έτρεξε ήδη, και το να τη σταματήσεις για τις σημερινές δοκιμές είναι ο τρόπος να μακρύνει μια διακοπή. Με την πύλη ενεργή και χωρίς σουίτα δεν υπάρχει τίποτα να αποτύχει, οπότε η ανάπτυξη προχωρά και το αρχείο καταγραφής λέει γιατί δεν ελέγχθηκε.

## Context και διαπιστευτήρια

Κάθε δοκιμή ξεκινά με κενό context, ό,τι κι αν άφησε η προηγούμενη. Ένας μετρητής που μια δοκιμή ανέβασε στο 42 δεν είναι εκεί που ξεκινά η επόμενη, γιατί μια σουίτα όπου η δεύτερη δοκιμή περνά μόνο αν έτρεξε πρώτα η πρώτη είναι μια σουίτα που λέει ψέματα τη μέρα που κάποιος τρέξει μία δοκιμή μόνη της. Έτσι, μια δοκιμή που χρειάζεται μετρητή στο 41 το λέει, και λέει τι πρέπει να κρατά το context όταν τελειώσει:

```yaml
  - name: picks up where the line left off
    context:                        # what the test starts with
      global: {limit: 90}
      flow: {Line 3: {count: 41}}   # flow context, by tab label or id
    credentials:                    # by node name or id; never the real ones
      historian: {token: test-token}
      plc api: {password: s3cret}
    inject: [{node: count, msg: {payload: 95}}]
    expect:
      - {node: out, msg: {count: 42}}
      - context:                    # what it holds at the end
          global: {alarm: true}
          flow: {Line 3: {count: 42}}
          node: {count: {last: 95}} # node context, by node name or id
```

Το `context` σε μια προσδοκία ταιριάζεται όπως το `msg`, και το `null` σημαίνει ότι το κλειδί δεν πρέπει να είναι ορισμένο. Μια αποτυχία λέει τι κρατά πράγματι το πεδίο, γιατί η συνηθισμένη απάντηση είναι ένα τυπογραφικό: `flow context of "Line 3" (t1): cuont: not set; it holds count`.

Μια δοκιμή δεν βλέπει ποτέ τα πραγματικά διαπιστευτήρια. Τρέχει με αυτά που ονομάζει, κι αυτό την κάνει ασφαλή να κατατεθεί, και φτάνουν σε έναν κόμβο ακριβώς όπως θα έφταναν τα πραγματικά: ο κωδικός ενός αιτήματος HTTP εμφανίζεται στην κεφαλίδα `Authorization` που θα έστελνε, και μια ρύθμιση InfluxDB που δεν ξεκινά χωρίς token ξεκινά με αυτό της δοκιμής. Ένας κόμβος που διαβάζει κωδικό από προσαρτημένο αρχείο μέσω `ew_credentialFiles` παίρνει αντί γι' αυτό το διαπιστευτήριο της δοκιμής για εκείνο το πεδίο, επειδή μια δοκιμή δεν διαβάζει τίποτα από τον δίσκο, και κενό όταν η δοκιμή δεν ονομάζει κανένα.

Το context ζει στη μνήμη για μια δοκιμή, ποτέ στη βάση κατάστασης, οπότε μια δοκιμή δεν μπορεί να διαβάσει ό,τι άφησαν οι ροές που τρέχουν ούτε να τους αφήσει κάτι. Ένα fixture είναι YAML μέσα στη δοκιμή, όχι ένα αρχείο που προσποιείται βάση δεδομένων.

## Τίποτα δεν βγαίνει από τη δοκιμή

Μια δοκιμή που θα έτρεχε στ' αλήθεια το MQTT Out σας θα δημοσίευε στον broker του εργοστασίου, και τότε δεν είναι δοκιμή, είναι ανάπτυξη. Γι' αυτό σε μια δοκιμή κάθε κόμβος που μιλά με τον κόσμο έξω από τη διεργασία παίρνει ένα αντικαταστάτη: MQTT είσοδο και έξοδο, HTTP in, response και request, PostgreSQL, InfluxDB, TCP και UDP είσοδο, έξοδο και request, WebSocket είσοδο και έξοδο με τον listener και τον client πίσω τους, τους κόμβους αρχείων, `exec`, `scan` και `netinfo`.

Ο κόμβος κάνει ακόμα όλη τη δουλειά του μέχρι το καλώδιο. Το MQTT Out υπολογίζει ακόμα το topic, το QoS και τα bytes· το HTTP Request φτιάχνει ακόμα το URL, χτίζει το σώμα και ακολουθεί τις ανακατευθύνσεις· ο κόμβος PostgreSQL χτίζει ακόμα το SQL και τις παραμέτρους του. Μετά τα παραδίδει στον αντικαταστάτη, που τα καταγράφει και απαντά με ό,τι έχει σεναριοποιήσει η δοκιμή. Χωρίς σενάριο, η απάντηση είναι τίποτα και επιτυχία: καμία γραμμή, ένα κενό 200, μια εντολή που τερμάτισε με 0. Οι πηγές (MQTT In, HTTP In, TCP και UDP In, WebSocket In, Watch) δεν εγγράφονται, δεν ακούν και δεν ρωτούν, οπότε ό,τι φτάνει είναι ό,τι εγχέει η δοκιμή.

```yaml
  - name: the limit comes from the database and the alarm goes to the broker
    inject:
      - node: reading
        msg: {topic: "3", payload: 92.5}
    replies:
      - node: lookup limit                   # a PostgreSQL query
        reply: {rows: [{limit_c: 90}]}
      - node: maintenance api                # an HTTP Request
        reply: {statusCode: 503, payload: {error: down for maintenance}}
      - node: historian                      # InfluxDB, and it's down
        error: connection refused
    expect:
      - node: lookup limit
        sent: {query: "select limit_c from limits where line = $1", params: ["3"]}
      - node: to the plant                   # an MQTT Out
        sent: {topic: line3/alarm, payload: HIGH, qos: 1, retain: true}
      - node: errors
        error: connection refused
```

Το **`sent`** είναι ό,τι θα είχε στείλει ο κόμβος, ταιριασμένο όπως το `msg`. Το **`replies`** σεναριοποιεί ό,τι επιστρέφει: η πρώτη απάντηση που αναφέρεται για έναν κόμβο απαντά στην πρώτη του κλήση, η επόμενη στη δεύτερη, και η τελευταία συνεχίζει να απαντά, οπότε το «απάντησε και μετά σταμάτησε» είναι δύο γραμμές. Το **`error`** κάνει την κλήση να αποτύχει όπως θα αποτύγχανε η πραγματική, ώστε η διαδρομή που ακολουθεί η ροή σας όταν ο historian είναι εκτός να δοκιμαστεί πριν βγει εκτός.

| Κόμβος | `sent` | `reply` |
|---|---|---|
| MQTT Out | `topic`, `payload`, `qos`, `retain` | |
| HTTP Request | `method`, `url`, `headers`, `payload` | `statusCode` (200), `headers`, `payload` |
| HTTP Response | `statusCode`, `headers`, `payload` | |
| PostgreSQL | `query`, `params` | `rows` για ερώτημα, `rowCount` για insert |
| InfluxDB | `line`, το line protocol | |
| TCP Out, UDP Out | `host`, `port`, `payload` (`session` όταν απαντά) | |
| TCP Request | `host`, `port`, `payload` | `payload`, διαβασμένο όπως ο κόμβος διαβάζει πραγματική απάντηση |
| WebSocket Out | `payload` (`session` όταν απαντά) | |
| File | `filename`, `action`, `payload` | |
| File In | `filename` | `payload`, τα περιεχόμενα |
| exec | `command`, `args` | `stdout`, `stderr`, `code` (0) |
| scan | `range`, `ports` | `devices` |
| netinfo | | `interfaces` |

Μερικά πράγματα μια δοκιμή δεν τα ελέγχει, επίτηδες, γιατί ανήκουν στο μηχάνημα και όχι στη ροή: η λίστα επιτρεπόμενων του `exec`, τα πεδία διαδρομών και ανακάλυψης και τα πιστοποιητικά ενός `tls-config`. Σε δοκιμή τίποτα δεν εκτελείται, ανοίγει, ερευνάται ή καλείται, οπότε δεν υπάρχει τίποτα να περιοριστεί ή να κρυπτογραφηθεί, και η ανάπτυξη εξακολουθεί να λογοδοτεί για όλα αυτά στο μηχάνημα όπου προσγειώνεται.

Η απόδειξη είναι μια δοκιμή που στρέφει κάθε έναν από αυτούς τους κόμβους σε μια θύρα TCP, μια θύρα UDP και έναν κατάλογο που κρατά η δοκιμή, περνά μια μέτρηση μέσα από όλους, ελέγχει byte προς byte τι θα είχε στείλει καθένας και μετά μετρά: μηδέν συνδέσεις, μηδέν datagram, κανένα αρχείο γραμμένο, τίποτα εκτελεσμένο. Ένας κόμβος που φτάνει προς τα έξω και δεν έχει αντικαταστάτη απορρίπτεται με το όνομά του πριν τρέξει οτιδήποτε, και η δοκιμή της παλέτας αποτυγχάνει αν κάποιος προσθέσει έναν.
