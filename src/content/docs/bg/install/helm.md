Chart-ът разгръща две натоварвания: gateway (Deployment, който не пази собствено устойчиво състояние) и TimescaleDB (StatefulSet с том). Това е по подразбиране. `database.type` избира друга база данни: обикновен PostgreSQL или SQLite, което изобщо не е второ натоварване ([SQLite](#sqlite), по-надолу).

## Инсталиране

През App Store на таблото на EmberNet или директно:

```bash
helm install hotloop ./charts/hotloop \
  --namespace hotloop --create-namespace
```

Или от хранилището с chart-ове, което е и адресът, към който сочи App Store:

```bash
helm repo add hotloop https://hotloop.io/hotloop
helm install hotloop hotloop/hotloop \
  --namespace hotloop --create-namespace
```

Тази втора форма работи от 4.16.0, първата версия, публикувана като `hotloop`. Последната преди нея беше `industrial-iot` 4.3.1, под старото име, а надграждането от нея е отделна процедура: вижте "Upgrading from 4.3.1" в бележките за 4.16.0 в README. Старият адрес на хранилището, `https://embernet-ai.github.io/industrial-iot/`, връща 404.

Гола инсталация работи. Chart-ът генерира парола за базата данни и MCP токен в Secret на версията и ги преизползва при надграждане, така че нищо не трябва да се подава и надграждането не сменя паролата под работеща база данни.

За достъп не са нужни ingress или поддомейн. Таблото открива приложението по етикетите му от магазина и го препраща през прокси на вътрешния адрес в клъстера:

```
<release>.<namespace>.svc.cluster.local:8080
```

За да го разгледате директно:

```bash
kubectl -n hotloop port-forward svc/hotloop 8080:8080
```

## Стойности, които си струва да зададете

### Удостоверяване

От 4.4.0. Вижте [Удостоверяване и потребители](/bg/iot/authentication/) за пълния модел; това е страната на chart-а.

```yaml
auth:
  enabled: true    # the default; requires a login
  insecure: false  # set true only for a deployment truly isolated behind the
                    # dashboard's own NetworkPolicy -- see AUTH.md
```

С `enabled: true` (по подразбиране) chart-ът генерира администраторски акаунт в Secret на версията при първата инсталация, както генерира паролата на базата данни и MCP токена, и го преизползва при надграждане:

```bash
kubectl get secret hotloop -n hotloop \
  -o jsonpath='{.data.admin-password}' | base64 -d
```

Изричното задаване на `auth.admin.password` замества генерираната.

### Безопасност

Стойностите, които решават дали този под може да движи машини.

```yaml
safety:
  allowWrites: false      # the master switch -- off by default since 4.4.0
  allowMcpWrites: true    # agents (MCP) write wherever an operator could, once writes are on
  confirmWrites: true     # the UI asks before writing
```

Записите са изключени по подразбиране. Тагът е само за четене, докато собственият му флаг `writable` не бъде зададен, стойност извън конфигурирания обхват на тага се отхвърля (никога не се подрязва: да изпратите 250, когато някой е въвел 500, е да правите нещо друго тихомълком), и всеки опит, **включително всяко отхвърляне**, се записва с участника и източника. Но свежата инсталация не бива да изисква и трите условия да съвпаднат, за да е безопасна, затова самият главен превключвател започва затворен.

За да включите записите, след като разгръщането е прегледано:

```yaml
safety:
  allowWrites: true
```

Това е всичко: MCP клиентите четат и пишат като оператор, със същите права, записваеми тагове и обхвати. `allowMcpWrites` се доставя включен във всеки chart; съществува за разгръщане, което реши друго, и никъде не е стойност по подразбиране.

### Историк

```yaml
historian:
  retentionDays: 90     # 0 keeps everything until the volume fills
  useTimescale: true

logbook:
  retentionDays: 90     # entity state changes; 0 keeps everything (see LOGBOOK.md)

database:
  postgresql:
    persistence:
      size: 20Gi
      storageClass: longhorn
```

Размерът зависи от броя тагове, честотата на сканиране и мъртвите зони. Хиляда тага на една секунда без мъртви зони са около 86 милиона реда на ден; същият завод с разумни мъртви зони обикновено е с порядък по-малко. Задайте мъртви зони, преди да купувате хранилище.

`useTimescale: false` налага пътя с вградено партициониране, какъвто е при работа срещу обикновен PostgreSQL. Полезно за възпроизвеждане на разгръщане на ръба.

**Когато образът на TimescaleDB се смени.** Образът носи библиотеката на всяка по-стара версия, така че база данни, създадена с по-стар образ, продължава да работи с новия, но със старата версия на разширението, и остава там, докато някой не изпълни `ALTER EXTENSION timescaledb UPDATE`. Gateway го прави при стартиране: сравнява инсталираната версия с тази, която доставя сървърът, и ако се различават, изпълнява обновяването като първи оператор на свежа връзка (TimescaleDB го отказва в сесия, която вече е заредила старата версия). Журналът казва `timescaledb extension updated from=... to=...`. Това изисква суперпотребител, какъвто е потребителят на включената база данни. Срещу външна или управлявана база данни, където не е, получавате предупреждение с командата за изпълнение, а историята продължава да работи на старата версия междувременно. Случва се само при включен `useTimescale` и миграции, които се изпълняват при стартиране (`HOTLOOP_DB_MIGRATE`, включено по подразбиране).

### Запитване

```yaml
runtime:
  defaultPollIntervalMs: 1000
  minPollIntervalMs: 100      # a floor applied to every device
  timeoutMs: 10000
  maxConcurrentPolls: 32
```

`minPollIntervalMs` се налага, а не се приема на доверие. Запитване на 10 ms към сериен gateway е отказ на услуга с допълнителни стъпки.

### OPC UA клиент

```yaml
opcuaClient:
  persistence:
    enabled: true      # off by default
    size: 64Mi
```

Устройство, което се свързва със защитен OPC UA сървър или влиза с потребителско име и парола, които сървърът изисква криптирани, пази сертификат и хранилище за доверие на одобрените сертификати на сървъри (`HOTLOOP_OPCUA_CLIENT_PKI_DIR`, `/data/opcua-client-pki`). Включете това, преди да добавите такова устройство: коренната файлова система е само за четене, така че без тома устройството съобщава грешка, която го казва, вместо да се свърже със сертификати, които биха се загубили при следващия рестарт. Изключено е по подразбиране, защото добавя PersistentVolumeClaim към съществуваща инсталация, който остава в Pending на клъстер без StorageClass по подразбиране. Анонимните устройства по незащитен канал не го ползват. Одобряването на сертификата на сървър и всичко останало за тези устройства е в [Протоколи и драйвери](/bg/iot/protocols/#opc-ua-сигурност-и-идентификационни-данни).

### Мрежа

```yaml
networkPolicy:
  enabled: true
  ingress:
    - from:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: dashboard-system
      ports:
        - protocol: TCP
          port: 8080
```

Ограничете ingress до namespace на таблото, щом е известен. Egress е умишлено неограничен: това приложение съществува, за да достига оборудване на адреси, които никой не може да изброи предварително, а egress политика, която тихо блокира запитване, прилича на счупен драйвер, а не на правило на защитната стена.

### Хардуер: USB радиа, серийни адаптери и Bluetooth

От 4.19.7 всеки chart на HotLoop (Gateway, IoT, Edge и Edge Relay) се доставя с включен достъпа, от който хардуерът има нужда, така че обикновена инсталация от App Store или от helm вижда какво е включено във възела без ръчна редакция, в мрежата на подовете. Това е блокът `hardware:` в `values.yaml`: три превключвателя, включени по подразбиране, и една опция, изключена по подразбиране:

| Стойност | По подразбиране | Какво прави |
|---|---|---|
| `hardware.privileged` | `true` | Контейнерът на приложението работи привилегировано (`privileged: true`, `allowPrivilegeEscalation: true`) и като root (`runAsUser: 0`, `runAsNonRoot: false`, без премахване на capabilities). Root, защото серийният USB възел е `root:dialout 0660`, а D-Bus политиката на BlueZ пуска root и групата `bluetooth`; потребител на контейнера в нито една от двете не отваря нищо. Коренната файлова система остава само за четене, а init контейнерът и включената база данни запазват собствения си контекст без root и без capabilities. |
| `hardware.usbDevices.enabled` | `true` | `/dev` на възела (`hardware.usbDevices.hostPath`) се монтира в `/dev`: серийни USB адаптери (`/dev/ttyUSB*`, `/dev/ttyACM*`, `/dev/serial/by-id/*`), включително такъв, включен след стартирането на пода. На привилегирован контейнер се дават само устройствата, които са съществували при стартирането му; монтирането е това, което кара включена наново пръчка да се появи. |
| `hardware.bluetooth.enabled` | `true` | D-Bus директорията на възела (`hardware.bluetooth.dbusPath`, `/run/dbus`, която съдържа `system_bus_socket`) се монтира на същия път, така че клиентът достига BlueZ на възела. Създава се празна на възел без D-Bus, така че подът пак стартира там. |
| `hardware.bluetooth.hostNetwork` | `false` | Опцията, която се включва по желание, изключена по подразбиране, за онова, което се нуждае от мрежата на възела: Bluetooth сокетите на ядрото (HCI, L2CAP) съществуват само в мрежовото пространство от имена на възела, така че клиент, който отваря такъв директно, и откриване, което слуша в собствената мрежа на възела (mDNS, SSDP, multicast на радио), се нуждаят от нея. Клиент, който минава през D-Bus API на BlueZ, се нуждае само от монтирания сокет и работи от мрежата на подовете. Включено, подът работи в мрежата на възела с последиците, описани в [Мрежа](#мрежа). |

Какво прави HotLoop с това днес: още нищо. HotLoop няма собствен код за Bluetooth, Z-Wave или сериен USB (Zigbee идва през мост Zigbee2MQTT върху MQTT, вижте [вградения MQTT брокер](/bg/iot/broker/)); това е достъпът, от който се нуждае функция или sidecar, четящ радио, подготвен, преди да бъде поискан.

Какво струва, умишлено и решено: подът е root на възела (привилегирован, с `/dev` на възела), а NetworkPolicy по подразбиране на chart-а остава включена за това, което покрива. Подът остава в мрежата на подовете. Изключете коя да е част с `--set hardware.privileged=false --set hardware.usbDevices.enabled=false --set hardware.bluetooth.enabled=false`; с изключени и трите изходът е, ред по ред, подът, който 4.19.6 генерираше (без root, всички capabilities премахнати, коренът само за четене, мрежа на подовете). За онова, което се нуждае от мрежата на възела, задайте `hardware.bluetooth.hostNetwork=true` (или `hostNetwork=true`): страницата тогава отговаря на всеки адрес на възела на `service.targetPort`, един HotLoop на възел на порт, NetworkPolicy не се прилага към пода, а `nodeSelector` го закрепва към възела, чието радио трябва да вижда.

### Разгръщания на ръба

Образът на приложението е изграден за amd64 и arm64, а TimescaleDB 2.30.1-pg17 е multi-arch, така че историкът не е това, което спира инсталация на ръба.

```yaml
resources:
  requests: {cpu: 100m, memory: 128Mi}
  limits:   {cpu: 500m, memory: 256Mi}

database:
  postgresql:
    persistence: {size: 5Gi}
    resources:
      requests: {cpu: 100m, memory: 256Mi}
      limits:   {cpu: 500m, memory: 512Mi}

historian:
  retentionDays: 30

nodeSelector:
  kubernetes.io/arch: arm64
```

### Публикуване нагоре през Sparkplug

Gateway на ръба може също да публикува всичко, което чете, към централен, като Sparkplug B възел на ръба. Вижте [Публикуване на ръба и store-and-forward](/bg/edge/edge-publish/) за това какво публикува и как се държи опашката за препращане; това е страната на chart-а.

```yaml
edgePublish:
  enabled: true
  broker: tcp://central.example.local:1883
  group: Plant1
  node: press-line-3          # empty uses the release name
  username: press-line-3
  existingSecret: central-mqtt # key "password", or set secretKey
  tls: false
  queueMaxBytes: 536870912     # 512 MiB; the default is 64 MiB, and 0 is unbounded
  persistence:
    size: 1Gi
```

Какво променя включването, и защо:

- **PVC от 1Gi за опашката за препращане**, монтиран в `/data/edge-publish`. Там се трупат показанията, докато връзката нагоре е прекъсната, така че трябва да надживее пода. `persistence.enabled: false` я слага на emptyDir, който оцелява при рестарт на контейнера и при нищо друго.
- **Deployment се обновява с `Recreate`.** Опашката е един файл с ключалка. Постепенно обновяване стартира първо новия под, новият под не може да отвори опашката, никога не става готов и разгръщането стои завинаги. Recreate спира първо стария; губите няколко секунди запитване при всяко надграждане.
- **`replicaCount` трябва да е 1**, и chart-ът отказва да се визуализира иначе. Две реплики биха били двама издатели, претендиращи за един Sparkplug възел.
- **Идентификаторът на възела е по подразбиране името на версията**, не името на хоста на пода. Името на хоста се сменя при всяко разгръщане, а Sparkplug хост би виждал чисто нов възел на ръба всеки път.

Паролата никога не е в стойност по подразбиране в открит текст. Оставете `password` и `existingSecret` празни за анонимен брокер и не се създава Secret; задайте `password` и chart-ът я слага в `<release>-edge-publish`; задайте `existingSecret`, за да ползвате такъв, който управлявате сами.

### Външна база данни

```yaml
database:
  postgresql:
    enabled: false
    auth:
      existingSecret: my-db-credentials
      secretKey: password
  external:
    host: timescale.plant.local
    port: 5432
    database: industrial
    username: industrial
  sslMode: require
```

Приложението открива TimescaleDB и превръща `tag_history` в хипертаблица, когато разширението е налично. Срещу обикновен PostgreSQL се връща към вградено партициониране по диапазони, вместо да се провали.

Решението се записва и е **трайно**. База данни, създадена като хипертаблица, отказва да стартира срещу сървър без разширението, вместо тихомълком да пише другаде; ако видите тази грешка, сте насочили приложението към различна база от тази, върху която е изградено.

### SQLite

Базата данни е настройка, не образ. Всеки продукт работи върху SQLite, Postgres или TimescaleDB от един и същ двоичен файл (IoT пропуска TimescaleDB, вижте по-долу):

| Променлива | По подразбиране | Какво прави |
|---|---|---|
| `HOTLOOP_DB_TYPE` | `postgres` | `postgres` или `sqlite`. TimescaleDB е `postgres` с разширението на сървъра |
| `HOTLOOP_DB_PATH` | `/data/hotloop.db` | Файлът на SQLite. Само SQLite го чете |

SQLite е чистата Go версия (`modernc.org/sqlite`), компилирана във всеки образ, така че няма втори контейнер, няма Postgres образ от 300 MB върху SD карта, а arm изграждането остава статично. Сложете файла на том, който надживява контейнера, а на Pi сложете този том на USB SSD. Историк, който пише върху SD карта цял ден, е начинът да купите много SD карти.

Какво е същото: всяка таблица, всяка колона, всяка функция. Какво е различно:

- Историята е една таблица с индекс, не партиции или хипертаблица, а съхранението изтрива стари редове вместо да изхвърля месеци. Обект с години история на всяка секунда иска Postgres или TimescaleDB, а преместването там е резервно копие и възстановяване (BACKUP.md).
- По един пишещ наведнъж. SQLite се редува при записите и чете успоредно с тях (WAL), което е предостатъчно за един HotLoop и помощник `--mcp-stdio` до него върху същия файл. Не е за две реплики върху мрежово хранилище: SQLite върху NFS се поврежда, така че разгръщането със SQLite е един под с локален том.
- Записите са `synchronous=FULL`: когато API казва, че е записало, то е на диска, с или без прекъсване на тока.

**HotLoop IoT** по подразбиране пази 30 дни история (`HOTLOOP_HISTORIAN_RETENTION_DAYS` пак печели, когато е зададена) и никога не изгражда хипертаблица: TimescaleDB е част от Edge и Gateway. Задайте `HOTLOOP_HISTORIAN_TIMESCALE=true` на IoT и той го казва при стартиране и работи върху обикновени партиции. База данни, преместена надолу от Edge или Gateway, която вече има хипертаблица, я запазва и продължава да работи.

#### Избор на база данни в chart-а

Една стойност, `database.type`, и всеки продукт приема онези, върху които работи:

| `database.type` | Какво се разгръща | IoT | Edge | Gateway |
|---|---|---|---|---|
| `timescaledb` | Приложението и TimescaleDB (StatefulSet и неговият том). История в хипертаблица | отхвърлено | по подразбиране | по подразбиране |
| `postgresql` | Приложението и обикновен PostgreSQL 17 (StatefulSet и неговият том). История в вградени партиции | по подразбиране | да | да |
| `sqlite` | Приложението самò, с файла на базата данни на собствен том | да | да | да |

```bash
helm install hotloop hotloop/hotloop-iot --namespace hotloop --create-namespace   --set database.type=sqlite
```

Ако поискате `timescaledb` за IoT, инсталацията се проваля и казва върху какво работи IoT (`database.type is "timescaledb", and HotLoop IoT runs on sqlite, postgresql`), а формулярът в App Store не го предлага. `helm lint` не го улавя (helm 3.22 го проверява чисто), така че отказва визуализацията. Пропускането на `database.type` дава собствената стойност по подразбиране на продукта, така че надграждане с `--reuse-values` отпреди съществуването на ключа запазва базата, която е имала.

`sqlite` генерира:

- `HOTLOOP_DB_TYPE=sqlite` и `HOTLOOP_DB_PATH=/data/db/hotloop.db`, и нито една от настройките за връзка с Postgres. Няма под на база данни, няма парола на база данни в Secret, няма init контейнер, който да чака такава.
- PersistentVolumeClaim с име `<release>-db` (`database.sqlite.persistence`: `size`, `storageClass`, `accessMode`, 10Gi и стойността по подразбиране на клъстера за начало), монтиран в `/data/db`. Директорията, не файлът: SQLite пази `-wal` и `-shm` до базата данни. Сложете я на локално хранилище; SQLite върху NFS се поврежда.
- Deployment с `Recreate`, не постепенно обновяване, защото томът е `ReadWriteOnce`, а файлът има един пишещ. `replicaCount` над 1 проваля инсталацията.

NetworkPolicy е непроменена и включена: собствената политика на приложението пак се прилага, а политиката на базата данни се визуализира само когато има под на база данни за защита.

Смяната на `database.type` на версия, която вече има данни, не премества данните. Новата база започва празна, така че преместването на завод между бази данни е резервно копие и възстановяване (BACKUP.md), както и с променливата. По-специално база данни, създадена като хипертаблица на TimescaleDB, отказва да стартира срещу обикновен PostgreSQL, така че не превключвайте съществуващ Edge или Gateway от `timescaledb` на `postgresql`, очаквайки да стартира.

#### Избор на база данни в Quadlet

Директорията на всеки продукт под `deploy/quadlet/` има файловете за PostgreSQL или TimescaleDB както бяха и директория `sqlite/` до тях: `hotloop.container` и `hotloop-data.volume`, приложението самò с файла в `/data/hotloop.db` на тома `hotloop-data`. Следва `:stable` и връща лошо обновяване по същия начин. Инсталирайте тези два файла вместо останалите (ползват едни и същи имена на единици) и направете два секрета вместо три: няма парола на база данни. [`deploy/quadlet/README.md`](/bg/install/quadlet/) има стъпките.

За обикновени Postgres партиции на Edge или Gateway под Quadlet запазете единицата на TimescaleDB и добавете `Environment=HOTLOOP_HISTORIAN_TIMESCALE=false` към `hotloop.container`. Единицата на IoT вече работи с обикновен PostgreSQL.

### Ключът за идентификационните данни на устройствата

```yaml
secretKey:
  enabled: true
  existingSecret: ""     # or a Secret you manage, with the key under secret.key
```

Паролите на устройствата (вход в UniFi конзола, парола за OPC UA или MQTT, HTTP API ключове) се криптират в базата данни с този ключ, така че дъмп или резервно копие съдържа шифрован текст. От кутията chart-ът генерира такъв в `<release>-secret-key` при първата инсталация, пази го при надграждане и го пази и при `helm uninstall` (`helm.sh/resource-policy: keep`), защото база данни, запазена на своя том, е безполезна за своите идентификационни данни без него. Монтира се като файл и се подава като `HOTLOOP_SECRET_KEY_FILE`, никога като променлива на средата.

Правете резервно копие на Secret отделно от копията на базата данни: ключ, който стои до копията, които защитава, не защитава нищо. За да доведете свой, `hotloop gen-secret-key` отпечатва такъв. Извън Kubernetes го запишете във файл, който само HotLoop може да чете, и насочете `HOTLOOP_SECRET_KEY_FILE` към него. Без ключ HotLoop работи, казва в стартовия си журнал, че паролите на устройствата се пазят както са въведени, и отказва да запази UniFi конзола. Вече запазените идентификационни данни се криптират при първото стартиране с ключ. Вижте [Резервни копия и възстановяване](/bg/iot/backup/#идентификационни-данни-на-устройства-и-тайният-ключ) какво означава това за възстановяването.

## Конфигурация и какво може да променя екранът Настройки

Почти всяка настройка идва от променлива на средата, която chart-ът задава от стойност на Helm. Това е правилното място: конфигурацията, която решава дали този процес може да командва машини, принадлежи на разгръщането, прегледана, а не на формуляр в уеб страница.

Екранът **Настройки** показва всичко, всяка настройка, действащата ѝ стойност, дали идва от базата данни, от променлива на средата или от вградената стойност по подразбиране, и променливата, която я променя. Повечето са само за четене, и това е смисълът: въпросът, на който отговаря, е "защо прави това и какво да променя?"

Четири настройки са идентичност на завода, а не поведение, и се редактират там. Съхраняват се в базата данни и влизат в сила веднага, защото един завод се преименува много по-често, отколкото се разгръща наново:

| настройка | променлива, която замества |
|---|---|
| Име на завода | `HOTLOOP_PLANT_NAME` |
| ID на обекта | `HOTLOOP_SITE_ID` |
| Часова зона | `HOTLOOP_TIMEZONE` |
| Потвърждение преди запис | `HOTLOOP_CONFIRM_WRITES` |

Под настройките има карти, които са данни, а не конфигурация, и се редактират по същата причина: **Потребители** ([Удостоверяване и потребители](/bg/iot/authentication/)), **Ескалация на аларми**, която казва кой се уведомява следващ, когато никой не потвърди аларма, и кога ([Известия за аларми](/bg/iot/notifications/#ескалация)), както и целите на историка и MQTT входовете. Каналите, които ескалацията може да ползва, остават на разгръщането, задавани от `HOTLOOP_NOTIFY_*`.

Съхранена стойност печели над променливата на средата, така че стойността на chart-а става отправна точка, а не последна дума. Часова зона, която машината не може да разреши, се отхвърля, вместо да бъде приета и тихомълком пренебрегната, което би оставило всеки времеви печат да се връща към UTC, без нищо да казва защо.

Същото важи за собствената стойност на разгръщането. Ако `HOTLOOP_TIMEZONE` (или `TZ`, когато тя не е зададена) назовава зона, която не се зарежда, HotLoop отказва да стартира и грешката назовава променливата и стойността. Преди свиваше рамене и работеше на UTC. Отчетите, графиците и сменните часове вървят по часовника на завода, а предположение с часове разлика е по-лошо от под, който казва защо не стартира.

Местоположението на обекта е `HOTLOOP_SITE_LATITUDE` и `HOTLOOP_SITE_LONGITUDE` (chart: `plant.latitude`, `plant.longitude`), десетични градуси, север и изток положителни. Изгревът, залезът и обектите и тригерите на слънцето се изчисляват от тях на устройството ([Слънцето](/bg/iot/sun/)). И двете или нито едно, а грешно спира стартирането с назована променлива. Екранът Настройки ги показва само за четене: правилата се задействат от изгрев, така че преместването му е разгръщане.

**Превключвателите за безопасност не се редактират и няма да се редактират.** `HOTLOOP_ALLOW_WRITES` е главният контрол върху това дали този процес може да командва оборудване; контрол, който може да бъде включен отново от същата браузърна сесия, която издава записите, не е контрол. `HOTLOOP_HISTORIAN_RETENTION_DAYS` също е само на разгръщането: политиката за съхранение се прилага към базата данни при стартиране, така че поле на екран би изглеждало като работещо и не би преместило никакви данни. Крайната точка отхвърля всеки ключ извън редактируемия набор **по име**, вместо да го пренебрегва.

Едно ограничение, казано, защото екранът също го казва: MCP сървърът изгражда инструкциите си при стартиране, така че обявява името на завода, с което е стартирал, докато подът не се рестартира. Всичко останало приема преименуването при следващата заявка.

## PostgreSQL 17

Базата данни на HotLoop е PostgreSQL 17 (с TimescaleDB 2.30.1 върху нея за Edge и Gateway, обикновен PostgreSQL 17.11 за IoT и за `database.type: postgresql`). Версиите преди това работеха на PostgreSQL 16, а PostgreSQL не отваря директорията с данни на друга основна версия. Затова преминаването се прави вместо вас, при надграждането, и няма нищо за изпълнение.

**В chart-а** подът на базата данни получава два init контейнера. Първият изпълнява образа на PostgreSQL 16 и, само когато томът съдържа данни от 16, копира тази инсталация в временен том. Вторият изпълнява новия образ и прави `pg_upgrade` в нова директория до старата. И двата оставят на мира свеж том или такъв, вече на 17. Надграждането е `helm upgrade`, нищо повече. Очаквайте подът на базата данни да стои в `Init`, колкото отнема копирането на данните, а приложението да го чака; `kubectl logs <release>-postgresql-0 -c pg-upgrade` е журналът.

**В Quadlet** `hotloop-db-upgrade.container` се изпълнява преди `hotloop-db.service` и прави същото в oneshot единица. Копирайте новите `hotloop-db.container`, `hotloop-db-upgrade.container` и `hotloop-db-upgrade.sh` от директорията на продукта си в директорията с единици и рестартирайте единицата на базата данни; [README на Quadlet](/bg/install/quadlet/) има командите. Единицата на базата данни изисква единицата за надграждане, така че устройство, получило само новата единица на базата данни, не стартира върху данни от 16 и казва защо: проваля се, не гадае. `journalctl -u hotloop-db-upgrade` е журналът. Единицата се изпълнява само когато томът съдържа данни от 16: на ново устройство и при всяко стартиране след надграждането systemd я пропуска (показва се като неактивна, не като неуспешна) и образът на PostgreSQL 16 никога не се тегли. Когато томът съдържа данни от 16, единицата първо тегли този образ.

Какво прави, по ред, всичко в `hotloop-pg-upgrade.sh` (един файл, същият, който изпълняват chart-ът и единиците):

1. Няма директория с данни или има такава, вече на 17: нищо, и го казва. Всяка друга основна версия се отхвърля, без да се променя нищо.
2. Стартира стария сървър веднъж на частен сокет и го спира чисто, което възпроизвежда журнала след прекъсване на тока и чете кодировката и локала, на които новият клъстер трябва да съответства.
3. Прави `initdb` на нова директория до старата с тези настройки, изпълнява `pg_upgrade` в режим на копиране (старата директория само се чете) и пренася `postgresql.conf`, `postgresql.auto.conf`, `pg_hba.conf` и `pg_ident.conf`.
4. Стартира новия сървър веднъж, за да докаже, че се отваря с крайните настройки, и събира статистиката на планировчика, която `pg_upgrade` не пренася.
5. Едва тогава разменя имената: старата директория става `pgdata.pg16`, новата `pgdata`.

Нужно ѝ е приблизително толкова свободно място до данните, колкото заемат данните, и проверява преди да започне. Ако нещо се провали преди стъпка 5, надграждането излиза с ненулев код, данните от 16 са точно каквито бяха, а базата данни не стартира върху наполовина изградена директория: в chart-а подът остава в `Init:Error`, в Quadlet единицата за надграждане се проваля, а единицата на базата данни зад нея никога не стартира. Поправете каквото казва журналът и стартирайте отново; недовършен опит се премахва и се прави наново. Разширението TimescaleDB минава във версията, в която е било, а приложението го обновява до доставената при следващото си стартиране, както винаги. Собствената насока на TimescaleDB за надграждане на PostgreSQL на място е `pg_upgrade` със старите и новите двоични файлове ([Tiger Data, "Upgrade PostgreSQL"](https://www.tigerdata.com/docs/deploy/self-hosted/upgrades/upgrade-pg)).

Резервното копие е самата стара директория. `pg_upgrade` в режим на копиране никога не пише в нея, така че `pgdata.pg16` е цялата база данни на PostgreSQL 16 такава, каквато беше, което е по-добро копие от дъмп и единственото, което прави възможен пътя назад по-долу. Собственото резервно копие на HotLoop ([Резервни копия и възстановяване](/bg/iot/backup/)) се прави от работещото приложение през работещата база данни, така че не може да се направи в стъпката, която се изпълнява преди стартирането на базата данни. Направете такова с по-старата версия преди надграждането така или иначе и го копирайте извън устройството.

### Връщане назад

`helm rollback` или връщането на предишния `hotloop-db.container` връща базата данни към образа на PostgreSQL 16 (автоматичното обновяване на Podman не го прави: то движи само приложението), а PostgreSQL 16 не отваря директория 17 (`database files are incompatible with server`, журналът казва, че директорията е инициализирана от версия 16). Нищо не се губи и нищо не е наполовина променено; базата данни просто не стартира. Това, от което предишната версия има нужда, е собствената ѝ директория 16, която е `pgdata.pg16`. Спрете базата данни, после върнете имената:

```sh
# chart: after the rollback, stop the database, swap in a one-off pod, start it
kubectl -n hotloop scale statefulset/hotloop-postgresql --replicas=0
kubectl -n hotloop run pgswap --rm -it --restart=Never --image=busybox \
  --overrides='{"spec":{"securityContext":{"runAsUser":999,"fsGroup":999},"containers":[{"name":"pgswap","image":"busybox","command":["sh","-c","cd /d && mv pgdata pgdata.pg17 && mv pgdata.pg16 pgdata"],"volumeMounts":[{"name":"d","mountPath":"/d"}]}],"volumes":[{"name":"d","persistentVolumeClaim":{"claimName":"data-hotloop-postgresql-0"}}]}}'
kubectl -n hotloop scale statefulset/hotloop-postgresql --replicas=1

# Quadlet: the volume is named hotloop-db
sudo systemctl stop hotloop.service hotloop-db.service
d=$(sudo podman volume inspect hotloop-db --format '{{.Mountpoint}}')
sudo mv "$d/pgdata" "$d/pgdata.pg17" && sudo mv "$d/pgdata.pg16" "$d/pgdata"
```

Това е базата данни такава, каквато беше при надграждането, без нищо записано оттогава. Връщането работи само веднъж: надграждането отказва да се изпълни, докато `pgdata.pg16` е на пътя, така че следващият опит за надграждане изисква първо `pgdata.pg17` и уреждане на старата директория. Напред е пътят, а връщането е за устройство, което изобщо не може да изпълнява 17. Правилото за връщане на самото приложение е непроменено: схемата на директорията 16 е тази, която версията преди надграждането е оставила, а версия, която намира миграции, които не познава, го казва, вижте [Миграциите само добавят](/bg/iot/migrations/).

### Когато сте доволни

`pgdata.pg16` остава, докато не го изтриете, защото изтриването му е изтриване на единствения път назад. Колкото е голяма базата данни, толкова е и то. След като устройството е работило на 17, колкото време желаете:

```sh
# chart
kubectl -n hotloop exec hotloop-postgresql-0 -c postgresql -- rm -rf /var/lib/postgresql/data/pgdata.pg16
# Quadlet
sudo rm -rf "$(sudo podman volume inspect hotloop-db --format '{{.Mountpoint}}')/pgdata.pg16"
```

### Изключване

`database.postgresql.upgrade.enabled: false` премахва init контейнерите. Том, който още е на 16, тогава пречи на базата данни да стартира, а преминаването е ваше. Оставете го включено: включено, свежа инсталация пак тегли образа на PostgreSQL 16 веднъж на възел, защото образът на init контейнер се тегли преди да се изпълни, и после никога не го изпълнява.

## Надграждане от 3.x

**Това е замяна, не надграждане.** 3.x беше друг продукт. Няма път за миграция на данните му, защото не споделя никакъв модел на данни с историк на тагове.

```bash
helm uninstall hotloop -n hotloop
# keep or delete the old PVCs deliberately, they hold the HA recorder database
helm install hotloop ./charts/hotloop -n hotloop
```

Неща, които вече не съществуват и ще бъдат отхвърлени, ако са зададени: `sidecarProxy`, `homeassistant`, добавките `mqtt`/`nodered`/`esphome`/`zigbee2mqtt`, `devices`, `cameras`, `customConfig`, `network.hostNetwork`.

## Връщане на обновяване

`helm rollback hotloop -n hotloop` връща образа на предишната версия. Не връща базата данни: версията мигрира при стартиране и това остава направено. Правилото и проверката са в [Миграциите само добавят](/bg/iot/migrations/).

Единственото, което връщане през версията с PostgreSQL 17 връща, е двигателят на базата данни: образът на базата данни на chart-а се връща на 16, който няма да отвори надградената директория. [Връщане назад](#връщане-назад) е изходът.

Безопасно е за една версия назад. Базата данни записва коя версия е приложила всяка миграция, а версия, която намира миграции от две или повече версии по-нови от нея, отказва да стартира:

```
refusing to start: this database's schema is more than one release ahead of
HotLoop 4.18.10. ...
```

Това не е неизправност, която да се заобикаля. Означава, че базата данни е стигнала по-далеч, отколкото тази версия някога е работила. Вървете напред към версия, която познава схемата, най-новата, или възстановете резервно копие, направено от версията, на която сте ([Резервни копия и възстановяване](/bg/iot/backup/)). Точно една версия назад стартира, с предупреждение в журнала, което назовава двете версии. Направете резервно копие преди надграждане; връщането не може да отмени данни, които по-новата версия е записала.

## Проверка на инсталация

```bash
kubectl -n hotloop get pods
kubectl -n hotloop logs deploy/hotloop | head -20
```

Здравото стартиране казва протоколите, на които говори, прилага миграциите, съобщава режима на историята и предупреждава за всичко, което си струва да се знае:

```
msg=starting version=4.0.0 protocols="[ethernet-ip http modbus mqtt mtconnect opcua s7comm]"
msg="writes are ENABLED: the UI, API, automations and MCP can all command devices"
msg="tag_history promoted to a hypertable" timescale=2.30.1
msg="history schema ready" mode=timescale
msg=listening addr=:8080 mcp=/mcp writes=true
```

После проверете етикетите, от които таблото има нужда. Това е проверката, която улавя отклонението, потвърдете **набора**, не броя, защото проверка на броя минава, докато наборът е грешен:

```bash
kubectl -n hotloop get svc <release> -o json \
  | jq -r '.metadata.labels | keys[] | select(startswith("embernet.ai/"))'
```

Точно четири, на Service и на пода:

```
embernet.ai/app-name
embernet.ai/gui-port
embernet.ai/gui-type
embernet.ai/store-app
```

Ако приложението работи, но липсва в Работещи приложения, етикетите на Service са първото място за поглеждане: таблото запитва Service по `embernet.ai/store-app`.

Разгръщане от App Store добавя още пет, от `tenantLabels`, които таблото подава: `embernet.ai/tenant`, `app-id`, `source`, `deployed-by` и `deployment-id`. Те отиват на всеки ресурс, който chart-ът визуализира, и на пода на gateway. Таблото чете наемателя от Service и никъде другаде, така че Gateway, разгърнат от магазина без `embernet.ai/tenant` на своя Service, не принадлежи на никого. Обикновен `helm install` не визуализира нито един от петте.

## Проби

- `/healthz`, liveness. Отговаря, докато процесът работи.
- `/readyz`, readiness. Допълнително изисква базата данни, така че под, загубил историка си, спира да приема трафик, вместо да сервира интерфейс, който не може да отговори на нищо.

Стартовата проба позволява две минути, защото първата инсталация изпълнява миграции, а пробата liveness не бива да я убие по средата на миграция.

## Изключване

`terminationGracePeriodSeconds: 45`. При SIGTERM приложението спира да приема заявки, после източва опашката на историка, така че вече взетите показания да се запишат, вместо да се изхвърлят. Прекалено кратък гратисен период губи всичко, което е било в движение.

## Отстраняване на проблеми

**Устройство стои в `connecting`.** Погледнете `lastError` на картата на устройството. Най-често защитна стена между пода и оборудването или грешен порт. Chart-ът не ограничава egress, така че NetworkPolicy, която го блокира, е нещо друго в клъстера.

**Таговете четат лошо качество.** Устройството отговори, но точката не. За Modbus проверете базата на адресите, `oneBased`, ако чертежите ви ползват номерация 40001. За OPC UA проверете дали идентификаторът на възела е разрешен; предпочитайте формата `nsu=`.

**Стойностите изглеждат правдоподобни, но са грешни.** При Modbus това е редът на думите, опитайте `CDAB`. Това е неизправността, която не се обявява, защото числото не е очевидно грешно.

**Нищо не се историзира.** Проверете диагностиката на екрана Протоколи. `filtered` брои показанията, потиснати от мъртвата зона, което работи както е предвидено; `dropped` брои показанията, загубени, защото базата данни не е смогнала, което не е така.

**MCP връща 401.** Bearer токенът. Прочетете го от Secret на версията.

**Всяка заявка към `/api/` връща 401.** Очаквано, щом `auth.enabled` е true и още никой не е влязъл, това е смисълът на 4.4.0. Прочетете генерираната администраторска парола от Secret на версията (вижте [Удостоверяване](#удостоверяване)) и влезте през интерфейса, или директно `POST /api/auth/login`. Вижте [Удостоверяване и потребители](/bg/iot/authentication/).

**Загубена администраторска парола и няма друг администраторски акаунт.** Генерирайте нов хеш и закърпете Secret, после рестартирайте пода, за да прочете средата наново; `EnsureAdminUser` няма да пипне акаунт, който вече съществува, така че това замества реда директно, вместо да минава през chart-а:

```bash
hotloop hash-password -password 'a-new-one'
kubectl exec -n hotloop deploy/hotloop -- \
  psql "$DATABASE_URL" -c \
  "UPDATE users SET password_hash = '<the hash>' WHERE username = 'admin'"
```

**Автоматизация е разрешена, но не работи.** Не се е компилирала. Екранът Автоматизации я показва като NOT ARMED с причината, а системният журнал има грешката.
