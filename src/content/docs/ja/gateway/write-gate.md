これは機械を動かせます。そのため、リクエストとデバイスの間に何があるのかを、コードが実行する順にそのままお見せします。

デバイスへ向かうすべての値は、**回避できない1つの関数**を通ります。画面でのクリック、`POST /api/write`、エンティティサービスの呼び出し、オートメーション、スクリプト、レシピ、MCP 経由のエージェントのすべてです。ポリシーはそこにだけあります。6か所にコピーしたチェックは7か所目で誰かが付け忘れるもので、その7か所目がいつも稼働中のプレスへ書き込む箇所だからです。ランタイムのどこかがゲートを通さずにデバイスの書き込みへ到達できる場合は、テストがビルドを失敗させます。パッケージのコピーに4種類の迂回を仕込み、そのすべてを検出することで、このテストが失敗しうることも証明しています。

読むより体験したい方は、[hotloop.io に対話式のバージョン](https://hotloop.io/gateway/#the-gate)があります。スイッチを切り替え、設定値を送って、どこで弾かれるかを確かめてください。

## チェックの順序

1. **呼び出し元に書き込み権限がある。** これはゲートの前、API の入口で行われます。ログイン中のユーザーが `POST /api/write` を呼ぶには `values.write` が必要です。オペレーターと管理者は持っていて、ビューアーは持っておらず、なければ API は 403 を返します。エージェントの入口は MCP の bearer トークンで、なければ 401 となり、ツール一覧も見えません。どちらの場合もゲートは何も聞かないため、書き込み監査には残りません。(エンティティサービスの呼び出しは動作が異なります。[後述](#どの入口も同じゲート)します。)
2. **書き込みがオンになっている。** `safety.allowWrites` はマスタースイッチです。4.4.0 からデフォルトはオフです。
3. **エージェントの書き込みがオンになっている。** `safety.allowMcpWrites` は、リクエストが MCP 経由で来たときだけ確認されます。マスタースイッチの範囲を狭めるだけで、迂回は決してできません。書き込みがオンでこちらがオフなら、オペレーターはタグに指令できますが、エージェントはできません。`safety.allowWrites` をオフにしたままこれをオンにすると、どちらが優先かを推測させず、Gateway は起動を拒否します。
4. **タグが有効化されている。** すべてのタグは、誰かが `writable` と印を付けるまで読み取り専用で、1つずつ意図して付けます。4,000 個のタグをブラウズでインポートしても、有効化されるものはありません。存在しないタグもここで拒否されます。
5. **値が範囲内にある。** タグに範囲があり値が数値のとき、範囲外の値は**拒否され、丸められることはありません**。最大 400 のタグに 500 と入力した人は間違えており、それを知る必要があります。黙って 400 を送るのは、誰も頼んでいないことをして、本人に知らせないことです。
6. **呼び出し元自身のチェックを通る。** エンティティは、自分だけが知っていることを加えます。数値のステップとより狭い範囲、テキストのパターンと長さ、選択肢、ループがいま手動でなければ拒否されるループの出力、呼び出しの途中で無効化または削除されたエンティティなどです。これはゲート内で、タグのポリシーと範囲の後に実行されるので、オペレーターは必ず先にタグについて知らされます。また監査行の前に実行されるので、エンティティの拒否もタグの拒否とまったく同じように記録されます。拒否することしかできません。値を変えたり、ゲートが止めたはずのものを通したりはできません。
7. **デバイスが稼働している。** HotLoop にそのデバイス用の実行中のワーカーがあることが条件です。無効化されたデバイスや一度も起動していないデバイスは、何もない場所へ値を投げる代わりに `the device is not connected` で拒否されます。

**そこで初めて監査行が開かれ、そこで初めて値が出ていきます。** 行を書き込めなければ、書き込みはまったく送られません。監査できない書き込みは後から誰も説明できない書き込みであり、動く機器ではそのような取引は割に合いません。行は、リクエストから切り離したコンテキストで結果と遅延を付けて完了するため、タイムアウトしたりキャンセルされたりした書き込みでも、何が起きたかが記録されます。

チェック 2 以降のすべての拒否は、拒否として監査されます。実行者、ソース、要求された値、置き換えるはずだった値、理由付きの `refused:` が1行に入り、システムログには警告が残ります。許可されていないタグに繰り返し指令しようとする行為は、書き残さなければ見えませんし、エンジニアは後からそれを見つけられるべきです。チェック 1 はゲートが目にしないので、書き込み監査にはありません。

### この順序の理由

ポリシーは監査行が開く前に実行されるので、拒否はたまたま失敗した試行ではなく、拒否として記録されます。監査行は値が通信路に出る前に開くので、固まった書き込みやプロセスごと落ちた書き込みでも、試みられた証拠は残ります。生産現場で「そのコマンドが出たのか分からない」は最悪の答えです。

### チェック 7 が捉えない 1 つのこと

チェック 7 が尋ねるのは、デバイスにワーカーがあるかどうかで、そのセッションがこの瞬間に立ち上がっているかではありません。ネットワークから外れて再接続中のデバイスは、これを通過します。監査行が開き、ドライバーにセッションがなく、書き込みは `the device is not connected` として失敗し、拒否ではなく失敗した試行として記録されます。どちらの場合も、デバイスには何も届きません。[ドライラン](#送る前に尋ねるドライラン)はセッションも確認し、それを最初に伝えます。

## 拒否ごとの応答

ステータスコードは、誰の問題かを示します。オペレーターはそう読むからです。

| 何が起きたか | エラーの内容 | HTTP |
|---|---|---|
| 入口で権限なし | `<user> does not have the "values.write" permission` | 403 |
| 書き込みがオフ | `writes are disabled on this deployment` | 403 |
| エージェントの書き込みがオフ | `writes from MCP clients are disabled on this deployment` | 403 |
| タグが有効化されていない | `this tag is not marked writable` | 403 |
| エンティティが無効 | `the entity is disabled` | 403 |
| タグが存在しない | そのタグと `not found` | 404 |
| 呼び出しの途中でエンティティが消えた、または許可しない状態(手動でないループ) | 変わった内容 | 409 |
| 値がタグの範囲外 | `value is outside the tag's configured range` | 422 |
| エンティティが値を受け付けない(ステップ、パターン、選択肢、独自の範囲) | `the value is not one this entity accepts` と理由 | 422 |
| デバイスが接続されていない | `the device is not connected` | 503 |
| デバイスが応答して拒否した | デバイス自身のメッセージ | 502 |
| 書き込みを監査できなかった、または API が分類できないその他のもの | `internal error (ref …)`、詳細はその参照番号でサーバーログに記録 | 500 |

API が分類できないものはすべて 500 です。以前は 400 でした。そのためデータベース障害がオペレーターに入力ミスだと伝え、存在しないタイプミスを探し回ることになっていました。

MCP にはステータスコードがありません。拒否は `isError` を付けたツール結果として、ゲート自身の言葉で返ります。

```
> write_tag tag=press-01/Zone1_Temp value=99 reason="testing"
write refused: press-01/Zone1_Temp: this tag is not marked writable
```

これは転送の失敗ではなく、答えです。呼び出しは理解された上で意図的に断られており、再試行しても同じ答えが返ります。

## 送る前に尋ねる:ドライラン

ゲートには、実行せずに尋ねるだけの第 2 の入口があります。同じチェックを同じ順序で行い、拒否には同じエラー文を返します。監査行は開かず、イベントも発生させず、何も集計せず、デバイスには決して届きません。実際の書き込みより一歩先まで確認します。ワーカーは動いているがセッションが切れているデバイスは、「このまま出る」ではなく接続されていないと報告されます。

利用できる場所:

- **エンティティサービスの呼び出し**: `POST /api/services/{domain}/{service}?dry_run=true`。判定とともに 200 を返します。行うはずの各書き込みは `would_write`、拒否される最初のものは `not_sent` として、理由はそのままの言葉で示されます。計画すらできなかったリクエスト(そのエンティティがない、ドメインが受け付けないサービス、不正なデータ)は、実際の呼び出しと同じステータスを返します。`dry_run` は `true` か `false` だけを受け付け、`yes` は 400 です。推測を誤ると質問が命令になってしまうからです。
- **コマンドプロンプト**は入力中に尋ね、誰かが確定する前に「Would be refused: ...」を表示します。
- **スクリプト**、4.17.0 で新登場: `POST /api/scripts/{id}/run?dry_run=true`、実行ドロワーの **Check first**、または `dryRun` 付きの MCP の `run_script`。すべてのステップをいまのプラントの状態に対してたどり、拒否される最初の書き込みで、ゲートの言葉とともに終了します。[スクリプト](/ja/iot/scripts/)を参照してください。
- **レシピ**、4.17.0 で新登場: 最初の値が出る前にすべてのターゲットがこれらのチェックを受け、1 つでも不正な値があればレシピ全体が拒否され、何も書き込まれません。`POST /api/recipes/{id}/validate` と MCP の `validate_recipe` は、適用せずに尋ねます。[レシピ](/ja/iot/recipes/)を参照してください。
- **Blueprints**、4.17.0 で新登場: **Check first** は、ルールがいま発火したら何をするかを、ルールが存在する前に、すべての書き込みをこれらのチェックにかけて示します。[Blueprints](/ja/iot/blueprints/)を参照してください。

きれいなドライランは助言であって、約束ではありません。質問とコマンドの間にデバイスが切れたり、誰かがタグを無効化したりすることがあるため、ゲートは実際の書き込み時にあらためて判断します。

:::caution[まだ 4.16.0 ですか?プロンプトが Set を飲み込むことがあります]
4.16.0 では、入力をやめてから約 4 分の 1 秒後にドライランの判定が表示されます。ちょうどマウスが Set へ向かうときで、その下でプロンプトが伸び縮みします。Set は約 30px 動くため、クリックは空白に落ちるか、背景に当たってプロンプトが閉じます。オペレーターはプロンプトが閉じるのを見て設定値が出たと思いますが、何も書き込まれていません。4.17.0 で修正されました。判定はボタンの横に置かれ、何も動きません。[アップグレード](/ja/gateway/upgrading/)するまでは、Set を押したあと値が実際に変わったかを確認してください。
:::

## どの入口も同じゲート

- **画面と `POST /api/write`。** 実行者はログイン中のユーザー名で、誰でも設定できるヘッダーではありません。
- **エンティティサービス**、`POST /api/services/{domain}/{service}`。`switch.press_01_pump` への `switch.turn_on` は、このゲートを通るタグの書き込みで、エンティティに対して entity_id、サービス、呼び出し ID とともに監査されます。ボタンの 1 回の押下は、1 つの呼び出し ID の下の 2 回の書き込みです。ここでは `values.write` のないユーザーは入口で止められません。不足している権限は呼び出し元自身のチェックとしてゲートに渡されるので、拒否されたエンティティ呼び出しは、ほかの拒否と同様に要求された値とともにエンティティに対して監査され、応答は引き続き 403 です。
- **オートメーション**は `automation:<rule-id>` として書き込みます。ルールには人間以上の権限は与えられません。[オートメーション](/ja/iot/automations/)を参照してください。
- **スクリプト**は 4.17.0 で新登場で、`script:<id>` として書き込み、起動した側のソースを保持します。そのためエージェントが起動したスクリプトは、エージェント自身の `write_tag` とまったく同じようにエージェントスイッチに当たります。
- **レシピ**は 4.17.0 で新登場で、すべてのターゲットを 1 つの呼び出し ID の下で書き込むため、`GET /api/writes?call=<id>` が監査証跡にある適用の全体です。
- **エージェント**は `mcp:<client name>` として書き込みます。`write_tag` と `call_service` はオペレーターと同じチェックを受け、どちらも理由の明示がなければ実行を拒否します。その理由は書き込みの隣のシステムログに残ります。半年後に誰も説明できない監査行は、後ろめたさのついたタイムスタンプにすぎません。`trigger_automation` はエージェントの書き込みがオフの間は完全に拒否され、`run_script` と `apply_recipe` も同様です。ルール、スクリプト、レシピは機器に指令でき、そうでなければスイッチを迂回する手段になってしまうからです。[Model Context Protocol](/ja/iot/mcp/)を参照してください。

## 書き込みがデフォルトでオフの理由

4.4.0 より前は、`safety.allowWrites` と `safety.allowMcpWrites` のデフォルトは `true` でした。いまは `false` です。タグは有効化されるまで常に読み取り専用でしたが、新規インストールが、誰も確認しないうちに `writable` フラグ 1 つで機器に指令できる状態であってはなりません。

ゲートの上には `safety.confirmWrites`(デフォルトでオン)があり、画面は何かを送る前に確認を求めます。これはゲートのチェックではなくブラウザーのプロンプトで、設定画面から変更できる唯一の安全設定です。`safety.allowWrites` と `safety.allowMcpWrites` は、あえてそこでは読み取り専用にしてあります。このプロセスが機器に指令できるかどうかのマスター制御は、書き込みを発行するのと同じブラウザーセッションの背後に置くべきではありません。

## 書き込みを意図してオンにする

1. デバイスを追加し、プロトコルが一覧できる場合はそのタグを検出します。Modbus と S7comm は自身のポイントを列挙できないため、デバイスのドキュメントから宣言してください。
2. タグは 1 つずつ、意図したものだけを書き込み可能にします。
3. values ファイルに `safety.allowWrites: true` を設定し、`helm upgrade` を実行します。それまでは、手順 1 と 2 のどれもバルブを動かせません。
4. エージェントにも機器へ指令させる場合に限り、`safety.allowMcpWrites: true` を設定します。

## できないこと

アプリケーションがすべてを強制できるわけではなく、思い込まれるより先にお伝えしておくほうがよいと考えます。

- **インターロックではありません。** 人やプラントを守るトリップは、ネットワーク上で動くものではなく、必要な場所にハードワイヤードされた PLC に置くべきものです。
- **ブローカーは監視しません。** MQTT でエッジリレーにノードコマンドを送る場合は、ブローカー自身のアクセス制御で、それを発行できるのを Gateway の認証情報に限定する必要があります。
- **OPC UA サーバーはまったく書き込めません。** 書き込みハンドラーも、それを追加する設定もない読み取り専用なので、それを読む SCADA は、これを通じて何も指令できません。
