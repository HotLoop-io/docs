フリート管理は 4.7.0 から、Gateway が登録済みのエッジリレーを追跡し、生きているかを把握し、権限のあるオペレーターがリレーに rebirth、再起動、送ったばかりの設定の採用を依頼できるようにします。既定では無効です(`HOTLOOP_FLEET_ENABLED`)。エッジリレーのない環境には、これを向けるブローカーがないためです。

## 何ではないか

フリート管理は独立した専用の MQTT 接続を持ち、別の問いに答えます。*登録された*エッジリレーが生きているかどうかであって、そのタグのひとつがどんな値かではありません。タグをポーリングするドライバーに組み込むと、フリートを見るためだけに互換のデバイスを設定させるか、共有する前提で作られていないそのパッケージのノードごとの内部記録に手を入れる必要がありました。

**自動ではありません。** エッジリレーがブローカーに現れても、フリートのメンバーにはなりません。メンバーシップは宣言するもので、`POST /api/fleet` で作る `fleet_members` の 1 行です。このアプリがすでに、ドライバーが見つけたタグと人が設定したタグを区別しているのと同じやり方です。誰も登録していないグループやノードからの NBIRTH は debug レベルで記録され、それ以外は無視されます。

## 全体の仕組み

- **プレゼンス**は NBIRTH と NDEATH から得ます。リレー側からはアウトバウンドのみで、測定値を発行するときと同じようにブローカーへ発信するため、リレーへのインバウンド接続なしで NAT を越えて動きます。

コマンドは Sparkplug NCMD で逆方向に流れ、リレーがすでに扱っているものを拡張します。

- 害のない冪等な合図です。
- **再起動**(`Node Control/Reboot`、このアプリが考えた名前ではなく Sparkplug 仕様自体の名前)では、リレーが自身の正常な NDEATH を発行して終了し、スーパーバイザー(Quadlet ユニットの `Restart=always`、または Deployment の既定の `restartPolicy: Always`)がその時点でディスクにある内容で再び立ち上げます。新しい停止経路はなく、リレーが `SIGTERM` で取る正常終了と同じ経路です。

コマンドはリレーがすでに外向きに張っている同じ MQTT 接続で流れるため、送るのにもリレーへのインバウンド接続は要りません。

オンラインと表示されたリレーには必ずコマンドを送れます。すべてのリレーは、接続のたびに誕生を発行する前に、自分の NCMD トピックを購読し、ブローカーが確認するのを待つので、「オンライン」が「到達可能」より先に出ることはありません。マネージャーも自分の側で同じ規則を守ります。NBIRTH と NDEATH の購読が確認されるまで開始済みとは報告しないので、Gateway が起動した瞬間に誕生したリレーも取りこぼしません。ブローカーの ACL がどちらかの購読を拒否した場合、その側は半分聞こえないまま動くのではなく、起動を拒否してそう伝えます。

## 設定のプッシュ

リレーがポーリングする内容のプッシュは NCMD を通りません。Sparkplug のメトリクスはデバイスファイル全体を載せる大きさではないからです。リレーごとの **retained の通常 MQTT トピック** `hotloop/edge-relay-config/<group>/<node>` に送ります。retained 配信のおかげで、「追いつかせてほしい」という別のリクエストなしでも動きます。そこに最後に発行された内容は、購読したどのクライアントにもすぐ渡され、オフラインから再接続するリレーや初めて起動するリレーにも渡されます。

リレーは受信時に再度検証します。このアプリは、そのトピックに発行するのが Gateway だけだとは仮定できず、自分自身が壊れたものを発行しないようにするだけです。

**デバイスファイルには認証情報が含まれることがあり、プッシュするとそれが発行されます。** デバイスの `config` ブロックには、ドライバーがログインに使う値、たとえば OPC UA の `username` と `password`(4.15.0)が入り、ファイルはそのまま retained で発行されます。`hotloop/edge-relay-config/#` を購読できる人は誰でも読めるため、認証情報を含むファイルをプッシュする前に、ブローカーにそのトピックの TLS と ACL が必要です。Gateway の API は 4.15.1 からデバイスの認証情報をすべてのロールに対して隠しますが、プッシュされたファイルは API の背後になく、この変更の影響を受けません。[Edge Relay リファレンス](/ja/edge-relay/reference/#デバイスファイルの認証情報-4150)と[認証とユーザー](/ja/iot/authentication/#資格情報がまだ平文の場所)を参照してください。

**プッシュはその場で適用され、何も再起動しません。** 4.17 まではプッシュはファイルを置くだけで、反映には 2 つ目の操作、`POST /api/fleet/{id}/restart` が必要で、タグ 1 つを変えるためにリレーのブローカーセッションと保持しているすべてのデバイスセッションを切っていました。現在は次のとおりです。

- **動作中のリレー**はファイルを検証して保存し、その場で適用します。新しいデバイスは接続し、削除されたデバイスは切断し、変更されたデバイスは再接続し、変更のないデバイスはセッションを保ちます。Sparkplug セッションと転送キューはずっと維持されます。ノードは新しいメトリクスセットで rebirth し、外したメトリクスを先に null にするので、ホストが削除済みデバイスの最後の正常値を表示し続けることはありません。[Edge Relay リファレンス](/ja/edge-relay/reference/#即時適用で維持されるものと変わるもの)に、回線に何が出るかとその理由が正確に書かれています。
- **リレーが拒否したファイル**(解析できない、検証できない、保存できない)はリレーを何も変えず、リレーの `/status` が `config.rejected` でそう示します。`GET /api/fleet` は `statusUrl` を持つすべてのメンバーについて、実行中のファイルのダイジェストの横にそれを表示するので、「プッシュした」と「実行している」は、思い込みではなく確認できる 2 つの事実になります。Gateway も発行前に検証するため、実際には、新しい、または古いリリースのリレーが規則について食い違っているか、Gateway 以外の何かがそのトピックに発行した場合です。
- **オフラインのリレー**は、接続した瞬間に retained のプッシュを受け取ります。起動時はローカルファイルを読み込む前に数秒それを待つので、古いリストで起動してから切り替えるのではなく、プッシュされたリストで立ち上がります。

プッシュされたファイルはリレーのローカルのデバイスファイルの上ではなくデータボリュームに置かれ、プッシュを取り消すまでローカルより優先されます。[Edge Relay リファレンス](/ja/edge-relay/reference/#プッシュされたファイルの場所とどちらが優先されるか)に、優先順位の規則と、それが必要になった 4.16.0 のバグが書かれています。

**プッシュの取り消し**は `DELETE /api/fleet/{id}/config`(`fleet.config`、プッシュと同じ)です。メンバーの設定トピックに空の retained メッセージを発行します。これが MQTT で retained の値を削除する方法で、その後のどの起動もプッシュを適用しません。その時点で接続しているリレーは、プッシュと同じようにその場でプッシュされたファイルを捨ててローカルのファイルに戻りますが、ローカルのファイルが読み込めない場合は、プッシュされたほうを保持してそう伝えます。オフラインだったリレーは削除を受け取れない(空のメッセージは保持されない)ので、リレーが戻ったらもう一度送ってください。

## 各リレーが実行しているものと更新

すべてのリレーは、誕生のたびに自分のバージョンとイメージのダイジェストを載せ、エッジ発行を有効にした Edge や Gateway も同様なので、ここでメンバーとして登録されたボックスも同じものを表示します(`Node Info/Version` と `Node Info/ImageDigest` という文字列メトリクス、エイリアスなしで、知らない Sparkplug ホストは無視します)。`GET /api/fleet` はそれらを各メンバーの `release` として表示します。`version`、`imageDigest`、`since`(Gateway がそのビルドを初めて受け取った時刻)です。それ以前のリレーは何も報告せず、Gateway は「不明なビルド」をでっち上げずに何も言いません。

メンバーのビルドが変わると、Gateway はそのメンバーの `config` イベントとしてシステムログに書き、詳細に古いバージョンとダイジェストと新しいバージョンとダイジェストを入れます(`{"kind":"fleet.release",...}`)。初めて受け取ったビルドも、次のビルドと比べる基準として記録されます。最後の記録はログから読み戻されるので Gateway の再起動後も保たれ、再起動が更新をでっち上げることはありません。これは、リレーが受けるあらゆる更新の監査記録で、経路は問いません(Podman のタイマー、承認、`helm upgrade`、ボックスの前の人)。Gateway は更新を起こさず、報告するだけだからです。移動するタグが `:stable` の更新の仕組みなので、同じバージョンのままダイジェストが変わった場合も「同じバージョンの別のイメージ」として記録されます。

`POST /api/fleet/{id}/update`(`fleet.update`、管理者のみ)は、リレーが保留している更新を承認します。更新を保留する設定のリレーにだけ作用し、ほかのリレーは無視したと記録します。リクエストはイメージを指定しません。インストールの種類ごとにこれが何をして何をしないかは、[Edge Relay リファレンス](/ja/edge-relay/reference/#relay-の更新)にあります。

## コマンドの権限

意図的に 1 層ではなく 2 層です。

- **API では**、オペレーターが rebirth を要求するには `fleet.rebirth` が必要です。再起動、更新の承認、設定のプッシュには、それぞれ `fleet.restart`、`fleet.update`、`fleet.config` が必要で、管理者にのみ付与されます。再起動は rebirth の合図よりも動作中のポーリング周期を妨げ、リレーがポーリングする内容のプッシュも同様に扱われます。`alarms.ack` と `automations.trigger` が、ほかの「今すぐ実行」の操作ですでに示しているのと同じ絞り込みです。
- **ブローカーでは**、このアプリは何も強制できません。NCMD の発行と設定トピックの両方を、ブローカー自身の ACL で Gateway 自身の MQTT 認証情報だけに制限する必要があります。そうしないと、ブローカーに届き、リレーのグループとノードを知っている人なら誰でも、この機能と同じコマンドや設定を発行できます。デプロイ時に設定してください。このアプリ自身のコードの外にあるからといって、任意ではありません。

## API

| ルート | 権限 | <span class="sr-only">詳細</span> |
|---|---|---|
| `GET /api/fleet` | `fleet.read` | 登録済みのすべてのメンバー。リアルタイムのプレゼンスと、設定されていればポーリングした `/status` つき |
| `POST /api/fleet` | `fleet.write` | メンバーを作成または更新します(既存の `id` を含む本文は更新) |
| `DELETE /api/fleet/{id}` | `fleet.write` | 登録済みのメンバーを削除します |
| `POST /api/fleet/{id}/rebirth` | `fleet.rebirth` | `Node Control/Rebirth` を発行します |
| `POST /api/fleet/{id}/restart` | `fleet.restart` | `Node Control/Reboot` を発行します |
| `POST /api/fleet/{id}/update` | `fleet.update` | リレーが保留しているイメージ更新を承認します(保留していないリレーには何もしません) |
| `POST /api/fleet/{id}/config` | `fleet.config` | 新しいデバイスファイルをプッシュします(生の JSON 本文、発行前に検証)。動作中のリレーはその場で適用します |
| `DELETE /api/fleet/{id}/config` | `fleet.config` | プッシュを取り消し、リレーをローカルのデバイスファイルに戻します。接続中ならその場で反映されます |

## 設定

| 変数 | 既定値 | <span class="sr-only">詳細</span> |
|---|---|---|
| `HOTLOOP_FLEET_ENABLED` | `false` | 設定するまで機能は無効です |
| `HOTLOOP_FLEET_BROKER` | n/a | 有効時は必須です。ホストのみ、`host:port`、または完全な URL |
| `HOTLOOP_FLEET_USER` / `_PASSWORD` | n/a | ブローカーの認証情報 |
| `HOTLOOP_FLEET_TLS` | `false` | |
| `HOTLOOP_FLEET_TLS_SKIP_VERIFY` | `false` | デプロイごとに自分で選ぶオプションです。既定では絶対に設定しないでください |
