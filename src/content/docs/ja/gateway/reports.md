スケジュールレポートは 4.14.0 から、オペレーターが定義したレポートをスケジュールに従って実行します。ヒストリアンに問い合わせ、結果を CSV と HTML にして、ボリュームに保存し、必要に応じてメールで送ります。Ignition の Reporting モジュールのうち、プラントが最もよく使う部分、つまり時間どおりに届く数値の表に相当します。デフォルトではオフです(`HOTLOOP_REPORTS_ENABLED`)。

## できることと、できないこと

- **API のみ。** このバージョンには画面がありません。レポートは `/api/reports` から定義、実行、一覧、ダウンロードします。UI は別の作業です。
- **CSV と HTML のみ。** PDF はありません。外部バイナリなし(ランタイムイメージには意図的に入れていません)の純粋な Go で良い PDF を作るには、PDF ライブラリとレイアウトエンジンを選ぶ必要があり、それ自体が1つの判断になります。HTML ファイルは自己完結しており、どのブラウザーからもきれいに印刷できるので、いまのところ「PDF が必要」はこれで足ります。
- **集計の表であり、自由なレイアウトではありません。** レポートは、タグのリスト、ウィンドウ、バケットの大きさ、集計の組み合わせです。ページデザイナーではありません。
- **Gateway インスタンスは 1 つ。** スケジューラーは、このデータベースに対してレポートを実行するのは自分だけだと想定しています。レプリカが 2 つあると、それぞれがすべてのレポートを実行します。このチャートはレプリカを 1 つだけ実行し、レポートのボリュームは `ReadWriteOnce` です。
- **アラームの機能ではありません。** アラームのメールは別の機能の[アラーム通知](/ja/iot/notifications/)です。レポートがアラームと共有するのは SMTP リレーの設定だけで、ほかには何もありません。

## レポートの定義

定義はオペレーターが編集するデータで、デバイス、タグ、アラーム定義、フリートメンバーと同様にデータベースに保存され、API で管理します。例:

```json
{
  "id": "line1-daily",
  "name": "Line 1 daily summary",
  "enabled": true,
  "tags": [
    {"deviceId": "press-01", "tagName": "Zone1_Temp"},
    {"deviceId": "press-01", "tagName": "Pressure"}
  ],
  "window": {"count": 1, "unit": "days", "end": "local_midnight"},
  "bucket": "hour",
  "aggregations": ["min", "max", "avg", "count"],
  "schedule": {"kind": "daily", "at": "03:00"},
  "format": "both",
  "recipients": ["ops@example.com"],
  "retain": 30
}
```

| フィールド | 意味 |
|---|---|
| `id` | 文字、数字、ドット、ダッシュ、アンダースコアからなる 1 から 64 文字で、文字か数字で始まります。ボリューム上のレポートのディレクトリ名になるため、このアプリのほかのすべての id と同じ方法で検証されます。 |
| `name` | HTML のタイトルとメールの件名に表示されます。制御文字は使えません。 |
| `enabled` | スケジューラーが実行するかどうか。無効なレポートも手動で実行できます。 |
| `tags` | デバイスとタグの組を 1 から 50 個。定義を保存するときにそれぞれが存在している必要があり、文字列タグであってはいけません。 |
| `window` | 各実行が対象にする履歴の範囲。以下を参照してください。 |
| `bucket` | `window`(タグごとに 1 行)、`hour`、`day`。デフォルトは `window` です。 |
| `aggregations` | `min`、`max`、`avg`、`first`、`last`、`count` の 1 つ以上で、それぞれ最大 1 回です。 |
| `schedule` | 以下を参照してください。 |
| `format` | `csv`、`html`、`both`。デフォルトは `csv` です。 |
| `recipients` | 省略可。通常のアドレスのみ(`ops@example.com` は可、`Ops <ops@example.com>` は不可)。最大 20 件。 |
| `retain` | 保持する実行の数。1 から 1000。デフォルトは 30 です。 |

`PUT` は定義全体を置き換えます。クライアントはレポートを読み、フィールドを 1 つ変えて、そのまま送り返せます。サーバーが追加する読み取り専用のフィールド(`nextRunAt`、`lastRun`、`lastRunAt`、`createdAt`、`updatedAt`)は受け付けられて無視されます。

1000 を超えるバケットになる定義は、保存時に拒否されます(たとえば約 41 日を超える範囲の 1 時間ごとのバケット)。

## ウィンドウ

ウィンドウは、実行が行われる時点からの相対です。

| 必要なもの | `count` | `unit` | `end` |
|---|---|---|---|
| 直前の 24 時間 | 24 | `hours` | `run_time` |
| 直前の暦日 | 1 | `days` | `local_midnight` |
| 直前のまるまる 7 日 | 7 | `days` | `local_midnight` |
| 直近 1 週間(ローリング) | 7 | `days` | `run_time` |

- `end` は実行が始まる瞬間です。`local_midnight` の場合は、その時刻以前で最も近い現地の午前 0 時です。03:00 に実行されて現地の午前 0 時で終わる実行は、まるまる暦日単位を対象にします。
- **時間は経過時間で、日は暦日**です。基準はプラントのタイムゾーンです。現地の午前 0 時で終わる 1 日のウィンドウは現地の 1 日分まるごとで、時計を進める日は 23 時間、戻す日は 25 時間になります。「直前の 24 時間」は常にちょうど 24 時間です。
- **ウィンドウは半開区間**です。開始を含み、終了を含みません。ちょうど午前 0 時のタイムスタンプを持つ値は、そこから始まる日に属します。連続する 2 つの日次レポートが、同じ値を両方で数えることも、両方で見逃すこともありません。
- 手動実行とキャッチアップ実行は、実行される時点でウィンドウを計算します。

## バケット

- `window`: ウィンドウ全体でタグごとに 1 行。
- `hour`: 現地の時計の時間ごと、タグごとに 1 行。ちょうどの時刻から始まらないウィンドウは短い部分バケットで始まり、ちょうどの時刻で終わらないウィンドウは部分バケットで終わります。時計の切り替えをまたいでも、オフセットが整数時間でないタイムゾーンでも、時間はちょうどの時刻に揃います。
- `day`: 現地の暦日ごと、タグごとに 1 行。

すべてのタグには、中身が空のバケットも含めて、すべてのバケットに行があります。レポートは、センサーが沈黙していた時間を決して省きません。行をこっそり省いたレポートは、何も伝えることがなかったセンサーのレポートと同じに見えてしまうからです。各行は対象とする正確な範囲(`period_start` と `period_end`、UTC オフセット付き)を示すので、23 時間の日は 23 時間として表示されます。

## 集計と品質ルール

集計は `min`、`max`、`avg`、`first`(期間内でタイムスタンプが最も早い値)、`last`(最も遅い値)、`count` です。

レポートはトレンドチャートと同じ品質ルールに従うので、同じ時間のレポートとトレンドは一致します。数値のない値(文字列の値)も除外されます。これをオフにするスイッチはありません。ヒストリアン自身が信頼できないと印を付けた値をこっそり混ぜた平均は、使わなかった件数を伝えるレポートより悪いからです。

そのため、すべての行に `excluded` 列があり、その期間で除外された値の件数を示します。`count` は使われた件数です。実行記録とメールには合計が入ります。

**何も捏造しません。** ある期間に使える値が 1 つもないタグには最小値がなく、レポートもそう示します。CSV ではセルが空になり、HTML では `no data` と表示されます。ゼロになることはありません。ゼロは値(閉じたバルブ、流量なし)であり、ほかの値と同じように集計されます。データがないときに数値になる列は `count` だけで、ゼロは「何もない」の正しい件数だからです。

## スケジュールと時刻

スケジュールは次のいずれかです。

```json
{"kind": "interval", "every": "6h"}
{"kind": "daily",    "at": "03:00"}
{"kind": "weekly",   "weekday": "monday", "at": "06:30"}
```

- **インターバル**は経過時間(最短 1 分)で、壁時計を無視します。
- **日次と週次**の時刻は、プラントのタイムゾーンの壁時計の時刻で、そのタイムゾーンは `HOTLOOP_TIMEZONE`(チャートの `global.timezone`)です。`America/Chicago` のような実在のゾーン名でなければなりません。使えない名前はレポートのオンオフにかかわらず起動拒否となり、UTC に黙って戻ることはありません。現地 03:00 のはずのレポートが UTC の 03:00 に実行されるのは、数字がおかしくなるまで誰も気づかないバグだからです。

### 夏時間

次の実行は、`time.Date` でプラントの所在地の壁時計の時刻を組み立てて計算します。前回の実行に 24 時間を足して計算することは決してありません。そうすると、時計の切り替えから次の切り替えまでのあいだに 1 時間早く、または 1 時間遅く実行されてしまいます。切り替えの日には、扱いにくい壁時計の時刻が 2 つあり、どちらも動作が未規定と文書化されているため、それぞれの規則は `time.Date` に任せずコードで固定しています。

- **存在しない時刻**(時計が 02:00 から 03:00 に飛ぶ春の切り替え日の 02:30)は、空白の直後の最初の瞬間である 03:00 に実行されます。空白の長さ分だけ遅れますが、その日を飛ばすことはありません。
- **2 度ある時刻**(秋の切り替え日の 01:30)は、最初に現れたときに 1 回だけ実行されます。

### last_run_at、次の実行、キャッチアップ

`last_run_at` は、スケジューラーが最後にレポートを**開始した**時刻で、その実行がその後に成功したか失敗したかを問いません。手動実行はこれを動かさないので、02:00 にレポートを手動で実行しても、今夜 03:00 の実行は取り消されません。

次の実行は、定義の作成時刻、最後の編集時刻、`last_run_at` のうち最も遅いものの後の、最初の予定時刻です。最後の編集から測るので、10:00 にレポートを 03:00 から 09:00 に移すと、すでに過ぎた時刻のために直ちに実行されるのではなく、明日まで待ちます。

**キャッチアップ。** Gateway の起動時に、`last_run_at` の後の次の実行がすでに過去であれば、Gateway がその場にいなかったということで、レポートは直ちに**1 回だけ**実行され、`catchup` と表示されます。見逃した時刻ごとに 1 回ずつ実行されるわけではありません。3 日見逃した日次レポートは、Gateway が戻った日に 1 回、その時点を基準にしたウィンドウで実行されます。見逃した日は補完されません。その後、レポートはスケジュールに戻ります。

`last_run_at` は実行が始まる**前に**書き込まれます。そのため、実行の途中で停止した Gateway が、すでに送信済みかもしれないメールの上に、再起動時に同じ実行を繰り返すことはありません。中断された実行は、代わりに失敗として記録されます。失敗した予定実行は再試行されません。次の予定時刻は通常どおり実行され、もう一度実行したいときは `POST /api/reports/{id}/run` があります。

## 出力

各実行は、`HOTLOOP_REPORTS_DIR`(`/data/reports`、チャートでは PVC)の下にファイルを書き込みます。

```
/data/reports/<report id>/<UTC timestamp>-<run id>.csv
/data/reports/<report id>/<UTC timestamp>-<run id>.html
```

- **ファイル名は、検証済みの id、UTC のタイムスタンプ、実行の整数 id だけから作られます。** パストラバーサルは設計上閉じられています。レポートの id はほかの場所と同じ識別子の規則を満たす必要があり、実行記録から読み戻したファイル名は、開く前に上記の厳密なパターンと照合されます。ダウンロード URL の `{run}` は整数として解析され、レポートの id と合わせて実行記録を引くためだけに使われます。開かれるファイルは、その記録が指しているものです。URL のどの部分もパスの一部にはなりません。
- ファイルは `O_EXCL` とモード `0640` で、ディレクトリは `0750` で作成されます。すでに存在するファイルはエラーで、上書きされることはありません。出力にはプラントのデータとタグ名が含まれるので、このモードは最低限のものであり、ボリュームの保護の代わりにはなりません。
- **保持。** 各実行の後、ファイルを保存した最新の `retain` 件の実行が保持され、それより古いものはファイルとともに削除されます。ファイルのない失敗した実行は別に(その中の最新の `retain` 件)保持されるので、失敗が続いても最後の正常なレポートが押し出されることはありません。レポートのディレクトリにある、命名パターンに一致するが残っているどの実行記録からも参照されていないファイル(停止した実行の部分的なファイル)も削除されます。パターンに一致しないファイル、たとえばオペレーターが置いたファイルは、そのままにされます。

### CSV

`encoding/csv` による RFC 4180 で、行末は CRLF です。列は `device_id`、`tag_name`、`unit`、`period_start`、`period_end`、定義に並べた順の集計ごとに 1 列、そして `excluded` です。タイムスタンプはプラントのタイムゾーンの RFC 3339 で、オフセット付きです。数値は完全な精度で書き込まれます。

**スプレッドシートの数式インジェクション。** タグ名や単位は誰かが入力したテキストで、スプレッドシートは `=`、`+`、`-`、`@` で始まるセルを数式として読みます。これらのいずれかで始まる(またはタブやキャリッジリターン、あるいは空白に続いてこれらが来る)テキストのセルには、先頭にアポストロフィが付きます。スプレッドシートはこれを「テキストである」という印として扱い、表示しません。数値の列は数値から書かれるので、負の値はそのままで、数値として読まれます。

ファイルにバイトオーダーマークはありません。Excel は BOM のない UTF-8 の CSV を古いコードページのように開くため、ASCII 以外の文字を含むタグ名は、UTF-8 としてインポートする必要があるかもしれません。

### HTML

`html/template` で作られる自己完結した 1 つのファイルで、タグ名と値は置かれる場所に応じてエスケープされます。`<script>` という名前のタグはテキストとして書かれます。スタイルシートはインラインで、デプロイ環境が外部から隔離されている場合があるため、スクリプト、フォント、画像、どこへのリンクもありません。何も読み込めないようにする `Content-Security-Policy` の meta タグも含み、API は `sandbox` を加えたポリシーとともに添付ファイルとして提供します。

## メールでの配信

レポートに `recipients` があると、各実行は `HOTLOOP_NOTIFY_SMTP_*`(ホスト、ポート、ユーザー名、パスワード、送信者、TLS)で設定した SMTP リレー経由で、ファイルを添付してメールで送ります。アラームのチャンネルと共有されるのはリレーだけです。そのチャンネルが有効かどうか、アラームの宛先が誰かは、レポートに影響しないので、誰にも通知を飛ばさずにレポートをメールで送れます。アラームのチャンネルがオフのとき、チャートはレポート専用にリレーの変数を書き込みます。

これはアラームのチャンネルと同じ SMTP コードで、2 つ目のコピーではありません。アラームのチャンネルも、いまはこれを通して送信します。接続の扱いは変わりません(465 番ポートは最初のバイトから TLS で通信するようになりました。[アラーム通知](/ja/iot/notifications/#implicit-tls-port-465)を参照してください)。リレーが提供すれば常に STARTTLS、認証情報が設定されていれば `AUTH`、`HOTLOOP_NOTIFY_SMTP_TLS` が設定されていてリレーが STARTTLS を提供しなければ `AUTH` の前に確実に失敗します。ASCII のアラームでは、メッセージは `Date` ヘッダー以外、以前と同じバイト列で、テストがそれを固定しています。ASCII 以外のアラームの件名は、生の UTF-8 ではなく RFC 2047 のエンコード語として送られます。

メッセージは `multipart/mixed` です。quoted-printable のテキスト部分に続いて、各ファイルが base64 で入ります。**ヘッダーインジェクションは、除去せずに拒否します。** 宛先、送信者、件名、添付ファイル名が検証されます。CR、LF、そのほかの制御文字を含む値、表示名の形式の宛先やリストを含む宛先、引用符やパスを含むファイル名は、リレーに何かが送られる前にメッセージを失敗させます。例外はアラームのチャンネル自身の件名だけです。アラームの名前が何であっても通知は出る必要があるため、先に制御文字を空白に置き換えます。

- **リレー未設定。** 宛先のあるレポートも実行されてファイルを保存し、実行は `failed` と記録され、`emailStatus` は `failed` で、リレーが設定されていないというエラーが入ります。黙って成功することはありません。
- **大きすぎる場合。** `HOTLOOP_REPORTS_MAX_EMAIL_BYTES`(10 MiB)が、1 通のメールの添付データの上限です。これを超えたレポートは保存されてダウンロードでき、実行記録にメールで送らなかった理由が残ります。
- 手動で行った実行は、`?deliver=false` でメールを省略できます。

## 実行記録と監査証跡

すべての実行は、開始の瞬間から `report_runs` に記録されます。開始と終了の時刻、トリガー(`schedule`、`catchup`、`manual`)、要求した人、ウィンドウ、結果とエラーのテキスト、タグ数、行数、集計した値と除外した値の件数、保存したファイル、メールの結果と宛先、そしてメモ(たとえば、タグがその後に削除され、記録された履歴から報告されていること)です。成功と失敗は、アラームやフリートの操作が使うものと同じ監査証跡である `rt.Event` にも書き込まれ、レポートの id が対象になります。

シャットダウン、時間制限(`HOTLOOP_REPORTS_RUN_TIMEOUT`)、またはレポートの削除で打ち切られた実行は、その理由とともに失敗として記録されます。停止したプロセスが `running` のまま残した実行は、Gateway が次に起動したときに失敗とマークされます。1 つのレポートの実行は同時に 1 つだけで、実行中に来た 2 つ目のリクエストは `409` になります。

## API

| ルート | 権限 | <span class="sr-only">詳細</span> |
|---|---|---|
| `GET /api/reports` | `reports.read` | すべての定義。それぞれに `nextRunAt` と直近の実行が付く |
| `POST /api/reports` | `reports.write` | 作成。id がすでにあれば `409` |
| `GET /api/reports/{id}` | `reports.read` | 定義を 1 つ |
| `PUT /api/reports/{id}` | `reports.write` | 置き換え。id は変更できない |
| `DELETE /api/reports/{id}` | `reports.write` | 実行とファイルも含めて削除。実行中のものは先にキャンセルされる |
| `POST /api/reports/{id}/run` | `reports.run` | いま実行して待つ。`?deliver=false` でメールを省略 |
| `GET /api/reports/{id}/runs` | `reports.read` | 実行記録を新しい順に(`?limit=`、最大 500) |
| `GET /api/reports/{id}/runs/{run}/download?format=csv\|html` | `reports.read` | 保存されたファイルを 1 つ添付としてストリーミング |

`POST .../run` は、実行が成功したかどうかにかかわらず、実行記録を `200` で返します。ステータスはリクエストが実行されたかを示し、記録自身の `status` はレポートが成功したかを示します。失敗した実行も結果であり、どちらの場合も記録されます。実行はクライアントの接続に結びついていません。切断しても、すでにメールを始めているかもしれないレポートは中断されません。

機能がオフのとき、一覧は `{"reports": [], "configured": false}` を返し、ほかのすべてのルートは `HOTLOOP_REPORTS_ENABLED` に言及したエラーを返します。

### 誰が何をできるか

| ロール | `reports.read` | `reports.run` | `reports.write` |
|---|---|---|---|
| ビューアー | はい | いいえ | いいえ |
| オペレーター | はい | はい | いいえ |
| 管理者 | はい | はい | はい |

- **読み取り**はビューアーに許可されています。保存されたレポートは、ビューアーが `values.read` ですでに読める履歴の集計なので、読んだりダウンロードしたりしても新しく与えられるものはありません。
- **実行**はオペレーターに許可されています。レポートの実行は、管理者がすでに選んだ宛先にしか配信されず、配信なしで実行することもできるからです。
- **書き込みは管理者のみです。** 定義には出力のメール送信先が指定されるため、定義を作れるということは、スケジュールに従って任意のアドレスにプラントのデータを送れるということです。これは読み取りよりも、`notify.test` や `fleet.config`(同じく管理者のみで、同じく「外の世界に何かをする」もの)に性質が近いものです。これは判断であり、実際の業務の流れでオペレーターにレポートを作らせる必要が出れば、見直せます。
- オペレーターは、レポートを実行することで、そのレポートの宛先にメールを送らせることができ、繰り返すこともできます。1 回に 1 実行という保護と `?deliver=false` はありますが、レート制限はありません。
- 明示的な権限リストを持つユーザーは、そこに書かれたものだけを持ちます。`reports.*` のワイルドカードは 3 つすべてを含みます。

## 設定

| 変数 | デフォルト | <span class="sr-only">詳細</span> |
|---|---|---|
| `HOTLOOP_REPORTS_ENABLED` | `false` | これを設定するまで、スケジューラーを含めて機能はオフ |
| `HOTLOOP_REPORTS_DIR` | `/data/reports` | 各実行のファイルの書き込み先。PVC(チャートの `reports.persistence`)を想定 |
| `HOTLOOP_REPORTS_RUN_TIMEOUT` | `5m` | 1 回の実行の上限: クエリ、レンダリング、書き込み、メール |
| `HOTLOOP_REPORTS_MAX_EMAIL_BYTES` | `10485760` | 1 通のメールに入る添付データの最大量 |
| `HOTLOOP_TIMEZONE` | `UTC` | プラントのタイムゾーン。実在のゾーン名でなければならず、でなければ HotLoop は起動しない |
| `HOTLOOP_NOTIFY_SMTP_HOST`, `_PORT`, `_USERNAME`, `_PASSWORD`, `_FROM`, `_TLS`, `_TLS_SKIP_VERIFY` | | レポートがメールを送るリレー。[アラーム通知](/ja/iot/notifications/)を参照 |

チャートの `reports` ブロックには、`enabled`、`runTimeout`、`maxEmailBytes`、`persistence`(サイズ、ストレージクラス、アクセスモード)があります。`notify.smtp` がリレーを提供します。レポートは、エージェントがバイナリをヘルパーとして起動する `--mcp-stdio` モードでは開始されません。実際の Gateway の隣に 2 つ目のスケジューラーがあると、期限が来たすべてのレポートを 2 回実行してしまうからです。

## バックアップ

レポートの定義と実行記録はユーザーデータで、データベースのバックアップに含まれます。出力ファイルは含まれません。ファイルはレポートのボリュームにあり、新しいデプロイにバックアップを復元すると記録は戻りますがファイルは戻らないので、そこで古い実行をダウンロードすると、ファイルがもうディスクにないと応答されます。ファイルが重要なら、レポートのボリュームをコピーしてください。

この 2 つのテーブルをバックアップの一覧に加えるのは、忘れやすい種類の変更なので、バックアップパッケージにはそのための保護があります。あるテストはスキーマのすべてのテーブルを列挙し、`backup.Tables` にも理由付きの明示的な除外リストにもないものがあれば失敗します。別のテストは、データベースから外部キーを読み取って、`Tables` が外部キーの順になっていることを確認します。ラウンドトリップのテストは、レポート定義と実行を 1 つ投入し、復元された値とシーケンスを確認します。
