Flow は、Modbus TCP、S7、EtherNet/IP、OPC UA、Sparkplug B で PLC やブローカーと通信します。それぞれ、機器との接続を保持する設定ノードと、それを指すアクションノードでできていて、InfluxDB ノードと同じ形です。エディターは、他のすべてと同じようにディスクリプターからすべてのダイアログを組み立てます。

HotLoop のドライバーからは何もコピーしていません。ドライバーはライセンスが異なり、これからもそのままです。

**Modbus TCP** は、`hotloop-flow-modbus` サーバー上の `modbus read` と `modbus write` です。ホールディングレジスタ、入力レジスタ、コイル、ディスクリート入力に対応します。レジスタは uint16、int16、uint32、int32、float32、uint64、int64、float64 として読み、バイト順とワード順はスイッチにしてあります。ラインにある2台の機器はどちらの順序でも一致しないでしょうし、マニュアルにも書かれていないからです。数量はレジスタ数ではなく値の個数なので、float32 を2つ読むとワイヤー上では4レジスタです。アドレスはワイヤーに載る形のままゼロ始まりで、ダイアログもエラーも、マニュアルのレジスタ 40001 がアドレス 0 であることをはっきり伝えます。

**S7** は、`hotloop-flow-s7` サーバー上の `s7 read` と `s7 write` で、TCP 上の ISO を使います。gos7 はプロトコルの Go 実装で、Snap7 の C ライブラリは一切含みません。Snap7 は LGPL で、私たちが出荷する製品にリンクしないため、これは重要です。アドレスは Siemens の書き方で書きます。`DB1.DBX0.0`、`DB1.DBW4`、`M10.2`、`MW20`、`I0.0`、`QB4` で、ドイツ語表記には `E` と `A` を使います。サイズの文字はデータ型と一致している必要があるので、float32 として読む `DB1.DBW0` は、どこへも送られる前に、意図したアドレスとともに拒否されます。ビットに対する数量3は、指定したビットから3ビットです。文字列は S7 の STRING で、書き込みはまず最大長を読み、収まらないテキストは、それを超えて書かずに拒否します。ビットはプロトコル自身のビット書き込みで書かれ、そのビットだけを変え、バイト内の他の7ビットには触れません。S7-1200 や S7-1500 は、PUT/GET が許可され、データブロックの Optimized block access がオフになるまで、すべてを拒否します。エラーもそのことを伝えます。誰もがつまずく点だからです。

**EtherNet/IP** は、`hotloop-flow-ethernetip` コントローラー上の `ethernetip read` と `ethernetip write` で、ControlLogix、CompactLogix、Micro800 のタグアクセスです。タグは Logix の綴りどおりに指定し、メンバー(`Pump1.Speed`)、配列要素(`Samples[4]`)、ビット(`Status.3`)と、それが持つデータ型を書きます。数量が1を超えると、指定した要素から、その数だけ配列要素を移動します。誤った型で読んだタグは拒否され、エラーはタグ自身の型を使うよう伝えます。CPU へのパスは、変更しない限り `1,0` で、直接つなぐコントローラーでは空です。PLC-5、SLC、MicroLogix は CIP タグではなく PCCC を話すので対象外です。はい、ライブラリにはベータの印があります。現存する最新のリリースであり、省くよりお伝えするほうがよいと考えています。

**OPC UA** は、`hotloop-flow-opcua` サーバー上の `opcua read`、`opcua write`、`opcua subscribe` です。セキュリティモードは None、Sign、SignAndEncrypt で、ポリシーは Basic256Sha256 または Aes128_Sha256_RsaOaep、匿名またはユーザー名とパスワードを使えます。クライアント証明書は `tls-config` から取得し(サブジェクト代替名にアプリケーション URI が必要です)、ない場合、ノードはフローが開始するたびに使い捨ての証明書を作って警告を記録します。サーバー側にそのたびに新しい証明書を信頼するよう伝える必要があるからです。サーバーのサムプリントを設定すると、ノードは他のすべての証明書を拒否します。設定しなければ、サーバーが示すものを何でも受け入れます。それは会話を暗号化しますが、誰と話しているかについては何も証明しません。固定してください。

**Sparkplug B** は、`hotloop-flow-sparkplug` 接続上の `sparkplug out`、`sparkplug in`、`sparkplug command` で、この接続はエッジノードかホストアプリケーションのどちらかです。それぞれに will メッセージがあり、MQTT 接続には1つだけあるからです。エッジノードとして、接続は接続時に誕生し、各 `sparkplug out` ノードをエッジノード自身のメトリクスまたは1つのデバイスのメトリクスとして発行し、切断されれば will とともに死に(ホストがセッションを区別できるよう、次の誕生では新しい bdSeq を使います)、正常な切断の前には NDEATH を送り、rebirth 要求に応答します。誕生は何かデータを送る前にすべてを列挙するので、すべてのメトリクスをノードで宣言する必要があります。エッジノード上の `sparkplug in` は、フローがコマンドに応じて動く方法です。ホストアプリケーションとしては、仕様が求めるとおり、will、retain フラグ、一致が必要なタイムスタンプとともに STATE を発行し、見えるすべてのエッジノードを追跡します。名前とエイリアスは誕生から、データ型も誕生から取得し、シーケンス番号を検査し、死が誕生で列挙されたものを古いものとして印を付け、並べ替えタイムアウト内に欠落が埋まらない場合や、誕生を見たことのないノードからデータが現れた場合に rebirth を要求します。`sparkplug command` は NCMD または DCMD を送り、型は誕生から、誕生にエイリアスがあればエイリアスで指定します。MQTT クライアントライブラリ経由の MQTT 3.1.1 です。ワイヤーフォーマットは Eclipse のスキーマと 3.0 仕様から手で書き、Google の protobuf でコンパイルした、そのスキーマに対してテストしています。これは私の実装とは別の実装です。本物の Mosquitto を相手にも、独立した Sparkplug 実装を相手にも手で、エッジノードとホストの両方向で実行しています。

エッジノードは**プライマリホストアプリケーション**を指定できます。そのホストの STATE を購読し、ホストがオンラインだと言うまで、NBIRTH も DBIRTH も含め何も言いません。最後のオンライン STATE より古い死亡証明書は古いセッションのものなので無視されます。現在のものであれば、NDEATH、切断、やり直しになります。**他のブローカー**のリストが、やり直す先です。1つずつ順番に回り、ブローカーに届かないとき、そこでホストがオフラインのとき、そしてブローカーが複数ある場合はホストがそこに一度も発行していないときに、次へ進みます。ブローカーが1つなら、オフラインのホストはエッジノードを接続したまま待たせるだけで、ホストが戻るまで待ちます。エッジノードは、仕様どおり一度に1つのブローカーにいます。配列型、**DataSet**、**Template**、メトリクスの **PropertySet** は双方向で運ばれます。配列は仕様が定めるパックされたリトルエンディアン形式、DataSet は `{columns, types, rows}`、Template は定義またはパラメータとメンバーを持つインスタンス、あらゆるメトリクスのプロパティは `{"engUnit": "degC", "Quality": {"type": "Int32", "value": 192}}` の形です。定義が NBIRTH にない Template のインスタンスは、何を宣言すべきかとともに、誕生時に拒否されます。Eclipse のスキーマはそのすべてをワイヤーから読み取れ、スキーマ自身のバイトも逆方向に読み返せます。未対応のもの:メトリクスのメタデータ(ファイルとマルチパートのバイト)、複数のブローカーと通信するホストアプリケーション、MQTT 5。

**機器が静かになったとき。** これは現場が一日中していることなので、汚いやり方でテストしています。本物のシミュレーターとの間に、トラフィックを飲み込む(固まった PLC)か、ドアを叩きつける(電源が切れた PLC)回線を挟みます。応答のない読み書きはタイムアウト内に失敗し、言葉でそれを伝え(`no answer from 10.20.1.15:502 within 3s. The device is silent. Check that it is powered...`)、接続を閉じて、次のメッセージで新しい接続を開きます。OPC UA のサブスクリプションは自分で気づき、バッジを赤くし、再試行ごとではなく障害ごとに Catch ノード向けのエラーを1つ上げ、1秒待ち、その後は最大30秒まで長くしていき、サーバーが戻ればサブスクリプションを再開します。再デプロイは不要です。エラーは、変えるべきものを名指しします。Modbus の例外コードとそれが通常意味すること、OPC UA のステータスコードとそれが指す設定、PUT/GET がオフであることを意味する S7 の拒否、拒否された接続と無言の接続の違いです。接続は受けるのにエンドポイント検出に一切応答しない OPC UA サーバーは、問い合わせたノードにだけタイムアウト分のコストを負わせ、他の誰にもコストを与えません。そのサーバー上の他のノードも、停止中のフローも、その後ろに並びません。

**HotLoop** は、`hotloop-flow-hotloop` 接続上の `hotloop in`、`hotloop state`、`hotloop script`、`hotloop recipe` で、接続は URL とアカウントです。Flow は HotLoop の隣で動き、外から HTTP API を呼び出すだけで、HotLoop を一度も選ばないフローは呼び出しを一切行いません。接続は `POST /api/auth/login` でサインインし、HotLoop が返す bearer トークンを送り、セッションがなくなったと HotLoop が言えば再度サインインします。オペレーターアカウントで、4つのノードすべてと下のゲート経由の書き込みに十分です。ログインなしで動く HotLoop に対してのみ、ユーザー名を空にしてください。

`hotloop in` は HotLoop のライブフィード(`GET /api/stream`)を追い、状態が変わるエンティティごとにメッセージを送ります。`msg.topic` はエンティティ id、`msg.payload` は新しい状態で、`msg.hotloop` にはエンティティ id、以前の状態、属性、品質、タイムスタンプが入ります。一覧に挙げたエンティティ id とパターン(`sensor.tank_*`、または `*`)を追います。ノードが接続したときに HotLoop が送る現在の状況は変更ではないので、「Send the current state when it connects」をオンにしない限り送られません。状態が変わらずに属性だけが動いた場合も、変更ではありません。リンクが落ちるとバッジが赤くなり、再試行ごとではなく障害ごとに Catch ノードにエラーが1つ届き、待ち時間は1秒から30秒まで伸び、復旧すると、その間に変わったエンティティは送られ、変わらなかったエンティティは送られません。HotLoop はすべての状態をテキストで送るので、「Numbers as numbers」は `12.5` を数値にし、`on` と `unknown` はそのままにします。

`hotloop state` はメッセージが届いたときに1つのエンティティを読み(`GET /api/states/{entity_id}`)、同じフィールドを付けてメッセージを先へ送ります。存在しない、または無効になっているエンティティは、HotLoop 自身の言葉でエラーを上げ、その言葉がどちらかを示します。

`hotloop script` は、与えたフィールドでスクリプトを実行し(`POST /api/scripts/{id}/run`)、`hotloop recipe` は、パラメータと、必要なら意図して指定した古いバージョンでレシピを適用します(`POST /api/recipes/{id}/apply`)。どちらも HotLoop 自身のものです。HotLoop はすべてのフィールドとパラメータを検査し、値を合わせるために動かすことはなく、すべての書き込みを書き込みゲートに通し、記録を残します。Flow は理由として `flow:<node id>` を送り、ノードに理由があればその後ろにあなた自身の言葉が付き、HotLoop はそれを実行や適用の隣に、書き込み監査とログブックに、Flow がサインインしたアカウントで記録します。スクリプトは、オフにしない限り実行の終了を待ち、実行が成功した場合にのみ、トレースを含む実行結果とともにメッセージが先へ進みます。レシピは、すべての対象が書き込まれたときにのみ、各値の `verification` とともに先へ進みます。それ以外はすべて、HotLoop の理由とステータスとともに Catch ノードに届きます。ビジー状態のスクリプト、範囲外のフィールド、ステップ2で失敗した実行、1つの対象が武装されていないために全体が拒否されたレシピ、途中で止まったレシピ(何個の対象が書き込まれたかを示します)などです。書き込まれたものは何も元に戻されません。それも HotLoop の規則だからです。

**書き込みは設備を変えます。HotLoop がいない限り、儀式はありません。** 従うべき確認の仕組みを Flow で探しましたが、設備向けのものはありません。存在するガードは、ノードが到達できる範囲を限定するもの(`scan` の `discovery.allowedCIDRs`、ファイルとシークレットのスコープ)で、メッセージが何かをする前に「よろしいですか」と尋ねるものはありません。だから書き込みノードも尋ねません。書き込みノードは、誰かがキャンバスに意図して置き、他のすべてと同じデプロイ記録を通したものであり、出力にメッセージが届くことは、機器が確認したことを意味します。

HotLoop がネットワーク上にあるときは、設備を守るのは HotLoop の役目です。すべての設備書き込みノード(`modbus write`、`opcua write`、`s7 write`、`ethernetip write`)には、既定で空の **Write through HotLoop** と、この書き込みの対象となる HotLoop 内のタグを `device/tag` と書く **HotLoop tag** があります。HotLoop を選ぶと、値は PLC ではなく `POST /api/write` に送られます。HotLoop の書き込みゲートが、次の順序で判断します。書き込みがオンになっているか、タグが武装されているか、値がタグの範囲内か。そのタグについての HotLoop 自身のアドレス、データ型、スケールが適用されるので、Flow ノード上のアドレスとデータ型は使われません。ノードの設備接続は選ばれたままなので、HotLoop をクリアするとノードはまったく元のとおりに戻ります。ゲートが拒否した書き込みは設備に届かず、ゲートの言葉とともに Catch ノードに届きます(`HotLoop's gate refused the write to plc-1/sp: value is outside the tag's configured range: 120 is outside 0..95 (HTTP 422)`)。到達できない HotLoop も書き込みを失敗させます。直接書き込みにフォールバックすることはありません。それはゲートが一度も見ていない書き込みになってしまうからです。ゲートは書き込みごとに bool、数値、テキストのいずれか1つを受け取るので、レジスタのリストは、その旨のメッセージとともに拒否されます。

テストでは、HotLoop 自身の API で機器、タグ、スクリプト、レシピ、オペレーターアカウントを作り、そのうえで両端を確認します。HotLoop が何と言ったかと、その後シミュレートされた PLC が何を保持しているかです。ゲートを通した書き込みはレジスタに入ります。タグの範囲外の書き込み、武装されていないタグへの書き込み、HotLoop にないタグへの書き込み、HotLoop に到達できない状態での書き込みは、すべてゲートの言葉とともに失敗し、レジスタは元のままです。スクリプトとレシピはゲートを通して実行・書き込みされ、範囲外のフィールドは拒否され、`hotloop state` は HotLoop が保持するものを読み、`hotloop in` はゲート経由の書き込みが起こした変更を、以前の状態とともに送ります。HotLoop の書き込み監査とログブックで、アカウントと理由を確認しました。HotLoop がセッションを忘れたあとの再サインインと、拒否されたログインもテストしています。再接続とフィードの差分検出は、文書化された形で応答する小さな HotLoop の代役を相手にテストしています。本物の HotLoop の接続を狙ったタイミングで切ることは、私たちにはできないからです。未対応:HotLoop は Flow がサインインしたアカウントを記録し、`flow:<node id>` が理由として入りますが、API はクライアントが自分の行為者を名乗る方法を与えていないためです。接続はシステムの証明書ルートだけを信頼するので、プライベート CA の `https` HotLoop には対応していません。`switch.turn_on` のような HotLoop のサービスを直接呼ぶノードはありません。それはスクリプトかレシピが、HotLoop のチェックとともに行います。

S7 は python-snap7 3.2.1(MIT)のサーバーを相手にテストしています。これは純粋な Python で書かれ、gos7 とは別のプロトコル実装です。

S7 ノードも EtherNet/IP ノードも、まだ Siemens や Rockwell の実機には出会っていません。python-snap7 のサーバーは CPU のようにビット書き込みをしない(バイト全体を上書きする)ので、ビット書き込みはバイトを読み返してではなく、ワイヤー上でリクエストごとに確認しています。`ab_server` はタグ名を大文字小文字を区別して照合しますが Logix は区別せず、gologix は小文字で送るので、シミュレーターのタグは小文字です。

**`Aes256_Sha256_RsaPss` は OPC UA のドロップダウンにありません。** このポリシーに `BadSecurityChecksFailed` で応答するサーバーがあるため、Flow はそれらで失敗するポリシーを提示しません。Basic256 と Basic128Rsa15 は非推奨で、シミュレーターも提供しないので、同じく外しています。テストできない設定にはドロップダウンの項目を与えません。

未対応:Modbus RTU、TLS 上の Modbus、OPC UA のイベント、履歴、メソッド呼び出し、ブラウズ、S7 のタイマーとカウンター、PCCC コントローラーはありません。2^53 を超える64ビット整数は、フローの数値では保持できないため、正確な桁の文字列として出てきます。
