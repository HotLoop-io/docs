絶対値だけを載せています。並べた比較表は機材が変わるたびに動き、結局この製品よりも別のものを説明することになります。

Flow は、デスクトップで毎秒約 15,000 件、Raspberry Pi 5 で毎秒約 13,000 件のリクエストに応答し、メモリはデスクトップで 30 MiB 未満、Pi で 42 MiB です。工場のラインにあるボックスに収まるほど小さなフローエンジンの意味は、まさにここにあります。

## フロー

5 つのノードです。HTTP エンドポイント、プロパティ編集 3 つ、応答 1 つ。意図的に速くしたものは何もありません。小さな実際のフローの形であり、フローエンジンのベンチマークが対象とすべきものです。負荷生成器はクローズドループです。各クライアントは前のリクエストが戻ってから次を送るため、相手側が受け止められる量を測定し、対象が遅れたときにオープンループの生成器が報告するような、誤解を招くレイテンシは生じません。

## 自分で実行する

`hotloop-flow bench` はバイナリに同梱されています。`-launch` はバイナリを起動し、フローが応答するまでの時間(コールドスタート)を計り、2 秒後にプロセスの常駐メモリ(アイドル)を読み取り、負荷中はそれをサンプリングしてピークを保持します。`-launch` なしの `-target` は、すでに動作中のインスタンス(コンテナや Pod)を HTTP 経由で動かし、スループットとレイテンシを測ります。

```bash
hotloop-flow bench -mode http -launch ./hotloop-flow -target http://127.0.0.1:18897 -path /bench -duration 30s -warmup 5s -connections 8
hotloop-flow bench -mode engine -chain 5 -messages 200000
```

## 結果

x86 デスクトップ(24 CPU)で、ネイティブの静的バイナリを使い、それぞれ 3 回測定しました。

| <span class="sr-only">詳細</span> | 実行 1 | 実行 2 | 実行 3 |
|---|---|---|---|
| コールドスタート | 0.05 s | 0.05 s | 0.05 s |
| RSS、アイドル | 16.7 MiB | 16.7 MiB | 16.4 MiB |
| RSS、負荷時のピーク | 26.4 MiB | 26.4 MiB | 28.5 MiB |
| HTTP スループット | 15.0k req/s | 15.3k req/s | 13.0k req/s |
| HTTP レイテンシ p50 / p95 / p99 | 0.39 / 1.22 / 1.82 ms | 0.39 / 1.20 / 1.78 ms | 0.41 / 1.49 / 4.03 ms |
| エンジン、メッセージあたり | 2.61 µs | 3.11 µs | 2.20 µs |
| エンジン、メッセージあたりの割り当て | 3,868 bytes | 3,869 bytes | 3,868 bytes |

## Raspberry Pi 5 での結果

8 GB の Raspberry Pi 5 1 台で、クロックを 2.0 GHz に制限し、k3s 上の Pod として、ノードには他に何も載せずに測定しました。同じフローを 3 回、それぞれ新しい Pod で実行しています。

| <span class="sr-only">詳細</span> | 実行 1 | 実行 2 | 実行 3 |
|---|---|---|---|
| コールドスタート | 0.46 s | 0.15 s | 0.10 s |
| RSS、負荷時のピーク | 40.3 MiB | 40.5 MiB | 40.3 MiB |
| HTTP スループット | 13.2k req/s | 13.4k req/s | 13.3k req/s |
| HTTP レイテンシ p50 / p95 / p99 | 0.48 / 1.45 / 2.78 ms | 0.48 / 1.42 / 2.72 ms | 0.48 / 1.44 / 2.74 ms |
| エンジン、メッセージあたり | 8.15 µs | 7.74 µs | 7.89 µs |

同じボードで同じコマンドを 600 秒続けると、11.4k req/s、p50 が 0.58 ms、p99 が 3.00 ms に落ち着きます。このボードは能動的な冷却なしのヒートシンクだけで動作し、これだけの負荷ではスロットリングされるため、負荷が続くボックスについてはこれが正直な数値です。

### この数値が示さないもの

**HTTP スループットには HTTP スタックが含まれます。** 意図的です。フローを呼び出すクライアントが体験するのはこの値だからです。スケジューラーの測定ではありません。エンジンの行は、経路に I/O がまったくないのでスケジューラーの測定です。

**フローの形、ペイロードの大きさ、同時実行数はそれぞれ 1 通りだけです。** MQTT の発行やデータベースへの書き込みのような実際の I/O を行うフローは、I/O が支配的です。この数値はランタイム自身のオーバーヘッドであり、すべてのワークロードについての約束ではありません。

**テールは中央値より大きく動きます。** 飽和すると、すべてが待ち行列に入り、p99 は待ち行列が決めます。リクエストを処理するコストが現れるのは中央値です。

**これはベンチマーク用のフローであり、永続ワイヤーではありません。** 永続ワイヤーの背後のストアや、SD カードへの書き込みは、ここでは測定していません。

## メモリ

RSS は、`/proc` から読み取ったプロセス自身の常駐メモリです。カーネルがコンテナに計上する量を示す `podman stats` の値とは異なり、そちらはプロセスが実際に保持している量よりはるかに低く表示されることがあります。
