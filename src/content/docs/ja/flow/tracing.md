午前2時に値がおかしくなっても、デバッグサイドバーが教えてくれるのはその値だけです。通った9つのノードのどれが変えたのか、遅いノードがどれだけ抱え込んだのか、入ってきたときはどんな姿だったのかは分かりません。それを知るには、フローのあちこちに Debug ノードを置いてデプロイし、再発を待ち、また外すしかありませんでした。

そこで、フローに入るすべてのメッセージにトレースが付きます。サイドバーのデバッグメッセージにはどれも **Trace** ボタンがあり、1回クリックするとそのメッセージが通った経路がキャンバス上で点灯します。通ったノードと辿ったワイヤーが光り、一度も触れなかった部分は暗くなります。経路上の各ノードは、そのメッセージを保持していた時間を示し(`8.3 µs`、3つに分かれたものを処理したなら `8.3 µs ×3`)、横の Trace パネルはすべてのホップを順に並べて、そのノードが受け取ったままのメッセージを見せます。行をクリックすればそのノードに移動します。失敗したホップは赤で、下にエラーが出ます。

メッセージが実際に進む道を、そのまま追います。

- **Split を通って。** 1つの測定値が3つになっても、3つすべてがトレースに載り、分割後のすべてのノードでそれぞれが独立したホップになります。
- **Join を通って。** Join のあとのホップは、たまたま最後に着いた1つだけでなく、Join がそのために取り込んだすべてのメッセージを親に持ちます。それを供給した3つの枝がすべて点灯します。
- **サブフローを通って。** 中のノードは独自の id を持つコピーとして動き、ホップはその id で記録されます。キャンバスが点灯させるのは、いま見ているタブにあるノードであるサブフローのインスタンスです。
- **Catch に入って。** 失敗したノードはそのホップにエラーを持ち、それを受けた Catch が次のホップで、エラーによって到達したと印が付きます。

トレースはメッセージに乗って運ばれますが、メッセージの中にはありません。どのフローも `msg = {...}` で読んだり壊したりできず、Debug ノードにもテストにもワイヤー上のペイロードにも現れません。

## 増え続けません

監視しているラインの上で動くため、あらゆる方向に上限があり、上限は[設定](/ja/flow/configuration/)の `trace:` にあります。

| 上限 | 既定値 |
|---|---|
| 保持するトレース、新しい順 | 256 |
| 1つのトレースが保持するホップ数、ループが際限なく書き込まれないように | 512 |
| ホップがコピーを保持する最大のメッセージ | 16 KiB |
| 合計の概算、古いものから忘れる | 16 MiB |
| 1秒に開始する新しいトレース | 1,000 |

16 KiB を超えるメッセージは時間情報を保ち、大きすぎて表示できないと印が付き、再生もテスト化もできません。1秒あたり新しいトレースが 1,000 を超えると、その秒の残りのメッセージはトレースされません。1秒に10万回話すセンサーが、そうしなければ1件ごとにトレースの代価を払うことになるからです。スキップされたメッセージや、移動中にトレースが押し出されたメッセージは、旅の残りをトレースなしで進みます。途中で新しいトレースを始めても、頭を失った旅の尾でバッファを埋めるだけだからです。すべて `/metrics` で数えられるので、いつ起きているか分かります。

耐久試験:**5つのノードに100万メッセージ、2026-10-18**、[上の数値](/ja/flow/overview/#数値)と同じマシンです。強制 GC 後のヒープを10万メッセージごとに計測しました。

| トレース | ヒープ、各チェックポイント | 毎秒のメッセージ数 |
|---|---|---|
| トレース無効 | **1.3 MiB** | 192,596 |
| すべてのメッセージをトレース (`perSecond: 0`) | **2.7 MiB** | 115,770 |
| 既定の上限 | **4.0 MiB** | 195,199 |

10回のチェックポイントすべてで同じ値です。トレーサーは最初から最後のチェックポイントまで、256件のトレースで 808,448 バイトを保ち、途中で100万件のうち 999,744 件を忘れ、16 MiB には一度も近づきませんでした。すべてのメッセージをトレースすればコストはかかります。このチェーンは毎秒 192k から 116k に落ちました。既定の上限があるのはそのためです。毎秒 1,000 件のトレースなら、コストは誤差に埋もれ、それ以下ならトレース1件は約 3 KB です。それでもすべてのメッセージが必要なら `perSecond: 0` を設定し、決める前にその表の最初の行を読んでください。次で再現できます。

ヒープが平らでなくなればテストは失敗します。

## 下書きで再生する

悪い値が見つかり、直し方も見当がついて、キャンバス上のノードを変えました。デプロイして確かめないでください。**Replay into draft** は、トレースを始めたメッセージを、いまキャンバスにある状態のフロー(デプロイ済みかどうかに関係なく)に流し込み、最初にどこへ着いたかと比べて今回どこに着くかを教えます。

「着く」とは、メッセージが止まった場所のことです。Debug ノード、MQTT Out、何にも一致しなかった Switch、まだ待っている Join などです。それぞれについて、比較は同じであること、変わったプロパティ(`payload: "HIGH" -> "CRITICAL"`)、元はそこで終わったのに再生は終わらなかったこと、またはその逆を示します。再生自体の経路もキャンバスに点灯するので、下書きがどこへ送ったか見えます。**Back to the original trace** で最初のトレースに戻せます。

[フローテスト](/ja/flow/tests/)と同じ方法で、本物のランタイムと本物のノードを持つ子プロセスで動き、理由も同じです。下書きは中のすべてのノードを起動し、その中の何も工場に触れられません。そのため、Web サービスを呼ぶはずだったノードは何も返さず、出力が応答に左右されるフローは差分として現れます。それが正直な結果です。話したことのない PLC と話したふりはしません。

## トレースがテストになる

Trace パネルの **Make test** は、トレース全体から[フローテスト](/ja/flow/tests/#エディタからのテスト)の下書きを作ります。トレースを始めたメッセージを入ってきたソースに入れ、テストが監視できるすべての終着点に、そのノードが受け取った値を期待値として置きます。デバッグメッセージからテストを作るときと同じ2回のクリックで、入り組んだフローにはこちらのほうが向いています。トレースは、メッセージが届いたすべての端を覚えているからです。3つの Debug ノードに分かれれば期待値は3つで、デバッグメッセージ1つなら1つでした。

作れないときは理由を伝えます。サブフローの中、ソースの2番目の出力、または保持するには大きすぎるメッセージから始まったトレースは、テストが必要とする形では戻せません。また、Switch に捨てられたメッセージは、テストが監視できる場所のどこにも着かないので、中身のないテストとして書かれる代わりに拒否されます。確認するもののないテストは通ってしまうからです。

## OpenTelemetry

コレクターを指定すると、すべてのホップがスパンとして出ていきます。

```yaml
trace:
  otlp:
    endpoint: http://collector:4318   # OTLP over HTTP; /v1/traces is added
    headers: {x-api-key: ...}         # if the collector wants one
    serviceName: hotloop-flow
```

トレースは OpenTelemetry のトレースで、ホップはスパンです。メッセージを送ったホップがその親になります。Join のスパンは最初のものを親に、残りをリンクに持ちます。各スパンは、ノード id、ノードタイプ、メッセージ id、ノードが次へ送ったメッセージ数、到達した出力ポートを持ち、エラーはエラーステータスを持つスパンです。**メッセージは決して外に出ません。** ペイロードは工場のデータで、コレクターは他人のサーバーなので、出ていくのは旅の形と時間だけです。

仕様が定める JSON エンコーディングの OTLP/HTTP で通信し、1つのファイルに手書きしています。同じ1回の POST のために protobuf と gRPC を伴う OpenTelemetry SDK を取り込むことはしません。バイナリにはサイズの予算があり、それをこのために使うつもりはありません。すべてのスパン id、親、リンク、名前、属性、エラーステータスが一致する必要があります。そのテストにはモックがどこにもありません。コレクターが落ちていれば、エクスポートはスパンを捨てて数え、フローは気づきません。`hotloop_flow_otlp_spans_failed_total` が 0 を超えれば分かります。
