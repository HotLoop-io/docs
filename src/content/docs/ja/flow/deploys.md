「何が変わったのか、誰が変えたのか、元に戻してほしい」。ラインが止まったあと、誰もが最初に尋ねることです。`.bak` ファイル3つでは、そのどれにも答えられません。誰がやったかを知らず、3回保存すると上書きされ、必要なのはいつも4つ目です。

そこで、デプロイのたびに `data/deployments/` の下に変更できない記録を書きます。誰がデプロイしたか(クライアントの主張ではなくトークンから)、どこから、いつ、残したメモ、置き換えたリビジョン、バイト単位のフローファイル、そしてデプロイ直後の認証情報です。認証情報は、認証情報ファイルとまったく同じ方法で暗号化されます。記録は追記のみです。ログは既定で直近100件を保持し(`history.retain`、0なら全件を保持)、最新のものは決して削除しません。最新のものが、いま動いているものだからです。

```bash
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:1880/deployments
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:1880/deployments/42/flows > flows-42.json
```

メモはデプロイと一緒に渡します。包んだドキュメントの `"note"`(`{"rev": ..., "flows": [...], "note": "..."}`)か、`HotLoop-Flow-Deployment-Note` ヘッダーです。ドキュメント形式があるのは、ブラウザーがヘッダーに Latin-1 以外の文字を入れられず、人は自分の言語でメモを書くからです。

痛い目に遭って初めて必要だと気づく機能が2つあります。

- **手作業の編集を見つけます。** プロセスが止まっているあいだに誰かがディスク上のフローファイルを編集し、ログが最後に記録したものと違う場合、起動時にそれを示す `baseline` 項目として記録します。フローファイルがすでにある状態での初回起動も同じです。そうでなければ、手作業の編集は誰も記録していない過去として静かに埋もれます。
- **書き込めないログがラインを止めることはありません。** その時点でフローファイルはすでに保存されているので、デプロイを拒否すると、次の再起動までディスクと実行中のフローが食い違ったままになります。デプロイは進み、レスポンスとログの両方が、このデプロイには記録がないと言葉で伝えます。

API は、記録の中の認証情報を、暗号化されていてもいなくても決して渡しません。認証情報は元に戻すという1つの仕事のために保管されており、履歴のエンドポイントはそれを持ち出す手段ではありません。

## 差分はレビューのように読める

フローファイルの行単位の diff は、正直ですが役に立ちません。ノードを20ピクセル動かせば変更で、しきい値を変えても変更です。どちらがプレスを止めかねないのか、レビューする人には分かりません。そこで Flow はノード単位で比較します。

```
1 changed, 2 moved

Tab "Line 3" (t1)
  ~ switch "Pressure check" (sw1)
      rules[1].v: "7.5" -> "8.0"
      wire added: port 1 -> change "set alarm" (alarm1)

Moved on the canvas only
  mqtt in "press 01" (in1)
  debug "ok" (ok1)
```

追加、削除、変更を、プロパティごとに古い値と新しい値とともに示し、どの配線が出力ポートごとに動いたかを示し、**レイアウトはロジックと分けて扱います**。ラベルの移動、サイズ変更、非表示は「キャンバス上で移動」であり、変更ではないので、整理整頓は整理整頓として読めます。認証情報は「設定」または「変更」と表示され、値は決して表示されません。サブフロー内の編集はサブフローに表示され、サブフローのポートをドラッグするのもレイアウトです。

どこでも同じ答えが出ます。エンジンのパッケージ1つから出ているからです。

- `GET /deployments/{from}/diff/{to}` は2つのデプロイを比較します。
- `POST /flows/diff` は、稼働中のものと、まだ誰もデプロイしていないドキュメントを比較します。デプロイを押す前に見るのがこれです。
- コマンドラインの `hotloop-flow diff old.json new.json` です。プログラム向けは `-json` です。違いがあると、`diff` と同じく終了コード 1 で終わります。
- **git の中で。** これをフローファイル用の git の diff ドライバーにすると、`git diff`、`git log -p`、`git show` が JSON の塊の代わりに意味単位の diff を表示します。

  ```bash
  git config diff.hotloop-flow.command 'hotloop-flow diff'
  echo 'flows.json diff=hotloop-flow' >> .gitattributes
  ```

  difftool としても使えます。`git config difftool.hotloop-flow.cmd 'hotloop-flow diff "$LOCAL" "$REMOTE"'` を設定し、`git difftool -t hotloop-flow` を実行します。

自分自身と比較したフローは、パーサーが受け付けるどのドキュメントでも、変更はまったくありません。

## 元に戻す

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  -H "HotLoop-Flow-Deployment-Rev: $CURRENT_REV" \
  -d '{"note":"42 broke the label printer"}' \
  http://localhost:1880/deployments/41/rollback
```

ロールバックは、古い記録を**新しい記録として**もう一度デプロイします。履歴は追記のみのままです。デプロイ41には触れず、ロールバックは「デプロイ41へのロールバック」と、誰が、なぜ行ったかを示す独立した項目になります。フローファイルはバイト単位で戻るので、当時と同じリビジョンです。

**認証情報も戻ります。** すべての記録がそのときの認証情報を持っているので、削除したノードはブローカーのパスワードとともに戻り、戻ったのにログインできない、ということが起きません。匿名クライアントを拒否する本物の Mosquitto に対してテストしています。サブスクライバーを削除し、デプロイし、ロールバックすると、再びログインしてメッセージが流れます。

何かを書く前に、3つの場合に拒否します。古い `HotLoop-Flow-Deployment-Rev` は、デプロイと同じ 409 を受け取ります。他の人のデプロイと競合するロールバックも、やはり競合だからです。保持期間によってすでに削除されたデプロイは 404 です。そして、現在の認証情報シークレットで認証情報を復号できない記録は 422 です。どこにもログインできないフローは、うまくいったように見えるだけのロールバックだからです。

## エディタで

**Deploy はデプロイしません。** レビューを開きます。稼働中のものに対するエンジンの diff を、キャンバスに描き、言葉でも一覧にし、メモを書く欄を添えます。緑は追加、琥珀色は変更、青は移動のみで、削除されたノードや配線があった場所には赤い幽霊が置かれます。変更のあるタブには点が付きます。2つ目の Deploy ボタンが実際にデプロイするボタンで、メモはログに入ります。レビューを開いているあいだに何かを編集すると、レビューは閉じます。その後に変更したものについてのレビューは、これから押し出すものについての嘘になるからです。

**履歴パネル**は、すべてのデプロイを、誰が、いつ、メモとともに一覧にします。*Changes* は、そのデプロイを読み取り専用のキャンバスで開き、変更点をその上に描きます。作業中のコピーは、置いたままの状態で残ります。*Roll back* は理由を尋ね、未保存の編集を捨てようとしていれば警告し、デプロイします。

**デプロイの競合では、相手が何をしたかが分かります。** 以前はブラウザーの `confirm()` が、相手のものが何かを言わずに、相手のものを上書きするか自分のものを失うかを尋ねていました。いまは、誰がデプロイしたか、いつか、そのメモと、ノード単位の変更を示し、そのうえで、相手のものを読み込むか、自分のもので上書きするか、編集を続けるかを選べます。

**コピー、切り取り、貼り付けは期待どおりに動き、フローファイルの形式で話します。** ノードを選んで Ctrl+C を押すと、クリップボードには他のすべてのフローツールが読むのと同じ JSON が入るので、チャット、チケット、別のボックスに貼り付けられます。貼り付けはポインターのある場所に、毎回新しい id で置かれるので、2回貼り付ければコピーが2つできるだけで、衝突は決して起きません。コピーしていないものへの配線は、何もない場所を指したままにせず切られ、ノードが使う設定ノードは一緒に付いてきます。貼り付け先のフローにその設定ノードがすでにある場合、接続数を数える相手に2本目の接続を開かず、コピーはそれを共有します。認証情報は決してクリップボードには入りません。貼り付けバッファにあるパスワードは、バグ報告に紛れ込む経路だからです。

**Import と Export** は、選択範囲、1つのフロー、すべてについて同じことを行い、コピー元の欄、Download ボタン、取り込み時のファイル選択があります。不正なものには理由が示され(「id a が2回出ています」「エントリー1に id がありません」)、ダイアログは開いたままです。このランタイムにないノードタイプは、グレーの破線で入り、どれなのかを取り込みが伝えます。黙って捨てられるノードは、騒ぐノードより悪いからです。

画面もそのファイルの一部です。フローが描くダッシュボード(`ui_tab`、`ui_group`、ウィジェット)はフロー内のノードなので、お客様の画面は Export と Import を通じてフローとともに移動し、どれも HotLoop Flow 自体の中には存在しません。

**サブフローは専用のキャンバスで編集します。** *+ subflow* を押すと、入力と出力のポートが付いた状態で開きます。他のものと同じように、内側のノードにつなぎます。*Subflow properties* で、名前、色、出力の数、インスタンスが設定できるプロパティを決めます。フロー上のインスタンスは、形が変わると追随し、パレットにはすべてのサブフローが並ぶので、1つ置けます。インスタンスをダブルクリックすると、固有の名前と、プロパティごとの固有の値を設定できます。サブフローは、自分自身の中にも、自分を含むサブフローの中にも置けず、まだ使われているサブフローは削除できません。エディタは、次のデプロイに見つけさせるのではなく、その場でそう伝えます。

**選択範囲からサブフローへ。** ノードを選んで *Selection to subflow* を押します。ノードは専用のサブフローに移り、その場所にインスタンスが入ります。選択範囲の境界を越えていたすべての配線はポートになります。内側への道が1つだけなら、それがサブフローの入力であり、別の場所へ向かっていた選択ノードの各出力はサブフローの出力になるので、フローはこれまでどおりに動きます。サブフローの入力は1つなので、選択範囲が2つの異なるノードにつながっていると、そう伝えて何も変更しません。両方を両方から供給すると別のフローになるからです。グループを選ぶと、その中のすべてと一緒に移ります。フローに属し、選択範囲だけが使う設定ノードは、指す先とともにサブフローへ入ります。残された側も使う設定ノードは、代わりにグローバルになり、両端が同じ接続を共有し続けます。接続数を数えるボックスでの2本目のブローカー接続は、私たちが出荷しない種類の驚きだからです。移したノードが読み(env 型、文字列中の `${NAME}` や `$(NAME)`、`env.get`)、フローが宣言している環境変数は、フローへ転送するサブフローのプロパティになるので、値はこれまでの場所から来続け、インスタンスが上書きできます。Ctrl+Z でまとめて元に戻せます。

**フロー。** タブをダブルクリックするか *Flow properties* を押して、名前を変えるか削除します。削除は確認を求め、フロー上のすべてのノードを一緒に消し、ファイルが何もない場所を指さないよう、他のフローからそのフローへ張られていた配線とリンクを切ります。削除したノードを名指ししていた Catch、Status、Complete のスコープからも、そのノードを外します。リストの全体が削除された Catch や Status は、最後の id を保ちます。空のリストはフロー全体を意味し、1つを見ていたノードを知らないうちにすべてを見る状態に切り替えることはしません。Ctrl+Z は、デプロイするまで元に戻します。最後のフローは削除できません。フローのないランタイムには、ノードを置く場所がないからです。

**設定ノード**は、パレットの *configuration* の下にあります。どのキャンバスにも置かれないので、タイプをダブルクリックしてダイアログを埋めると、*configuration in use* の下のリストに追加され、ダブルクリックで編集、バツで削除します。ノードがまだ使っているものは削除できず、いくつが使っているかを伝えます。ノードのダイアログにある「Add one from the palette first」が案内する先がここです。

**配線の削除。** Alt を押しながらクリックします。ふつうのクリックでは何も起きないので、選択中に配線をかすめてもフローは壊れません。Ctrl+Z で戻せます。

**永続配線。** 配線をダブルクリックします。*Durable* にチェックを入れると、太い青で描かれ、配線が出ていくノードのファイルに `ew_durable` が入ります。印はノードのペアに付くので、その間のすべての配線に効きます。ランタイムへの配線なので、印を付けてもノードは再起動しません。

**グループ。** Ctrl+G は選択範囲を包み、Ctrl+Shift+G はばらします。タイトルバーをダブルクリックして、名前と色を付けます。グループをドラッグすると、中のすべてが付いてきます。ノードをグループへドラッグすると加わり、外へドラッグすると抜けます。グループは入れ子にできます。グループを削除すると中のものも削除され、Ctrl+Z ですべて戻ります。

**検索**(Ctrl+F またはボタン)は、すべてのフローとサブフローを一度に見ます。名前、タイプ、id、すべての設定、関数本体の途中の1行まで対象です。ヒットすると、正しいタブへ移り、ノードが選択されて表示の中央に来ます。設定ノードも表示され、キャンバス上に場所がないので、ヒットするとそのダイアログが開きます。

**デバッグのフィルター。** サイドバーを、1つのフロー、選択中のノード、1つの語、またはエラーだけに絞れます。これは、これから届くものだけでなく、すでにログにあるものにも適用されるので、絞っても、見ていた行が消えることはありません。

これらすべては、プルリクエストのたびに、エディタを組み込んだ本物のバイナリに対して、本物のブラウザーでクリックして確認しています。ランタイムが提供するすべてのノードのダイアログが含まれます。リストは `GET /nodes` から来るので、来月追加されたノードは、誰かが追加を覚えていなくても、来月にはテストに入ります。このテストを書いているときに、Chromium でこれまで一度も動いたことのなかったものが2つ見つかりました。ノードをダブルクリックしてダイアログを開くことと、配線をノードの上にドラッグして落とすことです。キャンバスはドラッグのあいだずっとポインターを握っているので、イベントの対象はいつもキャンバスで、ノードの上で離した配線はノードを見つけられませんでした。どちらも、ビジュアルエディタのバグとしてはこれ以上ないほど恥ずかしいものです。どちらも直しました。

## コードとしてのフロー

フローがレビューされる場所はリポジトリなので、リポジトリがそれをデプロイできるべきです。フローファイルを git に置き、上の diff ドライバーを設定してプルリクエストがレビューのように読めるようにし、マージでデプロイさせます。

```bash
hotloop-flow export -o flows.json          # the live file, byte for byte, to commit
hotloop-flow deploy -file flows.json -note "PR #12: line 3 pressure check"
```

`deploy` は、稼働中のものとの diff を、他の場所と同じテキストで表示し、その diff を作ったリビジョンを基準にデプロイします。その間に誰かがデプロイすれば、黙って上書きされるのではなく、409 と赤いパイプラインになります。`-expect-rev` は、レビュー済みの計画が作られたリビジョンに固定し、`-dry-run` は diff を表示して何もデプロイしません。変更するものがないファイルは何もデプロイせず、履歴にも何も追加しないので、フローに触れなかったマージがログを散らかすことはありません。起動に失敗するノードはデプロイされ、それでもジョブは失敗にします。フローの残りは動いており、誰かが見る必要があるからです。`export -deployment 41` は、履歴からどのデプロイでも取り出します。

**パイプラインは、管理者パスワードを決して持ちません。** API トークンを受け取ります。

```bash
hotloop-flow token -name ci
```

トークンを一度だけ表示して pipeline のシークレットストアに入れられるようにし、ランタイムに渡すハッシュも表示します。デプロイ用トークンなら `HOTLOOP_FLOW_DEPLOY_TOKEN_HASH`、それ以外なら設定ファイルの `auth.tokens` です。ランタイムは、パスワードと同じく、ハッシュだけを保持します。デプロイ用トークンは、フローの読み取りとデプロイ(ロールバックを含みます)ができ、それ以外は何もできません。設定も inject もエディタも使えません。どちらのコマンドも、トークンを `HOTLOOP_FLOW_TOKEN`(または `-token-file`)から、インスタンスを `HOTLOOP_FLOW_URL`(または `-url`)から読み、コマンドラインにトークンを書くことは決してありません。書くと、プロセス一覧と、コマンドをそのまま表示するすべての pipeline ログに残るからです。履歴にはトークンがデプロイした者として `token:ci` と表示され、パイプラインが渡したメモが付きます。

認証情報は、この方法では決して移動しません。フローファイルの中にはないので、git からのデプロイは、すべてのブローカーのパスワードをそのままの場所に残します。

## ご希望なら git のミラー

デプロイのログはボックスにあります。リポジトリは、他の全員がすでに見ている場所で、Web 表示、blame、バックアップがあり、読み方を知っている人がいます。Flow をリポジトリに向けると、すべてのデプロイが、Flow だけが書き込むブランチへのフローファイルのコミットになり、**デプロイした人が作者**で、デプロイした時刻で、メモがメッセージになります。

```yaml
history:
  git:
    url: https://git.plant.example/line3/flows.git
    branch: main              # one nobody else pushes to
    path: flows.json
    emailDomain: plant.example  # dana deploys, the commit is from dana@plant.example
```

パスワードは git サーバーのアクセストークンで、ファイルではなく Secret から `HOTLOOP_FLOW_GIT_PASSWORD` に入れます(`HOTLOOP_FLOW_GIT_URL` と `HOTLOOP_FLOW_GIT_USERNAME` も使えます)。パスワードを含む URL は起動時に拒否されるので、URL はいつでもログに出せます。`http://` と `https://` のみです。イメージには `file://` 用の git バイナリも `ssh://` 用の鍵もなく、プッシュのたびに失敗するミラーは、起動を拒否するミラーより悪いからです。ロールバックと起動時のベースラインは、コミットの中で自分が何であるかを示し、すべてのコミットに `Flow-Deployment: N` トレーラーが付きます。これにより、再起動したプロセスや、クローンが消えたプロセスが、リポジトリが示す地点から、重複なしにそのまま再開します。

**デプロイを決して止めません。** プッシュは専用のゴルーチンで行われます。git サーバーが落ちている、遅い、プッシュを拒否する場合でも、デプロイには何のコストもかかりません。コミットは `data/git-mirror` の下のローカルクローンで待ち、次に成功するプッシュで出ていき、1分ごとに再試行されます。`GET /deployments` はミラーがどこまで進んだかと直近のエラーを示し、`hotloop_flow_git_mirror_behind_deployments` がアラートを設定する数字です。Basic 認証の後ろにある git 自身の smart-HTTP サーバーに対してテストしています。3回のデプロイで3人の作者による3つのコミットができ、サーバーが拒否したプッシュは待って、拒否をやめたときに追いつき、断るのに10秒かかる git サーバーがあっても、デプロイは数ミリ秒で戻ります。

純粋な Go(go-git)なので、バイナリは静的なままです。バイナリは約 3.8 MB 増え、だから推測ではなく測定しています。カタログ以前のバイナリは 48,083,106 バイトでした。
