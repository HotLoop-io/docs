---
title: "HotLoop Flow の2つのサンドボックス"
description: "Function ノードと WebAssembly サンドボックスがどう隔離されているか、それぞれが触れられるもの、後者でプラグインがどう動くかを説明します。"
---

Function ノードは JavaScript インタプリタ上で動きます([セキュリティ体制](/ja/flow/security/)を参照)。1回の呼び出しに 11.6 ~ 13.7 µs かかります。メモリに対する境界ではありません。ループの中でメモリを確保する関数は、ポッドが落ちるまで Go のヒープを増やし続け、JavaScript インタプリタにできるのは実時間でのタイムアウトだけです。

こちらは1回の呼び出しに 184 ~ 196 µs かかり、JavaScript インタプリタの呼び出しの15倍から16倍です。完全には信用していないコードを動かすときにだけ、払う価値があります。

フローは、プラグインを通して WASM ゲストを実行します。エディタがダイアログを描くもとになる記述子を持つ署名付きモジュールで、要求して、あなたが了承しない限り、ホストへのアクセスは得られません。メモリはノードごとに上限があり、メッセージにはタイムアウトがあり、どちらかを超えたゲストは中断され、理由とともに Catch ノードに届き、ほかには何も巻き込みません。すべては[npm のないプラグイン](/ja/flow/plugins/)にあり、発行者の鍵をどう信頼するか、拒否の際に何と表示されるかも含まれます。あなたにとっての意味はこうです。Node-RED が npm と Node.js 一式のインストールを必要とすることを、Flow は読み込む前に検証できるサンドボックス化されたファイルとして実行します。

プラグインは JavaScript の代わりに Rust、TinyGo、Zig、AssemblyScript で書けるので、OT のフローが本当に求める信号処理がコンパイルされた形で動き、メモリの上限にも逆らえません。

ゲストの ABI はエクスポート3つで、そのうち2つはアロケータのフックです。意図的にこれだけ小さくしています。エクスポートはどれも攻撃面であり、ゲストの作者が正しく作らなければならないものがもう1つ増えることになります。

| エクスポート | シグネチャ | 必須 |
|---|---|---|
| `hotloop_flow_process` | `(ptr i32, len i32) -> i64` | はい |
| `hotloop_flow_alloc` | `(size i32) -> i32` | はい |
| `hotloop_flow_free` | `(ptr i32, size i32)` | いいえ |

`i64` の結果は、上位32ビットにオフセット、下位32ビットに長さを詰め、ゲスト自身のメモリにある JSON の応答を指します。すべてが JSON でやり取りされるので、どの言語のゲストでも、共有のスキーマコンパイラなしで作れます。

上限は意図的に小さくしています。これは、本当に重要なフローのそばで、エッジのハードウェア上で動くためで、もっと必要なノードは、そう申告するべきだからです。

| 上限 | JavaScript インタプリタ | WASM |
|---|---|---|
| 呼び出しごとのタイムアウト | 5 s | 5 s |
| メモリの上限 | 強制できるものはなし | プラグインが別に指定しない限りノードごとに 16 MiB、`plugins.maxMemoryMiB` を上げない限り最大 64 MiB、ハードリミット |
| 最大出力 | 16 MiB | 8 MiB |

どちらのランタイムも cgo を使わない純粋な Go です。
