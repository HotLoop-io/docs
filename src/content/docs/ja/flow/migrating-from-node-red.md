---
title: "Node-RED のフローをそのまま移行"
description: "Node-RED の flows.json を変更せずにインポートし、ノードごとの対応と、Flow が実行を拒否するものとその理由を確認できます。"
---

Flow は Node-RED の `flows.json` の v1 形式を読み込みます。Node-RED のすべてのエクスポートとフローライブラリの項目が書かれる、フラットな JSON 配列です。ファイルを指定すればそのまま動きます。

**バイト単位でそのまま読み込み、保存します。** ファイルを読み込み、何も編集せずに保存すると、まったく同じバイトが返ります。キーの順序も空白も同じで、エスケープが勝手に書き換えられることもありません。プロパティを 1 つ編集すれば、差分はノード全体ではなく 1 行になります。

Go ではこれは見た目より難しい作業です。JavaScript のオブジェクトはキーの挿入順を保つため、JavaScript のランタイムでは `JSON.parse` と `JSON.stringify` により誰も意識せずにこれが実現します。Go のマップには順序がまったくなく、`encoding/json` は意図的にキーを並べ替えます。コード内のすべての読み込み経路に順序を保つマップを押し込む代わりに、各項目の元のバイトを保持し、解析した形が変わっていなければそのまま再出力し、変わっていれば元のキー順に合わせて再エンコードします。`json.Compact` と `json.Indent` はバイトレベルの変換なので、何も並べ替えずにインデントだけを変えられます。

理由は 2 つあり、どちらも地味ですが現実的です。フローのファイルはボリュームと git にあり、Pod が再起動しただけで変わってはいけません。そして、オペレーターがラインに展開する前にデプロイの差分を確認するとき、変わった箇所だけが見え、それ以外は一切見えないようにしなければなりません。テストや型がファイルに入ってもこのルールは変わりません。新しいデータは他のツールが無視するキーに入り、往復テストはそれらを含むファイルも対象にします。

このビルドが一度も見たことのないノード種別も、読み込みと保存を経てすべてのプロパティがそのまま残るため、ここでフローを実行してあとで返しても安全です。AES-256-CTR で暗号化された Node-RED の `flows_cred.json` は読み取り専用でインポートされ、そうして読み込んだものは次の保存時に GCM で再暗号化されます。

**何かをデプロイする前に、何が起こるかを確認してください。**

```bash
hotloop-flow import flows.json
```

ファイル内のすべてのノード種別を報告します。サブフロー内のものも含み、対応、一部対応(足りない点を明記)、非対応に分類されます。サブフローの内部は、ファイルではなく展開後のグラフを基準に数えるため、中身について何も語らないままインスタンスが「対応」と報告されることはありません。机の上で知るか、ラインが止まってから知るかの違いです。

ノードがファイルにない設定ノードを指していることもあります。フローを削除すると、そのフロー専用の MQTT ブローカーも一緒に消えますが、そのブローカーを使っていたサブフローは、何も指さない ID を指し続けます。手作業での編集や、途中までしかコピーしていないエクスポートでも同じことが起きます。以前は最初のメッセージがノードに届いて初めて分かり、サーバーを参照するだけのノードはその時点でも何も言いませんでした。現在はインポートレポートにそのためのセクションがあり、すべてのノードと見つからない ID が示され、エディターは読み込み時に同じ行をログに出し、デプロイはそれらを返して、該当ノードを起動失敗としてマークし、誤った ID を持つプロパティを示します。フローの残りは動き続けます。無効にしたノードや、空欄または `true`、`false` の TLS 設定は、間違いではないので報告されません。

存在する ID が動作する ID とは限りません。初回はこの点を見落としていました。設定がタブ、サブフロー、グループ、通常のノードを指している場合や、MQTT ブローカーを指す TLS 設定のように種類の違う設定ノードを指している場合も、同じレポートと同じ起動失敗になり、その行には ID が実際に何であるかと、設定が求める種類が示されます。エディターは正しい種類しか提示しないため、これが起きるのは手作業での編集や貼り付けた ID のときだけで、まさにそこで問題になります。

互換性レベル別では、108 のメッセージノード種別は、完全が 12、一部が 50、意図的に異なるものが 14、Flow 独自が 32 です。すべてのノードは、同名の Node-RED のノードとの関係を宣言し、**ノードが一部互換を名乗りながら何が足りないかを文書で示していなければ、テストがビルドを失敗させます。** 90% 互換で残りの 10% について黙っているノードは、明らかに存在しないノードより危険です。前者はフローが動いているように見せてしまうからです。完全なマトリクスは [Node-RED との互換性](/ja/flow/compatibility/)で、手作業ではなくレジストリから生成されます。手作業で保守する互換性の文書は、日付付きの嘘だからです。

相違点はすべて意図的で、それぞれがそこに書かれています。分岐の受信先はそれぞれ自分用のコピーを受け取り、`exec` ノードは許可リストを持ってシェルを使わず、ファイルノードは範囲が限定され、[バックプレッシャーを見える形に](/ja/flow/back-pressure/)に挙げたものにはすべて上限があります。

**Node-RED のコミュニティノードの大半はここでは動きません。** これらは Node.js を必要とする npm パッケージであり、Node を必要とするパッケージが突然動くようになる将来のバージョンはありません。小さな占有量とサンドボックスのための代償であり、反対の判断ができるようにはっきり述べています。自分で書くものについては、署名付きの WASM プラグインが Flow の答えです。[npm なしのプラグイン](/ja/flow/plugins/)をご覧ください。

工場が頼りにするコミュニティノードは別の話です。Flow は Node-RED の Modbus、ダッシュボード、PostgreSQL、メールの種別を、独自の種別名で Go によりネイティブに実行します。そのため、これらを使うフローは変更なしで読み込まれて動き、周囲の関数ノードが呼び出す `Buffer` や `setInterval` も同様です。何が動き、何が異なり、何が検証されたかは docs/node-red-types.md にあります。フロー内のそれ以外のコミュニティノードは、種別名が示されたうえで単独で失敗し、フローの残りは起動します。

JSONata は、インポートしたフローがつまずく項目の筆頭でした。動かない 13 件は、それぞれの理由とともにテストで固定されており、そのうち 10 件は引き続きエラーを出しますが、コードが異なるだけです。`$moment` は惜しまれる唯一の Node-RED 関数で、黙って失敗する代わりに、何を使えばよいかを教えてくれます。

cron でスケジュールされた Inject ノードがその次でした。いまは実行され、Node-RED と同じ分に動きます。crontab は Node-RED 自身の Inject ノード内のスケジューラーである cronosjs 1.7.1 のポートが読み、cronosjs 自身が生成した 22,620 回の実行を、6 つのタイムゾーンで実際の時刻変更の前後にわたって照合しています。午前 2 時にこれが効いてきます。春に消える時間帯にかかるシフト開始は、時計が飛んだ瞬間に実行され、秋に繰り返される時間帯は 2 回ではなく 1 回だけ実行されます。スケジュールは毎分壁時計も読み直すため、誤った時刻で起動して後から NTP で修正されたボックスも、何時間も遅れずに正しい時刻で実行され始めます。

Link Call は 3 つの最後でした。いまは Link Out の戻りモードとともに動きます。「このバッチを調べる」「このインターロックを確認する」といった 1 つのロジックを専用のタブに一度書き、すべてのラインから呼び出せます。戻り道はメッセージ上にスタックとして保持されるため、呼び出されたフローも自分で呼び出しができます。戻ってこない呼び出しは、ぶら下がる代わりにタイムアウト後にエラーを出します。遅れて届いた戻りは、Node-RED と同様にそのまま出ていきます。そして、戻り先のない戻りは、Node-RED がログに残しても誰も読まない警告ではなく、Catch ノードが見るエラーになります。
