---
title: "HotLoop Flow の保存と転送"
description: "配線を永続にしておくと、その先のノードが応答しなくなったとき、メッセージは順番どおりにディスクへ書かれ、kill -9 のあとも残ります。"
---

配線を永続にしておくと、反対側のノードが追いついているあいだは普通の配線で、ディスクには何も書きません。そのノードがメッセージを受け取らなくなった瞬間、送り手が先へ進む前に、配線は同じ SQLite ファイルへあふれ出し、ポンプが古いものから順に、宛先がそれぞれを受け取るまで届けます。データベースへ一度に書き込む宛先(InfluxDB がそうです)には最大256件ずつまとめて、それ以外には1件ずつです。そのため、ヒストリアンが止まると、読み取り値はフローを塞いだり捨てられたりせず、ディスクに溜まり、復旧すれば順番どおりに入ります。正常なあいだは何も書かない代償として、`kill -9` ではメモリにあったもの、ポーリング1回分ほどが失われます。ご自身で気づくより、ここでお伝えするほうがよいと考えています。

```json
{ "id": "count", "type": "function", "ew_durable": ["influx"], "wires": [["influx", "reply"]] }
```

キーを手で書く必要はありません。エディタで配線をダブルクリックし、*Durable* にチェックを入れてください。

再起動を越えて残り、順序を保ち、ディスクのクォータ(既定は 256 MiB で、満杯になったときに何が譲るかは反対側のノードのオーバーフローポリシーが決めます)を守り、深さを `hotloop_flow_durable_wire_depth` として示します。ちょうど1回ではなく少なくとも1回の配信です。事後の振り返りで気づくより、ここでお伝えするほうがよいと考えています。正確な文言と、それでも `influxdb out` が正しく保たれる仕組みは、[docs/durable](/ja/flow/durable-state/) にあります。

証拠は `docs/durable/store-and-forward.sh` です。Podman 上の本物の InfluxDB 2.9.1 に毎秒20件の読み取り値を送り込み、10分間止めてから復旧させ、停止の途中で1回、排出の途中で1回、ランタイムを `kill -9` で落としました。受け付けた読み取り値は 15,982 件、保存された行は 15,982 行で、欠落も重複もありませんでした。正常な永続配線はそれ自体では何も書かず、コンテキストを30秒ごとに書き出す設定で、プロセス全体が毎秒20メッセージのときに書いたのは1時間あたり 1.7 MiB(1日あたり 0.04 GB)でした。表とコマンドは [docs/durable](/ja/flow/durable-state/) にあります。

## 宛先が永遠に拒否するメッセージ

既定では、配線は、宛先が処理に失敗したメッセージを、最大5秒まで間隔を延ばしながら再試行し続け、そのメッセージより後ろは何も進みません。止まっているヒストリアンには、それがちょうどよい動作です。ヒストリアンが決して受け付けない不正な読み取り値1件のためには、永久に詰まった配線になってしまうので、抜け道があり、求めるまでは無効になっています。

```json
{ "id": "count", "type": "function", "ew_durable": ["influx"], "ew_durable_attempts": { "influx": 20 }, "wires": [["influx", "reply"]] }
```

エディタの配線ダイアログで、または上のように、配線に試行回数を指定すると、宛先がキューから取り出した1件のメッセージをその回数だけ拒否したあとで、配線はそれを、拒否したノードからのエラーとしてフローに上げ、どのノードのエラーとも同じようにメッセージを添付して、次へ進みます。そのフローの Catch ノードがそれを受け取り、退避、アラート、別の場所への書き込みができます。Catch がない場合でも、エラーはデバッグのサイドバーに表示され、メッセージは失われるので、1つ配線しておいてください。メモリ上の最初の拒否はこれまでどおり Catch に届くので、Catch は同じメッセージを2回見ます。最初に失敗したときと、配線が諦めたときです。回数はメッセージごとでメモリ上にあるため、再起動するとやり直しになります。`hotloop_flow_durable_wire_given_up_total` が、深さの隣でそれらを数えます。1以上の整数でない上限は報告され、配線は再試行を続けます。黙って無視すると、止めるよう指定された誰かの配線が詰まったままになるからです。
