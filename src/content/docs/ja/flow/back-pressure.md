---
title: "バックプレッシャーを見える形に"
description: "すべてのキューに上限を設け、上限に達したときの方針を決め、収まらなかったすべてのメッセージをOOMキルになる前にグラフで見せます。"
---

これがプロジェクトのすべてです。エッジボックス上のフローエンジンに典型的な障害は、kubelet に強制終了されるまで静かに膨らむ Pod であり、それが残すログは、ポケットベルを持つ人には何も説明してくれません。そのため、メッセージやバイトが溜まりうるすべての場所に上限があり、すべての上限は、私たちが決めたのに触れずにいた制限ではなく、[Node-RED との互換性](/ja/flow/compatibility/)に書かれた文書化された判断です。

| 溜まりうるもの | それを止めるもの |
|---|---|
| ノードの受信箱 | 上限(既定 1024)と 4 つのオーバーフローポリシーのいずれか |
| 遅延とレート制限のキュー | 上限。超えると Catch ノードへ拒否されます |
| Trigger のタイマー | 上限 |
| `exec` の出力 | ストリームごとの上限。切り詰めるとエラーになります |
| `exec` のプロセス | 同時実行数の制限。超えると拒否されます |
| ファイルの読み取り | 上限あり。行単位とチャンク単位のモードがあります |
| HTTP リクエストの本文 | 上限あり |
| HTTP 応答の待機 | タイムアウト後に 504 |
| TCP 接続とフレーム | 上限あり |
| WebSocket の送信キュー | 上限あり。遅いクライアントは切断されます |

全体で設定し、ノードごとに上書きできるオーバーフローポリシー:

| ポリシー | 動作 |
|---|---|
| `block` | 送信側は `blockTimeout` まで空きができるのを待ちます。バックプレッシャーが上流に伝わります。ほとんどの場合これが正解です。 |
| `drop-newest` | 到着したメッセージを破棄します。数えられ、通知されます。 |
| `drop-oldest` | キューの先頭を外して空きを作ります。数えられ、通知されます。「最新の値だけが重要」な場合に使います。 |
| `error` | 送信は拒否され、Catch ノードに送られるので、フローが判断します。 |

黙って捨てられるものはありません。破棄はすべて数えられ、イベントとしてエディターに送られ、アラートを設定できるメトリクスとして出力されます。上限に達したとき、それを知らせるのはオペレーターではなくグラフです。

## ノードごとに 1 つのゴルーチン

すべてのノードインスタンスは、それぞれ専用のゴルーチンと受信箱を持ちます。ノード内では順序どおり、ノード間では並列です。実際の処理をする Function ノードは 1 コアを占有しますが、その間もエディター、API、WebSocket、ほかのすべてのフローは動き続けます。

## 受信側はそれぞれ自分用のコピーを受け取ります

ワイヤーが分岐すると、反対側のすべてのノードがメッセージの自分用のコピーを受け取ります。そのため、自分が所有していると思っている 2 つの分岐が互いを壊すことはなく、見た目が同じ兄弟の分岐と、配線した順序のせいで挙動が変わることもありません。火曜日にだけ再現するバグで、ここには存在しません。

無料ではありません。小さなメッセージ(測定値とトピック)のコピーには 411〜453 ns と 680 バイトかかり、5 ノードのチェーンはコピーを含めて 1.14〜1.40 µs ごとにメッセージを 1 つ動かします。コピーが痛いのは大きなバイナリペイロードで、1 MiB のバッファは受信側ごとに 128〜156 µs とヒープ上のさらに 1 メガバイトを要します。そのため大きなバイナリペイロードは、コピーせずバッファを共有する `ImmutableBytes` として渡されます。**同じ 1 MiB のメッセージで 250〜279 ns と 360 バイトです。** ファイルノードと HTTP ノードはすでにバイナリペイロードをこの方法で渡しているので、頼まなくても利用できます。

## 数えられるコンテキスト

フローコンテキストとグローバルコンテキストには `get` と `set` があり、`CompareAndSwap`、`Increment`、`Update` もあります。1 つのカウンターに get-modify-set をする 2 つの分岐は競合して更新を失い、get と set だけではどうにもなりません。`Increment` なら競合するものがありません。

しかも再起動を越えて残ります。フロー、グローバル、ノードのコンテキストはボリューム上の SQLite ファイルにあり、スコープが最初に使われたときに読み込まれ、後から書き込まれるので、Pod が戻ってきたとき、フロー内のカウンターやラッチは残した場所にあります。アトミック操作は以前と同じコードです。変更は 30 秒に 1 回の書き込みにまとめられ、すでに同じ値のものを設定しても何も書き込まれません。気の利いたことをするより、これが SD カードに与える影響のほうが大事だからです。正常な停止はすべてを書き込み、`kill -9` では最大でその 30 秒分が失われ、`store.context.flushInterval` がそのつまみです。詳細と、カードにかかる負荷は [docs/durable](/ja/flow/durable-state/) にあります。
