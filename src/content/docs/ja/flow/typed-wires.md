形の間違ったメッセージは、稼働中のラインでいちばん避けたい障害です。文字列 `"hot"` で届いた温度、欠けた `id`、リストのはずの場所に来た数値。何もクラッシュせず、フローは動き続け、下流で何かが静かに間違ったことをします。Flow はこの問題に JSON Schema を3つの段階で当てはめます。

## `json` ノードのスキーマ

`json` ノードの設定にスキーマを与えると、そのノードが扱うすべての値がそれに照らして検査されます。合う値はそのまま進みます。合わない値は Catch ノードへ行き、ワイヤーをそのまま進むことはなく、エラーは誤ったすべてのフィールドを示します。

```
does not match the schema: payload.temp: got string, want number; payload.id: missing property "id"
```

`msg.schemaError` には同じ内容が `{path, keyword, message}` オブジェクトのリストとして入っており、それに基づいて振り分けたい Catch ノードで使えます。パスは Change ノードの書き方で読みます。`payload.sensors[2].temp`

ノードの設定にスキーマがなく、メッセージが `msg.schema` を持っている場合、Node-RED の `json` ノードと同じように、そのスキーマで検証します。通ったメッセージからは `msg.schema` が取り除かれます。失敗したメッセージは持ったままです。両方あるときは設定のスキーマが優先されます。

- スキーマは、`$schema` で別のドラフトを指定しない限り JSON Schema draft 2020-12 です。ドラフト 4、6、7、2019-09 も使えます。
- 設定のスキーマが無効なら、検証器の理由とともにデプロイが失敗します。無効な `msg.schema` は、そのメッセージのエラーになります。
- スキーマは自己完結しています。別の URL やファイルへの `$ref` は取得せず拒否するので、外へ出る経路のないエッジボックスも他と同じように動きます。
- `format` は検証器が知っている形式だけ検査し、残りは無視します。ほとんどの検証器と同じです。
- どこにもスキーマのないフローは、これまでとまったく同じように動きます。

値をスキーマに照らして検査する必要がある Flow の他の部分も、同じパッケージを使います。

## ポートのスキーマ

どのノードも、受け付けるものと各出力ポートが約束するものを宣言できます。ノードに任意のキーが2つあり、どちらもフローファイルの中にあって、そのファイルを読む他のどのツールにも無視されるため、これらを持つフローもバイト単位でそのまま往復します。

```json
{"id":"sensor","type":"function","outputs":2,"wires":[["limit"],[]],
 "ew_outSchemas":[{"type":"object","properties":{"payload":{"type":"object",
   "required":["temp"],"properties":{"temp":{"type":"number"}}}}}, null]},
{"id":"limit","type":"switch","wires":[[],[]],
 "ew_inSchema":{"type":"object","required":["topic"]}}
```

`ew_inSchema` はノードが受け取るものです。`ew_outSchemas` は、出力ポートごとにスキーマ1つまたは `null` を置いたリストです。スキーマはメッセージ全体を記述するので、ペイロードは `properties.payload` です。アンダースコアで始まるキー、つまり `_msgid` とランタイムのその他の内部管理用のキーは、スキーマが見る対象から外されるので、閉じたスキーマでもそれらを書く必要はありません。`json` ノードのものと同じ JSON Schema で、同じパッケージが検査します。

**エディターが見つけられる不一致は、デプロイで拒否されます。** ワイヤーの両端がスキーマを宣言していて、両方を満たせるメッセージがない場合、テストゲートと同じく1バイトも書き込む前にデプロイが拒否されます。422 が返り、何も再起動されず、何も保存されず、監査記録に理由 `typed wires` の `deploy.refused` が残ります。

```
the deploy was refused because of 1 typed wire problem, and the flows already running are untouched; junction "sensor" (sensor) output 1 -> "limit" (limit): payload.temp: the sender sends string and the receiver takes number
```

証明できるものだけを拒否します。同じフィールドの異なる型、相手側の `enum` や範囲を外れた値、受信側が必須としているのに送信側の閉じたスキーマが除外しているフィールド、送信側が必ず送るのに受信側の閉じたスキーマが拒否するフィールドです。受信側が必須とするフィールドを送信側が単に挙げていないだけなら、拒否しません。メッセージがそれを持っている可能性が十分あるからです。`$ref`、`allOf`、`anyOf`、`oneOf`、`not`、`if` を使うスキーマは、その部分については疑いません。誤った拒否は理由なくデプロイを止めますし、証明できないものは実行時にそれでも捕まります。コンパイルできないスキーマや、ノードの出力数より長い `ew_outSchemas` も同じように拒否されます。ロールバックはテストで止められないのと同じ理由で、検査しません。

**Inject ノードのリテラルは型として数えます。** Inject は自分のスキーマを持ちませんが、確実に設定する値はスキーマと同じ価値があります。Inject が `ew_inSchema` を持つノードに直接つながっているとき、リテラルのペイロードと、それが設定する他のリテラルのプロパティが、デプロイ時にそのスキーマに照らして検査され、受信側が決して受け付けられないリテラルは同じように拒否されます。同じ 422 と、監査記録の同じ `deploy.refused` が付きます。

```
inject "reading" (i1) output 1 -> "limit" (l1): payload: the inject sets "hot", which the receiver does not take: got string, want number
```

検査するのはリテラルだけです。文字列、数値、真偽値、JSON です。タイムスタンプ、環境変数、フローまたはグローバルのコンテキスト、別のメッセージプロパティ、JSONata、バッファ、正規表現は、ノードが動くまで分からないので、推測せずに飛ばします。Inject が設定しない必須プロパティも衝突ではありません。静的でない値がそれを設定するかもしれないからです。判定するのは Inject からノードへのワイヤーだけで、先に別のノードを通るリテラルは実行時の検査に任せます。エディターもそのワイヤーに同じ衝突を描きます。

**見つけられないものは、Catch ノードとメトリクスへ行きます。** ノードに届いてその `ew_inSchema` に反するメッセージは、ノードに到達しません。ポートを出てそのスキーマに反するメッセージは、送信側で止められ、配達されません。どちらの場合も、スキーマを持っていたノードからのエラーとして発生し、Catch ノードは誤ったすべてのフィールドのパスを `msg.error.message` に、リストとして `msg.error.violations` に受け取ります。各項目は `{path, keyword, message}` です。

```
the message does not match the schema of output 1: payload.temp: got string, want number
```

`hotloop_flow_node_schema_mismatches_total` はこれらをノードごとに数え、`json` ノードの不一致も数えます。スキーマのないノードにかかるのは nil チェック1回で、スキーマが1つもないフローはこれまでとまったく同じように動きます。

## エディターでのワイヤーの型

どちらかの端に型があるワイヤーは、その型を運びます。エディターはワイヤーの曲線の真ん中に型を書きます。送信側の型は数文字(`payload {temp: number}`)で、ワイヤーにカーソルを重ねると全体が表示されます。

- **両端が型を宣言し、一致している:** 緑の輪郭と、送信側の型。
- **片端だけが宣言している:** 破線で薄く表示され、ワイヤーがまだ型なしの場所が分かります。
- **両端が宣言していて、決して一致しない:** ワイヤーとラベルが赤くなってどのフィールドか(`≠ payload.temp`)を示し、ツールチップにはランタイムが挙げる理由が出ます。デプロイはこれを拒否するので、Deploy を押す前に見えるようになります。

この赤は、エディターの推測ではありません。エディターはランタイムに `POST /flows/types` で問い合わせ、デプロイが拒否するときと同じ検査を実行するので、キャンバスとデプロイが食い違うことはありません。エディターが問い合わせるのは、キャンバス上の何かにスキーマがあるときだけで、最後の編集の少しあとです。スキーマのないフローは呼び出しも新しい描画もしません。

型はノードのダイアログの **Types** で設定します。入力スキーマ1つと、出力ポートごとに1つです。空なら型なしを意味し、一度も型を付けていないノードにキーが増えることはありません。JSON でないもの、オブジェクトでないものを書くと、ダイアログで拒否されます。
