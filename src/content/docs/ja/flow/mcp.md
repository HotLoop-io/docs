Model Context Protocol を話すエージェントは、フローをツールとして呼び出せます。フローも、HotLoop 自身を含む任意の MCP サーバーのツールを呼び出せます。これを行うのは 3 つのノードと 1 つの設定ノードです。`mcp tool` と `mcp result` がフローを公開し、`hotloop-flow-mcp-server` 接続上の `mcp client` が外へ呼び出します。センサーをダッシュボードにつなぐだけなら、ここは読み飛ばして構いません。これらのノードを使わないフローは MCP 呼び出しを一切行わず、Flow が自ら提供するツールは、フローを読み取り変更するものだけです([下記](#flow-自身のツール))。

プロトコルは Go SDK(`github.com/modelcontextprotocol/go-sdk` v1.8.0、寛容なライセンスで、プロジェクトがライセンス変更を終えるまで一部のファイルは MIT のまま、MCP プロジェクトが保守)のものです。ハンドシェイクがなくすべてのリクエストにバージョンを載せる現行の仕様改訂 2026-07-28 と、2025-11-25 までのハンドシェイク改訂の両方を、同じエンドポイントで扱います。クライアントは接続を開いたときの改訂をそのまま受け取るので、設定は不要です。

## ツールとしてのフロー

`mcp tool` ノードはツールを宣言します。名前、それを読むモデル向けの説明、入力スキーマが必要です。フローがデプロイされている間、Flow はこれを `/mcp`(管理ルートを移動した場合はその下)で公開します。呼び出しはノードから出るメッセージになり、`msg.payload` は呼び出しの引数、`msg.topic` はツール名、`msg.mcp` は `tool`、`caller`、`callId` を保持します。下流にある `mcp result` ノードが、`http response` が `http in` に応答するのと同じように答えを返します。その間にあるものは、ほかと同じ普通のフローです。

```json
[
  {"id": "t1", "type": "tab", "label": "Line"},
  {"id": "tool", "type": "mcp tool", "z": "t1", "toolName": "line_status",
   "description": "Status of a production line: its state and speed.",
   "schema": "{\"type\":\"object\",\"properties\":{\"line\":{\"type\":\"string\",\"enum\":[\"L1\",\"L2\",\"L3\"]}},\"required\":[\"line\"],\"additionalProperties\":false}",
   "x": 100, "y": 100, "wires": [["status"]]},
  {"id": "status", "type": "function", "z": "t1", "name": "status", "outputs": 1,
   "func": "msg.payload = {line: msg.payload.line, state: 'running', askedBy: msg.mcp.caller};\nreturn msg;",
   "x": 300, "y": 100, "wires": [["answer"]]},
  {"id": "answer", "type": "mcp result", "z": "t1", "x": 500, "y": 100, "wires": []}
]
```

**スキーマはフローが動く前に検査されます。** JSON Schema で、`json` ノードが読むのと同じ方法で読みます(スキーマが別のドラフトを指定しない限りドラフト 2020-12 で、別の URL への `$ref` はエラーです)。無効なスキーマ、オブジェクトでないルート、MCP が許可しないツール名、同じ名前を公開する 2 つのノードは、理由を添えてそのノードのデプロイを失敗させます。引数が合わない呼び出しには、誤ったフィールドを示すツールエラー `arguments.line: value must be one of "L1", "L2", "L3"` が返るので、モデルは修正して再試行でき、フローにはその呼び出しが届きません。オブジェクトのペイロードはオブジェクトとその JSON テキストの両方で返り、テキストはテキストで返ります。Catch ノードが供給する `mcp result`、または "The work failed" にチェックを入れたものは、エラー自身の言葉を含むツールエラーで応答します。誰も答えなかった呼び出しは、応答タイムアウト(指定しなければ 30 秒)の後にそう伝えられ、エラーは Catch ノードに渡ります。再デプロイは実行中の呼び出しが終わるのを待ちます。

**エージェントもほかの呼び出し元と同じ呼び出し元です。** `/mcp` は管理 API と同じトークン、つまりセッショントークンか API トークンだけを受け付け、それ以外は受け付けません。匿名の呼び出しはありません。トークンがなければ 401、Flow が知らないトークンも 401、`mcp.call` 権限のないトークンは 403 で、プロトコルがリクエストを見る前に判定されます。`HOTLOOP_FLOW_INSECURE` で動いているインスタンスは、ツール呼び出しには監査ログに記録する呼び出し元が必要なので、すべての `/mcp` リクエストに 403 を返します。エージェント用のトークンも、ほかと同じトークンです:

```yaml
auth:
  tokens:
    - name: agent
      hash: sha256:...          # from: hotloop-flow token -name agent
      permissions: ["mcp.call"]
      rateLimit: {calls: 60, per: 1m}   # optional; no rateLimit, no limit
```

呼び出しは、そのアイデンティティの権限で実行されます。どの呼び出し元にも `mcp.call`(または `mcp.*`、または `*`)が必要です。ツールの "Extra permission" 欄に `mcp.line3` のような別の権限を入れると、呼び出し元にはその権限も必要になり、持たなければ一覧にそのツールが表示されません。2 つのエージェントが 1 つの Flow を共有しながら、異なるツールを見ることができます。

**トークンごとに呼び出し回数を制限できます。** `auth.tokens` 内の API トークンの `rateLimit` は、期間 `per` あたりの `calls` で、省略すると 1 分です。期間はそのトークンの最初の呼び出しで始まり、回数を超えた呼び出しは期間が終わるまで拒否され、その後カウントが最初からになります。拒否された呼び出しはフローに届かず、何秒待てばよいかを示すツールエラーで応答されるので、ループに陥ったエージェントは自分が読める言葉で速度を落とすよう伝えられます。仕様にはこのためのエラーがないため、実行できない呼び出しにすでに定義されているツールエラーを使います。`rateLimit` のないトークンは制限されず、セッショントークンも人のものなので制限されません。各トークンは別々に数えられ、カウントはメモリ上にあるので、再起動すると最初からになります。拒否は理由が `rate limit exceeded` の `mcp.refused` 行になるので、呼び出しの洪水も監査ログに残ります。

**すべての呼び出しは、呼び出し元の名前で監査ログに残ります。** `mcp.call` はフローが動く前に、ツール、ノード、呼び出し ID とともに書かれ、`mcp.result` は実行後に、結果と所要ミリ秒とともに書かれます。`mcp.refused` は、誤ったトークン、権限のないトークン、呼び出せないツール、合わない引数を表します。引数そのものは書き込まれません。トークンがまったくないリクエストも書き込まれません。名前を付ける相手がいないからです。`GET /audit?event=mcp.` ですべてを読め、`?user=token:agent` で 1 つのエージェントに絞り込めます。

Flow を必要としない、MCP プロジェクト自身のインスペクターで試してください:

```bash
npx @modelcontextprotocol/inspector@2.12.0 --cli http://localhost:1880/mcp \
  --transport http --header "Authorization: Bearer $TOKEN" \
  --method tools/call --tool-name line_status --tool-arg line=L3
```

フローテストは、呼び出しが作ったはずのメッセージを `mcp tool` ノードのある位置に置き、`mcp result` は自分が返したはずの内容を `{isError, text, structuredContent}` としてテストに渡すので、サーバーなしでフローをテストできます。

## Flow 自身のツール

フロー作成者が配線したものしか呼べないエージェントは、フローを見ることも変更することもできません。そこで Flow は、フローのツールと並べて、同じ `/mcp` で 45 個の自前のツールを公開します。読み取りも書き込みもできます。7 つはフローに関するもので下の表にあり、残りは管理 API のほかのルートです。設定、パレット、監査ログ、デプロイの詳細と差分、エクスポート、フローテスト、メッセージトレース、ランタイムの数値、2 要素認証のリセット、そしてダイアグラムと計器です。ダイアグラムの一覧と読み取り、実行と停止、デバッガーの操作、パネルのコントロール設定、計器の書き込みの切り替えがこれに当たります。MCP のページには、すべてのツールとそのルートと権限、ツールではないごく少数のルートとその理由があります。

| ツール | 内容 | 権限 |
|---|---|---|
| `list_flows` | すべてのタブとサブフロー: ID、ラベル、無効かどうか、ノード数、リビジョン | `flows.read` |
| `get_flows` | エディターが読むとおりの、デプロイ済みの全体とリビジョン | `flows.read` |
| `get_flow` | タブまたはサブフロー 1 つを、そのノードとともに ID で取得 | `flows.read` |
| `deploy_flows` | **deploy**: 読み取ったリビジョンとメモを付けて、全体を置き換える | `flows.write` |
| `list_deployments` | デプロイ履歴を新しい順に | `flows.read` |
| `rollback_deployment` | 以前のデプロイに**ロールバック**し、新しいデプロイとして記録 | `flows.write` |
| `inject_node` | inject ノードを、自分のメッセージで**押す** | `inject.write` |

どれも別の実装ではありません。各ツールは、エンドポイントが認証した呼び出し元として、同じ仕事をする管理 API 自身のハンドラーを実行するので、デプロイはエディターからのデプロイが出会うものすべてに出会います。文書は解析できなければならず、リビジョンは現在のものでなければならず(空のリビジョンは意図的に上書きします)、流れるものが食い違うワイヤーは拒否され、許可されていないプラグインは拒否され、失敗したフローテストはデプロイを拒否し、いずれもそのルート自身の言葉で伝えられます。デプロイ履歴には呼び出し元とメモが記録され、監査ログには、ツール呼び出しごとに残る `mcp.call` と `mcp.result` の行に加えて、呼び出し元の名前の `deploy` または `inject` の行も残ります。呼び出し元には `mcp.call` とそのツール自身の権限が必要で、呼び出せないツールは一覧に出ません。ツールはデプロイしても残り、デプロイが外すのはフローのツールだけで、フローはこれらの名前を公開できません。

`deploy_flows` は全体を置き換えるので、エージェントはまず `get_flows` を読み、受け取った `rev` を付けて、変更したものを送り返します。

## 他のサーバーのツールを呼び出す

`mcp client` ノードは、メッセージが届くと `hotloop-flow-mcp-server` 接続を通じてツールを呼び出します。接続には、サーバーの MCP アドレス、必要ならベアラートークン、タイムアウトを設定します。ツールと引数は型付きの入力なので、どちらもメッセージから取れます。`msg.payload` は、ツールに構造化された応答があればその応答、応答がすべてテキストならテキスト、それ以外ならコンテンツがそのまま入ります。`msg.mcp` にはサーバー、ツール、応答全体が入ります。もう 1 つの操作 "List the tools" は、サーバーが持つすべてのツールを、説明と入力スキーマとともに `msg.payload` に入れます。

エラーを報告するツールはエラーを発生させ、サーバーの言葉をそのまま伝えるので、Catch ノードにはモデルが見たはずのものが見えます。**呼び出しが 2 回送られることはありません。** ツールは設備を動かすことがあり、接続が切れてもサーバーが実行したかどうかは分からないので、エラーは接続に失敗したとだけ伝え、次のメッセージが再び接続します。トークンは指定したアドレスにだけ送られ、ほかには送られず、リダイレクトには従わず、エラーにもトークンは繰り返されません。接続はシステムの証明書ルートだけを信頼します。

HotLoop の場合は、その `/mcp` のアドレスと、リリースの Secret にある `mcp-token` を使い、HotLoop の MCP ドキュメントにあるすべてのツールを使えます:

```json
{"id": "plant", "type": "mcp client", "z": "t1", "server": "hotloop",
 "tool": "get_plant_status", "toolType": "str", "arguments": "{}", "argumentsType": "json",
 "x": 300, "y": 100, "wires": [["use"]]}
```

HotLoop はこの呼び出しを MCP クライアントのものとして、自身のルールで扱います。MCP は読み書きができ、ほかのすべてと同じ関門を通るので、アームされた範囲内のタグへの `write_tag` は通り(HotLoop 自身の書き込みを有効にした後)、拒否される呼び出し、たとえば誰も書き込み可としていないタグへのものは、HotLoop の言葉でノードのエラーとして返ります。MCP を使わずにフローから HotLoop の関門を通して書き込むには、上の HotLoop ノードを使ってください。

## テストした対象

**サーバー**は、Go SDK 自身のクライアントを使い、実際の HTTP 上で両方の世代についてテストしています。一覧取得、呼び出し、拒否された引数、拒否された権限、拒否されたトークン、監査行、ノードが止まると消えるツール、さらに実際の API トークンとセッショントークン、ディスク上の監査ログを備えた管理サーバー全体を前に置いた状態までです。MCP プロジェクトの Inspector CLI 2.12.0 は、稼働中の Flow のツールを一覧し、呼び出し、トークンなしの場合と作り話のトークンの場合には拒否されました。`mcp client` ノードは実際の HotLoop 4.18.10(公開された IoT イメージ)に対して実行しました。27 個のツールをすべて一覧し、`get_plant_status`、`list_devices`、`get_states` を呼び出してその答えを使い、誤ったトークンとトークンなしで拒否され、存在しないツールと MCP に許されない書き込みについて HotLoop 自身のエラーを受け取りました。また Inspector が呼び出した Flow のツールは、HotLoop の MCP を呼び出すフローを実行し、その答えを返しました。

**未実施:** OAuth(ベアラートークンが唯一の入口で、どちらの方向も同じ)、stdio サーバー、リソース、プロンプト、サンプリング、エリシテーションと進捗通知、ツールの出力スキーマです。HotLoop 4.18.10 はハンドシェイク改訂を話すので、ノードはその方法で接続します。現行改訂のサーバーに対しては Flow 自身のものでしかテストしていません。セッションを忘れるハンドシェイクサーバー(再起動)は、その直後の最初の呼び出しを 1 回失敗させ、次の呼び出しは再び接続します。呼び出し制限は API トークン単位で、設定するまでオフなので、`rateLimit` のないトークンは、すでに上限のあるキューとリクエストサイズ 4 MiB でしか制限されません。
