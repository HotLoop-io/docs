EmberNet のテナントは、工場やラインごとに 1 つずつ、複数の HotLoop Flow を運用できます。その 1 つ 1 つをステーションと呼びます。このページでは、1 つのフローファイル、つまり 1 セットの FlowLab ダイアグラムをすべてのステーションに配置し、それぞれを確認し、失敗したステーションを元に戻す方法を説明します。

要点は次のとおりです。`hotloop-flow stations push -tenant acme -file flows.json` は、EmberNet が `acme` で稼働中と表示しているステーションへ 1 台ずつプッシュします。その後あるステーションが正常でなければ、そのステーションは元の状態に戻り、プッシュは止まります。ファイルが稼働中のロガーを再起動させる場合は、許可すると伝えるまで何も起きません。

## ステーションの出どころ

ステーションは誰も手で入力しません。一覧は、EmberNet ダッシュボードがテナントについて稼働中と表示しているもので、Running Apps ページと同じ一覧です。`hotloop-flow` というラベルが付き、稼働中で、テナントに属するすべてのアプリが対象です。ステーションには、ダッシュボードが Flux アドレスを報告していればそのアドレスで、そうでなければクラスターアドレスで接続するため、そのアドレスを解決できる場所からプッシュを実行してください。

テナントは必ず指定し、プッシュは常にその 1 つのテナントだけが対象です。ダッシュボードにはダッシュボードトークンで問い合わせ、閲覧を許されたテナントに限られますが、返ってきた結果も改めて確認します。ほかのテナントについて届いた行は破棄されて数えられるだけで、使われることはありません。稼働中の Flow がないテナントは、エラーを返します。

## コマンド

```bash
hotloop-flow stations list -tenant acme
hotloop-flow stations push -tenant acme -file flows.json -note "new line 3 logger"
```

ダッシュボードのアドレスは `-dashboard` または `HOTLOOP_FLOW_DASHBOARD_URL` から、そのトークンは `-dashboard-token-file` または `HOTLOOP_FLOW_DASHBOARD_TOKEN` から取得します。ステーションが受け付けるトークンは、`hotloop-flow deploy` と同じく `-token-file` または `HOTLOOP_FLOW_TOKEN` から取得します。`hotloop-flow token` で作成し、各ステーションにそのトークンを `flows.read`、`flows.write`、`status.read` を持つ API トークンとして渡してください(通常のデプロイトークンには最初の 2 つしかありません)。確認では各ステーションのダイアグラムを読む必要があり、通常のデプロイトークンでは読めないためです。1 つのテナントのステーションは同じトークンを使います。

| フラグ | 動作 |
|---|---|
| `-dry-run` | すべてのステーションを計画だけして、何も変更しません。稼働中の内容、各ステーションが再起動するもの、計画できなかったものを表示します。 |
| `-confirm-restart` | このプッシュで稼働中のロガーが再起動されることに同意します。 |
| `-window 02:00-04:00` | 再起動に事前に同意している時間帯で、`-window-zone`(IANA 名、省略時は UTC)で解釈されます。この時間帯内のプッシュは先に進みます。`22:00-02:00` のように午前 0 時をまたげます。 |
| `-settle 5s` | 確認がダイアグラムを稼働していないと判断するまでに、ステーションのダイアグラムが起動に使える時間。 |
| `-json` | JSON 形式のレポート。 |

終了コード 0 はすべてのステーションが完了したことを表します。3 はステーションが失敗してプッシュが止まったことを表します。4 は再起動への同意をプッシュが待っていることを表します。5 は応答がなかった、または計画できなかったためにスキップされたステーションがあることを表します。

## プッシュの動作

まず、何も変更せずにすべてのステーションを計画します。各ステーションについて、稼働中のフローファイルとリビジョンを読み、戻れるデプロイ記録を探し、ダイアグラムを一覧し、ファイルによって再起動される稼働中のロガーを割り出します。そのあと、同意が必要なものがなければ、名前順に 1 台ずつ進みます。

1. **デプロイ**は、計画が見たリビジョンを付けてファイルをデプロイするので、その間に誰かが行ったデプロイは上書きされず拒否されます。変更されたものだけが再起動します。資格情報は送られません。各ステーションが自分のパスワードを保持し、計器の書き込みは、そのステーションの誰かがオンにするまでオフのままです。
2. **確認。** ステーションは、すべてのステーションが持つべきリビジョンで応答しなければなりません。リビジョンはファイルの内容から決まるので、同じファイルならどこでも同じリビジョンで、プッシュは開始前にそれが何かを伝えます。ファイル内で自動的に起動するダイアグラムはすべて、問題なくステーションにあり、安定待ちの時間内に稼働中か完了している必要があります。起動しなかったノードも確認を失敗させます。
3. **確認に失敗したステーションは元に戻ります。** それまでのデプロイへ、独立したデプロイとしてロールバックされ、元のリビジョンになっていることが確認されます。プッシュはそこで止まります。

レポートには、各ステーションに何が起きたかが示されます。

| ステータス | 意味 |
|---|---|
| `done` | デプロイされ、確認を通過しました。 |
| `unchanged` | すでにこのリビジョンで、ダイアグラムも正しい状態です。 |
| `failed` | デプロイされていません(ステーションが拒否したか、その間に誰かがデプロイした)、またはすでにこのリビジョンで正常ではありません。何も変更されていません。 |
| `reverted` | 確認に失敗し、以前のリビジョンに戻りました。 |
| `revert-failed` | 確認に失敗し、元に戻せませんでした。このステーションには人の対応が必要です。 |
| `skipped` | 手を触れていません。応答がなかったか、稼働中のリビジョンのデプロイ記録がなく、失敗したプッシュをそこで元に戻せないためです。一度手動でデプロイするか、接続を直してから、もう一度プッシュしてください。 |
| `not-started` | このステーションの手前でプッシュが止まりました。元のままです。 |
| `planned` | ドライランの応答。 |

スキップされたステーションがあってもプッシュは止まりません。プッシュは繰り返せます。すでにそのリビジョンにあるステーションは `unchanged` なので、2 回目のプッシュは 1 回目が終えられなかった分だけを完了します。

## 再起動

自動的に起動するダイアグラムはロガーです。変更されたものをデプロイすると再起動し、削除されたものは停止します。稼働中のロガーにそうなるプッシュは、何かに触れる前に止まり、レポートが各ステーションと各ロガーを示します。そのあと、次の 3 つのうちどれかで先に進めます。

- コマンドをターミナルで実行している場合、プロンプトで yes と答える。
- `-confirm-restart` を渡す。
- 時刻が `-window` で指定した時間帯の中にある。

このどれもなければ何も再起動しません。変更のないダイアグラムは実行を保ち、新しいものはそのまま起動します。

## インスタンスから、およびエージェント向け

インスタンスは、自分のテナントのステーションへ管理 API を通じてプッシュできます。MCP ツールの `list_stations` と `push_to_stations` が使うのがこれです。次の 4 つをすべて設定すると(設定ファイルの `stations:` の下か、環境変数で)、`GET /stations` と `POST /stations/push` のルートが現れます。設定しなければ存在しません。

| 設定 | 環境変数 | 内容 |
|---|---|---|
| `stations.dashboardUrl` | `HOTLOOP_FLOW_STATIONS_DASHBOARD_URL` | テナントのインストールを把握している EmberNet ダッシュボード。 |
| `stations.tenant` | `HOTLOOP_FLOW_STATIONS_TENANT` | このインスタンスがプッシュする唯一のテナント。リクエストで別のテナントを指定することはできません。 |
| `stations.dashboardTokenFile` | `HOTLOOP_FLOW_STATIONS_DASHBOARD_TOKEN_FILE` | ダッシュボードトークンを収めたファイル。 |
| `stations.deployTokenFile` | `HOTLOOP_FLOW_STATIONS_DEPLOY_TOKEN_FILE` | ステーションが受け付けるデプロイトークンを収めたファイル。 |

チャートでは `stations.dashboardUrl`、`stations.tenant`、`stations.dashboardTokenSecret`、`stations.deployTokenSecret` で、それぞれの Secret にトークンが 1 つ入り、ファイルとしてマウントされます。Podman と Quadlet では、[Flow のデプロイ](/ja/flow/deploying/)にある 4 つの環境変数と 2 つのマウントされたシークレットです。4 つすべてを設定するか、何も設定しないかです。一部だけ設定したチャートのレンダリングは拒否され、一部だけ設定した起動も拒否されます。

`POST /stations/push` は `flows.write` を必要とし、`{flows, note, confirmRestart, window, windowZone, dryRun}` を受け取ります。`flows` を省略すると、このインスタンスが実行しているものをプッシュします。同じレポートに `ok` を加えて応答し、プッシュは監査ログに `stations.push` として残ります。`GET /stations` は `flows.read` を必要とします。同意を待っているプッシュは `needsConfirm` を true にして応答し、何も変更していません。`confirmRestart` か時間帯を付けて、もう一度送ってください。

## 証明されていないこと

ダッシュボードの一覧の形は、実際のテナントについて稼働中のダッシュボードから読み取りました。テナントのステーションに Flux 経由でプッシュしたことはないため、ダッシュボードが示すアドレスがプッシュを実行する場所から到達できるかどうかは、`stations list` と `-dry-run` でご自身で確認してください。
