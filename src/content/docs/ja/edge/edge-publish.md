Edge Publish は 4.5.0 から、HotLoop を Sparkplug B の**エッジノード**にして、読み取ったすべてを MQTT 経由で中央の Gateway に発行します。Sparkplug をプライマリホストとして受け取る既存の MQTT ドライバーとは逆向きです。これを動かすとはこういうことです。

エッジパブリッシュは、GatewayとEdgeでデフォルトでオンになっており、ブローカーとSparkplugグループが指定されるまでは待機しています。指定はチャートや環境変数から、または管理者が設定の「アラームと測定値の送り先」に入力して行います（[アラーム通知](/ja/iot/notifications/#where-alarms-go-settings)を参照）。そこに保存された内容が優先され、HotLoopの起動時に読み込まれます。キューのファイルとノードをパブリッシャーが所有しているためです。何も指定がなければ何も発信せず、HotLoopの起動を妨げることもありません。

これをオンにすると、同じ Gateway プロセスの中で動き、TimescaleDB にも接続したままなので、現場で完全な Gateway の UI と履歴をローカルで使いつつ、中央の Gateway へのアップリンクも持ちたい場合に便利です。多数の Edge Relay のフリート管理は、4.7.0(Birth と Death からの追跡)と 4.8.0(設定プッシュ)で加わりました。フリート管理のページを参照してください。

## オンにする

```sh
export HOTLOOP_EDGE_PUBLISH_ENABLED=true
export HOTLOOP_EDGE_PUBLISH_BROKER=mqtt.example.local:1883
export HOTLOOP_EDGE_PUBLISH_GROUP=Plant1
export HOTLOOP_EDGE_PUBLISH_NODE=press-line-3   # defaults to the pod hostname
export HOTLOOP_EDGE_PUBLISH_QUEUE_PATH=/data/forward.db
```

タグバス(ライブ UI とアラーム評価器が読むのと同じストリーム)に届くすべての読み取り値は、Sparkplug B の `NDATA` として発行されます。ブローカーに到達でき、確認を返している間は、メモリから直接送られ、ディスクには触れません。ブローカーが確認を返さなくなると、読み取り値はディスク上の転送キューに入り、ブローカーが戻ると順番どおりに出ていきます。

## 実際に行うこと

**Birth の前にサブスクライブします。** 最初の接続でも再接続でも、接続のたびに、ノードは `NCMD` トピック(と設定プッシュのトピック)をサブスクライブし、ブローカーが両方を確認するまで待ってから何かを発行します。Sparkplug B 3.0 がこれを要求しており(「NBIRTH メッセージを送る前に、エッジノードに関連付けられた MQTT クライアントは NCMD メッセージを受信するためにサブスクライブしなければならない」)、それには理由があります。ホストは Birth に対して即座に Rebirth や再起動の要求で応答することが許されており、先に Birth するノードはそれを取りこぼす可能性があるからです。`Start()` はサブスクリプションが整うまで戻りません。ブローカーがどれかを拒否した場合(このノードが自分の `NCMD` トピックを読めない ACL)、`Start()` はそう伝えるエラーで失敗します。誰もコマンドできないノードが、そうでないふりをして立ち上がるべきではありません。再サブスクライブできない再接続では、そのセッションで Birth せず、読み取り値は転送キューに入り続けます。

**ブローカーがいなくても、起動は止まりません。** 拒否は設定の問題で、`Start()` を失敗させます。到達できないのは障害です。`Start()` はそれをログに出して戻り、ノードはバックグラウンドで試行を続け(1 秒から始めて 1 分まで倍々に)、すべての読み取り値は転送キューに入ります。以前はこの場合も失敗しており、Edge Publish の起動に失敗すると Gateway と Edge が終了するので、WAN 障害中に再起動した機器は、WAN が戻るまで、画面も、アラームも、自動化も、バッファもないままクラッシュループに陥っていました。

**接続ごとに 1 回の NBIRTH。** 既知のすべてのタグを、安定したエイリアスとともに名前で告知し、現在の値も送ります。Birth は、最初の接続時、すべての再接続時(Sparkplug のセッションは最初からやり直しになり、シーケンス番号は再接続をまたいで意味を持ちません)、誰も見たことのないタグがバッチに現れたとき、そして要求があったときに行われます。下を参照してください。

**それ以降はすべて NDATA** で、名前なしでエイリアスだけを使います。`seq` は Birth とともに 0 から始まり、次の Birth までメッセージごとに(mod 256 で)増えます。

**NDEATH** は 2 通りです。`Stop()` のときの正常な送信と、プロセスがその機会もなく死んだ場合の、MQTT 接続自身の last will 経由です。どちらも、終了させる Birth と対応する同じ `bdSeq` の値を持ちます。ホストは、前のセッションから残っている古い Death 証明書と現在のものを、この番号で見分けます。

**`bdSeq` はセッションを数え、その数は再起動をまたいで保たれます。** MQTT の CONNECT のたびに次の番号が付きます。キューの最初のセッションは 0 で、以後 1 ずつ増え、255 の次は 0 に戻ります(Sparkplug B 3.0、Operational Behavior、Edge Node Session Establishment: `tck-id-message-flow-edge-node-birth-publish-will-message-payload-bdSeq`)。その接続の NBIRTH は、登録した will と同じ番号を持ちます(`tck-id-message-flow-edge-node-birth-publish-nbirth-payload-bdSeq`)。この値は転送キューのファイルに保存されるので、再起動したノードは 1 からやり直してホストがすでに見た will を渡してしまうことなく、数え続けます。ホストはそうした will を古いものとして無視する権利があります。再接続は新しいセッションなので、新しい番号が付きます。以前のコードは、MQTT クライアントライブラリが作成時の will を再利用するため、プロセスの存続期間を通じて 1 つを保持していましたが、ノードは今では接続の試行ごとに新しいクライアントを、したがって新しい will を作ります。このメトリクスは仕様どおり INT64 です(以前は UInt64 で出ていました。値は同じフィールドに載るので、値として読むホストは気づきません)。

**`NCMD` → `Node Control/Rebirth`。** Rebirth を要求したホストは、同じ `bdSeq` の新しい NBIRTH を受け取ります。Rebirth は新しいセッションではないので、新しい番号は付きません(`tck-id-operational-behavior-data-commands-rebirth-action-3`)。

## アップリンクが切れたとき

**ディスクは障害のためのものであり、すべてのポーリングのためのものではありません。** アップリンクが生きていてブローカーが確認を返している間、読み取り値はドレイナーが送ってブローカーが確認するまでメモリにだけ置かれ、ディスクには何も書かれません。セッションがなくなる、確認が来ない、またはメモリが 100,000 件の読み取り値を超えそうになると、メモリにあるものはすべて順番どおりにディスクキューに移り、その後のものはすべてその後ろに付き、ドレイナーはディスクから古いものを先に読み、ブローカーが確認して初めて 1 件をキューから取り除きます。ノードはディスクが空になって初めてメモリに戻るので、新しい読み取り値が古いものを追い越す瞬間はありません。

これを 2 回作りましたが、最初の版はハードウェアに合っていませんでした。送る前にすべての読み取り値をディスクに書いたので、強制終了してもノードが受け付けたものは何も失われませんでした。しかし 1 秒あたり 2,000 件の読み取りで毎秒約 5 MB を書き込み、これは 1 日 450 GB に当たり、1 コミット約 8 ページ、毎秒約 160 回のキューコミットから来ています。これは SD カードを壊し、どんなフラッシュにとっても馬鹿げた量の摩耗です。定常状態でのディスクのコストは今ではゼロで(数値は下にあります)、その代わりに手放したものは次の節ではっきり述べています。

**回線が生きているときの強制終了は、メモリにあったものを失います。** 回線が生きていてブローカーが確認を返している間の SIGKILL、電源断、カーネルパニックは、まだ確認されていない読み取り値を持っていきます。それはおおよそ 1 回のポーリング分です。毎秒 2,000 件の読み取りと数ミリ秒の確認往復なら、多くても数百件で、ホストが少し後に見るはずだったのと同じポーリング回数分です。それらは、存在したことを誰も知らないので、破棄としては数えられません。正常な停止(`Stop`、SIGTERM、再起動)は、メモリにあるものを先にディスクに書き、何も失いません。回線が切れた場合も、どちらでも何も失いません。回線が確認を返さなくなったときにノードが最初にすることが、メモリをディスクに移すことだからです。この設計が扱わない唯一のケースは、回線が生きているままプロセスが死ぬことで、意図的に扱っていません。

`HOTLOOP_EDGE_PUBLISH_QUEUE_MAX_BYTES` は障害時のキューに上限を設け、既定値は 64 MiB で、毎秒 2,000 件の読み取りでおよそ 2 分の障害に当たります(下の試験環境がその条件で動かしています。約 248,000 件の読み取りが入り、4.21.1 で測定しました)。これを超えると、古い読み取り値から捨てられ、数えられます。0 にするとキューは無制限になり、プロセスは起動時にそれを警告します。無制限のキューで非常に長い障害が起きると、ヒストリアン自身のメモリ内キューがすでに行っているように古い読み取り値を捨てるのではなく、ボリュームがいっぱいになるからです。

ドレイナーがキューに入ってから数秒以内に取り出した読み取り値は、そのポーリングの残りとともに、タグの現在値として 1 つの `NDATA` で出ていきます。それより長く待ったもの、または死んだプロセスが残していったものは、`is_historical` の印が付いて出ていくので、ホストがそれでタグの現在の状態を上書きすることはありません。再接続すると、キューは、より新しいものが発行される**前に**、古いものから先に排出されます。キューから出る道は 1 つしかないからです。

再送はまとめて行われます。最大 200 件の履歴の読み取り値が 1 つの `NDATA` を共有し、各メトリクスが自分のタイムスタンプと `is_historical` を持ちます。仕様がこれを認めているため(「同じメトリクスに対する複数の値の変化は、タイムスタンプが異なる限り、同じ Sparkplug NDATA メッセージに含めてもよい ...」、Sparkplug B 3.0、Operational Behavior、Data Publish)、メッセージが同じミリ秒に 1 つのタグを 2 回含むことはなく、次のメッセージを始めます。メッセージごとに 1 件の読み取りがボトルネックだったのでまとめました。プロファイリングがそう示しました。再送の CPU の 57% は、MQTT クライアントライブラリがパケットごとに 1 回行う write システムコールで、キューにある 200,000 件の読み取りに 58.5 秒、毎秒 3,418 件かかりましたが、工場は毎秒 2,000 件を出しています。工場より遅い再送は、終わらない滞留です。まとめると、同じ 200,000 件が 2.9 秒、毎秒 68,237 件で、ノードがまだ QoS 1 だったときに測定しました。ライブの読み取り値は、今でも 1 回のポーリングが 1 つの `NDATA` で出ます。

**仕様どおり QoS 0 で、届いたことを知るための往復があります。** NBIRTH と NDATA は QoS 0 で、retained なしで出ます(`tck-id-topics-nbirth-mqtt`、`tck-id-topics-ndata-mqtt`、Sparkplug B 3.0、Topics and Messages、Edge Node)。NDEATH の will は QoS 1 で retained なしで(`tck-id-payloads-ndeath-will-message-qos`、Payloads)、`Stop` が発行する正常な NDEATH も同じです。QoS 0 の問題は確認応答がないことです。発行はバイトがローカルソケットに届いた時点で「完了」し、それは死んだ回線に対してもうまくいくので、それを配信として扱うと、読み取り値が最も重要なまさにそのときにディスクから取り除くことになります。そのかわりにノードは、各チャンクの後ろにリクエスト(どのみち許可されている必要がある、自分の NCMD トピックへの SUBSCRIBE)を送り、ブローカーが答えるまでそのチャンクを保持します。接続は順序のある 1 本のバイトストリームで、ブローカーはクライアントのパケットを読んだ順に処理するので、その答えはそれより前のすべてを読んだことを意味します。これは PUBACK が与えていた保証で、メッセージごとに 1 回の確認の代わりに、チャンクごとに 1 回の往復です。あるテストは、無応答の回線に書き込み、キューからメモリでもディスクでも何も出ていかないことを確認します。往復がなければ、その中の 30 件の読み取りはすべて出ていきました。

**応答しなくなった接続は、待たずに見切ります。** ブローカーがチャンクを確認しない、または MQTT クライアントライブラリがメッセージを受け付けられない場合、ノードはその接続を自分で閉じて、未確認のものをすべて保持したまま(メモリにあったならディスクに移して)新しいセッション(次の `bdSeq`、新しい Birth)を始めます。そうする必要があるのは、リセットなしに死んだ回線は、カーネルの送信バッファがいっぱいになるまで書き込みを受け付け、その後は MQTT クライアントライブラリの 1 つの書き込み goroutine が write で止まってしまうからです。その goroutine は keepalive の PING を送るものでもあるので、keepalive は決して動かず、ノードは障害が続く限り死んだ接続に居座ります。6 分間の試験遮断で、回線が戻るまで気づかなかったことが分かりました。さらに悪いことに、書き込んでいたパスは新しい接続で目を覚まし、新しいセッションの NBIRTH より前に、古いセッションのシーケンス番号のまま、古いチャンクの残りを送り続けました。今ではすべてのパスが、始まったセッションに属し、そのセッションが終わると、回線ではなくエラーを受け取ります。

配信は**少なくとも 1 回**です。ブローカーが受け取ったが確認しなかったチャンクは、履歴として再送されます。配信とノードがそれを記録する間の強制終了も同じ結果になります。これを消費するホストは重複を許容しなければならず、このキューがすでに重複を除いてくれていると決して仮定してはいけません。

### 約束することと、その裏付けとなる数値

- **正確な順序。** すべてのタグのすべての読み取り値が、読まれた順にホストに届きます。ライブと再送を合わせて、SIGKILL と再起動をまたいでも同じです。
- **上限のあるファイル。** 上限はキューのファイル、つまりボリュームをいっぱいにするものにかかり、その中のデータにはかかりません。キューのファイルは、データにページヘッダー、ブランチページ、フリーリスト、成長の余裕を足したものです。以前の上限(キュー自身によるリーフバイトの数え方)では、ファイルはデータの 2 倍になりました。1 MiB 未満は 1 MiB として動き、起動時に警告が出ます。
- **障害中に失われるものはありません。** 回線が確認を返さなくなった時点から、すべての読み取り値はディスクにあり、ブローカーが確認するまでそこに残るので、すべての読み取り値は、障害、死んだ接続、正常な停止、障害の最中の SIGKILL や電源断を経ても戻ってきます。例外は上の 1 つです。回線が生きているときの強制終了や電源断は、1 回のポーリング分、つまりまだメモリにあった読み取り値を失います。
- **上限を超えたときは、はっきりと数えて捨てます。** 古い読み取り値から捨てられ、それぞれがキューファイルに保存される破棄カウントに入るので、再起動しても証拠は消えません。これは `edgePublish` の下の `GET /api/diagnostics`(Relay の `/status` では `uplink` の下)にあり、キューに入っている量、ファイルのサイズ、再送が動いているかどうかの隣にあります。ログは、それが起きている間は 1 分に 1 回だけ報告し、ポーリングごとに報告することはありません。この数は実際の損失より少し先に進むことはあっても、遅れることはありません。遮断の直前にホストが受け取ったが確認が届かなかった読み取り値は、上限がそれを取り除くときにもまだディスクにあり、ホストが持っているのに数えられます。
- **ポーリングされただけの読み取り値は、回線が生きているときの強制終了で失われることがあります。** ドライバーが読み取り値を渡してから、ブローカーが確認するまでの間、それはプロセスの中にしか存在せず、SIGKILL や電源断が持っていきます。これはすべてのポーリングをディスクに書かないことの代償で、1 日 450 GB よりもこちらを選びました。処理中のものがないときに強制終了すれば、答えは正確です。工場が出したすべての読み取り値は、配信されたか、数えられました。

このすべては、実際の HotLoop Edge が HTTP デバイス 20 台、各 25 タグを 250 ms ごと(毎秒 2000 件の読み取り)にポーリングし、実際の Mosquitto に発行する状態で測定しています。各デバイスはポーリングのたびに、前回より 1 大きいカウンターで応答するので、ホスト側の判定器は、どの読み取りが欠け、どれが 2 回戻り、どれが順序を外れたかを正確に知ります。アップリンクは、ブローカーをネットワークから抜いて切ります。Edge のソケットは、リセットも切断もなく、静かになります。処理中のものがない状態で強制終了するため、工場は SIGKILL の前に数秒間停止します(「quiesced」)。ほかの強制終了は、ポーリングがたまたまどこにあってもそこで起こります(「instant」)。実行は 2026-10-12 で、上限は 64 MiB です。「Before」はこの作業の前のビルドである `15419f1` です。「Write-ahead」は、すべての読み取り値を先にディスクに書いた `165411f` で、私たちが取り下げたものです。「Now」は、回線が生きている間はメモリ、障害中はディスクです。

判定器は、障害のない実行で 4,000 から 6,000 件の重複を報告していました。誰のものか調べるためにトラフィックを取得したところ、すべてが、前のメッセージがすでに運んだタグの最後の値を、その読み取り自身のタイムスタンプとともに繰り返す NBIRTH で、2 回送られた NDATA は 1 つもありませんでした。Birth は、ノードが持つすべてのメトリクスの現在値を運ばなければならず(それが Birth の目的です)、ノードは新しいタグが現れるたびにまた Birth するので、後の Birth が前のものを繰り返します。パブリッシャーが正しく、判定器が間違っていました。今ではこれをスナップショットとして別に数え、「重複」は、ホストが新しいものと取り違えうる唯一の種類である、データとしてもう一度発行された読み取りにだけ使います。定常の実行と 10 回強制終了の実行では、受信数は送り出した数と正確に一致します。1,296,275 と 916,350 です。

## Helm チャートでは

Gateway のチャートには、これらすべてを設定する `edgePublish:` ブロックがあります。既定ではオフで、オフの場合はブロックが存在する前にチャートが生成していたものとまったく同じものを生成します。これらを `extraEnv` で設定することは、もうしないでください。

```yaml
edgePublish:
  enabled: true
  broker: tcp://central.example.local:1883
  group: Plant1
  node: ""               # empty uses the release name
  username: ""
  password: ""           # goes into a chart-managed Secret
  existingSecret: ""     # or name your own Secret (key: secretKey)
  tls: false
  tlsSkipVerify: false
  queueMaxBytes: 67108864   # 64 MiB; 0 is unbounded
  persistence:
    enabled: true
    size: 1Gi
```

チャートが代わりに決めることがいくつかあります。

- キューファイルは、専用の PVC 上の `/data/edge-publish/forward.db` です。Pod 内のほかの場所は読み取り専用のルートファイルシステムなので、これは値ではありません。`persistence.enabled: false` の場合は emptyDir に置かれ、コンテナの再起動をまたいで障害中の読み取り値を保持しますが、再スケジュールされた Pod ではそうなりません。
- ノード id の既定値は、Pod のホスト名ではなくリリース名です。Deployment の Pod はロールアウトのたびに新しいホスト名になり、ホストは毎回新しいエッジノードを見ることになり、バッファされた読み取り値がその下で再送されてしまいます。
- Deployment は `Recreate` に切り替わり、`replicaCount` は 1 でなければなりません。キューファイルはロックを取るので、ローリングアップデートでは新しい Pod がそれを開けず、準備完了にならず、ロールアウトが止まります。また、レプリカが 2 つあれば、1 つのノード id に 2 つのパブリッシャーがいることになります。

Edge Relay のチャート(`charts/hotloop-edge-relay`)には、`enabled` を除いて同様の、独自の `edgePublish:` ブロックがあります。Relay は常に発行します。
