HotLoop の OPC UA サーバーは 4.13.0 から、Gateway に設定されたデバイスとタグを OPC UA のアドレス空間として公開します。サードパーティの OPC UA クライアント、SCADA パッケージ、HMI、ヒストリアン、UaExpert のようなテストツールが、相手側のために HotLoop ドライバーを書かなくても、Gateway のライブのタグを読み取れます。

既定でオンです(`HOTLOOP_OPCUA_SERVER_ENABLED`)。バイナリでも Helm チャートでも同じです。HotLoop の認証がオンの状態で起動し、専用のログイン `opcua-reader` を持ちます。HotLoop は生成したパスワードでこのログインを作り、設定画面が管理者にそのパスワードを表示します(`GET /api/opcua/server`)。このログインはタグと値を読めるだけで、それ以外のことはできません。HotLoop の認証がオフならログインできるユーザーがいないため、サーバーは待機してそのことを知らせます(起動を拒否はしません)。機器上の別の OPC UA サーバーが 4840 を使っていれば待機して知らせ、自分で選んだポートを開けない場合はエラーです。プラントのネットワークでリスナーを開くのは、デプロイが意図して行うことだからです。既定のポートは 4840 です。

**読み取り専用です。** [読み取り専用である理由](#読み取り専用である理由)を参照してください。すべてのタグの履歴も提供します。[履歴](#履歴)を参照してください。

## 公開される内容

有効なデバイスごとに、標準の *Objects* フォルダー直下に **Object** ノードを 1 つ、有効なタグごとに、そのデバイスの下に **Variable** ノードを 1 つ作ります。オフのデバイスとタグは公開されません。ワーカーも読み取り値もないため、公開してもクライアントの前に常に Bad のノードが並ぶだけだからです。アドレス空間は、ランタイムがポーリングしている内容そのままです。

すべてが 1 つの名前空間 `urn:hotloop:ua:gateway` にあります。名前空間 URI は定数で、ホスト名やアプリケーション URI からは導きません。クライアントはノードを URI と識別子の組として保存し、接続のたびに名前空間インデックスを探し直します。Pod 名で変わる URI だと、SCADA プロジェクトに設定したすべてのサブスクリプションが宙に浮いてしまいます。実際のクライアントと同じように、サーバーの名前空間配列から URI でインデックスを引いてください。`ns=2` と決めつけないでください。

### NodeIds

識別子は文字列で、安定しています。

| ノード | NodeId 識別子 |
|---|---|
| デバイス | `<deviceId>` |
| タグ | `<deviceId>/<tagName>` |
| タグの `EngineeringUnits` / `EURange` プロパティ | `~EngineeringUnits/<deviceId>/<tagName>` および `~EURange/…` |

タグの形式は `model.TagKey.String()` で、コードの他の部分がすでに使っている `device/tag` という書き方です。そのため NodeId とタグキーは `model.ParseTagKey` で相互に変換できます。区切りに `.` を使うとうまくいきません。デバイス ID にはドットが含まれることがあり、`a.b.c` がデバイス `a` のタグ `b.c` なのか、デバイス `a.b` のタグ `c` なのか決まらないからです。デバイス ID にスラッシュは含められないので、最初のスラッシュが常に境界になり、スラッシュを含むタグ名(OPC UA のブラウズパスや MQTT のトピックにはあります)でも正しいデバイスに解決されます。プロパティ ID はデバイス ID が使えない `~` で始まるため、タグの名前が何であっても、プロパティがタグと衝突することはありません。

### 属性

| 属性 | 値 |
|---|---|
| `BrowseName` | デバイス ID / タグ名(HotLoop 名前空間内) |
| `DisplayName` | デバイスの名前 / タグの名前 |
| `Description` | デバイスまたはタグの説明 |
| `DataType` | 下記を参照 |
| `ValueRank` | スカラー(-1) |
| `AccessLevel`, `UserAccessLevel` | `CurrentRead` のみ(0x01) |
| `MinimumSamplingInterval` | デバイスの実効ポーリング間隔(ms)。値はランタイムがポーリングする速さより速くは変わらないため、これより速いサンプリングを求めたクライアントには、この間隔に引き上げて応答します |
| `Historizing` | false |

単位のあるタグには `EngineeringUnits` プロパティ(`EUInformation`、単位 ID -1 = 「UNECE コードではない」、単位のテキストは `DisplayName`)が付き、範囲のあるタグには `EURange` プロパティが付きます。どちらもないタグには、どちらも付きません。

### データ型

ランタイムは、すべての数値の読み取り値を工学単位の float64 にまとめます。そのため宣言する型は `kindForTag` で行う表示上の選択であり、値を常に表現できる型でなければなりません。

| タグの `dataType` | OPC UA の型 |
|---|---|
| `bool`, `boolean`, `bit`, `coil`, `discrete` | Boolean |
| `string`, `text`, `char` | String |
| `int16` | Int16 |
| `uint16`, `word` | UInt16 |
| `int32`, `dint` | Int32 |
| `uint32`, `dword` | UInt32 |
| `uint64` | UInt64 |
| `int`, `int64` | Int64(符号付きで最も広い型なので、何もあふれません) |
| それ以外すべて(`float` を含む) | Double |
| **スケールまたはオフセットのある整数型すべて** | **Double** |

最後の行が重要です。スケール 0.1 の `int16` レジスターは 23.4 を読みますが、これを Int16 に切り詰めると、クライアントには Good の状態で 23 が渡されます。宣言した型に収まらない値、たとえば 70000 を返す `int16` タグは、値なしで `BadOutOfRange` と報告され、もっともらしい値に折り返したり丸めたりされることはありません。読み取り値にテキストが入っている数値タグは `BadTypeMismatch` です。

### 値、品質、タイムスタンプ

すべての読み取り(およびすべてのサブスクリプションのサンプル)は、ランタイムのライブキャッシュから応答します。`/api/values` が返すのと同じ出どころで、データベースからは読みません。ステータスコードは、その読み取り値**とその裏にあるデバイスリンクの状態**から決まります。キャッシュだけでは足りないからです。キャッシュはデバイスが最後に返した読み取り値を保持するので、その後ネットワークから落ちたデバイスにも、見た目は申し分のない最後の読み取り値が残っています。

| デバイスリンク | 読み取り値 | ステータス | 値 |
|---|---|---|---|
| 接続済み、このセッションで 1 回以上ポーリングが届いた | 良好 | **Good** | 送信 |
| | 不確か | Uncertain | 送信 |
| | 不良、または認識できない品質 | Bad | なし |
| 接続済み、このセッションでまだポーリングが届いていない | 任意 | BadWaitingForInitialData | なし |
| 接続済み、キャッシュに何もない | n/a | BadWaitingForInitialData | なし |
| 性能低下(セッションは生きていて、ポーリングが失敗または一部のみ) | 良好 | **UncertainLastUsableValue** | 送信 |
| | 不確か | Uncertain | 送信 |
| | 不良 | Bad | なし |
| 切断、接続中、無効 | 任意 | **BadNoCommunication** | なし |
| デバイスのワーカーがない | 任意 | BadOutOfService | なし |
| タグまたはデバイスが削除された | n/a | BadNodeIdUnknown | なし |

Good を報告するのは、接続済みのデバイスで、現在のセッションのポーリングによる読み取り値が良好なときだけです。切断されたデバイスのタグは、最後の値に Good を付けず、Bad と読み取られます。

経過時間は、あえて判定に含めていません。イベント駆動のソース(MQTT/Sparkplug のタグ、OPC UA のサブスクリプション)は、何も変わらなければ何時間も同じ値を持つのが正常で、時計だけで古いと判断するのは誤りです。デバイスがまだデータを届けているかどうかは、リンクが判断することです。

**ソースタイムスタンプ**は読み取り値自身のタイムスタンプで、デバイスから最後に連絡があった時刻です。Bad のステータスでも報告されます。**サーバータイムスタンプ**は、読み取りに応答した時刻です。どちらも UTC です。

## サブスクリプション

クライアントは、タグの変数にサブスクリプションとモニター対象アイテムを作り、データ変更通知を受け取れます。SCADA クライアントが実際にタグを使うのはこの方法です。このライブラリのモニタリングはサンプリング方式です。サーバーはモニター対象アイテムごとに、サンプリング間隔(100 ms 以上、かつデバイスのポーリング間隔以上)で、読み取りと同じハンドラー経由で読み取り、値またはステータスが変わると通知します。そのため、*品質*の変化、つまりデバイスの脱落も、値の変化と同じ方法で通知されます。

削除されたタグ上のモニター対象アイテムが宙に浮くことはなく、`BadNodeIdUnknown` を受け取ります。

## 設定の変更中にクライアントに見えるもの

タグを削除すると、そのタグへの読み取りとモニター対象アイテムはすぐに `BadNodeIdUnknown` を受け取り、デバイスのブラウズからもすぐに消えます。ノード自体は、その後およそ 5 秒間、到達できない状態でサーバーのノードテーブルに残り、その後削除されます。削除されたデバイスも、Objects フォルダーの下で同じように扱われます。

編集で隙間ができることはありません。編集されたタグやデバイスは、同じ NodeId のまま 1 回の操作で新しい版に入れ替わるため、その瞬間の読み取りやブラウズには古い版か新しい版のどちらかが見え、「不明」にはなりません。その上のサブスクリプションも続きます。

削除前の遅延は飾りではありません。ライブラリの Browse は、ノードの参照リストを読んでから、その間にロックを持たずに各参照先を調べます。その間に参照先が 1 つ消えると、*親*のブラウズが `BadNodeIdUnknown` で失敗し、デバイスや Objects フォルダーが存在しないかのようになります。以前はノードをすぐ削除していたため、タグの削除中にデバイスをブラウズしているクライアントや、デバイスの編集中にタグを読んでいるクライアントが、実在するノードを存在しないと告げられることがありました。

## 読み取り専用である理由

この増分では書き込みを実装していません。どの単独の変更でも黙って書き込みを加えられないよう、3 か所で同時にそう明示しています。

- 公開されるすべてのノードは `AccessLevel = CurrentRead | HistoryRead` で、書き込みハンドラーは組み込まれていません。そのため書き込みは `BadNotWritable` で拒否され、クライアントは試す前にそのノードが書き込み不可だとわかります。
- テストは viewer、operator、admin としてタグに書き込みを試み、応答が `BadNotWritable` である**こと、そしてタグの裏にあるデバイスのレジスターが変わっていないこと**を確認します。

OPC UA の書き込み経路を作るなら、その関門を通し、プリンシパルを監査証跡に引き継ぎ、マスタースイッチを尊重する必要があります。それはタグの公開の副産物として入るものではなく、独自のレビューが必要な変更です。このバージョンには、それを有効にする設定をあえて用意していません。

## 履歴

すべてのタグノードは履歴化されており、HistoryRead のアクセスレベルを持ちます。サーバーは OPC UA の HistoryRead サービスに、HotLoop 自身の履歴、つまり `/api/history` が返すのと同じ読み取り値で応答します。そのため OPC UA 接続の向こう側のクライアントは、2 つ目のデータベースなしで Gateway が保存した内容を読めます。ユーザーには値の読み取りと同じ権限(`tags.read` と `values.read`)が必要で、値の読み取りと同じ方法で、サインイン時の 1 回だけでなくセッションのユーザーに対して確認されます。

- **Raw**(`ReadRawModifiedDetails`): ウィンドウ内の読み取り値で、それぞれ固有の品質をステータスとして、固有のタイムスタンプを持ちます。開始が終了より前なら順方向、後なら新しいものから逆方向に読みます。開始は含み、終了は含みません(OPC UA 10000-11、4.6 節)。クライアントが境界を求めた場合は、開始時点またはその直前の読み取り値と、終了側でウィンドウの外にある最初の読み取り値が加わります。`NumValuesPerNode` は 1 回の呼び出しがノードごとに返す件数で、それを超える場合や 10,000 件を超える場合はページに分けて返され、各ページには 5 分間、1 回だけ使える継続ポイントが付きます(同時に保持されるのは最大 1,000 件)。何もないウィンドウは `Good_NoData` です。変更された履歴は拒否されます(`BadHistoryOperationUnsupported`)。ここでは何も変更も削除もされません。
- **Processed**(`ReadProcessedDetails`): 開始時刻から `ProcessingInterval` ごとの間隔で、Average、Minimum、Maximum、Count、Start、End、Total を返します。品質ルール(README の「The quality rule」)に従い、有限の数値を持つ良好な読み取り値だけを数えます。読み取り値が 1 件もない間隔は `Good_NoData`(Count は 0)、読み取り値が除外された間隔は `Uncertain_DataSubNormal` と読み取られ、数値が中身より良く見えることはありません。それ以外の集計はそのノードでは拒否され(`BadAggregateNotSupported`)、文字列のタグには集計がありません。10,000 間隔または 500,000 件を超えるウィンドウは、途中で打ち切らず拒否されます(`BadTooManyOperations`)。応答するのは、両端のある順方向のウィンドウだけです。
- **At time**(`ReadAtTimeDetails`): 各時刻にタグが持っていた値、つまりその時刻またはそれ以前の最後の読み取り値を、要求された時刻のタイムスタンプで返します。読み取り値は誰かが実際に取った値なので、補間はしません。タグの最初の読み取り値より前の時刻は `Bad_NoData` です。
- **イベント**は提供しません(`BadHistoryOperationUnsupported`)。デバイスやその他のオブジェクトにも履歴はなく、プロパティノード(`EngineeringUnits`、`EURange`)には HistoryRead がありません。

ヒストリアンは、ポーリングのたびではなく、読み取り値が不感帯を抜けたときに保存するため、動きの少ないタグは行が少なくなります。いつ変わったかだけでなく、その時点で何を持っていたかが必要なときは、At time か、タグの最後の読み取り値の前後の Processed ウィンドウで読んでください。`HistoryServerCapabilities` は、履歴を読めること、1 回の呼び出しが最大 10,000 値を返すことを伝えます。

## EmberNet ダッシュボード向けのボックスの状態

ダッシュボードのタスクマネージャーは、ボックスの CPU、メモリ、ディスク、リアルタイムのジッターを、ボックス自身から読みます。HotLoop がそれらをデバイスとして公開し、サーバーがその履歴を提供する([履歴](#履歴))ので、ダッシュボードがそのために自分のデータベースを読むことはありません。何が作られていて、どう有効にするかは次のとおりです。

* **デバイス。** `HOTLOOP_BOX_HEALTH_NODE` を設定すると(チャートが Kubernetes ノードの名前に設定します)、HotLoop は ID がまさにその名前のデバイスを、プロトコル `boxhealth`([プロトコルとドライバー](/ja/iot/protocols/#ボックスの状態))で作ります。タグは `cpu_util_pct`、`mem_util_pct`、`disk_util_pct`(ボックス自身のディスク)、`data_util_pct`(HotLoop がデータを置くボリューム)で、`HOTLOOP_BOX_HEALTH_JITTER_FILE` がリアルタイムエージェントの書く JSON ファイルを指しているときだけ、`rtos_jitter_core1_us`、`rtos_jitter_core2_us`、`rtos_jitter_core3_us` が加わります。これらの OPC UA ノード ID は、名前空間 `urn:hotloop:ua:gateway` にあり、文字列識別子は `<device id>/<tag>` です。
* **ボックスの数値。** チャートはホストのルートを `/host` に、その `/proc` を `/host/proc` に、どちらも読み取り専用でマウントし、ノード名を**既定で**設定します(`opcuaServer.dashboard.boxHealth.enabled: true`)。そのため HotLoop をインストールした時点で、ダッシュボードのタスクマネージャーが動きます。読むのは `/host` の statfs と CPU、メモリのカウンターだけで、権限は追加しません。制限付きの Pod Security プロファイルを適用しているクラスターは hostPath を拒否します。その場合は `enabled: false`(デバイスもマウントもなし)か、`hostMount: false`(デバイスは作られますが、ボックスのディスクと CPU は Bad と読み取られ、何をマウントすべきかが示されます)に設定してください。このデバイスに OPC UA サーバーは必要ありません。
* **読み取りだけができるログイン。** チャートは初回インストール時に、`tags.read` と `values.read` だけを持つ(ロールではなく明示的な権限リスト)ユーザー `embernet-dashboard-read` を作り、生成したパスワードを Secret `<release>-opcua-dashboard`(キーは `username`、`password`、`password-hash`)に保存します。アップグレードでローテーションされることはありません。すでにあるアカウントが再起動で変更されることもありません。
* **ダッシュボードの証明書。** ダッシュボードは、証明書ごとに 1 つのキーを `<sha1 thumbprint>.crt` という名前で持つ Secret `<release>-opcua-trust` を作ります。チャートはこれを任意で `/etc/hotloop/opcua-trust` にマウントし、サーバーはそのファイルを `trusted/`(`HOTLOOP_OPCUA_SERVER_TRUST_DIR`)に保ちます。起動時と 30 秒ごとに、新しいファイルは追加され、変更されたファイルは書き直され、Secret から消えたファイルは再び取り除かれます。オペレーターが `trusted/` に置いたファイルには決して触れず、同じ名前の Secret のキーより優先されます。
* **ポート。** リリース自身の Service(ダッシュボードが見つけるもの)は、サーバーがオンのとき、OPC UA サーバー自身の Service と並んで OPC UA のポート 4840 を一覧に載せます。

サーバーは従来どおりです。Basic256Sha256 SignAndEncrypt で、匿名セッションはなく、すべてを信頼する設定もありません。

## セキュリティモデル

### トランスポート

セキュアチャネルは、ライブラリのポリシーを Sign と SignAndEncrypt で使います。**`Basic256Sha256` は両方のモードで提供され**、クライアントが選ぶべきなのはこれです。

**セキュリティポリシー None は明示的にオンにする設定です**(`HOTLOOP_OPCUA_SERVER_ALLOW_INSECURE`、既定は false)。オンのときは起動時に警告が出ます。オフのときは None のエンドポイントは通知されず、それでも None のチャネルを開いたクライアントは、ディスカバリーしかできません。他のサービスはすべて拒否されます。オンにしても、ユーザー名とパスワードは暗号化されたトークンの中を通ります(トークンのポリシーは `Basic256Sha256` で、None ではありません)。ただし、その後クライアントが読むすべての値は保護されません。

**非推奨のポリシーは既定でオフです。** OPC Foundation は `Basic128Rsa15`(PKCS#1 v1.5 パディングの RSA)と `Basic256`(SHA-1)を非推奨にしました。以前のリリースでは、この 2 つがすべてのエンドポイント一覧に含まれ、外す方法がありませんでした。`HOTLOOP_OPCUA_SERVER_ALLOW_DEPRECATED_POLICIES`(チャート: `opcuaServer.allowDeprecatedPolicies`、既定は `false`)が決めます。

- **オフ(既定。新規インストールもアップグレードも)。** どちらのポリシーも、クライアントに知らされるエンドポイントには含まれず、どちらかでセキュアチャネルを開いたクライアントは、セッションやログインより前に、チャネルを開く時点で拒否されます。`Basic256Sha256`、`Aes128_Sha256_RsaOaep`、`Aes256_Sha256_RsaPss` のクライアントには影響しません。
- **オン。** それより新しいものを話せない古いクライアントのために、両方が Sign と SignAndEncrypt で再び提供され、起動時に警告が出ます。そのクライアントが更新されるまでの間だけオンにしてください。

アップグレード後に接続できなくなったクライアントがこの 2 つのポリシーのどちらかを使っている場合は、チャネルが拒否されていることが表れます。設定をオンにするか、クライアントを `Basic256Sha256` に切り替えてください。

### サーバー証明書

`HOTLOOP_OPCUA_SERVER_CERT_FILE` と `_KEY_FILE` を設定すると、その RSA の鍵ペアがそのまま使われます。設定しない場合は、**初回起動時に自己署名のアプリケーションインスタンス証明書が生成され、保存されます。** 保存先は `HOTLOOP_OPCUA_SERVER_PKI_DIR`(`own/cert.pem`、`own/key.pem`、鍵のモードは 0600)で、次回の起動でも同じ証明書を提示するため、一度信頼するよう設定されたクライアントが再び案内されることはありません。証明書が自己署名の間は、起動のたびに警告が記録され、OPC UA ツールが表示する形式の SHA-1 サムプリントが添えられるので、オペレーターはクライアントの表示と見比べられます。

この証明書には、通常の TLS 証明書にはない、OPC UA クライアントが確認する内容が入っています。URI のサブジェクト代替名に入る**アプリケーション URI**(`HOTLOOP_OPCUA_SERVER_APPLICATION_URI`、既定は `urn:hotloop:gateway`、設定されていれば `:<siteId>` が付きます)、DNS と IP の SAN としてクライアントが使うホスト名とアドレス(エンドポイントのホスト、`HOTLOOP_OPCUA_SERVER_CERT_HOSTS`、`localhost`、ループバック、このマシンのホスト名)、そして Part 6 がアプリケーションインスタンスに挙げている鍵の用途です。RSA-2048、5 年です。

保存された証明書が置き換えられるのは、もう役目を果たせなくなった場合だけで、クライアントが新しい証明書を信頼する必要があるという警告が出ます。残りが 30 日未満、アプリケーション URI が設定と一致しなくなった、設定されたホストを網羅しなくなった、または鍵が読めなくなった場合です。

**マシンのホスト名は、設定されたホストではありません。** 新しい証明書には入りますが、ホスト名が変わっても、保存された証明書は保たれます。コンテナーではホスト名がコンテナーの ID、Kubernetes では Pod の名前なので、再デプロイのたびに変わります。これが修正されるまではホスト名も判定に入っており、コンテナー化した Gateway をアップグレードするたびに新しい証明書が作られていました。古い証明書を信頼するよう設定されていた Ignition は、誰かが再び信頼するまで `Bad_SecurityChecksFailed` でサーバーを拒否し、それがデプロイのたびにすべてのクライアントで起きていました。クライアントは `HOTLOOP_OPCUA_SERVER_ENDPOINT_HOST` と `_CERT_HOSTS` でサーバーに到達するので、これらを設定すれば、証明書は期限が近づくまで使われ続けます。(エンドポイントのホストが設定されていない Gateway は、マシンのホスト名をエンドポイントのホストとして使い、それはクライアントに伝える値なので判定に入ります。設定すべきもう 1 つの理由です。)

**使えない鍵があり、サーバーはそれを拒否します。** RSA 鍵のおよそ 20 本に 1 本は、暗号化された OPC UA ログインを運べず、その鍵に対するすべての暗号化ログインが毎回失敗し、クライアントには「セキュアチャネルが閉じられました」としか見えません。匿名セッションと暗号化なしのセッションは影響を受けないため、原因を取り違えやすくなります。生成された鍵は、そのような鍵でなくなるまで引き直されます。オペレーターが用意した鍵がそのような鍵だった場合は、起動時に理由を示すエラーで拒否されます。

### クライアントのアプリケーション証明書

OPC UA はユーザーだけでなくアプリケーションも認証します。サーバーは `<PKI_DIR>/trusted/` に信頼リストを持ち、証明書がそこにないクライアントはセキュアチャネルで拒否され、その証明書は `<PKI_DIR>/rejected/` に書き込まれます。**クライアントを承認するには、その証明書を `rejected/` から `trusted/` に移してください。** 再起動は不要で、ディレクトリは接続のたびに読み込まれます。`<PKI_DIR>/issuers/` と `<PKI_DIR>/crl` は、CA が発行したクライアント証明書のためにそのまま渡されます。

`HOTLOOP_OPCUA_SERVER_TRUST_ALL_CLIENT_CERTS`(既定は false、起動時に警告)は、この手順を省略します。外れるのはアプリケーション認証だけで、ユーザーは引き続き HotLoop のユーザー名とパスワードで認証する必要があります。

### ログインできるユーザー

**ユーザー名とパスワード。HotLoop 自身のユーザーに対して確認します。** ユーザーデータベースは 1 つで、別の資格情報ストアはありません。認証処理は、HTTP ログインが使うのと同じ `store.User` でユーザーを探し、同じ bcrypt ハッシュ(`auth.CheckPassword`)で比較し、ユーザー名を同じ方法(小文字化、前後の空白除去)で正規化し、ユーザーが存在するかどうかにかかわらず bcrypt の比較を 1 回実行して、応答時間から実在の名前がわからないようにし、無効なアカウントを拒否します。不明なユーザー、誤ったパスワード、無効なユーザー、権限のないユーザーは、すべて同じ応答 `BadUserAccessDenied` を受け取ります。

**ユーザーがタグを読めるのは、ロールが `tags.read` と `values.read` を付与している場合だけです。** HTTP API が `/api/tags` と `/api/values` を守るのと同じ組で、同じ `auth.Permissions` と `auth.Allows` で解決されるため、組み込みロールも明示的な権限リストも、HTTP API とまったく同じように動きます。OPC UA クライアントは 1 本の接続でタグ一覧をブラウズして値を読むので、両方が必要です。片方だけの権限を持つユーザーが、もう片方を無償で得ることがないようにするためです。`values.read` を持つ組み込みロールはすべて `tags.read` も持っているので、これが効くのは明示的な権限リストを持つユーザーだけです。

**権限は、ログイン時だけでなく使用時にも確認されます。** ライブラリは、ブラウズ、読み取り、サブスクリプションのサンプルのたびにセッションのロールを求め、それはユーザーデータベースの短命なキャッシュ(10 秒)から答えられます。無効化、削除された、または権限を失ったユーザーは、クライアントが次に再接続したときではなく、その間隔のうちに、稼働中のセッションでアクセスを失い、モニター対象アイテムは Bad になります。照会に失敗した場合は「不可」として扱います。

**匿名セッションはオフです**(`HOTLOOP_OPCUA_SERVER_ALLOW_ANONYMOUS`)。明示的にオンにしない限り匿名トークンは提供されず、オンにすると起動時に警告が出ます。X.509 ユーザー ID トークンもオフで、`HOTLOOP_OPCUA_SERVER_ALLOW_X509` を設定すると提供されます([X.509 ユーザー証明書](#x509-ユーザー証明書)を参照)。HotLoop 自身の認証がオフ(`HOTLOOP_AUTH_INSECURE`)の場合、ログインするユーザーが存在しないため、匿名アクセスを明示的にオンにしない限り、サーバーは起動を拒否します。

ログインに成功すると、HTTP ログインと同じようにシステムログに記録されます。失敗したログインは、認証されていない呼び出し元が監査証跡を埋め尽くせないよう、理由とともにプロセスログにだけ記録されます。パスワードの確認は同時に最大 4 件までです。それぞれがわざと遅く作られた bcrypt の比較であり、OPC UA には HTTP の前段にあるようなレートリミッターがないためです。それ以上のロックアウトやレート制限は、HTTP ログインと同様にありません。

ライブラリは、復号したユーザー ID をパスワードも含めて、セッションが続く間セッションオブジェクトに保持します。メモリ上だけにあってログには記録されませんが、稼働中の Gateway のヒープダンプには、その時点で接続しているユーザーのパスワードが含まれることになります。

**HotLoop が受け付けるどの長さのパスワードでも、最大 72 バイト(bcrypt の上限)までログインできます。** 以前のリリースでは、65 から 72 バイトのパスワードは Web UI にはサインインできても、ここではできませんでした(`BadIdentityTokenRejected`)。長さにはパスワードに 32 バイトのサーバー nonce を足した値が使われていたため、パスワードは 64 バイトまででした。RSA にも仕様にも、そのような要求はありません。トークンは必要な数のブロックに暗号化され、デコーダーはすでにそのすべてを読んでいます。現在の確認は、長さが 32 以上で、実際に復号されたバイト数以下であることで、これは確認が本来保証すべきことです。次に確保されるバッファーの大きさを決めるためです。届いた分より多いと主張する長さは、これまでどおり拒否されるので、クライアントが送っていない分をサーバーに確保させることはできません。アップストリームの `main`(2026-11-16 に確認)にはまだこの上限があり、この変更は HotLoop-io/opcua からのプルリクエストとしてアップストリームに提案されています。

### X.509 ユーザー証明書

クライアントは、パスワードの代わりに証明書でサインインできます。既定ではオフです。`HOTLOOP_OPCUA_SERVER_ALLOW_X509=true`(チャート `opcuaServer.allowX509`)を設定すると、サーバーはセキュアなエンドポイントで Certificate ユーザートークンを提供し、起動時にそのことを知らせます。設定しない場合、どのエンドポイントも提供せず、証明書によるログインは拒否されます。

**証明書がユーザーに対応づけられる仕組み。** 管理者が証明書を HotLoop のユーザーにアタッチします。設定、OPC UA 証明書、証明書を関連付ける、の順に操作します(または API の `POST /api/users/{username}/certificates`、MCP ツールの `add_user_certificate`)。レジストリは、公開証明書、その SHA-256 サムプリント、アタッチした人と時刻、失効しているかどうか、最後にサインインした時刻を保持します。その証明書を提示し、秘密鍵を持っていることを証明したクライアントは、**そのユーザーとして**サインインします。ほかに設定は必要なく、証明書自体の内容は何も信頼されません。共通名は見ず、運用する CA もなく、誰もアタッチしていない証明書は何もしません。

**トークンが運ぶもの。** クライアントは自分の証明書に続けて、それを発行した証明書を送れます。最初のものがアタッチされた証明書で、残りは無視されます。

**鍵の証明。** ライブラリは、サーバー証明書とセッションの nonce に対するトークンの署名を確認します。これは秘密鍵の持ち主にしか作れません。別の鍵の署名で提示された証明書は拒否されます。

**できること。** そのユーザーができることと、まったく同じです。サインインには、ユーザーが有効で、パスワードログインと同じ `tags.read` と `values.read` を持っている必要があり、セッションはパスワードのセッションと同じく 10 秒ごとに確認されます。無効になった、または権限を失ったユーザーは、その間隔のうちに稼働中の証明書セッションを失います。ここにあるすべてのセッションと同様に読み取り専用で、ユーザーのロールにかかわらず、証明書セッションは書き込めません。

**拒否され、理由がログに残ります。** 登録されていない、失効している、期限切れ、まだ有効でない、またはユーザーがいない、無効、権限がない証明書は、すべて同じ応答 `BadUserAccessDenied` を受け取るため、クライアントはどのケースなのかを知ることができません。理由はプロセスログと監査証跡に残ります。

**失効。** 同じ画面で失効させます(または `POST .../{thumbprint}/revoke`)。すぐにサインインできなくなり、その証明書で開いていたセッションは 10 秒以内に終了します。失効した証明書は、失効させた人と時刻とともに一覧に残るので、拒否されたログインは「不明」ではなく「失効」と読み取られます。忘れさせるには削除します。バックアップには、失効を含むレジストリが含まれます。

**監査。** 証明書によるサインインは、すべてログブックのエントリ(カテゴリ auth)になり、ユーザー、証明書のサムプリントとサブジェクト、クライアントアプリケーションが記録されます。拒否もすべて理由付きのエントリです。同じ拒否を繰り返すクライアントは、試行ごとではなく、その証明書と理由につき 1 分に 1 件のエントリを書きます。それでも、すべての拒否はプロセスログに残ります。証明書のアタッチ、失効、削除も、行った人とともにエントリになります。秘密鍵はどのエントリにも含まれず、HotLoop が秘密鍵を持つこともありません。送受信や保存の対象は公開証明書だけです。

**アプリケーションの信頼リストとは別物です。** `<PKI_DIR>/trusted/` にあるクライアントアプリケーションの証明書は、クライアントがセキュアチャネルを開けるようにするもので、ログインではありません。ユーザー証明書は別のオブジェクトで、人のものであり、ユーザーにアタッチされます。クライアント側では 1 つの証明書が両方に使えますが、サーバーは 2 つの別の行為として扱います。

**HotLoop 自身のクライアント**も、この方法でサインインします。[プロトコルとドライバー](/ja/iot/protocols/#opc-ua)の `userCertificate` と `userPrivateKey` を参照してください。

未実装のもの: クライアント証明書を保証するものとして信頼される認証局と、それをユーザーに対応づける名前のルール。レジストリは、クライアント証明書を 1 つずつアタッチするプラントを対象にしています。CA はそれに置き換わるものではなく、追加される機能になります。

### サーバー診断は削除されています

ライブラリのセッションごとの診断ノードがあると、サインインしている任意のユーザーが、他のすべてのセッションのユーザー名とクライアントのアドレスをブラウズできてしまうため、オフにしてあり、`Server/ServerDiagnostics` オブジェクトはアドレス空間から削除されています(ライブラリはカウンターをロックなしで書き込んでもいます)。

## 実行中のアドレス空間の変更

デバイスとタグは Gateway の稼働中に追加、編集、削除され、アドレス空間は再起動なしでそれに追従します。**仕組み: ランタイムのコールバックに、安全網としてタイマーを加えたものです。**

- `runtime.Manager.OnReload` は、`Reload` が成功するたびにコールバックします。API が行うデバイスとタグのあらゆる変更は `Reload` で終わるため、UI や API で行った変更はすぐに公開されます。コールバックは調整用の goroutine に合図するだけで、自分では作業をしません。そのため、遅い調整が、それを起こした API リクエストを止めることはありません。
- 定期的な調整(`HOTLOOP_OPCUA_SERVER_RECONCILE_INTERVAL`、既定は 30 秒)が、`Reload` なしで設定を変えたものを拾います。

どちらも、データベースにある有効なデバイスとタグに対して同じ冪等な差分処理を実行します。触れるのは差があるものだけです。編集されたタグは置き換えられ、削除されたものは消され、それ以外のすべて(クライアントがその上に持つモニター対象アイテムを含む)はそのままです。新しいデバイスのノードは 1 回の呼び出しで空間に入るため、調整の最中にブラウズしているクライアントには、すべてのタグを備えたデバイスか、何も見えないかのどちらかです。

ポーリングだけに頼らずコールバックを選んだのは、ランタイムにすでにきれいな合図(`Reload`)があり、それにより変更が最大 1 間隔分ではなく数ミリ秒で見えるようになるからです。タイマーを残してあるのは、今後設定を書き込むすべての処理がリロードを忘れずに行うことに、アドレス空間が左右されてはならないからです。

## クライアントを接続する

エンドポイントは `opc.tcp://<HOTLOOP_OPCUA_SERVER_ENDPOINT_HOST>:<port>` です。クラスター内では、チャートがホストの既定をリリースの Service の DNS 名にします。クラスター外では、クライアントが実際に使う名前またはアドレス(LoadBalancer のアドレス、DNS レコード)に設定してください。これはすべてのエンドポイント URL で通知され、生成される証明書にも書き込まれます。これはサーバーがバインドする場所では**ありません**。ライブラリはすべてのインターフェースで待ち受け、ポートだけを受け取ります。

UaExpert など任意のクライアントでは、次のようにします。

1. その URL でサーバーを追加し、`Basic256Sha256` / `Sign & Encrypt` を選びます。
2. *Username* を選び、`tags.read` と `values.read` を持つ HotLoop ユーザーでログインします。または `HOTLOOP_OPCUA_SERVER_ALLOW_X509` がオンなら *Certificate* を選び、管理者がユーザーにアタッチしたユーザー証明書とその鍵を指定します。
3. サーバーがまだクライアントの証明書を信頼していないため、最初の接続は拒否されます。`<PKI_DIR>/rejected/`(クラスターでは PKI のボリューム上)でそれを見つけ、`trusted/` に移してから、もう一度接続します。
4. 初回はクライアントがサーバーの証明書を信頼するかを尋ねます。サムプリントを起動ログのものと見比べてください。
5. *Objects* → デバイス → そのタグとブラウズし、タグをデータアクセスビューにドラッグすると、サブスクライブされます。

## クライアントとしての Ignition 8.3

**2026-09-27 に、現在の安定版である Ignition 8.3.9 で確認しました。** Inductive Automation 公式のコンテナーイメージ(`inductiveautomation/ignition:8.3.9`、トライアル中のスタンダード版)を使い、デモデバイス `extruder-1` をシミュレーターで動かした HotLoop Gateway に接続しました。端から端まで確認した内容は次のとおりです。

- HotLoop の **viewer** でサインインした、`Basic256Sha256` と `SignAndEncrypt` による `opc.tcp://<gateway>:4840` への Ignition の OPC UA 接続
- 以下のとおりの、双方向の証明書の信頼
- Ignition の `[default]` プロバイダーにある、HotLoop のノードを指す OPC タグが、Good の品質で読み取られ、シミュレーターの動きに合わせて変わること。Ignition が表示したすべての値は、HotLoop 自身の `/api/values` が保持していたものでした。同じ double がそのまま回線を流れるので、近さではなく等しさで比較できます。HotLoop で `string` と宣言したテキストタグは、Ignition の String タグで「RUNNING」と読み取られました。
- Ignition からの書き込みが拒否されること。Ignition は書き込みを送り、HotLoop は `Bad_NotWritable` で応答し(応答が署名されるが暗号化されない Sign のみのチャネルで、回線上で確認)、HotLoop の値は動きませんでした。
- Ignition が提供するすべてのセキュリティポリシーとモード(下記)

### 設定方法

Ignition より先に、HotLoop 側で行うことです。

1. サーバーをオンにし、`HOTLOOP_OPCUA_SERVER_ENDPOINT_HOST` を Ignition が Gateway に到達する名前に設定します。その名前は、サーバーが通知するすべてのエンドポイント URL と、その証明書に入ります。
2. Ignition 用の HotLoop ユーザーを **viewer** ロールで作成します(管理者が `POST /api/users` で行います。[認証とユーザー](/ja/iot/authentication/)を参照)。`tags.read` と `values.read` を持つロールならどれでもサインインでき、サーバーは読み取り専用なので、それ以上は提供されません。

Ignition Gateway(ポート 8088 の Web UI)では、次のようにします。

3. Connections の下の **OPC Connections** ページ(`/app/connections/opc-client-connections`)で、**OPC UA** 接続を作成します。エンドポイント URL は `opc.tcp://<gateway>:4840`、`Basic256Sha256` / `SignAndEncrypt` のエンドポイントを選び、認証は **Username** で、HotLoop のユーザーとパスワードを指定します。接続はすぐに Faulted になりますが、それで想定どおりです。次が手順 4 です。
4. **HotLoop で Ignition を承認します。** Ignition のクライアント証明書は、いま Gateway の `<PKI_DIR>/rejected/`(コンテナーとチャートでは `/data/opcua-pki/rejected`)に、SHA-1 サムプリントの名前 `<thumbprint>.crt` であります。そのサムプリントを、OPC 証明書ページ(`/app/connections/opc/security/certificates`)に表示される Ignition 自身の OPC UA クライアント証明書と見比べます。そのうえでファイルを `trusted/` に移します。どちら側も再起動は不要です。HotLoop は拒否をログに記録しないので、このファイルだけが手がかりです。
5. **Ignition で HotLoop を承認します。** 接続は、今度は逆向きに失敗します。ステータスに `Bad_SecurityChecksFailed ... unable to find valid certification path` と出ます。HotLoop の証明書は、同じページの Ignition の拒否された**クライアント**証明書にあります。そのサムプリントを、HotLoop が起動時に記録するもの(`generated a self-signed OPC UA application certificate ... thumbprint=`)と照合し、信頼します。再起動は不要で、接続は数秒で立ち上がります。
6. **タグ。** 接続を OPC サーバーに指定し、Ignition がそのまま受け付ける名前空間 URI 形式のアイテムパスで、OPC タグを作成します。

   ```
   nsu=urn:hotloop:ua:gateway;s=extruder-1/Emberburn_Temperature
   ```

   各タグは、HotLoop が公開する型で宣言します([データ型](#データ型)を参照)。float は Float8、Boolean、String、`int16` は Int2、`uint16` や `int32` は Int4、それより広い整数は Int8 です。タググループの周期でサブスクライブされ、これより速いサンプリング周期は、HotLoop がデバイスのポーリング間隔に引き上げます。

同じことは、ファイルや REST API でも行えます。

- 接続はリソース `data/config/resources/core/ignition/opc-connection/<name>/config.json` で、プロファイルの型は `com.inductiveautomation.OpcUaServerType` です。または `POST /data/api/v1/resources/ignition/opc-connection` を使います。わかりにくい点が 2 つあります。パスワードは埋め込みシークレットで、`POST /data/api/v1/encryption/encrypt` が平文から作る JWE です。単なる文字列は受け付けられません。もう 1 つは `security` ブロックで、ゲートウェイのクライアントキーストアのエイリアスとそのパスワードが必要です。省くと接続は NullPointerException で失敗し、エイリアスが空だと `Unable to retrieve KeyPair for alias 'client'` で失敗します。両方を持つ、標準の `Ignition OPC UA Server` ループバック接続からブロックをコピーしてください。
- 証明書は `data/config/local/com.inductiveautomation.opcua/client/security/pki/`(`rejected/certs`、`trusted/certs`)にあります。API では `GET /data/opc-ua/api/v1/client/pki/certificates/rejected` と `POST .../trusted/<sha1>` を使います。**Ignition はファイル名をサムプリントにしません。** API の `signature` フィールドが SHA-1 サムプリントで、HotLoop が記録するものと一致します。
- タグは `POST /data/api/v1/tags/import?provider=default&type=json` でインポートします。
- すべての API 呼び出しには API キー(API Keys ページ、`/app/platform/security/api-keys`)が必要で、キーのセキュリティレベルのどれかがゲートウェイの読み取りまたは書き込みの権限(`security-properties` リソース)に含まれている場合だけ通ります。

### 予想される動作

- **`Bad_SecurityChecksFailed` は 2 つの別の意味を持ちます。** Ignition は、HotLoop が Ignition の証明書を拒否したとき(手順 4。メッセージに理由なし)と、Ignition が HotLoop の証明書を拒否したとき(手順 5。メッセージに *unable to find valid certification path*)で、同じステータスを表示します。まず HotLoop の `rejected/` を見てください。
- **HotLoop を再デプロイしても証明書は保たれます。** 4.15.3 までは違いました。証明書がコンテナーのホスト名を含む必要があり、それはコンテナーを作り直すたびに変わるため、アップグレードのたびに新しい証明書が作られ、誰かが再び信頼するまで Ignition はサーバーを拒否していました。[サーバー証明書](#サーバー証明書)を参照してください。PKI ボリュームを失った場合は、証明書は変わります。
- **数値と宣言されたテキストタグは `Bad_TypeMismatch` と読み取られます。** HotLoop はタグを宣言された型で公開するため、「RUNNING」を保持する `float` タグは Double になれません。4.15.3 までの Discover tags が作ったタグは、すべて `float` と宣言されていました。[プロトコルとドライバー](/ja/iot/protocols/#opc-ua)を参照してください。`string` と宣言してください。
- **書き込みは拒否され、Ignition は理由をぼかします。** HotLoop は `Bad_NotWritable` と応答します。Ignition 自身の OPC UA サーバーは、同じタグへの書き込みを求められると、汎用の `Bad`(0x80000000)しか返しません。Ignition のタグの値は変わりません。
- **非推奨のポリシーは、オンにした場合にだけ動きます。** Ignition は `Basic128Rsa15` と `Basic256` を提供します。接続では `Basic256Sha256` か `Aes` のポリシーのどれかを選んでください。
- **トライアル。** ライセンスのない 8.3 のゲートウェイは 2 時間動いたあと、Gateway の Web UI でトライアルをリセットするまで実行を止めます。期限が切れるとタグは古くなりますが、それは Ignition の動作であり、接続の問題ではありません。

### ポリシーの対応表

各行は、そのポリシーとモードで新しく開いたセッションで、ライブの値を読み取ったものです。非推奨の 2 行は `HOTLOOP_OPCUA_SERVER_ALLOW_DEPRECATED_POLICIES` をオンにして測定しました。既定のようにオフのときは、その 2 つのポリシーは提供されず、それを求めるチャネルは拒否されます。

| ポリシー | SignAndEncrypt | Sign |
|---|---|---|
| `Basic256Sha256` | 動作する | 動作する |
| `Aes128_Sha256_RsaOaep` | 動作する | 動作する |
| `Aes256_Sha256_RsaPss` | 動作する | 動作する |
| `Basic256`(非推奨) | 動作する | 動作する |
| `Basic128Rsa15`(非推奨) | 動作する | 動作する |

`None` は `HOTLOOP_OPCUA_SERVER_ALLOW_INSECURE` を設定しない限り提供されず、試していません。

## 設定

| 変数 | 既定値 | <span class="sr-only">Details</span> |
|---|---|---|
| `HOTLOOP_OPCUA_SERVER_ENABLED` | `true` | バイナリでもチャートでもオン。`false` でサーバーを止めます |
| `HOTLOOP_OPCUA_SERVER_PORT` | `4840` | TCP ポート。すべてのインターフェースで待ち受けます |
| `HOTLOOP_OPCUA_SERVER_ENDPOINT_HOST` | このマシンのホスト名 | クライアントに接続先として伝える名前。生成される証明書にも書き込まれます。**必ず設定してください。** |
| `HOTLOOP_OPCUA_SERVER_APPLICATION_URI` | `urn:hotloop:gateway[:<siteId>]` | 再起動をまたいで変わらないこと。URI であること |
| `HOTLOOP_OPCUA_SERVER_PKI_DIR` | `/data/opcua-pki` | 証明書、鍵、`trusted/`、`rejected/`。ボリュームで裏づけてください |
| `HOTLOOP_OPCUA_SERVER_CERT_FILE` / `_KEY_FILE` | n/a | 生成する代わりに、この RSA の鍵ペアを使います。両方を設定するか、どちらも設定しません |
| `HOTLOOP_OPCUA_SERVER_CERT_HOSTS` | n/a | 生成される証明書に加える DNS 名 / IP |
| `HOTLOOP_OPCUA_SERVER_ALLOW_INSECURE` | `false` | SecurityPolicy None を提供します。起動時に警告が出ます |
| `HOTLOOP_OPCUA_SERVER_ALLOW_ANONYMOUS` | `false` | ID のないセッションを受け付けます。起動時に警告が出ます |
| `HOTLOOP_OPCUA_SERVER_TRUST_ALL_CLIENT_CERTS` | `false` | クライアント証明書の承認を省略します。起動時に警告が出ます |
| `HOTLOOP_OPCUA_SERVER_ALLOW_X509` | `false` | Certificate ユーザートークンを提供します。クライアントはユーザーにアタッチした証明書でサインインします([X.509 ユーザー証明書](#x509-ユーザー証明書))。起動時に通知されます |
| `HOTLOOP_OPCUA_SERVER_ALLOW_DEPRECATED_POLICIES` | `false` | 古いクライアントのために、非推奨の `Basic128Rsa15` と `Basic256` のポリシーを提供します([トランスポート](#トランスポート))。起動時に警告が出ます |
| `HOTLOOP_OPCUA_SERVER_MAX_SESSIONS` | `20` | 0 = 無制限 |
| `HOTLOOP_OPCUA_SERVER_MAX_SUBSCRIPTIONS` | `200` | 0 = 無制限 |
| `HOTLOOP_OPCUA_SERVER_RECONCILE_INTERVAL` | `30s` | 安全網としての調整の周期 |

サーバーは `--mcp-stdio` モードでは起動しません。そのモードはエージェントがこのバイナリを補助として起動するもので、2 つ目のプロセスが本物の Gateway とポート 4840 を取り合うことが起こりえてはならないからです。

### Helm

`charts/hotloop/values.yaml` の `opcuaServer.*` です。有効にすると、Service(`<release>-opcua`、既定は ClusterIP で、クラスター外のクライアント向けの LoadBalancer や NodePort は意図して選ぶもの)、PKI ディレクトリ用の PVC(`opcuaServer.persistence`、失うとすべてのクライアントが新しい証明書を信頼し直す必要があります)、コンテナーのポートが加わります。さらに、`networkPolicy.enabled` と `opcuaServer.enabled` を併用したときに、どこからも届かないまま待ち受けるサーバーが黙って残らないよう、既定の NetworkPolicy の ingress ルールにこのポートが入ります。独自の `networkPolicy.ingress` はブローカーの場合と同様にそのルールを置き換えるので、その場合はポートを自分で列挙する必要があります。`opcuaServer.tls.existingSecret` は、生成された証明書の代わりに `kubernetes.io/tls` の Secret を提供します。
