---
title: "スクリプト"
description: "サイクルを一度書いて名前を付け、ルール、画面、MCP から実行できます。ドライランは、何かが動く前に本物の書き込みゲートを通ります。"
---

スクリプトは、名前の付いたステップの並びです。CIP サイクル。ラインのパージ。製品 B への段取り替え。どの工場にも、毎回まったく同じやり方で実行する手順がいくつかあり、誰かがそのひとつを4つ目のオートメーションにコピーして、ステップの修正を3つにしか入れなかった日が、痛い目を見る日です。だから一度だけ書いて名前を付け、それを必要とするものはすべてその名前で呼び出します。スクリプト画面のオペレーター、`call_script` ステップを持つルール、`run_script` を使うエージェント、`POST /api/services/script/turn_on` を通したあらゆるものです。

スクリプトはオートメーションの言語で書かれ、ルールのアクションと同じシーケンスランナーで動き、行うすべての書き込みは唯一の書き込みゲートを通ります。裏口はありません。もともと最初から持っていません。

## 1つの構成

```json
{
  "id": "cip_cycle",
  "name": "CIP cycle",
  "description": "Caustic wash, rinse, done. Tank must be empty.",
  "fields": [
    {"name": "minutes", "label": "Wash time", "type": "number", "min": 5, "max": 60, "step": 5, "unit": "min", "required": true},
    {"name": "circuit", "type": "select", "options": ["tank_1", "tank_2"], "default": "tank_1"}
  ],
  "sequence": [
    {"type": "condition", "params": {"expression": "float(states['sensor.cip_tank_level']) < 5"}},
    {"type": "call_service", "params": {"entityId": "switch.cip_pump", "service": "switch.turn_on"}},
    {"type": "delay", "params": {"seconds": 5}},
    {"type": "wait", "params": {"expression": "float(states['sensor.cip_return_temp']) > 70", "timeoutSec": 900}},
    {"type": "log_event", "params": {"message": "CIP on {{ vars.circuit }} for {{ vars.minutes }} minutes"}},
    {"type": "call_service", "params": {"entityId": "switch.cip_pump", "service": "switch.turn_off"}}
  ],
  "mode": "skip",
  "maxRuntimeSec": 1800
}
```

- **`id`** は小文字、数字、アンダースコアで、先頭は文字です。エンティティのオブジェクト id でもあるため、これは `script.cip_cycle` であり、決して変わりません。
- **`fields`** は実行が受け取る値です。HotLoop のどこでも同じ型つきの入力(`model.Field`)です。`min`、`max`、`step`、`unit` を持つ `number`、`max_length` と `pattern` を持つ `text`、`boolean`、`options` を持つ `select`、受け付ける `domain` を持つ `entity`、`duration`(秒、または `90s`、`1h30m`)、`alarm`、`tag`。それぞれ `required` にしたり `default` を持たせたりでき、そのフィールド自身が拒否する既定値は保存時に拒否されます。ステップはフィールドを `vars.<name>` として読みます。
- **`sequence`** はオートメーションの言語のすべてです。`call_service`、`write_tag`、`condition`、`wait`、`stop`、`call_script`、`set_variable`、`delay`、`log_event` などがあります。すべてのステップは[オートメーション](/ja/iot/automations/)にあります。
- **`mode`** と **`maxRuntimeSec`** は後述します。

スクリプトはルールと同様、保存時にコンパイルされます。デコードできないステップ、コンパイルできない式、実行が許す時間より長い待機、意味をなさないフィールドは、すべて保存時に拒否されます。ポンプが洗浄の途中で止まった午前3時ではなく、エディターで分かります。

## フィールドは検査され、直されることはありません

最初のステップが実行される前に、実行に渡された内容がフィールドと照合して検査されます。すべての値はそのフィールドが受け付けるものでなければならず、必須の値はすべて揃っていなければならず、スクリプトにないフィールドは黙って無視されるのではなくエラーになります。**値が合わせるために動かされることは決してありません。** 最大値が60のフィールドに入れた70分は、60に切り詰められずに拒否されます。数値に入れた `"12"` は、解釈されずに拒否されます。刻みが5のところの12.5は、丸められずに拒否されます。設備にコマンドを出す値は、誰かが入力したものそのままか、何も実行されないかのどちらかです。拒否された実行は実行の記録を残しません。何も開始されていないからです。

## 実行する

| 実行元 | 方法 | 必要な権限 |
|---|---|---|
| スクリプト画面 | カードの**実行**を押し、フォームに入力します | `scripts.run` |
| そのエンティティ | タイルの**実行**、またはフィールドをデータにした `POST /api/services/script/turn_on` | `scripts.run` |
| API | `{"fields": {...}, "reason": "..."}` を送る `POST /api/scripts/{id}/run` | `scripts.run` |
| ルール | `call_script` ステップ | ルール自身の権限 |
| エージェント | MCP 経由の `run_script` | MCP の書き込みがオン |

スクリプトはオペレーターが実行し、管理者が書きます。CIP サイクルを実行することがボタンの役目で、CIP サイクルがどのバルブを開くかを決めるのはエンジニアの判断であり、これからもそうです。

実行は開始するとすぐに、その id とともに応答します。`wait` を指定すると、終了時に結果とすべてのステップのトレースとともに応答します。**停止**(`POST /api/scripts/{id}/stop`、または `script.turn_off`)は、そのスクリプトのすべての実行を、すべてのプロセスで、待機や遅延も含めて、その場で取り消します。ステップがすでに書いた内容は書かれたままです。元に戻すことも書き込みであり、誰も頼んでいないのにすでに動いた設備に対して行うことになるので、その判断は私たちではなくオペレーターのものです。

## すべての書き込みはゲートを通ります

スクリプトは **`script:<id>`** として実行されます。スクリプトが行うすべての書き込み、すべてのサービス呼び出し、すべてのログ行は、これを実行主体として持ち、すべての書き込みは拒否されたかどうかにかかわらず `GET /api/writes` でこの主体に対して監査されます。**ソース**は開始した者です。画面からなら `ui`、ルールからなら `automation`、エージェントからなら `mcp` です。ゲートがソースで判断するため、これは重要です。エージェントが開始したスクリプトは `mcp` として書き込み、`HOTLOOP_ALLOW_WRITES` がオフならそのすべての書き込みが、エージェント自身の `write_tag` と全く同じように拒否されます。この場合、`run_script` とエージェントの `script.turn_on` は、書き込みがすべて跳ね返されるスクリプトを実行する代わりに、最初から拒否します。

実行は、誰が頼んだか(`actor`)、どのように(`source`)、何が呼び出したか(`parent`: `automation_run:812`、`script_run:77`)を記録するので、書き込みからルール、スクリプト、その背後にいる人やエージェントまでたどれます。

## 先に尋ねる:ドライラン

`POST /api/scripts/{id}/run?dry_run=true`、実行ドロワーの**先に確認**、または `dryRun` を指定した `run_script` です。フィールドは同じように検査され、その後、すべてのステップが現在の工場の状態に対して順にたどられます。

- すべての `write_tag` と `call_service` は、書き込みゲート自身の検査(`CheckWrite`、`Services.Check`)にかけられます。本物の書き込みが実行するのと同じコードなので、ドライランが確認しなかった理由で本物の書き込みなら拒否することを、ドライランが許可することはありません。何も書き込まれず、何も監査されません。
- `condition` はその場で評価され、偽なら実行が終わるはずの地点でたどりも終わります。
- `set_variable` はバインドされるので、その後のステップは本来見る値を見ます。
- `call_script` は呼び出すスクリプトをたどり、そのステップは呼び出しの下に番号が付きます(`3.1`、`3.2`)。
- `wait`、`delay`、そしてどの設備にも書き込まないもの(メッセージ、HTTP 呼び出し、発生させたアラーム)は `not_checked` です。ドライランは、その時にタンクが何を示すかを伝えるために15分待つことはしません。

拒否されるはずの最初の書き込みでたどりは終わります。それが実行を終わらせるからで、応答はゲートの言葉でそれを伝えます。`step 2 (call_service): cip/pump: this tag is not marked writable`。問題なく戻ってきたドライランは助言であって約束ではありません。デバイスが落ちることもあり、誰かがタグを解除することもあり、待機は、確認からステップまでの間に工場が気を変えるのに十分な時間を与えます。

## 実行モード

同じスクリプトの別の実行が進行中に求められた実行がどうなるかを決めます。ルールと同じ用語で、違いは1つだけです。

| モード | 2つ目の実行 |
|---|---|
| `skip` | 拒否され、`409` が返り、理由を示す `skipped` の実行が履歴に残ります。**既定値**で、設備にコマンドを出すものにはこれが正解です |
| `queue` | 順番を待ち、前の実行が終わったら開始します。待てるのは1つだけで、3つ目は拒否されます |
| `restart` | 進行中の実行をその場で取り消し、停止してから開始します。2つの実行が重なることはありません |
| `parallel` | 並行して実行されます |

違いは次のとおりです。ルールのキューは待機中の古い実行を黙って捨て、スクリプトのキューは新しい方をはっきり拒否します。ルールはお構いなしのトリガーによって起動されます。スクリプトは応答を待っているかもしれない人や何かから求められるので、「あなたの実行は黙って起こらなかった」は答えになりません。

ビジー状態のスクリプトを待つ `call_script` ステップは失敗します(`script busy`)。待たないステップはトレースにそれを記して先へ進みます。もともとやるはずだったのは開始することだけだからです。

`maxRuntimeSec` は1つの実行の上限で、0 のときは5分です。これを使い切った実行は、ステップの合間でも待機の途中でも `timed_out` になります。

## スクリプトがスクリプトを呼び出す

`call_script` ステップは、ルールまたは別のスクリプトからスクリプトを実行します。`wait` を使うと、ステップはスクリプトの結果を自分のものとして受け取り、スクリプトは呼び出した実行の一部になります。呼び出し側を取り消したり、時間切れにしたりすると、待っていたスクリプトも停止します。`wait` がなければ、スクリプトは開始され、自力で終わるに任されます。

制限は2つで、どちらもスクリプトがループすることを防ぐためのものです。

- **自分自身を呼び出すことになるスクリプトは、保存時に拒否されます。** 直接でも、ほかのスクリプトの連なりを経由しても同じです。`script b would call itself: b calls a calls b`。ループを閉じてしまう編集も同様です。
- **実行時は5階層までです。** 1つの連なりの6つ目のスクリプトは、それを呼び出すはずだったステップを失敗させ、連なりも一緒に失敗します。そして、ループが保存をすり抜けた場合(2つのプロセスが同じ瞬間にその半分ずつを保存した場合など)も、実行がそれを捕まえます。自分の連なりですでに実行中のスクリプトは、2回目は実行されず拒否されます。

## スクリプトのエンティティ

すべてのスクリプトはエンティティ `script.<id>`、プラットフォームは `script` です。状態は、どのプロセスでも実行が進行中なら `on`、なければ `off` です。属性には `mode`、進行中の実行の数(`current`)、`fields`、最後に開始した時刻とどう終わったかが入ります。エンティティ画面に**実行**ボタンつきで表示され、MCP の `list_entities` や `/api/states` にもあり、ルールはその状態トリガーを持てます。「CIP サイクルがオフになったら、バッチを記録する」。スクリプトを削除すると、アラーム定義を削除したときと同じように、そのエンティティは孤立します。何も参照しなくなったら、管理者がその孤立したものを削除します。

## 実行履歴

すべての実行は `script_runs` の1行です。誰が、どのように、検査を経て渡されたフィールド、すべてのステップのトレース(テンプレートではなく解決済みの入力)、どう終わったか、その理由が入ります。`GET /api/scripts/{id}/runs`、実行ドロワー、そして[ログブック](/ja/iot/logbook/)があり、ログブックではスクリプトの実行は種別が `script` で、スクリプトのエンティティや、実行が書き込んだ対象から見つけられます。履歴はスクリプトごとに最新の500件の実行を保持します。オートメーションの実行と同じ上限です。

実行の行は最初のステップの前に開かれ、最後のステップの後に完了します。プロセスが停止すると、進行中のすべての実行がその場で取り消され、`cancelled: interrupted by restart` として記録されます。クラッシュで中断され、行を完了させる者がいない実行は、Gateway の次の起動時に同じように記録されます。**実行を再開するものはありません。** CIP サイクルのステップ4から1時間後に、頼まれてもいないのに、状況が変わった工場に対して続きを行うことは、止まったと伝えることより悪いからです。

## プロセスが複数ある場合

Gateway と、その隣の `--mcp-stdio` プロセス(またはロールアウト中の2つのポッド)は、どちらもスクリプトを実行します。実行の状態はデータベースにあり、すべてのプロセスが `hotloop_script` の変更を待ち受けるので、次のようになります。

- 1つのプロセスで開始したスクリプトは、すべてのプロセスのエンティティで `on` と表示されます。
- 1つのポッドで保存したスクリプトは、もう一方のスクリプトにもなり、ステップが変わった場合はそこでの実行は取り消されます。
- **停止**は、そのスクリプトのすべての実行を、すべてのプロセスで止めます。

実行モードはプロセスごとに保持されます。2つのプロセスが、同じ瞬間に `skip` スクリプトの実行をそれぞれ1つずつ開始することがあります。エージェントの補助プロセスとオペレーターの画面から同じ秒に同じ手順を実行する工場は、こちらのどんなロックでも解決できない話し合いをする必要があります。

## バックアップ

`scripts` と `script_runs` はすべてのバックアップに含まれ、復元すると履歴とともに戻ります。バックアップが途中で捉えた実行は `running` として戻り、ほかの実行と同様、最初の起動時に `interrupted by restart` と記録されます。[バックアップと復元](/ja/iot/backup/)を参照してください。

## API

すべてのルート、その権限、応答は[HTTP API](/ja/iot/api/#scripts)にあります。

| 権限 | 閲覧者 | オペレーター | 管理者 |
|---|---|---|---|
| `scripts.read`:一覧と実行履歴の閲覧 | はい | はい | はい |
| `scripts.run`:実行、ドライラン、停止、`script.turn_on`/`turn_off` | いいえ | はい | はい |
| `scripts.write`:作成、編集、削除 | いいえ | いいえ | はい |
