HotLoop は工場ネットワークを待ち受け、そこに何があるかを教えます。庭の ESPHome ノード、コンプレッサーの Shelly、ライン 3 の OPC UA サーバー、誰かが接続して忘れた UPnP 機器、たった今アドレスを要求したものです。それぞれは Devices の Discovered に、MQTT で自分自身を通知したデバイス([MQTT ディスカバリー](/ja/iot/mqtt-discovery/))の下に、何であるか、HotLoop がどう通信できるかとともに表示されます。

その後は人が判断します。ネットワーク上で聞き取ったものが自動的に追加されることはなく、有効化されることも決してありません。

## スキャンせず、待ち受ける

読み取り対象の OT ネットワークではスキャンしません。ポートスイープは、想定していないパケットに応答した PLC を 1 台ならず停止させたことがあり、「ただのディスカバリー」という言い訳は午前 3 時には慰めになりません。そのため既定では、HotLoop は何も送信しません。

- **mDNS**(オン):デバイスは起動時にサービスを通知し、誰かの問い合わせに対するすべての応答はセグメント全体にマルチキャストされます。アプリを開くスマートフォンやプリンターを探すノートパソコンが問い合わせ、HotLoop はそれを傍受します。
- **SSDP**(オン):UPnP デバイスは参加時とその後数分ごとに `NOTIFY ssdp:alive` をマルチキャストします。HotLoop はこれも傍受します。
- **DHCP**(オフ、後述):ネットワークに参加するデバイスは、自身の MAC と通常は名前を添えて、アドレスを要求するブロードキャストを送ります。

問い合わせは**プローブ**であり、ボタンではなくデプロイによってネットワークごとにオンにします。

| 変数 | 既定値 | <span class="sr-only">Details</span> |
|---|---|---|
| `HOTLOOP_NETDISC_MDNS` | `true` | mDNS を待ち受ける |
| `HOTLOOP_NETDISC_SSDP` | `true` | SSDP を待ち受ける |
| `HOTLOOP_NETDISC_DHCP` | `false` | UDP 67 の DHCP 要求を待ち受ける |
| `HOTLOOP_NETDISC_PROBE_NETWORKS` | 空 | プローブを有効にするネットワークを CIDR で指定:`10.20.0.0/24,192.168.7.0/24` |
| `HOTLOOP_NETDISC_PROBE_INTERVAL` | `15m` | そこでプローブを実行する頻度 |

指定されたネットワークでは、プローブはすべてのサービスタイプと HotLoop が知っているタイプについて mDNS の問い合わせを送り、見つかった各タイプについて再度問い合わせ、SSDP の `M-SEARCH` を 1 回送り、各 UPnP デバイスの説明(名前、メーカー、モデル)をデバイスから読み取ります。それ以外のネットワークでは何も送信せず、何も指定されていない場所では Probe now ボタンは拒否されます。対象にしたいネットワークを指定してください。/8 は 1,600 万個のアドレスで、そうするよう指示すれば HotLoop はそこに問い合わせます。

## 通信できる相手

| 聞き取ったもの | 正体 | 受け入れると |
|---|---|---|
| mDNS `_opcua-tcp._tcp` | OPC UA サーバー(OPC 10000-12 附属書 C:エンドポイントは SRV のアドレスとポートに TXT の `path` を加えたもの) | そのエンドポイントに OPC UA デバイスを作成します。最初は匿名で保護なし、タグなしです。Discover tags で参照し、重要なものを扱う前にセキュリティを設定してください |
| mDNS `_shelly._tcp`、または `gen` 付きの `_http._tcp` | Shelly Gen2 以降(TXT の `gen`、`app`、`ver`) | Shelly 自身のステータス呼び出しである `http://<it>/rpc/Shelly.GetStatus` を読み取る HTTP デバイスを、読み取り専用、タグなしで作成します。Discover tags がすべての値を一覧します。ログインが有効な Shelly は digest 認証を要求しますが、HTTP ドライバーは対応していません |
| mDNS `_esphomelib._tcp` | ESPHome ノード(TXT:`friendly_name`、`version`、`mac`、`platform`、`board`、`network`) | 既知として記録し、何も作成しません。HotLoop は ESPHome を MQTT で読み取ります。ノードに HotLoop のブローカーを指す `mqtt:` ブロックを設定すれば自分自身を通知し、カードにもその旨が表示されます(MAC で照合) |
| mDNS `_mqtt._tcp` | MQTT ブローカー | 記録します。Settings、MQTT に追加すると、そこで通知されるものを聞き取れます |
| mDNS `_http._tcp`、その他すべて | Web ページ、または HotLoop が名前を知らないサービス | 記録します |
| SSDP | uuid で識別される UPnP デバイス:デバイスタイプ、`SERVER`、プローブがオンなら説明も | 記録します |
| DHCP | アドレスを要求するデバイス:MAC、ホスト名、ベンダークラス | 記録します |

「記録します」も、クリックする価値があります。工場ネットワークでは、すべての機器を誰かが把握しているべきで、受け入れられた発見は名前と時刻が付いた判断です。次に現れる未知のものは目立ちます。

カードは、2 つの発見が同じ機器であるときにそれを知らせます。ESPHome ノードの mDNS MAC とその MQTT 通知、同じアドレスの DHCP 要求と mDNS ホストなどです。

受け入れても何も有効化されません。受け入れで作成されたデバイスは、誰かが選ぶまでタグを持たず、そのすべてのポイントは、他のすべてと同じ書き込みゲートを通って、誰かがタグエディターで有効化するまで読み取り専用です。提案内のアドレスはデバイス自身の通知に由来し、受け入れダイアログがそれを表示するので、想定している機器かどうかを確認できます。

**Ignore** は発見を非表示にし、再び聞き取られても非表示のままにします。**Un-ignore** で元に戻します。

## すべて信頼できないものとして扱います

セグメントにパケットを置ける人は誰でも、何者であるとでも名乗れます。そのため次のとおりにしています。

- すべての文字列は切り詰められ、制御文字が取り除かれ、画面は HTML ではなくテキストとしてページに表示します。
- UPnP の説明は、通知が来たアドレスからのみ、プローブネットワーク上でのみ、リダイレクトを経由せず、64 KiB を超えない範囲でのみ読み取ります。`LOCATION` を PLC の Web ページや HotLoop 自身に向けた偽の `NOTIFY` では、何も取得されません。
- 各リスナーは 1 秒あたり 500 データグラムを受け付け、残りは破棄して数えます。
- レコードは 1,024 件の発見を保持します。それを超える新しいものは、誰かが一部を処理するまで破棄されて数えられ、画面にその旨が表示されます。
- 回線上の質問は誰かの質問であって通知ではありません。質問が含む既知の回答は質問者の思い込みであり、それをもとに何かを作ることはありません。

## 何かを聞き取るために HotLoop が置かれるべき場所

マルチキャストとブロードキャストは、ルーター、NAT、コンテナネットワークを越えません。HotLoop は自分がいるセグメントだけを聞き取り、それ以外は何も聞き取りません。

- **工場ネットワーク上の機器**(バイナリ、または `--network host` の Podman):すべてを聞き取ります。
- **Pod ネットワークの Kubernetes**:工場のものは何も聞き取りません。Discovered 画面に待ち受けているインターフェースが表示されるので、それで分かります。Pod に `hostNetwork: true` を指定するか、工場セグメント上の 2 つ目のインターフェース(macvlan を使う Multus)を与えれば、工場を聞き取ります。チャートはどちらも代わりには行いません。Pod をホストのネットワークに置くことはノードに関する判断であり、既定ではありません。

mDNS(5353)と SSDP(1900)は 1024 より上の通常のポートなので、特権は不要です。HotLoop は、ホスト上の avahi-daemon を含め、すでにそれらを使っているものと共有します。

## DHCP

正直に言って実現可能ですが、コンテナが既定では得られない 2 つのものが必要で、そのためオフになっています。

1. **工場のブロードキャスト。** DHCP 要求は 255.255.255.255 に送られるため、HotLoop はセグメント上にいる必要があります。上記と同様に、ホストネットワーク、またはそのセグメント上のインターフェースです。
2. **UDP ポート 67**。1024 未満です。HotLoop のイメージは uid 65532 で実行されます。バイナリに `CAP_NET_BIND_SERVICE` を与えるか(`setcap cap_net_bind_service=+ep /hotloop`)、ホストの `net.ipv4.ip_unprivileged_port_start` を 67 以下に設定してください。Kubernetes では、非 root コンテナの capabilities に `NET_BIND_SERVICE` を追加するだけでは有効にならず、ファイル capability か sysctl が有効にします。

raw ソケットや特権コンテナは一切不要です。ポート 67 の通常の UDP ソケットがブロードキャストを受け取ります。応答せず、アドレスを提供せず、1 バイトも送信しません。ポートを共有するため、同じホスト上で同じく共有する DHCP サーバーは動作し続けます。ポートを独占するサーバーがあると HotLoop のリスナーは失敗し、画面に理由が表示され、サーバーには何も触れません。

見えないものは、サーバーへユニキャストされる更新です。HotLoop はデバイスが参加したときに聞き取り、その後 1 時間ごとには聞き取りません。

## 複数のレプリカ

ネットワークディスカバリーのロックを保持するレプリカだけが待ち受けとプローブを行います。他のレプリカは 30 秒ごとに再試行し、保持者がいなくなれば 1 つが引き継ぎます。2 つがプローブすると、すべてのデバイスに 2 回問い合わせることになります。

## バックアップ

`net_finds` はすべてのバックアップに含まれます。聞き取った内容と、誰が何を受け入れたか、あるいは無視したかです。判断は、ネットワークが二度と教えてくれない部分です。

## テスト方法

ディスカバリーは、実際のネットワーク上で実際の通知元(ESPHome、Shelly、OPC UA ノード、UPnP メディアサーバー、DHCP クライアント)を相手に実行しており、2026-11-17 には実機でも実行しました。
