ルールは3つの要素でできています。何かが起こり、条件が成り立ち、アクションが実行されます。

ルールは設備を操作できるので、2つの性質は譲れません。

**条件は、ルールが発火するときではなく、保存するときにコンパイルされます。** 構文エラーは、作者がまだエディターを見ているうちに分かります。黙ったまま一度も動かないルールや、さらに悪いことに、すでに半分実行されたシーケンスの途中で午前3時にエラーを出すルールになることはありません。エディターは入力中に検証し、コンパイルできないルールは保存時に拒否されます。

**条件はサンドボックスで評価されます。** [expr-lang](https://expr-lang.org)にはI/Oがなく、ファイルシステムにもネットワークにも届かず、コンパイル時に型を検査し、必ず終了することが保証されています。最後の性質がいちばん重要です。条件は書き込みに至る経路で評価されるため、無限に回れる式言語は、書き込みロックを握るエンジンを固まらせかねません。

## トリガー

トリガーのどれか1つが発火すれば、ルールが実行されます。

| 種類 | 発火する場面 | 主なフィールド |
|---|---|---|
| `tag_change` | タグの値が変わったとき | `deviceId`, `tagName` |
| `threshold` | 値が限界値を**またいだ**とき | `deviceId`, `tagName`, `threshold`, `direction`, `hysteresis` |
| `state` | エンティティの状態が変わったとき、または一定時間その状態を保ったとき | `entityId`, `from`, `to`, `forSec` |
| `schedule` | cron式の時刻になったとき | `cron` |
| `interval` | N秒ごと | `intervalSec` |
| `alarm` | アラームがある状態に入ったとき | `alarmId`, `alarmState` |
| `device_state` | デバイスが接続したとき、または切断したとき | `deviceId`, `toState` |
| `webhook` | 受信POSTが届いたとき | `webhookPath` |
| `mqtt` | トピックにメッセージが届いたとき | `topic` |
| `startup` | プロセスが起動したとき | n/a |
| `sun` | 現場の夜明け、日の出、南中、日没、または薄暮。必要ならオフセット付き | `event`, `offsetSec` |

### しきい値は、またいだ瞬間に発火します

`threshold`は、値が限界値を*またいだ*ときに発火し、上にとどまっている間は発火しません。「値が200を超えている」で発火させると、値が高いままのスキャンごとにルールが発火します。何かを操作するルールでは、これはコマンドの嵐です。

`hysteresis`は、限界値付近で揺れる値が、揺れるたびにルールを再武装するのを防ぎます。いったん上に出た値は、トリガーが再び発火できるようになる前に`threshold - hysteresis`を下回る必要があります。

```json
{
  "type": "threshold",
  "deviceId": "press-01", "tagName": "Zone1_Temp",
  "threshold": 200, "direction": "rising", "hysteresis": 5
}
```

`direction`は`rising`、`falling`、`either`のいずれかです。起動後の最初の読み取りは基準を確立するだけで発火しません。そうしないと、値が何であれ、すべてのしきい値ルールが起動時に一度発火してしまいます。

### 状態トリガーはエンティティに従います

`state`は、エンティティの状態の文字列が変わったときに発火します。`off`から`on`、`212.5`から`213`、`on`から`unavailable`などです。`from`と`to`で絞り込みます。両方を省くと、`unavailable`への変化と、そこからの変化を含め、すべての変化で発火します。「誰かに知らせる」にはたいていそれで構いませんが、「何かを操作する」には決して向きません。`to`を指定してください。

```json
{
  "type": "state",
  "entityId": "binary_sensor.press_01_run",
  "from": "off", "to": "on"
}
```

発火するのは状態に対してだけで、ほかには発火しません。属性が変わること、あるいは状態が最後の正常な値を保ったまま品質が悪くなることは、状態の変化ではありません。

設備を操作するルールには知る価値があるので、いつ発火するかを正確に書きます。トリガーは、タグバスではなく、エンティティエンジン自身の変更の記録に従います。エンジンは読み取りが届くたびにエンティティの状態を計算し、間に合わなかった一団のための保険として、1秒に1回すべてを再計算します。計算した変化はそれぞれ順番に1回だけ報告され、トリガーはそのすべてを見ます。つまり次のとおりです。

- **変化ごとに1回発火します。** 1秒ごとの再計算は、エンジンが前回見てから動いたものだけを報告するので、同じ変化を2回報告することはなく、ルールを再読み込みしても、状態トリガーが依存するものは何もリセットされません。
- **エンジンが見た変化は逃しません。** バスが遅いと1秒の遅延が生じますが、変化は失われません。
- **誰も見ていない変化は見えません。** 2回のポーリングの間にoff、on、offと動いたコイルは、プラントにとっては一度も変化していません。状態トリガーは、その背後のスキャンと同じ精度で、それ以上ではありません。速い信号のすべてのエッジが必要なら、PLCでラッチしてください。
- **起動は基準です。** Gatewayの起動時、またはエンティティが有効化されたときに現れるエンティティは、変化ではなく、発火しません。

ルールが10,000件の変化ぶん遅れた場合(ルールが開始する実行をデータベースが記録しきれないほど遅い場合)、最も古いものから破棄され、数えられ、ログに残されます。`GET /api/diagnostics`は`automations`の下に`stateChangesPending`と`stateChangesDropped`を表示します。

エンティティの名前を変更すると、古い`entity_id`を指定しているすべてのルールが発火しなくなります。意味のある名前の代償です。名前の変更は意図して行い、先にルールを検索してください。

### 状態を保つ: forSec

「ポンプが5分間動いている」は、`forSec`を使った状態トリガーです。変化はルールを発火させる代わりにタイマーを始動し、変化後の状態がその秒数だけ保たれたときにルールが発火します。

```json
{
  "type": "state",
  "entityId": "binary_sensor.press_01_run",
  "from": "off", "to": "on",
  "forSec": 300
}
```

- **状態が変わると、保持は取り消されます。** 5分以内にonからoff、そしてonに戻ると、変化は2回です。1回目が保持を終わらせ、2回目が0から新しい保持を始めます。時間は加算されません。`unavailable`への移行も状態の変化なので、保持の途中で応答しなくなったデバイスは保持を取り消します。
- **状態だけが数えられます。** 属性が変わること、または状態が保たれたまま品質が悪くなることは、通常の状態トリガーを発火させないのと同様に、保持を取り消しません。保持が不良な読み取りを乗り越えてはならない場合は、ルールの条件を`qualities`で守ってください。
- **保持ごとに1回発火します。** 1時間保持しても、5分のルールは5分の時点で1回発火するだけで、5分ごとには発火しません。
- **ルールごとに専用のタイマーがあります。** トリガーごとに1つです。同じエンティティに対して`forSec`が異なる2つのルールは、それぞれの時刻に発火します。
- **トレースに出ます。** 保持が発火させた実行は`binary_sensor.press_01_run changed from off to on and held for 300s`と表示され、`fromState`、`toState`、`entity`は保持を始めた変化のものです。
- **保持は再起動を越えられません。** メモリに保持されていて、再武装するものはありません。再起動前にプレスが保っていた分の時間は、その後は何の意味も持ちません。プロセスが戻ってきたときに見るのは、すべてのエンティティが現れること(基準であり変化ではありません)、たいていは`unknown`で、その後デバイスの最初の読み取りが読み取った値に動かすことです。`"from": "off"`ではこれは一致しないため、再起動前に動いていたプレスは保持を始めず、ルールはプレスが次にoffからonになって5分動いたときに発火します。`from`がなければ、制御できない競合に左右されます。最初の読み取りがルールの待ち受け開始後に届くと、それは`unknown`から`on`への変化であり、0から保持を始めます。ルールはその5分後に発火し、トレースには`changed from unknown to on`と表示されます。デバイスがGatewayの立ち上がりより早く応答すると、プレスは最初から単に`on`で、何も変わらず、次に変わるまで何も発火しません。再起動を開始として数えたくないときは`from`を指定し、それを必要とするルールは書かないでください。ルールの編集、無効化、削除でもその保持は破棄されます。ほかのルールを保存しても破棄されません。
- **保持の途中で消えるエンティティ**(無効化された、またはデバイスとともに削除された)は、決して発火しません。

`forSec`は最大1日(86400)で、`state`トリガーだけが受け付けます。ほかのすべてと同様に、保存時に検査されます。

### 太陽トリガー

庭の照明、ヒートトレース、駐車場、外が暗いかどうかを気にするものすべてです。`sun`はこの現場の`dawn`、`sunrise`、`noon`、`sunset`、`dusk`に発火し、`offsetSec`だけずらせます。負の値は前なので、これは日没の30分前です。

```json
{"type": "sun", "event": "sunset", "offsetSec": -1800}
```

- **ボックスの中で計算されます。** 現場の緯度と経度(`HOTLOOP_SITE_LATITUDE`、`HOTLOOP_SITE_LONGITUDE`)から、NOAAの太陽方程式で計算します。サービスもインターネットも不要です。アップリンクを失ったプラントでも、夕暮れに照明が点きます。[太陽](/ja/iot/sun/)を参照してください。
- **位置がなければ武装しません。** 緯度と経度のない現場で太陽トリガーを使うルールは武装されず、システムログが設定すべき2つの変数を示します。以前は、武装されたまま永遠に黙っていて、庭が暗くなって初めて誰かが気づく、そういう類のものでした。
- **その日のイベントごとに1回発火します。** その日の時刻に発火します。10月の日没は毎晩1分ほど早くなり、トリガーはそれに追従します。
- **夜明けと薄暮は市民薄明です。** 太陽の中心が地平線の6度下です。屋外照明が基準にしている「照明が必要なほど暗い」線です。
- **白夜の下では発火すべき日没がありません。** そのため日没トリガーは、何週間先でも次の日没を待ち、そのときに発火します。
- `offsetSec`は前後それぞれ最大6時間(21600)です。それより遠いなら`schedule`です。

トレースには、何がいつ発火させたかが出ます。`30m before sunset at 2026-10-01T22:38:00Z`で、条件では`trigger`は`sun`です。

## 条件

真偽値を返す式です。空なら無条件です。

式から見えるもの:

| 名前 | 意味 |
|---|---|
| `value`, `string`, `quality` | ルールを発火させた読み取り |
| `previous` | その前の読み取り |
| `tag`, `device` | 発火させたもの |
| `tags["device/tag"]` | 現在のすべての数値の読み取り |
| `strings["device/tag"]` | 現在のすべての文字列の読み取り |
| `qualities["device/tag"]` | 現在のすべての品質 |
| `states["sensor.x"]` | 有効なすべてのエンティティの状態(文字列) |
| `attrs["sensor.x"]["unit_of_measurement"]` | 有効なすべてのエンティティの属性 |
| `qualities["sensor.x"]` | タグの品質と並ぶ、すべてのエンティティの品質(タグのキーには`/`があり、entity_idには決してありません) |
| `entity`, `fromState`, `toState` | ルールを発火させた状態変化 |
| `alarm`, `alarmState` | ルールを発火させたアラーム |
| `deviceState` | 発火させたデバイスの状態 |
| `now`, `hour`, `minute`, `weekday` | 時計。weekdayの0は日曜日 |
| `trigger` | どのトリガーが発火したか |
| `vars` | 前のステップが束縛した値 |

```
value > 200
value > 200 and quality == 'good'
tags['press-01/Zone1_Temp'] > 200 and tags['press-01/Pressure'] < 50
hour >= 6 and hour < 18 and weekday != 0 and weekday != 6
qualities['press-01/Zone1_Temp'] == 'good'
strings['cnc-01/Program'] == 'PART_4471.NC'
value > previous
states['switch.press_01_pump'] == 'off' and toState == 'on'
float(states['sensor.press_01_zone1_temp']) > 200 and qualities['sensor.press_01_zone1_temp'] == 'good'
attrs['switch.press_01_pump']['armed'] == true
```

**品質で守ってください。** `value > 200`は、250という不良の読み取りでも真になり、不良の読み取りとは、システムが「分からない」と伝えている値です。設備を操作するものには、`value > 200 and quality == 'good'`と書いてください。エンティティも同じです。不良のエンティティは最後の正常な値を表示し続け、ルールがそれを見分ける手段が`qualities['sensor.x']`です。

**状態は文字列です。** `"212.5"`、`"on"`、`"unavailable"`のようなもので、数値ではありません。そのため`states['sensor.x'] > 200`は、黙って常に偽になる比較として保存される代わりに、保存時に型エラーとして拒否されます。`float(states['sensor.x']) > 200`と書き、それを守ってください。`float('unavailable')`はエラーで、エラーになる条件は実行を失敗させます。

`string`はルールを発火させた読み取りなので、expr-langの`string()`関数でもあるわけではありません。数値を文字列に入れるには`toJSON(value)`を使います。

条件は真偽値を返さなければなりません。数値や文字列を返すものは、誰も意図しない真偽に変換される代わりに、保存時に拒否されます。

## アクション

アクションは順番に実行されます。失敗したステップは、`continueOnError`を設定していない限りルールを止めます。バルブを閉じるはずだったのに閉じなかったステップのあとに、バルブが閉じていることを前提にするステップが続いてはなりません。

### write_tag

```json
{
  "type": "write_tag",
  "params": {
    "deviceId": "press-01", "tagName": "Cooling",
    "value": true
  }
}
```

または計算式で:

```json
{
  "type": "write_tag",
  "params": {
    "deviceId": "press-01", "tagName": "Setpoint",
    "expression": "tags['press-01/Zone1_Temp'] - 10"
  }
}
```

**ほかのすべてと同じゲートを通ります。** オートメーションは人間以上の権限を得ません。書き込みが有効で、タグが書き込み可能とマークされ、値が範囲内にあり、その試行は`automation:<rule-id>`として監査されます。

### call_service

`POST /api/services/...`やMCPの`call_service`ツールと同じように、エンティティをそのサービスで操作します。各ドメインが受け付けるものは[エンティティ](/ja/iot/entities/#services)を参照してください。

```json
{
  "type": "call_service",
  "params": {
    "entityId": "switch.press_01_pump",
    "service": "switch.turn_on"
  }
}
```

データはリテラルでも計算式でも指定できます:

```json
{
  "type": "call_service",
  "params": {
    "entityId": "number.press_01_zone1_sp",
    "service": "number.set_value",
    "dataExpressions": {"value": "float(states['sensor.press_01_zone1_temp']) - 10"}
  }
}
```

`service`は`domain.service`で、そのドメインはエンティティのドメインでなければなりません。数値エンティティにスイッチのサービスを指定したルールは保存時に拒否されます。ドメインが受け付けないサービスも同様で、各ドメインが受け付けるものの一覧はエンティティ層自体から来ます。ドメインにそこでサービスが追加されれば、ここを変更せずにルールで使えます。`data`はリテラルのサービスデータで、`dataExpressions`は実行時に評価されてその上に統合されます。

名前の付いた`write_tag`です。呼び出しは同じゲートを通るタグ書き込みになり、すべての行にエンティティ、サービス、呼び出しIDが付いて`automation:<rule-id>`として監査されます。拒否(書き込みオフ、タグの武装解除、エンティティのステップから外れた値)はステップと実行を失敗させ、拒否された`write_tag`とまったく同じようにトレースに拒否の理由が残ります。呼び出しが行った、または拒否された書き込みはすべてステップの出力にあります。呼び出しがロールバックされることはありません。3つのうち2つの書き込みを済ませた複合呼び出しは、そこで止まり、そのことを伝えます。

### condition

シーケンスの途中にある条件です。偽のときはシーケンスがそこで終わり、実行は**成功**です。ルールは書かれたとおり、止まるという仕事をしたのです。ステップの出力には`false; the steps after this one did not run`と出ます。

```json
{
  "type": "condition",
  "params": {
    "expression": "states['binary_sensor.press_01_run'] == 'on' and qualities['binary_sensor.press_01_run'] == 'good'"
  }
}
```

これはルールの`condition`ではありません。それは何かが動く前に、トリガーが発火したときのプラントに対して1回検査され、偽なら実行はスキップとして記録されます。条件ステップは、**ステップが実行されるときの**プラントを読みます。これが`delay`や`wait`のあとに置く意味です。「30秒後もプレスは動いているか」。`entity`、`toState`、`value`、およびルールを発火させたもののそれ以外は元のままで、`vars`も同じです。

評価できない条件(`float('unavailable')`)は、ルールの条件と同じようにステップと実行を失敗させます。`continueOnError`は条件では保存時に拒否されます。条件を通り越して続けると、条件が何も止めないことになるからです。

### wait

式が真になるまでシーケンスを保留します。最長で`timeoutSec`です。

```json
{
  "type": "wait",
  "params": {
    "expression": "states['binary_sensor.press_01_valve_closed'] == 'on'",
    "timeoutSec": 30
  }
}
```

すぐに1回確認し、**式が指すエンティティが変わるたびに**(状態、品質、属性)再び確認し、どの場合でも1秒に1回確認します。監視するエンティティは、`states['...']`、`attrs['...']`、`qualities['...']`にリテラルで書かれたものです。タグの読み取り、時計、ほかの形で指定されたエンティティは、1秒ごとの確認で捉えられます。したがって、Modbusコイルへのwaitは、その背後のポーリングと同じ速さで、1秒遅れません。

真になると次のステップが実行され、その後のステップは、waitが最後に見たとおりのプラントを見ます。先にタイムアウトすると、ステップは**失敗**し、実行もそれとともに失敗して`still false after 30s`と表示されます。ただしwaitが続行を指定している場合は別です:

```json
{
  "type": "wait",
  "params": {
    "expression": "float(states['sensor.press_01_zone1_temp']) < 60",
    "timeoutSec": 240,
    "continueOnTimeout": true
  }
}
```

どちらの場合も、その後`vars.wait.completed`は真か偽になり、`vars.wait.waitedSec`は待った時間になるので、続行するwaitのあとの条件ステップは`vars.wait.completed == true`で判断できます。

`timeoutSec`は必須で、最大1時間です。終わりのないwaitは、実行の予算がそれを奪うまで実行スロットを占有し、`skip`ではルールがもう発火しなくなることを意味します。また実行の予算(`maxRuntimeSec`、既定は5分)にも収まる必要があります。10分のwaitにはルールに`"maxRuntimeSec": 900`程度が必要で、なければ実行としてタイムアウトする代わりに、ルールが保存時に拒否されます。待っている間にエラーになる式は、ステップを失敗させます。

### stop

シーケンスを終了します。`reason`は必須で、`{{ expression }}`の置換を受け付け、トレースに表示されます。

```json
{
  "type": "stop",
  "params": {"reason": "pump already running, nothing to do"}
}
```

`error`がなければ、実行は成功です。`"error": true`なら実行は失敗し、理由がそのエラーとなり、ほかの失敗と同様にログに記録され、数えられます:

```json
{
  "type": "stop",
  "params": {"reason": "valve did not close in time", "error": true}
}
```

`continueOnError`はstopでは保存時に拒否されます。

### call_script

[スクリプト](/ja/iot/scripts/)を実行します。CIPサイクルやラインのパージを必要とするすべてのルールが、それぞれのコピーを持つ代わりに同じものを呼べるように、誰かが一度書いた名前付きのシーケンスです。`fields`はその入力で、`fieldExpressions`はステップの実行時に評価されてその上に統合され、スクリプトは画面から実行したときとまったく同じように、全体を自分のフィールドに照らして検査します。スクリプトが拒否した値はこのステップを失敗させ、合わせるために値が動かされることはありません。

```json
{
  "type": "call_script",
  "params": {
    "scriptId": "cip_cycle",
    "fields": {"circuit": "tank_2"},
    "fieldExpressions": {"minutes": "states['input_number.cip_minutes']"},
    "wait": true
  }
}
```

`"wait": true`なら、ステップはスクリプトの実行が終わるまで待ち、その結果を引き継ぎます。失敗したスクリプトはステップを失敗させ、ステップに`continueOnError`がない限りルールはそこで止まります。スクリプトの実行はこの実行の一部です。この実行がキャンセルされるか予算を使い切ると、スクリプトもそうなります。`wait`がなければ、スクリプトは開始されてルールは先へ進み、スクリプトは自分で終わります。

スクリプトは`script:<id>`として実行され、行うすべての書き込みにこのルールのソース`automation`が付き、その実行には`automation_run:<id>`が親だと表示されます。ビジー状態で、そのモードが別の実行を拒否するスクリプトは、待っているステップを失敗させ(`script busy`)、待たないステップでは失敗ではなく記録として残ります。スクリプトがスクリプトを呼ぶのは最大5段までで、自分自身を呼ぶことになるスクリプトは保存時に拒否されます。

### apply_recipe

[レシピ](/ja/iot/recipes/)を適用します。製品グレードや段取り替えなど、一緒に出ていく設定値のまとまりです。`params`はそのパラメーターで、`paramExpressions`はステップの実行時に評価されてその上に統合されます。`version`は意図的に古いバージョンを適用し、省略すると現在のものです。

```json
{
  "type": "apply_recipe",
  "params": {
    "recipeId": "grade_a",
    "params": {"line_speed": 120},
    "paramExpressions": {"batch": "states['input_number.next_batch']"}
  }
}
```

レシピは、レシピ画面から行うのと同じことを行い、適用者はこのルールです。まず全体が検査され、どれか1つでも対象が拒否されるなら何も書き込まれず、ステップはすべての理由とともに失敗します。そのあと対象は1つの呼び出しIDのもとで順番に出ていき、`automation:<id>`としてソース`automation`が付き、最初に失敗したものが残りを止めてステップを失敗させ、すでに書き込まれたものは書き込まれたままです。ステップが成功するのは、すべての対象が書き込まれたときだけです。出ていったがデバイスから読み戻されなかった値は、実際に出ていったので失敗ではありませんが、トレースには`NOT confirmed by read-back`と出て、適用にも同じことが記録されます。適用の親はこの実行、`automation_run:<id>`です。

### その他

| アクション | 内容 |
|---|---|
| `mqtt_publish` | MQTTデバイスの既存の接続でパブリッシュします |
| `http_request` | エンドポイントを呼び出します。`bindTo`は本文を`vars`に保存します |
| `raise_alarm` / `clear_alarm` | エンジンが自分では見えないアラームを操作します |
| `log_event` | システムログに書き込みます |
| `set_variable` | 後のステップのために値を束縛します |
| `delay` | 一時停止します。最長1時間 |
| `mcp_call` | 設定されたMCPサーバーのツールを呼び出します |

`mqtt_publish`、`http_request`、`log_event`、`stop`は、その文字列で`{{ expression }}`の置換に対応します。

```json
{
  "type": "mcp_call",
  "params": {
    "server": "maintenance",
    "tool": "create_work_order",
    "args": {"priority": "high"},
    "argExpressions": {"note": "'Zone 1 reached ' + toJSON(value)"},
    "bindTo": "workOrder"
  }
}
```

## 実行モード

前の実行がまだ進行中のときにルールがトリガーされたら、何が起こるかです。

| モード | 動作 |
|---|---|
| `skip` | 新しいトリガーを破棄します。**既定**で、デバイスの近くでは正しい答えです |
| `queue` | あとで実行します。待機は最大1つです |
| `restart` | 現在の実行を破棄してやり直します |
| `parallel` | 両方を実行します |

`queue`は意図的に待機中の実行を1つに制限しています。追いつけないルールは、状態がすでに先へ進んだプラントに向けて一斉に発射されるコマンドの滞留を、そうでなければ積み上げてしまいます。

`minIntervalSec`はトリガーの頻度にかかわらず速度を制限し、チャタリングするタグがデバイスを使い潰すのを防ぐ保険です。UIやMCPからの手動実行は速度制限を回避します(誰かが意図したことなので)が、実行モードは回避しません(誰が始めても、同時に2つ実行されることは同じく危険なので)。

`maxRuntimeSec`は1回の実行全体を制限し、既定は5分です。これがなければ、到達できないエンドポイントでハングしたルールは実行スロットを永遠に占有し、`skip`ではもう二度と発火しないことになります。これを使い切った実行は、ステップの間にいたか`delay`や`wait`の途中にいたかにかかわらず、タイムアウトとして記録されます。

### wait、delay、実行モード

`wait`や`delay`の中にいる実行は進行中の実行であり、トリガーがそれに何をするかは実行モードが決めます:

| モード | 実行が待っている間のトリガー |
|---|---|
| `skip` | 破棄され、スキップとして記録されます。待っている実行は続きます。 |
| `queue` | 待っている実行が、どう終わったかにかかわらず終わったあとに実行されます。 |
| `restart` | 待っている実行をその場でキャンセルして、新しい実行を始めます。古い実行は**キャンセル**として記録され、`a newer trigger restarted the rule`となります。これが「人感センサー照明」のパターンです。トリガーのたびに終わりが後ろへずれます。 |
| `parallel` | 別の実行を始め、それは独自に待ちます。 |

実行は、waitやdelayの最中であってもその場でキャンセルされ、理由とともに**キャンセル**として記録されます。次の場合です:

- **ルールが武装解除または削除されたとき**: `the rule was disarmed or deleted`。キュー中の実行と`forSec`の保持も破棄されます。
- **ルールが編集されたとき**: `the rule was edited`。作者がたった今変えた条件を待っている実行は、何事もなかったかのようには続きません。編集されたルールはきれいな状態で始まります。*ほかの*ルールを保存しても何も触れません。変更のないすべてのルールの実行、保持、キュー中の実行、実行スロット、インターバルのタイマーは、そのまま続きます。
- **プロセスが停止するとき**: `the process is stopping`。シャットダウンはwaitの終了を待ちません。次の起動で実行を再開するものはなく、プロセスがキャンセルとして記録できなかった実行(クラッシュ、停電)は、次の起動でキャンセルとしてマークされます。

キャンセルされた、または予算を使い切ったステップは、`continueOnError`があっても実行を止めます。そのフラグは失敗したステップのためのもので、誰かが止めた実行のためのものではありません。ステップがすでに行ったことは行われたままです。キャンセル前に出ていった書き込みは取り消されず、トレースにあります。

## 実行履歴

すべての実行は、ステップごとのトレースとともに記録されます。**解決された**入力、出力、所要時間、エラーです。テンプレートではありません。ルールが午前3時に誤動作したとき、知る価値があるのは`wrote 212.5 to press-01/Setpoint`であり、`wrote {{expression}}`ではありません。

オートメーション画面で実行を展開すると、そのステップが見えます。プロセスが停止したときにまだ進行中だった実行は停止時にキャンセルされ、プロセスが記録できなかった実行(クラッシュ)は次の起動でキャンセルとしてマークされるので、先週の火曜日から実行中であるかのように見えることはありません。

## 実例

シフト中にゾーンが熱くなったら冷却を始めます。10分に1回まで、そして誰かに知らせます。

```json
{
  "id": "cool-zone-1",
  "name": "Cool zone 1 when hot",
  "enabled": true,
  "mode": "skip",
  "minIntervalSec": 600,
  "triggers": [{
    "type": "threshold",
    "deviceId": "press-01", "tagName": "Zone1_Temp",
    "threshold": 200, "direction": "rising", "hysteresis": 5
  }],
  "condition": "quality == 'good' and hour >= 6 and hour < 18",
  "actions": [
    {"type": "write_tag", "params": {
      "deviceId": "press-01", "tagName": "Cooling", "value": true}},
    {"type": "delay", "params": {"seconds": 30}},
    {"type": "log_event", "params": {
      "severity": "warning",
      "message": "Cooling started, zone 1 at {{ value }}"}}
  ]
}
```

守りを順に読んでください。連続ではなく、またいだ瞬間に発火します。ヒステリシスが、揺れたときの再武装を防ぎます。条件は、信頼できない読み取りに基づく動作を拒み、シフト中だけ実行されます。そしてレート制限のおかげで、ほかのすべてが間違っていても、プラントを10分に1回より多く操作することはできません。

エンティティでの同じ考え方です。プレスが動き始めたら排気ファンを始動します。ただし誰もファンを武装解除していない場合に限ります。

```json
{
  "id": "fan-with-press",
  "name": "Extraction fan follows the press",
  "enabled": true,
  "mode": "skip",
  "triggers": [{
    "type": "state",
    "entityId": "binary_sensor.press_01_run",
    "from": "off", "to": "on"
  }],
  "condition": "qualities['binary_sensor.press_01_run'] == 'good' and attrs['switch.press_01_fan']['armed'] == true",
  "actions": [
    {"type": "call_service", "params": {
      "entityId": "switch.press_01_fan", "service": "switch.turn_on"}},
    {"type": "log_event", "params": {
      "message": "{{ entity }} went {{ toState }}, fan started"}}
  ]
}
```

`from`と`to`のおかげで、再接続(`unavailable`から`on`)がファンをひとりでに始動することはありません。条件のおかげで、武装解除されたファンは、プレスが始動するたびに監査証跡に拒否された書き込みが残るのではなく、スキップされた実行になります。

そしてシーケンスのステップを使うもの。プレスが10分動いたら、冷却バルブがすでに開いていなければ開き、そのリミットスイッチを待ち、いつまでも入らなければ大きく失敗させます。

```json
{
  "id": "cool-after-warmup",
  "name": "Open cooling after ten minutes of running",
  "enabled": true,
  "mode": "restart",
  "maxRuntimeSec": 120,
  "triggers": [{
    "type": "state",
    "entityId": "binary_sensor.press_01_run",
    "from": "off", "to": "on",
    "forSec": 600
  }],
  "actions": [
    {"type": "condition", "params": {
      "expression": "states['valve.press_01_cooling'] != 'open'"}},
    {"type": "call_service", "params": {
      "entityId": "valve.press_01_cooling", "service": "valve.open"}},
    {"type": "wait", "params": {
      "expression": "states['valve.press_01_cooling'] == 'open'",
      "timeoutSec": 60, "continueOnTimeout": true}},
    {"type": "condition", "params": {
      "expression": "vars.wait.completed == false"}},
    {"type": "stop", "params": {
      "reason": "cooling valve did not open within 60s, it is {{ states['valve.press_01_cooling'] }}",
      "error": true}}
  ]
}
```

上から下へ読んでください。保持のおかげで、2分でトリップするプレスはバルブを開きません。`from`のおかげで、Gatewayの再起動はプレスの始動ではありません。最初の条件は、すでに開いているバルブを、何も操作しない成功した実行にします。waitはバルブのエンティティが変わった瞬間に目を覚まします。そして決して開かないとき、2つ目の条件は実行をstopまで進ませて失敗させ、理由にバルブの実際の状態が入り、システムログに警告が残ります。バルブが開くと、同じ条件が偽になり、実行はそこで成功して終わります。

## Webhook

`webhook`トリガーは`POST /api/webhook/<path>`を登録します。本文は`vars.body`として使えます。どのルールも要求していないパスは、黙って受け入れる代わりに404を返します。何もない所へ投稿するWebhookは、動いているWebhookとまったく同じに見えるからです。

2つのルールが同じパスを要求することはできません。2つ目は読み込み時に、両方を挙げるログ行とともに拒否されます。

## ルールが武装されないとき

有効になっているがコンパイルされなかったルールは、オートメーション画面に赤い点と説明付きの**NOT ARMED**として表示され、システムログにエラーが残ります。これはいちばん声を大きくする価値のある状態です。作者は動いていると信じています。

1つの不良ルールがほかを武装解除することはありません。再読み込みで失敗したルールは破棄され、ほかはすべて武装されます。
