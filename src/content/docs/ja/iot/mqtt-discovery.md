デバイスを HotLoop のブローカーに向けると、そのデバイスが現れます。センサーは値を読み取り、スイッチは状態を表示し、エンティティにはデバイスが通知した名前、単位、クラスが付きます。タグの一覧を手で入力する人はいません。

そして、デバイスは何もコマンドできません。ディスカバリーが作るすべてのポイントは読み取り専用で、admin がデバイスを受け入れ、コマンドの送り先となる正確なトピックを確認しながら各ポイントを手動で有効にするまで、そのままです。自分を通知するデバイスは、自分が何者かを伝えるデバイスです。それは役に立ちます。しかし、工場のリレーを切り替える権利を得たわけではなく、HotLoop もそうであるかのように扱いません。

## 何が対応しているか

この形式は、`homeassistant/sensor/kitchen/power/config` のようなトピックを使うものです。これを定義したプロジェクトの名前が付いています。HotLoop がこれを扱うのは、パブリッシャーがそうしているからで、関係はそれがすべてです。

| パブリッシャー | ここへの届き方 | 何に対してテストしているか |
|---|---|---|
| **ESPHome**(`mqtt:` コンポーネント) | コンポーネントごと、既定で有効、retained | 実際のノードの録画出力(後述) |
| **Zigbee2MQTT** | コンポーネントごと、ほぼすべてにテンプレート | 実際のインストールの録画出力 |
| **Tasmota** | 独自形式、後述 | 実機 9 台の録画出力 |
| **Shelly**(Gen2、Gen3、Gen4) | 通知はなし。公開するステータスから学習、後述 | 実際のメッセージ 15 セットの録画出力と製造元のドキュメント |
| この形式を公開するその他すべて | 同じ | 形式自体の規則 |

ESPHome は、Zigbee2MQTT と同じく、実際のノードの録画に照らして検証されています。

録画は、実際のインストールが公開したメッセージを運用者が取得したもので、パブリッシャー、バージョン、デバイスが記録され、JSON の空白以外は何も変更されていません。

## Tasmota

現在の Tasmota は `homeassistant/` 形式を公開しません。ドキュメントには、すべてのビルドから削除されたと書かれています。代わりに retained で公開するのは独自の形式です。

- `tasmota/discovery/<MAC>/config`: デバイス(そのトピック、フルトピックのパターン、リレーとライト、オンとオフの語、last will の語)
- `tasmota/discovery/<MAC>/sensors`: その時点でセンサーが読み取っている値

どちらも Tasmota の `xdrv_12_discovery.ino` にある `TasDiscovery` が書き込みます(arendst/Tasmota の `development` 5c295fb、2026-10-12 時点で確認)。HotLoop はこの 2 つを他のパブリッシャーと同じコンポーネントに変換するため、その後のすべて(検出済み画面、受け入れ、有効化、書き込みゲート、読み取り)は 1 つのコードパスです。MAC がデバイスの識別情報です。`homeassistant/` 形式でも自分を通知するデバイス(SetOption19 のある古いファームウェア)は同じデバイスです。

| Tasmota の通知 | HotLoop が作るもの |
|---|---|
| リレー(`rl` 1) | スイッチ: `stat/<topic>/POWER` を読み取り(複数あれば `POWER1`、`POWER2` など)、デバイス固有のオンとオフの語を使います。`cmnd/<topic>/POWER[n]` に ON または OFF でコマンドします |
| ライト(`rl` 2) | ライト: オンとオフは同じ方法です。ディマーが 1 つなら、レベルは `tele/<topic>/STATE` の `Dimmer` キーで 0 から 100 まで、`cmnd/<topic>/Dimmer` で設定します |
| センサーメッセージ内のすべての数値 | それぞれ 1 つのセンサー。パス(`ENERGY` `Power`、`SCD40` `CarbonDioxide`)で `tele/<topic>/SENSOR` から読み取り、Tasmota がその名前に与える単位とクラスを使います。三相メーターの配列は相ごとに 1 つのセンサーになります |
| last will | 可用性: `tele/<topic>/LWT`、デバイス固有の Online と Offline の語 |

トピックは Tasmota が作るとおりに組み立てられます。フルトピックの `%prefix%` と `%topic%` を埋めるため、所有者がフルトピックを変更したデバイス(`tasmota/35D7A0/%prefix%/` や `bi/test/%topic%/%prefix%`)でも、実際に使っているトピックで読み取りとコマンドを行います。

読み取れないものは、黙らずにソースの問題として伝えます。シャッター、スイッチ入力、ボタン、iFan、カメラ、カラーライトの色、ライトが複数あるデバイスの明るさです。録画のどこにもこれらが動作する証拠がないため、ここでは読み取れるとは主張しません。

**問い合わせ。** Tasmota はリレーが変化したときにそれを報告し、すべてを 5 分ごとに報告します。そのため、デバイスの読み取りを始めるとき、HotLoop は `cmnd/<topic>/POWER` に空のメッセージを 1 つ送ります。Tasmota は何も動かさずにすべてのリレーの状態で応答します。これがなければ、変化していないデバイスは HotLoop の起動後最大 5 分間、不明と読み取られます。メッセージは空で、`POWER` で終わるトピック以外には送られず、受信専用のソースは何も送りません。

**ライトの明るさ**は、Tasmota のテレメトリ(デバイスの `TelePeriod` がそれより短くなければ 5 分ごと)で届き、変化した瞬間には届きません。オンとオフはすぐに届きます。

**各ブローカーで**、この形式はスイッチです(ブローカーの `tasmota`、設定、MQTT)。今追加したブローカーでは有効で、内蔵ブローカーでは常に有効です。すでにあったブローカーは以前とまったく同じように受信するため、誰かが有効にするまで無効です。無効とは、HotLoop がそこで `tasmota/discovery/#` を購読すらしないという意味です。

設定は、他のものと同じく信頼できません。名乗っている MAC ではない MAC で公開されたもの、`%topic%` がない、またはワイルドカードを含むフルトピック、スラッシュを含むトピック、引用符を含むオンの語、知らないバージョンは、それぞれ理由とともに拒否され、何も作られません。引用符を含むセンサー名がテンプレートに到達することはありません。

**何に対してテストしたか。** Tasmota 自身のコンソールから取得した、9 台のデバイスの実際のメッセージです。

## Shelly

Shelly の Gen2、Gen3、Gen4 は何も通知しません。待つべき設定トピックはありません。MQTT が有効でステータス通知が有効になると、変化するたびに各コンポーネントの完全なステータスを `<prefix>/status/<component>`(`switch:0`、`cover:0`、`light:0`、`input:0`、仮想の `boolean:200`)に公開し、last will を `<prefix>/online` に公開します。そのため HotLoop は、デバイスが発信する内容からデバイスを把握します。公開したコンポーネント、それぞれが運んだフィールド、そして `sys` ステータスの MAC です。プレフィックスは既定ではデバイスの id(`shellyplus2pm-485519968144`)で、これはモデルと MAC なので、既定のプレフィックスのデバイスは `sys` を待つ必要すらありません。誰かが入力したプレフィックス(`ShellyLichtGarten`)のデバイスは、他のデバイスと区別できるようになる前に `sys` を公開する必要があり、それまではソースの問題に名前が挙がり、作られません。

学習した内容はプレフィックスごとに保持され、増える一方です。静かになったコンポーネントは削除されたわけではなく、前回より内容が少ないステータスも何も取り除かないため、再起動してもデバイスが部品を失うことはありません。その後は他のすべてのパブリッシャーと同じ経路です。検出済み画面、受け入れ、各ポイントの有効化、書き込みゲート、読み取りです。

| Shelly の通知 | HotLoop が作るもの |
|---|---|
| `output` のある `switch:n` | スイッチ: `<prefix>/status/switch:n` から `output` を読み取り、`<prefix>/command/switch:n` に `on` または `off` でコマンドします |
| `light:n` | 同様のライト。`set,true` と `set,false` を使い、ステータスに `brightness` があれば 0 から 100 のレベルを `set,true,<level>` で送ります |
| `cover:n` | カバー: `state`(open、closed、opening、closing、stopped)を読み取り、`open`、`close`、`stop` を送ります。`pos_control` を通知するカバーはキャリブレーション済みなので、`current_pos` も読み取り、`pos,<n>` が送られます。そうでないカバーは開閉のみです |
| switch、light、cover の `apower`、`voltage`、`current`、`freq`、`pf`、`aenergy.total`、`temperature.tC` | それぞれ 1 つのセンサー。W、V、A、Hz、Wh、摂氏で、Shelly のドキュメントが定めるクラスを持ちます |
| `input:n` | その `state` のバイナリセンサー |
| `devicepower:n`、`voltmeter:n`、`illuminance:n`、`presencezone:n` | バッテリー、外部電源、電圧、照度、在室、オブジェクト数のセンサーとバイナリセンサー |
| `boolean:n`、`number:n`、`enum:n`(仮想コンポーネント) | 読み取り専用のセンサー。仮想コンポーネントの設定は RPC 呼び出しで、これは行わず、それぞれがソースの問題に示されます |
| `online` の last will | 可用性。Shelly 固有の `true` と `false` |

コマンドは、製造元の MQTT ページが MQTT Control の下に挙げているもので、テストは HotLoop がそのリストに従うことを確認します。スイッチは `on`、`off`、`toggle`、ライトは `set,<bool>,<brightness>`、カバーは `open`、`close`、`stop`、`pos,<n>` です。どれも、人が有効にしたゲートを通る書き込みです。

**問い合わせ。** Shelly はコンポーネントが変化したときに公開するため、変化していないデバイスは変化するまで不明と読み取られてしまいます。デバイスの読み取りを始めるとき、HotLoop は `<prefix>/command` に `status_update` を送ります。同じページによれば、これでデバイスはコンポーネントのステータスを公開し、何も動かしません。送るのはその 1 語だけで、`/command` で終わるトピック以外には送られず、受信専用のソースは何も送りません。デバイスの読み取りが始まるたびに行われるため、複数のポイントを続けて有効にすると、何度も問い合わせます。

**デバイス側で有効にしておくこと。** ブローカーのアドレスを指定した MQTT の有効化、ステータス通知の有効化(`status_ntf`)、そしてコマンドのための制御の有効化(`enable_control`)です。HotLoop 自身のブローカーには、デバイスのプレフィックスにちなんだ名前の `shelly` ログインプロファイルがあり、ステータスの公開と `<prefix>/command` の受信だけを許可し、それ以外は許可しません。

**読み取れないもの。** 黙らずにソースの問題として伝えます。見せられたことのない種類のコンポーネント(LoRa アドオン付き Gen4 の `lora:100`、`pm1`、`em`)、読み取り元のフィールドを省いた switch や cover、仮想コンポーネントの設定です。入力イベント(ダブルプッシュ、長押し)は RPC 通知トピック `<prefix>/events/rpc` に届き、読み取られません。読み取るのは入力の `state` だけです。2 階層を超えるプレフィックス(`home/garage/boiler`)は受信されず、1 階層か 2 階層は受信されます。RPC では何も送りません。

**各ブローカーで**これはスイッチです(ブローカーの `shelly`、設定、MQTT)。今追加したブローカーでは有効で、内蔵ブローカーでは常に有効です。すでにあったブローカーは以前とまったく同じように受信するため、誰かが有効にするまで無効です。スイッチなのは、受信するトピック `+/status/+` が広く、`*/status/*` の下で別のものを運ぶブローカーは無効にしたいからです。無効とは、HotLoop がそこでそれらを購読しないという意味です。

他のトピックと同じく信頼できません。英字、数字、`_.-` 以外を含むプレフィックス、`kind:number` ではないコンポーネント、オブジェクトでない、または 64 KiB を超えるペイロード、64 個を超えるコンポーネントを通知するデバイス、同時に学習される 512 台を超えるデバイスは、それぞれ無視されます。また、あるプレフィックスの下に保持された構造が別のプレフィックスだと名乗る場合は拒否されます。

## 何かが通知してきたときに起こること

1. **現れます。** 内蔵ブローカーでは、自分を通知したデバイスはすぐに HotLoop のデバイスになります。プロトコルは `mqtt`、ツリーには配置されず、自称した名前(`kitchen-plug`、衝突時は `-2`)で、読み取り中です。タグは通知した名前(`power`、`relay`)になります。エンティティには、設定が与えた名前、デバイスクラス、状態クラス、単位、カテゴリ、アイコンが付き、設定で既定が無効とされたエンティティは無効の状態で始まります。
2. **何も有効になっていません。** すべてのタグは読み取り専用で作られます。スイッチ、数値、テキストには制御エンティティがすぐに付きますが、有効化されていない状態(`armed: false`)なので、画面やオートメーションは初日から `switch.kitchen_plug_relay` という名前を指定できます。人がポイントを有効にした瞬間から動作し、それより前には動作しません。
3. **admin が決めます。** デバイス、検出済み。誰が通知したか(内蔵ブローカーでは、設定を公開したログインとクライアント id)、作られるすべてのコンポーネント、読み取るすべてのトピック、すべてのコマンドトピックの全体、そして確認すべき点です。

   - コンポーネントが読み取るトピックの外にあるコマンドトピック(コマンドが `cmnd/boiler/POWER` に向かう「ランプ」)
   - ディスカバリープレフィックスの内側にあるコマンドトピック、または別のデバイスも使用を主張しているコマンドトピック
   - retained コマンドを求める設定。retained コマンドはデバイスが再接続するたびに再送されるためです
   - HotLoop が評価できないテンプレート、形式が定義していない設定キー

   **受け入れ**ると、読み取りを続け、そのポイントをタグエディターで 1 つずつ有効にできるようになります。何も有効にはしません。デバイスがエリアを提案し、ツリーのノードにちょうどその名前があれば、受け入れダイアログが事前入力します。パブリッシャーが自分でボイラー室の下に分類することはできず、人が受け入れをクリックします。**無視**すると、デバイス、タグ、エンティティが破棄され(履歴はどのデバイスとも同様に残ります)、再び通知しても破棄されたままです。検出されたデバイスの削除は無視と同じです。通知し続けるデバイスは、また戻ってくるだけだからです。

## 通知内容が変わったとき

**別のログインは、何を名乗っても確認のために保留されます。** 内蔵ブローカーでは、デバイスは受け入れられたログインを記憶します。同じデバイスが別のログインから通知されると、設定がまったく同一でも 2 つのログインを並べて確認のために保留され、ログに警告が残ります。誰かがデバイスを新しいログインに移したか、ログインが自分のものでないデバイスを通知しているかのどちらかです。適用すると、新しいログインが受け入れ元になります。拒否すると、同じものを通知するそのログインは拒否されたままです。

**受け入れ済みのデバイスの設定が変わると、確認のために保留されます。** 受け入れた設定は動き続けます。検出済み画面は変更をフィールドごとに、実行中と通知されたものを比べて示し、admin が適用または拒否します。単位が °C から °F に変わったり、状態トピックが別の場所を指したりするのは、まさに間違った数値が信頼の顔を手に入れる方法です。変更を適用しても、ポイントが有効かどうかは決して変わりません。それは人の判断であり、これからもそうです。

ファームウェアの更新、新しいデバイス名、新しいモデル、別のアイコンは自動的に適用されます。バージョンが上がっただけで誰かがクリックする必要はありません。

誰かがデバイスを受け入れる前は、常に最新の通知が適用されます。まだ誰もその上に何も構築していないからです。

**空の設定はコンポーネントを撤回します。** そのポイントは「14:02 にパブリッシャーが撤回」という理由とともに不良として読み取られ、何も削除されません。そのポイントのアラームは対象を保ち、不良の理由を伝えます。同じコンポーネントが戻ると復元され、新しい値を送るまでは、離れる前の値を現在のものとして見せるのではなく、「撤回後に再通知、次の値を待機中」と読み取られます。誰も受け入れていないデバイスがすべてのコンポーネントを撤回すると消えます。誰もその上に何も構築していないからです。

**Zigbee2MQTT がデバイスの名前を変更すると**、古い設定トピックが消去され、同じ一意 ID で新しいものが通知されます。HotLoop は一意 ID でコンポーネントを識別するため、これは 1 秒違いの撤回と復元であり、何も失われません。

## 読み取り

状態は、コンポーネントに値テンプレートがあればそれを通り、次にコンポーネント自身の照合を通ります。バイナリセンサーは `payload_on`/`payload_off`(既定は `ON`/`OFF`)、スイッチは `state_on`/`state_off`、数値は数値、select は選択肢の 1 つです。**合わないものはすべて、理由付きの不良読み取りになり**、タイルに表示されます。

- `"CLOSE" is neither payload_on "CLOSED" nor payload_off "OPEN"`
- `value_json has no key 'temperature'`
- `"unavailable" is not a number`
- `the publisher sent no value`(`None`、`null`、空、または `unknown` を送った場合)
- `no update for 300 s (expire_after)`

最初のものは実例です。Zigbee2MQTT 1.41.0 は Avatto TRV07 の窓センサーをこのように通知し、それを取得した人は窓がまったく表示されないため issue を開きました。HotLoop は推測せずに不良として表示し、理由を伝えます。

**可用性**は読み取りではなく、デバイスの接続状態です。デバイスが可用性トピックでオフラインだと言っている間は、自身の言葉(「the device says it is offline (plug/status = offline)」)で切断と表示され、エンティティは利用できません。最初の可用性メッセージが届くまで、可用性が設定されたデバイスは利用できません。これが形式の規則であり、正しい規則です。そのためにブローカーのセッションを切断することはありません。そのブローカー上の他のすべてのデバイスと共有しているセッションだからです。

`expire_after` は、その秒数の間更新がなければ値を不良にします。`off_delay` は、設定がデバイスはオフを決して送らないと言っているため、その秒数後にバイナリセンサーをオフにします。JSON 属性は最大 64 キー、8 KiB までエンティティに入り、HotLoop 自身の属性(`friendly_name`、`source`、`armed` など)の下に置かれます(HotLoop 側が常に優先されます)。

状態トピックのないコンポーネントは、永遠に不良として読み取られます。HotLoop はコマンドから状態を推定することは決してありません。

## コマンド

次の 3 つがこの順序で成り立つまで、何もコマンドされません。

1. **人がデバイスを受け入れました。** それまでは、タグエディターはそのデバイスのポイントを有効にせず(「accept the device first」)、書き込みゲートも自らそのコマンドを拒否するため、手で編集した行や、ポイントが有効なままの古いバックアップでもどこにも到達しません。
2. **人がポイントを有効にしました。** タグエディターで、1 つずつ行います。チェックボックスの前で、エディターはコマンドの送り先と内容を示します。「Commands go to `plug/relay/set`, sending ON or OFF.」
3. **書き込みゲートがコマンドを通します。** 他のすべての書き込みと同じです。書き込みの有効化、エージェント向けの MCP スイッチ、タグの範囲、エンティティ自身の検査、有効なセッションです。拒否されたかどうかにかかわらず、呼び出し id とともに監査されます。ドライランもまったく同じ問いを行います。

送出されるのは設定が述べるとおりのものです。スイッチは `payload_on` と `payload_off`、ボタンは `payload_press`、select は選択肢、数値やテキストは値(整数は整数のまま、`5.0` ではなく `5`)で、設定にコマンドテンプレートがあればそれを通します。ボタンは 1 回押されます。その「離す」はデバイスが求めていない 2 つ目のコマンドになるため、検出されたボタンは単発です。

ライトは `payload_on`/`payload_off`(JSON スキーマのライトでは `{"state":"ON"}`)を受け取り、明るさのコマンドトピックには、自身の `brightness_scale` に合わせて換算し丸めたパーセントの明るさを受け取ります(JSON スキーマのライトでは `{"state":"ON", "brightness":128}`)。カバーは `payload_open`、`payload_close`、`payload_stop` を受け取り、位置は `set_position_template` を通して、パーセントから自身の `position_closed`..`position_open` に換算されて送られます。バルブは開閉のペイロード(位置を報告するバルブでは `position_open` と `position_closed`)を受け取り、コマンドトピックに位置を受け取り、`payload_stop` は 1 回です。ボタンと同じく、検出されたバルブの停止は単発です。設定が `null` で無効にしたペイロード(停止のないカバー)は、ゲートが理由付きで拒否するコマンドです。

ゲートは次の場合に、理由付きでコマンドを拒否します。

- 誰もデバイスを受け入れていない。
- デバイスが属するブローカーが受信専用である。
- パブリッシャーがコンポーネントを撤回した。
- コマンドテンプレートが対応範囲の外にある(「command template not supported: filter `regex_replace` is not supported at column 12」)。「生の値を代わりに送る」は決してありません。
- 設定にコマンドトピックがない。
- 設定に、求められた動作のペイロードがない。設定が `payload_stop: null` のカバーへの停止、select にない選択肢、100% を超える明るさです。ペイロードは検査の中で生成されるため、ドライランも拒否します。

**retained コマンドは設定に従います。** 設定が `retain: true` を求めると、HotLoop はそのコンポーネントのコマンドを retained で公開し、人がそれについて判断するあらゆる場所でそう伝えます。検出済み画面が印を付け、タグエディターが平易な言葉で説明します。有効にする前に、その意味を理解してください。ブローカーは最後のコマンドを保持し、デバイスが再接続するたびに、午前 3 時でも、誰も何も触っていないのに渡します。コマンドはやはりゲートを通っており、名前付きで監査証跡に残っています。ただ、もう一度起こるのです。

「これをあのトピックに公開する」という機能はどこにもありません。オートメーションにも、スクリプトにも、MCP にもありません。それは名前だけ立派にした、ゲートを迂回する脇のドアになってしまいます。コードでは、ディスカバリーで公開を行うものは 2 つです。ゲートだけが到達できるドライバーの書き込みと、birth です。ガードテストがドライバーパッケージを型検査し、他の何かがどちらかを呼び出すとビルドを失敗させます。仕込んだバイパスで、それが実際に機能することを証明しています。

## テンプレート

Python も Jinja エンジンもありません。ループがないため、テンプレートのコストはその長さのとおりです。

`{% set name = value %}` は含まれますが、その形だけです。Zigbee2MQTT はすべてのサーモスタットのモードを `{% set values = {'manual':'heat', ...} %}` と書いてから参照しており、モードが読み取れないサーモスタットは信頼できないサーモスタットだからです。名前空間、アンパック、ブロック形式はありません。`.keys()` も含まれますが `in` の右辺としてだけで、それらのテンプレートが使うのはその場所だけだからです。

| <span class="sr-only">詳細</span> | <span class="sr-only">詳細</span> |
|---|---|
| 構造 | テキスト、`{{ expr }}`、`{% if %}` / `{% elif %}` / `{% else %}`、`{% set name = value %}`、`{# comments #}`、`-` による空白制御 |
| 変数 | 値テンプレート: `value`、`value_json`(ペイロードが JSON のときのみ)、`entity_id`、`name`。コマンドテンプレート: `value`、`entity_id`、`name` |
| 式 | リテラル、`.attr`、`['key']`、`[0]`、スライス、`+ - * / // % **`、`~`、比較、`and or not`、`in`、`x if c else y`、マッピングの `.get(key, default)`、`in mapping.keys()` |
| テスト | `defined`、`undefined`、`none`、`number`、`integer`、`float`、`boolean`、`string`、`mapping`、`sequence`、`true`、`false`、`eq`、`ne`、`lt`、`le`、`gt`、`ge`、`in`、`odd`、`even`、`divisibleby` |
| フィルター | `float`、`int`、`round`、`bool`、`default`/`d`、`string`、`lower`、`upper`、`capitalize`、`title`、`trim`、`replace`、`truncate`、`abs`、`length`/`count`、`min`、`max`、`tojson`、`to_json`、`from_json`、`is_defined`、`iif` |
| 関数 | `float()`、`int()`、`bool()`、`iif()`、`min()`、`max()` |

形式がフィルターを標準の Jinja と異なる形で文書化している場合、HotLoop は形式に従います。重要なのはこれです。**既定値のない `float` と `int` は失敗します**、数値でないものに対しては。標準の Jinja は黙って `0` を返しますが、センサーが応答を止めたときのその 0 は、タンクが空だと伝えてしまう 0 です。

値は Python の `str()` が表現する方法で表現されます。すべてのパブリッシャーの設定がそれに合わせて書かれているからです。`True`、`None`、`21.0` は `21.0` のままです。これは見た目の問題ではありません。Zigbee2MQTT の接点センサーは `payload_on: false` を通知し、表現された `False` に一致します。

**欠けているキーは、処理していなければエラーです。** キーのないペイロードに対する `{{ value_json.temperature }}` は、空文字列ではなく、そう伝える不良読み取りです。`default`、`is defined`、単独の `{% if value_json.x %}` は意図的にそれを処理するため問題ありません。

**対応範囲外は、設定が届いたときに拒否され**、場所も示されます。「value template not supported: filter `regex_findall_index` is not supported at column 12」。コンポーネントは存在が分かるようにそれでも作られ、その理由で不良として読み取られます。ベストエフォートの部分的なレンダリングも、「生のペイロードを代わりに使う」もありません。実際のテンプレート 2 つは意図的に拒否されます。`now()`(HotLoop がいつ評価したかに依存する値は、デバイスの読み取りではありません)と、名前空間と `regex_findall` で正規表現パターンを組み立てる Zigbee2MQTT のイベントテンプレートです。

上限: テンプレート 4 KiB、ネスト 32 階層、出力 64 KiB、64 ビット整数(オーバーフローはラップではなくエラー)。

形式固有のフィルターは標準の Jinja ではないため、それぞれが求める文書化された動作を引用した手書きのテストケースがあります。録画内のすべてのテンプレートが解析できなければなりません。

ライト、カバー、バルブ、イベント、トリガー、そしてその後の行のすべてのコンポーネントでは、タグ自身の読み取りエンティティは非表示で作られ、画面では 1 つのエンティティとして見えます。各タグは引き続き個別に有効化されるため、位置は信頼できるが開閉は信頼しないカバーも、そのとおりに構成できます。受け入れの後で値を得たもの(明るさを報告し始めたファームウェア)は確認対象の変更であり、人が適用すると、エンティティはタグとともにそのロールを受け取ります。

JSON スキーマのライトの状態メッセージは、スキーマが変化したものだけを送るため、まとめて扱われます。明るさだけのメッセージや Zigbee2MQTT の `last_seen` だけのメッセージでは、ライトはオンのままです。色、色温度、エフェクトは属性として表示され、コマンドされません。オン、オフ、明るさはコマンドされ、検出済み画面は色のあるライトについてそう伝えます。既定スキーマのライトの色トピックも同様で、読み取られず、コマンドされず、一覧に載ります。テンプレートスキーマは未対応で、そう伝えます。カバーのチルトは読み取りもコマンドもされず、そう伝えます。

デバイストリガーは自身の `payload` でのみ発火します。Zigbee2MQTT はボタンのすべての動作を 1 つのトピックに載せ、各トリガーはその 1 つです。`payload` のないトリガーは、そのトピック上のあらゆるものに発火します。

ファンの速度は、形式と同じく設定自身の `speed_range_min`..`speed_range_max` で読み取ります。オフの上の最初の段階が最初のパーセントです。設定が起こり得ないとするレベル(4 段階を通知して 25 を報告する ESPHome のファン)は、625 パーセントではなく、そう伝える不良読み取りです。

検出済み画面は、コンポーネントのコマンドが向かう可能性のあるすべてのトピックを一覧にします。メインのトピックに加えて、ライトの明るさのトピックやファンの速度のトピックも含め、コンポーネントが読み取る範囲の外にあるもの、プレフィックスの内側にあるもの、別のデバイスが使用を主張しているものに印を付けます。

サーモスタットや給湯器の設定値の範囲は設定自身のもので、設定が与えない場合は形式の既定値です(サーモスタットは 7 から 35 °C、給湯器は 43.3 から 60 °C、設定が `temperature_unit: F` なら °F)。これはタグの範囲なので、ゲートは上限が 30 のラジエーターバルブへの 31 °C を、何かが送られる前に拒否します。モードは設定のリストで、挙げられていないモードも同じように拒否されます。画面はまさにそれらを提供し、適用された変更で新しいモードが加わると、画面もそれを受け取ります。

アラームパネルの `code` は、消費者側の画面が何かを送る前に求めるものです。HotLoop では、人が有効にしたタグとすべてのコマンドの監査により、誰が警戒または解除できるかはゲートが判断するため、動作は設定が述べるとおりに送出されます。コマンドテンプレートがコード自体(`{{ code }}`)を必要とするパネルはコマンドできません。HotLoop にはそこに入れるコードがなく、検出済み画面がそう伝えます。掃除機の `send_command_topic` は使用しません。任意のコマンドは、HotLoop が設定と照らして確認できない、まさにそのものだからです。

カメラや image の画像は、コンポーネントごとに最新のものをメモリに最大 4 MiB まで保持し、`GET /api/entities/{entity_id}/image` で提供されます。HotLoop は、設定の `content_type` が何を主張していても、バイトが JPEG、PNG、GIF、WebP である場合にのみ保持します。SVG はスクリプトを実行する文書であり、ダッシュボードを開いた人にスクリプトを実行する「画像」は穴だからです。タグは短いハッシュを保持するため、JPEG だらけのデータベースなしに、履歴で画像がいつ変わったか分かります。URL で通知された画像はリンクです。HotLoop は http または https の場合にのみそれを表示し、取得することは決してありません。デバイスが指定したアドレスを何でも取得するサーバーは、ネットワーク上のあらゆるものに向けられてしまうからです。どちらもログブックには記録されません。カメラは毎秒変化し、tag_history にはすでにすべての変更があります。

形式が定義するすべてのコンポーネントは、何かになります。定義していないコンポーネント(`kettle`)は、通知した内容とともに保存され、何も作らないものとして一覧に載ります。形式には日付、時刻、datetime のコンポーネントがないため、この一覧にもありません。

エンティティ ID は HotLoop のもので、デバイスとタグから作られます。設定の `object_id` と `default_entity_id` は無視されます。設定が HotLoop の名前空間の名前を選ぶことはなく、悪意のある設定なら `switch.boiler_main` を選ぶでしょう。

## すべて信頼できないものとして扱います

設定が述べるすべては、プレフィックスに公開できる誰かから来たものです。したがって次のようになります。

- 名前とテキストには上限があり、制御文字が除去され、画面はそれを HTML ではなくテキストとしてページに置きます。
- ワイルドカードを含むトピック、`$` トピック、置く場所となる基準のない `~` は、理由付きで拒否されます。
- 64 KiB を超える設定は拒否されます。デバイスは 512 個を超えるコンポーネントを持てません。1 つのブローカーで判断を待てるデバイスは 256 台までです。毎秒 200 を超える設定メッセージは破棄されて数えられます。すべての拒否は数えられて検出済み画面に表示され、何も言わずに破棄されることはありません。
- HotLoop は `<prefix>/+/+/config` と `<prefix>/+/+/+/config` を購読し、プレフィックス配下の `#` は決して購読しないため、迷い込んだ深いトピックで何かを解析させられることはありません。
- 256 KiB を超える、または UTF-8 でない状態ペイロードは不良読み取りです。

内蔵ブローカーで匿名接続を許可すると、ネットワーク上の誰でもデバイスを通知し、どのコマンドトピックにも公開できます。検出済み画面はそれを赤で示します。各デバイスに、HotLoop でプロファイルから作成した、トピック名にちなんだ専用のログインを与えてください([内蔵 MQTT ブローカー](/ja/iot/broker/))。そうすれば、デバイスは自分を通知することだけができ、他のデバイスのコマンドトピックには触れられません。

## ブローカー側

ディスカバリーは内蔵ブローカーで動作し([内蔵 MQTT ブローカー](/ja/iot/broker/)を参照)、ブローカーが有効であれば既定で有効です。HotLoop 自身のクライアントは、起動のたびに作成されメモリにのみ保持されるログインで接続するため、設定するものも、バックアップに漏れるものもありません。自身で公開するのは birth(`<prefix>/status` = `online`)の 1 つだけで、これを待ち受けるパブリッシャーに再通知させます。

| 変数 | 既定値 | <span class="sr-only">Details</span> |
|---|---|---|
| `HOTLOOP_BROKER_DISCOVERY` | `true` | 内蔵ブローカーで通知を受信する |
| `HOTLOOP_BROKER_DISCOVERY_PREFIX` | `homeassistant` | 通知が届くトピックのプレフィックス |

ブローカーごとに 1 つのクライアント `hotloop-disc-embedded` を、リスナーと検出されたすべてのデバイスのドライバーが共有します。`--mcp-stdio` ヘルパーは何も開きません。同じ id の 2 つ目のクライアントは、数秒ごとに Gateway のクライアントをブローカーから追い出してしまうからです。1 つのデータベースに複数のレプリカがある場合、ディスカバリーのロックを持つレプリカだけが受信します。

## 他のブローカー

多くの工場はすでにブローカーを運用しています。UNS である Mosquitto や、Zigbee2MQTT の機器が持ち込んだものです。HotLoop はそれらも受信します。設定、MQTT、ブローカーの追加で、id(そこから来たすべてのデバイスでブローカーを指す名前)、場所、ログイン、パブリッシャーが通知するプレフィックスを指定します。ブローカーは有効である必要はなく、HotLoop はこのために内蔵ブローカーを必要としません。

HotLoop 自身のブローカーとは、意図的に 3 点が異なります。

- **デバイスは受信トレイで待ちます。** 忙しい工場のブローカーでは、「自動で現れる」は、昼前に画面に 300 台のデバイスが並ぶことを意味します。そのため、通知されたデバイスは、誰かが受け入れるまで何も作らず読み取りもせず、検出済み画面に一覧表示されるだけです。受け入れると作られ、読み取りを始め、そのポイントは他と同じく有効にできます。何を流し込まれても信頼できるブローカーは、「デバイスが自動で現れる」に切り替えられます。
- **last will なし。** HotLoop は last will なしで接続します。共有ブローカー上の `offline` の will は、実際には HotLoop だけだったのに、そこの他のすべてのパブリッシャーに何かが消えたと伝えてしまいます。テストは CONNECT パケット自体を検査し、接続を切断して何も送られないことを証明します。
- **ACL はそのブローカー自身のものです。** HotLoop は他人のブローカーで誰が何を公開したか見られないため、そこには「ログインによる通知元」はなく、各ログインが何に触れてよいかはそのブローカーの管理事項です。HotLoop には、プレフィックスと受け入れたデバイスのトピックを読み取り、birth とコマンドトピックに書き込むだけのログインを与え、それ以外は与えないでください。Mosquitto の場合:

  ```
  user hotloop
  topic read homeassistant/+/+/config
  topic read homeassistant/+/+/+/config
  topic write homeassistant/status
  # the devices you accept, for example a Zigbee2MQTT bridge:
  topic read zigbee2mqtt/#
  topic write zigbee2mqtt/+/set
  ```

**受信専用**は、HotLoop が発信してはならないブローカー用です。本番の UNS や他社の工場です。HotLoop はそこに何も公開しません。birth もコマンドもありません。これは画面ではなくセッションの規則です。公開は拒否され、書き込みゲートは、誰かが受け入れたデバイスや誰かが有効にしたポイントであっても、ドライランを含め、そのデバイスへのすべてのコマンドを「the broker plant-uns is listen-only」として拒否します。ログインに必要なのは `topic read` の行だけです。

パスワードは、UniFi コンソールのものと同様に、デバイス資格情報キー(`HOTLOOP_SECRET_KEY_FILE`)で封印され、API から出てくることは決してありません。キーがなければ、パスワード付きのブローカーは平文で保存されず、拒否されます。バックアップには封印されたまま含まれ、デバイスの資格情報と同じ規則で復元されます([バックアップと復元](/ja/iot/backup/))。パスワードを開けないブローカーは接続されずに一覧に表示され、理由を伝えます。

ブローカーを変更すると、リスナーとそこから来たすべてのデバイスが新しい設定で再接続します。ブローカーを無効にしても、そのデバイスは残り、不良として読み取られ、ブローカーがここでは動作していないと伝えます。ブローカーを削除すると受信トレイも一緒に消え、そこから誰かが受け入れたデバイスがまだ存在する間は、それらを名指しして拒否されます。

## Edge Relay では

Edge Relay も同じコードでディスカバリーを行いますが、判断を保持するデータベースも、判断を下す画面もありません。そのため、聞いたものを取り込み、読み取って Sparkplug で転送し、見つけたものは何も有効にできません。タグはすべての検出済みタグと同じく読み取り専用で、デバイスは受け入れられず、リレーには書き込み経路がまったくありません。デバイスファイルにブローカーを指定してください。[Edge Relay リファレンス](/ja/edge-relay/reference/#ディスカバリー-41810)を参照してください。コマンドできるデバイスは反対側から到達します。Gateway で受け入れて有効にし、Gateway がプッシュするファイルで届きます。停止すると聞いたことは忘れ、ブローカーからもう一度聞きます。

## 再起動とリプレイ

受け入れ済みのデバイスは、デバイスの行から動作します。HotLoop は、工場とともに復帰するのに retained メッセージを 1 つも必要としません。

内蔵ブローカーは再起動をまたいで何も保持しないため、その後はすべての設定が「ない」状態になります。**設定がないことは撤回ではありません。** 撤回は明示的な空の設定だけです。そうでなければ、機器が再起動するたびに工場全体が撤回されてしまいます。デバイスが次の状態を送るまで、そのエンティティは、再起動前の値を現在の値のように見せかけることなく、不明と読み取られます。

数百の retained 設定を一度にリプレイするブローカーは、1 つのバッチです。2 秒の静止、1 回の処理、1 回の再読み込みです。すでに記録されているもののリプレイは、何も変更せず、何も再読み込みしません。

## バックアップ

`mqtt_devices`(誰が何を受け入れ、無視したか)、`mqtt_configs`(届いたままのすべての設定、バイト単位)、`mqtt_discovered`(正規化された各コンポーネント)は、すべてのバックアップに含まれます。判断は、どのデバイスも通知し直せない部分です。
