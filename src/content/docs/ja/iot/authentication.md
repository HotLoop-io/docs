HotLoop は 4.4.0 から独自のログインを備えており、すべての製品が既定でログインを必須にしています。ログインなしで動かす方法も引き続き用意されています。これは、ダッシュボードの背後で本当に隔離されていて、そのことを自分で明示したい環境のための意図的な選択です。[ログインなしでの運用](#ログインなしでの運用)を参照してください。ただし、素の `helm install` や Podman Quadlet ユニットは、今ではログイン必須の状態で起動します。

## 要点

- **ローカルユーザー、bcrypt パスワード、サーバー側セッション。** 外部 ID プロバイダーはまだありません。エージェントインターフェースを守る別個の Bearer トークンの境界については [MCP](/ja/iot/mcp/) を参照してください。この認証はそれを置き換えるものではありません。
- **ロールは 3 つ、admin、operator、viewer。** admin はユーザー管理を含め、すべてを行えます。operator はすべてを読み取り、タグの書き込み、アラームの確認応答、オートメーションの実行ができます。viewer はすべてを読み取れるだけです。もっと細かく絞りたい場合は、ロールの代わりに明示的な権限リストをユーザーに付与することもできます。
- **セッションは Cookie または Bearer トークンです。** クライアントが使いやすい方を選べます。ブラウザー UI は Cookie を使い、スクリプトや別のサービスは `Authorization: Bearer <token>` を使います。
- **共用パネルは PIN またはバッジでサインインし**、誰も触れていなければサインアウトするので、そこでのすべての書き込みには人の名前が残ります。[キオスクパネル](#キオスクパネル-pin-またはバッジとアイドル時のサインアウト)を参照してください。
- **セッションは期限切れになります。** `HOTLOOP_AUTH_SESSION_TTL` で、既定は 12 時間です。「ログインを保持する」はありません。勤務シフトより長く残るセッションは、誰も見ていないセッションだからです。

## 最初のアカウントを作る

チャートは初回インストール時にアカウントを 1 つ生成し、`helm install` の NOTES 出力に 1 度だけ表示します。

```
helm install hotloop ./charts/hotloop \
  --namespace hotloop --create-namespace
```

バイナリを直接実行する場合は、ハッシュを生成して 2 つの変数を設定します。

```sh
hotloop hash-password
# Password: ********
# Confirm password: ********
# $2a$10$....................................................

export HOTLOOP_AUTH_ENABLED=true
export HOTLOOP_ADMIN_USER=admin
export HOTLOOP_ADMIN_PASSWORD_HASH='$2a$10$....................................................'
```

`hash-password` は、すでにパスワードを持っているスクリプト向けに、`-password` を直接受け取ることもできます。

```sh
hotloop hash-password -password 'something-long'
```

ここで作られる admin アカウントは**ブートストラップ**であり、リセットのスイッチではありません。いったん作られると、`HOTLOOP_ADMIN_PASSWORD_HASH` を変更して再起動しても何も起きません。`EnsureAdminUser` はそのユーザー名がまだ存在しない場合にだけアカウントを作成するため、ここに設定した値が、運用者が UI から変更したパスワードを上書きすることは決してありません。これは Helm のアップグレードで特に重要です。同じ `values.yaml` を再適用しても、誰かのパスワードが黙って元に戻ってはいけません。

## ロール

| ロール | できること |
|---|---|
| **admin** | すべて: `*`。ユーザーの作成、無効化、削除を含みます。 |
| **operator** | すべての画面を読み取ります。タグの書き込み(`POST /api/write`)とコマンドエンティティ(`POST /api/services/...`)、ヘルパーの設定(`helpers.write`、[ヘルパー](/ja/iot/helpers/)を参照)、スクリプトの実行と停止(`scripts.run`、[スクリプト](/ja/iot/scripts/)を参照)、レシピの適用(`recipes.apply`、[レシピ](/ja/iot/recipes/)を参照)、ブループリントからのルール作成とそのアップグレード(`blueprints.apply`、[ブループリント](/ja/iot/blueprints/)を参照)、そのロールに提供されるダッシュボードの表示(`dashboards.read`、[ダッシュボード](/ja/iot/dashboards/)を参照)、使用エネルギーとそのコストの読み取り(`energy.read`、[エネルギー](/ja/iot/energy/)を参照。メーターや料金表の作成は admin の `energy.write` です)、ボードの並べ替え、アラームの確認応答、保留、保留解除、オートメーションの実行ができます。デバイス、タグ、アラーム、オートメーション、スクリプト、レシピ、ブループリント、ダッシュボードの*定義*は編集できず、ユーザーの管理もできません。 |
| **viewer** | すべての画面を読み取ります。それ以外は何もできません。 |

ロールの代わりに明示的な `permissions` リストをユーザーに付与できます。これはロールに追加されるのではなく、ロールを**完全に置き換えます**。ユーザーは「operator ロール」か「まさにこれらの権限」のどちらかで、両方になることはないため、誰が何をできるかを知るために見る場所は 1 つだけです。

権限の文字列は `resource.action` の形式で、`tags.write` や `alarms.ack` のようなものです。リソースのワイルドカード `tags.*` や、全体のワイルドカード `*` も使えます。

## キオスクパネル: PIN またはバッジと、アイドル時のサインアウト

自分のコンピューターでは、すでにサインインしています。パスワードを 1 度入力しており、書き込みは従来どおり書き込みゲートをそのまま通り、あなたの名前で記録されます。この点は何も変わっていません。壁に取り付けたパネルは、誰のコンピューターでもありません。パネルが `panel-3` としてサインインしていたら、監査証跡には「panel-3 がバルブを開けた」と残りますが、それは監査証跡とは言えません。そこでパネルは、PIN またはバッジで人をサインインさせ、すべての書き込みはその人のものになり、誰も触れていなければパネルがその人をサインアウトさせます。

### オペレーターに見えるもの

パネルは物理的な画面です。HotLoop を `/?screen=<name>` で開いたものです([ダッシュボード](/ja/iot/dashboards/#ロールと画面)を参照)。誰もサインインしていないときは「PIN またはバッジ」という入力欄が 1 つだけ表示され、工場の情報は何も表示されません。PIN を入力して Enter を押すか、バッジをスキャンします。パネルがそのダッシュボードを開き、隅にサインインしている人と**サインアウト**ボタンが表示されます。通常その情報を表示するヘッダーが、パネルにはないためです。書き込みボタンを押すと、他の場所と同様に確認と理由が求められ、書き込みはその人の名前で記録されます。

アイドル制限の時間、誰も画面に触れないと、パネルはその人をサインアウトさせて PIN の入力欄に戻ります。これはページだけでなくサーバーも強制します。それだけの時間アイドル状態だったキオスクセッションは削除され、その後にその Cookie で送られた書き込みは `401` で拒否されます。そのため、ページを閉じても、ページがハングしても、誰かがサインインしたままになることはありません。パネルをどうしてもパスワードで使う必要がある場合は、入力欄の下の「パスワードを使う」が通常のサインインで、通常の 12 時間が適用され、アイドル制限はありません。それはその人自身のログインだからです。

触れたと数えられるのは、タップ、クリック、キー入力、書き込みです。数えられないのは、ダッシュボードが数値を更新することと、ライブフィードです。これらは誰がいてもいなくても続きます。

### 設定方法

admin は **設定、ユーザー**で、各人にコードを付与します。その人の行の **PIN またはバッジ**で、コードを 2 回入力し、**設定**を押します。バッジを発行するスクリプトなら、API を使います。

```sh
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"code":"482913"}' https://gateway/api/users/olga/pin

# Take it away (also signs them out of every panel)
curl -X DELETE -H "Authorization: Bearer $TOKEN" https://gateway/api/users/olga/pin
```

- **PIN は資格情報です。** パスワードと同じコストの bcrypt ハッシュとして保存され、平文で保存されることも、システムログやレスポンスに現れることも決してありません。ユーザー一覧には `hasPin` とだけ表示されます。バックアップには、パスワードのハッシュとまったく同じようにこのハッシュが含まれます([バックアップと復元](/ja/iot/backup/))。
- **バッジは、キーボードウェッジ型リーダーが入力する値です。** ハードウェアドライバーはありません。キーボードとして動作するリーダーが、バッジの番号をパネルの 1 つの入力欄に入力して Enter を押すと、フォームが送信されます。つまりバッジは PIN と同じようなコードです。リーダーが入力するものであれば何でもよく、空白を含まない 6 文字から 72 文字で、同じ場所でアカウントに設定します。キーボードとして動作しないリーダーからの読み取りは実装されていません。
- **1 つのコードにつき 1 つのアカウント。** バッジリーダーはユーザー名を入力しないため、パネルはコードだけで人を特定します。そのため、他のアカウントがすでに持っているコードを設定しようとすると拒否されます。
- **コードは、コードを持つすべてのアカウントと照合されます。** パスワードと同じコストの bcrypt を使います。ソルト付きハッシュは値で検索できないためです。かかる時間はコードを持つアカウントの数に比例し、数十件なら最悪でも数秒です。コードが正しくても間違っていても、かかる時間は同じです。
- **コードはアカウントのロールでサインインします。** パネルで持つべきロールを持つ人に渡してください。キオスクセッションはアカウント自身の権限そのままで、それより狭くはなりません。viewer のコードは viewer としてサインインし、viewer の書き込みは従来どおりゲートが拒否します。
- **アカウントを無効にすると**、そのパネルセッションも他のセッションと一緒に終了し、無効なアカウントのコードではサインインできません。**コードを削除すると**、そのアカウントはパネルからサインアウトされ、パスワードとその人自身のコンピューターのセッションはそのままです。

### アイドル時のサインアウト時間

既定は 15 分です。クリップボードを持ってパネルで段取り替えを行ったり、バルブまで歩いて動くのを確認したりするには十分な長さで、作業の終わりに置き去りにされたパネルが、次の人が来るまで誰かの名前のままにならない程度には短い時間です。これは私の判断であり、コードや標準が定めた数字ではありません。**設定、プラント、キオスクのアイドル時サインアウト(秒)**で、再デプロイなしに 10 秒から 12 時間の範囲で変更できます。また、`HOTLOOP_AUTH_KIOSK_IDLE`(期間、`15m`)で既定値を設定することもできます。設定画面の値が変数より優先されます。セッションは、他のセッションと同様に `HOTLOOP_AUTH_SESSION_TTL` でも終了します。

### パスワードと PIN を間違えたときのロックアウト

パスワードや PIN の間違いは、試された**アカウント**に数えられます。連続して 10 回間違えると、そのアカウントだけが 5 分間ロックされ、他の人のアカウントには影響しません。10 回目より前に正しいパスワードや PIN を入力すると回数は最初からになり、ロックが終わると新たに 10 回が与えられます。ロックされたアカウントは、正しくても間違っていても何を入力してもサインインを拒否し、`429` で待つべき時間を伝えます。ロックが止めるのは新しいサインインだけで、それ以外は止めません。アカウントがすでに持っているセッションは、リクエストもライブフィードも含めて続くので、他の誰かが 10 回間違えて推測しても、ラインにいるオペレーターの画面が消えることはありません。ロックアウトはパスワードのサインインにも PIN のサインインにも同様に適用され、ロックはすべてシステムログ(カテゴリ `auth`)に記録されます。

- **数字の根拠。** NIST SP 800-63B は、検証者が単一のアカウントに対する連続した失敗の試行を制限することを求めています。第 3 版の 5.2.2 節と第 4 版の 3.2.2 節は、どちらも最大を 100 とし、運用者がそれより低く設定してよいとしています。第 4 版は、失敗後に請求者を待たせることも認めています。これはまさにその待機であり、恒久的な無効化ではありません。10 は NIST の上限の 10 分の 1 で、うっかり打ち間違える回数よりは多い値です。5 分は、5 分あたり 10 回の推測では 6 桁の PIN の 100 万通りに手が届かない(すべて試すのに約 350 日)だけの長さで、パスワードを打ち間違えたオペレーターがコーヒーを飲む間に戻れる短さです。PIN の最小長を 6 文字とするのは、第 3 版の 5.1.1.2 節が割り当てられる秘密に対して定めた下限で、管理者が PIN を配る場合がこれに当たります。10 と 5 は、NIST の上限の範囲内で私が選んだ値であり、NIST の数字ではありません。
- **どちらも設定です。** **設定、プラント**で、「この回数パスワードまたは PIN を間違えるとアカウントをロックする」(既定 10、1 から 100 まで、0 で無効)と「ロックされたアカウントがロックされたままの時間」(既定 5 分、10 秒から 1 日まで)を変更します。変数は `HOTLOOP_AUTH_LOCKOUT_ATTEMPTS` と `HOTLOOP_AUTH_LOCKOUT_DURATION`(期間、`5m`)です。設定画面の値が変数より優先されます。
- **admin はアカウントのロックを解除できます。** **設定、ユーザー**ではロックされたアカウントが `locked` と表示され、**ロック解除**ボタンがあります。`DELETE /api/users/{username}/lockout` でも解除できます。回数はゼロから数え直されます。
- **パネルは決してロックされません。** パネルで間違ったコードを入力しても、パネルには数えられないので、1 人のミスが次の人を止めることはありません。
- **コードだけでは数えられないため、パネルの応答を遅くします。** バッジリーダーはバッジだけを入力し、PIN だけを入力した場合は、間違っていると一致するアカウントがないため、数える相手のアカウントがありません。パネルに数えると、前の作業者のミスで次の作業者が締め出されることになりますが、パネルは決してロックされません。その代わり、連続して間違えるたびに、次の確認の前にそのパネルが 0.5 秒ずつ長く待ちます。最初のミスの後は 0.5 秒、2 回目の後は 1 秒、というように上限まで延び、既定の上限は 3 秒です。正しく入力すると最初からになります。そのため、次の作業者は長くても上限だけ待てば入れ、推測する人はパネルごとに上限ごとに 1 回しか試せません。6 桁の PIN 100 万通りを試すには 1 か月以上かかります。同時に送られた試行は並んで、それぞれ順番を待ちます。ユーザー名と一緒に入力された PIN は遅くなりません。それはアカウントのものであり、間違ったパスワードと同様にアカウントをロックします。最長の待ち時間は **設定、プラント、PIN を間違えた後にパネルが待つ最長時間(秒)** で、0 から 30 まで、既定値は `HOTLOOP_AUTH_PANEL_DELAY_CAP`(期間、`3s`)で、0 で無効になります。3 秒は、打ち間違えた作業者が我慢できる間であり、すべてのコードを試す人にとっては意味のある遅さです。0.5 秒という刻みは固定です。
- **どのパネルか。** クライアントのアドレスです。プロキシが設定していれば `X-Forwarded-For` の最初のホップ、そうでなければ接続自体のアドレスで、セッション一覧に記録されるのもこれです。サインイン前にはこれより良い情報はわかりません。まだセッションがなく、サーバーが渡した Cookie はクライアントが捨てて待機をやり直せるからです。そのため、`X-Forwarded-For` を設定するプロキシの背後では、各パネルが個別に待ちます。設定しないプロキシの背後では、すべてのパネルがプロキシのアドレスを共有して互いを遅くしますが、それは長くても上限までです。また、ポートに直接届くクライアントは、自分で `X-Forwarded-For` を送って待機を回避できます。だからこれは速度を落とす仕組みであり、統制手段はアカウントのロックアウトです。重要な推測攻撃にはユーザー名の形式を使うか、長いランダムなバッジ値を使ってください。
- **アカウントが存在することがわかります。** `429` は存在するアカウントに対して返されるため、名前を試している人にどの名前があるかが伝わります。ロックアウトとはそういうものです。

### できないこと

- **コードだけではロックアウトできません。** 理由は[ロックアウト](#パスワードと-pin-を間違えたときのロックアウト)に書かれています。
- **サインアウトの前に警告はありません。** 時間になると、パネルは PIN の入力欄に戻ります。
- **パスワードでサインインしたままのパネル**(これまでパネルはそのように運用するしかありませんでした)は、従来どおり動作し、そのアカウントとして書き込みを続けます。共用パネルには常設の operator ログインを置かず、パネルを使う人に PIN を渡してください。
- **リーダーのドライバー、SSO、パネルごとの権限はありません。**

## ユーザーの管理

admin 専用です。UI では**設定、ユーザー**で、すべてのアカウントのロール、有効かどうか、最後にサインインした日時が表示され、ユーザーの追加、編集(ロールと無効化)、新しいパスワード、削除ができます。`users.manage` を持たない人や、認証が無効のときは、何も描画されません。権限が 1 つずつ列挙されたアカウントは、件数とともに `custom` と表示され、編集でロールを選ばなければリストは保持され、ロールを選ぶとリストが置き換えられます。同じことは REST API でも行えます。

パスワードは 8 バイトから 72 バイトです。72 は bcrypt 自体の上限で、それより長いものは、その旨を示して拒否されます。OPC UA でも同じように動作します([OPC UA サーバー](/ja/edge/opc-ua-server/#ログインできるユーザー)を参照)。以前のリリースでは、64 バイトを超えるパスワードがこちらではサインインできてもあちらではできませんでした。

```sh
# List
curl -H "Authorization: Bearer $TOKEN" https://gateway/api/users

# Create
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"username":"j.smith","password":"something-long","role":"operator"}' \
  https://gateway/api/users

# Disable (does not delete; also revokes every session that account holds)
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"role":"operator","disabled":true}' \
  https://gateway/api/users/j.smith

# Reset a password an operator forgot
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"password":"a-new-one"}' \
  https://gateway/api/users/j.smith/password
```

誰かが驚く前に知っておくべき拒否が 2 つあります。

- **サインインしている自分のアカウントは削除できません。** 先に別の admin アカウントに切り替えてください。
- **有効な最後の admin アカウントは無効化も削除もできません。** 最初のアカウントを削除する前に、2 つ目のアカウントを admin に昇格させるか、そのままにしておいてください。このチェックがないと、スクリプトによるユーザー同期で 1 回ミスをしただけで、元に戻せる admin セッションが残らないまま締め出されてしまいます。

サインインしているユーザーは誰でも、上記の制限なしに自分のパスワードを変更できます。

```sh
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"currentPassword":"old","newPassword":"new"}' \
  https://gateway/api/auth/password
```

パスワードを変更すると、そのアカウントが持つすべてのセッションが失効し、リクエストを行ったセッションも含まれます。クライアントは再度ログインする必要があります。

## デバイスの資格情報は書き込み専用です

4.15.1 で追加されました。それ以前は、`GET /api/devices` と `GET /api/devices/{id}` がデバイスの `config` と `address` を保存されたまま返していたため、viewer を含むサインインしたすべてのユーザーが、MQTT ブローカーのパスワード、HTTP と MTConnect の資格情報、そしてデバイスに保存されたその他すべてを読み取ることができました。4.15.0 では OPC UA のパスワードだけが隠されていました。4.15.1 からは、**admin を含む**どのロールも、API でデバイスの資格情報を読み戻すことができません。変更するには新しい値を送ります。

### 資格情報として扱われるもの

| プロトコル | 構成で隠されるもの | そのほかに隠されるもの |
|---|---|---|
| MQTT | `password` | アドレス内のユーザー情報と秘密のクエリ値(`mqtt://user:pass@broker`) |
| HTTP | `password`。`headers` のすべての値(いくつかの一般的な値 `Accept`、`Accept-Encoding`、`Accept-Language`、`Cache-Control`、`Content-Type`、`User-Agent` を除く)。資格情報に言及する `body` と `writeBody`(`password`、`token`、`apiKey` など)。`writeUrl` 内の秘密に見えるクエリ値 | アドレスと `writeUrl` 内のユーザー情報と秘密のクエリ値 |
| MTConnect | `password`。`headers` のすべての値(同じ例外あり) | アドレス内のユーザー情報と秘密のクエリ値 |
| OPC UA | `password` | アドレス内のユーザー情報も隠され、ドライバーはそれを無視します。OPC UA のエンドポイント URL には資格情報が含まれないためです |
| Modbus、S7comm、EtherNet/IP | どのオプションも資格情報ではありません | アドレス内のユーザー情報は隠され、ドライバーは同じ理由で無視します |

鍵ファイルへのパス(`keyFile`)は鍵の素材ではないため表示されます。`allowInsecureCredentials` のようなフラグも同様です。

上のリストはコードで検証されています。テストがすべてのドライバーのオプション構造体を読み取り、あるオプションが資格情報のリストにも、資格情報ではないと分かっているオプションのリスト(`plainConfigKeys`)にも載っていないとき、自由形式のエントリのマップや自由記述のフィールドが資格情報のリストに載っていないとき、どちらかのリストがどのドライバーも読まないものを挙げているときに失敗します。そのため、新しいオプションは、どちらなのかを誰かが決めない限り出荷できません。

リストの下のセーフティネットとして、デバイスの構成のどの深さにあるキーも、どのプロトコルでも、名前に `password`、`passwd`、`passphrase`、`pwd`、`secret`、`token`、`apikey`、`authorization`、`credential`、`private`、`bearer`、`cookie`、`basicauth`、`signature`、`jwt`、`oauth`、`sessionid`、`connectionstring` を含むか、`key` で終わるか、単語全体として `pass`、`pw`、`pwd`、`passwd`、`auth`、`cred`、`creds`、`sig`、`signature`、`sas`、`jwt`、`otp`、`pin`、`psk` のいずれかを持つ場合、名前によって隠されます。単語は句読点と、小文字から大文字への境目で分割されるため、`db_pass`、`smtp_pw`、`apiAuth`、`sasToken` は該当し、`bypass`、`compass`、`passive`、`authority`、`pinned` は該当しません。大文字小文字と句読点は無視され、`encoding/json` が同じキーとして読む綴り(s の代わりの長い s、k の代わりのケルビン記号)も同様です。短い単語のルールは意図的に大雑把にしてあります。`authMode` のように誰も確認していないキーは、`plainConfigKeys` に追加されるまで隠されます。

名前によって隠される値と、そのようなキーの下にあるすべてのものは、型にかかわらず置き換えられます(数値も文字列と同様に隠されます)。ただし、資格情報になり得ない真偽値は除きます。テキストの中に資格情報を含む文字列は、どこにあってもまるごと隠されます。`--password hunter2` を含むコマンドライン、`password=...` の組や接続文字列、`Authorization: Bearer ...` がその例です。資格情報が設定されていないデバイスには何も表示されないため、「パスワードなし」と「見えないパスワードがある」を区別できます。JSON として読めない構成は、そのまま表示されるのではなく `{}` として表示されます。

隠された値は `[redacted]` と表示されます。アドレスでは、パスワードを置き換えてユーザー名は残し(`http://svc:[redacted]@meter/api`)、コロンがなければユーザー情報全体を、そしてクエリとフラグメントの秘密に見える各パラメーターの値を置き換えます(`?fmt=json&token=[redacted]`、`#access_token=[redacted]`)。パラメーターは `&` か `;`、またはそれらのパーセントエンコード形式 `%26` と `%3B` で区切られ、それぞれ単独で判断されるため、`?fmt=json` は読めるままです。`code` という名前のパラメーターは、アドレスの中でのみ秘密として扱われます。これは `?code=` にある Azure Functions のキーのためで、他の場所では当てはまりません。きれいに読めないクエリ(不正なパーセントエスケープ、制御文字)は、推測せずにまるごと隠されます。

### デバイスの保存

`POST /api/devices` は、id が新しければデバイスを作成し、すでにあれば置き換えます。別の `PUT` はありません。アドレスと構成にあるすべての資格情報について、次のとおりです。

| リクエストが送るもの | 結果 |
|---|---|
| 新しいデバイスで実際の値 | 値は与えられたまま保存されます。 |
| 新しいデバイスで `[redacted]` | 400 で拒否されます。プレースホルダーが資格情報として保存されることはありません。 |
| 既存のデバイスで `[redacted]` | 保存された値が保持されます。 |
| 既存のデバイスでキーを省略 | 保存された値が保持されます。秘密について知らないクライアントが、誤って消すことはできません。 |
| 既存のデバイスで新しい文字列または数値 | 保存された値を置き換えます。 |
| 既存のデバイスで空の文字列または `null` | 保存された値を消去します。資格情報を削除する唯一の方法です。 |
| 保持すべき保存値がないのに `[redacted]` | 400 で拒否されます。 |

プレースホルダーは、構成やアドレスのどこに現れても保存されません。同じ場所の保存された値に置き換えられるか、保存された値がない場合は拒否されます。

2 つ補足があります。`headers`(エントリを人が選んだマップ)では、マップが単位になります。省略したエントリは削除され、`{}` はすべてを消去し、`headers` キー全体を省略すると保持されます。キーは、ドライバーが照合するのと同じように、大文字小文字を区別せずに照合されます。また、資格情報ではないものはすべて従来どおり置き換えられます。`config` をまったく付けずに保存したデバイスは、資格情報を保持し、それ以外は保持しません。

Web UI のデバイスエディターは、デバイスの構成を API が返すとおりに、プレースホルダーも含めて表示し、表示されているものを保存します。したがって、資格情報に触れずにデバイスを編集すると、資格情報は保持されます。**UI で秘密を変更するには、構成(またはアドレス)内の `[redacted]` を新しい値に置き換えてください。** 以前の値が事前に入力されることはないため、デバイスを変更する人は、変更するために資格情報を知っている必要があります。

### デバイスを移動しても秘密は引き継がれません

保持された資格情報は、デバイスが指す先に送られます。デバイスを移動したときに資格情報が保持されるとすると、デバイスを保存できる人なら誰でも、自分のリスナーを指すようにして、ゲートウェイに資格情報を提示させることで、保存された資格情報を読み取れてしまいます。そのため、保存によってアドレスまたは `writeUrl` のホストやポートが変わり、保存された資格情報が(プレースホルダーまたは省略によって)保持されることになる場合は、その資格情報の名前を示す 400 で拒否されます。もう一度入力するか、空の文字列を送って消去してください。パス、スキーム、その他のデバイスに関する変更は移動とは見なされず、保存された資格情報のないデバイスは自由に移動できます。

### 資格情報が現れない場所

すべてのプロトコルのデバイスについて、資格情報が入りうるすべての場所に資格情報を入れて、テストは次のすべてを検索します。viewer、operator、admin それぞれに対するすべてのデバイスエンドポイント(一覧、取得、作成、更新のレスポンス)、その他すべての読み取りエンドポイント、`/api/diagnostics` と `/api/status`、`/api/sites` とそれが一覧にするアウトバウンドの MCP サーバー、ライブイベントストリーム、システムログと書き込み監査、エラーレスポンス、すべての MCP ツールとリソース、そしてデバッグレベルのプロセスログ(ランタイムとドライバーの両方)です。ドライバーのエラーテキストと、ランタイムのイベントやログからは、エラーがアドレスやサーバーの応答を繰り返すことがあるため、デバイスの資格情報が値と形の両方で除去されます。1 文字か 2 文字の資格情報は、独立した単語として現れる場所でのみ置き換えられます。あらゆる場所で置き換えるとメッセージが台無しになるためです。

### 資格情報がまだ平文の場所

書き込み専用とは API に関することです。ゲートウェイは接続するために実際の値を必要とするため、次の場所には保存されたとおりに値があります。

- **データベース。** デバイスの資格情報は `config` と `address` の列にあります。`HOTLOOP_SECRET_KEY_FILE` を設定すると、`config` 内のキー付きのもの(すべての `password` とヘッダー値)は、データベースの外に保管された鍵で暗号化され、テキストに資格情報が書かれたアドレスやオプション(`mqtt://user:pass@host`、`?token=`)もまるごと封印されます。[バックアップと復元](/ja/iot/backup/#デバイスの認証情報と秘密鍵)を参照してください。
- **バックアップ。** バックアップ内の `devices.copy` には、データベースとまったく同じように、暗号化された状態か暗号化されていない状態で資格情報が含まれます。[バックアップと復元](/ja/iot/backup/#バックアップファイルを守る)を参照してください。
- **Edge Relay のデバイスファイル。** リレーは、デバイスの資格情報を含む JSON ファイルを読み込みます。[Edge Relay リファレンス](/ja/edge-relay/reference/#デバイスファイルの認証情報-4150)を参照してください。
- **フリート構成のプッシュ。** リレーにプッシュされるデバイスファイルは、そのまま MQTT トピックにリテインメッセージとして発行されます。[フリート管理](/ja/gateway/fleet/)を参照してください。

それに応じて、データベース、バックアップボリューム、リレーのデバイスファイル、ブローカーを保護してください。API を伏せても、これらには何の影響もありません。

### 信頼できないユーザーが API に届いていた可能性がある場合

4.15.1 より前は、サインインしたユーザーなら誰でも API を通じて保存されたデバイスの資格情報を読み取れました。本来アクセスすべきでないユーザーがゲートウェイに届く状態だった運用者(たとえば、請負業者に渡した viewer アカウントなど)は、そのゲートウェイが持つデバイスの資格情報、つまり MQTT ブローカー、HTTP と MTConnect のエンドポイント、OPC UA のアカウントの資格情報をローテーションしてください。4.3.1 以降に公開リリースはないため、影響を受けるのは未リリースのビルドの環境に限られます。

## 監査証跡に記録されるもの

すべての書き込みは、すでに `actor` 列を持つ `write_audit` を通っていました。メインの README の書き込みゲートを参照してください。この列はいまではヘッダーではなくセッションから取得され、キオスクパネルでは、セッションは PIN またはバッジでサインインした人です。

```
> write_tag tag=press-01/Zone1_Temp value=99 reason="testing"
```

`X-Forwarded-User` が何と言っていたかではなく、呼び出しを行ったセッションのユーザー名である `j.smith` が記録されます。サインイン、キオスクサインイン、サインアウト、パスワード変更、PIN の設定や削除(PIN そのものは決して記録されません)を含むすべてのユーザー管理操作は、書き込み監査が存在するのと同じ理由で、システムログ(`GET /api/events`、カテゴリ `auth`)に記録されます。半年後の変更が、見えるだけでなく説明できるものであるべきだからです。

## ログインなしでの運用

`HOTLOOP_AUTH_INSECURE=true`(またはチャートの `auth.insecure: true`)を設定すると、4.4.0 より前のすべてのバージョンとまったく同じように動作します。セッションは不要で、書き込みに記録されるアクターは `X-EmberNET-User` などのプロキシヘッダーから取得され、何も設定されていなければ `"operator"` になります。

これは、EmberNet ダッシュボード自身の NetworkPolicy が実際の境界であり、他の何もポッドに届かない環境では、現実的で擁護できる選択です。もはや既定ではない理由は、その条件が成り立っていると信じることは簡単でも、ポッドの内部から確認することは難しいからです。4.4.0 の要点は、NetworkPolicy のミスや、結局ダッシュボードの背後にいなかった環境が、`actor(r)` が攻撃者の選んだ値を返すことにまでつながってはならない、ということです。

`config.Validate` は、認証が有効でも、この方法で承認されてもいない状態では起動を拒否します。「認証なし」が常に誰かが意図的に下した決定であり、環境自身の構成に書き残されているべきで、誰も選ばなかった既定値であってはならないからです。

## EmberNet ダッシュボードからのサインイン

EmberNet App Store から HotLoop をインストールしたテナントは、パスワードを渡されることなく、LAUNCH から自分自身としてサインイン済みの状態でアプリに入ります。ダッシュボードのアプリホストは、このポッドに中継するすべてのリクエストに `X-Embernet-Assertion` を付けます。これは約 1 分間有効な ES256 トークンで、ダッシュボードだけが持つ秘密鍵で署名されています。トークンには、人(`email`)、テナント、それが作られた 1 つのアプリ(`aud`、`<tenant>/<Service name>`)、そしてテナントがその人のダッシュボードロールに対応づけた HotLoop ロール(`role`: `admin`、`operator`、`viewer`)が含まれます。

公開鍵が設定されていなければ無効で、設定されても他のものは従来どおり動作します。ローカルアカウント、Cookie、Bearer トークン、キオスクパネルです。

| 変数 | チャートの値 | 役割 |
|---|---|---|
| `HOTLOOP_AUTH_ASSERTION_PUBLIC_KEY` | `embernetSignin.publicKey` | ダッシュボードの公開鍵で、PKIX PEM、ECDSA P-256 です。ストアがデプロイ時に設定します。 |
| `HOTLOOP_AUTH_ASSERTION_AUDIENCE` | 名前空間とリリース名から算出 | `<tenant>/<Service name>`。鍵とあわせて必須で、別のアプリやテナント向けに作られたトークンは拒否されます。 |
| `HOTLOOP_AUTH_ASSERTION_ISSUER` | `embernetSignin.issuer` | `embernet-dashboard` |
| `HOTLOOP_AUTH_ASSERTION_HEADER` | `embernetSignin.header` | `X-Embernet-Assertion` |

正しいアサーションが行うことは次のとおりです。ダッシュボードが初めてその人を保証したときにここにユーザーが作られ(アドレスで名前が付けられ、パスワードはないので推測するものがありません)、ユーザーのロールはダッシュボードが送ったものにリクエストごとに従い、監査証跡にその人の名前が残ります。不正なアサーションが行うことは 401 で、たまたまそこにあるセッション Cookie に黙って切り替えられることはありません。不正な署名、ES256 以外のあらゆるアルゴリズム、期限切れまたはまだ有効でないトークン、有効期間が 10 分を超えるもの、誤った発行者、別のアプリやテナントのオーディエンス、オーディエンスと食い違うテナントクレーム、私たちのものではないロール、アドレスのない名前は拒否されます。

ローカルの admin は、ダッシュボードが入れた人に対しても最終的な決定権を持ちます。ユーザーを無効にすればその人は入れず、明示的な権限リストを与えればその人はそのリストを保持します。書き込みには引き続きポッド自身の書き込みスイッチが必要で、アサーションがそれを広げることはありません。ダッシュボードが作ったセッションからサインアウトしても、そのセッションは終了しません。アクセスは、ダッシュボードが署名をやめた次のリクエストで終わります。

## まだ対応していないこと

- **OpenID Connect はありません。** ローカルアカウントと、上記の EmberNet ダッシュボードの署名付きアサーションがあります。ID プロバイダーの連携は実装されていません。
- **テナントごと、サイトごとのロールはありません。** ユーザーの権限は、ゲートウェイが動作するどこでも同じです。1 つのプラントなら問題ありませんが、`Sites` の複数サイトのロールアップではさらに検討が必要です。
- **PIN やバッジだけを入力した場合のロックアウトはありません。** パスワードと、ユーザー名と一緒に入力された PIN だけが対象です。[ロックアウト](#パスワードと-pin-を間違えたときのロックアウト)を参照してください。`handleLogin` のタイミング安全な比較は、応答時間によるユーザー名の列挙を防ぎます。ログインエンドポイントの前には、引き続き NetworkPolicy や上流のプロキシを置くことをお勧めします。
