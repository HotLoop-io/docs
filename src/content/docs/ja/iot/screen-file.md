画面はお客様のものであり、ファイルとして持ち運ばれます。あるインストールからダッシュボードをエクスポートして別のインストールにインポートすると、レイアウトもタグ名もテキストも、HotLoop のコードには何も残りません。同じファイルが HotLoop IoT、Edge、Gateway で動くのは、3 つが同じダッシュボードのセットを実行するからです([ダッシュボード](/ja/iot/dashboards/))。

Edge Relay には UI も画面もありません。Flow のダッシュボードはそのフローの一部で、フローには独自のインポートとエクスポートがあります。HotLoop for CODESYS の画面は Edge の画面です。

## 使い方

ダッシュボード画面で、**エクスポート**(表示中のダッシュボードの編集の隣)を押すと `<id>.hotloop-screen.json` が保存されます。**インポート**(新しいダッシュボードの隣のバーにあります)はファイルを読み、必要なものと、ここにないものを伝え、ないタグ、デバイス、エンティティ、スクリプト、レシピをそれぞれ存在するものに対応付けさせ、もう一度確認して保存します。インポートには `dashboards.write` が必要なので、管理者の作業です。エクスポートには `dashboards.read` が必要で、対象は表示されているダッシュボードに限られます。

API では [`GET /api/dashboards/{id}/export`](/ja/iot/api/#get-apidashboardsidexport) と [`POST /api/dashboards/import`](/ja/iot/api/#post-apidashboardsimport) で、画面が呼び出すのはこれです。インポートは、同じダッシュボードを作るときに拒否される内容を保存することはありません。

## ファイル

UTF-8 の JSON で、最大 4 MiB です。

```json
{
  "format": "hotloop-screen",
  "formatVersion": 1,
  "exported": { "product": "edge", "version": "4.22.1", "at": "2026-11-19T16:00:00Z" },
  "screen": {
    "id": "line-2",
    "name": "Line 2",
    "kind": "cards",
    "roles": ["operator", "admin"],
    "homeFor": ["operator"],
    "screens": ["line-2-panel"],
    "position": 1,
    "cards": [
      { "id": "temp", "type": "gauge", "title": "Zone 1", "w": 3, "h": 3, "config": { "tag": "press-01/Zone1_Temp" } }
    ]
  },
  "requires": {
    "tags": [ { "key": "press-01/Zone1_Temp", "dataType": "float", "unit": "C", "writable": false } ],
    "entities": [], "scripts": [], "recipes": [], "devices": [], "equipment": []
  }
}
```

**`format` と `formatVersion`。** `format` は常に `hotloop-screen` です。`formatVersion` は 1 から始まる整数です。HotLoop は自分のバージョンとそれ以前を読み、それより新しいものは、ファイルのバージョンと自分が読めるバージョンを示して拒否します。ファイルにフィールドを追加すると新しいバージョンになります。リーダーは知らないフィールドを拒否し、黙って捨てられたフィールドは拒否よりも悪いからです。これはバージョン 1 です。

**`exported`。** どの製品とバージョンが、いつ書いたかです。ファイルを読む人のためのものです。これで何かが決まることはありません。HotLoop が画面を表示できるかはカードの種類で決まり、未知のカードの種類は名前を挙げて拒否されます。

**`screen`。**ダッシュボードAPIが保持するままのダッシュボードで、インストール自体の管理項目（`version`、`updatedBy`、`createdAt`、`updatedAt`）は除きます。`description`は空なら省かれます。カードは読む順に並び、それぞれサイズ（12列のうちの`w`、行数の`h`）と`config`を持ち、[ダッシュボード](/ja/iot/dashboards/#カード)が各タイプを説明しているとおりです。レイアウトはそれだけです。カードの流れであり、ピクセル座標はありません。symbolsカードは、自分のページにシンボルをピクセル単位で置き、それはconfigの中にあり、配管（どのシンボルのどの接続点を何とつなぐか、どの媒体か、どのタグで流れるか）もその隣のconfigにあります。経路はファイルに入りません。画面が開かれるたびにページが計算し直すので、P&IDは出ていったとおりの姿で戻ってきます。

**アセットは中に入っています。** マップカードの平面図とシンボルカードの背景は、カードの `config` 内の base64 PNG データ URL なので、ファイル 1 つが画面全体であり、それを送ることは画像も送ることです。上限はダッシュボードのもので、画像 1 枚あたり 700 KB、画面 1 つあたり 2 MiB です。

**`requires`。** 画面が着いた先のインストールに必要とするものを、カードから計算したものです。画面が読み取るすべてのタグ(エクスポート元での型と単位、ボタンや設定値がそこに書き込むかどうかを含む)と、カードが挙げるエンティティ、スクリプト、レシピ、デバイス、設備の ID です。人と、インポート前に確認したいツールのためのものです。インポートはカードから再計算し、このブロックを決して信用しません。ファイル内のタグの型が着いた先のタグと違う場合は警告です。

**ウォールボードはエクスポートされません。** それはインストールにピン留めされたゲージであり、レイアウトではありません。エクスポートすると `400` になり、`kind` が `wall` のファイルは拒否されます。

**割り当て。** `roles`、`homeFor`、`screens`、`position` は、画面が出たとおりに戻るようにファイルに入っています。これらは 1 つのインストールに最も結び付いた部分でもあります。パネル名はインストール上の 1 つのダッシュボードに属し、ロールにはホームが 1 つあります。インポートはこれらを適用し、このインストールがすでにその画面名やそのロールのホームを別のダッシュボードに与えている場合は、そう知らせます(`assignment`)。**割り当てをスキップ**すると `screens` と `homeFor` を外し、`roles` は残します。

## インポート

チェックはこの順に行われ、すべてに合格するまで何も保存されません。

1. **ファイル。** JSON、正しい `format`、このビルドが読めるバージョン、知らないフィールドがないこと、種類が `cards` であること。
2. **ファイルへの変更。** 新しい ID または名前、割り当てなし、そして**対応付け**です。`tags`(キー全体からキー全体へ。ファイルがタグを指す名前のまま、またはデバイスが移った後の読み方で)、`devices`(ID から ID へ。`tags` の対応付けにないすべてのタグのデバイス部分も移るので、画面を 1 台の PLC から別の PLC へ移すのは 1 項目です)、`entities`、`scripts`、`recipes`、`equipment`(ID は作られた場所でしか意味を持たない数値なので、1 つずつ対応付けます)。トレンドの凡例テキストはタグと一緒に移ります。どのカードも使わなかった対応付けの項目は警告です。何もしなかった対応付けこそが、画面が古いものを指したままになる原因だからです。
3. **ダッシュボード自身のルール。** ID、名前、すべてのカードの config、サイズ、バイト上限を、保存される形で確認します。
4. **カードが挙げるすべて、例外なし。** ないタグ、エンティティ、スクリプト、レシピ、デバイス、設備の ID は、最初の 1 つだけでなくすべて一覧にされるので、1 回で何を対応付けるべきか分かります。書き込み可能でないタグへのボタンや設定値は `writable` です。タグの範囲を外れたボタンの値や設定値の限界、存在しないロールは `screen` です。
5. **ID と割り当て。** 使用中の ID は `exists` で、**置き換え**を求めた場合は例外です。置き換えは、そのダッシュボードの現在のバージョンの上に保存します(確認している間に行われた保存は上書きではなく `409` になります)。

ドライランはこれをすべて行い、何も保存しません。インポートはダッシュボードに `config` イベントとして記録されます。誰が、どの製品とバージョンから、カード何枚かです。

## 画面を移す

最初のインストールでエクスポートします。2 つ目のインストールでは、画面が読み取るデバイスとタグがあることを確認してください(それらにはプラントのものであるアドレスが含まれるので、画面ファイルには含まれません)。インポートします。タグ名が違う場合はダイアログで対応付け、違うのがデバイスだけならデバイスを対応付けます。画面は、2 つ目のインストールで最初のインストールにあったとおりに開きます。

## CODESYS のビジュアライゼーション

同じインポートが CODESYS のビジュアライゼーション(IDE のネイティブエクスポート)を読み、そこから画面を作り、省いたものを伝えます。[CODESYS の画面をインポート](/ja/iot/codesys-screen-import/)を参照してください。

## バージョン 1 にないもの

画面が読み取るデバイスとタグ(アドレスは画面のものではなくプラントのもの)、ウォールボード、1 つのファイルに複数の画面、ファイルへの署名です。ファイルは平文の JSON です。送られてきたファイルは、インポートする前に読んでください。
