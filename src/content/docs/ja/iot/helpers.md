ヘルパーは、PLC ではなくプラントの人が持つ値です。「ライン 2 は段取り替え中です。」「今日のバッチ目標は 1,250 kg です。」「B シフトが稼働中です。」「前回のリセット以降、12 個を廃棄しました。」「パージはあと 9 分です。」これらはどれもレジスタには入っていませんが、ルールや画面が知る必要があるのはまさにこうした内容です。

HotLoop には 7 種類のヘルパーがあります。ヘルパーは他と同じエンティティです。`entity_id`、状態、属性、サービスを持ち、設備ツリーに置かれ、`/api/states`、エンティティ画面、MCP の `list_entities`、オートメーションの状態トリガーに現れます。違うのは値の置き場所です。値は HotLoop がデータベースに保持し、**ヘルパーのどのサービスもタグには書き込みません**。

## 7 種類

| ドメイン | 状態 | オプション | サービス |
|---|---|---|---|
| `input_boolean` | `on` / `off` | `initial` (true/false)、`restore` | `turn_on`、`turn_off`、`toggle` |
| `input_number` | 数値、`"1250"` | `min`、`max` (どちらも必須)、`step` (既定値 1)、`mode` (`slider` または `box`)、`initial`、`restore`、`unit_of_measurement` | `set_value {value}`、`increment`、`decrement` |
| `input_select` | 選んだ項目 | `choices` (必須、最大 100)、`initial`、`restore` | `select_option {option}`、`select_next {cycle}`、`select_previous {cycle}` |
| `input_text` | テキスト | `max_length` (既定値かつ上限 255)、`pattern`、`initial`、`restore` | `set_value {value}` |
| `input_counter` | 整数 | `initial` (既定値 0)、`step` (既定値 1)、`min`、`max`、`restore` | `increment`、`decrement`、`reset`、`set_value {value}` |
| `timer` | `idle` / `active` / `paused` | `duration_sec` (必須、1 秒から 7 日)、`restore` | `start {duration}`、`pause`、`cancel`、`finish` |
| `schedule` | `on` / `off` | `schedule` (必須) | なし: 時計に従います |

カウンターは `counter` ではなく `input_counter` です。`counter` はすでに、リセットするとタグに書き込む PLC の複合エンティティであり、これまでどおりのままです。

すべてのオプションはヘルパーの保存時に検査され、`initial` は他のすべてのオプションと照合されます。0 から 100 の `input_number` が 150 から始まる設定は、100 で開始されるのではなく拒否されます。ドメインが受け付けないオプションは、黙って無視される設定ではなくエラーです。ヘルパーのオプション(`initial`、`restore`、`choices`、`duration_sec`、`mode`、`schedule`)は、同じ理由で他のすべてのドメインで拒否されます。

## 作成

ヘルパーを作成できるのは管理者です(`entities.write`)。エンティティ画面で、新しい設備の隣にある**新しいヘルパー**を使います。API では次のようにします。

```
POST /api/helpers
{"name": "Batch target", "domain": "input_number", "unit_of_measurement": "kg",
 "options": {"min": 0, "max": 5000, "step": 50, "initial": 1000}}
```

`entity_id` は、指定しなければ名前から作られます(`input_number.batch_target`)。`PUT /api/helpers/{entity_id}` で名前、アイコン、単位、オプションを変更し、`DELETE /api/helpers/{entity_id}` で値ごと削除します。API 全体は [HTTP API](/ja/iot/api/#ヘルパー)にあります。

ヘルパーの現在の値がオプションの範囲外になる変更は拒否されます。範囲を値より狭くする、選択中の項目を削除する、といった場合です。先に値を設定するか、その値を含むオプションを選んでください。値が、合わせるために動かされることはありません。

## 設定

`helpers.write` を持つ人は誰でもヘルパーを設定できます。オペレーターはこの権限を持っています。シフトの選択や廃棄数のカウントは構成ではなく運用だからです。閲覧者は持っていません。ヘルパーはタグに書き込まないので、`values.write` ではありません。

ヘルパーの設定は、他のすべてのエンティティが受け付けるのと同じ、エンティティサービスの呼び出しです。

```
POST /api/services/input_counter/increment   {"entity_id": "input_counter.scrap", "reason": "short shot"}
POST /api/services/timer/start               {"entity_id": "timer.purge", "duration": "0:15:00"}
```

応答はヘルパーの現在の状態を返します。`{"call_id": "...", "state": "13", "writes": []}`。`?dry_run=true` も使え、何も変更せずに、実際の呼び出しと同じ内容で応答します。

エンティティ画面では、ヘルパーは専用のタイルを持ち、他のタイルにまとめられることはありません(まとめる基準になるタグがありません)。`helpers.write` を持つ人向けの操作もあります。すべての変更は、他のコマンドと同様に、まず理由を添えて確認されます。

MCP に新しいツールはありません。`list_entities` がヘルパーを見つけ、`get_states` が読み取り、`call_service` が設定します。エージェントがヘルパーを変更できるのは `HOTLOOP_ALLOW_WRITES` が有効なデプロイだけで、これはタグへの書き込みに必要なのと同じスイッチです。ヘルパーは設備を動かしませんが、ルールが動作する基準です。エージェントが段取り替えのスイッチを切り替えれば、段取り替えルールが行うことが何であれ、それを開始することになります。

## 拒否され、丸められることはありません

ヘルパーが受け付けない値は拒否され、何も変わりません。

- `min`..`max` の範囲外、または `step` に合わない数値(`min` から数えます)
- `max` を超える `increment`、`min` を下回る `decrement`(上限で止まるのではなく拒否されます。「上限で停止」は誰も求めていない値だからです)
- 選択肢にない項目、`cycle: false` で最後の項目を超える `select_next`
- `max_length` より長いテキスト、または `pattern` に一致しないテキスト(テキスト全体が一致する必要があります)
- 整数でない、またはカウンターの `min` や `max` を超えるカウント
- 動いていないのに一時停止、アイドルなのにキャンセルや終了、または 1 秒未満や 7 日を超える時間での開始
- 無効なヘルパー、`helpers.write` を持たない呼び出し元、MCP の書き込みが無効なエージェント

拒否はすべて、ヘルパーに対する警告としてシステムログ(`GET /api/events`)に記録され、誰が要求したか、なぜ拒否されたかが、アラームの確認拒否とまったく同じように残ります。リクエスト自体の誤り(サービスが受け付けないフィールド、数値のところに `"50"` を入れるなど)は呼び出し側のエラーで、400 で応答し、何も変更せず何も記録しません。

## 変更の記録先

すべての変更は、ヘルパーに対するシステムログの 1 行として残ります。誰が、何から何へ、呼び出し id、どこから来たか、理由があればその理由です。

```
otto   input_counter.increment: 12 -> 13; reason: short shot
system timer finished: active -> idle, due at 2026-09-27T21:10:00Z
```

この行は値と同じトランザクションで書き込まれるため、行のない変更も、変更のない行も存在しません。

状態の変更は、同じトランザクション内で、同じ実行者、出所、呼び出し id とともに[ログブック](/ja/iot/logbook/)の 1 行にもなります。変更を行ったプロセスがどれであれ、そのプロセスが書き込むので、エージェントが `--mcp-stdio` 経由で行った変更も記録され、記録は 1 回だけです。ヘルパーの行にレート制限はありません。どの行も誰かが何かを決めた記録だからです。状態をそのままにする呼び出し(すでにその値になっている数値を同じ値に設定するなど)は、何も変わっていないため、システムログにはありますがログブックにはありません。

## 再起動

ヘルパーは再起動しても値を保ちます。Gateway が戻ってきたとき、シフトは B のまま、カウンターは 13 のままです。毎回最初から始めたいヘルパー(「前回の再起動以降」のカウンター)には `restore: false` を設定してください。Gateway は起動時にそれを初期値に戻し、その旨をログに残します。これを行うのは Gateway 自身だけです。稼働中の Gateway の隣でエージェントが起動した `--mcp-stdio` プロセスは同じヘルパーを持ってすべての変更を受け取りますが、何もリセットしません。エージェントが接続したという理由でプラントの値をリセットするのは不合理だからです。

## タイマー

タイマーは壁時計で動きます。10 分で開始すれば、その間に何があっても 10 分後に終わります。2 分かかった再起動があれば、残りは 8 分です。一時停止中のタイマーは、何回再起動しても残り時間を保ったまま一時停止のままで、`start` で再開します。

**HotLoop が動いていない間に**期限が来たタイマーは、HotLoop が次に起動したときに `idle` に戻り、`finished_late_at` に本来の期限の時刻が設定され、ログに警告が残ります。**そのために何かが発火することはありません。**そのタイマーがアイドルになるのを待つルールは実行されません。起動後にエンジンが最初に見るのは変更ではなく基準値だからです。タイマーが計っていたもの(パージ、硬化)は、ずっと前に起きたか、まったく起きなかったかのどちらかで、今になって遅れて頼まれもせず実行するのは、見逃したと伝えるより悪い結果になります。`finished_late_at` を確認して判断してください。

タイマーはインターロックではありません。データベースとネットワークを経由した、プロセスの時計で動き、精度は秒単位、通常はミリ秒単位です。時間どおりに止まらなければならないものは PLC に置いてください。

## スケジュール

スケジュールは、ブロックの内側でオン、外側でオフになります。

```json
{"schedule": {
  "mon": [{"from": "06:00", "to": "14:00", "data": {"crew": "A"}},
          {"from": "14:00", "to": "22:00", "data": {"crew": "B"}}],
  "fri": [{"from": "22:00", "to": "06:00", "data": {"crew": "C"}}]
}}
```

- 曜日は `mon` から `sun` です。時刻は `HH:MM` または `HH:MM:SS` で、`24:00` は一日の終わりです。
- `to` が `from` より早いブロックは、日付をまたぎます。金曜の 22:00 から 06:00 は、土曜の 06:00 までオンです。
- 接しているブロックは、ひとつながりのオンの区間になります。重なるブロックは、どのデータを使うかが推測になるため拒否されます。
- ブロックがオンの間は、その `data` がエンティティの属性(`crew: "B"`)に入り、`next_event` が次にスケジュールが変わる時刻を常に示します。
- スケジュールはサイトのタイムゾーン(`HOTLOOP_SITE_TIMEZONE`)の壁時計で読まれます。06:00 に始まるシフトは、時計が切り替わる日でも 06:00 に始まるからです。時計が進む夜は、存在しない 1 時間はオンになりません。時計が戻る夜は、2 回ある 1 時間は 2 回ともオンです。

## 複数のプロセス

すべての変更は Postgres の `NOTIFY` で通知され、ヘルパーを持つすべてのプロセスが受け取ります。あるプロセスで設定したヘルパーは、1 回の往復のうちに他のすべてのプロセスで新しい値になり、ひとつのプロセスで作成または削除したヘルパーは他でも現れたり消えたりし、`PUT /api/helpers/{entity_id}` による変更も同じように反映されます(`PUT /api/entities/{entity_id}` による変更は、どのエンティティとも同じく、他のプロセスの次のレジストリ同期で届きます)。すべての書き込みは行のリビジョンを条件とするため、2 つのプロセスが同じカウンターを同時に数えてもカウントが失われることはなく、両方が持つタイマーはどちらか一方だけが終了させます。

## バックアップ

ヘルパーはすべてのバックアップに含まれます。構成はエンティティとともに、値はリビジョンを含めて `helper_state` に入っています。復元されたプラントは、持っていたシフト、目標、カウントとともに戻り、動いていたタイマーは壁時計に従って動き続けます(その間に期限が来ていた場合は、前述のとおりアイドルで遅延の印が付きます)。

## オートメーションでの使い方

ヘルパーは、ルールが動作の基準にし、ルールが設定する対象です。

```json
{"triggers": [{"type": "state", "entityId": "input_boolean.changeover", "to": "on"}],
 "actions": [{"type": "call_service", "params": {"entityId": "number.line_2_speed_sp",
   "service": "number.set_value", "data": {"value": 0}}}]}
```

ルールによるタグへの書き込みは、他の書き込みと同じように、ルールを実行者として書き込みゲートを通ります。条件では `states['input_select.shift'] == 'B'` が使え、ルールはスイッチを操作するのと同じように、`call_service` でヘルパーを設定できます。
