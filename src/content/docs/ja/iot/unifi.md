工場のネットワークも設備です。PLC が応答しなくなったとき、最初の疑問は「PLC の問題か、それとも接続先のスイッチポートの問題か」であり、これまでその答えは誰かのスマートフォンの UniFi アプリの中にありました。そこで HotLoop は UniFi コンソールそのものを読み取ります。すべてのスイッチ、すべてのポート、PoE の消費電力、WAN リンク、サイトの状態を通常のタグとして取り込みます。そのため、アラーム、トレンド、エンティティ、オートメーション、OPC UA、MCP は、UniFi の存在を知らなくてもそのタグ上で動作します。

ここでは、ドライバー、その上で動く OT の監視、画面、イベントストリーム、最初のコマンド(U1 から U5、[ロードマップ](/ja/roadmap/)を参照)を説明します。**ネットワークを読み取るだけで、人がそのためにタグを有効にしたときにのみ変更します。** すべてのタグは読み取り専用で作成されます。コマンドにあたる少数のポイント(後述の「コマンド」)は、他のタグと同様に書き込みゲートを通ります。誰かがそのタグを書き込み可能にするまで何も送信されず、View Only のコンソールアカウントはコンソール自身が拒否します。コマンド以外のすべてには、View Only のアカウントで使えます。

## コンソールを追加する

HotLoop のデバイス 1 台は**1 つのコンソールの 1 つのサイト**です。Cloud Gateway とその背後の Express は 2 つのコンソールなので、デバイス 2 台、ログイン 2 つになります。各コンソールに独自のローカルアカウントがあるためです。

1. **コンソールにローカルアカウントを作成します。** Settings、Admins & Users、Add Admin の順に進み、**Restrict to Local Access Only** にチェックを入れ、ロールを **View Only** にします。Ubiquiti のクラウドアカウントはアプリ以外ではログインできません。MFA が必要で、スクリプトに対してコンソールは 403 を返します。当社では `hotloop-ro` という名前にしています。
2. **デバイスを追加します。** プロトコルは `unifi`、アドレスはコンソールの URL です。UniFi OS で動作するコンソール(Cloud Gateway、Dream Machine、UniFi OS Server)は `https://host`、セルフホストの Network Application は `https://host:8443` です。ポーリング間隔は 15 秒が目安です。ドライバーは設定値にかかわらず、1 つのコンソールを 10 秒に 1 回より頻繁には読みません。
3. **フィンガープリントなしで保存します。** 最初の接続は意図的に失敗し、コンソールが提示した証明書のフィンガープリントが表示されます。ご自身のコンソールであることを確認し(コンソールに証明書が表示されます。または `openssl s_client -connect host:443` の出力を `openssl x509 -pubkey -noout | openssl pkey -pubin -outform der
   | sha256sum` に渡しても同じ値になります)、`certFingerprint` に貼り付けて保存します。
4. タグは次のポーリングで自動的に作成されます。詳しくは以下を参照してください。

UniFi デバイスは、HotLoop にパスワードを暗号化するキー(`HOTLOOP_SECRET_KEY_FILE`。チャートが自動で設定します)がある場合にのみ保存できます。[バックアップと復元](/ja/iot/backup/#device-credentials-and-the-secret-key)を参照してください。

| オプション | 既定値 | 内容 |
|---|---|---|
| `site` | `default` | サイトの短い名前で、コンソールの URL に出てくるものです。`default` はすべてのコンソールの最初のサイトです |
| `username`, `password` | 必須 | ローカルアカウントです。パスワードは API 経由では書き込み専用で、データベース内では暗号化されます |
| `certFingerprint` | なし | コンソールの証明書の公開鍵の SHA-256 を 16 進数で指定します。コロン、スペース、大文字は問題ありません |
| `caFile` | なし | 正式な証明書を持つコンソール向けに、ピンの代わりに CA を信頼します |
| `insecureSkipVerify` | `false` | あらゆる証明書を信頼します。検証用のベンチ向けで、工場では使わないでください |
| `clientTimeoutSec` | `90` | コンソールがクライアントを最後に確認してから、どのくらいの間ネットワーク上にいるとみなすかを指定します。下限は 30 です。[クライアント](#クライアントot-ネットワークplc-の接続先)を参照してください |

### 証明書をピン留めする理由

コンソールは自己署名証明書付きで出荷されるため、手っ取り早いのは検証を省略することです。メーターを読むだけならそれでも構いません。しかし、工場のネットワーク全体を見渡せて、書き込み PR 以降はポートの電源を入れ直すこともできるログインでは許されません。ピン留めされたコンソールが別の証明書を提示した場合、**ユーザー名やパスワードを送る前に** TLS ハンドシェイクで拒否され、エラーには両方のフィンガープリントが示されます。ピンは公開鍵に対するものなので、同じ鍵で証明書を再発行するコンソールは引き続き動作します。

黙って信頼する「trust on first use」はありません。証明書を信頼することに意味があるのは人がそれを見ているときだけであり、そのときに信頼が行われます。

## ログイン:一度だけ、必要な場合以外は再ログインしない

点検のたびにログインすると、当社自身の Cloud Gateway が 429 を返してアカウントがロックされました。2 回です。そのため次のとおりにしています。

- **コンソールごと、プロセスごとにセッション 1 つ。** すべてのポーリングと、コンソール上のすべてのサイトが同じログインを使います。同じコンソールの 2 つのサイト用の 2 台のデバイスが同じアカウントを使う場合、セッションは 1 つです。
- **コンソールがセッションが失われたと伝えたとき(401)にのみ再ログインし**、一度に 1 つの呼び出し元だけで、何があっても**1 分に 1 回を超えません。** 1 分以内にセッションが 2 回切れると、その 1 分が過ぎるまでデバイスは不良として読み取られます。これが当社の望むトレードオフです。
- **拒否されたログインは再試行しません。** パスワードの誤り、クラウドアカウント、429 によるロックは、最低 5 分、コンソールの `Retry-After` がそれより長ければその分だけ待ち、デバイスのエラーにどれに当たるかが示されます。デバイスをオフにしてオンにしても再試行はできません。プロセスが覚えています。
- **コンソールを使う最後のデバイスが停止したときにログアウトします。** そのため、再起動してもコンソールにセッションが積み上がりません。
- **`--mcp-stdio` ヘルパーは決してログインしません。** すでにセッションを保持している Gateway の隣で動作しており、同じマシンからの 2 回目のログインはまさに 429 を招くためです。ヘルパー側では UniFi デバイスは停止したままに見え、実際には Gateway で動作しています。

## タグ

すべてのタグはドライバーが作成し、人が有効にするまで読み取り専用で、表示名ではなく MAC アドレスとポート番号で名前が付けられるため、UniFi アプリでスイッチの名前を変えても何も壊れません。`<mac>` は区切りなしの小文字のデバイス MAC、`<nn>` は 2 桁のポート番号です。

| タグ | 型 | 内容 |
|---|---|---|
| `d.<mac>.state` | テキスト | `connected`, `disconnected`, `pending`, `upgrading`, `provisioning`, `heartbeat_missed`, `adopting`, ... |
| `d.<mac>.online` | bool, connectivity | コンソールに接続中 |
| `d.<mac>.uptime_s` | int, s | 稼働時間 |
| `d.<mac>.cpu_pct`, `.mem_pct` | float, % | CPU とメモリ |
| `d.<mac>.temp_c` | float, °C | 温度(センサーを持つデバイスのみ) |
| `d.<mac>.clients` | int | このデバイス経由で接続しているクライアント |
| `d.<mac>.fw` | テキスト | ファームウェアのバージョン |
| `d.<mac>.wan<N>.up` | bool, connectivity | ゲートウェイ自身のヘルスチェック(`last_wan_interfaces`、次に `last_wan_status`)で WAN N が**稼働している**こと。WAN ブロックの `up`(設定済みの意味)ではありません。どちらも提供しないコンソールは不良として読み取られ、up になることはありません |
| `d.<mac>.wan<N>.latency_ms` | float, ms | 遅延。WAN が稼働している間のみ有効 |
| `d.<mac>.wan<N>.availability_pct` | float, % | ゲートウェイが報告する場合の、そのゲートウェイ自身のモニターによる可用性(期間は 1 日) |
| `d.<mac>.wan.active` | テキスト | トラフィックを運んでいる WAN。アップリンクの WAN が稼働していればそれ、そうでなければ最初に稼働している WAN、なければ `none` |
| `d.<mac>.wan.failover` | bool, problem | トラフィックが最初の WAN 以外を通っている状態。工場はバックアップ回線で動いています |
| `p.<mac>.<nn>.up` | bool, connectivity | ポートのリンク |
| `p.<mac>.<nn>.speed_mbps` | int, Mbit/s | リンク速度。リンクのないポートでは 0 で、これは正常な値です |
| `p.<mac>.<nn>.rx_bps`, `.tx_bps` | float, bit/s | トラフィック |
| `p.<mac>.<nn>.errors` | int | 受信エラーと送信エラーの合計 |
| `p.<mac>.<nn>.poe_w` | float, W, power | PoE の消費電力(PoE を供給できるポートのみ) |
| `p.<mac>.<nn>.poe_mode` | テキスト | `auto`, `off`, `pasv24`, `passthrough` |
| `site.<subsystem>.status` | テキスト | サイトの状態:`wan`, `www`, `lan`, `wlan`, `vpn` |
| `site.www.latency_ms` | float, ms | インターネットの遅延(報告される場合) |
| `site.network_version` | テキスト | コンソールが実行している Network のバージョン |
| `site.events_live` | bool, connectivity | コンソールのイベント用ウェブソケットが接続されています。0 は HotLoop がポーリングのみであることを意味し、失うのは速度だけです |
| `site.last_event` | テキスト | コンソールがサイトについて報告した最新のイベントで、コンソール自身の言葉のままです |
| `d.<mac>.last_event` | テキスト | そのデバイスに関する最新のイベント。最初のイベントが発生するまでは空です |

デバイスクラスはエンティティに引き継がれるため、ポートのリンクは接続状態のバイナリセンサーとして、PoE の消費電力は電力センサーとして、誰も設定しなくても現れます。

**タグは自動的に追加され、自動的に消えることはありません。** 来週アダプトしたスイッチは、次のポーリングで同じセッションのまま、何も再起動せずにタグとして現れます。取り外されたスイッチは `online` が 0 と読み取られ、そのポートは品質不良になるため、そのスイッチに設定したアラームは消えずに状況を知らせます。タグの削除は人が決めることです。誰かがオフにしたタグはオフのままです。ドライバーに決定権はありません。

アダプトされたデバイスのみがタグを受け取ります。誰かが接続したものの誰もアダプトしていないスイッチは、まだ工場のネットワークの一部ではありません。コンソールが報告しないポイントは不良として読み取られ、作り出した 0 になることはありません。PoE の消費電力を報告しないスイッチは、その `poe_w` タグが不良として読み取られます。

Edge Relay もコンソールをポーリングできます。デバイスファイルで宣言されたタグを読み取りますが、タグを保持する場所がないため追加はしません。

## コマンド

5 種類のポイントがコマンドです。それぞれ他のタグと同様に読み取り専用で作成され、誰かが書き込み可能にするまで何もしません。これらのコマンドには、HotLoop がログインに使うアカウントがローカルの Administrator である必要があります。View Only ではコンソールが HTTP 403 を返し、HotLoop がその旨を伝え、何も変更されません。

| タグ | 書き込み | コンソールの動作 |
|---|---|---|
| `d.<mac>.locate` | `true` または `false` | オフにするまでデバイスの LED を点滅させます。コンソールが返す値を読み戻します。 |
| `d.<mac>.restart` | `true` | デバイスが次に通信したときに再起動します。`false` は何もしません。読み取り値は 0 です。 |
| `p.<mac>.<nn>.power_cycle` | `true` | ポートの PoE をオフにしてからオンにします。`false` は何もしません。読み取り値は 0 です。 |
| `w.<id>.enabled` | `true` または `false` | 無線ネットワークをオンまたはオフにします。送信されるのはそのフィールドだけなので、パスフレーズなどほかの設定はそのまま残ります。`<id>` はコンソールがそのネットワークに付けた ID で、名前を変えても変わりません。 |
| `c.<mac>.blocked` | `true` または `false` | 監視対象のクライアントをネットワークからブロックするか、再び許可します。このポイントは、コンソールが確認したことのあるクライアントに対して存在します。 |

電源の入れ直しは工場に害を及ぼすことがあります(オートメーションが 2 分ごとに PLC を入れ直すと、その電源が焼けます)。そのため、誰が要求しても 2 つのルールが適用されます。ポートは 15 分に最大 1 回しか入れ直されません(最後の入れ直しの時刻はデータベースに保存されるので、再起動しても忘れられず、時刻を確認できない入れ直しは拒否されます)。そして、ネットワークを運んでいるポートは決して入れ直されません。これはアップリンク、およびコンソール自身のトポロジーで他の機器がぶら下がっているすべてのポートを指し、5G バックアップに給電するポートもその 1 つです。拒否された場合は、どのルールによるものかが示されます。コンソール自身が拒否したコマンドは、クールダウンを消費しません。

## クライアント、OT ネットワーク、PLC の接続先

2 つの役割があり、どちらも読み取り専用です。

**どこに接続されているか。** PLC が応答しなくなったとき、最初に知りたいのは PLC の問題かスイッチポートの問題かです。HotLoop のデバイスをネットワーク上のクライアントに一度リンクしておけば、誰かが UniFi アプリを開く前に、そのドロワーに「USW Lite 8 PoE ポート 5、リンクダウン」と表示されます。このリンクによって、コンソールのデバイス上にクライアントのタグも作られるため、止まった Modbus の値の隣で、ポートの状態がトレンドとアラームになります。

**SCADA ネットワークに何があるか。** ネットワークを OT に設定し、そこに属するものを承認すると、それ以外のものが現れたときに、それを名指しするアラームが上がります。誰かが午前 2 時に SCADA スイッチにノートパソコンを接続すれば、午前 2 時にわかります。

### IP をキーにしません

コンソールのクライアント一覧は遅れます。そのため次のとおりにしています。

- **クライアントは MAC で決まります。** リンクでは、PLC について知っているのは IP なので IP でクライアントを提案しますが、人が一度確認すれば、それ以降のキーは MAC です。IP タグには、それがコンソールの見解であることが示されます。
- **オンラインは「一覧にある」ことではありません。** クライアントは、コンソールが `clientTimeoutSec`(90 秒)以内に確認していて、**かつ**有線の場合はそのスイッチポートにリンクがあるときにオンラインです。ポートが速い側です。ケーブルを抜くと、一覧がまだ追いついていなくても、次の読み取りでポートはダウンと読み取られます。

### デバイスをリンクする

デバイスのドロワーを開きます。HotLoop が読み取っている UniFi コンソールがそのデバイスの IP でクライアントを一覧しているなら、Network セクションがそれを提案し、管理者が **Link** をクリックします。手がかりとなる IP がない場合(名前で指定されたデバイス)は、MAC でリンクします。または API の `PUT /api/devices/{id}/network` を使います。[HTTP API](/ja/iot/api/#put-apidevicesidnetwork) を参照してください。

リンクされたデバイスのクライアントにはタグとアラーム **「PLC-07 off the network」** が作られます。優先度は 1 で、再起動中の PLC で誰も呼び出されないように、オンディレイは 120 秒です。

### OT ネットワークと既知リスト

ネットワークを OT に設定し(`PUT /api/unifi/{id}/networks/{network}` に `{"ot": true}`)、そこにあるものを承認します。現在の状態のまま 1 回の呼び出し(`POST .../accept-all`)で承認するか、デバイスを 1 台ずつ承認します。設定すると、`n.<network>.unknown` に優先度 1 のアラーム **「Unknown device on SCADA」** が作られます。最新の未知の接続機器は、MAC、自称する名前、IP、接続してきたスイッチポートまたは SSID とともに `n.<network>.unknown_last` に示されます。

既知のデバイスは**監視**(`"watch": true`)できます。リンクされたデバイスと同じタグと同じネットワーク離脱のアラームが作られます。PLC は監視対象にします。許可されているが出入りする保守用のノートパソコンは、既知ではあっても監視対象にしません。そうしないと、離れるたびに誰かが呼び出されます。

アラームは通常のアラーム定義です。保留、確認応答、Discord への送信、遅延の編集ができます。監視、リンク、OT の設定を外すと、HotLoop はそのために作ったアラームも取り除くため、誰も読まなくなったタグがアラームを開いたままにすることはありません。管理者が手で作成したものには決して触れません。

この記録は HotLoop のものであり、HotLoop 自身のデータベース(`unifi_networks`、`unifi_known`、`unifi_links`、すべてバックアップに含まれます)に保存され、コンソールには保存されません。変更は、動作中のドライバーの次の読み取りで、すでに持っているセッション上で反映されます。デバイスは再起動しません。再起動するとログアウトされ、1 分に 1 回というログインの上限により 1 分間入れなくなるためです。

### タグ

| タグ | 型 | 内容 |
|---|---|---|
| `n.<network>.clients` | int | 上記の判定でオンラインである、現在ネットワーク上にいるクライアント。すべての LAN ネットワークに 1 つ作られます |
| `n.<network>.unknown` | int | OT ネットワーク上で、既知リストにないオンラインのクライアント |
| `n.<network>.unknown_last` | テキスト | そのうち最新のものを文章で表示します。該当がなければ空です |
| `c.<mac>.online` | bool, connectivity | ネットワーク上の監視対象またはリンク済みのクライアント |
| `c.<mac>.ip` | テキスト | コンソールが最後に確認した IP |
| `c.<mac>.sw_mac`, `.sw_port` | テキスト, int | 有線クライアントが接続しているスイッチとポート。ケーブルを抜いた後も保持されます。重要なのは、どこに*あったか*です |
| `c.<mac>.port_up` | bool, connectivity | そのポートのリンク。スイッチ自体がコンソールから外れているときは誰にもわからないので、不良になります |
| `c.<mac>.last_seen_s` | int, s | コンソールが最後に確認してからの秒数 |

`<network>` はコンソール上のネットワーク ID なので、アプリで SCADA の名前を変えても何も壊れません。OT に設定したネットワークがその後コンソールで削除された場合は、その理由とともに不良として読み取られ、黙って 0 になることはありません。コンソールが一度も確認したことのないクライアントは `online` が 0 で、残りは不良として読み取られ、その旨が示されます。

`c.*` タグを受け取るのは、監視対象とリンク済みのクライアントだけです。300 台のスマートフォンが出入りするゲスト用ネットワークで、タグのセットが 300 個できることはありません。

### コンソールに問い合わせずに読み取る

`GET /api/unifi/{id}/networks`、`/clients`、`/known`、ドロワー、MCP ツール `find_network_client` は、いずれもドライバーの直近の読み取り結果を読みます。どれも独自のリクエストを送らないため、画面を開いたままにしても、エージェントがループで問い合わせても、コンソールに負荷はかからず、429 の原因にもなりません。その裏返しとして、ログインしない `--mcp-stdio` ヘルパーは、そのプロセスにコンソールの読み取りがないと伝えます。

## 画面

UniFi タブには 6 つのビューとコンソールの選択があります。表示される内容はすべてドライバーが直近にコンソールから読み取ったものなので、開いたままにしてもコンソールに負荷はかからず、429 の原因にもなりません。数秒ごとに HotLoop に問い合わせ直し、何かが変わったときにだけ再描画するので、誰かが隅までスクロールしたマップはそのままの位置に残ります。

- **概要。** コンソールごとに 1 枚のカードです。ゲートウェイのカードの最上部には WAN ストリップがあります。WAN ごとに 1 区画で、ゲートウェイ自身のヘルスチェックが稼働中と判断していれば緑、そうでなければ赤、トラフィックを運んでいるものは枠線で囲まれます。サイトがバックアップで動作しているときは、ストリップ全体が琥珀色になり、どの回線でいつからかが表示されます。この「いつから」は、HotLoop が最初にそのように読み取った時刻であり、ゲートウェイが切り替えた時刻ではありません。サイトがすでに 5G で動作しているときに起動した HotLoop は、自分の起動時点からと表示します。わからない時刻を表示することはありません。その下には、オンラインのデバイス、有線と無線のクライアント、ネットワークごとのクライアント、コンソールが見失ったデバイス、最新のイベントがあります。コンソールが何も伝えない WAN は灰色で「no liveness reported」と表示され、決して緑にはなりません。遅延を報告するすべての WAN には、数値の横に推移線があります。これはエンティティのタイルが描くものと同じ線で、そのタグ用の HotLoop 自身のバッファから取得しています。管理者はカードの下部で **Create the usual alarms** を使えます。[基本アラーム](#基本アラーム)を参照してください。
- **マップ。** ゲートウェイから左から右へ配置されます。毎回同じ方法で配置され(整然としたツリー、物理シミュレーションなし、同じ入力から同じピクセルを出力)、壁掛けボードでも揺れません。ケーブルはコンソール自身の `downlink_table` です。スイッチが別のスイッチに接続されているのは、コンソールがそう伝えているからにほかなりません。何にも接続されていると記載されていないデバイスは単独で置かれ、「no uplink listed」と表示されます。推測でゲートウェイにぶら下げて、PLC のネットワークがどこへ向かうかを間違えることはしません。有線のクライアントはコンソールが学習したスイッチとポートに、無線のクライアントはその AP と SSID に置かれ、カード上のチップに数が表示されます。デバイスをクリックすると、それより下流にないものがすべて薄くなり、サイドパネルに下流にあるもの、そのクライアント、そのデバイスが給電する Plant ツリーの系統が一覧されます。下にあるクライアントにリンクされた HotLoop のデバイスと、それぞれが配置されている設備パスです。マップは拡大縮小と移動ができます。2 本の指でピンチ、1 本の指でドラッグ、ctrl とスクロールまたはトラックパッドのピンチでポインター周辺を操作、あるいはプラス、マイナス、Fit のボタンで、マップ全体から最大 8 倍まで拡大できます。純粋な SVG なので、どの倍率でも鮮明で、画面が更新されても置いた位置のままです。デバイスの上で終わったドラッグでは、そのデバイスは選択されません。**Plant overlay** は、クライアントにリンクされた HotLoop のデバイスを、Plant ツリーの系統ごとの破線のボックスに入れて、ネットワークの右側に系統のパスをラベルとして表示します。それぞれに接続先のスイッチポートへのケーブル、ネットワークが示す状態(up、down、未確認)、HotLoop が示す状態が付きます。リンク済みでもどの系統にもないデバイスは「Not on the Plant tree」というボックスに入ります。一度オンにするとオンのままです。2 つのコンソールは 1 枚の図になります。HotLoop が読み取っている別のコンソールの機器をこのコンソールが有線クライアントとして一覧している場合、その機器は独自のサブツリーとともに破線で描かれ、「separate console」と表示されます。マップは現場資料用に SVG として書き出せます。
- **デバイス。** 表で、1 つをクリックするとそのフェースプレートが表示されます。ポートは前面パネルのように描かれ、小型スイッチは 1 行、24 ポートと 48 ポートは 2 行で、奇数ポートが偶数ポートの上に並びます。リンクありは緑、なしは灰色、**稼働していたのにダウンしたポートは赤**(HotLoop は監視を始めてから稼働していたことを覚えています)、無効なポートは破線、PoE の稲妻マーク(ワット数はポートのツールチップと詳細にあります)、アップリンクには矢印が付きます。ポートをクリックすると、そこにいるもの、接続されているもの、PoE モード、ワット数、トラフィックが、受信と送信の推移線とともに表示されます。コンソールが見失ったデバイスは、最後に報告した内容が最新ではないため、数値もポートのリンクも表示しません。
- **クライアント。** 名前、MAC、IP で検索でき、場所、コンソールが最後に確認した時刻、OT ネットワークでの既知か未知か、リンクされた HotLoop のデバイスが表示されます。管理者は行から未知のクライアントを承認できます。
- **ネットワーク。** ネットワークごとの OT スイッチと「現在の状態のまま承認」です。変更されるのは HotLoop の記録であり、コンソールではありません。
- **WiFi。** SSID、それぞれが送信中かどうか、どのネットワークにあるか、クライアントが何台かを表示します。コンソールがアカウントに無線ネットワークを見せない場合、画面は「存在しない」と主張せず、その事実を表示します。

その背後のルートは `GET /api/unifi/consoles`、`.../overview`、`.../topology`、`.../devices`、`.../wifi`、`.../events` で、[HTTP API](/ja/iot/api/)に記載されています。

### 基本アラーム

誰かがあらためて考える前に、工場がネットワークに用意しておきたいアラームで、コンソールが現時点で把握している内容から作られます。概要で **Create the usual alarms**(または `POST /api/unifi/{id}/starter-alarms`、[HTTP API](/ja/iot/api/)を参照)を押すと、次のものが作られます。

| アラーム | 対象 | 優先度 | オンディレイ |
|---|---|---|---|
| デバイスのオフライン | `d.<mac>.online`、アダプト済みのすべてのスイッチ、AP、ゲートウェイ | 2 | 60 秒。ファームウェアの再起動で誰も呼び出されないようにします |
| アップリンクのダウン | `p.<mac>.<nn>.up`、各デバイスが上位に接続されているポート | 1 | 10 秒 |
| バックアップ WAN 上のゲートウェイ | `d.<mac>.wan.failover`、WAN が 2 つ以上あるゲートウェイ | 2 | 30 秒 |
| 上限を超えた PoE ポート | `p.<mac>.<nn>.poe_w`、ワット数の上限を指定した場合のみ | 3 | 30 秒 |

これらは通常のアラーム定義です。保留、確認応答、Discord への送信、遅延や上限の編集、削除ができます。機器をさらにアダプトしたあとにもう一度押すと、新しい機器の分だけが追加され、手動または以前の操作ですでにアラームがあるタグには手を付けません。PoE のアラームは、HotLoop が選ぶ値ではなく、指定された上限を使います。当社が読み取るどのコンソールもポートの電力予算を知らせず、当社が推測した数値は誰かが信頼してしまう数値になるためです。「Unknown device on an OT network」と「a watched client off the network」はこのボタンに含まれません。これらは、ネットワークを OT に設定したときと、デバイスを監視またはリンクしたときに、意味を与える記録とともに作られます。

## イベント

コンソールのイベント用ウェブソケット(UniFi OS では `/proxy/network/wss/s/<site>/events`、セルフホストのアプリケーションでは `/wss/s/<site>/events`)は、他のすべてと同じセッションを使います。自分でログインすることはありません。401 で拒否されたハンドシェイクは読み取りと同じログインの上限を通り、拒否されたログインは再試行せずに待ちます。

**ポーリングは引き続き正となります。** イベントがタグを書き込むことはありません。イベントが行うことは次のとおりです。

1. 到着した瞬間に**ログブック**へ記録されます。コントローラー自身の文言(「Switch[...] was disconnected」)とそのキーも含まれます。スイッチが落ちたことは、次のポーリングが気づいた時点ではなく、発生した時点でタイムラインに載ります。イベントは、コンソール自身のデバイスではなく、そのイベントが関係するスイッチ、アクセスポイント、ゲートウェイの下に整理されます。コンソールはコントローラーが動いているマシンであり、落ちたものではないためです。クライアントだけを名指しするイベント(コンソールは誰が参加したかを伝えますが、どこかは伝えません)は、直近の読み取りでそのクライアントがいるスイッチまたは AP の下に整理されます。クライアントが新しい場合は、そのイベントが今要求した読み取りを最大 30 秒待ち、その読み取りにもなければコンソールの下に入ります。ログブックの **Where** フィルターは、工場側からイベントを見つけます。クライアントにリンクされた HotLoop のデバイス、コンソールがそのクライアントがいると伝えているスイッチ、そこからゲートウェイまでの、コンソール自身の downlink テーブルに基づくすべてのスイッチです。落ちたスイッチは、それが給電するすべての系統のタイムラインに現れ、給電しない系統には現れません。コンソール自体を指定する場合は、従来どおり動作します。`subject` がコンソールの id と等しいシステムログと、対象デバイスにコンソールを含めたログブックは、スイッチごとのものを含め、そのコンソールのすべてのイベントを返します。
2. 概要に表示されるログに入り、`site.last_event` と `d.<mac>.last_event` にも入るため、オートメーションがそれをトリガーにできます。
3. 次の読み取りをすぐに要求します。読み取りの最小間隔は 10 秒ですが、イベントがあると 5 秒に短縮されるため、タグとエンティティは最大 10 秒後ではなく次のポーリングで追いつきます。混雑した WiFi ネットワークでは、通りかかるスマートフォンごとにイベントが送られますが、そのたびにコンソールを読み取ることはありません。

コントローラーは、問題が起きたことを意味するイベント(`is_negative`:スイッチが接続を失うのは該当し、クライアントが切断するのは該当しません)に印を付け、それらはログブックで警告になります。それ以外はすべて情報であり、HotLoop が見たことのないキーも含まれます。

**ウェブソケットが切れても失うのは速度だけで、正確さは失いません。** 2 秒から最大 1 分までのバックオフで再接続します。ping を送り、90 秒間何も応答しないストリームは、ネットワークが何と言おうと切れているものとして閉じて開き直します。切れている間は、`site.events_live` は 0 と読み取られ、概要には理由とともに「polling only」と表示され、ポーリングはこれまでとまったく同じように続きます。
## 検証済みの内容

UniFi ドライバーと画面は、実際の UniFi Network Application と UniFi OS コンソールを相手に、View Only アカウントで読み取り専用で実行し、2026-11-17 には実機でも確認しました。ログインとその単一のセッション、デバイス、ポート、PoE、WAN、クライアントの各タグ、ライブのイベントストリーム、そしてそれらの上に構築された画面です。
