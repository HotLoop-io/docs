HotLoopは4.11.0から、独自のMQTTブローカーをプロセス内で動かせるため、1台構成の小さなHotLoopには追加でデプロイするものがありません。デフォルトでオン（`HOTLOOP_BROKER_ENABLED`）で、バイナリでもHelmチャートでも同じです。:1883で待ち受け、そのポートが機器上の別のブローカーに使われている場合は、組み込みブローカーは待機してログにそう記録し、HotLoopは起動します（`HOTLOOP_BROKER_LISTEN_ADDR`を空いているアドレスに設定するか、オフにしてください）。自分で選んだポートにバインドできない場合は、これまでどおりエラーです。すでにMosquittoやEMQXを動かしているデプロイには、これを向ける先がなく、すでにあるブローカーの隣に2つ目のブローカーを起動するのは、推測で決めてよい安全なデフォルトではありません。

## このブローカーがある理由

エッジパブリッシュ(Gateway が Sparkplug のエッジノードとして動作)とフリート管理(登録されたエッジリレーの追跡)は、どちらも `BrokerAddress` を介して MQTT ブローカーに*外向きに*接続し、自身でブローカーを実行したことはありません。環境にすでにブローカーがあるなら、既存の Mosquitto インスタンスでも、別の理由で HotLoop の隣で動いているものでも問題ありません。しかし、それが*唯一の*選択肢では問題があります。このプロジェクトは、工場が依存する可動部品の数を減らすために存在しており、Gateway 1 台のために Sparkplug ハブを用意するだけで 2 つ目のインフラを必要とするのは、裏口から可動部品を戻すことになるからです。

`HOTLOOP_BROKER_ENABLED=true` にすると、この同じプロセスが自身のアドレスで MQTT 接続を待ち受けます。エッジパブリッシュ、フリート管理、または外部のエッジリレーの `HOTLOOP_EDGE_PUBLISH_BROKER` は、いずれも `localhost:1883`(クラスター内では Gateway 自身の Service アドレス)に向けられます。

## 使う場合と使わない場合

**使う場合。** Gateway が 1 台、エッジリレーが数台、そしてヒストリアン、アラームエンジン、HTTP API とプロセスを共有する内蔵ブローカーが余裕をもって処理できるトラフィック量、つまりこのプロジェクト全体が想定する一般的なケースです。工場 1 つ、機器 1 台、最小限のインフラです。

**使わない場合。** 実規模の本番グレードのブローカーの代わりとしては使わないでください。複数の独立した Sparkplug ホストアプリケーション、非常に大きなファンアウト、サイト間のブリッジ、あるいはクラスタリング、水平スケーリング、ブローカー自身の専用運用ツール(詳細なメトリクス、動的 ACL、プラグインのエコシステム)が必要なワークロードは、いずれも Mosquitto、EMQX、その他の専用ブローカーを運用し、他の環境がすでにそうできるように、Gateway の `EdgePublishConfig`/`FleetConfig` をそちらに向ける十分な理由です。このパッケージはその用途と競合するものではありません。ブローカーが一切ない環境のためにあります。

## ログインと、それぞれが触れられる範囲

3 種類のログインが接続でき、同じ扱いではありません。

**HotLoop で作成したログイン**(Settings、MQTT、または [HTTP API](/ja/iot/api/) の `/api/broker/logins`)にはルールがあります。そのログインが発行できるトピックと購読できるトピックです。ルール内の `%u` はそのログイン自身の名前、`%p` はディスカバリープレフィックスです。プロファイルから始まり、その後は自由に編集できます。

| プロファイル | 発行 | 購読 | 用途 |
|---|---|---|---|
| `shelly` | `%u/#`, `shellies/announce` | `%u/#`, `shellies/command`, `%p/status` | Shelly Gen2 以降、ログイン名は MQTT トピックのプレフィックスと同じにします |
| `esphome` | `%u/#`, `%p/+/%u/+/config`, `esphome/discover/%u` | `%u/#`, `%p/status`, `esphome/discover` | ESPHome ノード、ログイン名はノード名と同じにします |
| `tasmota` | `tele/%u/#`, `stat/%u/#`, `tasmota/discovery/+/config`, `tasmota/discovery/+/sensors` | `cmnd/%u/#`, `cmnd/tasmotas/#` | Tasmota デバイス、ログイン名はそのトピックと同じにします |
| `zigbee2mqtt` | `%u/#`, `%p/#` | `%u/#`, `%p/status` | Zigbee2MQTT ブリッジ、ログイン名はそのベーストピックと同じにします |
| `integration` | なし | `#` | ダッシュボード、ヒストリアン、MQTT Explorer を使うあなた |
| `full` | `#` | `#` | 何でも、工場全体 |

Shelly のログイン名をそのトピックのプレフィックスと同じにすると、自分自身を通知し、自分として報告できます。それだけです。`cmnd/boiler/POWER` には発行できず、他のデバイスの名前でデバイスを通知することもできず、`#` を購読して工場を読むこともできません。ブローカーはすべての発行、すべての購読、購読者へ送り出されるすべてのメッセージを検査するため、巧妙なワイルドカードでルールを広げることはできません。last will も、クライアントの接続時に検査されます。ブローカーのライブラリは誰にも尋ねずに will を発行するため、発行を許されていない場所を指す will を持つログインは接続できません。そうでなければ、安価なプラグがボイラーに保持された `ON` を残して、自分で電源コードを抜けてしまいます。

ログインへの変更は、そのクライアントの次のパケットから有効になります。ログインを絞ると、接続中のデバイスはその時点でトピックを失い、ログインを削除すると、まだ接続しているクライアントは何もできず、再接続もできません。パスワードは、すべてのバックアップに含まれる `broker_logins` に bcrypt ハッシュとして保存され、API はどちらも返しません。

Zigbee2MQTT は例外です。1 つのブリッジが自身の無線上のすべてのデバイスを通知するため、そのプロファイルはプレフィックス配下のどこにでも発行できます。それがブリッジの役割であり、Discovered 画面に誰が何を通知したかが表示される理由です。

**`HOTLOOP_BROKER_USERS`** は `user:password` のペアの従来のリストです(最初のコロンだけが区切りなので、パスワードにコロンを含められます)。これらは 4.16 と 4.17 とまったく同じように、すべてのトピックで何でもできます。これは意図したものです。自分で書いたことのない ACL に Sparkplug のトラフィックが突然はじかれる工場へアップグレードする人はいません。また、これらのログインの 1 つ 1 つが工場全体の鍵であることも意味します。デバイスは HotLoop で作成したログインに移し、環境変数のログインは本当にすべてが必要なもの(フリート、エッジリレー、エッジパブリッシャー)のために残してください。定数時間で検査され、パスワードが誤っているユーザー名は拒否されます。

**匿名**(`HOTLOOP_BROKER_ALLOW_ANONYMOUS`、既定は `false`)は、ポートに到達できる誰に対しても何でも許可します。信頼できる LAN やテスト用の環境向けに、環境ごとに選ぶオプトインであり、このプロセスが自分で問題ないと判断することは決してなく、オンの間は Discovered 画面に赤で表示されます。ユーザー名を送ってくるクライアントに対しては何も緩めません。誤ったパスワードは、やはり誤ったパスワードです。

`HOTLOOP_BROKER_USERS` がなく匿名がオフのブローカーも、問題なく起動します。誰かが HotLoop でログインを作成するまでは、接続できるのは HotLoop だけです。

他のブローカーはそれぞれの管轄です。Mosquitto や EMQX では、ACL はそのブローカーが適用します。これは[フリート管理](/ja/gateway/fleet/)が引くのと同じ境界で、[MQTT ディスカバリー](/ja/iot/mqtt-discovery/)には、そこでの HotLoop 自身のログイン用の ACL があります。

## ディスカバリーと HotLoop 自身のログイン

ブローカーがオンのとき、HotLoop はそのブローカー上で自分自身を通知するデバイスを待ち受けます([MQTT ディスカバリー](/ja/iot/mqtt-discovery/)を参照)。ブローカーは、各ディスカバリー設定をどのログインとクライアントが発行したかを記録します。Discovered 画面にそれが表示され、あるログインから受け入れたデバイスが別のログインから通知された場合は、ログインに警告("Kitchen re-announced by login garage-node; it was accepted from kitchen-node")を出して、人の判断のために保留されます。誰かがデバイスを新しいログインに移したか、あるいはログインが自分ではないデバイスになりすましているかのどちらかです。どちらかは人が決めます。

このブローカー上の HotLoop 自身のクライアント(ディスカバリーリスナーと、発見されたデバイスのドライバー)は、ブローカーが起動のたびに作り、メモリ内にのみ保持するログインでログインします。何でもできます。このために設定するものも、ディスク上にあるものも、バックアップに含まれるものもなく、再起動のたびに別のものになります。

## TLS

ブローカーを有効にすると、プレーンな TCP リスナー(`HOTLOOP_BROKER_LISTEN_ADDR`、既定は `:1883`)は常に利用できます。`HOTLOOP_BROKER_TLS_ENABLED=true` を `HOTLOOP_BROKER_TLS_CERT_FILE` と `HOTLOOP_BROKER_TLS_KEY_FILE` とともに設定すると、その証明書で終端する 2 つ目の独立したリスナー(`HOTLOOP_BROKER_TLS_LISTEN_ADDR`、既定は `:8883`)が追加されます。TLS を有効にすると両方のリスナーが同時に動作し、平文のリスナーを閉じるものはないため、TLS のみで到達できるようにしたい運用者は、ネットワーク層(NetworkPolicy やファイアウォールのルール)でそれを強制します。このチャートが、より広いネットワーク公開の判断を、アプリケーションが自分でどのポートに到達可能にするかを決めるのではなく `networkPolicy.ingress` に任せているのと同じやり方です。

SMTP チャネルが 1 つの接続内で行う STARTTLS のアップグレードとは異なり、ブローカーの TLS リスナーは 2 つ目の独立したソケットです。これは Mosquitto、EMQX、そしてほとんどの MQTT ブローカーが平文ポートと TLS ポートを並べて使うのと同じ形であり、(SMTP と違って)広く実装された接続内アップグレードを持たない MQTT により自然に合います。

このパッケージは、自己署名であれ何であれ、独自の証明書を生成しません。下流のどれも、勝手に作られた証明書を信頼することにならないためです。実際の証明書(社内 CA、`cert-manager`、またはその他の発行元から)は、常に運用者が用意します。

## 設定

| 変数 | 既定値 | <span class="sr-only">詳細</span> |
|---|---|---|
| `HOTLOOP_BROKER_ENABLED` | `false` | これを設定するまで機能はオフです |
| `HOTLOOP_BROKER_LISTEN_ADDR` | `:1883` | 平文の TCP リスナー |
| `HOTLOOP_BROKER_TLS_ENABLED` | `false` | 2 つ目の独立した TLS リスナーを追加します |
| `HOTLOOP_BROKER_TLS_LISTEN_ADDR` | `:8883` | TLS を有効にした場合にのみ使用されます |
| `HOTLOOP_BROKER_TLS_CERT_FILE` / `_KEY_FILE` | n/a | TLS を有効にする場合は必須です |
| `HOTLOOP_BROKER_ALLOW_ANONYMOUS` | `false` | 環境ごとに選ぶオプトインです。既定で有効にしないでください |
| `HOTLOOP_BROKER_USERS` | なし | `user:password,user2:password2`。それぞれ何でもできます。上記を参照してください。ルール付きのログインは HotLoop で作成します |
| `HOTLOOP_BROKER_DISCOVERY` | `true` | 自分自身を通知するデバイスを待ち受けます。[MQTT ディスカバリー](/ja/iot/mqtt-discovery/)を参照 |
| `HOTLOOP_BROKER_DISCOVERY_PREFIX` | `homeassistant` | 通知が届くトピックのプレフィックス |
