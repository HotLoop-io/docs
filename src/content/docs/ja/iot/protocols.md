このドキュメントは、ゲートウェイが何を話せるのか、各ドライバーをどこまで検証したのか、それ以外のものにはどう対処するのかを正確に説明します。最初に読むべきドキュメントであり、他の記述と食い違うときに信頼すべきものです。

ネイティブプロトコルの一覧は、バイナリにコンパイルされたドライバーから導かれます。`/api/protocols`、プロトコル画面、MCP の `describe_protocol` ツールはすべて同じレジストリを読むため、カタログがバイナリにないプロトコルを載せることはありません。

## ネイティブプロトコル

### OPC UA

デバイスが選択肢を提供しているなら、こちらを優先してください。ブラウズでき、適切に保護され、サブスクライブできます。

ドライバーは**ポーリングではなくサブスクライブします**。サーバーは値が変わったときに、処理できる速度で値を送ります。何か動いたかどうかも分からないクライアントが、スキャンのたびに同じ質問を繰り返すのとは違います。サーバーがサブスクリプションを拒否した場合、ドライバーはデバイスを失敗にせず、まとめ読みに切り替えます。

サブスクリプションが何も届けないときも、読み取りに切り替えます。サーバーは最初の publish で全ノードの現在値を送り、変化するまで二度と送りません。そのため最初の publish を失うと、セッションが続く限り設定値が bad のまま読まれます。発行間隔の 10 倍(最低 5 秒)が過ぎてもサブスクリプションから値が来ない場合、ドライバーは警告を記録してサブスクリプションを削除し、デバイスが次に再接続するまでポーリングのたびにタグを読み取ります。このドライバーの土台である OPC UA クライアントライブラリは、負荷の高いホストで publish ループを停止したまま起動し、publish 要求を一度も送らないことがあります。この機能はそのケースのためのものです。

値が届いたあとでサブスクリプションが止まる場合にも、読み取りに切り替えます。ライブラリは keep-alive を自分の中で処理するため、publish ループの停止は、プラントで何も変化していない状態と見分けがつきません。サブスクリプションが発行間隔の 10 倍(最低 30 秒)静かだった場合、ドライバーは全ノードを一度読み取り、サブスクリプションが最後に届けた値と比較します。値や品質が異なるノードが一つでもあれば、サーバーは送るはずのものを抱えていることになるため、ドライバーは警告を記録してサブスクリプションを削除し、デバイスが再接続するまでポーリングのたびに読み取ります。一致していればそのまま続け、同じ時間が経つとまた確認します。健全で静かなサブスクリプションのコストは、30 秒ごとのまとめ読み 1 回です。

**ノードは名前空間 URI で指定してください。**見た目以上に重要です。

```
nsu=http://opcua.edge.server;s=Zone1_Temperature    good
ns=3;s=Zone1_Temperature                            works until it doesn't
```

名前空間の*インデックス*は、サーバーが名前空間を読み込んだ順に割り当てられます。名前空間を追加したりファームウェアを更新したりすると、インデックス 3 が静かに別のものになり、どこにもエラーが出ないまますべての読み取り値が誤ります。URI はモデルの一部であり、動きません。`Browse` が URI 形式を返すのはこのためです。

文字列だけのアドレスは拒否されます。`ns=0;s=Temperature` として読むと、タイプミスも問題なく解析されて存在しないノードになり、タグは永遠に bad のままになります。保存するときにミスが表に出るよう、明示的な形式が必要です。

**Discover tags は、サーバーが示すノードの型で各タグを宣言します。**Boolean は `bool`、整数型は幅を保ち(`int16`、`uint16`、`int32`、`uint32`、`int64`、`uint64`。SByte と Byte は一つ上のサイズ)、Float と Double は `float`、String、DateTime、LocalizedText などドライバーがテキストとして読む型は `string` です。サーバーが示さない型や、より適切な名前がない型(列挙、構造体)は `float` のままです。下の Ignition での作業までは、検出されたタグはすべて `float` でした。ドライバーは String ノードのテキストを読んではいましたが、タグは float と言っており、ゲートウェイ自身の OPC UA サーバーはタグを宣言された型で公開するため、そのサーバーのクライアントは `Bad_TypeMismatch` を受け取りました。Ignition では Emberburn の `System_Status` がまさにそう見えました。修正前に取り込んだタグは型がそのままなので、テキストのタグは手で `string` に変更してください。

設定: セキュリティ、ID、証明書のオプションは [OPC UA: セキュリティと認証情報](#opc-ua-セキュリティと認証情報)で説明しています。残りは `subscribe`、`publishIntervalMs`、`samplingIntervalMs`、`queueSize`、`sessionTimeoutMs`、`browseMaxNodes`、`browseRoot`、`browseServerNodes` です。ドライバーが知らないオプション名は、黙って無視される設定ではなく、知っているオプションを列挙したエラーになります。`securityMode` のタイプミスがあると、セキュリティなしで接続して、正常に動くデバイスと全く同じに見えてしまうからです。

**Discover tags は、サーバー自身の `Server` オブジェクトを除外します**(`i=2253`: ステータス、機能、診断、名前空間配列、構成)。どの OPC UA サーバーにもあり、プラント自身の変数に数百個も混ざることがあります。デバイスで `browseServerNodes` を `true` にすると戻ってきます。`browseRoot` を `i=2253` にすると、意図してその中を見られます。そこから始めたブラウズは、中まで辿ります。

### OPC UA: セキュリティと認証情報

4.15.0 までは、ドライバーは匿名で保護されていない接続しか作れず、仕様に従うサーバーにはそれすら接続できませんでした。サーバーが提示する ID トークンポリシーを尋ねず、空のトークンポリシー ID を送っていたため、準拠サーバーはそれを拒否します。HotLoop 自身の OPC UA サーバーも同じでした。今のドライバーはサーバーのエンドポイントを検出し、デバイスに合うものを選び、そのエンドポイントが列挙したポリシー ID をそのまま返します。

#### デバイスオプション

| オプション | 既定値 | 内容 |
|---|---|---|
| `securityMode` | `None` | `None`、`Sign`、`SignAndEncrypt`。`None` 以外の `securityPolicy` と併せて省略した場合は `SignAndEncrypt` になります。 |
| `securityPolicy` | そのモードでサーバーが提示する最良のもの | `None`、`Basic256Sha256`、`Aes128_Sha256_RsaOaep`、`Aes256_Sha256_RsaPss`。`Basic128Rsa15` と `Basic256` は拒否されます。 |
| `username`, `password` | 匿名 | ユーザー名認証。 |
| `userCertificate`, `userPrivateKey` | なし | X.509 ユーザー認証: セッションは、サーバーがこの証明書に対応付けたユーザーとしてパスワードなしでサインインします。どちらも PEM で、両方を設定します。キーは RSA で(OPC UA ライブラリは RSA でしか署名しないため、EC キーはその旨を示して拒否されます)、パスワードと同様にシークレットです。保存時に封印され、すべての API 応答で伏せられ、ログには出ません。証明書はユーザーのものであり、`certFile` のクライアントアプリケーション証明書ではありません。`username` も設定した場合は、証明書が使われます。HotLoop 自身のサーバーでは、先に証明書をユーザーに関連付ける必要があります([OPC UA サーバー](/ja/edge/opc-ua-server/#x509-ユーザー証明書))。 |
| `allowInsecureCredentials` | `false` | 保護されていないチャネル(`securityMode` が `None`)や、何も暗号化しない場合に、パスワードの送信を許可します。 |
| `certFile`, `keyFile` | 生成 | 保護モードで使う、このクライアントのアプリケーション証明書とその RSA キー。両方設定するか、どちらも設定しません。 |
| `pkiDir` | `HOTLOOP_OPCUA_CLIENT_PKI_DIR` (`/data/opcua-client-pki`) | 生成された証明書と、`trusted/` と `rejected/` のストアの置き場所。 |
| `serverCertThumbprints` | なし | `trusted/` にファイルがなくても信頼するサーバー証明書の SHA-1(16 進 40 桁)または SHA-256(64 桁)サムプリント。コロンとスペースは無視されます。 |
| `insecureSkipVerify` | `false` | どのサーバー証明書も受け入れます。 |

これらを一つも設定していないデバイスは、従来どおりです。匿名で、保護されていないチャネルを使います。

#### ドライバーがエンドポイントを選ぶ方法

ドライバーは、保護されていないチャネルでサーバーのエンドポイントを尋ねます。仕様はディスカバリーのためにサーバーがこれを許可することを求めており、エンドポイント一覧は元々公開情報なので秘密は何も流れません。そのうち、セキュリティモードとポリシーがデバイスに合うエンドポイントを残し、その中からデバイスの ID(匿名、または `username` を設定した場合はユーザー名)に合うトークンポリシーを選びます。その後に送る ID トークンには、そのエンドポイントが列挙したポリシー ID が入り、空のものは決して送りません。

- **`Basic128Rsa15` と `Basic256` は絶対に選びません。**どちらも OPC Foundation によって非推奨とされています。サーバーが順位付けする方法でどちらかが一覧で最も高いセキュリティレベルを持つ場合も、サーバーが提示するのがそれだけの場合も同じで、後者では、その旨を示すエラーで接続が失敗します。デバイスにこれらを使うよう設定することはできず、パスワードをこれらで暗号化することになるトークンポリシーも拒否されます。HotLoop 自身のサーバーは最新のポリシーと並べて両方を提示し、無効にできません。そのため実際のサーバーに対して検証し、ドライバーが送る内容に両ポリシーの URI が現れないことをテストで確認します。
- **デバイスがポリシーを指定しない場合は、`Basic256Sha256`、次に `Aes128_Sha256_RsaOaep`、次に `Aes256_Sha256_RsaPss` の順に優先します。**サーバーがそれらに付けたセキュリティレベルは関係ありません。順序は強度ではなく、どれだけ広く動作するかで決めています。一部のサーバーは `Aes256_Sha256_RsaPss` でチャネルを開けず、理由を伝えずに接続を閉じるため、デバイスが指定したときだけ使います。
- **一致するものがない場合、エラーにはサーバーが実際に提示するものが列挙されます。**各エンドポイントのポリシーとトークンポリシー ID が含まれるため、メッセージだけで設定を直せます。

#### クライアント自身の証明書

保護モードにはアプリケーション証明書が必要です。デバイスが `certFile` と `keyFile` を指定していれば、チェック(RSA、2048 ビット以上、期限切れでない)のうえでそのまま使います。そうでなければ、初回の使用時に自己署名証明書を生成し、PKI ディレクトリに保存します。RSA-2048、5 年、サブジェクト代替名にアプリケーション URI `urn:hotloop:client:<host name>`、キーはモード `0600`、証明書は `0644`、ディレクトリは `0750` です。レイアウトは OPC UA サーバーのものと同じです。

```
own/cert.pem, own/key.pem   this client's certificate
trusted/                    server certificates an operator has approved
rejected/                   server certificates the driver turned away
```

通常の起動では再生成しないので、この証明書を信頼するよう指示されたサーバーに、改めて伝える必要はありません。読み取れない場合、2048 ビット以上の RSA でない場合、残りが 30 日未満の場合にだけ置き換え、すべてのサーバーが新しい証明書を承認する必要があるという警告を出します。同じ瞬間に起動するデバイスは、それぞれが別々に書くのではなく、一つの証明書を共有します。

ディレクトリは書き込み可能で永続的である必要があります。Helm チャートでは `opcuaClient.persistence.enabled` がその設定で(既存のインストールにボリュームが増えるため、既定ではオフ)、Edge Relay では既存の `/data` ボリュームです。書き込み可能なディレクトリがない場合、保護されたデバイスは、次の再起動で失われる証明書で接続する代わりに、設定すべき変数名を示すエラーを報告します。

**サーバー**もこの証明書を信頼する必要があり、これはサーバー自身の設定です。HotLoop 自身のサーバーでは同じ操作です。最初の試行が拒否されたあと、ドライバーの証明書がサーバーの `rejected/` ディレクトリに現れ、それを `trusted/` に移動すると承認されます。サーバーがセキュアチャネルを開いている途中で接続を閉じる場合(多くのサーバーは信頼しない証明書をこうして拒みます)、エラーにはこのクライアントの証明書ファイルとサムプリントが示されるため、オペレーターはサーバー側で何を探せばよいか分かります。

#### サーバー証明書の承認

保護モードの場合や、サーバーのキーに暗号化して送るパスワードがある場合、**ドライバーはサーバーが提示する証明書をそのまま受け入れません。**デバイスの `serverCertThumbprints` に固定されているか、`trusted/` にある完全に同じ証明書の場合にのみ信頼します。それ以外は `rejected/<thumbprint>.der` に書き出され、認証情報が送られる前に、次のようなメッセージとともに接続が失敗します。

```
opcua: the server at opc.tcp://plc-01:4840 presented a certificate that is not
trusted (subject "CN=PLC01", SHA-1 thumbprint 5A6DB35A..., expires 2031-09-18).
It has been saved to /data/opcua-client-pki/rejected/5A6DB35A....der. To approve
it, first check that the thumbprint matches the one the server shows, then move
that file into /data/opcua-client-pki/trusted (the next connection attempt picks
it up; no restart is needed). Alternatively pin it by adding the thumbprint to
this device's serverCertThumbprints. Until then this device will not connect
```

承認する前に、サーバー自身の表示でサムプリントを確認してください。この照合が信頼判断のすべてです。そのうえでファイルを `trusted/` に `mv` すると(PEM と DER のどちらも読み込まれます)、ランタイムの再接続間隔内の次の試行でデバイスが接続します。いくつかの詳細です。

- 信頼はチェーンではなく、証明書そのものに対して行われます。CA が発行した証明書を持つサーバーも、自己署名のものと同様に、そのサーバー自身の証明書を `trusted/` に置いて承認します。CA を信頼することはサポートされていません。
- 期限が切れていても、オペレーターが承認した証明書は引き続き信頼され、接続のたびにログに警告が出ます。オペレーターが意図して承認したものを拒否すると、`insecureSkipVerify` に向かわせるだけだからです。
- `trusted/` にある証明書でないファイルは、スキップして報告され、承認済みの他のサーバーに到達できなくなることはありません。
- `rejected/` には最大 256 ファイルを保持するので、接続のたびに別の証明書を提示するサーバーがディスクを埋めることはできません。それを超えても接続は拒否され、メッセージにはファイルが保存されなかったことと、それでも証明書を承認する方法が示されます。
- `insecureSkipVerify` はチェックをオフにします。すると経路上の第三者がサーバーになりすまし、パスワードを含め、サーバーへ送られるものを読み取れます。既定ではオフで、接続のたびに証明書のサムプリントとともに警告します。

保護されていないチャネル上の匿名デバイスには、サーバーのキーに対して署名や暗号化をするものがないため、これらは一切必要ありません。

#### 認証情報

チャネルが保護され、かつパスワードを暗号化する何かがない限り、パスワードは送信前に拒否されます。ドライバーは、一致したエンドポイントについてサーバーが提示する内容から、次のように判断します。

| チャネル | サーバーのユーザー名トークンポリシー | 結果 |
|---|---|---|
| `SignAndEncrypt` | パスワードを暗号化する(通常のケース) | 接続する |
| `SignAndEncrypt` | 暗号化しない | 接続する: 暗号化されたチャネルが運び、ログにそう記録される |
| `Sign` | パスワードを暗号化する | 接続する |
| `Sign` | 暗号化しない | `allowInsecureCredentials` がない限り**拒否**。`Sign` はメッセージを認証しますが、隠しはしません。 |
| `None` | パスワードを暗号化する | `allowInsecureCredentials` がない限り**拒否**。保護されていないチャネルでは、パスワードを暗号化する鍵が何も認証しない応答から来るため、通信を改ざんできる者なら誰でもパスワードを復元できます。オプトインすると、警告付きで接続します。 |
| `None` | 暗号化しない | `allowInsecureCredentials` がない限り**拒否** |

**`securityMode` が `None` のときのユーザー名は、サーバーのトークンポリシーがパスワードを暗号化していても拒否されます。**攻撃者が鍵を選べる暗号化は、その攻撃者に対する防御になりません。保護されていないチャネルでは、パスワードを暗号化する証明書は `CreateSession` へのサーバーの応答から取られますが、これは何も認証しません(下のテストは証明書を差し替えてパスワードを復元します)。エラーはこのことを述べ、対処法として `securityMode` `SignAndEncrypt` を示します。匿名セッションは影響を受けません。

`allowInsecureCredentials` は、そうした条件でパスワードを送信できるようにする唯一のスイッチです。既定ではオフで、これによって接続が許可されたときは、接続のたびに警告します。トークンポリシーがパスワードを暗号化する場合、これは盗聴者が読めるものを変えますが、通信を改ざんする者が読めるものは変えません。[ネットワークを流れるもの](#ネットワークを流れるもの)を参照してください。これを使っても、パスワードがサーバーの証明書に暗号化される場合は、先にサーバーの証明書を承認する必要があります。

パスワードは、ドライバーと API が扱うあらゆる場所でシークレットです。

- **API 応答。**デバイスを返すすべての応答(`GET /api/devices`、`GET /api/devices/{id}`、保存の応答)で `[redacted]` に置き換えられるため、`devices.read` を持つ viewer は読めません。4.15.1 からは管理者を含むすべてのロールに当てはまり、このプロトコルだけでなくすべてのプロトコルの認証情報に当てはまります。プレースホルダーのままデバイスを保存すると保存済みのパスワードが保たれ、新しい値は置き換え、空文字列は消去します。パスワードのないデバイスにプレースホルダーを入れると、保存されずに拒否されます。フィールドを省略した場合は保持されます(4.15.0 では消去されました)。完全な規則は[認証とユーザー](/ja/iot/authentication/#デバイスの資格情報は書き込み専用です)にあります。Web UI のデバイスエディターは API が返すとおりに設定を表示し、見えているものをそのまま保存しますが、これはそのケースを処理するので、デバイスを編集してもパスワードは失われません。(テストはブラウザーではなく API を通してこれを確認します。)
- **ログとエラー。**ドライバーのログ行にも、返すエラーにも、パスワードは含まれません。メッセージはステータスコードとデバイスの秘密でない設定から作られます。テストはプロセスログ、サーバーのログ、エラーを取得し、そのすべてからパスワードを検索します。
- **MCP ツールとリソース、ライブイベントストリーム、システムログ。**どれもデバイスの設定を返さず(それぞれ決まったフィールドでデバイスを説明します)、テストはパスワードを設定した状態ですべてのツールとリソースを呼び出し、ストリームを開き、システムログを読んで、どこにも見つからないことを確認します。
- **データベースとバックアップ。**パスワードは他のドライバーと同様に、デバイスの `config` 列に保存されます。4.16.0 まではそのままの形で、バックアップにも含まれます。4.17.0 からは、データベースの外に置かれた鍵で暗号化されるため(下の「保存時の暗号化」を参照)、ダンプやバックアップには暗号文が入ります。いずれにしても、[バックアップと復元](/ja/iot/backup/#バックアップファイルを守る)を参照し、データベースとバックアップボリュームを適切に保護してください。
- **Edge Relay。**デバイスファイルにもパスワードが入ります。Helm チャートでは、認証情報を含むデバイスファイルを Secret に入れ、`devicesSecret` に名前を指定してください。チャートの values に直接設定したデバイスは ConfigMap に入ります。フリートの設定プッシュで送ったデバイスファイルは MQTT トピックに retained で公開されるため、ブローカーは TLS を使い、そのトピックを読める人を制限する必要があります。

パスワードが間違っていれば、ドライバー内でハングも再試行もなく、1 回の試行で明確なエラーになります。

```
opcua: authentication rejected: the server at opc.tcp://plc-01:4840 rejected the
user name and password for "svc-hotloop" (StatusBadUserAccessDenied). ...
```

その後ランタイムは、通常の再接続バックオフ(`HOTLOOP_RECONNECT_MAX`、既定 60 秒)ではなく、次の試行まで**10 分**(5 分から 10 分の間でばらつかせます)待ちます。拒否されたログインは、ネットワーク障害より繰り返すコストが高いからです。数回の失敗でアカウントをロックするサーバーでは、素早い再試行が、そのアカウントを使う他の全員にとっての障害になります。また、拒否されたログインのたびに、サーバー上に**作成されたが有効化されないセッション**が残ることがあり、タイムアウトするまでセッション上限に数えられます(ライブラリは 20 分を要求し、`sessionTimeoutMs` で変更できます)。HotLoop 自身のサーバーでは、パスワードが間違ったデバイスが数秒おきに再試行して、既定の上限である 20 セッションを使い切り、その後サーバーが他のすべてのクライアントを `BadTooManySessions` で拒否しました。セッションテーブルが小さいコントローラーは、これ以上に影響を受けやすくなります。デバイスは再試行をやめないため、サーバー側でパスワードが直れば、誰も HotLoop に触れなくても 10 分以内に復旧します。デバイスのパスワードを直すか、オフにしてオンにすると、新しいワーカーが始まり、すぐに試行します。

#### ネットワークを流れるもの

推論ではなく測定です。テストはドライバーとサーバーの間に記録用プロキシを置き、両方向のすべてのバイトを検索します。この検索は、そこにあると分かっているバイト(平文で送られるサーバーのエンドポイント一覧)を見つけます。それがプロキシが会話を記録した証拠です。

| 構成 | パスワード | ユーザー名 | タグのノード ID と値 |
|---|---|---|---|
| `SignAndEncrypt` | 見えない | 見えない | 見えない |
| `Sign` | 見えない(トークンポリシーが暗号化) | **読める** | **読める** |
| `None`、ユーザー名、サーバーのトークンポリシーが暗号化(`allowInsecureCredentials` が必要) | 見えない | **読める** | **読める** |
| `None`、匿名 | 該当なし | 該当なし | **読める** |
| 暗号化されていないパスワードを提示するサーバー、`allowInsecureCredentials` あり | **読める** | **読める** | モードによる |

最後の行は、実際にはそうは提示しないサーバーに対してテストします。実サーバーの前にいる第三者が、何も認証しないディスカバリー用のチャネル上で、エンドポイント一覧を書き換えてパスワードが暗号化されないと言わせます。テストが拒否を示す方法もこれです。オプトインがなければドライバーは拒否し、ディスカバリー接続だけを開き、認証情報はワイヤー上に出ません。エンドポイント一覧は経路上の第三者が書き換えられるものそのものなので、ドライバーのルールは、サーバーに強制を任せるのではなく、ドライバーが伝えられた内容に適用されます。

パスワードを使う保護されていないチャネルには、表に現れない限界があり、テストがそれを示します。ドライバーがオプトインなしでその組み合わせを拒否する理由です。パスワードはサーバーの証明書に暗号化され、盗聴者からは隠れ、ドライバーはその証明書が承認されるまで送りません。しかし OPC UA ライブラリが暗号化に使う証明書は、セッション作成時のサーバーの応答にあるものであり、保護されていないチャネルでは、その応答は認証されません。通信を改ざんできる者が自分の証明書を入れると、パスワードはその者の鍵に暗号化されます。テストはこれを行い、差し替えた鍵でパスワードを復号して取り戻します。**`Sign` や `SignAndEncrypt` では、同じ第三者にはできません。**応答が、その者の持たない鍵で保護されているからです。`allowInsecureCredentials` がなければドライバーはパスワードをまったく送らず、テストは、その場合に同じ第三者が何も得られないことを示します。オプトインすると、ドライバーは接続のたびに警告します。サーバーが提供する場所では必ず `SignAndEncrypt` を使ってください。パスワードを使う保護されていないチャネルをオプトインで許可した場合、守れるのは盗聴に対してだけです。

#### 再接続

OPC UA ライブラリ自身の再接続は無効で、ランタイムが再接続します。ライブラリはセッションを失うと、与えられた認証情報で新しいセッションを開き、サーバーに拒否されると、遅延なしにすぐ再試行します。パスワードが変更されたサーバーに対して、12 秒間で約 20 回の拒否されたログインが測定されました。これが、アカウントを共有するすべての人がロックアウトされる原因です。今は、セッションを失うと `Poll` がエラーを報告し、ランタイムのワーカーがドライバーを閉じて新しく開き、新しいドライバーがエンドポイントを検出し、サーバーの証明書を確認し、再びサインインします。このとき、ランタイムのジッター付きバックオフと、認証失敗後の 10 分の待機が適用されます。サーバーの再起動も同じ方法で乗り越えます。デバイスは再サインインしたあと、再起動後の新しい値を読み取り、テストはサーバーのログイン回数を数え、再起動後に値を変えることでこれを確認します。

タグのないデバイスには読み取るものがなく、4.15.2 まではそのポーリングは何も送りませんでした。サーバーはセッションタイムアウト後にアイドルのセッションを閉じ、デバイスは誰もサーバーに尋ねていないので接続中と言い続け、プロセスを再起動するまで、すべてのブラウズが `BadSessionIDInvalid` で失敗しました。誰かがデバイスを追加して Discover tags をクリックする、まさにその瞬間のすべてのデバイスがそうでした。Ignition で見つかりました。今はタグのないデバイスもポーリングのたびにサーバーの状態を読み、セッションを保ち、切れたことに気付きます。セッションが消えたことを見つけたブラウズはそれを報告し、ランタイムが再接続します。

セッションの開始前から変化していないタグは、今は良好な品質で現在値を読み取ります。以前は、最初の値を待つ間に報告されるプレースホルダーの読み取り値が、値自身のソースタイムスタンプより新しく、ランタイムは最新の読み取り値を保持して値を捨てたため、安定したタグは次に変化するまで bad のまま読まれていました。

#### テストしたことと、していないこと

OPC UA は、Ignition 8.3.9 と独立した OPC UA サーバーに対して、`None`、`Sign`、`SignAndEncrypt` で匿名およびユーザー名とパスワードのサインインで実行し、2026-11-17 にはベアメタルでも実行しました。運用中のサーバーごとに、提示するポリシーや証明書の拒否の仕方に癖があるため、新しいベンダーのサーバーへの最初の接続は試運転として扱ってください。

知っておくこと:

- 接続のたびに、まずサーバーにエンドポイントを尋ねるようになり、セキュリティオプションのないデバイスには、ID 付きの匿名トークンポリシーを列挙する保護されていないエンドポイントが必要です。それを列挙せずに匿名セッションを受け付けていたサーバーは、提示するものを列挙したエラーで拒否されます。
- X.509 証明書と issued-token によるユーザー認証は、このドライバーには実装されていません。デバイスの `certFile` はアプリケーション証明書です。
- 信頼は証明書そのものに対するものです。認証局の信頼と証明書失効はサポートされていません。
- 楕円曲線のセキュリティポリシーはサポートされておらず、保護されていないチャネルでのディスカバリーを拒否するサーバーもサポートされていません。
- どちらの端も切断に気付かないまま途切れたネットワーク経路では、オペレーティングシステムが接続をあきらめるまで、デバイスは最後の値のままになります。
- 一部のサーバーは `Aes256_Sha256_RsaPss` でチャネルを開けません。
- HotLoop 自身のサーバーは最大 72 バイトのパスワードを受け付けます。他のサーバーには独自の上限があるかもしれません。

#### Ignition 8.3

**Ignition 8.3.9**(現在の安定版)で、Inductive Automation 公式のコンテナイメージを使って検証しました。HotLoop のドライバーがクライアント、反対側が Ignition の OPC UA サーバーで、`Basic256Sha256` と `SignAndEncrypt`、ユーザー名とパスワードでサインインしました。ブラウズで `nsu=urn:inductiveautomation:ignition:opcua:tags` の下に Ignition のタグが見つかり、`[System]/Gateway` の時計、CPU、メモリ、稼働時間のタグが取り込まれ、サブスクリプションで届けられて良好な品質で読み取られました。

標準の 8.3 ゲートウェイは、HotLoop が一言も話せないうちに 4 回止めてきます。

1. **OPC UA サーバーは localhost でしか待ち受けません。**初期状態の 8.3 はポート 62541 を `localhost` にバインドするため、別の場所にある HotLoop は接続拒否以外何も得られません。ゲートウェイの OPC UA サーバー設定で、Bind Addresses を `0.0.0.0` にしてください。HotLoop が接続するホスト名も Endpoint Addresses に追加しましたが、ドライバーにそれが必要かどうかはテストしていません。
2. **タグは初期状態では OPC UA に公開されません。**Expose Tag Providers をオンにしないと、ブラウズで見つかるのはサーバー自身の診断情報とデバイスフォルダーだけです。
3. **証明書は両方向です。**HotLoop は、上で説明したとおり、承認するまで Ignition の証明書を拒否します。Ignition は、ゲートウェイの OPC UA サーバー証明書で信頼するまで、HotLoop の証明書を拒否します。ディスク上では `data/config/local/com.inductiveautomation.opcua/server/security/pki/rejected/certs` から `.../trusted/certs` へ移動することで、再起動は不要です。**Ignition は、HotLoop がログに出す SHA-1 サムプリントでそのファイルに名前を付けません。**証明書を開いてフィンガープリントを比べてください。ファイル名が一致しなくても、なりすましの印ではありません。
4. **OPC UA のログインは `opcuauser` / `password`** で、新規インストールのたびに `opcua-module` ユーザーソースに入っています。実際のものを接続する前に変更してください。

この方向では、8.3 のサーバーが初期状態で提供するもの、つまり `Basic256Sha256` と `SignAndEncrypt` だけを試しました。

**逆の方向も検証済みです。Ignition 8.3.9 の OPC UA クライアントが HotLoop の OPC UA サーバーを読み取ります。**HotLoop の viewer としてサインインし、Ignition が提供するすべてのセキュリティポリシーとモードで確認しました。セットアップ、双方向の証明書の信頼、注意点、ポリシーの一覧は [OPC UA サーバー](/ja/edge/opc-ua-server/#クライアントとしての-ignition-83)にあります。これにより HotLoop のバグが 2 件見つかり、どちらも修正済みです。コンテナーを作り直すたびにサーバーが新しい証明書を生成し、アップグレードのたびに Ignition の信頼が壊れていたこと、そして Discover tags がすべてのタグを float と宣言していたため、テキストのタグが Ignition に `Bad_TypeMismatch` で届いていたことです(上記)。

HotLoop の Sparkplug エッジノードと Edge Relay を Ignition の MQTT Engine に対して検証する作業は次の段階で、まだ行っていません。

### OPC UA PubSub (UADP)

もう一つの OPC UA です。クライアントがサーバーに尋ねるのではなく、パブリッシャーが DataSet を UDP データグラムとして、ユニキャストまたはマルチキャストで、聞いている相手に送ります(OPC 10000-14、UADP エンコーディング)。HotLoop はデバイスとしてサブスクライブし、設定としてパブリッシュします。

**サブスクライブ。**プロトコルが `opcua-pubsub` のデバイスを追加します。アドレスは待ち受ける先です。`udp://239.0.0.1:4840` はマルチキャストグループに参加し、`udp://:4840` はユニキャストを待ち受けます。タグのアドレスは `<DataSetWriterId>/<field index>` で、パブリッシャーの DataSet の中の 0 から数えたフィールドの位置です。`1000/3` は writer 1000 が公開する 4 番目のフィールドです。UADP にはフィールド名がない(名前は、パブリッシャーが別の方法で提供する DataSetMetaData にあるか、まったくありません)ため、データグラムが伝えられるのは位置です。配列のフィールドは 1 要素ずつ読みます。`1000/3[17]` は、4 番目のフィールドである配列の 18 番目の値です。Browse は、これまでに受信したフィールドを型とともに一覧し、配列はその要素(最初の 1000 個)として一覧します。

```json
{"publisherId":"2234","writerGroupId":100,"interface":"eth0","timeoutMs":30000,
 "dataSets":[{"writerId":62541,"types":["Float","UInt16","Boolean","Int32","Double"]}]}
```

- `publisherId` と `writerGroupId` は、デバイスを一つのパブリッシャーとグループに絞ります。空と 0 はすべてを受け取ります。複数のデバイスが一つのアドレスを共有するための方法です。パブリッシャーが `udp://:4840` に 2 つの WriterGroup を送るなら、そこには 2 つのデバイスがあり、一方は `"writerGroupId":1`、もう一方は `"writerGroupId":2` です。
- デバイスはアドレスとポートを共有できます。HotLoop はそのためにソケットを 1 つ開き(1 枚のカードでのマルチキャストグループへの参加も 1 回)、すべてのデータグラムをそのアドレス上のすべてのデバイスに渡します。各デバイスは自分の `publisherId`、`writerGroupId`、`dataSets` を適用するので、それぞれが自分のパブリッシャーのストリーム全体を見て、デバイス間で分割されることはありません。そのアドレス上の最後のデバイスが削除または停止されるとソケットは閉じ、次のデバイスが起動すると再び開きます。デバイスは書かれたとおりのアドレスで照合されます。`udp://:4840`、`udp://0.0.0.0:4840`、`udp://[::]:4840` は HotLoop にとって 3 つの別のアドレスで、共存できるかどうかは、これまでどおりオペレーティングシステム次第です。2 枚の異なるカードで参加したマルチキャストグループは 2 つのソケットです。アドレスを単独で使うデバイスには、何も変わりません。
- グループ、ポート、カードはすべてデバイスの設定で、HotLoop に固定されたものはありません。`"interface":"eth0"` を付けた `udp://239.192.0.1:4850` はそのカードでそのグループに参加し、`udp://127.0.0.1:4842` は同じマシン上のパブリッシャーを待ち受けます。複数のデバイスが、異なるグループとポートを同時に、または同じものを待ち受けることができます。
- `interface` は、マルチキャストグループに参加するネットワークカードで、名前(`eth0`、`lo`)またはその IPv4 アドレス(`127.0.0.1`)で指定します。カードが複数あるマシンでは必要です。同じマシン上のパブリッシャーがループバックでグループに送る場合(`IP_MULTICAST_IF` 127.0.0.1、TTL 0、ループバックオン、ルートなし)、`"interface":"lo"` または `"127.0.0.1"` のデバイスが受信します。インターフェースを指定せずルートもない場合、参加は `no such device` で失敗し、そう伝えます。
- `dataSets` は、ワイヤー上に型を持たない RawData のためだけにあります。バイトを読み取れるよう、パブリッシャーのフィールドの型を順番に指定します。Variant と DataValue のメッセージは、自分で型を持っています。各エントリーは型名(`"Float"`)で、値のまとまりの並び方も指定できます。`"Float*250"` は、長さの前置きなしに 250 個のフィールドが連続するもので、REAL のまとまりを別々のフィールドとして送る PLC がこう書きます。`"Float[250]"` は最大 250 個の値を持つ 1 つの配列フィールドで、OPC Foundation スタックが RawData の配列を書く方法(Int32 の個数、値、250 個になるまでのゼロパディング)です。`"String(40)"` は 40 バイトに詰めた String で、単独でも `"String(40)[4]"` のようにも使えます。
- Key frame は DataSet のフィールドを置き換え、delta frame は指定したフィールドだけを変更し、keep alive はパブリッシャーが生きていることを示します。メッセージが失われた(シーケンス番号に欠落がある)場合、delta も一緒に失われた可能性があるため、次の key frame まで、その DataSetWriter のタグは **uncertain** になります。DataSet の構成バージョンが変わると、key frame が新しい意味を伝えるまで、すべてのフィールドを忘れます。
- writer が `timeoutMs`(設定がなければ 30 秒)の間無音だと、その理由を添えて **bad** として読まれ、タイムアウト内にパブリッシャーから何も聞こえないデバイスはダウンです。パブリッシャーが Bad と印を付けたフィールドは bad、Uncertain と印を付けたものは uncertain で、理由はステータスコードです。
- 読み取り値の時刻は、フィールド、DataSetMessage、NetworkMessage のうち設定されていて、このクロックより 1 分を超えて先でないもののパブリッシャーの時刻で、そうでなければ到着した時刻です。
- 配列は Variant と DataValue のメッセージ(Int32 の個数と値、OPC 10000-6 5.2.2.16。多次元の配列は行ごとに平坦化されて届く)で読み、レイアウトを指定すれば RawData でも読みます。データグラムが収められない個数は、何かを作る前に拒否されます。
- 読み取り専用です。メッセージのセキュリティ(署名または暗号化された NetworkMessage)、チャンクされたメッセージ、ディスカバリーメッセージ、イベント、構造体フィールドはサポートされていません。そのいずれかを含むデータグラムは拒否され、理由別に集計され、推測で処理されることはありません。

**パブリッシュ。**Edge と Gateway(OPC UA サーバーを持つ製品)で `HOTLOOP_UADP_PUBLISH_ENABLED` を設定するまではオフです。レイアウトが指定するタグを送ります。

```json
{"dataSets":[{"writerId":1,"name":"press","configMajor":1,"fields":[
  {"device":"press-01","tag":"Zone1_Temp","type":"Float"},
  {"device":"press-01","tag":"Cycle","type":"UInt32"}]}]}
```

| 変数 | 既定値 | <span class="sr-only">詳細</span> |
|---|---|---|
| `HOTLOOP_UADP_PUBLISH_ADDRESS` | | マルチキャストグループは `udp://239.0.0.1:4840`、サブスクライバー 1 つなら `udp://host:4840` |
| `HOTLOOP_UADP_PUBLISH_LAYOUT_FILE` または `_LAYOUT` | | 上のレイアウトをファイルまたはインラインで指定(ファイルが優先) |
| `HOTLOOP_UADP_PUBLISH_PUBLISHER_ID` | `1` | 数値またはテキスト |
| `HOTLOOP_UADP_PUBLISH_WRITER_GROUP_ID` | `1` | |
| `HOTLOOP_UADP_PUBLISH_INTERVAL` | `1s` | |
| `HOTLOOP_UADP_PUBLISH_KEY_FRAME_EVERY` | `10` | key frame の間隔は最大でこの回数 |
| `HOTLOOP_UADP_PUBLISH_DATAVALUE` | `false` | Variant の代わりに DataValue フィールド(値、ステータス、時刻) |
| `HOTLOOP_UADP_PUBLISH_DELTA_FRAMES` | `false` | 変化した DataSet を、key frame の間は delta frame(変化したフィールドだけ)として送信 |
| `HOTLOOP_UADP_PUBLISH_INTERFACE`, `_TTL` | システムの既定値、`1` | マルチキャストが出ていくカードと、そのホップ制限 |

各 DataSet は自分の DataSetWriter から、NetworkMessage 1 つとして送られます。値が変化した DataSet は key frame(全フィールド)として、変化しなかったものは keep alive として送られ、遅れて参加したサブスクライバーが追いつけるよう、key frame は少なくとも `KEY_FRAME_EVERY` 間隔ごとに送られます。Delta frame は既定ではオフです。key frame は完全なので、データグラムが失われても 1 間隔分の損失で済み、誤った値は残りません。`HOTLOOP_UADP_PUBLISH_DELTA_FRAMES=true` にすると、変化した DataSet は代わりに delta frame として送られ、最後のメッセージ以降に変化したフィールドとその位置だけを運びます。key frame は引き続き少なくとも `KEY_FRAME_EVERY` 間隔ごとに送られ、失われた delta は最大その間隔分、フィールドが古い値のままになります。これが、遅いリンクでメッセージを小さくする代償です。HotLoop 自身のサブスクライバーは delta frame を読み取ります。value。bad のタグは最後の値ではなくそのステータスとして公開され、まだ何も読まれていないものは `BadWaitingForInitialData` として公開されます。値は公開される型に収まるよう制限され、折り返されません。メッセージのセキュリティはサポートされていないため、プラントが信頼するネットワーク上で使ってください。同じレイアウトのタグは、別のボックスの HotLoop 自身のサブスクライバーで読み取れます。

**検証した内容。**独立した OPC UA PubSub スタックが HotLoop のサブスクライバーにパブリッシュし、HotLoop のパブリッシャーをマルチキャストでサブスクライブします。HotLoop のパブリッシャーは HotLoop 自身のサブスクライバーに正しく読み取られます。
### CODESYS

CODESYS Control ランタイム(Linux SL、ARM64、Raspberry Pi、Windows、仮想 PLC)を実行する PLC を、プログラマーが変数に付けた名前で読み書きします。ノード ID ではなく `Application.GVL_Line.rTemp` です。CODESYS の PLC に必要なものを足した OPC UA ドライバーなので、[OPC UA: セキュリティと認証情報](#opc-ua-セキュリティと認証情報)の内容はすべてこれにも当てはまり、そのオプションがそのまま使えます。

**なぜ OPC UA サーバーなのか、そして PLC には何を意味するのか。**CODESYS がサードパーティにコントローラーの変数の読み取り方として文書化しているのは 1 つで、ランタイム自身の OPC UA サーバーです。アプリケーションの Symbol Configuration(CODESYS 3.5 SP18 以降は Communication Manager の下の IEC Symbol Set)が、どの変数をどのアクセスで公開するかを決め、サーバーがそれを提供します。CODESYS Gateway のチャネルプロトコルはサードパーティ向けに文書化されておらず、このドライバーはそれを話しません。そのため、見たいものを PLC が公開する必要があります。

1. IDE でアプリケーションに **Symbol Configuration** を追加し、*Support OPC UA features* をオンにして、変数にチェックを入れるか、宣言に `{attribute 'symbol' := 'readwrite'}`(読み取り専用なら `'read'`)を付けて印を付けます。
2. ダウンロードします。Symbol Configuration のない PLC は、セットアップに、追加するよう伝えるメッセージで応答します。
3. 変数が HotLoop から書き込み可能になるのは、そのシンボルが `readwrite` で、接続するユーザーに書き込みが許可されている場合(デバイスの *Symbol Rights*)だけです。HotLoop はアクセスレベルを読み取り、どちらが書き込みを拒否したかを伝えます。

出典: [CODESYS ヘルプ、Symbol Configuration](https://content.helpme-codesys.com/en/CODESYS%20Communication/_cds_symbolconfiguration.html)と [IEC Symbol Set](https://content.helpme-codesys.com/en/CODESYS%20Communication/_comm_symbol_configuration.html)(シンボル名は `<application>.<POU>.<variable>`、アクセスはシンボルごとに読み取り、書き込み、実行、グループの権限はデバイスの Symbol Rights タブにあり、OPC UA にはコントローラー上の証明書が必要)、[IEC 61131-3 向け PLCopen OPC UA 情報モデル](https://plcopen.org/system/files/downloads/plcopen_opc_ua_information_model_for_iec61131-3_version1.02.pdf)(リリース 1.02、下のレイアウト)、OPC UA Part 5(OperationLimits)。ノード ID は、このドライバーの作成時に基準とした 4.22.0.0 ランタイムが返したもので、正確な `|var|` の綴りは公開された契約ではなくランタイムのものです。そのため、タグはシンボルで指定し、ノード ID はドライバーが作ります。

**レイアウト。**ランタイムは OPC UA Device Integration の `DeviceSet` に、PLC 用のデバイスを 1 つ、その下に `Resources`、さらにその下にアプリケーションを公開し、その中に `GlobalVars`(変数リスト)と `Programs` があります。変数のノードは、名前空間 `CODESYSSPV3/3S/IecVarAccess` の `ns=<n>;s=|var|<device>.<application>.<list or program>.<variable>` です。ドライバーはブラウズでデバイスとアプリケーションを見つけるので、プロジェクト名が変わってもタグは残ります。

**アドレス。**アプリケーション名の有無を問わない IEC シンボルです。

```
Application.GVL_Line.rTemp        a variable of a variable list
GVL_Line.rTemp                    the same; the application is assumed
Application.PLC_PRG.nCount        a program's variable
GVL.motors[2].speed               a field of an element of an array of structures
nsu=CODESYSSPV3/3S/IecVarAccess;s=|var|CODESYS Control for Linux SL.Application.GVL.x
                                  a node id, if you have one
```

**Discover tags** は、アプリケーションがエクスポートするものを、その型で一覧します。STRING は `string`、BYTE は `uint16`、TIME は `int64`(ミリ秒)、列挙は `int32`、整数の幅はそのまま、REAL と LREAL は `float` です。ランタイムは STRING、BYTE、TIME を PLCopen モデルの型として伝えます(例: `ns=3;i=3013`)。ドライバーは `HasSubtype` 参照をたどって、それが属する標準の型を求めます。BYTE への書き込みを Byte として送るのもこの方法です。各変数は、そのシンボルに与えられたアクセスを持ちます。構造体と配列は中まで辿り、フィールドごと、要素ごとに 1 つのポイントになります。ランタイム自身のプロパティ(`|vprop|`)、タスクリスト、Server オブジェクトは除外します。

配列は最初の 32 要素(`arrayElements`)を一覧します。1000 要素のバッファはダッシュボードにとって 1000 個の項目ではないからで、タグはシンボルで任意の要素を指定できます。一覧は `browseMaxNodes` で止まり、そのことを伝えます。`browseRoot` にシンボル(`Application.GVL_Demo`)を指定すると、アプリケーションの一部を一覧します。ブラウズは幅優先なので、リストの変数はその配列の要素より先に来ます。応答は、ランタイムが受け付けるサイズに収められます(1000 要素の配列が 100 個ある応答では、ランタイムは接続を閉じます)。

設定: OPC UA のオプションに加え、`device`(PLC の名前で、ランタイムが複数を一覧する場合のみ)、`application`(Application という名前のものがない場合のみ)、`arrayElements`。綴りを誤ったオプションは、有効なものを列挙したエラーになります。パスワードはシークレットで、すべてのデバイスのシークレットと同様に保存され、伏せられます。

**ランタイムがクライアントに求めること。**ランタイムは、読み取り、ブラウズ、モニターアイテムについて、1 リクエストあたり 100 の `OperationLimits` を公開し、それより大きいリクエストは `BadTooManyOperations` で拒否します。ドライバーは接続時にこの制限を読み、すべての OPC UA デバイスで、すべてのリクエストをそれに合わせて分割します(CODESYS ランタイムが最初に問題になったケースでした。それ以前は、ドライバーは検出したすべてのタグを float として報告し、100 を超える変数を持つデバイスのタグは 1 つも読めませんでした)。サンプリングの既定は 1 秒、キューは 1 項目です。PLC には守るべきスキャンがあり、すでに読み取っている Ignition ゲートウェイからそれを奪うべきではないからです。もっと多く求めるには `samplingIntervalMs` を設定してください。

**ダウンロード、再起動、リンク切れ。**ランタイムの再起動や新しいプログラムのロードでセッションが切れます。デバイスは切断状態になり、すべてのタグは「PLC のランタイムが応答していません」という理由で bad と読まれ、HotLoop はバックオフを置いて自動的に再接続し、今あるシンボルを読み取ります。読み取れていたシンボルが 2 回続けて存在しないとして拒否された場合は、ランタイムがセッションを保ったままダウンロードが行われたものとみなし、同じ再接続のためにセッションを破棄します。プログラムにない変数のタグは、サーバーの理由とともに bad と読まれ、再接続は起こしません。

**ランタイムの OPC UA サーバーの保護。**CODESYS Control ランタイムは、OPC UA サーバーに証明書ができるまで、保護されていないエンドポイントしか提供しません。証明書ができると、`CommunicationPolicy` のポリシー(既定は AES128-SHA256-RSAOAEP、Basic256Sha256、AES256-SHA256-RSAPSS)も Sign と SignAndEncrypt で提供します。CODESYS は、その証明書を Security Screen(CODESYS Security Agent、Devices、コントローラー、OPC UA Server)で作成し、クライアントの証明書を「Certificates in Quarantine」から「Trusted Certificates」に移してクライアントを信頼する方法を文書化しています。Linux ランタイムの PLC シェルは、IDE なしで同じことができ、CODESYS がデバイスエディターの PLC シェル用に挙げているコマンド(`cert-getapplist`、`cert-genselfsigned <n>`、`cert-getcertlist quarantine`、`cert-export`、`cert-import trusted`)を、Linux ランタイムが文書化している Unix ソケット(`/var/opt/codesyscontrolapi/plcshell.sock`、「Accessing the PLC Shell」)経由で実行します。デバイスを `securityMode` `SignAndEncrypt` と `securityPolicy` に設定して一度接続すると(HotLoop 自身の証明書がランタイムの quarantine に入り、その旨のメッセージとともに接続は拒否されます)、その証明書を信頼すれば、デバイスは読み取れます。示していないもの: IDE の Security Screen、CA 署名の証明書、保護されたランタイムでのユーザー管理。

**ライセンスのないランタイムは自分で止まります。**ライセンスのない CODESYS Control ランタイムはデモモードで動作し、約 2 時間後にシャットダウンします(ランタイムのログには、起動のたびに `no runtime license - running in demo mode(~2 hours)` と出ます)。HotLoop から見れば、他のランタイム再起動と同じです。デバイスは「PLC のランタイムが応答していません」とともに切断状態になり、何かがランタイムを再び起動する(コンテナーの再起動ポリシー、systemd ユニット)と、自動的に復帰します。HotLoop の中で 2 時間を数えるものはなく、この停止を特別扱いすることもなく、ランタイムを代わりに再起動することもありません。再び起動されないランタイムは、切断されたままです。ライセンスなしでコンテナー内の 4.22.0.0 ランタイムに対して実行した結果、起動から 2 時間 5 分後に終了コード 0 で自分で停止し、コンテナーの再起動ポリシーが 31 秒後に再起動し、その 82 秒後にアプリケーションが動作し、アプリケーションの開始から 35 秒後にデバイスが再び良好に読み取られました(停止から 2 分 28 秒)。手作業は一切ありません。

**書き込み。**タグは、すべてのデバイスと同様に、誰かが書き込み可能と印を付けるまで読み取り専用で、セットアップが作るものは一つも書き込み可能ではありません。その上で、書き込みのゲートは OPC UA と同じで、その手前に PLC 側の半分が加わります。読み取り専用でエクスポートされたシンボルや、ユーザーに書き込みが許可されていないシンボルへの書き込みは、PLC の言葉で拒否され、送信されません。

**統合フローからのセットアップ**(`codesys`): ランタイムのアドレス、OPC UA のセキュリティに関する質問、そして必要に応じて、保持するポイントの最初のダッシュボード(WebVisu になるはずだった画面。[統合](/ja/iot/integrations/#codesys)を参照)。コンテナー内の 4.22.0.0 ランタイムで検証しました。それが意味しないことは、状況の表を参照してください。

### Modbus TCP/RTU

1979 年からの働き者です。PLC、VFD、電力メーター、RTU、そして他に良いものがないすべてのゲートウェイの最後の砦です。

```
holding:100:float32:CDAB    a float across registers 100-101, word-swapped
holding:40:bit3             bit 3 of register 40
holding:200:string16        16 characters from register 200
input:12:int16              a signed input register
coil:5                      a single coil
```

**ワード順序**は人が最もよく間違える設定で、順序の誤った float は画面上では明らかな間違いに見えず、真実ではないもっともらしい数字になります。ベンダーのマニュアルが載せている名前で、4 つの並びをすべてサポートします。`ABCD`、`CDAB`、`BADC`、`DCBA`。デバイスの既定は `byteOrder` で設定し、タグごとに 4 番目のアドレスフィールドで上書きします。

**アドレス指定**は加工しない 0 始まりです。図面が従来の 40001 形式の番号を使っているなら、`oneBased: true` にして、図面の番号をそのまま書いてください。これを 1 つ間違えるのは、Modbus で最も古いバグです。

読み取りはブロックにまとめられます。隣接または近接するレジスターは 1 つのリクエストになります。`maxGap` は、往復をもう 1 回するのを避けるために、使っていないレジスターをいくつまで一緒に読む価値があるか(既定 8)を制御し、`maxBlock` は 1 リクエストの上限です(既定 120、プロトコルの上限 125)。

ホールディングレジスターの 1 ビットを書き込むのは、読み取り、変更、書き込みです。Modbus にはそこにアトミックなビット設定がないからです。他の 15 ビットは保たれます。

### MQTT と Sparkplug B

通常の MQTT、または **完全な primary host application** としての Sparkplug B。

通常のトピック:
```
mqtt:plant/line1/temperature              a scalar payload
mqtt:plant/line1/state|data.temperature   JSON, extracted by path
mqtt:plant/+/flow                         wildcards work
```

Sparkplug のメトリクス:
```
spb:GroupId|EdgeNodeId|DeviceId|Metric/Name
spb:Plant|Edge1||Node/Uptime               empty device = a node-level metric
```

primary host として、ドライバーは仕様が求めるのに、ほとんどの統合が省略していることを行います。

- retained の `STATE` birth を対応する will とともに公開するため、エッジノードはタイムアウトで推測するのではなく、ホストが落ちたことを見られます。既定は Sparkplug 3.0 形式(JSON を運ぶ `spBv1.0/STATE/<host>`)で、3.0 より前の `ONLINE`/`OFFLINE` 文字列にするには `legacyState` を設定します。
- ノードごとの循環するシーケンス番号を追跡し、番号が飛んだらノードに rebirth を求めます。飛んだということはメッセージを取りこぼしたということで、エイリアステーブルをもう信頼できないからです。
- 自分が再接続したあとに rebirth を要求します。離れていたホストには、その間に何が変わったか分かりません。
- `NDEATH` を `bdSeq` で `NBIRTH` と対応付けるため、前のセッションから残った death certificate が現在のセッションを終わらせることはできません。

メッセージの順序は強制されます。Sparkplug のメッセージを並行して配信すると順序が入れ替わり、健全なノードがメッセージを落としているように見え、rebirth の嵐を引き起こします。

### EtherNet/IP (CIP)

Allen-Bradley の ControlLogix、CompactLogix、Micro820。タグに名前があるので、コントローラーに何を持っているか尋ねられます。

```
Temperature                    type from the tag's declared dataType
Speed:dint                     an explicit type wins
Program:MainProgram.Speed      a program-scoped tag, the colon is part of the path
Zones[0].Heater.On:bool        array elements and UDT members
```

CIP は型が厳格で、宣言された型が一致しない読み取りはコントローラーが拒否するため、型をどこかから得る必要があります。タグの `dataType` から、または優先される `:type` サフィックスから取ります。不明な場合は、ほとんどのプロセス値がそうである `REAL` に戻ります。

読み取りは multi-service リクエストにまとめられ、まとめが失敗したときは、1 つの誤ったタグパスが他の 19 個を見えなくしないよう、個別の読み取りに戻ります。

### S7comm

Siemens の S7-300、400、1200、1500 を、ラックとスロットによる ISO-on-TCP で接続します。

```
db1:0:real        a REAL at DB1.DBD0
db1:4:dint        a DINT at DB1.DBD4
db1:8.3:bool      bit 3 of DB1.DBB8
db2:20:string32   a 32-character STRING
m:10:word         merker word MW10
i:0.1:bool        input I0.1
q:2:byte          output byte QB2
```

1 バイトより広いものには型が必要です。4 バイトが REAL なのか DINT なのかはプロトコルには分からず、それはワイヤーではなく PLC プログラムに関する事実です。

既定はラック 0、スロット 1(S7-1200/1500)です。S7-300/400 は通常スロット 2 です。`connectType` の既定は 3(S7 Basic)なので、エンジニアが TIA Portal に使いたい PG 接続スロットをゲートウェイが占有しません。

ブラウズはありません。S7 CPU はデータブロックの構成を公開せず、それは TIA Portal のプロジェクトにあります。

### MTConnect

読み取り専用の工作機械テレメトリーです。MTConnect にはコマンドチャネルがなく、このドライバーもあるふりはしません。

`dataItemId` または名前で指定してください。どちらが安定しているかはエージェントによって異なり、機械のドキュメントはどちらか一方しか示していません。

動く統合と、もっともらしいだけの統合を分ける 2 つの詳細です。`UNAVAILABLE` はエージェントが読み取り値がないと明示的に言っているもので、テキストの「UNAVAILABLE」でも 0 でもなく、bad の品質になります。そして Condition の意味は、たいてい空の文字データではなく、要素名(`Normal`、`Warning`、`Fault`、`Unavailable`)にあります。

`Browse` は `/probe` を読み、コンポーネントツリーを任意の深さまでたどります。

### HTTP / REST

電力量計、環境センサー、OEM コントローラー、そして内部で独自のプロトコルを話すゲートウェイの REST 側のための、何でも受ける手段です。

```
power.kw                      nested fields
readings[0].value             array indexing
zones[name=Zone1].temp        select an array element by a field value
$.data.temperature            a leading $. is accepted
```

3 番目の形式が重要です。こうした API は順序のない `{name, value}` オブジェクトの配列を返したがり、位置でインデックスするのは、ファームウェアの更新を待っているバグです。

1 つのリクエストでデバイスのすべてのタグを扱います。`Browse` はドキュメントをたどり、すべてのスカラーを、そこに至るパスとともに報告します。

### ボックスの状態

HotLoop が動いているマシンを、読み取り専用のデバイスとして公開します。`cpu_util_pct`(最後の読み取り以降の、アイドルでない CPU 時間)、`mem_util_pct`(MemTotal に対する MemAvailable)、`disk_util_pct`(ボックスのディスクで、`diskPath` に読み取り専用でマウントされたホストのルートの statfs、既定は `/host`)、`data_util_pct`(`dataPath` のボリューム、`/data`)、そして `jitterFile` がリアルタイムエージェントが書き換える JSON ファイル `{"core1_us":3.2,"core2_us":2.9,"core3_us":4.1}` を指す場合の `rtos_jitter_core1_us` から `core3_us`(5 分より古いファイルは bad と読まれます)です。CPU とメモリは `procRoot`(`/proc`、ホストのものがマウントされている場合は `/host/proc`)から取ります。読み取れない値は理由付きの bad の品質になり、0 にはなりません。このデバイスは `HOTLOOP_BOX_HEALTH_NODE` が作ります([OPC UA サーバー](/ja/edge/opc-ua-server/#embernet-ダッシュボード向けのボックスの状態))。

### UniFi Network

プラントのネットワークをデバイスとして扱います。UniFi コンソール 1 台の 1 サイト、そのスイッチ、すべてのスイッチポート、PoE の消費、WAN リンク、サイトの状態が、機器がアダプトされるにつれて自動的に作られるタグになり、有効化するまでは読み取り専用です。コンソールごとにログイン 1 つ、証明書は固定され、コンソールのパスワードはデータベースで暗号化されます。コンソールを変更するのは、人が有効化するいくつかのコマンドタグ(位置確認 LED、再起動、ポートの PoE 電源サイクル。UNIFI.md を参照)に限られます。コンソールのイベント websocket も待ち受けるため、スイッチが落ちるとその時点でログブックに記録されます。その下では引き続きポーリングが真実です。UniFi タブは、概要、マップ、フェイスプレート、クライアント、ネットワーク、WiFi を描画します。詳細は [UniFi Network](/ja/iot/unifi/) にあります。

### SNMP

SNMP エージェントを持つものなら何でも対象です。スイッチ、UPS、PDU、電力メーター、SNMP エージェントを実行しているすべての Linux ボックス。読み取り専用です。HotLoop は SNMP SET を決して送りません。SET はスイッチの設定を変更できてしまい、このドライバーの目的はプラントのネットワークを運用することではなく、見ることだからです。

```
1.3.6.1.2.1.1.5.0             sysName
.1.3.6.1.2.1.1.3.0            sysUpTime, a leading dot is accepted
1.3.6.1.2.1.2.2.1.8.2         ifOperStatus of the interface with ifIndex 2
```

タグのアドレスは、1 つのインスタンスの OID で、ドットで区切った数字です。スカラーは `.0` で終わり、テーブルのセルはその行のインデックスで終わります。タグの `dataType` が、何になるかを決めます。

* エージェントが送った数値(Integer、Gauge32、Counter32、Counter64、TimeTicks)は、その数値です。スケールとオフセットは他と同じように適用されます。
* OCTET STRING はテキストで、タグが数値の場合は解析されます。負荷平均(`laLoad` はテキストの `0.15`)や、エージェントの向こうの温度がこうして届きます。数値でないテキストは、そう伝える bad の読み取り値になり、0 にはなりません。
* 印字できない OCTET STRING(MAC アドレス)は `0x` と 16 進数です。

**カウンターは生の値です。**Counter32 や Counter64 は増えるだけで、折り返します。タグはエージェントが送ったものを保持し、レートはタグを読む側の仕事です。Counter64 は float として保持され、2^53 まで正確です。回線速度のポートでも、そこに達するには数十年かかります。

**TimeTicks は 100 分の 1 秒単位**なので、`sysUpTime` を通常のタグとして読むと 1/100 秒です。統合が代わりに秒に変換します。手で作ったタグは `scale` を `0.01` にしてください。

**エージェントにないオブジェクトは、理由付きの bad の読み取り値であり**、同じリクエストの他のものは読めます。v2c と v3 はどれがなかったかを伝え、存在しないオブジェクトにリクエスト全体のエラーで答える v1 では、ドライバーがそれを外して残りをもう一度尋ねます。エージェントにとって大きすぎる応答は、半分ずつに分けて再度尋ねられます。

デバイスオプション(`config`):

| オプション | 意味 |
|---|---|
| `version` | `1`、`2c`、`3`。既定は `2c` |
| `community` | v1 と v2c のコミュニティ。それらでは必須で、**既定値はありません。**`public` は、プラントのスイッチが尋ねた人なら誰にでも読まれるようになる方法だからです。シークレット |
| `username` | v3 のユーザー |
| `securityLevel` | `noAuthNoPriv`、`authNoPriv`、`authPriv`。既定: プライバシーのパスフレーズがあれば `authPriv`、認証のパスフレーズだけなら `authNoPriv`、それ以外は `noAuthNoPriv` |
| `authProtocol` | `MD5`、`SHA`、`SHA224`、`SHA256`、`SHA384`、`SHA512`。既定は `SHA` |
| `authPassword` | 認証のパスフレーズ。シークレット |
| `privProtocol` | `DES`、`AES`、`AES192`、`AES256`、`AES192C`、`AES256C`。既定は `AES` |
| `privPassword` | プライバシーのパスフレーズ。シークレット |
| `contextName` | v3 のコンテキスト。ほとんどの場合は空 |
| `transport` | `udp`(既定)または `tcp` |
| `retries` | 応答のなかったリクエストを再送する回数、0 から 10。既定は 1 |
| `maxRepetitions` | ウォークでの GETBULK 1 回あたりの行数。既定は 10 で、最小のエージェントでも応答できる値 |
| `browseRoots` | ポイントを検出するときにたどる OID。既定: system、インターフェーステーブル、ホストリソース、ロードテーブル、SNMP エージェントの extend の出力 |
| `browseMaxNodes` | ブラウズが止まる位置。既定は 2000 |

アドレスは `host` または `host:port` で、ポートの既定は 161 です。

**誤ったコミュニティには何も返ってきません。**SNMPv1 や v2c のエージェントは、知らないコミュニティを持つリクエストを捨てるので、誤ったコミュニティ、誤ったポート、ファイアウォール、停止したエージェントは、すべてタイムアウトに見えます。HotLoop のメッセージはこの 4 つすべてを伝えます。SNMPv3 は区別してくれます。誤ったパスフレーズや未知のユーザーはそのまま拒否され(`ErrAuthRejected`)、HotLoop は同じ認証情報を再試行するまで長く待ちます。

`Browse` は HotLoop が名前を挙げられるサブツリーをたどり、各オブジェクトに名前を付けます。`sysName`、`ifOperStatus.2`、`ifHCInOctets.2`、`laLoad.1` のような MIB の名前で、知らないものは `oid.1.3.6.1...` の形の OID です。その名前と、背後にある OID、型、単位は、それを定義する MIB から取られます。SNMPv2-MIB(RFC 3418)、IF-MIB(RFC 2863)、HOST-RESOURCES-MIB(RFC 2790)、SNMP エージェントの UCD-SNMP-MIB と NET-SNMP-EXTEND-MIB です。エージェントが持つそれ以外のものも読み取れます。OID でタグに追加してください。

統合([統合](/ja/iot/integrations/#snmp)を参照)が代わりに尋ねてくれます。

### BACnet/IP

ビルオートメーションのコントローラー、メーター、サーモスタットなど、BACnet を話す IP ネットワーク上のあらゆるものです。読み取り専用です。HotLoop は BACnet のプロパティを決して書き込みません。書き込みは優先度配列を通じてコマンド可能な出力に反映され、設定されたまま残った優先度は、設定した人が帰ったあとも機器をその状態に留めてしまうからです。これは意図して設計するべき機能であり、放置しておくものではありません。

実際のデバイスから記録したフレームを、常に実行されるテストでデコードして検証し、テスト中はそのデバイスに対して検証しています。

```
analog-input:1                present value of analog input 1
ai:1                          the same, abbreviated
av:3.units                    a property other than the present value, by name
analog-input:1.117            or by number
multi-state-value:2           present value of a multi-state value
```

タグのアドレスはオブジェクトで、`<type>:<instance>` です。現在値でない場合は、ドットとプロパティが付きます。型は名前または略称で書きます。`analog-input`(`ai`)、`analog-output`(`ao`)、`analog-value`(`av`)、`binary-input`(`bi`)、`binary-output`(`bo`)、`binary-value`(`bv`)、`multi-state-input`(`msi`)、`multi-state-output`(`mso`)、`multi-state-value`(`msv`)、`accumulator`(`acc`)、`integer-value`(`iv`)、`positive-integer-value`(`piv`)、`large-analog-value`(`lav`)、`characterstring-value`(`csv`)。名前で書けるプロパティは `present-value`、`object-name`、`description`、`units`、`status-flags`、`out-of-service`、`reliability`、`number-of-states`、`state-text`、`object-type`、`object-identifier`、`object-list`、`vendor-name`、`vendor-identifier`、`model-name`、`firmware-revision`、`application-software-version` で、それ以外のプロパティは番号で書きます。

タグが何になるかは `dataType` に従います。デバイスが送った数値(real、double、unsigned、signed、enumerated、boolean)はその数値で、バイナリオブジェクトの `active` は 1、`inactive` は 0 です。文字列はテキストで、タグが数値でテキストが数値ならその数値です。`null` の現在値は、デバイスに報告するものがないと伝える bad の読み取り値です。複数の値を持つプロパティ(オブジェクトリスト)はタグにできません。

**ステータスフラグは読み取り値の一部です。**ポーリングのたびに、オブジェクトのステータスフラグを現在値と同じリクエストで尋ね、**fault** フラグが立っているオブジェクトは、理由付きで **bad** と読まれます。**out of service** や **overridden** のものは **uncertain** と読まれます。その現在値は、測定値ではなく、人やプログラムが置いたものだからです。トレンドチャートとレポートは、uncertain の読み取り値を bad と同様に除外します(品質のルール)。**In alarm** だけの場合は、アラーム中のポイントの良好な読み取り値です。

**デバイスにないものは理由付きの bad の読み取り値で、残りは読み取れます。**ReadPropertyMultiple はプロパティごとに個別に応答するため、存在しないオブジェクト(`unknown-object`)や、持っていないプロパティ(`unknown-property`)は、そのタグだけが失敗し、他は失敗しません。ReadPropertyMultiple を拒否するデバイスは、それ以降、1 プロパティずつ読み取ります。

**セグメント化はしません。**クライアントはデバイスに、セグメント化された応答は受け取れないと伝えます。応答が 1 フレームに収まらないデバイスは中断し(`segmentation-not-supported`)、HotLoop は一度に尋ねるオブジェクト数を半分にします。オブジェクトリストが大きすぎて一度に送れないデバイスは、1 要素ずつ読み取ります。

デバイスオプション(`config`):

| オプション | 意味 |
|---|---|
| `deviceInstance` | このアドレスのデバイスが持つはずのインスタンス番号。設定されていてデバイスが別の番号を言った場合、接続は拒否されます。再利用されたアドレスで別のデバイスが応答したり、コントローラーが交換されたりすることが、プラントがきれいに見える誤った数字を得る原因だからです |
| `localAddress` | 送信に使う、このマシンのネットワークカードのアドレスで、複数のカードを持つホスト用。通常は空 |
| `retries` | 応答のなかったリクエストを再送する回数、0 から 10。既定は 1 |
| `browseMaxObjects` | ブラウズが止まる位置。既定は 1000 |

アドレスは `host` または `host:port` で、ポートの既定は 47808 です。BACnet/IP には認証情報がないので、隠すものもありません。

**接続すると、デバイスに誰かを尋ねます。**HotLoop はデバイスにユニキャストの Who-Is を送り、I-Am からデバイスインスタンスを取得します。それに応答しないデバイスには、ワイルドカードインスタンス(4194303)で自分自身のデバイスオブジェクトを尋ねます。標準では、デバイスはこれに自分自身として応答します。どちらにも応答しないデバイスは、両方を試したと報告されます。よくある原因が、見た目では同じだからです。誤ったアドレスやポート、ファイアウォール、停止したデバイス、ルーターの向こうのネットワークにあるデバイスです。

**ルーティングは実装されていません。**HotLoop は UDP データグラムを送れるデバイスと通信します。BACnet ルーターの向こうの MS/TP トランクや、別の BACnet ネットワークにあるコントローラーには到達できず、BBMD からしか到達できないデバイス(foreign device registration)にも到達できません。ルーター自身の BACnet/IP 側のアドレスを指定するか、前にゲートウェイを置いてください。[ゲートウェイモード](#それ以外すべて-ゲートウェイモード)を参照してください。

`Browse` は、デバイス自身のオブジェクト(名前、ベンダー、モデル、ファームウェア)、そのオブジェクトリスト、そして HotLoop が読み取るすべてのオブジェクトの名前、説明、単位、現在値、ステータスフラグ、マルチステートオブジェクトの状態テキストを読み取ります。タグはオブジェクト自身の名前から付けられ、2 つのオブジェクトが名前を共有する場合はアドレスが追加されます。単位はラベルになり、意味がある場合はエンティティクラスになります。摂氏は `°C` と `temperature`、相対湿度のパーセントは `%` と `humidity`、キロワット時は `kWh` と `energy` です。HotLoop にラベルがない単位は、ラベルなしのままにして、説明にその番号で記載します。これらの単位の番号と名前は、それぞれの名前に自らの表が与える番号を送る実際のデバイスで検証されています。統合([統合](/ja/iot/integrations/#bacnetip)を参照)が代わりに尋ねてくれます。

## 外へ送る: Kafka API

ここまでのすべては、デバイスの値を取り込みます。HotLoop は、値を Kafka ブローカーにイベントストリームとして送り出すこともできます。ヒストリアンが保持するすべての読み取り値と、システムログのすべての行(アラーム、デバイスの接続と切断、変更)を、指定したトピックに JSON で送ります。設定のヒストリアンのターゲットで設定し、Apache Kafka、Redpanda、その他 Kafka API を話すものを、TLS と SASL ログインで受け付けます。レコードの形式、ここでの「at least once」の意味、検証済みのものとそうでないものは、[ヒストリアンのターゲット](/ja/iot/historian-targets/#kafka-apiイベントストリーム)にあります。クライアントは [franz-go](https://github.com/twmb/franz-go) です。

## それ以外すべて: ゲートウェイモード

**PROFINET · EtherCAT · HART · DNP3 · FINS · MELSEC/SLMP · CANopen · FANUC FOCAS**

これらはネイティブには話さず、ドライバーもありません。スタブで埋められるのを待っている穴ではなく、意図した選択です。

これらのプロトコルを使う現場には、ほとんどの場合、OPC UA や Modbus で再公開するゲートウェイがすでにあります。OPC UA サーバー付きの PROFINET IO コントローラー、Modbus マップ付きの HART マルチプレクサなどです。デバイスをそのエンドポイントに向け、OPC UA または Modbus として設定してください。

現場の既存のゲートウェイがすでにやっていることを、それぞれ重複して行うドライバーをさらに 8 つ書けば、機器のテストが最も難しいプロトコルで、微妙に誤る可能性のあるものが 8 つ増えます。現場に本当にゲートウェイがなく、これらのいずれかをネイティブで必要とするなら、それはスケジュールすべき実際の作業であり、「not implemented」を記録するファイルを追加することではありません。

**このツリーにはプレースホルダーのドライバーはありません。**プロトコルは、動く実装があるか、このセクションにあるかのどちらかです。モデルが宣言するすべてのプロトコルにコンパイル済みのドライバーがあり、その逆もそうであることを、テストが強制しています。

## デバイスの認証情報

デバイスの `config` と `address` は、ドライバーがログインに使うものを見つける場所です。以下は各プロトコルが読む認証情報で、すべて API からは書き込み専用です(4.15.1)。すべてのロールに `[redacted]` と表示され、プレースホルダーを送るかキーを省略して保存すると保存済みの値が保たれ、新しい文字列は置き換えます。規則と、API を通らないものは[認証とユーザー](/ja/iot/authentication/#デバイスの資格情報は書き込み専用です)にあります。

| プロトコル | 設定内の認証情報 | アドレス内の認証情報 |
|---|---|---|
| OPC UA | `password`(`username` とともに) | なし: アドレスのユーザー情報は隠され、ドライバーは無視します |
| MQTT / Sparkplug B | `password`(`username` とともに) | クライアントが使う `mqtt://user:pass@host` |
| HTTP / REST | `password`(`username` とともに、Basic 認証で送信)、`Accept` や `Content-Type` のような通常のものを除く `headers` のすべての値(API キーや `Authorization` ヘッダーを入れる場所)、認証情報に触れる `body` と `writeBody` | アドレスと `writeUrl` の `http://user:pass@host` と `?api_key=` 形式のクエリ値 |
| MTConnect | `password`(`username` とともに)、同じ例外を除く `headers` のすべての値 | `http://user:pass@host` とクエリ値 |
| UniFi Network | `password`(`username` とともに)。暗号化された状態でしか保存されません: 鍵(下記)がないとデバイスを保存できません | なし: アドレスはコンソールの `https://` の URL |
| BACnet/IP | なし | なし: アドレスは `host` または `host:port` |
| CODESYS | OPC UA と同様に `password`(`username` とともに) | なし: アドレスのユーザー情報は隠され、ドライバーは無視します |
| SNMP | `community`(v1、v2c)、`authPassword` と `privPassword`(v3)、`username` とともに | なし: アドレスは `host` または `host:port` |
| Modbus、S7comm、EtherNet/IP | なし | なし: アドレスのユーザー情報は隠され、ドライバーは無視します |

**保存時の暗号化。**`HOTLOOP_SECRET_KEY_FILE` を設定すると(チャートが、生成した鍵で設定します)、上の表の設定の列にあるすべての認証情報が、データベースの外にあるその鍵で暗号化されてデータベースに保存されるため、ダンプやバックアップには暗号文が入ります。HotLoop の他の部分とドライバーは、その違いを知りません。URL(`mqtt://user:pass@host`、`?api_key=`)や HTTP の `body` のような自由テキストに書いた認証情報も暗号化されます。アドレスやオプション全体が封印され、入力したとおりに戻り、秘密のない URL は読める状態のままです。それでも、認証情報を置く場所としては `password` オプションのほうが整っています。[バックアップと復元](/ja/iot/backup/#デバイスの認証情報と秘密鍵)を参照してください。

認証情報のように見える名前を持つ他のオプション(`password`、`token`、`secret`、`apikey`、`authorization`、`private`、`passphrase` を含む、`key` で終わる、あるいは `pass`、`pw`、`auth`、`cred`、`sig` などの単語を含むもの)も、どのプロトコルのものであっても隠されます。そのため、後からドライバーに追加されたオプションは、隠さなくてよいと誰かが決めるまで隠されます。テストはすべてのドライバーのオプションをたどり、それぞれが認証情報のリストか、認証情報ではないと分かっているオプションのリストに載るまで失敗します。完全な規則は[認証とユーザー](/ja/iot/authentication/#デバイスの資格情報は書き込み専用です)を参照してください。

## デバイスの追加

1. **Devices → Add device.**プロトコルを選び、アドレスを入力します。
2. プロトコルが対応している場合は **Discover tags** を使います。OPC UA、EtherNet/IP、MTConnect、MQTT(Sparkplug の birth のあと)、HTTP、SNMP、BACnet/IP、CODESYS が対応します。Modbus と S7comm は自分のポイントを列挙できないので、デバイスのドキュメントを見て宣言してください。
3. 取り込んだタグは**読み取り専用**で作成されます。デバイスがたまたま公開しているポイントは、誰かがコマンドしてよいと決めたポイントではありません。タグは 1 つずつ、意図して書き込み可能にしてください。
4. 生のカウントには `scale` と `offset` を設定します。`engineering = raw × scale + offset`。チャネルが死んでいるときや範囲外のときに計器がコードを送る場合は、数値として読まれずに bad と読まれるよう、[データなしの値](#データなしの値)に挙げてください。
5. ノイズのあるものには `deadband` を設定します。問題にならないほど小さな変化についてのヒストリアンへの書き込みを抑えます。設定しないと、最下位ビットが揺れる 12 ビットセンサーが、スキャンのたびに永遠に 1 行を書き込みます。

## データなしの値

熱電対が焼き切れた記録計は、静かになりません。答え続け、レジスターに入れるのはコードです。「undefined」は 0x8005、「over range」は 0x7FFF です。スケール 0.1 の int16 として読むと、0x8005 は -3276.3 度で、これを直すまでは **good** の品質で返り、本物の温度としてヒストリアンに入り、アラームが判断するよう、そこに残っていました。壊れたセンサーが冷たいセンサーに見えたのです。

そこで、タグには「測定なし」を意味する生の値を挙げられるようにしました。それぞれに理由があります。読み取り値の生の値がリストにあれば、読み取り値は **bad** になり、理由が付き、スケールとオフセットはそれに触れません。

```json
{
  "deviceId": "dx-1", "name": "ch01", "address": "input:1:int16",
  "dataType": "float", "unit": "C", "scale": 0.1, "enabled": true,
  "noData": [
    {"raw": "0x7FFF", "reason": "+over"},
    {"raw": "0x8001", "reason": "-over"},
    {"raw": "0x8002", "reason": "skip"},
    {"raw": "0x8004", "reason": "error"},
    {"raw": "0x8005", "reason": "undefined"},
    {"raw": "0x7F7F", "reason": "power fail"},
    {"raw": "0x7FFA", "reason": "burnout up"},
    {"raw": "0x8006", "reason": "burnout down"}
  ]
}
```

この 8 つは、Yokogawa DX シリーズのコードで、DX 通信マニュアル(IM 04L41B01-17E、4.3 節、4-35 ページ)にあるものです。HotLoop 固有のものではなく、すべてのプロトコルのすべてのタグにある同じフィールドで、DX のリストは、最初に問題になったものにすぎません。各コードはタグにあるので、別の単位で本当に 0x7F7F を読み取れる記録計のチャネルは、それを読み取り値として保ちます。

| フィールド | <span class="sr-only">詳細</span> |
|---|---|
| `raw` | デバイスのコード。マニュアルが印刷しているとおりに書きます。`"0x8005"`(16 進)、`"-32763"` または `32773`(10 進)。文字列、または数値そのまま。必須 |
| `reason` | 読み取り値の品質が伝える内容。最大 120 文字。省略すると `raw value 0x8005 means no measurement` と読まれるため、読み取り値が理由を言わずに bad になることはありません |

タグエディターでは **データなしの値** のボックスです。1 行に 1 つ、コード、スペース、理由の順に書きます。

### 書く数値

レジスターに基づく Modbus のポイントでは、コードは、ポイントのバイト順とワード順を適用したあとにデバイスが保持する整数です。ポイントがデコードされる数値と同じなので、マニュアルが「計器は 8005h を返す」と言っているなら、ここでは正確に `"0x8005"` です。

- **int16 とその他の符号付きの型。**`0x8005` と `-32763` は同じレジスターで、`32773` も同じです。マニュアルが使っている書き方で書いてください。3 つとも一致します。型に収まらないコード(int16 での `0x10000`)は、デバイスが接続するときに拒否されます。決して一致しないリストはエラーより悪いからです。同じ値を 1 つのタグで 2 通りに書くことも拒否されます。
- **uint16 とその他の符号なしの型。**`0` から、その型の最大値まで。負の数は拒否されます。
- **int32、uint32、int64、uint64。**32 ビットと 64 ビットで同じ規則です。`CDAB` のワード順の int32 での `0x7FFFFFFF` は、ワイヤーから来た順ではなく、ワードを正しい向きに直したあとの値です。
- **float32 と float64。**コードはレジスターのビットパターンなので、16 進でなければなりません。quiet NaN は `0x7FC00000` です。10 進は拒否されます。float としての 32773 とビットパターンとしての 32773 は別のもので、推測しないからです。
- **ビット、コイル、ディスクリート入力、文字列。**比較する生の数値がないため、これらに `noData` を設定すると、デバイスが接続するときに拒否されます。

チェックは、デコード、スケール、オフセットの前の、生のビットで行われます。

### 他のプロトコル

すでにデコードされた数値を渡すすべてのドライバーが、同じリストをチェックします。S7comm、EtherNet/IP、OPC UA、HTTP、MQTT(検出されたデバイスを含む)です。比較されるのはそのデコード済みの数値で、整数として比較されるので、その数値のとおりに書いてください。0x8005 を保持する S7 INT は -32763 なので、`-32763` と書きます。ここでの 16 進は、同じ数を書く別の方法にすぎません。デコードされた数値は幅を失っており、ビットパターンとして読み戻せないからです。小数の値は決して一致しません。このリストは、デバイスがこのようなコードを送る場所でだけ設定する価値があり、MTConnect と UniFi が報告するもののほとんどはそうではありません。

### センチネルが行うこと

- **品質**は `bad` で、読み取り値に理由が付きます。`GET /api/values` とライブストリーム(`reason`)、タグ画面の品質の隣、そしてタグのエンティティでは `quality_reason` 属性として表示されます。
- **値**は空で、0 でも、スケールされたコードでもありません。スケールとオフセットは適用されません。
- **ヒストリアン**は、他の bad の読み取り値と同じく、品質を bad として記録し、値の列には意味のあるものが入りません。良好な読み取り値がないバケットは、他の bad の読み取り値と同様に、トレンドで空白として表示されます。
- **アラーム。**bad の読み取り値は、値のアラームを決して作動させません。上限、下限、等しい、変化率のすべてが、他の bad の読み取り値と同様に、以前の状態を保ちます。タグの `bad-quality` アラームは作動し、その既定のメッセージに理由が入ります(`dx-1/ch01 bad-quality: undefined`)。独自のメッセージに理由を入れるには `{reason}` を使ってください。
- **ログブック**はタグのエンティティが bad になったことを記録し、理由はエンティティの `quality_reason` 属性です。

### 保存される場所

タグに、タグとともに保存されます。API では `POST /api/tags` の `noData` リスト([HTTP API](/ja/iot/api/#post-apitags)を参照)で、エディターでは上のボックスで、Edge Relay ではデバイスファイルのタグにある同じ JSON です([Edge Relay リファレンス](/ja/edge-relay/reference/)を参照)。タグを保存すると実行中のデバイスが再読み込みされるため、変更は次のポーリングから有効になり、手で再起動するものは何もありません。再検出しても、タグのリストはそのままです。

## 品質

すべての読み取り値は `good`、`uncertain`、`bad` のいずれかを持ちます。

**Bad は値が分からないという意味で、0 という意味ではありません。**ポイントを読み取れないドライバーも、bad の印を付けた読み取り値を出し続けます。沈黙は値が変化していないことと区別できず、トレンドでは「センサーが 0 を読んでいる」と「センサーが応答しなくなった」の違いが、プロセスの問題と計器の問題の違いだからです。

アラームの評価は、bad の読み取り値を評価せず、以前の状態を保ちます。ゼロに落ちて故障するセンサーがあると、そうしなければユニットのすべての下限アラームが作動し、プロセスのイベントのように見えてしまうからです。
