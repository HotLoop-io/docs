アラーム通知は4.10.0から、午前3時にアラームが発生したときに携帯電話に知らせます。アラームが**発生**すると、HotLoopは、設定されて有効になっているチャネルのうち、そのアラームが優先度の下限を満たすすべてのチャネルを通じて通知を送ります。Helmチャートでは4.23.6からオンになっており（`HOTLOOP_NOTIFY_ENABLED`）、チャネルを送り先つきで有効にするまでは何も送りません。通知する相手がいないデプロイには、ここで設定するものがありません。

## なぜ「発生」だけなのか

`alarm.Engine.OnTransition`は、ISA-18.2のすべての遷移(発生、復旧、確認応答、保留、保留解除)で呼ばれます。このパッケージはすべてを監視しますが、動作するのは1つだけです。遷移のたびに通知すると、オペレーターが自分のアラームを確認応答したとき、アラームが自然に復旧したとき、誰かが1シフト分保留にしたときにも、スマートフォンが鳴ることになります。点滅するアラームがアラームを無視するよう人を慣らすのと同じように、通知を読まずに払いのけるよう慣らしてしまいます。「発生」は「画面を見ていないかもしれない人間が必要だ」ということを意味する唯一のイベントであり、このパッケージの存在理由そのものです。

通知が出るもう1つのケースは、エスカレーションです。アラームが発生し、誰も確認応答せず、ポリシーが次の担当者に知らせるよう定めている場合です。これは新しいイベントではなく、まだ誰かを必要としている同じアラームを別の人に改めて伝えるものです。「エスカレーション」を参照してください。

保留解除のように見えて、実際には発生であるケースが1つあります。アラームが保留中に条件が成立した場合、誰にも通知されていないため、保留が終わったとき(時間切れまたは手動の解除)に、エンジンは保留解除を記録し、続けて発生を記録し、この発生が通知を送ります。保留にした時点ですでにアラーム状態で、今もそのままのアラームは、未確認で戻りますが再通知はしません。最初に通知済みだからです。

## チャンネル

6つあり、これが全リストです(やらないことと理由は[HotLoopロードマップ](/ja/roadmap/)の「通知」を参照してください)。いずれもベンダーのSDKや有料アカウントを必要としません。これは本プロジェクトの基本方針に沿っています。クラウド連携はオペレーターが設定する任意の送信接続であり、アプリの動作に必須のものではありません。

- **ntfy**: スマートフォンへのプッシュ通知で、アラームをHotLoopへ直接確認応答する**確認応答**ボタンが付きます。無料で、サーバーをインターネットなしでプラントのネットワーク内に置くこともできます。「ntfyの設定」を参照してください。
- **Gotify**: スマートフォンへのプッシュ通知です。無料で、自己ホスト型で、インターネットなしで動作します。ボタンもiPhoneアプリもないため、双方向ではなくポケットベルのようなものです。「Gotifyの設定」を参照してください。
- **Discord Webhook**: Discordチャンネルへの埋め込みメッセージで、優先度ごとに色分けされ、タグ、値、限界値、エリア、ラインが表示されます。URLを貼り付ければ動きます。重大なアラームではロールにメンションできます。ボタンはありません。「Discord」を参照してください。
- **Discordボット**: 同じメッセージに、アラームを操作して押した人を記録する**確認応答**ボタンと**保留**ボタンが付きます。ボタン操作はHotLoopがDiscordへ開く接続を通じて戻ってくるため、プラントに公開アドレスは不要です。「Discord」を参照してください。

- **Webhook**: HotLoop独自のJSON本文(`alarmId`、`name`、`priority`、`priorityLabel`、`message`、`deviceId`、`tagName`、`raisedAt`、`event`。値は`raised`で、エスカレーションでは`escalated`)を、設定したURLへPOSTします。送られたJSONをそのまま受け取るものなら何とでも連携できます。小さなHTTPリスナーの後ろに置いた自作スクリプト、Node-RED、n8n、ワークフローツールの「任意のWebhookを受け取る」トリガーなどです。(ntfyのトピックを指定すると通知は届きますが、生のJSONがそのままテキストになります。代わりに上のntfyチャンネルを使ってください。)要約(「レート制限と要約」を参照)では`event`が`summary`になり、含まれるすべてのアラームを名前で列挙する`alarms`リストが付きます。独自形式の本文を要求するサービスには対応しません。Discordは`content`も`embeds`もないため400を返します。Slack、Teams、Google Chatは独自のテキストフィールドを求めます。Pushoverは`token`、`user`、`message`のフィールドを、PagerDutyのEvents APIは`routing_key`、`event_action`、`payload`を求めます。Webhookをこれらに向けると、通知はすべて失敗します。Discordには、Discordが期待する本文を組み立てる専用チャンネルがあるので、そちらを使ってください。
- **SMTPメール**: オペレーターがすでに持っているリレー(社内メールサーバー、トランザクションメール事業者のSMTPエンドポイント、自己ホストのリレー)経由で送信します。APIキーもベンダーのライブラリも不要で、`net/smtp`と手組みのプレーンテキストメッセージだけを使います。多くのスマートフォンはすでにメールをプッシュ通知として表示し、多くの呼び出しツールはメールからSMSへのブリッジアドレスを「連絡手段」として受け付けるため、このチャンネルだけでも、有料の依存なしに「スマートフォンを呼び出す」場面の相当部分をカバーできます。

## アラームの送り先：設定

すべてのチャネルはデフォルトでオンで、送り先ができるまで待機します。送り先のない有効なチャネルがHotLoopの起動を妨げることはなく、待機してその旨を伝えます。管理者は、設定の「アラームと測定値の送り先」で各チャネルに送り先を指定します。WebhookのURL、メールのリレーと受信者、ntfyのサーバーとトピック、Gotifyのサーバーとトークン、DiscordのWebhookのURL、Discordボットのトークンとチャネル、エッジパブリッシャーのブローカーとSparkplugグループです。それぞれが、今何をしているか（送信中、送り先を待機中、オフ）と、何が足りないかを表示します。

- アラームチャネルは、設定を保存した瞬間に反映されます。ディスパッチャーがその場で作り直され、古いチャネルが保留していたものが先に送られ、Discordボットの接続は新しい接続を開く前に閉じられます。その後、**テスト送信**（`POST /api/notify/test`）は、保存したばかりのチャネルに届きます。
- エッジパブリッシャーはキューのファイルとSparkplugノードを所有しているため、その送り先はHotLoopの起動時に読み込まれます。画面には「Saved, applies when HotLoop restarts」と表示されます。
- そこに保存された内容は、初期値を与えるだけのチャートや環境変数より優先されます。空のままの値は保存済みの値を保持し、クリアはそれを削除します。シークレット（WebhookのURL、ntfyのトピック、トークン、パスワード）は二度と表示されず、設定済みかどうかだけが表示され、HotLoopにシークレットキーがあればデータベース内で封印されます。
- 送り先は、何かを保存する前に、起動時に環境変数を検証するのと同じ方法で検証され、誤った送り先は何が悪いか（値は決して表示しない）を示して拒否されます。
- チャネルごとのスイッチで、そのチャネルを完全にオフにできます。オフはチャネルなし、送信なしを意味します。
- `GET /api/destinations`と`PUT /api/destinations/{kind}`がルートで、PUTには`settings.write`が必要です。[HTTP API](/ja/iot/api/)を参照してください。

## WebhookのURLは決して出力されません

多くの受信先では、URLがパスワードそのものです。Discordはトークンをパス(`/api/webhooks/{id}/{token}`)に含め、ntfyは`?auth=`で、Google Chatは`?key=`と`?token=`で受け取ります。URLを持つ人は誰でもチャンネルに投稿できます。そのため、送信に失敗したときのエラーには、スキームとホストだけが表示され、それ以外は何も表示されません。

```
webhook request to https://discord.com failed: context deadline exceeded
webhook https://ntfy.example.com returned 401 Unauthorized
```

ログ、監査イベント、`POST /api/notify/test`のレスポンスで同じ文言です。どの受信先が壊れたかはホストだけで分かり、パスとクエリがプロセスの外に出ることはありません。起動時の検証に失敗したURLも、そのエラーでは繰り返されません。URLを確認する必要がある場合は、設定した場所の`HOTLOOP_NOTIFY_WEBHOOK_URL`を見てください。

## ntfyの設定

[ntfy](https://ntfy.sh)は、パブリッシュ/サブスクライブ型のプッシュサーバーです。HotLoopがアラームごとにトピックへ発行し、スマートフォンのntfyアプリがそれを購読します。

1. サーバーを立てるか、ntfy.shを使います。プラントのネットワークでは自前で立て(`binwiederhier/ntfy`、コンテナ1つ)、アクセスを絞ってください。`auth-default-access: deny-all`を設定し、トピックに書き込めるHotLoop用のユーザーと、読み取れる人ごとのユーザーを作成します。ntfy.shや、誰でも到達できるサーバーでは、**トピック名がパスワード**です。推測した人は誰でもアラームを読めます。長くランダムな名前にしてください。
2. HotLoopにアクセストークン(`ntfy token add hotloop`)、またはそのユーザーのユーザー名とパスワードを渡します。
3. `HOTLOOP_PUBLIC_URL`に、スマートフォンがHotLoopへ到達できるアドレスを設定します。たとえば`https://hotloop.plant.example`です。設定しないと通知は届きますが、確認応答ボタンもタップで開く機能もありません。スマートフォンにはどちらの送信先もないためです。
4. 設定して再起動します。

```
HOTLOOP_NOTIFY_ENABLED=true
HOTLOOP_NOTIFY_NTFY_ENABLED=true
HOTLOOP_NOTIFY_NTFY_URL=https://ntfy.plant.example
HOTLOOP_NOTIFY_NTFY_TOPIC=boiler-house-alarms
HOTLOOP_NOTIFY_NTFY_TOKEN=tk_...
HOTLOOP_PUBLIC_URL=https://hotloop.plant.example
```

5. `POST /api/notify/test`はテスト通知を送ります。確認応答する対象のアラームがないため、確認応答ボタンはありません。

URLはサーバーだけを指します。トピックはURLに入れず、独立した設定に入れます。そうすることで、HotLoopはどの部分が秘密かを把握でき、すべてのエラー、ログ行、監査イベントから除外できます。

届く内容は次のとおりです。

| <span class="sr-only">Details</span> | <span class="sr-only">Details</span> |
|---|---|
| タイトル | アラーム名 |
| 本文 | アラームのメッセージ、優先度、発生元(`device/tag`)、発生時刻 |
| 優先度 | 重大は5(最大。Androidでは、許可していればサイレントモードを突破できます)、高は4、中は3、低は2 |
| タグ | 重大度別の絵文字と、単語で表した優先度。スマートフォンの一覧をざっと見分けられます |
| タップ | `HOTLOOP_PUBLIC_URL`が設定されていれば、HotLoopのアラーム一覧を開きます |
| ボタン | `HOTLOOP_PUBLIC_URL`が設定されていれば**確認応答**。「確認応答リンク」を参照してください |

### iPhoneに関する注意

Androidはインターネットなしで動作します。ntfyアプリがサーバーとの接続を自分で保ち、プラントのWi-Fi経由ですべてのメッセージを即座に受け取ります。

iPhoneはそうではありません。Appleはプッシュを自社のサーバー(APNs)経由でしか通さず、APNsと通信できるのはntfy.shだけです。自己ホスト型サーバーは`upstream-base-url: https://ntfy.sh`を設定する必要があり、そうするとポーリング要求(メッセージの内容はなく、「このトピックに何か届いた」という通知だけ)をntfy.shへ転送し、ntfy.shがスマートフォンを起こし、スマートフォンがあなたのサーバーからメッセージを取得します。したがって、インターネットのないプラントでは、自己ホストのntfyではiPhoneに即時通知が届きません。アプリを開いたときに表示されます。担当者がiPhoneを使っていてプラントが外部と遮断されている場合、ntfyはポケットベルになりません。リレー経由のメール、またはプラントがDiscordに到達できるならDiscordが代わりになります。GotifyにはiPhoneアプリがそもそもありません。

確認応答ボタンはスマートフォンから`HOTLOOP_PUBLIC_URL`へのリクエストなので、スマートフォンがそのアドレスに到達できる必要があります。プラントのWi-Fi上か、お使いのVPN経由です。どちらのプラットフォームでも同じように動作します。

## Gotifyの設定

[Gotify](https://gotify.net)は、Androidアプリを備えた小さな自己ホスト型プッシュサーバーです。インターネットは不要で、どこにもアカウントは要りません。

1. `gotify/server`を起動し、そのWeb UIにログインします。
2. **Apps**の下で、HotLoopという名前のアプリケーションを作成します。そのトークンをコピーします。
3. 設定して再起動します。

```
HOTLOOP_NOTIFY_ENABLED=true
HOTLOOP_NOTIFY_GOTIFY_ENABLED=true
HOTLOOP_NOTIFY_GOTIFY_URL=https://gotify.plant.example
HOTLOOP_NOTIFY_GOTIFY_TOKEN=A...
HOTLOOP_PUBLIC_URL=https://hotloop.plant.example
```

トークンは`X-Gotify-Key`ヘッダーに入れます。URLの`?token=`には決して入れません。すべてのプロキシのアクセスログに残ってしまうためです。

優先度は、Androidアプリでの扱いに対応づけられます。重大の10と高の8は高い重要度(音とヘッドアップ表示)、中の5は音付きの通常の通知、低の2は無音です。メッセージはMarkdownです(アラーム名は太字、詳細は箇条書き、アラーム自身のテキストはエスケープされるため、アスタリスクを含む名前もその名前のまま表示されます)。`HOTLOOP_PUBLIC_URL`が設定されていれば、タップするとHotLoopのアラーム一覧が開きます。

**確認応答はできません。** Gotifyの通知にはアクションボタンがないため、確認応答ボタンを付ける方法がありません。また、単純なGETで確認応答するリンクで代用することもしません。リンクのプレビューやセキュリティスキャナーは勝手にリンクを開くため、アラームがロボットに確認応答されることがあってはならないからです。確認応答はHotLoopで行ってください。**iPhoneアプリもありません。**

## Discord

方法は2つあります。Webhookはポケットベルです。URLを貼り付ければ、チャンネルにアラームが届きます。ボットは双方向です。同じメッセージに**確認応答**ボタンと**保留**ボタンが付き、監査記録には誰が押したかが残ります。どちらも、プラントがインターネット経由でDiscordに到達できる必要があります(`discord.com`への送信HTTPS、ボットの場合は`*.discord.gg`へのWebSocket)。どちらも、Discordからプラントへの到達は必要ありません。

### 届く内容

| <span class="sr-only">Details</span> | <span class="sr-only">Details</span> |
|---|---|
| テキスト | `[Critical] Boiler Trip`。スマートフォンのプッシュ通知に表示される内容です。重大なアラームでは、その前に設定したロールへのメンションが付きます |
| 埋め込みタイトル | 同じ内容で、`HOTLOOP_PUBLIC_URL`が設定されていればHotLoopのアラーム一覧へのリンクになります |
| 色 | 重大は赤、高はオレンジ、中は黄、低は青 |
| 説明 | アラームのメッセージ |
| フィールド | タグ(`device/tag`)、値(アラームを発生させた測定値)、限界値(定義にある`hi 90`)、エリア / ライン(デバイスから)、発生(各閲覧者のタイムゾーンで) |
| フッター | `HotLoop | <HOTLOOP_PLANT_NAME>`。複数のプラントがあるサーバーで区別できます(プラント名が未設定なら`HotLoop`のみ) |
| ボタン(ボットのみ) | 確認応答、1時間保留、HotLoopで開く |

アラームが大量に発生した場合は、ほかのチャンネルと同じように要約になります。最初の5件はそのまま送られ、続いて残りを列挙する1通が送られます。収まる分だけの名前と残りの件数が表示されるため、件数が途切れることはありません。

Discordは長すぎるメッセージ(テキスト2000文字、タイトル256文字、説明4096文字、フィールド25個、合計6000文字)を拒否し、拒否されたメッセージは届かなかった通知です。そのためHotLoopは、文字の境界で切り詰め、切った箇所に`...`を付けます。

### 誤ってメンションされる人はいません

すべてのメッセージは`allowed_mentions: {"parse": []}`付きで送られます。これがないと、Discordはテキストにあるメンションをすべて実行するため、誰かが「@everyone tank overflow」と名付けたアラームがサーバー全体を起こしかねません。これがあれば、テキスト内の何も誰にもメンションしません。唯一の例外は、重大用に設定したロール(`..._CRITICAL_ROLE`)で、許可される唯一のメンションとして明示され、重大なアラーム、または重大なアラームを含む要約の場合に限ります。テスト通知がメンションすることはありません。アラーム自身のテキストもMarkdownエスケープされるため、`*`を含む名前はその名前のまま表示され、名前の中の`<@&role>`は使われずに表示されるだけです。

メンションを機能させるには、ロールがメンション可能である必要があります。サーバーのロール設定で**Allow anyone to @mention this role**をオンにするか、ボットに**Mention @everyone, @here, and All Roles**権限を与えてください。

### Discordのレート制限とBAN

Discordは「速すぎる」を429で返し、待つべき時間を本文(`retry_after`、ミリ秒単位)と`X-RateLimit-Reset-After`で伝えます。HotLoopは再試行の前にその時間だけ待ちます。通常の3回の試行と30秒の範囲内です(「再試行」を参照)。Discordが、拒否する前に予算を使い切ったと伝えてきた場合(`X-RateLimit-Remaining: 0`)、次の送信は429を受けるのではなく、リセットを待ちます。

Discordは、10分間に拒否されたリクエスト(401、403、429)が10,000件に達したアドレスをBANし、そのアドレスのすべてのDiscord連携が巻き込まれます。そのため、Discordが**401、403、404**(Webhookの誤りや削除、ボットトークンの誤り、ボットから見えないチャンネル)を返すと、HotLoopはその1回のリクエストのあとで**そのチャンネルをオフにします**。ログに一度だけ記録し、以降のアラームはリクエストなしで拒否され(「未送信」として監査にも記録されるため、「誰かに通知されたか」という問いに答えが残ります)、理由と時刻が`GET /api/diagnostics`の`notify.channels`の下に表示されます。

```json
{"channel": "discord-webhook", "broken": true,
 "reason": "discord webhook https://discord.com returned 404 Not Found: Unknown Webhook (Discord error 10015)",
 "since": "2026-09-27T03:00:01Z"}
```

設定を直して、HotLoopを再起動してください。500や無応答では何もオフになりません。それらはほかのチャンネルと同様に再試行されます。

### Webhookの設定

1. Discordで、チャンネルの設定(歯車)、**Integrations**、**Webhooks**、**New Webhook**を開きます。名前をHotLoopにします。**Copy Webhook URL**。
2. 任意: 重大でメンションするロール。**Developer Mode**(User Settings、Advanced)をオンにし、Server Settings、Rolesでそのロールを右クリックして**Copy Role ID**を選びます。名前ではなく数値です。
3. 設定して再起動します。

```
HOTLOOP_NOTIFY_ENABLED=true
HOTLOOP_NOTIFY_DISCORD_WEBHOOK_ENABLED=true
HOTLOOP_NOTIFY_DISCORD_WEBHOOK_URL=https://discord.com/api/webhooks/1234.../AbCd...
HOTLOOP_NOTIFY_DISCORD_WEBHOOK_CRITICAL_ROLE=123456789012345678
HOTLOOP_PUBLIC_URL=https://hotloop.plant.example
```

4. `POST /api/notify/test`はテストメッセージを送ります。

**URL全体がパスワードです。** URLを持つ人は誰でも、Webhookとしてチャンネルに投稿できます。HotLoopはこれを決して出力しません。ログにも、エラーにも、監査イベントにも、APIレスポンスにも出ず、起動時の検証に失敗したURLも、そのエラーでは繰り返されません。Helmチャートでは、Secretに入ります。漏えいした場合は、Discordでそのwebhookを削除して新しく作り直してください。

Webhookは何かを実行するボタンを持てないため、ここには確認応答がありません。タイトルはHotLoopのアラーム一覧へのリンクです。ボタンが必要な場合はボットを使ってください。

### ボットの設定

1. [Discord開発者ポータル](https://discord.com/developers/applications)で**New Application**を選び、名前をHotLoopにします。General Informationページの**Application ID**が、招待リンクに必要です。
2. **Bot**タブで**Reset Token**を選んでコピーします。Discordが表示するのは一度だけです。これが`HOTLOOP_NOTIFY_DISCORD_BOT_TOKEN`です。同じページで、**Public Bot**をオフにして自分以外がサーバーに追加できないようにし、3つの**Privileged Gateway Intents**はすべてオフのままにします。HotLoopはDiscordにイベントを一切要求せず(intents 0)、ボタン操作はそれでも届きます。
3. 必要最小限の権限であるView Channels、Send Messages、Embed Links(権限`19456`)で、スコープは`bot`のみとして、サーバーに招待します。

```
https://discord.com/oauth2/authorize?client_id=<APPLICATION ID>&scope=bot&permissions=19456
```

   重大用のロールがメンション可能でなく、そうしたくない場合に限り、**Mention @everyone, @here, and All Roles**(`permissions=150528`)を追加してください。ボタン操作のあとに自分のメッセージを編集するのに権限は不要です。操作そのものを通じて行われます。
4. チャンネル: Developer Modeをオンにして、チャンネルを右クリックし、**Copy Channel ID**を選びます。チャンネルが非公開なら、ボットのロールを追加してください。
5. ボタンを押せるロール。ロールを1つ作り(たとえば「Alarm ack」)、Discordから確認応答してよい人に付与し、そのIDをコピーします。保留はアラームを1時間一覧から外すため、独立した設定があります。同じロールでも、より限定したロールでもかまいません。
6. 設定して再起動します。

```
HOTLOOP_NOTIFY_ENABLED=true
HOTLOOP_NOTIFY_DISCORD_BOT_ENABLED=true
HOTLOOP_NOTIFY_DISCORD_BOT_TOKEN=MTIz...
HOTLOOP_NOTIFY_DISCORD_BOT_CHANNEL=223456789012345678
HOTLOOP_NOTIFY_DISCORD_BOT_ACK_ROLES=323456789012345678
HOTLOOP_NOTIFY_DISCORD_BOT_SHELVE_ROLES=423456789012345678
HOTLOOP_NOTIFY_DISCORD_BOT_CRITICAL_ROLE=323456789012345678
HOTLOOP_PUBLIC_URL=https://hotloop.plant.example
```

7. ログに`connected to the Discord Gateway; Discord buttons work`と出て、`GET /api/diagnostics`の`discord`チャンネルの下に`"gateway": {"connected": true}`が表示されます。`POST /api/notify/test`はテストメッセージを投稿します(ボタンなし。背後にアラームがないためです)。

**ロールを設定するまで、誰も何も押せません。** `HOTLOOP_NOTIFY_DISCORD_BOT_ACK_ROLES`または`_SHELVE_ROLES`が空だと、そのボタンの操作はすべて拒否され、押した人にはどの設定が空かが伝えられ、HotLoopも起動時にそれを知らせます。

```
WARN NOBODY can acknowledge alarms from Discord, because HOTLOOP_NOTIFY_DISCORD_BOT_ACK_ROLES is empty...
```

これは意図的です。サーバーの誰でも押せるボタンを既定にして出荷すべきではありません。サーバーには人が集まってくるものです。

**誰が押したか。** Discordからの確認応答は`discord:<username>#<user id>`として記録されます(Discordのユーザー名は変更できますがIDは変わらないため、IDを使います)。メモは"acknowledged from Discord by alice (1010...)"です。HotLoopのユーザーとして記録したい場合は、対応づけてください。`HOTLOOP_NOTIFY_DISCORD_BOT_USERS=101010101010101010=alice,202020202020202020=bob`。この対応づけは、操作者の名前を決めるだけです。HotLoopユーザーの権限は確認せず、誰が押せるかはDiscordのロールで決まります。

**保留**は`HOTLOOP_NOTIFY_DISCORD_BOT_SHELVE`の時間だけ保留します。既定は1時間で、どの保留とも同じく最大24時間です。メニューではなく固定時間です。午前3時には、決まった1つのことをするボタンが1つあるほうが、ドロップダウンよりずっと良いからです。正常に戻ったアラーム(保留すると、次にそれを発生させる原因を隠してしまいます)と、すでに保留中のアラームは拒否されます。

押したあと、メッセージには誰がいつ何をしたかが表示され、2つのボタンはグレーになるため、次にチャンネルを見た人が対応済みだと分かります。拒否された操作への返答は、押した本人にだけ理由とともに返され、システムログに記録されます。

### ボタン操作はどう認可されるか

ntfyの確認応答リンク(「確認応答リンク」を参照)と同じ仕組みに、押した人についてのDiscord自身の証明が加わります。

- **ボタンは署名されています。** 各ボタンには、確認応答リンクと同じ秘密鍵で署名されたトークンが付き、その動作(確認応答か保留か。署名に含まれるため、片方をもう片方として再利用できません)、そのアラーム、その発生時刻に対するものです。Discordはボタンに100文字のデータを許し、アラームIDは64文字まであり得るため、これは同じ主張をコンパクトにした形です。発生時刻が8バイト、有効期限が4バイト、96ビットのHMACです。偽造するには96ビットを推測する必要があり、1回の推測ごとにDiscordのボタンを1回、正しいロールを持つ人としてサーバー内から押さなければなりません。
- **押した人が指定したロールを持っています。** Discordは、押した人のロールをボタン操作と一緒に、ボット自身の認証済みの接続で伝えます。サーバーでロールを付与できる人は、このロールも付与できます。そのため、これらのロールは権限そのものとして扱ってください。
- **その発生が現在のものです。** エンジンは、自身のロックの下で、アラームの現在の発生がボタンにある発生と同じかを確認します。昨日のメッセージで今日のトリップを確認応答することはできません。
- **1回だけ。** 通知(ntfyかDiscordか)を問わず、ある発生に対する最初の操作が記録され、以降はすべて拒否されます。2人が同時に押した場合は、1人が処理され、もう1人にはその旨が伝えられます。
- **期限があります。** `HOTLOOP_NOTIFY_ACK_TTL`(12時間)が過ぎるとボタンは動作しなくなります。HotLoopで対応してください。

ボットのトークンは、ボット全体の認証情報です。ログに出力されず、エラーにも、APIレスポンスにも出ません。Helmチャートでは、Secretに入ります。Discordがボットに応答のために15分間与える、各操作のインタラクショントークンも同様です。ボットのトークンが漏えいした場合は、開発者ポータルでリセットしてください。

### Gateway接続

ボタン操作は、Discord Gatewayを通じて届きます。これは、HotLoopがDiscordに対して開き、維持しているWebSocketです。クライアントはHotLoop独自のもので、[gorilla/websocket](https://github.com/gorilla/websocket)(v1.5.3、バージョン固定。このモジュールの依存関係にすでに含まれており、小さく、Goで最も使われているWebSocketライブラリです)の上に作られています。discordgoのようなDiscordライブラリは採用しませんでした。必要なイベントは1つだけなのに、REST、音声、状態キャッシュまで備えたDiscord SDK一式を取り込むことになり、このプロジェクトはベンダーSDKを持たないためです。クライアントは次のように動作します。

- intents 0で識別するため、Discordはボタン操作以外を何も送ってきません。
- Discordが指定する間隔でハートビートを送り、ハートビート要求にはただちに応答し、確認されなかったハートビートは切断とみなします。
- 切断、Reconnect(op 7)、再開可能なInvalid Session(op 9)のあとにセッションを再開するため、再接続中に行われた操作は失われずに再生されます。再開できないセッションは1秒から5秒待って新しく開始します。
- 識別は5秒に1回までで、Discordがその日のセッション開始回数を使い切ったと伝えてきたら、リセットされるまで行いません。
- 1秒から1分まで倍々に増えるバックオフで再接続します。
- トークンやintentsが拒否された場合は完全に停止し、チャンネルをオフにして`/api/diagnostics`に表示します。永遠に再接続し続けることはしません。

Discordはボットに、操作への応答のために3秒を与えるため、HotLoopが最初に行うのは「受け取った」(遅延更新)という応答で、そのあとに処理を行います。この応答は、2つのHotLoopレプリカが1回の操作に両方とも動作するのを防ぐ役割も果たします。両方が操作を受け取りますが、Discordは最初の応答を受け付け、2番目を拒否し、拒否されたレプリカは処理を止めます。MCPヘルパー(`--mcp-stdio`)として実行される場合、HotLoopはGateway接続をまったく開かず、本体の側が操作を処理します。

## レート制限と要約

停電後の電圧低下やPLCの再起動で、1秒間に40件のアラームが発生します。アラームごとに1通送ると、DiscordのWebhookのIPがBANされ、ntfyのIPごとの制限に引っかかり、受け取るスマートフォンでは、重要な1件が重要でない39件に埋もれてしまいます。そのため、各チャンネルには予算、つまりトークンバケットがあります。一度に送れるバーストがあり、その後は補充のたびに1件ずつ送れます。

| チャンネル | 既定のバースト | その後の間隔 |
|---|---|---|
| ntfy | 10 | 5 s(ntfy.sh自身の上限である60未満、その後はIPごとに5 sに1件) |
| Gotify | 10 | 5 s |
| Webhook | 10 | 5 s |
| SMTP | 5 | 12 s |
| Discord Webhook | 5 | 2 s(Discordは、Webhookに約2 sあたり5リクエスト、チャンネルに毎分30メッセージを許します) |
| Discordボット | 5 | 2 s |

`HOTLOOP_NOTIFY_<CHANNEL>_BURST`と`HOTLOOP_NOTIFY_<CHANNEL>_REFILL`でチャンネルごとに変更できます(`WEBHOOK`、`SMTP`、`NTFY`、`GOTIFY`、`DISCORD_WEBHOOK`、`DISCORD_BOT`)。

予算の範囲内のものは、すぐにそのまま送られます。範囲を超えたものは保留され、次の送信の時刻になると、保留されたものすべてが**1通の**要約として送られます。

```
7 more alarms raised in the last 12 s:
- [High] Line 3 Stopped
- [Critical] Boiler Trip
...
```

アラームは1件も失われません。要約には、最大25件までのすべてのアラームの名前が載り、残りは件数で示されます("...and 13 more")。要約の重大度は、その中で最も重大なアラームと同じで、その監査イベントには、要約が代表したすべてのアラームIDが列挙されます。確認応答する単一のアラームがないため、確認応答ボタンはありません。保留されたのが1件だけなら、ボタンも含めてそのアラームとして送られます。アラームが保留され始めると、予算が戻っていても新しいアラームはその束に加わるため、要約が、その中のどのアラームよりあとに発生したアラームの後ろに届くことはありません。シャットダウン時には、まだ保留中のものが予算を超えてただちに送られます。このときの選択は、送信が1回余分になることと、誰にも通知されないアラームが出ることの間にあるからです。

予算はチャンネルごとなので、SMTPリレーを待たせる大量発生がntfyを止めることはなく、各チャンネルの下限も引き続き適用されます。低のアラームが、高以上に設定されたチャンネルの要約に入ることはありません。

## 再試行

429、5xx、または応答なし(拒否、切断、タイムアウト)となった送信は、最初の試行から30秒以内に、合計3回まで再試行されます。受信側が待ち時間を指定した場合(`Retry-After`、秒または日付)は、その時間だけ待ちます。指定がなければ1秒、次に2秒です。残りの30秒を超える待機を求める受信側は待たず、その旨を添えてただちに失敗として報告します。30秒たっても届かなかった通知は、アラームが残ったまま何分も黙って再試行するより、ログと監査記録に失敗として残したほうが適切です。

それ以外の4xx(誤ったトークン、ユーザーが書き込めないトピック、不正なリクエスト)は再試行しません。誰かが設定を直すまで毎回同じ答えが返りますし、Discordはすでに拒否したリクエストを送り続けるIPをBANします。

`POST /api/notify/test`は、チャンネルごとにちょうど1回だけ試行します。テストは、チャンネルがいまどう動くかを尋ねるものであり、再試行をすると不安定な受信先が正常に見えてしまいます。

## 確認応答リンク

ntfy通知の確認応答ボタンは、`HOTLOOP_PUBLIC_URL`にある`POST /api/notify/ack/{token}`へのリクエストです。午前3時にこれを押す人は、どこにもログインしていないため、**トークンが認可のすべて**です。これが成り立つのは、トークンが偽造不能で、範囲が狭く、1回限りで、短命な場合だけであり、それぞれが強制されています。

- **偽造不能。** トークンは、主張(どのアラームか、いつ発生したか、どのチャンネルか、リンクがいつ期限切れになるか)と、サーバーの秘密鍵によるそのHMAC-SHA256です。1バイトでも変えるか、別の鍵で署名すれば拒否されます。秘密鍵は、設定すれば`HOTLOOP_NOTIFY_ACK_SECRET`です(32文字以上。`openssl rand -hex 32`)。設定しない場合、HotLoopは最初に必要になったときに32バイトの乱数を生成してデータベース(`settings`テーブル、キー`notify.ackSecret`)に保存するため、再起動後もリンクは動作し、すべてのレプリカが同じ値を使います。設定画面にも、どのAPIレスポンスにも表示されません。データベース内のほかのものと同様に、データベースのバックアップには含まれます。それが問題になる場合は、Kubernetes Secretから変数を設定すれば(チャートの`notify.ackSecret.existingSecret`)、データベースには一切触れません。秘密鍵を変更すると、すでに送ったすべてのリンクが無効になり、これはすべてを一度に失効させる方法でもあります。
- **範囲が狭い。** 主張は、1つのアラームと**それが発生した時刻**を指定します。同じアラームの昨日のトリップのボタンでは、まだ誰も見ていない今日のトリップを確認応答することはできません。エンジンは、確認応答と同じロックの下で、アラームの現在の発生が主張にあるものと同じかを確認します(`alarm.Engine.AckOccurrence`)。リンクができるのは確認応答だけです。保留、復旧、タグの書き込み、何かの読み取りはできないため、漏えいしたリンクにできる最悪のことは、ボタンを押したときと同じことだけです。
- **1回限り。** ある発生に対するリンクの最初の使用はデータベース(`notify_ack_links`)に記録され、以降の使用はすべて拒否されます。新たな発生がないのにアラームの再確認が必要になった場合(アラーム状態のまま保留され、解除されて未確認で戻った場合)でも同じです。これにはアラーム自身の状態では足りず、記録が必要です。
- **短命。** 既定では送信の12時間後に期限切れになります(`HOTLOOP_NOTIFY_ACK_TTL`、最大168h)。「出社したら見ます」には十分長く、通知のスクリーンショットが恒久的な認証情報にならないよう十分短い期間です。

成功した操作は、アラームエンジンを通じた通常のISA-18.2の確認応答であり、アラーム画面からの確認応答とまったく同じように監査されます。アラームイベントと、操作者`notify:ntfy`、メモ"acknowledged from the ntfy notification"が付いたシステムログの項目です。ntfyのHTTPアクションはどのスマートフォンが押したかを伝えないため、追記できる個人名はありません。複数の人が1つのトピックを共有している場合、監査記録には誰がではなく、スマートフォンが行ったと残ります。Discordのボットはユーザーを把握しているため、それを記録します(「Discord」を参照)。

拒否はすべて、何が問題だったかとともに応答され、システムログの`notify:<channel>`(どのチャンネルが送ったか分からないほど壊れたトークンの場合は`notify:ack-link`)に記録されます。黙って何もしなかったボタンは、誰も押さなかったボタンと区別がつかないためです。

| 応答 | 理由 |
|---|---|
| 403 | 偽造、改ざん、または別の秘密鍵で署名された |
| 410 | 本物だが期限切れ |
| 409 | すでに使用済み、またはそれ以降にアラームが再度発生した、または確認応答するものが残っていない |
| 404 | アラームがもう存在しない、または確認応答リンクがオフ |

トークン自体は、ログに残らず、監査イベントにも入らず、どのAPIからも返されません。有効な間は認証情報だからです。ただし、ntfyのメッセージには必然的に含まれるため、ntfyのトピックを読める人は誰でもボタンを押せます。トピックのアクセスを絞ってください。

エンドポイントは`Access-Control-Allow-Origin: *`で応答するため、自身のオリジンから押すntfyのWebアプリでもボタンが動作します。これで何かが漏れることはありません。このルートでは、Cookieもセッションも読まれないためです。

## エスカレーション

N分間誰もアラームを確認応答しなければ、次の人に届きます。最初の通知は、アラームが下限を満たすすべてのチャンネルに、従来とまったく同じように送られます。エスカレーションは、その後もアラームが未確認のまま残っている場合に起こることです。誰も手に取っていないスマートフォンに届いた通知こそ、これが防ぐ失敗です。午前3時、当番の人は眠っており、アラームがその人を待ってはいけません。

**Settings、Alarm escalation**で設定するか、API(`GET`と`PUT /api/notify/escalation`)で設定します。人々のntfyトピックを保持し、誰を起こすかを決めるため、管理者専用です。HotLoopの起動時に環境から読み込まれるチャンネルと違い、ポリシーは自分で編集するデータで、保存した時点で有効になります。使えるチャンネルは、環境にすでに設定されているものです。ここで選べるのは、4つのチャンネルにWebhookとメールを加えたものだけで、新しいものは追加されません。

### ポリシー

| フィールド | <span class="sr-only">Details</span> |
|---|---|
| `enabled` | オンにするまではオフです。オフのポリシーは何もエスカレーションしません |
| `minPriority` | エスカレーションする最も軽いアラーム: `critical`、`high`、`medium`、`low`。既定は`high`。1時間放置された中のアラームは、午前3時の電話ではなく作業指示です |
| `contacts` | 担当者。それぞれに`name`と、`ntfyTopic`、`emails`、またはその両方があります。最大50件 |
| `steps` | 最大10件。それぞれに`afterMinutes`(1から1440)と、通知先があります。名前で指定する`contacts`、名前で指定する`channels`、またはその両方 |
| `repeatEveryMinutes`、`repeatTimes` | 最後のステップのあと、この間隔でこの回数だけ追加で再送します(最大20)。両方0なら繰り返しません |

**担当者**は、専用の通知を受け取ります。その人の`ntfyTopic`は、このHotLoopがすでに発行しているntfyサーバー上のトピックで、同じログインを使うため、その人のスマートフォンは自分専用のトピックを購読します。`emails`は、HotLoopがすでに持っているSMTPリレーを通ります。トピックを持つ人にはntfyの設定が、アドレスを持つ人にはメールの設定が必要で、設定されていなければ、その旨を伝えてポリシーは拒否されます。誰でも到達できるサーバーでは、トピックはパスワードです。長くランダムにしてください。APIはトピックを管理者にだけ見せ、ログブック、システムログ、エラーには決して出ません。

ステップの**チャンネル**は、環境にすでにあるもの(`ntfy`、`gotify`、`smtp`、`webhook`、`discord-webhook`、`discord`)のいずれかで、そこにいる全員に届きます。共有のDiscordチャンネル、チームで共有しているGotifyアプリ、呼び出しサービスにつながるWebhookなどです。このHotLoopに設定されていないチャンネルをステップが指定している場合、ポリシーは拒否され、応答には設定済みのチャンネルが列挙されます。

### いつ送られるか

ステップは、直前のステップから`afterMinutes`後に実行され、最初のステップはアラームの発生から`afterMinutes`後です。これは、直前の送信が終わった時刻ではなく、発生時刻からの合計なので、遅いリレーや再起動があっても、書いたスケジュールが延びることはありません。5分と10分のステップで、15分間隔の繰り返しを2回にした場合は次のとおりです。

```
 0 min  alarm raised: the first page, as always
 5 min  step 1
15 min  step 2
30 min  step 2 again (repeat 1)
45 min  step 2 again (repeat 2), and that is the last
```

### 何が止めるか

チェーンは、1つのアラームの1回の発生に対するもので、次のいずれかが起きると、理由を記した行を残して止まります。

- **誰かが確認応答した。** どこからでも構いません。アラーム画面、ntfyやDiscordの確認応答ボタン、API、自動化のいずれも、最終的にアラームエンジンに行き着き、各ステップが送られる前に、エスカレーターはエンジンに、この発生がまだ未確認かを尋ねます。遅れて届いたフックが、すでに誰かが対応したアラームを通知してしまうことはありません。
- **正常に戻った。** アラームは、誰かの確認応答を待ってアラーム一覧に残りますが、自然に直ったもののために誰も起こされません。これは意図的に下した判断です。違う動作にしたい場合は、下限かステップを変更してください。
- **保留された。**
- **再びトリップした。** これは新しい発生で、その発生時刻から数える独自のチェーンを持ちます。昨日のチェーンが今日のアラームを通知することはありません。

ステップ1の時刻前に誰かが対応したアラームは、エスカレーションの記録に一切痕跡を残しません。これは、システムが正しく機能している状態です。

### 届く内容

エスカレーションは、タイトルを変更して1行を加えた、アラーム自身の通知です。

```
NOT ACKNOWLEDGED 15 min: Boiler Trip
Nobody has acknowledged this alarm in 15 minutes (step 2 of 4). boiler/Pressure hi 90 (now 95)
```

アラームの優先度は維持されるため、重大なものはAndroidで引き続き最大優先度です。ntfyとDiscordでは最初の通知と同じ署名付きの確認応答ボタンが付くため(「確認応答リンク」を参照)、呼び出された人は、通知を受けたその場から確認応答できます。Gotifyとメールにはボタンがありません。Webhookには、`event`を`escalated`にした、通常のHotLoopのJSONが送られます。

共有チャンネルは、ほかのチャンネルと同様にペース配分されるため(「レート制限と要約」を参照)、40件のアラームが未確認のまま残る電圧低下は、40通の通知とBANではなく、1通の要約、"40 alarms nobody has acknowledged"としてエスカレーションされます。担当者個人への通知は、それぞれ独立した送信です。

### 監査記録

エスカレーションはすべて、アラーム自身の記録に1行として残り、[ログブック](/ja/iot/logbook/)がそれを読み取るため、追加の設定なしにそこに表示されます。アラームの下に、操作者`escalation`として分類されます。

```
alarm Boiler Trip escalated: boiler/Pressure hi 90 (now 95) (note: step 1 of 2: nobody acknowledged it in 5 min; notified Ana (email), Ana (ntfy))
alarm Boiler Trip escalation-ended: boiler/Pressure hi 90 (now 95) (note: escalation stopped after 1 sent: acknowledged by notify:ntfy)
```

`GET /api/alarms/events`とログブックの`alarm`種別は、同じ行を`escalated`と`escalation-ended`というタイプで返します。誰にも届かなかったステップは、大文字(`NOBODY WAS REACHED`)でそう示し、その後に各失敗を付けます。それでもチェーンは次のステップへ進みます。1つのリレーが死んでいても、別の経路で出る通知を止めてはいけないからです。ポリシーの保存は、トピックを除いてシステムログに残ります。

### 再起動と実行場所

チェーンはメモリ上にあるため、午前3時の再起動で進行中のチェーンが失われてはいけません。HotLoopは起動すると、まだ未確認のすべてのアラームを調べ、その発生について監査の行がいくつのステップが送信済みと示しているかを読み取り、そこから続行します。ステップ1を再送せず、ステップ2を飛ばしません。HotLoopが停止していた間に時刻が来たステップは、復帰後の数秒以内に送られます。プロセスが強制終了されたときに送信途中だったステップは、2回送られることがあります。アラームの場合、間違えるならこの向きが正しいのです。

保存したポリシーは、保存後に発生したアラームに適用されます。再起動すると、いつ発生したかにかかわらず、まだ未確認のすべてのアラームを引き継ぎます。

実行するのはGatewayです。`--mcp-stdio`ヘルパーは実行しないため、1つのアラームが2つのプロセスからエスカレーションされることはありません。

## SMTPチャンネルのTLS

リレーが拡張を通知した場合、チャンネルは、以下のどの設定にも関係なく、STARTTLSで自動的にTLSへ切り替わります。これは任意で選ぶ動作ではありません。Goの`net/smtp.PlainAuth`自体が、すでにTLSになっていない接続(または名前がそのまま`localhost`であるサーバー)へユーザー名とパスワードを送ることを拒否し、認証を必要とする実質すべての実在の事業者、Gmail、SendGrid、Mailgun、ISPのリレーは、そこに至るために、ポート587のSTARTTLS、またはポート465の暗黙的TLS(下を参照)を要求します。認証を設定していない、隔離されたネットワークで到達できるリレーはSTARTTLSをまったく提供しないこともあり、その場合、このチャンネルはそれを要求しません。

`HOTLOOP_NOTIFY_SMTP_TLS`は切り替えをオンにするものではなく、切り替えが*ない*ことを致命的な失敗にします。設定されていてリレーがSTARTTLSを通知しない場合、`Send`は`AUTH`を試みる前に拒否し、たまたま`localhost`として到達できるリレーに対して黙って平文で認証してしまうことを防ぎます。`HOTLOOP_NOTIFY_SMTP_TLS_SKIP_VERIFY`は、切り替え時の証明書の検証を省略します。`HOTLOOP_EDGE_PUBLISH_TLS_SKIP_VERIFY`と`HOTLOOP_FLEET_TLS_SKIP_VERIFY`が、それぞれのMQTT接続にすでに用意している抜け道と同じもので、自己署名証明書を提示するリレー向けです。

### 暗黙的TLS、ポート465

ポート465のリレーは、平文の挨拶と切り替えではなく、最初のバイトから接続全体がTLSであることを前提とします(RFC 8314)。HotLoopは以前は切り替えしか行わなかったため、465では、TLSハンドシェイクを待つリレーに最初に平文を送ってしまい、送信が失敗していました。現在は**ポート465は暗黙的TLS**で、ほかのすべてのポートは従来どおりSTARTTLSです。操作する設定はありません。

```
HOTLOOP_NOTIFY_SMTP_PORT=465
```

リレーが独自のポートで暗黙的TLSを使う場合、または465でSTARTTLSを話す場合は、`HOTLOOP_NOTIFY_SMTP_IMPLICIT_TLS`に`true`か`false`を指定します。これはポートより優先されます。Helmチャートでは、`extraEnv`の下に設定します。それ以外はどちらも同じです。ユーザー名とパスワードは暗号化された接続上で送られ、`HOTLOOP_NOTIFY_SMTP_TLS`はそれによって満たされ(要求するものがありません)、`HOTLOOP_NOTIFY_SMTP_TLS_SKIP_VERIFY`はそのハンドシェイクの証明書チェックを省略します。オフにしない限り、リレーの証明書は検証されます。定期レポートも同じリレー設定を使うため、同じルールが適用されます。

ハンドシェイクに失敗した場合、エラーがそう伝え、`HOTLOOP_NOTIFY_SMTP_IMPLICIT_TLS=false`を示します。平文で始まるリレーに必要なのはこれです。

TLS専用のリスナーを持つ実際のSMTPサーバーライブラリと、`--smtp-require-tls`付きで実行したMailpit(ラボのバージョン固定、v1.31.2)に対して検証しました。商用事業者の465番エンドポイントに対しては検証していません。

## 定期レポートと共有する1つのSMTP経路

4.14.0以降、アラームチャンネルは、添付ファイルを任意で付けて宛先リストへ1通のメッセージを送る汎用関数`notify.SendMessage`を通じて送信します。定期レポート([定期レポート](/ja/gateway/reports/)を参照)は、CSVとHTMLのファイルを、同じ関数と同じリレー設定(`HOTLOOP_NOTIFY_SMTP_HOST`、`_PORT`、`_USERNAME`、`_PASSWORD`、`_FROM`、`_TLS`、`_TLS_SKIP_VERIFY`)で送るため、接続し、STARTTLSで切り替え、認証し、ヘッダーに何を含めてよいかを決める場所は1か所です。共有されるのはリレーだけです。`HOTLOOP_NOTIFY_ENABLED`、`HOTLOOP_NOTIFY_SMTP_ENABLED`、`HOTLOOP_NOTIFY_SMTP_TO`はアラーム用であり、レポート用に設定したリレーがアラームチャンネルをオンにすることはありません。

アラームメールの動作が2点変わりました。どちらも安全側への変更です。送信者とすべての宛先は、接続する前に通常のアドレスとして検証されるようになりました。以前は、不正なものはリレーで失敗していました。また、ASCII以外の文字を含む件名は、生のUTF-8ではなくRFC 2047のエンコード語として送られます。制御文字を含むアラーム名は、拒否されずに空白に置き換えられます。アラームの名前が何であれ、通知は送られなければならないためです。

## 優先度の下限

各チャンネルには独自の`MinPriority`があり、それがそのチャンネルがなお反応する最も軽いアラーム優先度です。`model.AlarmPriority`は1(重大、最も重い)から4(低)までなので、「高以上」は`MinPriority = 2`です。アラーム自身の優先度の番号が下限以下であれば、そのアラームはチャンネルの下限を満たします。重大のみに設定したWebhookと、中以上に設定したSMTPリレーは、同じアラームエンジンを見ながら、まったく異なるアラームの集合に反応でき、両者が一致する必要はありません。

## 対象外のこと

**チャンネルのライブリロードではありません。** チャンネルは、`EdgePublishConfig`や`FleetConfig`と同様に、プロセスの起動時に設定から1回だけ読み込まれます。`HOTLOOP_NOTIFY_*`を変更するには再起動が必要で、このMVPには、実行中にチャンネルを追加または削除するAPIはありません。エスカレーションのポリシーは例外です。次に誰へいつ知らせるかは、自分で編集するデータで、保存した時点で有効になります(「エスカレーション」を参照)。

**専用のテーブルではありません。** 通知の試行は、成功でも失敗でも、すべて`runtime.Manager.Event`を通じて書き込まれます。これは、すべてのアラームとフリート操作がすでに記録されている、汎用の監査イベントの仕組みです。この規模の機能のために専用の`notifications`テーブルを作る必要はなく、システムログがすでに「通知は送られたか、うまくいったか」に答えています。

**永続キューではありません。** 再試行には上限があり(3回、30秒、「再試行」を参照)、保留されたアラームは、要約が送られるまでメモリ上にあります。失敗し続ける通知はログに記録され、監査され、ディスパッチャーは先へ進みます。誰も確認応答しないため発生したままのアラームは、通知が届いたかどうかにかかわらず、アラーム画面と`alarm_events`に引き続き表示されます。通知はアラームシステムの上に載った利便性であり、その代わりではありません。

| `GET /api/diagnostics` | `status.read` | `notify.channels`の下に、各チャンネルの状態を表示します。Discordに拒否されたか(その理由といつから)、Discordボットのゲートウェイ接続です |

`notify.escalation`も同じく管理者専用です。ポリシーには人々のntfyトピックが含まれるため、ポリシーの読み取りにもこれが必要です。

`notify.test`は管理者専用で、管理者ロールがすでに持つワイルドカードによって付与され、オペレーターロールの権限リストには意図的に追加していません。実際の外部メッセージを送り、呼び出し事業者やSMTPリレーが許す枠を消費することは、読み取りよりも、`fleet.restart`や`fleet.config`(これらも管理者専用で、同じく「いますぐ外の世界に何かをする」操作)に近く、このアプリがその2つにすでに適用しているのと同じ絞り込みです。

レスポンスは、リクエスト全体に対する1つの成功または失敗ではなく、各チャンネルの結果を報告します。

```json
{
  "results": [
    {"channel": "webhook", "success": true},
    {"channel": "smtp", "success": false, "error": "dial smtp server mail.example.com:587: i/o timeout"}
  ]
}
```
