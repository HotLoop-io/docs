工場の屋上にある気象ステーションを、画面上では 1 つのものとして扱います。雨が降っているかを知るために HotLoop が誰かに電話することはありません。ステーションが教えてくれます。MQTT 経由の Ecowitt や Tempest、Modbus 経由の Davis や Vaisala、OPC UA 経由ならどれでもかまいません。そのいずれかの値はすでにタグであり、天気エンティティは 1 つのステーションのタグを、それぞれの役割に割り当てたものです。気温、湿度、気圧、風、雨、日射がその役割です。

気象サービスも API キーもインターネットも要りません。3 週間前にアップリンクが切れた現場でも、自分の屋上の気温は表示されます。(太陽の位置については[太陽](/ja/iot/sun/)を参照してください。現場の緯度と経度から計算するので、ステーションはまったく必要ありません。)

## 作り方

天気エンティティは、モーターと同じ方法で作ります([エンティティ](/ja/iot/entities/#複合設備)を参照)。管理者がタグを指定します。エンティティ画面で、新しい設備、天気を選びます。API でも作れます。

```json
POST /api/entities
{
  "domain": "weather",
  "name": "Roof station",
  "bindings": [
    {"role": "temperature", "device_id": "roof", "tag_name": "Temp"},
    {"role": "humidity",    "device_id": "roof", "tag_name": "Humidity"},
    {"role": "wind_speed",  "device_id": "roof", "tag_name": "Wind"},
    {"role": "wind_bearing","device_id": "roof", "tag_name": "Bearing"}
  ]
}
```

必須なのは `temperature` だけです。雨量計のないステーションには `rain_rate` がなく、雨の行も表示されません。どの役割も数値タグを 1 つ受け取り、書き込まれるものはありません。ステーションは読み取るだけで、コマンドは送らないので、有効にするタグはなく、エンティティはサービスを受け付けません。

| 役割 | <span class="sr-only">Details</span> | 作られる属性 |
|---|---|---|
| `temperature` | 必須、状態 | `unit_of_measurement` |
| `humidity` | 相対湿度、パーセント | `humidity` |
| `pressure` | 気圧、タグの単位 | `pressure` |
| `wind_speed` | 平均風速 | `wind_speed` |
| `wind_gust` | 直近で最も強い突風 | `wind_gust` |
| `wind_bearing` | 風が吹いてくる方向、0 から 360 度 | `wind_bearing` |
| `rain_rate` | 今の雨の強さ | `rain_rate` |
| `rain_today` | 午前 0 時からの雨量 | `rain_today` |
| `solar_radiation` | センサーに当たる日射、通常は W/m² | `solar_radiation` |
| `uv_index` | UV インデックス | `uv_index` |

各属性にはそのタグの単位を持つ `<name>_unit` も付くので、画面が気圧を hPa と inHg のどちらか推測する必要はありません。

## ボックスで計算されるもの

ステーションがめったに送らない 3 つの値を、ステーション自身の測定値から計算します。

| 属性 | 元の値 | 方法 |
|---|---|---|
| `dew_point` | 気温、湿度 | Magnus の式(Sonntag 1990)。0 から 30 °C の乾湿計表と照合済みです |
| `heat_index` | 気温、湿度 | 米国気象局(NWS)の Rothfusz 回帰式と、公表されている 2 つの補正。NWS が使うのをやめる 80 °F(26.7 °C)以上でのみ存在します |
| `wind_chill` | 気温、風速 | NWS の 2001 年の指数。当てはめた範囲である 50 °F(10 °C)以下で風速が 3 mph を超えるときだけ存在します |

気温自身の単位で返されるので、華氏で送るステーションの露点も華氏になります。HotLoop が変換する気温の単位は °C、°F、K、風速の単位は m/s、km/h、mph、ノット、ft/s で、タグの単位から読み取ります。単位のない気温タグを推測で変換することはありません。エンティティ自身の `unit_of_measurement` で単位を指定でき、どちらもなければ、そのタグからは何も計算しません。

ヒートインデックスや風冷えがないのは故障ではありません。80 °F 未満ではヒートインデックスがなく、風が穏やかか暖かい空気では風冷えがないので、カードにはその行がありません。

## 欠けた値はゼロではありません

天気エンティティは決して楽観せず、欠けた部分を数値で埋めません。

* バインドされていないセンサーは行になりません。
* バインドされているが今は読めないセンサー(タグが不良、デバイスが停止、まだ何も届いていない)は、属性から外れ、`unavailable` に名前が載ります。カードには、その数値があるはずの場所に**利用不可**と表示されます。
* 測定値になり得ない値も同じ扱いです。105 パーセントを超える湿度、0 から 360 度の外にある方位、負の雨量や風速などです。霧の中のセンサーが読む 101 や 102 の湿度は次の値で表示します:
  100. 日射計が夜に出す小さな負の値は 0 と表示します。
* 利用できない値から計算した値も利用できず、名前が載ります。湿度がなければ `dew_point` も `heat_index` もありません。
* 気温が読めないときの状態は `unknown`(デバイスが停止しているときは `unavailable`)で、品質は通常どおりです。カードの残りは、ほかのセンサーの値をそのまま表示します。

## 画面では

エンティティ画面では、気象ステーションは 1 枚のタイルです。大きな文字の気温と、その下にステーションが出す値ごとの行が決まった順序で並びます(湿度、気圧、風、風向、突風、降雨強度、今日の雨量、日射、UV インデックス、露点、ヒートインデックス、風冷え)。気温にはいつもの推移線があります。カードは画面が対応するすべての言語で読め、アラビア語では右から左に配置されます。

## MCP

エージェントは、すべてのエンティティが持つツールと、ステーションが何を受け取るかを教えるツールで、ステーションを読み取り、作成します。

| ツール | 内容 |
|---|---|
| `list_composite_entities` | `create_entity` が作れるものを読みます。各ドメインの役割、必須の役割、サービスが書き込む役割が分かります。天気は役割が 10 個、必須が 1 つで、サービスはありません |
| `create_entity` | `POST /api/entities` と同様に、タグからステーションを作ります。ほかの変更と同じく、理由と MCP 書き込みスイッチが必要です |
| `get_states` | 1 つを読みます。状態は気温で、モデルが読むテキストには `unavailable` を含むすべての属性が並びます |
| `list_entities` | `domain: weather` でステーションを探します |
| `delete_entity` | 1 つを削除します |

天気エンティティへの `call_service` は拒否されます。サービスを受け付けないためです。

## できないこと

* 予報はしません。ほかに問い合わせなければ予報はできず、HotLoop はそうしません。
* どのセンサーもそうであるように、ステーションの気温をログブックの行として記録しません。履歴はタグのものです。タイルの推移線は気温タグのもので、ほかのタグもほかのタグと同じようにヒストリアンに入っています。
* ステーションを代わりに読み取ることはしません。ステーションはまずタグとして届きます。デバイス(MQTT、Modbus、OPC UA)を追加し、そのあとでタグをバインドしてください。
