---
title: "マイグレーションは追加だけ"
description: "マイグレーションが何も削除せず、名前も型も変えない理由と、そのおかげで失敗した更新が 1 行も失わずに前のリリースへ戻れるしくみです。"
---

マイグレーションは追加します。何も削除せず、名前も型も変えず、前のリリースが書き込む列や制約を厳しくすることもなく、データを消すこともありません。ルールはこれがすべてで、マイグレーションがこれを破るとテストがビルドを失敗させます。

## 理由

どのボックスも `:stable` に従い、Podman の自動更新がそれを動かします。リリースがデータベースをマイグレーションしたあとヘルスチェックに失敗すると、更新はロールバックされ、前のリリースは新しいリリースが残したスキーマの上で起動します。マイグレーションは一緒にロールバックできません。そのため前のリリースが新しいスキーマで動かなければならず、それを約束できる唯一の方法は、新しいスキーマが古いものの持っていたすべてを同じ形で持ち、同じ書き込みを受け付けることです。

列を追加しても、古いリリースはそれを見ません。列を削除すると、古いリリースの最初のクエリがエラーになります。工場で、午前 3 時に、戻る先が何も残っていない状態でです。

Helm チャートにも同じ問題があります。`helm rollback` は古いイメージを戻しますが、データベースは新しいリリースが動かした場所に残ります。

## もっと必要に見える変更

削除はできないので、削除が必要に見える変更は、追加して古いものには触れないことで行います。

- **列の名前を変える。** 既定値付きの新しい列を追加します。新しいリリースは新しい列を読み、両方に書き込みます。古い列は使われないまま残り続けます。
- **型を変える。** 同じです。新しい型の新しい列を置き、新しいリリースは両方に書き込み、古い列は残ります。
- **今後 NOT NULL にしたい列。** アプリケーションで強制します。制約が本当に必要なら、新しいテーブルに付けます。
- **テーブルを廃止する。** 使うのをやめます。テーブルは残ります。
- **古いデータを整理する。** マイグレーションではなく、アプリケーションが実行時に行います(保持機能がすでにそうしています)。

使われない列のコストは数バイトです。所属するリリースは戻せるのに戻せないマイグレーションのコストは、工場 1 つ分です。

## ガード: アプリケーションは信頼できないスキーマを拒否します

追加が安全なのは 1 つのリリースの間だけで、永遠ではありません。リリースが検証されているのは直後のスキーマだけなので、アプリケーションはデータベースがどれだけ先に進んでいるかを数えます。

`schema_migrations` は各マイグレーションの横に、どのリリースが適用したか(`app_version`)を記録します。起動時、何かに触れる前に、アプリケーションはデータベースにあるマイグレーションと、自分に組み込まれたマイグレーションを比べます。

| データベースにあるもの | 起こること |
|---|---|
| このリリースが知らないものはない | 起動します |
| 1 つ新しいリリースのマイグレーション | 両方のバージョンを示す警告付きで起動します。ロールバックされた更新です。何もマイグレーションせず、新しいリリースが戻ってきたとき、自分のスキーマがすでにあるのを見つけます |
| 2 つ以上新しいリリースのマイグレーション | 起動を拒否し、このリリース、このリリースが知る最新のマイグレーション、データベースの最新のマイグレーション、それらを書き込んだリリースを示します |

拒否のメッセージは次のとおりです。

```
refusing to start: this database's schema is more than one release ahead of
HotLoop 4.18.10. 0022_x.sql is the newest migration this release knows, and the
database has 2 it does not (up to 0024_z.sql), written by 4.19.0 and 4.20.0.
Only the release right after this one is known to work on that schema. Start
HotLoop 4.20.0 or newer against this database (an update to :stable gets
there), or restore a backup taken by HotLoop 4.18.10 or earlier
```

`:stable` に従うボックスでは、次の更新で直ります。`:stable` がすべてのマイグレーションを知る最新リリースに移るからです。それまでユニットは「activating」のままです。これは意図したものです。停止していて理由を言うボックスは、動いていて間違っているボックスより優れています。

ガードは、起動時にマイグレーションするかどうか(`HOTLOOP_DB_MIGRATE`)にかかわらず、また同じ方法でデータベースを開く復元のときにも動きます。ガードより前のデータベースには `app_version` 列がなく、読み込むリリースより新しいマイグレーションを持てないので、起動します。列はガードを持つリリースの最初の起動で追加されます。

## 実際のリリースでの検証

リリースを出す前に、新しいリリースがマイグレーションしたデータベースの上で前のリリースを起動し、ログインし、デバイスとタグを読み、ゲートを通して書き込み、履歴を読めるようにします。できなければ、そのリリースは出しません。
