インテグレーションとは、アドレスがわかっている種類のデバイスに HotLoop を向け、いくつかの質問に答え、そのデバイスに実際に何があるかを確認して、必要なポイントを残すための方法です。デバイスとそのタグが作成されます。エンティティは他のすべてのタグと同じようにタグから作られるため、新しいポイントは 1 分後にはエンティティ API、オートメーション、ダッシュボードで使えます。

デバイスが HotLoop に入る方法は 3 つあり、互いに並行して使うことを想定しています。

| <span class="sr-only">詳細</span> | 開始する側 | 必要なもの |
|---|---|---|
| [MQTT ディスカバリー](/ja/iot/mqtt-discovery/) | デバイスが、ブローカーに自分自身を通知する | いずれかの形式で発行するパブリッシャー |
| [ネットワークディスカバリー](/ja/iot/network-discovery/) | ネットワークが、傍受される | デバイス側では不要。聞き取った内容と、HotLoop がどう通信できるかを知らせます |
| **インテグレーション**(このページ) | アドレスを持つあなた | 自身のプロトコルに応答するデバイス |

インテグレーションがデバイスに書き込むことは決してなく、作成されるものはいずれも有効化されていません。見つかったポイントは、まだ誰もコマンドしてよいと決めていないポイントです。そのため、セットアップが作成するすべてのタグは、他のあらゆるソースのタグと同様に、誰かがタグエディターで 1 つずつ有効化するまで読み取り専用です。

## 利用できるもの

| インテグレーション | プロトコル | 検証に使用したもの |
|---|---|---|
| OPC UA サーバー(`opcua`) | [OPC UA](/ja/iot/protocols/#opc-ua) | 実際の OPC UA サーバー |
| SNMP デバイス(`snmp`) | [SNMP](/ja/iot/protocols/#snmp) | 実際の SNMP エージェント、v1、v2c、v3 |
| BACnet/IP デバイス(`bacnet`) | [BACnet/IP](/ja/iot/protocols/#bacnetip) | 独立した BACnet スタック |
| CODESYS PLC(`codesys`) | [CODESYS](/ja/iot/protocols/#codesys) | CODESYS Control for Linux SL 4.22.0.0、実際の PLC プログラム 2 本(1 本はずっと大規模) |

実際のサーバーで確認できたものから順に、このフレームワークに追加されます。

## 逆方向

インテグレーションはデバイスを取り込みます。HotLoop の測定値とイベントを Kafka ブローカーに送り出すには、ヒストリアンのターゲットにある [Kafka API イベントストリーム](/ja/iot/historian-targets/#kafka-apiイベントストリーム)を参照してください。Apache Kafka と Redpanda、TLS と SASL に対応し、測定値は 1 つのトピックに、システムログは別のトピックに送ります。OPC UA PubSub(UDP 上の UADP)として送る場合や、パブリッシャーのものを読む場合は、[OPC UA PubSub](/ja/iot/protocols/#opc-ua-pubsub-uadp) を参照してください。読み取りは `opcua-pubsub` プロトコルのデバイスとして構成し、データグラムには名前ではなくフィールドの位置が含まれるため、セットアップの手順はありません。

## SNMP

スイッチ、UPS、PDU、電力計など、SNMP エージェントが動作するあらゆる機器向けです。質問はバージョンによって変わります。v2c ではコミュニティを、v3 ではユーザーと、そのセキュリティレベルで必要なパスフレーズだけを尋ねます。既定のコミュニティはありません。

プローブは、SNMP エージェントの system グループ、インターフェーステーブル、ホストリソース、負荷テーブル、extend の出力、つまり HotLoop が名前を付けられるオブジェクトをたどり、それぞれをエージェントが現在保持していると答えた値とともに表示します。新しいデバイスに向ける人が必要とするものを**提案**します。デバイスの名前、設置場所、稼働時間(エージェントの 100 分の 1 秒ではなく秒単位)、各インターフェースの動作状態とエラー数、バイトカウンター(エージェントが対応していれば 64 ビット版)、負荷平均、extend の各行です。提案されたポイントのうちカウンターがいくつあるかをノートに記します。グラフ上のカウンターには変化率が必要だからです。

エージェントが持つそれ以外のものも引き続き読み取れます。アドレスが OID のタグとして手動で設定してください。タグがどうなるか、存在しないオブジェクトがどう扱われるか、v2c コミュニティが間違っているとなぜデバイスが応答しないように見えるかは、[SNMP ドライバー](/ja/iot/protocols/#snmp)を参照してください。

ここでの SNMP は常に読み取り専用です。HotLoop は SET を送信しません。

## BACnet/IP

ビル管理コントローラー、メーター、サーモスタットなど、IP ネットワーク上で BACnet を使うあらゆる機器向けです。質問は、デバイスのアドレス、わかっている場合はデバイスインスタンス(この場合、HotLoop はそのアドレスで別のデバイスが応答することを拒否します)、マシンにネットワークカードが 2 枚ある場合にどちらから送信するか、です。

プローブはデバイスに自分が何者かを尋ね、オブジェクトリストを読み取り、見つかったすべてのアナログ、バイナリ、マルチステートのオブジェクト(および整数、大きなアナログ、アキュムレーター、文字列の値)を読み取ります。名前、説明、単位、現在値、ステータスフラグを読みます。それぞれを今読み取った値とともに表示し、最初の 100 個を提案します。単位はラベルとして、また該当する場合はデバイスクラスとして取り込まれるため、`degrees-celsius` の入力は `°C` の温度になります。

ノートには、フォールトを報告しているオブジェクトの数(デバイスが解除するまで不良として読み取られます)と、使用停止中のオブジェクトの数(書き込まれた値が残っているため不確かとして読み取られます)が記されます。マルチステートのオブジェクトの説明にはその状態が列挙され、サンプルには数値に加えて状態が表示されます。

ここでの BACnet は常に読み取り専用です。HotLoop はプロパティを書き込まず、BACnet ルーターの先にあるデバイスにも到達しません。何が対象で何が対象外かは、[BACnet/IP ドライバー](/ja/iot/protocols/#bacnetip)を参照してください。

## CODESYS

CODESYS Control ランタイムを実行する PLC 向けです。質問は OPC UA のもの(アドレス、セキュリティ、PLC のユーザー管理が有効な場合はユーザー名とパスワード)で、必要な場合に限り、一覧するアプリケーションの範囲、PLC とアプリケーションの名前、一覧する配列の要素数も尋ねます。

プローブはランタイムの OPC UA サーバーに接続して PLC とそのアプリケーションを見つけ、アプリケーションがエクスポートしている変数(Symbol Configuration)を、プログラマーが付けた名前で、型と書き込み可能かどうかとともに一覧します。バッファの要素ではなくアプリケーション自身の変数を提案し、一部だけ一覧した配列がいくつあるかをノートに記します。何もエクスポートしていない PLC には、エクスポートの方法を案内します。

CODESYS デバイスは 1 秒に 1 回読み取られます。これはドライバーがランタイムの OPC UA サーバーに各変数を監視するよう求める頻度であり、画面は PLC より約 1 秒遅れるだけで、それ以上ではありません。ランタイム自体の既定値は 5 秒で、画面には遅すぎます。ポンプが始動してもページには 5 秒後に表示されます。もっと速く求めるには、デバイスのポーリング間隔か `samplingIntervalMs` を変更してください。すべてのデバイスに課される下限とサーバーの OperationLimits は引き続き適用されます。

リクエストに `"dashboard": true` を指定してセットアップすると、残したポイントに加えて、デバイス名の付いたダッシュボードも作成されます。見出し、動く数値のトレンド、デバイスのアラーム、変数リスト用の見出しの下にポイントごとの値カードが含まれます。プログラムをそのまま元に作られた最初の画面で、他のダッシュボードと同じように編集できます。この画面からは何もコマンドせず、すべてのタグは有効化するまで読み取り専用です。

ランタイムが再起動した PLC や新しいプログラムがダウンロードされた PLC は、自動的に再び取り込まれます。[CODESYS ドライバー](/ja/iot/protocols/#codesys)を参照してください。

## 流れ

呼び出しは 3 回で、順番に行い、最初の 2 回は何も保存しません。

1. **尋ねる。** `GET /api/integrations` は、すべてのインテグレーションとその質問を一覧します。各質問には種類(`text`、`number`、`bool`、`choice`、`secret`)、既定値、必須かどうか、別の回答に応じてのみ意味を持つ場合の `showWhen` があります。画面はこれだけで描画されるため、新しいインテグレーションに新しい画面は不要です。
2. **確認する。** `POST /api/integrations/{id}/probe` は回答を受け取って検証し、インテグレーション自身のドライバーで実際のデバイスに接続して、それが何で何を持っているかを報告します。提案名、デバイス自身の申告内容、読む価値のあるノート、そして見つかったすべてのポイントを、読み取った値の `sample` を含むタグの形のレコードで返すので、機械自身の表示にある数値と比べられます。
3. **残す。** `POST /api/integrations/{id}/setup` は同じ回答と残すポイントの名前を受け取り(名前がなければ `suggested` と印の付いたものを残します)、デバイスとそのタグを作成して、ランタイムを再読み込みします。デバイスは有効化され、ポーリングされます。最初のダッシュボードを作成できるインテグレーション(CODESYS)は、リクエストに `"dashboard": true` があれば作成し、ダッシュボードの id を返します。

セットアップはプローブを信用せず、デバイスをもう一度確認します。クライアントが 1 分前に見つけたと思っている内容は主張にすぎず、ポイントはデバイスが作成される時点のデバイスの状態と照合されます。デバイスにない名前は、飛ばされるポイントではなく `400` になります。誰かが名前を指定して求めたからです。

セットアップが途中で失敗した場合(デバイスは保存されたがタグは保存されなかった場合)は、作成したばかりのデバイスを削除します。すでに存在するデバイスは、上書きされずに `400` で拒否されます。既存のデバイスにポイントを追加するには、そのデバイスの Browse と Import を使ってください。

## 何かを試す前に回答を検証します

フレームワークは、インテグレーションが回答を見る前にすべての回答を質問と照合し、すべての問題を一度に報告するため、フォームは 1 回で修正できます。

* 空の必須の質問は「X is required」になります。
* 数値は質問の範囲内の整数、選択はその選択肢のいずれか、bool は bool でなければなりません。
* インテグレーションが尋ねていない質問への回答は、無視されず拒否されます。スペルミスの `pasword` が何も言わずに捨てられると、理由のヒントもなくログインに失敗するデバイスになるからです。
* シークレットは、保存された値の代わりに API が表示する `[redacted]` というプレースホルダーであってはなりません。それを送り返すと、プレースホルダーがパスワードとして保存されてしまいます。
* 表示されない質問(`showWhen`)は無視され、必須にはなりません。

認証情報はデバイスのものと同じ方法で保持されます。HotLoop に封印キーがあれば保管時に封印され、すべての API 応答とすべてのエラーで隠されます。プローブは、受け取った内容を保存することは決してありません。

## デバイスが応答しないとき

`502` で、何が起きたかが示されます。何も接続できなかった場合は "could not reach the device: ..."、接続はできたがその後応答しなかった場合は "connected, but could not list its points: ..." です。これは読み取るべきデバイスの応答であり、HotLoop の不具合でも不正なリクエストでもありません。閉じたポート、間違ったコミュニティ、ファイアウォールはいずれもここに行き着き、メッセージはドライバー自身のものです。

## 製品内での位置づけ

プローブとセットアップは HotLoop のマシンからネットワーク越しに接続するため、デバイスの保存と同様に、どちらも `devices.write` が必要です。一覧には `devices.read` が必要です。すべての製品に備わっています。ルートは [HTTP API](/ja/iot/api/#インテグレーション) にあります。

## 追加するには

* `Info()` は、それが何かを示します。id、名前、ドライバーのプロトコル、アドレスの尋ね方、質問です。
* `Configure()` は、検証済みの回答をアドレスとドライバー自身の設定ブロックに変換し、質問では表現できないものを拒否します。
* `Discover()` は、実際のデバイスに接続して、そこに何があるかを報告します。

フレームワークは起動時に、カタログの項目になれないインテグレーションを拒否します。id の重複、モデルが宣言していないプロトコル、ラベルのない質問、選択肢のない選択、有効な回答ではない既定値、存在しない質問を指す `showWhen` です。テストでは、すべてのインテグレーションがドライバーのコンパイル済みのプロトコルを使っていることも確認します。

実行できる実際のサーバーがない場合、インテグレーションはなく、どれがハードウェアを待っているかは[ロードマップ](/ja/roadmap/)に記載されています。
