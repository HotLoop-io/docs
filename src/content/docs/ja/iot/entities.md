エンティティレジストリと、エンティティの状態を計算するエンジンは、HotLoopのすべてのオートメーション、ヘルパー、スクリプト、画面の土台です。

## タグがあるのに、なぜエンティティなのか

タグはドライバーが扱うものです。ホールディングレジスタ、NodeId、S7のDBオフセットがそれにあたります。タグはデバイスとタグ名で特定され、名前を変えることはできず、配線上のちょうど1点だけを指します。

エンティティは人とルールが扱うものです。「ゾーン1の温度」「コンベアの運転スイッチ」のようなものです。エンティティには固有の安定した名前(`sensor.zone_1_temperature`)があり、どう表示できて何ができるかを示す種類があり、構成要素であるタグへのバインディングがあります。

エンティティはタグを包みます。タグを置き換えるものではなく、エンティティのためにタグについて変わったことは何もありません。2つ目の値パイプラインも、2つ目のヒストリアンもありません。エンティティの状態は、`/api/values`、アラームエンジン、OPC UAサーバーがすでに読んでいるのと同じライブキャッシュから計算されます。エンティティが登場する前からあるタグのエンドポイント、ボード、`/api/write`、MCPツール、オートメーションルールは、すべて以前とまったく同じように動きます。エンティティは既存のものの代わりではなく、その隣に追加されます。

## 何もしなくても手に入るもの

すべてのタグは、自動的に**読み取りエンティティ**を持ちます。

| タグのデータ型 | 読み取りエンティティのドメイン |
|---|---|
| `bool`, `boolean`, `bit`, `coil`, `discrete` | `binary_sensor` |
| それ以外すべて | `sensor` |

タグが初めて書き込み可能になると、**制御エンティティ**も持ちます。

| タグのデータ型 | 制御エンティティのドメイン |
|---|---|
| boolの仲間 | `switch` |
| intとfloatの仲間 | `number` |
| `string`, `text`, `char` | `text` |

制御エンティティは、タグの有効化が解除されても削除されません。書き込みゲートはこれまでどおり、有効化が解除されたタグへの書き込みを拒否し、エンティティの`armed`属性は`false`になるので、画面は制御部分をグレーアウトできます。エンティティを残すことが肝心です。`switch.press_01_pump`を名前で使うオートメーションやダッシュボードが、シフトの間だけ誰かがポンプの有効化を解除したせいで壊れてはいけません。

既存のタグのエンティティは、アップグレードの中で作られます。マイグレーション`0005_entities.sql`が、テーブルを作るのと同じトランザクションの中で、すべてのタグの読み取りエンティティと、すでに書き込み可能なすべてのタグの制御エンティティを補充します。新しいバージョンが最初のリクエストに応答する時点で、すべてのタグにエンティティがあるか、何も変わっていないかのどちらかです。

すべてのアラーム定義も、同じように**アラームエンティティ**を持ちます。[アラームエンティティ](#アラームエンティティ)を参照してください。

制御エンティティへの指令(スイッチをオンにする、数値を設定する)はサービス呼び出しであり、サービス呼び出しは、ほかのあらゆる書き込みと同じく`runtime.Manager.Write`と書き込みゲートを通るタグへの書き込みです。ほかの入口はありません。[サービス](#サービス)を参照してください。

タグ1つでは済まない設備(運転指令、運転接点、故障を持つポンプ、リミットスイッチを持つバルブ、PIDループ)は、構成するタグから意図して作る**複合エンティティ**です。[複合設備](#複合設備)を参照してください。

## エンティティID

`entity_id`は`<domain>.<object_id>`の形で、小文字、数字、アンダースコアからなり、最大255文字です。タグの自動IDは`<domain>.<device>_<tag>`で、どちらの部分も小文字になり、ASCIIの英字と数字以外の連続は1つのアンダースコアになります。

| デバイス | タグ | 読み取りエンティティ |
|---|---|---|
| `press-01` | `Zone1_Temp` | `sensor.press_01_zone1_temp` |
| `Line.A-2` | `Motor/Speed.PV` | `sensor.line_a_2_motor_speed_pv` |
| `press-01` | `温度` | `sensor.press_01_tag` |

同じIDになるタグが複数ある場合は、登録された順に`_2`、`_3`と続きます。255文字を超える名前は、サフィックスの手前で切られ、サフィックスが切られることはありません。

**`entity_id`は一度だけ生成され、保存され、二度と再生成されません。** タグの説明を変えても、データ型を変えても、別のレジスタに移しても、entity_idには影響しません。変えられるのは、`PUT /api/entities/{entity_id}`による明示的な名前変更だけで、これは管理者の操作であり、システムログに記録されます(カテゴリは`config`、対象は新しいID、古いIDはメッセージと詳細)。

名前を変えてもドメインは保たれます。エンティティの同一性はデータベースの`id`と`unique_id`であり、どちらも決して動きません。

| エンティティ | `unique_id` |
|---|---|
| タグの読み取りエンティティ | `tag:<device>/<tag>` |
| タグの制御エンティティ | `tag-control:<device>/<tag>` |
| アラームエンティティ | `alarm:<definition id>` |
| 複合エンティティ | `composite:<32 random hex digits>` |

最初の3つは、エンティティが包むものから導かれます。そのため、削除されたタグやアラーム定義が戻ってくると、同じエンティティを引き継げます。複合エンティティには、そこから導けるものがありません。同じPLC上の同一のポンプ2台は別々のタグにバインドされ、同じタグが意図的に2つの複合エンティティを支えることもあります。そのため`unique_id`は、作成時に一度だけランダムに作られます。削除してから作り直した複合エンティティを含め、ほかのどれとも衝突することはなく、作り直したものは新しいエンティティであるべきです。

## 削除されたタグ、孤立エンティティ、再引き継ぎ

タグを削除すると、そのエンティティは削除されず**孤立**します。`orphaned_at`が設定され、状態は`unavailable`になります。タグエディタやブラウズの再インポートで同じタグを戻すと、レジストリが`unique_id`で孤立エンティティを見つけて引き継ぎます。entity_id、名前、デバイスクラス、アイコン、そのほかすべてのカスタマイズが一緒に戻ってきます。

これは意図した動作です。現場では、タグの削除と再インポートが、「この点についてすべて忘れる」という意味で行われることはめったになく、ずっと頻繁に起きます。`sensor.oven_temperature`を名前で使うオートメーションは、その間も動き続けるべきです。

デバイス全体の削除は別です。タグが一緒に消えるのと同じく、そのエンティティも一緒に消えます。タグがすべてそのデバイス上にある複合エンティティも含まれます。複数のデバイスにまたがる複合エンティティはどのデバイスにも属さず、デバイスが1つ消えても失うのは状態だけです。

アラームエンティティは、同じ規則でアラーム定義に従います。定義を削除するとエンティティは孤立し、同じidで定義を保存すると引き継がれます。

複合エンティティは孤立しません。意図して作ったものなので、誰かが削除するまで残り、タグが1つなくなっている間は`unavailable`です。

`DELETE /api/entities/{entity_id}`は、複合エンティティか孤立エンティティを削除します。包んでいるものがまだ存在するタグやアラーム定義のエンティティは拒否(409)し、どうすれば消えるかを伝えます。タグか定義を削除し、そのあとで孤立エンティティを削除します。生きているものを削除しても、次の同期が新しいIDで作り直すだけで、その間、その名前を使うすべてが壊れます。画面から外すには、非表示にするか無効にしてください。

## レジストリが追従する仕組み

レジストリは、タグが変わりうるすべての場所にフックを仕掛けるのではなく、突き合わせます。すべてのタグとすべてのエンティティを読み、足りないものを作り、タグを失ったものを孤立させ、タグが戻ったものを引き継ぎます。突き合わせは、来年誰かが追加する経路も取りこぼさず、2回実行しても1回実行したのと同じです。次のタイミングで実行されます。

- 起動時。アップグレードとバックアップからの復元を含みます。
- ランタイムの再読み込みのたび。タグやデバイスの変更のたびにすでに起こります。
- タグ(`POST /api/tags`、`DELETE /api/tags/...`、`POST /api/devices/{id}/import`、`DELETE /api/devices/{id}`)とアラーム定義(`POST /api/alarms`、`DELETE /api/alarms/{id}`)を変えるAPIハンドラー内で同期して。そのため、タグや定義を作ってすぐにそのエンティティを求めるクライアントも、見つけられます。

登録はデータベースのアドバイザリロックでレプリカ間で直列化されるので、同じデバイスをインポートする2つのレプリカが同じ`_2`を配ることはありません。何かを変えた突き合わせは、エンティティごとではなく、システムログに1行だけ書きます。5千点のインポートでも、イベントは1つです。

## 状態

`GET /api/states/{entity_id}`:

```json
{
  "entity_id": "sensor.press_01_zone1_temp",
  "state": "212.5",
  "attributes": {
    "friendly_name": "Zone1_Temp",
    "unit_of_measurement": "F",
    "device_class": "temperature",
    "source": ["press-01/Zone1_Temp"]
  },
  "quality": "good",
  "last_changed": "2026-09-26T14:02:11.482Z",
  "last_updated": "2026-09-26T14:02:11.482Z",
  "last_reported": "2026-09-26T14:07:40.100Z"
}
```

`state`は、単位を除いた値です。数値は`/api/values`が表示するとおり、`binary_sensor`と`switch`は`on`か`off`、文字列はそのテキストそのものです。単位は属性です。ときに`212.5`、ときに`212.5 F`になる状態は、何とも比較できません。

適用される順の規則です。OPC UAサーバーがステータスコードに使うのと同じ規則で、理由も同じです。**状態は、その根拠より良くなることはありません。**

| 条件 | `state` | `quality` |
|---|---|---|
| エンティティが孤立している、またはタグがない | `unavailable` | `bad` |
| デバイスが無効、削除済み、またはリンクが上がっていない | `unavailable` | `bad` |
| リンクは上がっているが、このセッションではまだ何も読めていない | `unknown` | `bad` |
| 不良な読み取り | **最後の良好な値**。一度もなければ`unknown` | `bad` |
| 読み取りは良好だが、デバイスのほかの点が失敗している(劣化) | その値 | `uncertain` |
| 良好な読み取り | その値 | `good` |

不良な読み取りの規則は、見かけより重要です。ドライバーは、読めなかった点を値0の不良な読み取りとして報告します。その0を状態として見せると、「レベル発信器が応答しなくなった」が「タンクが空だ」に変わってしまいます。エンティティは、信頼できた最後の値を表示し続け、`quality`で、もうその値を保証できないことを伝えます。

点の故障とデバイスの故障の違いに注意してください。すべてのブロックが失敗するModbusデバイスはセッションを切って再接続するので、そのエンティティは`unavailable`になります。一部の点には応答し、ほかには応答しないデバイスは接続を保ち(劣化)、失敗している点のエンティティだけが`bad`になります。

**応答しなくなったModbusデバイスがどのくらいで表示されるか。** 接続を拒否したり閉じたりするデバイスは、次のポーリングまでに`unavailable`になります。ただ応答を止めたデバイス(抜けたケーブル、固まったPLC、再起動したスイッチ)はソケットを開いたままなので、ポーリングのタイムアウトで判定されます。そのエンティティは、ポーリング間隔にデバイスのタイムアウトの2倍を加えた時間、さらにエンジンのバックアップ再計算の最大1秒を加えた時間のうちに`unavailable`になります。たいていはタイムアウト1回分で、2回分になるのは、ポーリングの途中でデバイスが止まったときです。すでに配線上にあるリクエストにも、タイムアウト全体が与えられるからです。それまでは新しく読めたものがないので、エンティティは最後の読み取りをそのまま表示します。接続を受け付けるのに固まったデバイスはすぐに再接続されるため、その後は、デバイスが再び応答するまで、エンティティは`unavailable`と`unknown`(接続済み、未読み取り)を行き来します。どちらも値と取り違えられることはありません。調整できるのはタイムアウトです。タイムアウトが20秒のデバイスは、停止してから20秒から40秒は正常に見えることがあるので、デバイスが応答するのに必要な時間より長くは設定しないでください。

この表は、1つのタグのエンティティについてのものです。複合エンティティはより厳しく(不良な読み取りは最後の値を保たない。[複合エンティティの状態の決まり方](#複合エンティティの状態の決まり方)を参照)、アラームエンティティの状態はアラームエンジンのものです([アラームエンティティ](#アラームエンティティ)を参照)。

### タイムスタンプ

- `last_changed`は、`state`が変わったときだけ動きます。
- `last_updated`は、`state`、`quality`、または属性が変わったときに動きます。
- `last_reported`は、状態の元になった読み取りのタイムスタンプです。読み取りができるまでは存在しません。

状態は保存されず計算されますが、ログブックはすべてのエンティティの最新の状態と、最後に変わった時刻を保持します(`entity_last_state`、[ログブック](/ja/iot/logbook/)を参照)。再起動後に同じ状態で戻ったエンティティは、**`last_changed`を保ちます**。火曜日から動いているポンプは、引き続き火曜日と表示します。デバイスの再接続中にタグのエンティティが通るunavailableとunknownは、変化として数えません。Gatewayが止まっている間に実際に変わった状態は、新しい`last_changed`を得て、ログブックに1行残ります。数値のエンティティ(センサー、数値、ループ、カウンター)とボタンは追跡されないため、それらの`last_updated`と同様に、再起動からやり直しになります。

### 属性

すべてのエンティティは`friendly_name`と`source`(バインドされたタグのキー)を持ちます。そのうえで、該当する場合に次を持ちます。

| 属性 | いつ |
|---|---|
| `unit_of_measurement` | `sensor`と`number`: エンティティ自身の単位、なければタグの単位 |
| `device_class`, `state_class`, `icon` | エンティティに設定されているとき |
| `armed` | 制御エンティティ: いまタグが書き込み可能かどうか |
| `min`, `max` | `number`: エンティティのオプション、なければタグに範囲があればその範囲 |
| `step` | `number`: エンティティのオプション、なければ整数タグでは1 |
| `max_length`, `pattern` | `text`: エンティティのオプション。`max_length`の既定は255 |
| `quality_reason` | タグのエンティティ: 読み取りが良好でなく、ドライバーが理由を知っているとき。`no field at ENERGY.Power`、`payload is not JSON`など。次の良好な読み取りで消えます |

### 無効と非表示

**無効**のエンティティには状態がまったくありません。`/api/states`に現れず、IDで求めると、見つからないではなく無効だと答えます。**非表示**のエンティティは、状態は通常どおりで、このフラグは画面が既定の表示から外すためのものです。

### エンジンの動き

エンジンは`entities`という名前でタグバスを購読し、キューは256バッチです。アラームエンジンやオートメーションエンジンと同じ、取りこぼしを許す約束で、遅い消費者はバッチを失いますが、ポーリングを止めることはありません。エンジンはキャッシュからすべてのエンティティを毎秒1回再計算するので、ここでバッチが落ちても、損失は最大でも1秒です。このティックは、デバイスの最初のポーリングが届くことなど、誰も知らせない変化も拾います。

プロセス内の購読者は`Engine.OnStateChanged`で登録します。エンジン自身のgoroutine上で、変化が起きた順に呼ばれ、「XからYへ」を気にするルールに必要なのはこの点です。素早くなければなりません。エンジンはそれらを待たず、1万件以上遅れると、古いものから捨てて数えます。

`GET /api/diagnostics`は、これを`entities`の下に報告します。

| フィールド | 意味 |
|---|---|
| `entities` | 状態を持つエンティティの数 |
| `droppedBatches` | エンジンが遅すぎて受け取れなかったバスのバッチ(`bus.droppedPerSubscriber.entities`にもあります) |
| `pendingChanges`, `droppedChanges` | 状態変化フックのキュー。バックログが増え続ける、または1件でも捨てられた場合は、フックが遅すぎるということです |

## デバイスクラスと単位

デバイスクラスは、値が何であるか(`temperature`、`pressure`、`volume_flow_rate`、`running`、`problem`)を示し、画面がアイコンを選び、統計の利用側が扱い方を知れるようにします。各クラスには、通常使われる単位があります。完全な表は`model.DeviceClasses`です。

- ドメインにないデバイスクラスは拒否されます。
- クラスで通常使われない単位は、**警告つきで保存されます**。現場は現場のやり方で表記するもので、温度に`degF`と書いたくらいで保存を止める価値はありません。温度では、`F`と`C`が警告なしで受け入れられます。ほとんどのPLCのタグデータベースが実際に使う表記だからです。
- `state_class`(`measurement`、`total`、`total_increasing`)はセンサー専用です。
- **単位の換算はありません。** 単位はラベルです。

## API

エンティティのエンドポイントは、このAPI通常のcamelCaseではなく、snake_caseのフィールド名(`entity_id`、`last_changed`)を使います。意図したものです。その形をすでに理解しているものが、このAPIも理解できるように、エンティティAPIは存在します。

| エンドポイント | 権限 | 内容 |
|---|---|---|
| `GET /api/entities` | `entities.read` | 孤立エンティティを含むすべてのエンティティ。フィルター: `?domain=`、`?device=`、`?orphaned=true\|false` |
| `GET /api/entities/{entity_id}` | `entities.read` | `{"entity": ..., "state": ...}`。無効なエンティティでは`state`はnull |
| `GET /api/entities/{entity_id}/image` | `entities.read` | カメラや画像の最新の画像 |
| `PUT /api/entities/{entity_id}` | `entities.write` | 名前変更を含め、レジストリのフィールドを変更。`{"entity": ..., "warnings": [...]}`を返す |
| `POST /api/entities` | `entities.write` | 複合エンティティを作成。201 `{"entity": ..., "warnings": [...]}`を返す。[複合設備](#複合設備)を参照 |
| `DELETE /api/entities/{entity_id}` | `entities.write` | 複合エンティティか孤立エンティティを削除。それ以外は409 |
| `GET /api/states` | `entities.read` | 有効なすべてのエンティティの状態をentity_id順に。フィルター: `?domain=` |
| `GET /api/states/{entity_id}` | `entities.read` | 1つの状態 |
| `POST /api/services/{domain}/{service}` | `values.write`(`alarm`は`alarms.ack`) | 1つのエンティティに対するサービス呼び出し。[サービス](#サービス)を参照。`?dry_run=true`は、実行する代わりに何をするかを尋ねます。[先に尋ねる](#先に尋ねる-ドライラン)を参照 |
| `GET /api/writes?entity={entity_id}` | `values.read` | 1つのエンティティに対してサービス呼び出しが行った、または拒否されたすべての書き込み。新しい順 |

すべてのロールが`entities.read`を持ちます。エンティティの状態は、別の名前のタグの値であり、ビューアーはすでにそれを読めるからです。`entities.write`を持つのは管理者だけです。entity_idは、すべてのオートメーション、ダッシュボード、エージェントがエンティティを指す名前であり、それを変えるのは操作ではなく設定だからです。

`PUT`の本文は、名前を挙げたフィールドだけを変えます。不明なフィールドは拒否され、同一性のフィールド(`unique_id`、`domain`、`platform`、デバイス、バインディング)も拒否されます。

```json
{
  "entity_id": "sensor.zone_1_temperature",
  "name": "Zone 1 temperature",
  "device_class": "temperature",
  "state_class": "measurement",
  "unit_of_measurement": "°F",
  "icon": "mdi:thermometer",
  "entity_category": "",
  "options": {},
  "disabled": false,
  "hidden": false
}
```

`options`は、`number`では`min`、`max`、`step`(画面が提示する範囲を狭めます。書き込みゲートは、いずれの場合もタグ自身の範囲を確認します)を、`text`では`max_length`と`pattern`を受け付けます。複合エンティティのオプションは固有のもので(下の各ドメインを参照)、オプションを変える`PUT`は、作成時とまったく同じようにタグに照らして検査されます。`sensor`、`binary_sensor`、`switch`、`alarm`はオプションを受け付けません。

エンティティには、設備ツリー上の場所とラベルの集合もあります。`equipment_id`(nullならデバイスに従う)、クライアントがグループ化に使う読み取り専用の`area_id`、そして`labels`です。`PUT`は`equipment_id`と`labels`をほかのフィールドと同じように受け付けます。[設備ツリーとラベル](/ja/iot/equipment/)を参照してください。

## サービス

サービスは、エンティティに対してできることです。`switch.turn_on`や`number.set_value`のようなものです。エンティティに対してしてほしいことを名前で示すもので、その下にあるのはタグへの書き込みだけです。

```
POST /api/services/switch/turn_on
{"entity_id": "switch.press_01_pump", "reason": "start of shift"}

POST /api/services/number/set_value
{"entity_id": "number.press_01_zone1_sp", "value": 212.5}
```

本文は、`entity_id`、任意の`reason`、サービスデータです。1回の呼び出しにつき1つのエンティティで、リストは受け付けません。「何が送られたか」への答えは、1つのエンティティについてのものであるべきだからです。

### ドメインごとに受け付けるもの

| サービス | データ | 書き込む内容 |
|---|---|---|
| `switch.turn_on`, `switch.turn_off` | なし | コマンドタグに`true`または`false` |
| `switch.toggle` | なし | 状態そのものと同じ規則でライブキャッシュから読んだ現在の状態の反対。状態が`unknown`、`unavailable`、または品質が不良なら、呼び出しは拒否されます。状態がわからないものを切り替えるのは、どちらに動かすかを当てずっぽうで決めることです。`turn_on`か`turn_off`を指定してください |
| `number.set_value` | `value`、数値 | コマンドタグにその値 |
| `text.set_value` | `value`、文字列 | コマンドタグにその文字列 |

| `button.press` | なし | コマンドタグに`press_value`、`pulse_ms`後に`release_value`。`single_shot`のボタンは`press_value`を1回書き、その後は何も書かない |

ロールがバインドされていない複合サービス(`speed_command`のないモーターの`set_speed`)は、何かを計画する前に、不明なサービスとして拒否されます。

`sensor`と`binary_sensor`は読み取り専用で、サービスを受け付けません。サービスが受け付けないフィールドを含むサービスデータは、ほかの本文でフィールド名の綴りを間違えたときと同じように拒否されます。意図したフィールドを黙って落として進む呼び出しは、できないと伝える呼び出しより悪いのです。

整数である数値は、整数タグには整数として届きます。`42.0`は`42`です。

### すべての呼び出しは書き込みゲートを通ります

サービス呼び出しは、順序のある書き込みのリストになり、すべての書き込みが`runtime.Manager.Write`を通ります。そのため、ゲートがタグへの書き込みに課すことは、サービス呼び出しにも同じ順序で課されます。

1. 書き込みが有効であること(`safety.allowWrites`)。エージェントの場合は、エージェントの書き込みも有効であること
2. タグが有効化されていること(`writable`)
3. 値がタグの範囲内にあること。拒否され、丸められることはありません
4. そのうえで、エンティティだけが知っていることを、その時点のエンティティとタグに対してゲートの中で検査
   - エンティティが無効でないこと(状態のないものへの指令は許されません)
   - `number`自身の`min`と`max`。タグの範囲を狭めることしかできません
   - `number`の`step`。最小値(自身の最小値、なければタグの範囲の最小値、なければ0)から数えます。整数タグは、エンティティが別に定めない限りstepが1なので、ホールディングレジスタへの`1.5`は、ドライバーが黙って`1`に切り捨てるのではなく、拒否されます
   - `text`の`max_length`(文字数、未設定なら255)と、値全体が一致しなければならない`pattern`
   - エンティティのものではない`select`のオプションやループのモード。要求されたオプションやモードのままゲートに送られ、そこで拒否されるので、存在しないオプションを試した人は記録に残ります
   - 0から100の範囲外のバルブ位置
   - モードタグをその瞬間のライブキャッシュから読んで、手動以外(自動、カスケード、どのモードでもない値、読み取り不能)のときのループの`set_output`

これらのどの段階での拒否も**監査されます**。エンティティ、サービス、呼び出しIDが載り、`succeeded`がfalseで、理由が`refused:`で始まる`write_audit`の行が残ります。`values.write`のないユーザーも含みます。APIは403を返して忘れるわけではありません。呼び出しを拒否済みの印をつけてゲートに送り、ゲートは何も書く前にそれを拒否し、拒否は求められた値とともにエンティティの記録に残ります。

この検査は名前ではなくデバイスへの書き込みの形に合わせてあるので、新しいラッパーや、その場で宣言したインターフェースを通した迂回も捕まえます。

### 呼び出しの応答

```json
{
  "call_id": "9f2c4e1a7b3d5c60",
  "entity_id": "switch.press_01_pump",
  "service": "switch.turn_on",
  "writes": [
    {"tag": "press-01/pump", "value": "true", "status": "written"}
  ]
}
```

各書き込みには、ステータスがあります。

| ステータス | 意味 |
|---|---|
| `written` | デバイスが受け付けた |
| `not_sent` | デバイスに届く前にゲートが退けた: 拒否、セッションなし、開けなかった監査の行 |
| `failed` | 送られたが、デバイスまたは接続がエラーを報告した。反映されたかどうかはわからない |
| `skipped` | 同じ呼び出しの前の書き込みが成功しなかったため、試みなかった |

失敗した呼び出しは、エラーのステータスコードで応答します(403はポリシーまたは権限による拒否、422は値の拒否、409は状態のわからない切り替え、またはサービスに合わない状態の設備、503はデバイスが未接続、502はデバイスが書き込みを受けてエラーを報告、404は該当するエンティティなし、400は不正な形式の呼び出し、500は解放が通らなかった押下、またはGateway内部の障害で、この場合の`error`はサーバーログへの参照だけです)。本文は同じで、`error`が加わります。

1回の呼び出しの書き込みは順番に送られ、成功しなかった最初のものでその呼び出しは終わり、**すでに書いたものは巻き戻されません**。元に戻すこと自体が、すでに動いた設備に対して、誰も頼んでいない書き込みを行うことだからです。それを決めるのは運転員の仕事で、応答は呼び出しがどこで止まったかを正確に伝えます。1回の呼び出しのすべての書き込みは、監査記録と応答で同じ`call_id`を共有します。

例外が1つあり、瞬間的な指令です。ボタンの押下、モーターのリセット、バルブの停止、ビットのカウンターのリセットです。これらは2回の書き込みで、押下と、pulse_ms後の解放です。解放を飛ばすと押しボタンが押されたままになるので、軽々しく飛ばせません。そのため次のようにします。

- 押下が送られてエラーを報告した場合(`failed`)でも、解放は送られます。反映されたかもしれないからです。飛ばすのは、押下が`not_sent`のときだけです。その場合は何も押されたままにはなっていません。
- パルスの最中に呼び出し元が切断しても、解放は送られます。呼び出しは、呼び出し元なしで続きます。
- 押下は書かれ、解放が拒否または失敗した場合、呼び出しは500で失敗し、そう伝えます。タグが**まだ押下の値を保持しているかもしれません**。確認して、手で解放してください。解放の拒否や失敗は、同じ呼び出しIDで監査記録に残り、呼び出しは警告ではなくエラーの重大度でエンティティの下に記録されます。

パルスは`pulse_ms`の長さで、既定は500、最大は10,000です。呼び出しは解放が終わったときに応答するので、呼び出し元はパルスの間待ちます。

各呼び出しは、システムログにも1行として残ります。entity_idの下に、カテゴリ`write`、理由つきで、詳細には、呼び出しID、ソース、ステータスつきのすべての書き込みが入ります。個々のタグへの書き込みは、これまでどおり、それぞれのタグの下に自分の行を持ちます。

`GET /api/writes?entity=switch.press_01_pump`は、拒否を含め新しい順に並べた、そのエンティティの監査記録です。行には`entityId`、`service`、`callId`があり、タグへの直接の書き込みはこれらを持たないので、`/api/writes`を読む既存のすべてのものは、以前とまったく同じものを目にします。マイグレーション`0007_service_audit.sql`が3つの列を追加し、既存のすべての行では空です。

### 先に尋ねる: ドライラン

`POST /api/services/{domain}/{service}?dry_run=true`は、呼び出しで何をするかをゲートに尋ね、実際には何も行いません。本文も権限も同じです。

```json
{"dry_run":true,"entity_id":"number.press_01_zone1_sp","service":"number.set_value","writes":[{"tag":"press-01/zone1_sp","value":"212.5","status":"would_write"}]}
```

```json
{"dry_run":true,"error":"press-01/zone1_sp: this tag is not marked writable","entity_id":"number.press_01_zone1_sp","service":"number.set_value","writes":[{"tag":"press-01/zone1_sp","value":"212.5","status":"not_sent","error":"press-01/zone1_sp: this tag is not marked writable"}]}
```

呼び出しは実際と同じように計画され、行うはずのすべての書き込みが、ゲート自身の検査に、同じ順序で、いまのタグ、エンティティ、デバイスに対して通されます。書き込みの有効化、エージェントのスイッチ、タグの有効化、範囲、エンティティだけが知っているすべて(step、pattern、手動のループ、無効なエンティティ)、そしてデバイスへのセッションです。拒否されることになる最初の書き込みは理由つきで`not_sent`、残りは`skipped`で、`error`は実際の呼び出しが失敗するときのエラーと**一字一句同じ**です。送られることになる書き込みは`would_write`です。両方に答えるのはゲートの1つの関数(`precheck`)なので、ドライランが、実際の書き込みがしない検査で通ることはありません。`alarm`エンティティはタグに書き込まないので、そのドライランは代わりにアラームの検査を行い(エンジンが動作中、定義がまだある、エンティティが有効、保留中のアラームだけ保留解除)、書き込みなしで応答します。アラームには触れず、アラームの記録には何も残りません。

これは質問なので、拒否であろうとなかろうと、判定は200で応答します。実際の呼び出しならどの検査よりも前に退けるリクエスト(該当するエンティティなし、ドメインが受け付けないサービス、受け付けないデータ、状態のわからない切り替え、パスのドメインの誤り)は、実際の呼び出しと同じステータスとエラーで応答します。権限のないユーザーには、同じ403が返ります。

ドライランは何も書かず、監査の行を開かず、システムログに何も残さず、呼び出しIDも消費しません。何も試みていないので、説明すべきことがありません。

これが伝えるのは、**いまこの瞬間に**何が起きるかです。ドライランと実際の呼び出しの間に、デバイスが落ちたり、誰かがタグの有効化を解除したりすることがあり、実際の呼び出しは、書き込みの瞬間に最初からすべて検査し直されます。1つの場合だけ、実際の呼び出し自身の検査より正確に答えます。ワーカーが再接続している間にセッションが切れたデバイスです。実際の書き込みはドライバーまで進んでそこで失敗し(`failed`、503、試みの監査の行)、ドライランは最初から同じエラーで`not_sent`と言います。

エンティティ画面のコマンドプロンプトとエンティティのドロワーは、これを使います。プロンプトが開くときと、値を入力するときに尋ね、拒否は、確認を押す前に、ゲートの言葉のままプロンプトに表示されます。助言であって、ロックではありません。確認は引き続きゲートに行き、ゲートが改めて判断します。

## 複合設備

タグ1つは、エンティティ1つに対応します。ポンプはタグ1つには対応しません。運転指令、運転接点、故障、リセット、場合によっては速度があり、運転員はそれを1つのものとして考えます。複合エンティティはその1つのもので、名前のついた**ロール**ごとに、それぞれのタグにバインドされます。

管理者が`POST /api/entities`で作ります。

```json
{
  "domain": "motor",
  "name": "Infeed pump",
  "device_class": "pump",
  "options": {"pulse_ms": 500},
  "bindings": [
    {"role": "running",       "device_id": "press-01", "tag_name": "P101_Running"},
    {"role": "run_command",   "device_id": "press-01", "tag_name": "P101_RunCmd"},
    {"role": "fault",         "device_id": "press-01", "tag_name": "P101_Fault"},
    {"role": "reset_command", "device_id": "press-01", "tag_name": "P101_Reset"}
  ]
}
```

`entity_id`は任意です。省略すると、名前から作られます(`motor.infeed_pump`、続いて`_2`など)。指定すれば、そのまま使われ、すでに使われているものは黙って`_2`にならず409です。その名前を求めたからです。`name`、`device_class`、`unit_of_measurement`、`icon`、`entity_category`、`options`は、すべてのエンティティが持つレジストリのフィールドと同じです。設備ツリーへの配置とラベル付けは、あとで`PUT`で行います。

作成時には、いまのタグに照らして確認できることをすべて確認し、正しくないものは、何であれ拒否(400、直すべき点を伝える)します。

- ドメインが`select`、`button`、`motor`、`valve`、`loop`、`counter`、`weather`のいずれかであること(`GET /api/entities/composites`が、どれか、また各ドメインのロールを伝えます)。タグのドメインはタグから、`alarm`はアラーム定義から作られます。
- 必須のロールがすべてバインドされ、ドメインにないロールがないこと
- **バインドされたすべてのタグが存在すること**
- **すべてのタグの型がロールに合っていること**: モーターの`running`はbool、バルブの`position`は数値、カウンターのカウントは整数
- **サービスが書き込むすべてのタグが、すでに有効化されていること**(`writable`)。複合エンティティは何も有効化しません。点を有効化するのは、これまでどおり、タグごとに1つずつ人が下す判断です。
- オプションのすべての生の値(selectのオプションの値、ボタンの押下と解放の値、ループのモード)が、そのタグの取りうる値であること。整数レジスタへの`1.5`は、誰かがボタンを押したときではなく、いま拒否されます。

複合エンティティは、タグがすべて1つのデバイス上にあるときはそのデバイスとともに消え、複数にまたがるときはどのデバイスにも属しません。バインディングは固定です。別のタグの組は別のエンティティなので、削除して別のものを作ってください。

すべての作成と削除は、entity_idの下に、カテゴリ`config`で、バインディングとともにシステムログに1行残ります。

### 複合エンティティの状態の決まり方

複合エンティティの状態は、その**フィードバック**から決まります。HotLoopが指令を送ったという事実から計算されることは決してありません。起動を指令されたのに運転接点が入っていないモーターは、運転中ではなく起動中で、接点がいつまでも入らなければ、誰かが見に来るまで起動中のままです。指令タグの読み返しはフィードバックとして数えます。HotLoopが書いたことを覚えているのではなく、PLCが自分の持っている値を伝えているからです。

複合エンティティは**決して楽観的ではありません**。単独のセンサーは、不良な読み取りの間も最後の良好な値を表示し続けますが、複合エンティティはそうしません。状態を決めるすべてのフィードバックのロールに良好な読み取りがなければなりません。そうでなければ、次のとおりです。

| 条件 | `state` | `quality` |
|---|---|---|
| 決定するタグがない、またはそのデバイスが停止している | `unavailable` | `bad` |
| 決定するタグにまだ読み取りがない、または不良 | `unknown` | `bad` |
| 決定するすべてのタグが良好で、そのうち1つが不確定または劣化したデバイス上にある | その状態 | `uncertain` |
| 決定するすべてのタグが良好 | その状態 | `good` |

故障入力が応答しなくなったモーターは、1秒前まで`running`だったとしても、`unknown`です。どのロールが決定するかは下にあり、ほかは属性を埋めるだけで、読めないものは単に省かれます。

複合エンティティの`armed`属性は、そのサービスが書き込むすべてのタグが、いま有効化されているときだけtrueです。ここから起動はできるのに停止はできないモーターは、画面が提示すべきものではありません。

### `motor`

決定するロールは`running`と、バインドされていれば`fault`です。状態は、最初に一致した規則で決まります。

1. `fault`がオン: ほかに何が真でも**`fault`**。運転と故障が同時というのは矛盾で、人が必要なのは故障のほうです。`running`属性は、回っていることをなお伝えます。
2. 運転中で、運転指令の読み返しがオフ: **`stopping`**。
3. 運転中: **`running`**。
4. 運転中でなく、運転指令の読み返しがオン: **`starting`**。
5. それ以外: **`stopped`**。

運転指令の読み返しが読めない場合、それは何も決定せず、モーターは接点だけで`running`か`stopped`になります。HotLoopは、成立しない起動にタイムアウトを設けません。それは起動失敗であり、PLCか、運転接点へのアラーム定義の仕事です。

属性: `running`、`fault`(バインドされていれば)、`command`(読み返し)、`speed`(バインドされ、読めるなら)、`device_class`(`pump`、`fan`、`conveyor`、`compressor`、`agitator`)。

### `valve`

自ら名乗ったバルブ(MQTTディスカバリー)は、`state`ロールで自分の位置を言葉で伝えます。`open`、`closed`、`opening`、`closing`、`stopped`で、それが状態となり、位置を報告する場合は`position`から`current_position`が付きます。これらのどれでもない言葉は`unknown`で、言った内容は`raw_value`に残ります。この節の残りは、PLCのタグで作ったバルブについてです。

決定するロールは、バインドされている`opened`、`closed`、`position`、`fault`のすべてです。状態は、最初に一致した規則で決まります。

1. `fault`がオン: **`fault`**。
2. 両方のリミットスイッチが入っている: **`fault`**、`limit_conflict: true`つき。バルブが開いていて同時に閉じていることはありえないので、スイッチの1つが嘘をついており、どちらかを当てるのは推測の仕事ではありません。
3. 開リミットが入っている: **`open`**。閉リミットが入っている: **`closed`**。
4. リミットスイッチがなく位置だけ: 1%以下は**`closed`**、99%以上は**`open`**。
5. 両端の間で、動作中か、指令されたとおりに停止: 位置指令の読み返しが位置より1%を超えて上なら**`opening`**、1%を超えて下なら**`closing`**、1%以内なら**`stopped`**。オンオフ指令の読み返しがオンなら**`opening`**、オフなら**`closing`**。手がかりがなければ**`stopped`**。

リミットの間で止まっているのに、まだ開指令が出ているオンオフ弁は、`opening`と読まれます。そこで止まっていることを見たいなら、`position`をバインドしてください。

`current_position`は、バインドされていれば位置のフィードバックで、なければ開リミットで100、閉リミットで0、その間では存在しません。そのほかの属性: `open_limit`、`closed_limit`、`fault`、`device_class`(`water`、`gas`、`steam`、`air`)。

### `loop`

状態はプロセス変数で、`pv`だけから、センサーと同じ方法で表示されます。属性は、`setpoint`と`output`(読めるとき)、`mode`(モードタグが読んだモードの名前。読めない場合や、どのモードでもない値のときは`unknown`)、`modes`(設定された名前)、`unit_of_measurement`(エンティティの単位、なければPVタグの単位)です。ループは、センサーのデバイスクラスを受け付けます。温度ループ、圧力ループがその例です。

`set_output`は、**書き込みの瞬間に**ループが手動と読めなければ、ゲートの中で拒否されます。自動のループに出力を書くとコントローラーと争い、カスケードでは2つと争います。読めないモードは、手動ではありません。拒否はほかと同じく、エンティティ、サービス、呼び出しID、求められた値を持つ`write_audit`の行で、呼び出しは409で応答します。先に`set_mode`でループを手動にしてください。

### `counter`

状態はカウントで、整数のタグです。`reset`は、数値型の`reset_command`に0を書くか(PLCがそうやってリセットするなら、カウントのレジスタ自体をバインド)、bool型にパルスを出します。`reset_command`のないカウンターは読み取り専用です。`unit_of_measurement`は、エンティティの単位、なければタグの単位です。

### `weather`

屋上の観測所を1つのエンティティとして: [天気](/ja/iot/weather/)を参照してください。状態は温度で、ほかのすべての読み取りは属性で、そのセンサーが読めるときだけあり、露点、熱指数、風冷えは、それらから算出されます。バインドされているのに読めない読み取りは、`unavailable`に名前が挙がり、0として表示されることは決してありません。サービスは受け付けません。

### `select`

状態は、`state`タグが読んだ生の値に対応するオプションです。どのオプションでもない値は、最も近いオプションや最後のオプションではなく`unknown`で、生の値は`raw_value`に入ります。`options`属性は、オプション名を順に並べます。selectのものではないオプションはゲートで拒否され、求められたオプションとともに監査されます。

### `button`

ボタンにフィードバックはありません。状態は、このGatewayを通した最後の押下の時刻で、Gatewayの起動後に押されていなければ`unknown`です。コマンドタグがなくなったか、デバイスが停止している場合は`unavailable`です。そのときは、押しても働きようがないからです。最後の押下はメモリに保持されるので、再起動でリセットされます。監査記録にはすべての押下が残り、ログブックがボタンの状態を記録しないのも、そのためです。

何を送れるかは、設定に従って属性に入っています。サーモスタットの`hvac_modes`、`fan_modes`、`preset_modes`、`swing_modes`、加湿器の`available_modes`、給湯器の`operation_list`、ファンの`preset_modes`、掃除機の`fan_speed_list`(エンティティの`role_choices`オプションから来ており、ディスカバリーが設定に合わせて保つ)、そして設定値の`min_temp`/`max_temp`と`min_humidity`/`max_humidity`(タグの範囲から)です。画面が提示するのはこれらです。規則を決めるものではありません。属性が何を言っていても、ゲートは設定値をタグの範囲に収め、ドライバーは設定にない言葉を拒否します。3つのキーのどれもない`set_temperature`は、何もしない呼び出しではなく、拒否されます。電源トピックのないサーモスタットの`turn_on`も、「オン」がどのモードかを当てずに、拒否されます。

### `light`

`state`フィードバックによるオンかオフで、読めなければ`unknown`、状態のトピックがまったくなければ、ずっと`unknown`で`feedback: none`です。明るさは属性で、JSONスキーマの照明の`color_mode`、`color`、`color_temp`、`effect`も属性です。表示するだけで、指令はしません。`toggle`はフィードバックに従い、頼れるフィードバックがなければ拒否されます。

### `cover`

あれば`state`フィードバックです。位置だけの場合は、1%以下が`closed`、それより上は`open`です。5つのどれでもない言葉は、`raw_value`つきで`unknown`です。`current_position`は、位置があればその位置です。

### `event`

イベントの状態は、最後に発生した**時刻**(RFC 3339)で、`event_type`はそれが何だったかであり、`event_types`は発生させられるものを列挙します。HotLoopが読み始めてから一度も発生していなければ`unknown`です。サービスは受け付けません。イベントに指令するものはありません。1回のポーリングに2つのイベントがあれば、あとのものとして見え、ログブックと履歴には、それぞれの読み取りが届いたとおりに残ります。

## アラームエンティティ

すべてのアラーム定義はエンティティです。`alarm.<definition id>`(タグと同じ方法でスラッグ化されるので、`oven-temp-hi`は`alarm.oven_temp_hi`)、プラットフォームは`alarm`、`unique_id`は`alarm:<definition id>`で、定義の名前がつきます。バインディングもデバイスもありません。状態はタグのものではなくアラームエンジンのもので、定義は、タグのようにデバイスに属しません(デバイスを削除しても、アラーム定義は残ります)。監視しているタグは、`source`属性です。

状態は、アラームエンジンが保持するISA-18.2の状態で、エンティティの状態の綴り方で表されます。

| アラームエンジン | エンティティの状態 | <span class="sr-only">詳細</span> |
|---|---|---|
| `normal` | `normal` | 条件は解消、未処理なし |
| `unack-active` | `active_unack` | 条件は真、誰も確認応答していない |
| `ack-active` | `active_ack` | 条件は真、確認応答済み |
| `rtn-unack` | `rtn_unack` | 誰かが確認応答する前に解消した |
| `shelved` | `shelved` | 運転員により、決められた時間だけ消音 |
| `suppressed` | `suppressed` | 設計上、消音 |

品質は`good`です。エンジンの状態は読み取りではありません。エンティティが孤立している場合や、Gatewayにアラームエンジンがない場合は`unavailable`です。確認応答を含め、すべての遷移を起きたとおりに追います。

属性: `definition_id`、`source`、`condition`、`limit`、`priority`(1から4)、`priority_label`、`enabled`、`message`、`count`、`active`、`needs_ack`、`trip_value`、`raised_at`、`cleared_at`、`acked_at`、`acked_by`、`shelved_until`、`shelved_by`。最後のものは、該当するときだけあります。

サービス`acknowledge`、`shelve`、`unshelve`はタグに書き込まないので、書き込みゲートを通りません。アラーム画面と`POST /api/alarms/{id}/ack`が呼ぶのと同じ、アラームエンジン自身の`Ack`、`Shelve`、`Unshelve`を呼ぶので、それらとまったく同じように、アラームの記録(`alarm_events`)とシステムログに残ります。必要なのは`values.write`ではなく**`alarms.ack`**です。アラームを確認応答するのは運転員で、ビューアーではありません。拒否された呼び出しは403で応答し、試みた人とともにエンティティの下に記録されます。呼び出しは、理由つきで、エンティティの下のシステムログにも1行残ります。

`unshelve`は、保留中でないアラームには拒否(409)されます。アラームエンジンも拒否し、保留中のアラームを、むやみにnormalにではなく、条件が実際にある状態に戻します。アラームが受け付けないサービス(`turn_on`)は、エンジンに近づく前に、不明なサービス(400)として拒否されます。

### プロバイダーを持つプラットフォーム

アラームエンティティは、最初の**プロバイダー**プラットフォームです。真実の源がタグ以外にあるエンティティです。プロバイダーは、自分のプラットフォームにいまどのエンティティがあるかを伝え、その状態を作り、サービスを実行し、ドライランに答えます。レジストリはタグのエンティティとまったく同じように、`unique_id`でこれらを導き、孤立させ、引き継ぎます。状態エンジンは、プロバイダー自身のイベントと毎秒のティックでそれらを再計算し、それらへのサービス呼び出しは、タグへの書き込みに計画されるのではなくプロバイダーに行きます。タグに書き込むプロバイダーも、ゲートを通して書き込みます。

ヘルパーは2つ目です。`input_boolean`、`input_number`、`input_select`、`input_text`、`input_counter`、`timer`、`schedule`で、PLCではなく工場の人が持つ値であり、HotLoopが保持し、`helpers.write`で設定します。タグには書き込みません。[ヘルパー](/ja/iot/helpers/)を参照してください。

スクリプトは3つ目です。すべてのスクリプトは`script`エンティティ`script.<id>`で、どのプロセスでも実行が進行中ならオン、なければオフです。`turn_on`はサービスデータをフィールドとして実行し、`turn_off`は停止し、どちらも`scripts.run`が必要です。スクリプトを削除すると、アラーム定義を削除したときと同じく、そのエンティティは孤立します。[スクリプト](/ja/iot/scripts/)を参照してください。

レシピは4つ目です。すべてのレシピは`scene`エンティティ`scene.<id>`で、状態は工場に最後に書き込んだ時刻、属性は最新の適用がどうなったかを伝えます。`turn_on`は、`recipes.apply`と、レシピが指定していればそのレシピ自身の権限で適用します。レシピを削除すると、そのエンティティは孤立します。[レシピ](/ja/iot/recipes/)を参照してください。

太陽は5つ目です。`binary_sensor.sun_up`、`sensor.sun_elevation`、`sensor.sun_azimuth`で、現場の緯度と経度から、機器の上で毎秒算出されます。読み取り専用で、サービスは受け付けません。位置のない現場にはなく、位置があったころから残っているものは、unavailableと読まれ、どの変数を設定すべきかを伝えます。[太陽](/ja/iot/sun/)を参照してください。

## ほかのあらゆる場所のエンティティ

### ライブフィード

`GET /api/stream`は、`values`の隣に`entities`イベントを運びます。同じ方法でまとめられ、毎秒最大4回、エンティティごとの最新の状態です。

```
event: entities
data: {"changed":[{"entity_id":"sensor.press_01_zone1_temp","state":"212.5",...}],"removed":[]}
```

`changed`は、前回のイベント以降に変わったすべてのエンティティの完全な状態で、`GET /api/states/{entity_id}`と同じ形です。`removed`は、もう状態がまったくないentity_idです。無効になった、デバイスとともに削除された、または名前が変わって去ったもの(新しい名前は`changed`で届きます)。新しい接続での最初の`entities`イベントは、`snapshot`がすべての読み取りを運ぶのと同じように、すべての状態を運ぶので、何かが変わる前に画面が埋まります。`values`、`snapshot`、`alarm`、`device`のイベントは、以前とまったく同じです。

### MCP

エージェントは、`list_entities`、`get_states`、`call_service`を得ます。`call_service`は、`POST /api/services/...`と同じサービスランナーを通るので、エージェントの呼び出しは、`write_tag`と同様にMCPスイッチで制御され、ソース`mcp`としてエンティティに対して監査されます。[MCP](/ja/iot/mcp/#エンティティ)を参照してください。

### オートメーション

`state`トリガーは、エンティティの状態が変わったときにルールを起動し、条件は`states`、`attrs`、エンティティの`qualities`を読むことができ、`call_service`アクションは、ゲートを通してエンティティに指令し、`automation:<rule-id>`として監査されます。[オートメーション](/ja/iot/automations/#状態トリガーはエンティティに従います)を参照してください。

どちらもエンジンの`OnStateChanged`フックに従っており、[エンジンの動き](#エンジンの動き)の規則が重要なのはそのためです。stateトリガーは、エンジンが計算したすべての変化を、1回ずつ、順番に目にし、エンジンが見なかったものは目にしません。

## 画面

**エンティティ**は、すべてのエンティティを、設備ツリー上の場所(自身の場所、なければデバイスの場所)の下に一覧し、横にツリーがあり、場所、ドメイン、ラベル、テキスト、品質で絞り込みます。1つの場所の中では、設備が先(アラーム、モーター、バルブ、ループ、select、ボタン、カウンター)、次に指令できるもの、そのあとに生の読み取りの順です。

既定では、画面は各信号を1回だけ表示します。エンティティモデルは、1つの点に意図して複数のエンティティを与えます。どれも自分のIDを保ちますが、タイルとして描くと、同じ信号が2回か3回出ることになります。有効化されたタグはセンサーでありスイッチでもあり、モーターにバインドされたタグも、なお自分のセンサーです。実際のラインでは、タイルがほぼ倍になり、設備が埋もれました。そこで、画面はまとめます。

- タグの読み取りエンティティは、制御エンティティの裏に入ります。スイッチや数値がタイルになります。すでにライブの状態を表示しているからです。そのドロワーには、オートメーションやエージェントをつなぐ人のために、センサーのentity_idとともに「センサーとしても利用可能」と表示されます。
- 複合エンティティにバインドされたタグは、複合エンティティの中に、両方のエンティティが入ります。複合エンティティのドロワーには、信号が一覧されます。ロール、タグ、いま読んでいる値、読み取りと制御のentity_idです。2つの複合エンティティにあるタグは、名前順で最初のほうに入ります。
- 非表示でも無効でもない制御か複合エンティティだけが、ほかのものを取り込みます。スイッチを非表示にするか無効にすると、そのセンサーにタイルが戻ります。
- まとめられた信号のアラームは、それが入っているタイルに、アラームの名前つきで印が付き、そこからアラームを開きます。まとめは画面を整えるもので、アラームを隠すことは決してありません。
- 品質バーの横の件数は「13件を表示 · 25件をまとめて表示」と表示され、ほかを含むタイルは、その下部でそう表示します(「信号5件」、「+ センサー」)。ドメインのチップ、ツリーの件数、品質バーは、表示されているタイルを数えます。
- 検索とラベルのフィルターは、タイルの中まで見ます。まとめられたentity_idやタグを検索すると、それを含むタイルが、枠で強調されて、「ここで見つかったもの:」とentity_idつきで現れます。画面全体をすべてのエンティティに切り替えるより、こちらを選びました。タイルの壁ではなく、探していたポンプにたどり着きます。

「すべてのエンティティを表示」は、まとめをオフにして、すべてのエンティティに自分のタイルを与えます。生のレジストリがほしいエンジニアのためです。既定ではオフで、このブラウザーが覚えます(ローカルストレージ。プライベートウィンドウでは忘れます)。ほかの人の画面は変わりません。

状態は、ライブフィードの`entities`イベントで届き、画面がポーリングすることはありません。タイルは、状態が変わると再描画され、中のボタンにフォーカスがあっても再描画されます。それが理由で古い状態を保つタイルは、過去を現在として見せてしまうからです。品質は、値より先に描かれます。

| 品質 | 画面での表示 |
|---|---|
| 良好 | 値、印なし |
| 不確定 | 値、琥珀色の縁と「不確定」のバッジ |
| 不良 | 最後の良好な値を、ハッチの上にグレーで、「不良」と「最後の正常値、読み取り不良」、ドライバーが伝えていればその後に理由 |
| まだ読み取りなし | 斜体の「不明」と、理由があればその理由つきの「読み取り不良」 |
| 利用不可 | 「利用不可」、タイル全体がハッチ |

コントロールは、ドメインとロールに従います。ビューアーには何も見えません。運転員には、`values.write`の背後にあるもの(アラームは`alarms.ack`の背後)が見え、この配備で書き込みがオフのとき、またはエンティティが書き込むタグが有効化されていないときは、理由つきで無効になります。ループの出力は、手動と読めるときだけ提示されます。ゲートが許すのはそのときだけだからです。すべての指令は、どのサービスか、どのタグか、エンティティがいま何を読んでいるかを伝えるプロンプトを開き、監査記録のための理由を受け取ります。拒否されると、プロンプトは開いたまま、ゲートの言葉と、送られた、または送られなかったすべての書き込みを表示します。新しい状態は、指令から仮定されることはありません。デバイスが読み返したときにフィードで戻ってくるか、戻ってこないかです。

ドロワーには、状態とそのタイムスタンプ、コントロール、バインドされたタグの1時間、6時間、または1日の履歴(階段状のトレース、最後の値を現在まで延長、不良な読み取りに印)、同じ信号のほかのエンティティ、バインディング(複合エンティティでは信号)、属性、そしてそのエンティティを通して出された、または拒否されたすべての指令があります。管理者には、entity_id、名前、ツリー上の場所、ラベル、非表示と無効、複合エンティティや孤立エンティティの削除もあります。

**新しい設備**(管理者)は、複合エンティティを作ります。ドメインを選び、名前をつけ、各ロールにタグを選びます。各ロールには、型の合うタグだけが提示され、指令のロールでは、有効化されていないタグを、隠さずに無効として表示します。必須のものには印が付きますが、フォームは強制しません。判断するのはレジストリで、その拒否は書かれたとおりに表示されます。

**工場**は、設備ツリーとラベルです。[設備ツリーとラベル](/ja/iot/equipment/)を参照してください。

## バックアップと復元

`entities`と`entity_bindings`は、entity_idとカスタマイズを含めてバックアップに入っています。複合エンティティ、すべてのロール、すべてのオプションを含み、これはほかのどれより複合エンティティにとって重要です。タグのエンティティはタグから作り直せますが、複合エンティティはバックアップ以外には何も作り直せません。アラームエンティティは定義とともに戻り、エンティティのない復元された定義は、最初の同期でエンティティを得ます。このバージョンより前に取ったバックアップには、どちらのテーブルもありません。復元してGatewayを起動すると、レジストリの最初の同期が、復元されたすべてのタグにエンティティを与えます。`entity_labels`もバックアップに入っており、設備ツリー以前のバックアップを復元する方法は、[設備ツリーとラベル](/ja/iot/equipment/)にあります。

マイグレーション0007は、`write_audit`に3つの列を追加します。それより前に取ったバックアップも復元できます。復元は、今日のテーブルより列が少ないファイルを先頭の列に読み込み、新しい列は既定値を取らせるからで、列を追加するマイグレーションは、常に末尾に追加します。より新しいバージョンのバックアップは、引き続き拒否されます。[バックアップと復元](/ja/iot/backup/)を参照してください。

## まだないもの

コア、設備ツリー、書き込みゲートを通したエンティティへの指令、複合設備、アラームエンティティ、MCPのエンティティ、オートメーション、ライブフィード、そして画面は、すべてそろっています。[HotLoopロードマップ](/ja/roadmap/)を参照してください。stateトリガーの`forSec`(「5分間オン」)は、[オートメーション](/ja/iot/automations/#状態を保つ-forsec)にあります。
