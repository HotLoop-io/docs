ブループリントは、空欄を残して一度だけ書くルールです。「*このモーター*が*この時間*より長く稼働したら知らせ、*私が頼んだら*停止する。」ルールの中身を分かっている人が一度だけ書きます。ほかの全員は、ポンプごと、タンクごと、ラインごとに空欄を埋めるだけで、最後に普通のオートメーションができあがります。

代わりのやり方は、どの工場にもすでにあるものです。同じルールを40台のポンプにコピーし、誰かがバグを見つけた日に37台だけ直す。コピーはずれていきます。ブループリント1つと40組の入力なら、ずれません。

できあがるのは通常のルールです。手書きのルールと並んでオートメーション画面に表示され、同じエンジンが有効にし、ルールが行うすべての書き込みは、拒否も含めて監査され、`automation:<id>` として書き込みゲートを通ります。ブループリント専用のランタイムも、裏口もありません。あるのはフォームとルールだけです。

## ブループリントの唯一の決まり

**ルールは、作成元のブループリントのバージョンを保ちます。**

ブループリントを編集するとバージョンが上がります。そのブループリントから作られたルールは1つも変わりません。火曜日に正しかった7番ポンプのルールが、水曜日に誰かが12番ポンプのことを考えてブループリントを編集したせいで、いつの間にか別のルールになることはありません。地下室を水浸しにするのは7番ポンプだからです。

ルールを新しいバージョンに移すことは**アップグレード**であり、アップグレードは人が求めて行うものです。

1. オートメーション画面がルールの上に表示します。*ブループリント「モーター長時間稼働」バージョン1から作成*、そして*バージョン2が利用可能*。
2. **アップグレードを確認**は、何が変わるのかを部分ごとに変更前と変更後で示し、今すぐルールが起動したら何をするかを正確に示します。書き込みはすべてゲートの検査にかけられます。この時点では何も変わっていません。
3. **アップグレード**は、確認したとおりの内容をそのまま反映します。その間にブループリントがさらに変わった場合や、ほかの誰かがルールをアップグレードした場合は拒否され、もう一度確認することになります。確認した内容がそのまま入るか、何も入らないかのどちらかです。

実行した人とともに記録されます。*オートメーションがブループリント pump_watch のバージョン1から2にアップグレードされました*。

ルールが作られてから誰かが手で編集していた場合、確認画面はその編集が置き換えられるものとして表示します。誰の変更も、先に画面に表示されることなく消えることはありません。

## 1つの構成

```json
{
  "id": "pump_watch",
  "name": "Pump start watch",
  "description": "Says when a pump starts, with the limit it runs to.",
  "inputs": [
    {"name": "pump", "label": "Pump", "type": "entity", "domain": ["switch"], "required": true},
    {"name": "limit", "label": "Limit", "type": "number", "min": 0, "max": 100, "step": 5, "unit": "%", "required": true}
  ],
  "template": {
    "triggers": [{"type": "state", "entityId": {"!input": "pump"}, "to": "on"}],
    "condition": "float(states['sensor.tank_level']) < ${limit}",
    "actions": [
      {"type": "log_event", "params": {"message": "${pump} started, running to ${limit}%"}}
    ],
    "mode": "skip"
  }
}
```

- **`id`** は小文字、数字、アンダースコアで、先頭は文字です。
- **`inputs`** は型つきの空欄です。HotLoop のほかの場所と同じフィールドで、`min`、`max`、`step`、`unit` を持つ `number`、`max_length` と `pattern` を持つ `text`、`boolean`、`options` を持つ `select`、受け付ける `domain` を持つ `entity`、`duration`(秒、または `90s`、`1h30m`)、`alarm`、`tag` があります。それぞれ `required` にしたり `default` を持たせたりできます。
- **`template`** はルール本体です。オートメーションの言語([オートメーション](/ja/iot/automations/))で書いた `description`、`triggers`、`condition`、`actions`、`mode`、`minIntervalSec`、`maxRuntimeSec` です。`id`、`name`、`enabled` は含みません。これらは、そのブループリントから作られる各ルールのものです。

### 空欄

値として書いた **`{"!input": "pump"}`** は、入力の値にその型のまま置き換えられます。entity_id は文字列として `entityId` に入り、duration は数値として `forSec` に入ります。誰も入力しなかった任意入力は `null` です。

文字列の中の **`${pump}`** も置き換えられ、その方法は置かれた場所によって変わります。

- 式(ルールの `condition`、アクションの `expression`、`dataExpressions`、`argExpressions`、`fieldExpressions`、`paramExpressions` の値、メッセージ内の `{{` と `}}` の間にあるすべて)の中では**リテラル**として入ります。文字列は引用符で囲まれ、数値は数値、`true`、`false`、`nil` になります。したがって、上の条件は上限40のとき `float(states['sensor.tank_level']) < 40` になります。
- それ以外の場所では、ただのテキストです。`switch.pump_1 started, running to 40%`。

**`${counter.domain}`** はエンティティ入力のドメインで、選ばれたエンティティの種類に合わせる必要があるサービス名に使います。`"${counter.domain}.reset"` は、PLC のカウンターなら `counter.reset`、カウンターヘルパーなら `input_counter.reset` になります。

この引用符の扱いこそが、テキスト入力を式の中で安全に使える理由のすべてです。テキスト入力に `' || true || '` と入力すると、条件は入力したままのその文字列と比較します。式の一部になることはありません。また、テキスト入力には `{{` を含めることが一切できません。ルールが送るメッセージはどれも、送信時に `{{` と `}}` の間を式として実行するため、フォームに入力された値が式になることがあってはならないからです。

### 保存時の検査

ブループリントは、誰かが試したときではなく、保存される前に検査されます。

- すべての空欄は入力を指しており、`.domain` はエンティティ入力の後にだけ付きます。
- すべての入力はどこかで使われています。テンプレートが無視する入力は何もしないフォームフィールドであり、誰かがそのために午後を無駄にします。
- 各入力の型のサンプル値(既定値があればそれ)で埋めたとき、テンプレートはコンパイルできるルールを作ります。URL になるテキスト入力には、それを示す `pattern`、つまり `https?://\S+` が必要で、なければ URL の検査がサンプルを拒否します。

## 埋めるには

**ブループリント**画面で**使う**を押すとフォームが開きます。ルールの id と名前、そして範囲つきの数値、リスト、エンティティ選択など適切なコントロールで表示された各入力があります。その後は次のとおりです。

- **先に確認**は、どんなルールができるか、そして今すぐ起動したらそのルールが何をするかを答えます。評価された条件、`automation:<id>` として書き込みゲート自身の検査にかけられるすべての書き込みとサービス呼び出し、ゲートの言葉による最初の拒否が示されます。保存も、書き込みも、監査もされません。
- **ルールを作成**はルールを作ります。チェックを外さない限り有効な状態で作られ、オートメーション画面に作成元つきで表示されます。

すべての入力は先に検査され、**合わせるために値を動かすことは決してありません**。最大値が100の入力に150を入れると、黙って100にされるのではなく拒否されます。数値に `"12"` を入れると、解釈されずに拒否されます。誤っている入力はすべて一度に報告されるので、フォームは一覧全体とともに戻ってきます。ルール自身が拒否する値(最長1日までの保持時間に2日)は、ルール自身の言葉で拒否されます。すべてが正しくなるまで、何も作られません。

ルールを作成しても、**既存のルールが置き換えられることはありません**。手書きのルールでもブループリントから作ったルールでも、使用中の id は拒否されます。

API では `POST /api/blueprints/{id}/instantiate` で、確認には `?dry_run=true` を付けます。[HTTP API](/ja/iot/api/#ブループリント) を参照してください。

## 組み込みのブループリント

バイナリに同梱されています。読み取り専用です。**コピー**を押すと、新しい id でバージョン1から始まる自分用のものができ、好きなように変更できます。

| ブループリント | 入力 | ルールの動作 |
|---|---|---|
| `motor_running_too_long` | モーター、稼働を許す時間(既定は1時間)、停止するかどうか | モーターが一度にその時間 `running` だったとき、警告を記録します。求められれば `motor.stop` で停止します。 |
| `tank_high_level_stop_pump` | レベルセンサー、上限、ポンプ(モーター) | レベルが上限以上で、測定値の品質が良好で、ポンプがまだ停止していなければ、ポンプを停止して記録します。 |
| `alarm_to_notify` | アラーム、動作する状態(既定は `unack-active`)、Webhook の URL | アラームがその状態になったとき、`{"text": "Alarm temp-hi is unack-active"}` を URL に POST します。 |
| `device_silent_cycle_its_port` | デバイスのオンラインセンサー、無応答を許す時間(既定は5分)、UniFi デバイスとポートの電源再投入タグ、その後に待つ時間(既定は3分)、アラーム、実行間の最短間隔(既定は1時間) | デバイスがその時間オフのとき、書き込みゲートを通してスイッチのポートの電源を一度入れ直し、復帰を待ち、復帰しなければアラームを上げます。ドライバーは同じポートの2回目の再投入を15分以内は拒否し、ネットワークを担うポートは再投入しません。 |
| `shift_schedule_counter_reset` | スケジュールヘルパー、カウンター(PLC またはヘルパー) | スケジュールがオンになったとき、カウンターをリセットして記録します。 |

これらについての率直な補足です。

- **`tank_high_level_stop_pump` は便利機能であり、インターロックではありません。** 人や工場を守るトリップは、ネットワーク上で動くものではなく、必要な場所に配線された PLC に置くものです。これは、誰かがレベルを見張らなくて済むようにするものです。高レベルスイッチの代わりにはなりません。
- 信頼できない測定値では動作しません。品質の悪いレベルでは何も停止しません。でたらめな数値に基づく停止も、やはり停止だからです。
- **`shift_schedule_counter_reset` はスケジュールがオンになったときに起動します。** また、接している2つのスケジュールブロックは、ひと続きのオンの区間になります。そのため、各シフトに専用のブロックを与え、間にスケジュールがオフの時間を、たとえ1分でも置いてください(06:00から13:59、14:00から21:59)。そうしないと、続いた区間の最初のシフトだけがカウンターをリセットします。
- **`alarm_to_notify`** はチャットルームやチケットシステム向けです。送信頻度の制限、再試行、確認リンクつきで電話を呼び出すには、HotLoop 自身が送る通知([アラーム通知](/ja/iot/notifications/))を使ってください。

## 誰が何をできるか

| <span class="sr-only">詳細</span> | 閲覧者 | オペレーター | 管理者 |
|---|---|---|---|
| ブループリントを見る(`blueprints.read`) | はい | はい | はい |
| ブループリントからルールを作る、アップグレードする(`blueprints.apply`) | いいえ | はい | はい |
| ブループリントを書く、編集する、コピーする、削除する(`blueprints.write`) | いいえ | いいえ | はい |

オペレーターがルールを作れる理由は次のとおりです。ブループリントは、エンジニアがルールの動作を決めた場所であり、どのポンプを監視するかを選ぶのは、オペレーターが一日中行っている判断そのものです。危険な部分、つまりルールが何を制御するかは、ブループリントを書いたとき、`blueprints.write` を持つ人が決めています。その後でルールを削除したり手で編集したりすることは、引き続き管理者の `automations.write` です。

どれかのルールの作成元になっているブループリントの削除は、そのルールの名前とともに拒否されます。先にそれらを削除してください。組み込みのブループリントは編集も削除もできません。

## エージェント

エージェントには `list_blueprints`、`preview_blueprint`、`instantiate_blueprint`(および `upgrade_blueprint_automation`、`create_blueprint`、`update_blueprint`、`delete_blueprint`)が与えられます。適切なブループリントを見つけ、入力を割り出し、ルールが何をするかを示し、画面が使うのと同じ経路で、同じ入力検査を経てルールを作り、ログブックにはエージェントの名前が残ります。ルールは、トリガーが発火するたびに設備へコマンドを出し続ける常設の指示なので、プレビューが先に来ます。ルールがその後に行う書き込みはすべて、書き込みゲートに出会います。[MCP](/ja/iot/mcp/#blueprints) を参照してください。

## すべての保存先

- 工場が書いた**ブループリント**は `blueprints` テーブルにあります。組み込みのものはバイナリにあり、保存されることはありません。
- **ブループリントから作ったルール**はほかと同じ `automations` の1行で、作成元を示す `blueprint_id`、`blueprint_version`、`blueprint_inputs` を持ちます。`GET /api/automations` はこれらを `blueprintId`、`blueprintVersion`、`blueprintInputs` として返します。
- **すべての変更**は、実行した人とともにシステムログとログブックに記録されます。*ブループリントを作成しました*、*ブループリントを保存しました、バージョン2になりました*、*ブループリント motor_running_too_long バージョン1からオートメーションを作成しました*、*オートメーションがブループリント pump_watch のバージョン1から2にアップグレードされました*、*ブループリントを削除しました*。
- **バックアップ**には、ブループリントと各ルールの固定バージョンの両方が含まれるため、復元された工場は以前と全く同じアップグレードを提供します。ブループリントが存在する前のバックアップは、すべてのルールを手書きのものとして復元します。
- ブループリントがなくなったルール(たとえば、後のリリースで外された組み込みのもの)は、今のままそのまま動き続けます。アップグレード先がないだけです。
