HotLoopは4.12.0から、ヒストリアンの論理スナップショット（テーブルデータのみ）を取り、復元します。デフォルトでオンで、毎日実行され（`HOTLOOP_BACKUP_ENABLED`、`HOTLOOP_BACKUP_INTERVAL` 24h）、バイナリでもHelmチャートでも同じです。バックアップは`HOTLOOP_BACKUP_DIR`の下に保存され、既定ではHotLoopのデータディレクトリ内の`backups`です（`HOTLOOP_DATA_DIR`、なければ書き込める`/data`、それもなければ`~/.local/share/hotloop`）。バックアップ用のボリュームを設定していないデプロイで、このプロセスがコンテナの一時的なファイルシステムに黙って書き込むことがあってはならないからです。

## これは何か

バックアップはディレクトリです。テーブルごとに1つのファイルと、小さな`manifest.json`で構成されます(HotLoopのバージョン、データベースに適用済みのスキーママイグレーション、タイムスタンプ、各テーブルの行数と列およびその型)。

## これは何ではないか

- **`pg_dump`/`pg_restore`ではありません。** Gatewayのランタイムイメージ(`gcr.io/distroless/static-debian12:nonroot`)は意図的に静的バイナリだけで、シェルもパッケージマネージャーも、いかなる外部バイナリもありません。ここでの処理はすべて、アプリがすでに保持している同じデータベース接続を通して行われます。
- **スキーマのバックアップではありません。** スキーマは起動のたびに自動的に再構築されます(`HOTLOOP_DB_MIGRATE`、既定でオン)。バックアップが取得するのはテーブルの*データ*だけで、復元は常に、そのマイグレーションによってスキーマが先に再構築されていることを前提とします。
- **ポイントインタイムリカバリではありません。** ここにはWALアーカイブも継続的なレプリケーションもありません。バックアップは実行した瞬間のスナップショットであり、その後から次のバックアップまでに書き込まれたものは対象外です。
- **機器の外への保存ではありません。** バックアップディレクトリ(`HOTLOOP_BACKUP_DIR`、このチャートが用意する`backup.persistence`のPVCを背後に置く想定)は、依然として同じクラスター内の1つのボリュームです。バックアップを本当に耐久性のある、レプリケートされた、またはオフラインのストレージに移すこと(ボリュームをオブジェクトストレージにコピーする、PVCのスナップショットを取るなど、運用者の実際のインフラが提供する方法)は運用者の仕事です。このプロジェクトが、耐久性のあるストレージをインフラの責任として扱い、アプリがマルチクラウドのバックアップアダプターを作り直さないのと同じ考え方です。

## バックアップファイルを守る

バックアップファイルは機密性が高いものです。`users.copy`ファイルにはパスワードとキオスクPINのbcryptハッシュが、`sessions.copy`と`write_audit.copy`にはセッション記録と書き込み監査証跡が入っています。ファイルはモード`0640`で(バックアップディレクトリは`0750`で)作成され、すでに存在するファイルは上書きされずエラーになりますが、これは最低限の防御であってボリューム保護の代わりにはなりません。バックアップ用ボリュームは保存時に暗号化されるストレージに置き、誰が何で読めるかを制限し、運用者が作る機器外のコピーにも同じ注意を払ってください。

`devices.copy`ファイルには、各デバイスのアドレスとプロトコル設定が保存されたとおりに入っており、ドライバーがログインに使う認証情報も含まれます。どの程度読めるかは、下記の鍵によります。4.15.1以降、APIは管理者を含むすべてのロールからすべてのデバイス認証情報を隠しますが、バックアップファイルはAPIの背後にはありません。[認証とユーザー](/ja/iot/authentication/#資格情報がまだ平文の場所)を参照してください。

## デバイスの認証情報と秘密鍵

バックアップは、ノートパソコンや共有フォルダー、チケットにコピーされて出回るファイルです。そのため、中の認証情報は、データベースにもバックアップにも存在しない鍵で暗号化されます。

- **`HOTLOOP_SECRET_KEY_FILE`が設定されている場合**(チャートが設定し、インストール時に鍵を生成してアップグレードやアンインストールをまたいで保持します)、鍵で保護されるすべての認証情報(OPC UA、CODESYS、MQTT、HTTP、MTConnect、UniFiデバイスの`password`、SNMPデバイスの`community`とパスフレーズ、APIキーなどのHTTPおよびMTConnectヘッダー値、検出が待ち受ける他の各MQTTブローカーのパスワード、各ヒストリアンターゲットのパスワード)はデータベース内で暗号化され、`devices.copy`、`mqtt_sources.copy`、`historian_targets.copy`には暗号文が入ります。マニフェストには、暗号化に使われた鍵が`secretKeyIds`として記載されます。鍵そのものではなくIDです。
- **設定していない場合**、これらの認証情報はデータベースと`devices.copy`に平文で入り、HotLoopは起動ログでその旨を知らせます。UniFiコンソール、パスワード付きのMQTTブローカー、パスワード付きのヒストリアンターゲットは、鍵がなければそもそも保存できません。鍵を設定して再起動すると、すでに保存されているものすべてがその起動時に暗号化されます。
- **URLやテキストに書かれた認証情報も封印されます**(`mqtt://user:pass@host`、`?token=`や`?api_key=`のクエリ値、パスワードに言及するHTTPの`body`)。そのようなものを含むデバイスのアドレスやオプションは丸ごと封印され、ドライバーは入力されたとおりの形で受け取ります。秘密を含まないURLは読める形のままです。鍵がなければこれらも他と同様に平文で、起動ログがその旨を知らせます。鍵があれば、すでに保存されているものすべてがその起動時に封印されます。パスワードは引き続きパスワードオプションに入れるのが望ましい方法です。

**復元には同じ鍵が必要です。** `--restore-from`は、行を読み込む前にマニフェストを確認します。復元するHotLoopが持っていない鍵で暗号化されたバックアップは拒否され、エラーに必要な鍵が示されます。その鍵ファイルをマウントして復元してください。鍵が完全に失われた場合は`--restore-keep-unreadable-credentials`を追加します。それ以外はすべて復元され、認証情報を開けないデバイスは必要な鍵を示したまま停止状態になり、誰かが認証情報を入力し直すまでそのままです。鍵が存在する前に取ったバックアップはどこにでも復元でき、復元が終わるとすぐにその認証情報が暗号化されます。

**鍵はバックアップがない場所に保管してください。** バックアップの隣に置いた鍵は何も守りません。チャートでは`<release>-secret-key`のSecretがそれにあたります。クラスターの他のsecretをバックアップするのと同じように、別にバックアップしてください。

## 何がどの順でバックアップされるか

すべてのユーザーデータテーブルを、外部キーの依存順(テーブルは、自身の外部キーが指すすべてのテーブルの後に来ます)でバックアップします。

```
devices → tags → tag_latest → alarm_definitions → alarm_state →
alarm_events → automations → automation_runs → blueprints → scripts → script_runs →
recipes → recipe_versions → recipe_applications → events → write_audit →
settings → users → sessions → user_certificates → energy_meters → energy_meter_state →
energy_buckets → fleet_members → report_definitions →
report_runs → entity_state_log → tag_history
```

(抜粋です。`backup.Tables`が全リストで、エンティティと設備のテーブルおよび`entity_last_state`も含まれます。)ログブックの`entity_state_log`は、どちらの履歴モードでも月ごとにパーティション分割されており、これより大きい唯一のテーブルである`tag_history`の直前に来ます。復元では月別パーティションがまだ1つもない状態で行を読み込むため、行はデフォルトパーティションに入ります。記録するGatewayが起動するとき、ログブックのメンテナンスが先月と今月のパーティションを、それに属する行の周りに作成し、保持期間を過ぎた古い行をデフォルトパーティションから削除するため、保持期間は復元されたすべての行に及びます。[ログブック](/ja/iot/logbook/)を参照してください。

スクリプトは履歴とともに戻ります。バックアップが途中で捉えた実行は`running`として戻り、Gatewayの最初の起動でクラッシュによって途切れた実行と同様に、`interrupted by restart`としてキャンセル扱いになります。実行を再開するものはありません。[スクリプト](/ja/iot/scripts/)を参照してください。

レシピは、すべてのバージョンとすべての適用記録とともに戻ります。バックアップが適用の途中で捉えたものは`applying`として戻り、Gatewayの最初の起動で書き込み監査内の呼び出しIDを指しながら`failed`として記録されます。適用を再開したり取り消したりするものはありません。[レシピ](/ja/iot/recipes/)を参照してください。

`schema_migrations`は意図的に除外されています。`store.Migrate`が、組み込みのマイグレーションからこのテーブルと、すべてのテーブルのDDLを再構築します。これは、除外された各テーブルがなぜ除外されているかを記録する`backup.ExcludedTables`の唯一の項目です。

このリストは手作業で管理されており、そのためマイグレーションがテーブルを追加しても、その後のすべてのバックアップから黙って漏れることがありえます。これを防ぐテストが2つあり、どちらも両方のストレージモードで実際のデータベースに対して実行されます。スケジュール済みレポートのテーブル(`report_definitions`、`report_runs`)は、これらの保護のもとで最初に追加されたテーブルです。レポートの出力ファイルはレポート用ボリュームにあり、データベースのバックアップには含まれません。`tag_history`は復元時に最後に読み込まれます。独自の外部キーを持たず、圧倒的に大きいテーブルなので、小さな設定テーブルは、失敗するなら、その長い処理が始まる前に早く失敗します。

**`settings`には意図的な例外が1つあります。** `history_mode`の行は、`Migrate`がゼロからスキーマを作る瞬間に、`store.ensureHistorySchema`自身が1回だけ書き込みます。*このサーバー*が`tag_history`をTimescaleDBのhypertableとして作ったか、ネイティブのパーティションテーブルとして作ったかを記録するもので、これは工場についてではなく、`Migrate`がいま実行されたデータベースについての事実です。この行は、`settings`のバックアップと復元の両方から除外されます。元の環境での過去の判断を、機能の異なる復元先(あるいは同じ種類のサーバーに対する新しい`Migrate`の実行)に復元すると、復元先が実際には持たない構造を説明するようにこの行が書き換わる可能性があるためです。復元先自身の`Migrate`は、`Restore`が`settings`を見る前にすでに正しい判断を下しており、その判断はそのまま残されます。

## オンデマンドのバックアップ

- `POST /api/backup`(`backup.run`、管理者のみ)は、今すぐバックアップを取得し、マニフェストを返します。
- `GET /api/backup`(`backup.read`、管理者のみ)は、バックアップ用ボリューム上のものを一覧表示します。名前、ディスク上のサイズ、各バックアップのマニフェスト(テーブル一覧、行数、HotLoopのバージョン、タイムスタンプ)です。

どちらもオペレーターロールに含まれていないため管理者のみで、`fleet.restart`/`fleet.config`/`notify.test`が、他の運用上の「今すぐ実行」や管理範囲の操作にすでに適用しているのと同じ絞り込みです。`users`と`sessions`を含むバックアップ一覧の行数は、オペレーターロールが見ることを想定した現場の読み取り(デバイス、タグ、アラーム)よりも管理上の診断に近いため、一部の読み取りのように`backup.read`をより低い権限に分けていません。これは技術的な制約ではなく判断であり、実際のオペレーターの作業にとって必要であれば見直せます。

## スケジュールと保持

`HOTLOOP_BACKUP_INTERVAL`(例: `24h`)は、一定の間隔でバックアップを実行します。これは意図的に単純な間隔であり、cron式のパーサーではありません。現実的な要望は「ときどきバックアップを取る」ことで、まだ誰も必要としていないもののために作らないというのがこのプロジェクトの方針だからです。未設定(または`0`)のままにするとスケジューラーは無効になります。オンデマンドのエンドポイントは、自分でトリガーしたい運用者や外部のcronのために引き続き動作します。

`HOTLOOP_BACKUP_RETAIN`(既定`7`)は、最新のN個のバックアップディレクトリを保持し、バックアップが成功するたびに古いものを削除します。`0`以下はすべてを保持します。小さなボリュームでは、運用者が意図して選ぶ設定です。

## バックアップの復元

**復元は意図的にAPIエンドポイントにしていません。** 本番のトラフィックを処理している可能性のあるデータベースに対して、「今すぐ復元」をネットワークからトリガーできるライブ操作として自動化するのは現実の危険です。クリックを1つ間違えるか、管理者セッションが1つ乗っ取られるだけで本番データが上書きされ、このプロジェクトは明示的に求められない限りそれを作りません。復元はバイナリ自体のフラグであり、復元先のデータベースがそれを受け取るべきだとすでに判断した運用者が、手動で1回だけ実行します。

```sh
hotloop --restore-from=/data/backups/20260918T220000Z
```

実行される内容は、次の順序です。

1. 通常の起動とまったく同じように、設定を読み込んでデータベースに接続します。`store.Open`が同じマイグレーションを実行し、復元がこれからデータを読み込むスキーマを構築します。
2. **何かを失わずには読み込めないバックアップを拒否します。** このデータベースより新しいスキーマで取られたもの、またはこのバージョンにもうないテーブルや列を持つものです。どちらも、1行も読み込む前に確認されます。下の「別のバージョンへの復元」を参照してください。
3. **復元先のいずれかのテーブルにすでにデータがある場合は拒否します。** `Migrate`自身がいま投入したもの(`settings`の`history_mode`行1つ)を超えるデータがある場合です。復元は、まだ何も入っていないデータベースに対してのみ実行されます。これが安全確認です。既存の行が1つでもあるテーブルがあれば、`COPY FROM STDIN`が実行される前に復元全体が停止します。
4. すべてのテーブルを、依存順に、単一のトランザクション内で、マニフェストが示す列に読み込みます。
5. `bigserial`主キーを持つすべてのテーブル(`tags`、`alarm_events`、`automation_runs`、`events`、`write_audit`、`sessions`)のシーケンスを、復元された最大のidの1つ先にリセットします。`COPY FROM STDIN`はシーケンスに触れずに明示的なid値を読み込むため、この手順を省くと、次の通常のINSERTが復元された行と衝突します。
6. まだ開いている同じトランザクション内で、すべてのテーブルの行数を数え直し、マニフェストの行数と比較します。
7. すべての数が一致した場合にのみコミットします。不一致、またはそれ以前の手順でのエラーがあれば、トランザクション全体をロールバックし、復元先のデータベースを見つけたときとまったく同じ空の状態のままにします。一部だけ読み込まれた状態にはなりません。
8. 終了します。プロセスの他の部分は何も起動しません。ポーリングスケジューラーも、アラームエンジンも、APIサーバーもありません。復元にはどれも不要であり、復元の途中のデータベースに対してランタイムを起動すること自体が危険だからです。

### PostgreSQL 17への移行

このバックアップは、稼働中のアプリが稼働中のデータベースへの接続を通して作るため、PostgreSQL 16から17への移行用のバックアップにはなりえません。その移行はデータベースが起動する前に行われます。アップグレード自体の安全策は、PostgreSQL 16のディレクトリに一切書き込まず、`pgdata.pg16`としてそのまま保持することです(k3sとHelmのページ、「PostgreSQL 17」)。それでも、アップグレードの前に旧リリースでこのバックアップを取ってください。機器の外にあるコピーだからです。これを新しいデータベースに復元するのは、下の通常の復元です。エンジンではなく行を運ぶので、どのメジャーバージョンが書いたかは問われません。

### 別のバージョンへの復元

復元に使うリリースが、バックアップを取ったリリースであることはまれです。バックアップは数か月前に、そのとき動いていたもので取られており、再構築する機器は現在のものを動かしています。そこで、何が何に復元できるかを示します。

**古いバックアップを新しいHotLoopへ: できます。** これが重要なケースで、`0001_core`から現在までの、これまでのすべてのスキーマレベルから、TimescaleDBと通常のPostgreSQLの両方で、その後にアプリを起動してテストされています。

- すべてのマニフェストは、各テーブルの列を、名前と型とともに記録しています。復元は、各ファイルをまさにそれらの列に、名前で読み込みます。バックアップ以降に追加された列は、既定値を取ります。`write_audit`の`entity_id`、`service`、`call_id`は、エンティティサービスより前のすべての監査行では空で戻ります。それらの行は単純なタグの書き込みだったからです。
- バックアップ以降に追加されたテーブルは空のままで、アプリが起動時に埋められるものを埋めます。エンティティレジストリの最初の同期で、復元されたすべてのタグに読み取りエンティティが、アームされたすべてのタグに制御エンティティが、すべてのアラーム定義にアラームエンティティが、レジストリが付けたはずの名前で与えられます。設備ツリーより前のバックアップのデバイスは、復元の際にサイト、エリア、ラインのテキストに基づいてツリー上に配置されます。アップグレードが配置したのと同じ方法です。バックアップにそもそもなかったものは戻りません。ラベル、複合エンティティ、バックアップ取得後に運用者がカスタマイズしたエンティティ名です。

**新しいバックアップを古いHotLoopへ: できません。拒否されます。** マニフェストには、バックアップ元のデータベースに適用されていたすべてのマイグレーションが記録されています。このデータベースが一度も実行していないものがあれば、復元は1行も読み込む前に停止し、その旨を伝えます。

```
refusing to restore: this backup was taken by HotLoop <its version> with the
database schema at <its newest migration>, which is newer than this database's
schema at <this database's newest migration> (HotLoop <this version>). ...
Restore it with HotLoop <its version> or a later release
```

「新しい」とは、バージョン文字列ではなくマイグレーションのことです。バージョン文字列はどのバイナリがバックアップを取ったかを示すだけで、開発ビルド、リリース候補、ホットフィックスのブランチがあるため、その比較は推測になります。マイグレーションは、スキーマが実際にどうだったかを示し、集合として比較されるため、順序のどこにあっても、欠けているマイグレーションは検出されます。メッセージにバージョンが含まれるのは、バージョンこそがあなたが行動できる情報、つまりどのリリースで復元すべきかだからです。

**このバージョンにもうない列を持つバックアップ: 名前を示して拒否されます。** マイグレーションが列を削除、名前変更、または型変更する日以降、それより前のバックアップには、新しいテーブルが受け入れる場所のないデータがあります。復元は推測しません。何かを読み込む前に、すべてのテーブルにわたって、そのような列をすべて名前で示します。

- 稼働中のテーブルにない列は、`backup.columnRenames`が新しい名前に対応付けていない限り拒否されます。列の名前を変更するマイグレーションは、その項目と、それより前のバックアップを復元するテストを、同じ変更の中で追加します。現時点では名前変更がないため、マップは空です。
- 型が変わった列は拒否されます。バイナリCOPYは型を運ばないため、バイト列が新しい型として読まれるか、途中で拒否されることになります。
- 稼働中のテーブルが既定値なしの`NOT NULL`として追加した列は拒否されます。それを埋められるものがないからです。

3つとも、対処は同じです。バックアップを取ったリリースで復元し、そのデータベースをその場でアップグレードしてください。それが、そのマイグレーションがそのデータと出会うことを想定していた方法です。

名前による読み込みは、誰も気づかない変更にも対応します。列が削除されて再追加された、あるいはテーブルが再構築されて列の順序が変わった場合です。位置による読み込みでは、型が合うたびに、エラーなしにある列の値が別の列に入ってしまいます。名前による読み込みなら、それぞれが正しい場所に入ります。

**マニフェストがこれらを記録するようになる前に取られたバックアップ**(このリリース以前に取られたすべてのバックアップ)には、列のリストもスキーマもありません。それでも復元できます。

- 列のリストがない場合、復元は位置に切り替わります。テーブルより列の少ないファイルは、テーブルの先頭の列に入り、残りは既定値になります。これは現在までのすべてのスキーマで正しいです。今日までのすべてのマイグレーションは列を追加しただけで、`ALTER TABLE ADD COLUMN`は常に末尾に追加するからです。テーブルより列の多いファイルは、PostgreSQL自身が拒否します。
- スキーマがない場合、復元はバックアップができる限り新しいものだと仮定します。マニフェストが記録を始めた時点で最新のマイグレーションだった`0007_service_audit.sql`です。この仮定は、成功したはずの復元を拒否することしかありえず、成功しないはずの復元を通してしまうことは決してありません。実際には何も拒否しません。このチェックを持つHotLoopは、そのマイグレーションまでのすべてをすでに実行しているからです。

このリリースが最初に取るバックアップからはすべてが記録されるため、この代替動作が意味を持つのは、すでにバックアップ用ボリュームにあるバックアップだけです。

### 復元の手順、ステップごと

1. 復元先の`hotloop`バイナリが読めるマシンまたはボリュームに、バックアップディレクトリを持ってきます。運用者自身が作った、バックアップ用ボリュームの機器外コピーが再び登場するのは、ここです。
2. `HOTLOOP_DB_*`を**復元先**のデータベースに向けます。到達可能で、バックアップ対象のどのテーブルにもまだデータがない必要があります(新品の空のデータベースが通常のケースで、スキーマはステップ3で構築されます)。
3. `hotloop --restore-from=<path to the backup directory>`を実行します。
4. 最後のログ行を読みます。テーブル数と行数を伴う`restore complete`、または何がなぜ拒否されたかを正確に説明するエラーです。
5. 同じデータベースに対して`hotloop`を通常どおり起動します。

## データベース間の移行

バックアップは、どのデータベースが取ったものでも同じものです。PostgreSQLのバイナリCOPYファイルと、各列のPostgres型を示すマニフェストだからです。そのため、工場を1つのデータベースから別のデータベースに移すことは、古い方でバックアップを取り、新しい方に復元することに尽きます。それ以外は何もありません。

- **SQLiteからPostgresまたはTimescaleDBへ。** ファイルでは足りなくなったPiの場合です。バックアップを取り、`HOTLOOP_DB_*`を新しいサーバーに向け(`HOTLOOP_DB_TYPE=postgres`)、復元します。TimescaleDBサーバーでは、履歴はhypertableに入ります。
- **PostgresまたはTimescaleDBからSQLiteへ。** 小さな機器に規模を落とす工場の場合です。逆方向も同じで、`HOTLOOP_DB_TYPE=sqlite`を使います。
- **通常のPostgresからTimescaleDBへ、そしてその逆。** 履歴モードは固定されるため、GatewayをIoT機器の通常のPostgresに向けるとパーティションが維持されます。hypertableにしたい場合は、新しいTimescaleDBに復元します。逆方向ではパーティションになります。

受け入れ時に確認されるのは、あらゆる復元で確認されるものと同じです。SQLiteの列をそのPostgres型として読み、すべての列を名前と型で復元先と照合するので、一方のバックアップは他方に復元されるか、どこでも拒否されるのと同じ理由で拒否されます。`history_mode`はコピーされません。復元先は自身のマイグレーションが決めたものを保持します。シーケンスは両方で正しくなります。Postgresでは`fixSequences`が移動し、SQLiteのAUTOINCREMENTは、復元されたどのidも超えて自動的に進みます。

## 設定

| 変数 | 既定値 | <span class="sr-only">詳細</span> |
|---|---|---|
| `HOTLOOP_BACKUP_ENABLED` | `false` | これを設定するまで、APIルートを含め、この機能はオフです |
| `HOTLOOP_BACKUP_DIR` | `/data/backups` | バックアップの書き込み先。PVC(チャートの`backup.persistence`)にすることを想定しています |
| `HOTLOOP_BACKUP_RETAIN` | `7` | 最新のN個のバックアップを保持します。`0`以下ではすべて保持します |
| `HOTLOOP_BACKUP_INTERVAL` | 未設定 | 例: `24h`。未設定の場合はオンデマンドのみです |

`--restore-from=<dir>`は、環境変数ではなく`hotloop`バイナリのコマンドラインフラグです。上の「バックアップの復元」を参照してください。

## 検証されたことと、されていないこと

HotLoopは、実機と実サーバーを相手に、そして2026-11-17にはベアメタル上で実行されています。
