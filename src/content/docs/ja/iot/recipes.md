title: "製品レシピの適用"
description: "製品グレードの設定値を一度に適用します。全体を先に検査し、全体を拒否し、順に書き込み、デバイスから読み戻して確認します。"
---

レシピは、工場へまとめて送り出される値の集まりです。グレード A のゾーン温度、ライン速度、ダイギャップ。500 ml ボトルへの切り替え。夜間のセットバック。どの工場にもこうしたものがあり、どの工場にも数字が書かれたラミネート加工の紙がどこかにあって、オペレーターが1つずつ入力し、どの工場にもそのうちの1つを入力ミスした夜の話があります。

だから数字はその代わりにここに置き、一度に送り出します。先に全体を検査し、順番に送り、その後デバイスから読み戻して確認し、1つ1つがすべて記録に残ります。すべてのレシピはエンティティ `scene.<id>` でもあります。人にけがをさせうる設備のために作られており、このページの大半が、何かがうまくいかなかったときに何が起きるかについてなのはそのためです。

## 1つの構成

```json
{
  "id": "grade_a",
  "name": "Grade A",
  "description": "The 2pm run. Die at 210, line at whatever the order says.",
  "equipment_id": 7,
  "apply_permission": "recipes.apply",
  "params": [
    {"name": "speed", "label": "Line speed", "type": "number", "min": 0, "max": 400, "step": 10, "unit": "rpm", "required": true}
  ],
  "precondition": "states['input_boolean.line_ready'] == 'on'",
  "targets": [
    {"entity_id": "loop.line_02_die_tic", "service": "set_mode", "data": {"mode": "auto"}},
    {"entity_id": "loop.line_02_die_tic", "service": "set_setpoint", "data": {"value": 210}},
    {"entity_id": "number.line_02_speed", "service": "set_value", "data_expressions": {"value": "vars.speed"}},
    {"entity_id": "switch.line_02_heater", "service": "turn_on"},
    {"entity_id": "input_select.product", "service": "select_option", "data": {"option": "Grade A"}}
  ],
  "verify_sec": 10
}
```

- **`id`** は小文字、数字、アンダースコアで、先頭は文字です。エンティティのオブジェクト id である `scene.grade_a` で、決して変わりません。
- **`equipment_id`** は、レシピが属する設備ツリーのノードで、探しやすくするためのものです。レシピ画面はこれでグループ化します。工場全体のレシピなら省略します。
- **`params`** は適用が受け取る値です。スクリプトと同じ型つきフィールド(`model.Field`:`min`、`max`、`step`、`unit` を持つ `number`、`text`、`boolean`、`select`、`entity`、`duration`、`alarm`、`tag`)です。対象は `data_expressions` の項目で、これを `vars.<name>` として読みます。
- **`precondition`** は、レシピが開始するために真でなければならない、オートメーションの言語の式です。省略すると、なしになります。
- **`targets`** は値で、**送り出す順番どおり**に並べます。それぞれ、エンティティ、それを設定するサービス、そのサービスのデータで、データは値(`data`)か、パラメーターから計算したもの(`data_expressions`)です。最大200件です。
- **`verify_sec`** は、書き込んだ各値がデバイスの読み取り値に現れるまで待つ時間です。1から600で、既定値は10です。

### 対象になれるもの

レシピは**値を設定**します。受け付けるサービスは、設備が値を保持した状態にするものです。

| ドメイン | サービス |
|---|---|
| `switch`、`input_boolean` | `turn_on`、`turn_off` |
| `number`、`input_number`、`input_counter` | `set_value` |
| `text`、`input_text` | `set_value` |
| `select`、`input_select` | `select_option` |
| `valve` | `set_position` |
| `motor` | `set_speed` |
| `loop` | `set_setpoint`、`set_mode` |

ボタンを押す、モーターを始動する、カウンターをリセットする、バルブを止めることは、保存時に拒否されます。これらは値ではなくアクションであり、[スクリプト](/ja/iot/scripts/)に属します。誰かが適用するたびにリセットボタンを押す「グレード A を適用」は、誰もレシピとは考えないものであり、それが運転中に起きた日が、それに気づく日です。トグルも拒否されます。スイッチを反転させるレシピは、2回に1回は逆のことをします。

対象のエンティティは保存時に存在していなければならず、その式はコンパイルできなければならず、同じエンティティを同じサービスで2回設定することはできません(1つの設定に2つの値があると、どちらが勝つかは誰も読まない順序に左右されます)。ループのモードと設定値は2つの別の設定で、両方を設定できます。手動のままのループには自動用の設定値は意味がないので、モードを先に設定してください。

## 適用する

レシピ画面、エンティティ画面のレシピのタイル、ルールまたはスクリプトの `apply_recipe` ステップ、MCP の `apply_recipe`、または `POST /api/services/scene/turn_on` から適用します。どれも、まったく同じことを行います。

### 1. 全体を検査し、全体を拒否する

値が1つでもどこかへ送られる前に、次を確認します。

- パラメーターをフィールドと照合して検査します。**値が合わせるために動かされることは決してありません。** 最大値が400のフィールドの450は拒否され、最大値に合わせて切り詰められることはありません。その最大値は
  400. `"250"` を数値に入れると、解釈されずに拒否されます。刻みが10のところの255は、丸められずに拒否されます。工場に送られる数値は、誰かが入力したものそのままか、何も送られないかのどちらかです。
- レシピが独自の権限を指定している場合(後述)はその権限、およびエージェントの場合は MCP の書き込みスイッチ。
- 事前条件を、現在の工場の状態に対して評価します。
- すべてのデータ式を評価します。1つでも失敗するとレシピは拒否されます。対象は、持つべき値なしに送られることはありません。
- このプロセスで、ほかの何もそのエンティティのいずれかに書き込んでいてはなりません(後述)。
- **すべての対象は、書き込みゲート自身の検査にかけられます。** その書き込みが出会うのと同じ検査です。書き込みがオン、タグが書き込み可能、値がタグの範囲内、エンティティが有効でその値を受け付けること(刻み、選択肢、出力のために手動になっているループ)、デバイスが接続されていること。`Services.Check` で、タグの場合は `runtime.Manager.CheckWrite` です。何も書き込まれず、何も監査されません。

**何か1つでも失敗すれば、レシピ全体が拒否され、何も書き込まれません。** 最初の10個の対象を書き込んでから拒否する、ということはありません。何もです。しかも、最初の1つだけでなく、すべての理由が返されます。1つずつ問題を告げられたオペレーターは、それを直して次の問題を告げられることになりますが、40個の対象があるレシピは一度で直せるべきです。各対象は、どれだったかを示します。`would_write`、ゲートの言葉つきの `refused`、または `not_sent` です。

### 2. 順に書き込み、呼び出し id は1つ、ロールバックはしない

その後、対象は順番に送り出され、それぞれ `Services.Call` を経て、つまり唯一の書き込みゲートである `runtime.Manager.Write` を通ります。裏口はありません。すべての書き込みには適用の**呼び出し id** が付くので、適用全体は監査記録で `GET /api/writes?call=<id>` となり、工場がこれまでに受け付けたほかのあらゆる書き込みと並んでいます。

検査は通っても、その直後に書き込みが失敗することはあります。PLC は書き込みに例外で応答します。誰かがケーブルを蹴ります。検査と書き込みの間に誰かがタグを解除します。**通らなかった最初の対象が適用を止めます。** それ以降の対象は送られず、`skipped` と表示されます。

**すでに書き込んだものは元に戻されません。** これは意図したもので、HotLoop のすべての書き込みが従う決まりです。元に戻すこと自体が書き込みだからです。誰も頼んでいないのに、すでに動いた設備に対して、以前の値はこうだったという私たちの推測に基づいて、工場が期待どおりに動いていないことが今まさに証明された瞬間に行われます。こうして、半分適用されたレシピが完全に混乱したラインになります。半分適用されたレシピをどうするかを決めるのはオペレーターの仕事で、そのための情報は過不足なく手元に届きます。

```text
PARTIAL v3: 2 of 5 written before one failed, nothing undone
  1. set_mode loop.line_02_die_tic: written, verified
  2. set_setpoint loop.line_02_die_tic: written, verified
  3. set_value number.line_02_speed: failed: the device answered the write with an exception
  4. turn_on switch.line_02_heater: skipped
  5. select_option input_select.product: skipped
```

対象は `written`、`failed`(送ったがデバイスが拒否した、または何も返さなかったため、反映されたかは不明)、`not_sent`(ゲートが直前に退けた)、`skipped` のいずれかです。適用は `applied`(すべての対象が書き込まれた)、`partial`(一部が書き込まれた)、`failed`(最初のものが書き込まれなかった)のいずれかです。

その後、レシピ画面に**残りの対象を適用**が表示されます。これは書き込まれなかった対象についての新しい適用で、同じバージョンとパラメーターを使い、先に全体をもう一度検査し、独自の呼び出し id で監査され、2つが一緒に見つかるよう `application:<id>` が親になります。自動で実行されることは決してありません。誰かが何が起きたかを見て、止めた原因を直し、ボタンを押します。

### 3. 読み戻し

書き込まれたことと反映されたことは同じではありません。PLC は書き込みを受け付けても、次のスキャンで自分のロジックがそれを上書きすることがあります。スケーリングされたレジスターは 12.34 を受け取っても 12.3 を保持することがあります。そのため、最後の書き込みの後で、書き込んだ各値を読み戻します。

- デバイス上の対象については、**その書き込みの後に取得した**読み取り値からのみ確認するので、デバイスが以前に答えた内容を覚えているキャッシュが何かを確認してしまうことはありません。
- エンティティの状態から、またはバルブ、モーター、ループの場合は、サービスが設定する属性(`current_position`、`speed`、`setpoint`、`mode`)から読みます。
- 数値は自分自身の百万分の一以内なら一致とみなし(浮動小数点のレジスターは 0.1 を 0.10000000149 として返しますが、これは同じ設定値です)、それ以外は完全一致です。

書き込んだ対象は、読み戻せれば **`verified`**、`verify_sec` 以内に読み戻せなければ、代わりに読み取った値とともに **`unconfirmed`** になります。

```text
  3. set_value number.line_02_speed: written, unconfirmed (not confirmed within 10s: read back 240, not 250)
```

未確認は、レシピ画面では緑ではなく必ず**琥珀色**で表示され、ログブックとシステムログでは警告です。失敗ではありません。値は送られ、デバイスは受け付けており、適用は引き続き `applied` です。反映されていないかもしれないので、見に行ってくださいという目印です。ヘルパーは自分の値を保持しているので、ヘルパーの対象はそのまま値から確認されます。

読み戻しが終わると応答が返るので、レシピの適用には最大で `verify_sec` かかります。

## 重複

同じ設定値への書き込みを交互に行う2つのレシピは、最後に着いたほうの値でそれを止めてしまいますが、それは誰のレシピでもありません。そのため、適用が書き込んで読み戻している間は、対象とするすべてのエンティティを確保し、そのいずれかを対象とする別の適用は、どのレシピが妨げているかを示して `409` で拒否されます。終わるのを待ってから適用してください。

この確保はプロセス内で行われます。Gateway からの適用と、その隣の `--mcp-stdio` プロセスからの適用は、互いを確保しません。書き込み側を1つにするか、エージェントのレシピとオペレーターのレシピを別々の設備に置いてください。

## バージョン

レシピの名前、説明、設備ノード、権限はレシピのものであり、その場で変わります。**何を書き込むかはバージョンであり、バージョンは決して変更されません。** 別の対象、別のパラメーター、別の事前条件、別の `verify_sec` を保存すると、次のバージョンが保存され、現行になります。バージョン3は保存された日のままの内容で永久に残り、すべての適用は実行したバージョンとパラメーターを記録します。先週の火曜日に工場へ何が送られたかには、いつでも答えられます。

- 名前だけ、またはメモだけを変更しても、バージョンは作られません。
- その後ほかの誰かが置き換えたバージョンに対する保存は、その人の変更を黙って捨てる代わりに `409` で拒否されます。エディターは編集していたバージョンを送ります。
- 古いバージョンも、意図して適用できます。適用ドロワーで選ぶか、`"version": 2` を指定します。適用にはバージョン2だったと記録されます。
- バージョンドロワーには、すべてのバージョンが、保存した人、そのメモ、直前のバージョンからの変更点とともに、対象ごとに表示されます。

レシピを削除すると、そのバージョンも削除されます。適用の記録は残ります。工場に送られた内容そのものであり、その履歴はレシピより長く残ります。

## キャプチャする

ラインがすでにグレード A で動いているときに、40個の対象があるレシピを手で書く人はいません。**キャプチャ**は、選んだエンティティを受け取り、選んだ順に、それぞれを今保持している値に戻すレシピの下書きを作ります。数値の値、スイッチのオンまたはオフ、セレクトの選択肢、バルブの位置、モーターの速度、ループのモード、続いてその設定値です。名前を付け、整え、注文ごとに変わる数値をパラメーターにして、保存します。

値が不明、または信頼できないエンティティは、**キャプチャされずに拒否されます**。品質が良好でない読み取り値、`unknown`、`unavailable`、無効化されたエンティティが該当します。不良な読み取り値から作ったレシピは、誰かが適用するたびに、その不良な読み取り値を工場に書き戻します。

## 誰が適用できるか

オペレーターはレシピを適用し(`recipes.apply`)、管理者は書き(`recipes.write`)、全員が読みます(`recipes.read`)。グレード A を読み込むことが、オペレーターがそこにいる理由です。グレード A とは何かを決めるのは、エンジニアの判断です。

レシピは、より狭い独自の権限を指定できます。`"apply_permission": "recipes.apply.night_setback"`。その場合、適用にはそれも必要で、オペレーターロールはそれを持っていません。そのレシピを適用してよい人に、各自の権限リストで与えてください。

```json
["recipes.read", "recipes.apply", "recipes.apply.night_setback"]
```

`recipes.apply.*` はすべてのレシピの権限を与え、管理者はすべてを持ちます。持たないユーザーは拒否され、**その拒否は記録に残ります**。レシピの履歴に、そのユーザーの名前つきの拒否された適用として、ほかの適用と同じように残ります。シーンエンティティ経由でも同じです。

エージェントはどのユーザーの権限も持たないため、**エージェントは独自の権限を指定したレシピを決して適用しません**。読むことと、適用されるかどうかを尋ねることはでき、答えはなぜ適用できないのかを示します。

## 事前条件

```json
"precondition": "states['input_boolean.line_ready'] == 'on' and float(states['sensor.line_02_die_temp']) < 250"
```

誰かが適用を押した時点の工場の状態に対して、パラメーターを `vars` として評価される、オートメーションの言語です。偽ならそのことを示してレシピを拒否します。正しい数値を間違った瞬間に適用することへの歯止めであり、インターロックではありません。インターロックは PLC にあり、ネットワークが動かなくても働き続けます。

## ルール、スクリプト、エージェントから

ルールまたはスクリプトは、`apply_recipe` ステップでレシピを適用します([オートメーション](/ja/iot/automations/)を参照)。

```json
{"type": "apply_recipe", "params": {"recipeId": "grade_a", "params": {"speed": 250}}}
```

ルール `automation:<id>` またはスクリプト `script:<id>` として適用し、すべての書き込みにその実行のソースが付き、適用の親はその実行です。すべての対象が書き込まれなければ、ステップは失敗します。未確認の値では失敗せず、トレースには `NOT confirmed by read-back` と表示されます。スクリプトのドライランもレシピを検査します。

MCP では、`list_recipes` がすべてのレシピを対象とパラメーターとともに表示し、`validate_recipe` が今適用されるかどうかを尋ね、`apply_recipe` が**必須**の理由とともに適用します。エージェントの書き込みにはソース `mcp` が付くため、ゲートはそのすべてに適用され、書き込みがオフ(`HOTLOOP_ALLOW_WRITES`)のときは、何かを検査する前に `apply_recipe` が拒否されます。[MCP](/ja/iot/mcp/#recipes) を参照してください。

## レシピのエンティティ

すべてのレシピは `scene` エンティティ `scene.<id>` です。状態は最後に適用された時刻(何かを書き込んだ適用)をタイムスタンプで表し、一度も適用されていなければ `unknown` です。属性は、最新の適用がどうなったかを示します。`last_result`、`last_version`、`last_applied_by`、`last_application`、そして適用されたものの値の一部が読み戻されなかったときのその件数を示す `unconfirmed` です。タイルには適用ボタンがあります。`scene.turn_on` が、データの `params` と `version` で適用します。ルールはその状態でトリガーでき、状態は何かを書き込んだ適用ごとに1回変わります。

レシピを削除すると、スクリプトを削除したときと同じように、そのエンティティは孤立します。

## 記録

すべての適用は、拒否されたものも含め、`recipe_applications` の1行です。レシピ、バージョン、パラメーター、誰が、どこから、なぜ、呼び出し id、各対象がどうなったか、読み戻したかが入ります。最初の書き込みの前に開かれ、読み戻しの後に完了するので、途中でプロセスが死んだものも、開始したことは残ります。Gateway の次の起動時に、書き込み監査にある呼び出し id を指して `failed`、`interrupted by restart` と記録されます。それを再開するものはありません。

すべての適用は、シーンの下のシステムログに1行、[ログブック](/ja/iot/logbook/)に種別 `recipe` のエントリが1件残り、行った書き込みと並びます。レシピの履歴は、最新の5000件の適用を保持します。

## プロセスが複数ある場合

レシピのすべての変更とすべての適用は、データベース上のすべてのプロセスに通知されるので、1つのポッドで保存したレシピはもう一方が適用するレシピであり、`--mcp-stdio` プロセスが行った適用は Gateway のシーンエンティティを更新します。

## バックアップ

レシピ、すべてのバージョン、すべての適用はバックアップに含まれ、そのままの状態で戻ります。バックアップが途中で捉えた適用は `applying` として戻り、クラッシュと同様に最初の起動時に `failed` と記録されます。[バックアップと復元](/ja/iot/backup/)を参照してください。

## API

すべてのルートは [HTTP API](/ja/iot/api/#レシピ) にあります。要点は次のとおりです。

| <span class="sr-only">詳細</span> | <span class="sr-only">詳細</span> |
|---|---|
| `GET /api/recipes` | すべてのレシピ、現在の内容、最後の適用 |
| `POST /api/recipes` | 1つをバージョン1として作成 |
| `POST /api/recipes/capture` | エンティティが今保持している値からの下書き |
| `PUT /api/recipes/{id}` | 保存。新しい内容は新しいバージョン |
| `GET /api/recipes/{id}/versions` | 保存されたとおりのすべてのバージョン |
| `POST /api/recipes/{id}/validate` | 今適用されるか。何も書き込まれません |
| `POST /api/recipes/{id}/apply` | 適用する:`200` 適用済み、`409` 拒否、`502` 一部または失敗 |
| `GET /api/recipes/{id}/applications` | 拒否されたものを含むすべての適用 |
