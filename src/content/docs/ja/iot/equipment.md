プラントにはもともと自分を整理する方法があり、所有しているどの SCADA、MES、ヒストリアンもそれを使っています。ISA-95 です。企業、サイト、エリア、ライン、セル、ユニット、設備。HotLoop もこれをそのまま使います。フロア用、エリア用、デバイス用とリストを分けるのではなく、ひとつのツリーです。そこに何がぶら下がるかは[エンティティ](/ja/iot/entities/)をご覧ください。

## レベル

| レベル | 通常の意味 |
|---|---|
| `enterprise` | 会社 |
| `site` | 1 か所のプラント |
| `area` | 部門または建屋: 包装、ユーティリティ、タンクヤード |
| `line` | 生産ライン |
| `cell` | ライン上の作業セル、またはバッチプラントのプロセスセル |
| `unit` | 生産ユニット: 反応器、チラー、加熱炉 |
| `equipment` | 機械または機械の一部: ポンプ、スキッド、モーター |

子は常に親より下のレベルになるので、サイトがラインの下に入ることはありません。レベルを飛ばすことはできます。エリアの直下のユニットも、エリアのないプラントでサイトの直下にあるラインも問題ありません。唯一の例外は `equipment` の中の `equipment` です。スキッドにはポンプがあり、ポンプにはモーターがあり、ISA-95 がレベルに名前をつけるのをやめるのは、プラントが入れ子をやめるよりずっと前だからです。ノードはどのレベルでもルートに置けます。多くのプラントは `site` から始めます。

レベルも名前も同じ兄弟 2 つは同じ場所なので、ツリーは 2 つ目を拒否します。

ノードが自分自身の祖先になることはありません。ノードを自分自身の下、またはその下にあるノードの下へ移動する操作は拒否されます。ループができるのは、`equipment` テーブルを手で編集したときだけです。そうなっても、ツリーをたどる処理はどれも止まらず、ループ内のノードを変更しようとすると、該当ノードの名前を挙げ、そのうちひとつの `parent_id` を NULL にするよう伝えるメッセージとともに拒否されます。

## サイト、エリア、ラインのテキストも引き続き使えます

すべてのデバイスには、ツリーができる前から自由入力の `site`、`area`、`line` フィールドがあります。これらはなくなりません。4.15 のデバイスエディターがこれを書き込み、`list_devices` と `describe_device` が読み取り、これを前提に作られたすべてのエージェントとスクリプトも同じです。そのため、テキストとツリーは変更と同じトランザクション内で、双方向に同期されます。

**テキストがあり `equipmentId` がないデバイスを保存すると**、テキストが指すサイト、エリア、ラインを探し、なければそれぞれ前のものの下に作成して、デバイスを最も深いノードに置きます。同じテキストの 2 台のデバイスは同じノードに入り、重複は一切できません。送ったテキストはそのまま保存されます。ツリーを知らないクライアントには、従来どおりの応答に無視できる `equipmentId` が加わって返ります。

**デバイスを移動させる `equipmentId` 付きで保存すると**、一緒に送られたテキストが何であっても、ノードのパスからテキストが取られます。デバイスを `Plant A / Packing / Line 2` の下のセルに置くと、テキストは `Plant A`、`Packing`、`Line 2` になります。

ツリーを知らないクライアントでも安全なように、次の 2 点が決まっています。

- デバイスの現在のノードが示す内容と同じテキストなら、デバイスはその場所に留まります。テキストには 3 つの列しかないため、ラインの下のセルや機械にあるデバイスはラインまでしか表せません。同じテキストで保存しても、ラインまで引き上げられることはありません。
- デバイスを読み取り、`equipmentId` も含めた全体をテキストだけ編集して送り返すクライアントには、テキストの編集が反映されます。送り返された `equipmentId` はデバイスがすでに持っていたものなので移動にはならず、テキストが優先されます。

サイトはルートだけでなくどこにあっても見つかるので、企業の下に `Plant A` を置いても、次に `Plant A` と指定するデバイスが 2 つ目を作ることはありません。

**ノードの名前変更や移動**を行うと、そのノードとその下にあるすべてのデバイスのテキストが、同じトランザクション内で書き換えられます。どれかが失敗すれば、何も起きなかったことになります。ツリーとデバイスのテキストが食い違う状態は、両方を同期させる目的がまさに防ごうとしたものだからです。応答とシステムログには、テキストが変わったすべてのデバイスが一覧されます。

### アップグレード

マイグレーション `0006_hierarchy.sql` は、既存のすべてのデバイスがすでに持っているテキストからツリーを作ります。サイト名ごとに 1 つのサイト、サイトの下のエリア名ごとに 1 つのエリア、エリアの下のラインごとに 1 つのラインを作り、各デバイスはテキストが指す最も深いノードに置かれます。エリアがありサイトがないデバイスにはルートのエリアが、ラインがありエリアがないデバイスにはサイト直下のラインが作られます。空白だけのテキストは何も指しません。テキストは空白や大文字小文字も含め、保存されているとおりに使われます。ツリーの名前が後でテキストを書き換える元になるため、アップグレード中にトリミングすると、余分な空白を持っていたすべてのデバイスが黙って名前を変えられることになるからです。アップグレードでデバイスのテキストが変わることはありません。

Go 側も同じルールでデバイスを配置し、テストが両者を一致させています。アップグレードが配置したすべてのデバイスは、何も触らずに再保存しても同じ場所に残り、ツリーを 1 つも増やしません。

## ノードの削除

**下に何かあるノードは拒否されます。**子ノード、またはその上に置かれたデバイスが対象です。先にそれらを移動してください。拒否メッセージには、何が邪魔をしているかが示されます。

別案は、子を削除されたノードの親に付け替えることでした。しかしそれでは、誰も触っていないノードの下で、その下のすべてのデバイスが移動してテキストが書き換わり、エリアを挟まずにサイトの直下にラインが来る、誰も描いていないツリーができることがあります。代わりにデバイスの配置を外すと、テキストが存在しない場所を指したままになり、そのうちどれかを次に保存したときにノードが黙って再作成されてしまいます。どちらも予想外の結果です。何を移動すべきかを伝える拒否なら、予想外にはなりません。

削除されたノードに置かれていたエンティティは配置を失い、再びデバイスに従います。

## ツリー上のエンティティ

すべてのエンティティの応答に、新しく 3 つのフィールドが加わりました。

| フィールド | 内容 |
|---|---|
| `equipment_id` | エンティティ自身が置かれている場所。デバイスの行き先にそのまま従う場合は null |
| `area_id` | エンティティ自身のノード以上で最も近い `area`。自身のノードがなければデバイスのノード。エリア別にまとめる処理はすべてこのフィールドを読みます。上にエリアがなければ null |
| `labels` | エンティティの label_id |

エンティティ自身の配置は、デバイスの配置より優先されます。これは PLC 全体がひとつのデバイスである場合に重要です。温度のタグは加熱炉に、チラーのタグはユーティリティに属します。エンティティは `PUT /api/entities/{entity_id}` で配置します。

```json
{ "equipment_id": 42, "labels": ["critical"] }
```

`"equipment_id": null` はデバイスに従う状態に戻します。`labels` は集合全体を置き換えます。どちらも他のレジストリのフィールドと同じく `entities.write` が必要です。

## ラベル

ラベルは、日常的な意味でのタグです。`critical`、`line 1 utilities`、`calibrate quarterly` などです。デバイスとエンティティには、いくつでもラベルを付けられます。

ラベルには `label_id` と `name` があります。`label_id` は最初に名前から作られ(小文字、数字、アンダースコア。衝突した場合は `_2`、`_3`)、二度と変わりません。オートメーションや画面が参照するのがこれだからです。名前はいつでも変更できます。ラベルを作成するときに、`label_id` を自分で決めることもできます。

ラベルを削除すると、それを持つすべてのものから外れます。

デバイスのラベルは `POST /api/devices` ではなく `PUT /api/devices/{id}/labels` で設定します。現在デバイスを保存するクライアントはどれもラベルなしでデバイス全体を送るため、保存のたびにラベルが消えてしまうからです。

## API

設備とラベルのエンドポイントは、エンティティのエンドポイントと同じくフィールド名に snake_case を使います。ツリーはエンティティモデルのエリアレジストリであり、同じ利用者向けに作られているためです。デバイスに加わった新しいフィールドは、他のデバイス API と同じ camelCase の `equipmentId` です。

| エンドポイント | 権限 | 内容 |
|---|---|---|
| `GET /api/equipment` | `equipment.read` | すべてのノードと、ルートからの名前の `path`。フィルター: `?level=` |
| `GET /api/equipment/{id}` | `equipment.read` | `{"equipment", "children", "devices", "entities"}`: ノード、その直下のノード、その直上に置かれたもの |
| `POST /api/equipment` | `equipment.write` | `{"parent_id", "level", "name", "description"}` |
| `PUT /api/equipment/{id}` | `equipment.write` | `name`、`description`、`level`、`parent_id` のいずれか(ルートは null)。`{"equipment", "devices_rewritten"}` を返す |
| `DELETE /api/equipment/{id}` | `equipment.write` | 下に何かある間は 409 で拒否 |
| `GET /api/labels` | `equipment.read` | すべてのラベル |
| `GET /api/labels/{label_id}` | `equipment.read` | そのラベルを持つ `{"label", "devices", "entities"}` |
| `POST /api/labels` | `equipment.write` | `{"label_id"?, "name", "color", "icon", "description"}` |
| `PUT /api/labels/{label_id}` | `equipment.write` | 名前、色、アイコン、説明。label_id は変更不可 |
| `DELETE /api/labels/{label_id}` | `equipment.write` | すべてから外す |
| `PUT /api/devices/{id}/labels` | `equipment.write` | `{"labels": [...]}`、集合全体 |
| `POST /api/devices` | `devices.write` | 前述の任意項目 `equipmentId` が加わる |
| `GET /api/devices/{id}` | `devices.read` | `device` と `tags` に加えて `labels` が付く |

すべてのロールが `equipment.read` を持ちます。ものがどこにあるかは、デバイスのサイトとエリアがすでに閲覧者に伝えていた内容だからです。`equipment.write` を持つのは管理者だけです。ノードをひとつ名前変更または移動すると、その下のすべてのデバイスのサイト、エリア、ラインが書き換わり、それは設定にあたるからです。

すべての変更はシステムログにカテゴリ `config`、件名 `equipment:<id>` または `label:<label_id>` で記録されます。

## MCP

`list_devices` と `describe_device` はこれまでどおりテキストから応答し、出力は変わりません。テストが出力をツリー導入前のバージョンの応答とバイト単位で固定し、そのうえでデバイスの周りのツリーを並べ替え(サイトの上に企業、ラインの下にセル、ラベル)、エージェントから見えるものが何も動いていないことを確認します。名前変更などでツリーがテキストを実際に変えた場合は、誰かがデバイスに入力したときと同じように、エージェントには新しいテキストが見えます。エージェントがツリーを見るのは `list_entities` です。ノードとその下のすべてで絞り込み、各エンティティの配置を返します。[MCP](/ja/iot/mcp/#エンティティ)をご覧ください。

## バックアップと復元

`equipment`、`labels`、`entity_labels`、`device_labels` はバックアップに含まれ、新しい `equipment_id` 列も同様です。`equipment` は自分自身を参照(`parent_id`)しますが、復元ではこれを順序づけできません。ノードを移動した後は、親が子より後に保存されることが十分ありうるからです。この制約は `DEFERRABLE INITIALLY DEFERRED` なので、復元がコミットされるとき、すべての行が入った後に検査されます。ツリーを複数の文で書き換える他のあらゆる処理も同じです。バックアップのガードテストは、この制約が遅延されている場合にのみ、テーブルが自分自身を参照することを許し、往復テストは意図的に子を親より先に保存します。

このバージョンより前に取得したバックアップも、引き続き復元できます。その `devices` と `entities` のファイルは列が 1 つ少なく、復元はそれらをテーブルの先頭の列に読み込み(新しい列は常に末尾に追加されます)、新しい列には既定値が入ります。その後、同じトランザクション内で、アップグレードが行うのと同じ方法で、復元されたすべてのデバイスをテキストに基づいてツリーに配置します。

## プラント画面

横にツリーがあり、選択したノードのカードが表示されます。そのパス、その上のデバイス、その上に置かれたエンティティ、その下にあるものです。管理者は、ルートまたは選択したノードの下にノードを追加し、名前を変更し、レベルを変更し、移動し、削除し、デバイスを置いたり外したりし、デバイスのラベルを設定できます。レベルの一覧には、親に対しても、すでに下にある子に対しても、ルールが許すレベルだけが表示され、移動では、そのレベルのノードが入れる親だけが表示されます。ノード自身やその下のものは決して表示されません。サーバーがすべてを再度検査し、拒否(下にまだ何かある状態での削除など)はサーバーが書いたとおりに表示されます。デバイスの移動は、デバイスエディターが行うのと同じ保存で、`equipmentId` が付くため、前述のとおりテキストがツリーに従います。

ラベルは画面の下部で管理します。名前、色、説明があり、`label_id` は一度選ぶと固定されます。エンティティは、エンティティ画面のドロワーから配置とラベルを設定します。

それ以外のユーザーには、押すものが何もない同じ画面が表示されます。
