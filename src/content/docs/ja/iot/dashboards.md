ダッシュボードは、誰かが作ったカードのページです。ゲージ、トレンド、エンティティの一覧、ポンプを始動するボタン、各ゾーンの位置に温度を置いたフロアプランなどを載せられます。プラントに必要なだけ作り、必要とするロールか、そのダッシュボードが置かれる画面ひとつに割り当ててください。従来のBoardは、そのうちのひとつにすぎません。

HotLoop IoT、Edge、Gatewayにあります。Edge RelayにはUIがないので、ダッシュボードもありません。Edge HMIはこのページだけで作られており、残りがいまの形になっている理由もそこにあります。

## この作りにした理由

**カードは何も命令しません。** ボタンのページを設計するとき、最初に問うのは、そのページがプラントを動かす第二の手段になっていないかです。なりません。カードはタグ、エンティティ、スクリプト、レシピのどれかを指すだけで、それをどう扱うかは、ブラウザが他のすべての画面と同じように行います。書き込みボタンは `POST /api/write` を送ります。エンティティのコントロールは `POST /api/services` を呼びます。スクリプトのボタンはスクリプト画面の実行確認を開き、レシピのカードはレシピ画面の適用ドロワーを開きます。どれも固有の権限があり、書き込みゲートを通るので、ダッシュボードが抜け道になることもありません。`dashboards.write` が守っているのは、ボタンを何にするかを決める人が誰かという点で、これはスクリプトを書くのと同じ理由でエンジニアの判断であり、管理者だけが行えます。

その結果、管理者が保存したダッシュボードは、オペレーターが何かを押すまで何もしません。押したときに起きることは、他の画面で押すのとまったく同じで、監査記録の行まで同じです。

**レイアウトは座標ではなく流れです。** カードは読む順に並びます。各カードが宣言するのは、12列のうち何列の幅か、何行の高さかだけで、どこに置かれるかは知りません。パネルPCでは12列、隣に別のウィンドウを置いたノートPCでは6列、タブレットでは2列、スマートフォンでは1列です。ピクセル位置のレイアウトは、描いた画面でしか正しくありません。Edge HMIは、機械についている画面がどれであっても正しくなければなりません。

その結果、スマートフォン版を作る人は誰もいません。そもそも存在しません。

**保存はバージョンを明示します。** 交代の時間帯に、ひとつのダッシュボードを二人が同時に編集することは実際に起こります。保存は開いた時点の `version` を持っていき、古いバージョンは、誰が先に保存したかを伝える `409` で拒否されます。これがなければ、二番目に保存する人が最初の人の午後の作業を、どちらも気づかないまま消してしまいます。

## モデル

```json
{
  "id": "line-2",
  "name": "Line 2",
  "description": "The extruder, for the floor.",
  "kind": "cards",
  "roles": ["operator", "admin"],
  "homeFor": ["operator"],
  "screens": ["line-2-panel"],
  "position": 1,
  "version": 3,
  "cards": [
    {"id": "temp", "type": "gauge", "title": "Zone 1", "w": 3, "h": 3,
     "config": {"tag": "press-01/Zone1_Temp"}},
    {"id": "go", "type": "button", "w": 3, "h": 1,
     "config": {"tag": "line-02/Speed", "value": 250, "label": "Run at 250", "confirm": true}}
  ]
}
```

- **`id`** は小文字の英字、数字、ハイフン、アンダースコアで、英字から始まります。アドレスに入り、変わることはありません。`wall` はウォールボードのものです。
- **`kind`** は `cards`、ウォールボードの場合は `wall` です。
- **`roles`** は、そのダッシュボードを利用できるロールです。空なら全ロールです。`dashboards.write` を持つ人は、設定に関係なくすべてのダッシュボードが見えます。誰も開けないものを直せなければならないからです。提供されていないロールが名前で要求すると `404` を受け取るので、どんなダッシュボードがあるかを、閲覧者が尋ねて知ることはできません。
- **`homeFor`** は、アドレスで何も指定せずに入ってきたロールが最初に開くダッシュボードです。ロールひとつにつき最大ひとつで、そのダッシュボードはホームにするロールに提供されている必要があります。
- **`screens`** は、そのダッシュボードの対象となる物理的な画面です。画面名はひとつのダッシュボードにだけ属します。
- **`position`** は切り替えバーの順序を決めます。新しいものは最後に入ります。
- **`cards`** は読む順で、ダッシュボードごとに最大60枚、全体で2 MBまでです。
- **`version`** は保存のたびにひとつ上がります。

カードは `id`（ダッシュボード内で一意で、ページが作ります）、`type`、任意の `title`、`w`（1から12）、`h`（1から8）、そしてタイプによって変わる `config` で構成されます。`w` と `h` を省くとタイプの既定値が使われます。config は厳密に検査されます。タイプにないキーはエラーで、保存される内容にはすべての既定値が入ります。存在しないタグ、エンティティ、スクリプト、レシピを指すカードは、ダッシュボードの保存時に拒否されます。書き込み可能になっていないタグへのボタンや、数値がタグの範囲外のボタンも拒否されます。ゲートはどの押下も拒否するはずなので、それを聞くべきは押す人ではなく作る人です。

## カード

| タイプ | 内容 | 設定 | 既定のサイズ |
|---|---|---|---|
| `status` | 稼働中のデバイス、報告中のタグ、アラーム、ヒストリアン、稼働時間: Boardの帯 | なし | 12 x 1 |
| `gauge` | タグ1つをBoardのダイヤルで表示。範囲とアラーム限界の印つき | `tag` | 3 x 3 |
| `value` | タグ1つを大きな数字で表示。アラーム状態で色が変わる | `tag`, `decimals` | 3 x 2 |
| `trend` | 最大6つのタグを15分から1週間の範囲で表示 | `tags`, `minutes`, `labels` | 6 x 3 |
| `entities` | 選んだエンティティを、それぞれのコントロールつきタイルで表示 | `entities` (最大30) | 6 x 3 |
| `alarms` | アラーム一覧。権限のある人には確認応答ボタンつき | `outstanding`, `limit`, `devices`, `equipment` | 6 x 3 |
| `button` | 確認のあと、タグ1つに値1つを書き込む | `tag`, `value`, `label`, `confirm` | 3 x 1 |
| `script` | スクリプト画面の確認を通してスクリプトを実行 | `script`, `label` | 3 x 1 |
| `recipe` | 最大8つのレシピから1つを選び、適用ドロワーを開く | `recipes` | 4 x 2 |
| `markdown` | テキスト: 見出し、リスト、太字、斜体、コード、http(s)リンク | `text` | 4 x 2 |
| `camera` | 更新されるスナップショット、またはモーションJPEGストリーム | `url`, `stream`, `refreshSec` | 6 x 4 |
| `map` | ライブのタグを配置したフロアプラン | `image`, `markers` | 6 x 5 |
| `setpoint` | タグ1つに入力する数値: 限界、単位、確認つきで、デバイスが返した値も表示 | `tag`, `label`, `min`, `max`, `step`, `unit`, `decimals`, `confirm` | 3 x 3 |
| `symbols` | 機械またはプロセスの絵：背景の上にピクセル単位で置いたシンボルを配管でつなぎ、タグから描画します | `image`、`width`、`height`、`symbols`、`pipes`、`view` | 8 x 5 |

わかりにくいものについて、知っておくとよい点です。

- **`button`** は `value` を、保存されたときの型のまま送ります。数値は数値、`true` は真偽値、文字列はテキストです。PLCでは `1` と `1.0` は別の書き込みで、ゲートはJSONの型で判断するので、カードが一方を他方に変えることはありません。`confirm` はオフにしない限りオンで、オンのときは「これは実際の設備に命令します」と、現在の値と、監査記録に残る理由を添えて尋ねます（理由を空にすると `dashboard <id> / <card>` が入ります）。オフにするのは、ボタンを押し続けることに意味があるパネル向けで、エンジニアの判断です。設定画面の「書き込み前に確認」がオンなら、それが優先されて再びオンになります。
- **`alarms`** は、場所を指定しない限りプラント全体のアラームを並べます。`devices` はデバイスidのリストです。`equipment` は `GET /api/equipment` の設備ノードidのリストで、サイト、エリア、ライン、セルのどの階層でもよく、ノードひとつは、その位置とその下に置かれたすべてのデバイスを表すので、エリアのページにそのエリアのアラームだけを出せます。両方を指定すると、どちらかに当てはまるアラームが並びます。省略するか空にすると、カードはプラント全体になり、この項目ができる前に保存されたカードはすべてそうでした。件数の上限は、フィルタの後に残ったものを数えます。`outstanding` は、正常に戻って確認済みのものを引き続き除外します。アラームのない場所に絞ったカードは「ここには」と表示して、静かなプラントと誤読されないようにし、設備がその後削除されたカードは、空のリストの代わりにそう表示します。設備はノードのidで保存されるので、ノードの名前を変えたり移動したりしてもカードは壊れません。デバイスやノードがなければ、保存時にダッシュボードは拒否されます。ビルダーではパス（`Plant 2 / Scrubbers / Kettle 3`）を入力すると、idが保持されます。このカードはツリーを読むので、ロールに `equipment.read` が必要です（オペレーターと閲覧者にはあります）。

  ```json
  {
    "id": "kettle-alarms", "type": "alarms", "title": "Scrubber alarms", "w": 6, "h": 3,
    "config": { "outstanding": true, "limit": 10, "equipment": [14], "devices": ["oven-1"] }
  }
  ```
- **`trend`** は、要求した範囲を現在時刻までで描きます。読み取りがたまたま記録された範囲だけではありません。`minutes: 480` は直近8時間の軸で、きりのよい時刻ごとに目盛りがつき、見ている人のタイムゾーンで表示されます。動いていないタグは、最後の正常な読み取り値での水平線です。止まったミルや閉じたバルブはそう見えるからです。ヒストリアンは値がデッドバンドを超えて動いたときだけ記録するので、範囲内の記録が1件の場合も、ない場合もあります。線の上に作り物はありません。範囲が始まったときにタグが持っていた値は、その直前の最後の正常な読み取り値で（`GET /api/history` が `carry=true` で知らせます）、線は範囲の開始から範囲内の最初の記録まで、その値です。最後の記録のあとは、タグから最後に応答があった時刻まで保持され、現在を越えることはありません。誰も最初の記録を持たない時点より前には線がなく、範囲の直前の最後の読み取りが不良だったタグには、引き継ぐ値がまったくありません。保持していた値がわからないからです。不良な読み取りが続いた区間は、従来どおり途切れた空白です。記録がひとつだけなら現在までの線、描く先がなければ点です。

  凡例は、各線をタグ自身の名前、つまり数値カードが表示するのと同じ名前から、前のデバイス名を除いたもので呼びます。異なるデバイスの同じ名前の2本の線は、区別できるように完全なidのままです。`labels` は、`tags` にあるタグから、代わりに表示するテキスト（1から80文字）へのオプションのオブジェクトで、描画されていないタグのラベルは拒否されます。ホバーのツールチップには、常にラベルの隣に完全なidがあります。

  ```json
  {
    "id": "mills", "type": "trend", "title": "Mill temperatures", "w": 6, "h": 3,
    "config": {
      "tags": ["plant-5-temperatures/Large Sand Mill Temperature", "plant-5-temperatures/Small Sand Mill Temperature"],
      "minutes": 480,
      "labels": { "plant-5-temperatures/Large Sand Mill Temperature": "Large mill" }
    }
  }
  ```
- **`camera`** は、サーバーではなくブラウザでアドレスを読み込みます。カードのconfigは、ダッシュボードを開くすべてのロールが読めるので、ログインやトークンを含むアドレスは、ダッシュボードの保存時に拒否されます。認証が不要なプラントネットワーク上のアドレスか、ログインを付け足してくれるプロキシを使ってください。静止画は `refreshSec` 秒ごとに、`_hl` クエリパラメータをつけて取得し直すので、ブラウザが最初の1枚を出し続けることはありません。
- **`map`** は、画像とマーカーです。画像は http(s) のアドレスか、カードにアップロードしたもの（png、jpeg、webp、gif、最大500 KB、カード内に保存）です。マーカーはタグで、画像の幅と高さに対するパーセントで置かれるので、どのサイズでも置いた場所に留まります。これはフロアプランで、地図ではありません。タイル地図にはインターネット上のタイルサーバーが必要で、プラントのパネルPCは通常そこに届きません。
- **`setpoint`** は、人が入力する数値のためのものです。温度、速度、レベルなどです。フィールドはタグの単位（またはカードの `unit`）と限界を知っています。`min` と `max` を一緒に指定するか、カードが指定しなければタグ自身の範囲です。カードはタグの範囲を狭めることしかできず、広げることはできません。カードが何を言おうと、書き込みゲートはタグの範囲外の値を拒否するからです。より広く提供するカードは、ダッシュボードの保存時に拒否され、テキストやスイッチを保持するタグのカードも同様です（それらには `button` を使ってください）。限界の外、`step` に合わない、または数値でない場合は、フィールドの下にそう表示され、**Set** はオフのままです。**Set** は、現在の値と監査記録用の理由を添えてまず確認します（カードが `confirm` をオフにして作られていて、設定がそれを上書きしていない場合を除く）。そのあと `POST /api/write` を通ります。マスター書き込みスイッチ、タグの書き込み可フラグ、ロールの権限、監査行は、他のすべての書き込みと同じです。カードは次に、デバイスの読み取り値にその値が現れるのを待ち、さらに2秒間見守って、デバイスが保持している値を伝えます。「デバイスから70 Cを読み戻しました: 送った値です」。PLCが書き込みを受け入れたあと自身の限界に戻した場合は「デバイスは70 Cを受け取り、そのあと60 Cに変えました」。読み取り値にいつまでも現れなかった場合は「デバイスは70 Cではなく60 Cを報告しています」。「いまデバイスにある値」の行は常にライブの読み取り値なので、PLCプログラムがあとから値を上書きする様子も見えます。デバイスに正常な読み取り値がない間（電源が切れている、または到達できないPLC）は、フィールドとSetがオフになり、書き込みは拒否されるしかないので、カードはデバイスが応答していないと伝えます。
- **`symbols`**は機械の絵です。`width`と`height`はページ自体のサイズ（ピクセル、省略すると800 x 450）、`image`は任意の背景（http(s)アドレス、または`map`と同じくカードにアップロードした画像）、`symbols`は左上の角からピクセル単位で置く要素のリストです：`{"id": "p1", "type": "pump", "x": 120, "y": 300, "tag": "plc/bPumpRun"}`。ページは拡縮される1枚の絵として描画されるので、どのカードサイズでも、スマートフォンでも、各シンボルは位置を保ちます。タイプは`pump`、`motor`、`fan`（タグがオンの間回る）、`valve`（開または閉）、`tank`（`min`と`max`の間、またはタグの範囲、または0から100で満たす）、`heater`と`lamp`（オンの間点灯）、`pipe`（任意のタグがオンの間、中のものが動く）、`readout`（`unit`と`decimals`つきの数値）、`label`（固定テキスト）です。`invert`はタグを逆に読み、ランプの`tone`（`ok`、`warn`、`bad`、`info`）は点灯する色です。運転ランプは緑、故障ランプは赤で、タグは点灯するかどうかだけを示します。どのシンボルも、タグを読むルールを2つまで持てます。`show`は、ルールが成り立つ間だけシンボルを表示します（`"show": {"tag": "plc/bDoorOpen", "op": "off"}`）。成り立たない間はシンボルは描画されず、ビルダーでは選べるように薄く表示されます。`colors`は最大4つのルールで、それぞれ`tone`（`ok`、`warn`、`bad`、`info`）を持ちます。最初に成り立つルールが、シンボル自身のタグが何を示していてもそのトーンで塗り、どれも成り立たなければ元のとおり描画されます。ルールは`tag`、`op`、そして必要な比較では`value`でできています。指定できる値は`on`（タグが0でない、デフォルト）、`off`、`eq`、`ne`、`gt`、`ge`、`lt`、`le`です。タグに正常な読み取り値がないルールは成り立たず、何も隠さないので、接続が切れてもシンボルが消えることはありません。ルールは、代わりにルールを組み合わせることもできます。`{"all": [...]}`はすべてが成り立つ間、`{"any": [...]}`は1つが成り立つ間成り立ち（PLCのANDとOR）、深さは最大3段、部品は最大8つで、自身のタグは持ちません。タグを失うと`all`は成り立たず、`any`はほかのものを通じて成り立ちます。ランプは、比較や組み合わせで点灯する場合、タグの代わりに`lit`ルールを持つこともでき（`"lit": {"tag": "plc/Mode", "op": "eq", "value": 3}`）、その場合タグは不要です。ルールのタグは画面が名前を挙げるタグなので、画面ファイルがそれらを一覧にし、ほかのものと一緒に移します。シンボルは色だけでなく言葉でも状態を伝え（キャプションとタイトル）、タグがアラーム中、またはアラームから復帰した状態なら赤または暖色で描かれ、タグに正常な読み取り値がなければ「no reading」と表示されて薄くなります。動きの軽減をシステムに求めている人には、動きは止まります。シンボルはHotLoopのためにHotLoopが描いたもので、借りたものはありません。タグのあるシンボルは、クリックするとそのタグを開きます。フロアプランのピンと同じです。何も命令しないので、それが必要なら、横に`setpoint`か`button`のカードを置いてください。ビルダーでは、シンボルをポインターでつかんで動かすか、矢印キーで動かすか（Shiftで10ピクセル）、ピクセル値を数字で入力できます。

  **プロセスシンボルと配管。**symbolsカードはP&IDでもあります。上のタイプに加えて、`controlvalve`、`checkvalve`、`compressor`、`heatexchanger`、`filter`、`vessel`、`flowmeter`、`instrument`（ISAバブル：`label`が文字で、タグの数値を表示）、`junction`、`source`、`sink`を置けます。シンボルには、中心を軸に90度ずつ回す`rot`（`90`、`180`、`270`）があり、テキストは回りません。ほとんどのシンボルには接続点があります。ポンプの`in`と`out`、タンクの`top`、`bottom`、`left-1`から`left-3`、`right-1`から`right-3`、バルブの`w`と`e`などです。配管はそのうちの2つをつなぎます。

  ```json
  "pipes": [
    { "id": "tank-out", "from": { "symbol": "tank-1", "port": "bottom" },
      "to": { "symbol": "p1", "port": "in" }, "medium": "water", "tag": "plc/Flow" }
  ]
  ```

  保存されるのは、つながれているものだけです。経路は、ページが配管を描画するたびに計算します。直角で、ページ上のすべてのシンボルを余裕をもって避け、曲がりをできるだけ少なくし、シンボルから出る配管は接続点が向いている方向に出ます。シンボルを動かすと、動いている間に配管の経路が引き直され、ビルダーでも保存したファイルでも同じです。Tは配管が3本つながった`junction`シンボルで（点`n`、`e`、`s`、`w`はすべて中心にあります）、ビルダーで配管を別の配管の上に置くと、その配管が分岐でつながれて分割されます。`medium`は`process`（デフォルト）、`water`、`wastewater`、`fuel`、`oil`、`air`、`steam`、`gas`、`chemical`、`coolant`、`hydraulic`、`vacuum`、`nitrogen`、`power`、`signal`のいずれかです。それぞれに色があり、signalとpowerには専用の線のパターンもあるので、配管が色だけで区別されることはありません。`tag`（`invert`と併用）は、媒体が配管の中を`from`から`to`へ動く時を示し、`flow`は同じことをルールで示します。シンボルの`show`と`colors`が使うのと同じルールです。どちらもない配管は、満たされたまま静止して描かれます。`label`は配管に沿って最大24文字です。配管が持てるのはタグ1つかルール1つで、両方は持てません。1ページには、シンボル最大120個、配管最大240本を置けます。

  **ツールバー。**すべてのsymbolsカードには、表示時にもビルダーでも、右上にツールバーがあります。拡大、縮小、ページに合わせる、ミニマップ、高性能ビューがあります。ズームはCtrlとホイール（ホイールだけならダッシュボードのスクロールのまま）、ページ上の`+`、`-`、`0`でもでき、ページをドラッグして移動します。拡大すると、ミニマップが現在位置を枠で示したページ全体を表示し、そこを押すかドラッグするとその位置に移動します。高性能ビューはISA-101のグレーのページです。機器と配管はグレーで、運転中や開の状態は緑ではなく濃い塗りで示し、配管の媒体は横に短いコード（水はW、蒸気はS、信号はSIG）で示し、色が付くのはアラーム中のものかルールで塗られたものだけです。`view`を`hp`にすると、ページはこのビューで開きます。見ている人はツールバーでどちらにも切り替えられ、それで保存されるものはありません。フローのアニメーションは、動きの軽減をシステムに求めていない場合だけ動きます。
- **`markdown`** はHTMLではなくDOMノードとして組み立てられるので、入力した内容がマークアップやスクリプトになることはありません。
- **`gauge`、`value`、`map`、`setpoint`** は、ダッシュボードを保存したあとでタグが削除されると、動かないダイヤルの代わりに「このゲートウェイにはもうありません」と表示します。

## ウォールボード

ウォールボードは、`wall` ダッシュボードで、kind は `wall` です。常に存在し、削除できず、カードはありません。ゲージはBoard画面にピン留めされたタグで、従来どおりボード自身の設定に保持されます。`GET` と `PUT /api/board`、`#board` のアドレス、ピンの選択、ドラッグでの配置はそのままです。

ダッシュボードになることで得られるのは、切り替えバー（すべてのダッシュボードで最初のピルで、Boardにもバーがあります）と割り当てです。一部のロールに提供でき、ロールのホームにでき、物理的な画面のものにできます。壁のテレビが `/?screen=wall-tv` を開くと、ヘッダーとタブのないBoardが表示されます。

## ロールと画面

**ロール別。** `roles` は誰にダッシュボードを提供するかを決め、`homeFor` はロールが最初に着く場所を決めます。ホームが `line-2` のオペレーターがHotLoopを開くと、ライン2が表示されます。アドレスにURLフラグメント（`#alarms`）があれば、ページはアドレスが指す場所で開きます。

**画面別。** 画面は物理的なディスプレイです。HotLoopを `/?screen=<name>` で開くと、`screens` にその名前を持つダッシュボードが、ヘッダーもタブもなく、大きめのタッチ領域で表示されます。パネルPCの前を通りかかる人に、ページから出る手段は必要ないからです。どのダッシュボードにもない名前は、別のものを表示する代わりに、そうだと伝えます。

**パネルが人をサインインさせるのであって、パネル自身がサインインするのではありません。** 誰もサインインしていないときは「PINまたはバッジ」の入力欄がひとつだけ表示されます。オペレーターがPINを入力するか、バッジをスキャンすると（キーボードウェッジ式のリーダーが入力欄に入力します）、パネルがダッシュボードを開きます。名前と **サインアウト** ボタンは隅にあります。それを表示するヘッダーがないからです。そのダッシュボードのボタンによるすべての書き込みは、その人として書き込みゲートを通り、監査記録とログブックには「panel-3」ではなく「olgaが line-02/Speed に250を書き込み」と残ります。15分間（設定です）誰も画面に触れないと、パネルはその人をサインアウトして入力欄に戻り、そのあとに送られた書き込みは拒否されます。管理者は **設定、ユーザー** で各人にコードを発行します。バッジとは何か、コードがどう保存されるか、何をしないかを含む全体は、[認証とユーザー](/ja/iot/authentication/#キオスクパネル-pin-またはバッジとアイドル時のサインアウト)にあります。

自分のコンピューターでは、これらはどれも当てはまりません。パスワードでサインインしているので、ボタンの書き込みはそのままゲートを通って自分として記録され、アイドルでのサインアウトもありません。PIN以前のパネルの運用方法だった、固定のオペレーターアカウントでサインインしたパネルも、いまも動き、そのアカウントとして書き込みます。共有のパネルには、そのようなログインを与えないでください。

Edge HMIとはこれです。`screens` を設定したダッシュボードを、そのアドレスを開く機械で使い、その前の人がPINかバッジでサインインします。

## 作成

`dashboards.write` を持つ人（管理者）には、ダッシュボードに **編集** が、バーに **新しいダッシュボード** が表示されます。編集中は次のようになります。

- カードは動作しないので、動かそうとしてボタンをつかんでも押されません。
- カードを別のカードの上にドラッグして置くか、カードのツールバーの矢印を使います。タッチスクリーンではドラッグが始まらないので、スマートフォンには矢印があります。
- 角をドラッグしてサイズを変えます。幅は12列のうちの1列に、高さは1行に吸着します。
- 歯車はカードを編集し、コピーのボタンは複製し、バツは削除します。
- **設定** は、名前、誰に提供するか、誰に最初に開くか、物理的な画面、切り替えバーでの位置です。

**保存** するまで何も保存されません。**破棄** は変更を捨てます。保存時の `409` は、誰かが先に保存したという意味で、ページがその人のものを読み込むかどうかを尋ねます。

**エクスポート**（編集の隣）は、画面のダッシュボードをファイルとして保存し、**インポート**（`dashboards.write` を持つ人向けに、新しいダッシュボードの隣のバーにあります）は、ファイルをこのインストールに読み込みます。画面はお客様のデータなので、誰も作り直さずにインストール間を移動できます。[画面ファイル](/ja/iot/screen-file/)を参照してください。

## レイアウト

| 幅 | 列 | `w` のカードが取る列 |
|---|---|---|
| 1100 px超 | 12 | `w` |
| 700 pxから1100 px | 6 | `w` の半分、切り上げ |
| 480 pxから700 px | 2 | 1列、`w` が4を超えるときは2列 |
| 480 px未満 | 1 | すべて |

広いレイアウトでは、行は76 px、間隔は16 pxです。スマートフォンでは、カードの高さは内容に合わせ、行数から決まる最小値があるので、切れるものはありません。切り替えバーはその中で横にスクロールし、ページ全体は横にスクロールしません。

## スマートフォンで

Web UIはスマートフォンにインストールでき、接続がなくても開きます。同じページにマニフェスト、アイコン、サービスワーカーを付けたもので、HotLoop自身が配信するので、サーバー側でビルドするものも、インストールするものもありません。

**インストール。** Androidでは、Chromeのメニューに **アプリをインストール** があります。iPhoneでは、Safariの共有シートに **ホーム画面に追加** があります。プラント名つきで全画面で開き、Androidではアイコンを長押しすると、アラームとダッシュボードが選べます。ブラウザがページをインストールしてサービスワーカーを動かすのは、**https** か `localhost` の上だけです。プラントの通常の `http://` アドレスでは、HotLoopはこれまでどおりタブで開きますが、インストールはできず、オフラインでも動きません。スマートフォン向けに、手前に証明書を置いてください（すでにあるイングレスやリバースプロキシです）。インストールできない理由は、ブラウザが教えてくれます。Chromeの開発者ツールの、Application、Manifestです。

**保持するもの。** ページ自体と、人が見る読み取りへの最後の応答です。アラーム一覧、ダッシュボード、読み取り値とエンティティの状態、デバイスとタグ、ステータス、設備ツリー、ボードです。ページが開いていて接続されている間は、開いたときに見せるものがあるように1分に1回これらを取得し、スマートフォンがポケットの中にあるときは取得しません。接続なしで開くとページは読み込まれ、アラーム一覧とダッシュボードにはスマートフォンが最後に見た内容が表示され、下部のバーが時刻つきでそう伝えます。

```
Offline. This is what this phone last saw as of 10/22/2026, 05:42:23. Nothing you
do here is sent until the connection is back.
```

接続が戻ると、数秒以内にバーが消え、画面はライブの応答で更新され、ライブフィードが再接続されます。

**オフラインで、一度もサインインしていない場合。** アプリはあるがサインインしていないスマートフォン（一度もしていないか、サインアウトして保持内容が空になった）は、接続がないと見せるものがないので、サインイン画面を表示して理由を伝えます。HotLoopがここから応答していないこと、そして再試行を続けていることです。HotLoopが応答した瞬間に、ページが自動で再読み込みされ、本物のサインイン画面になります。中身のないアプリを表示することはありません。

**絶対にしないこと。** 何かを変更するものは、オフラインのページから一切送られません。タグへの値の書き込み、スクリプト、レシピ、アラームの確認応答といった書き込みは、ページを出る前に、理由とともに拒否されます。

```
You are offline, so nothing was sent. Everything here is as of 10/22/2026, 05:42:23.
Try again when the connection is back.
```

サービスワーカーは、書き込みに応答せず、保持せず、キューにも入れず、中にバックグラウンド同期もありません。設備への命令は、ライブの応答を見ている人だけが送るもので、接続がないときに押したボタンが、どこかで待っていて後から出ていくことはありません。通知からの確認応答は別の話で、同じくネットワークが必要です。ntfyアプリが自分のボタンを押します。

**保持しないもの。** ライブフィード、トレンドと履歴、ログブック、設定、ユーザー、エスカレーションポリシー、通知に関するすべてです。大きすぎて毎回内容が違うために保持する価値がないものもあれば、スマートフォンのキャッシュに置くべきでないもの（人々のntfyトピック、アカウント）を含むものもあるので、これらの画面にはHotLoopの応答が必要です。

**スマートフォンでは。** 保持されるものは、そのスマートフォンのブラウザのキャッシュストレージに、最大200件の応答として置かれ、古いものから捨てられます。**サインアウトすると空になり**、期限切れや取り消されたセッションでも空になります（最初の `401` で空になります）。保持されるのはサインイン中のセッションだけなので、オフラインのスマートフォンが他の人のデータを開くことはありません。新しいHotLoopバージョンは自分専用のページキャッシュを持ち、古いものは削除されます。接続があればページは常にライブで取得されるので、新しいバージョンやプラント名の変更は、次に開いたときに表示されます。

同じテストが、ページとワーカーの両方でサーバーを取り去って再読み込みします。ページは開き、アラーム一覧とダッシュボードには保持された内容が表示され、タグへの書き込みも確認応答も拒否され、接続が戻ったあともアラームは未確認のままで、書き込みの監査記録は空で、サインアウトすると保持内容が空になります。ベアメタルで実行しました（2026-11-17）。実際のスマートフォンへのインストール、iPhoneのSafari、実際のプラントのWi-Fiが切れる状況を含みます。

## 権限

| 権限 | 閲覧者 | オペレーター | 管理者 |
|---|---|---|---|
| `dashboards.read` | はい | はい | はい |
| `dashboards.write` | いいえ | いいえ | はい |

読み取りはすべてのロールのもので、`roles` で絞り込まれます。書き込みは管理者のものです。カードを押したときにできることは、押す人自身の権限です。閲覧者には書き込みボタンが無効に見え、それをすり抜けてもサーバーが拒否します。

| メソッド | ルート | 権限 |

| `GET` | `/api/dashboards` | `dashboards.read` |
| `POST` | `/api/dashboards` | `dashboards.write` |

本文とエラーを含むリファレンスは、[HTTP API](/ja/iot/api/#ダッシュボード)にあります。作成、保存、削除はすべて、サブジェクト `dashboard:<id>` への `config` イベントとして記録に残るので、パネルに表示される内容を誰が変えたかをログブックで確認できます。

テーブルは `dashboards` で、PostgreSQL、TimescaleDB、SQLite向けのマイグレーション0023で追加されました。追加するだけです（[マイグレーションは追加するだけ](/ja/iot/migrations/)）。ウォールボードの行は、マイグレーションではなく、アプリケーションが最初に要求されたときに作るので、ダッシュボードができる前に取ったバックアップから復元したデータベースにも、再び作られます。

## ここにないもの

- **ピクセル単位のレイアウト。** 上で述べたとおり、意図的です。機械のHMIで、コントロールが固定の位置にどうしても必要なら、それはその機械のために作る画面であり、この機能が担うものではありません。
- **カードごとの表示制御。** ダッシュボードはロールに提供されますが、カードはそうではありません。カードが違う二つの読者は、二つのダッシュボードです。
- **タイル地図。** `map` カードを参照してください。
- **ボタンの押し続け。** ボタンは押したときに一度だけ書き込みます。押したときに書き込み、離したときにもう一度書き込む瞬時のコントロールは別のカードで、作られていません。
- **Edge Relayのダッシュボード。** UIがありません。
