誰が入れて、入ってから何ができるかを決める機能です。Cascadeはこのすべてを全員に提供します。有料プランはなく、裏でライセンス確認をすることもありません。

以下のエンドポイントはすべて`/api/v1/openapi.json`のOpenAPIドキュメントに載っており、それぞれを呼び出すテストがあります。

## カスタムロール

エディターの設定、ロールで操作します。ロールは誰でも読めます。オーナーまたは管理者がカスタムロールを作成、変更、削除し、同じ画面でプロジェクトのメンバーに割り当てます。

プロジェクトには、admin、editor、operator、viewerの4つの組み込みロールがあります。これらはコードの中にあり、変わることはありません。どれも合わないときは、名前とプロジェクト権限の一覧でカスタムロールを作ります。

よくある理由は、ラインのワークフローを開始して実行結果を読めるが、何も編集できないライン責任者が必要な場合です。

```sh
curl -X POST $CASCADE/api/v1/roles -H "Authorization: Bearer $KEY" \
  -d '{"name":"line-lead","description":"runs the line","permissions":["project.read","workflow.read","workflow.execute","execution.read"]}'
```

その後、組み込みロールと同じ呼び出しで、そのロールの人をプロジェクトに入れます。

```sh
curl -X PUT $CASCADE/api/v1/projects/$PROJECT/members/$USER -d '{"role":"line-lead"}'
```

知っておくこと:

- `GET /api/v1/permissions`はロールが持てるすべての権限を一覧にし、`GET /api/v1/roles`は4つの組み込みロールとカスタムロールを、それぞれができることとともに一覧にします。プロジェクト管理者がロールを選ぶのに必要なので、サインインしていれば誰でも両方を読めます。
- カスタムロールの作成、変更、削除はインスタンスのオーナーまたは管理者の役目で、`role.manage`権限です。プロジェクト管理者は自分のプロジェクトの人にロールを与えられますが、新しいロールは作れないため、受け取った以上の権限を自分に与えることはできません。
- ロールが持てるのはプロジェクト権限だけです。`user.manage`、`audit.read`などのインスタンス権限は持てず、求めると400になります。
- 名前は小文字、数字、ダッシュで2〜40文字、先頭は文字です。メンバーとサービスアカウントは名前でロールを保持するため、後から変更できません。4つの組み込み名はすでに使われています。
- ロールの権限を変更すると、そのロールを持つ全員に次のリクエストから反映されます。キャッシュはないため、削除した権限がまだ使える時間はありません。
- サービスアカウントのキーは、カスタムロールをプロジェクトロールとして持てます。APIキーのスコープは引き続きそれを絞り込みます。
- 誰かが持っているロールを削除すると409で拒否され、そのロールを持つメンバーとサービスアカウントキーの数が示されます。先にそれらを移してください。
- ロールの変更は、監査ログに`role.created`、`role.updated`(変更前後の権限付き)、`role.deleted`として残ります。

## LDAPとActive Directory

工場ですでに使っている名前とパスワードでサインインします。OpenLDAP、389 Directory Server、FreeIPA、Active Directoryに対応しています。ローカルアカウントやOIDCと並んで使え、`HOTLOOP_CASCADE_LDAP_URL`を設定するまでは無効です。

サインインの流れは次のとおりです。

1. サービスアカウント(ディレクトリが許可していれば匿名検索)が、ユーザーフィルターでその人を見つけます。
2. その人が所属するグループを調べます。
3. ディレクトリ自身が、その人としてbindしてパスワードを確認します。Cascadeはそのパスワードを保存せず、ハッシュも見ません。ここで作られるアカウントには独自のパスワードがないため、ディレクトリのパスワードを`/login`でローカルのパスワードとして使うことはできません。
4. アカウントは初回サインイン時に作られ(無効にした場合を除く)、以降はサインインのたびにロールがグループに従います。

有効にすると、サインインページに2つ目のフォームが表示されます。同じことは`{"username": "...", "password": "..."}`を付けた`POST /auth/ldap/login`の1回の呼び出しでもできます。名前が違う場合もパスワードが違う場合も、応答は同じです。ほとんどのディレクトリは空パスワードのbindを成功として応答するため、空のパスワードがディレクトリに届くことはありません。

### 設定

すべて環境変数です。Helmチャートでは`env`に入れ、bindのパスワードはシークレットから`extraEnv`に入れます。

| 変数 | 内容 |
|---|---|
| `HOTLOOP_CASCADE_LDAP_URL` | `ldap://host:389`または`ldaps://host:636`。これで有効になります。 |
| `HOTLOOP_CASCADE_LDAP_FLAVOR` | `ldap`(既定)または`ad`。下の既定値を選ぶだけです。 |
| `HOTLOOP_CASCADE_LDAP_START_TLS` | `true`にすると、何かを送る前に`ldap://`接続を暗号化接続へ切り替えます。 |
| `HOTLOOP_CASCADE_LDAP_CA_FILE` | ディレクトリの証明書で信頼する認証局のPEMファイル。空ならシステムのものを使います。 |
| `HOTLOOP_CASCADE_LDAP_TLS_SERVER_NAME` | URLのホストと異なる場合に、証明書が対象とすべき名前。 |
| `HOTLOOP_CASCADE_LDAP_BIND_DN` | 人を検索するサービスアカウント。空なら匿名検索です。 |
| `HOTLOOP_CASCADE_LDAP_BIND_PASSWORD`または`_FILE` | そのパスワード、またはそれを入れたファイル。両方は不可です。パスワードのないDNは匿名bindになるため拒否されます。 |
| `HOTLOOP_CASCADE_LDAP_USER_BASE` | 必須。人を検索する起点のDN。 |
| `HOTLOOP_CASCADE_LDAP_USER_FILTER` | 1人を見つけます。`{username}`は入力された値で、エスケープされます。 |
| `HOTLOOP_CASCADE_LDAP_GROUP_BASE` | グループを検索する起点のDN。空ならグループ検索をしません。 |
| `HOTLOOP_CASCADE_LDAP_GROUP_FILTER` | その人が所属するグループを見つけます。`{dn}`はその人のDN、`{username}`は入力された値です。 |
| `HOTLOOP_CASCADE_LDAP_ID_ATTR`、`_EMAIL_ATTR`、`_NAME_ATTR` | 固定ID、メール、表示名に使う属性。 |
| `HOTLOOP_CASCADE_LDAP_ROLES` | カンマ区切りの`group=role`の組: `supervisors=admin, operators=member`。グループは`cn`または完全なDNで指定します。その人のグループのうち最も強いロールが適用されます。 |
| `HOTLOOP_CASCADE_LDAP_DEFAULT_ROLE` | `member`、`admin`、`none`。ロールの割り当てがある場合の既定は`none`なので、割り当て済みグループに入っていない人は断られます。 |
| `HOTLOOP_CASCADE_LDAP_JIT` | `false`にすると、アカウントは手動でしか作られません。既定は`true`です。 |
| `HOTLOOP_CASCADE_LDAP_NAME` | サインインボタンに表示される名前。 |

`ldap`の既定値: ユーザーフィルター `(&(objectClass=inetOrgPerson)(uid={username}))`、グループフィルター `(&(|(objectClass=groupOfNames)(objectClass=groupOfUniqueNames)(objectClass=group))(member={dn}))`、ID `entryUUID`、メール `mail`、名前 `cn`。

`ad`の既定値: ユーザーは`sAMAccountName`またはユーザープリンシパル名で見つかるため、`alice`でも`alice@plant.example`でも使え、無効なアカウントは検索から外れます。グループは入れ子のメンバーシップ規則(`member:1.2.840.113556.1.4.1941:={dn}`)を使うので、割り当て済みグループの中にあるグループのメンバーもそのロールを受け取ります。IDは`objectGUID`をGUID形式にしたもの、メールは`mail`、名前は`displayName`です。

### 知っておくこと

- **Active Directoryは暗号化を求めます。** 暗号化されていない接続での単純bindを拒否します。`ldaps://`を使うか、`START_TLS=true`を付けた`ldap://`を使ってください。Cascadeは証明書をCAファイル(またはシステムのルート)とサーバー名に照らして確認し、この確認を省く設定はありません。自己署名のディレクトリは、そのCAを`CA_FILE`に入れる必要があります。
- **アカウントは名前ではなくディレクトリのIDに結び付きます。** ディレクトリで名前を変えたり別のOUへ移したりしても、ここでは同じアカウントです。`mail`がない人にはアカウントを作れません(サインイン画面でそう表示されます)。
- **アドレスの権威はディレクトリです。** ここにすでに同じメールのアカウントがある場合、その人が初めてサインインしたときに、追加の確認なしでディレクトリのエントリーに結び付けられます。確認済みのOIDCアドレスと同じ扱いです。自分で運用していないディレクトリには向けないでください。
- **インスタンスの最初のアカウントがオーナーです。** 作られ方は問いません。先に初期セットアップでオーナーを作ってください。
- **ここで設定した第2要素は引き続き有効です。** ディレクトリのパスワードは1つの要素です。アカウントに認証アプリやパスキーがある人には、その後にそれが求められ、インスタンス全体のMFA必須設定も全員と同じように適用されます。
- **パスワードを間違えると、ここでもアカウントがロックされます。** すでにディレクトリに結び付いたアカウントで5回続けて間違えると、ローカルアカウントと同じく1分間ロックされ、回数ごとに倍になります。ディレクトリ側のロックが働く前に止まります。ディレクトリが知らない人、間違ったパスワード、ロックされたアカウントはすべて、監査ログに`auth.login_failed`または`auth.login_refused`として残ります。ディレクトリは通したがCascadeが断った人(グループなし、メールなし、JITオフ)は`auth.sso_refused`です。
- **ディレクトリが停止している場合は、パスワードの誤りではなくサーバーエラーです。** サインイン画面にはディレクトリが応答しなかったと表示され、詳細はログにあります。
- ディレクトリへの呼び出しは1回15秒までに制限され、ユーザーフィルターに一致できるのは1人だけです。2人一致した場合は、問題を示して拒否し、最初の1人を選ぶことはありません。

## SAML

任意のSAML 2.0 IDプロバイダーを使ったシングルサインオンです。Cascadeがサービスプロバイダーになります。ローカルアカウント、OIDC、LDAPと並んで使え、プロバイダーのメタデータを指定するまでは無効です。

手順は次のとおりです。

1. Cascadeは自分のメタデータを`/auth/saml/metadata`で公開します。それをプロバイダーに渡すか、そこに含まれる2つの値、エンティティIDとassertion consumer service(`<public url>/auth/saml/acs`、HTTP-POSTバインディング)を入力します。
2. `HOTLOOP_CASCADE_SAML_IDP_METADATA_URL`にプロバイダーのメタデータのアドレス(`https://sso.plant.example/saml/metadata`のようなもの)を設定するか、`HOTLOOP_CASCADE_SAML_IDP_METADATA_FILE`に同じ文書をディスクに保存したものを指定します。
3. サインインページに「でサインイン」ボタンが表示されます。このボタンは`/auth/saml/start`に進みます。

戻ってきたときに確認するのは、プロバイダーのメタデータにある証明書に対する応答の署名、オーディエンス、有効時間、このブラウザーが開始したリクエストへの応答であること、そしてサインインがこのブラウザーで開始されたことです。誰も求めていない応答(プロバイダー側で開始したサインイン)は拒否されます。各サインインの状態は1回しか使えないので、盗まれた応答を再利用することはできません。

| 変数 | 内容 |
|---|---|
| `HOTLOOP_CASCADE_SAML_IDP_METADATA_URL`または`_FILE` | プロバイダーのメタデータ。どちらか一方でSAMLが有効になります。両方は不可です。 |
| `HOTLOOP_CASCADE_SAML_ENTITY_ID` | このインスタンスがプロバイダーに名乗る名前。既定はそのメタデータURLです。 |
| `HOTLOOP_CASCADE_SAML_KEY_FILE`と`_CERT_FILE` | このインスタンスの鍵ペア(PEM、RSAまたはEC)。両方指定するか、どちらも指定しません。既定は、初回起動時にデータディレクトリへ`saml-sp.key`と`saml-sp.crt`として作られ、保持されるペアです。 |
| `HOTLOOP_CASCADE_SAML_SIGN_REQUESTS` | `true`にすると、Cascadeが送るすべてのリクエストに署名します。プロバイダーに証明書を伝える必要があります。既定は`false`です。 |
| `HOTLOOP_CASCADE_SAML_NAMEID_FORMAT` | Cascadeがプロバイダーに人の識別を求める形式: `persistent`(既定)、`email`、`unspecified`。 |
| `HOTLOOP_CASCADE_SAML_SUBJECT_ATTR` | NameIDの代わりに人を識別する属性。 |
| `HOTLOOP_CASCADE_SAML_EMAIL_ATTR`、`_NAME_ATTR`、`_GROUPS_ATTR` | メール、表示名、グループを保持する属性。 |
| `HOTLOOP_CASCADE_SAML_ROLES`、`_DEFAULT_ROLE`、`_JIT`、`_NAME` | LDAPと同じです。グループとロールの組、どのグループにもいない人のロール、初回サインインでアカウントを作るかどうか、ボタンの名前です。 |

属性の設定がなければ、Cascadeは一般的な名前を探します。メールは`email`、`mail`、`emailAddress`、LDAPオブジェクトID `urn:oid:0.9.2342.19200300.100.1.3`、またはクレームURI `.../claims/emailaddress`で、NameIDがアドレスならそれにフォールバックします。名前は`displayName`、`name`、または姓と名です。グループは`groups`、`group`、`memberOf`、URI `.../claims/Group`、そしてMicrosoftのグループクレームです。

知っておくこと:

- **永続IDを求めてください。** アカウントはNameIDに結び付き、一時的なものはサインインのたびに変わります。Cascadeは永続IDを求め、一時的なものはそう伝えるメッセージとともに拒否します。サインインのたびに新しいアカウントを作らないためです。プロバイダーが一時IDしか送れない場合は、変わらない属性を`SUBJECT_ATTR`に指定してください。
- **アドレスの権威はプロバイダーです。** LDAPと同様に、同じメールの既存アカウントは初回のSAMLサインインで結び付けられます。
- **プロキシの背後では、`HOTLOOP_CASCADE_PUBLIC_URL`に人々が使うアドレスを設定してください。** プロバイダーは、それから作られたassertion consumer URLにPOSTします。
- **HTTPSを使ってください。** プロバイダーは別のサイトからのPOSTで応答するため、サインインをそのブラウザーに結び付けるCookieをサイトをまたいで送る必要があり、ブラウザーが許可するのは安全な接続だけです。
- **Podが複数ある場合**は、すべてに同じ鍵ペアが必要です。シークレットに入れて`KEY_FILE`と`CERT_FILE`で指定してください。そうしないと各Podが独自に作ります。
- ここで設定した第2要素はSAMLサインイン後も引き続き有効で、SAMLがプロバイダー自身の多要素認証を代わりに認めることはありません。
- シングルログアウトには対応していません。サインアウトすると、ここでのセッションだけが終わります。

## SCIM

エディターの設定、サインインとSCIMで、SCIMが有効か、プロバイダーに渡すベースURL、トークンを確認でき、トークンを作成するボタン(表示は1回だけ)と失効させるボタンがあります。LDAP、SAML、OpenID Connectはインスタンスの起動時に環境で設定するので、同じ画面は、どれが有効か、プロバイダーがどこを指しているか(SAMLのメタデータとACSのURL)を示すだけで、変更できるふりはしません。

SCIMは、IDプロバイダーがアカウントをディレクトリと同期させる仕組みです。人が入社すれば作成し、異動すれば変更し、退職すれば無効にし、グループも管理します。CascadeがSCIMサーバー(RFC 7643と7644、バージョン2.0)で、プロバイダーがクライアントです。RFCの内容と一般的なIDプロバイダーが送る内容に合わせて作られ、別のチームが作ったSCIMクライアントで、持っているすべての確認を実行するscim2-testerで、リリースごとに試験しています。`HOTLOOP_CASCADE_SCIM=true`を設定するまでは無効です。

設定の手順は次のとおりです。

1. `HOTLOOP_CASCADE_SCIM=true`で有効にして再起動します。
2. インスタンスのオーナーまたは管理者として、プロバイダー用のトークンを作ります。`{"name": "plant directory"}`を付けて`POST /api/v1/scim-tokens`を呼びます。応答の`secret`(`hlcs_`で始まる)は1回しか表示されないので、すぐにプロバイダーに入力してください。`GET /api/v1/scim-tokens`は各トークンの最終使用日時とともに一覧にし、`DELETE /api/v1/scim-tokens/{token}`は1つを失効させます。トークンは人がサインインして作る必要があります。APIキーでは作れないので、漏れたキーでさらに作られることはありません。
3. プロバイダーにベースURLの`<public url>/scim/v2`と、bearerトークンとしてのトークンを渡します。

すべての呼び出しにトークンが必要で、すべての応答は`application/scim+json`です。呼び出しはトークン名を実行者として監査ログに残るため、`user.created`、`user.disabled`などでどのプロバイダーが行ったかが分かり、SCIMイベントの`scim.user_deleted`、`scim.group_created`、`scim.group_updated`、`scim.group_deleted`も残ります。

### 提供する内容

`/ServiceProviderConfig`、`/ResourceTypes`、`/Schemas`は対応している内容を示し、事実だけを示します。フィルターとPATCHに対応し、bulk、ソート、ETag、パスワード変更には対応しません。

| リソース | 呼び出し |
|---|---|
| `/Users` | `GET`(一覧、`filter`、`startIndex`、`count`、`attributes`、`excludedAttributes`に対応)、`POST`、`GET /{id}`、`PUT /{id}`、`PATCH /{id}`、`DELETE /{id}` |
| `/Groups` | 同じ |
| `/.search`、`/Users/.search`、`/Groups/.search` | 本文にクエリを入れた`POST` |

- **ユーザー**は`userName`、`externalId`、`name`(`formatted`、`givenName`、`familyName`)、`displayName`、`emails`、`active`で構成されます。アカウントのメールは、プライマリのもの、なければ勤務先のもの、なければ最初のもの、なければアドレス形式の場合の`userName`です。アドレスのないものは400です。プロバイダーが送ったものは送られたとおりに返され、送られていない名前を作り出すことはありません。`groups`は読み取り専用で返ります。
- **グループ**は`displayName`、`externalId`、`members`で構成され、各メンバーはユーザーのIDです。ユーザーでないメンバーは400です。
- **フィルター**は完全な構文に対応します。`eq ne co sw ew gt ge lt le pr`、`and`、`or`、`not`、括弧、`attr[filter]`です。`id`と`externalId`以外は大文字小文字を区別せずに比較します。不正なフィルターは`scimType: invalidFilter`付きの400です。
- **PATCH**は、パスの有無を問わず`add`、`replace`、`remove`を受け付け、`emails[type eq "work"].value`や`members[value eq "id"]`のような値パスを大文字小文字を問わず受け付け、一部のプロバイダーが送るブール値を`true`でも文字列の`"False"`でも受け付けます。PUTが変更できるものとまったく同じものを変更します。
- **一覧**はアカウントが作られた順で、`count`で指定しない限り1ページ100件、最大200件です。

### しないこと

- **オーナーを表示も変更もしません。** インスタンスのオーナーは一覧に出ず、取得、パッチ、削除ができず、グループにも入れられません。オーナーのメールは競合として扱われます。
- **アカウントを削除しません。** `DELETE`はその人を無効にし、セッションを終了し、グループから外し、SCIMから隠します。その人が作ったものと監査記録はすべて残ります。プロバイダーが同じアドレスで再作成すると、同じアカウントが有効な状態で戻ります。`active: false`は隠さずに無効にします。
- **SCIMのアカウントにはパスワードがありません。** OIDC、SAML、LDAPでサインインし、これらがアドレスでそのアカウントに結び付きます。
- **プロジェクトには手を触れません。** SCIMが扱うのはアカウントとインスタンスのロールです。誰がどのプロジェクトに入るかは、これまでどおりここで決めます。

### グループからロールを決める

既定では新しいアカウントはメンバーで、SCIMが誰かのロールを変えることはありません。グループでロールを決めるには、グループ名をロールに割り当てます。

```
HOTLOOP_CASCADE_SCIM_ROLES="Plant Admins=admin, Plant Members=member"
HOTLOOP_CASCADE_SCIM_DEFAULT_ROLE=member
```

すると、メンバーシップが変わるたびにその人のロールがグループに従います。割り当て済みのうち最も強いロールが適用され、どのグループにも入っていない人は既定値になります。プロバイダーはオーナーを作らないため、割り当てられるのは`admin`と`member`だけです。ロールの出どころは1つにしてください。OIDCやSAMLもグループをロールに割り当てる場合は、最後にロールを変えた方が優先され、両者が競合します。

プロバイダーには同じグループ名が必要で、グループをメンバーとともに送る必要があります。SCIMグループに対応しているプロバイダーならどれでもできます。
