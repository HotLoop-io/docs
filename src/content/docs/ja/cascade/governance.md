増え続けるワークフローを工場がどう管理するかを説明します。共有設定、フォルダー、注釈付きの実行、マスキング、時間経過の数値、外部シークレット、ログストリーミング、大きなデータの置き場所です。ここにあるものはすべて無料で、すべてのビルドに入っています。

以下に挙げるエンドポイントはすべて`/api/v1/openapi.json`のOpenAPIドキュメントにあり、それぞれをSQLiteとPostgresの両方で呼び出すテストがあります。

## 変数

エディターの上部バーの「変数」で扱います。インスタンス全体の変数は一番上に、各プロジェクトの変数はその名前の下にあります。ロールが許可するものだけが表示されます。

変数は、ワークフローが`vars.NAME`として読む名前付きの値です。セットポイントの上限、工場の名前、試験ラインと本番ラインで異なるベースURLなどが当てはまります。

```yaml
- name: Check limit
  type: core.if
  version: 1
  params:
    condition: "{{ item.json.temp > toNumber(vars.TEMP_LIMIT) }}"
```

- 変数は**インスタンス全体**のものか、**1つのプロジェクト**に属するものです。両方に同じ名前がある場合は、プロジェクトのものが優先され、そのプロジェクトのワークフローにだけ適用されます。
- 値は最大8 KiBのテキストです。数値が必要なときは`toNumber(vars.X)`を使います。
- 名前は文字、数字、アンダースコアで、文字またはアンダースコアで始まり、最大64文字です。`vars.NAME`として読めなければならないからです。
- **変数はシークレットではありません。** プロジェクトを読める人は誰でもその変数を読め、値は実行データから消されません。パスワード、トークン、キーは、認証情報の保管庫か、外部のシークレットストア(後述)に入れてください。
- 実行は開始時に変数を読み、待機や再起動のあとに再開するときにも読み直します。変更は次の実行に届き、すでにステップの途中にある実行には届きません。存在しない名前は、エラーではなく空として読まれます。

| 呼び出し | 内容 |
|---|---|
| `GET /api/v1/variables` | インスタンス変数と、読めるプロジェクトの変数。`?project=`で1つのプロジェクトに絞り込みます。 |
| `POST /api/v1/variables` | 変数を作ります。`projectId`があればそのプロジェクトのもの、なければインスタンス全体のものです。 |
| `PUT /api/v1/variables/{variable}` | 名前と値を変更します。 |
| `DELETE /api/v1/variables/{variable}` | 削除します。 |

権限: プロジェクトでは`variable.read`権限で一覧でき、`variable.create`、`variable.update`、`variable.delete`で変更できます。viewerとoperatorは読み、editorとadminは変更します。インスタンス全体の変数は、どのプロジェクトのワークフローも読めるため、サインインしていれば誰でも読め、変更できるのはインスタンスのオーナーまたは管理者だけです。カスタムロールはこの4つの権限のどれでも持てます。変更は監査ログに`variable.created`、`variable.updated`、`variable.deleted`として残り、名前は記録されますが値は記録されません。

## フォルダー

エディターでは、ワークフローの一覧がフォルダーです。「新しいフォルダー」で作成し、「サブフォルダーを追加」で入れ子にし、一覧のワークフロー自身の行から移動します。ワークフローを作るときにフォルダーを選ぶと、そこに置かれます。

フォルダーはプロジェクトのワークフローをまとめ、工場の構成と同じように入れ子になります。エリア、ライン、セルといった具合です。

- フォルダーは1つのプロジェクトに属します。名前は隣り合うフォルダー間で一意で、最大100文字です。
- フォルダーは最大10階層まで入れ子にできます。
- ワークフローは1つのフォルダーの中か、プロジェクトの最上位にあります。新しいバージョンを保存しても移動しません。
- ワークフローやフォルダーが入っているフォルダーは削除できない(409)ため、フォルダーの削除でワークフローが行方不明になることはありません。フォルダーは自分自身や自分のサブフォルダーの中へは移動できず、別のプロジェクトにも移動できません。

| 呼び出し | 内容 |
|---|---|
| `GET /api/v1/folders` | 読めるプロジェクトのフォルダーを、フラットな形で`parentId`付きで返します。`?project=`で絞り込みます。 |
| `POST /api/v1/folders` | `projectId`に、`parentId`の中または最上位にフォルダーを作ります。 |
| `PATCH /api/v1/folders/{folder}` | 名前を変更するか、`parentId`で移動します(最上位は空文字列)。 |
| `DELETE /api/v1/folders/{folder}` | 空のフォルダーを削除します。 |
| `PUT /api/v1/workflows/{workflow}/folder` | ワークフローをフォルダーに入れるか、空の`folderId`で最上位に置きます。 |
| `GET /api/v1/workflows?folder=` | 1つのフォルダーのワークフロー、または`folder=none`で各プロジェクトの最上位。 |

APIが返すすべてのワークフローには`folderId`が含まれます。`folder.read`、`folder.create`、`folder.update`、`folder.delete`権限は変数の権限と同じように働き、ワークフローの移動には`workflow.update`が必要です。フォルダーの変更は監査ログに残り、移動は`workflow.moved`として残ります。

## 実行への注釈

エディターでは、各実行のページに、高評価または低評価、メモ、タグを入れる注釈欄があり、実行一覧はタグと評価で絞り込めます。

実行が終わったあとで、その実行について書き残せます。高評価または低評価、メモ、探すためのタグです。「金型交換後の最初の良品ロット」や`scrap`のようなことがここに入ります。

```sh
curl -X PUT $CASCADE/api/v1/executions/$RUN/annotation -H "Authorization: Bearer $KEY" \
  -d '{"vote":"up","note":"first good batch after the die change","tags":["die-change","first-shift"]}'
```

- 評価は`up`、`down`、または空です。メモは最大2000文字です。1つの実行には最大20個のタグを付けられ、各タグは制御文字を含まない1〜40文字で、重複なく並びます。
- `PUT`は注釈全体を置き換えるので、残したい内容をすべて送ってください。何も書かれていない注釈は、注釈がないのと同じです。`DELETE /api/v1/executions/{execution}/annotation`で消去します。
- APIが返すすべての実行には注釈が付き、一覧でも各行に付きます。`GET /api/v1/executions?tag=scrap`と`?vote=down`で絞り込め、ほかのフィルターと組み合わせられます。
- 注釈には、監査ログと同じIDで、誰がいつ残したかが記録されます。
- 注釈を付けるには、operator、editor、adminが持つ`execution.annotate`権限が必要で、viewerにはありません。viewerは注釈を読めます。
- 注釈は、その実行が削除されると消えます。監査ログには評価とタグとともに`execution.annotated`と`execution.annotation_cleared`が残り、メモが残されたことだけが記録され、内容は記録されません。

## 完了した実行の保持

エディターの設定、完了した実行の保持期間(日)で設定します。APIでは、`{"retentionDays": 90}`を付けて`PATCH /api/v1/settings`を呼びます。ほかの設定と同じく`instance.settings`権限が必要です。

既定では、完了したすべての実行がこれまでどおり永久に保持されます。日数を設定すると、mainが1時間に1回、それより前に終わった完了済みの実行(成功、失敗、キャンセル)をステップのデータとともに削除します。0にすると再び無効になります。

- キューにある、実行中、または待機中の実行は決して触れません。親がまだ進行中の実行にも触れません。親がその実行が何をしたかを尋ねるからです。
- 最大500件の実行のまとまりごとに独立したトランザクションで処理され、削除件数と基準日時を記した`execution.pruned`の行が監査ログに1つ書かれます。設定を変更すると`instance.retention`が記録されます。
- すべてのmainがこの処理を実行し、2つが同時に実行しても、やることが少なくなるだけです。
- ブロブの整理は同じ処理に続いて行われ、保持の設定が有効かどうかにかかわらず1時間に1回実行されるので、手動で削除した実行も整理されます。後述の「ブロブの整理」を参照してください。

## APIキーの制限

エディターの設定、キーあたり毎分のAPIリクエスト数で設定します。APIでは、`{"apiRateLimit": 120}`を付けて`PATCH /api/v1/settings`を呼び、`instance.settings`権限が必要です。

既定では、キーは好きなだけ呼び出せます。数値を設定すると、各APIキーと、そのキーでMCPにサインインした各エージェントが、毎分その回数のリクエストを行えます。制限を超えた呼び出しには、待つべき秒数を示す`Retry-After`ヘッダー付きで`429`が返ります。キーごとに独自のカウントがあるので、暴走したスクリプト1つが別のキーの分を使い切ることはありません。エディターにサインインしている人は制限の対象外です。

カウントは各プロセス単位です。プロセスを守るのはそれだからです。mainが3つあれば、キー1つがその数の最大3倍まで呼び出せ、それは3つに分散されます。設定の変更は5秒以内にすべてのmainに届きます。変更すると、変更前と変更後の数値を付けた`instance.api_rate_limit`が監査ログに書かれます。

Webhookにはトリガーで設定する独自の制限があり、アカウントはパスワードの誤りが続くとロックされます。どちらも変わりません。

## バックアップと復元

```
hotloop-cascade backup /backups/2026-11-20
hotloop-cascade restore /backups/2026-11-20
```

`backup`は新しいディレクトリを作り、SQLiteデータベースの整合した複製(サーバー稼働中に`VACUUM INTO`で取得したもの)、保存済みの認証情報をすべて封印するキーファイル、ブロブファイル、それぞれのSHA-256を記した`manifest.json`を入れます。サーバーと同じ`--database`、`--key-file`、`--blob-dir`の設定を、同じ環境変数から受け取ります。ディレクトリはまだ存在しないか、空である必要があり、バックアップが古いものと混ざることはありません。キーファイルがなければバックアップはありません。キーのないデータベースには、誰も読めない認証情報が入っているからです。

`restore`はそれらを元に戻し、事前にサーバーを停止する必要があります。何かを書き込む前にすべてのファイルをマニフェストと照合するので、破損したバックアップや不完全なバックアップは何も変更しません。すでにあるデータベースや、異なるキーファイルの上書きは拒否され、`--replace`で意図を示します。その後サーバーを起動するとスキーマが最新になり、自分より新しいリリースで取ったバックアップは拒否されます。

PostgreSQLでは、`backup`はキー、ブロブ、マニフェストを書き出し、データベース部分を作る`pg_dump --format=custom`コマンドを表示します。そのプログラムはPostgreSQL自身のもので、Cascadeのイメージには含まれていないためです。`restore`はキーとブロブを戻し、`pg_restore`コマンドを表示します。S3やAzureに置いたブロブはコピーされないので、そのバケットはそちらでバックアップしてください。

マイグレーションを伴うリリースにアップグレードする前に、バックアップを1つ取ってください。マイグレーションは前にしか進まず、古いイメージに戻すにはバックアップが必要です。

## 実行のマスキングポリシー

エディターの設定、マスキングでポリシーを作ります。ワークフローは、何も選択していない状態のエディター側面パネルの、ワークフロー設定の下でポリシーを選びます。

認証情報の保管庫は、すでにシークレットを実行が保存するあらゆるものから外しています。マスキングポリシーは、認証情報ではないものの実行履歴にも残すべきでないデータのためのものです。バッジ番号、作業者の名前、Webhookで届いたカード番号などです。

ポリシーは名前とルールで構成されます。

- **fields**: アイテムのキー名です。ポリシーが名指ししたキーは、深さや値の型にかかわらず、値全体が`[redacted]`に置き換えられます。照合は大文字小文字を区別せず、`*`と`?`はワイルドカードとして働くので、`*secret*`は`plant_secret`と`SecretKey`に一致します。
- **patterns**: GoのRE2構文の正規表現です。どのテキストの中でも一致した部分が`[redacted]`に置き換えられます。空のテキストに一致するパターンは拒否されます。
- **steps**: 省略可。ポリシーは列挙したステップだけを対象にします。空なら全ステップです。
- **appliesToAll**: 省略可。ワークフローがポリシーを指定しているかどうかにかかわらず、すべてのワークフローが対象になります。

ワークフローは設定で名前を指定してポリシーを選びます。

```yaml
settings:
  redaction: Badges
```

動作とタイミングは次のとおりです。

- **実行が終了したとき**に、その実行を成功、失敗、停止として記録する同じトランザクションの中で動きます。それまで実行は実データを保持しています。次のステップがそれを必要とし、再起動もそこから再開するからです。待機中の実行は引き続き実データを保持します。
- 各ステップの保存済み出力、各ステップの保存済みエラーメッセージ、実行自体のエラー、保存済みのWebhook応答をマスクします。ファイルの内容には触れません。ポリシーが読むのはアイテムのデータで、ファイルはバイト列への参照だからです。
- 保存された内容が、その実行の途中からのリプレイや再試行の出発点になるので、リプレイにはマスク後の値が見えます。ワークフローのトリガーのアイテムは最初のステップの出力にあり、これもマスクされます。
- その実行が持っていた時点のワークフローを読むので、ワークフローやポリシーを編集しても、すでに終わった実行は変わりません。
- 存在しないポリシーを指定したワークフローは**閉じる側に失敗します**。その実行はアイテムデータを一切保持せず、`metadata`の保存設定と同じ動作になり、ワークフローの`problems`にもそう表示されます。ポリシーがないことが、誰かがマスクしたかったデータの保持を意味してはなりません。
- ワークフローが指定しているポリシーは削除できず(409)、名前も変更できません。ルールは変更できます。

| 呼び出し | 内容 |
|---|---|
| `GET /api/v1/redaction-policies` | すべてのポリシー。ワークフローを書く人に名前が必要なので、サインインしていれば誰でも読めます。 |
| `POST /api/v1/redaction-policies` | ポリシーを作ります。 |
| `PUT /api/v1/redaction-policies/{policy}` | 説明とルールを置き換えます。 |
| `DELETE /api/v1/redaction-policies/{policy}` | どのワークフローも指定していないポリシーを削除します。 |

ポリシーの作成、変更、削除には、オーナーと管理者が持つインスタンス権限`redaction.manage`が必要です。それぞれ監査ログに`redaction.created`、`redaction.updated`、`redaction.deleted`として残ります。

## Insights

エディターの上部バーの「Insights」です。期間、プロジェクト、ワークフローを選ぶと、合計、日ごとのグラフと表、ワークフローごとの表が表示されます。

`GET /api/v1/insights`は、ある期間の実行を集計します。どう終わったか、どれくらいかかったかを、日ごととワークフローごとに示します。

```sh
curl "$CASCADE/api/v1/insights?from=2026-10-10&to=2026-10-14&project=$PROJECT" -H "Authorization: Bearer $KEY"
```

- `from`と`to`はRFC 3339の時刻、または日付(UTCの午前0時)です。どちらもなければ、現在までの直近7日間です。応答する最長期間は366日です。
- `project`と`workflow`で絞り込みます。指定しなければ、呼び出し元が実行を読めるすべてのプロジェクトを集計するので、各人の数値は自分のものになります。
- 実行は、作成されたUTCの日に数えられます。
- `totals`と、`days`および`workflows`の各行には、`total`、`succeeded`、`failed`、`canceled`、`unfinished`(キュー中、実行中、待機中)、開始と終了の両方がある実行の平均および最長の実行時間(ミリ秒)、`failureRate`が含まれます。
- `failureRate`は、失敗数を成功数と失敗数の合計で割った値です。キャンセルされた実行は失敗ではなく、終わっていない実行はまだ結果が決まっていないので、どちらも含まれません。どちらにも終わったものがなければ0です。
- `days`は期間内のすべてのUTCの日を並べ、何も実行されなかった日は0にするので、グラフに推測が必要な隙間はありません。`workflows`は最も忙しい50件で、最も忙しいものが先頭です。

実行一覧と同じ実行の行を読むので、`execution.read`権限と、それに対応するスコープのキーが必要です。

## 外部シークレット

エディターの設定、外部シークレットで扱います。プロバイダーを追加し、同じカードからパスで試し、それを指す参照がどう見えるかを確認します。

認証情報のシークレットフィールドは、シークレット自体を保持する代わりに、HashiCorp VaultやOpenBaoに保管されたシークレットを指せます。ストアでパスワードをローテーションすれば、誰も認証情報を編集しなくても、すべてのワークフローが次の実行で新しいパスワードを使い、データベースの複製にもパスワードは入りません。

参照は、認証情報のどのシークレットフィールドでも、次のような形です。

```
secret://bao/plant/line-3/db#password
```

これは、`bao`という名前のプロバイダー、`plant/line-3/db`にあるシークレット、そしてその`password`キーです。認証情報はこのテキストを、ほかのシークレットと同じように封印して保存します。指している先のものはここには一切保存されません。値は実行が認証情報を開くときに読まれ、プロバイダーのキャッシュ時間のあいだメモリに保持され、保管庫のパスワードと同じように、実行が保存するあらゆるものからマスクされます。参照を受け付けるのはシークレットフィールドだけです。シークレットでないフィールドに入力した参照は、ただのテキストです。

### プロバイダーの設定

プロバイダーは、サーバー、Cascadeがそこにサインインする方法、読める場所で構成されます。作成、変更、削除はインスタンスのオーナーまたは管理者の役目で、`secrets.manage`権限が必要であり、APIキーではなくサインインした人が行う必要があります。

```sh
curl -X POST $CASCADE/api/v1/secret-providers -H "X-CSRF-Token: ..." -d '{
  "name": "bao",
  "address": "https://bao.plant.example:8200",
  "authMethod": "approle", "roleId": "...", "secretId": "...",
  "allowedPaths": ["plant"]
}'
```

| フィールド | 内容 |
|---|---|
| `name` | 小文字、数字、ダッシュで1〜40文字。すべての参照に入るので、あとから変更できません。 |
| `address` | サーバーのURL。 |
| `mount`, `kvVersion` | KVエンジンのマウント先(既定は`secret`)と、バージョン1か2か(既定は2)。 |
| `namespace` | サーバーのネームスペース用に`X-Vault-Namespace`として送られます。 |
| `authMethod` | `token`と`token`、または`approle`と`roleId`および`secretId`。`authMount`はAppRoleのマウント先(既定は`approle`)です。AppRoleは自分でサインインし、トークンが切れると再度サインインします。 |
| `caCert` | サーバーの証明書がシステムの信頼する認証局のものでない場合に、サーバーについて信頼するPEM形式の認証局。 |
| `allowedPaths` | **必須。** 参照が読める唯一の場所です。`plant`は`plant`とその下のすべてを許可し、`plantation`は許可しません。 |
| `projects` | 省略可。プロバイダーを使える唯一のプロジェクトです。空なら、すべてのプロジェクトが使えます。 |
| `cacheSeconds` | 読み取ったシークレットをメモリに保持する秒数。0〜3600。既定は30。0なら毎回読みます。 |

Cascadeがサインインする方法(トークン、またはAppRoleのIDとシークレット)は、インスタンスキーで封印され、キーのローテーションでほかのものと一緒に包み直され、どの呼び出しでも表示されません。変更時に省略すれば、保存済みのものがそのまま残ります。

`POST /api/v1/secret-providers/{provider}/test`はサインインし、`path`があればそれを読み、成功したかどうかを返します。値は決して返しません。`GET /api/v1/secret-providers`は、認証情報を作る人に名前が必要なので、サインインしていれば誰にでもプロバイダーの一覧を返します。呼び出しは監査ログに`secrets.provider_created`、`_updated`、`_deleted`として残ります。

### しないこと

- **プロバイダーには許可されたパスが必要です。** Vaultのトークンは通常、認証情報を編集する人が名指しできるべき範囲よりはるかに多くを読めます。リストがなければ、認証情報を作れる人なら誰でも、トークンが届く任意のシークレットを指す認証情報を作り、ワークフローにそれをどこかへ送らせることができてしまいます。プロバイダーには認証情報が必要とするパスを与え、そのポリシーにも同じものを与えてください。
- **参照は、実行が使うときだけでなく、認証情報を保存するときに検査されます。** プロバイダーが存在し、認証情報のプロジェクトに開かれていて、パスを許可している必要があります。空の部分、ドット、`..`を含むパスは拒否されます。
- **シークレットを読めなかった実行は、失敗して理由を示します。** プロバイダー、パス、キーを示しますが、値は決して示しません。該当するプロバイダーがない、プロバイダーが許可しないパス、そこにシークレットがない、そのキーがない、またはサーバー自身の拒否(読み取りを許可しないポリシーは「permission denied」)です。
- **プロバイダーを削除しても認証情報は編集されません。** それを指す認証情報は、実行が開くときに、プロバイダーがなくなったと示して失敗します。
- 実際に`secret://`で始まるシークレットの値は、参照として読まれるため、シークレットとして保存できません。
- 数値やtrue、falseの値はテキストとして読まれます。オブジェクト全体やリストである値は拒否されます。
## ログストリーミング

エディターの設定、ログストリーミングで扱います(オーナーと管理者)。各宛先には、送った量、最後に配信した時刻、最後のエラーが表示され、テストイベントを1つ送るボタンがあります。

監査ログと、終了するすべての実行の1行を、工場がすでにログを置いている場所へ送ります。syslogサーバー、またはHTTPでOTLPログを受け取るもの(OpenTelemetryコレクター、Loki、ログプラットフォーム)です。イベントは発生と同時に出ていくので、SIEMはサインインの失敗を数秒で把握でき、監査の記録は、このインスタンスの管理者が書き換えられない場所に残ります。

宛先は1つの場所です。必要な数だけ作ってください。

```sh
curl -X POST $CASCADE/api/v1/log-destinations -H "X-CSRF-Token: ..." -d '{
  "name": "plant syslog", "kind": "syslog",
  "address": "syslog.plant.example:6514", "network": "tls",
  "caCert": "-----BEGIN CERTIFICATE-----..."
}'
curl -X POST $CASCADE/api/v1/log-destinations -H "X-CSRF-Token: ..." -d '{
  "name": "collector", "kind": "otlp", "endpoint": "https://otel.plant.example/v1/logs",
  "headers": {"Authorization": "Bearer ..."}
}'
```

宛先の作成、変更、削除はインスタンスのオーナーと管理者(`logstream.manage`)の役目で、宛先は監査ログの送り先なので、APIキーではなくサインインした人が行います。呼び出しは監査ログに`logstream.destination_created`、`_updated`、`_deleted`として残ります。

### 送られるもの

- **監査イベント**: 監査ログのすべての行が、連番とハッシュ付きで送られます。連番とハッシュは、受信側が重複を見分ける手段で、ハッシュはその行自身のものなので、届いたものからチェーンを検証できます。失敗または拒否されたサインインは警告で、それ以外は通知です。
- **実行イベント**: どのように終わっても、終了する実行ごとに1つ送られます。実行ID、ワークフローのIDと名前、プロジェクト、ステータス、モード、作成、開始、終了の時刻、実行時間、エラーと失敗したステップが含まれます。失敗した実行はエラー、停止した実行は通知、成功した実行は情報です。実行が終わって数秒後に送られます。
- **アイテムのデータは決して送りません。** 実行のステップが見たもの、作ったものは、マスキングポリシーが守る実行の中に留まります。監査ログにシークレットが入ることはありません。

`events`は、どちらか一方または両方を選びます(`["audit"]`、`["execution"]`、既定は両方)。`start`は、新しい宛先がどこから始まるかを決めます。既定の`now`は作成後に起きることを送り、`beginning`は監査ログ全体と終了済みのすべての実行を最初に送ります。

### Syslog

メッセージはRFC 5424形式です。`<priority>1 time host hotloop-cascade pid msgid - {json}`で、イベントはJSON 1行です。priorityはfacilityの8倍にseverityを足した値です。msgidは監査アクション(`workflow.saved`)または実行のステータスです。

| フィールド | 内容 |
|---|---|
| `address` | `host:port`。 |
| `network` | `tcp`(既定)、`udp`、`tls`。 |
| `framing` | `tcp`と`tls`用: `octet`(RFC 6587のオクテットカウント、既定)または`newline`。UDPは1イベントにつき1データグラムです。 |
| `facility` | 既定は`local0`。任意のsyslog facility名。 |
| `appName` | ヘッダーのAPP-NAME。既定は`hotloop-cascade`。 |
| `caCert`, `serverName` | `tls`用: 信頼する認証局と、ホストでない場合に証明書が対象とすべき名前。検査を省く設定はありません。 |

### OTLP

ログはJSON本文のHTTP上のOTLPとして`endpoint`に送られます。イベントごとに1つのログレコードがあり、本文はJSONのイベントで、各部分は属性(`cascade.event`、`cascade.action`、`cascade.status`、`cascade.project`、`cascade.actor.name`など)として付くので、受信側は解析せずに絞り込めます。リソースには`service.name=hotloop-cascade`、そのバージョン、ホストが入ります。`headers`は、トークンやテナントのために、すべてのリクエストとともに送られます。インスタンスキーで封印され、キーのローテーションで包み直され、表示されません。一覧に出るのは名前だけです。`caCert`と`serverName`はsyslogと同じように働きます。

### 配信の振る舞い

- **少なくとも1回、順序どおりに。** 宛先は、最後に送った監査の行と、最後に送った終了済みの実行を覚えています。停止していた宛先は、復帰したときに取りこぼしたものすべてを順序どおりに受け取り、再起動しても止まった場所から続きます。送信と記録の間に送信側が切断された場合は、そのイベントが再送されます。連番はそのためにあります。
- **失敗する宛先は待ち時間を延ばします。** 1秒から倍々に増えて5分までで、ステータスには何がいつ失敗したかが`lastError`、`lastErrorAt`で示されます。成功すると消えます。停止中は何も捨てられないので、上限はキューではなく監査ログです。
- **同時に送信するのは1つだけです。** mainが複数ある場合は、宛先のリースを持つものがそこへ送り、ほかは待機して、止まったら引き継ぎます。
- **宛先を変更しても位置は保たれます。** 別のアドレスに移しても、何も再送せず、何も飛ばしません。変更で省略したヘッダーは維持され、空のオブジェクトで消去されます。名前と種類は変更できません。
- `POST /api/v1/log-destinations/{destination}/test`は、同じ経路で作り物のイベントを1つ送り、届いたかどうかを、届かなかった場合は理由とともに返します。何も動かしません。
- `GET /api/v1/log-destinations`は、各宛先のステータスを示します。送ったイベント数、最後に配信された監査の連番、最後に成功した時刻、最後のエラーです。

## 大きなデータの置き場所

実行が運ぶファイルや大きなペイロード(ダウンロードしたPDF、カメラのフレーム、スプレッドシート)は、データベースとは別にブロブとして保存されます。既定ではインスタンスのディスクにあります。`HOTLOOP_CASCADE_BLOB_STORE`を設定すると、代わりにS3バケットやAzureのブロブコンテナーに置くことができ、mainをブロブを運ばずに作り直せて、複数のmainが1つのコピーを共有します。

| 設定 | 意味 |
| --- | --- |
| `HOTLOOP_CASCADE_BLOB_STORE` | `fs`(既定)、`s3`、`azure`。 |
| `HOTLOOP_CASCADE_BLOB_SPOOL_DIR` | アップロード前にハッシュを計算する間、ブロブが待機する場所。既定はデータディレクトリの`blob-spool`。 |
| `HOTLOOP_CASCADE_BLOB_S3_BUCKET`, `_ACCESS_KEY`, `_SECRET_KEY` | `s3`に必須。シークレットは`_SECRET_KEY_FILE`も読みます。 |
| `HOTLOOP_CASCADE_BLOB_S3_ENDPOINT`, `_REGION` | AWSではエンドポイントを省略します。Garage、MinIO、Cephでは設定します。 |
| `HOTLOOP_CASCADE_BLOB_S3_PATH_STYLE` | `true`または`false`。エンドポイントを設定した場合は、パススタイルが既定です。 |
| `HOTLOOP_CASCADE_BLOB_S3_CA_FILE` | プライベート証明書を使うエンドポイント用のCAバンドル。 |
| `HOTLOOP_CASCADE_BLOB_S3_PREFIX` | バケット内のフォルダー。1つのバケットに複数のインスタンスを置けます。 |
| `HOTLOOP_CASCADE_BLOB_AZURE_CONTAINER` | `azure`に必須。 |
| `HOTLOOP_CASCADE_BLOB_AZURE_CONNECTION_STRING`、または`_KEY`付きの`_ACCOUNT`、または`_SAS` | サインイン方法の1つ。シークレットは`_FILE`形式も読みます。 |
| `HOTLOOP_CASCADE_BLOB_AZURE_ENDPOINT`, `_PREFIX` | Azuriteやプライベートクラウド用のエンドポイントと、コンテナー内のフォルダー。 |

チャートでは、これらを`env`と`extraEnv`で設定し、シークレットはKubernetes Secretから取ります。

- **内容でアドレス指定されます。** ブロブはそのSHA-256(`sha256/ab/cdef...`)の下に保存されるので、同じファイルは、いくつの実行が運んでいても1回だけ保存されます。もう一度置いても何も起きず、2つの実行が同時に置いた場合も同じです。
- **アップロード前にハッシュします。** データはスプールファイルに一度読み込まれ、ハッシュされてから送られるので、サイズによらずメモリ使用量は一定です。サイズ制限を超えるブロブは拒否され、キャンセルされたアップロードはバケットに何も残しません。
- **読み出し時に検査されます。** 読み取りはストリーミング中にハッシュと照合されるので、壊れたオブジェクトは、実行に誤ったデータを渡す代わりに、はっきりと失敗します。
- **サイズ。** 1回のアップロードは、S3ではマルチパート転送、Azureではブロック単位で送られるので、リクエストあたり5 GiBという通常の制限は適用されません。
- **ブロブの整理。** 1時間に1回、どの行からも指されていないブロブを取り除く処理が走ります。データベースに入れるには大きすぎてファイルとして保存されたステップ出力と、アイテムが運ぶ添付ファイルです。ステップ実行、部分出力、保存済みの応答、ワークフローのどれかが、直接または添付ファイルを保持する保存済み出力を通じて、そのブロブをまだ指している間は保持されるので、出力が同じ2つの実行が共有するファイルは、最後の1つがなくなるまで残ります。最後に書き込まれてから24時間を超えたブロブだけが対象で、すでに保存されているバイトをもう一度置くことは、最初の1時間が過ぎたあとは書き直したものとして扱われるので、ステップが保存したばかりでまだ記録していないファイルが取り除かれることはありません。保存済みの出力を読めなかった処理は、何も取り除きません。取り除いたファイル数とバイト数を記した`blobs.collected`の行を1つ監査ログに書きます。この処理は、ブロブストアが1つのインスタンスのもの(1つのインストールのworkerとmainが共有するもの)だと仮定します。同じバケットやフォルダーを指す2つのインストールは互いのファイルを取り除いてしまうので、それぞれに別のものを与えてください(`HOTLOOP_CASCADE_BLOB_S3_PREFIX`はそのためにあります)。
- **あとからストアを変更する。** 既存のブロブは書き込まれた場所に残ります。切り替える前に新しいストアへ移してください。新しいストアにないブロブへの参照は、ファイルが見つからないことになるからです。

この2つのバックエンドは、ディスクストアと同じ適合性テストスイートで、テストスタック内のGarageとAzuriteを相手に試験しています。書き込みと読み取り、空のブロブ、並行時の重複排除、破損、制限、不正なID、削除、一覧、キャンセルされた書き込み、ヒープ検査付きの192 MiBのストリーミングアップロードが含まれます。

利用者にとっての意味: 再構築または交換したmainは、実行が運んでいたすべてのファイルを、コピーなしで見つけられます。
