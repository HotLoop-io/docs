どの機器も `:stable` に従い、Podman が更新します。これは4製品すべてに共通のルールで、ここにあるユニットがどれもリリース番号を固定していないのはそのためです。`4.17.0` に固定された機器は、誰かがインストールした日のまま古くなり、タグを1つ変えるためにわざわざ現場へ戻る人はいません。リリースタグはすべて `:stable` を動かし、ユニットがそれに従わないリリースは受け付けられません。

タイマーは機器ごとに一度だけ有効にします。

```sh
sudo systemctl enable --now podman-auto-update.timer
```

## 更新が行うこと

タイマーが作動すると Podman は `:stable` を取得し、ダイジェストが変わっていれば新しいイメージでアプリのユニットを再起動します。再起動するのはアプリのユニットだけで、データベースのコンテナには触れないため、更新でヒストリアンが止まることはありません。ユニットにはシェルを必要としないヘルスチェックがあります（イメージにシェルはありません）。`hotloop healthcheck` がアプリ自身の `/readyz` に問い合わせ、これはデータベースが応答している間だけ応答します。ユニットはチェックに通るまで「activating」のままなので、Podman は無事に立ち上がった更新とそうでない更新を見分けられ、新しいイメージが立ち上がらなければ前のイメージを `:stable` に戻して起動します。

新しいイメージを起動すると、まず既存のデータベースに対してマイグレーションが実行され、大きなデータベースでは時間がかかります。ユニットは更新を失敗とみなす前にアプリへ15分の猶予を与え、最初の5分間の失敗はマイグレーションが失敗ではないため数えません。

2点は読んだのではなく実際に動かして見つけたもので、ユニットにはそれぞれの修正が入っています。単純な `HealthCmd` の文字列は `/bin/sh -c` を通して実行されますが、イメージにはシェルがないため、チェックは決して通りませんでした。そのため JSON 配列で指定します。また、古い Quadlet は `Notify=healthy` を単なる `true` として読み、`--sdnotify=conmon` を渡します。これはコンテナが起動した瞬間にアプリを稼働とみなす指定で、起動できない更新が成功と報告され、何もロールバックされませんでした。ユニットは `--sdnotify=healthy` を自分で指定します。

## ポッドを使わない理由

以前はアプリとデータベースが1つのポッドを共有していました。そのせいでロールバックができず、これもマニュアルを読んだのではなく実際に動かして分かりました。ポッド内のコンテナに対する Podman の自動更新は**ポッドの**ユニットを再起動しますが、ポッドのユニットは中のアプリにどんな問題があっても正常に立ち上がります。起動できないリリースが `UPDATED true` と報告され、アプリはそのリリースでクラッシュを繰り返し（最初の数分で20回の再起動）、機器の `:stable` は壊れたイメージになりました。アプリを更新するたびにデータベースも再起動していました。代わりにネットワークを使うと、アプリは独立したユニットになり、Podman はそれを再起動し、アプリが `/readyz` に応答するまでユニットは「activating」のままです。同じリリースが `UPDATED rolled back` で戻ってきました。

## ロールバックで戻せないもの

マイグレーションです。リリースがデータベースをマイグレーションしたあとヘルスチェックに失敗すると、Podman は前のリリースを戻し、前のリリースは失敗したリリースが残したスキーマの上で起動します。これは安全で、3つの方法で安全に保たれています（詳細は[マイグレーションは追加のみ](/ja/iot/migrations/)）。

- **マイグレーションは追加のみです。** テーブル、デフォルト値付きの列、インデックスです。削除、名前変更、型変更は行わないため、前のリリースは知っているものがすべて元の場所にあり、追加されたものは見ません。
- **アプリは信頼できないスキーマを拒否します。** データベースは、各マイグレーションをどのリリースが適用したかを記録します。1つ前に戻ったリリースは起動し、ログにそう記録します。2リリース以上前のものは起動せず、両方のバージョンを挙げて理由を示します。機器が更新に失敗してロールバックし、さらに別の更新に失敗して、データベースがすでに2回進んでいる場合がこれにあたります。アプリは `journalctl -u hotloop` のメッセージとともにすぐ終了し、ユニットの `Restart=always` が再試行を続けては拒否され続けます。解決するのはスキーマを知っているリリース、つまり `:stable` である最新のリリースです（`sudo podman auto-update`、またはイメージを取得して再起動）。あるいは、いま動いているリリースで取ったバックアップを復元します（[バックアップと復元](/ja/iot/backup/)）。

このため、ロールバックにリリースノート上の但し書きはもうありません。それでも戻せないのはデータです。失敗したリリースが、古いリリースの無視する行を書き込んでいる可能性があります。更新を有効にする前にバックアップを取ってください。不具合のあるリリースと復元の間にある唯一の備えです。

## データベースが `:stable` に従わない理由

アプリには自動更新のラベルが付いています。データベースのコンテナには付いておらず、その `Image=` は正確なタグです。アプリの更新は元に戻せますが、データベースの更新は戻せないからです。

- **PostgreSQL のメジャーバージョン**（16から17）は再起動ではありません。PostgreSQL のバージョニングポリシーによると、データディレクトリはメジャーバージョン間で後方互換を保てず、ダンプと再読み込み、または `pg_upgrade` が必要です（[postgresql.org/support/versioning](https://www.postgresql.org/support/versioning/)）。メジャーをまたいで動くタグなら、無関係な再起動のときに工場のヒストリアンでそれが起きてしまいます。メジャーを固定するのは最低限のことで、上のルールが言う「エンドポイントの固定」ではありません。HotLoop が行った唯一の移行である16から17は `hotloop-db-upgrade.container` で、新しいユニットをコピーするときに意図して実行します。
- **マイナーリリース**（16.14から16.15）にはダンプと復元は不要です。同じページには、一部は「追加の手順が必要な場合があるため、必ず先にリリースノートを読むこと」とも書かれています。無人の機器はリリースノートを読みません。
- **TimescaleDB**（Gateway と Edge）はもう半分です。アプリは新しいイメージの起動時に `ALTER EXTENSION timescaledb UPDATE` を自分で実行し、拡張の更新はデータベースへの一方向の変更なので、あとで古いイメージを戻しても元には戻りません。Timescale のタグが浮動していると、アプリの元に戻せる更新が、戻せない更新を引きずることになります。
- 起動して動いている新しいデータベースイメージが、健全なイメージとは限りません。ヘルスチェックが見分けられるのは、起動しないコンテナと起動するコンテナの違いだけです。ヒストリアンがエンジンのアップグレードを無事に越えたかどうかは、`pg_isready` では分かりません。

そのため、データベースのタグは、それに対してテストされた HotLoop リリースとともに動きます。`release_guard.sh` は各 `hotloop-db.container` をチャートのデータベースと同じに保つので、同じ製品の Quadlet 機器とチャートのインストールは同じものを実行し、そこへの `AutoUpdate=` は拒否します。その代償として、PostgreSQL 自体のパッチリリースは、リリースに含まれて届くか、タグを手で変えたときに機器へ届きます。同じメジャーの範囲では、リリースノートを読みバックアップを取ったうえで、`hotloop-db.container` を編集し、`daemon-reload` を実行して、ポッドを再起動します。メジャーバージョンの変更は `pg_upgrade` で、HotLoop は16から17について実行し、それ以外は自分で実行するか、その中へ復元します。

## 承認するまで更新を止める

既定では保留はなく、タイマーが作動すると更新されます。人が判断したいサイトには2つの方法があり、どちらもアプリに接続できる必要はありません。

- **保留。** `podman-auto-update.timer` をオフのままにします。何も更新されません。準備ができたら `sudo podman auto-update` を実行します。これが承認で、同じヘルスチェックと同じロールバックが働きます。Podman は実行時に、これらだけでなくマシン上のラベル付きコンテナすべてを更新し、1つを除外するよう指示することもできないため、他のコンテナのためにタイマーを動かす必要がある機器では、これらだけを保留にはできません。
- **時間帯。** `update-window.conf` はタイマー用のドロップインで、既定の毎日深夜ではなく、たとえば日曜の 03:00 のように、いつ作動できるかを指定します。

  ```sh
  sudo mkdir -p /etc/systemd/system/podman-auto-update.timer.d
  sudo cp update-window.conf /etc/systemd/system/podman-auto-update.timer.d/
  sudo systemctl daemon-reload && sudo systemctl restart podman-auto-update.timer
  ```

Edge Relay は1点だけ異なります。リレーは転送先の Gateway からのコマンドをすでに待ち受けているため、Gateway はフリート画面からリレーの更新を承認できます。IoT、Edge、Gateway にはそのようなチャネルがなく、作ると、`sudo podman auto-update` がすでに果たしている機能のために、Web UI に「この機器を再起動」ボタンを置くことになります。リレーの保留については [Edge Relay リファレンス](/ja/edge-relay/reference/#relay-の更新)と `edge-relay-hold.conf` を参照してください。

## Gateway から見えるもの

3製品のどれでも `GET /api/status` は `version` を返し、ユニットが通知した場合は `imageDigest` も返します（起動のたびに先に通知します）。Edge 公開が有効な Edge や Gateway はリレーと同じ Sparkplug ノードで、同じ2つの値をすべての birth に入れるため、それをフリート一覧に持つ Gateway は、バージョンとダイジェストを表示し、自動更新で動いたときはその変化を記録します（[フリート管理](/ja/gateway/fleet/)）。IoT には上流がないため、ダイジェストは自身の `/api/status` にだけあります。

## Helm の場合

ポッドは自分自身を置き換えられないため、チャートには無人の更新がありません。`helm upgrade` が更新で、チャートの `image.tag` は既定でリリースである `appVersion` になります。
