画面インポートが CODESYS から TwinCAT に広がります。`.TcVIS` ファイル、そして cds-text-sync と codescribe のエクスポートが、ボタン、フレーム、ランプとともに HotLoop の画面として取り込まれ、取り込めなかったものは、何かを保存する前にそのテキストとともに一覧されます。

## 変更点

- **TwinCAT の画面をインポートします。** TwinCAT の `.TcVIS` ファイルは IDE のアーカイブ XML にある同じビジュアライゼーションなので、CODESYS コンバーターを通ります。実際の TwinCAT PackML のサンプル(画面 3 つ、MIT、ライセンスを隣に保持)で確認しました。60 個の要素がマップされ、マップされなかったものはありません。[Import a CODESYS screen](/ja/iot/codesys-screen-import/)をご覧ください。
- **ボタン。** ボタンの入力アクションにあるすべての単純な代入(`X := 5`、`X := TRUE`、列挙型のメンバー)は、その値を書き込むボタンカードになり、キャプションがラベルになります。設定済みの Toggle 入力は、オンのボタンとオフのボタンになります。代入以上のコード(条件、呼び出し、算術)は、そのテキストとともに報告されます。OMAC PackML の列挙型は既知で、そのほかのものはインポートの `enums` に入れ、既知の番号がないメンバーは名前で書き込まれ、その旨が示されます。
- **式によるランプの表示と非表示。** ランプの変数や非表示の変数は、1 つのタグと、数値、TRUE、FALSE、列挙型メンバーとの比較にでき、NOT、AND、OR と括弧で結べます。2 つのタグの比較、算術、呼び出しは引き継げず、報告されます。
- **フレーム。** フレームは別のビジュアライゼーションを表示します。プロジェクトのほかのファイルを最初のファイルと一緒に送ると(`codesysRelated`。ダイアログで複数のファイルを選ぶと、最初のものが画面です)、フレームのビジュアライゼーションがフレームの中に配置され、各入力はフレームに渡された変数にバインドされます。
- **シンボルのルールを組み合わせられます。** `show` や `colors` のルールは `{"all": [...]}` や `{"any": [...]}` にでき、PLC の AND と OR で、深さ 3 段、8 要素までです。タグを失うと `all` は成り立たず、`any` はほかのものを通して成り立ちます。ランプは、タグの代わりに `lit` ルールを持てます。[ダッシュボード](/ja/iot/dashboards/)をご覧ください。
- **テスト。** エネルギーメーターのテストは、メーターが数えた量を、固定の 10 秒ではなく実際に経過した時間で制限します。

## マイグレーション

ありません。

## API の変更

`POST /api/dashboards/import` は、`codesys` に加えて `codesysRelated` と `enums` を受け付けます。ルートは変わっていません。[HTTP API](/ja/iot/api/)をご覧ください。

## 4.23.3 からのアップグレード

通常の `helm upgrade` です。マイグレーションも新しい secret もありません。

## 検証していないこと

- インポーターは、TwinCAT PackML のサンプルと、cds-text-sync と codescribe のサンプルエクスポートに対して検証したもので、顧客自身のプロジェクトでは検証していません。ビジュアライゼーション言語をより多く使うプロジェクトでは、配置できなかったものがより多く一覧されます。
- 式は、1 つのタグと定数の比較を NOT、AND、OR で結んだものです。ほかのものは推測せず、報告します。
