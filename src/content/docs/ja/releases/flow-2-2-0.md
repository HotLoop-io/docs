HotLoop Flow 2.2.0 は、Flow が PLC と話し、再起動しても知っていたことを覚えていて、メッセージがどこを通ったかを見せてくれるリリースです。HotLoop の Business Source License のもとで出る最初のリリースでもあり、ここが読んでいただきたい部分なので最初に書いています。

## 新機能

**トレースとリプレイ**
- すべてのメッセージに上限付きのトレースが付きます。デバッグメッセージをクリックすると、エディタがそのメッセージの通った経路を光らせ、分岐、結合、サブフローをまたいで各ホップの時間とペイロードを表示します。
- トレースはフローのテストになるほか、下書きに再生できるので、問題を起こしたメッセージで修正を試せます。
- すべてのホップをスパンとして OpenTelemetry コレクターに送れます(`trace.otlp.endpoint`)。

**再起動をまたいで残る状態**
- フロー、グローバル、ノードのコンテキストは、データボリューム上の SQLite ファイル `state.db` に保存されます。再起動しても消えなくなりました。
- 耐久ワイヤー。ワイヤーを耐久に設定すると、反対側のノードが追いついている間は通常のワイヤーで、何も書き込みません。そのノードがメッセージを受け取れなくなると、ワイヤーは同じファイルへ順番に退避し、宛先が戻ると流し出します。実際の InfluxDB を 10 分間止め、障害の最中と流し出しの最中にランタイムを `kill -9` で落として確かめました。欠落も重複もありませんでした。

**プラントのノード**
- Modbus TCP の読み書き、OPC UA の読み取り、書き込み、サブスクライブ、S7 の読み書き、EtherNet/IP の読み書き、そしてエッジノードとホストとしての Sparkplug B。Flow は `scan` が見つけたものと話せるようになりました。
- Sparkplug は、仕様が求める誕生、ウィル、`bdSeq`、再誕生の要求、コマンドを行います。独立した Sparkplug 実装を相手に、エッジノードとホストの両方向で確認しました。
- 応答しない機器は、タイムアウト内にリクエストを失敗させ、次のメッセージで再接続します。OPC UA のサブスクリプションは切断に気づくと一度だけ知らせ、自分で復帰します。

**エディタ**
- コピーと貼り付け、選択範囲のインポートとエクスポート、独自のキャンバスを持つサブフロー、入れ子のグループ、全フローを横断する検索、デバッグフィルタ、Alt+クリックでのワイヤー削除。ブラウザのテストが、ランタイムが返す一覧のすべてのノードダイアログを順に開くので、新しいノードは出荷の日からカバーされます。
- ワイヤーをノードへドラッグする操作は、Chromium では一度も動きませんでした。今は動きます。

**チェック**
- 設定ノードがファイルにないノード(サブフローがまだ名指ししている削除済みのブローカー、またはタブや種類の違う設定ノードへの参照)は、インポート時、読み込み時、デプロイ時に報告され、起動しません。以前は黙って動かないままでした。
- フローやノードを削除すると、それを指していた Catch、Status、Complete の範囲から ID が外れます。

## 変更点

- コンテキストは既定で保持されます。`store.context.persist` がオンなので、再起動の前に設定した値は後にも残ります。以前は再起動のたびに空から始まっていました。起動時にコンテキストが空であることを当てにしていたフローは、空であってほしいものを自分で消す必要があります。以前の動作にするには `persist` を `false` にします。
- トレースは既定でオンで、あらゆる面に上限があります。256 の経路、各 512 ホップ、合計 16 MiB、1 秒あたり 1000 の新しい経路。メモリ上だけなので、再起動で一覧は最初からになります。`trace.enabled: false` でオフにできます。
- gos7 は S7 のタイムアウトのたびに Go のグローバルロガーに生の行を出力し、ノード側からそれを止める手段はありませんでした。
- 耐久キューは、メッセージがディスクに書かれた後で待機中と数えます。前ではありません。
- イメージは Docker ではなく Podman でビルドしてプッシュします。同じイメージ、同じタグ(`2.2.0`、`2.2`、`2`)、引き続き linux/amd64 と linux/arm64 です。

## アップグレードの注意

2.1.0 からはイメージを替えるだけです(`helm upgrade`、または Quadlet ユニットの新しいタグ)。移行もフラグも要りません。2.1.0 で動いていた `flows.json` と設定ファイルは 2.2.0 でも動き、フローファイルのバイト単位の往復は手つかずです。

- 初回起動で、ボリューム上の `data.dir` に `state.db` が作られます。チャートで `persistence.enabled` が false の場合、コンテナの再起動には耐えますが、Pod の置き換えには耐えません。
- 2.1.0 に戻しても `state.db` はそのまま残ります。2.1.0 にはそれを読むコードがありません。
- `state.db` への書き込みはすべて SD カードや SSD への書き込みなので、既定値はまとめて書きます。コンテキストの変更は `flushInterval`(30 秒)待ってまとめて書かれ、すでに同じ値への設定は何も書きません。`kill -9` ではその分を失うことがあります。`docs/durable/README.md` に数値とカードへの負担があります。

## 新しい設定

| YAML | 環境変数 | 既定値 |
|---|---|---|
| `store.path` | `HOTLOOP_FLOW_STORE_PATH` | 空。`data.dir` 内の `state.db` を意味します |
| `store.synchronous` | `HOTLOOP_FLOW_STORE_SYNCHRONOUS` | `normal`。`full` はコミットごとに fsync し、その分カードを消耗させます。 |
| `store.context.persist` | `HOTLOOP_FLOW_CONTEXT_PERSIST` | `true` |
| `store.context.flushInterval` | `HOTLOOP_FLOW_CONTEXT_FLUSH_INTERVAL` | `30s`。`0s` はフローが進む前にすべての変更を書き込みます。 |
| `store.durable.maxBytes` | `HOTLOOP_FLOW_DURABLE_MAX_BYTES` | すべての耐久ワイヤーの合計で 256 MiB |
| `store.durable.ackFlush` | `HOTLOOP_FLOW_DURABLE_ACK_FLUSH` | `100ms`。`0s` は次を送る前に各メッセージに印を付けます。 |
| `trace.enabled`, `trace.traces`, `trace.maxHops`, `trace.maxMessageBytes`, `trace.maxBytes`, `trace.perSecond` | | `true`, 256, 512, 16384, 16 MiB, 1000。`perSecond: 0` はすべてのメッセージをトレースします。 |
| `trace.otlp.endpoint`, `trace.otlp.serviceName`, `trace.otlp.interval` | `HOTLOOP_FLOW_TRACE_OTLP_ENDPOINT` | 空(エクスポートなし), `hotloop-flow`, `2s` |
| `trace.otlp.headersSecret`(チャート) | `HOTLOOP_FLOW_TRACE_OTLP_HEADERS` | なし。カンマで区切った `Name=value` の組を持つ Secret のキーで、ホスト型コレクターの API キー用です。 |

チャートには、これらすべてが `values.yaml` の `store` と `trace` の下にあります。
