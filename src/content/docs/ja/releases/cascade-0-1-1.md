## 概要

0.1.1 は候補版ではない最初のリリースです。0.1.0 のタグは存在しましたが、何も公開されませんでした。レジストリに何かが届く前にキャンセルされたためです。タグは動かないので、これは同じコードを公開したものです。

その正体は、プラントの現場に欲しかったワークフローエンジンです。静的な Go バイナリが 1 つ。1 台なら SQLite、もっと必要ならワーカー付きの Postgres。エディターはバイナリに組み込まれているので、ほかに動かすものはありません。

## 含まれるもの

すべてのステップをチェックポイントとして保存するエンジンなので、実行の途中で `kill -9` しても止まった場所から再開します。永続的な待機、リトライ、エラーポート、エラーワークフロー。式と、独自のプロセス内で JavaScript を隔離して実行する Code ステップ。

永続的な受信箱を持つ Webhook、メインノードがいくつ監視していても各スロットでちょうど 1 回だけ起動するスケジュール、MQTT、ディレクトリに届いたファイル用のトリガー。API を持つものすべてに使える HTTP ステップと、HotLoop、Postgres、EmberOps、メール、ntfy、Gotify、Discord 用のコネクター。それ以外は、あえて入れていません。

キーローテーションに対応した認証情報の保管庫、プラントに必要なあらゆる種類の OAuth2、パスワード、TOTP、パスキー、または OpenID Connect プロバイダーでのサインイン、必須の MFA、プロジェクトとロール、検証できる監査ログ、保存のたびに残るバージョン、スコープ付き API と OpenAPI ドキュメント。メトリクス、トレース、プローブを備え、私以外の誰でも止まっているときに分かります。

## 動かし方

イメージは amd64 と arm64 です。動かないデプロイが必要なら、上のダイジェストで取得してください。

k3s では Helm チャートを使います。単体でも、サーバーとワーカーに分けても使えます。

通常のマシンでは、`deploy/quadlet` の Quadlet ユニットを使います。1 台なら SQLite、ワーカーを増やすなら Postgres です。ユニットは `:stable` に追従し、Podman の自動更新タイマーが進めます。正常に起動しない更新は、動いていたイメージに戻ります。両方の構成を実際に動かして確認しました。systemd 上の Podman 5.8.7 で、起動は正常になるまで待ち、停止したコンテナは戻り、正しい更新は適用され、不正な更新はロールバックされ、そのたびにワークフローが実行されます。

## 知っておくこと

マイグレーションは前にしか進みません。ロールバックは古いイメージを戻すだけで、データベースのマイグレーションは元に戻りません。更新を有効にする前にバックアップを取ってください。

このリリースではレジストリが非公開だったため、最初に root で `podman login ghcr.io` が必要でした。イメージとチャートは 0.1.2 から公開されており、ログインなしで取得できます。

保存された認証情報を暗号化するキーを失うと、保存済みの認証情報はすべて読めなくなります。コピーはマシン以外の場所に保管してください。
