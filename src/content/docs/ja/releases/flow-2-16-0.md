HotLoop Flow 2.16.0 は、1 つのフローファイル、つまり 1 組の FlowLab ダイアグラムを、テナントが EmberNet で動かしているすべての Flow に押し込み、それぞれの後に確認を行い、失敗したものを元に戻せるようにします。また、2 つのインストールが 1 つの仕事を共有できるようにし、リースによって、一度に装置へ書き込むのはそのうち 1 つだけであることを保証します。amd64 が先で、arm64 は 2.16.1 で続きます。

## 新機能

- **テナントのステーションへのプッシュ(#201)。** `hotloop-flow stations list -tenant ID` と `hotloop-flow stations push -tenant ID -file flows.json` は、EmberNet がそのテナントで稼働中と示す各 Flow に、1 つずつフローファイルを置きます。ステーションは EmberNet ダッシュボードから取得し、手で入力することはなく、ほかのテナントの行は破棄されます。各デプロイの後、ステーションは、全ステーションが持つべきリビジョンで応答し、起動に失敗したノードがなく、ファイル内の自動起動するすべてのダイアグラムが存在して実行中または完了している必要があります。失敗したステーションは元のデプロイに戻され、プッシュは止まります。レポートには、完了、失敗、スキップ、一度も開始されなかったステーションが示されます。実行中のロガーを再起動してしまうプッシュは、オペレーターがプロンプトではいと答えるか、`-confirm-restart` を渡すか、今を含む `-window` を与えるまで、何も変更しません。説明は `docs/stations.md` にあります。
- **API と MCP を通した同じプッシュ(#201)。** `GET /stations` と `POST /stations/push`、そして MCP ツール `list_stations` と `push_to_stations` で、ツールは 43 になります。ステーションの 4 つの設定が指定されている場合にだけ存在します。
- **フェンシングリースを持つウォームスタンバイ(#204)。** 2 つの Flow インストールが 1 つの仕事を共有できます。PostgreSQL の 1 行がリースと、保持者が変わるたびに増える番号を持ちます。保持者は、装置への書き込みの直前ごとにリースを確認します。対象は、Modbus、S7、OPC UA、EtherNet/IP の書き込みノード、HotLoop のスクリプトとレシピのノード、そして HotLoop、計測器、シリアルポートへの FlowLab ダイアグラムの書き込みです。スタンバイ、またはリースを失った保持者は、何かが送られる前に、数えられるエラーで書き込みを拒否され、スタンバイは、稼働側のリースが切れた後にリースを引き継ぎます。`GET /failover` と MCP ツール `get_failover`(ツールは 44 になります)は、このインストールが稼働中、スタンバイ、喪失のどれか、誰がリースを持っているか、いくつの書き込みが保留されたかを示します。エディタはスタンバイ側にバナーを 13 言語で表示し、説明は `docs/failover.md` にあります。
- **そのためのチャート値と Quadlet の行(#204)。** チャートの `failover.urlSecret`、`failover.name`、`failover.ttl`、`failover.renewEvery`、`failover.writeMargin` があり、PostgreSQL の URL を持つ Secret はファイルとしてマウントされます。Quadlet ユニット用の環境変数と Podman のシークレットは `docs/deploying.md` にあります。
- **チャートの値と Quadlet の行(#202)。** チャートの `stations.dashboardUrl`、`stations.tenant`、`stations.dashboardTokenSecret`、`stations.deployTokenSecret` があり、2 つの Secret はファイルとしてマウントされます。Quadlet ユニット用の 4 つの環境変数と 2 つのマウントされたシークレットは `docs/deploying.md` にあります。

## 変更点

- 書き込みマージンがリースと同じ長さの場合のように、更新の合間に稼働側がリース切れになりかねないフェイルオーバーの設定では、起動が拒否されます。
- 4 つのステーション設定のうち一部だけを設定した起動は拒否され、一部だけを設定したチャートのレンダリングも拒否されます。4 つすべて設定するか、すべて空にします。
- ステーションにプッシュするトークンには、`flows.read` と `flows.write` に加えて `status.read` が必要です。各デプロイ後の確認がステーションのダイアグラムを読むためです。`hotloop-flow token` がこれを表示するようになり、README とステーションのページにも書かれています。通常のデプロイ用トークンは、`deploy` についてはこれまでどおり使えます。
- フローのセットを保存した後に持つリビジョンを、保存の前に知れるようになりました。保存も使う 1 つの関数から得ます。リビジョンについて変わったことはありません。
- ドキュメントは、`mcp-server` と書いていたところを `hotloop-flow-mcp-server` と書くようになりました(#197、#199、#200)。
- 静的バイナリは 51,859,618 バイト(49 MiB)で、`ci.yml` の 50 MiB の予算内に収まっています。

## 新しい設定

設定ファイルの `stations.dashboardUrl`、`stations.tenant`、`stations.dashboardTokenFile`、`stations.deployTokenFile`、または `HOTLOOP_FLOW_STATIONS_DASHBOARD_URL`、`HOTLOOP_FLOW_STATIONS_TENANT`、`HOTLOOP_FLOW_STATIONS_DASHBOARD_TOKEN_FILE`、`HOTLOOP_FLOW_STATIONS_DEPLOY_TOKEN_FILE`。すべて既定では空で、その場合この機能はオフです。チャートでは上の `stations.*` の値です。

設定ファイルの `failover.urlFile`、`failover.name`、`failover.holder`、`failover.ttl`、`failover.renewEvery`、`failover.writeMargin`、または `HOTLOOP_FLOW_FAILOVER_URL_FILE`、`HOTLOOP_FLOW_FAILOVER_NAME`、`HOTLOOP_FLOW_FAILOVER_HOLDER`、`HOTLOOP_FLOW_FAILOVER_TTL`、`HOTLOOP_FLOW_FAILOVER_RENEW_EVERY`、`HOTLOOP_FLOW_FAILOVER_WRITE_MARGIN`。名前の既定値は `flow`、保持者はホスト名、ttl は 15 秒、更新はその 3 分の 1、書き込みマージンは 5 秒です。URL ファイルがなければこの機能はオフで、すべての書き込みはこれまでどおり出ていきます。チャートでは上の `failover.*` の値です。

## アップグレード

2.16.0 のイメージとチャートへの単純な `helm upgrade`、または Quadlet ユニットの新しいタグです。初回起動で起きることはなく、移行も不要です。フローファイルは以前どおりバイト単位で読み込み、保存されます。このリリースは amd64 のみです。arm64 のマシンは 2.16.1 まで 2.15.1 のままで、2.16.1 は arm64 イメージを加えた同じコードです。

イメージ: `ghcr.io/hotloop-io/hotloop-flow:2.16.0`、まずlinux/amd64で、arm64は2.16.1で続きます。チャート: `https://hotloop.io/hotloop-flow/`。このタグのREADMEに残りが写真つきであります: https://github.com/HotLoop-io/hotloop-flow/blob/v2.16.0/README.md
