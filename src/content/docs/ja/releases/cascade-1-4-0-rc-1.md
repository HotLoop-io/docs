これは 1.4.0 のリリース候補です。`stable`、`latest`、`1.4`、`1` のタグは動かさず、App Store のインデックスにもないので、既定では何もこれを取得しません。1.4.0 が出荷するコードで、本物のタグの前に実際の Podman ホストで取得して実行しました。1.4.0 は、バージョン文字列だけを変えたこのコードになります。中身は 1.4.0 のノートをご覧ください。

## 概要

1.4.0 は、Cascade のインストールを長く運用しやすくします。サーバーはクラッシュせずにデータベースを待ち、完了した実行は指定した日数だけ保持してファイルごと整理でき、所有者は 1 つの API キーの呼び出し頻度に上限を設けられ、インスタンス全体のバックアップと復元ができます。ロードマップに残っていた規模のテストも 1 つ片付けます。エンジン、ワークフローのファイル形式、REST API、MCP サーバー(83 ツール)、14 言語は 1.3.0 と同じです。

## データベースを待つ

分割インストール(PostgreSQL 上のサーバー、ワーカー、Webhook の各ポッド)では、データベース名が解決される前にポッドが起動し、準備ができるまでに 2、3 回再起動していました。1.2.1 と 1.3.0 も同じでした。データベースに届かないサーバー、ワーカー、Webhook は、ログに「waiting for the database」と待った時間を出し、最大 5 分間リトライして、データベースが応答したら接続します。パスワードの誤り、不正な形式のアドレス、存在しないデータベースは、待っても直らないため、これまでどおりすぐに停止します。チャートの起動プローブはプログラムと同じだけ待ちます。実際の k3s でのまっさらな分割インストールは、チャートテストの 3 回の実行すべてで再起動がありませんでした。

## 完了した実行の保持

設定に、完了した実行の保持日数という新しいフィールドが加わり、`PATCH /api/v1/settings` は `retentionDays` を受け取ります。初期値はオフ(0)で、すべての実行はこれまでどおり保持されます。数値を設定すると、1 時間に 1 回、メインノードが、それより前に終わった成功、失敗、キャンセルの実行を、ステップのデータごと削除します。まだ実行中のものや、親が実行中のものには触れません。各バッチは監査ログに `execution.pruned` を書き、設定を変更すると `instance.retention` を書きます。

同じ 1 時間ごとの処理が、保持の設定にかかわらず Blob ストアも整理するようになりました。データベースに入れるには大きすぎる出力と、どの実行からも参照されなくなった添付ファイルです。2 つの実行が共有するファイルは最後の実行がなくなるまで残り、24 時間以上前に書かれたファイルだけが対象なので、ステップが保存したばかりのファイルが消えることはありません。手動で削除した実行にも新たに適用されます。以前は、削除した実行の大きな出力がディスクに残り続けていました。必要なものを読み取れなかった処理は何も削除せず、各処理は監査ログに `blobs.collected` を書きます。

## API キーごとの上限

設定に、キーごとの 1 分あたり API リクエスト数という新しいフィールドが加わり、`PATCH /api/v1/settings` は `apiRateLimit` を受け取ります。初期値はオフです。数値を設定すると、各 API キーと、キーで MCP にサインインした各エージェントは、1 分間にその回数までリクエストできます。上限を超えた呼び出しには `Retry-After` 付きの 429 が返ります。キーごとに別々のカウントがあり、エディターにサインインしている人には適用されません。カウントはプロセスごとなので、メインノードが 3 つなら、1 つのキーで最大 3 倍まで可能です。変更すると監査ログに `instance.api_rate_limit` を書きます。

## バックアップと復元

`hotloop-cascade backup DIR` は、サーバーの稼働中に取った SQLite データベースの一貫したコピー、保存済みの認証情報をすべて暗号化するキーファイル、Blob ファイル、そのハッシュを記した `manifest.json` を、新しいディレクトリに書き出します。`hotloop-cascade restore DIR` は、すべてのファイルをマニフェストと照合してから元に戻し、`--replace` を指定しない限り、データベースや別のキーの上書きを拒否します。PostgreSQL では、バックアップにキー、Blob、マニフェストが入り、データベース分のための `pg_dump` コマンドを表示します。復元は `pg_restore` のコマンドを表示します。S3 や Azure にある Blob はコピーされません。詳細は `docs/GOVERNANCE.md` にあります。

## 裏付けとなったテスト

- ロードマップが定めた規模のテストが完了しました。1 つの PostgreSQL 上の 2 つのメインノードで、毎分起動するワークフローを 1 時間実行し、その間に一方をスロットの境界で SIGKILL により止め、毎回約 25 秒停止させたまま、これを 7 回連続で行いました。61 の 1 分スロットに対して 61 回実行され、取りこぼしも二重実行もありませんでした。
- テストスタックの OAuth サーバー(Hydra)が Postgres 上で動くようになりました。以前は並列実行で失敗し、変更後は通り、変更を戻すと再び失敗しました。Cascade のコードはトークンの確認を行いません。
- チャートテストは、インストール時にポッドが再起動すると失敗するようになりました。
- 新しい設定の拒否メッセージ 2 つはすべての言語に翻訳され、設定のヘルプには大きな出力が実行とともに削除されると記されています。

## amd64 のみの理由

このリリースは amd64 のみをビルドします。マルチアーキテクチャは別の実行で出すため、この次のリリースは、両方をビルドする小さなバージョンアップになります。`stable`、`latest`、`1.4`、`1` は、すでに指していた arm64 イメージと並んで、新しい amd64 イメージを載せます。

## アップグレードと戻し方

マイグレーションはありません。スキーマは 1.3.0 のものです。1.4.0 に `helm upgrade` するか、`:stable` に Quadlet ユニットを進めさせてください。データベースには何も変わりがないので、1.3.1 に戻しても安全です。ロールバックで元に戻せないのは、削除です。保持の設定が削除した実行は戻らず、1 時間ごとの整理が取り除いた Blob も戻りません。保持はオンにするまでオフなので、先にバックアップを取ってください。Blob の整理は保持なしでも実行されます。
