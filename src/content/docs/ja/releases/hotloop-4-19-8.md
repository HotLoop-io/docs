4.19.4 のマルチアーキテクチャビルドである 4.19.5 より前に変わったことは、[4.19.4 のノート](/ja/releases/hotloop-4-19-4/)を読んでください。

このビルドは amd64 のみで、次のリリースは、2 回に分けて進める方式のとおり、arm イメージをビルドする小さなバージョンアップです。それまでの間、`stable` は持っている arm イメージをそのまま保ちます。

## 4.19.8 に含まれるそのほかの内容

- **Logbook の Older entries ボタンが、ライブ更新でページを失わなくなりました。** Logbook は、ライブフィードが新しいものがあると伝えるたびに最新のページを取得し直します。古いページが届く途中でログ行が着くと、その更新が走り、画面は古いページがリストの以前の取得に属するという理由でそれを捨て、ボタンは何もせずクリックが失われました。その瞬間にログ行を書いたプラントはすべて(その時間帯は古いリクエスト自身の所要時間です)、旧 UI でも新 UI でもこれに当たりました。更新は古いページが届くのを待ち、より古いものが来なかった場合にだけ、その後に実行されます。ブラウザーテストは古いリクエストをネットワーク上で保留し、ログ行が着いて画面が更新されるのを待ってからページを通し、リストに結合されることを求めます。4.19.7 の画面では失敗し、今回の画面では通ります。

- **タグを選ぶすべての場所がプラント全体を検索し、どこも数で切られません。** 3 台のデバイスに 2232 個のタグがあるテスト機(4.19.5)で、Tags 画面は最初のデバイスのものだけ 200 個を表示し、Trends のピッカーの選択肢は 201 個、デバイスの Details ドロワーはカードに 1105 個のタグとあるすぐ横で「No tags on this device」と表示し、最初の 200 個より先のタグを検索すると、`/api/tags?q=` は返しているのに「No tags match」と表示されました。4.19.6 のタグ一覧の変更(5000 までの limit と超過の拒否、offset、`X-Total-Count`、すべてのページを読むページ、件数付きのウィンドウ)がこれを直しており、今回のリリースに入っています。4.19.8 が加えるもの:ダッシュボードのカードエディターのタグフィールド(Gauge、Value、Trend、Map、Button の書き込み可能なタグ)は最初の 3000 個で切られた候補だったため、3000 個を超えるプラントでは、一度も候補に出ないタグがありました。今はテキストを入力するあいだにサーバーが行う検索です(最大 100 件、`GET /api/tags?q=&limit=100`、書き込みピッカー用の新しい `writable=true` フィルター)。タグが 3200 個あるデバイスのブラウザーテストは、Tags の検索ボックス、デバイスのドロワー、Pin a tag のピッカー、Trends のピッカー、カードエディターから、200 個より先のタグを旧 UI でも新 UI でも見つけます。

## 4.19.7 にも含まれるもの(引き継ぎ)

- **すべての HotLoop チャートは、ハードウェアアクセスがオンの状態で出荷されます。** `hardware:` ブロックに、既定でオンの 3 つのスイッチがあります。アプリのコンテナーは privileged かつ root で動き、ノードの `/dev` が `/dev` にマウントされ(USB の無線機とシリアルアダプター、あとから挿したものも含む)、ノードの `/run/dbus` がマウントされます(ノードの BlueZ 経由の Bluetooth)。pod は pod ネットワークのままです。App Store や helm による通常のインストールは、手作業の編集なしでノードに接続されたものを見られます。HotLoop にはまだ Bluetooth、Z-Wave、USB シリアルの独自コードはなく(Zigbee は MQTT 上の Zigbee2MQTT を通ります)、これはそのコードやサイドカーが必要とするアクセスです。代償があります。pod はノード上で root です(NetworkPolicy の既定はオンのままです)。`hardware.bluetooth.hostNetwork` は、ノードのネットワークを必要とするもの(生の Bluetooth ソケット、ノード自身のネットワーク上でのディスカバリー)のためのオプトインで、既定はオフです。オンにすると、ページはノードのすべてのアドレスの `service.targetPort` で応答し、ノードとポートごとに HotLoop は 1 つで、NetworkPolicy はその pod には適用されません。3 つのスイッチでどの部分もオフにでき、3 つすべてオフなら、レンダリングは 1 行ずつ 4.19.6 がレンダリングした pod と同じです。[DEPLOYMENT.md の Hardware](/ja/install/helm/#ハードウェア-usb-無線機シリアルアダプターbluetooth)をご覧ください。Edge Relay のチャートにも同じブロックがあります。
- **UniFi マップと Entities のストリップが「null」という単語を書かなくなりました。** 欠けた値を `append` や `replaceChildren` に渡したスクリプトが、それをテキストとして書いていました。UniFi マップの上に「null」が、ノードが選択されていないときは Entities のヘルスストリップにも 1 つ表示されました。修正済みで、ブラウザーテストはすべての画面で、null、undefined、NaN、[object Object] だけのテキストノードがあると失敗します。

## 変更点

- **Tags 画面とすべてのデバイスのドロワーが、すべてのデバイスのすべてのタグに届きます。** ページはサーバーに 2000 個のタグを求め、サーバーは 1000 を超える limit を黙って 200 に変えていました。3 台のデバイスと 2232 個のタグがあるプラントで、Tags 画面は最初のデバイスのものだけ 200 個を保持し、ほかのデバイスのドロワーは「TAGS 0」と「No tags on this device」と表示しました。`GET /api/tags` は `limit`(1 から 5000。それ以外は 5001 を含め `400` で、少ない結果で答えることはありません)と `offset` を受け付け、合計を `X-Total-Count` ヘッダーで返し、`device` と `q` を同時に受け付けるため、クライアントは最後までページを送り、それをやったと分かります。ページはすべてのページを読み、リストのウィンドウ(Tags で 500 個、ドロワーとピンのピッカーで 200 個)を描き、その下に総数と残りのためのボタンを表示します。同じ黙った上限が履歴の一覧(オートメーションの実行、アラームのイベント、書き込みの監査、スクリプトの実行、レシピの適用、レポートの実行)にもありました。上限を超える limit は黙って既定値になり、求めた数の 10 分の 1 でした。今は上限が適用されます。MCP の `list_tags` ツールにもあり、今は渡された limit をそのまま使います。
- **ライブフィードは、変わったものだけをページごとに圧縮して送ります。** ドライバーはポーリングのたびにすべてのタグを読み、フィードは変わったかどうかにかかわらず全部を 1 秒に 4 回送っていました。テスト機の 2232 個のタグで毎回約 150 KB です。85 KB/s の回線のページは、現在のメッセージの前にメッセージが並ぶため数分遅れました。`values` イベントは、最後に送ったものと値、テキスト、単位、品質、理由が違う読み取り値だけを運び、変わらないものは 30 秒後にもう一度送ることで、安定した値の経過時間が正直に保たれます。ブラウザーが受け付ければストリームは gzip です。テスト機の最初の画面は JSON で約 326 KB、回線上では約 11 KB です。各ページの読み取り値は、そのページ自身の書き込み側が送れるようになるまでタグごとに最新のものだけが保持され、書き込み側は直前の送信にかかった時間(最大 5 秒)だけ休むため、遅い回線のページはプラントより 1、2 回遅れるだけで、何も失わず、ほかのページから何も奪いません。300 KB/s で読む回線で、すべてのタグが 250 ms ごとに変化するとき、ページは 4.19.5 では 27.8 秒、4.19.6 では 3.7 秒遅れていました。
- **デバイスカードのポーリング回数と Board の数字が動きます。** ページが読み込まれたときの数字のままでした。ライブフィードには乗っておらず、その背後の更新(30 秒ごと)は何も再描画しませんでした。今は、ページが表示されている間 2 秒ごとに 1 リクエストずつ取得し、画面は数字をその場で書き換えるため、手元のボタンが置き換えられることはありません。デバイスのドロワーは同じ一覧からカウンターを読みます。

## フィードの読み方

`GET /api/stream` は、リクエストが `Accept-Encoding: gzip` と言うと `Content-Encoding: gzip` を送り、言わないスクリプトにはこれまでどおりプレーンテキストを返します。`values` イベントは引き続き `GET /api/values` の形の読み取り値の配列で、変わっていないものを繰り返さなくなっただけなので、スナップショットとイベントから自分の画面を組み立てるクライアントは、何も変える必要がありません。

## 既知の問題

- **ディスク不足でブローカーがすべての書き込みを拒否する Kafka や Redpanda の履歴ターゲットは、「records have timed out before they were able to be produced」と報告するだけで、理由は報告しません。** 読み取り値は失われません。ターゲットはバッチを保持し、1 秒から 30 秒へ延びる待機で再試行し、その区間を未送信として抱え、ブローカーが応答すると HotLoop 自身の履歴から追いつき、ステータスとシステムイベントはダウンと伝えます。Redpanda は、その下のディスクの空きが `storage_min_free_bytes`(既定 5 GiB)を下回ると書き込みを拒否し、それを自身のログ(「rejecting produce request: no disk space」)にしか書きません。この場合、クライアントライブラリは拒否のコードを HotLoop に渡さない(巻き戻し、producer epoch を上げ、再試行する)ため、このリリースでは理由を正直に示す方法がありませんでした。設計は bead bc49eb にあります。Redpanda のターゲットがこのメッセージでダウンしているときは、ブローカーのログとディスクを確認してください。
