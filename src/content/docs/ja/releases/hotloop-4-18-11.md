このリリースから HotLoop のデータベースは PostgreSQL 17 になり、PostgreSQL 16 のデータがあるすべてのインストールは、何も実行しなくても次のアップグレードで 17 に移ります。これが、稼働中のプラントに触れる前に 4.18.11 で読むべき唯一の点です。データベースエンジンの変更であり、ディスクが必要で、通常のロールバックではない戻り方が 1 つあるからです。

完全なノートは README にあります。4.18.11 の変更点をご覧ください。

## PostgreSQL 17 と、それに伴うアップグレード

- **何が変わったか。** チャートと Quadlet ユニットが動かすデータベースは PostgreSQL 17 です。Edge と Gateway にはその上に TimescaleDB 2.30.1 が、IoT と `database.type: postgresql` には素の PostgreSQL 17.11 が載ります。SQLite のインストールには PostgreSQL がなく、手を加えません。PostgreSQL は別のメジャーバージョンのデータディレクトリを開けないため、イメージを差し替えるだけでは既存のすべてのボックスが起動できないデータベースを抱えることになります。それを出荷するつもりはありませんでした。
- **初回起動で起きること。** 1 つのスクリプト `hotloop-pg-upgrade.sh` がデータベースより先に実行されます。チャートではデータベース pod の 2 つの init container です。古いイメージが PostgreSQL 16 のインストールを渡し、新しいイメージが `pg_upgrade` を実行します。Quadlet では、`hotloop-db.container` が要求する oneshot ユニット `hotloop-db-upgrade.container` です。古いディレクトリの隣の新しいディレクトリにコピーモードで作業し、新しいサーバーを一度起動して開けることを確かめてから、初めて名前を入れ替えます。新規インストールや、すでに 17 のボリュームでは何もしません。
- **待ち時間を見込んでください。** データベース pod は、データのコピーにかかる時間だけ `Init` にとどまり、アプリはそれを待ちます。ログは、チャートでは `kubectl logs <release>-postgresql-0 -c pg-upgrade`、Quadlet では `journalctl -u hotloop-db-upgrade` です。
- **空き容量。** データの隣にデータと同じくらいの空き容量が必要で、開始前に確認します。足りなければ、16 のデータを元のまま、データベースを起動せずに停止します。
- **`pgdata.pg16` は残され、消すかどうかはあなた次第です。** 古いディレクトリは `pgdata.pg16` に名前が変わってボリュームに残ります。アップグレード時点の PostgreSQL 16 データベース全体で、バックアップであり戻る道であり、データベースと同じ大きさです。あなたが削除するまで残ります。ボックスが望むだけ 17 で動いたら:

  ```sh
  # chart
  kubectl -n hotloop exec hotloop-postgresql-0 -c postgresql -- rm -rf /var/lib/postgresql/data/pgdata.pg16
  # Quadlet
  sudo rm -rf "$(sudo podman volume inspect hotloop-db --format '{{.Mountpoint}}')/pgdata.pg16"
  ```

- **失敗しても元の場所に留まります。** 入れ替えの前に何か失敗しても、16 のデータは手つかずで、データベースは作りかけのディレクトリでは起動しません。チャートでは pod が `Init:Error` のままになり、Quadlet ではアップグレードユニットが失敗して、その後ろのデータベースユニットは起動しません。ログが示す問題を直して、もう一度起動してください。
- **4.18.10 への `helm rollback` はそのデータベースを起動しません。** これが注意点です。ロールバックするとチャートのデータベースイメージが PostgreSQL 16 に戻り、16 は 17 のディレクトリを開けません。失われるものも中途半端に変わるものもなく、データベースが起動しないだけです。戻すには、[k3s と Helm のページ](/ja/install/helm/#元に戻す)の入れ替えを行います。データベースを止め、`pgdata` を `pgdata.pg17` に、`pgdata.pg16` を `pgdata` に移します。**これはアップグレード以降に 17 で行われたすべての書き込みを捨てます。** `pgdata.pg16` はその時点のデータベースだからです。可能なら前に進んでください。入れ替えて戻せるのは一度だけで、次のアップグレードは `pgdata.pg16` が残っている間は実行を拒否します。
- **Quadlet のボックスはこの影響を受けません。** Podman の auto-update が巻き戻すのはアプリだけでデータベースは巻き戻さず、マイグレーションは追加のみなので、4.18.10 のアプリは PostgreSQL 17 のデータベースを問題なく読めます。更新を巻き戻した Quadlet のボックスは動き続けます。
- **それでも先にバックアップを取ってください。** HotLoop 自身のバックアップは、動いているアプリが動いているデータベースを通して作るため、データベースが起動する前に走るステップでは取れません。アップグレード前に 4.18.10 で 1 つ取り、ボックスの外にコピーしてください。17 への復元は通常の復元です。
- **オフにする。** `database.postgresql.upgrade.enabled: false` は init container を外し、16 のままのボリュームではデータベースが起動しなくなります。オンのままにしてください。オンでも、init container のイメージは実行前に取得されるため、新規インストールはノードごとに一度 PostgreSQL 16 のイメージを取得します。

### API の変更

- **新しいルート:**`GET` と `PUT /api/notify/escalation`、そして `GET /manifest.webmanifest` と `GET /sw.js`。スマートフォンは誰かがサインインする前に要求するため、セッションは不要です。すべて docs/API.md にあります。
- **統合のルート:**`GET /api/integrations`(`devices.read`)、`POST /api/integrations/{id}/probe` と `/setup`(`devices.write`)。新しい権限はありません。
- **新しいプロトコルが 2 つ、** `snmp` と `bacnet` が `GET /api/protocols` と `no driver for protocol` エラーの一覧に加わります。HotLoop は 10 種類を話せるようになりました。
- **キオスクとロックアウトのルート:**`POST /api/auth/kiosk`(セッションなし)、`POST /api/auth/activity`、`PUT` と `DELETE /api/users/{username}/pin`、`DELETE /api/users/{username}/lockout` で、後者 2 つは `users.manage` の下にあります。`GET /api/users` は `hasPin` と `locked` を返し、コードは返しません。ログインルートはロックされたアカウントに `Retry-After` 付きの `429` を返します。キオスクセッションは `idleSec` を報告します。新しい設定は `ui.kioskIdleSeconds`、`ui.lockoutAttempts`、`ui.lockoutSeconds`、`ui.panelDelaySeconds` です。
- **新しい権限:**`notify.escalation`、管理者のみ。viewer と operator ロールには付与されていません。
- **アラームの履歴に新しいイベントタイプが 2 つ、** `escalated` と `escalation-ended` が加わり、`actor` は `escalation` になります。アラームの履歴を読んで従来の一覧を前提にしているスクリプトは、これらに出会います。
- `GET /api/stream` はセッションが終わると閉じ、履歴が返すすべての時刻は UTC です。どちらも「そのほかに含まれるもの」にあります。

### 4.18.10 からのアップグレード

- **チャート:**`helm upgrade <release> hotloop/hotloop --version 4.18.11 --reset-then-reuse-values`。`hotloop-edge` と `hotloop-iot` も同様です。データベース pod が、上で説明したとおり先にアップグレードを実行します。
- **Quadlet:**`deploy/quadlet/` の自分の製品のディレクトリから、新しい `hotloop-db.container`、`hotloop-db-upgrade.container`、`hotloop-db-upgrade.sh` をユニットディレクトリにコピーし、`systemctl daemon-reload` を実行して `hotloop-db.service` を再起動してください。データベースユニットはアップグレードユニットを要求するため、新しいデータベースユニットだけを取り込んだボックスは 16 のデータでは起動せず、その理由を表示します。PostgreSQL 16 のイメージは、ボリュームが必要とするときだけ取得されます。
- **新しいマイグレーションが 1 つ、`0025_kiosk_pin`。** PostgreSQL と SQLite 用です。追加するのは列だけ(PIN のハッシュ、セッションのアイドル上限、ロックアウトのカウンター)で、すべて既定値があるため、4.18.10 はこれが残すスキーマでも動きます。いつも通り先に `pg_dump` を取ってください。
- **Edge Relay:**データベースはなく、することもありません。すべての製品が歩調を合わせて出るため、4.18.11 で出ます。

### そのほかに含まれるもの

- **統合:アドレスがわかっているデバイスに HotLoop を向けます。** あらゆる種類のデバイスで同じ流れです。統合に必要なものを尋ね、答えをもとに実際のデバイスを見て、欲しいポイントを残します。作られたものは何も有効になりません。セットアップが作るタグはすべて読み取り専用で、途中で失敗したセットアップはデバイスを残しません。OPC UA が最初にここを通ります。大事な理由:新しい種類のデバイスには専用の画面と、セットアップが何をするかという独自の考え方が必要でしたが、今は 1 つ加えるのも同じ 3 ステップです。[統合](/ja/iot/integrations/)。
- HotLoop は SET を決して送りません。SET はスイッチを変えてしまうことがあるからです。既定の community もありません。`public` は、尋ねる誰にでもプラントのスイッチが読まれる方法だからです。community と v3 のパスフレーズは、ほかのデバイスの秘密と同じく暗号化して保存されます。テストで SNMP エージェントを相手に、v3 のすべてのセキュリティレベルで確認しました。
- **BACnet/IP、読み取り専用。** IP ネットワーク上のビルコントローラーとメーターを扱い、オブジェクト、単位、ステータスフラグを読みます。ルーターの向こうのデバイスは、黙って欠けるのではなく到達不能と表示されます。HotLoop は BACnet のプロパティを決して書きません。書き込みは priority array に入り、設定されたまま残った優先度は設備を置かれた状態に固定してしまうからです。
- **キオスクのサインインと、既定でオンのロックアウト。** `/?screen=<name>` で開いたパネルは、PIN またはキーボード型のバッジリーダーが入力するものという 1 つのフィールドだけを求め、ゲートを通るすべての書き込みはその人のものになるため、監査記録には「panel-3」ではなく誰がバルブを開けたかが残ります。15 分放置するとページとサーバーの両方でサインアウトされ、固まったページが名前をサインインしたままにすることはありません。管理者は Settings、Users、または API でアカウントごとにコードを設定します。コードはパスワードと同じ bcrypt で、6 文字以上、1 つのコードで開けるアカウントは 1 つです。自分のコンピューターでは何も変わりません。サインイン済みで、書き込みはそのまま通ります。**知っておくべき動作の変更:**誤ったパスワードと PIN が 10 回続くと、そのアカウントが 5 分間ロックされ、管理者は解除できます。キオスクを使わないインストールを含め、すべてのインストールでオンです。誤ったパスワードを 10 回より多く再試行するスクリプトは `429` を受け取り始めます。ロックアウトを無効にするには `HOTLOOP_AUTH_LOCKOUT_ATTEMPTS=0` を設定してください。コードだけを誤って入力してもどのアカウントもロックされないため、パネル全体をロックするのには使えません。パネルは 1 回ミスするごとに 0.5 秒余計に待ち、最大 3 秒までで、ロックされることはありません。未実装:キーボードではないリーダーからのバッジ読み取り。[認証とユーザー](/ja/iot/authentication/#キオスクパネル-pin-またはバッジとアイドル時のサインアウト)。
- **アラームのエスカレーション。** 誰も確認しなかったアラームは、次の人に回ります。管理者は Settings でポリシーを編集します。ntfy のトピックや自分のアドレスを持つ人、何分後に誰へ知らせるかを決めるステップ、繰り返しです。どこからの確認でも止まります。エスカレーターは送信のたびにアラームエンジンへ問い合わせ、すべてのステップと停止がアラーム自身の履歴の 1 行になるため、logbook にも残ります。チェーンの途中で再起動しても、監査行が送信済みと示すところから続けます。オンにするまではオフで、`HOTLOOP_NOTIFY_ENABLED` が必要であり、デプロイにすでにあるチャネルだけを使えます。大事な理由:枕元のスマートフォンへの通知 1 回で、それっきりでした。
- **UI をスマートフォンにインストールでき、接続なしで開けます。** HotLoop はマニフェスト、アイコン、service worker を配信します。スマートフォンはページと、人が見る読み取りの最後の応答を保持し、下部のバーがそれが何時時点のものかを示し、すべての書き込みはページを出る前に拒否されます。worker は書き込みに応答も保持もキューイングもしません。サインアウトするとスマートフォンが保持したものは空になります。https または `localhost` でのみ動くため、プレーンな http のプラントはこれまでと同じ UI になります。大事な理由:まさにそこで必要なときに Wi-Fi が落ちたら、古いと言ってくれる古いページは、空白のページよりずっとましです。[ダッシュボード](/ja/iot/dashboards/#スマートフォンで)。
- **セッションが終わるとライブフィードも止まります。** `GET /api/stream` は開くときにセッションを 1 度見るだけで、ストリームは何時間も開いたままなので、サインアウト、期限切れ、取り消されたセッション、無効化されたアカウントのあとも、プラントのライブデータを送り続けていました。今は 5 秒ごとに確認し、セッションがなくなると閉じます。この確認はセッションの利用として数えないため、壁に出しっぱなしの画面もアイドルになります。ルート、フィールド、権限は変わりません。
- **履歴が返す時刻はすべて UTC で書かれます。** 履歴は一部の時刻をボックス自身のタイムゾーンで返していたため(SQLite では読み取り値そのもの)、同じトレンドがニューヨーク設定のプラントでは `-04:00`、UTC 設定のプラントでは `Z` と書かれていました。対象は、区間の端、生の読み取り値、タグの最新値、ウィンドウの前に保持していた値、診断ページの最古と最新の時刻、ウィンドウの `from` と `to` です。どれもどちらの書き方でも同じ瞬間なので、時刻を比較するスクリプトは変化を感じません。文字列を比較していたスクリプトは、オフセットが `Z` に変わるのを目にします。
- **再接続したノードは 1 度だけ名乗ります。** edge ノードが接続を取り戻したとき、再接続側とノードの送信側がそれぞれセッションがまだ生まれていないと見なし、それぞれが NBIRTH を 1 ミリ秒違いで、同じ bdSeq で、2 つ目には何も新しいことがない状態でパブリッシュすることがありました。ちょうどノードが停止される途中だと、2 つ目が NDEATH の後に届き、ホストは停止したノードが再び名乗るのを見ました。送信側は、セッションに birth がないとき、またはタグを知らせる必要があるときだけ birth をパブリッシュします。Edge Relay にも入っています。トピック、フィールド、設定は変わりません。
- **4.18.10 で誤っていたドキュメント。** リンクと数が 4 つです。Edge Relay のページが見出しではないディスカバリーのアンカーにリンクし、4.18.10 のノートが 4.18.4 のアンカーにリンクし、MCP のページは、コードが登録している 27 個の表の上で 25 個のツールと書いていました。README とロードマップは IoT と Edge が次のリリースで来ると書いていましたが、4.18.10 で出ています。

- 所要時間はデータ量に比例するので、大きなデータベースでは初回にログを見守ってください。
