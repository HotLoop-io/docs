HotLoop Flow 2.14.0 は、エージェントが MCP 経由で Flow の残りの部分に届くようにし、障害後のたまったバックログを 1 件ずつではなくバッチで流し出します。22 個の MCP ツール、29 個すべてを並べたページ、そして不在だった InfluxDB に耐久ワイヤーが追いつくより速い方法を加えます。amd64 が先で、arm64 は 2.14.1 で続きます。

## 新機能

- **残りの管理 API のための MCP ツール。** Flow 自身のツールはフローを扱うだけで、その周辺は扱っていませんでした。一覧、読み取り、デプロイ、ロールバック、inject ノードを押すことです。さらに 22 個あり、エージェントは設定、パレット、プラグインを読み、監査ログを読み、デプロイと 2 つのデプロイ間の変更を読み、下書きを実行中のものと比較して型チェックし、フローをエクスポートし、フローのテストを読み、置き換え、追加して実行し、メッセージのトレースを読んでそこからテストの下書きを作り、トレースを再生し、ランタイムの数値を読み、ユーザーの二要素認証を無効にできます(`reset_mfa`、`auth.admin` が必要)。各ツールは、それぞれのハンドラーで動く 1 つの管理ルートで、そのルートが求める権限に従うため、拒否はルート自身の文言で返り、すべての呼び出しは呼び出し元の名前で監査ログに残ります。サインイン、個人の二要素認証、ライブのエディタソケットはツールではなく、その理由は MCP ページに書いてあります。そのページには 29 個のツールがルートと権限とともに並んでいます。
- **耐久ワイヤーがバッチで流れます。** 障害の後、`influxdb out` はバックログを 1 リクエストあたり最大 256 件で書き込みます。書き込みの応答に 8 ms かかるヒストリアン、毎秒 100 件の読み取りを送るプラント、キューにたまった 2,000 件の読み取りで同じテストをすると、以前は流し切るのに 2 分 38 秒かかり、今は 2.7 秒で、すべての読み取りが 1 回ずつ順番どおりに入ります。

## 変更点

- バッチを受け付けるノードへの耐久ワイヤーは、一度に最大 256 件を取り出します。バッチが受け付けられなければ、最初に失敗したものより前のメッセージは完了としてマークされ、その 1 件はワイヤーが常に持っていた再試行と断念の仕組みで単独で再試行され、残りは再送されるので、失われたり順序が入れ替わったりしません。ほかの宛先は引き続き 1 件ずつ受け取ります。配信は引き続き少なくとも 1 回で、プロセスが落とされたときに処理中だったメッセージは以前どおり再び来ることがあります。バッチ対象の場合それは 1 件ではなく最大 1 バッチ、最大 256 件で、`_queuedAt` スタンプによって InfluxDB への繰り返しは以前どおり上書きになります。
- `LICENSE` ファイルの Licensed Work の行は HotLoop Flow だけを挙げています。ほかの製品はそれぞれ独自のライセンスに移るためです。条件は変わっていません。
- エディタには何も変更がありません。
- それ以外は、2.13.1と動作が変わるものはありません。

## 新しい設定

ありません。

## アップグレード

2.14.0 のイメージとチャートへの単純な `helm upgrade`、または Quadlet ユニットの新しいタグです。初回起動で起きることはなく、移行も不要です。`/mcp` に接続するエージェントには、新しいツールのうち、そのトークンの権限が許すものだけが見えます。このリリースは amd64 のみです。arm64 のマシンは 2.14.1 まで 2.13.1 のままで、2.14.1 は arm64 イメージを加えた同じコードです。

イメージ: `ghcr.io/hotloop-io/hotloop-flow:2.14.0`、まずlinux/amd64で、arm64は2.14.1で続きます。チャート: `https://hotloop.io/hotloop-flow/`。このタグのREADMEに残りが写真つきであります: https://github.com/HotLoop-io/hotloop-flow/blob/v2.14.0/README.md
