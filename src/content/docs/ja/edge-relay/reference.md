Edge Relay は 4.6.0 から独立して動く 2 つ目のバイナリです。データベース、Web UI、認証、書き込み経路を持たない、ポーリングして転送する Sparkplug B エッジノードです。Pi やエッジの小型産業用 PC で動かすためのもので、読み取ったものをすべて、4.5.0 で追加されたのと同じ Sparkplug B パブリッシャーを通して、実際のデータベースがある場所で動く完全な Gateway に転送します。

4.5.0 のリリースノートにもはっきり書かれていました。Edge Publish は完全な Gateway プロセスの中でオンにできる機能として存在し、「単体で動くより軽量な Edge Relay エディションはまだありません」とありました。これがそのエディションです。

## 何ではないか

**オプションを減らした小さな Gateway ではありません。** 依存関係がはるかに少ない、別のバイナリです。データベース、Web UI、認証、MCP サーバーやクライアント、自動化エンジン、エンティティレジストリは含まれません。

**UI の提供、書き込みの受け付け、MCP ツール呼び出しへの応答はできません。** 3 つとも、このバイナリが意図的に持たないもの、つまり操作の主体として記録できる認証済みの ID を必要とします。Edge Relay は何も決めず、人に何も確認を返さず、読み取って転送するだけです。

**データベースで設定せず、独自の設定 API もありません。** デバイスとタグは、起動時に読み込むローカルの JSON ファイル、または Gateway がブローカー経由でプッシュするファイルから取得され、プッシュされたファイルはすぐに適用されます([設定プッシュ](#設定プッシュ-480)を参照)。新しい設定を待ち受けるものは Relay にはありません。唯一の入り口は、Relay が自分から接続しているブローカー接続です。

## 全体の仕組み

内部では、Gateway の実際のポーリングエンジンを作り直さずそのまま使っています。Gateway の一部として本番で動いてきたワーカー、再接続とバックオフ、ポーリングループのコードが、ここでも変更なしで動きます。違うのは*設定と履歴の行き先*です。

ポーリングより後のすべて、つまりドライバー、タグバス、Sparkplug パブリッシャー、ディスク上の転送キューは、`HOTLOOP_EDGE_PUBLISH_ENABLED` を設定したときに Gateway が使うコードとまったく同じです。このパブリッシャーが実際に行うこと、つまり Birth、シーケンス番号、障害中のバッファリング、再接続時の再送については、Edge Publish のページを参照してください。ここでは何も変わっておらず、このバイナリは同じ `Offer()` 呼び出しにたどり着く別の道にすぎません。

## デバイスファイル

```json
{
  "devices": [
    {
      "id": "press-01",
      "name": "Press 1",
      "protocol": "opcua",
      "address": "opc.tcp://press-01.local:4840",
      "enabled": true,
      "pollIntervalMs": 1000
    }
  ],
  "tags": [
    {
      "deviceId": "press-01",
      "name": "Zone1_Temp",
      "address": "ns=2;s=Zone1.Temp",
      "dataType": "float",
      "enabled": true
    }
  ]
}
```

タグは Gateway のタグができることをすべてサポートし、`noData` も含みます。これは「測定値なし」を意味する生の値のリスト(レコーダーの 0x8005 など)で、それぞれに理由が付いているため、死んだチャネルが数値としてではなく、Relay と Sparkplug ストリームで不良として読めます。[データなしの値](/ja/iot/protocols/#データなしの値)を参照してください。

Gateway の 7 つのプロトコルドライバーはすべて組み込まれています。OPC UA、Modbus、MQTT/Sparkplug B、EtherNet/IP、S7comm、MTConnect、HTTP です。デバイスファイルの形式に Edge Relay 専用の部分はありません。

### ディスカバリー (4.18.10)

Relay は Gateway と同じように、自分から名乗り出るデバイスを MQTT ブローカーで待ち受け([MQTT ディスカバリー](/ja/iot/mqtt-discovery/)を参照)、聞こえたものを読み取って転送できます。デバイスファイルにブローカーを指定します。

```json
{
  "devices": [],
  "tags": [],
  "discovery": [
    {
      "id": "yard",
      "broker": "10.0.0.5:1883",
      "username": "hotloop",
      "password": "...",
      "prefix": "homeassistant",
      "listenOnly": true,
      "tasmota": true,
      "shelly": true
    }
  ]
}
```

`id` は小文字、数字、`-` で 1 文字から 63 文字、`embedded` は使えません。`broker`、`username`、`password`、`useTls`、`insecureSkipVerify` は Gateway の設定、MQTT で受け付ける値と同じで、同じコードで検証されます。`prefix` の既定値は `homeassistant` で、`tasmota` と `shelly` は既定でオンです。ブローカーを指定しないファイルは、Relay の動作を何も変えません。

聞こえた内容はデバイスとタグになり、Gateway が動かすのと同じコード(`homeassistant/` 形式、Tasmota 独自の形式、Shelly のステータス)で作られ、ほかのデバイスと同様にポーリングされて Sparkplug で転送されます。デバイスの id はブローカーの id とデバイスが名乗る ID から作られ、毎回同じ値(`disc-<identity>-<hash>`)になるので、再起動した Relay でもメトリクス名は変わりません。デバイスは名乗ってから数秒で現れ、撤回されたものは Rebirth でノードの Birth から外れ、どちらも Sparkplug セッションや転送キューには影響しません。ブローカーを追加または削除するプッシュファイルも即時に適用されます。

**ディスカバリーで見つけたものは、書き込み可能にできません。** チェックがそう言っているからではありません。ディスカバリーが作るタグはすべて Gateway と同様に読み取り専用で、作られたデバイスはすべて未承認で、Relay には承認する人がおらず、Relay には書き込み経路そのものがないので、発見されたポイントでもほかのポイントでも、コマンドはデバイスに届く前に拒否されます。そのテストでは、書き込みを許可した Relay に発見したポンプをオンにするよう依頼し、ポンプのコマンドトピックが静かなままだったことを確認します。

コマンドできるデバイスは逆の経路で Relay に届きます。Gateway でデバイスを承認し、操作したいポイントを有効にして、ファイルをプッシュします。Relay も聞いているデバイス(同じブローカー id、または同じアドレスと同じ ID)がファイルにある場合は、ファイルの方が優先され、発見されたコピーは作られないので、1 つのデバイスが 2 回転送されることはありません。

`listenOnly` は、オフにしない限りオンで、その間 Relay はそのブローカーに何も発行しません。パブリッシャーに自分をもう一度名乗らせる Birth メッセージも、Shelly の `status_update` も、Tasmota の電源照会も送りません。変化したときにしか話さないデバイスは、話すまで不明として読めます。オフにすると、DISCOVERY.md に書かれたトピックにこれらだけが送られます。

Relay は聞こえたことを何も保存しません。`homeassistant/` と Tasmota の設定はブローカー上に retained で残るので Relay の起動時に戻ってきます。Shelly は何か変わるたびにステータスを送るので、Relay の起動後ずっと静かだったデバイスは、話すまで現れません。この点と、承認したデバイスを覚えておくデータベースがない点が、Gateway との違いです。

`/status` は `discovery` の下に、ブローカーごとにリッスンして接続しているか、受信、破棄、拒否したメッセージ数、問題の数、そしてディスカバリーが作ったデバイスとタグの数を示します。ブローカーの場所や、問題が起きたトピックは示しません。

### デバイスファイルの認証情報 (4.15.0)

Relay の OPC UA ドライバーは Gateway のものなので、デバイスは `config` ブロックに OPC UA の `username` と `password`([プロトコルとドライバー](/ja/iot/protocols/#opc-ua-セキュリティと認証情報)のセキュリティオプション)を持てます。ほかのプロトコルのデバイスも同様です(MQTT と HTTP のパスワード、HTTP ヘッダー、アドレス内の認証情報)。これらはデバイスファイルに平文で入っていて、Relay にはそれを隠す API がないため(4.15.1 で Gateway に加わった API の伏せ字処理は Relay には適用されません。[認証とユーザー](/ja/iot/authentication/#資格情報がまだ平文の場所)を参照)、ファイルの置き場所が重要です。

- **Helm チャートでは `devicesSecret` を使います。** チャートの `devices` と `tags` の値で設定したデバイスは ConfigMap として生成され、名前空間の ConfigMap を読める人なら誰でも読めるうえ、Helm リリース記録にも残ります。認証情報を持つデバイスでは、デバイスファイル全体を `devices.json` というキーで Secret に入れ、`devicesSecret` にその名前を指定します。Secret が ConfigMap の代わりにマウントされ、ConfigMap は作られません。
- **プッシュされたデバイスファイルにも含まれます。** `POST /api/fleet/{id}/config` でプッシュしたファイルは MQTT トピックに retained で発行されるので、ブローカーは TLS を使い、`hotloop/edge-relay-config/#` を読める人を制限する必要があります。そうしないと、購読できる人なら誰でもそこにあるすべての認証情報を読めます。Relay はプッシュされたファイルをデータボリューム上にモード `0600` で書き込みます(チャートでも Quadlet ユニットでも `/data/pushed-devices.json`)。そのため Secret ではなく PVC にも残ります。
- **セキュリティを使う OPC UA デバイスは、証明書と信頼ストアを保持します。** これらは転送キューと同じ永続ボリュームの `/data/opcua-client-pki`(`HOTLOOP_OPCUA_CLIENT_PKI_DIR`)にあります。チャートの永続化をオフにすると emptyDir になり、新しい Pod ができるたびに新しい証明書が作られ、セキュリティを使うすべてのサーバーがもう一度それを信頼する必要があります(下の「永続化をオフにした場合」を参照)。保護のないチャネルの匿名デバイスには関係ありません。サーバーの証明書を承認する方法は Gateway と同じで、Relay のボリューム上で `rejected/` から `trusted/` に移します。

## リモートコマンド (4.7.0)

Sparkplug の NCMD コマンドが 2 つあり、どちらも Relay がすでに外向きに接続している同じ接続を使うので、受信方向の接続は不要です。

- **再起動**(`Node Control/Reboot`)、4.7.0 から: Relay が自分で正常な NDEATH を発行して終了し、スーパーバイザー(Quadlet ユニットの `Restart=always`、または Deployment の既定の `restartPolicy: Always`)が起動し直します。

- **更新**(`Node Control/Update`): 更新を保留している Relay に対して、オペレーターがイメージの更新を承認するコマンドです。更新を保留する設定の Relay にだけ効果があります。[Relay の更新](#relay-の更新)を参照してください。

これらを誰が送れるかを決める仕組みは Relay 側にはありません。送信する Gateway 側のフリートマネージャーと、実際の認可の境界であるブローカー ACL の要件については、フリート管理のページを参照してください。

## Relay の更新

Relay は Gateway では更新されません。できないのです。Gateway にはそのマシンに入る手段がなく、Relay は自分のコンテナを置き換えられないので、「リモート更新」は 2 つの導入方法で意味が異なります。このページはそれぞれを明記します。プラットフォームが守れない約束は、ないよりも悪いからです。

**ルールは、すべての HotLoop マシンが従うものと同じです。`:stable` を追い、固定しません。** `4.17.0` に固定された Relay は、誰かが導入した日と同じ古さのままで、工場の現場まで戻って更新する人はいません。そのため Relay が追うイメージは `ghcr.io/hotloop-io/hotloop-edge-relay:stable` で、リリースのたびにこのタグが動きます。違うのは、誰が Relay を再起動してそこに乗せるかです。

### Quadlet(Pi または小型産業用 PC): 自分で更新します

[`deploy/quadlet`](/ja/install/quadlet/) のユニットは `:stable` を追い、Podman の自動更新が探すラベルを持っています。マシンごとに一度、タイマーをオンにします。

```sh
sudo systemctl enable --now podman-auto-update.timer
```

タイマーが動くと、Podman が `:stable` を取得し、ダイジェストが変わっていればユニットを新しいイメージで再起動します。放っておいても安全な理由が 3 つあり、どれも読んだだけではなく実際に動かして確認しました。

- **戻れない Relay は元に戻されます。** ユニットにはヘルスチェック(`/edge-relay --healthcheck`、イメージにシェルも curl もないため)があり、これが通るまで systemd に起動完了を伝えません。新しいイメージが通らなければ、Podman は前のイメージを `:stable` に戻してそれを起動します。起動できないリリースの代償は、1 台で数分です。止まったままの Relay にはなりません。Podman 4.9(Ubuntu 24.04)では `Notify=healthy` だけではそうならず、単なる `true` として読まれ、コンテナが起動した瞬間に Relay は起動済みとされ、Relay が止まっているのに Podman は更新成功と報告します。そのためユニットは `--sdnotify=healthy` を明示的に設定しています。
- **Gateway はすべての更新を把握します。** Relay はすべての Birth に自分のバージョンとイメージのダイジェストを載せます。Gateway のフリート一覧は Relay ごとに両方を表示し、変わるとシステムログに、以前の値、現在の値、両方のダイジェストを書きます。これが監査証跡で、マシン上のオペレーターによるものを含め、どんな原因の更新も対象になります。
- **更新はデータに触れません。** 転送キューとプッシュされたデバイスファイルは、新しいイメージが触れないデータボリュームにあります。失われるのは Relay が再起動している間のポーリングだけで、長くても数秒です。

Relay が報告するダイジェストは、そのマシンで `podman image inspect --format '{{.Digest}}'` が出力する値で、自動更新が追うものでもあります。レジストリが Podman の扱うものとは別のマニフェスト形式を保存している場合、Podman は 1 つのイメージを複数のダイジェストで認識することがある(`RepoDigests` の下に並びます)ので、レジストリのヘッダーとではなく、すべての Relay で同じ方法で比較してください。

### Quadlet、オペレーターが承認するまで更新を保留する(任意)

いつ更新するかを自分で決めたい現場もあります。シフト中に止められないラインの Relay がそうです。そのための systemd ドロップインが `edge-relay-hold.conf` で、既定になることはありません。これを使うと、Relay は `"updateMode": "approve"` を報告し、タイマーはオフになり、管理者が Gateway から `POST /api/fleet/{id}/update` を送るまで何も更新されません。すると Relay は終了ステータス 75 で終了し、systemd が現在のイメージで起動し直し、別のジョブが Relay が正常になるのを待って `podman auto-update` を実行します。新しいイメージがあれば同じロールバック付きでそれになり、なければ意味もなく一度止まった Relay になります。実際の更新を 30 秒保留し、その間 Relay は影響を受けずに動き続け、承認で適用されることを確認しました。

代償を理解しておいてください。Podman の自動更新はラベルの付いたすべてのコンテナに作用し、1 つだけ除外することができないので、タイマーはマシン全体でオフにする必要があります。ほかの用途でタイマーを動かす必要があるマシンでは、この Relay を保留にできません。また、Gateway は更新が待機中であることは伝えられず、各 Relay が現在何を動かしているかだけを伝えるので、承認する前にフリート一覧を現在の `:stable` と比べてください。承認にイメージは含まれません。Relay は、自分のユニットが追うものにだけ更新するよう指示できます。

### Helm: `helm upgrade` を自分で実行します

Pod は自分を置き換えられず、Deployment は Helm が変更するものなので、チャートにはリモート更新がありません。チャートの `image.tag` の既定値はリリースである `appVersion` なので、次のようにします。

```sh
helm repo update
helm upgrade edge-relay hotloop/hotloop-edge-relay --reuse-values
```

これで Pod が新しいリリースにローリングされます。チャートの戦略は、新しい Pod を起動する前に古い Pod を停止するので(`maxSurge: 0`、転送キューが 1 つのボリューム上の単一ライターのファイルであるため)、起動するまでの間に空白があります。Gateway は Relay の次の Birth で新しいバージョンを確認し、変更を記録します。Helm では Relay はイメージのダイジェストを報告せず(コンテナは自分のダイジェストを見られず、Kubernetes も渡さないため)、バージョンだけを報告します。ここでは `Node Control/Update` は何もせず、Relay はログにそう書きます。Helm が承認です。

### ここにないものとその理由

- **署名付きイメージとダイジェストの許可リスト。** Gateway は入る手段のないマシンでどちらも強制できず、Relay が自分自身に行うチェックは、侵害された Relay が飛ばすチェックです。Podman は取得時に署名を検証できて(`policy.json`)、それが機能する場所です。ここではそのポリシーの設定は行わず、`:stable` はほかのタグと同じように信頼されます。
- **段階的ロールアウト。** 1 台のマシン上のすべての Relay は、それぞれのタイマーで同じタグを追うので、フリートは段階的にではなく、タイマーのばらつきの範囲で更新され、上のロールバックが問題のあるリリースの影響を抑えます。意図的に段階を分けるには、待たせたい現場を保留ドロップインで止めておき、望む順番で承認します。

## 設定プッシュ (4.8.0)

新しいデバイスファイルは、Sparkplug ではない通常の retained MQTT トピックでプッシュできます。Gateway 側は、フリート管理のページの「設定プッシュ」の節を参照してください。4.17 まで、プッシュはファイルを準備するだけで、何かが再起動するまで Relay は古いリストをポーリングし続けました。そのため Relay がポーリングする対象の変更はすべて、Relay、ブローカーセッション、保持しているすべてのデバイスセッションの再起動になり、数か月触らずに置いておくはずのマシンには負担でした。今は、プッシュは届いた瞬間に適用されます。

- この Relay が**稼働中**にプッシュされた場合: 起動時に `LoadDeviceFile` が適用するのと同じルールでバイト列を検証し、`HOTLOOP_EDGE_RELAY_PUSHED_FILE`(未設定なら `HOTLOOP_EDGE_RELAY_DEVICES_FILE` を上書き、下を参照)に保存して、すぐに適用します。先に保存するのは意図的です。動いたが保存されなかったリストは、次の起動で黙って元に戻ってしまうからです。
- **不正なプッシュは拒否され、古いリストが動き続けます。** 解析できない、検証に通らない(重複したデバイス、宣言されていないデバイスのタグ、不明なプロトコル)、保存できないプッシュは、何も変えません。動いているデバイスも、ディスク上のファイルもそのままです。ログに理由が出て、Gateway のフリート画面が参照する `/status` の `config.rejected` にも出ます。
- この Relay が**オフライン**中にプッシュされた場合: 次の起動まで受け取るものがありません。起動時に Relay はローカルのデバイスファイルを読み込む*前に*、retained のプッシュが届くのを数秒待つので、そのまま新しいファイルで起動します。その数秒後に届いたプッシュは、ほかのプッシュと同様にすぐ適用されます。
- ブローカーは再接続のたびに retained のプッシュを返します。Relay は動かしているファイルを sha256 で把握しているので、同じバイト列が再び届いても何も変わりません。

### 即時適用で維持されるものと変わるもの

Relay は、動かしているファイルと新しいファイルの違いをデバイスごとに調べ、変わったものだけに触れます。

- **変更のないデバイスはセッションを維持します。** PLC への同じ TCP 接続、同じ OPC UA サブスクリプションで、読み取りに途切れがありません。
- **変更されたデバイス**(アドレス、プロトコル、ポーリング間隔、タイムアウト、config ブロック、タグ)は、新しい定義で再接続されます。
- **新しいデバイス**は接続され、ポーリングを始めます。
- **削除されたデバイス**(または `"enabled": false` になったもの)は切断されます。
- **Sparkplug セッションは維持されます。** NDEATH も再接続もなく、bdSeq も同じで、転送キューにも触れません。ブローカー障害中のリロードでも、バッファされたすべての読み取り値はキューに残り、リロードしなかった場合と同じように、ブローカーが戻ると送り出されます。

ネットワーク上では Sparkplug B に従います。Relay は 1 つのエッジノードで、すべてのタグは `device/tag` という名前のノードメトリクスなので、変わるのはノードのメトリクスの集合であり、Sparkplug はノードにそれを変える方法を 1 つだけ与えます。直前の NBIRTH を丸ごと置き換える新しい NBIRTH です。そのため次のようになります。

- **なくなったメトリクス**(削除されたデバイス、削除または無効にされたタグ)は、NDATA で一度 null として送られ、その後ノードはそれらを除いて Rebirth します。同じセッション、同じ bdSeq、seq は 0 に戻り、`Node Control/Rebirth` を受け取ったときと同じ Rebirth です。null を送る理由は、ホストは新しい Birth に含まれないメトリクスの最後の値を保持してよく、Gateway 自身の Sparkplug ホストが実際にそうするからです。null がなければ、Relay から外したバルブが最後の正常な読み取り値のまま、いつまでも健全に見えてしまいます。
- **新しいメトリクス**は、そのデバイスの最初のポーリングで Birth に入り、起動時にすべてのメトリクスが入るのと同じです。Birth は、裏付けとなる読み取り値がある前にメトリクスを載せません。
- **削除されたタグの読み取り値で転送キューに残っているもの**は、キューが排出されるときに破棄され、その件数を数えたログが 1 行出ます。ノードの Birth にはもうそのメトリクスがなく、Sparkplug には載っていないメトリクスを送る正規の方法がないので、送ればどのホストも知らないエイリアスを送ることになります。

ローカルのデバイスファイルを手で編集する場合は、今も再起動が必要です。Relay はこのファイルを起動時とプッシュが解除されたときに読み込み、監視はしません。チャートでは、`devices` を変更する `helm upgrade` がもともとその役を果たします。

### プッシュされたファイルの場所と、どちらが優先されるか

サポートされる 2 つの導入方法はどちらも、ローカルのデバイスファイルを読み取り専用でマウントします。チャートは ConfigMap(または Secret)から、Quadlet ユニットは `:ro` のバインドで、どちらも読み取り専用のルートファイルシステム上です。4.16.0 までは、Relay はプッシュをそのファイルのすぐ隣に書き込んだため、どちらの導入方法でもすべてのプッシュが次のエラーで失敗していました。

```
a pushed config was rejected; keeping the current one and continuing to run
error="write /etc/edge-relay/devices.json.tmp: open /etc/edge-relay/devices.json.tmp: read-only file system"
```

そして Relay は古いリストをポーリングし続けました。Gateway は `config pushed` と言い、再起動も通りましたが、何も変わりませんでした。プッシュに専用の置き場所を与えることで修正されました。

- **`HOTLOOP_EDGE_RELAY_PUSHED_FILE`** はプッシュが書き込まれる場所です。チャートはこれを PVC 上の `/data/pushed-devices.json`(values.yaml の `pushedDevicesFile`)に設定し、Quadlet ユニットも名前付きのデータボリューム上で同じパスに設定します。どちらもコンテナより長く残り、PVC は再スケジュール後も残ります。この最後の点は意図的です。emptyDir も書き込めますが、Pod が移動した時点で消え、ノードのドレイン後に Relay が黙って古いデバイスリストに戻るのは、形を変えた同じバグです。
- **プッシュされたファイルが優先されます。** 起動時、Relay はプッシュされたファイルがあればそれを読み込み、なければローカルのファイルを読み込みます。これは再起動後も、再スケジュール後も、ブローカーが retained のプッシュを失った後(永続化なしの Mosquitto 再起動)も、`devices` や `tags` を変更する `helm upgrade` の後も変わりません。プッシュはより新しい意図的な変更であり、どのみちブローカーは次の起動で retained のコピーをそのまま返すので、ローカルのファイルを優先しても 1 回の再起動しか持ちません。ログの最初の数行に、どのファイルで起動したかが出ます。`booting from the pushed device file; the local one is ignored until the push is cleared`
- **ローカルのファイルに戻す**(チャートの `devices`、または Quadlet の `/etc/edge-relay/devices.json`)には、Gateway で `DELETE /api/fleet/{id}/config` を実行します。削除するとブローカー上の retained のプッシュが消えるので、以後の起動では適用されず、そのとき接続している Relay はローカルのファイルを読み込み、プッシュされたファイルを削除し、`the config push was cleared; the local device file takes over` をログに書いて、プッシュが適用されるのと同じ方法でローカルのファイルを即座に適用します。ローカルのファイルが読み込めない場合、Relay はプッシュされたファイルを動かしたままディスクにも残し、ログと `/status` でそう伝えます。先に削除すると、次の再起動で壊れたファイルから起動する Relay になってしまうからです。ローカルのファイルを直して、もう一度削除を送ってください。Relay が**オンライン**のときに行ってください。解除は retained されないので、その間オフラインだった Relay は解除を知らず、プッシュされたファイルを持ち続けます。起動してから、もう一度削除を送ってください。繰り返しても安全です。
- プッシュされたファイルが存在するのに読み込めない場合(ディスク障害、またはより厳しいルールを持つ後のリリース)は、エラーとして記録され、Relay は止まったままにならず、ローカルのファイルで起動します。
- `HOTLOOP_EDGE_RELAY_PUSHED_FILE` を設定しない場合、プッシュは `HOTLOOP_EDGE_RELAY_DEVICES_FILE` 自体を上書きします。これは 4.8.0 の動作です。書き込み可能なデバイスファイルを持つバイナリ単体での実行でしか役に立たず、その場合は解除時に破棄できる別のコピーがありません。

プッシュが「反映されなかった」ときは、まず Relay のログを見てください。どのファイルで起動したか、またはプッシュがなぜ拒否されたかが書かれています。

## HTTP インターフェース

エンドポイントは 2 つで、どちらも認証がなく、どちらも読み取り専用です。

- `GET /healthz`、プロセスが動いていることを示します。それ以上ではありません。デバイスが切断されていても、このプロセスが不健全という意味ではありません。
- `GET /status`、スナップショットです。接続状態ごとのデバイス数、タグ数、転送キューの現在の深さ、組み込まれたプロトコルの一覧、そして `uplink` があります。これはブローカーに接続しているか、再送中か、転送キューが何を保持し、ディスク上でどれだけの大きさで、上限でどれだけ破棄したかを示します(Edge Publish のページの「アップリンクが切れたとき」を参照)。タグの値も、デバイスのアドレスも、設定も含みません。これは監視用で、Gateway のダッシュボードの縮小版ではありません。`version`、`imageDigest`、`updateMode` は、どのビルドか、更新を保留するかを示します。また、どのデバイスファイルが動いているかを `config` の下に示します。`source`(`local` または `pushed`)、`path`、sha256 の `digest`、`appliedAt`、そして Relay が最後に拒否したファイルとその理由である `rejected` で、後続のプッシュが適用されるまで残ります。ファイルそのものではなくダイジェストなので、認証のないポートにファイルのアドレスや認証情報を出さずに、Gateway はプッシュしたものと照合できます。ファイルに `discovery` のブローカーがある場合は、`discovery` の下に、各ブローカーの状況と見つかったデバイスの数も示します([ディスカバリー](#ディスカバリー-41810)を参照)。

どちらの前にも、意図的に認証を置いていません。Edge Relay にはユーザーデータベースも、セッションストアも、認証を作るための ID システムもなく、機密性のない情報しか出さない 2 つのエンドポイントに共有トークンを 1 つ付けても、セキュリティではなく見せかけになるからです。デバイス自体が置かれているネットワーク境界の内側で動かしてください。これは、信頼できるプロキシの後ろにデプロイする場合について、Gateway 自身の `auth.insecure` モードがすでに文書化している前提と同じです。

変数名と既定値は Gateway 自身の `RuntimeConfig` と同じです。同じ設定を Helm の値で表したものは、k3s と Helm のページの「ポーリング」の節を参照してください。2 つのバイナリは、この設定を同じ `config.LoadRuntimeConfig()` 関数で読み込んでおり、ずれが生じうる 2 つのコピーではないからです。

そして、Edge Publish のページに記載されているすべての `HOTLOOP_EDGE_PUBLISH_*` 変数があり、違いが 1 つあります。`HOTLOOP_EDGE_PUBLISH_ENABLED` は無視され、転送は常にオンです。読み取ったものを発行することがこのバイナリの存在理由であり、Gateway のようにオプトインの機能ではありません。

## 検証済みの内容と、そうでない内容

HotLoop は実際の機器と実際のサーバーに対して実行しており、2026-11-17 には実機でも実行しました。

## デプロイ

サポートされる経路は 2 つで、どちらもコンテナです。セッションとともに終了するシェルから実行する素の `podman run` はなく、Docker もありません。

- **`charts/hotloop-edge-relay`**、Gateway 自身のチャート(`charts/hotloop`)とは別の k3s Helm チャートです。Edge Relay は、転送先の Gateway より小さな別のクラスターで動くことも多い、本質的に別の成果物だからです。デバイスとタグは `values.yaml` に宣言され、ConfigMap として生成されます。転送キューは小さな PVC に置かれます(オフにする前に、下の「永続化をオフにした場合」を参照してください)。
- **`deploy/quadlet`**、k3s クラスターにまったく属さない Pi や小型産業用 PC のための Podman Quadlet ユニットです。Quadlet はコンテナを本物の systemd サービスにして、起動時に開始し、失敗時に再起動し、journald にログを出します。導入手順はそのディレクトリの README を参照してください。

どちらも同じイメージと、上に記載した同じ環境変数を使います。

すべてのリリースは、4.16.0 以降、両方を公開します。イメージは `ghcr.io/hotloop-io/hotloop-edge-relay` で、リリースバージョンのタグが付きます(さらに `major.minor`、`major`、`latest`、`stable`。Quadlet ユニットは `stable` を追います。[Relay の更新](#relay-の更新)を参照)。amd64 と arm64 に対応し、4.17.0 の次のリリースからは 32 ビット arm(arm/v7)にも対応します。Pi 3 や 32 ビットの Pi OS 環境が、まさに Relay の置かれるマシンだからです。チャートは Gateway のチャートと同じ Helm リポジトリにあります。

```sh
helm repo add hotloop https://hotloop.io/hotloop/
helm install edge-relay hotloop/hotloop-edge-relay \
  --namespace hotloop --create-namespace \
  --set edgePublish.broker=tcp://gateway.example.local:1883 \
  --set edgePublish.group=Plant1
```

### 永続化をオフにした場合

`persistence.enabled=false` にすると、PVC なしで動く Relay になり、それだけです。4.16.0 では動作すらしませんでした。`/data` に何もマウントされず、ルートは読み取り専用で、Relay は起動時に `open forward queue at /data/forward.db: no such file or directory` で終了しました。現在は `/data` が `persistence.size` で容量が制限された emptyDir になり、Relay が書き込むものはすべてそこに入ります。

emptyDir は Pod が存在する間だけ残ります。同じ Pod 内でのコンテナの再起動では残ります。新しい Pod では残らず、ノードのドレイン、ノードの障害、退避、`kubectl delete pod`、そして Deployment をローリングするすべての `helm upgrade` で新しい Pod ができます。そのたびに、次のものを失います。

- **転送キュー。** ブローカーが落ちている間にバッファされたすべての読み取り値が失われ、Gateway 側では誰も欠けていることに気づきません。
- **プッシュされたデバイスファイル。** Relay は何事もなくチャートの `devices` で起動し直し、Gateway が再度プッシュするか、ブローカーが retained のプッシュを再送するまで、そのままです。これは PVC が防ぐはずのまさにその障害で、オフにすると再びそれを受け入れることになります。
- **OPC UA クライアント証明書と信頼ストア。** セキュリティを使うすべてのサーバーが新しい証明書を信頼し直す必要があり、オペレーターはすべてのサーバーの証明書をもう一度承認する必要があります。

上限を使い切ることは、上限のないキュー(`queueMaxBytes: 0`、既定は 64 MiB)が十分に長い障害の間に起こしうることで、Pod が退避され、3 つすべてを一度に失います。それでも、ノード上のほかのすべてのものの下でノードのディスクを埋めるよりはましです。導入時の案内は、永続化がオフのときに警告を表示します。試用なら問題ありません。読み取り値が重要な Relay には、PVC を付けてください。

### EmberNet App Store から

ストアには、Relay がノードごとに 1 つ、HotLoop Edge Relay として掲載されています。ストアからのデプロイは、チャートに 3 つのものを渡します。表示名(リリース名)、ノードセレクター、テナントラベルです。それ以外を尋ねるフォームはなく、Relay はブローカーと Sparkplug グループなしでは動けません。そのため Relay のストアデプロイは、意図的にレンダリングの段階で止まり、helm-install ジョブのログに、何が足りないかと、直すための正確なコマンドを示すエラーを出します。

既定のブローカーは用意していません。どの工場にも当てはまるブローカーは存在せず、作り物のアドレスを指す Relay は、何も転送していないのにデプロイ済みに見えてしまうからです。プッシュされたデバイスファイルを待つこともできません。プッシュは、まだ存在しないブローカー接続を通って届くからです。

直すには、ストアが書き込んだものに 2 つの値を入れます。インストールは自動的に再試行されます。

```sh
# a node on the local cluster: add them under spec.valuesContent
kubectl -n default edit helmchart hotloop-edge-relay-<node>

# a tenant on its own cluster (Fleet): add them under spec.helm.values
kubectl -n fleet-default edit helmop hotloop-edge-relay-<node>
```

```yaml
edgePublish:
  broker: tcp://<gateway-or-broker>:1883
  group: <sparkplug group id>
```

起動すると、Running Apps にストアが付けた名前で HotLoop のアイコンとともに表示され、デプロイしたテナントに限定され、LAUNCH ボタンはありません。この最後の点は意図的です。チャートが `embernet.ai/gui-type: none` というラベルを付けるのは、`/healthz` と `/status` がプローブとオペレーターの curl のためのもので、iframe に入れるページではないからです。

Relay と Gateway はバージョン番号を共有します。2 つのチャートがタグのバージョンを持ち、Relay の Quadlet ユニットが `:stable` を追っていないとリリースは開始されないので、Relay は、自身のコードが変わったかどうかにかかわらず、リリースのたびに新しいバージョンになります。これは意図的です。確認する番号が 1 つで、誰もプッシュしていない Relay イメージを指す Relay チャートがなくなります。Quadlet ユニットは以前リリース番号を固定していましたが、それは自分で更新するマシンのやり方とは正反対でした。
