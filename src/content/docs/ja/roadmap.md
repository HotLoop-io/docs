HotLoop とは何か、何を作り残しているか、何が壊れているかをまとめています。このリストにないものは実施されないので、必要なものはリストに載せてください。

## HotLoop とは

**HotLoop は現場のためのオートメーションプラットフォームで、Go でゼロから書かれています。** 静的バイナリ 1 つです。Python も、面倒を見るランタイムも、特権コンテナも、不要な capability もありません。エンティティ、オートメーション、ヘルパー、スクリプト、ログブック、ダッシュボード、お知らせ、MCP、ディスカバリー付き MQTT が、産業用の層の上に載ります。その層とは、実際の PLC プロトコル、本物のヒストリアン、ISA-18.2 アラーム、OPC UA、Sparkplug B です。

すべての行が自社のコードです。組み込みも、ブリッジも、フォークもないので、午前 3 時に何かが壊れても、読むコードベースは 1 つで、他人のバグを待つ必要はありません。

HotLoop は現場のための 8 つの製品です。サイトとともに成長する 4 つ(IoT、Edge、Gateway、Edge Relay)に、ロジックをつなぐ Flow、ワークフローを担う Cascade、PLC 自身の画面のための HotLoop for CODESYS、PLC の値をネットワークへ送り出す Transmitter が加わります。このロードマップは、1 つのコードベースから生まれる 4 製品、HotLoop core のものです。[製品](#製品)を参照してください。Flow、Cascade、HotLoop for CODESYS、Transmitter にはそれぞれ <a href="/ja/flow/roadmap/">Flow のロードマップ</a>、<a href="/ja/cascade/roadmap/">Cascade のロードマップ</a>、<a href="/ja/codesys/roadmap/">HotLoop for CODESYS のロードマップ</a>、<a href="/ja/transmitter/roadmap/">Transmitter のロードマップ</a>があります。

## 製品

HotLoop core は、1 つのコードベースと 1 つのタグで作る 4 製品です。コアのリリースでは 4 製品が同じバージョンで同時に出荷され、それぞれ専用のイメージと Helm チャートを持ちます。たまたま必要なドライバーを持つ製品ではなく、機器に合う製品を選んでください。

| 製品 | 概要 | データベース | 現状 |
|---|---|---|---|
| **HotLoop IoT** | エンティティ、オートメーション、ヘルパー、スクリプト、ログブック、ダッシュボード、お知らせ、MCP、ディスカバリー付き MQTT、ISA-18.2 アラームエンジン、バックアップ、すべてのドライバー。Edge と Gateway の土台 | SQLite または Postgres | 分離済み:専用のイメージ(`hotloop-iot`、amd64、arm64、arm/v7)、チャート、Quadlet ユニットを、タグごとにビルドして公開します。4.18.10 で出荷 |
| **HotLoop Edge** | IoT に加えて、OPC UA サーバー、上位への蓄積転送、機械そばのローカル画面 | SQLite、Postgres、または TimescaleDB | 分離済み:専用のイメージ(`hotloop-edge`、amd64、arm64、arm/v7)、チャート、Quadlet ユニットを、タグごとにビルドして公開します。4.18.10 で出荷(Gateway は 4.5.0 からエッジで動作し、Sparkplug を上位へ配信しています) |
| **HotLoop Gateway** | Edge に加えて、フリート、マルチサイト、定期レポート。サイトの頭脳 | SQLite、Postgres、または TimescaleDB | 提供中 |
| **HotLoop Edge Relay** | シンプルで頑丈:ポーリングして、転送して、生き残る。データベースも UI もありません。画面を外した Edge ではなく、独立した製品です | なし | 提供中。4.16.0 以降、リリースごとにイメージとチャートを公開します |

**製品を分けるのは機能であり、プロトコルではありません。** どの製品も、用意しているすべてのドライバーの上で MQTT に対応します。中古の S7-1200 を机に置いた趣味のユーザーは IoT ユーザーであり、IoT はアップグレードなしでその PLC と通信します。

- [x] 分離そのものをコードに反映しました。`-tags hotloop_edge` で Edge、`-tags hotloop_iot` で IoT になり、両方を同時に指定するとコンパイルできません。その製品にない機能の API ルートは 404 を返し、その機能を持つ製品を伝えます。`hotloop --product` と `GET /api/status` で、どの製品と通信しているかが分かります
- [x] 1 つのタグから 4 つのイメージと 4 つのチャートを並行してビルドし、同じ Helm リポジトリに公開します。4 つのチャートのどれかがタグと一致しなければ、リリースは拒否されます。Gateway は `ghcr.io/hotloop-io/hotloop` とチャート `hotloop` を維持するので、4.16 を使っている人が壊れた状態で朝を迎えることはありません
- [x] データベースはイメージではなく設定です。SQLite、Postgres、TimescaleDB を実行時に選び、すべて同じバイナリに入っています。SQLite は cgo のない純粋な Go 版なので、arm ビルドも静的なままで、Pi にコンパイラのツールチェーンは要りません。テストスイート全体を 3 つすべてに対して実行します。テストしないデータベースは、サポートしないデータベースだからです
- [x] サイトを IoT から Edge、Gateway へ移しても、すべてのデバイス、タグ、アラーム、ユーザー、履歴が残ります。イメージを替えるだけです。戻しても何も消えず、なくなった機能が戻るまで休止しているだけです
- [x] IoT や Edge にある Gateway 専用の設定は、警告を出しつつ動作し、設定画面にも表示されて保存されます。何を設定し、なぜ何も起きないのかを、推測せずにそのまま確認できます
- [x] IoT は既定で 30 日分の履歴を保持します。Pi のディスクは小さく、長期の履歴は Gateway の役目です
- [x] ライセンスキーも、実行時のロック解除もありません。有料の等級はありません。等級とはイメージであり、アップグレードは同じデータの上でイメージを替えることです
- [x] **すべての機器が `:stable` を追い、自分で更新します。** Gateway、Edge、IoT の Quadlet ユニットはリレーと同様に `:stable` を追い、Podman の自動更新、シェルが不要なヘルスチェック、新しいイメージが起動できないときのロールバックを備えます。`release_guard.sh` は、ユニットが固定されている、異常を報告できない、データベースを自動更新する、のいずれかに当てはまるリリースを拒否します。データベースはチャートが実行するタグに固定されたままです。PostgreSQL のメジャーバージョンはダンプと再読み込みが必要で、アプリの TimescaleDB 拡張の更新は一方通行のため、アプリと違って元に戻せないからです。Gateway で実際に実行して確認しました。マイグレーションを含む更新をデータそのままで適用したものと、マイグレーション後に起動できず、ロールバックしたものです。この実行が、ポッドをやめた理由です。アプリをポッドに入れていると、Podman はポッドのユニットを再起動し、そのユニットは問題なく起動するため、壊れたリリースが成功と報告されてロールバックされませんでした。[Quadlet の README](/ja/install/auto-update/)を参照してください
- [x] ライセンスの適用範囲の行は、正本のライセンスとそのすべての写しで 4 製品すべてを挙げています。以前は Gateway とだけ書かれており、残り 3 製品には許諾がないと読める余地がありました
- [x] **分離は MQTT ディスカバリーとともに 4.18.10 で出荷されました**(フェーズ 4)。IoT の最初のリリースで、Shelly と ESPHome のデバイスがすぐに見つかります

## オートメーションの土台

順番に進めます。各フェーズは個別にテストした PR として出荷され、前のフェーズの上に積み上がります。すべて HotLoop IoT に入るので、Edge と Gateway にも入ります。

### フェーズ 1:エンティティ

基礎です。HotLoop のすべてのオートメーション、ヘルパー、スクリプト、画面はエンティティを扱うので、最初に作りました。4.15.3 の後に PR 1 から 6 でマージされ、4.16.0 で初めて出荷されました。詳細は[エンティティ](/ja/iot/entities/)と[設備ツリーとラベル](/ja/iot/equipment/)にあります。

- [x] エンティティモデル:型を持つドメイン(センサー、バイナリセンサー、スイッチ、数値、選択、ボタン、テキストと、OT 向けのバルブ、モーター、PID ループ、カウンター、アラーム)、状態、属性、変わらないエンティティ ID。ポンプ、ファン、コンベヤ、コンプレッサーは独立したドメインではなく、モーターの一種です
- [x] 複合設備:始動、停止、リセット、運転中、故障、速度のタグから 1 つのモーターエンティティを構成します。モーターとは実際にそういうものだからです
- [x] 既存のタグをエンティティに対応づけます。タグ、API 呼び出し、MCP ツール、OPC UA ノード、オートメーション、エッジリレーのデバイスファイルは 1 つも壊しません
- [x] `switch.turn_on`、`number.set_value` などのサービスは、既存の書き込みゲートを通り、他の経路はありません
- [x] ISA-95 の設備ツリー 1 つ(企業、サイト、エリア、ライン、セル、ユニット、設備)とラベル。すでにあるサイト / エリア / ライン フィールドは引き続き動作します
- [x] 単位とデバイスクラス
- [x] MCP、オートメーション、リアルタイムフィードでのエンティティと、エンティティ画面、工場画面
- [x] エンティティの状態トリガーの `for:` 継続時間(「ポンプが 5 分間停止している」)。フェーズ 2 で `state` トリガーの `forSec` として出荷されました。進行中の待機は再起動後に引き継がれません([オートメーション](/ja/iot/automations/#holding-a-state-forsec))

### フェーズ 2:ヘルパー、スクリプト、シーン、ログブック

- [x] ヘルパー:入力ブール、数値、選択、テキストと、タイマー、カウンター、スケジュール。工場では設定値やシフトのスケジュールにあたります。再起動後もバックアップにも保持され、タイマーは壁時計基準です。[ヘルパー](/ja/iot/helpers/)を参照してください
- [x] スクリプト:名前付きの動作シーケンスで、オートメーション、UI、MCP から呼び出せます。型付きフィールド、実行モード、本物のゲートを通るドライラン、`script:<id>` として記録されるすべての書き込み、ログブックとバックアップへの記録。[スクリプト](/ja/iot/scripts/)を参照してください
- [x] シーンは**レシピ**として提供されます。設定値のまとまりを取り込み、まとめて適用し、監査記録を残します。全体を検査して全体を拒否し、値を丸めることはありません。1 つの呼び出し ID の下で順に書き込み、ロールバックはせず、デバイスから読み戻して確認します。バージョンは不変で、UI、ルール、スクリプト、MCP から適用できます。[レシピ](/ja/iot/recipes/)を参照してください
- [x] ログブック:すべての状態変化、書き込み、アラーム、オートメーション実行を、エンティティ別、エリア別に並べた 1 本のタイムラインです([ログブック](/ja/iot/logbook/))
- [x] ブループリント:再利用できるオートメーションのテンプレート。範囲外の型付き入力は拒否し、丸めることはありません。ルールは、誰かがアップグレードを確認して受け入れるまで、作成時のバージョンを保ちます。標準で 4 つ。[ブループリント](/ja/iot/blueprints/)を参照してください
- [x] オートメーション言語:シーケンス内の条件、待機、停止のステップと、状態トリガーの `forSec`(「5 分間オン」)

### フェーズ 3:ダッシュボード

ここは「より良く、よりかっこよく」が部屋の反対側からでも分からなければならない部分です。

- [x] ダッシュボードビルダー:カード、ドラッグ&ドロップ、好きなだけのダッシュボード。保存時に元のバージョンを記録するので、2 人が同じページを作っても気づかないまま上書きすることはありません。[ダッシュボード](/ja/iot/dashboards/)を参照してください
- [x] 画面ファイル:ダッシュボードをバージョン付きファイルとして保存し、別のインストールに取り込みます。お客様の画面はお客様のものであり、製品の一部にはなりません。足りないタグやデバイスは、保存する前にすべて一覧にして対応づけます。[画面ファイル](/ja/iot/screen-file/)を参照してください
- [x] カードセット:ゲージ、数値、トレンド、エンティティ一覧、確認付きの書き込みボタン、スクリプトボタン、アラーム一覧、マークダウン、カメラ、ライブタグ付きのフロアプラン、レシピ選択、工場ステータスバー。カード自体は何も命令せず、ボタンが書き込みゲートを通して書き込みます
- [x] ロール別、画面別のダッシュボード。壁掛けボードもその 1 つで、同じ切り替えと同じ割り当てを使います
- [x] パネル PC、ノートパソコン、スマートフォンのどれでも同じように見えます。12 列から 1 列に折りたたまれる 1 つのレイアウトで、5 つの幅でテストしました
- [x] Web UI は英語と 13 の言語に対応します。スペイン語、フランス語、イタリア語、ドイツ語、ノルウェー語、ブルガリア語、ギリシャ語、韓国語、日本語、ベトナム語、ヒンディー語、簡体字中国語、アラビア語(右から左)で、上部バーで選択でき、ブラウザーが記憶します。[言語](/ja/iot/languages/)を参照してください
- Edge の HMI をこれから作れるように設計しました。画面名に結びつけたダッシュボードは、ヘッダーもタブもなしで `/?screen=<name>` に開きます
### フェーズ 4:統合とディスカバリー

- [x] 統合フレームワーク:統合はデバイスとエンティティを追加し、設定フローを持ち、実機を相手にテストします
- [x] **MQTT ディスカバリー**:Zigbee2MQTT と ESPHome は公開する形式で、Tasmota は独自の形式で、Shelly Gen2 以降は公開するステータスから見つけます。デバイスは内蔵ブローカーでも他のブローカーでも読み取りとして現れ、人がデバイスを受け入れて各ポイントを有効化するまで、何も有効になりません。Edge Relay もディスカバリーに対応し、読み取りと転送のみです。Frigate は含まれません。その MQTT のページにディスカバリーメッセージの記載がないためです。すべて実機の記録で検証し、Tasmota と Shelly はメーカーの資料でも検証しました。作業台の実機で検証したものではありません。[MQTT ディスカバリー](/ja/iot/mqtt-discovery/)と [Edge Relay リファレンス](/ja/edge-relay/reference/#discovery-41810)を参照してください。4 製品への分離は、これを待っていました
- [x] ネットワークディスカバリー(mDNS、SSDP、DHCP):工場のネットワークで見つかったデバイスは、何であるか、HotLoop がどう通信できるかとともに「発見済み」画面に現れ、人が 1 つずつ受け入れるか無視します。OPC UA サーバーは OPC UA デバイスに、Shelly は HTTP デバイスになり、ESPHome ノードは MQTT を案内します。自動で追加されるものも、有効になるものもありません。既定は受信のみで、プロービングは展開側でネットワークごとに有効にします。DHCP はホストネットワークと 67 番ポートが必要なので、展開が両方を与えるまで無効です。本物の avahi、MiniDLNA、udhcpc でテストしました。作業台の実機ではまだテストしていません。[ネットワークディスカバリー](/ja/iot/network-discovery/)を参照してください
- [x] CODESYS:プログラマーが付けた名前のまま、ランタイム自身の OPC UA サーバーを通して PLC の変数を扱います。アプリケーションがエクスポートするものの検出、読み取りと書き込み、設定からの最初のダッシュボード、再起動やダウンロード後の無人での再接続に対応します。HotLoop のラボ用プログラムとはるかに大きい 2 つ目のプログラムを動かすコンテナ内の 4.22.0.0 ランタイムと、ベアメタル(2026-11-17)で検証しました。[CODESYS](/ja/iot/protocols/#codesys)を参照してください
- [x] BACnet/IP と SNMP、読み取り専用です。[プロトコルとドライバー](/ja/iot/protocols/)を参照してください
- [ ] ONVIF カメラ、Shelly ネイティブ
- [ ] **Firmata**、USB 接続の Arduino 向け。実機でのみ検証します。Arduino といくつかの Firmata デバイスが作業台に向かっており、Firmata のエミュレーターは自分たちで納得し合うだけになります
- [ ] UniFi、[UniFi](#unifi)を参照してください
- [x] 屋外向けの太陽:`binary_sensor.sun_up`、太陽の高度と方位角、夜明け、日の出、正午、日の入り、薄暮のオフセット付き `sun` トリガー。サイトの緯度と経度から NOAA の式で機器内で計算し、外部サービスは使いません。NOAA が 2026 年に公表した、ウトキアグヴィクからキトまで 6 か所のすべての日の出、日の入り、正午と照合しました。[太陽](/ja/iot/sun/)を参照してください
- [x] 天気:クラウドの天気 API ではありません。HotLoop は雨が降っているかを知るために誰にも電話しません。`weather` エンティティは工場自身の屋根にある観測装置で、タグをロール(温度、湿度、気圧、風、雨、日射)に結びつけ、露点、熱指数、体感温度を機器内で計算して NWS の表と照合します。読み取れないセンサーは 0 ではなく利用不可になります。カード 1 枚、14 言語で、エージェントが MCP で作成して読み取ります。[天気](/ja/iot/weather/)を参照してください

### フェーズ 5:エネルギー、スマートフォン、お知らせ

- [x] エネルギー:kWh、ガス、水、圧縮空気、生産単位あたりのコスト。生産現場に向けた 1 つのエネルギーダッシュボードです。メーターはカウンターまたは電力として読むタグで、データベースに 15 分単位で保存し(マイグレーション 0029)、計測された時点で固定料金または時間帯別料金で価格を付けるので、後から単価を変えても先月のコストは変わりません。生産単位あたりのコストは、生産カウンターが数えた量で割ったコストで、何も生産していなければ「生産なし」と表示します。エネルギー画面、すべてのルール向けセンサー、14 言語、MCP。最も高い 15 分の需要料金(マイグレーション 0030)と、名前を付けたシフトの合計を、画面、API、エージェントから取得できます。[エネルギー](/ja/iot/energy/)を参照してください
- [x] スマートフォンにインストールでき、オフラインでも動作する Web アプリ
- [x] お知らせ、以下を参照してください

## お知らせ

Webhook、メール、ntfy、Gotify、Discord Webhook、Discord ボットがあり、すべて同じ基盤の上で動きます。[アラームのお知らせ](/ja/iot/notifications/)を参照してください。

- [x] **まず基盤から:**チャネルごとのレート制限、まとめ送信(「直近 1 分でアラーム 7 件追加」を 1 通に)、`Retry-After` を守る回数制限付きの再試行
- [x] **署名付きの確認リンク:**スマートフォンからの確認は本物の ISA-18.2 の確認として記録され、古いボタンで同じアラームの次回の発生を確認することはできません。ntfy は誰が押したかを伝えないため、記録される名前はチャネルのもの(`notify:ntfy`)で、Discord ボットは押した人の名前を記録します

チャネルは 4 つです。それがリストのすべてです。

- [x] **まず ntfy。**無料でセルフホストでき、インターネットのない工場ネットワークでも動作します(Android。iPhone はサーバーが ntfy.sh 経由で中継する必要があります)。アクションボタンは、工場ネットワークを通してアラームの確認を HotLoop にそのまま返します。
- [x] **Gotify。**無料でセルフホストでき、インターネットなしで動作します。確認ボタンも iPhone アプリもないので、双方向ではなくポケットベルのようなものです。
- [x] **Discord Webhook。**URL を貼り付けるだけです。`allowed_mentions` は固定されており、アラーム名が @everyone にメンションすることはなく、重大なアラームはロールを呼び出せます。Discord が拒否した Webhook は、IP の遮断に至るまで再試行せず、無効になります。
- [x] **Discord ボット。**チャネル内で直接使える確認と保留のボタンで、Discord のロールで制限し(指定するまで誰も使えません)、押した人の名前で記録します。アウトバウンド接続(Gateway)で Discord と通信するので、工場に公開アドレスは不要です。
- [x] エスカレーション:N 分以内に誰も確認しなければ、次の担当者または次のチャネルを呼び出します
- 対応しないもの:SMS と Google Messages(RCS は会社ごと、国ごとに通信事業者の承認が必要で、セルフホストの機器では取得できません)、Slack、Teams、Google Chat、Pushover、PagerDuty、Telegram、Opsgenie、Signal、Matrix

## UniFi

工場のネットワークも設備です。PLC が静かになったとき、最初の疑問は「PLC か、スイッチか」で、今は UniFi アプリまで歩いて行って確かめています。そこで UniFi は別システムではなく**プロトコルドライバー**として入ります。すべてのスイッチ、ポート、PoE 予算、WAN がタグです。1 社のために各機能の半分を作り直す必要がなく、書き込みゲート、監査、ドライラン、アラーム、トレンド、エンティティ、オートメーション、OPC UA、MCP をそのまま使えます。

IoT の土台に入るので 4 製品すべてで使え、Edge Relay も他のデバイスと同じようにコンソールをポーリングできます。

### ネットワーク

順番に進めます。U5 まで、コントローラーに書き込むものはありません。

- [x] **U1:読み取り専用ドライバー。**コンソールごとに 1 つのセッションをすべてに使い回し、ログイン回数の予算があります。確認のたびにログインしたところ、自社の Cloud Gateway が 429 を返して 2 回ロックアウトされたため、HotLoop は 1 回だけログインし、ロックアウトを延ばさずに解除を待ちます。コンソールの証明書は初回使用時に固定され、無条件には通しません。デバイス、スイッチポート、PoE 消費、WAN、フェイルオーバーは自動で同期されるタグとして入ります。明日採用したスイッチは自動で現れ、消えたスイッチはアラームの下から蒸発せず、品質不良になります。最初の実読み取りでは、2 日間止まっていた 5G バックアップを稼働中と報告しました。コンソールの要約と同じく、WAN ブロックの古い `up` を信じたためです。ヘルスチェックは知っていたので、ドライバーは今はそちらを読み、テストで固定しています。完了。[UniFi Network](/ja/iot/unifi/)を参照してください
- [ ] **U2:クライアントと OT 監視。**コントローラーのクライアント表には機械が数時間前に離れたアドレスが残っているため、IP ではなく MAC でクライアントを識別します。ネットワークを OT として印を付け、そこにあるものを受け入れると、そこに新しく現れたものはすべてアラームになります。HotLoop デバイスをスイッチのポートに 1 度ひもづけておくと、静かになった PLC がどのポートにあり、そのリンクが生きているかを教えてくれます。ラックの前に人が必要な 2 つの手順、実際のケーブル抜きと、スマートフォンの SCADA への参加を済ませてからチェックを付けます。[UniFi Network](/ja/iot/unifi/)を参照してください
- [x] **U3:画面とトポロジーマップ。**WAN の帯(サイトが 5G バックアップで動いているとアンバー色になります)がある概要、壁掛けボードで揺れないよう毎回同じ配置のトポロジーマップ、スイッチの前面、クライアント、ネットワーク、WiFi。2 つのコンソールを 1 つの図につなぎました。スイッチをクリックすると、工場ツリーのどのラインに給電しているかが分かります。ケーブルはコンソール自身のダウンリンク表から取るので、どこにも接続されていると書かれていないスイッチは、推測でゲートウェイにぶら下げず、単独で置かれます。実機ではまだ確認していません。マップはピンチ、ドラッグ、最大 8 倍までのズームができ、ひもづけた HotLoop デバイスをラインの下にまとめる工場オーバーレイがあり、各 WAN の横に遅延が表示され、ポートの入出力が記録され、管理者は通常のアラーム(デバイスのオフライン、アップリンクのダウン、ゲートウェイがバックアップ状態、指定した上限を超える PoE)をワンタッチで作成できます。これらは 2026-10-19 に、画面上ではなくエミュレートしたタッチで検証しました。WAN スループットのトレースはまだありません。そのためのコンソールのフィールドを実機のゲートウェイから読み取っていないためです。[UniFi Network](/ja/iot/unifi/#画面)を参照してください
- [x] **U4:イベント。**コントローラーのイベント WebSocket により、スイッチが落ちると次のポーリングではなく数秒で表示され、ログブックに記録されます。ポーリングが正であり続けます。死んだ WebSocket で失われるのは速さであり、正確さではありません。切断された WebSocket も沈黙した WebSocket も、ログインなしで再接続します。イベントは該当するスイッチまたは AP の下のログブックに記録され、設備フィルターが、ひもづけたデバイスからそれに給電するスイッチをたどって見つけます。エージェントツール `get_network_topology` と `get_network_events` がマップとイベントを読み取ります。[UniFi Network](/ja/iot/unifi/#イベント)を参照してください
- [ ] **U5:ゲートを通した書き込み。**まず所在確認 LED です。リスクはゼロで、部屋の反対側からも見え、実機での書き込み経路全体を証明します。次に PoE モード、ポートの電源サイクル、WLAN のオンとオフ、クライアントのブロック、未知のデバイスのポート無効化を、実際のコントローラーと空きポート 1 つでその形が証明された後に提供します。電源サイクルにはポートごとに 15 分のクールダウンがあります。2 分ごとに PLC の電源を入れ直すオートメーションは、電源ユニットを焼く方法だからです。保護ポートはトポロジーから決まります。誰が頼んでも、HotLoop はアップリンクや 5G バックアップに給電するポートの電源を入れ直しません。デバイスの再起動は単なるボタンです。押せばデバイスが再起動し、確認はなく、監査記録は残ります
- [ ] **U6:自己修復。**標準のブループリント:デバイスが N 分間静かならそのポートの電源を 1 度入れ直し、その後アラームを出します。永遠にではなく、1 度だけです

### Protect、Access、電源

Ubiquiti の資料をもとに作り、それぞれ作業台の実機で動かしてからマージします。それより前にはマージしません。

- [ ] **Protect。**カメラをエンティティとして、動きとスマート検知をバイナリセンサーとオートメーショントリガーとして扱い、スナップショットをオンデマンドで取得してアラームのお知らせに添付します。HotLoop のアラームから Protect のアラームトリガーを起動して、カメラに録画させることができます。ライブ映像はフェーズ 3 のカメラカードで対応します
- [ ] **Access。**ドアの位置、ログブックへのドアイベント、ゲートを通した書き込みとしての解錠。MCP からの解錠も他の書き込みと同じく書き込みゲートを通して許可され、他の書き込みと同じく監査されます
- [ ] **SmartPower PDU。**コンセントの電力、オン、オフ、電源サイクルをタグとして扱い、フェーズ 5 のエネルギーの作業に反映します

## HotLoop Edge Relay

## レビューで修正した項目

コードレビューで見つかり、`main` で修正しました。各バージョンのリリースノートに、稼働中のサイトにとって何が変わったかが書かれています。

- [x] **リストアが古いスキーマのバックアップを読み込めず、バックアップの `hotloopVersion` をまったく確認していませんでした。**マニフェストにすべてのテーブルの列と適用済みのスキーママイグレーションを記録するようにしました。リストアは各ファイルを名前でそれらの列に読み込み、新しい列には既定値を入れ、新しいテーブルはアプリに任せ、新しいスキーマのバックアップや、このバージョンが削除、改名、型変更した列を持つバックアップは、1 行も読み込む前に拒否します。それ以前のバックアップは従来どおり位置で復元できます。これまでに存在したすべてのスキーマの段階からテストしました。修正済み。[バックアップと復元](/ja/iot/backup/#restoring-onto-a-different-version)を参照してください
- [x] **お知らせ用 Webhook が URL を漏らしていました。**エラー、ログ、監査イベント、`/api/notify/test` の応答に出ており、入力を間違えた URL は起動ログにも出ていました。Discord と ntfy では URL がパスワードにあたります。修正済み
- [x] アラームのお知らせのページが、汎用 Webhook は Discord、Pushover、PagerDuty で使えると書いていました。使えないので、そう書き直しました。修正済み
- [x] ログのスクラバーが、通常のログメッセージで `token:` の後の単語を消していました。修正済みで、それらの名前に続く本物の認証情報は引き続き隠されます
- [x] 0 から始まるタグの範囲が、書き込みのツールチップで 0 の代わりにダッシュを表示していました。API が最小値の 0 を省いていたためです。今は常に `minValue`、`maxValue`、`hasRange` を送り、MCP の `list_tags` は範囲があるときにだけ正確に範囲を送ります。修正済み
- [x] 1 つの MQTT ブローカーや 1 つの Mailpit を共有するローカルテストの実行が互いに干渉していました。Sparkplug のトピックが衝突し、一方の実行のレポートメールがもう一方のメールボックスに届いていました。今はすべてのテストが独自のトピック名前空間、メールボックス、UniFi サイトを持つので、並列実行でも衝突しません。修正済み
- [x] トレンドチャートとレポートで不良データの扱いが食い違っていました。`store.HistoryBuckets` は不良と不確実な測定値を平均に入れ、レポートは除外していました。今は両方が品質ルール(README の「品質ルール」)に従い、正常値が 1 つもない区間はチャートの空白になります。修正済み
- [x] `HOTLOOP_DB_STATEMENT_CACHE=false` にするとデバイスの作成(`invalid input syntax for type json`)と、他のすべての jsonb 書き込みが壊れていました。シンプルプロトコルでは `[]byte` が bytea として送られるためです。今はすべての json パラメーターがテキストとして送られます。修正済み
- [x] `writeError` が、シャットダウンやデータベース障害を含むすべての不明なエラーを 400 にしていました。今はログの行を示し、何も漏らさない 500 になり、本当に呼び出し側の誤りであるものは発生した場所で印が付けられます。修正済み
- [x] 読み込めないタイムゾーンが何も言わずに UTC にフォールバックしていました。今は HotLoop が起動を拒否し、変数と値を示します。設定画面はすでにそのような値を拒否していました。修正済み
