HotLoop Flow 2.16.2 macht einen großen Flow günstig im Betrieb. Eine Anlage mit 12.000 Nodes bei etwa 3.000 Nachrichten pro Sekunde, ohne dass jemand ein Dashboard ansah, lag an ihrem CPU-Limit. Derselbe Flow braucht jetzt rund ein Drittel der CPU und weniger als die Hälfte des Arbeitsspeichers. An Ihren Flows, Einstellungen und am Chart ändert sich nichts.

## Was sich geändert hat

- **Function-Nodes bauen ihre JavaScript-Laufzeit nicht mehr neu auf.** Jeder Function-Node hielt seinen eigenen kleinen Vorrat an Laufzeiten, und der Garbage Collector von Go leerte jeden dieser Vorräte in jedem Zyklus. Ein Flow mit Tausenden Function-Nodes baute dadurch für fast jede Nachricht eine neue Laufzeit, und der dabei entstehende Müll löste die nächste Sammlung aus. Das Profil eines Flows mit 12.000 Nodes legte 41 % seiner CPU genau dorthin. Die Laufzeiten kommen jetzt aus einer gemeinsamen Liste, die der Collector nicht leeren kann. Eine Laufzeit, deren globales Objekt eine Funktion verändert hat, wird verworfen und nie an einen anderen Node weitergegeben.
- **Eine wartende Nachricht braucht 24 Bytes statt 64.** Der Eingangspuffer jedes Nodes wird beim Start des Nodes mit allen 1.024 Plätzen angelegt, daher waren die Puffer in einem Flow mit 12.000 Nodes allein etwa 800 MB Speicher, die der Collector in jedem Zyklus durchsuchen musste. Jetzt sind es etwa 300 MB.
- **Das Dashboard bereitet keine Updates mehr vor, die niemand sehen kann.** Ohne offene Seite baute das Dashboard zehnmal pro Sekunde ein JSON-Update jedes geänderten Widgets und verwarf es. Jetzt löscht es die Änderungen und baut nichts. Eine später geöffnete Seite startet trotzdem mit dem vollständigen Zustand, einschließlich der Punkte.
- Das Budget wird durch eine feste Spinschleife skaliert, sodass eine langsamere Maschine nicht bestraft wird. Es schlägt auf 2.16.1 fehl.
- **Der Helm-Index behält jede veröffentlichte Version.** Beim Veröffentlichen eines Charts wurde `index.yaml` früher allein aus der neuen Version neu gebaut, sodass ein Kunde, der auf einem älteren Chart festgelegt war, nicht mehr rendern konnte, sobald ein neueres erschien. Jetzt bleibt jede Version erhalten, die Pages hält.
- **Die Browser-Tests warten bis zu 20 Sekunden pro Prüfung.** Auf einem ausgelasteten Runner brauchte die Seite länger als die voreingestellten 5 Sekunden, um einen vom Runtime gesendeten Wert anzuzeigen. Das ändert nur die Tests.

## Was es behebt, mit Zahlen

Gemessen auf einer Maschine, am selben synthetischen Flow, bei etwa 2.930 Nachrichten pro Sekunde und ohne verbundenen Client:

| <span class="sr-only">Details</span> | 2.16.1 | 2.16.2 |
|---|---|---|
| Genutzte CPU | 0,79 Kerne | 0,29 Kerne |
| CPU pro 1.000 Nachrichten | 268 ms | 99 ms |
| Vom ruhenden Flow gehaltener Speicher | 799 MB | 333 MB |

## Neue Einstellungen

Keine.

## Upgrade

Ein einfaches `helm upgrade` auf das Image und Chart 2.16.2, oder der neue Tag in Ihrer Quadlet-Unit. Beim ersten Start passiert nichts, und es muss nichts migriert werden. Eine Flow-Datei wird Byte für Byte wie bisher geladen und gespeichert. Diese Version baut das amd64-Image. Die Tags `2.16` und `2` behalten das arm64-Image, das sie schon aus 2.16.1 halten, und arm64 kommt mit 2.16.3 zurück. Wenn Sie auf arm64 sind, bleiben Sie bis dahin auf 2.16.1.
