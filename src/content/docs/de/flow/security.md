---
title: "Sicherheitshaltung"
description: "Ohne Anmeldung kein Start, exec ist aus, Datei-Knoten sind eingegrenzt, Zugangsdaten verschlüsselt. Was Flow ablehnt und wie man es bewusst abschaltet."
---

Die Regel darunter: Wer einen Flow deployen kann, kann die Maschine Dinge tun lassen, denn dafür sind Flows da. Also wird „wer einen Flow deployen darf“ vom Betreiber beantwortet, bewusst, und nie von einem Standardwert.

**Er startet nicht ohne Authentifizierung.** Keine Warnung in einem Log, das niemand liest, kein Standardwert, den man hoffentlich ändert: ein Startfehler mit der Lösung direkt daneben. Das Abschalten erfordert `HOTLOOP_FLOW_INSECURE=true` in der Umgebung, bewusst, weil eine Konfigurationsdatei das nicht allein kann: Die Datei ist der Ort, an dem ein Copy-and-paste landet. Wer es tut, bekommt bei jedem Start eine Warnung im Log, und der Editor trägt ein **no login**-Abzeichen, damit der Nächste weiß, dass die Tür offen ist.

**Die Zwei-Faktor-Anmeldung ist kostenlos und eingebaut.** Jeder Benutzer schaltet sie über die Schaltfläche Two-factor im Editor ein: den QR-Code scannen (oder den Schlüssel eintippen) in einer beliebigen Authenticator-App, einen Code zurücktippen, und von da an braucht die Anmeldung das Passwort und die sechs Ziffern. Nichts ändert sich, bis dieser erste Code beweist, dass das Telefon ihn hat, sodass eine halb abgebrochene Einrichtung niemanden aussperren kann. Ein Code funktioniert nur einmal: Der Zeitschritt, aus dem er stammt, wird gemerkt, sodass ein über die Schulter abgelesener Code in dem Moment tot ist, in dem sein Besitzer ihn verwendet, und ebenso jeder ältere Code. Dreißig Sekunden Uhrenabweichung in beide Richtungen sind erlaubt. Auch das Abschalten erfordert einen Code, sodass eine auf einem gemeinsamen Bildschirm offen gelassene Sitzung nicht reicht, um es einem Konto zu entziehen. Ein verlorenes Telefon ist ein Konto mit `auth.admin`, das `POST /auth/mfa/reset` aufruft, was mit Angabe, wer es wem angetan hat, im Audit-Protokoll landet. Registrierungen werden mit dem Zugangsdaten-Geheimnis verschlüsselt, genau wie die Zugangsdaten der Knoten. Nichts an sicherer Anmeldung ist hier eine kostenpflichtige Stufe, und das wird es auch nie sein.

**Passwörter zu erraten führt nirgendwohin.** Fünf falsche Passwörter (oder richtige Passwörter mit falschen Codes) für ein Konto von einer Adresse sperren dieses Konto von dieser Adresse fünfzehn Minuten lang, und zwanzig Fehlversuche von einer Adresse über beliebige Konten sperren die Adresse. Die Kontosperre gilt bewusst pro Adresse: Sperrt man das Konto überall, kann jeder, der den Port erreicht, den echten Bediener von der anderen Seite des Werks aussperren. Gesperrte Versuche erhalten ein 429 mit `Retry-After`, noch bevor das Passwort überhaupt geprüft wird, und die Sperre und jeder Versuch, den sie abweist, stehen im Audit-Protokoll. Hinter einem Reverse-Proxy trägt jede Anfrage die Adresse des Proxys, sodass das Limit pro Adresse dann für alle zusammen gilt; das ist die sichere Art, falsch zu liegen, und die Zahlen stehen in `auth.lockout`. Es gibt keine Einstellung, die es abschaltet.

**Sitzungen überleben einen Neustart.** Früher lagen sie im Speicher, sodass jede Pod-Neuplanung und jedes Upgrade alle abmeldete, und wer gerade einen Flow ändern musste, suchte stattdessen nach einem Passwort. Jetzt liegen sie in `data/sessions.json`, nur als SHA-256-Hashes, sodass die Datei ein Token beweist, wenn eines vorgelegt wird, und für jeden, der sie kopiert, nutzlos ist. Eine Sitzung merkt sich, wer, nicht, was er darf: Nimmt man eine Berechtigung oder einen Benutzer aus der Konfiguration, weiß es die nächste Anfrage.

**Senden Sie das Token in einem Header, nicht in einer URL.** Ein Browser kann beim WebSocket-Handshake keinen `Authorization`-Header setzen, daher trug der Ereignisstrom des Editors sein Token früher in der Query-String, und genau dort bewahren Zugriffslogs, Proxys und der Browserverlauf Dinge auf. Jetzt bietet er das Token als zweites WebSocket-Subprotokoll neben `hotloop-flow` an, `hotloop-flow.bearer.<token>`, ein Header, den gewohnheitsmäßig nichts protokolliert, und der Server antwortet mit `hotloop-flow`. Ein Skript, das weiterhin `?access_token=` sendet, funktioniert weiter, weil es bei einem Upgrade zu brechen schlimmer wäre, und der Server protokolliert bei jeder solchen Verbindung eine Warnung, die sagt, was stattdessen zu senden ist. Flow schreibt die URL oder das darin enthaltene Token nie in sein eigenes Log oder das Audit-Protokoll.

**Alles, was zählt, hinterlässt eine Spur.** Anmeldungen, fehlgeschlagene Anmeldungen (mit der Angabe, ob der Name überhaupt existiert, was ein Client nie erfährt, ein Betreiber aber wissen sollte), Abmeldungen, Deploys, abgelehnte Deploys, Rollbacks, Injects, MCP-Tool-Aufrufe und das Speichern der Flow-Tests gehen nach `data/audit.log`, je eine JSON-Zeile, auf den Datenträger synchronisiert, bevor die Anfrage beantwortet wird. Jede sagt, wer, von welcher Adresse und was: Ein Deploy verweist auf seinen Deployment-Eintrag, ein Inject nennt den Knoten. `X-Forwarded-For` wird neben der Adresse des Sockets aufbewahrt und nie an deren Stelle, weil jeder diesen Header senden kann. `GET /audit` liest es, das Neueste zuerst, gefiltert mit `?event=` (`login.` für jede Art von Anmeldung), `?user=`, `?since=` und `?limit=`, und es erfordert seine eigene Berechtigung `audit.read`, denn deployen zu dürfen heißt nicht, lesen zu dürfen, wer sich sonst angemeldet hat. Es rotiert nach Größe (`audit.maxBytes`, `audit.keep`), damit eine stark ausgelastete Instanz ihr Volume nicht füllen kann, und ein Protokoll, das nicht geschrieben werden kann, stoppt nie die Aktion, die es aufzeichnete: Es wird protokolliert und in `hotloop_flow_audit_write_failures_total` gezählt, das für immer null sein sollte.

**Der `exec`-Knoten wird deaktiviert ausgeliefert.** Ein Betreiber benennt die Befehle, die ein Flow ausführen darf, und ein aktivierter Knoten mit leerer Allowlist ist ein Startfehler, keine Lizenz, alles auszuführen. Die Allowlist wird mit dem **aufgelösten absoluten Pfad** verglichen, nicht mit der Zeichenfolge, die der Flow getippt hat. Vergleicht man Zeichenfolgen, fragt ein Flow nach `curl` und bekommt das `curl`, das in einem `PATH` zuerst steht, den ein Function-Knoten lesen und ein Sidecar beeinflussen kann. Und es gibt keine Shell. Die Befehlszeile wird nur nach Anführungszeichenregeln zerlegt, und ein nicht in Anführungszeichen gesetztes Shell-Metazeichen (`|`, `&`, `;`, `$` und Verwandte) wird abgelehnt, statt als Literal durchgereicht zu werden und auf das Beste zu hoffen. Also ist `ping -c1 10.0.0.1; rm -rf /data` ein Fehler, nicht zwei Befehle.

**Die Datei-Knoten sind auf das Datenverzeichnis beschränkt.** Symlinks werden über das längste vorhandene Präfix des Pfades aufgelöst, was das offensichtliche Loch schließt: einen Symlink unter das Volume legen, der auf `/` zeigt, und direkt hindurchlesen. Eine einfache Präfixprüfung winkt das ohne Zögern durch, und dann kann ein Flow alles lesen, was der Prozess lesen kann.

**Geheimnisse haben ihren eigenen Geltungsbereich, und es ist nicht der der Datei-Knoten.** Eine tls-config liest ihr Zertifikat, ihren Schlüssel und ihre CA über `secrets.allowedPaths`: das Datenverzeichnis plus das, was Sie auflisten. Hängen Sie das von cert-manager erzeugte Secret dort ein, und die TLS-Konfiguration nutzt den Schlüssel, während kein Flow ihn lesen kann, denn alles, was über diesen Geltungsbereich gelesen wird, landet in einem Handshake, nie in einer Nachricht. Legen Sie denselben Schlüssel stattdessen unter `files.allowedPaths`, und jeder Flow mit einem File-In-Knoten kann ihn abholen und an jeden schicken, den er mag.

**Ein Passwort kann in einem Secret statt im Flow liegen.** Die Zugangsdaten jedes Knotens können eine Datei benennen, statt den Wert zu enthalten:

```json
{"id": "b1", "type": "mqtt-broker", "broker": "plc-broker", "user": "line3",
 "ew_credentialFiles": {"password": "/etc/hotloop-flow/secrets/plc-broker/password"}}
```

Die Datei wird beim Start des Knotens über denselben Geheimnis-Geltungsbereich gelesen. Ein abschließender Zeilenumbruch wird entfernt, weil `echo` ihn hinterlässt und ein Passwort mit Zeilenumbruch am Ende eine Anmeldung scheitern lässt, ohne dass im Log steht, warum. Die Flow-Datei, das Deployment-Log, das Diff und ein Git-Mirror tragen den Pfad und nie das Passwort, sodass der Flow in Git liegen kann und das Passwort dort bleibt, wo derjenige, der den Cluster betreibt, Passwörter ohnehin aufbewahrt. Eine fehlende oder außerhalb des Geltungsbereichs liegende Datei lässt das Deployment dieses Knotens scheitern, statt ihn ohne Passwort verbinden zu lassen. Das Chart hängt Secrets für Sie unter `secrets.mounts` ein. Ein rotiertes Secret wirkt beim nächsten Deployment oder Neustart.

**Zugangsdaten sind AES-256-GCM, mit Argon2id abgeleitet.** GCM lehnt eine manipulierte Datei rundweg ab, statt sie zu etwas zu entschlüsseln, das ein Angreifer ausgewählt hat, und Argon2id lässt jeden Versuch gegen ein schwaches Geheimnis 64 MiB Speicher kosten. Die Flow-Datei wird temporär geschrieben, fsync, umbenannt, fsync des Verzeichnisses, drei Sicherungen tief, sodass ein Stromausfall mitten im Speichern die alte oder die neue Datei hinterlässt, nie die Hälfte von jeder. Liest er je eine beschädigte, weicht er auf eine Sicherung aus und sagt es laut.

**Die Discovery-Knoten sind standardmäßig aus** und durch eine vom Betreiber konfigurierte CIDR-Allowlist begrenzt. Ein Hostname, der zu einer Adresse im Geltungsbereich und einer außerhalb aufgelöst wird, wird rundweg abgelehnt, weil DNS sonst nur der Weg um die Allowlist herum ist.

**Der Function-Knoten hat nichts, wohin er greifen könnte.** Er läuft auf einem JavaScript-Interpreter in reinem Go ohne Host-Anbindungen, es sei denn, jemand fügt sie hinzu, und das hat niemand getan. Kein `require`, kein `process`, kein `Buffer`, kein Dateisystem, kein Netzwerk, und ein Test führt den klassischen Ausbruch über die Konstruktorkette aus, um zu beweisen, dass er nichts erreicht.
