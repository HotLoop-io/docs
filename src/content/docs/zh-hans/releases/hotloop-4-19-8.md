关于 4.19.5 之前发生的变化(4.19.5 是 4.19.4 的多架构构建),请读 [4.19.4 的说明](/zh-hans/releases/hotloop-4-19-4/)。

这次构建只有 amd64,下一个版本是一次小的版本号提升,用来构建 arm 镜像,两轮就是这样进行的。在此期间 `stable` 保留它已有的 arm 镜像。

## 4.19.8 中还有

- **Logbook 的 Older entries 按钮不再因为一次实时刷新而丢掉它的页面。** 每当实时推送说有新内容,Logbook 就会重新取最新一页。一条日志行在较旧页面还在路上时到达,会触发那次刷新,而屏幕会因为较旧的页面属于对列表的较早一次查看而把它丢掉:按钮什么也不做,点击丢失。当时恰好写入日志行的任何工厂(这个窗口就是较旧请求自己的耗时)都会碰到这个问题,旧界面和新界面都一样。现在刷新会等较旧的页面落地,之后只有在没有更旧内容到来时才运行。一个浏览器测试把较旧的请求扣在网络上,让一条日志行到达、屏幕刷新,然后放行该页面,要求它被并入列表;它在 4.19.7 的画面上失败,在这些画面上通过。

- **每个选择 tag 的地方都搜索整个工厂,没有一个在某个数字处被截断。** 在一台有 2232 个 tag、分布在三台设备上的测试机上(4.19.5),Tags 画面只显示了其中 200 个,全部来自第一台设备,Trends 的选择器有 201 个选项,设备的 Details 抽屉在一张写着 1105 个 tag 的卡片旁边写着“No tags on this device”,而搜索前 200 个之后的 tag 会显示“No tags match”,虽然 `/api/tags?q=` 返回了它。4.19.6 的 tag 列表改动(最高 5000 的 limit 以及超出即拒绝、offset、`X-Total-Count`、读取每一页的页面、带计数的窗口)修复了这些问题,它们都在这个版本里。4.19.8 新增的是:仪表板卡片编辑器的 tag 字段(Gauge、Value、Trend、Map 以及 Button 的可写 tag)原来是在前 3000 个 tag 处被截断的建议,所以在超过 3000 个 tag 的工厂里,有的 tag 永远不会被提供;现在它们是服务器在键入文字时做的搜索(最多 100 个匹配,`GET /api/tags?q=&limit=100`,以及写入选择器用的新过滤器 `writable=true`)。一个有 3200 个 tag 设备的浏览器测试,能从 Tags 的搜索框、设备抽屉、Pin a tag 选择器、Trends 选择器和卡片编辑器里找到第 200 个之后的 tag,旧界面和新界面都是如此。

## 4.19.7 中还有(沿用)

- **每个 HotLoop chart 出厂时都开启了硬件访问。** 一个 `hardware:` 块,三个默认开启的开关:应用容器以 privileged 和 root 运行,节点的 `/dev` 挂载到 `/dev`(USB 无线电和串口适配器,包括之后插入的),节点的 `/run/dbus` 被挂载(通过节点的 BlueZ 使用蓝牙)。pod 仍留在 pod 网络上。普通安装,无论来自 App Store 还是 helm,无需手工修改就能看到插在节点上的东西。HotLoop 自己还没有蓝牙、Z-Wave 或 USB 串口的代码(Zigbee 通过 MQTT 上的 Zigbee2MQTT 到来);这是那些代码或 sidecar 将需要的访问权。它有代价:pod 在节点上是 root(NetworkPolicy 默认保持开启)。`hardware.bluetooth.hostNetwork` 是需要节点网络的场景(原始蓝牙套接字、节点自身网络上的发现)的 opt-in,默认关闭:开启后,页面在节点的每个地址上通过 `service.targetPort` 应答,每个节点每个端口一个 HotLoop,并且 NetworkPolicy 不适用于该 pod。可以用这三个开关关闭任何一部分;三个全关时,渲染结果逐行就是 4.19.6 渲染出的 pod。参见 [DEPLOYMENT.md 中的 Hardware](/zh-hans/install/helm/#硬件usb-无线电串口适配器和蓝牙)。Edge Relay 的 chart 有同样的块。
- **UniFi 地图和 Entities 条不再写出“null”这个词。** 一个把缺失值交给 `append` 或 `replaceChildren` 的脚本把它写成了文本:UniFi 地图上方有一个“null”,没有选中节点时 Entities 健康条里也有一个。已修复,并且现在浏览器测试会在每个画面上对任何只是 null、undefined、NaN 或 [object Object] 的文本节点报失败。

## 变更内容

- **Tags 画面和每台设备的抽屉都能到达每台设备的每个 tag。** 页面向服务器请求 2000 个 tag,服务器把任何超过 1000 的 limit 悄悄变成 200。在一个有三台设备和 2232 个 tag 的工厂里,Tags 画面只有 200 个,全部来自第一台设备,其他设备的抽屉写着“TAGS 0”和“No tags on this device”。`GET /api/tags` 现在接受 `limit`(1 到 5000;其他任何值,包括 5001,都是 `400`,绝不会给出更少的回答)和 `offset`,在 `X-Total-Count` 响应头中给出总数,并且同时接受 `device` 和 `q`,所以客户端可以翻页到最后并且知道自己做到了。页面读取每一页,绘制列表的一个窗口(Tags 中 500 个,抽屉和 pin 选择器中 200 个),并在下面说明一共有多少个,还有一个按钮用于其余部分。同样的悄悄上限也存在于历史列表中(自动化运行、报警事件、写入审计、脚本运行、配方应用、报告运行):超过其上限的 limit 会悄悄变成默认值,是所请求数量的十分之一。现在它就是上限。MCP 的 `list_tags` 工具也有这个问题,现在它使用给它的 limit。
- **实时推送只发送变化的内容,经过压缩,按页面处理。** 驱动在每次轮询时读取每个 tag,推送会把它们全部发出,变没变都一样,每秒四次:一台测试机的 2232 个 tag 每次约 150 KB。一个在 85 KB/s 链路上的页面会落后几分钟,因为消息排在当前消息之前。`values` 事件现在只携带在值、文本、单位、质量或原因上与上一次发送不同的读数,并在 30 秒后重发一个未变的读数,让稳定值的存续时间保持真实。浏览器接受时,数据流使用 gzip:一台测试机的第一张画面约 326 KB 的 JSON,线路上约 11 KB。每个页面的读数按 tag 保存,只保留最新的,直到它自己的写入端能够发送,写入端会休息与其上一次发送同样长的时间(最多五秒),所以慢链路上的页面只落后工厂一两次发送,什么也不丢,也不占用其他页面的任何东西。在以 300 KB/s 读取的链路上,每个 tag 每 250 ms 变化一次,一个页面在 4.19.5 里落后 27.8 秒,在 4.19.6 里落后 3.7 秒。
- **设备卡片上的轮询计数和 Board 的数字会动了。** 它们原来是页面加载时的数字。它们不走实时推送,它们背后的刷新(每 30 秒)也不重绘任何东西。现在页面可见时每两秒请求一次,一次一个请求,屏幕就地更新它的数字,所以你手下的按钮不会被替换。设备抽屉从同一个列表读取它的计数器。

## 读取推送

当请求说 `Accept-Encoding: gzip` 时,`GET /api/stream` 会发送 `Content-Encoding: gzip`,不这样说的脚本像以前一样得到纯文本。`values` 事件仍然是 `GET /api/values` 形状的读数数组;只是它不再重复没有变化的那些,所以用快照和事件重建自己画面的客户端不需要任何不同的东西。

## 已知

- **Kafka 或 Redpanda 历史目标,如果其 broker 因缺少磁盘而拒绝每次写入,会报告“records have timed out before they were able to be produced”,而不说明原因。** 读数不会丢失:目标保留这一批,以增长的等待时间重试(一秒到三十秒),记下欠的区间,并在 broker 应答时从 HotLoop 自己的历史中追赶,它的状态和系统事件说明它已下线。当其下的磁盘空闲少于 `storage_min_free_bytes`(默认 5 GiB)时,Redpanda 会拒绝写入,并且只在它自己的日志里这样说(“rejecting produce request: no disk space”)。在这种情况下,客户端库不会把拒绝的代码交给 HotLoop(它会回退、提高 producer epoch 然后重试),所以这个版本里没有诚实的办法点出原因;设计在 bead bc49eb 里。如果一个 Redpanda 目标带着这条消息下线,请查看 broker 的日志和它的磁盘。
