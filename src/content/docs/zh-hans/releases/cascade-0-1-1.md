## 这是什么

0.1.1 是第一个不是候选版本的发布。曾经有一个 0.1.0 标签,但它从未发布任何内容:在任何东西到达镜像仓库之前就被取消了。标签留在原处不动,所以这是同一份代码,现在已发布。

它是什么:我们想要的、用在工厂现场的工作流引擎。一个静态 Go 二进制文件,单机用 SQLite,需要更多时用带 worker 的 Postgres,编辑器就内置在二进制文件里,没有别的要运行。

## 包含什么

引擎把每一步都保存为检查点,所以运行中途 `kill -9` 之后,会从中断的地方继续。持久等待、重试、错误端口和错误工作流。表达式,以及在独立进程中隔离运行 JavaScript 的 Code 步骤。

带持久收件箱的 Webhook,无论有多少个主节点在监视,每个时间槽都只触发一次的计划任务,MQTT,以及用于目录中新到文件的触发器。适用于任何带 API 的服务的 HTTP 步骤,以及 HotLoop、Postgres、EmberOps、电子邮件、ntfy、Gotify 和 Discord 的连接器。没有别的了,这是有意为之。

支持密钥轮换的凭据保管库,覆盖工厂所需各种授权方式的 OAuth2,密码、TOTP、通行密钥或你的 OpenID Connect 提供商登录,强制 MFA,项目和角色,可验证的审计日志,每次保存都留作一个版本,以及带作用域的 API 和 OpenAPI 文档。指标、追踪和探针,让除我之外的人也能知道什么时候卡住了。

## 运行方式

镜像支持 amd64 和 arm64。如果你想要一个不会移动的部署,就按上面的摘要值拉取。

在 k3s 上:使用 Helm chart,可以单独部署,也可以拆成 server 和 worker。

在普通机器上:使用 `deploy/quadlet` 下的 Quadlet 单元,单机用 SQLite,需要更多 worker 时用 Postgres。它们跟随 `:stable`,由 Podman 的自动更新定时器推进。启动后不健康的更新会回退到之前运行的镜像。我们真实运行过两种形态,在 systemd 下的 Podman 5.8.7 上:启动会等到健康,被杀掉的容器会回来,正常的更新会落地,有问题的更新会回滚,每次之后都有一个工作流运行成功。

## 需要了解的事

迁移只会向前。回滚只是把旧镜像放回去,并不会撤销数据库的迁移,所以在开启更新之前请先备份。

这个版本的镜像仓库是私有的,所以需要先以 root 身份执行 `podman login ghcr.io`。镜像和 chart 从 0.1.2 起公开,无需登录即可拉取。

如果丢失了用来加密存储凭据的密钥,所有已存储的凭据都将无法读取。请把副本保存在这台机器之外的地方。
