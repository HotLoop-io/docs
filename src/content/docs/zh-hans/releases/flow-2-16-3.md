HotLoop Flow 2.16.3 让仪表盘图表所占用的 CPU 不再随 Flow 运行时间变长而增加。在一个运行约 13,700 个节点、每秒约 3,000 条消息的工厂里，2.16.2 起始于约 130 毫核，两小时内升到约 420。原因是仪表盘为稍后打开的页面保存的图表历史。您的流程、设置和 chart 都不会有任何变化。

## 变更内容

- **图表的一个数据点不再复制整张图表。** 图表收到的每个点，都会重建该图表的点列表，并数遍所有点来应用每条线的上限。一个点的开销随已保存的点数增长，所以它在第一个小时里不断上升，直到图表装满它所保留的全部内容，然后就停在那里。在一张有四条线、每条 4,800 个点的图表上，一个点约耗时一毫秒，产生三兆字节垃圾；按工厂每秒 96 个图表点计算，这相当于每秒约 260 MB 垃圾，每三秒一次回收周期。现在每条线都是自己的列表，通过切片丢弃旧点，所以一个点在空图表和满图表上的开销相同。
- **页面打开时得到的内容不变。** 点按各条线首次出现的顺序到达，已经安静下来的线仍会随老化而退出所发送的内容，每条线的上限（`removeOlder`、`removeOlderPoints` 以及每条线 5,000）不变。
- 除非设置了该变量，否则会被跳过。仪表板包中的一个单元测试会在 16,000 个点的完整图表中任意一个点分配超过 4 KB 时失败；在这个版本之前它测得是 191 KB。

## 它解决了什么，用数字说话

在工厂自己的 pod 上，2.16.2 的回收周期从最初 90 分钟的每秒 0.11 次升到每秒 0.37 次，CPU 从约 130 升到约 420 毫核。满图表上一个点的开销，在一台机器上测得：

| <span class="sr-only">详情</span> | 2.16.2 | 2.16.3 |
|---|---|---|
| 一条 4,800 个点的线 | 157 微秒，535 KB | 0.14 微秒，217 字节 |
| 四条 4,800 个点的线 | 1.1 毫秒，2.9 MB | 0.11 微秒，106 字节 |

## 新设置

无。

## 升级

直接 `helm upgrade` 到 2.16.3 的镜像和 chart，或者在您的 Quadlet 单元里换成新标签。首次启动不会发生任何事，也不需要迁移。流程文件的加载和保存与以前逐字节一致。这个版本构建 amd64 镜像。`2.16` 和 `2` 标签保留它们从 2.16.1 就已有的 arm64 镜像，arm64 在 2.16.4 中回归。如果您用的是 arm64，请在那之前留在 2.16.1。

镜像：`ghcr.io/hotloop-io/hotloop-flow:2.16.3`，linux/amd64。Chart：`https://hotloop.io/hotloop-flow/`。这个标签的 README 有其余内容，还配有图片：https://github.com/HotLoop-io/hotloop-flow/blob/v2.16.3/README.md
