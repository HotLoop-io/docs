4.19.0、4.19.1、4.19.2 和 4.19.3 都打了标签但从未发布,所以没有任何东西叫这些名字,`stable` 也从未移动到其中任何一个。这是第一个包含它们说明里所列全部内容的版本,其中有一件事是自 4.19.1 以来的新增:chart 接受 `hostNetwork`。

- 4.19.1 加入了对此的修复和另一项(一个在能听到之前就说自己已就绪的发现监听器,见下文),并在发布之前被跳过。
- 4.19.2 加入了 `hostNetwork`。
- 两者都在下面修复了。
- 4.19.0 说明里的所有内容(MCP、带缩放的写入、商店登录、CODESYS、Kafka 事件流、基于 UADP 的 OPC UA PubSub 以及各项修复)都在下面的说明里。

自 4.19.1 以来的新内容:chart 有了 `hostNetwork` 设置。

## hostNetwork

每个带 pod 的 HotLoop chart(Gateway、IoT、Edge 的 chart 以及 Edge Relay 的)都接受 `hostNetwork: true`。默认关闭,关闭时 chart 渲染的结果与 4.19.1 的完全一样。

- **它的用途。** 用于一个必须听到其节点所听到内容的 pod:节点 loopback 上的 UDP 组播(同一台设备上的 PLC 运行时通过 loopback 向组播组发布 OPC UA PubSub),或第二块网卡。pod 网络两者都不承载。
- **它做什么。** Deployment 得到 `hostNetwork: true` 和 `dnsPolicy: ClusterFirstWithHostNet`,所以集群的 DNS 名称仍可解析。
- **对 pod 意味着什么。** 它使用节点的地址和端口:页面在节点的每个地址上通过 `service.targetPort` 应答,所以请选一个节点上没有其他东西使用的端口,并保持认证开启。NetworkPolicy 不适用于 host-network 的 pod(集群的网络插件会忽略它们)。用 `nodeSelector` 把 pod 固定在它的节点上。
- **loopback 上的监听器。** OPC UA PubSub 订阅者按名称或地址加入某块具名网卡上的组:设备选项里的 `"interface": "127.0.0.1"` 会在 loopback 网卡上加入。
- **仅此而已。** 代码就是 4.19.1 本来会发布的代码。发布守卫现在会在有和没有这个设置两种情况下渲染每个 chart,任何一种渲染不对就会失败。

这个版本的其余内容,来自 4.19.0 和 4.19.1:

4.19.4 里有两件事会改变现有工厂的行为,所以在动手处理正在运行的工厂之前请先读它们。通过 MCP 的代理现在可以写入,而且 MCP 端点总是有 token。并且你写入带缩放 tag 的值终于会按你的本意落进寄存器,这意味着任何绕过旧行为的人都必须停下来。这两件事之后的一切都是新增或修复。

完整说明在 README 里:4.19.4 的变化。

### MCP 已开启,它能写入,并且总有 token

- **在 operator 能写的地方,代理现在也能写。** MCP 在每个 HotLoop 产品中都已开启,并且可读可写。`allowMcpWrites` 在代码和全部三个 chart 里默认是 true。一个 `allowWrites` 已开启、从未设置过 `allowMcpWrites` 的部署,在这次升级后会得到代理写入,经过与屏幕相同的关口:用户的权限、tag 的可写标记及其范围仍然全部适用。
- **`allowWrites` 没有变。** 它默认仍然关闭,并且仍决定任何东西能否写入,界面和代理都一样。如果它关闭,包括 MCP 在内什么都不能写。
- **保存了 `allowMcpWrites: false` 的部署保持关闭。** 这包括从 App Store 安装的部署,它会保存每个回答。如果你希望代理写入,请把它切换过来。
- **端点永远不会是开放的。** chart 总会设置 MCP token。一个没有 `HOTLOOP_MCP_TOKEN` 启动的 HotLoop(Quadlet 单元、裸二进制)过去会向任何能到达该端口的人提供 `/mcp`,只记录一条警告。现在它在第一次启动时生成一个 24 字节的 token 并保存在自己的数据库里,所以每个副本和每次恢复都带着同一个 token。不带 token 的调用是 `401`。你配置的 token 永远不会被替换。
- **在裸安装或 Quadlet 安装上获取 token:** `hotloop mcp-token` 会打印它。如果你有一个指向这类安装上 `/mcp` 的代理且没有 token,它会在这次升级后停止工作,直到你把那个 token 给它。这是有意为之。
- **谁发起了调用。** 静态 token 只说明是哪个客户端调用的,从不说明是哪个人。开启 OIDC 设置后,`/mcp` 上的 Vord 登录或 hub assertion 会让审计记录点名那个人(`mcp:pat@example.com`),并且一个可选的写入角色会在上面这些开关之上按调用者进一步收窄写入。除非你设置,否则它是关闭的,token 仍与它并行工作。设置方法见 [MCP 页面](/zh-hans/iot/mcp/)。

### 对带缩放 tag 的写入

- **哪里出了问题。** 带缩放的 tag,比如一个保存十分之一度的温度寄存器上缩放 0.1,会显示工程值:寄存器说 555,屏幕说 55.5。写入则朝相反方向走,却没有同样的处理。你为设定值键入 55.5,HotLoop 把 55 放进寄存器,然后读回来是 5.5。每个画面、通过 API、来自自动化、脚本、配方、回路以及通过 MCP 都一样,因为它们都经过同一个写入关口。审计行一直写着 55.5,所以日志里看不出任何问题。
- **改变了什么。** 你写入的数字使用 tag 自己的单位,和你读到的数字一样。HotLoop 在发送之前把缩放和偏移还原:在缩放 0.1 的 tag 上写 55.5 会把 555 放进寄存器,读回来是 55.5。没有缩放也没有偏移的 tag 完全不会被动。位、线圈、字符串,以及对标志的 Sparkplug 和 MQTT 写入也不会被缩放。
- **如果你绕过了它,请停止。** 如果有人曾向带缩放的 tag 键入原始计数来得到正确的数字,键入 555 来得到 55.5,现在那会发送 5550,读回来是 555。请键入工程值。升级前先看看你带缩放的 tag:任何缩放不是 1 或带偏移、并且有人手动、通过自动化或通过配方写入的 tag,都值得看一眼。曾经写入计数的配方和自动化,需要在升级的同一步里把它们的数字改成工程值。
- **寄存器容纳不了的值会被拒绝。** 去掉缩放之后,放不进寄存器的计数,比如缩放 0.1 的 `uint16` 上的 7000,会被拒绝,并给出点明计数和寄存器的清楚消息,什么也不会发送。过去它会悄悄回绕:16 位寄存器上的 70000 会以 4464 发出。这适用于 Modbus、S7、EtherNet/IP 和 OPC UA 的整数类型。
- **带有放不下的值的配方会整个被拒绝。** 在第一次写入之前会检查每个目标,所以配方不会应用到一半再拒绝。对于 Modbus、S7 和 EtherNet/IP,检查会从每个 tag 的地址得知其寄存器类型。对于 OPC UA,也就是通往 CODESYS 运行时的路径,它使用 tag 最近一次读数到达时的类型。自 HotLoop 启动以来从未被读取过的 tag 还没有可供检查的类型,所以以它为目标的配方会在该 tag 自己的写入处被拒绝,此时它之前的目标已经写入,应用会记录是哪些。把它读一次就能解决,轮询会在连接后一秒内完成这件事。
- **计数的小数部分会被截掉。** 寄存器保存整数计数,所以在十分之一缩放的寄存器上写 12.34 保存的是 12.3,一直如此。
- **没有改变的。** tag 的范围检查和审计行使用你键入的数字。写入关口、权限和拒绝规则都一样。

### 商店安装会让你以自己的身份登录

chart 过去在 tenant 读不到的 Secret 里生成一个随机的管理员密码,所以商店安装会落在一个无路可走的登录页面。配置了仪表板的公钥后,携带针对此 tenant 和此 Service 的有效签名 assertion 的请求会让那个人登录,首次登录时创建他们的用户,让他们的角色与仪表板发送的保持同步,审计记录会写下他们的名字。无效、过期、tenant 不对或应用不对的 assertion 会被拒绝,本地登录不受影响。除非设置了密钥,否则它是关闭的,三个产品 chart 都从商店取得密钥。设置见[认证与用户](/zh-hans/iot/authentication/)。

### CODESYS,使用程序员给变量起的名字

HotLoop 按 CODESYS 文档所述,通过运行时自己的 OPC UA 服务器读写 CODESYS PLC:应用的 Symbol Configuration,在 PLCopen IEC 61131-3 模型下发布。发现功能会列出应用导出的内容,带有程序员给它们的类型和访问权限,并深入数组和结构,而 tag 是一个 IEC 符号,可以在项目给它的 PLC 和应用起的任何名字下找到。重启、下载或丢失的链路会被读成坏并附上原因,无需人工干预就会恢复。我们在测试中对一个真实的 4.22.0.0 运行时做了验证,运行我们自己的程序,并带有一次由 PLC 自己的逻辑应答的写入,还对第二个有超过十万个变量的程序做了验证,读取用了 2.4 秒。

这涉及工厂正在运行的驱动,所以直说:OPC UA 驱动每次请求 200 个节点,从不读取服务器允许的上限。CODESYS 运行时发布的 OperationLimits 是 100,超过就拒绝,而驱动的回应是把每个发现的 tag 都声明为 float,并且完全不读取一个超过一百个 tag 的设备的任何 tag。现在请求会按服务器在连接时发布的上限切分,并且在一个没有发布上限的服务器说太多时减半。作为标准类型子类型的数据类型(CODESYS 的 STRING、BYTE 或 TIME)会一直追到标准类型,所以按那个类型确定类型并写入。每个 OPC UA 设备都会得到这一点,而不只是 CODESYS 设备。

### Kafka 事件流

- **它是什么。** HotLoop 可以把它的读数和系统日志发送到任何使用 Kafka API 的 broker:Apache Kafka、Redpanda 以及那个家族里的其他成员。它是一种新的 historian 目标,位于 Settings、Historian targets 之下,所以有那些目标所具有的队列、从 HotLoop 自己的历史中追赶以及状态。读数发往一个 topic,系统日志(报警、设备上线和下线、变更)发往另一个,格式为 JSON。
- **TLS 和 SASL。** SCRAM-SHA-256、SCRAM-SHA-512 和 PLAIN(PLAIN 仅在 TLS 上),如果 broker 的证书不是公共 CA 签发的,可以使用你自己的 CA。客户端证书、Kerberos 和 OAuth 登录尚不支持。
- **至少一次。** 中断之后,一个读数可能到达两次,因为追赶有意与已经发出的内容重叠。`deviceId`、`tag` 和 `ts` 可以标识重复。事件是实时推送,没有可供追赶的历史,所以在 broker 不在时产生的事件会丢失,目标的状态会计入。
- **写入中途消失的 broker。** 目标会在 25 秒内变为下线,那次写入中的读数记为尚欠,而不是保持上线、队列不断溢出。
- **刚刚创建的 topic。** 第一次查看一个刚创建的 topic,无论是你创建的还是目标自己上一次尝试创建的,都会等它存在并有 leader,而不是报告目标下线。
- **代价。** 每个带数据库的产品的二进制增加约 5 MiB。Edge Relay 没有 historian 目标,所以不带它。客户端是 franz-go,在 `NOTICE` 中注明。
- **升级。** 迁移 0026 给 historian 目标增加一个 `options` 列,对每个已有的目标都是空的。对它们没有任何变化。记录格式以及哪些已验证哪些没有,见 [Historian 目标](/zh-hans/iot/historian-targets/#kafka-api事件流)。

### 基于 UADP 的 OPC UA PubSub

- **订阅。** 协议为 `opcua-pubsub` 的设备监听发布者通过 UDP(单播或组播)以 UADP 发送的 DataSet。tag 的地址是 `<DataSetWriterId>/<field index>`。支持 Variant、DataValue 和 RawData 字段,以及 key、delta 和 keep alive 帧。丢失一条消息会把该 writer 的 tag 标为不确定,直到它的下一个 key 帧,静默的 writer 会被读成坏。
- **发布。** Edge 和 Gateway 可以把 layout 所指定的 tag 以 UADP 发布,在设置 `HOTLOOP_UADP_PUBLISH_ENABLED` 之前是关闭的。值变化时发 key 帧,不变时发 keep alive。坏的 tag 会以它的状态发布,绝不以它的最后一个值发布。
- **尚未支持。** 消息安全(签名或加密的消息)会被点名拒绝,分块消息、发现、事件和结构字段也一样。delta 帧会被读取但不发送。
- **数组。** 数组字段在 Variant 和 DataValue 消息中会被读取,在设备的 DataSet 说明了其布局时,RawData 中也会被读取(带个数的数组用 `"Float[250]"`,250 个独立字段用 `"Float*250"`)。tag 指向一个元素,如 `1000/3[17]`,Browse 会列出它们。
- **它在哪里监听。** 组、端口和网卡都是设备自己的。具名网卡上的组播组和这台机器上的单播端口都可以使用。
- 设置和限制见[协议与驱动](/zh-hans/iot/protocols/#opc-ua-pubsub-uadp)。

### 镜像,以及第二套画面

- **这一次只有 amd64。** 4.19.4 的镜像是为 amd64 构建的。版本标签只列出 amd64,而 `stable` 和 `latest` 在已有的 arm64 和 arm/v7 镜像(它们是上一个版本的)旁边带有新的 amd64 镜像。跟随 `stable` 的 arm 设备盒会继续拉取并继续运行它原来运行的东西。下一个版本会重新构建所有架构,并且只是一次版本号提升,没有别的内容。
- **新画面在 `/next`。** 每个镜像里都有一个重建的 Web 界面,排在旧界面之后,`/` 上得到的仍是旧界面。在任何安装上都可以在 `/next` 试用;默认的不会有任何变化。

### 修复

- **进程不再因为自己发出的停止信号返回而停掉脚本的下一次运行。** 停止脚本会通知每个进程,包括发起停止的那个进程,片刻之后再次听到的通知会取消当时正在进行的那个脚本的运行:在负载下,一次在等待的运行在开始 8 ms 后被取消,另一次始终没有结束。进程会忽略自己发出的停止,而另一个进程发出的停止仍会停掉它。
- **发现监听器只在 broker 回复了它的订阅之后才算就绪。** 超时的等待曾被算作回复,在已断开的连接上收到的回复也是如此;现在两者都不算,迟到的回复仍然算。
- **发现监听器在能听到时才说自己就绪。** MQTT 会话在 broker 接受它的瞬间就把自己算作已连接,然后才发出订阅并等待 broker 授予。一个据此报告就绪的监听器会把下一条消息发进空档,设备的状态或配置若没有被保留就丢了。现在它在订阅被授予时才报告就绪,首次连接和每次重连都一样。
- **在看板上加一个 pin 不再清空看板。** 页面只在看板画面打开时读取看板,所以在 tag 画面重新加载时持有的是空列表,第一个 pin 就用那一个 tag 替换了已保存的看板。现在页面在启动时读取看板,读取之前 pin 会被拒绝,保存会带上看板的 `rev`,所以服务器对读取之后已变化的看板上的保存回答 `409`。`rev` 在 API 中是可选的:省略它,保存就不会被检查。
- **会发现停滞的 OPC UA 订阅。** 库把它的 keep alive 留给自己,所以停止的发布循环看起来像一个安静的工厂,并把它最后的值当作良好提供出去。在十个发布间隔(至少三十秒)的静默之后,驱动会读取一次节点,与它持有的值比较,只要有一个不同就退回到读取方式。
- **打开套接字却沉默的 PLC 是掉线,而不是降级。** Modbus、S7 和 EtherNet/IP 会保留最后的值直到 TCP 放弃,因为轮询在评判会话之前就返回了。现在它们会评判。测试中还没有 S7 或 CIP 服务器在线路上,路线图也这样说明。
- **键入 URL 或自由文本中的凭据会在静态存储时加密。** 每个画面都已经向人隐藏了 `mqtt://user:pass@host` 和 `?token=`,但数据库和备份是按键入的样子保存它们的。携带其中之一的字符串,按脱敏隐藏它所用的同一判断,会被整体密封,并按原样返回,所以驱动得到的仍是给它的那个 URL。稍后开启的密钥会密封之前保存的内容,恢复仅在只有地址需要它时才会询问密钥。
- **API 写出的每个时间都是 UTC。** 设为纽约的工厂写作 `-04:00`,而设为 UTC 的工厂写作 `Z`,涉及约三十个字段:`created_at`、`updated_at`、报警的 `raisedAt`、事件的时间、设备的 `lastPoll`、tag 的时间戳、logbook 条目、报告的下次运行。现在两者读起来一样。如果你在一个期望本地偏移的脚本里解析这些,它现在得到的是 `Z`。
- **每月分区在 31 号被跳过。** 历史和 logbook 的表通过给今天加一个月来创建下一个分区,而在 31 号这会跳过一个月,所以一个月的行落在默认分区里。现在它们从当月 1 号开始计算。
- **UniFi 事件日志按事件发生的时间排序,** 而不是按帧到达这里的时间,所以重连之后的回放不再排在最上面。
- **交换机的面板图可以在手机上放下。** 八个端口比 390 像素的屏幕还宽,页面会向旁边滚动 113 像素。现在端口是紧凑的方块,PoE 瓦数放在端口的详情里,而仍然超出卡片的面板图会在卡片内部滚动。
- **既没有会话也没有连接的手机会看到登录画面和原因,** 而不是一个空的应用,并在 HotLoop 应答时重新加载。
- **回滚只需一条命令。** chart 索引会合并进线上的那份,而不是从该版本自己的 chart 重建,所以较旧的版本仍能解析。

### 从 4.18.11 升级

- 在对正在运行的工厂做任何事之前,请先读上面的前两节。
- 迁移 0026 是唯一的一个。它是增量的,每个已有的行都能继续工作。
- 裸安装或 Quadlet 安装在第一次启动时会得到一个 MCP token。`hotloop mcp-token` 会打印它。
- 照常 `helm upgrade`。Quadlet 单元跟随 `:stable`,什么都不用做。对这个版本来说,`helm rollback` 到 4.18.11 没问题:数据库已经是 PostgreSQL 17,这里没有任何东西改变它。
