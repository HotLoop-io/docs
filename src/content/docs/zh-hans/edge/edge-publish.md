Edge Publish 自 4.5.0 起，把 HotLoop 变成一个 Sparkplug B **边缘节点**，通过 MQTT 把它读到的一切发布到中央 Gateway，方向与现有的 MQTT 驱动相反，后者是作为主机来消费 Sparkplug。运行它就是这个意思。

边缘发布在 Gateway 和 Edge 中默认开启，在有了 broker 和 Sparkplug 组之前保持空闲，这些可以来自 chart 或环境变量，也可以由管理员在设置的“报警和读数发往何处”中填写（见[报警通知](/zh-hans/iot/notifications/#报警发往何处设置)）。那里保存的内容优先，并在 HotLoop 启动时读取，因为发布器拥有队列文件和节点。如果没有给出任何内容，它不发布任何东西，也不会阻止 HotLoop 启动。

打开它之后，它运行在同一个 Gateway 进程内，仍然连接着 TimescaleDB，适用于现场既想在本地使用完整 Gateway 的界面和历史数据，又想向中央 Gateway 上行的情况。针对多个 Edge Relay 的设备群管理，在 4.7.0（根据它们的 Birth 和 Death 进行跟踪）和 4.8.0（配置推送）中加入；见设备群管理页面。

## 打开它

```sh
export HOTLOOP_EDGE_PUBLISH_ENABLED=true
export HOTLOOP_EDGE_PUBLISH_BROKER=mqtt.example.local:1883
export HOTLOOP_EDGE_PUBLISH_GROUP=Plant1
export HOTLOOP_EDGE_PUBLISH_NODE=press-line-3   # defaults to the pod hostname
export HOTLOOP_EDGE_PUBLISH_QUEUE_PATH=/data/forward.db
```

到达变量总线的每一条读数（与实时界面和报警评估器读取的是同一个数据流）都会作为 Sparkplug B `NDATA` 发布。只要代理可达并在确认，这一切直接在内存中进行，不会碰磁盘。当代理不再确认时，读数会进入磁盘上的转发队列，并在它恢复时按顺序从中出来。

## 它实际做什么

**先订阅，再诞生。** 在每一次连接上，无论首次还是每次重连，节点都会订阅它的 `NCMD` 主题（以及它的配置推送主题），并等代理对两者都确认之后，才发布任何东西。Sparkplug B 3.0 要求这样做（“在发送 NBIRTH 消息之前，与边缘节点关联的 MQTT 客户端必须订阅以接收 NCMD 消息”），原因很充分：主机可以用立即的 rebirth 或重启请求来回应一个 birth，而先 birth 的节点可能错过它。`Start()` 在订阅就位之前不会返回。如果代理拒绝了其中之一（某个 ACL 不让这个节点读取它自己的 `NCMD` 主题），`Start()` 会以说明此事的错误失败；一个没有人能向它下命令的节点，不应该假装一切正常地启动。无法重新订阅的重连不会在那个会话上 birth；读数继续进入转发队列。

**代理不在，不会阻止启动。** 被拒绝是配置问题，会使 `Start()` 失败。不可达则是一次中断：`Start()` 记录日志后返回，节点在后台继续尝试（一秒，翻倍直到一分钟），而每条读数都进入转发队列。过去它在这种情况下也会失败，而 Edge Publish 启动失败时 Gateway 和 Edge 都会退出，所以在 WAN 中断期间重启的盒子会陷入崩溃循环，没有画面、没有报警、没有自动化，也没有任何缓冲，直到 WAN 恢复。

**每个连接一次 NBIRTH。** 每个已知的变量，以稳定的别名按名称宣告，并带上它的当前值。birth 发生在首次连接时、每次重连时（Sparkplug 会话重新开始，它的序号在重连之后没有意义）、当一个没人见过的变量出现在某个批次中时，以及应请求时，见下文。

**之后的一切都是 NDATA**，只用别名，不带名称。`seq` 从 birth 起以 0 开始，并随每条消息（对 256 取模）递增，直到下一次 birth。

**NDEATH** 有两种方式：在 `Stop()` 时正常发出，以及在进程没机会发出就死掉时，通过 MQTT 连接自己的 last-will。两者带有相同的 `bdSeq` 值，与它们所结束的 birth 相匹配。主机凭这个数字区分上一个会话遗留的旧死亡证明和当前的。

**`bdSeq` 统计会话，并且这个计数在重启后依然保留。** 每个 MQTT CONNECT 都获得下一个编号：队列的第一个会话为 0，之后每次加一，255 之后回到 0（Sparkplug B 3.0，Operational Behavior，Edge Node Session Establishment：`tck-id-message-flow-edge-node-birth-publish-will-message-payload-bdSeq`），并且该连接上的 NBIRTH 带有与它所注册的 will 相同的编号（`tck-id-message-flow-edge-node-birth-publish-nbirth-payload-bdSeq`）。它存放在转发队列的文件里，所以重启后的节点会接着计数，而不是从 1 重新开始，把主机已经见过的 will 再交给它，主机有权把那样的 will 当作过期而忽略。重连是一个新会话，所以也会得到新编号；旧代码在整个进程生命周期内只保留一个，因为 MQTT 客户端库会重复使用创建它时带的 will，而现在节点为每次连接尝试都新建一个客户端，因此也是一个新的 will。该指标是 INT64，与规范要求一致（它以前是以 UInt64 发出的；值放在同一个字段里，所以按值读取的主机不会察觉）。

**`NCMD` → `Node Control/Rebirth`。** 请求 rebirth 的主机会得到一个新的 NBIRTH，`bdSeq` 不变。rebirth 不是新会话，所以不会获得新编号（`tck-id-operational-behavior-data-commands-rebirth-action-3`）。

## 上行链路中断时

**磁盘是为中断准备的，不是为每一次轮询准备的。** 只要上行链路正常、代理在确认，读数就只停留在内存中，直到排空器把它们发出、代理确认它们，期间不会向磁盘写入任何东西。一旦没有会话、确认不来，或者内存将超过 100,000 条读数，内存中的所有内容就按顺序进入磁盘队列，之后的一切排在它后面，排空器从磁盘读取，最老的先读，只有在代理确认之后才把一条读数从队列中取下。只有磁盘空了，节点才回到内存，所以绝不会出现较新的读数超过较旧读数的时刻。

我们把它做了两次，第一个版本对硬件来说是错的。它在发送前把每条读数都写到磁盘，所以强制终止不会丢失节点已接受的任何东西。但它在每秒 2,000 条读数时每秒也写约 5 MB，也就是每天 450 GB，来自每秒约 160 次队列提交、每次八页。那会毁掉 SD 卡，对任何闪存来说也是荒唐的磨损量。稳态下的磁盘成本现在是零（数字在下面），而为此我们放弃的东西，在下一节中如实写明。

**链路正常时的强制终止，会丢失内存中的内容。** 在链路正常、代理在确认时，一次 SIGKILL、断电或内核崩溃，会带走尚未确认的读数。那大约是一次轮询：在每秒 2,000 条读数、确认往返几毫秒的情况下，至多几百条读数，也是主机稍后本该看到的同样数量的轮询。它们不被算作丢弃，因为没有任何东西知道它们存在过。正常停止（`Stop`、SIGTERM、重启）会先把内存中的内容写到磁盘，什么也不丢。链路被切断时两种情况也都不丢，因为链路不再确认时，节点做的第一件事就是把内存移到磁盘。这个设计唯一不覆盖的情况，是链路正常时进程死亡，而这是有意不覆盖的。

`HOTLOOP_EDGE_PUBLISH_QUEUE_MAX_BYTES` 限制中断队列，默认是 64 MiB，大约相当于每秒 2,000 条读数时两分钟的中断（下面的测试装置就在那个速率下运行：大约能放下 248,000 条读数，在 4.21.1 上测得）。超过之后，最老的读数先走并被计数。把它设为 0，队列就不受限制：进程会在启动时对此发出警告，因为在不受限制的队列上发生很长的中断，会把卷填满，而不是像 historian 自己的内存队列早已做的那样丢弃旧读数。

排空器在读数入队后几秒内取出的读数，会作为变量的当前值，与它所在轮询的其余部分一起放进一个 `NDATA` 发出。等了更久的读数，或者被一个已死亡的进程遗留下来的读数，会带着 `is_historical` 标记发出，这样主机就不会让它覆盖变量此刻的状态。重连时，队列在任何更新的内容发布**之前**排空，最老的先出，因为从中出去只有一条路。

回放是打包的：最多 200 条历史读数共用一个 `NDATA`，每个指标带有它自己的时间戳和 `is_historical`。规范允许这样做（“同一指标的多个值变化可以包含在同一个 Sparkplug NDATA 消息中 ... 只要它们的时间戳不同”，Sparkplug B 3.0，Operational Behavior，Data Publish），所以一条消息绝不会在同一毫秒内包含同一个变量两次，而是开始下一条消息。我们之所以打包，是因为每条消息一条读数就是瓶颈，性能分析也这么说：回放 CPU 的 57% 是 MQTT 客户端库对每个数据包做一次的 write 系统调用，队列中的 200,000 条读数用了 58.5 秒，每秒 3,418 条，而工厂每秒产生 2,000 条。比工厂慢的回放，就是永远追不完的积压。打包之后，同样的 200,000 条读数只需 2.9 秒，每秒 68,237 条，这是在节点仍用 QoS 1 时测得的。实时读数仍然是每次轮询一个 `NDATA`。

**如规范所说是 QoS 0，并用一次往返来确认它到达。** NBIRTH 和 NDATA 以 QoS 0 发出，且不是 retained（`tck-id-topics-nbirth-mqtt`、`tck-id-topics-ndata-mqtt`，Sparkplug B 3.0，Topics and Messages，Edge Node）。NDEATH 的 will 是 QoS 1 且不是 retained（`tck-id-payloads-ndeath-will-message-qos`，Payloads），`Stop` 发布的正常 NDEATH 也是如此。QoS 0 的问题在于没有确认：当字节到达本地套接字时，一次发布就“完成”了，而这对一条已死的链路也照样成立，所以把它当作送达，会在读数最重要的时候把它们从磁盘上拿走。节点的做法是在每个数据块后面发送一个请求（对它自己的 NCMD 主题的 SUBSCRIBE，这本来就必须被允许），并保留这个数据块，直到代理回应它。一个连接是一条有序的字节流，代理按读取顺序处理客户端的数据包，所以这个回应意味着它读完了在它之前的一切。这就是 PUBACK 曾经提供的保证，只是每个数据块一次往返，而不是每条消息一次确认。有一项测试向一条沉默的链路写入，并检查队列里没有任何东西离开，无论内存还是磁盘；没有这次往返时，其中的 30 条读数全部都走了。

**不再应答的连接会被放弃，而不是等到结束。** 如果代理不确认某个数据块，或者 MQTT 客户端库无法接受消息，节点会自己关闭那个连接，并开始一个新会话（下一个 `bdSeq`，新的 birth），所有未确认的内容都保留（如果在内存中就移到磁盘）。它必须这样做，因为一条没有 reset 就死掉的链路会一直接受写入，直到内核的发送缓冲区满，随后 MQTT 客户端库唯一的写协程就卡在一次 write 里。那个协程同时也负责发送 keepalive PING，所以 keepalive 永远不会触发，节点会在中断持续的整个期间一直待在死连接里：一次六分钟的测试切断发现，它直到链路恢复才察觉。更糟的是，一直在写入的那一轮在新连接上醒来，继续在新会话的 NBIRTH 之前，用旧会话的序号发送它旧数据块的剩余部分。现在每一轮都属于它开始时的会话，该会话结束后，它得到的是一个错误，而不是线路。

投递是**至少一次**。代理收下但从未确认的数据块会作为历史再次发送，投递与节点记下它之间发生的强制终止也会得到同样的结果。消费这些数据的主机必须能容忍重复；它绝不能假定这个队列已经替它去重。

### 它承诺什么，以及背后的数字

- **精确的顺序。** 每个变量的每条读数，都按读取的顺序到达主机，实时和回放放在一起，跨越一次 SIGKILL 和一次重启。
- **有界的文件。** 界限施加在队列的文件上，也就是会填满卷的那个东西，而不是其中的数据。队列的文件是数据加上页头、分支页、空闲列表和增长余量；在旧的界限（队列自己统计的叶子字节数）下，文件的大小是数据的两倍。小于 1 MiB 的任何值都按 1 MiB 运行，并在启动时给出警告。
- **中断期间不丢任何东西。** 一旦链路不再确认，每条读数都在磁盘上，并一直留在那里，直到代理确认，所以每条读数都能熬过一次中断、一个死连接、一次正常停止，以及中断期间的一次 SIGKILL 或断电。例外就是上面那一种：链路正常时的强制终止或断电，会丢失大约一次轮询，也就是仍在内存中的读数。
- **超出界限的丢弃响亮而且有计数。** 最老的读数先走，每一条都计入一个保存在队列文件中的丢弃计数，所以重启不会抹掉证据。它出现在 `edgePublish` 下的 `GET /api/diagnostics` 中（以及 relay 的 `/status` 的 `uplink` 下），与队列中的内容、文件大小以及回放是否在进行并排显示。发生期间日志每分钟说一次，绝不会每次轮询一次。这个计数可能比实际损失略多，绝不会少：主机在一次切断之前刚收到、但其确认始终没来的读数，在界限把它们带走时仍在磁盘上，所以即使主机已经有了它们，也会被计入。
- **仅仅被轮询过的读数，可能因链路正常时的强制终止而丢失。** 在驱动交出一条读数和代理确认它之间，它只存在于进程中，一次 SIGKILL 或断电就会把它带走。这是不把每次轮询都写入磁盘的代价，我们选择了它，而不是每天 450 GB。在没有任何东西在途时终止，答案是精确的：工厂交出的每条读数，要么被送达，要么被计数。

以上全部是用一台真实的 HotLoop Edge 测得的，它每 250 ms 轮询 20 台 HTTP 设备，每台 25 个变量（每秒 2000 条读数），并发布到真实的 Mosquitto。每台设备对每次轮询都回答一个比上一次大 1 的计数器，所以主机侧的判定器能确切知道哪条读数丢了、哪条回来了两次、哪条乱了序。上行链路是通过把代理从网络上拔掉来切断的：Edge 的套接字变得沉默，没有 reset，没有挂断。为了在没有任何东西在途时终止，工厂在 SIGKILL 之前暂停几秒（“quiesced”）；其他终止则落在轮询恰好所处的任何位置（“instant”）。运行时间为 2026-10-12，界限为 64 MiB。“Before”是 `15419f1`，也就是这项工作之前的构建。“Write-ahead”是 `165411f`，它先把每条读数写入磁盘，后来被我们撤掉了。“Now”是链路正常时用内存、中断期间用磁盘：

代价在第一行。先写后发每秒大约做 160 次提交（每次轮询一次放到磁盘上，每个数据块一次取下来），每次约八个 4 KB 的页，也就是 5 MB/s 和每天 450 GB，SD 卡扛不住这个。在稳态下，节点现在根本不向队列写入：Edge 在 `/proc` 里的 `write_bytes` 计数器十分钟内纹丝不动。十次即时终止在那次运行中没有丢任何东西，那是运气，不是承诺：风险窗口是进程死亡时在内存中的读数，大约一次轮询。

更早的一个构建发现了这项工作目的的另一半：QoS 0 和不再应答的连接。见上文“不再应答的连接会被放弃”。那次修复之前的五分钟切断，让节点在整个中断期间待在死连接里，随后在新会话的 birth 之前发送了一个过期的数据块；100 条读数乱序到达。

在这个负载下，一个 64 MiB 的队列能容纳大约两分钟的中断：大约 248,000 条读数，也就是在变量名为九个字符时每条约 236 字节（在 4.21.1 上测得，队列文件 61.7 MB），变量名越长开销越大。请根据你自己的速率和你自己的变量名来确定界限。上面 2026-10-12 的几行与此吻合：5 分钟中断回放了 244,335 条读数，正是同样的两分钟。回放不再是限制：它的运行速度是读数到达速率的一百多倍。

判定器过去在没有中断的运行中会报告 4,000 到 6,000 条重复。我们抓取了流量来弄清是谁的：每一条都是一个 NBIRTH，重复了某个变量的最后一个值，而这个值先前的某条消息已经携带过，并带着该读数自己的时间戳，没有一条是被发送两次的 NDATA。birth 必须携带节点所拥有的每个指标的当前值（这正是 birth 的用途），而节点每次出现新变量就会再次 birth，所以后面的 birth 重复了前面的。发布器是对的，判定器是错的。现在它把这些单独算作快照，而把“重复”留给作为数据再次发布的读数，这是主机唯一可能误当作新数据的一类。在稳态运行和十次终止运行中，收到的数量现在恰好等于交出的数量：1,296,275 和 916,350。

## 在 Helm 图表中

Gateway 图表有一个 `edgePublish:` 块，可以设置以上所有内容。它默认关闭，关闭时渲染出的内容与这个块出现之前图表渲染的完全一样。不要再通过 `extraEnv` 设置这些变量。

```yaml
edgePublish:
  enabled: true
  broker: tcp://central.example.local:1883
  group: Plant1
  node: ""               # empty uses the release name
  username: ""
  password: ""           # goes into a chart-managed Secret
  existingSecret: ""     # or name your own Secret (key: secretKey)
  tls: false
  tlsSkipVerify: false
  queueMaxBytes: 67108864   # 64 MiB; 0 is unbounded
  persistence:
    enabled: true
    size: 1Gi
```

图表替你决定了几件事：

- 队列文件是 `/data/edge-publish/forward.db`，位于它自己的 PVC 上。它不是一个值，因为 Pod 中其他任何位置都是只读的根文件系统。当 `persistence.enabled: false` 时它放在 emptyDir 上，这样中断期间的读数能熬过容器重启，但熬不过被重新调度的 Pod。
- 节点 id 默认是发布名称，而不是 Pod 的主机名。Deployment 的 Pod 每次滚动发布都会得到新的主机名，主机每次都会看到一个新的边缘节点，缓冲的读数就会在它名下回放。
- Deployment 切换为 `Recreate`，`replicaCount` 必须为 1。队列文件会加锁：在滚动更新下，新 Pod 打不开它，永远不会就绪，发布就会卡住。而且两个副本就会是同一个节点 id 上的两个发布器。

Edge Relay 图表（`charts/hotloop-edge-relay`）有它自己的 `edgePublish:` 块，思路相同，只是没有 `enabled`：relay 总是发布。
