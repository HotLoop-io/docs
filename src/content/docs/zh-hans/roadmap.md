HotLoop 是什么、还有什么要做、什么出了问题。不在这份清单上的事不会去做，所以请把它加进清单。

## HotLoop 是什么

**HotLoop 是面向工厂现场的自动化平台，用 Go 从零写成。** 一个静态二进制文件。没有 Python，没有需要照看的运行时，没有特权容器，没有多余的 capability。实体、自动化、辅助项、脚本、日志簿、仪表板、通知、MCP，以及带发现功能的 MQTT，建在工业层之上：真实的 PLC 协议、真正的历史数据库、ISA-18.2 报警、OPC UA、Sparkplug B。

每一行都是我们自己的。没有嵌入，没有桥接，没有分叉，所以凌晨 3 点出问题时，只有一个代码库要读，也不用等别人修他们的缺陷。

HotLoop 是面向工厂现场的八款产品：四款随站点一起成长（IoT、Edge、Gateway 和 Edge Relay），另有负责逻辑编排的 Flow、负责工作流的 Cascade、负责 PLC 自身画面的 HotLoop for CODESYS，以及把 PLC 的值送上网络的 Transmitter。这份路线图是 HotLoop core 的，也就是出自同一个代码库的四款产品。参见[产品](#产品)。Flow、Cascade、HotLoop for CODESYS 和 Transmitter 各有自己的路线图：<a href="/zh-hans/flow/roadmap/">Flow 路线图</a>、<a href="/zh-hans/cascade/roadmap/">Cascade 路线图</a>、<a href="/zh-hans/codesys/roadmap/">HotLoop for CODESYS 路线图</a>和 <a href="/zh-hans/transmitter/roadmap/">Transmitter 路线图</a>。

## 产品

HotLoop core 是四款产品，一个代码库，一个标签。每次核心发布都会同时推出这四款，版本号相同，各自有独立的镜像和 Helm 图表。您选适合设备的那一款，而不是碰巧带着您所需驱动的那一款。

| 产品 | 是什么 | 数据库 | 进展 |
|---|---|---|---|
| **HotLoop IoT** | 实体、自动化、辅助项、脚本、日志簿、仪表板、通知、MCP、带发现功能的 MQTT、ISA-18.2 报警引擎、备份和所有驱动。Edge 和 Gateway 建立在它之上 | SQLite 或 Postgres | 已拆分：独立的镜像（`hotloop-iot`，amd64、arm64、arm/v7）、图表和 Quadlet 单元，每个标签都会构建并发布。已在 4.18.10 中发布 |
| **HotLoop Edge** | IoT，加上 OPC UA 服务器、向上存储转发，以及机器旁的本地画面 | SQLite、Postgres 或 TimescaleDB | 已拆分：独立的镜像（`hotloop-edge`，amd64、arm64、arm/v7）、图表和 Quadlet 单元，每个标签都会构建并发布。已在 4.18.10 中发布（Gateway 自 4.5.0 起在边缘运行并向上发布 Sparkplug） |
| **HotLoop Gateway** | Edge，加上设备群、多站点和定时报表。站点的大脑 | SQLite、Postgres 或 TimescaleDB | 已提供 |
| **HotLoop Edge Relay** | 简单而耐用：轮询、转发、扛住故障。没有数据库，没有界面。是独立的产品，不是拔掉屏幕的 Edge | 无 | 已提供。自 4.16.0 起，每次发布都会发布其镜像和图表 |

**功能区分产品，协议不区分。** 每款产品都在我们所有驱动之上支持 MQTT。拿着一台二手 S7-1200 放在工作台上的爱好者就是 IoT 用户，IoT 无需升级就能与那台 PLC 通信。

- [x] 拆分本身，在代码里。`-tags hotloop_edge` 是 Edge，`-tags hotloop_iot` 是 IoT，两者同时指定无法编译。其 API 路由返回 404，并说明哪款产品有它。`hotloop --product` 和 `GET /api/status` 会告诉您当前在与哪一款通信
- [x] 一个标签生成四个镜像和四个图表，并行构建，发布到同一个 Helm 仓库。四个图表中任何一个与标签不一致，发布都会被拒绝。Gateway 保留 `ghcr.io/hotloop-io/hotloop` 和图表 `hotloop`，所以使用 4.16 的人不会醒来发现东西坏了
- [x] 数据库是一项设置，不是镜像。SQLite、Postgres 或 TimescaleDB，在运行时选择，全部在同一个二进制文件里。SQLite 是纯 Go 版本，不用 cgo，所以 arm 构建保持静态，Pi 也不需要编译器工具链。完整的测试套件会针对这三种数据库运行，因为我们不测试的数据库就是我们不支持的数据库
- [x] 把站点从 IoT 换到 Edge 再换到 Gateway，会保留每台设备、变量、报警、用户和每一小时的历史：换个镜像就行。降回去不会删除任何东西，缺少的功能只是休眠，直到您再回来
- [x] IoT 或 Edge 上的 Gateway 专属设置会发出警告并继续运行，仍会在设置中显示和保存。您能清楚看到自己设置了什么，以及为什么它什么也没做，而不必猜
- [x] IoT 默认保留 30 天历史。Pi 的磁盘很小，长期历史放在 Gateway 上
- [x] 没有许可密钥，也没有运行时解锁。没有任何一档是收费的。一档就是一个镜像，升级就是在同一份数据上换镜像
- [x] **每个设备都跟随 `:stable` 并自行更新。** Gateway、Edge 和 IoT 的 Quadlet 单元和中继的一样跟随 `:stable`，带有 Podman 的自动更新、不需要 shell 的健康检查，以及新镜像无法启动时的回滚。`release_guard.sh` 会拒绝单元被固定、无法报告不健康或会自动更新其数据库的发布。数据库保持固定在其图表运行的标签上：PostgreSQL 的大版本需要导出再重新导入，而应用对 TimescaleDB 扩展的更新是单向的，所以和应用不同，它无法撤销。已在 Gateway 上真实运行过：一次带迁移的更新，在数据完好的情况下完成；一次迁移后无法启动的更新，已回滚。这次运行正是 pod 被取消的原因：应用放在 pod 里时，Podman 会重启 pod 的单元，而它启动得很顺利，于是坏掉的发布被报告为成功，也从不回滚。参见 [Quadlet 的 README](/zh-hans/install/auto-update/)
- [x] 许可证的适用范围一行在规范许可证及其每一份副本中都列出了全部四款产品。以前写的是 Gateway，这可能让其他三款没有任何授权
- [x] **拆分与 MQTT 发现一起在 4.18.10 中发布**（第 4 阶段）。IoT 的第一个版本开箱即可找到 Shelly 和 ESPHome 设备

## 自动化基础

按顺序进行。每个阶段作为单独测试的 PR 发布，每个阶段都建立在前一个之上。全部进入 HotLoop IoT，也就是说 Edge 和 Gateway 里也都有。

### 第 1 阶段：实体

基础。HotLoop 中的每个自动化、辅助项、脚本和画面都围绕实体，所以它们最先完成。在 4.15.3 之后通过 PR 1 到 6 合并，并在 4.16.0 中首次发布。全部内容见[实体](/zh-hans/iot/entities/)和[设备树与标签](/zh-hans/iot/equipment/)。

- [x] 实体模型：带类型的域（传感器、二进制传感器、开关、数字、选择、按钮、文本，以及 OT 域：阀门、电机、PID 回路、计数器、报警）、状态、属性、稳定的实体 ID。泵、风机、输送机和压缩机属于电机的种类，不是独立的域
- [x] 复合设备：一个电机实体由它的启动、停止、复位、运行、故障和速度变量组成，因为电机本来就是这样的
- [x] 把现有变量映射到实体，而不破坏任何变量、API 调用、MCP 工具、OPC UA 节点、自动化或边缘中继设备文件
- [x] 服务（`switch.turn_on`、`number.set_value` 等）只经过现有的写入关口，没有其他途径
- [x] 一棵 ISA-95 设备树（企业、站点、区域、产线、单元格、单元、设备），加上标签。我们已有的站点 / 区域 / 产线字段继续有效
- [x] 单位和设备类别
- [x] MCP、自动化和实时数据流中的实体，以及实体和工厂画面
- [x] 实体状态触发器上的 `for:` 持续时间（“泵已关闭 5 分钟”）。在第 2 阶段以 `state` 触发器上的 `forSec` 发布；进行中的等待不会在重启后保留（[自动化](/zh-hans/iot/automations/#保持一个状态forsec)）

### 第 2 阶段：辅助项、脚本、场景、日志簿

- [x] 辅助项：输入布尔、数字、选择、文本；定时器、计数器、计划。在工厂里，这些就是设定值和班次计划。重启后保留，也包含在备份中，定时器按墙上时钟计时；参见[辅助项](/zh-hans/iot/helpers/)
- [x] 脚本：有名称的动作序列，可由自动化、界面和 MCP 调用。带类型的字段、运行模式、经由真实关口的试运行、每次写入都记为 `script:<id>`，并出现在日志簿和备份中；参见[脚本](/zh-hans/iot/scripts/)
- [x] 场景以**配方**形式提供：捕获一组设定值，一起应用，并有审计记录。整体检查、整体拒绝，绝不截断，在同一个调用 ID 下按顺序写入且绝不回滚，从设备读回确认，版本不可变，可从界面、规则、脚本或 MCP 应用；参见[配方](/zh-hans/iot/recipes/)
- [x] 日志簿：每次状态变化、写入、报警和自动化运行的一条时间线，按实体和区域划分（[日志簿](/zh-hans/iot/logbook/)）
- [x] 蓝图：可复用的自动化模板。超出范围的带类型输入会被拒绝，绝不截断；规则会保留它创建时的版本，直到有人审阅并接受升级；内置四个；参见[蓝图](/zh-hans/iot/blueprints/)
- [x] 自动化语言：序列中的条件、等待和停止步骤，以及状态触发器上的 `forSec`（“开启五分钟”）

### 第 3 阶段：仪表板

这里要让“更好、更酷”从房间另一头也能一眼看出来。

- [x] 仪表板构建器：卡片、拖放、想要多少仪表板都行。保存时会记录它所基于的版本，所以两个人同时构建同一页面时，不会在不知情的情况下互相覆盖；参见[仪表板](/zh-hans/iot/dashboards/)
- [x] 画面文件：把仪表板保存为带版本的文件，再导入另一套安装，这样客户的画面属于客户，永远不是产品的一部分；保存任何内容之前，会先列出并映射每个缺失的变量或设备。参见[画面文件](/zh-hans/iot/screen-file/)
- [x] 卡片集：仪表、数字、趋势、实体列表、带确认的写入按钮、脚本按钮、报警列表、markdown、摄像头、带实时变量的平面图、配方选择器和工厂状态栏。卡片自己不下达任何命令；按钮通过写入关口写入
- [x] 按角色和按画面划分的仪表板；墙面看板就是其中之一，使用同一个切换器和同样的分配
- [x] 在面板 PC、笔记本和手机上看起来一致：一个从十二列折叠为一列的布局，在五种宽度下测试过
- [x] 网页界面支持英语和另外 13 种语言：西班牙语、法语、意大利语、德语、挪威语、保加利亚语、希腊语、韩语、日语、越南语、印地语、简体中文和阿拉伯语（从右到左），在顶栏中选择并由浏览器记住。参见[语言](/zh-hans/iot/languages/)
- 构建时就考虑到可以据此制作 Edge 的 HMI：绑定到画面名称的仪表板在 `/?screen=<name>` 打开，没有页眉也没有标签页
### 第 4 阶段：集成与发现

- [x] 集成框架：集成会添加设备和实体，有配置流程，并针对真实设备测试
- [x] **MQTT 发现**：Zigbee2MQTT 和 ESPHome 按它们发布的格式，Tasmota 按它自己的格式，Shelly Gen2 及更新型号根据它发布的状态。设备以只读形式出现，不论在内置代理还是任何其他代理上，在有人接受设备并启用每个点之前，什么都不会被启用。Edge Relay 也能发现，只读和转发。这里没有 Frigate：它的 MQTT 页面没有记录任何发现消息。一切都对照真实设备的录制数据验证，Tasmota 和 Shelly 还对照了厂商文档，不是对照工作台上的设备。参见 [MQTT 发现](/zh-hans/iot/mqtt-discovery/)和 [Edge Relay 参考](/zh-hans/edge-relay/reference/#发现-41810)。拆分成四款产品一直在等它
- [x] 网络发现（mDNS、SSDP、DHCP）：在工厂网络上监听到的设备会出现在“已发现”画面，说明它们是什么以及 HotLoop 可以如何与它们通信，由人逐个接受或忽略。OPC UA 服务器变成 OPC UA 设备，Shelly 变成 HTTP 设备，ESPHome 节点会指引您去用 MQTT；不会自动添加任何东西，也不会启用任何东西。默认只监听；探测由部署按网络开启。DHCP 需要主机网络和 67 端口，所以在部署同时提供二者之前保持关闭。已用真实的 avahi、MiniDLNA 和 udhcpc 测试；尚未用工作台上的真实设备测试。参见[网络发现](/zh-hans/iot/network-discovery/)
- [x] CODESYS，PLC 的变量使用程序员起的名字，通过运行时自身的 OPC UA 服务器：发现应用导出的内容、读和写、从设置生成的第一个仪表板，以及重启或下载后无需人工介入的重新连接。已对照运行 HotLoop 实验程序和另一个大得多的程序的容器中的 4.22.0.0 运行时，以及裸机（2026-11-17）验证。参见 [CODESYS](/zh-hans/iot/protocols/#codesys)
- [x] BACnet/IP 和 SNMP，只读，参见[协议与驱动](/zh-hans/iot/protocols/)
- [x] ONVIF 摄像头：发现（WS-Discovery）、设备信息、每个媒体配置文件的流和快照地址（Media 和 Media2）、PTZ 位置和命令，以及摄像头自己的事件（作为变量和日志行）。已针对 onvif_srvd 运行，这是一个由 ONVIF 自己的 WSDL 文件生成的 ONVIF 协议栈，每个请求都按 ONVIF 的模式校验；没有实体摄像头上过测试台。参见 ONVIF.md 和[协议与驱动](/zh-hans/iot/protocols/#onvif)
- [x] Shelly 原生：Gen2 及更高版本通过 RPC 和实时 websocket（变化和按键在发生的瞬间到达），Gen1 通过其自己的 HTTP 接口。已对照真实设备的录制数据校验；没有 Shelly 实物上过测试台。参见 SHELLY.md 和[协议与驱动](/zh-hans/iot/protocols/#shelly)
- [x] **Firmata**，面向通过 USB 串口或 TCP 连接的 Arduino：数字和模拟 I/O、PWM、舵机和 I2C。已针对 Arduino 项目自己的 StandardFirmata 在模拟的 Uno 上运行（应答的是固件，而不是我们的程序）；没有实体板卡上过测试台。参见 FIRMATA.md 和[协议与驱动](/zh-hans/iot/protocols/#firmata)
- [ ] UniFi，参见 [UniFi](#unifi)
- [x] 太阳，用于一切室外场景：`binary_sensor.sun_up`、太阳高度角和方位角，以及在黎明、日出、正午、日落和黄昏带偏移的 `sun` 触发器。用站点的纬度和经度，按 NOAA 的公式在设备上计算，不用任何服务，并与 NOAA 为 2026 年公布的、从乌特恰格维克到基多六个地点的每个日出、日落和正午核对过。参见[太阳](/zh-hans/iot/sun/)
- [x] 天气。不是来自云端天气 API：HotLoop 不会打电话去问是不是在下雨。`weather` 实体是工厂自家屋顶上的一个气象站，其变量按角色绑定（温度、湿度、气压、风、雨、日照），露点、热指数和风寒在设备上计算，并与 NWS 的表核对过。读不到的传感器显示为不可用，绝不是零。一张卡片，14 种语言，智能体通过 MCP 构建并读取一张。参见[天气](/zh-hans/iot/weather/)

### 第 5 阶段：能耗、手机、通知

- [x] 能耗：kWh、燃气、水、压缩空气，以及每件产品的成本。一个能耗仪表板，面向生产现场。电表是按计数器或功率读取的变量，在数据库中按 15 分钟区间保存（迁移 0029），在计量时按固定电价或分时电价计价，所以之后改了价格也绝不会改变上个月的成本。一件产品的成本是成本除以生产计数器统计的数量，什么都没生产时显示“未生产”。能耗画面、为每条规则提供的传感器、14 种语言和 MCP。对最高的一个 15 分钟区间的需量电费（迁移 0030），以及一个命名班次的合计，可从画面、API 或智能体获得。参见[能耗](/zh-hans/iot/energy/)
- [x] 可安装到手机上并可离线使用的网页应用
- [x] 通知，见下文

## 通知

已有 Webhook、电子邮件、ntfy、Gotify、Discord Webhook 和 Discord 机器人，全部基于同一套底层机制。参见[报警通知](/zh-hans/iot/notifications/)。

- [x] **先做底层机制：**每个通道的限速器、合并（“过去一分钟又有 7 条报警”合成一条消息），以及遵守 `Retry-After` 的有限重试
- [x] **带签名的确认链接：**从手机上确认会作为真正的 ISA-18.2 确认记入，过期的按钮无法在同一报警下次触发时确认。ntfy 不会说明是谁按的，所以记录的名字是通道的（`notify:ntfy`）；Discord 机器人则写入那个人的名字

四个通道。就是这份清单。

- [x] **首先是 ntfy。**免费、可自托管，在没有互联网的工厂网络上也能工作（Android；iPhone 需要服务器通过 ntfy.sh 中转），它的操作按钮通过工厂网络把报警确认直接送回 HotLoop。
- [x] **Gotify。**免费、可自托管，没有互联网也能工作。没有确认按钮，也没有 iPhone 应用，所以它是寻呼机，不是双向的。
- [x] **Discord Webhook。**粘贴一个 URL 就行。`allowed_mentions` 被锁定，报警名称无法提及 @everyone，严重报警可以呼叫某个角色。Discord 拒绝的 Webhook 会被关闭，而不是重试到 IP 被封。
- [x] **Discord 机器人。**在频道里直接提供确认和搁置按钮，由 Discord 角色控制（在您指定之前没有人能用），记在按下的人名下。通过出站连接（Gateway）与 Discord 通信，所以工厂不需要公网地址。
- [x] 升级：N 分钟内没人确认，就去叫醒下一个人或下一个通道
- 不做：SMS 和 Google Messages（RCS 需要运营商按公司、按国家批准，自托管的设备拿不到）、Slack、Teams、Google Chat、Pushover、PagerDuty、Telegram、Opsgenie、Signal、Matrix

## UniFi

工厂的网络也是设备。PLC 沉默时，第一个问题是“是 PLC 还是交换机”，如今您得走到 UniFi 应用那里才能回答。所以 UniFi 以**协议驱动**的形式引入，而不是旁边的独立系统：每台交换机、端口、PoE 预算和 WAN 都是一个变量。这样就能免费获得写入关口、审计、试运行、报警、趋势、实体、自动化、OPC UA 和 MCP，而不用为一家厂商把每项功能重做一半。

它进入 IoT 基础，所以四款产品都有，Edge Relay 也能像轮询任何其他设备一样轮询控制台。

### 网络

按顺序进行。在 U5 之前，这里没有任何东西会向控制器写入。

- [x] **U1：只读驱动。**每个控制台一个会话，用于所有操作，并有登录次数预算。每次检查都登录，曾让我们自己的 Cloud Gateway 回复 429 并把我们锁在外面两次，所以 HotLoop 只登录一次，遇到锁定就等它结束，而不是延长它。控制台的证书在首次使用时固定，不会不加检查地放行。设备、交换机端口、PoE 功耗、WAN 和故障切换以自行同步的变量形式进入：明天接入的交换机会自己出现，消失的交换机会变成质量不良，而不是从它的报警底下蒸发。它的第一次真实读取把已经停了两天的 5G 备份报告为在线，因为它像控制台摘要一样相信了 WAN 块中过期的 `up`。健康检查是知道真相的，所以驱动现在读取那些，并有测试固定下来。已完成，参见 [UniFi Network](/zh-hans/iot/unifi/)
- [ ] **U2：客户端和 OT 监视。**客户端按 MAC 识别，绝不按 IP，因为控制器的客户端表里会显示机器几小时前就已离开的地址。把一个网络标记为 OT，接受上面已有的东西，之后上面出现任何新东西都会触发报警。把 HotLoop 设备与它的交换机端口关联一次，沉默的 PLC 就会告诉您它在哪个端口以及该链路是否通着。这一项在需要有人在机架旁的两个步骤之后打勾：真实拔一次线缆，以及一部手机加入 SCADA。参见 [UniFi Network](/zh-hans/iot/unifi/)
- [x] **U3：画面和拓扑图。**带 WAN 条的概览（站点运行在 5G 备份上时变为琥珀色）、每次都按同样方式布局的拓扑图，让墙面看板上什么都不抖动、交换机面板、客户端、网络和 WiFi。两个控制台拼成一张图。点击一台交换机，就能看到它给工厂树上的哪些产线供电。线缆来自控制台自己的下行链路表，所以没有任何记录说明接在哪里的交换机会独立存在，而不是凭猜测挂到网关上。尚未在真实设备上查看。地图可捏合、拖动并放大到八倍，有一个工厂叠加层，把已关联的 HotLoop 设备归到各自的产线下，每个 WAN 旁边显示延迟，端口的进出流量会绘制轨迹，管理员可以一键创建常用的报警（设备离线、上行链路中断、网关在备份上、PoE 超过他们设定的上限）。这些在 2026-10-19 验证过，使用的是模拟触摸，不是在真实屏幕上，而 WAN 吞吐量轨迹尚未构建：还没有从真实网关读取过相关的控制台字段。参见 [UniFi Network](/zh-hans/iot/unifi/#界面)
- [x] **U4：事件。**控制器的事件 websocket，让掉线的交换机在几秒内显示，而不是等到下一次轮询，并进入日志簿。轮询仍是事实依据；websocket 失效只损失速度，绝不损失正确性。断开的 websocket 和沉默的 websocket 都会无需登录就重新连接。事件会归档到日志簿中它们所涉及的交换机或 AP 名下，设备筛选器可以从已关联的设备出发，经过给它供电的交换机找到这些事件。智能体工具 `get_network_topology` 和 `get_network_events` 读取地图和事件。参见 [UniFi Network](/zh-hans/iot/unifi/#事件)
- [ ] **U5：通过关口写入。**首先是定位 LED：零风险，隔着房间也看得见，并在真实设备上证明整条写入路径。然后是 PoE 模式、端口电源循环、WLAN 开关、客户端阻止，以及在该形式于真实控制器和一个空端口上得到证明之后，对未知设备的端口禁用。电源循环对每个端口有 15 分钟的冷却时间，因为每两分钟就循环一次 PLC 的自动化，正是烧坏电源的办法。受保护的端口来自拓扑：无论谁提出要求，HotLoop 都不会循环上行链路，也不会循环给 5G 备份供电的端口。设备重启是一个简单的按钮：按下，设备重启，没有确认，仍然会被审计。已构建并在测试中证明：定位、重启、电源循环、PoE 模式、WLAN 开关和客户端阻止。端口禁用在等待：Network 10.6 不存储任何能关闭端口的端口设置，参见 [UniFi Network](/zh-hans/iot/unifi/#命令)
- [ ] **U6：自愈。**一个内置蓝图：设备沉默 N 分钟，就把它的端口循环一次，然后报警。只做一次，不是永远。已构建：`device_silent_cycle_its_port` 蓝图，建立在端口电源循环之上，带有其 15 分钟冷却时间和受保护的端口，参见[蓝图](/zh-hans/iot/blueprints/)。在它于真实交换机上循环过真实 PoE 设备的端口之前，复选框保持未勾选

- [x] **SmartPower PDU。**插座功率、开、关和循环作为变量，供第 5 阶段的能源工作使用。按控制台自己的插座 API 构建：插座的开、功率、电流、电压和循环作为 UniFi Network 设备的变量。参见 [UniFi Network](/zh-hans/iot/unifi/#smartpower-pdu-插座)

- [x] SQL Server
- [x] InfluxDB（2 和 3）
- [x] MySQL 和 MariaDB
- [x] 宕机的目标绝不会拖慢轮询或内置历史数据库。它恢复后会追上，或者明确说出丢弃了什么。它从 HotLoop 自己的历史中追赶，所以在故障期间重启也不会丢任何东西

- [x] **恢复无法加载来自较旧模式的备份，并且根本不检查备份的 `hotloopVersion`。**清单现在会记录每张表的列和已应用的模式迁移。恢复会按名称把每个文件加载到这些列中，让较新的列取默认值，把较新的表留给应用去填充，并在加载任何一行之前，拒绝来自较新模式的备份，或带有本版本已删除、重命名或改变类型的列的备份。在此之前的备份仍按位置恢复。已从存在过的每一个模式级别测试。已修复，参见[备份与恢复](/zh-hans/iot/backup/#恢复到不同版本)

## 最后：现代化界面

这一项有意放在本页其他一切之后。新前端是最有意思的东西，也是花掉一个季度的最容易的办法，而工厂仍然做不到它所需要的事。所以它要等，上面的一切都不会因它而推迟。
