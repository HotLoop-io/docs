它能让机器动起来。因此这里完整说明，一个请求到达设备之前会经过什么，并按代码实际执行的顺序排列。

发往设备的每一个值都要经过**一个无法绕过的函数**：界面上的一次点击、`POST /api/write`、一次实体服务调用、一条自动化、一个脚本、一个配方、一个通过 MCP 的代理。策略只存在于那里，因为复制到六处的检查，就是有人会在第七处忘记加上的检查，而第七处总是写向正在运行的压力机的那一处。只要运行时里有任何东西能不经过这道门就到达设备的写入，就会有一个测试让构建失败，并且它通过在软件包的副本中植入四种绕过方式并全部抓住，来证明自己确实会失败。

想亲身体验而不只是阅读？[hotloop.io 有一个交互版本](https://hotloop.io/gateway/#the-gate)。拨动开关，发送一个设定值，看它究竟在哪里被挡回。

## 检查的顺序

1. **调用者有权写入。** 这一步发生在 API 的入口，早于写入门。已登录的用户需要 `values.write` 才能调用 `POST /api/write`：操作员和管理员有，查看者没有，没有时 API 返回 403。代理的入口是 MCP bearer 令牌，没有它就会得到 401，连工具列表都看不到。无论哪种情况，写入门都毫不知情，所以它不在写入审计里。（实体服务调用的工作方式不同，见[下文](#每道门同一道写入门)。）
2. **写入已开启。** `safety.allowWrites`，总开关。自 4.4.0 起默认关闭。
3. **代理写入已开启。** `safety.allowMcpWrites`，只在请求经由 MCP 到来时检查。它收窄总开关，永远无法绕过它：写入开启而它关闭时，操作员可以向变量下达命令，代理不行。如果在 `safety.allowWrites` 关闭时把它打开，Gateway 会拒绝启动，而不是让您猜哪一个生效。
4. **变量已布防。** 每个变量都是只读的，直到有人把它标记为 `writable`，一次一个，并且是有意为之。浏览导入 4,000 个变量，不会布防其中任何一个。不存在的变量在这里同样会被拒绝。
5. **值在范围内。** 变量有范围而值是数字时，超出范围的值会**被拒绝，绝不会被截断**。在最大值为 400 的变量上输入了 500 的人犯了错，需要听到这个消息。悄悄发送 400，就是做了没人要求的事，而他们永远不会知道。
6. **调用者自己的检查通过。** 实体会补充只有它自己知道的内容：数字的步长和更窄的范围、文本的模式和长度、选择项的选项、除非回路此刻处于手动否则会被拒绝的回路输出、调用过程中被禁用或删除的实体。它在门内运行，位于变量的策略和范围之后，这样操作员总是先听到关于变量的问题，又位于审计行之前，这样实体的拒绝会和变量的拒绝记录得完全一样。它只能拒绝。它不能改变值，也不能放过门本来会拦住的任何东西。
7. **设备正在运行。** HotLoop 里有一个为它运行的 worker。已禁用或从未启动的设备会以 `the device is not connected` 被拒绝，而不是把一个值扔向虚空。

**只有到这一步，审计行才会打开，值才会发出。** 如果这一行无法写入，写入根本不会发送。无法审计的写入，是事后没有人能交代的写入，而在会动的设备上，这笔交易不值得做。这一行在与请求分离的上下文中，带着结果和延迟完成，因此超时或被取消的写入也会记录发生了什么。

从检查 2 起的每一次拒绝都会作为拒绝被审计：一行内含操作者、来源、被请求的值、它本来会替换的值，以及带原因的 `refused:`，另外系统日志里还有一条警告。反复尝试向自己无权操作的变量下命令的人，如果不写下来就是隐形的，而工程师应当事后能找到它。检查 1 不在写入审计里，因为写入门从未见过它。

### 为什么是这个顺序

策略在审计行打开之前运行，所以拒绝会被记录为拒绝，而不是碰巧失败的一次尝试。审计行在值到达线路之前打开，所以挂起或把进程一起带走的写入，也留下了它曾被尝试的证据。在工厂现场，“我们不知道那条命令有没有发出去”是最糟糕的答案。

### 检查 7 抓不到的一件事

检查 7 问的是设备有没有 worker，而不是它的会话此刻是否在线。一台掉出网络、正在重连的设备能通过检查。审计行打开，驱动没有会话，写入以 `the device is not connected` 失败，被记录为失败的尝试，而不是拒绝。无论哪种情况，都没有东西到达设备。[试运行](#发送前先问试运行)也会检查会话，并在开头就说明。

## 每种拒绝的返回内容

状态码说明问题出在谁那里，因为操作员就是这样读它的。

| 发生了什么 | 错误信息 | HTTP |
|---|---|---|
| 在入口处无权限 | `<user> does not have the "values.write" permission` | 403 |
| 写入已关闭 | `writes are disabled on this deployment` | 403 |
| 代理写入已关闭 | `writes from MCP clients are disabled on this deployment` | 403 |
| 变量未布防 | `this tag is not marked writable` | 403 |
| 实体已禁用 | `the entity is disabled` | 403 |
| 变量不存在 | 该变量，以及 `not found` | 404 |
| 实体在调用中途消失，或所处状态不允许（不在手动的回路） | 发生的变化 | 409 |
| 值超出变量的范围 | `value is outside the tag's configured range` | 422 |
| 实体不接受该值（步长、模式、选项、自身范围） | `the value is not one this entity accepts`，以及原因 | 422 |
| 设备未连接 | `the device is not connected` | 503 |
| 设备回应并拒绝 | 设备自己的原话 | 502 |
| 写入无法审计，或 API 无法归类的其他任何情况 | `internal error (ref …)`，细节在服务器日志中该编号之下 | 500 |

API 无法归类的一切都是 500。它过去是 400，这意味着数据库故障会告诉操作员他们输错了东西，于是他们去找一个根本不存在的笔误。

通过 MCP 没有状态码。拒绝以标有 `isError` 的工具结果返回，用的是写入门自己的话：

```
> write_tag tag=press-01/Zone1_Temp value=99 reason="testing"
write refused: press-01/Zone1_Temp: this tag is not marked writable
```

这是一个答复，而不是传输故障。调用已被理解并被有意拒绝，重试只会得到相同的答复。

## 发送前先问：试运行

写入门有第二个入口，只问不做。它按相同的顺序运行相同的检查，拒绝时给出相同的错误文本。它不打开审计行，不触发事件，不计数，也永远不会到达设备。它甚至比真正的写入多走一步：worker 在运行但会话已断开的设备，会被报告为未连接，而不是“这个会发出去”。

获取方式：

- **实体服务调用**：`POST /api/services/{domain}/{service}?dry_run=true`。它返回 200 和裁定：它会执行的每次写入标为 `would_write`，第一个会被拒绝的标为 `not_sent`，原因逐字给出。连计划都无法制定的请求（没有这个实体、域不接受的服务、错误的数据）会返回与真实调用相同的状态。`dry_run` 只接受 `true` 或 `false`，`yes` 会得到 400，因为朝错误方向猜测会把一个问题变成一条命令。
- **命令提示**在您输入时发问，并在有人确认之前显示“Would be refused: ...”。
- **脚本**，4.17.0 新增：`POST /api/scripts/{id}/run?dry_run=true`，运行抽屉中的 **Check first**，或带 `dryRun` 的 MCP `run_script`。每一步都对照工厂此刻的状态走一遍，第一个会被拒绝的写入用写入门的原话结束这次走查。参见[脚本](/zh-hans/iot/scripts/)。
- **配方**，4.17.0 新增：第一个值发出之前，每个目标都要通过这些检查，只要有一个坏值，整个配方就被拒绝，什么也不会写入。`POST /api/recipes/{id}/validate` 和 MCP 的 `validate_recipe` 只询问，不应用。参见[配方](/zh-hans/iot/recipes/)。
- **Blueprints**，4.17.0 新增：**Check first** 在规则存在之前，显示规则如果此刻触发会做什么，每次写入都经过这些检查。参见 [Blueprints](/zh-hans/iot/blueprints/)。

一次干净的试运行是建议，不是承诺。写入门仍然在真正写入时做决定，因为在您提问和下命令之间，设备可能掉线，或者有人可能撤防某个变量。

:::caution[还在 4.16.0？命令提示可能吞掉一次 Set]
在 4.16.0 中，试运行的裁定在您停止输入约四分之一秒后出现，恰好是鼠标移向 Set 的时候，命令提示在它下面变大或变小。Set 会移动约 30px，所以点击落在空白处，或落在背景上并关闭提示。操作员看着它关闭，以为设定值已发出，其实什么也没写入。已在 4.17.0 修复：裁定位于按钮旁边，没有任何东西移动。在您[升级](/zh-hans/gateway/upgrading/)之前，按下 Set 后请核对值确实变了。
:::

## 每道门，同一道写入门

- **界面和 `POST /api/write`。** 操作者是已登录的用户名，而不是任何人都能设置的请求头。
- **实体服务**，`POST /api/services/{domain}/{service}`。对 `switch.press_01_pump` 的 `switch.turn_on` 是经过这道门的变量写入，针对该实体、连同其 entity_id、服务和调用 ID 进行审计。一次按钮按下是同一个调用 ID 下的两次写入。没有 `values.write` 的用户在这里不会在入口被拦住：缺失的权限会作为调用者自己的检查交给写入门，因此被拒绝的实体调用会像其他任何拒绝一样，带着被请求的值针对该实体审计，并且仍返回 403。
- **自动化**以 `automation:<rule-id>` 的身份写入。规则得到的特权不会比一个人更多。参见[自动化](/zh-hans/iot/automations/)。
- **脚本**，4.17.0 新增，以 `script:<id>` 的身份写入，并保留启动者的来源，所以由代理启动的脚本，会像代理自己的 `write_tag` 一样撞上代理开关。
- **配方**，4.17.0 新增，在同一个调用 ID 下写入每个目标，所以 `GET /api/writes?call=<id>` 就是审计记录中的整次应用。
- **代理**以 `mcp:<client name>` 的身份写入。`write_tag` 和 `call_service` 经过与操作员相同的检查，并且都拒绝在没有说明原因的情况下运行，原因会和写入一起记入系统日志。六个月后没人能解释的审计行，只是一个心里有愧的时间戳。代理写入关闭时，`trigger_automation` 会直接拒绝，`run_script` 和 `apply_recipe` 也一样，因为规则、脚本或配方都能向设备下命令，否则就会成为绕过开关的办法。参见 [Model Context Protocol](/zh-hans/iot/mcp/)。

## 为什么写入默认关闭

在 4.4.0 之前，`safety.allowWrites` 和 `safety.allowMcpWrites` 默认为 `true`。现在是 `false`。变量一直是只读的，直到被布防，但全新安装不应该在还没有人看过之前，就只差一个 `writable` 标记便能向设备下命令。

在写入门之上，`safety.confirmWrites`（默认开启）让界面在发送任何内容之前请求确认。那是浏览器里的一个提示，不是写入门里的检查，也是您唯一可以在设置界面中更改的安全设置。`safety.allowWrites` 和 `safety.allowMcpWrites` 在那里是只读的，这是有意的：决定这个进程能否向设备下命令的总控制，不应放在发出写入的同一个浏览器会话背后。

## 有意开启写入

1. 添加设备，并在协议能列出的地方发现它的变量。Modbus 和 S7comm 无法枚举自己的点位，所以请根据设备文档来声明它们。
2. 逐个把变量标记为可写，并且只标记您确定要标记的。
3. 在您的 values 文件中设置 `safety.allowWrites: true` 并执行 `helm upgrade`。在您这样做之前，步骤 1 和 2 里的任何内容都无法移动一个阀门。
4. 只有在代理也应向设备下命令时，才设置 `safety.allowMcpWrites: true`。

## 它不做什么

应用程序无法强制一切，说明白比让您自行假设要好。

- **它不是联锁。** 保护人员或工厂的跳闸属于 PLC，硬接线在它必须在的地方，而不属于任何运行在网络上的东西。
- **它不监管您的代理服务器。** 如果您通过 MQTT 向边缘中继推送节点命令，代理服务器自己的访问控制必须限制谁能发布它们，只允许 Gateway 的凭据。
- **OPC UA 服务器完全不能写入。** 它是只读的，没有写入处理程序，也没有能添加一个的设置，所以读取它的 SCADA 无法通过它向任何东西下命令。
