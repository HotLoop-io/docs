定时报表自 4.14.0 起，按计划运行由操作员定义的报表：查询历史库，把结果生成 CSV 和 HTML，保存到卷上，并可选地通过邮件发送。它对应 Ignition 的 Reporting 模块中工厂最常用的那一部分，也就是按时送达的一张数据表。默认关闭（`HOTLOOP_REPORTS_ENABLED`）。

## 它是什么，不是什么

- **仅限 API。** 此版本没有对应的界面。报表通过 `/api/reports` 定义、运行、列出和下载。界面是另一项工作。
- **仅限 CSV 和 HTML。** 没有 PDF。在不依赖外部二进制文件（运行时镜像特意不带任何外部二进制文件）的纯 Go 中生成好的 PDF，意味着要选择 PDF 库和排版引擎，这本身就是一个决定。HTML 文件是自包含的，在任何浏览器中都能干净地打印，目前这就满足了“我需要一份 PDF”的需求。
- **汇总数据表，不是自由版式。** 报表是一组变量、一个时间窗口、一个分桶大小和一组聚合。它不是页面设计器。
- **只有一个 Gateway 实例。** 调度器假定自己是唯一对此数据库运行报表的程序。两个副本会各自触发每一份报表。此 chart 只运行一个副本，报表卷是 `ReadWriteOnce`。
- **不是报警功能。** 报警邮件是另一项功能，即[报警通知](/zh-hans/iot/notifications/)。报表只与它共享 SMTP 中继设置，别的什么都不共享。

## 报表定义

定义是由操作员编辑的数据，像设备、变量、报警定义和设备群成员一样存放在数据库中，并通过 API 管理。示例：

```json
{
  "id": "line1-daily",
  "name": "Line 1 daily summary",
  "enabled": true,
  "tags": [
    {"deviceId": "press-01", "tagName": "Zone1_Temp"},
    {"deviceId": "press-01", "tagName": "Pressure"}
  ],
  "window": {"count": 1, "unit": "days", "end": "local_midnight"},
  "bucket": "hour",
  "aggregations": ["min", "max", "avg", "count"],
  "schedule": {"kind": "daily", "at": "03:00"},
  "format": "both",
  "recipients": ["ops@example.com"],
  "retain": 30
}
```

| 字段 | 含义 |
|---|---|
| `id` | 1 到 64 个字符，由字母、数字、点、短横线或下划线组成，以字母或数字开头。它命名报表在卷上的目录，因此与本应用中其他所有 id 一样经过校验。 |
| `name` | 显示在 HTML 标题和邮件主题中。不含控制字符。 |
| `enabled` | 调度器是否运行它。已禁用的报表仍可手动运行。 |
| `tags` | 1 到 50 个设备与变量的组合。保存定义时每个都必须存在，且不能是字符串变量。 |
| `window` | 每次运行所覆盖的历史跨度。见下文。 |
| `bucket` | `window`（每个变量一行）、`hour` 或 `day`。默认为 `window`。 |
| `aggregations` | `min`、`max`、`avg`、`first`、`last` 或 `count` 中的一个或多个，每个至多一次。 |
| `schedule` | 见下文。 |
| `format` | `csv`、`html` 或 `both`。默认为 `csv`。 |
| `recipients` | 可选。仅限普通地址（`ops@example.com`，不能是 `Ops <ops@example.com>`）。至多 20 个。 |
| `retain` | 保留多少次运行。1 到 1000。默认为 30。 |

`PUT` 会替换整个定义。客户端可以读取一份报表，修改一个字段，再原样发回：服务器添加的只读字段（`nextRunAt`、`lastRun`、`lastRunAt`、`createdAt` 和 `updatedAt`）会被接受并忽略。

保存时，会拒绝产生超过 1000 个分桶的定义（例如跨度超过约 41 天的按小时分桶）。

## 时间窗口

窗口是相对于运行发生的时刻而言的。

| 您想要 | `count` | `unit` | `end` |
|---|---|---|---|
| 前 24 小时 | 24 | `hours` | `run_time` |
| 前一个日历日 | 1 | `days` | `local_midnight` |
| 前 7 个整天 | 7 | `days` | `local_midnight` |
| 滚动的一周 | 7 | `days` | `run_time` |

- `end` 是运行开始的时刻，对于 `local_midnight`，则是不晚于该时刻的最近一个本地午夜。03:00 运行、在本地午夜结束的窗口，覆盖的是完整的日历日。
- **小时是经过的时间，天是日历日**，按工厂所在时区计算。在本地午夜结束的一天窗口就是完整的一个本地日，在时钟拨快的那天是 23 小时，在拨慢的那天是 25 小时。“前 24 小时”则始终恰好是 24 小时。
- **窗口是半开区间**：包含起点，不含终点。时间戳恰好在午夜的读数属于从那里开始的那一天。连续两份日报表绝不会都计入同一个读数，也绝不会都漏掉它。
- 手动运行和补跑，都按它们运行时的时刻来计算窗口。

## 分桶

- `window`：整个窗口内每个变量一行。
- `hour`：每个变量每个本地时钟小时一行。不从整点开始的窗口，以一个较短的部分分桶开头，不在整点结束的窗口，以一个部分分桶结尾。小时在时钟切换时，以及在偏移量不是整数小时的时区中，仍保持在整点。
- `day`：每个变量每个本地日历日一行。

每个变量对每个分桶都有一行，包括里面什么都没有的分桶。报表从不省略传感器静默的那个小时，因为悄悄漏掉这一行的报表，看起来会和一个无话可说的传感器的报表一模一样。每一行都写明它覆盖的确切跨度（`period_start` 和 `period_end`，带 UTC 偏移），所以 23 小时的一天会如实显示为 23 小时。

## 聚合与质量规则

聚合有 `min`、`max`、`avg`、`first`（该时段内按时间戳最早的读数）、`last`（最晚的读数）和 `count`。

报表遵循质量规则，与趋势图所遵循的相同，因此同一小时的报表与趋势一致。没有数值的读数（字符串读数）也会被剔除。对此没有开关：悄悄混入历史库自己标记为不可信的读数的平均值，比一份说明自己没用多少条读数的报表更糟。

因此每一行都带有一个 `excluded` 列：该时段内有多少条读数被剔除。`count` 是用了多少条。运行记录和邮件中带有合计。

**绝不编造数据。** 在某个时段内没有可用读数的变量没有最小值，报表会如实说明：CSV 中单元格为空，HTML 中显示 `no data`。它们永远不会是零。零是一个读数（阀门关闭、流量为零），与其他任何值一样参与聚合。`count` 是唯一在没有数据时仍是数字的列，因为零是对“什么都没有”的真实计数。

## 计划与时间

计划是下列之一：

```json
{"kind": "interval", "every": "6h"}
{"kind": "daily",    "at": "03:00"}
{"kind": "weekly",   "weekday": "monday", "at": "06:30"}
```

- **间隔**是经过的时间（至少一分钟），不理会挂钟时间。
- **每日和每周**的时间是工厂时区的挂钟时间，即 `HOTLOOP_TIMEZONE`（chart 的 `global.timezone`）。它必须是真实的时区名称，例如 `America/Chicago`。无法使用的名称会导致启动被拒绝，无论报表是否开启，而不是悄悄回退到 UTC，因为本应在本地 03:00 触发的报表在 UTC 03:00 触发，是一个直到数字出错才会有人发现的缺陷。

### 夏令时

下一次运行，是用 `time.Date` 在工厂所在地构造一个挂钟时间来计算的。绝不会通过在上一次运行上加 24 小时来计算，那样会在每次时钟切换之间提前一小时或推迟一小时触发。切换当天有两种挂钟时间很棘手，每一种的规则都固定在代码里，而不是交给 `time.Date`，因为它对这两种情况的行为文档中都写作未指定：

- **不存在的时间**（春季拨快当天的 02:30，此时时钟从 02:00 跳到 03:00）在间隙之后的第一个瞬间，即 03:00 触发。它最多晚上间隙那么长的时间，并且不会跳过这一天。
- **出现两次的时间**（秋季拨慢当天的 01:30）只触发一次，在它第一次出现时。

### last_run_at、下一次运行和补跑

`last_run_at` 是调度器上一次**启动**报表的时间，无论那次运行之后成功还是失败。手动运行不会移动它，所以在 02:00 手动运行一份报表，不会取消今晚 03:00 的运行。

下一次运行，是在定义创建时间、最近一次编辑时间和 `last_run_at` 三者中最晚的一个之后的第一个计划时间。从最近一次编辑算起，意味着在 10:00 把报表从 03:00 改到 09:00，会等到明天，而不是为了一个已经过去的时间立即触发。

**补跑。** 如果 Gateway 启动时，`last_run_at` 之后的下一次运行已经过去，说明 Gateway 当时不在，无法执行，报表会立即运行**一次**，并标记为 `catchup`。它不会为每一个错过的时间各运行一次：错过三天的日报表，会在 Gateway 回来的那天运行一次，窗口按此刻来算。错过的天数不会回填。之后，报表回到它的计划上。

`last_run_at` 在运行开始**之前**写入，这样在运行中途崩溃的 Gateway，重启后不会在一封可能已经发出的邮件之上重复这次运行。被中断的运行会改记为失败。失败的计划运行不会重试；下一个计划时间正常运行，需要再来一次时，可以用 `POST /api/reports/{id}/run`。

## 输出

每次运行都会把文件写入 `HOTLOOP_REPORTS_DIR`（`/data/reports`，chart 中的一个 PVC）之下：

```
/data/reports/<report id>/<UTC timestamp>-<run id>.csv
/data/reports/<report id>/<UTC timestamp>-<run id>.html
```

- **文件名只由经过校验的 id、UTC 时间戳和运行的整数 id 构成。** 路径遍历在构造上就被堵死：报表 id 必须满足与其他各处相同的标识符规则，从运行记录读回的文件名在打开之前，会与上面的精确模式比对。下载 URL 中的 `{run}` 被解析为整数，仅用于连同报表 id 一起查找运行记录。打开的文件是该记录所指明的那一个。URL 中的任何内容都不会成为路径的一部分。
- 文件以 `O_EXCL` 和模式 `0640` 创建，目录以 `0750` 创建。已存在的文件是一个错误，绝不会被覆盖。输出包含工厂数据和变量名，所以该模式只是底线，不能替代对卷的保护。
- **保留。** 每次运行之后，保留存了文件的最新 `retain` 次运行，更早的连同其文件一并删除。没有文件的失败运行单独保留（其中最新的 `retain` 次），这样一连串失败不会把最后一份良好的报表挤出去。报表目录中任何符合命名模式、但没有被任何剩余运行记录引用的文件（死亡运行留下的残缺文件）也会被移除。不符合该模式的文件，比如操作员放进去的文件，则原样保留。

### CSV

RFC 4180，来自 `encoding/csv`，行尾为 CRLF。各列是 `device_id`、`tag_name`、`unit`、`period_start`、`period_end`，然后是按定义中列出的顺序每个聚合一列，最后是 `excluded`。时间戳是工厂时区的 RFC 3339，带偏移。数字以完整精度写出。

**电子表格公式注入。** 变量名或单位是有人输入的文本，而电子表格会把以 `=`、`+`、`-` 或 `@` 开头的单元格当作公式读取。任何以其中之一开头（或以制表符或回车符开头，或以空格后接其中之一开头）的文本单元格，前面都会加一个撇号，电子表格把它当作“这是文本”，并且不显示它。数值列是由数字写出的，所以负数读数保持原样，仍然作为数字读取。

文件没有字节顺序标记。Excel 会把没有该标记的 UTF-8 CSV 当作旧代码页来打开，所以含有非 ASCII 字符的变量名可能需要按 UTF-8 导入。

### HTML

一个自包含的文件，用 `html/template` 构建，因此变量名和值会按它们所在的位置做转义：名为 `<script>` 的变量会被写成文本。样式表是内联的，没有脚本、字体、图片，也没有指向任何地方的链接，因为部署环境可能处于物理隔离。它还带有一个 `Content-Security-Policy` meta 标签，禁止加载任何内容，API 在提供它时会附上增加了 `sandbox` 的策略，并作为附件。

## 邮件送达

如果报表有 `recipients`，每次运行都会把文件作为附件通过邮件发出，使用在 `HOTLOOP_NOTIFY_SMTP_*`（主机、端口、用户名、密码、发件人、TLS）下配置的 SMTP 中继。与报警通道共享的只有中继：该通道是否启用、报警发给谁，对报表没有任何影响，所以部署可以发送报表邮件而不惊动任何人。报警通道关闭时，chart 会只为报表写入中继的变量。

它与报警通道是同一份 SMTP 代码，而不是第二份拷贝。报警通道现在也通过它发送。连接处理保持不变（465 端口现在从第一个字节起就使用 TLS，见[报警通知](/zh-hans/iot/notifications/#隐式-tls465-端口)）：中继提供时就用 STARTTLS，设置了凭据时用 `AUTH`，在设置了 `HOTLOOP_NOTIFY_SMTP_TLS` 而中继不提供 STARTTLS 时，在 `AUTH` 之前直接失败。对于 ASCII 报警，除 `Date` 头之外，消息的字节与以前相同，并有测试固定这一点。非 ASCII 的报警主题现在以 RFC 2047 编码词发送，而不是原始 UTF-8。

消息是 `multipart/mixed`：一个 quoted-printable 文本部分，然后是每个 base64 编码的文件。**头部注入会被拒绝，而不是被清理。** 收件人、发件人、主题和附件文件名都会经过校验：含有 CR、LF 或其他控制字符的值、显示名形式或包含列表的收件人、含有引号或路径的文件名，都会使消息在向中继发送任何内容之前就失败。报警通道自己的主题是唯一的例外，因为无论报警叫什么名字，通知都必须发出：它会先把控制字符变成空格。

- **未配置中继。** 有收件人的报表仍会运行并保存其文件，该次运行被记录为 `failed`，`emailStatus` 为 `failed`，并带有说明中继未配置的错误。它不会悄悄成功。
- **太大。** `HOTLOOP_REPORTS_MAX_EMAIL_BYTES`（10 MiB）限制一封邮件中的附件数据量。超出的报表会被保存并可下载，其运行记录会写明为什么没有通过邮件发送。
- 手动进行的运行可以用 `?deliver=false` 跳过邮件。

## 运行记录与审计轨迹

每次运行从开始的那一刻起就记录在 `report_runs` 中：何时开始和结束、触发方式（`schedule`、`catchup` 或 `manual`）、谁请求的、窗口、结果和错误文本、变量数、行数、已聚合的读数数和被剔除的读数数、保存的文件、邮件结果及其收件人，以及备注（例如，某个变量此后已被删除，正根据其记录的历史报告）。成功和失败也通过 `rt.Event` 写入，这与报警和设备群操作使用的是同一条审计轨迹，以报表 id 作为主体。

因关机、因其时间限制（`HOTLOOP_REPORTS_RUN_TIMEOUT`）或因报表被删除而中途结束的运行，会连同该原因被记录为失败。被死亡的进程留在 `running` 状态的运行，会在 Gateway 下次启动时被标记为失败。同一份报表同一时间只有一次运行在进行；有一次在运行时再来第二个请求，会得到 `409`。

## API

| 路由 | 权限 | <span class="sr-only">详情</span> |
|---|---|---|
| `GET /api/reports` | `reports.read` | 每个定义，各带其 `nextRunAt` 和最近一次运行 |
| `POST /api/reports` | `reports.write` | 创建。id 已存在时返回 `409` |
| `GET /api/reports/{id}` | `reports.read` | 一个定义 |
| `PUT /api/reports/{id}` | `reports.write` | 替换。id 不能更改 |
| `DELETE /api/reports/{id}` | `reports.write` | 删除，连同其运行记录和文件。正在进行的运行会先被取消 |
| `POST /api/reports/{id}/run` | `reports.run` | 立即运行并等待。`?deliver=false` 跳过邮件 |
| `GET /api/reports/{id}/runs` | `reports.read` | 运行记录，最新的在前（`?limit=`，最多 500） |
| `GET /api/reports/{id}/runs/{run}/download?format=csv\|html` | `reports.read` | 以附件形式流式传输一个已保存的文件 |

无论运行是否成功，`POST .../run` 都以 `200` 返回运行记录。状态码说明请求是否已执行，而记录自己的 `status` 说明报表是否成功。失败的运行是一个结果，两种情况都会被记录。运行不与客户端的连接绑定：挂断不会中止一份可能已经开始发邮件的报表。

功能关闭时，列表回答 `{"reports": [], "configured": false}`，其他所有路由都以一个提到 `HOTLOOP_REPORTS_ENABLED` 的错误作答。

### 谁能做什么

| 角色 | `reports.read` | `reports.run` | `reports.write` |
|---|---|---|---|
| 查看者 | 是 | 否 | 否 |
| 操作员 | 是 | 是 | 否 |
| 管理员 | 是 | 是 | 是 |

- **读取**面向查看者，因为已保存的报表是查看者本来就能通过 `values.read` 读取的历史的聚合，所以读取或下载一份并不授予任何新东西。
- **运行**面向操作员，因为运行报表只会发给管理员已经选定的收件人，并且可以不送达地运行。
- **写入仅限管理员。** 定义会指明其输出要邮寄到的地址，所以能定义一份报表，就等于能按计划把工厂数据发往任意地址。这在性质上更接近 `notify.test` 和 `fleet.config`（同样仅限管理员，同样是“对外部世界做点什么”），而不是读取。这是一个判断，如果实际工作流程需要操作员构建报表，可以重新考虑。
- 操作员仍然可以通过运行报表，让邮件发往该报表的收件人，并且可以反复这样做。有一次只运行一个的保护和 `?deliver=false`，但没有速率限制。
- 拥有明确权限列表的用户，恰好持有其中所列的权限；`reports.*` 通配符涵盖这三项。

## 配置

| 变量 | 默认值 | <span class="sr-only">详情</span> |
|---|---|---|
| `HOTLOOP_REPORTS_ENABLED` | `false` | 在设置之前，功能（包括调度器）都是关闭的 |
| `HOTLOOP_REPORTS_DIR` | `/data/reports` | 每次运行的文件写到哪里。应当是一个 PVC（chart 中的 `reports.persistence`） |
| `HOTLOOP_REPORTS_RUN_TIMEOUT` | `5m` | 限定一次运行：查询、渲染、写入和邮件 |
| `HOTLOOP_REPORTS_MAX_EMAIL_BYTES` | `10485760` | 一封邮件中附件数据的最大量 |
| `HOTLOOP_TIMEZONE` | `UTC` | 工厂时区。必须是真实的时区名称，否则 HotLoop 无法启动 |
| `HOTLOOP_NOTIFY_SMTP_HOST`, `_PORT`, `_USERNAME`, `_PASSWORD`, `_FROM`, `_TLS`, `_TLS_SKIP_VERIFY` | | 报表发送邮件所用的中继。见[报警通知](/zh-hans/iot/notifications/) |

chart 的 `reports` 块包含 `enabled`、`runTimeout`、`maxEmailBytes` 和 `persistence`（大小、存储类、访问模式）。`notify.smtp` 提供中继。报表不会在 `--mcp-stdio` 模式下启动，该模式是代理把二进制文件当作辅助程序启动，而真正的 Gateway 旁边再有第二个调度器，会把每份到期的报表运行两次。

## 备份

报表定义和运行记录是用户数据，属于数据库备份的一部分。输出文件则不是：它们在报表卷上，把备份恢复到新的部署中，会带回记录但带不回文件，所以在那里下载旧的运行，会得到文件已不在磁盘上的答复。如果文件很重要，请复制报表卷。

把这两张表加入备份清单，是容易被忘记的那种改动，所以备份包现在为此设有防护。一个测试列出模式中的每张表，只要有表既不在 `backup.Tables` 中，也不在附有原因的明确排除清单里，就会失败。另一个测试从数据库读取外键，检查 `Tables` 是否按外键顺序排列。往返测试会播种一份报表定义和一次运行，并检查恢复后的值和序列。
