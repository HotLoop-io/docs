工厂的网络也是设备。PLC 不再响应时，第一个问题是“是 PLC 的问题，还是它所接交换机端口的问题”，而到现在为止，答案一直在某个人手机上的 UniFi 应用里。所以 HotLoop 直接读取 UniFi 控制台本身：每台交换机、每个端口、PoE 功耗、WAN 链路和站点的健康状况，都作为普通变量。这样，报警、趋势、实体、自动化、OPC UA 和 MCP 都可以直接使用这些变量，无需知道 UniFi 的存在。

本页介绍驱动、建立在它之上的 OT 监控、界面、事件流和第一批命令（U1 到 U5，见[路线图](/zh-hans/roadmap/)）。**它读取网络，只有在有人为此启用了某个变量时才会改动网络。** 每个变量创建时都是只读的。少数属于命令的点（见下文“命令”）和其他变量一样经过写入门：在有人把该变量标记为可写之前，不会发送任何命令，而 View Only 的控制台账户会被控制台本身拒绝。除命令外的所有功能，所用账户都可以是 View Only。

## 添加控制台

一个 HotLoop 设备是**一个控制台上的一个站点**。Cloud Gateway 和它后面的 Express 是两个控制台，因此是两个设备、两次登录，因为每个控制台都有自己的本地账户。

1. **在控制台上创建本地账户。** Settings、Admins & Users、Add Admin，勾选 **Restrict to Local Access Only**，角色选 **View Only**。Ubiquiti 云账户只能通过应用登录：它需要 MFA，控制台对脚本会返回 403。我们的账户叫 `hotloop-ro`。
2. **添加设备。** 协议填 `unifi`，地址填控制台的 URL：运行 UniFi OS 的控制台（Cloud Gateway、Dream Machine、UniFi OS Server）用 `https://host`，自托管的 Network Application 用 `https://host:8443`。轮询间隔 15 秒比较合适；无论如何设置，驱动读取同一个控制台的间隔都不会短于 10 秒。
3. **不填指纹先保存。** 第一次连接会故意失败，并给出控制台所出示证书的指纹。请确认这确实是您的控制台（控制台会显示它的证书，或者把 `openssl s_client -connect host:443` 的输出通过 `openssl x509 -pubkey -noout | openssl pkey -pubin -outform der
   | sha256sum` 处理，得到的结果相同），把它粘贴到 `certFingerprint`，然后保存。
4. 变量会在下一次轮询时自动创建。见下文。

只有当 HotLoop 拥有加密密码的密钥时，才能保存 UniFi 设备（`HOTLOOP_SECRET_KEY_FILE`，由 chart 自行配置）。参见[备份与恢复](/zh-hans/iot/backup/#设备凭据与密钥)。

| 选项 | 默认值 | 作用 |
|---|---|---|
| `site` | `default` | 站点的简称，即控制台 URL 中的那个。`default` 是每个控制台的第一个站点 |
| `username`, `password` | 必填 | 本地账户。密码通过 API 只能写入，并在数据库中加密保存 |
| `certFingerprint` | 无 | 控制台证书公钥的 SHA-256，十六进制。冒号、空格和大写字母都可以 |
| `caFile` | 无 | 信任某个 CA 而不是固定指纹，用于带有正规证书的控制台 |
| `insecureSkipVerify` | `false` | 信任任何证书。仅用于试验台，工厂中绝不要使用 |
| `clientTimeoutSec` | `90` | 控制台最后一次看到某个客户端之后，多久之内仍算它在网络上。下限为 30。参见[客户端](#客户端ot-网络以及-plc-插在哪里) |

### 为什么要固定证书

控制台出厂时带的是自签名证书，图省事的做法是跳过验证。读取一块电表时这没问题。但对于一个能看到整个工厂网络、并且从写入 PR 开始还能对其端口断电重启的登录来说，这是不行的。已固定指纹的控制台如果出示了不同的证书，会在 TLS 握手期间被拒绝，**在用户名或密码发送之前**，并且错误信息会同时列出两个指纹。固定的是公钥，所以用同一把密钥重新签发证书的控制台仍能继续工作。

不存在悄悄的“首次使用即信任”。信任一张证书只有在有人正在查看它时才有意义，所以信任就发生在那一刻。

## 登录：只登一次，非必要不再登录

每次检查都登录，曾让我们自己的 Cloud Gateway 回应 429 并锁定账户。两次。因此：

- **每个控制台、每个进程一个会话。** 每次轮询，以及控制台上的每个站点，都共用同一次登录。同一个控制台上两个站点的两个设备，使用同一账户，就是一个会话。
- **只有控制台说会话已失效时才重新登录**（401），一次一个调用方，并且**无论发生什么，每分钟最多一次**。如果一个会话在一分钟内失效两次，设备会读为坏值，直到这一分钟过去，这就是我们想要的权衡。
- **被拒绝的登录不会重试。** 密码错误、云账户或 429 锁定，会至少等待五分钟，如果控制台的 `Retry-After` 更长则等更久，设备的错误信息会说明是哪一种。把设备关了再开并不能多换来一次尝试：进程记得。
- **在最后一个使用某控制台的设备停止时会登出，** 这样重启不会在控制台上堆积会话。
- **`--mcp-stdio` 辅助程序从不登录。** 它运行在已经持有会话的 Gateway 旁边，而同一台机器上的第二次登录恰恰会招来 429。它的 UniFi 设备在那里保持停止，而在 Gateway 中正常运行。

## 变量

每个变量都由驱动创建，在有人启用之前保持只读，并按 MAC 地址和端口号命名，绝不使用显示名称，所以在 UniFi 应用里给交换机改名不会破坏任何东西。`<mac>` 是设备的 MAC，小写且不带分隔符，`<nn>` 是两位数的端口号。

| 变量 | 类型 | 含义 |
|---|---|---|
| `d.<mac>.state` | 文本 | `connected`, `disconnected`, `pending`, `upgrading`, `provisioning`, `heartbeat_missed`, `adopting`, ... |
| `d.<mac>.online` | bool, connectivity | 已连接到控制台 |
| `d.<mac>.uptime_s` | int, s | 运行时间 |
| `d.<mac>.cpu_pct`, `.mem_pct` | float, % | CPU 和内存 |
| `d.<mac>.temp_c` | float, °C | 温度，仅限有传感器的设备 |
| `d.<mac>.clients` | int | 通过它连接的客户端数 |
| `d.<mac>.fw` | 文本 | 固件版本 |
| `d.<mac>.wan<N>.up` | bool, connectivity | 按网关自己的健康检查（先看 `last_wan_interfaces`，再看 `last_wan_status`），WAN N 是**存活**的。不是 WAN 块里的 `up`，那个只表示已配置。两者都不提供的控制台读为坏值，绝不会是 up |
| `d.<mac>.wan<N>.latency_ms` | float, ms | 它的延迟，仅在 WAN 存活时有效 |
| `d.<mac>.wan<N>.availability_pct` | float, % | 按网关自己的监控在其统计窗口（一天）内得出的可用率，在它提供时才有 |
| `d.<mac>.wan.active` | 文本 | 哪条 WAN 在承载流量：上行链路所用的 WAN（若存活），否则是第一条存活的 WAN，没有则为 `none` |
| `d.<mac>.wan.failover` | bool, problem | 流量走的不是第一条 WAN：工厂正在使用备用线路 |
| `p.<mac>.<nn>.up` | bool, connectivity | 端口链路 |
| `p.<mac>.<nn>.speed_mbps` | int, Mbit/s | 链路速率；无链路的端口为 0，属正常 |
| `p.<mac>.<nn>.rx_bps`, `.tx_bps` | float, bit/s | 流量 |
| `p.<mac>.<nn>.errors` | int | 接收与发送错误之和 |
| `p.<mac>.<nn>.poe_w` | float, W, power | PoE 功耗，仅限能够供应 PoE 的端口 |
| `p.<mac>.<nn>.poe_mode` | 文本 | `auto`, `off`, `pasv24`, `passthrough` |
| `site.<subsystem>.status` | 文本 | 站点的健康状况：`wan`, `www`, `lan`, `wlan`, `vpn` |
| `site.www.latency_ms` | float, ms | 互联网延迟，在上报时才有 |
| `site.network_version` | 文本 | 控制台运行的 Network 版本 |
| `site.events_live` | bool, connectivity | 控制台的事件 websocket 已连接。0 表示 HotLoop 只在轮询，代价是速度，没有其他损失 |
| `site.last_event` | 文本 | 控制台就该站点上报的最新事件，保持其原话 |
| `d.<mac>.last_event` | 文本 | 关于该设备的最新事件。在发生第一个事件之前为空 |

设备类别会延续到实体中，因此端口的链路会以连接状态二值传感器的形式出现，它的 PoE 功耗会以功率传感器的形式出现，无需任何人设置。

**变量会自动添加，并且不会自行消失。** 下周被接管的交换机，会在下一次轮询时以变量的形式出现，在同一个会话中，无需重启任何东西。被拔掉的交换机读为 `online` 0，它的端口变为质量不良，所以针对它的报警会说明情况，而不是随它一起消失。删除它的变量由人来决定。有人关掉的变量会保持关闭：驱动没有发言权。

只有已接管的设备才有变量。有人插上但没人接管的交换机，还不属于工厂网络。控制台不上报的点读为坏值，绝不会是编造的零：不上报 PoE 功耗的交换机，其 `poe_w` 变量读为坏值。

Edge Relay 也可以轮询控制台。它读取其设备文件中声明的变量，但不添加新的，因为它没有地方保存它们。

## 命令

有五种点是命令。每个都像其他变量一样以只读方式创建，在有人把它标记为可写之前什么也不做。HotLoop 用于登录的账户必须是本地 Administrator 才能执行这些命令；如果是 View Only，控制台会回应 HTTP 403，HotLoop 会如实说明，并且什么都不会改变。

| 变量 | 写入 | 控制台的动作 |
|---|---|---|
| `d.<mac>.locate` | `true` 或 `false` | 让设备的 LED 闪烁，直到被关闭。读回控制台所报告的值。 |
| `d.<mac>.restart` | `true` | 在设备下次上报时将其重启。`false` 什么也不做。读为 0。 |
| `p.<mac>.<nn>.power_cycle` | `true` | 先关闭再开启该端口的 PoE。`false` 什么也不做。读为 0。 |
| `w.<id>.enabled` | `true` 或 `false` | 开启或关闭一个无线网络。只发送这一个字段，所以密码和其他所有设置都保持不变。`<id>` 是控制台给该网络的 ID，改名不会改变它。 |
| `c.<mac>.blocked` | `true` 或 `false` | 阻止被监视的客户端接入网络，或让它重新接入。该点只对控制台见过的客户端存在。 |

电源循环可能伤害工厂（一个每两分钟重启一次 PLC 的自动化会烧坏它的电源），所以无论谁提出请求，都遵守两条规则：同一个端口 15 分钟内最多循环一次（上次循环的时间保存在数据库中，所以重启不会让它被忘记，而时间无法核实的循环会被拒绝），并且承载网络的端口绝不循环。那是上行链路，以及按控制台自己的拓扑有其他设备挂在其下的任何端口；给 5G 备用线路供电的端口就是其中之一。拒绝时会说明是哪条规则。被控制台自己拒绝的命令不会消耗冷却时间。

## 客户端、OT 网络，以及 PLC 插在哪里

两项工作，都是只读的。

**它插在哪里。** PLC 没了响应，第一个问题是 PLC 的问题还是交换机端口的问题。把 HotLoop 设备与它在网络上的客户端关联一次，它的抽屉就会在有人打开 UniFi 应用之前显示“在 USW Lite 8 PoE 端口 5，链路 down”。这个关联还会在控制台的设备上提供客户端变量，所以端口状态会和已经停止更新的 Modbus 数值并列进入趋势和报警。

**SCADA 网络上有什么。** 把一个网络标记为 OT，接受属于它的设备，之后出现在其中的任何其他设备都会触发一条点名它的报警。有人在凌晨 2 点把笔记本电脑插到 SCADA 交换机上，您在凌晨 2 点就知道了。

### 不用 IP 做标识

控制台的客户端列表会滞后。因此：

- **客户端就是它的 MAC。** 关联时会按 IP 提出客户端，因为您对 PLC 了解的就是 IP，但由人确认一次，此后 MAC 就是关键字。IP 变量会说明这是控制台的看法。
- **在线不等于“在列表中”。** 客户端在线的条件是：控制台在 `clientTimeoutSec`（90 秒）内见过它，**并且**对于有线客户端，其交换机端口有链路。端口是反应快的一半：拔掉网线，下一次读取时端口就读为 down，而列表还在追赶。

### 关联设备

打开设备的抽屉。如果 HotLoop 所读取的某个 UniFi 控制台在该设备的 IP 上列出了一个客户端，Network 部分会提出它；管理员点击 **Link**。没有可依据的 IP（按名称寻址的设备）时，用 MAC 关联。也可以通过 API，`PUT /api/devices/{id}/network`，参见 [HTTP API](/zh-hans/iot/api/#put-apidevicesidnetwork)。

已关联设备的客户端会获得变量和一条报警 **“PLC-07 off the network”**，优先级 1，带 120 秒的开启延时，这样重启中的 PLC 不会呼叫任何人。

### OT 网络与已知列表

把一个网络标记为 OT（`PUT /api/unifi/{id}/networks/{network}`，请求体为 `{"ot": true}`），然后接受其中已有的设备：一次调用接受当前的全部（`POST .../accept-all`），或者一台一台接受。标记之后会在 `n.<network>.unknown` 上生成报警 **“Unknown device on SCADA”**，优先级 1。最新的陌生设备会在 `n.<network>.unknown_last` 中被点名，附带它的 MAC、它自称的名字、IP，以及它接入所用的交换机端口或 SSID。

已知设备可以被**监视**（`"watch": true`）：它获得与已关联设备相同的变量和同样的离开网络报警。PLC 要监视。允许接入但时来时往的维护笔记本电脑是已知而不监视的，否则它每次离开都会呼叫某个人。

这些报警是普通的报警定义。可以搁置、确认、发送到 Discord、编辑它们的延时。取消监视、关联或 OT 标记，HotLoop 就会撤掉它为此创建的报警，所以没人再读的变量不会让一条报警一直开着。管理员手写的报警则绝不会被碰。

这份记录属于 HotLoop，保存在它自己的数据库中（`unifi_networks`、`unifi_known`、`unifi_links`，都包含在备份里），绝不属于控制台。变更会在运行中驱动的下一次读取时生效，使用它已有的会话：不会重启设备，因为重启会登出，而每分钟一次登录的额度会把它挡在外面一分钟。

### 这些变量

| 变量 | 类型 | 含义 |
|---|---|---|
| `n.<network>.clients` | int | 当前在网络上的客户端数，按上面的判定为在线。每个 LAN 网络都有一个 |
| `n.<network>.unknown` | int | 在 OT 网络上：不在其已知列表中的在线客户端 |
| `n.<network>.unknown_last` | 文本 | 其中最新的一个，用文字描述。没有时为空 |
| `c.<mac>.online` | bool, connectivity | 在网络上的受监视或已关联客户端 |
| `c.<mac>.ip` | 文本 | 它的 IP，即控制台最后一次看到的 |
| `c.<mac>.sw_mac`, `.sw_port` | 文本, int | 有线客户端所在的交换机和端口。网线拔掉后仍会保留：它*曾经*在哪里才是关键 |
| `c.<mac>.port_up` | bool, connectivity | 该端口的链路。交换机本身从控制台上掉线时为坏值，因为那时没人知道 |
| `c.<mac>.last_seen_s` | int, s | 控制台上一次看到它至今的秒数 |

`<network>` 是控制台中该网络的 ID，所以在应用里给 SCADA 改名不会破坏任何东西。被标记为 OT、之后被控制台删除的网络会带着这个原因读为坏值，绝不会是悄悄的零。控制台从未见过的客户端读为 `online` 0，其余为坏值，并且会说明这一点。

只有受监视和已关联的客户端才有 `c.*` 变量。一个有 300 部手机来来去去的访客网络，不会产生 300 套变量。

### 不询问控制台就能读取

`GET /api/unifi/{id}/networks`、`/clients` 和 `/known`、抽屉，以及 MCP 工具 `find_network_client`，读取的都是驱动最近一次的读数。它们都不会自己发起请求，所以一直开着的界面，或循环提问的代理，不会给控制台增加任何负担，也不会是招来 429 的原因。另一面是：从不登录的 `--mcp-stdio` 辅助程序会说明它的进程中没有控制台读数。

## 界面

UniFi 标签页有六个视图和一个控制台选择器。其中的所有内容都是驱动最近一次对控制台的读数，所以让它一直开着不会给控制台增加任何负担，也不会是招来 429 的原因。它每隔几秒向 HotLoop 再询问一次，只在有变化时才重绘，所以有人滚动到角落的地图会停留在他们放的位置。

- **概览。** 每个控制台一张卡片。网关卡片的顶部是 WAN 条：每条 WAN 一段，网关自己的健康检查说它存活时为绿色，否则为红色，承载流量的那条有轮廓线。当站点运行在备用线路上时，整条条带变为琥珀色，并说明是哪一条以及从什么时候开始。那个“从什么时候”是 HotLoop 第一次读到这种状态的时间，而不是网关切换的时间，在站点已经使用 5G 时才启动的 HotLoop 会从它自己的启动时间算起。我们不会打印我们没有的时间。其下是：在线设备、有线和无线客户端、各网络的客户端、控制台已经丢失的设备，以及最新的事件。控制台对其什么也不说的 WAN 是灰色的，并显示“no liveness reported”，绝不会是绿色。每条上报延迟的 WAN 在数字旁边都有一条走势线，与实体磁贴所画的是同一条线，取自 HotLoop 自己对该变量的缓冲。管理员在卡片底部可以使用 **Create the usual alarms**，参见[起始报警](#起始报警)。
- **地图。** 从网关出发，由左向右。每次都以相同的方式布局（整齐的树形，没有物理模拟，相同的输入得到相同的像素），所以在墙上的看板上不会抖动。线缆就是控制台自己的 `downlink_table`：一台交换机接在另一台上，仅仅因为控制台这么说。没有任何记录说明它接在哪里的设备会单独存在，并显示“no uplink listed”。我们不会凭猜测把它挂到网关上，然后在 PLC 的网络通向哪里这件事上出错。有线客户端放在控制台学到它们的交换机和端口上，无线客户端放在它们的 AP 和 SSID 上，数量显示在卡片上的一个标签里。点击一个设备，不在它下游的一切都会变暗，侧面板会列出在它下游的内容、它的客户端，以及它所供电的 Plant 树上的产线：关联到它下方某个客户端的 HotLoop 设备，每个都带有它所在的设备路径。地图可以缩放和移动：双指捏合、单指拖动、按住 ctrl 滚动或在触控板上围绕指针捏合，或者使用加号、减号和 Fit 按钮，从整幅地图放大到最多八倍。它是纯 SVG，所以在任何缩放比例下都保持清晰，在界面刷新时，您放置的位置也保持不变。以某个设备为终点的拖动不会选中它。**Plant overlay** 把关联到某个客户端的 HotLoop 设备放进 Plant 树上每条产线各自的虚线框中，位于网络右侧，并标有产线路径，每个设备都有一条线连到它所插的交换机端口，以及网络对它的说法（up、down 或未见到）和 HotLoop 对它的说法。已关联但不属于任何产线的设备在名为“Not on the Plant tree”的框里。打开之后它保持开启。两个控制台是同一幅图：HotLoop 所读取的另一台控制台的设备，如果本控制台把它列为有线客户端，就会连同它自己的子树画在这里，用虚线并标记为“separate console”。地图可以导出为 SVG，用于站点档案。
- **设备。** 一张表，点击其中一个会看到它的面板图：端口按前面板的样子绘制，小型交换机一排，24 口和 48 口为两排，奇数口在偶数口上方。绿色表示有链路，灰色表示没有，**红色表示曾经 up 后来掉线的端口**（HotLoop 记得自开始监视以来它曾是 up），虚线表示已禁用，PoE 闪电标记（瓦数在端口的提示和详情中），上行链路上有一个箭头。点击端口可以看到上面有谁、接了什么、PoE 模式、瓦数和流量，并附有它收发情况的走势线。控制台已经丢失的设备不显示数字和端口链路，因为它最后说的内容已不是最新的。
- **客户端。** 可按名称、MAC 或 IP 搜索，显示它在哪里、控制台最后一次看到它的时间、在 OT 网络上是已知还是未知，以及与它关联的 HotLoop 设备。管理员可以直接在该行上接受未知客户端。
- **网络。** 每个网络的 OT 开关，以及“按现状全部接受”。这会改变 HotLoop 的记录，而不是控制台。
- **WiFi。** SSID、各自是否在广播、属于哪个网络以及有多少客户端。如果控制台不向该账户显示其无线网络，界面会如实说明，而不是声称没有。

这背后的路由是 `GET /api/unifi/consoles`、`.../overview`、`.../topology`、`.../devices`、`.../wifi` 和 `.../events`，记录在 [HTTP API](/zh-hans/iot/api/) 中。

### 起始报警

工厂希望在有人费心去想之前就已经配置在网络上的那些报警，根据控制台当前有的内容创建。在概览中点击 **Create the usual alarms**（或 `POST /api/unifi/{id}/starter-alarms`，参见 [HTTP API](/zh-hans/iot/api/)）会创建：

| 报警 | 作用于 | 优先级 | 开启延时 |
|---|---|---|---|
| 设备离线 | `d.<mac>.online`，每台已接管的交换机、AP 和网关 | 2 | 60 秒，这样固件重启不会呼叫任何人 |
| 上行链路 down | `p.<mac>.<nn>.up`，位于每个设备接向其上游的那个端口 | 1 | 10 秒 |
| 网关使用备用 WAN | `d.<mac>.wan.failover`，适用于有两条或更多 WAN 的网关 | 2 | 30 秒 |
| PoE 端口超过限值 | `p.<mac>.<nn>.poe_w`，仅在您给出以瓦为单位的限值时 | 3 | 30 秒 |

它们是普通的报警定义：可以搁置、确认、发送到 Discord、编辑延时或限值、删除其中一条。接管更多设备后再次点击，只会添加新设备的报警，而已经有报警的变量，无论是手工创建的还是之前点击创建的，都不会动。PoE 报警使用您给出的限值，而不是 HotLoop 选的值，因为我们所读取的控制台都不会说明端口的功率预算，我们猜的数字会成为有人信以为真的数字。“Unknown device on an OT network”和“a watched client off the network”不在这个按钮里：它们是在网络被标记为 OT、以及设备被监视或关联时创建的，附带赋予它们意义的记录。

## 事件

控制台的事件 websocket（UniFi OS 上是 `/proxy/network/wss/s/<site>/events`，自托管应用上是 `/wss/s/<site>/events`），与其他一切使用同一个会话。它从不自己登录：以 401 被拒绝的握手走的是与一次读取相同的登录额度，而被拒绝的登录会被等待，而不是重试。

**轮询仍然是事实依据。** 事件从不写入变量。它做的是：

1. 一到达就进入**日志簿**，带有控制器自己的原话（“Switch[...] was disconnected”）和它的键。交换机掉线时会在发生的那一刻出现在时间线上，而不是等下一次轮询才发现。它归入它所涉及的交换机、接入点或网关名下，而不是控制台自己的设备名下，因为控制台是运行控制器的那台机器，而不是掉线的东西。只点名某个客户端的事件（控制台说明了谁加入，但没说在哪里）会归入最近一次读取中该客户端所在的交换机或 AP 名下，如果客户端是新的，就等待该事件刚请求的那次读取，最长三十秒，如果那次读取里仍然没有它，则归入控制台名下。日志簿的 **Where** 过滤器可以从工厂的角度找到事件：与其客户端关联的 HotLoop 设备、控制台所说该客户端所在的交换机，以及按控制台自己的 downlink 表从那里到网关之间的每台交换机。掉线的交换机会出现在它所供电的每条产线的时间线上，而不会出现在它不供电的产线上。查询控制台本身仍和以前一样有效：以 `subject` 等于控制台 id 查询系统日志，以及把控制台列入范围内设备的日志簿，会返回该控制台的所有事件，包括每台交换机的事件。
2. 它进入概览所显示的日志，并进入 `site.last_event` 和 `d.<mac>.last_event`，所以自动化可以由其中一个触发。
3. 它立即请求下一次读取。读取的最小间隔是十秒；事件会把它缩短为五秒，所以变量和实体会在下一次轮询时跟上，而不是最多晚十秒。繁忙的 WiFi 网络会为每部经过的手机发送一个事件，而控制台不会为每一个都读取一次。

控制器会标记那些意味着出了问题的事件（`is_negative`：交换机失联算一个，客户端断开连接不算），这些在日志簿里是警告。其余的都是信息，包括 HotLoop 从未见过的键。

**websocket 断了只损失速度，绝不损失正确性。** 它会以两秒到一分钟的退避重新连接。它会发送 ping，一个 90 秒内毫无回应的流，不管网络怎么说都视为已死，所以会被关闭并重新打开。在它断开期间，`site.events_live` 读为 0，概览会连同原因显示“polling only”，轮询则与以前完全一样地继续。
