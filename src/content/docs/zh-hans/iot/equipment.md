工厂本来就有自己的组织方式，它拥有的每一套 SCADA、MES 和历史数据库都用这种方式：ISA-95。企业、站点、区域、产线、单元、装置、设备。HotLoop 用的就是它，一棵树，而不是楼层一份清单、区域一份清单、设备再一份清单。它下面挂着什么，请看[实体](/zh-hans/iot/entities/)。

## 层级

| 层级 | 通常指什么 |
|---|---|
| `enterprise` | 公司 |
| `site` | 一座工厂 |
| `area` | 一个部门或一栋建筑：包装、公用工程、罐区 |
| `line` | 一条生产线 |
| `cell` | 产线上的一个工作单元，或批处理工厂里的一个工艺单元 |
| `unit` | 一个生产装置：反应器、冷水机、加热炉 |
| `equipment` | 一台机器或机器的一部分：水泵、撬装设备、电机 |

子节点的层级总是低于它的父节点，所以站点永远不会放在产线下面。可以跳过层级：区域下面直接放装置没有问题，在没有区域的工厂里，站点下面直接放产线也没有问题。唯一的例外是 `equipment` 里面再放 `equipment`，因为撬装设备里有水泵，水泵里有电机，而 ISA-95 早在工厂停止嵌套之前就不再给层级命名了。节点可以以任何层级放在根上，多数工厂从 `site` 开始。

层级和名称都相同的两个同级节点就是同一个地方，所以树会拒绝第二个。

节点永远不能成为它自己的祖先：把节点移到它自己下面，或移到它下面的任何节点之下，都会被拒绝。得到环路的唯一办法是手工编辑 `equipment` 表。如果有人这样做，遍历这棵树的任何操作都不会卡住，修改环路中的节点会被拒绝，并给出一条消息，列出这些节点，并告诉您把其中一个的 `parent_id` 设为 NULL。

## 站点、区域和产线的文本仍然有效

在树出现之前，每台设备就已经有自由文本字段 `site`、`area` 和 `line`。它们不会消失。4.15 的设备编辑器会写入它们，`list_devices` 和 `describe_device` 会读取它们，别人针对它们写的每个智能体和脚本也是如此。所以文本和树会双向保持同步，并且与修改在同一个事务中完成：

**保存有文本但没有 `equipmentId` 的设备**，会找到文本所指的站点、区域和产线，找不到就创建，每一个都建在前一个之下，并把设备放在最深的那个节点上。文本相同的两台设备落在同一个节点上，不会出现任何重复。您发送的文本就是原样存储的文本：对树一无所知的客户端拿到的还是它一直拿到的内容，外加一个可以忽略的 `equipmentId`。

**保存带有会移动设备的 `equipmentId` 的设备**，会从节点的路径取得文本，不管随请求带来的是什么文本。把设备放到 `Plant A / Packing / Line 2` 下面的一个单元上，它的文本就变成 `Plant A`、`Packing`、`Line 2`。

有两个细节让这对不了解树的客户端也是安全的：

- 如果文本仍然和设备当前节点所表示的内容一致，设备就留在原处。文本只有三列，所以放在产线下面某个单元或机器上的设备只能表示到产线。用同样的文本保存它，不会把它提升到产线上。
- 读取设备后把整个设备原样送回的客户端，连同 `equipmentId` 一起，只是改了文本，就会得到文本的修改。它送回的 `equipmentId` 是设备本来就有的那个，所以这不算移动，由文本决定。

无论站点在哪里都能被找到，不只是在根上，所以把 `Plant A` 放在某个企业下面，不会让下一台写着 `Plant A` 的设备再创建第二个。

**重命名或移动节点**，会在同一个事务中重写位于该节点上及其下面的每台设备的文本。如果其中任何一步失败，则什么都没有发生：树说一套、设备文本说另一套，正是让两者保持同步所要防止的情况。响应和系统日志会列出文本发生变化的每台设备。

### 升级

迁移 `0006_hierarchy.sql` 根据每台现有设备已有的文本构建这棵树：每个不同的站点名称对应一个站点，每个不同的区域名称在其站点下对应一个区域，每条不同的产线在其区域下对应一条产线，每台设备放在其文本所指的最深节点上。有区域但没有站点的设备会得到一个根区域；有产线但没有区域的设备会得到一条直接位于其站点下的产线。只有空格的文本不指向任何东西。文本按存储的原样使用，包括空格和大小写，因为树中的名称是之后重写文本的依据，而在升级期间去掉空格，就等于悄悄给每台多出一个空格的设备改了名。升级期间不会改变任何设备的文本。

Go 一侧按同样的规则放置设备，并有一项测试让两者保持一致：升级放置的每台设备，不加改动再次保存，仍留在原处，也不会让树多出任何东西。

## 删除节点

**下面有任何东西的节点会被拒绝删除**：子节点，或放在它上面的设备。请先把它们移走。拒绝消息会说明是什么挡了路。

另一种做法是把子节点改挂到被删节点的父节点上。这样会移动它下面的每台设备并重写它们的文本，发生在一个没人动过的节点之下，还可能让一条产线直接位于站点之下、中间没有区域，那是没人画过的树。反过来，如果取消设备的放置，它们的文本就会指向一个不再存在的地方，其中任何一台下次保存时都会悄悄重新创建这个节点。两种做法都会让人意外。一条告诉您该移动什么的拒绝则不会。

放在被删除节点上的实体会失去放置，重新跟随它们的设备。

## 树上的实体

现在每个实体响应都多了三个字段：

| 字段 | 含义 |
|---|---|
| `equipment_id` | 实体本身放在哪里，当它只是跟随其设备所在位置时为 null |
| `area_id` | 实体自身节点或其上方最近的 `area`，实体没有自身节点时取其设备的节点。凡是按区域分组的功能都读取此字段。上方没有区域时为 null |
| `labels` | 实体的 label_id |

实体自己的位置优先于其设备的位置。对于整台 PLC 就是一个设备的情况，这很重要：它的温度变量属于加热炉，它的冷水机变量属于公用工程。用 `PUT /api/entities/{entity_id}` 放置实体：

```json
{ "equipment_id": 42, "labels": ["critical"] }
```

`"equipment_id": null` 会回到跟随设备。`labels` 替换整个集合。两者都需要 `entities.write`，和其他注册表字段一样。

## 标签

标签就是日常意义上的标记：`critical`、`line 1 utilities`、`calibrate quarterly`。设备和实体可以带任意多个标签。

标签有一个 `label_id` 和一个 `name`。`label_id` 在第一次时由名称生成（小写字母、数字和下划线，冲突时加 `_2`、`_3`），并且永远不会改变，因为自动化和画面引用的就是它。名称可以随时更改。创建标签时，您也可以自己选择 `label_id`。

删除标签会把它从所有带有它的对象上移除。

设备标签通过 `PUT /api/devices/{id}/labels` 设置，而不是通过 `POST /api/devices`。如今每个保存设备的客户端发送的都是不带标签的整个设备，每次保存都会把标签清掉。

## API

设备树和标签的端点使用 snake_case 字段名，与实体端点一致，因为这棵树就是实体模型的区域注册表，是为同样的使用者设计的。设备新增的字段是 `equipmentId`，采用 camelCase，与设备 API 的其余部分一致。

| 端点 | 权限 | 含义 |
|---|---|---|
| `GET /api/equipment` | `equipment.read` | 每个节点，带有从根开始的名称 `path`。筛选：`?level=` |
| `GET /api/equipment/{id}` | `equipment.read` | `{"equipment", "children", "devices", "entities"}`：该节点、它正下方的节点，以及直接放在它上面的内容 |
| `POST /api/equipment` | `equipment.write` | `{"parent_id", "level", "name", "description"}` |
| `PUT /api/equipment/{id}` | `equipment.write` | `name`、`description`、`level`、`parent_id` 中的任意一个（根用 null）。返回 `{"equipment", "devices_rewritten"}` |
| `DELETE /api/equipment/{id}` | `equipment.write` | 下面有任何东西时以 409 拒绝 |
| `GET /api/labels` | `equipment.read` | 每个标签 |
| `GET /api/labels/{label_id}` | `equipment.read` | 带有该标签的 `{"label", "devices", "entities"}` |
| `POST /api/labels` | `equipment.write` | `{"label_id"?, "name", "color", "icon", "description"}` |
| `PUT /api/labels/{label_id}` | `equipment.write` | 名称、颜色、图标、说明。绝不改 label_id |
| `DELETE /api/labels/{label_id}` | `equipment.write` | 把它从所有对象上移除 |
| `PUT /api/devices/{id}/labels` | `equipment.write` | `{"labels": [...]}`，整个集合 |
| `POST /api/devices` | `devices.write` | 增加可选的 `equipmentId`，如上所述 |
| `GET /api/devices/{id}` | `devices.read` | 在 `device` 和 `tags` 之外增加 `labels` |

每个角色都有 `equipment.read`：东西在哪里，正是设备的站点和区域原本就告诉查看者的信息。只有管理员有 `equipment.write`，因为重命名或移动一个节点，会重写它下面每台设备的站点、区域和产线，而这属于配置。

每次更改都会记入系统日志，类别为 `config`，主题为 `equipment:<id>` 或 `label:<label_id>`。

## MCP

`list_devices` 和 `describe_device` 像以前一样根据文本作答，输出不变。一项测试把它逐字节固定为树出现之前的版本所给出的答案，然后围绕设备重新排列这棵树（在站点之上放一个企业，在产线之下放一个单元，加一个标签），并检查智能体看到的内容没有任何变化。当树确实改变了文本时，比如重命名，智能体看到的是新文本，就和有人把它直接输入到设备里一样。智能体通过 `list_entities` 查看这棵树：它可以按某个节点及其下面的一切来筛选，并给出每个实体的位置。请看 [MCP](/zh-hans/iot/mcp/#entities)。

## 备份和恢复

`equipment`、`labels`、`entity_labels` 和 `device_labels` 都在备份中，新的 `equipment_id` 列也是。`equipment` 引用它自己（`parent_id`），而恢复无法为此排序：节点移动之后，父节点很容易排在它的子节点之后存储。该约束是 `DEFERRABLE INITIALLY DEFERRED`，所以它在恢复提交时、所有行都已进入之后才检查，对于用多条语句重写这棵树的其他操作也是如此。备份防护测试只在该约束为延迟时才允许表引用自身，往返测试则故意先存子节点、再存它的父节点。

在此版本之前做的备份仍然可以恢复。它的 `devices` 和 `entities` 文件少一列；恢复会把它们载入表的前几列（新列总是加在末尾），新列取默认值。然后，在同一个事务中，它根据文本把每台恢复的设备放到树上，就像升级所做的那样。

## 工厂画面

树在一侧，旁边是所选节点的卡片：它的路径、它上面的设备、放在它上面的实体，以及它下面的内容。管理员可以在根下或所选节点下添加节点，重命名、更改层级、移动、删除，在它上面放置设备或移走设备，并设置设备的标签。层级列表只提供规则允许的层级，既要符合父节点，也要符合已在其下的子节点；移动只提供该层级节点可以放到其下的父节点，绝不包括节点本身或它下面的任何节点。服务器会再次检查所有内容，拒绝（比如下面还有东西时的删除）会原样显示它写下的消息。移动设备就是设备编辑器所做的同一次保存，带一个 `equipmentId`，所以文本会按上面所述跟随树。

标签在画面底部管理：名称、颜色和说明，`label_id` 选定一次后即固定。实体通过实体画面里它们自己的抽屉获得位置和标签。

其他人看到的是同一个画面，只是没有任何可以按的东西。
