工厂屋顶上的一座气象站，在屏幕上就是一个整体。HotLoop 不会给任何人打电话来确认是否在下雨。这由气象站自己说：通过 MQTT 的 Ecowitt 或 Tempest，通过 Modbus 的 Davis 或 Vaisala，通过 OPC UA 的任何设备。其中任何一个的读数本身就是变量，而天气实体就是一座气象站的各个变量，每个变量各司其职：温度、湿度、气压、风、雨和日照。

不需要天气服务，不需要 API 密钥，也不需要互联网。上行链路三周前就断了的现场，照样显示自己屋顶上的温度。（太阳在哪里，请见[太阳位置与日出日落](/zh-hans/iot/sun/)；那是根据现场的纬度和经度算出的，根本不需要气象站。）

## 创建

天气实体的创建方式与电机相同（见[实体](/zh-hans/iot/entities/#复合设备)）：由管理员指定变量。在实体界面选择新建设备，再选天气。也可以通过 API：

```json
POST /api/entities
{
  "domain": "weather",
  "name": "Roof station",
  "bindings": [
    {"role": "temperature", "device_id": "roof", "tag_name": "Temp"},
    {"role": "humidity",    "device_id": "roof", "tag_name": "Humidity"},
    {"role": "wind_speed",  "device_id": "roof", "tag_name": "Wind"},
    {"role": "wind_bearing","device_id": "roof", "tag_name": "Bearing"}
  ]
}
```

只有 `temperature` 是必需的。没有雨量计的气象站没有 `rain_rate`，也不显示降雨行。每个角色接受一个数值变量，且都不会被写入：气象站只被读取，从不被命令，所以不需要启用任何变量，实体也不接受任何服务。

| 角色 | <span class="sr-only">详情</span> | 生成的属性 |
|---|---|---|
| `temperature` | 必需，即状态 | `unit_of_measurement` |
| `humidity` | 相对湿度，百分比 | `humidity` |
| `pressure` | 气压，使用变量的单位 | `pressure` |
| `wind_speed` | 平均风速 | `wind_speed` |
| `wind_gust` | 最近最强的阵风 | `wind_gust` |
| `wind_bearing` | 风的来向，0 到 360 度 | `wind_bearing` |
| `rain_rate` | 现在的降雨强度 | `rain_rate` |
| `rain_today` | 午夜以来的降雨量 | `rain_today` |
| `solar_radiation` | 传感器上的日照，通常为 W/m² | `solar_radiation` |
| `uv_index` | 紫外线指数 | `uv_index` |

每个属性还带有 `<name>_unit`，写明其变量的单位，因此界面不必去猜气压是 hPa 还是 inHg。

## 在盒子上算出的内容

气象站很少发送的三个值，由它自己的读数算出：

| 属性 | 来源 | 方法 |
|---|---|---|
| `dew_point` | 温度、湿度 | Magnus 公式（Sonntag 1990），与 0 到 30 °C 的湿度计算表核对 |
| `heat_index` | 温度、湿度 | 美国国家气象局（NWS）的 Rothfusz 回归及其公布的两项修正。仅在 80 °F（26.7 °C）及以上存在，因为 NWS 到此不再使用它 |
| `wind_chill` | 温度、风速 | NWS 2001 年的指数。仅在 50 °F（10 °C）或以下且风速超过 3 mph 时存在，这是它拟合的范围 |

它们以温度自身的单位返回，因此使用华氏度的气象站得到的露点也是华氏度。HotLoop 转换的温度单位是 °C、°F 和 K，风速单位是 m/s、km/h、mph、节和 ft/s，均从变量的单位读取。没有单位的温度变量不会靠猜测来转换：实体自己的 `unit_of_measurement` 可以说明它是什么，两者都没有时，就不会据此算出任何东西。

热指数和风寒缺失并不是故障。80 °F 以下没有热指数，空气平静或温暖时没有风寒，所以卡片上没有它们的行。

## 缺失的读数不是零

天气实体从不乐观，也从不用数字填补空缺。

* 没有绑定的传感器不是一行。
* 已绑定但现在读不到的传感器（变量不良、设备停机、尚未收到任何数据），会被排除在属性之外，并在 `unavailable` 中点名。卡片在它的数字应该出现的位置显示**不可用**。
* 不可能是测量值的读数也同样处理：高于 105% 的湿度、超出 0 到 360 度的方位、负的降雨量或风速。起雾时传感器读到的 101 或 102 的湿度，显示为
  100. 日射计夜间的小幅负读数显示为 0。
* 由不可用的读数算出的值同样不可用，并会点名：没有湿度，就没有 `dew_point` 和 `heat_index`。
* 如果读不到温度，状态为 `unknown`（设备停机时为 `unavailable`），质量如常，卡片的其余部分仍显示其他传感器所报告的内容。

## 在界面上

在实体界面上，一座气象站是一块磁贴：大字号的温度，下面是气象站给出的每个读数各一行，顺序固定（湿度、气压、风、风向、阵风、降雨强度、今日降雨、日照、紫外线指数、露点、热指数、风寒）。温度带有常见的趋势线。卡片以界面支持的每种语言显示，在阿拉伯语中从右到左排版。

## MCP

代理通过每个实体都有的工具，以及一个说明气象站接受什么的工具，来读取和创建气象站：

| 工具 | 作用 |
|---|---|
| `list_composite_entities` | 读取 `create_entity` 能创建什么，每个域及其角色，哪些必需，哪些由服务写入。天气有十个角色，一个必需，没有服务 |
| `create_entity` | 由变量创建气象站，如同 `POST /api/entities`。和所有更改一样，需要理由和 MCP 写入开关 |
| `get_states` | 读取一座：状态是温度，模型读到的文本在旁边列出所有属性，包括 `unavailable` |
| `list_entities` | 用 `domain: weather` 查找气象站 |
| `delete_entity` | 删除一座 |

对天气实体调用 `call_service` 会被拒绝：它不接受任何服务。

## 它不做什么

* 不做预报。不问别人就没有预报，而 HotLoop 不这样做。
* 不会把气象站的温度记成日志簿行，就像没有任何传感器这样做一样。历史是变量的历史：磁贴上的趋势线是温度变量的，其他每个变量也和其他任何变量一样存在于历史库中。
* 不会替您读取气象站。气象站首先以变量的形式到来：添加它的设备（MQTT、Modbus 或 OPC UA），然后绑定变量。
