HotLoop 自 4.12.0 起会对历史数据库做逻辑快照（仅表数据）并可恢复。默认开启，每天一次（`HOTLOOP_BACKUP_ENABLED`，`HOTLOOP_BACKUP_INTERVAL` 24h），二进制和 Helm chart 都是如此。备份保存在 `HOTLOOP_BACKUP_DIR` 下，默认是 HotLoop 数据目录中的 `backups`（`HOTLOOP_DATA_DIR`，否则在 `/data` 可写时用它，否则用 `~/.local/share/hotloop`）：没有配置备份卷的部署，不应让这个进程悄悄写进容器的临时文件系统。

## 这是什么

备份是一个目录：每张表一个文件，外加一个小的 `manifest.json`（HotLoop 版本、数据库已应用的架构迁移、时间戳，以及每张表的行数和列及其类型）。

## 这不是什么

- **不是 `pg_dump`/`pg_restore`。** Gateway 的运行时镜像（`gcr.io/distroless/static-debian12:nonroot`）刻意只是一个静态二进制文件，别无其他：没有 shell，没有包管理器，没有任何外部二进制文件。这里的一切都通过应用已经持有的同一个数据库连接完成。
- **不是架构备份。** 架构在每次启动时自动重建（`HOTLOOP_DB_MIGRATE`，默认开启）。备份只捕获表的*数据*，恢复始终假定架构已先由这些迁移重建好。
- **不是时间点恢复。** 这里没有 WAL 归档，也没有持续复制。备份是它运行那一刻的快照；那一刻之后、下一次备份之前写入的内容不在覆盖范围内。
- **不是设备之外的存储。** 备份目录（`HOTLOOP_BACKUP_DIR`，设计上由本 chart 提供的 `backup.persistence` PVC 承载）仍然是同一集群里的一个卷。把备份放到真正持久、有复制或离线的存储上（把卷复制到对象存储、给 PVC 做快照，或运维人员实际基础设施提供的其他方式）是运维人员的工作，就像本项目一向把持久存储视为基础设施的责任，而不是由应用重新发明一个多云备份适配器。

## 保护备份文件

备份文件是敏感的。`users.copy` 文件包含密码和自助终端 PIN 的 bcrypt 哈希，`sessions.copy` 和 `write_audit.copy` 包含会话记录和写入审计轨迹。文件以 `0640` 权限创建（备份目录为 `0750`），已存在的文件会报错而不是被覆盖，但这只是底线，不能代替对卷本身的保护：请把备份卷放在静态加密的存储上，限制谁和什么可以读取它，并对运维人员做的任何设备外副本给予同样的小心。

`devices.copy` 文件按保存时的样子包含每台设备的地址和协议配置，其中包括驱动用来登录的凭据。它们的可读程度取决于下面的密钥。自 4.15.1 起，API 对所有角色（包括管理员）隐藏所有设备凭据；备份文件不在 API 之后。参见[身份验证与用户](/zh-hans/iot/authentication/#凭据仍是明文的地方)。

## 设备凭据与密钥

备份是会被复制到笔记本电脑、共享文件夹和工单里的文件。所以其中的凭据是加密的，所用的密钥从不在数据库中，也从不在备份中。

- **设置了 `HOTLOOP_SECRET_KEY_FILE` 时**（chart 会设置它，密钥在安装时生成，并在升级和卸载之间保留），每一个带密钥的凭据（OPC UA、CODESYS、MQTT、HTTP、MTConnect 和 UniFi 设备的 `password`，SNMP 设备的 `community` 和口令，API 密钥这类 HTTP 和 MTConnect 头的值，发现功能所监听的每个其他 MQTT broker 的密码，以及每个历史库目标的密码）都在数据库中加密，`devices.copy`、`mqtt_sources.copy` 和 `historian_targets.copy` 保存的是密文。清单把加密所用的密钥列为 `secretKeyIds`：是一个 id，绝不是密钥本身。
- **没有它时**，这些凭据在数据库和 `devices.copy` 中是明文，HotLoop 会在启动日志中说明。UniFi 控制台、带密码的 MQTT broker 和带密码的历史库目标，没有密钥时根本无法保存。设置一个并重启：已存储的所有内容会在那次启动时被加密。
- **写在 URL 或文本里的凭据也会被封存**（`mqtt://user:pass@host`、`?token=` 或 `?api_key=` 查询值、提到密码的 HTTP `body`）。设备的地址或选项只要含有这样的内容，就会整体封存，驱动拿回的是原样输入的内容。不含任何机密的 URL 保持可读。没有密钥时，这些和其余内容一样是明文，启动日志会说明；有密钥时，已存储的所有内容会在那次启动时被封存。密码选项仍然是存放密码的更好位置。

**恢复需要同一个密钥。** `--restore-from` 在加载任何一行之前先检查清单：用恢复方 HotLoop 没有的密钥加密的备份会被拒绝，错误信息会指出所需的密钥。请挂载那个密钥文件再恢复。如果密钥已永久丢失，请加上 `--restore-keep-unreadable-credentials`：其他一切都会恢复，凭据无法打开的设备会保持停止状态，并说明它需要哪个密钥，直到有人重新输入凭据。在有密钥之前做的备份可以恢复到任何地方，恢复一结束它的凭据就会被加密。

**请把密钥保存在备份所在之外的地方。** 与备份放在一起的密钥什么也保护不了。使用 chart 时它是 `<release>-secret-key` 这个 Secret；请像备份集群其他 secret 那样，单独备份它。

## 备份什么，按什么顺序

每一张用户数据表，按外键依赖顺序（一张表总是排在它自己的外键所指向的所有表之后）：

```
devices → tags → tag_latest → alarm_definitions → alarm_state →
alarm_events → automations → automation_runs → blueprints → scripts → script_runs →
recipes → recipe_versions → recipe_applications → events → write_audit →
settings → users → sessions → user_certificates → energy_meters → energy_meter_state →
energy_buckets → fleet_members → report_definitions →
report_runs → entity_state_log → tag_history
```

（节选；`backup.Tables` 是完整列表，包含实体和设备表以及 `entity_last_state`。）日志簿的 `entity_state_log` 在两种历史模式下都按月分区，排在 `tag_history` 之前，后者是唯一比它更大的表。恢复在它的任何月度分区存在之前加载其行，所以这些行会落入默认分区。日志簿的维护在记录数据的 Gateway 启动时，会围绕属于它们的行创建上个月和这个月的分区，并在旧行超过保留期时将其从默认分区中删除，因此保留期会作用于每一条恢复的行。参见[日志簿](/zh-hans/iot/logbook/)。

脚本会带着它们的历史一起回来。备份在运行中途抓到的一次运行会以 `running` 回来，Gateway 第一次启动时把它标记为已取消，`interrupted by restart`，与被崩溃打断的运行相同：没有任何东西会继续一次运行。参见[脚本](/zh-hans/iot/scripts/)。

配方会带着每个版本和每次应用一起回来。备份在应用到一半时抓到的应用会以 `applying` 回来，Gateway 第一次启动时把它标记为 `failed`，并指向它在写入审计中的调用 id：没有任何东西会继续一次，也没有任何东西会撤销一次。参见[配方](/zh-hans/iot/recipes/)。

`schema_migrations` 被刻意排除：`store.Migrate` 会根据内嵌的迁移重建它以及每张表的 DDL。它是 `backup.ExcludedTables` 中唯一的条目，该列表记录了每张被排除的表为什么被排除。

这个列表是手工维护的，所以才会出现迁移新增了一张表、之后却悄悄被每一份备份漏掉的情况。有两个测试防着这一点，两者都在两种存储模式下针对真实数据库运行。计划报告的表（`report_definitions`、`report_runs`）是在这些保护之下新增的第一批表。报告的输出文件在报告卷上，不属于数据库备份。`tag_history` 在恢复时最后加载：它没有自己的外键，并且是迄今最大的表，所以每张小的配置表如果要失败，会在那个漫长的步骤开始之前就很快失败。

**`settings` 有一个刻意的例外。** `history_mode` 这一行由 `store.ensureHistorySchema` 自己写入，只写一次，就在 `Migrate` 从零开始构建架构的那一刻：它记录*这台服务器*把 `tag_history` 构建成了 TimescaleDB hypertable 还是原生分区表，这是关于 `Migrate` 刚刚运行所针对的数据库的事实，而不是关于工厂的事实。它同时被排除在 `settings` 的备份和恢复之外：把源安装的历史决定恢复到能力不同的目标上（甚至只是恢复到针对同类服务器的一次全新 `Migrate` 运行上），可能会把这一行改写成描述目标实际并不具备的形态。目标自己的 `Migrate` 在 `Restore` 看到 `settings` 之前已经做出了正确的决定，这个决定保持不变。

## 按需备份

- `POST /api/backup`（`backup.run`，仅限管理员）立即做一次备份并返回清单。
- `GET /api/backup`（`backup.read`，仅限管理员）列出备份卷上的内容：名称、磁盘大小，以及每一份的清单（表列表、行数、HotLoop 版本、时间戳）。

这两个都因操作员角色中没有而仅限管理员，与 `fleet.restart`/`fleet.config`/`notify.test` 已对其他运维类、“立即执行”类或管理范围的操作所做的收窄相同。备份列表的行数，包括 `users` 和 `sessions`，读起来更像管理诊断，而不是操作员角色应当看到的车间读数（设备、变量、报警），因此 `backup.read` 没有像某些读取那样拆成更低的权限；这是一个判断，不是技术限制，如果真实的操作员工作流需要，可以重新考虑。

## 计划与保留

`HOTLOOP_BACKUP_INTERVAL`（例如 `24h`）按固定间隔运行备份。这刻意只是一个简单的间隔，而不是 cron 表达式解析器：现实的需求是“每隔一段时间备份一下这个”，而本项目自己的惯例是不为尚无人有的需求去构建。不设置（或设为 `0`）会关闭调度器；按需端点仍然可用，供想自己触发的运维人员或外部 cron 使用。

`HOTLOOP_BACKUP_RETAIN`（默认 `7`）保留最新的 N 个备份目录，每次备份成功后删除更旧的。`0` 或更小表示全部保留，在小的卷上，这是运维人员必须有意做出的选择。

## 恢复备份

**恢复刻意不是 API 端点。** 把“立即恢复”自动化成一个可经网络触发的实时操作，并且针对可能正在提供生产流量的数据库，是真实的危险：一次误点，或一个被攻破的管理员会话，就会覆盖线上数据，而本项目在没有被明确要求的情况下不会去构建它。恢复是二进制文件本身的一个标志，由已经决定目标数据库应当接收它的运维人员手动运行一次：

```sh
hotloop --restore-from=/data/backups/20260918T220000Z
```

它按顺序做的事情：

1. 加载配置，并像一次普通启动那样连接数据库：`store.Open` 运行相同的迁移，构建恢复即将向其加载数据的架构。
2. **拒绝无法在不丢失任何东西的情况下加载的备份**：在比这个数据库更新的架构上做的备份，或者含有此版本已不再有的表或列的备份。两者都在加载任何一行之前检查。参见下面的“恢复到不同版本”。
3. **如果任何目标表已有数据则拒绝**，超出 `Migrate` 自己刚刚写入的部分（`settings` 中唯一的 `history_mode` 行）：恢复只会针对尚无任何内容的数据库运行。这就是安全检查：哪怕只有一行已有数据的表，也会在任何 `COPY FROM STDIN` 运行之前停止整个恢复。
4. 按依赖顺序，在单个事务内，把每张表加载到清单所列的列中。
5. 把每张带 `bigserial` 主键的表（`tags`、`alarm_events`、`automation_runs`、`events`、`write_audit`、`sessions`）的后备序列重置为比已恢复的最大 id 大一：`COPY FROM STDIN` 加载显式的 id 值而不触动序列，所以跳过这一步会让下一次普通插入与已恢复的行冲突。
6. 在同一个仍然打开的事务内，重新统计每张表并与清单的行数比较。
7. 只有每个计数都匹配才提交。任何不一致，或前面任何一步的任何错误，都会回滚整个事务，使目标数据库保持被发现时一样的空，绝不会只加载一部分。
8. 退出。进程中不会启动其他任何东西：没有轮询调度器，没有报警引擎，没有 API 服务器。恢复用不上其中任何一个，而针对恢复到一半的数据库启动运行时本身就是一个危险。

### 迁移到 PostgreSQL 17

这份备份由正在运行的应用通过它与正在运行的数据库的连接制作，所以它不可能成为 PostgreSQL 16 到 17 迁移的备份：那次迁移发生在数据库启动之前。升级本身的安全保障是它从不写入 PostgreSQL 16 目录，并把它完整保留为 `pgdata.pg16`（k3s 和 Helm 页面，“PostgreSQL 17”）。尽管如此，请在升级前先在旧版本上做这份备份，因为它是存放在设备之外的那份副本。把它恢复到新数据库就是下面的普通恢复：它携带的是行，而不是引擎，所以不在乎是哪个主版本写入的。

### 恢复到不同版本

您用来恢复的版本很少是制作备份的那个版本。备份是几个月前用当时运行的版本做的，而您正在重建的设备运行的是今天的版本。所以下面说明什么可以恢复到什么上。

**较旧的备份恢复到较新的 HotLoop：可以。** 这是最重要的情形，从曾经有过的每一个架构级别（从 `0001_core` 到今天），在 TimescaleDB 和普通 PostgreSQL 上都经过测试，并在之后启动了应用。

- 每份清单都记录了每张表的列、名称和类型。恢复把每个文件按名称加载到恰好这些列中。备份之后新增的列取其默认值。`write_audit` 的 `entity_id`、`service` 和 `call_id` 在实体服务之前的每一行审计记录上回来时是空的，这些行本来就是这样：单纯的变量写入。
- 备份之后新增的表保持为空，应用在启动时会填充它能填的内容。实体注册表的首次同步会给每个已恢复的变量其读取实体，给每个已布防的变量其控制实体，给每个报警定义其报警实体，使用注册表本来会给它们的名称。来自早于设备树的备份的设备，会在恢复过程中根据其站点、区域和产线文字被放入设备树，与升级时放置它们的方式相同。从未在备份中的内容无法回来：标签、组合实体，以及运维人员在备份之后自定义的实体名称。

**较新的备份恢复到较旧的 HotLoop：不可以，会被拒绝。** 清单记录了备份所在数据库已应用的每一个迁移。如果其中有这个数据库从未运行过的迁移，恢复会在加载任何一行之前停止并说明：

```
refusing to restore: this backup was taken by HotLoop <its version> with the
database schema at <its newest migration>, which is newer than this database's
schema at <this database's newest migration> (HotLoop <this version>). ...
Restore it with HotLoop <its version> or a later release
```

“较新”指的是迁移，而不是版本字符串。版本字符串说明是哪个二进制文件做的备份，而开发构建、候选版本和热修复分支使比较它们变成一种猜测。迁移说明了架构究竟是什么样的，并且作为一个集合来比较，所以不论缺失的迁移落在顺序的哪个位置都能被发现。消息里有版本，是因为版本是您可以据以行动的内容：用哪个版本来恢复。

**含有此版本已不再有的列的备份：被拒绝，并指出名称。** 迁移删除、重命名或更改某列类型的那一天，在此之前的备份中有新表没有位置存放的数据。恢复不会猜。在加载任何内容之前，它会指出所有表中的每一个这样的列：

- 运行中的表没有的列会被拒绝，除非 `backup.columnRenames` 把它映射到新名称。重命名列的迁移会添加该条目，并在同一次变更中添加一个恢复该迁移之前备份的测试。目前没有重命名，所以该映射为空；
- 类型改变的列会被拒绝。二进制 COPY 不携带类型，所以这些字节会被当作新类型读取，或在中途被拒绝；
- 运行中的表新增为 `NOT NULL` 且没有默认值的列会被拒绝，因为没有任何东西能填充它。

三种情况的出路相同：用制作备份的版本恢复，然后就地升级该数据库，这正是迁移原本设计用来遇到那些数据的方式。

按名称加载也涵盖了没人会注意到的变化：某一列被删除后又重新添加，或某张表被重建，使各列的顺序不同。按位置加载在类型一致时会毫无报错地把一列的值放进另一列。按名称，每一列都落在它该在的位置。

**在清单记录这些内容之前做的备份**（此版本之前做的每一份备份）没有列列表，也没有架构。它们仍然可以恢复：

- 没有列列表时，恢复退回到按位置。列数少于表的文件会进入表的前几列，其余取其默认值。这对迄今为止的每个架构都是正确的，因为到目前为止每个迁移都只新增了列，而 `ALTER TABLE ADD COLUMN` 总是追加到末尾。列数多于表的文件会被 PostgreSQL 自己拒绝。
- 没有架构时，恢复假定备份尽可能新：`0007_service_audit.sql`，即清单开始记录它时最新的迁移。这个假定只可能拒绝一次本来能成功的恢复，绝不会放过一次不会成功的。实际上它什么也不拒绝，因为任何带有这项检查的 HotLoop 都已经运行了直到那个迁移的每一个迁移。

此版本做的第一份备份就记录了一切，所以这种回退只对已经放在备份卷上的备份有意义。

### 恢复步骤，逐步说明

1. 把备份目录放到目标部署的 `hotloop` 二进制文件能读取的机器或卷上：这就是运维人员自己做的备份卷设备外副本重新派上用场的地方。
2. 把 `HOTLOOP_DB_*` 指向**目标**数据库。它必须可访问，并且在任何已备份的表中都还没有数据（全新的空数据库是常规情形；架构将在第 3 步构建）。
3. 运行 `hotloop --restore-from=<path to the backup directory>`。
4. 阅读最后一行日志：带有表数和行数的 `restore complete`，或一条准确说明拒绝了什么以及原因的错误。
5. 针对同一个数据库正常启动 `hotloop`。

## 在数据库之间迁移

无论是哪种数据库做的备份，备份都是同一种东西：PostgreSQL 的二进制 COPY 文件，加上一份写明每列 Postgres 类型的清单。所以把工厂从一个数据库迁到另一个，就是在旧库上做备份，再恢复到新库里。别无其他。

- **SQLite 到 Postgres 或 TimescaleDB。** 那台已经超出文件承载能力的 Pi。做一次备份，把 `HOTLOOP_DB_*` 指向新服务器（`HOTLOOP_DB_TYPE=postgres`），恢复。在 TimescaleDB 服务器上，历史数据会落入 hypertable。
- **Postgres 或 TimescaleDB 到 SQLite。** 缩减到小型设备的工厂。反方向做法相同，使用 `HOTLOOP_DB_TYPE=sqlite`。
- **普通 Postgres 到 TimescaleDB，以及反过来。** 历史模式是固定的，所以把 Gateway 指向 IoT 设备的普通 Postgres 会保留其分区。要得到 hypertable，请恢复到全新的 TimescaleDB。反方向则得到分区。

导入时检查的内容与任何恢复检查的内容相同：每一列按名称和类型与目标核对，SQLite 的列按其对应的 Postgres 类型读取，所以一方的备份可以恢复到另一方，或者因与任何地方相同的原因被拒绝。`history_mode` 从不复制：目标保留它自己的迁移所做的决定。序列在两边都会正确：在 Postgres 上由 `fixSequences` 移动，而 SQLite 的 AUTOINCREMENT 会自己越过任何恢复到其中的 id。

## 配置

| 变量 | 默认值 | <span class="sr-only">详情</span> |
|---|---|---|
| `HOTLOOP_BACKUP_ENABLED` | `false` | 在设置它之前，该功能（包括 API 路由）处于关闭状态 |
| `HOTLOOP_BACKUP_DIR` | `/data/backups` | 备份写入的位置；设计上应为 PVC（chart 中的 `backup.persistence`） |
| `HOTLOOP_BACKUP_RETAIN` | `7` | 保留最新的 N 份备份；`0` 或更小表示全部保留 |
| `HOTLOOP_BACKUP_INTERVAL` | 未设置 | 例如 `24h`；未设置表示仅按需 |

`--restore-from=<dir>` 是 `hotloop` 二进制文件的命令行标志，不是环境变量，参见上面的“恢复备份”。
