一条时间线，记录工厂里发生的一切，最新的在最前：水泵启动了，有人把 180 写入 1 区的设定值，高温报警触发并被确认，冷却自动化运行了，一台设备被重新配置。可以看整座工厂、设备树上的某个位置及其下面的一切，或某一个实体。它就是日志簿标签页、每个实体抽屉里的一个部分、`GET /api/logbook`（请看 [HTTP API](/zh-hans/iot/api/#日志簿)）和 MCP 工具 `get_logbook`（请看 [MCP](/zh-hans/iot/mcp/)）。

出了问题之后的第一个问题是“刚才发生了什么？”，而到现在为止，答案分散在五个地方：写入审计、报警历史、自动化运行记录、系统日志，以及没有人记得的设备自己做过什么。日志簿就是这五样合在一个列表里。

## 里面有什么

| 类型 | 来源 | 一行表示什么 |
|---|---|---|
| `state` | `entity_state_log` | 某个实体的状态变了：`changed to on (was off)` |
| `write` | `write_audit` | 对变量的一次写入，成功、被拒绝或失败，由谁通过哪个入口 |
| `alarm` | `alarm_events` | 一次报警触发、确认、清除、搁置，附带所给的备注 |
| `automation` | `automation_runs` | 一条规则运行了，如何结束，由什么启动 |
| `event` | `events` | 配置更改、服务调用的摘要和写入所给的理由，以及 UniFi 控制台在事件发生的当下所报告的内容，归在它所涉及的交换机或接入点之下（交换机失去联系是一条警告） |
| `script` | `script_runs` | 一个[脚本](/zh-hans/iot/scripts/)运行了，如何结束，由谁启动，由什么调用 |
| `recipe` | `recipe_applications` | 一个[配方](/zh-hans/iot/recipes/)被应用或被拒绝：哪个版本，由谁，有多少个目标收到了值并被读回 |

只有 `state` 是新增的。其余的在查询时从它们原本所在的地方读取并合并。没有任何东西被写两次，所以不会有什么与它的来源记录不一致，每一份记录也保留各自的保留期限（见下文）。

从系统日志中，日志簿取 `config` 类别，以及 `write` 类别自己的行：服务调用的摘要、报警服务调用、写入所给的理由。写入关卡自己的“wrote ...”和“write of ... refused”行被排除在外，因为它们说的正是写入审计里已有的内容，否则每次写入都会出现两遍。

### 有意不包含的内容

**数值读数。**传感器、数字、回路或 PLC 计数器每次轮询都在变化，每个读数早已在历史数据库中。再把它们记一遍，会把每一行有人想读的内容埋在每天一百万行没人想读的内容之下。请改用趋势来看。

**按钮。**按钮的状态是它最后一次按下的时间，每一次按下都已经是审计中的一次写入。它每次重启还会回到未知，那就是每个按钮每次重启一行什么也不说的记录。

**报警实体的状态。**报警自己的历史在日志簿里以 `alarm` 行的形式存在，包含更多内容（值、备注、是谁确认的）。

其余一切都会记录：二值传感器、开关、文本、选择项、电机、阀门、辅助项，以及到来的脚本。

**辅助项由改动它的一方记录。**辅助项的变化与它的值在同一个事务中写入日志簿，由做出改动的进程写入，包含谁做的、来自哪里、使用哪个调用 id，并且从不限速。记录器不管辅助项：它只在 Gateway 里运行，所以智能体通过 `--mcp-stdio` 做的更改它会漏掉，而每个持有该辅助项的进程都看得到这一变化，那它就会每个进程记一次。计划是例外，因为没人设置它，是时钟在推动它：记录器像对其他实体一样记录它。

## 抖动

一个以 10 Hz 抖动的触点是一个事实（“它抖动了这么多次”），而不是每小时三万六千行。每个实体先连续记录十次变化，之后每两秒记一次。超出的变化不记录，而是计入该实体的下一行：

```
changed to closed (was open); 14 changes before this not logged, it was changing faster than the logbook records
```

计数是精确的：这些行加上它们的计数，就是该实体做出的每一次变化。抖动停止时，实体的最终状态总是会在两秒内记录下来，所以日志簿不会停在设备已经离开的状态上。自启动以来被抑制的数量是 `/api/diagnostics` 中 `logbook` 下的 `suppressed`。

## last_changed 在重启后依然保留

实体的状态由实时变量计算，从不存储，所以在有日志簿之前，每次重启都会让所有实体看起来像是刚刚变化过。日志簿保存每个被跟踪实体的最新状态和它上次变化的时间（`entity_last_state`），实体引擎启动时读取它。状态恢复为相同的实体保留它的 `last_changed`。

从内部看，一次重启是这样的：某台设备尚未连接，所以它的实体变为不可用，然后未知，然后显示读数。这些步骤是这个进程在追赶，不是工厂在变化，所以会等它们过去。在 Gateway 停机期间真正变化的状态会得到新的 `last_changed` 和一行说明它之前是什么的记录。出于同样的原因，日志簿在启动后的第一分钟会压住变为不可用或未知的变化：在那之后仍然停机的设备会在那时被记录，时间是它第一次被看到停机的时间。

## 筛选

- **地点：**设备树的一个节点及其下面的一切。一个地点会被转换成各份记录所知道的它的所有名称：那里的实体（按它们自己的位置，否则按设备的位置，与实体画面所用规则相同），那里的设备及其上的每个变量，这些变量上的报警，在其中任何一个上设有触发器的自动化，以及节点本身（用于其配置更改）。自动化的一次运行如果在运行时写入过那里，也属于该地点，不管是什么触发了它。UniFi 控制台的事件通过网络查找，而不是依据人在树上放置的任何东西：所链接设备挂靠的交换机，以及它与网关之间的每台交换机，所以一台交换机掉线会显示在它供电的每一行之下。放在树上的控制台会找到关于它所接管的一切的事件。请看 [UniFi Network](/zh-hans/iot/unifi/#事件)。
- **实体：**对一个实体同样如此：它的状态变化、对它及其变量的写入、它的报警、它触发的或对它写入过的规则，以及对它或它的变量的配置更改。后来被删除的实体仍然可以用它原来的名称找到。
- **谁：**执行者的一部分，不区分大小写：`alice`、`automation:cooldown`（该规则的运行和它做出的每次写入）、`mcp:`（任何智能体所做的一切）。设备自己产生的状态变化没有执行者。
- **类型：**五种中的任意几种。
- **时间：**`from` 和 `to`。

翻页使用游标，也就是最后一行的时间、类型和 id，所以页面不会因为上一页之后新增的行而发生偏移。

画面实时更新。有人在看的时候，实时推送每秒查看一次各份记录，并发送一个 `logbook` 事件，指明哪些类型有新内容；然后画面再次请求它的页面。它监视的是数据表，而不是这个进程，所以智能体通过 `--mcp-stdio`（那是另一个进程）所做的写入同样会显示出来。

## 保留多久

`entity_state_log` 按月分区，在两种历史模式下都是如此（不论 `tag_history` 是否为超表，它都是一张普通的 PostgreSQL 分区表），当某个月里的每一行都早于 `HOTLOOP_LOGBOOK_RETENTION_DAYS` 时，这个月整体被丢弃。默认 **90**。丢弃一个月是瞬间完成的；逐行删除则不是，这就是要分区的原因。所以一行会被保留 90 天到 90 天加一个月之间。`0` 表示全部保留，Gateway 会在启动时说明这一点，因为那样表会一直增长，直到卷被占满。

日志簿自身的维护负责这件事，启动时一次，之后每天一次。它会提前创建上个月以及接下来三个月的分区，让每一行总有地方可落；没有分区的月份的行会落入默认分区，维护在创建该月分区时会把它们移到所属的月份（还原之后就是这种情况，请看[备份和恢复](/zh-hans/iot/backup/)），或者在它们超过保留期限后删除。

其他记录保留它们一直以来保留的内容：

| 记录 | 保留 |
|---|---|
| `write_audit` | 全部，直到有人裁剪 |
| `alarm_events` | 全部，直到有人裁剪 |
| `automation_runs` | 每个自动化最新的 500 次运行 |
| `events` | 最新的 100,000 行 |

所以在繁忙的工厂里，日志簿的写入和报警能追溯到比状态变化更早，而它的自动化运行和配置更改追溯得没那么远。日志簿显示的是各份记录所拥有的内容。

## 由一个进程记录

由 Gateway 记录。用 `--mcp-stdio` 启动的第二个进程（Gateway 旁边智能体的辅助进程）读取日志簿及其基线，所以它所说的 `last_changed` 与 Gateway 一致，但它不写入任何东西，也不维护任何东西：两个记录器会把每次变化记两遍。

记录器是实体引擎上的一个钩子，只负责排队。每秒一次，一个 goroutine 把排队的内容变成行，应用限速，并通过一次 `COPY` 和一次对最新状态的 upsert，在一个事务中写入。队列容纳 50,000 次变化；超出后最旧的会被丢弃并计数。数据库停机时，行会留在队列中，直到同样的上限，数据库恢复后它们会写入。`/api/diagnostics` 在 `logbook` 下显示这一切：

```json
{"recording":true,"retentionDays":90,"queued":0,"dropped":0,"written":212,"suppressed":36,"writeErrors":0}
```

`dropped` 大于零，意味着日志簿里缺少一些变化；`queued` 持续增长，意味着数据库跟不上；`lastError` 说明上一次写入为什么失败。
