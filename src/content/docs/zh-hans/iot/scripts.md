脚本是一串有名字的步骤。CIP 周期。产线吹扫。切换到产品 B。每家工厂都有少数几套每次都完全按同样方式执行的流程，而某天有人把其中一套复制进第四条自动化，却只在其中三条里修正了一个步骤，那天就是您吃亏的日子。所以只写一次，起个名字，凡是需要它的地方都按这个名字调用：脚本屏幕上的操作员、带有 `call_script` 步骤的规则、使用 `run_script` 的代理，以及任何通过 `POST /api/services/script/turn_on` 发起的调用。

脚本使用自动化语言，运行在与规则动作相同的序列运行器上，它做的每一次写入都经过唯一的写入闸门。没有旁门。它从来就没有过。

## 它长什么样

```json
{
  "id": "cip_cycle",
  "name": "CIP cycle",
  "description": "Caustic wash, rinse, done. Tank must be empty.",
  "fields": [
    {"name": "minutes", "label": "Wash time", "type": "number", "min": 5, "max": 60, "step": 5, "unit": "min", "required": true},
    {"name": "circuit", "type": "select", "options": ["tank_1", "tank_2"], "default": "tank_1"}
  ],
  "sequence": [
    {"type": "condition", "params": {"expression": "float(states['sensor.cip_tank_level']) < 5"}},
    {"type": "call_service", "params": {"entityId": "switch.cip_pump", "service": "switch.turn_on"}},
    {"type": "delay", "params": {"seconds": 5}},
    {"type": "wait", "params": {"expression": "float(states['sensor.cip_return_temp']) > 70", "timeoutSec": 900}},
    {"type": "log_event", "params": {"message": "CIP on {{ vars.circuit }} for {{ vars.minutes }} minutes"}},
    {"type": "call_service", "params": {"entityId": "switch.cip_pump", "service": "switch.turn_off"}}
  ],
  "mode": "skip",
  "maxRuntimeSec": 1800
}
```

- **`id`** 由小写字母、数字和下划线组成，以字母开头。它也是其实体的对象 id，所以这一个是 `script.cip_cycle`，并且永远不会改变。
- **`fields`** 是一次运行所接收的内容。与 HotLoop 其他地方相同的带类型输入（`model.Field`）：带 `min`、`max`、`step` 和 `unit` 的 `number`，带 `max_length` 和 `pattern` 的 `text`，`boolean`，带 `options` 的 `select`，带可接受 `domain` 的 `entity`，`duration`（秒，或 `90s`、`1h30m`），`alarm` 和 `tag`。每个都可以是 `required`，也可以有 `default`，而字段自己会拒绝的默认值在保存时就会被拒绝。步骤以 `vars.<name>` 的形式读取字段。
- **`sequence`** 是自动化语言的全部：`call_service`、`write_tag`、`condition`、`wait`、`stop`、`call_script`、`set_variable`、`delay`、`log_event` 等等。每一个步骤都在[自动化](/zh-hans/iot/automations/)中。
- **`mode`** 和 **`maxRuntimeSec`** 见下文。

脚本在保存时就会编译，和规则一样：无法解码的步骤、无法编译的表达式、比一次运行允许的时间更长的等待、没有意义的字段，全部在保存时被拒绝。您是在编辑器里发现问题，而不是在凌晨 3 点、水泵洗到一半的时候。

## 字段只检查，不修正

在第一个步骤运行之前，运行收到的内容会对照字段进行检查：每个值都必须是其字段能接受的，每个必填项都必须存在，脚本中没有的字段是一个错误，而不是被悄悄忽略的东西。**值绝不会被改动来迁就。** 在最大值为 60 的字段里填 70 分钟会被拒绝，而不是被截成 60；数字填 `"12"` 会被拒绝，而不是被解析；步长为 5 时填 12.5 会被拒绝，而不是被四舍五入。继续去控制设备的值，恰恰就是某人输入的那个值，否则什么都不会运行。被拒绝的运行不会留下任何运行记录：什么都没有开始。

## 运行一个

| 来源 | 方式 | 需要 |
|---|---|---|
| 脚本屏幕 | 点击其卡片上的**运行**，填写表单 | `scripts.run` |
| 它的实体 | 点击其磁贴上的**运行**，或以字段为数据调用 `POST /api/services/script/turn_on` | `scripts.run` |
| API | `POST /api/scripts/{id}/run`，带 `{"fields": {...}, "reason": "..."}` | `scripts.run` |
| 规则 | 一个 `call_script` 步骤 | 规则自身的权限 |
| 代理 | 通过 MCP 的 `run_script` | 已开启 MCP 写入 |

操作员运行脚本。管理员编写脚本。运行 CIP 周期正是这个按钮的用途；决定 CIP 周期打开哪些阀门，是工程师的判断，并且一直如此。

运行一开始就会立即返回，并带上它的 id。要求它等待（`wait`），它就会在结束时返回结果和每个步骤的跟踪。**停止**（`POST /api/scripts/{id}/stop` 或 `script.turn_off`）会在所有进程中，把它的每一次运行在当前位置取消，等待或延时也包括在内。步骤已经写入的内容仍然保留。撤销本身也是一次写入，是在没有人要求的情况下，对已经动作过的设备做的，这是操作员的决定，而不是我们的。

## 每一次写入都经过闸门

脚本以 **`script:<id>`** 的身份运行。它做的每一次写入、每一次服务调用、每一行日志都以此作为执行者，并且每一次写入，无论是否被拒绝，都会在 `GET /api/writes` 中针对它进行审计。**来源**是启动它的人：从屏幕启动是 `ui`，从规则启动是 `automation`，从代理启动是 `mcp`。这一点很重要，因为闸门依据来源作出决定。由代理启动的脚本以 `mcp` 写入，而在 `HOTLOOP_ALLOW_WRITES` 关闭时，它的每一次写入都会被拒绝，和代理自己的 `write_tag` 会被拒绝的情形完全一样。在这种情况下，`run_script` 和代理的 `script.turn_on` 会一开始就拒绝，而不是去运行一个每次写入都会被退回的脚本。

运行会记录是谁请求的（`actor`）、通过什么方式（`source`），以及是什么调用了它（`parent`：`automation_run:812`、`script_run:77`），这样您就能从一次写入一路追溯到规则、脚本，以及背后的人或代理。

## 先问一下：试运行

`POST /api/scripts/{id}/run?dry_run=true`、运行抽屉中的**先检查**，或带 `dryRun` 的 `run_script`。字段的检查方式相同，然后每个步骤都对照工厂当前的实际状态走一遍：

- 每个 `write_tag` 和 `call_service` 都要交给写入闸门自身的检查（`CheckWrite`、`Services.Check`），也就是真实写入所运行的同一段代码，所以试运行不会对某件事说可以，而真实写入却会因试运行没有检查的原因拒绝它。不会写入任何内容，也不会审计任何内容；
- `condition` 会立即求值，为假时，在它会终止运行的位置终止这次走查；
- `set_variable` 会被绑定，因此其后的步骤看到的就是它们本该看到的；
- `call_script` 会走查它所调用的脚本，脚本的步骤在该调用之下编号（`3.1`、`3.2`）；
- `wait`、`delay`，以及任何不写入设备的内容（一条消息、一次 HTTP 调用、一个被触发的报警）都是 `not_checked`。试运行不会为了告诉您届时水箱会读到多少，而等上十五分钟。

第一个会被拒绝的写入会终止走查，因为它会终止运行，答复会用闸门自己的话说明：`step 2 (call_service): cip/pump: this tag is not marked writable`。一次顺利通过的试运行是建议，而不是承诺。设备可能掉线，有人可能解除某个变量的启用，而一次等待会给工厂留出足够的时间，在您检查与该步骤之间改变主意。

## 运行模式

当同一脚本的另一次运行正在进行时，被请求的运行会怎样。与规则使用的措辞相同，只有一处不同。

| 模式 | 第二次运行 |
|---|---|
| `skip` | 被拒绝，返回 `409`，并在历史中留下一条说明原因的 `skipped` 运行。**默认值**，也是任何控制设备的内容的正确做法 |
| `queue` | 排队等待，在前一次结束后开始。只排一层：第三次会被拒绝 |
| `restart` | 在当前位置取消正在进行的那次，待其停止后再开始。两次运行绝不重叠 |
| `parallel` | 并行运行 |

区别在于：规则的队列会悄悄丢弃较早的待处理运行，而脚本的队列会明确拒绝较新的那次。规则由并不在意的触发器触发。脚本则是由某个人或某个东西请求的，对方可能正在等答复，而“您的运行就这样悄悄地没有发生”不是答复。

等待一个忙碌脚本的 `call_script` 步骤会失败（`script busy`）；不等待的步骤则在跟踪中记下这一点并继续，因为它本来要做的只是把脚本启动起来。

`maxRuntimeSec` 限制一次运行的时长，为零时是五分钟。用完这个时间的运行会变为 `timed_out`，无论它是在步骤之间还是在等待中途。

## 脚本调用脚本

`call_script` 步骤从规则或另一个脚本运行一个脚本。使用 `wait` 时，该步骤把脚本的结果当作自己的结果，脚本也成为调用它的那次运行的一部分：取消调用方，或让它超时，它所等待的脚本也会停止。不使用 `wait` 时，脚本被启动后就任由它自行结束。

有两个限制，都是因为不这样做就会出现循环的脚本：

- **会调用自身的脚本在保存时就会被拒绝**，无论是直接调用，还是经过任何由其他脚本组成的链：`script b would call itself: b calls a calls b`。形成回路的编辑也一样。
- **运行时最多五层深。** 一条链中的第六个脚本会使本该调用它的那个步骤失败，整条链也随之失败。而如果某个循环曾经绕过了保存（两个进程在同一时刻保存它的两半），运行会将其拦下：已经在自己所在链中运行的脚本会被拒绝，而不是运行第二次。

## 它的实体

每个脚本都是一个实体，`script.<id>`，平台为 `script`。在它的某次运行进行时，无论在哪个进程，其状态为 `on`，没有运行时为 `off`；其属性包含它的 `mode`、正在进行的运行数量（`current`）、它的 `fields`，以及上次启动的时间和结束的方式。它出现在实体屏幕上，带有**运行**按钮，在通过 MCP 的 `list_entities` 中，在 `/api/states` 中，规则也可以对它设置状态触发器：“当 CIP 周期变为 off 时，记录批次”。删除脚本会使其实体成为孤儿，就像删除报警定义一样：当不再有东西引用它时，由管理员删除这个孤儿。

## 运行历史

每次运行都是 `script_runs` 中的一行：谁、怎样、检查之后收到的字段、每个步骤的跟踪（解析后的输入，而不是模板）、怎样结束以及原因。可通过 `GET /api/scripts/{id}/runs`、运行抽屉和[事件日志](/zh-hans/iot/logbook/)查看，在事件日志中，脚本运行的类型是 `script`，可按脚本的实体或某次运行写入过的任何内容找到。历史为每个脚本保留最新的 500 次运行，与自动化运行的上限相同。

一次运行的行在其第一个步骤之前打开，在最后一个步骤之后完成。进程停止时，会在当前位置取消每一次正在进行的运行，并将其记录为 `cancelled: interrupted by restart`。被崩溃截断、没有人再来完成其行的运行，会在 Gateway 下次启动时以同样方式标记。**没有任何东西会恢复一次运行。** 一个小时后，在没有人要求的情况下，对一个已经变化了的工厂，从 CIP 周期的第四步继续，比说它已经停止更糟。

## 不止一个进程

Gateway 和它旁边的 `--mcp-stdio` 进程（或滚动发布中的两个 pod）都会运行脚本。运行的状态保存在数据库中，每个进程都监听 `hotloop_script` 上的变化，因此：

- 在一个进程中启动的脚本，在每个进程的实体中都显示为 `on`；
- 在一个 pod 上保存的脚本，就是另一个 pod 上的脚本，如果它的步骤发生了变化，那里的运行会被取消；
- **停止**会在所有进程中停止它的每一次运行。

运行模式是按进程保存的。两个进程可以在同一时刻各自启动一次 `skip` 脚本的运行。一家工厂在同一秒内从代理的辅助进程和操作员的屏幕运行同一套流程，需要进行一次我们的任何锁都解决不了的沟通。

## 备份

`scripts` 和 `script_runs` 包含在每一份备份中，恢复时连同历史一起恢复。备份在中途捕获的运行会以 `running` 状态回来，并与其他运行一样，在第一次启动时被标记为 `interrupted by restart`。参见[备份与恢复](/zh-hans/iot/backup/)。

## API

每个路由、它的权限和它的答复都在 [HTTP API](/zh-hans/iot/api/#脚本) 中。

| 权限 | 查看者 | 操作员 | 管理员 |
|---|---|---|---|
| `scripts.read`：列出脚本及其运行 | 是 | 是 | 是 |
| `scripts.run`：运行、试运行、停止、`script.turn_on`/`turn_off` | 否 | 是 | 是 |
| `scripts.write`：创建、编辑、删除 | 否 | 否 | 是 |
