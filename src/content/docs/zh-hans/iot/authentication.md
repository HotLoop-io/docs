HotLoop 自 4.4.0 起有了自己的登录，每个产品默认都要求登录。不登录运行仍然可以，这是刻意保留的，适用于确实隔离在仪表板之后、并且愿意明确声明这一点的部署，见[不登录运行](#不登录运行)，但单纯的 `helm install` 或 Podman Quadlet 单元现在启动时就要求登录。

## 简要说明

- **本地用户、bcrypt 密码、服务器端会话。** 目前没有外部身份提供方，保护代理接口的另一道 Bearer 令牌边界见 [MCP](/zh-hans/iot/mcp/)，本机制不取代它。
- **三种角色：admin、operator、viewer。** admin 可以做所有事，包括管理用户。operator 可以读取一切，写入变量、确认报警、触发自动化。viewer 可以读取一切，别的都不行。也可以给用户一份明确的权限列表来取代角色，用于更窄的需求。
- **会话是一个 Cookie 或一个 Bearer 令牌**，客户端觉得哪个方便就用哪个。浏览器界面使用 Cookie，脚本或其他服务使用 `Authorization: Bearer <token>`。
- **共用面板用 PIN 或工牌登录**，没人操作时自动退出，所以那里的每一次写入都是某个人的名字。见[自助终端面板](#自助终端面板pin-或工牌以及空闲退出)。
- **会话会过期。** `HOTLOOP_AUTH_SESSION_TTL`，默认 12 小时。没有“记住我”，因为一个比工作班次还长的会话，就是没人看管的会话。

## 获取第一个账号

图表在首次安装时生成一个账号，并只在 `helm install` 的 NOTES 输出中显示一次：

```
helm install hotloop ./charts/hotloop \
  --namespace hotloop --create-namespace
```

直接运行二进制文件时，先生成哈希，再设置两个变量：

```sh
hotloop hash-password
# Password: ********
# Confirm password: ********
# $2a$10$....................................................

export HOTLOOP_AUTH_ENABLED=true
export HOTLOOP_ADMIN_USER=admin
export HOTLOOP_ADMIN_PASSWORD_HASH='$2a$10$....................................................'
```

`hash-password` 也可以直接接受 `-password`，供已经有密码的脚本使用：

```sh
hotloop hash-password -password 'something-long'
```

这样创建的 admin 账号是一个**引导账号**，不是重置开关。它一旦存在，修改 `HOTLOOP_ADMIN_PASSWORD_HASH` 并重启不会有任何效果，`EnsureAdminUser` 只在该用户名尚不存在时才创建账号，所以这里的值永远无法覆盖运营人员之后通过界面修改的密码。这在 Helm 升级时最重要：重新应用同一份 `values.yaml`，不能悄悄把某人的密码改回去。

## 角色

| 角色 | 可以做什么 |
|---|---|
| **admin** | 一切：`*`。包括创建、停用和删除用户。 |
| **operator** | 读取每个画面。写入变量（`POST /api/write`）和向命令实体下达指令（`POST /api/services/...`），设置辅助项（`helpers.write`，见[辅助项](/zh-hans/iot/helpers/)），运行和停止脚本（`scripts.run`，见[脚本](/zh-hans/iot/scripts/)），应用配方（`recipes.apply`，见[配方](/zh-hans/iot/recipes/)），从蓝图创建规则并升级规则（`blueprints.apply`，见[蓝图](/zh-hans/iot/blueprints/)），查看提供给该角色的仪表板（`dashboards.read`，见[仪表板](/zh-hans/iot/dashboards/)），读取用电量及其成本（`energy.read`，见[能源](/zh-hans/iot/energy/)；创建电表或电价是 `energy.write`，属于 admin），重新排列看板，确认、搁置、取消搁置报警，触发自动化。不能编辑设备、变量、报警、自动化、脚本、配方、蓝图或仪表板的*定义*，也不能管理用户。 |
| **viewer** | 读取每个画面。别的都不行。 |

可以给用户一份明确的 `permissions` 列表来取代角色，它**完全替换**角色而不是在角色之上追加，一个用户要么是“operator 角色”，要么是“恰好这些权限”，绝不是两者兼有，这样要知道某人能做什么，只需要看一个地方。

权限字符串的形式是 `resource.action`，如 `tags.write`、`alarms.ack`，或资源通配符 `tags.*`，或全局通配符 `*`。

## 自助终端面板：PIN 或工牌，以及空闲退出

在你自己的电脑上，你已经登录了：你输入过一次密码，写入会直接通过写入关口并记在你名下，一如既往。这一点没有变。挂在墙上的面板不是任何人的电脑。如果它以 `panel-3` 登录，审计轨迹会写“panel-3 打开了阀门”，这不是审计轨迹。所以面板用 PIN 或工牌让一个人登录，每一次写入都属于这个人，没人操作时面板会让他退出。

### 操作员看到什么

面板是一块实体屏幕：HotLoop 在 `/?screen=<name>` 打开（见[仪表板](/zh-hans/iot/dashboards/#角色和屏幕)）。没有人登录时，它只显示一个输入框，“PIN 或工牌”，看不到工厂的任何内容。输入 PIN 后按 Enter，或者刷工牌。面板会打开它的仪表板，角落里显示当前登录的人和一个**退出登录**按钮，因为平时显示这些的页眉在面板上没有。按下写入按钮，会像其他地方一样要求确认并填写原因，写入会记在这个人名下。

空闲时限到后仍没人触碰屏幕，面板会让这个人退出并回到 PIN 输入框。服务器和页面一样会强制执行：空闲这么久的自助终端会话会被删除，之后用它的 Cookie 发出的写入会被 `401` 拒绝，所以关闭页面，或者页面卡死，都不会让某人一直处于登录状态。如果面板必须改用密码，输入框下面的“使用密码”就是普通登录，有普通的 12 小时，没有空闲限制，因为那是某个人自己的登录。

算作触碰的有：点按、点击、按键或写入。不算的有：仪表板刷新数字，或实时推送，无论有没有人在场，它们都会继续。

### 设置方法

admin 在**设置，用户**中给每个人一个代码：在他们那一行点 **PIN 或工牌**，输入两次代码，**设置**。或者通过 API，签发工牌的脚本会这么用：

```sh
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"code":"482913"}' https://gateway/api/users/olga/pin

# Take it away (also signs them out of every panel)
curl -X DELETE -H "Authorization: Bearer $TOKEN" https://gateway/api/users/olga/pin
```

- **PIN 是一种凭据。** 它以与密码相同成本的 bcrypt 哈希存储，绝不存明文，绝不出现在系统日志中，也绝不出现在响应里。用户列表只显示 `hasPin`。备份里保存这些哈希，与保存密码哈希完全一样（[备份与恢复](/zh-hans/iot/backup/)）。
- **工牌是键盘楔形读卡器输入的一个值。** 没有硬件驱动。读卡器像键盘一样，把工牌号码输入面板唯一的输入框并按下 Enter，也就是提交表单。所以工牌就是一个像 PIN 一样的代码：读卡器输入什么都行，6 到 72 个字符、不含空格，在同一个位置设置到账号上。不像键盘那样工作的读卡器，目前不支持读取。
- **一个代码，一个账号。** 面板仅凭代码找到这个人，因为工牌读卡器不输入用户名，所以设置一个别的账号已经在用的代码会被拒绝。
- **代码会与每一个有代码的账号核对，** 用的是与密码相同的 bcrypt，因为加盐的哈希无法按值查找。耗时随有代码的账号数量增加，账号有几十个时最坏也就几秒，而且无论代码对错，耗时都一样。
- **代码以账号的角色登录。** 把它交给角色正好适合在面板上使用的人。自助终端会话就是账号自己的权限，不会更窄，viewer 的代码登录的是 viewer，其写入关口照常拒绝。
- **停用账号**会连同其他会话一起结束它的面板会话，被停用账号的代码无法登录。**删除代码**会让账号从面板上退出，而它的密码和它在自己电脑上的会话保持不变。

### 空闲退出时间

默认十五分钟。足够拿着写字板在面板前处理一次换线，或者走到阀门旁看着它动，又短到让作业结束后被丢下的面板，不会在下一个人走近时还挂着某个人的名字。这是我的判断，不是代码或某个标准规定的数字。在**设置，工厂，自助终端空闲退出（秒）**中修改，范围 10 秒到 12 小时，无需重新部署，或者用 `HOTLOOP_AUTH_KIOSK_IDLE`（一个时长，`15m`）设置默认值。设置中的值优先于变量。会话仍会在 `HOTLOOP_AUTH_SESSION_TTL` 时结束，和任何会话一样。

### 密码和 PIN 输错后的锁定

输错的密码或 PIN 会记在被尝试的**账号**上。连续输错十次，该账号锁定五分钟，不影响其他任何人。在第十次之前输入了正确的密码或 PIN，计数重新开始，已经过期的锁定会给十次新机会。被锁定的账号无论输入什么，对的还是错的，都拒绝登录，并用 `429` 说明要等多久。锁定只阻止新的登录，别的都不阻止：账号已有的会话照常继续，包括它的请求和实时推送，所以别人十次错误的猜测，不会让产线上操作员的屏幕黑掉。它同时适用于密码登录和 PIN 登录，每次锁定都会记入系统日志（类别 `auth`）。

- **数字从哪里来。** NIST SP 800-63B 规定验证方要限制单个账号上连续失败的尝试次数：第 3 版 5.2.2 节和第 4 版 3.2.2 节都把上限定为 100，并说运营方可以设得更低。第 4 版还允许在失败后让申请人等待。这就是那种等待，不是永久停用。十次是 NIST 上限的十分之一，比任何人无意输错的次数都多。五分钟足够长，使每五分钟十次猜测让六位 PIN 的一百万种可能无法穷尽（全部试完大约 350 天），又足够短，让输错密码的操作员喝杯咖啡就能回来。PIN 最少 6 个字符，是第 3 版 5.1.1.2 节对分配的秘密规定的下限，admin 发放 PIN 就属于这种情形。十次和五分钟是我在 NIST 限制之内做的选择，不是 NIST 的数字。
- **两者都是设置。** **设置，工厂**：“输错这么多次密码或 PIN 后锁定账号”（默认 10，范围 1 到 100，0 表示关闭）和“被锁定的账号保持锁定多久”（默认 5 分钟，范围 10 秒到一天）。变量是 `HOTLOOP_AUTH_LOCKOUT_ATTEMPTS` 和 `HOTLOOP_AUTH_LOCKOUT_DURATION`（一个时长，`5m`）。设置优先于变量。
- **admin 可以解锁账号。** **设置，用户**把被锁定的账号显示为 `locked`，并带一个**解锁**按钮，也可以用 `DELETE /api/users/{username}/lockout`。计数从零重新开始。
- **绝不锁面板。** 在面板上输错的代码绝不会记在面板上，所以一个人的失误不会挡住下一个人。
- **单独的代码无法计数，所以改为让面板变慢。** 工牌读卡器只输入工牌，而单独输入的 PIN 一旦错误就不匹配任何账号，没有可记账的账号。记在面板上会让下一个工人因为上一个人的失误被挡在外面，而面板永远不会被锁。因此每连续错误一次，该面板在检查下一次之前就多等半秒：第一次失误后 0.5 秒，第二次后 1 秒，依此类推，直到上限，默认 3 秒。输对一次就重新开始。所以下一个工人最多等一个上限的时间就能进入，而猜测的人每个面板每个上限只能试一次：一百万个六位 PIN 要花一个多月。同时发来的尝试会排队，各自等待轮到自己。带用户名输入的 PIN 不会变慢，它属于账号，并像输错密码一样锁定账号。最长等待时间是**设置，工厂，PIN 输错后面板的最长等待（秒）**，范围 0 到 30，`HOTLOOP_AUTH_PANEL_DELAY_CAP` 作为默认值（一个时长，`3s`），0 表示关闭。三秒是输错的工人可以忍受的停顿，对试遍每个代码的人来说又足够慢。半秒的步长是固定的。
- **哪个面板是哪个。** 客户端地址：代理设置了 `X-Forwarded-For` 时取它的第一跳，否则取连接本身的地址，会话列表记录的也是它。登录之前没有更好的信息：还没有会话，而服务器发出的 Cookie，客户端可以丢弃来重新开始等待。所以在设置 `X-Forwarded-For` 的代理之后，每个面板各自等待。在不设置的代理之后，所有面板共用代理的地址，彼此拖慢，最多到上限。而且能直接访问端口的客户端可以自己发送 `X-Forwarded-For` 来躲开等待。这就是为什么这只是减速，账号上的锁定才是控制手段：对于要紧的猜测，请使用带用户名的形式，或者很长的随机工牌值。
- **它会说明账号存在。** `429` 只针对存在的账号，所以会告诉试名字的人哪些名字是存在的。锁定本来就是这样。

### 它不做什么

- **单独的代码无法被锁定。** 原因见[锁定](#密码和-pin-输错后的锁定)。
- **退出之前没有警告。** 时间一到，面板就回到 PIN 输入框。
- **用密码一直保持登录的面板**（在此之前面板只能这样运行）仍和原来一样工作，仍以该账号写入。不要给共用面板配常驻的 operator 登录，而是给使用它的人发 PIN。
- **没有读卡器驱动，没有 SSO，没有按面板区分的权限。**

## 管理用户

仅限 admin。在界面里是**设置，用户**：每个账号及其角色、是否启用、上次登录时间，并有添加用户、编辑（角色，以及停用）、新密码和删除。没有 `users.manage` 的人，或者认证关闭时，不会绘制任何内容。逐条列出权限的账号显示为 `custom` 并带数量，编辑会保留该列表，除非你选一个角色，那会替换它。同样的操作也可以通过 REST API 完成：

密码为 8 到 72 字节：72 是 bcrypt 自身的上限，更长的会被拒绝并说明这一点。通过 OPC UA 也一样（见 [OPC UA 服务器](/zh-hans/edge/opc-ua-server/#who-may-log-in)）；在早先的版本中，超过 64 字节的密码可以在这里登录，却不能在那里登录。

```sh
# List
curl -H "Authorization: Bearer $TOKEN" https://gateway/api/users

# Create
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"username":"j.smith","password":"something-long","role":"operator"}' \
  https://gateway/api/users

# Disable (does not delete; also revokes every session that account holds)
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"role":"operator","disabled":true}' \
  https://gateway/api/users/j.smith

# Reset a password an operator forgot
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"password":"a-new-one"}' \
  https://gateway/api/users/j.smith/password
```

有两种拒绝值得提前了解，免得让人意外：

- **你不能删除自己当前登录所用的账号。** 请先切换到另一个 admin 账号。
- **你不能停用或删除最后一个启用的 admin 账号。** 在移除第一个之前，先把第二个账号提升为 admin，或者别动其中一个。没有这项检查，脚本化的用户同步中一次失误，就会变成一次把人锁在外面的事故，而且没有 admin 会话可用来撤销。

任何已登录的用户都可以修改自己的密码，不受以上两条限制：

```sh
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"currentPassword":"old","newPassword":"new"}' \
  https://gateway/api/auth/password
```

修改密码会撤销该账号持有的每一个会话，包括发出请求的那个。客户端需要重新登录。

## 设备凭据只写不读

在 4.15.1 中加入。在此之前，`GET /api/devices` 和 `GET /api/devices/{id}` 会原样返回设备的 `config` 和 `address`，所以任何已登录的用户，包括 viewer，都能读到 MQTT 代理的密码、HTTP 和 MTConnect 的凭据，以及设备中保存的其他一切内容。4.15.0 只隐藏了 OPC UA 的密码。从 4.15.1 起，任何角色都无法通过 API 读回设备的凭据，**包括 admin**。要修改一个凭据，就发送新值。

### 什么算凭据

| 协议 | 在配置中被隐藏 | 同时被隐藏 |
|---|---|---|
| MQTT | `password` | 地址中的用户信息和机密查询值（`mqtt://user:pass@broker`） |
| HTTP | `password`；`headers` 中除少数普通项（`Accept`、`Accept-Encoding`、`Accept-Language`、`Cache-Control`、`Content-Type`、`User-Agent`）之外的每个值；提到凭据时的 `body` 和 `writeBody`（`password`、`token`、`apiKey` 之类）；`writeUrl` 中看起来像机密的查询值 | 地址和 `writeUrl` 中的用户信息和机密查询值 |
| MTConnect | `password`；`headers` 中的每个值，例外相同 | 地址中的用户信息和机密查询值 |
| OPC UA | `password` | 地址中的用户信息同样被隐藏，驱动也会忽略它，因为 OPC UA 端点 URL 不携带凭据 |
| Modbus、S7comm、EtherNet/IP | 它们的选项都不是凭据 | 地址中的用户信息被隐藏，驱动出于同样的原因忽略它 |

密钥文件的路径（`keyFile`）不是密钥材料，会显示出来。`allowInsecureCredentials` 这样的标志也一样。

以上列表是在代码中检查的。一个测试会读取每个驱动的选项结构，并在以下情况失败：某个选项既不在凭据列表中，也不在已知不是凭据的选项列表（`plainConfigKeys`）中；自由格式条目的映射或自由文本字段不在凭据列表中；任一列表列出了没有驱动会读取的内容。所以一个新选项，在有人决定它属于哪一类之前，不可能发布。

作为这些列表之下的兜底，设备配置中任何深度的任何键，在任何协议中，只要包含 `password`、`passwd`、`passphrase`、`pwd`、`secret`、`token`、`apikey`、`authorization`、`credential`、`private`、`bearer`、`cookie`、`basicauth`、`signature`、`jwt`、`oauth`、`sessionid` 或 `connectionstring`，或以 `key` 结尾，或含有 `pass`、`pw`、`pwd`、`passwd`、`auth`、`cred`、`creds`、`sig`、`signature`、`sas`、`jwt`、`otp`、`pin` 或 `psk` 中的任何一个完整单词，就会按名称被隐藏。单词在标点处以及小写转大写的边界处拆分，所以 `db_pass`、`smtp_pw`、`apiAuth` 和 `sasToken` 算，而 `bypass`、`compass`、`passive`、`authority` 和 `pinned` 不算。大小写和标点会被忽略，`encoding/json` 仍会读成同一个键的写法也一样（用长 s 代替 s，用开尔文符号代替 k）。短词规则故意定得很粗：一个没人审查过的键，比如 `authMode`，在被加入 `plainConfigKeys` 之前一直是隐藏的。

按名称被隐藏的值，以及这种键之下的一切，无论是什么类型都会被替换（数字和字符串一样被隐藏），布尔值除外，因为它不可能是凭据。文本中带有凭据的字符串，无论在哪里都整体隐藏：带 `--password hunter2` 的命令行、`password=...` 键值对或连接字符串、`Authorization: Bearer ...`。没有设置凭据的设备什么也不显示，所以“没有密码”和“有一个我看不到的密码”可以区分开。无法解析为 JSON 的配置显示为 `{}`，而不是原样显示。

被隐藏的值显示为 `[redacted]`。在地址中，它替换密码并保留用户名（`http://svc:[redacted]@meter/api`），没有冒号时则替换整个用户信息，并替换查询和片段中每个看起来像机密的参数的值（`?fmt=json&token=[redacted]`、`#access_token=[redacted]`）。参数以 `&` 或 `;` 分隔，或以其百分号编码形式 `%26` 和 `%3B` 分隔，每个参数单独判断，所以 `?fmt=json` 仍可读。名为 `code` 的参数只在地址中算机密，用于 `?code=` 中的 Azure Functions 密钥，别处不算。无法干净解析的查询（无效的百分号转义、控制字符）会整体隐藏，而不是去猜。

### 保存设备

`POST /api/devices` 在 id 是新的时创建设备，在 id 已存在时替换它。没有单独的 `PUT`。对于地址和配置中的每个凭据：

| 请求发送什么 | 结果 |
|---|---|
| 新设备，带真实值 | 值按给定的原样存储。 |
| 新设备，带 `[redacted]` | 以 400 拒绝。占位符绝不会作为凭据存储。 |
| 已有设备，`[redacted]` | 保留已存储的值。 |
| 已有设备，省略该键 | 保留已存储的值。不了解机密的客户端无法意外清除它。 |
| 已有设备，新的字符串或数字 | 替换已存储的值。 |
| 已有设备，空字符串或 `null` | 清除已存储的值。这是移除凭据的唯一方式。 |
| `[redacted]`，但没有可保留的已存储值 | 以 400 拒绝。 |

占位符绝不会被存储，无论它出现在配置还是地址的哪个位置：它会被同一位置已存储的值替换，没有则被拒绝。

有两个细节。在 `headers`（其条目由用户选择的映射）内部，映射本身是一个单位：省略的条目会被移除，`{}` 清除全部，整个省略 `headers` 键则全部保留。键的匹配不区分大小写，与驱动的匹配方式一致。而所有不是凭据的内容，都照常替换：完全不带 `config` 保存的设备，保留它的凭据，其余都不保留。

网页界面的设备编辑器会按 API 返回的样子显示设备的配置，包括占位符，并保存它所显示的内容。所以编辑设备而不碰凭据，就会保留它。**要在界面中修改机密，请把配置（或地址）里的 `[redacted]` 替换为新值。** 旧值不会被预先填入，所以修改设备的人必须知道凭据才能修改。

### 移动设备不会带走它的机密

被保留的凭据会发送给设备所指向的地方。如果设备被移动时凭据被保留，任何被允许保存设备的人，只要把它指向自己的监听端，让网关出示凭据，就能读到已存储的凭据。所以当一次保存改变了地址或 `writeUrl` 中的主机或端口，并且会保留某个已存储的凭据（通过占位符或省略），它会被以 400 拒绝，并指出这些凭据的名称。请重新输入它们，或发送空字符串来清除。改变路径、协议方案，或设备的其他任何内容，都不算移动，没有已存储凭据的设备可以随意移动。

### 凭据不会出现在哪里

对每种协议的设备，在凭据可能出现的每个位置都放入凭据，测试会在以下所有地方搜索它：针对 viewer、operator 和 admin 的每个设备端点（列表、获取、创建和更新的响应）；其他所有读取端点；`/api/diagnostics` 和 `/api/status`；`/api/sites` 及其列出的出站 MCP 服务器；实时事件流；系统日志和写入审计；错误响应；每个 MCP 工具和资源；以及调试级别的进程日志，包括运行时和驱动的。驱动的错误文本以及运行时的事件和日志，都会按值和按形态清除设备的凭据，因为一个错误可能重复一个地址或服务器的回复。只有一两个字符的凭据，仅在它作为独立单词出现时才被替换，因为到处替换会毁掉消息。

### 凭据仍是明文的地方

只写不读指的是 API。网关需要真实的值才能连接，这些地方按存储的原样保存它们：

- **数据库。** 设备凭据在 `config` 和 `address` 列中。设置 `HOTLOOP_SECRET_KEY_FILE` 后，`config` 中带键的内容（每个 `password`、请求头的值）会用保存在数据库之外的密钥加密，文本中写有凭据的地址或选项（`mqtt://user:pass@host`、`?token=`）也一样，整体密封。见[备份与恢复](/zh-hans/iot/backup/#设备凭据与密钥)。
- **备份。** 备份中的 `devices.copy` 保存着它们，是否加密与数据库完全一致。见[备份与恢复](/zh-hans/iot/backup/#保护备份文件)。
- **Edge Relay 设备文件。** 中继读取一个携带其设备凭据的 JSON 文件。见 [Edge Relay 参考](/zh-hans/edge-relay/reference/#设备文件中的凭据-4150)。
- **机群配置推送。** 推送给中继的设备文件会原样发布到一个 MQTT 主题，并被保留。见[机群管理](/zh-hans/gateway/fleet/)。

请相应地保护数据库、备份卷、中继的设备文件和代理。在 API 上隐藏，并不会改变其中任何一项。

### 如果不受信任的用户可以访问过 API

在 4.15.1 之前，任何已登录的用户都可以通过 API 读取已存储的设备凭据。网关曾被不该有权限的用户访问到的运营方（比如把 viewer 账号交给了承包商），应当轮换它所持有设备的凭据：MQTT 代理、HTTP 和 MTConnect 端点，以及 OPC UA 账号。自 4.3.1 以来没有公开发布，所以暴露范围仅限于运行未发布构建的部署。

## 审计轨迹记录什么

每次写入本来就经过带有 `actor` 列的 `write_audit`，见主 README 中的写入关口。这一列现在来自会话，而不是请求头，在自助终端面板上，会话就是用 PIN 或工牌登录的那个人：

```
> write_tag tag=press-01/Zone1_Temp value=99 reason="testing"
```

记录的是 `j.smith`，即发出调用的会话上的用户名，而不是 `X-Forwarded-User` 碰巧说了什么。登录、自助终端登录、退出、密码修改，以及每一项用户管理操作，包括设置或清除 PIN（绝不记录 PIN 本身），都会记入系统日志（`GET /api/events`，类别 `auth`），原因与写入审计存在的原因相同：六个月后的一项变更应当可以被解释，而不只是被看到。

## 不登录运行

设置 `HOTLOOP_AUTH_INSECURE=true`（或图表的 `auth.insecure: true`），就能和 4.4.0 之前的每个版本一样运行：不需要会话，写入所记录的操作者来自 `X-EmberNET-User` 或类似的代理请求头，没有设置时回退为 `"operator"`。

对于 EmberNet 仪表板自己的 NetworkPolicy 才是真正的边界、没有其他东西能访问该 Pod 的部署，这是一个真实且站得住脚的选择。它不再是默认值，是因为这个条件很容易让人相信成立，却很难从 Pod 内部验证，4.4.0 的全部意义在于：NetworkPolicy 的一次失误，或者一个最终发现并不在仪表板之后的部署，不应该同时意味着 `actor(r)` 返回攻击者选的内容。

当认证既没有启用、也没有以这种方式确认时，`config.Validate` 拒绝启动，正是为了让“不认证”始终是某人有意做出的决定，写在部署自己的配置中，而不是一个没人选过的默认值。

## 从 EmberNet 仪表板登录

从 EmberNet App Store 安装 HotLoop 的租户，从 LAUNCH 进入应用时已经以自己的身份登录，无需分发任何密码。仪表板的应用主机会在它转发给此 Pod 的每个请求上加上 `X-Embernet-Assertion`：一个 ES256 令牌，有效期约一分钟，用只有仪表板持有的私钥签名。它写明了这个人（`email`）、租户、它为之生成的那一个应用（`aud`，`<tenant>/<Service name>`），以及租户把这个人的仪表板角色映射到的 HotLoop 角色（`role`：`admin`、`operator` 或 `viewer`）。

除非配置了公钥，否则它是关闭的，配置之后其他一切仍和以前一样工作：本地账号、Cookie、Bearer 令牌、自助终端面板。

| 变量 | 图表值 | 作用 |
|---|---|---|
| `HOTLOOP_AUTH_ASSERTION_PUBLIC_KEY` | `embernetSignin.publicKey` | 仪表板的公钥，PKIX PEM，ECDSA P-256。商店在部署时填入。 |
| `HOTLOOP_AUTH_ASSERTION_AUDIENCE` | 由命名空间和发行名推算 | `<tenant>/<Service name>`。与密钥一起必填；为另一个应用或租户生成的令牌会被拒绝。 |
| `HOTLOOP_AUTH_ASSERTION_ISSUER` | `embernetSignin.issuer` | `embernet-dashboard` |
| `HOTLOOP_AUTH_ASSERTION_HEADER` | `embernetSignin.header` | `X-Embernet-Assertion` |

有效的断言会做什么：仪表板第一次为某人担保时，这个人在这里得到一个用户（以其地址命名，没有密码，所以没有可猜的东西），用户的角色每次请求都跟随仪表板发来的内容，审计轨迹会记下他们的名字。无效的断言会怎样：401，而且不会悄悄改用碰巧存在的会话 Cookie。以下情况会被拒绝：签名错误，ES256 以外的任何算法，已过期或尚未生效的令牌，有效期超过十分钟的令牌，错误的签发方，另一个应用或租户的受众，与受众不一致的租户声明，不属于我们的角色，以及不含地址的名称。

本地 admin 对仪表板放进来的人有最终决定权：停用该用户，他们就进不来；给他们一份明确的权限列表，他们就保留它。写入仍然需要 Pod 自己的写入开关，断言绝不会扩大它们。从仪表板创建的会话中退出，并不会结束它：访问在仪表板停止签名的下一个请求时结束。

## 目前尚未涵盖的内容

- **没有 OpenID Connect。** 有本地账号，加上上面 EmberNet 仪表板的签名断言。身份提供方集成尚未构建。
- **没有按租户或按站点的角色。** 用户的权限在 Gateway 运行的每个地方都一样，对一个工厂来说没问题，对 `Sites` 中的多站点汇总则需要更多考虑。
- **单独输入的 PIN 或工牌没有锁定，** 只有密码和带用户名的 PIN 有；见[锁定](#密码和-pin-输错后的锁定)。`handleLogin` 中的恒定时间比较，防止通过响应时间枚举用户名。登录端点前面仍然值得放一个 NetworkPolicy 或上游代理。
