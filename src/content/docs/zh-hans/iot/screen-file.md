画面属于客户，并以文件的形式流转。从一个安装导出仪表板，导入另一个安装，它的任何内容都不存放在 HotLoop 的代码里：不是布局，不是变量名，也不是文字。同一个文件在 HotLoop IoT、Edge 和 Gateway 中都能用，因为它们运行同一套仪表板（[仪表板](/zh-hans/iot/dashboards/)）。

Edge Relay 没有界面，也没有画面。Flow 的仪表板是其流程的一部分，流程有自己的导入和导出。对于 HotLoop for CODESYS，画面就是 Edge 的画面。

## 使用方法

在仪表板界面，**导出**（在编辑旁边，针对当前显示的仪表板）会保存 `<id>.hotloop-screen.json`。**导入**（在新建仪表板旁边的栏中）会读取文件，告诉您它需要什么、这里缺少什么，让您把每个缺失的变量、设备、实体、脚本或配方映射到现有的某一个，再次检查并保存。导入需要 `dashboards.write`，所以这是管理员的事。导出需要 `dashboards.read`，并且仪表板必须是向您提供的那一个。

通过 API 是 [`GET /api/dashboards/{id}/export`](/zh-hans/iot/api/#get-apidashboardsidexport) 和 [`POST /api/dashboards/import`](/zh-hans/iot/api/#post-apidashboardsimport)，界面调用的就是它们。导入绝不会保存搭建同一个仪表板时会被拒绝的内容。

## 文件

UTF-8 JSON，最大 4 MiB。

```json
{
  "format": "hotloop-screen",
  "formatVersion": 1,
  "exported": { "product": "edge", "version": "4.22.1", "at": "2026-11-19T16:00:00Z" },
  "screen": {
    "id": "line-2",
    "name": "Line 2",
    "kind": "cards",
    "roles": ["operator", "admin"],
    "homeFor": ["operator"],
    "screens": ["line-2-panel"],
    "position": 1,
    "cards": [
      { "id": "temp", "type": "gauge", "title": "Zone 1", "w": 3, "h": 3, "config": { "tag": "press-01/Zone1_Temp" } }
    ]
  },
  "requires": {
    "tags": [ { "key": "press-01/Zone1_Temp", "dataType": "float", "unit": "C", "writable": false } ],
    "entities": [], "scripts": [], "recipes": [], "devices": [], "equipment": []
  }
}
```

**`format` 和 `formatVersion`。** `format` 始终是 `hotloop-screen`。`formatVersion` 是从 1 开始的整数。HotLoop 读取自己的版本及更早的版本，对更新的版本则拒绝，并说明文件是哪个版本、自己读取哪个版本。向文件添加字段就是一个新版本，因为读取器会拒绝它不认识的字段：悄悄丢弃的字段比拒绝更糟。这是版本 1。

**`exported`。** 由哪个产品和版本在何时写入。给读文件的人看。不据此决定任何事：卡片类型决定 HotLoop 能否显示画面，不认识的卡片类型会按名称被拒绝。

**`screen`。** 仪表板 API 所保存的仪表板，不含安装自己的记账信息（`version`、`updatedBy`、`createdAt`、`updatedAt`）。`description` 为空时省略。卡片按阅读顺序排列，每张都有尺寸（12 列中的 `w`，以行计的 `h`）和 `config`，各类型与[仪表板](/zh-hans/iot/dashboards/#the-cards)的描述完全一致。布局就是这样：卡片的流，从来不是像素坐标。符号卡片在自己的页面上按像素放置符号，写在它的 config 里。

**资源在文件之内。** 地图卡片上的平面图和符号卡片的背景，是卡片 `config` 中的 base64 PNG 数据 URL，所以一个文件就是整个画面，发送它也就是把图片一起发送。限制是仪表板的限制：每张图片 700 KB，每个画面 2 MiB。

**`requires`。** 画面对其落地的安装有什么需要，由卡片算出：它读取的每个变量（包含它在导出处的类型和单位，以及按钮或设定值是否写入它），以及卡片所指的实体、脚本、配方、设备和装置的 id。它供人以及想在导入前先看一眼的工具使用。导入会从卡片重新算出，从不信任这个块。文件中某个变量的类型与它落地的变量不同时，会给出警告。

**墙面看板不会导出。** 它是一个安装中固定的仪表，不是布局。导出它会得到 `400`，`kind` 为 `wall` 的文件会被拒绝。

**分配。** `roles`、`homeFor`、`screens` 和 `position` 写在文件中，使画面按原样回来。它们也是与某个安装绑定最紧的部分：面板名称在一个安装上属于一个仪表板，一个角色只有一个主页。导入会应用它们，并在此安装已把该画面名称或该角色的主页给了另一个仪表板时说明（`assignment`）。**跳过分配**会去掉 `screens` 和 `homeFor`，保留 `roles`。

## 导入

检查按以下顺序运行，在全部通过之前不会保存任何内容：

1. **文件。** JSON，正确的 `format`，此版本能读取的版本，没有它不认识的字段，类型为 `cards`。
2. **您对它的更改。** 新的 id 或名称，不含分配，以及**映射**：`tags`（完整键到完整键，按文件中变量的名称，或按设备迁移后的读法），`devices`（id 到 id；同时也迁移 `tags` 映射中没有点名的每个变量的设备部分，所以把画面从一台 PLC 搬到另一台只需一条），`entities`、`scripts`、`recipes` 和 `equipment`（id 是只在创建处才有意义的数字，所以逐个映射）。趋势图的图例文字随其变量一起迁移。没有任何卡片用到的映射条目会给出警告，因为什么也没做的映射，正是画面最后仍指向旧对象的原因。
3. **仪表板自身的规则。** id、名称、每张卡片的 config、尺寸、字节上限，按其存储的形式检查。
4. **卡片所指的一切，毫无例外。** 每个缺失的变量、实体、脚本、配方、设备和装置 id 都会列出，而不只是第一个，所以一次就知道要映射什么。对不可写变量的按钮或设定值是 `writable`。超出变量范围的按钮值或设定值限值，以及不存在的角色，是 `screen`。
5. **id 和分配。** 已被占用的 id 是 `exists`，除非您要求**替换**，这会在该仪表板当前的版本上保存（所以您查看期间发生的保存是 `409`，而不是覆盖）。

试运行会做这一切，但不保存任何东西。导入会作为仪表板上的 `config` 事件记入日志：谁，来自哪个产品和版本，多少张卡片。

## 移动一个画面

在第一个安装上导出。在第二个安装上，确保画面所读取的设备和变量已存在（它们带有属于工厂的地址，所以画面文件不携带它们）。导入。如果变量名不同，就在对话框中映射它们，如果只有设备不同，就映射设备。画面在第二个安装上打开时，与它在第一个安装上的样子一样。

## CODESYS 可视化

同样的导入可以读取 CODESYS 可视化（IDE 的原生导出）并据此生成画面，同时说明它省略了什么：[导入 CODESYS 画面](/zh-hans/iot/codesys-screen-import/)。

## 版本 1 中没有的内容

画面所读取的设备和变量（它们的地址属于工厂，而不属于画面）、墙面看板、一个文件中包含多个画面，以及文件上的签名。文件是纯 JSON：在导入别人发给您的文件之前，请先读一读。
