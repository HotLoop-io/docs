集成是这样一种方式：把 HotLoop 指向一类您知道地址的设备，回答几个问题，查看上面实际有什么，并保留您想要的点。它会创建设备及其变量。实体由变量生成，与其他所有变量一样，所以新的点在一分钟后就出现在实体 API、自动化和仪表板中。

设备进入 HotLoop 有三种方式，它们设计为并存：

| <span class="sr-only">Details</span> | 由谁发起 | 需要什么 |
|---|---|---|
| [MQTT 发现](/zh-hans/iot/mqtt-discovery/) | 设备，通过在 broker 上自我宣告 | 一个使用其中一种格式的发布者 |
| [网络发现](/zh-hans/iot/network-discovery/) | 网络，通过被监听 | 不需要设备做任何事；它会告诉您它听到了什么，以及 HotLoop 如何与它通信 |
| **集成**（本页） | 您，提供一个地址 | 一台能用自身协议应答的设备 |

集成从不向设备写入，它创建的任何东西都没有启用写入。找到的点是还没有人决定可以对其下达命令的点，所以设置创建的每个变量都是只读的，直到有人在变量编辑器里逐个启用它，与来自任何其他来源的变量一样。

## 目前有哪些

| 集成 | 协议 | 验证对象 |
|---|---|---|
| OPC UA 服务器（`opcua`） | [OPC UA](/zh-hans/iot/protocols/#opc-ua) | 一台真实的 OPC UA 服务器 |
| SNMP 设备（`snmp`） | [SNMP](/zh-hans/iot/protocols/#snmp) | 一个真实的 SNMP 代理，v1、v2c 和 v3 |
| BACnet/IP 设备（`bacnet`） | [BACnet/IP](/zh-hans/iot/protocols/#bacnetip) | 一个独立的 BACnet 协议栈 |
| CODESYS PLC（`codesys`） | [CODESYS](/zh-hans/iot/protocols/#codesys) | CODESYS Control for Linux SL 4.22.0.0，运行两个真实的 PLC 程序，其中一个大得多 |

只要能在真实服务器上得到证明，就会在这个框架上继续添加。

## 反方向

集成是把设备引进来。要把 HotLoop 的读数和事件发送出去给 Kafka broker，请参见历史库目标下的 [Kafka API 事件流](/zh-hans/iot/historian-targets/#kafka-api事件流)：Apache Kafka 和 Redpanda，TLS 和 SASL，读数放在一个 topic，系统日志放在另一个。要以 OPC UA PubSub（基于 UDP 的 UADP）发送，或者读取某个发布者的数据，请参见 [OPC UA PubSub](/zh-hans/iot/protocols/#opc-ua-pubsub-uadp)：读取一个发布者就是创建一个协议为 `opcua-pubsub` 的设备，没有设置流程，因为数据报携带的是字段位置，不是名称。

## SNMP

适用于交换机、UPS、PDU、电表，或任何运行 SNMP 代理的设备。问题随版本而定：v2c 询问 community，v3 询问用户，并且只询问其安全级别所需的口令。没有默认的 community。

探测会遍历 system 组、接口表、主机资源、负载表以及 SNMP 代理的 extend 输出，也就是 HotLoop 能命名的对象，并把每一个与代理所说它此刻保存的值一起显示。它会**建议**指向新设备的人想要的那些点：设备的名称、位置和运行时间（以秒显示，而不是代理的百分之一秒），每个接口的运行状态和错误计数，它的字节计数器（代理有 64 位的就用 64 位的），平均负载，以及所有 extend 行。它会在备注中说明建议的点里有多少是计数器，因为图表上的计数器需要的是速率。

代理拥有的其他一切仍然可读：请手工设置为一个地址是 OID 的变量。关于变量会变成什么、缺失的对象会怎样，以及错误的 v2c community 为什么看起来像设备已死，请参见 [SNMP 驱动](/zh-hans/iot/protocols/#snmp)。

这里的 SNMP 始终是只读的。HotLoop 不发送 SET。

## BACnet/IP

适用于楼宇自动化控制器、电表、恒温器：IP 网络上任何使用 BACnet 的设备。问题包括设备的地址、您知道的话还有设备实例（此时 HotLoop 会拒绝该地址上由另一台设备应答），以及如果机器有两块网卡，从哪一块发送。

探测会询问设备它是谁，读取它的对象列表，并读取它找到的每一个模拟、二进制和多状态对象（以及整数、大模拟量、累加器和字符串值）：名称、描述、单位、当前值和状态标志。它会连同刚读到的值一起显示每一个，并建议前一百个。单位以标签的形式传来，如果含义明确，还会带上设备类别，所以 `degrees-celsius` 输入就是 `°C` 温度。

它会在备注中说明有多少对象报告故障（在设备清除之前读为坏值），以及有多少处于停用状态（读为不确定，因为其值是写入它们的值）。多状态对象的描述会列出它的各个状态，它的采样除了数字还会显示状态。

这里的 BACnet 始终是只读的。HotLoop 不写入属性，也不会到达 BACnet 路由器后面的设备：哪些被覆盖、哪些没有，请参见 [BACnet/IP 驱动](/zh-hans/iot/protocols/#bacnetip)。

## CODESYS

适用于运行 CODESYS Control 运行时的 PLC。问题就是 OPC UA 的那些（地址、安全性，以及在 PLC 的用户管理开启时的用户名和密码），并且仅在您需要时，才会问要列出应用的哪一部分、PLC 和应用的名称，以及要列出数组的多少个元素。

探测会连接到运行时的 OPC UA 服务器，找到 PLC 及其应用，并按程序员写的名称列出应用导出的变量（它的 Symbol Configuration），连同其类型和每个变量是否可写。它建议的是应用自己的变量，不是它缓冲区的元素，并在备注中说明有多少数组只列出了一部分。对于没有导出任何内容的 PLC，它会告知如何导出。

CODESYS 设备每秒读取一次，也就是驱动请求运行时的 OPC UA 服务器查看每个变量的频率，所以界面比 PLC 最多晚大约一秒，不会更多。运行时自身的默认值是五秒，对界面来说太慢：水泵启动了，页面五秒后才显示。更改设备的轮询间隔或它的 `samplingIntervalMs` 来请求更快的速度；每个设备都受的下限以及服务器的 OperationLimits 仍然适用。

在请求中使用 `"dashboard": true` 进行设置，您保留的点还会得到一个以设备命名的仪表板：一个标题、一个随数值变化的趋势、设备的报警，以及在其变量列表标题下每个点的一张数值卡。这是根据程序现状生成的第一个界面，和任何仪表板一样可以编辑。上面没有任何东西会下达命令，并且每个变量在启用之前仍然是只读的。

运行时重启或下载了新程序的 PLC 会被自动重新接管：请参见 [CODESYS 驱动](/zh-hans/iot/protocols/#codesys)。

## 流程

三次调用，按顺序进行，前两次不保存任何内容。

1. **询问。** `GET /api/integrations` 列出每个集成及其问题。每个问题都有类型（`text`、`number`、`bool`、`choice` 或 `secret`）、默认值、是否必填，以及仅在另一个回答之后才有意义时的 `showWhen`。界面仅由这些绘制，这就是新的集成不需要新界面的原因。
2. **查看。** `POST /api/integrations/{id}/probe` 接收回答，检查它们，用该集成自己的驱动连接到真实设备，并报告它是什么以及有什么：建议的名称、它对自己的说明、值得一读的备注，以及找到的每个点，以变量形式的记录给出，并附上所读内容的 `sample`，这样您可以与机器自己显示屏上的数字对比。
3. **保留。** `POST /api/integrations/{id}/setup` 接收相同的回答和要保留的点的名称（没有指定任何名称时，保留标记为 `suggested` 的点），创建设备及其变量并重新加载运行时。设备已启用并在轮询。能够布置第一个仪表板的集成（CODESYS），在请求中带有 `"dashboard": true` 时会这样做，并返回仪表板的 id。

设置会重新查看设备，而不是信任探测。客户端一分钟前认为自己找到的内容只是一种声称，这些点会按设备创建时的状态对照设备进行检查。设备上没有的名称会得到 `400`，而不是被跳过的点，因为有人是按名称请求它的。

设置中途失败（设备已保存而变量没有）时，会删除它刚创建的设备。已经存在的设备会被 `400` 拒绝，而不是被覆盖：要给您已有的设备添加点，请使用它的 Browse 和 Import。

## 在尝试任何操作之前先检查回答

框架会在集成看到每个回答之前，先对照其问题进行检查，并一次性报告所有问题，所以表单只需修正一次：

* 留空的必填问题会得到 "X is required"；
* 数字必须是问题范围内的整数，选项必须是其选项之一，bool 必须是 bool；
* 对集成没有问的问题给出的回答会被拒绝，而不是被忽略，因为拼错的 `pasword` 若被不吭一声地丢弃，设备就会登录失败，还没有任何原因提示；
* 机密值不能是 API 用来代替已保存值显示的 `[redacted]` 占位符。把它送回去会把这个占位符存成密码；
* 不显示的问题（`showWhen`）会被忽略，也不是必填。

凭据的保存方式和设备的一样：当 HotLoop 有封存密钥时静态封存，并在每个 API 响应和每个错误中隐藏。探测从不保存它得到的内容。

## 设备不应答时

`502`，附带出了什么问题："could not reach the device: ..." 表示什么都没连上，"connected, but could not list its points: ..." 表示连上了随后没有应答。这是需要阅读的设备的应答，不是 HotLoop 的故障，也不是错误的请求。端口关闭、community 错误或防火墙最终都会到这里，消息来自驱动本身。

## 它在产品中的位置

探测和设置从 HotLoop 主机跨网络访问，所以两者都需要 `devices.write`，与保存设备相同。列出需要 `devices.read`。每个产品都带有它们。路由见 [HTTP API](/zh-hans/iot/api/#集成)。

## 添加一个

* `Info()` 说明它是什么：id、名称、驱动的协议、如何询问地址以及这些问题；
* `Configure()` 把检查过的回答变成地址和驱动自己的配置块，并拒绝问题无法表达的内容；
* `Discover()` 访问真实设备并报告上面有什么。

框架在启动时会拒绝不能成为目录条目的集成：重复的 id、模型没有声明的协议、没有标签的问题、没有选项的选择、不是有效回答的默认值，或者指向不存在的问题的 `showWhen`。一项测试还要求每个集成都使用已编译进驱动的协议。

没有真实服务器可运行的地方，就没有集成，[路线图](/zh-hans/roadmap/)会说明哪些在等待硬件。
