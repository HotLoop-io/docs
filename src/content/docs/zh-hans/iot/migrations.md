---
title: "迁移只增不减"
description: "为什么迁移从不删除、重命名或更改任何东西的类型，让失败的更新可以回到上一版而不丢失任何一行数据。"
---

迁移只做添加。它从不删除、重命名或更改任何东西的类型，从不收紧上一版正在写入的列或约束，也从不删除数据。这就是全部规则，迁移一旦违反，测试就会让构建失败。

## 为什么

每个盒子都跟随 `:stable`，Podman 的自动更新会推动它。当某一版迁移了数据库，随后健康检查失败，更新就会回滚，上一版在新版留下的结构上启动。迁移无法随之回滚。所以上一版必须能在新结构上运行，而唯一能做出这个保证的办法，是新结构完整保留旧结构的一切，形状相同，接受相同的写入。

添加一列，旧版本根本不会去看它。删除一列，旧版本的第一条查询就会报错，发生在工厂里，凌晨三点，而且已经没有可以回退的东西。

Helm chart 有同样的问题：`helm rollback` 会换回旧镜像，却把数据库留在新版把它推到的地方。

## 看起来需要更多的变更

您不能删除，所以看起来需要删除的变更，是通过添加、再不去碰旧东西来完成的。

- **重命名一列。** 添加带默认值的新列。新版本读新列，并同时写入两列。旧列留在那里，不再使用，永远保留。
- **更改类型。** 同样：新增一个新类型的列，新版本同时写入两列，旧列保留。
- **现在必须为 NOT NULL 的列。** 在应用中强制执行。如果确实需要约束，就放在新建的表上。
- **淘汰一张表。** 停止使用它。它仍然保留。
- **清理旧数据。** 由应用在运行时完成（保留策略已经这样做），而不是迁移。

废弃的列只占用几个字节。一个无法撤销、而它所属的版本却可以回滚的迁移，代价是一座工厂。

## 保护机制：应用会拒绝一个无法信任的结构

添加对一个版本来说是安全的，但不是永远安全。一个版本只在紧随其后的结构上得到过验证，所以应用会计算数据库领先了多少。

`schema_migrations` 在每个迁移旁边记录是哪个版本应用了它（`app_version`）。启动时，在碰任何东西之前，应用会把数据库中的迁移与自身内置的迁移做对比：

| 数据库中有 | 会发生什么 |
|---|---|
| 没有这一版不认识的东西 | 启动 |
| 来自较新一版的迁移 | 启动，并给出点明两个版本的警告。这是一次被回滚的更新。它不迁移任何东西，较新的版本回来时会发现自己的结构已经就位 |
| 来自较新两版或更多版本的迁移 | 拒绝启动，并点明这一版、它所知道的最新迁移、数据库中最新的迁移，以及写入它们的版本 |

拒绝时的提示如下：

```
refusing to start: this database's schema is more than one release ahead of
HotLoop 4.18.10. 0022_x.sql is the newest migration this release knows, and the
database has 2 it does not (up to 0024_z.sql), written by 4.19.0 and 4.20.0.
Only the release right after this one is known to work on that schema. Start
HotLoop 4.20.0 or newer against this database (an update to :stable gets
there), or restore a backup taken by HotLoop 4.18.10 or earlier
```

在跟随 `:stable` 的盒子上，下一次更新就能修复，因为 `:stable` 会移到最新的版本，而它认识每一个迁移。在此之前，该单元停在“activating”。这是故意的：一个停机并说明原因的盒子，胜过一个在运行却出错的盒子。

无论启动时是否迁移（`HOTLOOP_DB_MIGRATE`），保护机制都会运行，恢复数据时也会运行，因为恢复以同样的方式打开数据库。保护机制出现之前的数据库没有 `app_version` 列，也不可能包含比读取它的版本更新的迁移，所以它可以启动；该列会在带有保护机制的版本首次启动时添加。

## 为真实版本验证

一个版本发布之前，会让上一版在新版迁移过的数据库上启动，并要求它登录、读取设备和变量、通过关口写入、读取历史。如果做不到，这个版本就不发布。
