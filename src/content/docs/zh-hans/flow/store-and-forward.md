title: "HotLoop Flow 的存储并转发"
description: "把连线标记为持久，后面的节点停止应答时消息会按顺序写入磁盘，并且在 kill -9 之后依然在。"
---

把连线标记为持久，只要另一端的节点跟得上，它就是一条普通连线，不会向磁盘写入任何内容。该节点一停止接收消息，连线就会在发送方继续之前溢写到同一个 SQLite 文件，由一个泵从最旧的开始逐条投递，直到目标接收每一条；对于一次性写入数据库的目标（InfluxDB 就是），每批最多 256 条，其余目标则一条一条投递。所以历史数据库停机时，读数会堆积在磁盘上，而不是阻塞流程或被丢弃，等它恢复后按顺序写入。运行正常时什么都不写的代价是，此时 `kill -9` 会丢失内存中的内容，大约是一次轮询的量，我们宁愿在这里说明，也不愿让您自己发现。

```json
{ "id": "count", "type": "function", "ew_durable": ["influx"], "wires": [["influx", "reply"]] }
```

您不必手写这个键。在编辑器里双击连线，勾选 *Durable* 即可。

它能在重启后保留，保持顺序，遵守磁盘配额（默认 256 MiB，配额满时由另一端节点的溢出策略决定什么让步），并把深度显示为 `hotloop_flow_durable_wire_depth`。它是至少一次，而不是恰好一次，我们宁愿在这里告诉您，也不愿让您在事后复盘时才发现：确切的措辞，以及 `influxdb out` 如何仍然保持正确，见 [docs/durable](/zh-hans/flow/durable-state/)。

证据是 `docs/durable/store-and-forward.sh`：Podman 里一个真实的 InfluxDB 2.9.1，每秒二十条读数，停机十分钟后恢复，并在故障中途和排空中途各用 `kill -9` 终止一次运行时。接收 15,982 条读数，存入 15,982 行，没有缺失，没有重复。正常的持久连线自己不写任何内容，上下文每三十秒写出一次时，整个进程在每秒二十条消息的情况下每小时写入 1.7 MiB（每天 0.04 GB）。表格和命令见 [docs/durable](/zh-hans/flow/durable-state/)。

## 目标永远拒绝的消息

默认情况下，连线会不断重试其目标处理失败的消息，停顿时间逐渐增加到五秒，该消息后面的一切都不会移动。对停机的历史数据库来说，这恰好是正确的。对于历史数据库永远不会接受的一条格式错误的读数，这就成了永久卡住的连线，所以有一条出路，并且在您要求之前是关闭的。

```json
{ "id": "count", "type": "function", "ew_durable": ["influx"], "ew_durable_attempts": { "influx": 20 }, "wires": [["influx", "reply"]] }
```

为连线设置一个尝试次数，在编辑器的连线对话框里设置或如上所述，当目标把队列中的一条消息拒绝了那么多次之后，连线就会把它作为拒绝它的节点所产生的错误上报给流程，消息像任何节点错误那样附带其中，然后继续处理下一条。该流程上的 Catch 节点会收到它，可以把它搁置、为它告警或写到别处。没有 Catch 时，错误仍会显示在调试侧栏里，而消息就丢了，所以请连一个。内存中的第一次拒绝像以前一样到达 Catch，所以 Catch 会看到同一条消息两次：一次是它第一次失败时，一次是连线放弃时。计数是按消息计的，并且保存在内存中，所以重启会让它重新开始。`hotloop_flow_durable_wire_given_up_total` 在深度旁边统计这些消息。不是 1 或更大的整数的限制会被报告，连线继续重试，因为悄悄忽略它会让一条已被人要求停止的连线一直卡住。
