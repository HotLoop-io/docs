凌晨 2 点某个值出了错，调试栏会告诉你这个值。但它不会告诉你，经过的九个节点里是哪一个改了它，最慢的那个压了它多久，也不会告诉你它进来时是什么样子。要弄清楚，只能在流程里到处插 Debug 节点，部署，等它再次发生，再把节点拆掉。

所以进入流程的每条消息都会有一条追踪。调试栏里的每条调试消息都有一个 **Trace** 按钮，点一下，这条消息走过的路径就会在画布上亮起来：经过的节点、走过的连线都会点亮，从未碰过的部分则变暗。路径上的每个节点会显示它持有这条消息多长时间（`8.3 µs`，如果它处理了其中三份，则是 `8.3 µs ×3`），旁边的 Trace 面板按顺序列出每一跳，以及该节点收到时的消息原样。点一行就到了那个节点。失败的一跳是红色，错误显示在下面。

它跟随消息实际走过的路：

- **经过 Split。** 一个读数变成三个，三个都在追踪里，在拆分之后的每个节点上各自成为一跳。
- **经过 Join。** Join 之后的那一跳，把 Join 为它收进来的所有消息都当作父级，而不只是碰巧最后到的那一条。喂给它的三条分支全部点亮。
- **经过子流程。** 里面的节点以带各自 id 的副本运行，每一跳记在这些 id 下。画布点亮的是子流程实例，因为它才是你正在看的标签页上的节点。
- **进入 Catch。** 失败的节点在它那一跳上带着错误，接住错误的 Catch 是下一跳，并标记为由错误到达。

追踪随消息一起走，但不在消息里面。没有任何流程能通过 `msg = {...}` 读取或破坏它，它也不会出现在 Debug 节点、测试或连线上的 payload 中。

## 它不会无限增长

它运行在它所监视的产线上，所以每个方向都有上限，上限在[配置](/zh-hans/flow/configuration/)的 `trace:` 下：

| 上限 | 默认值 |
|---|---|
| 保留的追踪，最新的 | 256 |
| 一条追踪保留的跳数，避免循环无限记录自己 | 512 |
| 一跳会保留副本的最大消息 | 16 KiB |
| 全部加起来，粗略计数，先忘掉最旧的 | 16 MiB |
| 每秒新开始的追踪 | 1,000 |

超过 16 KiB 的消息会保留耗时，并标记为太大无法显示，也无法回放或变成测试。每秒新追踪超过 1,000 条之后，那一秒里其余的消息不再追踪，因为一个每秒说十万次话的传感器，否则要为每一条都付出一条追踪的代价。被跳过的消息，或者在途中追踪被挤掉的消息，在剩下的旅程里一直不被追踪；中途开一条新追踪，只会让缓冲区被一些头部已经丢失的旅程的尾巴填满。这些全部在 `/metrics` 上计数，所以你能看到它何时发生。

耐久测试：**一百万条消息经过五个节点，2026-10-18**，与[上面的数字](/zh-hans/flow/overview/#数据)是同一台机器。强制 GC 后的堆，每十万条消息采样一次：

| 追踪 | 堆，每个检查点 | 每秒消息数 |
|---|---|---|
| 追踪关闭 | **1.3 MiB** | 192,596 |
| 追踪每条消息 (`perSecond: 0`) | **2.7 MiB** | 115,770 |
| 默认上限 | **4.0 MiB** | 195,199 |

十个检查点上都是同一个数。追踪器从第一个检查点到最后一个，在 256 条追踪里保持着 808,448 字节，一路上忘掉了一百万条中的 999,744 条，从未接近它的 16 MiB。追踪每条消息确实有代价：这条链路从每秒 192k 降到 116k。这就是默认上限存在的原因。每秒 1,000 条追踪时，代价淹没在噪声里，低于这个数，一条追踪大约 3 KB。如果你仍然想要每条消息，请设置 `perSecond: 0`，并在决定之前先读那张表的第一行。可以这样复现：

## 在草稿中回放

你找到了错误的值，觉得知道怎么修，并且已经改了画布上的一个节点。别为了验证而部署。**Replay into draft** 取出启动这条追踪的消息，放进你此刻画布上的流程（不管是否已部署），并告诉你它最终落在哪里，与第一次落在哪里相比如何。

"落在"指消息停下的地方：Debug 节点、MQTT Out、什么都没匹配到的 Switch、仍在等待的 Join。对每一处，比较会告诉你相同，或者哪些属性变了（`payload: "HIGH" -> "CRITICAL"`），或者原来在那里结束而回放没有，反之亦然。回放自己的路径也会在画布上点亮，所以你能看到草稿把它送到了哪里。**Back to the original trace** 会把第一条追踪换回来。

它的运行方式和[流程测试](/zh-hans/flow/tests/)一样，在带有真实运行时和真实节点的子进程里，原因也相同：你的草稿会启动其中的每个节点，而其中的任何东西都碰不到工厂。这意味着本来要调用网络服务的节点会得到空应答，所以输出取决于应答的流程会表现为一处差异。这是诚实的结果。它不会假装自己和一个从没通信过的 PLC 通信过。

## 追踪变成测试

Trace 面板里的 **Make test** 会根据整条追踪起草一个[流程测试](/zh-hans/flow/tests/#在编辑器里生成测试)：启动它的消息，从它进来的源头放回去；以及它到达的、测试能够观察的每一个终点，并把该节点收到的内容作为那里的期望值。这和从调试消息生成测试是同样的两次点击，对复杂的流程更好，因为追踪记得消息到达的每一个末端。拆分到三个 Debug 节点就是三条期望，而一条调试消息只有一条。

做不到的时候它会说明原因。在子流程内部开始的追踪、从源的第二个输出开始的追踪，或者由太大而无法保留的消息开始的追踪，都无法按测试需要的方式放回去。被 Switch 丢弃的消息也不会结束在任何测试能观察的地方，所以会被拒绝，而不是被写成一个空的测试，因为没有可检查内容的测试总会通过。

## OpenTelemetry

把它指向一个收集器，每一跳都会作为一个 span 发出去：

```yaml
trace:
  otlp:
    endpoint: http://collector:4318   # OTLP over HTTP; /v1/traces is added
    headers: {x-api-key: ...}         # if the collector wants one
    serviceName: hotloop-flow
```

一条追踪就是一条 OpenTelemetry 追踪，一跳就是一个 span，发送该消息的那一跳是它的父级。Join 的 span 以第一个为父级，其余的作为链接。每个 span 带有节点 id、节点类型、消息 id、该节点向后发送的消息数，以及到达它所经过的输出端口，错误则是带有错误状态的 span。**消息从不离开。** payload 是工厂的数据，而收集器是别人的服务器，所以送出去的只是旅程的形状和耗时。

它使用规范定义的 JSON 编码说 OTLP/HTTP，在一个文件里手写完成，而不是为了完成同样的一次 POST 引入带着 protobuf 和 gRPC 的 OpenTelemetry SDK。二进制有体积预算，我们不会把它花在这上面。每个 span id、父级、链接、名称、属性和错误状态都必须匹配。这个测试里任何地方都没有 mock。如果收集器宕机，导出会丢弃 span 并计数，流程毫无感觉；`hotloop_flow_otlp_spans_failed_total` 超过零，就是你发现它的方式。
