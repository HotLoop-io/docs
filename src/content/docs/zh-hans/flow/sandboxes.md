---
title: "HotLoop Flow 的两个沙箱"
description: "Function 节点和 WebAssembly 沙箱是如何隔离的，各自能接触什么，以及插件如何在第二个沙箱中运行。"
---

Function 节点运行在 JavaScript 解释器上（见[安全态势](/zh-hans/flow/security/)）。一次调用耗时 11.6 至 13.7 µs。它不是针对内存的边界：在循环里分配内存的函数会让 Go 堆不断增长，直到 Pod 死掉，而 JavaScript 解释器对此唯一能做的是按墙钟时间的超时。

这需要每次调用 184 至 196 µs，是一次 JavaScript 解释器调用的十五到十六倍。只有在运行您并不完全信任的代码时才值得付出这个代价，其他情况不值得。

流程通过插件运行一个 WASM 客户模块：它是带有描述符的已签名模块，编辑器据此绘制对话框，除非它提出请求并且您答应，否则得不到任何主机访问权限。内存按节点设上限，消息有超时，超出任何一项的客户模块会陷入中断，带着原因到达 Catch 节点，不会拖垮其他任何东西。全部内容见[无需 npm 的插件](/zh-hans/flow/plugins/)，包括如何信任发布者的密钥以及拒绝时给出的说明。对您的意义是：Node-RED 需要 npm 和完整的 Node.js 安装才能做到的事，Flow 以一个沙箱化文件来运行，您可以在加载前先验证它。

插件可以用 Rust、TinyGo、Zig 或 AssemblyScript 编写，而不必用 JavaScript，所以 OT 流程真正需要的信号处理以编译后的形式运行，并带有无法争辩的内存上限。

客户模块的 ABI 是三个导出，其中两个是分配器钩子，它有意做得这么小。每个导出都是攻击面，也是每个客户模块作者必须做对的又一件事。

| 导出 | 签名 | 是否必需 |
|---|---|---|
| `hotloop_flow_process` | `(ptr i32, len i32) -> i64` | 是 |
| `hotloop_flow_alloc` | `(size i32) -> i32` | 是 |
| `hotloop_flow_free` | `(ptr i32, size i32)` | 否 |

`i64` 结果把偏移量打包在高 32 位，把长度打包在低 32 位，指向客户模块自身内存中的一个 JSON 响应。一切都以 JSON 传递，所以任何语言的客户模块都可以不借助共享的模式编译器来生成它。

这些限制有意设得很小。它运行在边缘硬件上，紧挨着真正重要的流程，需要更多资源的节点就应该明说：

| 限制 | JavaScript 解释器 | WASM |
|---|---|---|
| 每次调用的超时 | 5 s | 5 s |
| 内存上限 | 无法强制 | 每个节点 16 MiB，除非插件另有说明，最多 64 MiB，除非您调高 `plugins.maxMemoryMiB`，硬性上限 |
| 最大输出 | 16 MiB | 8 MiB |

两种运行时都是纯 Go，没有 cgo。
