历史数据库停机一小时，不该让您丢掉一小时的读数，前提是这次停机在磁盘配额之内（默认 256 MiB：每个读数 120 字节、每秒 100 个读数时约一小时，在 2.13.1 上实测）。流程里的计数器也不该因为 Pod 换了地方就从头开始。这两件事靠的都是卷上的一个 SQLite 文件，本页说明里面存什么、保证什么、不保证什么，以及它对闪存卡的代价。

只有一个文件，就是数据目录里的 `state.db`。持久上下文和持久连线背后的队列共用它，因为两个存储就意味着两份要规划容量、要备份、要保持同步的东西。

## 重启后仍保留的上下文

流程、全局和节点上下文在某个作用域第一次被使用时从文件载入，之后一直在内存中，所以读取从不碰磁盘，`CompareAndSwap`、`Increment` 和 `Update` 与以前是同一份代码，在同一把锁下保持原子。重启后计数器会回来，并从那里继续；对从磁盘恢复的值做 `CompareAndSwap` 仍然有效，包括 function 节点存入的整数。

放弃的部分是有意为之：写入是滞后的。改动的值要等 `store.context.flushInterval`（30 秒），这个窗口内所有改动在一次事务中写入文件。一个计数器在一个窗口内自增一万次，只写一行。把值设成它本来就是的值，则根本不写，这正是每秒存同一个温度的流程，以及否则会因此恨您的 SD 卡的情况。正常停止会先把所有内容写入。`kill -9` 或断电最多丢失一个间隔。把它设为 `0s`，每次改动都会在调用返回前写入，代价由卡来付。

只有能经受 JSON 的内容才能经受重启：数字、字符串、布尔值、时间、字节缓冲、列表和对象。把函数或套接字放进上下文，`set` 会失败并指出键名，而不是只存一半。节点的上下文在节点被删除时消失，流程的上下文在标签页被删除时消失，发生在部署时，与 Node-RED 的清理方式相同。

## 持久连线

在连线所出自的节点上把它标记为持久。键是 `ew_durable`，值是这条连线所通向的节点 id 的列表，流程文件仍然逐字节地载入和保存，因为其他工具会忽略它：

```json
{
  "id": "count", "type": "function", "z": "line3", "x": 290, "y": 100,
  "ew_durable": ["influx"],
  "wires": [["influx", "reply"]]
}
```

从 `count` 到 `influx` 的每条连线现在都是持久的。通向 `reply` 的连线仍是普通连线。

持久连线的行为如下：

- **目标跟得上时什么都不写。** 消息从内存直接进入目标的收件箱，与普通连线相同，状态数据库不会被触碰。我们定下这条规则，是因为一个先写入一切的设计在闪存卡上实测每天要写数百 GB，而它防备的故障一年只出现几个小时。
- **跟不上时溢写到磁盘。** 一旦目标的处理程序返回错误、收件箱已满或目标没有运行，连线就开始溢写。从那时起，每条消息都在发送节点的 `Send` 返回之前提交到文件，所以发送方一旦继续往下走，`kill -9` 就带不走它。已经在发往目标途中的消息，会按顺序转到磁盘上，排在失败的那条之后。在上面的例子里，`reply` 在接线中排第二，所以连线在溢写期间，HTTP 200 就表示读数已经在磁盘上。
- **按顺序排空，目标能收批量时按批投递。** 泵把磁盘上最旧的消息交给目标，并等到它们被接收。任何消息后面的内容都不会超过它。写入数据库的目标可以把最多 256 条消息作为一次写入来接收，`influxdb out` 就是这样：历史数据库响应一次写入需要 8 ms 时，积压按一条一条投递，大约每秒 110 个读数，每秒发送 100 个的工厂几乎追不上；当每次写入带几百条时，则按写入所允许的速度排空。其他任何目标仍然每次收一条。如果一批没有被接收，第一条失败消息之前的消息标记为完成，那一条按下面的重试单独再试，其余的作为一批重新发送。队列为空时，连线回到内存并停止写入。
- **目标失败的内容会重试。** 同一条消息在 250 ms 后再次发送，然后是 500 ms，翻倍直到 5 秒，需要多久就多久。流程里的 Catch 节点只会听到第一次失败，而不是每一次重试。已停止、被一次部署替换或启动失败的目标会被等待，而不是被跳过。
- **能经受重启。** 进程回来时磁盘上还留着的内容，会最先投递。
- **遵守磁盘配额。** `store.durable.maxBytes`（256 MiB）对所有持久连线合计生效，每条消息按正文加 64 字节计算。配额满时，由连线所通向的节点按它已有的溢出策略决定：`block` 最多等待 `blockTimeout` 的空位，然后报错，`drop-newest` 拒绝到达的消息，`drop-oldest` 挤出尚未在投递的最旧消息，`error` 向 Catch 节点抛出错误。每一种都会被计数，并作为丢弃事件通告。有一个例外：已经被内存接收、连线又必须移到磁盘的消息，会超出配额进入，因为拒绝它意味着丢掉更旧的消息而保留较新的。超出量最多是目标所持有的内容，即它的收件箱，加上它的 goroutine 已取走但还没开始处理的那一条，所以配额可能一时多出几条。文件会比配额稍大，原因是 SQLite 的页开销和预写日志，并且有一项测试把它填满、排空、再填满，重复六次，以证明它不会持续增长。
- **显示自己的深度。** `hotloop_flow_durable_wire_depth{wire="..."}` 是等待中的消息数，旁边有 `_bytes`、`_delivered_total`、`_retries_total` 和 `_dropped_total`，把 `hotloop_flow_durable_bytes` 与 `hotloop_flow_durable_max_bytes` 对照就是配额。
- **不会重启节点。** 在运行中的流程里把连线标记为持久只是接线的改动，就像移动一条连线。

一条不再持久或被删除的连线，它的队列会被清空，计为已丢弃并通告。这些消息已无处可去，留着它们会让配额被一个没人看得见的队列占满。

### 它承诺什么，不承诺什么

**连线正常时存在一个丢失窗口。** 内存里的是目标的收件箱和它正在进行的调用，`kill -9` 或断电会把它们带走。这是不写任何东西的代价，我们是有意接受的：收件箱 1024、目标又快时，那大约是一次轮询的消息。连线一旦开始溢写，也就是目标宕机、数据有风险的时候，就没有窗口了。下面的 kill -9 测试正是因为这个原因在故障中途、队列在磁盘上时做的。我们没有在连线正常时杀掉运行时去数，因为答案是“会丢几条”，而这就是设计。

**投递是至少一次。** 目标的处理程序无错误返回时，目标就算收下了消息，之后连线在磁盘上把它标记为完成。两者之间发生 `kill -9`，消息就会在重启后再发一次。有多少取决于 `store.durable.ackFlush`：标记是一起写的，所以默认的 `100ms` 下是最近 100 ms 内完成的消息；设为 `0s` 时每个标记都在发送下一条消息之前写入，所以最多是飞行中的那一条，或对接收批量的目标而言飞行中的那一批，最多 256 条。

这听起来像个漏洞，所以下面说明它在这个功能所针对的目标上是怎么被堵上的。穿过持久连线的消息会被打上 `msg._queuedAt`，值是它进入连线的时间，没有配置时间戳的 `influxdb out` 就用这个时间写入数据点。重复写入是同一时间的同一序列，InfluxDB 把它当作覆盖，所以行数不变。这也修复了存储转发中另一个会出错的地方：没有它，故障期间扣下的每个读数都会在 InfluxDB 恢复时才打时间戳，一小时的历史在一分钟内涌入。到达时才打时间戳的接收端，比如 Postgres insert 里的 `now()`，会把一次重复存两遍，还会把重放的那一小时放到错误的位置。请使用 `msg._queuedAt`。

**“已收下”只和节点一样可靠。** `influxdb out` 在处理程序内部完成写入，所以收下就意味着写入完成。把工作交给另一个 goroutine 就返回的节点，承诺得更少，而连线的持久程度不可能超过它所连接的对象。

**有些属性不会随行。** 活动的句柄无法跨过重启，事后也无法回复，所以 `msg.req` 和 `msg.res`（HTTP In 节点的）以及其他无法序列化的内容，会从持久连线上的消息里去掉，并且在一条连线上第一次发生这种情况时，会连同属性名记入日志。负载永远不会被去掉：如果无法保存，消息会被拒绝，并给出指明路径的错误。

**一条坏消息可能卡住一条连线。** 总是让同一条消息失败的目标会一直收到它，每次尝试之间停 5 秒，后面的消息就得等着。重试计数器和深度能让您看到这一点。对宕机的历史数据库来说这是正确的做法，对格式错误的消息来说则是错误的，所以可以给连线设一个上限：在它所出自的节点上设 `"ew_durable_attempts": {"influx": 20}`，或使用编辑器里的连线对话框。目标从队列里拒绝同一条消息达到这么多次之后，它会作为拒绝它的节点所产生的错误连同该消息进入流程，Catch 节点可以把它存放起来，连线继续往前走。没有这个键，一切照旧。仍然没有死信队列：Catch 节点就是您自己搭建它的地方，`hotloop_flow_durable_wire_given_up_total` 会统计去了那里的数量。

## 设置

```yaml
store:
  path: ""              # empty is state.db in data.dir
  synchronous: normal   # normal | full
  context:
    persist: true
    flushInterval: 30s  # 0s writes every change at once
  durable:
    maxBytes: 268435456
    ackFlush: 100ms     # 0s marks each message before the next is sent
```

环境变量：`HOTLOOP_FLOW_STORE_PATH`、`HOTLOOP_FLOW_STORE_SYNCHRONOUS`、`HOTLOOP_FLOW_CONTEXT_PERSIST`、`HOTLOOP_FLOW_CONTEXT_FLUSH_INTERVAL`、`HOTLOOP_FLOW_DURABLE_MAX_BYTES`、`HOTLOOP_FLOW_DURABLE_ACK_FLUSH`。Chart 在 `values.yaml` 的 `store:` 下使用同样的名称。

`synchronous: normal` 让文件以预写模式运行，每次提交不做 fsync。提交能经受进程被杀死，这就是下面的 `kill -9` 测试。它并不能在所有文件系统上经受断电。`full` 可以，而磨损卡的也正是 `full`。

## 实测证明

用 Podman 里真实的 InfluxDB 2.9.1 测得。没有任何模拟。

一个生产者每秒二十次向 flow.json 里的流程发送一个带编号的读数。流程在流程上下文中计数，并通过一条持久连线把它发给 `influxdb out`。读数不带时间戳，所以被投递两次的消息就会变成两行。流程与 InfluxDB 之间有一个小的直通环节，记录 InfluxDB 接受的每一次写入，因为 InfluxDB 把同一时间写两次的点视为一个点，仅靠行数无法显示重复。

| 时间 | 发生了什么 |
|---|---|
| 00:13:53 | 流程启动，每秒 20 个读数。 |
| 00:14:53 | 对 InfluxDB 执行 `podman kill`。它停了十分钟。连线溢写到磁盘。 |
| 00:19:54 | 五分钟后，磁盘上的队列深度 5,989。对运行时执行 `kill -9`。 |
| 00:19:59 | 运行时再次启动，InfluxDB 仍然停着。它在磁盘上找到 5,992 条消息，并继续接收新的消息。 |
| 00:24:59 | InfluxDB 启动。队列深度 11,989。 |
| 00:25:25 | 正在排空，队列深度 5,987。在队列中途对运行时再次执行 `kill -9`。 |
| 00:25:30 | 运行时再次启动，磁盘上有 5,948 条。 |
| 00:25:53 | 积压排空。再持续九十秒的稳定输入，然后统计。 |

```
deliveries      15987 writes InfluxDB answered 204 to
delivered twice 5 [7829, 7830, 7831, 7832, 7833]
sent            16185
accepted (200)  15982
failed          203
rows stored     15982
distinct seqs   15982
missing         0 []
doubled         0 []
unacked stored  0 []
```

流程回复过 200 的每一个读数都在 InfluxDB 里，各一次。**没有缺失，没有重复。**失败的 203 个是运行时停着期间到达的请求，也就是生产者被告知不行，其中没有一个被存储。

有五条消息被交给 InfluxDB 两次。它们是第二次 kill 恰好撞在 InfluxDB 收下与“完成”标记写到磁盘之间的那些，位于 `ackFlush` 窗口之内。每一条都带着相同的 `_queuedAt`，所以第二次写入覆盖了第一次，行数没有动。[至少一次](#它承诺什么不承诺什么)在正常工作时就是这个样子。这也是到达时才打时间戳的接收端会存两遍的内容。

这没有涵盖的是：连线正常时的 `kill -9`。那一刻内存里的读数会丢失，这是设计使然，我们没有去数。

## 它向磁盘写了什么

`/proc/<pid>/io` 里的 `write_bytes` 是内核为该进程被要求送往存储的量，已扣除被取消的写入。这是闪存卡关心的数字。每一行是一个场景的 300 秒，在 30 秒稳定期之后，由 disk-writes.sh 测得。流程是后面带着 InfluxDB 的实测证明流程，所以负载是真实的。

```bash
BIN=./hotloop-flow SECS=300 bash docs/durable/disk-writes.sh
```

| 场景 | 速率 | 上下文刷新 | 每小时写入 | 每天 |
|---|---|---|---|---|
| 空闲，流程中有一条持久连线 | 无 | 5 s | 0 字节 | 0 |
| 健康的持久连线，稳定负载 | 20 msg/s | 30 s | 1.7 MiB | 0.04 GB |
| 健康的持久连线，稳定负载 | 50 msg/s | 30 s | 1.2 MiB | 0.03 GB |
| 同上，上下文每 5 s 刷新 | 20 msg/s | 5 s | 5.1 MiB | 0.12 GB |
| 同上，上下文每 5 s 刷新 | 50 msg/s | 5 s | 4.2 MiB | 0.10 GB |
| 仅上下文，普通连线 | 20 msg/s | 30 s | 1.2 MiB | 0.03 GB |
| 连线正在溢写，InfluxDB 停机 | 20 msg/s | 5 s | 728 MiB | 17 GB |
| 连线正在溢写，`synchronous: full` | 20 msg/s | 5 s | 1,011 MiB | 24 GB |

分三部分来读。

**空闲不写任何东西。**五分钟内零字节。

**健康的连线自己不写任何东西。**健康的几行是持久上下文，也就是每条消息都加一的计数器，没有别的。普通连线、仅上下文的那一行与它们相差在噪声之内。在做这张表之前，上下文刷新默认是五秒：每秒二十条消息时是每小时 5.1 MiB、每天 0.12 GB，改成三十秒降到 1.7 MiB，这就是默认值定为三十的原因。此时 kill -9 最多丢失三十秒的上下文。

**溢写的连线代价高，而且只在溢写期间。**每条消息是各自的提交，每条大约写 10 KB，因为发送方在等磁盘。每秒二十条、停机十分钟约 120 MiB，停机一整天约 17 GB。这是“发送方继续之前先落盘”的代价，只在历史数据库宕机期间支付。组提交会让并发的发送方共用一次事务，但只有一个发送方就只有一次提交。

再说一个数字，因为它让我意外。每秒 100 条消息时，这套测试环境没能让连线保持健康：目标跟不上，连线溢写，并在整个运行期间一直溢写，每小时 3,548 MiB。我们没有去查慢的是直通环节还是 InfluxDB。这是设计按所写的方式工作，因为“积压”也算跟不上，这意味着比输入更慢的目标会让持久连线落到磁盘上。每秒 50 条时它保持健康。

在此之前的设计是先把每条消息写到磁盘。在第一版结构上（4 KiB 页、一张表和一个索引），即使 InfluxDB 健康，每秒 20 条消息时也测得每小时 632 MiB，每个“完成”标记立即写入时是 1,163 MiB。“只在故障期间用磁盘”就是这么来的。

### 在裸机上

这些数字是在 WSL2 下的一台 x86 机器上测得的，此后持久存储也在裸机上运行过（2026-11-17）。写入的字节数取决于代码和页大小，所以上面的数字依然适用。卡拿这些数据会怎样（写放大、磨损）则不适用，内存、启动时间和持续的每秒消息数也不适用，所以这些数字仍然标明是在哪里测得的。
