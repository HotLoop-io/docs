这就是整个项目。边缘盒子上的流程引擎，典型的故障是一个 Pod 悄悄膨胀，直到被 kubelet 杀掉，而它留下的日志对拿着呼机的人没有任何解释。所以每一个可能积压消息或字节的地方都有上限，每个上限都是写下来并记录在 [Node-RED 兼容性](/zh-hans/flow/compatibility/)里的决定，而不是我们定了却从不提起的限制。

| 可能积压的东西 | 由什么阻止 |
|---|---|
| 节点的收件箱 | 一个上限（默认 1024）和四种溢出策略之一 |
| 延迟和限速队列 | 一个上限；超过后被拒绝并交给 Catch 节点 |
| Trigger 定时器 | 一个上限 |
| `exec` 输出 | 按流设上限；截断会产生错误 |
| `exec` 进程 | 并发上限；超过后被拒绝 |
| 文件读取 | 有上限，提供逐行和分块模式 |
| HTTP 请求体 | 有上限 |
| 等待 HTTP 响应 | 超时后返回 504 |
| TCP 连接和帧 | 有界 |
| WebSocket 发送队列 | 有界；慢客户端会被断开 |

溢出策略，全局设置，也可以按节点覆盖：

| 策略 | 会发生什么 |
|---|---|
| `block` | 发送方等待空位，最长 `blockTimeout`。反压向上游传递，这几乎总是正确的答案。 |
| `drop-newest` | 丢弃到达的消息。会计数并通知。 |
| `drop-oldest` | 队首被挤出以腾出空间。会计数并通知。适用于“只有最新读数才重要”。 |
| `error` | 发送被拒绝并抛给 Catch 节点，由流程来决定。 |

没有任何东西会被悄悄丢掉。每一次丢弃都会被计数，作为事件推送到编辑器，并导出为可以设置告警的指标。限制起作用时，你从图表里得知，而不是从操作员那里。

## 每个节点一个 goroutine

每个节点实例都有自己的 goroutine 和自己的收件箱。节点内部有序，节点之间并行。一个做实际工作的 Function 节点占用一个核心，而编辑器、API、websocket 和其他所有流程继续运行。

## 每个接收者都有自己的副本

当一根连线分叉时，另一端的每个节点都会收到消息的独立副本，所以两条都以为自己拥有这条消息的分支不会互相破坏，一条分支也不会因为你连线的先后顺序而和外观相同的兄弟分支表现不同。那是一个只在周二才复现的 bug，在这里不存在。

这不是免费的。复制一条小消息（一个读数和一个主题）需要 411 到 453 ns 和 680 字节，五个节点的链路每 1.14 到 1.40 µs 传递一条消息，包含复制。复制最痛的地方是大的二进制负载：一个 1 MiB 的缓冲区，每个接收者要花 128 到 156 µs，并多占 1 MB 堆内存。所以大的二进制负载以 `ImmutableBytes` 传输，它共享缓冲区而不是复制：**同样的 1 MiB 消息只要 250 到 279 ns 和 360 字节。** 文件节点和 HTTP 节点已经用这种方式交出二进制负载，所以你不用要求就能得到。

## 会计数的上下文

流程上下文和全局上下文有 `get` 和 `set`，也有 `CompareAndSwap`、`Increment` 和 `Update`。两条分支对同一个计数器做 get-modify-set 会互相竞争并丢失更新，只用 get 和 set 对此无能为力。用 `Increment` 就没有什么可竞争的。

而且它能在重启后保留。流程、全局和节点上下文存放在卷上的一个 SQLite 文件里，在某个作用域第一次使用时加载，并延迟写入，所以 Pod 回来时，流程里的计数器或锁存器还在你离开时的位置。原子操作还是原来的同一套代码。变更每三十秒合并成一次写入，设置成原有值的操作什么都不写，因为我们更在意它对 SD 卡的影响，而不是显得聪明。正常停止会写入全部内容；`kill -9` 最多丢失那三十秒，`store.context.flushInterval` 就是调节旋钮。细节，以及对存储卡的代价，见 [docs/durable](/zh-hans/flow/durable-state/)。
