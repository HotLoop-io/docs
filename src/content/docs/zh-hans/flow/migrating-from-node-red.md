title: "带上你的 Node-RED 流程"
description: "原样导入 Node-RED 的 flows.json，逐个节点查看对应关系，以及 Flow 拒绝运行什么、为什么拒绝。"
---

Flow 读取 Node-RED `flows.json` 的 v1 格式，也就是每一次 Node-RED 导出和流程库中每一条记录所用的扁平 JSON 数组。指向你的文件，它就能运行。

**按字节原样加载和保存。** 加载一个文件，不做任何编辑就保存，得到的字节完全相同：键的顺序相同，空格相同，没有被擅自改写的转义。只改一个属性，差异就是一行，而不是整个节点。

这在 Go 里比听起来难。JavaScript 对象会保留键的插入顺序，所以 JavaScript 运行时通过 `JSON.parse` 和 `JSON.stringify` 就能白得这一点，没人需要考虑。Go 的 map 完全没有顺序，`encoding/json` 还会有意对键排序。我们没有把保持顺序的 map 强行塞进代码里的每一条读取路径，而是保留每个条目的原始字节：解析后的形式没有变化时原样输出，变化时再按原来的键顺序重新编码。`json.Compact` 和 `json.Indent` 是字节级的转换，所以它们只重新缩进，不重排任何内容。

这很重要，原因有两个，都不起眼，也都是真的。你的流程文件放在卷上，也放在 git 里，不应该仅仅因为一个 Pod 重启就发生变化。而且当操作员在把部署推到产线之前审阅差异时，应该只看到改动了什么，绝对不多不少。即使测试和类型进入文件，这条规则也不变：新数据放在其他工具会忽略的键里，往返测试也覆盖带有这些键的文件。

这个版本从未见过的节点类型，在加载和保存之后所有属性都完好无损，所以可以放心地在这里运行流程，之后再交还。Node-RED 的 `flows_cred.json` 使用 AES-256-CTR，以只读方式导入，这样读入的内容会在下一次保存时用 GCM 重新加密。

**部署任何东西之前，先问问会发生什么：**

```bash
hotloop-flow import flows.json
```

它会报告文件中的每一种节点类型，包括子流程内部的节点，分为支持、部分支持（并写明缺少什么）和不支持。子流程的内部按展开后的图而不是按文件来计数，所以一个实例不会在对内部内容保持沉默的同时被报告为“支持”。这就是在办公桌前发现问题和在产线停机时才发现问题的区别。

节点还可能指向文件中不存在的配置节点。删除一个流程，它自己的 MQTT 代理也随之消失，而用过该代理的子流程仍指向一个什么都不指代的 id。手工编辑或只复制了一半的导出也会造成同样的情况。以前我们要等第一条消息到达该节点才发现，而只是查找服务器的节点当时什么也不说。现在导入报告里有专门的一节，列出每个节点和它找不到的 id；编辑器在加载时把同样的行写进日志；部署会带着这些内容作出响应，并把这些节点标记为启动失败，同时指出包含错误 id 的属性。流程的其余部分继续运行。你停用的节点，以及留空或为 `true`、`false` 的 TLS 设置，不会被报告，因为这些不是错误。

存在的 id 不等于可用的 id。第一次我们漏掉了这一点。如果设置指向的是标签页、子流程、分组或普通节点，或者指向类型不对的配置节点，比如指向 MQTT 代理的 TLS 设置，它会得到同样的报告和同样的启动失败，这一行会说明该 id 实际是什么，以及设置需要哪种类型。编辑器只提供正确的类型，所以这只会来自手工编辑或粘贴的 id，而那正是最容易出问题的地方。

按兼容级别划分，108 种消息节点类型中，完全兼容 12 种，部分兼容 50 种，有意不同的 14 种，Flow 自有的 32 种。每个节点都声明它与 Node-RED 同名节点的关系，**如果某个节点声称部分兼容却没有书面说明缺少什么，测试就会让构建失败。** 一个 90% 兼容却对其余 10% 沉默的节点，比明显缺失的节点更危险，因为前者会让流程看起来能用。完整的矩阵是 [Node-RED 兼容性](/zh-hans/flow/compatibility/)，由注册表生成而不是手工维护，因为手工维护的兼容性文档就是带时间戳的谎言。

这些差异都是有意的，每一项都写在那里：分叉上的每个接收者都得到自己的副本，`exec` 节点有允许列表而没有 shell，文件节点有范围限制，[反压，一目了然](/zh-hans/flow/back-pressure/)中列出的一切都有上限。

**大多数 Node-RED 社区节点在这里无法运行。** 它们是需要 Node.js 的 npm 包，而且不会有哪个未来版本能让需要 Node 的包突然运行起来。这是为了小体积和沙箱所付出的代价，明说出来是为了让你可以据此决定取舍。对于你自己编写的部分，签名的 WASM 插件是 Flow 的答案：参见[无需 npm 的插件](/zh-hans/flow/plugins/)。

工厂所依赖的社区节点则是另一回事。Flow 用 Go 原生运行 Node-RED 的 Modbus、仪表板、PostgreSQL 和电子邮件类型，使用它们自己的类型名，所以使用这些节点的流程无需修改即可加载和运行，周围函数节点所调用的 `Buffer` 和 `setInterval` 也一样。哪些能运行、哪些有差异、哪些已被验证，见 docs/node-red-types.md。流程中任何其他社区节点都会单独失败并标明其类型，流程的其余部分照常启动。

JSONata 曾经排在导入流程会出问题的清单之首。不能用的 13 项都在测试中固定下来并附有各自的原因，其中十项仍会报错，只是错误代码不同。`$moment` 是你唯一会怀念的 Node-RED 函数，它会告诉你该用什么来替代，而不是悄悄失败。

按 cron 调度的 Inject 节点是清单上的下一项。它们现在会触发，而且和 Node-RED 在同一分钟触发：crontab 由 cronosjs 1.7.1 的移植版读取，这是 Node-RED 自己的 Inject 节点内部的调度器，并对照了 cronosjs 自身在六个时区、真实时钟变更前后产生的 22,620 次触发。凌晨 2 点这很重要。落在春季消失的那一小时里的班次开始，会在时钟跳变的那一刻运行；秋季重复的那一小时只运行一次，而不是两次。调度还会每分钟重新读取墙上时钟，所以一个以错误时间启动、之后由 NTP 校正的设备，会在正确的时间开始触发，而不是晚上好几个小时。

Link Call 是三项中的最后一项。它现在可以使用了，连同 Link Out 的返回模式：一段逻辑，比如“查询这个批次”“检查这个联锁”，在自己的标签页写一次，从每条产线调用，返回路径作为栈保存在消息上，所以被调用的流程也可以发起自己的调用。一个永远不返回的调用会在超时后产生错误，而不是挂起。迟到的返回仍会发出，和 Node-RED 一样。而没有可返回之处的返回，是 Catch 节点能看到的错误，而不是 Node-RED 记录下来却没人看的警告。
