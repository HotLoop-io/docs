“改了什么，谁改的，把它改回去”，这是产线停下之后每个人最先问的话。三个 `.bak` 文件一个也回答不了。它们不知道是谁，保存三次后就被覆盖，而您需要的永远是第四个。

所以每次部署都会在 `data/deployments/` 下写一条不可变的记录：谁部署的（来自他的令牌，绝不来自客户端自称的内容）、从哪里、何时、留下的备注、被替换的修订、逐字节的流程文件，以及部署后的凭据原样，加密方式与凭据文件完全相同。记录只追加。日志默认保留最近 100 条（`history.retain`，0 表示全部保留），并且从不裁剪最新的一条，因为最新的一条就是正在运行的那一条。

```bash
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:1880/deployments
curl -s -H "Authorization: Bearer $TOKEN" http://localhost:1880/deployments/42/flows > flows-42.json
```

备注随部署一起提交，写在封装文档的 `"note"` 中（`{"rev": ..., "flows": [...], "note": "..."}`），或写在 `HotLoop-Flow-Deployment-Note` 请求头里。之所以有文档形式，是因为浏览器不会把 Latin-1 之外的内容放进请求头，而人们是用自己的语言写备注的。

它做了两件事，您要等吃过亏才会发现少不了：

- **手工修改会被发现。** 如果磁盘上的流程文件不是日志最后记录的内容，因为有人在进程停止期间编辑了它，启动时会把它记为一条 `baseline` 条目，并如实说明。第一次启动时已有流程文件的情况也一样。否则，手工修改就会悄悄变成一段没人记录的过去。
- **写不进的日志不会让产线停下。** 到那时流程文件已经保存了，所以拒绝部署会让磁盘和运行中的流程不一致，直到下次重启。部署照常进行，响应和日志都会用文字说明这一次没有记录。

API 从不交出记录中的凭据，无论是否加密。保留它们只为一件事，把它们放回去，而历史端点不是把它们带走的途径。

## 对比读起来像一次评审

对流程文件做逐行对比，诚实但没用。把一个节点拖动二十像素，是一处改动。改一个阈值，也是一处改动。评审的人分辨不出哪一个会让压力机停下来。所以 Flow 逐节点对比：

```
1 changed, 2 moved

Tab "Line 3" (t1)
  ~ switch "Pressure check" (sw1)
      rules[1].v: "7.5" -> "8.0"
      wire added: port 1 -> change "set alarm" (alarm1)

Moved on the canvas only
  mqtt in "press 01" (in1)
  debug "ok" (ok1)
```

新增、移除和修改，逐属性给出旧值和新值，哪些连线按输出端口发生了移动，并且**布局与逻辑分开**：移动、调整大小或隐藏标签属于“在画布上移动”，绝不算改动，所以整理看起来就是整理。凭据显示为“已设置”或“已更改”，绝不带值。子流程内部的编辑显示在子流程上，拖动它的某个端口也属于布局。

各处答案一致，来自引擎中的同一个包：

- `GET /deployments/{from}/diff/{to}` 对比两次部署。
- `POST /flows/diff` 把正在运行的内容与一份尚未有人部署的文档对比，也就是按下部署之前要看的东西。
- 命令行里的 `hotloop-flow diff old.json new.json`。给程序用的是 `-json`。有差异时像 `diff` 一样以 1 退出。
- **在 git 里。** 把它设为流程文件的 git diff 驱动，`git diff`、`git log -p` 和 `git show` 就会打印语义对比，而不是一大段 JSON：

  ```bash
  git config diff.hotloop-flow.command 'hotloop-flow diff'
  echo 'flows.json diff=hotloop-flow' >> .gitattributes
  ```

  或者作为 difftool：`git config difftool.hotloop-flow.cmd 'hotloop-flow diff "$LOCAL" "$REMOTE"'`，然后 `git difftool -t hotloop-flow`。

一个流程与自身对比，对解析器接受的任何文档来说，都没有任何改动。

## 把它改回去

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" \
  -H "HotLoop-Flow-Deployment-Rev: $CURRENT_REV" \
  -d '{"note":"42 broke the label printer"}' \
  http://localhost:1880/deployments/41/rollback
```

回滚会把旧记录**作为一条新记录**重新部署。历史仍然只追加：部署 41 不会被触碰，回滚是它自己的条目，写明“回滚到部署 41”、是谁做的、为什么。流程文件逐字节恢复，所以它就是当时的同一个修订。

**凭据也会一起回来。**每条记录都带着当时的凭据，所以您删掉的节点会连同它的 broker 密码一起回来，而不是回来了却登录失败。这已对一个拒绝匿名客户端的真实 Mosquitto 做过测试：删掉订阅者，部署，回滚，它会重新登录，消息继续流动。

在写入任何内容之前，它会以三种方式拒绝。过期的 `HotLoop-Flow-Deployment-Rev` 得到与部署相同的 409，因为与他人部署赛跑的回滚仍然是一场竞争。已被保留策略清除的部署是 404。而凭据无法用当前凭据密钥解密的记录是 422，因为无法登录任何地方的流程，只是看起来成功了的回滚。

## 在编辑器里

**Deploy 并不部署。**它会打开一次评审：引擎对运行中内容的对比，画在画布上并用文字列出，还有一个填写备注的框。绿色是新增，琥珀色是修改，蓝色只是移动，红色幽灵出现在被移除的节点和连线原来的位置。有改动的标签页会带一个圆点。第二个 Deploy 按钮才是真正部署的那个，备注会写入日志。评审打开时编辑任何内容，评审就会关闭，因为对您此后已改过的东西做的评审，是在对您即将推送的内容撒谎。

**历史面板**列出每次部署的操作人、时间和备注。*Changes* 在只读画布上打开那次部署，把它改动的内容画在上面，覆盖在您的工作副本之上，而工作副本保持您离开时的样子。*Roll back* 会询问原因，在您即将丢弃未保存的编辑时发出警告，然后部署它。

**部署冲突会显示对方做了什么。**以前它是浏览器的 `confirm()`，让您覆盖对方的或丢掉自己的，却不说对方的是什么。现在它会说明是谁部署的、何时、他的备注，以及他逐节点的改动，然后让您加载他的、用您的覆盖，或继续编辑。

**复制、剪切和粘贴的表现和您预期的一样，并且使用流程文件的格式。**选中节点，按 Ctrl+C，剪贴板里就是其他所有流程工具都能读的同一种 JSON，所以您可以把它粘贴到聊天、工单或另一台机器上。粘贴会把它放在指针所在的位置，每次都用新的 id，所以粘贴两次得到两份副本，绝不会冲突。通向您没有复制的内容的连线会被切断，而不是指向空处，节点用到的配置节点会一起带上。如果粘贴目标的流程里已经有那个配置节点，副本就共用它，而不是向一个会计数的对象再开第二个连接。凭据绝不会放进剪贴板。粘贴缓冲区里的密码，正是它最终出现在错误报告里的原因。

**Import 和 Export** 对选区、一个流程或全部内容做同样的事，有一个可复制的框、一个 Download 按钮，导入时还有文件选择器。垃圾内容会得到一个原因（“id a 出现了两次”“第 1 条没有 id”），对话框保持打开。此运行时没有的节点类型会以灰色虚线形式进来，导入会告诉您是哪些，因为悄悄丢掉的节点比吵闹的节点更糟。

屏幕是那个文件的一部分。流程所绘制的仪表盘（`ui_tab`、`ui_group` 和各个控件）就是流程中的节点，所以客户的屏幕会随流程一起通过 Export 和 Import 迁移，而它们都不存放在 HotLoop Flow 自身里。

**子流程在它自己的画布上编辑。**按 *+ subflow*，它会带着输入和输出端口打开。像连接其他东西一样把它们连到里面的节点。*Subflow properties* 设置名称、颜色、输出的数量，以及实例可以设置的属性。形状改变时，各流程中的实例会跟着变化，调色板列出每个子流程，您可以拖一个出来。双击实例，可以给它起自己的名字，并为每个属性设自己的值。子流程不能放进它自己里面，也不能放进包含它的子流程里，仍在使用的子流程不能删除。编辑器会直接说出来，而不是让下一次部署去发现。

**把选区变成子流程。**选中节点，按 *Selection to subflow*。它们会移入自己的子流程，原处由一个实例取代。每条穿过选区边缘的连线都会变成一个端口：唯一的入口是子流程的输入，选中节点中每个原本通向别处的输出都是子流程的一个输出，所以流程的行为和原来一样。子流程只有一个输入，所以如果选区连到两个不同的节点，它会说明并且不改动任何东西，因为把两个都从两处供给，就成了另一个流程。选中一个分组，它会连同里面的一切一起走。属于该流程且只被选区使用的配置节点，会连同它所指向的东西一起进入子流程。被留下的东西也在使用的配置节点则改为全局，让两端继续共用同一个连接，因为在会对连接计数的机器上多出第二个 broker 连接，正是我们不会发布的那种意外。被移动的节点读取、且流程已声明的环境变量（类型为 env，或字符串中的 `${NAME}` 或 `$(NAME)`，或 `env.get`）会变成子流程的属性并转发给流程，所以值仍然来自原来的地方，实例也可以覆盖它。Ctrl+Z 会撤销全部。

**流程。**双击标签页，或按 *Flow properties*，可以重命名或删除它。删除会先询问，带走流程上的每个节点，并切断其他流程通向它的连线和链接，让文件不会指向空处。它还会把已删除的节点从点名过它们的所有 Catch、Status 或 Complete 范围中移除。整个列表都被删掉的 Catch 或 Status 会保留最后一个 id，因为空列表意味着整个流程，我们不会在您背后把节点从监视一件事变成监视一切。Ctrl+Z 在您部署之前都能把它找回来。最后一个流程不能删除，因为没有流程的运行时没有地方放节点。

**配置节点**在调色板的 *configuration* 之下。它们不在任何画布上，所以双击类型，填写对话框，它就会加入 *configuration in use* 下的列表，在那里双击可以编辑，叉号可以删除。仍被节点使用的不会被删除，并会说明有多少个在用。节点对话框里的“Add one from the palette first”指引您去的就是这里。

**删除连线。**按住 Alt 点击。普通点击什么也不会发生，所以选择时蹭过连线不会弄坏流程。Ctrl+Z 把它放回来。

**持久连线。**双击一条连线。勾选 *Durable*，它会画得更粗、呈蓝色，它所出自的节点在文件中会得到 `ew_durable`。标记在这对节点上，所以对它们之间的每条连线都有效。这是面向运行时的接线，所以标记一条连线绝不会重启节点。

**分组。**Ctrl+G 包住选区，Ctrl+Shift+G 把它拆开。双击标题栏为它命名并上色。拖动分组，里面的一切都跟着走。把节点拖进分组，它就加入；拖出来，它就离开。分组可以嵌套。删除分组会删掉里面的内容，Ctrl+Z 会全部放回来。

**搜索**（Ctrl+F，或按钮）同时查看所有流程和子流程：名称、类型、id 和每一项设置，包括函数体中间的某一行。命中项会带您到正确的标签页，节点被选中并位于视图中央。配置节点也会出现，它们的命中项会打开其对话框，因为它们在画布上没有位置。

**调试过滤。**把侧栏收窄到一个流程、您选中的节点、一个词，或只看错误。它适用于日志里已有的内容，而不只是接下来到达的内容，所以收窄从不会让您正在看的那一行消失。

以上所有内容，在每个 pull request 上都会在真实浏览器中针对内嵌编辑器的真实二进制逐一点击验证。这包括运行时提供的每一个节点对话框：列表来自 `GET /nodes`，所以下个月新增的节点下个月就在测试里，不需要任何人记得去添加。在写这些测试时，我们发现了两件在 Chromium 里从未生效过的事：双击节点打开它的对话框，以及把连线拖到节点上。画布在整个拖动过程中一直占着指针，所以事件的目标始终是画布，在节点上松开的连线从来找不到那个节点。两者都尴尬得不能再尴尬，在可视化编辑器里这样的 bug 再没有比这更糟的了。两个都已修复。

## 流程即代码

流程是在仓库里评审的，所以仓库也应该能部署它们。把流程文件放在 git 里，设置上面的 diff 驱动，让 pull request 读起来像一次评审，再让合并去部署它：

```bash
hotloop-flow export -o flows.json          # the live file, byte for byte, to commit
hotloop-flow deploy -file flows.json -note "PR #12: line 3 pressure check"
```

`deploy` 打印与运行中内容的对比，文字与其他各处相同，然后针对生成这份对比时所依据的修订进行部署。如果中间有人部署了，结果是 409 和一条红色的流水线，而不是悄悄覆盖。`-expect-rev` 把它固定到经过评审的方案所依据的修订上，`-dry-run` 打印对比但不部署任何东西。没有任何改动的文件不会部署任何东西，也不会往历史里添加任何东西，所以没动过流程的合并不会弄乱日志。启动失败的节点仍会部署，并且仍会让任务失败，因为流程的其余部分在运行，需要有人去看一眼。`export -deployment 41` 能从历史中取出任何一次部署。

**流水线从不持有管理员密码。**它拿到的是一个 API 令牌：

```bash
hotloop-flow token -name ci
```

打印一个令牌，只打印一次，交给流水线的密钥存储，并打印要交给运行时的哈希：部署令牌用 `HOTLOOP_FLOW_DEPLOY_TOKEN_HASH`，其他任何令牌用配置文件里的 `auth.tokens`。运行时和对待密码一样，只持有哈希。部署令牌可以读取流程并部署，包括回滚，仅此而已：不能改设置，不能 inject，不能用编辑器。两个命令都从 `HOTLOOP_FLOW_TOKEN`（或 `-token-file`）读取令牌，从 `HOTLOOP_FLOW_URL`（或 `-url`）读取实例，绝不把令牌放在命令行上，否则它会出现在进程列表和每一份回显命令的 pipeline 日志里。历史把令牌显示为部署者 `token:ci`，并附上流水线传入的备注。

凭据绝不会以这种方式传递。它们不在流程文件里，所以从 git 部署会让每个 broker 密码保持在原处。

## 如果您想要，可以用 git 镜像

部署日志保存在这台机器上。仓库是其他所有人已经在看的地方：它有网页视图、blame、备份，以及会读它的人。把 Flow 指向一个仓库，每次部署就会成为流程文件在一个只有 Flow 写入的分支上的一次提交，**作者是部署它的人**，时间是他部署的时间，备注就是提交信息：

```yaml
history:
  git:
    url: https://git.plant.example/line3/flows.git
    branch: main              # one nobody else pushes to
    path: flows.json
    emailDomain: plant.example  # dana deploys, the commit is from dana@plant.example
```

密码是 git 服务器的访问令牌，通过 Secret 放进 `HOTLOOP_FLOW_GIT_PASSWORD`，绝不放进文件（`HOTLOOP_FLOW_GIT_URL` 和 `HOTLOOP_FLOW_GIT_USERNAME` 也可用）。带有密码的 URL 在启动时会被拒绝，所以 URL 始终可以记入日志。仅支持 `http://` 和 `https://`：镜像里没有用于 `file://` 的 git 二进制，也没有用于 `ssh://` 的密钥，而每次推送都失败的镜像比拒绝启动的镜像更糟。回滚和启动基线会在提交中说明自己是什么，并且每次提交都带有 `Flow-Deployment: N` 尾注，重启后的进程，或克隆被清除的进程，就靠它从仓库所说的位置准确接着往下走，不会重复。

**它从不拖住部署。**推送在它自己的 goroutine 里进行。git 服务器宕机、缓慢或拒绝推送，对部署没有任何代价：提交在 `data/git-mirror` 下的本地克隆里等着，在下一次成功的推送时发出，每分钟重试一次。`GET /deployments` 会说明镜像进行到了哪里和最近一次错误，`hotloop_flow_git_mirror_behind_deployments` 是要为其设置告警的数字。已针对 git 自带的 smart-HTTP 服务器在基本认证之后做过测试：三次部署生成三个作者的三次提交，被服务器拒绝的推送会等待，并在服务器不再拒绝时追上，而在需要十秒才回绝的 git 服务器面前，部署仍在几毫秒内返回。

它是纯 Go（go-git），所以二进制仍是静态的。它大约增加 3.8 MB 的二进制体积，所以是测出来的，不是假设的。在加入这些目录之前，二进制是 48,083,106 字节。
